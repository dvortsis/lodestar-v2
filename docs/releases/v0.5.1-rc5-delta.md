## What changed in the notice
- The heading says which release the notice applies to (v0.5.1), separately from the notice's own version.
- Section 2: the peer table's entry expires 30 minutes after its most recent refresh (`crates/dht/src/node/peers.rs` `TTL`, refreshed on re-announce), not "within half an hour".
- Section 5: the data-folder sentence excepts the structured log folder (`settings.logging.file_folder`, default `<data>/logs`; on this release it is set only through the settings API, since the field has no `config.toml` path) and the Windows service's start and logging failures, which go to `%SystemRoot%\Temp\lodestar-service.log` with paths and account names only (`windows/service.rs`, `logging/file.rs`, `windows/temp_log.rs`). It says where the console output is kept (Docker's container log, the systemd journal). Not named: the Windows Event Log, because `event_log_errors` is a settings field no code reads on this branch and no Event Log writer exists; and a restart record, which this release doesn't have.
- Section 8: the publisher's reading of AGPL §16 is removed; the summary of §16 and "the licence text controls" stay.
- Section 9: the owner's wording. Content reports never go to the maintainers; removal requests to the operator; child sexual exploitation to the CyberTipline or the appropriate authority; other crimes to law enforcement; no files, screenshots, magnet links, hashes or identifying descriptions; synthetic examples in bug and security reports; no override of independent legal duties.
- Section 10: "a new version of this notice", since "this version" now names the software.

## What tests it
`cargo test -p lodestar-api` on this branch: `legal::` (the version line matches `NOTICE_VERSION`, the built-in copy is the published file, the text uses only what the in-app renderer handles) and `tests/legal.rs` (the gate, setup and acceptance against the constant, so the raised number is exercised, not assumed).

## NOTICE_VERSION
**Raised to 3 (runner, 2026-11-06, §2.33; flagged to the owner under §2.19).** The reasoning both ways, as put to the runner: X-legal-docs' rule says only that a substantive change raises the version and an editorial one doesn't. The case for 2: the behaviour is unchanged, the peer-table and §8 edits are editorial, and no released install has accepted version 2 (v0.5.1 isn't tagged; rc.4 users are testers). The case for 3: anyone who accepted version 2 on rc.4 was told that everything stays in the data folder (§5) and read an older section 9; the corrected §5 discloses two places outside the data folder, and §9 now asks the user not to send hashes, magnet links, screenshots or descriptions to the maintainers and to use synthetic examples in bug reports, which bears on what the user is asked to do. The runner ruled the change substantive on the second case. An rc.4 install, which stored 2, sees the corrected notice once at its next sign-in and stores 3; a fresh v0.5.1 install accepts 3 at setup. `main`'s notice goes to 4 in a follow-up PR there, so `main` stays above every number a build has shown.
