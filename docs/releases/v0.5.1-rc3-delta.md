## What it changes, so r3's soak evidence doesn't carry over
**#402 changes the crawler's lifecycle: how leases on harvested keys end.** Under the delta rule (`docs/build-plan.md` §0.4), r3's soak on rc.2 doesn't carry over to rc.3. r3 also failed the memory gate (1.88 MiB/h, 95 % CI [1.43, 2.33]; `docs/decisions/2026-11-03-soak-r3-verdict.md`, on `main`). #406 fixes the cause of that private-memory growth, which the M1-exp experiment confirmed: the search index's mmap caches kept an entry for every file a commit or merge replaced.

rc.3 needs:
- **A fresh frozen soak, r4** (Track R step R1′). It runs on the Linux main leg with the frozen rc.3 image: the 6-hour sampling wait, a 30-minute warm-up, then a 24-hour baseline. It passes when the upper 95 % CI of the `anon` private-memory slope over hours 12–24 is ≤ 2.0 MiB/h, with gate evidence yes.
- **The gluetun leg** (R2) on rc.3.
- **The short Windows MSI service smoke** (R-win): at least 1 hour, covering start, stop and a clean restart, with a non-zero stored rate. #402 and #406 are platform-independent, so a full Windows re-soak isn't needed.

What still carries over: rc.3 changes no store schema, no migration and no outbound endpoint policy. r1's clean upgrade still counts (§2.28). #357 changes only filter loading and its reporting, and with every stored row readable, which is true on a fresh data directory, the filter's hot path is unchanged.

## The stand-in gap
rc.3 holds what an unreadable rule's stand-in matches: quarantines, and adult holds and Adult labels from an unreadable Is adult classification rule. **Nothing in rc.3 undoes those holds automatically** when the row becomes readable again (for example, after upgrading to a version that reads it). rc.3 also **doesn't write the `filter.stand_ins` record** that a later version needs to find them. F-filter-standin-undo (#367, on `main`) does both. It isn't in rc.3, because §2.31 limits rc.3 to rc.2 + #357 + #402 + #406's fix.

**What is lost if nobody acts:** adult holds made meanwhile by an unreadable Is adult rule show as `adult_hold` in the review queue and **become tombstones when their quarantine period ends** (§20.3) unless they're released by hand. A stand-in's quarantines expire the same way. In v0.5.1 that period is a fixed 30 days (`PipelineConfig::quarantine`, used at `crates/pipeline/src/writer.rs:341`); the 0–30-day retention setting (§20.11, `filter_hits`) only governs the filter-hit log, not when holds are purged.

What still works in rc.3: editing or removing the row in Filters & Safety **while rc.3 still can't read it** repairs it. Fixing a rule releases its stand-in's quarantine, and removing an unreadable Is adult rule re-queues every torrent for classification. Once a later version reads the row again, that repair is only partial: removing the now-readable rule re-queues only what its real query matches, so torrents that only the stand-in marked Adult keep the label until they're next re-enriched. Until #367 ships, release anything the rule held from the review queue by hand. The gap only ever over-holds; it never loosens filtering.
