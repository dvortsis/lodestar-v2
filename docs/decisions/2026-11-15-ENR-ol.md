# ENR-ol decisions (Open Library parser and plugin)

Slice ENR-ol (`runner/slices.yaml`; no brief). Spec: architecture §18.2 (enrichment plugin 9) and §18.7, plan `docs/plan/2026-11-05-v07-m7.md` (ENR-ol row, the caps line "OpenLibrary ≤ 1/s", Q4, Q5 and Q12). Built on Wikidata's pattern and its "How to add the next plugin" (`docs/decisions/2026-11-12-ENR-14.md`); only what differs is written here.

## Terms and usage policy (owner §2.28), checked 2026-11-15

- **How it was checked:** Open Library's own pages, read directly on 2026-11-15: the API overview (`openlibrary.org/developers/api`), the search API (`openlibrary.org/dev/docs/api/search`) and the licensing page (`openlibrary.org/developers/licensing`). No request was sent to the API itself.
- **What they say, and what the plugin does:**
  - **Rate limits.** A client that doesn't identify itself gets 1 request a second, one that does 3. **The plugin keeps to one a second with no burst** (the plan's cap, §2.26), with back-off from 60 s to 6 h on a 429 or 5xx, through its host limiter.
  - **Identify the client.** Open Library asks for a `User-Agent` with the application's name and a contact email or phone. **The plugin sends `Lodestar/<version> (<the project's repository URL>) lodestar-sources-plugins`** (`openlibrary::USER_AGENT`), as Wikidata does: the project's URL, the same for every install, never the user's email or anything about the install (the lane's rules). Without an email it stays at the unidentified 1 request a second, which is the plan's cap anyway. **Open question for the runner to put to the owner (§2.19):** whether a project contact address should be added to the User-Agent, which would be the project's, not the user's.
  - **No bulk use.** "These APIs are not intended to serve as a bulk data backend"; bulk users are pointed at the monthly data dumps, and "please do not use our APIs to bulk download metadata". The plugin sends one search a lookup, only for items the runtime finds eligible (user interest first, then the capped background, Q12), and asks for at most ten works and five fields. At one request a second that's at most 86,400 lookups a day, under Q12's 100,000. **The same open question as Wikidata's (ENR-14):** whether a background walk over a whole index through the API counts as bulk use; a dump-based local match would answer it. Not in this PR.
  - **No hundreds of single-book requests:** the documentation asks clients to use `search.json` for batch results instead. The plugin uses `search.json` only, never the per-work or per-edition APIs.
  - **Licensing.** The Internet Archive "does not assert any new copyright or other proprietary rights" over the catalogue data and names no attribution requirement. None is stored or shown. Descriptions, covers and other page text aren't read.
- **No API key, no account:** Open Library has none for reading.

## Off by default, External class

- **The manifest:** `openlibrary`, an Enrichment source, Consent `External`, endpoint `https://openlibrary.org` only, `enabled_by_default: false`, never always-adult, never finds private. `tests/openlibrary.rs` `off_by_default_nothing_is_sent` and `a_private_item_is_never_sent` run it under ENR-10's runtime.
- **Kinds: Ebook and Audiobook.** Open Library catalogues books, and an audiobook is a reading of one. Comics are left out: a comic torrent is usually an issue or a volume of a series, which Open Library catalogues unevenly, so a title match there would mostly be a wrong work.
- **No host wiring**, as ENR-14 left it (runner, 2026-11-12): the plugin is library code listed in the catalogue, and is wired with the slice that lifts the External consent gate.

## What is sent (Q5)

- **One request a lookup:** `GET https://openlibrary.org/search.json?title=<title>&fields=key,title,alternative_title,first_publish_year,publish_year&limit=10`. There's no second request: the search answer holds all the plugin reads.
- **The title is sent folded** (`openlibrary::fold`: lower case, letters and digits, each run of anything else one space). Open Library hands search parameters to its Solr index, so a raw title could carry field names (`author:`), quotes, wildcards or brackets into the service's query syntax. Folded, it's words only; Solr's operators `AND`, `OR`, `NOT` are upper case and so can't survive either. It's also one URL parameter, encoded by the `url` crate (`a_hostile_title_is_one_folded_parameter`). The comparison folds the same way, so folding before sending loses nothing the match needs.
- **The book's own title, never the author** (`openlibrary::book_title`). The release parser keeps a book's `Author - Title` together as its title (`crates/release-parser/tests/golden/books_other.txt`: `Brandon Sanderson - The Way of Kings`), and ENR-10's runtime hands that to the plugin as the query's title. Sent as it is, it would put a person's name on the wire and never equal a work's title. So the plugin takes the part after the first `-` (when it has a letter or digit) as the title to send and compare, and drops the rest (`an_author_before_the_title_is_never_sent`). The cost: a `Title - Subtitle` name is looked up by its subtitle, which mostly finds no work, a miss rather than a wrong match, since the title must still be equal and the year agree.
- **`fields` is fixed:** the work's key, title, alternative titles and years. Never authors (people), subjects, editions or ISBNs. A `limit` of 10, twice Wikidata's 5: books share titles more often than films, and the one-work rule below needs to see the other works with the same title to refuse a guess.
- **The year isn't sent,** nor the kind. The headers are `Accept` and `User-Agent`, nothing else.

## The parser (`sources-feeds/src/openlibrary.rs`)

- **On the shared bounded JSON reader**, with Wikidata's rules: pure, no panics, no unwraps, no truncating casts, linear time (a bitmask over the five keys read), and an answer is used only when `Page::whole()`.
- **The caps (`SEARCH_LIMITS`):** 512 KiB (ten works of five fields are a few KiB; the slack covers a service that sends every field anyway), depth 8 (the shape is three deep), 50,000 values, 2,000 elements per array (a classic's `publish_year` can list a few hundred years, its `alternative_title` dozens), 4 KiB per decoded string, 10 works, 64 titles and 256 years kept per work. Past the work cap the parse stops (`Stop::Items`); past the title or year cap the rest are passed over undecoded and the work says `truncated`.
- **Strict where it reads:** a work must be an object with a `key` that is a work's id; `title` a string; `alternative_title` an array of strings; `first_publish_year` a number; `publish_year` an array of numbers. A wrong type, a repeated or escaped key among these, or a lone surrogate spoils the work, and with it the answer. Every other key, in a work or at the root, is passed over unread, and its repeats don't matter. A number that isn't a year 1–9999 (negative, fractional, huge) keeps no year without spoiling anything.
- **Lenient where the documentation is unsure:** a work may leave out every field but `key` (it then can't match). The documentation's sample shows `"key": "OL27448W"` while the live answer is known for `"/works/OL27448W"`, so both are read; anything else (an author `OL…A`, an edition `OL…M`, a leading zero, a number past `u64`) is a bad id and spoils the answer. Re-check both against real recordings before enabling.

## Choosing a match (`openlibrary::choose`)

- **One work must agree:** its title or an alternative title equal to the query's after folding, and, when the query has a year, that year as its first publication year or among its publication years (a torrent of a later edition names that edition's year). **None, or more than one, is no match** (`openlibrary_candidates`: the year picks one Dune; with no year, two works tie).
- **Confidence:** 80 with a matching year, 60 without. Lower than Wikidata's 90/70: without the author, which Q5 never sends, a book title is weaker evidence than a film's.
- **The answer:** `olid:OL…W` (the work, never an edition or an author: `id_ok` refuses those); the work's title as the canonical one; its alternative titles, once each and not repeating the canonical one, as alternatives in language `und` (Open Library doesn't say which language an alternative title is in); no genres (subjects mix genres with people and places); the query's year, else the first publication year. ENR-10's `into_claims` clamps it again.

## Judged before storage

- **Nothing here judges text.** `an_answer_is_judged_and_a_held_one_is_not_stored` runs the plugin's real answer through `unverified::ingest`: clean, it's stored; when its French title completes a child-safety pattern with the torrent's name, the hash is held and nothing is stored.

## Errors

- As Wikidata's: 200 is parsed; 429 is "limiting requests" and the host is held; a 3xx is never followed; anything else, or a transport failure, is "the request failed". A 200 whose root has an `error` key holds the plugin for its `Retry-After` (60 s when there's none, at most an hour) and is "answered with an error". A 200 that isn't `whole` is "wasn't understood". A title that folds to nothing sends nothing. **None of them is a miss**, so none is cached as one, and no error holds the service's text.

## Known limits (for the runner)

- **The query's title for books** comes from the release parser, outside this slice. Two things it does cost Open Library matches: it keeps `Author - Title` as one title (worked around above), and it doesn't read a year before about 1900, so `Frankenstein (1818)` is queried as the title `Frankenstein (1818)` with no year, which matches nothing. A follow-up in `pipeline/src/identify.rs` (hand over the parsed title without the author for books) or the release parser (older years for books) would fix both for every book plugin. Not changed here.
