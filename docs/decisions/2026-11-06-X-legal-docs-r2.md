# X-legal-docs-r2 decisions (#534)

**The owner's consistency review of Legal Notice version 3 against `main` (owner, 2026-11-06).** The owner compared the version-3 notice and the operator guidance with `main` at 63a2c6df and the code of the v0.5.1 release candidate, and found that the two described different software. This PR applies every correction, records the owner's two new instructions (owner §2.48) and specifies a slice that keeps the notice's facts tied to the code. Docs only; the embedded copy `crates/api/src/legal/notice.md` is the published file, as LEGAL-1's test requires.

## What the review found, and the fix
- **"This version" had no version.** The notice's claims about Settings controls, credentials and the crawler described rc.4 in one place and `main` in another. The notice now carries, under its version heading, the software it applies to ("Lodestar 0.5.2 and the development builds that lead to it, the `main` branch") and says the v0.5.1 release carries its own copy (version 2). The notice's revision and the software release are two different things and are labelled separately. The operator guidance's status line names the same baseline.
- **Built sources were called "not built".** `Services::start` registers the torrent cache (SRC-13b, External consent) and the Sonarr/Radarr webhooks (SRC-11c), both off until enabled. Section 2's inventory now lists what this version has (DHT, tracker swarm counts, the Magnetico/Bitmagnet importer, the torrent cache, the webhooks, the download-client hand-off, notification channels), marks each source class built or not, and says plainly that off by default is not the same as absent.
- **"Private findings never leave" exceeded the store.** `commit_one` clears `flags::PRIVATE_SOURCE` when a non-private source reports a torrent already stored (`make_public`; the field doc "A public sighting clears PRIVATE_SOURCE"). The notice and guidance §7 now say the flag lasts as long as only private sources have reported the item, that a later public sighting clears it, and why (the description is public knowledge by then). The behaviour is unchanged; the promise is bounded to it. Whether to preserve the classification instead is a design question for the runner (§2.26), not taken here.
- **The backup sentence was wrong about keys.** `lodestar backup` copies `lodestar.db`, `config.toml`, `seal.key` (quarantined names) and `auth.json`; it does not copy `secrets.key` (`SecretStore::KEY_FILE`, integration and proxy credentials). The notice now names both files and says that a restore to a new installation leaves stored credentials unreadable until re-entered.
- **The two documents disagreed on filters.** The notice said packs are on by default for a new data folder (RP-DEF, #454) and the unauthorised-copy pack exists (RP-UC, #469); the guidance still said "(planned)". The guidance's status line and §8 now match the notice.
- **Two factual slips.** "Everything it stores is in your data folder" now excepts the structured log folder (`settings.logging.file_folder`, default `<data>/logs`, changeable), the Windows service's start and logging failures (`%SystemRoot%\Temp\lodestar-service.log`, paths and account names only) and the safe-restart witness (`restart_witness_dir`, outside the data folder by design, CR-0d), and says where the console output is kept. It doesn't name the Windows Event Log: `event_log_errors` exists only as a settings field, and no code writes to the Event Log. "Expires within half an hour" is now "an announcement expires 30 minutes after its most recent refresh" (`peers.rs` `TTL`, refreshed on re-announce).
- **Removed (owner):** the sentence in section 8 that gave the publisher's reading of AGPL §16. The summary of §16 and "the licence text controls" stay.
- **Reporting (owner's wording):** section 9 now opens "Do not send reports of suspected illegal content to Lodestar's maintainers", separates removal requests, child-exploitation reports and other crimes, forbids sending files, screenshots, magnet links, hashes or identifying descriptions, asks for harmless synthetic examples in bug and security reports, and says these directions override no independent legal obligation. Guidance §4 gains the same instruction for operators.
- **The user guide** had the same `seal.key` slip in its backup table (§3.7) and the unbounded private promise for webhook finds (§5.5); both are corrected, with revisions row 2.3. `secrets.key` also seals the notification secrets (`settings/notifications.rs`), so the notice and the guide name notification channels among what a restore to a new server loses.
- **Smaller:** "switch any pack or rule off there or in Settings" now matches the wizard (per pack there, per rule in Settings); "Block the hash" in guidance §4 is "Quarantine the hash (section 3)".

## NOTICE_VERSION stays 3 (runner's call; the substance test is X-legal-docs', §2.33 for who decides; flagged to the owner)
Two of the changes alter substance: the private-source promise is narrower, and the source inventory names code that can contact named websites once enabled. LEGAL-1 raised the version to 3 for `main` and kept it at 3 through RP-UC's merge because v0.5.2 is unreleased, so no released install has accepted version 3. The same reasoning applies: the only version-3 acceptances are development installs. The date line moves to 2026-11-06. **If anyone has shipped a v0.5.2 pre-release that shows version 3, the runner raises the constant to 4 before the tag.** `legal.rs`'s tests (version line, published copy, renderable syntax) pass unchanged.

## Owner instruction for releases (§2.48)
"Tell the runner to ensure the legal documents are up to date before publishing versions." For the runner: before any version is tagged, (1) check `docs/legal/legal-notice.md` and `docs/legal/operator-guidance.md` against that build, (2) keep both on one release baseline and set the notice's "applies to" line, (3) decide the version (X-legal-docs' substance test; §2.33), (4) record the check in the release decisions file. The release checklist (`docs/build-plan.md` §0 release rung, runner's file) gains the step. **The first version it covers is `v0.5.1`:** its version-2 notice shares four of the slips found in version 3 (the data-folder sentence, "within half an hour", the §8 reading, the older section 9), and the owner chose a text-only rc.5 that corrects them before the tag (2026-11-06, to the runner: "No, do the text-only rc.5 (a)"; slice `R-rc5-notice`, a PR into `release/v0.5.1`).

## LEGAL-3: the notice's facts checked in CI (proposed slice; runner schedules)
The owner asked whether updated information can be pulled automatically. The first, cheap step is a test, the second a template.
- **LEGAL-3a, a facts test** in `crates/lodestar/tests/legal_facts.rs` (`crates/api` can't see the plugins, the CLI, the config or the notify modules; it is a dependency of `lodestar`, not the other way round): one table of claims the notice makes, each checked against the code it describes, failing with the notice section to update. Claims: the registered source plugins and their consent classes (from `Services::start`'s plugin list or the plugins' manifests) against section 2's inventory; the peer table's TTL (today `pub(crate)` in a private module, so the slice exports it, for example as `lodestar_dht::PEER_TTL`) against the 30-minute sentence; the backup file list (today an inline array in `cli/backup.rs`, so the slice extracts it to a constant) against section 5; `SecretStore::KEY_FILE` and the seal key against the key sentences; the notification channel modules (`integrations::notify`) against the outbound list; the `PRIVATE_SOURCE`-clearing rule against the private-source sentence (a store test that commits a private then a public sighting and reads the flag); the default `file_folder` and `restart_witness_dir` against the data-folder sentence. Each claim is matched by a short canonical phrase the notice must contain, so wording stays the writer's. Also covered: the two built sources' consent (`Consent::External` for the torrent cache, `Consent::None` for the webhooks) against section 2's sentence on how each is turned on, and the Windows service's temp log (`windows/temp_log.rs`) against the data-folder sentence. Not the Windows Event Log: `event_log_errors` is a settings field no code reads, and no Event Log writer exists; the sentence doesn't name it. Owns: the new `crates/lodestar/tests/legal_facts.rs`, the two small exports above, and a new `docs/legal/README.md` listing the checked phrases. Sonnet-eligible; the facts are read-only.
- **LEGAL-3b, templated facts** (later, if 3a proves too brittle): the notice keeps `{{peer_ttl_minutes}}`-style placeholders for numbers and lists only, rendered at build time from the same constants; `docs/legal/legal-notice.md` becomes generated output with a check that it is current. Not for prose.
- **Not in scope:** anything that changes the notice's wording automatically. A changed fact still needs a person to decide whether the version rises (§2.33).
