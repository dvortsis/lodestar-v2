# S-updates, part 3: Install now

Completes the Updates screen now that `POST /updates/install` exists (B-update-5, #312). It fills the slot left in `2026-11-01-S-updates.md` and `-S-updates-2.md`.

## What is wired
- **Install now** sits beside Check now and Skip this version for the newest release. `store.install(version, confirmManual)` posts `{version, when: 'now', confirm_manual}` through `run()`, so it shares the one-action-at-a-time rule, the busy state and stale handling. There are no retries.
- **Manual steps:** a release with `manual_steps` asks first in the confirm dialog. Cancel and Esc send nothing. Only Install sends `confirm_manual: true`; every other call sends `false`.
- **Answers:** 202 → the install steps the screen already renders from the `updates` topic. `404 unknown_version`, `409 version_skipped`, `409 install_unavailable` (its reason read from the message's parentheses, e.g. `(busy)`), `422 manual_confirmation_required` and `500 updates_not_saved` each get a plain message in the existing error area (en and zh). Reasons reuse the capability labels (`trust_damaged`, `image_mode`, …); `busy`, `not_candidate`, `not_current` and `upgrade_path` are new.

## Hidden, not disabled
The button is not rendered when `capability.can_install` is false (any reason, `trust_damaged` included), while a step is shown, while `installing` is set, or when the engine is unavailable. Reasons the server might still accept Install now for (for example `image_mode`, `dev_build`) are hidden too: we can't tell from the status which rules Install now skips, and the existing "Install automatically" line already explains the capability. Revisit if the server exposes an Install-now-specific capability.

## Not built
- **"Install in the window"** (`when: window`): the §10 copy has only "Install now · Skip this version", so no choice is offered. The store can pass it later.
