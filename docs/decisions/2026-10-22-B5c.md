# B5c decisions: result cache and `?explain=1`

Architecture §8 ("Result cache", "Ranking"). Code: `crates/search/src/cache.rs`, `crates/search/src/explain.rs`; wired into `/search` and `/facets` in `crates/api/src/{search.rs,facets.rs}`.

## Result cache

- **Where it lives:** one `ResultCache` per `Serving` (beside the leases), reached through `SearchHandle::cache()`. A fixed index (tests, tools) gets its own. Bounds are `ServingConfig::cache` (`CacheConfig`): per kind (searches, facets) 512 entries and 8 MiB estimated, entries dropped 10 minutes after they were computed. `enabled: false` turns it off.
- **The key:** the query as the index runs it (the visibility clauses ANDed on: the hidden-torrent flag and `-type:adult`), a scope string with the visibility bits (`hidden=…,adult=…`), the sort and page size for searches or the facet parameters (limits, `first_run`, `hide_adult`) and the always-on filters for facets, `now` when the query has relative dates (to the second), and the **generation**.
  - **The generation is the snapshot's segment set:** every segment id with its delete opstamp, from Tantivy's `SearcherGeneration`, plus the file index's for a query with `file:(…)`. Segments are immutable and their ids random, so equal generations see the same documents, and any commit that changes documents is a new generation. A swap to a rebuilt index has other segment ids. A reload that changed nothing keeps the generation.
  - Never the text alone: two requests whose visibility differs never share an entry, even if their queries printed alike.
- **What's cached:**
  - a search's **first page** (offset 0, no cursor, not explained): its hit ids and scores, the position after them, and **the lease they were read from**, which carries the count and its approximate flag. A hit inserts the same lease under the client's own lease id, so page 2 after a cached page 1 reads the snapshot page 1 came from. Rows are read from SQLite on every request, as before, so the per-hit Adult check against the stored class still applies.
  - **whole facet responses** and the count of the lease they were computed on. On a search's lease (`lease=`), the key is that lease's snapshot and `now`, so it shares entries with a facet request on the same snapshot; the count reported is the lease's own as it is now.
- **Invalidation: the simple rule, any commit.** A new generation misses by construction; entries of a generation no longer serving are dropped at the next lookup that sees a new one, by the lease sweeper (every ≤ 30 s), and at a swap (`Serving` clears the cache when readers move).
  - **Why not a finer rule** ("until the next commit that affects them"): it would have to test each entry against each commit's new segments and deletes. Live indexing commits every 2 s or 5k torrents; at the coordinator's ingest target (≥ 1,000 torrents/s, owner's decisions §1.6.5) each commit holds about 2,000 torrents. Testing 512 cached entries against that segment costs roughly 0.05–0.5 ms each, up to about 250 ms of a core every 2 s, against hits that save 0.5–8 ms (keyword search p95 on the 200k bench corpus) or 40 ms (facets on a browse). And the queries cached most (browses, the global facet counts, broad words) match new torrents in almost every commit, so a finer rule would rarely keep them. While the crawler is paused or idle, nothing commits and entries live their 10 minutes.
- **Filter changes reach the key through the index.** Hiding, releasing, relabelling or deleting a stored torrent writes its flags or row and a `reindex_log` entry in one transaction (`lodestar-store`); the live indexer re-indexes it at its next commit, which is a new generation. No filter epoch is needed: there's no way for a visibility change to take effect without a commit, and until that commit the uncached path shows the same thing. "Show adult content" is in the key (the scope, and the `-type:adult` clause). Tested in `crates/search/tests/cache.rs` (`a_filter_change_never_shows_what_it_hides`).
- **Concurrency:** a mutex per kind, held only to look up, insert or evict, never across a search. Identical misses at the same time compute once: the first computes, the others wait for its result (giving up when their own token stops); if it fails, each computes for itself. Values are dropped after the lock is released, so the last lease on a retired index unmaps it outside the lock.
- **Memory:** a cached search is estimated at 2,304 bytes plus its key and 16 bytes per hit (a lease is 1–2 KB, B5a); facets at their values and bins. A cached lease pins its searcher like any lease; entries of the serving generation share one. A cached lease never outlives the lease bounds: it's handed out at most 10 minutes after it was taken, and the swap clears the cache.
- **Metrics:** `ResultCache::stats()` gives, per kind, `hits`, `joined` (waited for an identical miss), `misses`, `evictions` (to stay in bounds), `retired` (generation or ttl), `entries` and `bytes`. `/metrics` doesn't render them yet: the rows are proposed in the PR for `crates/lodestar/src/metrics.rs` and `docs/metrics.md`, which this slice doesn't own.
- **Budget:** a cached hit takes about 2 µs in the cache (p95, release, 5k torrents); a cached browse through `/search` with its 50 rows read from SQLite about 1.2 ms p95, and cached facets through `/facets` about 0.3 ms p95 (both ≤ 2 ms). The ignored tests `cached_hits_are_within_two_milliseconds` and `a_cached_browse_and_facets_answer_within_two_milliseconds` measure them.

## `?explain=1`

- **`GET /search?explain=1`** (or `"explain": true` in the POST body) adds an `explain` block; without it the response is unchanged.
  - The request field is left out of the OpenAPI schema (`#[schema(ignore)]`): every other `SearchRequest` field has a default, which makes the generated client types require it, and the web callers build the body field by field. `GET` lists it as a parameter; `POST` accepts it all the same.
- **It never changes ranking:** it runs on the same lease and returns exactly `Lease::page`'s first page, then scores each hit's parts on the same snapshot. It bypasses the cache (its lease isn't cached).
- **Capped:** first page only (`offset` > 0 or `cursor` is a `400 explain_first_page`), and `limit` is capped at 100 (`EXPLAIN_MAX`).
- **Never about a hidden torrent:** it lists only the hits the response serves, after visibility and the per-hit Adult check. It's behind the session like the rest of `/search`.
- **Fields (stable):** `explain.ranked_by` (`relevance`, `discovered`, `size`, `files`), `explain.two_phase`, `explain.weights` (`name` 3, `path` 1, `title` 2, `stem_score` 0.25, `rerank_window` 200) and `explain.hits[]` in the hits' order: `id`, `score` (as `hits[].score`), `phase1`, `phase2 { name, title, phrase, exact_name, file_cap }`, `priors { seeders, freshness, junk, trackers, swarm_consistency }`.
  - Relevance today is `phase1 + phase2.name + phase2.title`, to float rounding: phase 1 is BM25 on the combined name-and-paths field plus fielded words, filters and the stem tier's constant; phase 2 adds each unfielded word's name and title boosts.
  - `phrase`, `exact_name`, `file_cap` and every prior are null: they aren't part of ranking yet (the priors arrive with swarm health, M4). Under a field sort `phase1` and `phase2` are null.
- **Weights are constants, not config, yet.** §8 says all weights live in config; they're constants in `schema.rs` (`NAME_BOOST`, `PATH_BOOST`, `TITLE_BOOST`, `STEM_SCORE`) and `index.rs` (`RERANK_WINDOW`). Explain reports them from those constants, so it stays right when they move to config.

## B5a polish

- The exact-count test cancels with a tripwire on the 1,000th document instead of a 30 ms timer.
- `expired_leases_are_swept_without_another_search` waits for the swept lease to be dropped, not for the map to empty: the sweeper drops leases after releasing its lock, so the map could be empty a moment before the drop.
- `Serving::open_or_rebuild` joins the rebuild thread when the lease sweeper fails to start, so the thread never outlives the failed start.
