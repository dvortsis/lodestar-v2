# WK-18w decisions

The Windows installer's "Join an existing Lodestar as a worker" mode (brief `briefs/WK-18w.md`, from the WK-18 split in `2026-11-12-WK-18.md`). Affects architecture §11 (Windows packaging) and §19.6 (joining).

## What the code showed (checked 2026-11-12)
- **The crates half is WK-18s (#801, merged 2026-11-13):**
  - `lodestar worker --join … --token-file … --join-only` joins, saves the credentials and exits 0. Without it, `--join` goes on to run the worker, so a one-shot join with a deadline could only time out.
  - Plain `lodestar worker` runs under the Service Control Manager, with its data folder defaulting to `%ProgramData%\Lodestar` as `serve`'s does.
  - A service never joins from its environment: it ignores `LODESTAR_TOKEN`, `LODESTAR_TOKEN_IGNORED` and `LODESTAR_JOIN`. The installer sets no environment for it anyway.
  - `--join-only` exits 3 on a folder that has already joined. Exit 3 also covers other refusals (a coordinator's folder, another worker holding the lock), so `join-worker.ps1` treats it as a failed join and the install rolls back.
- **The token can't reach the deferred action through `WixQuietExec`**, because that runs a command line, and the token is never put on one. So the join is a small C# custom action (`join-ca/`, built with WiX 3's DTF and `MakeSfxCA` in `build-msi.ps1`). It reads the token from its `CustomActionData` and writes it to `join-worker.ps1`'s standard input. All the logic is in that script, which the tests drive through the same C# code (`JoinRunner.cs`).

## How the token is kept out of sight
- **The MSI property `JOIN_TOKEN` is Hidden and Secure**, and the wizard's field is a password field. The action that copies it into `CustomActionData` and the action that reads it are both `HideTarget`, and that property (`JoinWorker`) is Hidden too. So neither the action lines nor the property list at the end of a verbose log show it.
- **It's never written to the registry or to any file the product keeps.** The registry keeps only `Software\Lodestar\Mode = worker`, never the address or the token.
- **It's on disk for the join only:** a file in `C:\Windows\Temp\lodestar-join-<random>\t-<random>\`, a folder created with a protected list for SYSTEM and Administrators in the same call (the `secure-datadir.ps1` pattern). The script creates the file empty (`CreateNew`), checks the folder and the file are private (raw access-list check, `dacl-check.ps1`), and only then writes the token. It deletes the folder in a `finally`, retries for up to 10 s while a stopped process still holds the file, and fails the install, naming the folder, if it can't.
- **Nothing that prints can show it.** `join-worker.ps1` and the C# action both replace the token (in any case) with `[join token]` in every line they relay. lodestar itself never prints it. The user-facing failure line may name the address, never the token. The work folder keeps `join-worker.log` (no token) for a failed install to point to, as `secure-datadir.ps1` does.
- **The address can't redirect the action.** `CustomActionData` is `key=value;…`, so a `;` or `=` in the address could add keys. The wizard's checks refuse both in the address and the token, the address and token come first, and the C# action never takes a folder from the data. It uses `Program Files\Lodestar` and `ProgramData\Lodestar`, and refuses any other install folder (as `WrongInstallFolder` does). The address must start with a letter, a digit or `[`, so PowerShell can't read it as a parameter name.
- **If the C# action has to stop the script, it deletes the token folder itself.** The folder names are made in one place, `JoinRunner.WorkFolders`, and the script gets the exact paths (`-WorkDir`, `-TokenDir`) and checks their shape, so the two sides can't drift. After the action's 5-minute deadline it kills PowerShell and its children, deletes the token folder, checks it's gone, and fails the install if it isn't. Reading the rest of the output is also bounded (30 s).
- **A token pasted into the address field is caught.** `JOIN_ADDRESS` is Hidden too, and an address starting with `lsj1` is refused, by the action and by the script, with a message that doesn't repeat it. The action's own messages pass the address through the token scrub.
- **The service's account owns the worker's files.** The join runs as SYSTEM, and `secrets.key` and the credentials allow only OWNER RIGHTS, SYSTEM and Administrators (`integrations/src/secret.rs`). So after the join, `icacls /setowner` hands them to `NT SERVICE\Lodestar`, without following links. If that fails, the install fails.
- **No environment fallback.** `LODESTAR_TOKEN`, `LODESTAR_JOIN` and `LODESTAR_TOKEN_IGNORED` are removed from the child processes' environment, so only the file joins.
- **Wizard only (runner's call to confirm).** A worker-mode install with less than the full wizard (`/qn`, `/qb`, `/passive`) stops with a message. A silent install would mean the token on msiexec's command line, which the brief rules out. A later slice can add a `JOIN_TOKEN_FILE` for scripted installs if one is wanted.
- **Residual, accepted:** while the install runs, Windows Installer holds `CustomActionData` in its in-progress script under `C:\Windows\Installer` (SYSTEM and Administrators only), and .NET and PowerShell strings can't be wiped. A token works once, within 15 minutes (§19.6, owner §2.47).

## How the modes stay apart
- **The default, "This PC runs Lodestar", installs as before.** The only differences on that path are the extra Mode page in the wizard and the service's arguments coming from a private property whose value is `serve`. Its components and actions are unchanged, and `smoke.ps1` runs on that path unchanged.
- **The service's arguments are a private property** (`LodestarServiceArgs`, `serve` or `worker`). It can't be set from the command line, so nothing but the mode decides what the service runs, and the worker never carries `--join` or `--token-file`. Its account, service SID, privileges, recovery actions and delayed start are the default mode's.
- **The mode is kept.** A Repair or upgrade (also the updater's silent one) reads `Software\Lodestar\Mode` and sets the mode from it, whatever the command line or wizard says, skips the Mode and Join pages, and never joins again: the join runs only on a first install (`NOT Installed AND NOT WIX_UPGRADE_DETECTED`).
- **A worker gets no Start-menu shortcut, no web-page firewall box and no 8090 rule**, even with `WEB_FIREWALL=1` (it has no web page). The DHT rule and the optional Defender exclusion are the same as the default's.
- **A failed join rolls the install back** (`Return="check"`). The message shows in the wizard and is logged. The data folder is kept, as on every rollback.
- **The join checks the data folder is secured before anything goes in it.** `--join-only` doesn't check the folder's permissions itself (WK-18s), so `join-worker.ps1` refuses, before any token file or process, unless the folder exists, isn't a link, is owned by SYSTEM, Administrators or the service, has a protected list, and allows only those three. That backs up the sequencing below at run time.
- **The join runs after the data folder is secured and before the service starts,** as SYSTEM, against `C:\ProgramData\Lodestar`. lodestar refuses a folder that holds a coordinator's database, so a PC that ran Lodestar before needs its data removed first (uninstall with `REMOVE_DATA=1`).

## Tests
- `test-join-worker.ps1` builds a stub `lodestar.exe` and runs joins through `JoinRunner` and `join-worker.ps1`. It checks the private folder and file (owner, entries, protection) at the moment lodestar reads the file; that a folder that isn't private is refused with nothing written; that the token folder is gone after success, refusal, a lodestar that echoes the token, a run over the deadline (the process is gone too) and an exit with no credentials; that a held file is reported; and that a sentinel token never appears in the output, the relayed lines or `join-worker.log`, nor on lodestar's command line or in its environment.
- It also covers the action's own deadline (the script killed before its `finally`: the result, the stub gone, no token folder left), a data folder that isn't secured, a folder that has already joined, a hand-off to the service that fails, and a token pasted into the address field.
- **No join-mode smoke run of the MSI in CI.** That needs a coordinator on the runner that issues a token, which `smoke.ps1` doesn't start today.

## Known gaps (follow-ups)
- **A join that succeeded and was then rolled back** (a later step failed, or the user cancelled) leaves the worker registered on the coordinator and its files in `C:\ProgramData\Lodestar`. Nothing is installed then, so uninstalling can't help. The next setup says how to start over: remove the worker on the main Lodestar (Settings, Workers), delete `C:\ProgramData\Lodestar` as an administrator, and run setup again with a new join token. A rollback action that removes the worker's files is follow-up X-wk18w-rollback.
- **A downgrade to an MSI from before this slice** reinstalls a worker as `serve`.
- **The work folder** `C:\Windows\Temp\lodestar-join-<id>` (log only) is kept after every join, as `secure-datadir.ps1`'s is.
- **The update helper's task** is registered in worker mode too. The task and the helper aren't checked against a worker's folder.

## What WK-19's workers chapter must say about Windows
- Install with the wizard and choose "Join an existing Lodestar as a worker". It needs the main Lodestar's cluster address (`https://<ip>:8091`) and a join token from Settings, Workers, Add worker, which works once, within 15 minutes.
- A silent install can't join; the wizard refuses `/qn`, `/qb` and `/passive` for this mode.
- If joining fails, setup is undone and says why. Make a new token and try again. If setup says this PC has already joined (an earlier setup joined and was then undone): remove the worker on the main Lodestar, delete `C:\ProgramData\Lodestar` as an administrator, and run setup again. The log is `C:\Windows\Temp\lodestar-join-<id>\join-worker.log` (Administrators only).
- A PC that ran Lodestar before must have its data removed first (uninstall with `REMOVE_DATA=1`).
- The worker has no web page and no Start-menu shortcut. Check it on the main Lodestar's Workers page.
- Repair and updates keep it a worker and never ask for a token again.
- To move a worker to another coordinator: remove it in Settings, Workers, uninstall with `REMOVE_DATA=1`, and install again.
