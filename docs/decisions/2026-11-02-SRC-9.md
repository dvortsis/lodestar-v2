# SRC-9 decisions (Internet Archive JSON parser)

Slice SRC-9 of `docs/plan/2026-11-01-v06-sources.md`. It covers architecture §18.2 (rank 6, Internet Archive item torrents and the metadata API) and §18.9. The parser feeds SRC-10c (the Internet Archive plugin). It holds to the safety bar SRC-6 set (`docs/decisions/2026-11-01-SRC-6.md`) and cleans text as `2026-11-02-X-strip-format-chars.md` says.

- **`archive_org::parse_each(body, &Limits, emit)`** is a pure function from bytes to items, in `crates/sources-feeds/src/archive_org.rs`. It returns a `Page`: SRC-6's `Summary` plus the paging a search answer gives (`total`, and the scrape API's `cursor`). `archive_org::parse` collects the items with the default caps. No I/O and no network code; SRC-10c fetches.
- **Three answer shapes, matched by key in the root object**, so one call parses whichever the plugin fetched:
  - `advancedsearch.php?output=json`: the docs in `response.docs`, the count in `response.numFound`;
  - the scrape API (`services/search/v1/scrape`): the docs in `items`, with `cursor` and `total`. It isn't in the plan's row, but it's IA's paging for deep result sets and costs a few lines;
  - `metadata/<identifier>`: the root object is the item, read from its `files`, `metadata` and `item_size`. `{}` (IA's answer for an unknown identifier) gives no item and no stop.
- **The JSON reader is our own, not `serde_json`.** `serde_json` builds the whole tree first, so a 16 MiB body could take many times that in memory before any cap applied, and it can't keep the items finished before a fault. The reader here checks every cap as it reads:
  - Nesting outside the known shapes is walked without recursion. The skip routine's stack is bounded by `max_depth`.
  - A string is copied only when it's a field the parser keeps. Its raw length is checked against `max_text` first; decoding only shrinks text.
  - It follows RFC 8259: strict number grammar, no raw control characters in strings, only the defined escapes, and no trailing commas, single quotes or text after the root. A lone UTF-16 surrogate escape in a kept field skips the item (`malformed`). Outside a kept field it's only scanned.
  - Keys are compared as written: IA doesn't escape keys, so an escaped key (a backslash-`u` spelling of `btih`) is an unknown key.
- **Caps.** As in SRC-6, structural caps stop the parse with a `Stop` reason and keep the finished items. Field caps skip the one item and count it in `Skipped`. A half-read item is never used, so a metadata answer cut short has no item.

  | Cap | Default | Over it | Why this value |
  |---|---|---|---|
  | `max_bytes` | 16 MiB | stop (`Bytes`); the prefix is parsed | SRC-6's, the `Fetch` contract's `MAX_BODY`. A 100-doc search page is about 50 KiB; a metadata answer with 10,000 files is about 3 MiB |
  | `max_depth` | 16 | stop (`Depth`) | SRC-6's. The deepest field read is 5 levels (`root > response > docs > doc > collection`) |
  | `max_values` | 1,000,000 | stop (`Elements`) | SRC-6's `max_elements`, counting JSON values (containers included). 16 MiB of `0,` is 8 M values |
  | `max_items` | 5,000 | stop (`Items`) | SRC-6's. Kept and skipped items both count; a metadata answer is one. SRC-10c asks for at most this many rows per page |
  | `max_array` | 10,000 elements | skip the item | Any array inside a doc or metadata item except `files`. A real `subject` or `collection` list has a few dozen. Outside items, arrays cost only values |
  | `max_text` | 64 KiB raw | skip the item | SRC-6's. Only strings the parser reads are measured; a long `description` is skipped unread |
  | `max_files` | 10,000 | keep the first ones, set `files_truncated` | The claims' `MAX_FILES` (SRC-1). The rest of `files` is still read for the `.torrent` entry |
  | `max_name_bytes` | 1 MiB − 4 KiB | keep the files before it, set `files_truncated` | The claims' `MAX_TOTAL` of text, less the title (1 KiB) and the ids SRC-10c may claim (the identifier and 16 collections, under 3 KiB). SRC-0's clamp counts them in the same budget, so a list this parser calls whole is never cut there silently. A test checks the sum (runner's review) |

  Smaller per-field limits trim, as SRC-6's do: title ≤ 1,024 B (`MAX_NAME`), cut on a character boundary after `lodestar_metainfo::hidden_char`s are removed; at most 16 collections; a cursor ≤ 1,024 B. A file path over 4,096 B (`MAX_PATH`) is left out, not cut, since a cut path names another file, and the list is marked truncated.
- **Hashes come only from `btih`, and only v1 counts.** `btih` is a v1 hash by name: 40 hex digits (either case) or 32 base32 characters, not all zero. A 64-digit value (v2) is invalid.
  - A search doc's hash is its `btih` field.
  - A metadata item's hash comes from, in order:
    1. the `btih` of the `<identifier>_archive.torrent` entry in `files` (IA's own torrent);
    2. any `*_archive.torrent` entry (ASCII case aside), so a missing or odd identifier doesn't hand the item to another torrent;
    3. the `metadata` object's `btih`;
    4. the first other `.torrent` entry with a `btih`.
  - **With the fourth, the item claims only the hash and title.** That torrent may be an uploader's torrent of something else, so the identifier, link, size, dates, media type, collections and files would be claims about another torrent. They're dropped, and `files_truncated` is set when there were files (runner's review).
  - At most 16 `*_archive.torrent` entries and the first other `.torrent` are remembered as candidates; later ones are only files.
  - The chosen source being malformed (not a string, or not a v1 hash) skips the item (`bad_hash`), even when another source is good. This is SRC-6's rule: the answer's statements disagree. No source skips it as `no_hash`. A dark item (`is_dark`, no files) is `no_hash`.
  - A `btih` on a file that isn't a `.torrent` is ignored. A `.torrent` without a `btih` is an ordinary file.
- **Fields kept:** `identifier`, `title`, `item_size`, `publicdate` (else `addeddate`), `mediatype`, `collection`, and a metadata item's files (`name`, `size`). The first value of each field wins; IA writes some fields as a string or an array of strings, and the array's first string is used.
  - **Identifiers and collections** must be 1–100 ASCII letters, digits and `._-` (IA's own rule), or they're dropped. A dropped identifier keeps the item but leaves it without a link.
  - **The external reference is built, not copied:** `https://archive.org/details/<identifier>` from the validated identifier. Nothing from the answer that looks like a URL is stored, so there is nothing to strip credentials from.
  - **Sizes** are a JSON number or a string of at most 20 digits that fits a `u64`. Signs, fractions and exponents are refused.
  - **Dates:** RFC 3339 (the search index's form), or `YYYY-MM-DD HH:MM:SS` and `YYYY-MM-DD`, read as UTC (the metadata form).
  - **`mediatype`** is kept only as lower-case ASCII letters and digits, at most 32 B.
  - **File paths** have hidden characters removed, as titles do. They're claims only, never opened or written: an IA name can hold `/`, and the filter pipeline judges them (SRC-0).
  - **No file is dropped silently** (runner's review). The filter judges the listed names, so a name that slipped past the list would hide it from the filter. Each of these sets `files_truncated`:
    - a `name` that isn't one string, such as an array, `null` or an object;
    - a second `name` key in an entry;
    - a `files` element that isn't an object;
    - a `files` value that isn't an array.
  - **Every `.torrent` is listed except the one the hash came from,** which describes the torrent rather than a file in it. A candidate `.torrent` past a cap counts as missing unless it turns out to be the hash source.
  - **An entry with no `name`, or one that is empty or only hidden characters, is dropped without the flag.** It names nothing, so there is no text the filter could have judged. Its size alone isn't a claim worth keeping.
  - **Not kept:** `description`, `uploader`, `creator`, `subject`, reviews and every other field. An uploader is an e-mail identity, and §18.7 forbids profiles of people.
- **A metadata answer over 16 MiB has no item.** Only items with roughly 50,000 or more files are that big. The search doc's `btih` still names the torrent, so the key isn't lost, only the file claims.
- **Fuzzing:** `fuzz/fuzz_targets/archive_org.rs`, with seeds in `fuzz/seeds/archive_org/`. The first byte picks tight caps. CI's fuzz matrix lists `fuzz/fuzz_targets/*.rs` itself. `fuzz/Cargo.lock` didn't need regenerating.
  - **This session had no cargo-fuzz or nightly toolchain,** so the target was built (`cargo check`, stable) but not run. `tests/archive_org_props.rs` runs the target's checks over 200,000 inputs in every `cargo test`: random bytes, and the fixtures with bits flipped, bytes inserted and deleted, JSON tokens spliced in, chunks duplicated and other fixtures spliced on. About 39,000 of them still parse to items, with about 21,000 files, so the checks reach the item and file code.
- **Golden fixtures are synthetic**, written for the tests in the shapes IA's APIs answer with (key names and order, string-or-array fields, string sizes, the `_archive.torrent` entry, the scrape cursor). They use made-up identifiers, `.example` hosts and open-licence wording. No real item's metadata is copied.
