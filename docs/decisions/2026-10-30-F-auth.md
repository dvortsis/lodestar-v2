# F-auth decisions

Fixes Area 2 review finding 1 (`docs/code-review/codex-review-v0.5-area-2-results.md`): a failed `auth.json` save used to replace the credentials in effect.

- **Every auth change saves first and publishes second.** `Auth` builds the whole next state, writes it with the existing atomic write, and only then swaps it in under the write lock (`Auth::commit`). Setup, password change, sign-out-others and the trusted-proxy settings all go through it; `set_proxy` and `rotate_sessions` drop their own restore-on-error code. A storage error now leaves the password, session key, setup state and proxy settings as they were, on the running instance and after a restart, which is what the M2 decision's "atomic auth persistence" (§12) promised. One pattern, rather than per-method restore code, so a future field can't be forgotten in a restore path.
- **Setup spends its token only after the save succeeds.** A failed setup leaves the instance unclaimed and the same token valid, so the owner can retry once the disk is fixed without reading a new token out of the logs.
- **A failed write removes its temporary file**, best effort. It may hold a half-written password hash and session key; it was already owner-only (0600), and the next save would overwrite it, so this is hygiene, not a fix.
- **Tests:** `crates/api/tests/auth_failed_save.rs` has the review's two reproductions and a table test over every saving method: error ⇒ the observable state (setup pending, the caller's session, both passwords, proxy settings, the file's bytes) is unchanged before and after a restart, and the same call succeeds once the obstacle is gone. A second table test pins the success paths.
- No owner decision, security decision or owner-set number changes.
