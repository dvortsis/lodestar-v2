# X-live-banner-flake decisions

- **Cause: the event beat the id.** The OpenAPI mock records a call when its handler runs, before `route.fulfill`. So `mock.calls('registerSearchLive')` can count the registration before the page has read `{ id: 'a1' }`. An `a1` event that arrives first meets `id === null` in `live.svelte.ts` and is dropped. Nothing resends it, so `results-live` never appears, which is the failure seen on #1082 and #1165. Delaying the mock's answer by 400 ms reproduces it every time. The `/events` stream was not the cause: `LiveHost` subscribes to `search_live` in the same task that sends the registration, so the stream for that topic is open before the request reaches the mock.
- **`liveEvents().answered(pathname)` (test helper).** The fake `fetch` counts each JSON body the page reads, per pathname. The count goes up inside the promise the caller awaits. So by the time a later `page.evaluate` sees the count, the caller's own code after `await` (here `id = r.id`) has already run. That makes the wait exact, not a matter of timing. The search-live spec waits for `answered('/api/v1/search/live')` to reach 1, then 2, before it sends events for that id.
- **`send` waits for a stream that takes the event.** It waits, with a 10 s deadline, until a connection is open whose `?topics=` lists the event (for `resync`, any open connection). A frame sent before then used to be dropped silently. Now it is either delivered or fails with a clear message. This applies to every spec that uses `liveEvents`. It is a test-only change: no `web/src` change, and no assertion loosened.
