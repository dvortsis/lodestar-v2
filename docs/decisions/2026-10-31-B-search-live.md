# B-search-live decisions: query-scoped live match counts

Part 4 of B-search-recovery, built to the design in `2026-10-31-B-search-recovery.md` ("Live counts for a query"). Code: `crates/api/src/search_live.rs` (registry, matching entry point, `POST /search/live`, `DELETE /search/live/{id}`), `crates/api/src/events.rs` (per-session delivery), `crates/search/src/percolate.rs` (count-only entries), `crates/lodestar/src/percolator.rs` (the run). Spec: §8 (percolation), §9 (`/events`), §10.4 (Live row), §10.13 (throttle), §20 (visibility).

## As designed
- **Registration** `POST /search/live {q | ast, hidden, tz}` → `{id, since}`; `DELETE /search/live/{id}` releases it. In memory only, no store rows, no index change. The stored query is `base_query(ast, visibility).query()` with visibility read at registration; `q`/`ast` and `tz` go through `/search`'s own `request_ast` and `tz_param`, so the same parser bounds (2,048 bytes, 64 clauses, depth 16) and errors apply. Auth required (`auth::protected`), and `same_origin_json` on both, as every state-changing route.
- **Matching:** the percolator runs live queries as count-only `Due` entries of `percolate` over the new id range, with the run's budget and `max_range`, after its saved searches (see below).
- **Delivery:** `event: search_live {id, matched, through}` on `/events`, throttled to §10.13's 5 s, counts in between combined.
- **Bounds:** 4 per session (a fifth replaces the oldest), and released by `DELETE`.

## Decided here
- **Live queries run after the saved searches, on what's left of the same budget.** A run percolates the saved searches, records and announces their alerts, then runs the live queries with the same `CancelToken`. So an alert never waits on a live query. After saved searches ran, even the first live query can be stopped inside its scan (`Due::stoppable`), so a nearly spent budget isn't overrun; once it's spent they're `more`, and the next run (straight away, now with no saved searches due) takes them with the whole budget, where the first always completes as before, so the task never spins.
- **The throttle is per connection per registration.** The event names one registration, so "at most one per subscriber per 5 s" is read as one batch per connection per 5 s: each of the session's registrations (at most 4) whose count changed gets its event in it.
- **Released 30 s after the session's last `/events` connection closes, not at once** (deviation from the design's "released when its connection closes"). `EventSource` reconnects after a network blip, a proxy cut or a restart of the stream; releasing at once would reset every banner's count to 0 and lose the matches that arrived in the gap. A reconnect within 30 s (`LiveConfig::grace`) keeps the registration, count and all; a closed tab's goes 30 s later. One registered while no connection is open goes after 10 minutes (the design's "10 minutes without one") unless a connection opens.
- **A `content` settings save drops every registration, eagerly.** `EventHub::settings_saved("content", …)` clears the registry, so an on-off-on change of "Show adult content" that nothing observed in between still drops them. As a second guard, each registration remembers the Adult setting it was made under, and every read of the registry drops those made under another setting.
- **The same tier as the page.** `/search` falls back to the stem tier (§8) when the exact query finds fewer than 10 and the tier finds more; the registration decides it the same way (`Lease::new_at` on the stored query) and stores it (`Due::stems`), so a narrow query whose page showed stem matches counts them too. **Measured** (`percolator::tests::live_queries_follow_the_saved_searches`, debug build, 2,000 new torrents): 200 saved searches took 4.2 s (mostly recording 200 × 1,000 alerts), and 256 live queries (the most a hub holds) then took 12 ms.
- **`matched` is cumulative since registration**, not a delta: a missed or combined event loses nothing, and every tab of a session can show the same number. Throttled events only go out when `matched` changed.
- **Per session, never broadcast.** `search_live` events skip the ring and the broadcast (`publish` refuses them) and carry no `id:`, so they're never replayed: each client's own task reads its session's counts from the registry. A new topic, `search_live` (the eighth, so the `u8` topic set is now full), lets a client opt in or out with `?topics=`; with no `?topics=` it gets them like every topic.
- **Ids are random** (16 hex digits), not sequential, so they say nothing about other sessions; another session's id is a 404, the same as none.
- **No ids while Adult is hidden:** `since` and `through` are null for a registration made while "Show adult content" is off, as `torrents`' `max_id` is (§20.9): ids are sequential, so the gap between two would tell how many hidden torrents arrived.
- **Filter-hidden torrents** follow the stored `-hidden:yes` clause; quarantined, dropped and hash-listed torrents are never indexed (§20), so they can't count.
- **Known limits, documented on the endpoint:** swarm clauses (`seeders:>N`) match nothing at index time (the swarm isn't scraped yet, as for alerts), so such a query counts only what it can see then; and where the percolator doesn't run (fixture mode) nothing is counted.
- **A total cap of 256** (4 for each of the hub's 64 streams), past which a new session's registration is a 429 `too_many_live_queries`. A session already at 4 still replaces its oldest.
- **`since` is the searcher's snapshot**, the highest id search can see now, not the committed watermark, so what's counted is what the page couldn't have shown yet.
- **Live queries honour `tz`:** `percolate::Due` gained `utc_offset` (saved searches still run at 0) and `count_only`, and `Matched` gained `count` (every match, past `keep`).
- **"Closes" means the session's last connection.** A registration isn't tied to one `/events` connection (the POST can't name one), so a session with two tabs keeps both tabs' registrations until its last connection closes; the 4-per-session cap and `DELETE` bound the rest.
- **A count made before a connection opens** is delivered as soon as it opens, without waiting for the count to grow again.

## What S-search-6's banner should switch to (no UI in this slice)
1. On each query change (and when a page with a query opens), `DELETE` the previous registration if there is one, then `POST /search/live` with the query shown (`ast`, `hidden`, `tz`) and keep its `id`.
2. **Re-register after a `settings` event for `content`** (it released every registration) and after a `resync` with reason `restarted` (a server restart forgets them; a stream that never got an `id:` gets no `resync`, so also re-register on a reconnect before the first `id:`). A plain reconnect keeps it. A 404 on `DELETE` is fine to ignore.
3. Listen for `search_live`; when `id` is yours, show "N new results" with N = `matched`. It counts on the same tier and visibility as the page, so the `total_approx` checks can go; a query with a swarm clause (`seeders:` and the like) may under-count, as alerts do.
4. Stop the 30 s `limit: 1` polling. Keep the rest of the banner (pause while scrolled, Show reloads and clears, throttled announcement). Show re-registers, so the count starts again from 0.
5. On a 503 (`events_unavailable` or `search_disabled`) or a 429, show no banner rather than fall back to polling.
