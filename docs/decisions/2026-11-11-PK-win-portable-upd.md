# PK-win-portable-upd decisions: the portable build's update and rollback

The portable build now installs its own updates (architecture §12.2 "Windows portable"; plan `docs/plan/2026-11-06-m6-gap-audit.md` §4.3). It verifies the zip, renames the running `lodestar.exe` aside, puts the new one in place and relaunches (PK-win-restart). The new version then has a probation; if it fails, the old program is renamed back. It runs as the user who unpacked the zip: no helper, no new rights. The code is in `crates/lodestar/src/update/windows/portable.rs`, wired through `check.rs`, `windows/mod.rs`, `main.rs` and `services.rs` (runner, 2026-11-11). Calls marked "runner" are the runner's under §2.19; the owner can veto them.

## Who supervises
- **No separate supervisor; each start judges the journal (runner, approving the design).** §12.2 says "the same helper supervises probation", but the portable build has no helper, and a watcher process would hold the console, the port or the data lock that the new copy needs. So every start of `lodestar.exe`, before anything opens the store, finishes whatever step `<data>\bin\portable.json` is at. The new version also runs the self-test in its own process.
  - **What this doesn't catch:** a new version that crashes without exiting through `serve` (an abort). The launcher's window then says Lodestar stopped. The next start counts an attempt, and a start past the third rolls back (§12.2's 3 attempts). Nothing restarts it by itself, because the portable build has no service manager.
- **Probation:** the self-test is the Unix child's: the search index answers, the HTTP port is bound (and the DHT's unless it's off), and `/healthz` is green. It must pass within **5 minutes of `Services::start` returning** (§12.2's timer, which starts once migrations finish; migrations run in that start). Its clock is a trait, so the window is tested with a fake clock (no tokio `test-util`).
  - **Failure** (the window passes, or `Services::start` fails) renames the programs back and restarts into the old one: through Restart now's relaunch while serving, or at once when the start failed.
  - **A graceful stop (Ctrl+C, Restart now) before the self-test decides gives its attempt back,** as §12.2's "restarts aren't failures".

## The journal and the files
- **`<data>\bin\portable.json`**, written by temporary file and rename before and after each step: `staged` → `swapping` → `swapped` → (`rolling_back`). The files are `bin\next.exe` (staged), `bin\previous.exe` (the old program while on probation) and `bin\failed.exe` (the new program after a rollback). The tests cover a crash after each step.
- **The one gap with no `lodestar.exe`** (runner review B1): between the two renames of a swap (the running program aside, then the new one in) or of a rollback (the new one out, then the old one back). Everything that can fail slowly happens first: the file that will move in is hashed and held open, so nobody can write to it, before anything moves. The two renames then run back to back, both within the portable folder on one volume. A power cut in that moment still leaves `lodestar.exe` missing, with the program it needs in `data\bin\previous.exe`. The journal says `swapping` or `rolling_back`, and once that file is back as `lodestar.exe` the next start finishes the step by the hashes.
  - **`Start Lodestar.cmd` puts it back** (runner, approving the shared edit): with no `lodestar.exe` and a `data\bin\previous.exe`, the launcher moves that back first and says so, in one guarded line with no labels. It never overwrites an existing `lodestar.exe` and never touches `next.exe` or `failed.exe`. A unit test pins the line. It isn't run for real on CI, because the launcher also opens the browser.
  - **What the fallback can't help:** a launcher run that lands inside the rename gap itself, while the other copy is between its two renames, moves `previous.exe` back to `lodestar.exe`. The other copy's second rename then replaces it, because on Windows a rename replaces an existing `lodestar.exe` unless that file is running. So the old program can be lost to that step, with only the new one left in place (review of 7f651d0, N-a; reworded after #659's review, N2). The gap is two renames long, but Defender holding a new file open (the sharing conflicts that `rename_retrying` retries for about 1.3 s) can stretch it. Starting the launcher during an update's restart is unusual, and the journal and hashes still never put an unrecorded program in place.
  - **Line endings** (runner, approving the shared edit, review of 7f651d0, I2): `.gitattributes` now checks every `packaging/windows/**/*.cmd` out with CRLF, as cmd expects; the repository keeps LF. The unit test reads the file as checked out and doesn't depend on either.
  - **For PK-guide-3:** the user guide says that if `lodestar.exe` is ever missing after an update, starting Lodestar with `Start Lodestar.cmd` puts the previous version back. Started any other way, the user moves `data\bin\previous.exe` back to `lodestar.exe` by hand. An earlier draft said every state left a runnable `lodestar.exe`; that was wrong, because the install hashed `next.exe` between the renames.
- **Untrusted input:** capped at `MAX_STATE`, a strict `format` (1), versions that parse, SHA-256 fields that are 64 hex digits, at most 10,000 snapshot names. Unknown fields are accepted, as in PK-win-upd-3's journal, because after a rollback the older version reads what the newer one wrote. The runner allowed "deny_unknown_fields **or** a strict version field"; this is the second. A field an older version mustn't ignore bumps `format`. A journal that fails these checks is left alone: nothing is moved, and Install answers `update_in_progress` until someone removes it.
- **A journal is acted on only in a private `bin`:** at a start with a journal, `bin` is checked first (the same rule as Install's), and in a folder others can write nothing is moved or run (self-review B2). Otherwise someone who can write there could plant a journal and a `previous.exe` that a rollback would put in place.
- **Nothing is taken from the journal on trust.** The program is this process's own path, recorded at start. Which program is where is decided by SHA-256: a file is moved into `lodestar.exe` only if it's the recorded one, and `lodestar.exe` is never overwritten. The running version is compared with `from` and `to`.
- **No relaunch loop, whatever the journal says.** A start relaunches only when it has just moved the new program out of `lodestar.exe` and isn't the old version. The old program never relaunches, and nor does a start that moved nothing. (An earlier draft guarded with "a relaunched copy never relaunches"; that would have stopped the main failure path, where a relaunched new version fails to start.)
- **A failed undo never leaves `lodestar.exe` empty** (self-review B3): when the old program can't be renamed back, the verified new one goes into place and the journal stays, so the next start judges it (the new version's probation, or the old one put back). A rollback whose old program can't go back puts the new one back the same way.
- **Same volume:** the portable kind requires `<data>` to be `<program folder>\data` (`check::detect`), so every move is a rename. Windows allows renaming a running program; `tests/update_windows_portable.rs` checks this on the Windows CI job.

## Two copies
- **A second copy started during probation judges nothing** (runner reviews I1, twice): `at_start` takes `<data>\bin\.lock` first. The new version on probation keeps it from that moment until its self-test decides; `serve` holds it through `Services::start` and the self-test, then drops it, and the notifier's next try takes it. That closes the gap the first fix left, while the probation copy was still starting and its notifier didn't hold the lock yet (or never would, if its download client couldn't be built). It's dropped before any relaunch, so the old version's start can take it. A running copy's notifier holds it for its whole life. While another process holds it, a start doesn't count an attempt, read the journal's steps or roll anything back. It goes on to fail on the taken port or index, as any second copy does. Otherwise that copy's failed start could roll back a healthy update, mark it `failed`, and restore a snapshot over writes made since.

## Verifying
- **The zip** is downloaded as the MSI is (`download.rs`, checked against the pin as it arrives). It's then hashed again and extracted **from one handle**, so the bytes checked are the bytes unpacked. On Windows that handle shares read and delete but not write. Extraction is `lodestar-companions`' bounded extractor (already a dependency: no `Cargo.toml` change). It requires `lodestar-<version>-x86_64-windows-portable/lodestar.exe`, the layout `build-portable.ps1` writes. Only `lodestar.exe` is taken; the launcher and README stay as they were unpacked.
- **`next.exe` is hashed again before the running program is moved aside,** through a handle that lets nobody write to it until both renames are done (runner; review of 7f651d0, N-b). The renames themselves go by path (std can't rename through a handle, and `unsafe` is forbidden). That handle shares delete, so `lodestar.exe` is hashed once more after the move, and a mismatch takes it out again and puts the old program back (self-review I5). The old program is held and rechecked the same way whenever it's moved back.
- **The new `lodestar.exe` keeps `bin`'s ACL** (moved, not copied): this user, SYSTEM and Administrators. Other accounts on the machine that could run the old one can't run the new one. That's the private folder's purpose, and other users have no business running someone else's portable copy.

## `<data>\bin` is private (PK-win-upd-1 self-review, #630 security review)
- **Created private:** at every start, before the notifier first opens it, a missing `bin` is created with a protected DACL for this user, SYSTEM and Administrators. It goes through `windows::acl`'s PowerShell create, not `integrations::secret::restrict_dir_acl`, whose `icacls` inherits the relaunch token. Without this user's SID it isn't created (the DACL would lock the user out).
- **Checked before anything is written or run:** at a start with a journal (above), and Install answers `bin_not_private` unless `bin` passes `windows::acl::log_folder`'s rule (owner and every entry this user, SYSTEM or Administrators; inherited entries allowed). It's never repaired. A folder found private is remembered for the run, so `/updates` doesn't start PowerShell on every poll; one that isn't is checked again each time.
  - A `bin` that an earlier version created with the inherited ACL passes when the folder was unpacked under the user's profile (which inherits only those three). Under a shared folder such as `C:\Lodestar` (where Authenticated Users can write) it's refused. The user can stop Lodestar and delete `data\bin` (it holds only update state: the skip list, the pause, `trust.json`), and the next start creates it private.
- **The relaunch token stays out of every tool the updater runs** (PK-win-restart review): the ACL check's and create's PowerShell and `whoami` come from `windows::system32_command`, which removes it (now tested). Only the relaunched copy gets it, by design.

## The rollback's store
- **Only in the old version, before anything opens the store** (runner): the failed version's earliest pre-migration snapshot (one not there before the install), renamed over the store, its `-wal`, `-shm` and `-journal` removed first. It's chosen by name, as in PK-win-upd-3.
  - **Chosen once and recorded** (`restore` in the journal: the name and SHA-256, or "none"), before anything is removed. A repeat after a crash restores that one only; if it's gone, the step is done only when the store is it (self-review B1). Without the record, a crash after the rename would have restored the next snapshot along over the good store.
  - **Refused:** a snapshot that changed since it was chosen, one with its own `-wal` or `-journal` beside it (it was mid-write), or one that isn't a regular file right before the rename.
  - **With no such snapshot,** the failed version took none and the store is kept. The old version's own open refuses a newer schema, so a store migrated without a snapshot is never guessed at.
  - **A restore that fails starts neither version** (§12.2): `serve` exits with a console message naming the data folder, and the journal stays for the next start.
- **The failed version is marked `failed` in `skipped`,** through `check::add_skip` (PK-win-upd-2's trim: the oldest `user` skips go first, never a `failed` one). A version that never started (the old one came back first) isn't marked.

## The relaunch (PK-win-restart, changed)
- **`windows::relaunch` records `current_exe()` once, first thing in the hook, and starts the successor from that path** (runner, item 2), so after the running file is renamed aside the successor is still `<folder>\lodestar.exe`. A unit test pins it.
- **Installing then restarting:** after the new program is in place, the run prepares Restart now (it starts the successor from `lodestar.exe`) and requests it. If the successor can't be started, the old program goes back and the journal goes (`restart_unavailable`), and this run keeps serving.

## Logging
- Existing `update.*` events only: `update.install_failed` (codes `verify_failed`, `zip_refused`, `swap_failed`, `bin_not_private`, …, and `rolled_back`, `store_not_restored`, `skip_unsaved`), `update.probation_failed` (the failing check, `attempts`, `not_started`, `start`) and `update.probation_passed`. A dedicated `update.rolled_back` event would need `log_events.rs` and the catalogue docs; it's left for PK-guide-3's pass over the Windows update texts.

## CLI commands during a rollback (self-review I1; runner, approving `cli/util.rs`)
- **Windows only** (runner review I2): on Unix the CLI never reads the portable journal, so it never opens `<data>/bin` through `Bin`, whose owner check would refuse, or chmod, a folder another user owns. A test on Unix pins it.
- **The commands that open the store** (`backup`, `vacuum`, `reindex`, `stats`) **refuse while `portable.json` is at `rolling_back`**, as they do for the MSI's `rollback.json`, which is checked unchanged. The journal is read with its own parser, capped, as untrusted input. One that exists but can't be read refuses too (fail closed), with a message that says to start Lodestar once and, if it stays, how to clear a damaged file. A missing one doesn't refuse.
- **`serve` checks only the MSI's marker** (`refuse_during_helper_rollback`): it finishes the portable rollback itself, before it opens the store, so refusing there would leave the rollback unfinishable.

## Not done here
- **`new_sha256` hashes `next.exe` after extraction** (runner review N2, left as it is): the extractor writes the file it names, from the zip that was verified through the same handle, into the private `bin`. Hashing the stream instead would need a hook in `lodestar-companions`' extractor. Every move after that is checked against this hash.
- **A manual unpack during probation** (N4, left as it is): someone who unzips a release over the folder while the journal is at `rolling_back` replaces `lodestar.exe` with a program that matches neither recorded hash. The journal then stays, nothing is moved, and Install answers `update_in_progress` until `data\bin\portable.json` is deleted with Lodestar stopped. Recovering by itself would mean trusting an unrecorded program.
- **`history.json` and the index folder** (§12.2's rollback steps): as on the MSI path (PK-win-upd-3), the portable rollback writes no history entry and doesn't touch the index folder. The Windows updater has no install history yet (`clear_history` is a no-op there).

## Tests
- `update::windows::portable` (every OS, with a fake system and a hand-built zip): the install and each failure point (extracted, aside, between, recorded) leaving the old program in place; a tampered `next.exe` refused before anything moves (and, on Windows, a write refused while it's held); a rollback that checks the old program before moving the new one out; a second copy during probation; the CLI never touching `bin` on Unix; both renames failing; a journal in a shared `bin`; a crash after the side files go and after the snapshot's rename; a changed, mid-write or missing snapshot; refusals; three starts then a rollback; the store restored only from the failed version's snapshot; a crash after each step; hostile and corrupt journals; no relaunch loop; the 5-minute window on a fake clock.
- `update::windows::check`: the portable build's Install offered only with a private `bin`, and the zip handed to its steps.
- `windows::tests`: the successor path recorded at start; the relaunch token removed from system tools (Windows).
- `tests/update_windows_portable.rs` (Windows CI): a rollback finished by the real binary before it opens the store; a new `bin` created with a protected DACL; the running program renamed aside and back.
