# M8-THEME decisions

The nightly all-themes run opens or updates one tracking issue when it fails, and keeps a run summary. Brief: runner, 2026-11-11 (`runner/slices.yaml` M8-THEME; spec §10.17, §17).

- **A separate job holds the write token.** `all-themes` runs `npm ci` and the Playwright specs, so it keeps the workflow's read-only `contents: read` and never gets `issues: write`. The new `all-themes-issue` job (`needs: all-themes`) has job-level `permissions: { issues: write, contents: read }`, no container, no checkout and no npm. No other job in the workflow gets `issues: write`.
- **The summary is data, not code.** `all-themes` writes `playwright-json/results.json` with Playwright's JSON reporter (`--reporter=list,html,json`, with `PLAYWRIGHT_HTML_OPEN=never` so the html reporter doesn't try to open a server), then a `Run summary` step (every run, `if: always()`) turns it into counts (passed, failed, flaky, skipped) and up to 25 failing spec titles. It appends that to `$GITHUB_STEP_SUMMARY` and uploads `all-themes-summary` (`summary.json` and `summary.md`, 30 days, `if: always()`). The full report stays failure-only, as before.
- **The issue job treats that artifact as untrusted** (the test code that produced it ran in the other job). It reads `summary.json` with `jq`, keeps only numbers and printable ASCII titles of at most 200 characters (no backticks, at-signs, angle brackets or pipes), writes the comment to a file and passes it with `gh issue comment|create --body-file`. Nothing from the artifact reaches a shell command line or a `${{ }}` expression; the only expressions in the job are GitHub's own values (`github.token`, repository, server URL, run id, ref name, default branch, SHA, `runner.temp` and the `needs` result), passed through `env:` or used in `with:` and `if:`. The failing titles go in a fenced block (a title can't contain a backtick, so it can't close the fence).
- **One issue, fixed label `nightly-all-themes`** (created with `gh label create … || true`). On `failure`: the lowest-numbered open issue with the label gets a comment (date in UTC, run URL, counts, failing titles); if there is none, one is created with that label. The job has its own concurrency group, so two runs can't both create it.
- **Close on pass.** On `success`, an open tracking issue gets a "passed on <run URL>" comment with the ref, SHA and counts, and is closed as completed only when the run was on the default branch (a manual run on another branch says nothing about whether the default branch is fixed). Comments always name the ref and SHA.
- **Fail-soft summary:** a summary of an unexpected shape produces fallback text instead of failing the job, and a report with errors outside the tests (a web server that didn't start) says so rather than reading as all zeros. `cancelled` and `skipped` do nothing (a `workflow_dispatch` that regenerates snapshots skips `all-themes`).
- **Not part of `ci-ok`.** `all-themes` is not a pull-request job, so neither is the issue job; `e2e-ok` is unchanged.
- **How it was checked** (a dispatch isn't possible from a session): `actionlint` on the workflow (its one finding, SC2155 in the Lighthouse step, is on `main` too); the `Run summary` script run against a fake Playwright JSON containing hostile titles (backticks, an `@` mention, `$(...)`); and the issue script run with `gh` stubbed for failure with and without an open issue, success with and without one, and cancelled, confirming the exact `gh` calls, the body file, and that nothing in a title was executed.
