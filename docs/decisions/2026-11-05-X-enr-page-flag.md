# X-enr-page-flag decisions

Runner brief, 2026-11-05T20:25Z. The enrichment parsers in `crates/sources-feeds` (ENR-2b's `tpdb`, ENR-3's `stashdb`) now report the shape of the answer they read, and the ENR-4 and ENR-5 plugins decide match, miss or error on those reports alone. This removes the HOLD precondition both plugins carried (the parser flag); the other HOLD items (the owner's Q2 terms check, host wiring, StashDB's recorded fixtures) stay. It supersedes the "Accepted gap" sentence in `2026-11-05-ENR-4.md` and the `shape` description and "stopgap" sentence in `2026-11-05-ENR-5.md`.

- **One reader.** Before this, each plugin re-read the raw body to tell a real miss from an error object (`tpdb`'s hand-written byte scanner `data_start`; `stashdb`'s second, typed serde read `shape`). Two readers can disagree, and the #503 and #506 reviews found where they did (`findScene` taken as the match, duplicate keys read as a miss, `errors` after an early stop). Both second readers are gone; there's one bounded reader per answer and the plugin reads its `Page`.
- **What `tpdb::Page` reports:** `data`, the kind of the root's first `data` key (`List`, `Object`, `Null`, `Other` or `Absent`); `data_repeated`, a second `data` (reported, never read: the first wins, the parser's house rule); `others`, the count of root keys other than `data` and `meta` (a real page has `links`; an error object has `message`); `trailing`, bytes after the root value.
- **What `stashdb::Page` reports:** `search`, the kind of the first `data.searchScene`; `find`, a `findScene` key in `data` with any value, `null` included; `errors`, now summed over every root `errors` key, before or after `data` and in a repeat of the key (a repeat mustn't hide one); `repeated`, any key appearing twice in the root or in `data`, whatever the key (the parser already spoiled a scene on a repeated key; this extends that to the envelope); `trailing`. As in a scene, the first of a repeated envelope key is the one read, so a `searchScene: null` followed by a `searchScene` list no longer reads the list, and a `findScene: null` followed by a scene no longer reads the scene.
- **Envelope keys are compared unescaped** (`"data"` is `data`), in both parsers, for the root, `meta` and `data` keys. JSON names are equal after unescaping, and a raw comparison would let an escaped repeat hide from the repeat check. Keys inside a match or scene are still compared as written, as before; a key that doesn't decode (a lone surrogate) stays as written and so can't equal a known name.
- **Past the item cap the parser reads on.** Previously `Stop::Items` ended the read, so nothing after the cap (a later `errors`, a repeated key, a cut, trailing bytes) was seen; that's why the plugins needed a second reader. Now items past `max_items` are read past without being decoded (bounded by the byte, depth and value caps, which are unchanged), `stop` records `Items`, and the rest of the document is read. A structural fault after the cap (`Malformed`, `Depth`, `Elements`) replaces `Items` as the stop, so `Some(Stop::Items)` now means "read to its end, only the item cap reached". A byte or UTF-8 stop from before the read stays first, as before. For a well-formed answer the same items are kept and skipped and the same stop is reported. What changes is only what's now seen after the cap: ThePornDB's `meta.total` when `meta` follows a `data` over the cap, StashDB's `errors` after the cap, and a page over the cap is read to its end (bounded as above) rather than left there. Every existing property test and cap test passes unchanged.
- **`trailing` implies a stop:** `Malformed`, or the byte or UTF-8 stop that came first (the fuzz target found the second case: a body cut at a bad UTF-8 byte right after a complete root value).
- **The plugins' rules (same as before, now on the flags).** Both: a match only as the service's top result (`max_items: 1`, so the one kept item is the first); a miss only on an empty list (or, for ThePornDB, `data: null`); an error on everything else. The answer must be whole: stop `None` or `Items`, no trailing bytes, no skipped item.
  - **ThePornDB** also needs one `data` key (`data_repeated` is an error) and a `data` that is a list or object for a match, a list or `null` for a miss. `others` isn't used: a real search page has `links` and `meta`, and an object with no `data` is already an error.
  - **StashDB** also needs `search == List`, no `find`, no `repeated` and `errors == 0`.
- **Tightened for ThePornDB, on purpose.** The old plugin took the first match even when the body was cut after it, had trailing bytes, had a structural fault after it, or repeated `data`; and took a miss when the first of two `data` keys was empty. Each is now "not understood", as StashDB already was. The brief's rule is "an error on everything else", and a body that isn't one whole document isn't understood. No existing test expected otherwise.
- **A repeated field inside the top item differs between the two, on purpose.** ThePornDB's parser keeps ENR-2b's house rule (the first value of a field is used, the repeat read past), StashDB's keeps ENR-3's (a repeat spoils the scene, so its answer is an error). Each is one reader, so neither can be read two ways; changing ENR-2b's item rule wasn't in this brief. A test pins ThePornDB's behaviour.
- **Narrowed for StashDB, on purpose.** `shape` deserialised every `searchScene` entry as an object with a string `id`, so a malformed second entry was an error. The parser doesn't decode entries past the cap, so now a second entry is checked only for being valid JSON within the caps. Only the top result is ever used (`limit: 1` is asked), so a second entry's fields can't reach the section; a cut or broken second entry is still an error. Tests on both sides pin this.
- **Tests.** `crates/sources-feeds/tests/{tpdb,stashdb}.rs`: each flag per kind and position, escaped and repeated keys, trailing bytes, reading past the item cap (a later `errors`, `findScene`, repeat, cut, fault and depth stop), and the shared `check` helper now asserts the flags agree with what was kept (so the mutated-corpus tests run those checks too). Three existing assertions there compared a whole `Page` and now name the new fields. `crates/sources-plugins/tests/{tpdb,stashdb}.rs` are unchanged apart from added tests with the missing probes: `findScene` variants (any value, before or after, repeated, escaped), duplicate keys at the root, in `data` and in the top item, escaped keys (built at run time, so no editor or tool decodes them), `errors` after the first item, trailing garbage, and a body cut after the first item.
- **Fuzz.** `fuzz/fuzz_targets/{tpdb,stashdb}.rs` also assert the flags agree with what was kept, and run the plugin's `parse_answer` on the same bytes: a miss or a match only from a whole answer with no repeat, no trailing bytes and no skipped item, and for StashDB never beside `errors`, a `findScene` or a non-list `searchScene`. Each target ran for 10 minutes.
- **Unchanged:** the byte, depth, value, array, text and performer caps (`LIMITS`, `ANSWER_LIMITS`); what a match keeps; the property tests.
