# OP-1 decisions (fleet control plane, dry-run)

The slice builds `.github/workflows/fleet.yml` and `infra/fleet/` in dry-run, as the plan's OP-1 row asks (`docs/plan/2026-11-08-cloud-operator.md` §2–§4). No cloud call runs anywhere. These are the choices the plan left open, or narrowed. None loosens an owner or security decision, or changes an owner-set number; the runner flags them to the owner (§2.19).

## Grammar and limits
- **`run <step> <vm>` takes a commit only for the steps that need one.**
  - **What:** a step whose `limits.yaml` entry has `takes_commit` (today only `start-block`) requires exactly one 40-hex commit; every other step refuses one.
  - **Why:** the plan's block starts "at a rules commit", and the brief requires the ancestor-of-`main` check on every commit argument. The commit is checked with `git merge-base --is-ancestor` against `origin/main`, and so is the fleet's pinned commit, before any `run`.
- **The committed step list** is `leak-test`, `start-block`, `arm-switch`, `outage-watcher`, `vm-status`, `copy-off` and `renew-vpn`, in `limits.yaml`. OP-3 and OP-2b may rename them in their own PRs. There is no WireGuard step: it runs only inside `deliver-pia` and `renew-vpn` (plan §3).
- **Refusals use a fixed list of reasons** (`command.REASONS`). Logs and result comments carry only those, never the comment text, so nothing a commenter writes reaches a log or a workflow command.
- **`limits.yaml` is written in JSON syntax** (still valid YAML; a test checks both parse the same), so the control plane needs nothing beyond the Python standard library. The values: one fleet, the `screen` preset (Main `g6-standard-4` at $0.072/h, Worker `g6-nanode-1` at $0.0075/h, the list rates in `main.tf`), 44 h lifetime, a $40 monthly fleet-compute cap, a 90-minute lock and the 15-minute grace before the emergency path.
- **The cap check** refuses `up` when this month's recorded spend plus the new fleet's full 44 h at list price would pass $40.

## Gates
- **`OPERATOR_STOP` fails closed.** Anything but exactly `false`, unset included, is a stop. `down`, the reaper and the owner's dispatched `down` are exempt.
- **The filter job holds no write token.** A refused `/fleet` command from the operator is answered by a separate `refuse` job with `pull-requests: write` only, after the filter job, which has `contents: read` and nothing else.
- **`act` repeats every gate in code before it touches the lock** (the channel PR, `created` only, the bot's numeric ID, the parser, the stop), so the lock is never taken for a comment that fails them. A test checks that a stranger's or an edited comment makes no lock call at all.
- **The owner's dispatched `down` gates on a new repository variable, `OWNER_USER_ID`** (the owner's numeric GitHub ID; today the same value as `RUNNER_USER_ID`). The plan names "the owner's user ID" but no variable for it. A separate name keeps the gate right if the runner ever gets its own identity. **Owner setup gains one variable** in step 2.7; the runner adds it to the setup list.
- **A re-run never acts.** GitHub re-runs a workflow with the original event and the original commit, so anyone with write access (the owner's login, and so every session) could replay an old `/fleet` command, which the plan's author table forbids. So:
  - the gates refuse any `GITHUB_RUN_ATTEMPT` but `1`;
  - `act` refuses unless the checked-out commit is `origin/main`'s head, so only `main`'s current code acts, and `up` pins that same commit.
- **A re-run of the owner's dispatched `down` keeps the owner's `actor_id`,** so anyone with write access could repeat it. It can only cause `down`, which the plan already accepts for any session posting as the owner.
- **Jobs that declare `cloud-fleet` also check `github.ref == 'refs/heads/main'`** in their `if:`, as defence in depth beside the environment's `main`-only rule.
- **Nothing but disabling the workflow stops the reaper** (plan §3): its `if:` checks only the schedule event and the ref.

## The lock and state
- **An expired lock is taken over with `If-Match` on its ETag,** so two runs can't both take it. An unreadable lock body counts as busy until the reaper pre-empts it.
- **Fencing also checks the lease:** a run whose own lock entry has expired can't write, even if nobody has taken the lock over.
- **A lost lock or an invalid `fleet.json` ends the job with a fixed result line and a failing exit,** never a traceback. A top-level guard in `fleet.py` turns any other exception into `internal error (<type>)`, because a traceback could carry private values in live mode.
- **The reaper decides again once it holds the lock,** because a `down` may have run while it waited.
- **Fencing covers more than rule-set writes.** Writing `fleet.json` at `up`, destroying at `down`, and the age reap all run through `FleetLock.fenced`, which checks the lock still holds this run's ID first. OP-2's rule-set writes use the same call.
- **Keys:** the lock is `locks/fleet.json` in the control bucket (inside the plan's `locks/fleet*` prefix); `fleet.json` is `fleet/fleet.json` in the state bucket. OP-2a's policies grant those exact keys.
- **Dry-run state doesn't persist.** Each run starts with an empty in-memory lock store and inventory. `S3Store` is written but refuses to construct unless live, and with `FLEET_LIVE=true` every acting subcommand exits with an error until OP-2 builds live mode.
- **The reaper releases its reaping marker after its dry-run `down`.** OP-2 replaces that with the plan's rule: clear the marker and the mismatch flag only once `down` has emptied the inventory. The firewall audit is a hook, `reaper.audit_not_built`, which OP-2 replaces.
- **The reaper waits up to 5 minutes** for a live holder (polling every 30 s) before it gives up until the next hour; the emergency cases don't wait.

## Comments and logs
- **The status comment is found by `github-actions[bot]`'s numeric ID and a marker,** and only its ID is used. `fleet.yml` still never reads state from a comment.
- **Every `act` result comment carries a fresh copy of the status.** The status comment is edited in place, so the reader helper (unedited comments only) drops it. The operator learns the fleet's state from the newest result comment instead. The reader's edit check stays strict, because the App can edit other authors' comments.
- **The reader helper trusts `github-actions[bot]` (41898282) as the control plane.** Residual: any workflow in this repo posts as that identity. A workflow that does so had to merge to `main` or run from a same-repo branch, which is the same trust as the owner's login (plan §4, "Residual risk").
- **Logs print fixed strings and counts only:** the age reap prints how many Linodes, never their IDs. The leak test runs every script `fleet.yml` invokes with marked fake secrets, and the in-process flows with marked fake addresses, fingerprints, firewall IDs and Linode IDs, and fails if a mark reaches stdout, stderr or a posted comment. It covers `operator-wake.yml` and `operator-injection.yml` too: once either exists, every script it runs needs a scenario there.

## Tests and CI
- **Test-only dependencies,** pinned exactly in `infra/fleet/requirements-test.txt`: `hypothesis` (the brief names it for the parser's property tests) and `PyYAML` (to read the workflows), with `sortedcontainers` for `hypothesis`, installed with `--no-deps --require-hashes`. The runner approved PyYAML as test-only (§2.33); workflows are read with `yaml.safe_load` only. The hashes are for CI's platform (CPython 3.13, manylinux x86_64; `hypothesis` 6.170.15 ships a compiled wheel), so other platforms install the same versions without `--require-hashes`.
- **The leak test's coverage check is strict:** every `run:` step in a covered workflow must be exactly one `python3 infra/<script>.py <sub>`, with a scenario registered, so a script can't be started some other way and slip past the leak test.
- **CI:** the `infra` job runs `infra/fleet/run_tests.sh`, and `ci_changes.py`'s `infra` filter also matches `fleet.yml`, `operator-wake.yml` and `operator-injection.yml`.
