# M6-cli: the clap CLI and filesystem detection

Slice M6-cli (`docs/build-plan.md` P3 [M]). These decisions extend architecture §7, §8, §11 and §12; they replace §16's "M1 implementation decisions: arguments are parsed by hand".

## Command line

- **clap 4.6.7** (derive; features `std`, `derive`, `help`, `usage`, `error-context` only, no colour or suggestions). `serve` stays the default, so a bare `lodestar` (Docker, Unraid, systemd) and every `LODESTAR_*` variable behave as before. `--config` is global, so it goes before or after the command as it did.
- **Exit status:** 0 done, 1 failed, 2 bad arguments (clap's), **3 refused for safety**, in which case nothing was changed. Scripts can tell "the server is running" from a real failure.
- `main.rs` only parses and dispatches; the maintenance commands live in `crates/lodestar/src/cli/`. The privilege drop (D-puid) belongs right after `cli::parse()`, before anything else, as it did after the hand-written parser.

## Guards shared by every maintenance command

- **B-update's journal:** `backup`, `rollback`, `vacuum`, `reindex` and `stats` all refuse while `<data>/bin/rollback.json` exists (§12.2: no process opens the store mid-rollback). The CLI never writes in `<data>/bin`.
- **The store lock is SQLite's own.** The offline commands (`rollback`, `vacuum`, `reindex`) open the store with `locking_mode = EXCLUSIVE` and switch it to `journal_mode = DELETE`. Leaving WAL needs an exclusive lock, so it fails at once while any process has the store open, the server's read-only connections included, on every platform; and the exclusive locking mode keeps the lock until the command closes it, so a server started meanwhile fails to open the store instead of racing it. Leaving WAL also checkpoints it, so a WAL left by a crash is folded in, not lost. No lock file, no new dependency, and `serve` needed no change. The store goes back to WAL when the command ends (and `Store::open` sets WAL on every open anyway).
- **Two `serve` instances are kept apart only by the search index's lock** (`index/.lock`, `Error::Locked`), not by this store lock: `serve` doesn't take it. With search turned off, nothing stops a second server; that's a gap for B-update's `<data>/bin` lock to close.
- **Replacing the store is a rename** of a complete, checked file in the store's own folder, after the stale `-wal`, `-shm` and `-journal` are removed under the lock. On Unix the rename happens under the lock, which is then held 6 s more (longer than the store's 5 s busy timeout), so a process that opened the old file meanwhile gives up rather than writing to the unlinked file. Windows can't rename over an open file, so the lock is closed first; anyone opening the store in that moment makes the rename fail and the store stays as it was. The lock connection keeps `-journal` open (exclusive locking mode), which Windows can't delete while it's open, so there it's removed just after the close; its header is zeroed after each commit, so it's never hot either way.

## The commands

- **`backup [--to PATH]`** writes a new folder `lodestar-backup-<UTC time>` under `PATH` (default `<data>/backups`; it's created, canonicalised, and an existing backup folder is never written into). Its README and output give the restore steps, including `lodestar reindex` (the old index doesn't match a restored store and would show the wrong torrents) and signing out sessions and replacing API keys (a restored `auth.json` brings back revoked ones). It holds `lodestar.db` (`VACUUM INTO` on a read-only connection: one read transaction, consistent while the server writes, then `quick_check`ed), `config.toml` (the file the config was loaded from), `seal.key`, `auth.json` (admin password hash, sessions, API keys) and a `README.txt` with the restore steps. Folder `0700`, files `0600` on Unix. The search index isn't included, and the output says so.
  - **"Trust files" means `auth.json`, not `bin/trust.json`.** §12.2 keeps the update trust state out of every snapshot and backup, so that no restore can undo a key revocation; the architecture outranks the brief here. The README says so.
- **`rollback [SNAPSHOT] [--yes]`** lists `lodestar.pre-v<N>[.<k>].db` without an argument. With one (a listed file name, or `vN` when it's unique; never a path), it locks the store, checks the snapshot (`quick_check`, schema version, torrent count), shows what will be lost and asks for "yes" unless `--yes`. Without a terminal and without `--yes` it refuses. Then: the current store is kept as `lodestar.before-rollback-<time>.db` (`VACUUM INTO`), the search index root is renamed to `index.before-rollback-<time>` (its documents and watermarks follow the newer store, and ids reused after the restore would show other torrents' data), and a copy of the snapshot is renamed into place. The snapshot itself is kept. It tells you to start the release that used the restored schema, since this one would migrate again.
  - This is the manual rollback of §12.2 for stores, without B-update's journal: it never touches `<data>/bin`, and B-update's `Roll back` keeps its own journaled path. When B-update lands, `lodestar rollback` for a whole update (binary + store) should go through its journal.
- **`vacuum`** is `VACUUM INTO` a temporary file beside the store, checked, then renamed over it, instead of a plain `VACUUM`. Same free space (one more copy), but built on the store's disk rather than the system temporary folder, which in a container is the image layer (on Unraid, `docker.img`). Page size and incremental auto-vacuum carry over. It reports the size before (file + WAL) and after.
- **`reindex`** with the server stopped renames this build's index directory (and any `.building` one) to `….trash`. At the next start `Serving::open_or_rebuild` finds no index for this version and builds one from the store, and its sweep deletes the trash. With the server running it refuses with exit 3 and says to stop it first: **the API has no rebuild endpoint yet** (named in the PR as a missing public API). The blue/green rebuild with the old index serving (§8) also needs a public "rebuild this version" call in `crates/search`; the trash rename is what's possible without editing it.
- **`stats [--json]`** reads only: a read-only store connection (schema version, torrents, file and WAL size, free pages), the index root's directories with their sizes and state (`ready`, `building`, `missing`), snapshots, the filesystem report, and whether a server answers `/healthz`.

## Filesystem detection (`fsdetect.rs`)

- **Linux reads `/proc/self/mountinfo` instead of calling `statfs`:** the workspace forbids `unsafe` and there's no `libc`/`rustix` dependency. The mount table names the source's type for Docker bind mounts too, so a container's `/data` mapped from `/mnt/user/appdata` shows as `fuse.shfs`. The longest mount point containing the canonical data path wins.
- **Kinds:** `fuse.shfs` (or a host path under `/mnt/user` or `/mnt/user0`) is Unraid's user share; `fuse`, `fuseblk` and `fuse.*` are FUSE, except network ones mounted through it (`sshfs`, `rclone`, `s3fs`, `davfs`, `glusterfs`); `nfs`, `nfs4`, `cifs`, `smb3`, `smbfs`, `9p`, `ceph`, `afs` and similar are network filesystems.
- **Unraid 6.12+ exclusive shares** (a share kept on one pool is bind-mounted at `/mnt/user/<share>`, bypassing shfs): on the host, a path under `/mnt/user` counts as the user share only when its mount isn't itself under `/mnt/user`, so an exclusive share isn't flagged. A host whose mount table doesn't show that bind mount would still get the warning, a false positive that only costs a log line. Inside the container, where Lodestar normally runs, the mount's type decides.
- **Windows** recognises shares by the canonical path (`\\server\share`, `\\?\UNC\…`; a mapped drive letter canonicalises to the UNC form). Other platforms report `unknown`.
- `fsdetect::detect` and `FsReport::warning` are public for `/stats` and the wizard (wiring is B14's or later); `serve` logs the warning at start, with the safe alternative (a pool path such as `/mnt/cache/appdata/lodestar`; a local disk, with only backups on the share).

## PUID/PGID (after D-puid)

- **Every command that touches the data folder drops root first** (`privdrop::Scope::DataDir`): `serve`, `import-bitmagnet`, `backup`, `rollback`, `vacuum` and `reindex`. None needs root, and running as PUID/PGID means a backup, a kept copy, a restored or compacted store and a trashed index are never root-owned. A `backup --to` folder must therefore be writable by PUID/PGID.
- **`stats` and `healthcheck` drop without preparing the folder** (`ProcessOnly`): they only read, so they never take ownership of anything.
- **`lists`** prints a built-in table and touches nothing, so it runs as started.
- The maintenance commands log the drop's report once the config (and so the log filter) is loaded, as `serve` does.
