# WK-10d decisions (worker runtime hardening)

The fourth of WK-10's PRs (runner, 2026-11-08T01:54Z, a §2.26 call): the follow-ups from #592's, #599's and #601's reviews. Politeness is WK-10e (runner, 2026-11-08T02:27Z). The drain fencing is its own slice, X-worker-drain-fence (runner, 2026-11-08T04:52Z).

## Sealing (#599's delta review)
- **An install ends a sealing outage at once.** It used to end only at the next result or find that looked. Now the install itself calls `sealing_down`, which clears `unsealable_since` when the new key covers now.
- **A result past its wait is released without pausing the pool.** It used to pause the pool even with no time left, so a backlog behind it waited on a pause that bought nothing.
- **Finds sifted before an outage aren't claimed after it starts.** The claims task checks `sealing_down` again before each batch, and drops the batch as `sift` would (`Counts::held_back`).
- The `unsealable_since` doc comment now lists everything that clears it.
- The late-snapshot test now checks the pool pauses while the result waits, resumes after the install, and that the outage is over.

## The pool's pause
- **The pool pauses before the DHT.** On a lost session the pool is told to pause first. The DHT pauses once the pool has been told, waiting at most a second. Before, lookups queued at an already-paused DHT finished empty, and each cost a key an attempt (#601's self-review).
- **On a reconnect the pool waits for the new session's first `Assign`**, as the DHT does, since that `Assign` may re-plan the worker.
- **No caller waits on the pool to decide** (#601's review, moved here). `refresh_pause` only records the wanted pause, working it out from the state under the watch's write lock. One task per stage run (`apply_pause`) tells the pool the latest value, in order. Before, the decision held a lock across `set_paused`, a send on the pool's bounded command channel, so every caller could block behind a slow pool.

## `Assign`
- **`fetch` or `prepare` turned off pauses the pool and claims nothing; turned on again, both resume.** A worker can't send results it didn't prepare, so either flag off means no fetching. The stages aren't stopped, since they couldn't be started again without a restart. The planner sets both on for every worker today (WK-5).
- **A fresh session's first `Assign` applying a lower revision** has its test now.

## Supervision
- **A stage task that ends by itself is noticed.** A watcher looks every second: a pool or prepare task that finished while the runtime wasn't stopping it has failed (a panic, or a bug that ended its loop). That's logged once (`worker.stage_failed`), and `Runtime::failed` completes. `lodestar worker` then stops with an error, so Docker or the service manager starts it again. The coordinator re-grants the keys it held when their leases end.
- **Why stop, not restart the stages in place:** the outbound queue's sender and the pool's queue go into the stages when they start, and a dead stage's copies can't be recovered. A process restart gives a clean worker, and it can't seal until a fresh snapshot arrives anyway (WK-8).

## Bounds
- **Claims stop at the pool's room.** The pool's cap (the budget's, from `Assign`) less the leases held, so the leases held never pass the cap. That bounds the queue into the pool and the losses queued, both by the cap, as WK-7 assumed. Keys over it are dropped and found again (`Counts::held_back`).
- **The snapshot acknowledgement and `Accepted` queues are bounded** (1,024 and 4,096), filled with `try_send`. A lost acknowledgement stalls that transfer, which the coordinator starts over. A lost `Accepted` leaves its batch to be sent again and answered again.
- **The flush path** now counts the batches it sends in `Counts::sent`, once each. On a drain it also resends batches refused for now, rather than leaving them for the next 5 s retry tick (the drain may not last that long).

## Snapshots
- **A snapshot that arrives whole but doesn't decode is logged** (`worker.snapshot_failed`, with its kind). Its last chunk was acknowledged, so the coordinator counts it delivered, and the worker keeps the one it has until the next version. **It also asks for a fresh session**, which starts every snapshot over (WK-10a), through the debounced path below.
- **The expired wire key is dropped** (#599's first review). `Judge` keeps the installed key as `Option<WireKey>`. The first judgment that finds `now` past the key's day drops it, which overwrites it (`WireKey`'s `Drop`), instead of keeping it until the next snapshot. A clock that goes back after that doesn't bring the key back: a fresh snapshot is needed.

## Fresh sessions (runner-approved, 2026-11-08T04:52Z)
- **A new public address asks for a fresh session**, because the coordinator learns a worker's address only from `Hello` (WK-5). Every stats tick compares the DHT's voted address with the one the last `Hello` carried. A different, public one asks the session to reconnect.
- **Debounced:** at most one ask per `RECONNECT_DEBOUNCE` (10 minutes). An address that flaps between votes can't cause a reconnect storm; asks held back are counted.
- **The session's side:** `Work::reconnects` (a default method; WK-2's idle runtime returns none) gives a counter. A bump ends the session, which connects again at once with no back-off and a fresh `Hello`. An ask made before the session doesn't end it, and none is taken while draining.

## The coordinator's address (runner-approved, 2026-11-08T04:52Z)
- **`set_coordinator_ips` from the coordinator DHT's vote.** Every 60 s the tick reads the coordinator DHT node's snapshot, waiting at most 2 s. A public voted address goes to the planner, which ignores an unchanged set (WK-5: without one, every plan treats the fleet as one address). Only public addresses enter it, with the same filter as a worker's `Hello`: never loopback, private, link-local, CGNAT or unspecified, and a v4-mapped address counts as its v4. A missing vote changes nothing.
- **The coordinator's own share of the resulting replan** (its DHT's shard, its pool's politeness) is WK-10e's.

## Saved pauses on a new server (runner-approved, 2026-11-08T04:52Z)
- **A new cluster server is seeded with the saved pauses before it serves anyone.** It reads them from WK-14's rows (`workers.prefs.<id>`) and parses them with `ops::Saved`. This closes WK-14's window, where a paused worker that reconnected at once could be granted keys before `Workers` re-applied its pause. A row that doesn't read pauses nobody here; `Workers` still applies its own copy afterwards, as before.

## ResetOnPanic (#592's review, runner-approved)
- **Armed until the rebuild finishes.** Its reset used to run whenever the thread was panicking. Now an `armed` flag is cleared once the scan returns, and any other way out resets the rebuild's state: a panic in the sizing, the allocation or the scan above all. The normal path clears the state itself under its own locks. The new test panics in the scan, then checks that the old filter stays, the flags are clear, and the next rebuild runs.

## #601's delta notes
- **`Drop` sends `Stop` before closing the DHT's channel,** so a `Run` the task hadn't seen yet can't start a node during the teardown.
- **A streak of failed DHT starts ends when no node is wanted,** and a changed error warns again within a streak.
- **The save test now catches a stop path that stops closing the channel.** It checks both paths end well inside `stopped`'s 11 s, and the drop case holds the shared state across the drop, as an install on a blocking thread would. With `close_dht` removed from either path, the test fails at about 11 s.

## Floor drops from workers (the runner's (b′), 2026-11-08T05:19Z; flagged to the owner)
- **A worker's floor drop leaves a permanent tombstone, as a local one does.** The coordinator's sink (`serve.rs`'s `Sink::outcomes`) takes each `Lost(Blocked)` under the holder's current token. The key is written as a `worker-floor:<id>` tombstone through #604's `Store::tombstone_from_worker`, so it's never claimed, fetched or stored again. `RemoteSink::outcomes` (`crates/pipeline`) is untouched.
- **Worker-floor rows are floor holds everywhere except WK-13's purge-by-worker** (#604 and its decisions file, `2026-11-08-WK-10d-store.md`).
- **Refused everywhere, as soon as the sink sees it** (#607's security review). A report goes, on the sink's path (short locks, nothing that waits), into an in-memory map *and* the built-in worker's `HeldSet`, which its intake, its parked keys and its commit all refuse. Before that review, only the claim check read the map, so until a restart the built-in worker could still claim, fetch and store a reported hash.
- **The claim check reads the map before the store** (#607's review). `flush` removes a report from the map only after its row is committed, so a key the map no longer holds is in the store by the time the store is read. Read the other way round, a claim could miss both. The check also **fails closed**: a `held_among` read error refuses the claim. And it consults the floor's hash lists (`blocked_hash`), as the built-in intake does.
- **Never dropped within a worker's budget,** and written promptly (runner, 2026-11-08T06:01Z). A report wakes the writer at once, so its row is normally in within a second. A burst is written in batches of 1,024. A failed write keeps the report, logs once per streak (`cluster.floor_report_failed`) and tries again after 5 s.
- **A per-worker budget and a cap** (#607's security review; the numbers are the runner's call, proposed here). A compromised worker could claim 512 arbitrary hashes a batch and report each one `Lost(Blocked)`, again and again, so the leases a worker holds don't bound the reports.
  - **The budget:** each worker may report **100 floor drops per rolling hour**. An honest worker reports one rarely, since the hash lists refuse most floor keys before a claim and a CS-8a repost is rare.
  - **Over budget** (#607's delta review): the first report past it, in this order, **pauses the worker** in the server, **takes its leases back** (`LeaseAuthority::evict`, so its later reports are stale), logs once (`cluster.floor_reports_over_budget`, with the worker's id only), and then **saves the pause** through `Workers` (WK-14's row, under `edits`). So Workers shows it paused, a new server or a restart keeps it paused, and only an admin's resume ends it.
    - The save goes through a hook `Workers::open` registers on the `ClusterHandle` (a `Weak<Workers>`, so no cycle; runner-approved 2026-11-08T11:21Z). The save never comes first, and the pause and the eviction stand without it: with no hook registered yet (startup), `Workers` gone, or no runtime. A failed save (`PrefsFull` or a write error) logs `workers.pause_not_saved` (the worker's id and a code); the worker then stays paused until a restart.
    - That report and every later one over the budget are **dropped**: counted (`cluster_floor_reports_over_budget_total`), neither in the map nor in the held set. The worker is untrusted by then, and the floor still applies to whoever fetches the key next.
  - **The budget decides first, on its own:** whether the map has room never changes whether a report is over budget, or the first one over it. A report turned away by a full map uses up no budget slot. (Before the delta review, the first-over mark could be used up by a report the full map turned away, so the worker was never paused.)
  - **The cap:** the map holds at most **100,000 reports** (about 5 MB), and only reports within a budget are in it, so a worker over its budget can't fill it for everyone. Past the cap, a report is counted (`cluster_floor_reports_turned_away_total`) and nothing else. That only happens if writes keep failing for a long time. (Before the delta review, over-budget reports stayed in the map until a restart, so one worker could fill it and every honest report after that was turned away.)
  - **A revoked worker is forgotten** (`ClusterHandle::forget_floor_reports`, from `revoke_now`): its reports not written yet and its budget window. Its written tombstones stay until WK-13's purge-by-worker. The built-in worker's held set keeps the dropped keys until the next start, which refuses more, never less.
  - **The first report of a key keeps its worker.** With over-budget reports out of the map, every entry is written, so there's nothing to upgrade (the review's 1d).
- **Reports during a shutdown land** (#607's review). The writer has its own stop, fired only after the serve task has ended and the sessions are gone (`Cluster::shutdown` stops serving, then lets the writer finish). Before, the writer shared `run`'s stop and could flush once and end while sessions were still delivering reports.
- **Delete, then tombstone** (#607's review). The writer deletes any torrent stored under a reported hash (`Store::delete_torrents`, which tells the indexer) before writing the tombstone. A crash between the two then leaves only the crash window below, never a torrent stored and searchable under a hold. A key can be stored after its grant, by another worker's result or the built-in worker, which is why the delete is needed at all (#604's review, N8).
- **The crash window.** A coordinator crash before the write loses a pending report, which lives only in memory. The key can then be claimed again, but nothing unsafe follows: the next worker that fetches it judges it under the same floor and drops it before anything is sent or stored. That's `Judge::judge_at`'s `Dropped` path in `crates/pipeline/src/wire/filter_snapshot.rs`, tested by `a_hash_list_drop_never_goes_out`. The cost is one fetch more, and the report comes again.
- **A residual window between the report and the map** (#607's reviews, L3/NB1). The server ends the lease (`LeaseAuthority::report`) before the sink fills the map, and a claim of the same key from another worker can land in between and be granted. That costs one extra fetch, which the next worker's floor drops as above. Closing it needs a `LeaseAuthority::report` change in `crates/cluster`: record a `Blocked` loss there the way a commit is recorded, so a claim racing the sink is refused (a follow-up for the runner to log). So the report is refused *as soon as the sink sees it*, not "at once".
- **Why a map, not a bounded queue with a nack:** the server ends the lease before the sink sees the outcome, and `InboundSink::outcomes` has no way to refuse one. A nack would mean changing `crates/cluster`'s trait. The map needs no nack: the per-worker budget and the 100,000 cap (above) bound it, and nothing within a worker's budget is dropped.
- **A re-grant is checked as a claim is** (#607's review, item 6c; runner-approved 2026-11-08T09:30Z as a shared edit of `crates/cluster/src/server.rs`). Before, `regrant` sent waiting keys out with no store check, so a key stored or reported since its lease ended could go to another worker. Now, with a store check:
  - Under the fleet lock, the waiting keys are leased to their targets under new tokens (`regrant_pending`), so no claim or other re-grant can take them, and nothing is sent (the runner accepted reserving them rather than leaving them pending). The lock is released for the check (`StoredKeys::regrant_check`, on a blocking thread), then taken again.
  - **Cancelled, nothing stays reserved** (#607's delta review): a `revoke` or `revoke_worker` runs from an admin's request, whose future is dropped if the request goes away. A guard (`Reserved`) holds the reserved keys across the check and, dropped armed, requeues each one (`requeue` checks the token). It's disarmed once the answer is in; everything after that is synchronous.
  - **Every key is re-validated** under the lock: it's acted on only if its target still holds it under the same token. One that expired, was evicted or was granted again meanwhile is left alone.
  - **One answer per key** (`KeyCheck`, #607's delta review), each acted on under the target's token:
    - `Free`: it goes out, or waits again if the target has gone, drained or paused, or its queue is full.
    - `Stored`: the lease ends with **no loss**. Nothing was lost, and a LOST shouldn't be charged to a target that never had the key.
    - `Held` (a tombstone, a quarantine, a worker's floor report or the floor's hash lists): it **ends as lost, blocked**, as the target's own floor would have ended it.
    - `Unknown` (a read failed): that key alone waits for the next re-grant, so one key whose read keeps failing doesn't hold up the rest.
  - **Fails closed:** a check that dies or comes back short answers `Unknown` for every key: nothing is granted or ended. Either case counts in `check_failures` (`cluster_store_check_errors_total`). `StoredKeys::regrant_check` defaults to `stored` (`true` reads as `Stored`).
- **The claim check fails closed too** (#607's delta review). A check that dies or comes back short denies the whole batch as busy, and counts in `check_failures`. Before, it granted every key. `StoreCheck` answers `Unknown` for any failed read (`held_among` or `find`), which a claim refuses. Before, a failed `find` read as not stored.
  - The re-grants that ran under a held lock (a resume, an unpause, a sweep) can't wait for a check. With a store check they now send nothing, and the next tick (every heartbeat) re-grants. The ones on async paths (a tick, a revoke, a new session, a drain) run the checked re-grant after releasing the lock. Without a store check (tests, `ClusterServer::new(.., None)`), nothing changes.

## Releasing a worker's floor report (#604's review, N4)
- The review queue's Release on a hash a worker's floor report holds used to answer "not found", for a row the UI lists. It now answers `409 held_by_worker_floor`: the torrent was blocked by a worker under the locked floor, can't be released here, and removing that worker clears its blocks. That's `crates/api/src/filters.rs`, one more shared edit (the runner assigned N4 to this PR).

## The claim check refuses held keys (runner-approved, 2026-11-08T05:21Z)
- **A key that's tombstoned or quarantined is never granted to a worker.** `StoreCheck::stored` used to look only for stored torrents, so a key held here, a floor drop included, could be granted to a remote worker and fetched. Only the writer's commit refused it then. Held keys now count as stored for a claim (`held_among`), as the built-in worker's intake refuses them, and so do floor reports not yet written.

## The coordinator's tick (`serve.rs`)
- **`close` waits for the tick itself,** not only its watcher (#592's review). Aborting the watcher aborts the tick, which goes at its next await; `close` now waits for that, up to 10 s, before shutting the server down. Blocking work the tick started (a rebuild, an install) finishes by itself and finds the server gone. The test (`a_close_releases_the_server`) checks that nothing holds the server after a shutdown. It doesn't catch the wait's removal, since an aborted tick normally goes before `close` gets on.

## Tests that cover the midnight window
- The runtime tests that seal under today's key wait out the last minute before midnight UTC first. It's a condition with a 90 s deadline, not a fixed sleep. Serve's key test accepts either side of midnight.

## Memory

## After the merge: #607's last review notes (WK-10d-polish, runner, 2026-11-08T13:34Z)
