# WK-10d decisions (worker runtime hardening)

The fourth of WK-10's PRs (runner, 2026-11-08T01:54Z, a §2.26 call): the follow-ups from #592's, #599's and #601's reviews. Politeness is WK-10e (runner, 2026-11-08T02:27Z). The drain fencing is its own slice, X-worker-drain-fence (runner, 2026-11-08T04:52Z).

## Sealing (#599's delta review)
- **An install ends a sealing outage at once.** It used to end only at the next result or find that looked. Now the install itself calls `sealing_down`, which clears `unsealable_since` when the new key covers now.
- **A result past its wait is released without pausing the pool.** It used to pause the pool even with no time left, so a backlog behind it waited on a pause that bought nothing.
- **Finds sifted before an outage aren't claimed after it starts.** The claims task checks `sealing_down` again before each batch, and drops the batch as `sift` would (`Counts::held_back`).
- The `unsealable_since` doc comment now lists everything that clears it.
- The late-snapshot test now checks the pool pauses while the result waits, resumes after the install, and that the outage is over.

## The pool's pause
- **The pool pauses before the DHT.** On a lost session the pool is told to pause first. The DHT pauses once the pool has been told, waiting at most a second. Before, lookups queued at an already-paused DHT finished empty, and each cost a key an attempt (#601's self-review).
- **On a reconnect the pool waits for the new session's first `Assign`**, as the DHT does, since that `Assign` may re-plan the worker.
- **No caller waits on the pool to decide** (#601's review, moved here). `refresh_pause` only records the wanted pause, working it out from the state under the watch's write lock. One task per stage run (`apply_pause`) tells the pool the latest value, in order. Before, the decision held a lock across `set_paused`, a send on the pool's bounded command channel, so every caller could block behind a slow pool.

## `Assign`
- **`fetch` or `prepare` turned off pauses the pool and claims nothing; turned on again, both resume.** A worker can't send results it didn't prepare, so either flag off means no fetching. The stages aren't stopped, since they couldn't be started again without a restart. The planner sets both on for every worker today (WK-5).
- **A fresh session's first `Assign` applying a lower revision** has its test now.

## Supervision
- **A stage task that ends by itself is noticed.** A watcher looks every second: a pool or prepare task that finished while the runtime wasn't stopping it has failed (a panic, or a bug that ended its loop). That's logged once (`worker.stage_failed`), and `Runtime::failed` completes. `lodestar worker` then stops with an error, so Docker or the service manager starts it again. The coordinator re-grants the keys it held when their leases end.
- **Why stop, not restart the stages in place:** the outbound queue's sender and the pool's queue go into the stages when they start, and a dead stage's copies can't be recovered. A process restart gives a clean worker, and it can't seal until a fresh snapshot arrives anyway (WK-8).

## Bounds
- **Claims stop at the pool's room.** The pool's cap (the budget's, from `Assign`) less the leases held, so the leases held never pass the cap. That bounds the queue into the pool and the losses queued, both by the cap, as WK-7 assumed. Keys over it are dropped and found again (`Counts::held_back`).
- **The snapshot acknowledgement and `Accepted` queues are bounded** (1,024 and 4,096), filled with `try_send`. A lost acknowledgement stalls that transfer, which the coordinator starts over. A lost `Accepted` leaves its batch to be sent again and answered again.
- **The flush path** now counts the batches it sends in `Counts::sent`, once each. On a drain it also resends batches refused for now, rather than leaving them for the next 5 s retry tick (the drain may not last that long).

## Snapshots
- **A snapshot that arrives whole but doesn't decode is logged** (`worker.snapshot_failed`, with its kind). Its last chunk was acknowledged, so the coordinator counts it delivered, and the worker keeps the one it has until the next version. **It also asks for a fresh session**, which starts every snapshot over (WK-10a), through the debounced path below.
- **The expired wire key is dropped** (#599's first review). `Judge` keeps the installed key as `Option<WireKey>`. The first judgment that finds `now` past the key's day drops it, which overwrites it (`WireKey`'s `Drop`), instead of keeping it until the next snapshot. A clock that goes back after that doesn't bring the key back: a fresh snapshot is needed.

## Fresh sessions (runner-approved, 2026-11-08T04:52Z)
- **A new public address asks for a fresh session**, because the coordinator learns a worker's address only from `Hello` (WK-5). Every stats tick compares the DHT's voted address with the one the last `Hello` carried. A different, public one asks the session to reconnect.
- **Debounced:** at most one ask per `RECONNECT_DEBOUNCE` (10 minutes). An address that flaps between votes can't cause a reconnect storm; asks held back are counted.
- **The session's side:** `Work::reconnects` (a default method; WK-2's idle runtime returns none) gives a counter. A bump ends the session, which connects again at once with no back-off and a fresh `Hello`. An ask made before the session doesn't end it, and none is taken while draining.

## The coordinator's address (runner-approved, 2026-11-08T04:52Z)
- **`set_coordinator_ips` from the coordinator DHT's vote.** Every 60 s the tick reads the coordinator DHT node's snapshot, waiting at most 2 s. A public voted address goes to the planner, which ignores an unchanged set (WK-5: without one, every plan treats the fleet as one address). Only public addresses enter it, with the same filter as a worker's `Hello`: never loopback, private, link-local, CGNAT or unspecified, and a v4-mapped address counts as its v4. A missing vote changes nothing.
- **The coordinator's own share of the resulting replan** (its DHT's shard, its pool's politeness) is WK-10e's.

## Saved pauses on a new server (runner-approved, 2026-11-08T04:52Z)
- **A new cluster server is seeded with the saved pauses before it serves anyone.** It reads them from WK-14's rows (`workers.prefs.<id>`) and parses them with `ops::Saved`. This closes WK-14's window, where a paused worker that reconnected at once could be granted keys before `Workers` re-applied its pause. A row that doesn't read pauses nobody here; `Workers` still applies its own copy afterwards, as before.

## ResetOnPanic (#592's review, runner-approved)
- **Armed until the rebuild finishes.** Its reset used to run whenever the thread was panicking. Now an `armed` flag is cleared once the scan returns, and any other way out resets the rebuild's state: a panic in the sizing, the allocation or the scan above all. The normal path clears the state itself under its own locks. The new test panics in the scan, then checks that the old filter stays, the flags are clear, and the next rebuild runs.

## #601's delta notes
- **`Drop` sends `Stop` before closing the DHT's channel,** so a `Run` the task hadn't seen yet can't start a node during the teardown.
- **A streak of failed DHT starts ends when no node is wanted,** and a changed error warns again within a streak.
- **The save test now catches a stop path that stops closing the channel.** It checks both paths end well inside `stopped`'s 11 s, and the drop case holds the shared state across the drop, as an install on a blocking thread would. With `close_dht` removed from either path, the test fails at about 11 s.

## Floor drops from workers (the runner's (b′), 2026-11-08T05:19Z; flagged to the owner)
- **A worker's floor drop leaves a permanent tombstone, as a local one does.** The coordinator's sink (`serve.rs`'s `Sink::outcomes`) takes each `Lost(Blocked)` under the holder's current token. The key is written as a `worker-floor:<id>` tombstone through #604's `Store::tombstone_from_worker`, so it's never claimed, fetched or stored again. `RemoteSink::outcomes` (`crates/pipeline`) is untouched.
- **Worker-floor rows are floor holds everywhere except WK-13's purge-by-worker** (#604 and its decisions file, `2026-11-08-WK-10d-store.md`).
- **Never dropped, and refused at once.** A report goes into an in-memory map on the sink's path: a short lock, nothing that waits. The claim check reads that map as well as the store, so a re-claim is denied before the row lands. A writer task writes the map in batches of 1,024 on a blocking thread, and removes a report only once its row is in. A failed write keeps the report, logs once per streak (`cluster.floor_report_failed`), counts it, and tries again after 5 s. A shutdown writes what's left before the pipeline stops.
- **Why a map, not a bounded queue with a nack:** the server ends the lease before the sink sees the outcome, and `InboundSink::outcomes` has no way to refuse one. A nack would mean changing `crates/cluster`'s trait. The map needs no nack: it's bounded by the leases workers held, because the server passes on a loss only under the holder's current token, and nothing in it is dropped.

## The claim check refuses held keys (runner-approved, 2026-11-08T05:21Z)
- **A key that's tombstoned or quarantined is never granted to a worker.** `StoreCheck::stored` used to look only for stored torrents, so a key held here, a floor drop included, could be granted to a remote worker and fetched. Only the writer's commit refused it then. Held keys now count as stored for a claim (`held_among`), as the built-in worker's intake refuses them, and so do floor reports not yet written.

## The coordinator's tick (`serve.rs`)
- **`close` waits for the tick itself,** not only its watcher (#592's review). Aborting the watcher aborts the tick, which goes at its next await; `close` now waits for that, up to 10 s, before shutting the server down. Blocking work the tick started (a rebuild, an install) finishes by itself and finds the server gone. The test (`a_close_releases_the_server`) checks that nothing holds the server after a shutdown. It doesn't catch the wait's removal, since an aborted tick normally goes before `close` gets on.

## Tests that cover the midnight window
- The runtime tests that seal under today's key wait out the last minute before midnight UTC first. It's a condition with a 90 s deadline, not a fixed sleep. Serve's key test accepts either side of midnight.

## Memory
- Hello's memory comes from `system::info::memory_bytes` (#601's review), which now reads cgroup v1's limit as well as v2's. That change also reaches the system info page.
- **The encoded copy of the batches in flight** (up to 8 MiB more than the outbound budget) is counted in WK-10c's RSS breakdown, which is already within the 256 MB budget.
