# WK-10d decisions (worker runtime hardening)

The fourth of WK-10's PRs (runner, 2026-11-08T01:54Z, a §2.26 call): the follow-ups from #592's, #599's and #601's reviews. Politeness is WK-10e (runner, 2026-11-08T02:27Z). The drain fencing is proposed as its own slice.

## Sealing (#599's delta review)
- **An install ends a sealing outage at once.** It used to end only at the next result or find that looked. Now the install itself calls `sealing_down`, which clears `unsealable_since` when the new key covers now.
- **A result past its wait is released without pausing the pool.** It used to pause the pool even with no time left, so a backlog behind it waited on a pause that bought nothing.
- **Finds sifted before an outage aren't claimed after it starts.** The claims task checks `sealing_down` again before each batch, and drops the batch as `sift` would (`Counts::held_back`).
- The `unsealable_since` doc comment now lists everything that clears it.
- The late-snapshot test now checks the pool pauses while the result waits, resumes after the install, and that the outage is over.

## The pool's pause
- **The pool pauses before the DHT.** On a lost session the pool is told to pause first. The DHT pauses once the pool has been told, waiting at most a second. Before, lookups queued at an already-paused DHT finished empty, and each cost a key an attempt (#601's self-review).
- **On a reconnect the pool waits for the new session's first `Assign`**, as the DHT does, since that `Assign` may re-plan the worker.
- **No caller waits on the pool to decide** (#601's review, moved here). `refresh_pause` only records the wanted pause, working it out from the state under the watch's write lock. One task per stage run (`apply_pause`) tells the pool the latest value, in order. Before, the decision held a lock across `set_paused`, a send on the pool's bounded command channel, so every caller could block behind a slow pool.

## `Assign`
- **`fetch` or `prepare` turned off pauses the pool and claims nothing; turned on again, both resume.** A worker can't send results it didn't prepare, so either flag off means no fetching. The stages aren't stopped, since they couldn't be started again without a restart. The planner sets both on for every worker today (WK-5).
- **A fresh session's first `Assign` applying a lower revision** has its test now.

## Supervision
- **A stage task that ends by itself is noticed.** A watcher looks every second: a pool or prepare task that finished while the runtime wasn't stopping it has failed (a panic, or a bug that ended its loop). That's logged once (`worker.stage_failed`), and `Runtime::failed` completes. `lodestar worker` then stops with an error, so Docker or the service manager starts it again. The coordinator re-grants the keys it held when their leases end.
- **Why stop, not restart the stages in place:** the outbound queue's sender and the pool's queue go into the stages when they start, and a dead stage's copies can't be recovered. A process restart gives a clean worker, and it can't seal until a fresh snapshot arrives anyway (WK-8).

## Bounds
- **Claims stop at the pool's room.** The pool's cap (the budget's, from `Assign`) less the leases held, so the leases held never pass the cap. That bounds the queue into the pool and the losses queued, both by the cap, as WK-7 assumed. Keys over it are dropped and found again (`Counts::held_back`).
- **The snapshot acknowledgement and `Accepted` queues are bounded** (1,024 and 4,096), filled with `try_send`. A lost acknowledgement stalls that transfer, which the coordinator starts over. A lost `Accepted` leaves its batch to be sent again and answered again.
- **The flush path** now counts the batches it sends in `Counts::sent`, once each. On a drain it also resends batches refused for now, rather than leaving them for the next 5 s retry tick (the drain may not last that long).

## Snapshots
- **A snapshot that arrives whole but doesn't decode is logged** (`worker.snapshot_failed`, with its kind). Its last chunk was acknowledged, so the coordinator counts it delivered, and the worker keeps the one it has until the next version or a reconnect. Reconnecting on it waits on the session change below.

## The coordinator's tick (`serve.rs`)
- **`close` waits for the tick itself,** not only its watcher (#592's review). Aborting the watcher aborts the tick, which goes at its next await; `close` now waits for that, up to 10 s, before shutting the server down. Blocking work the tick started (a rebuild, an install) finishes by itself and finds the server gone. The test (`a_close_releases_the_server`) checks that nothing holds the server after a shutdown. It doesn't catch the wait's removal, since an aborted tick normally goes before `close` gets on.

## Tests that cover the midnight window
- The runtime tests that seal under today's key wait out the last minute before midnight UTC first. It's a condition with a 90 s deadline, not a fixed sleep. Serve's key test accepts either side of midnight.

## Memory
- Hello's memory comes from `system::info::memory_bytes` (#601's review), which now reads cgroup v1's limit as well as v2's. That change also reaches the system info page.
- **The encoded copy of the batches in flight** (up to 8 MiB more than the outbound budget) is counted in WK-10c's RSS breakdown, which is already within the 256 MB budget.
