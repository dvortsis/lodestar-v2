# M8-PERF-3 decisions

The 10M benchmark on the owner's dedicated runner (`bench-10m.yml`), the `runner-guard` check and the owner's setup page (`docs/operations/bench-runner.md`). It implements plan `2026-11-06-m8-hardening.md` §4.3 (M8-PERF-3) and §5 OQ1 with mitigations (a)–(d), not (e) (`docs/owner-decisions.md` §2.47: the plan row is the decision). Step 0's design was approved by the runner on 2026-11-28.

- **Triggers follow the plan row, a correction to the brief** (runner, 2026-11-28). The brief said `push` to `main`. The plan row says a weekly `schedule` on `main` plus `workflow_dispatch`, and it's the decision under §2.47. `main` takes dozens of merges a day and a run takes hours, so a push trigger would either never finish (cancelled runs) or keep the machine busy all the time. So: `schedule` Mondays 03:17Z (main), `push` to release lines, and `workflow_dispatch` with one boolean input, `smoke_only`. Never `pull_request`, `pull_request_target`, `workflow_run`, `issue_comment` or any other trigger a pull request or comment can start. A 10M regression is caught up to a week later, as OQ1's trade-off says. The 200k gates stay in `ci-ok`.
- **Release lines only, by the runner's decision (2026-11-28, a refinement of the plan row's `release/*`).** Origin holds 14 `release/*` branches, and 12 of them are session backport PR branches (`release/rc4-docs`, `release/v052-rc1`, …). A push to any of those would have queued a multi-hour run on the owner's machine. The push filter is now `release/v[0-9]+.[0-9]+` and `release/v[0-9]+.[0-9]+.[0-9]+` (the guard tests which names match). The job's `if:` splits by event: schedule on `main`, push on `release/v…`, dispatch on either. The ruleset on the setup page uses `release/v*.*` and `release/v*.*.*`, which need a dot like the filter does. GitHub's ruleset docs couldn't be fetched from the session (the host is outside its network), so the owner's ruleset screen confirms the match.
- **Mitigation (b), stated accurately.** Sessions push with the owner's login, and the owner is on the ruleset's bypass list, so the ruleset stops collaborators, not sessions. Mitigations (a), (c) and (d) cover sessions. The decision is unchanged; the setup page now says what (b) actually stops.
- **The registration token never reaches the job.** The setup page has the owner type it at a prompt inside the container, then `unset` it and `exec` the runner. A token on the command line or in `--env-file` would be readable by every job step (`/proc/1/cmdline`, `/proc/1/environ`) and could register a hostile runner (found by the self-review).
- **One label, no defaults.** The runner registers with `--ephemeral --no-default-labels --labels lodestar-bench-10m`, so `runs-on: self-hosted` (or `linux`, `x64`) can't reach it, and the workflow says `runs-on: lodestar-bench-10m` alone.
- **Nothing to steal in the job.** Top-level `permissions: {}`, `contents: read` on the job, no `secrets`, no `vars`, checkout with `persist-credentials: false`, actions pinned by SHA, and no rust-cache or `actions/cache`, so a job can't write a cache that `main` later reads. The ref `if:` on the job isn't a barrier (a branch can edit it out, OQ1). `concurrency: bench-10m` without cancellation, because there's one machine.
- **The dataset persists on its own disk; everything else is reset.** Each job runs in a fresh container (or VM) that is deleted after one job. Only the dataset disk, mounted at `/bench`, survives. It must be writable, because `dataset::scratch` writes `DIR/scratch` inside the dataset. When the bench refuses the folder for a changed key or store schema, the job empties it and rebuilds once. Any other refusal (a folder this tool didn't build, an unreadable manifest) stops the job, so it never deletes what it didn't make. **Residual risk, accepted and named on the setup page:** a hostile job could tamper with the dataset and so skew numbers. The disk holds no secrets, every open checks the key and that the index covers the corpus, and the owner can delete it to force a rebuild.
- **No root.** `search-bench` runs without `--drop-caches`, so cold start is reported as `page-cache-as-found`. Cold start is a reported row with no §3 number, and giving jobs root on the machine would be the larger risk.
- **Smoke step, then the four runs, then verdicts.** A 20,000-torrent dataset in the job's temporary folder proves the machine and both tools first; `ext:bench-runner` is a manual run on `main` that passes it. The full run is `bench/README.md`'s four commands (each tool, default and `--low-resource`). The step summary has one row per JSON report. The job fails on a `fail` verdict in a 10M report, or a missing or unreadable report. Smoke verdicts are shown, not gated: at 20,000 torrents `size-report`'s per-torrent size rows fail, because fixed costs aren't spread out (measured 2026-11-28; the build and smoke took about 8 minutes on a cloud container). `incomplete` passes, because rows stay `unavailable` until their features land; G-v1-10m judges the full reports. The reports are uploaded as `bench-10m-<sha>` and kept 90 days.
- **The guard's rules** (`.github/scripts/runner_guard.py`, on every push, every pull request and by hand). It's a detector, not a barrier (OQ1). It fails when:
  - a workflow other than `bench-10m.yml` names the label in any form or case, or a file elsewhere under `.github/` does (a script could print it into a matrix);
  - a job elsewhere could reach any self-hosted runner. That covers `runs-on` naming `self-hosted` or anything but a GitHub-hosted image, a `group:`/`labels:` mapping, or an expression other than `matrix.<key>` over a literal matrix of hosted images. The one dynamic matrix allowed is ci.yml's `test` job, `fromJSON(needs.changes.outputs.test_os)`, written by `ci_changes.py` (scanned like every file under `.github/`);
  - a job calls a reusable workflow from another repository;
  - `bench-10m.yml` breaks the rules above (triggers, push branches, inputs, permissions, secrets or vars, the ref `if:`, pinning, checkout credentials, environment, container or services).

  A file that doesn't parse fails. A test runs the guard over every workflow on `main` and requires it to pass.
- **The guard uses the hosted image's PyYAML** (`ubuntu-24.04`, pinned so that holds), and downloads nothing.
- **Runner registration is manual by default (refinement under §2.19, to flag to the owner).** Mitigation (a) says the machine holds no credentials. Starting each ephemeral runner by hand keeps it that way. Automatic restarts need a repository token with Administration write. The setup page offers that only as an option, says it's weaker, and says to keep the token outside the job's container (a VM is preferred). Scheduled runs wait in the queue until a runner is started; GitHub drops a job that has waited 24 hours.
- **`runner-guard` as a required check is the owner's choice.** Making it required in the `main` ruleset turns detection into a block on merging. The trade-off is one more check, about a minute, on every pull request (setup page, step 3). The guard doesn't edit `ci.yml` (X-ci-test-shard owns it) or join `ci-ok`.
