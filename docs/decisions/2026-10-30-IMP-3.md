# IMP-3 decisions: the Bitmagnet PostgreSQL adapter

The Bitmagnet adapter (the plan's "Bitmagnet PostgreSQL", `docs/plan/2026-10-29-magnetico-bitmagnet-migration.md` §5), hardened from the M-era importer. It builds on IMP-1's contracts (`docs/decisions/2026-10-30-IMP-1.md`) and follows IMP-2's pattern (`docs/decisions/2026-10-30-IMP-2.md`) section by section. Where Bitmagnet needs a different answer, the entry says so. It redefines nothing in IMP-1: records go through `Store::commit_import_batch` as `ImportRecord::{Torrent, Candidate, Invalid}`.

Code: `crates/sources-importers/src/bitmagnet.rs` (the adapter and the legacy `import()`), `bitmagnet/conn.rs` (settings, credential, TLS and session), and their tests `bitmagnet/tests.rs` (unit and property) and `bitmagnet/pg_tests.rs` (PostgreSQL 16).

**The adapter replaces the old importer in place.** The legacy `import()` that `lodestar import-bitmagnet` calls now runs on the adapter: it reads `Source` batches and writes `Torrent` records through `Store::insert` as before, counting candidates and invalid rows as `skipped`. So the CLI gets every hardening below now, and IMP-4 swaps it for the job-based driver. Its old `String` reads, its URL and its `NoTls` are gone.

**The legacy cursor file is bound to the source** (self-review, blocking). It holds `bitmagnet-cursor-v2`, the dataset identity and the position, in hex.
- A cursor whose dataset differs from the database just opened is refused as `source_changed`. So a run pointed at another restore, even one with the same name, can't resume past the old cursor and silently skip rows.
- A pre-IMP-3 cursor holds a bare hash. IMP-1 says it's never trusted automatically, so it's refused with the safe step: delete it and start over. Rows already imported are recognised and merged.

## Column mapping
Each parent row becomes exactly one IMP-1 record. Nothing in a row is ever used as SQL, in an error or in a log.

| Bitmagnet column | IMP-1 field | Rule |
|---|---|---|
| `torrents.info_hash` | the keyset key; `Prepared.info_hash` / candidate `hash` | 20 bytes and not all zeros, or `Invalid`, finding `bad_hash`. Any width up to 500 bytes is still a keyset key, so a 32-byte row is stepped past and counted. A key over 500 bytes is the refusal `bad_key`, because no position can carry it. |
| `torrents.name` | `name` / `name_raw` | Raw bytes (see "Untrusted text"). Empty is missing. |
| `torrents.size` | `size` | > 0, else missing. Never coerced to 0. |
| `torrents.private` | privacy, `Info.private` | **Private only when `true`.** `false` and NULL are `unknown`: Bitmagnet's `false` isn't verified, so IMP-1's sticky-private merge decides. |
| `torrents.files_status` (0.2+) or `single_file` (legacy) | completeness, single-file | See "Quality". The enum is read by comparing it with its labels in a `CASE`, never cast (see "Capability detection"). The legacy `single_file` is read as `true` → `single`, `false` → `multi`, NULL → `no_info`, as Bitmagnet's own migration 00002 maps it. |
| `torrents.files_count` (0.10) | completeness | A count that differs from the kept rows makes the record partial. |
| `torrent_pieces.piece_length`, `octet_length(pieces)` (0.7+), or the same columns on `torrents` (before 0.7) | `piece_len`, `piece_count` | Kept only when the length is > 0, the pieces are a multiple of 20 bytes, and the count is `ceil(size / piece_length)`; else 0, finding `pieces_malformed`. The pieces themselves are never transferred. |
| `torrents.created_at` | `source_at` | Unix seconds, in `[2008-01-01, batch time + 1 day]`; ±infinity reads as NULL. Otherwise `None`, finding `date_out_of_range`. |
| `torrent_files.index` | file order | Rows are read in `(info_hash, index)` order. |
| `torrent_files.path`, `size` | one `File` | As IMP-2's file rules. A NULL or negative `index` makes the row malformed. |
| Everything else | — | Never selected: `updated_at`, `extension`, `search_string`, `tsv` and the content tables. |

**Every text value is size-guarded in the SQL,** as IMP-2's: `CASE WHEN octet_length(x) <= 4096 THEN convert_to(x, 'SQL_ASCII') END` beside `octet_length(x)`. PostgreSQL reads a TOASTed value's length from its header, so an over-limit name or path is never transferred. It reaches the normaliser as `Bytes::TooLong`.

## Quality, privacy and file order
- **Verification is always `unverified`.** Bitmagnet fetched the info dict once, but keeps no copy that ties the stored fields to the hash.
- **Completeness:**
  - `single` with no file rows: one file named after the torrent, of its size, `reported_complete`, **with `single_file` claimed.** Bitmagnet sets `single` only when the info dict has no `files` list, so the schema proves it. That's a different answer from IMP-2, where the rows can't tell.
  - `multi`: `reported_complete` only when every row was kept, the indexes are exactly 0, 1, 2 … with no gap, the count equals `files_count` where the column exists, and the sizes add up to `size`. Otherwise `partial`: `MISSING_FILES` with no rows (finding `no_files`), else `INCONSISTENT_FILES` (findings `files_incomplete`, `size_mismatch` or `file_malformed`).
  - `single` with file rows: `partial` with `INCONSISTENT_FILES`, finding `status_mismatch`, and single-file isn't claimed.
  - `over_threshold`, `no_info`, NULL or an unknown label: always `partial`, findings `over_threshold` or `no_info`. `MISSING_FILES` with no rows; otherwise the kept rows are an incomplete list, `INCONSISTENT_FILES`.
- **File order is claimed by the complete record.** `index` is the position in the info dict's `files` list, and a complete record has every index from 0 with no gap, so its stored order is the original order. A partial record keeps its rows in `index` order without that claim. That's also different from IMP-2, whose row ids say nothing about order.
- **Torrent or candidate:** as IMP-2. A valid hash missing its name or size is a `Candidate`, with privacy as above. **Rows with no name are kept, never dropped.**

## Untrusted text
- **Names and paths are read as `bytea` with `convert_to(col, 'SQL_ASCII')`,** which converts nothing (IMP-0 verified it on the restore). They are never read as `String`, so the `SQL_ASCII` bytes IMP-0 found can't fail a read.
- **Then they're decoded as IMP-2 decodes them:** valid UTF-8 as is; anything else lossily, flagged `name_lossy` or `path_lossy`, with the exact original bytes in `name_raw`.
- **No hash of the original bytes,** as runner A decided for IMP-2: `name_raw` keeps the bytes themselves.
- **No declared-encoding step.** IMP-0's rule is that `SQL_ASCII` means "unknown". Bitmagnet wrote Go strings, so as in IMP-2 nothing is guessed as GBK or Latin-1.

## Opening the source
- **Structured settings only** (`bitmagnet::Settings`): host, port, database, user, a password, a TLS mode and the statement timeout.
  - No URL, no connection `options`, no `search_path` and no SQL are taken from input.
  - The database and user must be 1–63 bytes with no NUL.
  - The host must be a name or IP literal (letters, digits, `.`, `-`, `:`, brackets), or an absolute socket folder. Anything else is `bad_settings`.
- **The credential comes only from a file or an environment variable,** never argv.
  - **`--password-file`:** at most 4 KiB, with one trailing newline removed, and refused if empty. The CLI warns if others can read the file.
  - **Otherwise `LODESTAR_IMPORT_PG_PASSWORD`.**
  - `Password` is zeroed on drop, its `Debug` prints `Password(..)`, and no error carries it.
  - **Why the job table's `credential` stays empty:** IMP-1 stores only a sealed-secret reference there. Sealing the password is the IMP-4 CLI's step.
- **TLS:**
  - **Required with certificate and name verification for any host that isn't loopback,** through rustls on ring: TLS 1.2 or 1.3, against the platform verifier, or only the CAs in `--ca-file`.
  - **Plaintext only to a Unix socket or a loopback address, and only with `--allow-plaintext-loopback`** (`Tls::PlaintextLoopback`). `localhost` counts as loopback only when every address it resolves to is, and the connection is pinned to the first. Anything else is refused as `tls_required` before any connection is made.
  - **A server without TLS is `tls_failed`,** never a fallback to plaintext.
  - **No channel binding:** the certificate check is what authenticates the server.
- **The session, before its first query:**
  - `default_transaction_read_only = on` and the statement timeout go in the startup packet too.
  - `statement_timeout` (30 s by default), `lock_timeout = 10s`, and `idle_in_transaction_session_timeout` = the statement timeout + 60 s.
  - `search_path = pg_catalog`, as IMP-0 does it: a function the source put in `public` can't win overload resolution.
  - `row_security = off`: a policy can't hide rows silently.
  - `enable_seqscan` and `enable_sort` off, so the keyset reads stay on their indexes when the statistics are stale.
  - **Every read is an allowlisted, schema-qualified constant** (`public.torrents`, `public.torrent_files`, `public.torrent_pieces`, `pg_catalog.*`). Only the capability set chooses among them.
- **Client-side bounds too:** the connect takes at most 20 s, and the open and each batch take at most ten statement timeouts. A stalled server can't hang the import.
- **Errors map to fixed refusals.** The server's text is never kept, since it can quote the source's own bytes.
  - `57014` is `statement_timeout`, and `55P03` (a lock wait) is `source_not_quiescent`.
  - A dropped table or column is `source_changed`.
  - The rest are `source_unavailable` with a fixed label: `auth_failed`, `no_database`, `permission_denied`, `tls_failed`, `connect_failed`, `connection_lost`, `session_setup`, `ca_file_unreadable`, `ca_file_invalid` or `read_failed`.
  - `auth_failed` blocks a running job with `needs_credentials`.

## Capability detection and source identity
- **By columns, from `pg_catalog`, never version numbers.**
  - **Required:** `torrents(info_hash bytea, name text, size int8, private bool, created_at timestamptz)` and `torrent_files(info_hash bytea, index int4, path text, size int8)`, both ordinary tables (`relkind = 'r'`), plus `torrents.files_status` (the `FilesStatus` enum) or the legacy `torrents.single_file bool`.
  - **Optional:** `files_count`; `torrent_pieces(info_hash, piece_length, pieces)` with a unique `info_hash` (without one, the join could duplicate rows, so pieces are skipped); or `torrents.piece_length` and `pieces`.
  - **Required indexes,** valid, non-partial btree indexes on plain columns:
    - a unique index on exactly `torrents.info_hash`, which must be `NOT NULL`, so `> last` never skips a duplicate;
    - an index on `torrent_files` leading with `(info_hash, index)`, so the files read streams in order with no sort.
  - **Anything missing** is `unsupported_schema`, named from the adapter's own list.
  - Catalog names are read as bytes too, so a hostile name can't fail the read.
  - **Types are checked by namespace and kind, not just name** (self-review, important). Each column's type must be the built-in one in `pg_catalog`, and `FilesStatus` must be an enum. So a `public` domain or type named `text` or `bytea` doesn't pass, and a test checks a `public.text` domain is refused.
  - **A source with any cast to or from `FilesStatus` is refused** (runner review, blocking, security). Reproduced on PostgreSQL 16:
    - a non-superuser who owns the enum can `CREATE CAST ("FilesStatus" AS text) WITH FUNCTION public.f(…) AS IMPLICIT`;
    - casts are global, so `search_path = pg_catalog` doesn't stop it;
    - its function runs as the importer's role, once per row, even inside a read-only transaction.

    So `schema()` counts the `pg_cast` rows whose source or target is the enum, and refuses any as `unsupported_schema`, before a row is read. `FilesStatus` is the only type a read column may come from outside `pg_catalog`, so it's the only type the source can define a cast on. The query also never casts the enum, comparing it with its labels instead. Tests refuse an implicit cast to `text` and one to `bool`.
  - **Indexes must use built-in operator classes** (runner review). A source's own `bytea` class could order keys differently, and the keyset would then silently skip rows. So an index with any operator class outside `pg_catalog` doesn't count, and a test refuses a unique index built with one.
- **Fixtures,** built from Bitmagnet's own migrations (v0.10.0's `migrations/`):
  - **0.10.0**, the observed schema;
  - **without `files_count`** (0.7–0.9, migrations 00013–00015);
  - **without `torrent_pieces`**, with no piece data at all;
  - **piece columns on `torrents`** (0.2–0.6, migrations 00002–00012);
  - **the legacy `single_file` layout** (migration 00001).
- **Source identity** (IMP-1's `{adapter, dataset, schema_sig}`):
  - `adapter = "bitmagnet"`, adapter version 1.
  - `schema_sig` is a domain-separated SHA-256 of the known columns (table, name, type, `NOT NULL`) and the two read queries. 32 bytes.
  - `dataset` is a domain-separated SHA-256 of a **fingerprint**, the read tables' cumulative write counters, and SHA-256s of the first and last `info_hash`. The fingerprint covers the database's OID and name, and each read table's OID and file node.
    - **What binds it to this database:** a database restored again under the same name gets a new database OID and new table OIDs, so a resumed job refuses it as `source_changed` through IMP-1's `revalidate`. A test drops the database, restores the same rows under the same name and checks this.
    - **Why not the system identifier:** `pg_control_system()` is superuser-only by default, so the least-privilege role from IMP-0 can't read it. The brief allowed the database OID and name instead.
    - **What it can't detect:** an edit that leaves the OIDs, file nodes, ends and write counters alone. The counters see every insert, update and delete, so that takes a statistics reset. A **crash or `pg_stat_reset()`** resets the counters, so a resumed job blocks as `source_changed`: a false alarm, but on the safe side.
  - **Each batch rechecks the fingerprint** inside its own transaction. A changed database, a table rewritten (`TRUNCATE`, `VACUUM FULL`) or a dropped table is `source_changed`.

## Quiescence
A complete snapshot needs a source nothing writes. It's checked at open and again inside every batch's transaction, and refused as `source_not_quiescent`:
- **Write locks:** another session holds or waits for `RowExclusiveLock` or stronger on a read table in `pg_locks`. Every writer holds that until its transaction ends, and `pg_locks` needs no privilege.
  - A prepared (two-phase) transaction has a NULL `pid`, so the check uses `IS DISTINCT FROM` to count it too.
  - `ShareUpdateExclusiveLock` (autovacuum, `ANALYZE`) isn't a write and doesn't count.
- **The cluster's next transaction id** (`pg_snapshot_xmax(pg_current_snapshot())`) moved since the open (self-review, important).
  - Our reads assign no transaction id, and any committed write moves it at once. The table counters below can lag by up to 10 s (60 s under contention).
  - **It's cluster-wide, so it's strict:** a write to another database on the same server, or an autoanalyze, also refuses the batch. The job blocks with `source_unavailable` and resumes once the server is quiet; the identity doesn't include it.
  - So the source should be a server nothing else writes to, which IMP-0's isolated restore is. IMP-4's docs say so.
- **Write counters:** the read tables' inserted, updated and deleted tuple counters moved since the open.
- **A standby,** whose replayed changes move neither locks nor counters.
- **`track_counts` off,** which leaves nothing to check.

*Refined from the brief:* it suggested `pg_stat_database.xact_commit`. Every read-only transaction, our own included, advances it, so it can't tell a writer from a reader. `pg_stat_activity` hides other roles' transaction ids from an unprivileged role, so it isn't used either. Live, best-effort import stays out of scope.

## Keyset reads
- **Torrents:** `… FROM public.torrents t [LEFT JOIN public.torrent_pieces p USING the unique info_hash] WHERE t.info_hash > $1 ORDER BY t.info_hash LIMIT 500`. The first batch uses `>=` the empty key, so even an empty `info_hash` is read. No `OFFSET`, no `COUNT(*)`.
- **Files: one ranged query per batch,** `WHERE info_hash BETWEEN first AND last ORDER BY info_hash, index`, read through a portal **1,000 rows per round trip.** Orphan rows (constraint-free sources only) aren't any parent's, and are skipped.
- **A parent over its budget is capped, not spooled:** over `max_files` (200,000) rows or 8 MiB.
  - Its rows are kept as a prefix in `index` order. The record is `partial` with `INCONSISTENT_FILES`, finding `files_over_limit`.
  - **The reader then closes the portal and restarts the range after that parent,** so the rest of its rows are never transferred.
  - **The cost:** `files_dropped` counts only the rows it read and didn't keep, a lower bound for that record. Counting the rest would need a scan of every one of them.
- **Each batch is one read-only, `REPEATABLE READ` transaction:** the identity and quiescence checks and both reads see one snapshot. It's committed before the batch returns, so no transaction stays open between batches or while a job is paused.
- **Batch bounds,** as IMP-2's: **500 parents or 8 MiB**, with each kept row charged its bytes plus 64, and each path segment 24 more. A parent is never split across batches.
- **Position** is a version byte (1) plus the last parent's `info_hash`: at most 501 bytes, within IMP-1's 512. Anything else is `bad_position`.
  - **The legacy cursor file** holds the position in hex, with the dataset (see the top of this file). A file from before IMP-3 is refused, never read as a bare hash.

## Findings, refusals, logs
- **Findings, a fixed enum with counts, returned with each batch:** `bad_hash`, `name_lossy`, `path_lossy`, `name_over_limit`, `files_over_limit`, `file_malformed`, `no_files`, `size_mismatch`, `date_out_of_range`, `missing_name`, `missing_size`, `files_incomplete`, `no_info`, `over_threshold`, `status_mismatch`, `pieces_malformed`.
- **Refusals:** `bad_settings`, `tls_required`, `source_unavailable` (with its label), `source_not_quiescent`, `unsupported_schema`, `statement_timeout`, `cancelled`, `source_changed`, `bad_position`, `bad_key`. `Refusal::job_reason` maps each to the IMP-1 reason a running job blocks with, or none when it should fail.
- **No content in `Debug`:** rows, records, batches, identities and settings print lengths and counts only. A test checks that a name, path, size, date, hash and password never appear.

## Tests
- **Unit and property tests** (`bitmagnet/tests.rs`):
  - every status and completeness rule;
  - malformed file shapes;
  - raw bytes kept exactly;
  - candidates for each missing field;
  - bad hashes, dates and pieces;
  - privacy;
  - positions and the legacy cursor;
  - `Debug` output;
  - the password file;
  - the plaintext refusal with no I/O, and settings validation;
  - the session SQL;
  - every read schema-qualified.
- **The property test runs the row-to-record mapping** over arbitrary bytes, odd sizes, missing values and every status. It checks: no panic, kept + dropped = rows + overflow, a complete record's files add up, names stay in bounds, and privacy is private only for `true`. The brief allowed a property test in place of a fuzz target, so the fuzz workspace is untouched.
- **PostgreSQL** (`bitmagnet/pg_tests.rs`, SQL_ASCII databases):
  - every layout fixture, with its capabilities and a stable identity on reopen;
  - unsupported schemas: an empty database, no status column, no files index;
  - the read-only session: the settings as `SHOW` reports them, four kinds of write refused with `25006`, and the statement timeout;
  - TLS: a server without TLS refused, and plaintext off loopback;
  - a non-UTF-8 name and path, an infinite date, nameless and zero-size rows kept as candidates, and the bytes in `name_raw` after a commit through IMP-1;
  - batches of 500/500/100;
  - a parent over 8 MiB capped, with the next parent still read;
  - a writer mid-transaction refused at open, and a committed write refused at the next batch;
  - another database with the same name refused on resume, with a replay writing nothing;
  - the legacy `import()`.
- **No silent skip in CI:** the importer job sets `LODESTAR_REQUIRE_POSTGRES=1`, which makes a missing `LODESTAR_TEST_POSTGRES` or an unreachable server fail the tests. Elsewhere they skip. The old `tests/bitmagnet.rs` is replaced by these tests.
- **A certificate test against a fake server** (`tests.rs`): an in-process server answers the SSLRequest and does a real rustls handshake with a fixed test certificate for `localhost` (`bitmagnet/testdata/`, issued by a test CA, valid for 100 years).
  - These are refused as `tls_failed`: the platform's trust store, another CA, and the right CA with a name the certificate doesn't cover.
  - The right CA and name get through the handshake to the server's password refusal (`auth_failed`).
  - A CA file that isn't one is `ca_file_invalid`.
- **The PostgreSQL tests run one at a time,** because the transaction-id check is cluster-wide.
- **Each test flushes its fixture writer's table statistics before opening** (`pg_stat_force_next_flush`), so a late flush can't read as a write mid-import or change the identity between opens.
- **The resume test asserts the fingerprint itself differs** between the two same-named databases, so the OID binding is what's proved.
- **The legacy test checks the cursor binding:** a recreated database under the same name is refused with `source_changed`.
- No fixed sleeps. The quiescence test polls the statistics with a 20 s deadline.

## Known follow-ups
- **Query plans aren't asserted.** `enable_seqscan` and `enable_sort` only discourage the other plans. An `EXPLAIN` test on the fixtures would lock the index scans in (IMP-4's pilots measure them on the real restore).
- **The password from `LODESTAR_IMPORT_PG_PASSWORD` stays in the process environment,** and tokio-postgres's `Config` keeps an unzeroed copy for the connection's life. Removing an environment variable is `unsafe` in Rust 2024, and the import is a short-lived CLI process. IMP-4, which seals the credential, revisits it.
- **`localhost` is resolved with a blocking call** before connecting. It's a local lookup on a CLI path.

## Out of scope
The SQL/ZIP dump parser, live-source import, the new CLI verbs, the job driver and sealing the credential (IMP-4), merge and dedupe (IMP-4), the Insights cohorts (IMP-5), recovery (CR-3), and a spool for huge file lists (capped instead, as above). No migration.
