# X-cmp4b-mounts decisions (#613)

A follow-up to CMP-4b (#608): the runner's follow-up to the CMP-4b delta review. This file adds to `2026-11-08-CMP-4b.md`'s "Nor through a second mount" entry; it supersedes nothing there.

- **An alias of the companion's own folder below home is refused (W^X).** The mount check's "what lies inside home" exemption skipped two rules: the home rule (right, since home's grant covers what's inside it) and "the companion's own folder itself" (wrong). A mount below home that showed the companion's own folder, and so its install folder, passed. The companion could then rewrite its verified binary and run it. Only the home rule is skipped now.
- **The mount table is read as bytes.** A mount point needn't be UTF-8 (a USB disk with a Latin-1 label). Reading `/proc/self/mountinfo` as text failed on such a table and refused every start. It's now read, split and unescaped as bytes, and its paths are compared as OS strings.
- **An unreadable table has its own reason, `mounts_unreadable`.** That covers both an unreadable table and one that can't place a folder. It still fails closed, but it no longer reports a misleading `downloads_overlap_data`.
- **The install folder must be exactly `<data>/companions/<id>/<version>`** (CMP-2's layout; runner, in this PR). `check` used to accept any folder inside the companion's own. With a deeper install folder (`<own>/v/5.0.3`), a downloads folder of `<own>/v` passed both the path check and the mount check, and took write access over the install folder. Nothing used a deeper layout, but it's now refused (`install_outside_companion`).
- **The mount-table parser has property tests:** escaping any path the kernel's way and unescaping it gives the original bytes, and the parser never panics on any table or path. Fixed cases cover short or invalid escapes.
- **Residuals, recorded:**
  - **The check is a snapshot taken at start.** A mount added below a grant later (autofs, Unraid's Unassigned Devices) isn't checked until the companion's next start. Until then the running companion's Landlock rule extends to the new mount, so a second mount of the data folder placed there is reachable.
  - **(L-1) The deepest mount point wins,** even where a later mount on a parent folder shadows it. A table can therefore place a folder on the wrong mount after an over-mount. The fix is to identify the mount by `statx(STATX_MNT_ID)` and look up that mount's line. It isn't built here: for folders that don't exist yet (home before the first start) it needs a fallback to the current rule, so it doesn't fit in this follow-up's size.
  - **(L-2) The protection is tied to the data folder's device.** A separate filesystem mounted under `<data>` is a different device from the data folder, so a second mount of it elsewhere isn't recognised as data. Nothing Lodestar ships mounts one there.
