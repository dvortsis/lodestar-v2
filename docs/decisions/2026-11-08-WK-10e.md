# WK-10e: Politeness applied: per-peer-IP dials, the BEP 51 scale, the coordinator's share

The runtime half of plan Q9 ("same-IP politeness"). WK-5's planner already splits one install's per-remote limits between the fleet members that may share a public address (`Politeness` in `crates/cluster/src/assign.rs`). This slice makes the fetch pool, the DHT node and the coordinator obey that split. Brief: runner, 2026-11-08T13:45Z.

## The pool asks a policy for each peer IP
- **`PeerIpCap`** (`crates/sources/src/pool.rs`): `connections_to(ip) -> usize`. The pool's cap for an IP is the policy's answer, never above its own `per_ip`. With no policy (the default, `IpCap(None)`) it's `per_ip` alone, exactly as before. The existing per-IP counts are reused; there's no second map.
- **0 means never dial that IP.** The IP is in another same-IP member's bucket.
  - A peer the policy refuses is never added to a key. So a key whose only peers are refused asks for more at once, as a key with no peers does.
  - A peer added before a change that now refuses it is dropped at the next pick. If none is left, the key takes the failure path: a stream keeps its lookup, and anything else backs off for its next lookup. It's never put off for ever.
  - With 3 or more members on one address, a member can't dial peers outside its bucket. That's the cost of the split, recorded in WK-5's decisions. A key whose peers are all elsewhere can end as `NoPeers` on that member.
- **Live changes** (`PoolHandle::set_ip_cap`) apply to the next dial. A connection already open finishes, and no in-flight fetch is dropped.
- **The first policy is in `PoolConfig::ip_cap`**, so a worker's pool never dials before it has its share.

## The DHT waits N times a node's interval
- After a `sample_infohashes` answer, the node isn't sampled again for its interval × `bep51_interval_scale`. So N same-IP members together sample it no faster than one install.
- **The node's own interval is bounded first, then multiplied:** `wait.clamp(MIN_INTERVAL, MAX_INTERVAL).saturating_mul(scale)` (`Sampler::complete_scaled`).
  - The 6 h clamp alone would cancel the scale for the common case: a node asking 6 h. The runner approved this edit to `sampler.rs` (2026-11-08T13:56Z).
  - The scale is taken as `1..=MAX_SCALE` (8, the planner's `MAX_DHT_PER_IP`). A scale of 0 reads as 1 and never means "no wait". So **a cooldown is at most 48 h.**
  - A failure, a timeout or "not supported" isn't scaled, so a node that fails isn't penalised N×.
- **Live changes** (`NodeHandle::set_sample_scale`, `Config::sample_interval_scale`) apply from the next answer; a cooldown already running keeps its end.
- **Slot pressure.** The sampler's table (`MAX_KNOWN`, 200,000) already binds today.
  - At Balanced the sample budget is 100/s, but 200,000 cooldowns of 6 h sustain about 9 nodes/s. When the table is full, `next` returns nothing and `sample_tick` counts `sample_deferred` until cooldowns end. Cooling entries are never evicted: evicting one would break the promise not to resample.
  - With scale N, a member sustains about 9/N per second, and N members behind one address about 9/s together: one install's worth, which is the point of Q9.
  - Fewer distinct nodes cool on each member. The fleet still covers the keyspace through WK-4's shards, which are separate for each member. Only BEP 51 sampling is throttled; `get_peers`, announces, exploration and routing are not.
  - The sampler's policy is unchanged; the runner was told so before the push.
- **Across a restart.** CR-0d's snapshot horizon `H` is `MAX_INTERVAL + query_timeout`, and `restart::capture` refuses a whole snapshot if one entry is beyond it. So the proof's commit saves each cooldown as at most `H` from now (`proof.rs`, one line).
  - The bound is `H` itself, not `MAX_INTERVAL`. A sample in flight at shutdown is sealed for the full `H` (P6), and a `MAX_INTERVAL` bound broke that, as `in_flight_samples_are_sealed_for_the_full_horizon` showed.
  - Every remote node's own interval is still honoured across a restart, which is what CR-0d protects. Only the extra N× part of a member's own cooldowns is cut, once, when that member restarts.
  - The file format and the horizon are unchanged, so old files load as before.

## Wiring
- **Workers** (`worker/runtime.rs`, `worker/dht.rs`): an `Assign` that changes the share updates a `politeness` watch.
  - The task that already applies the pool's pause also applies a changed share (`set_ip_cap`), in order, and records what it told the pool (`share_told`).
  - The DHT's `Want` carries `sample_scale`: a new node starts with it, and a running one gets `set_sample_scale` (counted in `scale_changes`) with no restart. A new shard still restarts the node, as WK-10c decided.
- **An invalid share is refused, and the previous one stands.**
  - For a worker, `Assignment::from_message` already refuses one (`AssignError::Field("politeness")`), and nothing from that `Assign` is used.
  - The coordinator runs the same check (`checked_share`, through `Assignment::validate`), so it never applies a share a worker would refuse. Nothing falls back to "unlimited".
- **The coordinator** (`serve.rs`, `services.rs`): each tick, after the placement sync, applies `Placement::coordinator().politeness` through `Wiring::coordinator_share` (`ApplyShare`).
  - In production that's `CoordinatorShare`: the pipeline's pool (`set_ip_cap`) and the coordinator DHT node (`set_sample_scale`).
  - It's applied at once when the share changes, and again every 60 s, so a DHT node restarted meanwhile by a settings change gets it within a minute. The call is bounded at 2 s, so it never holds the tick.
  - The coordinator's DHT shard stays its own (`[dht]` settings), as before.

## The numbers' sources
None are owner-set:
- `INSTALL_PER_PEER_IP = 2` is the pool's existing `per_ip` (§6).
- The scale comes from WK-5's planner, capped by `MAX_DHT_PER_IP = 8`.
- `MAX_SCALE` (8) mirrors that cap in the dht crate, which can't depend on the cluster crate.
- The 48 h bound is 6 h × 8.

Changing either number is a runner call. The 48 h bound and the slot-pressure trade-off are flagged under §2.19.

## Tests
- **The fleet-wide property gate** is WK-5's `per_remote_limits_never_exceed_one_install` (`crates/cluster/tests/placement.rs`, 512 cases).
  - For every address and every remote, the members that may appear as that address have summed `connections_to(remote)` ≤ `INSTALL_PER_PEER_IP`, and summed BEP 51 rates (1 / scale) ≤ one install's.
  - Its members include the coordinator (`fleet()` makes it member 0, with addresses of its own). It's cited rather than copied, since that crate is read-only here.
- **Pool** (`crates/sources/tests/pool.rs`):
  - `a_peer_ip_outside_our_share_is_never_dialled`: a 0-cap IP is never dialled, a 1-cap IP gets one connection, and a key whose only peer is refused asks for more at once;
  - `a_single_installs_policy_dials_as_today`: two per IP, as with no policy;
  - `a_lowered_cap_stops_new_dials_and_lets_open_ones_finish`.
- **DHT:**
  - `a_sample_scale_spaces_repeat_samples_of_a_node` (actor; scale 1, 3 and 8 after a real answer);
  - `a_scaled_cooldown_is_the_interval_times_the_scale`;
  - `a_full_table_of_scaled_cooldowns_holds_new_nodes_until_one_ends` (scale 8, a full table: the new node waits, isn't lost, and goes as soon as one cooldown ends);
  - `a_scaled_cooldown_is_saved_as_the_horizon` (the proof: a 48 h cooldown commits, the next run resumes, and it holds until `H`).
- **Worker:**
  - `a_live_share_change_applies_without_a_restart`: a fetch out to an IP that's no longer ours finishes; the next key's peer there is never dialled, and its peer on our IP is; nothing is dropped;
  - `a_live_shard_change_restarts_only_the_dht` now also checks that a new scale reaches the running node with no restart.
- **Coordinator:** `the_coordinator_applies_its_own_share` (applied once while unchanged, then the split share when a worker that may share its address joins) and `an_invalid_share_is_refused`.
- **Mutation-checked.** Each of these fails without its change:
  - dropping peers the policy refuses;
  - the refused-peer filter on add;
  - the horizon bound in the proof's commit;
  - the actor's scale;
  - the live `set_ip_cap`;
  - the coordinator's change check.
