# X-worker-service-log decisions

Under the Windows service control manager the worker's progress lines (from #801, WK-18s) went to a stderr no one reads. Each line now also gets a `worker.*` log event (§12.1, §19.6). The console still prints the lines as before.

- **Logged only under the service.** `cli::worker::run_until` (the service's entry) wraps its `report` so each line is logged and then passed on. `run` (the console) only prints, as before, so a console run doesn't log every line twice. Reason: the brief's problem is the service, and in a console the lines are already read.
- **Classified by the line's fixed start, in `cli/worker.rs`.** The session (`worker/session.rs`, not this slice's file) says its lines through `report`. `classify` maps each line to its event by the fixed text it starts with. A test reads `session.rs` and checks that every `self.say(` literal maps to an event other than `worker.status`, so a new line without an event fails the build instead of being lost.
- **The line's text is never logged.** Events carry only which line it was, plus fixed reasons and numbers: no worker name, address, token, join code, certificate detail or error text. `worker.connect_failed` has a fixed `reason` (unreachable, timeout, refused, stopped, protocol, invalid, closed, or `other` for TLS and link errors) taken from `ClientError`'s fixed texts. `worker.retrying` has `wait_ms` and `worker.clock_skewed` has `seconds` (absolute), both `Count`. A test checks that a marker in a line never reaches the log.
- **`worker.status` catches lines with no event of their own** (for example the start-up warnings from `plan`), so no line goes unlogged. Its text isn't logged either; the help says to run the worker in a console to see it.
- **`worker.exited` (Error) for a stop the user has to act on**: revoked, expired, outdated, identity_mismatch or replaced, as a fixed `reason`. The full text still goes beside the installer's log, as `windows/service.rs` already does, and `service.failed` follows. A plain stop or a drain is already logged as `worker.stopped` or `worker.drained`.
- **Levels:** lost connections, refusals, failed connects, clock skew, renewal problems and a timed-out handback are Warn. The rest are Info. `worker.exited` is Error.
- **Two edits outside the slice's `owns` list:**
  - `web/src/lib/features/settings/logging/event-names/workers.ts` is where `npm run event-names` writes the workers events. `event-names.ts` itself is only the per-component loader map, which hasn't changed.
  - `web/.size-limit.mjs`: the workers event-names chunk budget goes from 3780 B to 6370 B. That is the measured 5785 B with the 18 new events, plus 10%, the formula the file already uses. This is the runner's call under `docs/owner-decisions.md` §2.26, flagged in the PR.
- **Left as is:** the doc comment on `windows/service.rs`'s `worker()` still says the progress lines have no log event. It isn't this slice's file. A follow-up can fix that one line.
