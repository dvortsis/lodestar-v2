# X-restart-save-lag decisions

The restart banner and the status pill learn of a Settings save as soon as it answers, instead of at the restart watch's next poll. This is the follow-up named in `2026-11-11-X-restart-banner.md`.

- **A save sends one window event, `ls-settings-saved`.** The form's `send()` (`web/src/lib/features/settings/form/saving.ts`) dispatches it right after a `PATCH /settings` succeeds. Every save made through the Settings form goes through `send()`: batch saves, instant changes, Undo, removing a secret and a 422 confirm's resend. A few screens `PATCH` settings directly (logging privacy, updates, appearance, the adult-content flows, shortcuts, Bitmagnet). None of them writes a field that needs a restart, so they send no event. A new restart field saved outside the form needs the same dispatch, or it waits for the poll. The literal is inline and the form imports nothing from `restart/`, so no restart code joins the form's or the wizard's bundle. `restart/saved.ts` names the event for the watch, and `form.test.ts` pins the two names together: a successful save sends it, a failed one doesn't. **Outside the slice's owned paths: that one line and its test, a shared edit the runner approved (2026-11-12).** A save made before the watch starts goes unheard, which is harmless: the watch's first ask then comes after the save.
- **A save drops any `/system` read that left before it** (`restart.saved()` bumps the store's generation and asks again). That read may still carry the old `restart_required`, and if it landed after the fresh read it would hide the banner until the next poll. A plain `refresh()` would join that read instead of asking again. The case is real: the save's click can be the first interaction that starts the watch, and the watch's first read is then still out when the PATCH answers. Store and watch tests set this up, and each fails with the bump or the listener removed.
- **A save while a restart lasts asks nothing,** like any refresh then: the Restarting page checks the server itself.
- **Left as is:** Keep or Go back answering while a save's fresh read is still out drops that read too, since the answer bumps the generation. `restart_required` then waits for the next poll. It takes two actions inside one round trip, and changing Keep's "use the answer, don't ask again" rule belongs to a later slice. Quick saves each start their own `GET /system`, because each bumps the generation. That costs one small read per save.
- **The polls stay as they were** (15 s on Settings, a minute elsewhere, checked every 5 s). They still catch changes made elsewhere, such as another tab or the CLI.
