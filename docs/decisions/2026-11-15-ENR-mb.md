## Terms and usage policy (owner §2.28), checked 2026-11-15
- **How it was checked:** MusicBrainz's own documentation pages, read directly on 2026-11-15: "MusicBrainz API / Rate Limiting" and "MusicBrainz API / Search". No request was sent to the web service itself.
- **Rate limit:** one request a second on average per IP address; over it, every request is declined with **HTTP 503** until the rate drops. **The plugin sends at most one request a second with no burst** (the plan's cap, §2.26; `HostRate::per_second(1)`), one request a lookup (`min_interval` 1 s), one lookup at a time. A 503 or 429 reads as "limiting requests", and the host limiter backs off from 60 s to 6 h.
- **User-Agent:** every request must carry one that lets MusicBrainz reach the maintainers, in the form `Application/<version> ( contact-url )` or with an email. **The plugin sends `Lodestar/<version> ( <the project's repository URL> )`** (`musicbrainz::USER_AGENT`), built from the workspace's `repository` field, the same for every install, with nothing about the user, their host or their account (slice notes). As with Wikidata, the repository URL names the maintainer's public GitHub account: the project's public identity, not the user's.
- **Bulk:** the page asks clients not to start work at fixed times and not to poll for changes; it sets no bulk quota beyond the rate. The runtime's lookups go user interest first, then the capped background walk (Q12), and the cache keeps an answered item from being asked again, so nothing polls. At one lookup a second a plugin makes at most 86,400 lookups a day; Q12's 100,000 ceiling is above that. MusicBrainz offers database dumps for bulk use; the same open question the runner put to the owner for Wikidata (whether a whole-index background walk through the API counts as bulk) applies here.
- **Licence:** MusicBrainz's core data (release groups, their titles, dates and artist credits) is CC0. Its supplementary data, tags among it, is CC BY-NC-SA. **The plugin keeps only core data**; tags are never read, so no attribution or licence condition applies to what's stored.
- **No API key, no account.** The search needs none.

## Terms (ENR-terms), checked 2026-11-16
ENR-terms (#962) gives every plugin a `Terms` and an adult marker on each answer (`crates/sources/src/terms.rs`). MusicBrainz's `musicbrainz::TERMS`, from its "About / Data License" and "MusicBrainz API / Rate Limiting" pages, read again on 2026-11-16:
- **`background_walk: true`.** The "Rate Limiting" page sets one request a second per address as the only bulk rule, and asks that background work be spread at random through the day rather than run at a fixed hour. The runtime's capped walk does that, within the plugin's one-a-second cap. The data it reads is CC0, so bulk use of it is free. The same reading the runner made for Wikidata.
- **`redistribute: true`.** The plugin keeps only core data (a release group's id, title and first release year), which "About / Data License" puts under CC0: anyone may use it in any way. The supplementary data (tags, ratings), under CC BY-NC-SA, is never read.
- **`retention: Retention::DEFAULT`** (180 days). CC0 asks for nothing shorter; the runner's default keeps claims fresh.
- **`attribution`: "MusicBrainz (CC0)", linking `https://musicbrainz.org`.** CC0 needs no credit; it's a courtesy, as Wikidata's is.
- **`adult_marker_required: false`, `adult: None`.** A release group has no adult marker to read. The runtime's gate never asks about an Adult item, and the plugin's kind is Music only. A marked-adult answer is still refused by the runtime (`terms_tests`).

## What is sent (Q5)
- **One request a lookup:** `GET https://musicbrainz.org/ws/2/release-group?query=<query>&limit=5&fmt=json`, headers `Accept` and `User-Agent` only.
- **The title is split, not sent whole.** The release-name parser writes a music title as `Artist - Album` (`release-parser`'s music rule), so the plugin splits it at its first ` - ` into artist and album, when both sides have a letter or digit. Otherwise the whole title is the album and no artist is sent.
- **The query is a fixed Lucene template:** `releasegroup:"<album>"`, or `releasegroup:"<album>" AND artist:"<artist>"`. MusicBrainz's search has no non-Lucene form, so the title has to go inside the query language, unlike Wikidata. Each piece is **one phrase with every Lucene special character backslash-escaped** (`musicbrainz::phrase`: `+ - & | ! ( ) { } [ ] ^ " ~ * ? : \ /`; a control character becomes a space). Inside a phrase only `"` and `\` have a meaning, so the escaping is more than needed, which is the safe side. A property test (`any_title_is_one_phrase_each`) reads the query back as Lucene does and checks it's the template with exactly the title's text in each phrase; `a_hostile_title_is_one_phrase_in_one_parameter` checks the obvious attacks. The whole query is one URL parameter, encoded by the `url` crate.
- **The year and the kind aren't sent.** The year chooses among the answer's groups locally.

## The parser (`sources-feeds/src/musicbrainz.rs`)
- **On the shared bounded JSON reader**, Wikidata's shape: pure, no I/O, no panics, no unwraps, linear time (a bitmask over the read keys; `many_unknown_keys_are_read_in_linear_time` reads 300,000 unknown keys in the root and in a result).
- **The caps** (`SEARCH_LIMITS`): 4 MiB, depth 16, 500,000 values, 20,000 elements per array, 4 KiB per decoded string, 10 results, 16 credits per result. Why: a release group in a search answer lists every one of its releases (a popular album has hundreds, about 150 bytes each), which is most of the answer and is passed over unread; five groups of a few hundred releases are well under 1 MiB, and 4 MiB leaves room for the largest. The answer is parsed on the blocking pool. Past 10 results the parse stops (`Stop::Items`); a credit past 16 is passed over and the result says `truncated`, with no printed credit; any array past 20,000 spoils its result, or stops the parse when it's the result list.
- **Strict shape:** used only when `Page::whole()`. A result needs a lower-case UUID `id` (`Mbid::parse`; not the nil UUID; the store's `mbid` rule) and a `title` that's not empty once cleaned. `first-release-date` is `YYYY`, `YYYY-MM`, `YYYY-MM-DD`, empty or `null`; any other form spoils the result. `primary-type` is a string or `null`; a type MusicBrainz adds later reads as `Other` rather than spoiling. Each credit needs a `name`; its `joinphrase` and `artist.name` are optional. A repeated or escaped read key spoils its part; repeats of keys not read don't matter.
- **What it keeps:** the group's id, title, first release year (year 0 keeps none) and primary type; the credit as printed (each credited name and its join phrase, such as `A & B`); each credited name and its artist's name. Never tags, ratings, scores, disambiguation comments, releases, artists' ids, sort names or aliases.

## Choosing a match (`musicbrainz::choose`)
- **A group agrees** when its title folds to the album (lower case, letters and digits, runs of anything else one space), and, when the query names an artist, its printed credit or one of its credited names folds to the artist, and, when the query has a year, its first release year is that year.
- **One group agreeing is the match.** Several (the same id listed twice counts once) are no match, **unless exactly one of them is an Album**: an album and its same-named single of the same year are common, and a torrent of the name is far more often the album (`musicbrainz_candidates`, 2010). Two albums are still no match: it never guesses between works.
- **The year is the first release's.** A reissue's torrent with its reissue year won't match; that's a miss, never a wrong match. Matching a later release's year needs a second request a lookup (the releases' dates), which can come with real recordings if misses show it's needed.
- **Confidence:** 90 with artist and year, 75 artist only, 70 year only, 60 title only. All under ENR-10's cap (95). Without an artist a title alone is weak evidence, so it's the lowest.
- **The answer:** `mbid:<release group id>`; the group's title as the canonical title; the year (the query's, else the group's). **No alternative titles** (a search result carries none), **no genres** (MusicBrainz's genres need a second request, and its tags are user-written and under a non-commercial licence), **no artist** (the claims have no field for one, and an artist names a person; the torrent's own name already holds it).

## Judged before storage
- **Nothing here judges text.** The title goes into ENR-10's claims and the writer's ingest judges it with the torrent's name (`an_answer_is_judged_and_a_held_one_is_not_stored`).

## Errors
- **Status first:** 200 is parsed; 429 or 503 is "limiting requests" and the host limiter holds the host; a 3xx is never followed; anything else, or a transport failure, is "the request failed". A 200 whose body is an error object holds the plugin for its `Retry-After` (60 s when there's none, at least 1 s, at most an hour), as Wikidata does; MusicBrainz documents its errors with error statuses, so this is a guard. A 200 that isn't `whole` is "wasn't understood". **None of them is a miss**, and no error holds the service's text. A title with nothing to search for sends nothing.
