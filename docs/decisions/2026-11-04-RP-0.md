# RP-0 decisions: pack manifest, applied versions, pending changes, SC-2

Slice RP-0 of `docs/plan/2026-11-04-v06-rulepacks.md` (§4.3 RP-0, Q1, Q7, Q16), with the nits from #412's final review (`notes/rulepacks-brief-nits.md` on `runner-state`). Architecture §20.6, §20.7, §20.8, §20.10; owner §1.8.7, §1.8.8, §2.8. No migration: `settings` rows only (plan §3, Q9). Any doubt was resolved as weakening.

## Manifest and changelogs
- **Every pack rule has a version list, compiled in** (`crates/filter/src/packs/manifest.rs`). Each version records its number, action, code and **direction** against the one before (`widens`, `narrows`, `action-heavier`, `action-lighter`, `mixed`). A first version `widens`. Today every rule is at version 1, `widens`, the behaviour it had before RP-0 (baseline).
- **The newest version's code is the arm in `Ctx::matches`** (`Code::Current`). When a release changes a rule, the old code moves to a function kept as `Code::Fn` beside the new one, so an install that hasn't accepted the change keeps applying it. Once no supported upgrade path can still have it applied, its code is dropped (`code: None`) and its record stays, so a skipped step's direction is still known.
- **Combining steps is conservative.** Two steps of the same direction keep it; anything else is `mixed`, which counts as weakening. So a widening followed by a heavier action asks for the password even though both strengthen: no single record says both.
- **A changelog per pack**, `crates/filter/data/packs/<pack>/CHANGELOG.md`, one `## <RULE>@<version>` entry per version naming its direction, compiled in (`manifest::changelog`, `changelog_entry`) for RP-3. A test fails when a version has no entry.
- **The per-rule golden** (`manifest.rs`, `rules_match_as_their_version_says`) runs every rule over 3,000 generated torrents and pins, per `RULE@version`, how many match and a hash of which. Changing what a rule matches without a version bump fails it. RP-1's corpus takes over once it exists.

## SC-2 (Q16)
- **SC-2 is its own `PackRule`**, hide, in the scams pack. SC-2 reads the online games and currencies of SC-1's old service list (`robux`, `vbucks`, `roblox`, `fortnite`); SC-1 reads the rest. Same scam words and guards. So SC-1 ∪ SC-2 is exactly SC-1 before RP-0: checked on every item of the golden set, and on the pre-RP-0 pack tests, whose helper reports SC-2 as SC-1 (the one change to them).
- **Seeding copies SC-1's stored switch and its `filter_exceptions` rows to SC-2** in the seeding transaction (nit 2), and records SC-2 at version 1 (it was part of SC-1). Before seeding is written, the engine does the same copy in memory, so a store is never judged without it.
- **An Undo step saved before RP-0** gets the same copy when it's restored: snapshots now carry `"packs_seeded": true`, and one without it is pre-RP-0. Without the copy, Undo would only have tightened (SC-2 on and without exceptions), but it would also have lost what you chose for SC-1.

## Stored state
- **`filter.packs.applied` and `filter.packs.applied.2`:** one `RULE-ID@version` per line, written together in one transaction with the marker `filter.packs.seeded`. Ids this build doesn't know are kept. None of them is in `RuleSet`'s Undo data or written by `replace_rule_set`: Undo never changes versions, so it can't undo an acceptance or accept a pending version.
- **The store reads them with the rule set** (`RuleSet::pack_versions`, re-exported from `lodestar_store`), so every engine load sees them without changing the callers. A row is `Option<Result<String, Vec<u8>>>`: absent, text, or the raw bytes of a value that isn't text.
- **Version 0 (`UNKNOWN`) means "not known".** Only an acceptance after both rows were lost writes it, for the rules it didn't accept (below).
- **A row that exists but won't read** (not text, not UTF-8, not a record) counts as state (nit 3): it never lets seeding run.

## Seeding, once
- **Only when none of the three rows exists**, checked again inside the seeding transaction. It writes the baseline record (every rule that existed before RP-0 at version 1, SC-2 included), the SC-1 → SC-2 copy and the marker.
- **Where:** the pipeline's start (`crates/pipeline/src/lib.rs` `prepare`, before `StoreFilter::read`; a shared edit the runner asked for), and the filters API before every change and at each start (`FiltersApi::resume_requeues`) as a fallback. The engine applies what seeding records before it's written (an unseeded store resolves to the seed record, SC-2 copy included), so `lodestar import`, which reads the filter without the pipeline's start, judges the same.
- **Applied rows without the marker never seed** (nit 3): they're used as they are and reported (`packs.marker`); the next write adds the marker.
- **Seeding on a store whose rule set wasn't empty is reported** (nit 3), in the marker's own value (`rules@<time>`, else `1`), written in the seeding's transaction so it can't be lost, and read as `PackVersions::seeded_over_rules` for the Filters & Safety notice (RP-3, RP-6). Not in `filter.stand_ins`: that record holds conditions that last, and the stand-in re-judge treats it as empty once its rows read. That's the normal upgrade from before RP-0, and also what an install whose three rows were all deleted would look like, which can't be told apart; the report makes it visible either way.

## Resolution (`packs::upgrade::PackVersions::resolve`)
- **Pending:** a rule recorded at an older retained version applies that version, and its current version runs in **shadow**. A rule not in the record that was added after RP-0 (as SP-3 and SP-4 will be) applies nothing and is pending: an upgrade never turns it on unpreviewed.
- **A readable record that doesn't know a rule fails closed** (self-review). Seeding records every rule that existed before RP-0, and writes only add, so one of them missing from a readable record (an emptied or truncated row) means damage: it runs the interim mode, reported as `packs.unknown.<ID>`, as does a rule recorded at version 0.
- **One row unreadable:** the other is used (`packs.row`); the next write repairs it.
- **Both rows read but differ** (nit 3): per rule, both recorded versions apply, a match if either matches and the heavier action winning (`packs.differ`). A version only one row records counts as unaccepted (below). An off → on write merges into each row on its own, so neither loses anything; acceptance writes one record again, with the higher version of the two per rule, and is weakening while the rows differ.
- **Neither row reads** (or the marker is there and both rows are gone): every known rule runs the **interim mode**, the stronger of its oldest retained and current versions, rules added after RP-0 included (`packs.lost`). Accepted widenings stay applied, since the current version includes them.
- **Which version is unaccepted with both rows lost** (nit 4): only version 1 of a rule that existed before RP-0 is known to be accepted (seeding recorded it). Every other version counts as unaccepted.
- **Skipped versions:** a recorded version whose code is gone runs the interim mode for that rule (`packs.skipped.<ID>`); both retained versions are unaccepted, since the accepted one is older than both. If any step from it to the current one isn't `widens` or `action-heavier`, or it has no record, it's also `packs.narrowed.<ID>`.
- **Unaccepted versions hold at most by quarantine.** Their action is capped at quarantine; an accepted version's isn't. This is slightly stricter than "an item matched *only* by an unaccepted version": an item an accepted version hides and an unaccepted one drops is quarantined, not dropped, because a drop isn't reversible without a preview (§1.8.7).
- **Downgrades:** a recorded version newer than the build's applies the build's current version (`packs.downgrade.<ID>`) and leaves the row. No record shows that version accepted on this install, so it's capped at quarantine like any unaccepted version: a downgraded MW-4 or FK-4 quarantines rather than drops. A downgrade has nothing pending. Every write merges per rule and never replaces a version newer than the build's current one (nit 5), so the upgrade back finds what was accepted.
- **Conditions are recorded in `filter.stand_ins`** as `packs.*` entries, replaced at each change and start, keeping when each was first found. `StandIns::reconcile` already keeps labels it doesn't know, so the stand-in re-judge never treats them as rules or classification rules. Showing them as a Filters & Safety notice is RP-3's (API) and RP-6's (screen).

- **The interim mode has a shadow too:** the current version alone. Accepting leaves it applying alone and accepted, so the preview has every torrent that changes (what only the older version held, and anything an unaccepted drop would now drop).

## Shadow and directions
- **Per torrent, each pending rule's two sides** come from `Engine::judge_shadowed` (`PackShadow`: the applied side's action, the shadow side's, so which side holds and whether the shadow action is heavier or lighter). `Verdict` itself is unchanged because `crates/filter/src/reclassify.rs` builds it field by field and isn't this slice's; the shadow side is also added to `Verdict::shadow` as a pack decision, so the writer logs it as a shadow hit (action bit `0x80`) the way it logs shadow rules, and nothing applies.
- **Shadow disagreement** (nit 1), any one of which makes accepting weakening whatever the record says:
  - `widens` (matches more, same action): a torrent only the applied version holds, or one both hold with a different action;
  - `action-heavier` (matches the same, heavier action): a torrent only one side holds, or one both hold without a heavier action.
- **Accepting strengthens** (`acceptance_strengthens`, for RP-3) only when the combined direction from the applied version is `widens` or `action-heavier`, the record isn't in doubt for the rule (both rows lost or differing, skipped, downgraded) and no shadow result disagrees. Anything else needs the password.

## Off → on, and what never accepts
- **A pack switched off → on records its rules' current versions** (those not switched off), and a rule switched back on from `rules_off` while its pack is on records its own, in the same transaction as the switch (`upgrade::set_pack_switch`). Both were previewed against those versions under §20.10.
- **A rule switched on while its pack is off records nothing:** turning the pack on later records it. On → on (a wizard re-run), a full-state write that leaves a pack on and Undo or redo restoring "on" record nothing.
- **With both rows lost, an off → on records nothing:** a record of only that pack's rules would leave every other rule pending, while the interim mode applies them all.

## Acceptance (Q7)
- **`upgrade::accept`, and `FiltersApi::accept_pack_versions` for RP-3,** set the accepted rules to their current versions and change nothing else, then reload the engine. The engine's version moves, so the writer's sweeps re-judge through the ordinary rule-change path. Nothing is released: tombstones and stored holds the new version wouldn't make stay for review, and only `release` with the warning and password lets them go.
  - **Rows that differ are merged one by one** (self-review), so a rule nobody accepted keeps both rows' versions rather than one being picked unpreviewed. They stay `packs.differ` until the differing rules are accepted.
  - **With both rows lost,** the fresh record has the accepted rules at their current versions and every other known rule at version 0, which keeps it in the interim mode. Ids this build doesn't know can't be recovered.
- **Seeding and acceptance never touch `rule_set_prev`.**

## SC-1 holds from before the split
- Holds made before RP-0 of game-currency items are stored under `SC-1`. Switching SC-1 off releases them although SC-2 would hold them; they're held again by SC-2 when seen again. Switching SC-2 off previews no holds of them. Neither releases anything SC-2's switch covers today without the warning and password, but RP-3's counts should know (named for its brief).
