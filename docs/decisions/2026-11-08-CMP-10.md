# CMP-10 decisions (PR pending)

Plugin dependencies on companions (architecture §18.1, §18.10; plan `docs/plan/2026-11-06-v06-companions.md` §4.3, CMP-10). It records the choices the brief delegates (§2.33) and the runner's answers of 2026-11-08 (marked *runner*). The runner flags the fourth answer, about the download-client source, to the owner (§2.19).

- **The map is a closed table in `lodestar_companions::requires`.** It maps a plugin manifest id to a `Requirement { satisfiers, suggest }`, met by any one of its satisfiers.
  - **Satisfiers** are `Companion(id)`, `AnyCompanion(Need)`, `ExternalClient` and `ExternalIndexer`.
  - **Entries:**
    - `prowlarr`: `[ExternalIndexer, Companion("prowlarr")]`, suggesting `prowlarr`.
    - `download_clients`: `[ExternalClient, AnyCompanion(DownloadClient)]`, suggesting `qbittorrent`.
    - i2pd gets an entry once its plugins and catalogue entry exist.
  - Nothing in a manifest or setting can add to the table or change it.
  - Plugin ids are written out, not imported, so `crates/companions` keeps no dependency on the plugin crates or the pipeline.
  - **Drift tests:** `pipeline/tests/requires.rs` checks every mapped id against `lodestar_sources_plugins::catalogue::manifests()`, and that none of them is a peer finder. The module's own tests check every companion against `builtin()`.
- **The download-client source needs "a download client", not a catalogue companion** (*runner*, 4).
  - **What meets it:** a client configured in Settings → Integrations that Lodestar doesn't manage (`Present::external_client`), or a healthy catalogue companion needed for `download_client`.
  - **Health:** an external client's own health stays the integration's business, as before. Only a companion Lodestar manages can make the source `unhealthy`.
  - **With neither:** the source reports `missing` and suggests qBittorrent, the wizard's recommendation (§18.10).
  - **Who reports it:** the configured-clients input arrives in the same snapshot, so `crates/companions` still doesn't depend on `crates/pipeline`. The sender decides which configured clients are external and which are managed. A managed one is listed under `companions` with its health.
- **The Prowlarr/Jackett source needs an indexer manager, not only the Prowlarr companion** (*runner*, review of #616, option a). The `prowlarr` plugin is the Prowlarr/Jackett source, and with Prowlarr alone a Jackett user would read "Needs Prowlarr" for ever once the gate is on.
  - **What meets it:** an indexer the user set as the source's own endpoint (a Prowlarr or Jackett that Lodestar doesn't manage, `Present::external_indexer`), or a healthy Prowlarr companion.
  - **Health:** an external indexer never reports `unhealthy`; only a managed Prowlarr can.
  - **With neither:** it reports `missing` and suggests Prowlarr.
  - **Who reports it:** CMP-5 sets `external_indexer` (the runner tells CMP-5).
- **`AnyCompanion` resolves through the catalogue and `MAPPED_IDS`,** so a requirement never borrows the catalogue.
  - A test fails when a catalogue download client isn't in `MAPPED_IDS`.
  - The suggested id always counts. If the catalogue fails to load, the role adds nothing, so the set only ever shrinks.
- **Per-plugin state is `State::{Ok, Needs(id), Unhealthy(id)}`, with ids as `&'static str`.**
  - `Ok`: a healthy companion that can meet it, or an external client where one counts.
  - `Unhealthy`: otherwise, the first companion present that can meet it.
  - `Needs(suggest)`: nothing present.
- **The gate fails closed.** `Snapshot::Unknown` (not read yet, or unreadable) and a closed channel both read as `Needs`. This holds in the gate and in the API (`Monitor::companion_state`), including a channel already closed before the gate first looks: the last value a sender left behind never counts.
  - So no gated plugin starts, and a running one pauses.
  - There's no fourth "unknown" state. The chip says "Needs X", which is true whenever the plugin isn't running.
- **The input is a `watch::Receiver<Snapshot>`,** `PipelineConfig::companions`.
  - `Snapshot::Known(Present { companions, external_client })`. A companion id that isn't listed is missing.
  - A watch gives "arrives → starts without a restart" with no polling, and only the latest value matters, so a burst of updates can't queue starts.
- **`companions: None` turns the gate off** (*runner*, 3). This mirrors `setup_done: None`, so the Prowlarr and download-client sources run as today until CMP-5 lands.
  - **CMP-5 must wire `Some`** (the runner is writing that into CMP-5's brief).
  - With `Some`, the gate is strict. Tests cover no snapshot yet, a closed channel from the start and a sender dropped later, and a unit test checks that a closed channel is never waited on again (no silent spin).
- **CMP-5 debounces companion health before sending.** Each health flip it reports restarts or pauses the plugin once and logs one line. The gate bounds this by the manager's send rate, not by a timer of its own.
- **The hook wraps the plugin's run inside its existing task, after the setup hold.** In `lib.rs`, the call to `p.run(ctx)` became `requires::run(...)`.
  - **Pause:** when the plugin leaves `Ok`, its run gets its own stop. The gate waits up to the plugin stop timeout, then drops the run and logs `pipeline.source_stop_timeout`, as the purge path does.
  - **Restart:** the plugin starts again once the requirement is met, with the same emitter and kit (so its state store too) and a fresh shutdown.
  - **A stop already requested** starts nothing, including one that lands between the last check and the run's creation: the gate re-checks after setting `running`, and a stop or snapshot is seen before the run is first polled.
  - **`running`** reads false while the plugin waits, and only after a paused run has ended or been dropped. A stop during a pause's wind-down (a purge's `stop_source`, or shutdown) drops the run at once, without waiting for it to end.
  - **Peer-request receiver:** this goes to the first run only, and no mapped plugin is a peer finder (tested).
- **Logs only on transitions:**
  - `pipeline.source_needs_companion` (info);
  - `pipeline.source_companion_unhealthy` (warn, "Source held: …");
  - `pipeline.source_companion_ready` (info, only when leaving a held state).

  Their fields are the `plugin` and `companion` labels, nothing else. A start that's `Ok` from the beginning logs nothing new.
- **API: `Source.companion_need: {companion, state} | null`, with `state` of `missing` or `unhealthy`** (*runner*, 1). The brief's name `needs` is already taken on `Source` (what enabling asks for, §18.7).
  - It's null when the plugin needs nothing, when the requirement is met, and while the gate is off.
  - It's computed live, for disabled sources too, so the Sources screen can show "Needs Prowlarr · Set up" before a source is enabled.
  - `/sources` already serves every source row the same way, so visibility is unchanged.
- **Shared edits beyond the brief's list** (*runner*, 2, approved):
  - `crates/lodestar/src/ops.rs` fills the field and tests its mapping and wire shape.
  - `crates/api/src/ops.rs` re-exports `CompanionNeed` and `CompanionNeedState` in its `pub use` of the DTOs.
  - The `Source` literals in `crates/api/tests/ops.rs` and `sources_spec.rs`, and `web/src/lib/features/sources/fixtures.ts`, gain `companion_need: None`/`null`.
  - `crates/pipeline/src/lib.rs` gains the config field, the `Monitor` field and the hook (`SourceStatus` and `SourceEntry` are unchanged).
  - `crates/pipeline/Cargo.toml` gains a dev-dependency on `lodestar-sources-plugins` for the registry test. That's a dev-only edge, and `cargo tree -p lodestar-companions` still shows no `lodestar-pipeline`.
