# CMP-10 decisions (PR pending)

Plugin dependencies on companions (architecture §18.1, §18.10; plan `docs/plan/2026-11-06-v06-companions.md` §4.3, CMP-10). These are the runner-delegated choices the brief lists (§2.33), plus the points I flagged to the runner.

- **The map is a closed table in `lodestar_companions::requires`.** It maps a plugin manifest id to a `Requirement`. There are two entries: `prowlarr → Companion("prowlarr")` and `download_clients → AnyOf { need: DownloadClient, suggest: "qbittorrent" }`. i2pd gets no entry until its plugins and catalogue entry exist. Nothing in a manifest or setting can add to the table or change it. Plugin ids are written out, not imported, so `crates/companions` keeps no dependency on the plugin crates or the pipeline. Two tests catch drift: `pipeline/tests/requires.rs` checks every id against `lodestar_sources_plugins::catalogue::manifests()`, and the module's own tests check every companion against `builtin()`.
- **"One of the download clients" is a role.** `AnyOf` is any catalogue entry whose `needed_for` holds `download_client`. It must also be listed in the module's `MAPPED_IDS` (a test fails when a catalogue download client isn't), so a result never borrows the catalogue. `suggest` is the client named while none is there: qBittorrent, the wizard's recommendation (§18.10). It counts even when the catalogue fails to load, which only ever shrinks the set.
- **Per-plugin state: `State::{Ok, Needs(id), Unhealthy(id)}`, ids `&'static str`.** Any healthy candidate gives `Ok`. Otherwise the first present (unhealthy) candidate gives `Unhealthy`. With no candidate present, it's `Needs(suggested)`.
- **Fail closed:** `Snapshot::Unknown` (not read yet, unreadable) and a dropped sender both read as `Needs`, so no gated plugin starts and a running one pauses. There's no fourth "unknown" state: the chip says "Needs X", which is true in every case where the plugin isn't running.
- **The input is a `watch::Receiver<Snapshot>`.** The binary hands it to `PipelineConfig::companions`. `Snapshot::Known` maps each installed or detected companion's catalogue id to `Healthy` or `Unhealthy`, and an id that's absent is missing. CMP-5's manager will be the sender. A watch gives "arrives → starts without a restart" with no polling, and only the latest value matters, so a burst of updates can't queue starts.
- **`companions: None` turns the gate off** (flagged to the runner). This mirrors `setup_done: None`. Until CMP-5 sends snapshots, a gate with nothing to read would switch off the Prowlarr and download-client sources on every install. With `Some`, the gate is strict as above. CMP-5 wires the receiver in `crates/lodestar/src/services.rs`.
- **The hook wraps the plugin's run inside its existing task, after the setup hold.** In `lib.rs`, the call to `p.run(ctx)` became `requires::run(...)`. The plugin waits on the snapshot and starts when the requirement is met. When it leaves `Ok`, the gate sends that run its own stop, waits up to the plugin stop timeout and then drops it. It starts again once the requirement is met again, with the same emitter and kit (so the same state store) and a fresh shutdown. Other plugins never see any of this. `running` reads false while the plugin waits or is paused.
  - **Peer-request receiver:** this goes to the first run only, so a paused peer finder would come back without it. No mapped plugin is a peer finder, and the registry test asserts that.
- **Logging on transitions only:** `pipeline.source_needs_companion` (info), `pipeline.source_companion_unhealthy` (warn) and `pipeline.source_companion_ready` (info, only when leaving a held state). Fields are `plugin` and `companion` labels, nothing else. A start that's `Ok` from the beginning logs nothing new.
- **API: `Source.companion_need: {companion, state} | null`, with `state` of `missing` or `unhealthy`.** The brief's name `needs` is already taken on `Source` (what enabling asks for, §18.7), so the field is `companion_need`. It's null when the plugin needs no companion, when the requirement is met, and while the gate is off. `Monitor::companion_state(plugin)` computes it live from the snapshot, for disabled sources too, so the Sources screen can show "Needs Prowlarr · Set up" before you enable one. `/sources` already serves every source row the same way, so visibility is unchanged.
- **Flagged to the runner (owner-level):** `download_clients` also reads Transmission and Deluge from Settings → Integrations, and neither is a catalogue companion. Once CMP-5 wires a snapshot, gating the plugin on "any catalogue download client" stops it for those users unless the snapshot counts a client configured in Integrations as present. That belongs to CMP-5's snapshot, not to the map.
- **Shared edits beyond the brief's list (told to the runner):** the `Source` literals in `crates/api/tests/ops.rs` and `sources_spec.rs` gain `companion_need: None`. `crates/lodestar/src/ops.rs` fills the field. `crates/pipeline/Cargo.toml` gains `lodestar-sources-plugins` as a dev-dependency for the registry test. That's a dev-only edge, and `cargo tree -p lodestar-companions` still shows no `lodestar-pipeline`.
