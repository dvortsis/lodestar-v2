# D-docker-guide-1115 decisions

Fixes to the Docker parts of the user guide, from the tester's run of the Docker install (2026-11-15). The guide describes v0.5.1 (runner's call: it matches what people install). This file says only what the guide now says and how it was checked.

## How the commands were checked

- The proxy here blocks ghcr's blob host, so the published image couldn't be pulled. The v0.5.1 binary was built from tag `v0.5.1` and run in a local test image with the same entrypoint, user, `/data` volume, environment and health check as `packaging/docker/Dockerfile` at that tag (an Ubuntu base in place of distroless).
- Run that way:
  - the v0.5.1 `docker-compose.yml` with the pinned image;
  - `docker exec lodestar /lodestar backup` and `docker cp`;
  - the named-volume restore, from a backup taken before setup (afterwards setup was required again);
  - `reindex` with Compose and with an Unraid-style bind mount owned by 99:100;
  - `reindex` while Lodestar runs, which refuses and changes nothing.

  The output in the guide is copied from those runs.
- Image tags were checked against ghcr: `0.5.1`, `0.5`, `latest` and `nightly` exist; `v0.5.1` doesn't. The wrong-tag and wrong-name errors in section 6.1 are Docker's own output.
- The gluetun Compose file passes `docker compose config`. `qmcgaw/gluetun:v3.41.3` exists on Docker Hub and has its own health check, which `depends_on: condition: service_healthy` relies on. It's the version the post-rules were checked on. The file wasn't run against a real VPN: no VPN keys are available here. Its step 6 check is the reader's proof that the rules loaded.

## What changed

- **G1:** a callout in section 2.4, before `docker compose up -d`, sends VPN users to section 3.3 first. v0.5.1 starts crawling as soon as the container starts.
- **G2:** section 3.3 gains a self-contained Compose file for v0.5.1:
  - Lodestar on `network_mode: "service:gluetun"`, starting only once gluetun is healthy;
  - gluetun pinned to `v3.41.3`;
  - the post-rules downloaded by commit and SHA-256 and mounted read-only;
  - port 8090 published on gluetun;
  - the VPN values as `FILL_IN_YOURSELF` placeholders.

  The companion templates are now marked newer than v0.5.1, with a pointer to chapter 8. The tester's "refused" Compose file is the companion one on `main`, which waits for a pinned gluetun digest (`awaiting_pin`). v0.5.1 has no companion files, so for this guide it's a docs gap, not a product bug (runner's reading, 2026-11-15).
- **G3/G4:** section 2.5 keeps v0.5.1's order (setup token, Legal Notice, password) and now ends on v0.5.1's **Setup complete** page. In v0.5.1 that page is **Setup complete**; the **Finish setting up** wizard the tester saw is on `main`. One line marks the next release's order (Legal Notice first) and wizard as planned.
- **G5:** section 3.7 gains Docker Compose backup and restore for the named volume.
  - The image has no shell, so the restore reaches the volume with `busybox:1.36`, one plain command per step.
  - Restored files are given to the image's user `65532`, or the reader's `PUID`/`PGID`. Start-up re-owns files inside `/data` only when the folder itself has another owner, so files copied in as root would otherwise be unreadable.
- **G6:** one way to rebuild the index, `lodestar reindex` with Lodestar stopped, as the backup's README and output say.
  - The Unraid restore uses it in place of deleting `index`.
  - A new part, "Rebuild the search index", gives the command for Compose and Unraid.
- **T1:** the image row in section 6.1 also matches Docker's `failed to resolve reference … not found`, and names the two usual mistakes: `lodestar` for `lodestar-v2`, and a `v` in the tag.
- **T2:** the parent-folder row is gone from section 6.1. The tester found it can't happen with a Docker bind mount. The message still exists in the code, for Linux installs without Docker (runner's call).
