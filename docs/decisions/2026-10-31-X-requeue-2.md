# X-requeue-2 decisions

Follow-up to X-polish-1031c (#286). Nothing is loosened: a classification re-queue now stays pending in more cases, never fewer. No schema, wire, setting or log-event change.

- **A pending re-queue is cleared only once an index has marked its matches** (`crates/api/src/filters.rs`). Without a search index (`search.enabled = false`), `FiltersApi::requeue` keeps the `classify.requeue_pending` entry instead of clearing it. This covers a rule added while search is off, and a re-queue cut short by a shutdown and followed by a start with search off.
- **Search is turned on by a restart, so the existing start hook is the index-available hook.** `search.enabled` is a restart field (`crates/lodestar/src/settings/search.rs`), and the search handle is fixed when `FiltersApi` is built. `services.rs` already runs `resume_requeues` at every start, so the first start with search on marks the matches of every entry left pending. Only its comment changed in `services.rs`. A fresh index that hasn't caught up yet is covered too: everything past its watermark is marked.
- **Pending entries are deduped,** so the list stays bounded while search is off: there's at most one per query text, however often that rule is added and removed. Because two rule changes can now share an entry, a re-queue clears it only if the classification generation hasn't moved since the re-queue began. Every change up to that generation was in force before its search, so its marks cover them. If another change came in meanwhile, the entry stays and is redone at the next start, which is harmless. A refused removal (no such rule) clears the entry only if it added that entry itself.
- **`resume_requeues` doesn't stall:** an entry that fails stays, and the loop goes on with the rest. Only the shutdown stops the loop. The failure is already logged where it happens by `api.internal_error`, which records the error's type only. That follows the Private preset: no query text and no names. So no new log event was added.
- **The search sibling-stop test** (`crates/search/src/files.rs`) injects the failure with a test-only query whose scorer fails for one segment once both siblings are scanning. The siblings match their one document endlessly until a 20 s deadline. The test asserts three things: the injected error is the one returned, no sibling reached its deadline, and nothing was cached. No production hook was needed.
- **The failing-entry test** uses a `#[cfg(test)]` thread-local in `filters.rs` that makes one query text fail every time.
