# RP-5 decisions: SP-4, clones of hidden spam, judged in the writer

Plan `docs/plan/2026-11-04-v06-rulepacks.md` §4.3 "RP-5", line 47 (storage) and Q12; architecture §20.1, §20.6, §20.7. Builds on RP-0 (versions, shadow, lost state), RP-2 (overrides) and RP-4 (SP-3's entry point in the writer). No migration: SP-4's set is `settings` rows (Q9). No owner decision, security or content-safety decision, or owner-set number changes. Q12's numbers are the runner's; two refinements of them below are flagged for the runner (§2.19, §2.26).

## The set (`crates/filter/src/spam_sigs.rs`)
- **Q12's numbers:** at most 1,000,000 signatures, the oldest dropped first. Packed at 8 bytes per signature as stored, so 8 MB at the cap.
  - **In memory it's about 45 MB at the cap** (a refinement, flagged): 8 bytes per entry, plus an index from signature to entry. Q12 states the stored size. The index is a std `HashMap` under SipHash with keys drawn at start, because a payload signature is a hash of file sizes the sender chooses (`fmix64` can be inverted).
  - 45 MB is 4.5% of the 1 GB RSS budget. A tighter index (a `u32` location, or sorted runs) can win back about half if needed.
- **Rows:** `settings` keys `filter.sp4.sigs.<n>`, numbered in the order they're started. A row is a blob: the format byte `1`, then 8 bytes per entry, little-endian. `Store::update_settings_raw` writes it and `settings_with_prefix_raw` reads it. An entry is the signature with its low three bits replaced by flags: removed, hide (otherwise demote) and by SP-3 (otherwise SP-2). The signature keeps 61 bits, and a sender can't set the flag bits. Entries are appended to the newest row only. When it's full, the next row starts.
- **Row numbers stay below 2^39** (`ROW_BAND`, half the index's 2^40 bound; runner, #510).
  - A key at or past that, corrupted or another build's numbering, is listed as lost under a sanitized label. It never sets where new rows start, so numbering can't wrap or land on it.
  - No row is started at or past the band. Reaching it from row 0 takes 2^39 rows of 511 hides; only a stray readable row just under it can bring it close.
  - If the numbers ever run out, the set stops growing and lists `packs.sp4.row.numbers`, rather than write a row a restart wouldn't read.
  - Cap eviction stops if it ever finds nothing to drop, rather than spinning under the lock.
- **Rows of 4 KB, not 64 KB** (a refinement of Q12, the runner's call under §2.26; flagged). A row is rewritten whole with each batch that adds to it. In this session's container, writing a 64 KB row cost about 200 µs. A 4 KB row cost about 17 µs, which is mostly the transaction itself. At 4 KB a batch's write stays inside the 5% gate (measurements below). Q12's 64 KB is still the limit a row may have when read, so a longer row another build wrote still loads. A row holds 511 entries, so 1M signatures take about 2,000 rows.
- **Releases append removals.** The row that holds the signature isn't rewritten. On load the last entry for a signature wins.
- **Compaction:** once a quarter of a row's entries are dead (removed, added again later, or dropped by the cap), that row alone is rewritten without them, or deleted when nothing is left.
  - A removal is kept while a stale add of its signature is still stored. That's an add no longer live, counted per signature as adds die and as compaction drops them.
  - So the check is one map read, and compacting a row costs that row, never the set. A flood that keeps adding one payload after a release stays cheap (measured below).
  - **Known limit** (runner, #510): a row left holding only removals, still needed when it was last compacted, isn't revisited once the add they cancel goes. It stays until something else in it changes. Removals come only from your releases, so such rows are bounded by them.
- **The cap isn't written.** It's applied again on load, oldest first, and dropped entries go when their row is compacted. Until then, a restart after releases have taken the set below its cap can bring a few back: at most a quarter of a row, the newest of those dropped. That errs strict.
  - A release of a signature the cap dropped but whose add is still stored appends a removal, so a release never comes back. The property test found that case.
- **Recorded, not looked up:** the brief left the choice open. The inherited action and the original's rule go in the entry's flag bits. A lookup would read the original's `filter_hits` row at each clone's commit. It would also lose the action once `filter_hits` retention drops the row, while the signature can outlive it.
- **The lock is held across a write** (runner, #510). `flush` and `release` hold the set's lock while their row is written, so a store busy with another connection's transaction makes a commit's lookup wait, up to the store's busy timeout. It can't deadlock: neither side holds a transaction open while it waits for the lock.
- **Shared, not copied.** `Engine` holds the set in an `Arc`, so every engine version shares it, and so do the writer that adds and the API that releases. A rule reload neither copies nor reloads it. It's loaded once, at start (`load_filter`, through `Engine::load_spam_sigs`). Each write to the store happens under the set's lock, so the writer's and the API's rows can't land out of order. Neither holds a store transaction open while it waits for the lock.

## Fail closed
- **An unreadable row loses only its own signatures.** That covers a row that isn't text, one that isn't this format (a newer build's row after a rollback), and a key that isn't a row number. The row is left as it is and never written over: new rows are numbered past every row seen, lost ones included. It's reported as `packs.sp4.row.<n>` in `filter.stand_ins` and in `GET /filters`'s `pack_conditions`, the way RP-0's lost-version conditions are: `note_pack_conditions` adds the labels, and `StandIns::with_packs` keeps them while they hold.
- **A lost row goes once the cap passes it.** When the cap drops something newer than anything the row could hold, every signature in it would have been dropped already. The row is then deleted and drops off the notice.
- **`Store::settings_with_prefix_raw`** (new) reads each row as text or as its bytes. One non-text row then spoils only itself, where `settings_with_prefix` would fail the whole read.

## What feeds the set
- **SP-2 at hide, or SP-3 at demote or hide, deciding a stored torrent at commit** (`Original::of`). The brief says "hidden by SP-2, or by SP-3 at demote or above" and "only real hides of stored torrents count".
  - A quarantine or a drop, through an override, isn't stored, so it doesn't feed the set.
  - SP-2 at flag or demote through an override isn't a hide.
  - SP-3's flag never counts.
- **Only specific payloads** (a refinement, flagged): at least 50 MB, or two files of distinctive size. This is the same test that keeps CS-8a from blocking unrelated torrents (`PayloadSig::specific`). §20.6 says SP-4 needs no false-positive guard, but a lone 30 KB text file or a round-sized placeholder is a payload unrelated torrents share by chance. Without the test, one keyword-stuffed `.txt` would hide every torrent of that size. A non-specific payload never joins the set and is never looked up.
- **In memory at judging, in commit order; written after the batch.** A clone later in the same batch is caught, which matters because spam floods send clones together. Each batch writes one row (two when a row fills, plus a compaction now and then), in its own transaction after the batch's. The write happens whether or not the batch committed, so memory and the store agree, and a failed write stays pending for the next batch.
  - **Errs strict:** a batch whose write failed, or a commit refused at the write because its hash was held since judging, keeps the signatures it added.
  - **Errs loose, by one batch:** a crash between a batch's commit and its row loses that batch's signatures.
- **Added with SP-4 off,** so switching it on finds the originals. A clone that SP-4 hid adds nothing: its signature is its original's.
- **Only the deciding rule feeds the set.** A torrent SP-2 matches but another rule outranks (a heavier action, or a tie with a rule later in the evaluation order) adds nothing. Its stored mark isn't SP-2's, so releasing it wouldn't be SP-2's either.
- **Imports neither feed nor check SP-4.** `lodestar import` and the importers judge through their own driver, not the writer's commit: the same scope as SP-3.
- **Never fed by claims, enrichment or the torrent cache's lookups.** Those are judged outside the writer's `judge` and never add a signature (`sp4_is_never_fed_by_claims`). A torrent cache's file is a real stored torrent, judged at its commit like any other, so its hide counts.
- **Not on later re-judgments:** a stored torrent judged again later (reclassified as adult, §20.9) neither adds nor checks. The writer's commit is the only place.

## The rule (`crates/filter/src/packs/sp4.rs`)
- **Judged in the writer only,** like SP-3: prepare's verdict leaves it out. The writer looks a commit's signature up only while SP-4 is on and the set holds something. On a hit, it judges the torrent again through `Engine::judge_at_commit`, RP-4's entry point generalized (`AtCommit { flood, clone_of }`; `judge_flooded` remains as its SP-3 case). A commit that's both flooding and a clone is judged once with both. Precedence is the engine's own: the floor, CSX-5 Override, the core, your exceptions, *Always allow*, your rules, then the pack layer with SP-4's switches, your exception for it and your override, where the strongest action wins. Every SP-3 precedence test has an SP-4 twin in `crates/filter/tests/sp4.rs`.
- **A clone inherits its original's action,** demote or hide. The version's action is hide, capped at the original's (`sp4::cap`). An override you set (RP-2) replaces it wherever SP-4 matches.
- **SP-4 is first in the spam pack's evaluation order,** so a tie never moves a decision from a rule that matches the torrent on its own. The spam pack's overview and versions line now list SP-4 first (SP-4, SP-2, SP-1, SP-3). That's harmless, but RP-6's overview shows that order. The pack layer's strongest-action pick keeps the last of equals. A keyword-stuffed clone stays SP-2's, and an SP-3 demote that's also a clone stays SP-3's. `PackRule::index` keeps its declaration order (SP-4 last), and the `pack_versions` record is unaffected.
- **Added after RP-0** (`ADDED_AFTER_RP0`): pending in shadow on an upgraded store, applied on a fresh one. Its first version `widens`, its shadow side holds only what the applied side (nothing) doesn't, and the sequence fixtures check that. RP-1's corpus already exempts it (`corpus::STATEFUL`). The manifest's per-rule golden marks every third item as a clone.
- **CHANGELOG:** `SP-4@1` in `crates/filter/data/packs/spam/CHANGELOG.md`. The API goldens are re-blessed for that text and the spam pack's version line only.

## Release follows the original
- **The switch:** a clone matches only while the original's rule (SP-2 or SP-3) is on. Turning that rule or the spam pack off, which goes through `release_rules`, lets the clones through. Turning it back on restores them, because the signature stays.
- **An exception to the original's rule that covers the clone** lets it through at judging: one for the payload covers every clone, one by name or query covers the clones it matches.
- **The release hook** (`crates/api/src/filters.rs`):
  - An exception for SP-2 or SP-3 by hash removes the signature of each stored torrent among its hashes. An exception by payload removes that signature. Either way, only a signature that rule added is removed, so an exception to SP-2 leaves what SP-3 hid.
  - `release` and `release_many` remove the signatures of the stored torrents among the hashes they free.
  - **A clone releases only itself** (runner, #510; errs strict). When a hash's own newest hit is SP-4's, a release or an exception by its hash leaves the signature: the clone is let through by its own mark, and the rest of its family stays held.
  - `Change::Release` on a stored original the set holds succeeds: it removes the signature, and the clones follow. The original itself stays hidden: its own rule still matches it, as a quarantine release is judged again.
  - Each removal is written under the set's lock before the change returns. A failure returns 500 after what committed, as `unhold` does.
  - **Undo follows too:** a change that removes or restores exceptions (removing one, Undo, redo) compares SP-2's and SP-3's exceptions by hash before and after.
    - One that's gone puts the stored original's signature back only if that rule decided it: the torrent's newest applied hit in `filter_hits` names the rule, with an action that feeds the set (`Store::latest_hit`), and its mark is still on. A torrent your rule or another pack rule hid never becomes an original this way (the runner's blocking finding on #510). A signature already in the set is left as it is.
    - `latest_hit` scans `filter_hits`, which has no index on the hash. It runs only on these rare changes, and in the release hook only for a signature that's in the set. Once `filter_hits` retention drops an original's hit, its Undo puts nothing back, which errs loose for that original until it's hidden again.
    - One that's back removes the signature again.
    - An exception by payload that's gone can't put a signature back, because the original isn't known. Its clones stay released until an original is hidden again.
  - The `Release` change's warning still describes a quarantine release. On a stored original it lifts the clones and leaves the original hidden; RP-6's copy can say so.
- **Known limit, for the runner** (a narrowing of the plan's "an exception for the original removes its signature"; flagged): an exception by name or query doesn't remove the original's signature. It lifts the clones it matches itself, but a clone it doesn't match stays hidden. That errs strict. Finding the stored originals a query matches needs a walk of `filter_hits` or the index, left for RP-6 if the screens want it.

## A threat, for the runner
- **Pre-hiding a real release:** a payload signature is only file sizes. Someone who publishes a keyword-stuffed torrent with the exact sizes of a popular release gets it hidden by SP-2, and later copies of that release are then hidden by SP-4.
  - It touches spam hides only, never the core or the floor, and torrents already stored keep their marks.
  - You undo it with an exception for the planted original, or for the payload.
  - §20.6 gives SP-4 no guard, and the specific-payload test doesn't help, since the copied payload is specific.
  - **A follow-up guard slice, decided by the runner** (#510): no signature is added while a stored torrent with that payload isn't hidden. It's flagged to the owner. Until then the remedy is an exception for the planted original, or for its payload.

**The writer** (`sp4_writer_cost`, ignored; `cargo test --release -p lodestar-pipeline --lib sp4_writer_cost -- --ignored --nocapture`).
