# GS-2b decisions (`group_key` producer, a fast column only)

Spec: architecture §8 "Results, facets and features" (collapse-by-group) and §3 (the 512 B torrent-index budget); plan `docs/plan/2026-11-05-v07-m7.md` Q8, Q10; `docs/decisions/2026-11-12-GS-2.md`, which left `group_key`'s shape for GS-3 to settle with the runner; the population contract (`docs/decisions/2026-11-04-SB-6.md`).

- **The runner's call (2026-11-16, under §2.26 and Q10), flagged to the owner (§2.19): `group_key` is a fast column only, ~8 B per torrent.**
  - GS-2 left `group_key` with no producer. Declared `INDEXED | FAST`, writing it would copy `title_identity`'s whole term dictionary (~30 B per torrent).
  - Collapse-by-group (GS-3) needs each document's group in a column: to keep one row per group while it walks the ranked order, and to count groups exactly up to 100k. It finds a group's members through `title_identity`'s term, which holds the same value, so `group_key` doesn't need to be indexed.
  - Without a producer, collapse would always answer ungrouped, and the owner wants "Group versions" on by default (owner-decisions §2.66 item 2). The other options are in GS-3's message to the runner: inverting the terms in RAM costs ~9 B per document of memory, and store lookups are too slow for exact group counts.
  - `INDEX_BUDGET` (512 B) is unchanged.
- **The value is `doc::title_identity`, the same value as the document's `title_identity` term** (plan Q8: one identity rule). `TorrentDoc::to_document` writes both from one `Option<u64>`, so a torrent without a parsed title has neither, and "+N others" (GS-3) agrees with Related's other versions (B13b). `crates/search/tests/grouping.rs` checks, for every document against a real store, that the column equals its record's identity and that the field isn't indexed.
- **Schema v8: `SCHEMA_VERSION` 7 → 8.** Tantivy can't change a field's options in place, so the change is a version bump on the existing blue/green rebuild path (§8 "Index evolution"). An existing index keeps serving while v8 is built from the store, then the swap.
  - `crates/search/tests/rebuild.rs` adds `a_v7_index_rebuilds_to_v8_and_group_key_reads_ready`. A v7 index (`group_key` indexed and fast, never written) serves during the rebuild. After the swap, `group_key` reads `Ready`, is a column only, and every torrent carries its record's identity.
  - The v5 → current test now counts `group_key` as produced and expects schema 8.
  - **Release note for the runner:** v0.7 already walks once for the M7 producers (plan §3). The bump turns that into a full rebuild, which plan §3 measured at ~1 h 55 min idle at 10M (both indexes). Search serves throughout.
- **`GENERATIONS["group_key"]` 0 → 1.** A rebuild writes it for every torrent, and new documents carry it. A same-schema index from GS-2's build would walk for it under SB-6's contract, but with the schema bump no such index opens as current. A v7 index serving during the rebuild isn't reconciled with this build's generations (`read_only_population`), so it isn't walked. It keeps reporting `group_key` as having no producer, and GS-3 answers ungrouped from it. `population.rs` adds `the_group_key_producer_starts_a_walk` for that path.
- **The "field without a producer" stand-in moves to `name_trigram`**, which nothing writes until RX-1. It replaces `group_key` in `population.rs`'s minhash test and in `tests/index.rs`'s fresh-index test, so that path stays covered (as GS-2 moved its stand-ins off `group_minhash`). `population.rs`'s empty-index and missing-record test keeps `group_key` at an artificial generation 2: it tests the walk rule, not the producer.
- **Ownership:** `crates/search/tests/rebuild.rs` was added to GS-2b's owns (its version assertion and produced list change with the bump; no other running slice owns it). Named to the runner in the PR.
- **Size (`size-report --torrents 50000`, local):**
  - **Before (main at 5523583d):** the torrent index is 495.8 B per torrent. CI's gate measured 495.7 B on #804's final head (X-gs2-nits).
  - **After:** 502.6 B and 503.0 B in two runs, PASS under 512 B. `fast group_key` adds 8.0 B, and the 1.0 B of `group_key` norms that came with `INDEXED` is gone, so the net is about +7 B.
  - The other budgets are unchanged: store 948.3 ≤ 1024, file index 789.2 ≤ 800, file-tree blob 346.1 ≤ 600.
  - **Headroom left under 512 B for RX-1 and ENR-11 together: about 9 B** (9.0–9.4 B locally). CI's `size budget (§3)` figure on the PR head supersedes it.
  - Plan §3's estimates already put RX-1's trigrams over the budget (Q10's expected case). That's Q10's steps (a)–(d), unchanged by this file.
- **Unchanged:** the relevance gate (NDCG@10 0.9186, floor 0.9176, PASS) and the search goldens. `group_key` isn't in the query language, and nothing ranks by it.
