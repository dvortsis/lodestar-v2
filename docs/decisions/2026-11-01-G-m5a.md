## The reporting-overhead benchmark

`bench/examples/reporting-overhead.rs`. **It is an example, not a bin:** it drives `lodestar-api`'s router in process, and as a dev-dependency the API stays out of the bench gates' change detection (`.github/scripts/ci_changes.py` follows normal dependencies only). As a normal dependency, every API change would start the search-latency, size and relevance jobs.

- **What it measures.** A 100,000-torrent synthetic corpus with a year of the widened rollup hour (below) in the same store. Search p95 goes through the real `/api/v1/search` route, sharing the store reader with Insights as the server does. Ingest is store, enrich and index in the writer's 500-torrent batches, with a commit each. Each runs with and without a load: an open Insights tab's refetch (the overview and the Fetch page at `range=7d`, with the cache made stale first, as a flush does) plus a digest preview (the digest job's whole computation), once per 30 s.
- **The UI's rate, not faster.** The tab refetches on each `insights` event, one every 30 s (`crates/api/src/events.rs`). An early run at one round per second measured collisions with the overview's turn on the shared reader (+5 to +87% per run), not an open tab. A round costs about 25 ms, about 0.1% of a 30 s period.
- **Phases.** Six pairs of 30 s search phases on a fixed corpus, then six pairs of 10,000-torrent ingest phases. Base and loaded alternate which goes first, and the count is even, so each goes first in half the pairs: each ingest phase grows the corpus and the next one is slower (base ingest fell from 622 to 574/s across one run). The first version ran five pairs, which put loaded second three times. Reported: medians, the median of the paired per-run deltas, and their spread.
- **Storage.** The bench fixture's busiest hour of rollup and cohort rows (14 + 13–15) is repeated for a year, compacted (30 days hourly, the rest daily) and vacuumed: 0.66–0.69 MB a year (0.46 MB before watermark rows were counted). B11a's wide hour (`year_of_rollups`, 113 + 28 rows), widened with every other metric code (6–8, 13–15) and all ten loss reasons, is the busy crawler's bound (173 + 30 rows): 3.44 MB a year. Both years include an `index_watermark_hour` row an hour, which is never pruned. Budget 50 MB (50,000,000 bytes).

### How each gate runs
- **Matrix:** `cargo test --workspace`, so every PR that touches Rust runs it (about 4 s for the fixture test, under 1 s for the counters test).
- **Overhead:** about 17 minutes, too long for a PR's CI. It is a nightly job, `reporting overhead (§3)` in `ci.yml`, run on `schedule` and `workflow_dispatch` and kept out of `ci-ok`. The workflow's `concurrency` group cancels a run in progress when `main` takes a push, so a nightly can be cancelled. A separate workflow file would avoid that, but it's outside this slice's paths. It is also a local gate for changes to Insights, the digest or the store reader: `cargo run --release -p lodestar-bench --example reporting-overhead -- --gate`.
- **The operative gate is the duty cycle:** one round (overview, Fetch page, digest preview) may take at most 1% of the UI's 30 s period (300 ms). That share bounds what Insights can take from search or ingest, and it carries no run-to-run noise. Today's round is about 25 ms (0.1%).
- **Noise allowance, proposed for the runner to decide (`docs/owner-decisions.md` §2.26; flag for the owner, §2.19):** the timed gates are each budget plus **3 points**: search p95 at most +8%, ingest at least −5% (median of the six paired deltas). At the UI's rate the timed deltas are noise, so these gates catch only gross regressions; a regression up to 3 points past a budget passes them by design, and the duty-cycle gate is what holds the budget. Storage needs no allowance. Against the raw budgets, two runs measured ingest past −2% (−2.3% in the first table, −3.2% in the five-pair run) and one measured search at +4.9%, just inside +5%. All are inside the per-pair spread, and the other runs land on the other side.
