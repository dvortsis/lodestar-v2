# X-sec-S8-27 decisions

Fixes held finding S8-27 (low; surface dht restart snapshot). Builds on `docs/decisions/2026-11-24-X-split-resume-gate.md`, whose restart path for the spill filter it changes as below; everything else there stands.

§2.19 flag for the owner: security-relevant change to the restart snapshot (a new snapshot version, fresh spill filter keys on every start, and owner-only file modes on Unix).

## What the code now does
- **A rebuilt spill filter never places a new cooldown with keys read from a snapshot.** `Spill::restore` keeps each section of the snapshot read-only, under the SipHash keys it was made with, and draws fresh random keys for everything the filter takes in from then on (`crates/dht/src/node/sampler.rs`, `spill::Frozen`).
  - **Lookups ask every set of keys.** `contains` and `shares` count matching live slots under the filter's own keys and under each read-only section's, so every restored cooldown is still found and still counts against its IP and block until it ends. A count is still never low, only sometimes high.
  - **A read-only section is dropped** by `Spill::sweep` once its last cooldown has ended. Seeded ends are capped at the restart horizon H, so that is within H of the start (`read_only_sections_are_dropped_by_the_horizon`).
  - **Capacity is judged over all of them.** The fallback line (`spill::FALLBACK`) counts live cooldowns in the read-only sections too, so the filter never holds more live cooldowns in total than before.
- **A snapshot taken while read-only sections are kept stores every set with its own keys.** `Spill::export` writes one section per set that still holds a live slot: the read-only ones oldest first, then the filter's own. The next start restores all of them read-only and draws fresh keys again (`a_rebuilt_filter_takes_new_cooldowns_under_fresh_keys`). So keys move from live to read-only at every start and never back.
- **At most `MAX_SPILL_GENS` (8) sets.** With 8 read-only sections kept (eight restarts within about H that each spilled), the filter takes nothing new until the oldest is dropped: `has_room` is false and `insert` refuses, so cooldowns stay in the table, as with the switch off. No cooldown is shortened and no hold is added (`with_every_section_place_taken_nothing_new_moves_in`; the proptest `no_node_is_sampled_in_cooldown` still asserts a restart needs no hold).
- **Under the `testing` feature** fresh keys are a fixed per-thread sequence instead of random, so simulator runs repeat and a rebuilt filter's keys still differ from the restored ones. Only `crates/crawler-sim` enables `testing`; release builds are `cargo build -p lodestar`, and `cargo tree -p lodestar -e features -i lodestar-dht` shows no `testing`.

## Restart files
- **On Unix the restart files are created with mode 0600** (owner read and write only). `restart::write_atomic` (the snapshot, the state file and the clean marker) removes a temp file left by a crash and creates the temp file afresh with that mode, so the renamed file has it. `overwrite_in_place` creates a missing marker or witness the same way; an existing one keeps its mode, and none of those holds keys (`restart_files_are_written_private`).
- **On Windows** a new file takes the data folder's permissions (its inherited ACL); the code sets nothing there.

## Format (for the runner's review)
- **Version 3 of the snapshot container, written only when the filter holds more than one set of keys.** One set is version 2, byte for byte as before; nothing spilled is version 1, as before.
  - `spill`: the sections end to end, oldest first, each in version 2's layout (a count byte per block, then its words).
  - `spill_keys`: 16 bytes per section, in the same order, two to eight sections. Version 3 has no `spill_key`.
  - Decoding is strict: each section is cut at the length its count bytes give and checked as version 2's is (no empty section, no block over 64, no bad tag or minutes), the sections must fill `spill` exactly, and together they hold at most one filter's slots (2^23). Capture refuses what decode would (`key_generations_roundtrip_and_are_checked`).
- **Compatibility:** version 1 and version 2 files decode and resume as before; a version 2 section is restored read-only like any other. A binary before this one reads a version 3 file as an unknown version and takes the full suppression, never a shorter wait.
- **Size:** the read bound grows by a count byte per block for each extra section (128 KiB each, 1 MiB at most). The slot bound is unchanged, so a full snapshot is still about 32 MiB.
- **Fuzzing:** the `dht_restart` target also seals at version 3 (form bit 2), and its expansion builds two sections from the sparse list (bit 23 of a record's block picks the section). New seed `v3_two_keys.bin`, a valid snapshot built by `the_fuzz_seeds_are_current`; the other seeds are unchanged.

## Memory (against `2026-11-24-X-split-resume-gate.md`)
- **A read-only section costs 4 bytes a live slot, plus a 512 KiB block index and 16 KiB of end counts.** It replaces the restored 32 MiB slot table, and the filter's own 32 MiB is allocated at its first new insert, as before.
- **So for at most about H after a start the filter can hold up to about 32 MiB more than before:** decode bounds the read-only sections to one filter's slots in all, a snapshot this binary writes holds no more than the fallback line (about 7.9M live slots, about 30 MiB), and a typical filter (about 2.2M live at WK-10e scale 1) adds about 9 MiB. Once they are dropped, the filter is as before.
- **The start's peak is unchanged:** the file, the decoded sections and their seeded copy as before, and the rebuild packs the sections instead of filling a 32 MiB table, so still about 130 MiB at worst, once. This fits the 1 GB steady-state RSS budget (architecture §3).
- **Lookups** cost one keyed placement and two block scans per kept section: twice today's in the first hours after a start, at most nine times with eight sections kept.
