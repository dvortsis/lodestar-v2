# WK-4 decisions (PR pending)

WK-4 adds the DHT keyspace shard of §19.5 `sharded(keyspace)` (`docs/plan/2026-11-06-v06-workers.md` §4, WK-4 row). These points refine the plan row where it left something open. None of them loosens an owner decision or changes an owner-set number.

- **What counts as the full shard.** The full shard covers every prefix (`0..256`) and all 8 BEP 42 slots (`Shard::FULL`). The actor treats it as no shard: it doesn't store the shard, and it takes the code path from before WK-4 (`cfg.shard.filter(|s| !s.is_full())`). That makes "full-range shard = no shard" hold by construction, at any id count. Any other shard is a sub-range shard, and that includes a shard with every prefix but fewer slots, or every slot but a narrower range. A sub-range shard caps the node's ids at its slot count (`Shard::id_cap`). The plan row ties the cap to sub-range shards only; this point makes the boundary exact.
- **A shard narrower than the 256 prefixes always uses the prefix cursor.** With `dht.target_prefixes` off, targets are drawn at random, and a random target wouldn't stay in a narrower range. So such a shard turns on CR-1b's cursor over its range whatever the switch says. A shard over every prefix (fewer slots only) needs no cursor to stay in range, so the switch decides, as it does with no shard (§19.8 single-machine parity). With the cursor on, the `target_prefix_*` counters count the shard's queries, and a cycle is a pass over the shard's range.
- **`docs/metrics.md` needs a follow-up.** Its target-prefix section says the `dht_target_prefix_*` series stay 0 with the switch off and that a cycle is a pass over 256 prefixes. Neither holds once a narrower shard is set. Nothing sets a shard until the worker runtime (WK-10), so nothing is wrong at runtime today. `metrics.md` isn't in WK-4's owns: the runner amends it, or names the slice that does (WK-10 is the natural one). The `Stats` doc comment in `node/mod.rs` already says so.
- **How the cursor walks a sub-range.** It walks the same bit-reversed pass as the full range and skips positions whose prefix is outside the range. Each prefix in range is still used once per pass, and consecutive targets stay spread across the range. With the full range, the cursor is the one from before WK-4, step for step.
- **Slot assignment.** In `secure_id::virtual_ids_in`, id `i` takes the `i mod n`-th set slot in ascending order. Bits 3–5 of `r` count `i / n`. With all 8 slots this is `virtual_ids`, draw for draw, and `virtual_ids` now calls it.
- **Disjoint slots never share a prefix, for any address.** CRC-32C is affine over GF(2) for a fixed input length. Two slots' BEP 42 inputs differ only in their top 3 bits, so their 21-bit prefixes differ by an amount that depends only on the XOR of the two slots, never on the address. The test `slot_prefixes_differ_for_every_address` checks all 7 possible XORs for IPv4 and IPv6, which covers every address. So shards that share an external IP and hold disjoint slot sets never mint the same BEP 42 prefix. A property test checks the same thing directly.
- **When saved ids are kept.** With a saved public (non-exempt) external address, the saved ids are kept only if there are at least as many as the cap and the first ones up to the cap are all valid for that address, in the shard's slots and in distinct slots (a hand-edited or corrupt state file could repeat one). Otherwise every id is regenerated in the shard's slots. A partial keep would save little: ids change only when the shard or the address changes. Without a saved public address the ids aren't BEP 42 yet. The saved ids are then kept as before, capped, and the address vote re-ids them inside the shard.
- **The shard is fixed for a node's lifetime.** The actor reads `Config::shard` once at start. When WK-5 or WK-10 assigns a different shard, the node restarts with the new config; WK-4 adds no runtime setter.
- **Unchanged.** Per-node BEP 51 intervals and per-IP limits stay as they are. Dividing them among workers behind one IP is WK-5's job (plan Q5, Q9).
- **Shared-file edits.** WK-4 adds `pub mod shard;` and the `shard` field to `crates/dht/src/node/mod.rs`, as the slice notes allow. Three integration tests build `Config` with every field listed (`crates/dht/tests/{harvest,network,scrape}.rs`). Each gains one line, `shard: None,`: a struct-literal update for the new field; no assertion or behaviour change. The runner approved it (2026-11-06T15:25Z), and WK-4's `owns` in `runner/slices.yaml` now list the three paths.
