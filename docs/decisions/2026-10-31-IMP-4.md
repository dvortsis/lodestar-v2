# IMP-4a decisions: the import driver, merge, provenance and removal

The first of IMP-4's two PRs (the runner's planned split). This one runs a job end to end: the driver, the full filter on every record, the merge rules, provenance, and taking a job's records back. The `lodestar import` CLI, the user docs and the throughput measurement are IMP-4b, which adds its own file (`…-IMP-4b.md`). No migration.

## The driver (`crates/sources-importers/src/driver.rs`)

- **One driver for both adapters.** `Adapter` wraps an opened `magnetico::Source` or `bitmagnet::Source`. Each record goes to the store through **its adapter's own mapping** (`TorrentRecord::import`, `CandidateRecord::import`), so the completeness, verification and privacy rules IMP-2 and IMP-3 set stay in one place.
- **Identity before anything is read.** The adapter's identity is compared byte for byte with the job's `{dataset, schema_sig}`. If it differs, the running job is blocked with `source_changed` and nothing is read. Each adapter also checks again before every batch (IMP-2, IMP-3).
- **Phases:** the driver moves a new job `inspecting → ready → reading`. When the source is exhausted it moves it to `committing`, then `indexing`, where IMP-1 says it waits for the index. Completing it after indexing is IMP-4b's job (the CLI reads the index watermark the server records).
- **One transaction per batch:** the driver calls `Store::commit_import_batch` once per source batch, with `seq` = cursor + 1 and the adapter's position. Records, filter hits, quality, provenance, counters and the cursor commit together (IMP-1).
- **A record `Store::prepare` rejects is committed as `Invalid`** (IMP-2's rule), and counted as `prepare_rejected` in the run's per-reason counts.
- **Refusals:**
  - an adapter refusal with a job reason (`source_changed`, `source_unavailable`) blocks the job with it;
  - one without (an unsupported or refused source) fails the job with `source_unavailable`, since IMP-1's reasons are a fixed enum. The adapter's own label and message are returned to the caller, which prints them;
  - `cancelled` (the adapter's canceller, set on Ctrl-C) pauses the job.
- **A store error** blocks the job with `store_error` when that can still be written, and returns the error. If it can't, the next start's `interrupt_import_jobs` blocks it.
- **Logs:** the driver logs nothing itself. It returns a `Report` (fixed labels and counts only), and the CLI prints it.

## The filter on every record

Every record is judged as ingest judges a fetched torrent (`pipeline::worker::prepare_one`), in the same order:

1. **The hash lists first:** `Engine::blocked_hash`, which covers the floor, the CS-1 hash list and dropping subscribed lists.
2. **Then the full judgement:** `Engine::judge_classified` on the name and file list, with the classification from `enrich_corrected`. That covers the floor's terms, the core, packs, your rules and your classification rules.
3. **The hits are recorded as the writer records ingest's:**
   - one hit per decision: held, marked or shadow;
   - the `HIDDEN`, `DEMOTED` and `FLAGGED` marks on a kept record;
   - a sealed name for quarantine, when a sealer is given;
   - the adult-hold bit, when your rule made the record adult.
4. **Your classification rule's fix** is applied to the stored enrichment.
   - **The rules' generation comes from the caller,** read _before_ it loaded the engine's rules, as the writer does it (`Filter::class_gen`).
   - So if the classification rules change during a run, the store sees an older generation and marks that batch's new rows for re-enrichment (IMP-1).
   - **The engine is fixed for a run.** A drop rule or floor term added mid-run isn't applied until the next run, though `store_hold` still rechecks hashes. IMP-4b runs imports with the server stopped, where rules can't change mid-run (fresh review, important).
5. **Candidates are judged by hash, and by name when they have one** (no files).
6. **The store checks tombstones, quarantine and the floor's hashes again** inside the batch transaction (IMP-1). So a hash held after the driver judged it, or deleted earlier, is never resurrected. A test imports a hash a first job tombstoned through a second source, with a filter that no longer holds it, and it stays gone.
7. **The engine and sealer are the caller's.** IMP-4b builds them from the store as the server does (the floor, CS-1 entries and signatures, switches, packs and your rules).

## Pause, cancel and crashes

- **Pause is checked between batches.** The caller's stop flag pauses the job before the next read. Cancelling the adapter's read stops a slow batch sooner, and a read cancelled that way is never committed. Either way the job is paused with exactly the committed counters, and the report says so.
- **A limit** (`Options::limit`) pauses the job once the run has committed that many records, rounded up to a whole batch. That's what a pilot of a big source needs (master plan D5).
- **A job that isn't running** (paused, blocked or finished elsewhere) isn't run. A commit refused with `ImportNotRunning` ends the run and loses nothing (IMP-1).
- **Changes made elsewhere between batches** (a test hook at the same points):
  - a job paused through another connection commits nothing more, and the run ends `NotRunning` with exactly the batches before it;
  - a source written mid-import blocks the job at the next batch.
- **Crash injection** (`driver::Fault`, test-only): the driver crashes after a batch is read, halfway through judging it, just before the commit, and just after it. Each time, the restart (`interrupt_import_jobs`, then `resume_import_job`, then `run`) finishes with exactly a clean run's counters and rows. That's on top of IMP-1's fail points inside the transaction.

## Merge and dedupe

IMP-1's store rules already implement these:

- **An import never overwrites a network-verified record:**
  - its name, flags and dates stay;
  - it gains only the adapter's source bit and the job's membership row (`created = 0`).
  - The driver tests this end to end.
- **Private is sticky:** a source that says private wins (sticky-private merge), and an import never clears `PRIVATE`.
  - The store's tests cover the merge (`private_is_sticky`). The Bitmagnet driver test covers a private record stored new.
- **A candidate never replaces a richer record:** one under a stored hash merges as provenance only (store tests).
- **Provenance per record and source:** the job's `import_membership` row says whether the job inserted the row or only added provenance. The registered source bit says which adapter has reported it, not which job.
- **Imported cohorts keep their origin:** `IMPORTED`, the membership rows and the quality rows let IMP-5 keep them out of crawl-yield Insights. Nothing here touches the crawler gate's counters.
- **Tests through the driver:** names judged by your rules (drop, quarantine with a sealed name, flag, shadow), a candidate judged by its name, the floor's hashes, and a tombstone that stays gone.

## Taking a job's records back (master plan F17)

`Store::remove_import_job_records(job, limit)` runs in bounded steps, one transaction each. The caller repeats it until `done`.

- **A torrent the job inserted is deleted** and logged in `reindex_log`, so the indexer drops it.
- **It's kept instead, losing only this job's provenance, when** (fresh review, blocking and important):
  - **another job touched it too.** The oldest such job inherits the insert (`created = 1`), so removing two overlapping pilots deletes it whichever is removed first;
  - **a network fetch has verified it since.** That's `upgrade_partial`, which covers partial imports only;
  - **another source has reported it since,** such as the crawler's touch. It then carries a source bit other than the adapter's, and its swarm observations are the crawler's;
  - **you've kept something of your own on it:** a favourite, label, note, collection entry or classification correction. Deleting it would cascade into those.
- **A torrent the job only merged into** loses this job's membership row only.
  - Its source bit stays, because other jobs of the same adapter may share it.
  - A privacy the import made stricter stays too: a restriction is never loosened.
- **The job's waiting candidates are deleted, except private ones** (fresh review, important). Candidates fold together keeping the oldest row's job, so a private claim from a later job can live in this job's row. Deleting it could let a later import store that torrent as public. The report counts the private candidates kept.
- **What stays:** filter hits, tombstones and quarantine the job wrote. They're safety records, not imported data.
- **The job's counters stay as its history.**
- **Only a job that no longer reads its source can be removed:** cancelled, failed, finished or indexing. A paused job is refused (fresh review, important). Resumed after a removal, its cursor would skip the removed records while its counters still claimed them. Cancel it first.
- **A limit of 0 is treated as 1,** so a caller looping until `done` always finishes.
- `Store::import_job_members(job, after, limit)` lists a job's records by id, for the CLI and later the UI.
- **A deletion here isn't journalled for snapshots.** It isn't a safety deletion, and a snapshot from before the import doesn't hold the row anyway.

## Source registration

- **The adapters register as stable sources** named `magnetico` and `bitmagnet` (`Store::register_source`; IMP-4b's CLI does it). The store refuses a batch whose source isn't the job's adapter (IMP-1).
- **Upstream labels** (Bitmagnet's `torrent_sources`, Magnetico's lack of any) aren't read by either adapter. So nothing upstream is ever counted as an independently observed discovery. Keeping them as annotations is IMP-06's rich merge.

## Dependencies and ownership

- **`lodestar-sources-importers` now depends on `lodestar-filter` and `lodestar-classify`,** both workspace crates the binary already links. It reuses the engine and enrichment ingest uses, not a copy. No third-party dependency was added.
- **Store change, in the import paths only:** `Store::remove_import_job_records`, `Store::import_job_members` and `import::Removed`. They read and delete through V13's existing tables and index (`import_membership_job`), so there's no schema change.
- **The driver is an `async fn` that does SQLite work inline.** That's fine on the CLI's own runtime. Run inside the server, it would need `spawn_blocking` or a sync driver.
- **Unsupported or refused sources fail with the stored reason `source_unavailable`,** since IMP-1's reasons are a fixed enum. The report carries the adapter's own label. A dedicated reason would need a schema change, which is out of scope here.
- **Tests:** the driver's in `driver/tests.rs`, over real Magnetico fixtures. Bitmagnet's end-to-end run is `bitmagnet/pg_tests.rs::the_driver_imports_through_the_filter`, under the same PostgreSQL gate as IMP-3's. The store's removal test is in `crates/store/tests/import.rs`.
