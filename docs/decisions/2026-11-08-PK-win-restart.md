# PK-win-restart decisions

Restart now on Windows (architecture §10.10.6, §11; `docs/decisions/2026-10-23-B2c.md` "Restart"; plan `docs/plan/2026-11-06-m6-gap-audit.md` §4, Q9, Q10), and free space on Windows.

## The service
- **Restart now takes the stop's graceful shutdown, then exits with service-specific code 80, which the SCM sees as `0x20000050` (536870992)** (decided in the slice, §2.33). `windows/service.rs` races `Restart::requested()` with its stop channel, as B2c planned. 80 is distinct from 1 (error) and 3 (refused) and is the Unix supervisor's `EXIT_RESTART`, so "80" means "restart me" on every platform. It goes through `scm_code`, so it carries the customer bit like the others (X-win-refusal-ux). A stop wins over a restart, even one that arrives during the restart's shutdown, as on Unix: it's checked again after the runtime has shut down, just before the exit code is chosen, so the SCM doesn't restart a service someone stopped.
- **`Restart::request` refuses on a paused or refused service,** whoever calls it: the API checks `available` first, but an updater calling `request()` directly (PK-win-upd-*) must not use a recovery a crash may need.
- **`main.wxs` needs no change.** `FailureActionsWhen="failedToStopOrReturnedError"` sets `FailureActionsOnNonCrashFailures`, which queues the recovery actions when the service reports `SERVICE_STOPPED` with a `dwWin32ExitCode` other than 0. A service-specific code is reported as `ERROR_SERVICE_SPECIFIC_ERROR` (1066) with the code beside it (`windows-service`'s `ServiceExitCode::ServiceSpecific`), so the clean stop triggers the restart after 60 s. The recovery numbers (60 s, two restarts, reset after a day) are unchanged. `smoke.ps1` presses Restart now on the installed service and sees it stop with 536870992 and come back.
- **The guard (plan Q10): `<data>\service-restarts.txt`** (name and format decided in the slice, §2.33). The SCM doesn't expose its failure count, so Lodestar counts what may have used a recovery in the last 24 hours: every Restart now and every start after an unclean stop. Restart now is offered only while the count is 0, that is until the newest entry is 24 hours old: the pause lifts by itself, without a restart. Meanwhile `/system` reports `available: false`, `method: "manual"` and a hint to restart the service from Windows Services, and the start logs `service.restart_paused` with the reason (`restart`, `unclean_stop`, `unverified` or `unwritable`).
  - **Format:** `lodestar-service-restarts 1`, then `state running|stopped`, then one `<kind> <unix seconds>` line per entry (`restart`, `unclean_stop`, `unverified`). A start writes `state running` before the store opens (adding `unclean_stop` if the previous state was still `running`), so a start that fails or dies while the store opens is counted by the next one; a clean stop writes `stopped`; Restart now writes `stopped` plus a `restart` entry. An error exit leaves `running`, so the next start counts it. Entries over 86,400 s old are dropped; an entry from the future (the clock went back) counts from now.
  - **Untrusted input, fails closed.** At most 4 KiB, read without following a link (`FILE_FLAG_OPEN_REPARSE_POINT`, then a reparse-point attribute check; `O_NOFOLLOW` in the tests on Unix), UTF-8, an exact header, digits only, at most 32 entries. Anything else, or a missing file when the store already existed, records an `unverified` entry, which pauses Restart now for a day. A missing file with no store is a fresh install. A record that can't be written pauses it for the whole run, because the next start couldn't count this run. Writing goes to a new `service-restarts.txt.tmp` (a stale one, or a link in its place, is removed, not followed), synced, then renamed over the record, which replaces a link rather than writing through it. All of this is in the private data folder.
  - **Known gap:** a start refused because the data folder isn't private (exit 3) can't write the record, since the folder isn't trusted. Those failures use SCM recoveries without being counted. Once the folder is fixed, the next start counts 0, so Restart now may be offered while the SCM has none left; it would then stay stopped until someone starts it. The refusal tells the administrator to fix the folder and start the service themselves, so this needs a refusal, a manual fix and a Restart now within the same day. Closing it needs Q13's helper or a record outside the data folder; neither is in this slice.
- **The estimate is the measured start plus 60 s** (`Restart::estimated_seconds` for `service`), so the dialog says about a minute. It still leaves out the graceful shutdown, as B2c says.

## The portable build
- **Race strategy: the new copy waits for the old process to exit** (decided in the slice, §2.33). At the request, before anything stops, `Restart::request` starts the new copy: `current_exe()` with `args_os()`, never through a shell, no argument added. Its stdin is a pipe from the old process, and `LODESTAR_RELAUNCH_TOKEN` in its environment holds a one-time token. The new copy's first step (`windows::hook`) waits for that token on stdin, which the old process writes only after its graceful shutdown (`restart::reexec` → `relaunch::hand_over`), then for end of file, which comes when the old process has exited and Windows has released its port, data lock and files. Then it starts as usual. Neither side sleeps: both are conditions with deadlines (10 minutes for the shutdown, 60 s for the exit, after which it goes ahead and a port still taken fails its start like any other).
  - **A failed spawn keeps the old process serving.** The spawn happens before `requested` is set; if it fails, `app.restart_failed` is logged with the error kind and nothing stops. If the copy started at the request has died by the time of the hand-over, a fresh one is started then (it also waits for the exit); only if that fails too does `serve` return an error, after the shutdown, and the process exits non-zero.
  - **A stop instead of a restart** (Ctrl+C, closing the window, a crash during the shutdown) closes the pipe without the token, and the new copy ends quietly. So a stop still wins.
  - **The new copy shares the old one's console and output.** The console window keeps showing Lodestar, and Ctrl+C there stops the new copy. A new console was rejected: the inherited output handles would still point at the old console.
  - **Known gap: the 202 comes first.** `POST /system/restart` answers `202 {"restarting": true}` before `Restart::request` runs (B2c: on the response body's drop), so a copy that can't be started is logged (`app.restart_failed`) while the page already says it's restarting; it waits out its timeout and finds the old process still serving. Starting the copy before the answer, and answering 409 if that fails, needs a hook in `crates/api/src/system.rs`, outside this slice; left to the runner.
- **The token stays in the new copy's environment:** edition 2024 makes removing a variable `unsafe`. Children started through `windows::system32_command` drop it; any later code that starts `lodestar.exe` itself (PK-win-portable-upd) must `env_remove(windows::relaunch::MARKER)` or go through `relaunch::command`, or the child would wait for a hand-over and end.
- **A token on stdin, not only the variable:** an inherited `LODESTAR_RELAUNCH_TOKEN` (a child process, a shell that kept it) does nothing without a pipe that delivers the same token, and a console stdin skips the wait entirely.
- **`RestartMethod` gains `service` and `relaunch`** (decided in the slice, §2.33). Neither `reexec` (same process id) nor `supervised` (Lodestar's own supervisor) describes them. Additive: `openapi.json` and `schema.d.ts` regenerated with the repo's tooling. The web dialog reads only `available`, `estimated_seconds` and `hint`, so no string changes.

## `/system` on Windows
- **Free space through `fs4::available_space`** (`GetDiskFreeSpaceExW`, the bytes available to this user, so quotas count), a Windows-only dependency already in the lock through tantivy.
- **Memory stays unknown on Windows** (plan Q9). The only way is `GlobalMemoryStatusEx`; the workspace forbids `unsafe`, `windows-sys` in the lock is raw FFI, and no safe crate in the lock wraps it. About already shows unknown memory.

## For the runner
- **The portable launcher:** after a restart, `Start Lodestar.cmd` sees `lodestar.exe` exit, prints "Lodestar stopped." and waits for a key while the new copy runs in the same window. Pressing a key closes the window and stops the new copy. The launcher is outside this slice's paths; a follow-up could loop while the exit code is 0 after a restart, or change the message. PK-guide-3 should say this, and that each service Restart now logs SCM events 7024 and 7031.
- **`smoke.ps1` runs in `release.yml` only,** so this PR's CI doesn't run the new Restart now check; the next release (or a manual `release.yml` run) does. `windows_service.rs` covers the exit code, the paused next start and the portable relaunch on the Windows test job.
- **Logs:** new events `service.restarting` (required), `service.restart_paused`, `service.restarts_unwritable`, `app.restart_failed` and `app.relaunch`. They carry codes and error kinds, never paths or arguments.
