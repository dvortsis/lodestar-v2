# B-update decisions, part 5b: Roll back from the API (PR pending)

Part 5b finishes B-update part 5 (`2026-11-01-B-update-5.md`, "Follow-ups"): manual Roll back from the API (§12.2), "trust survives a rollback", the structured reason in the error envelope, the download timeout's writer, the loopback fake-source test and a log capture over an install. The code is in `crates/lodestar/src/update/{engine,journal,control,download}.rs` and `crates/api/src/{updates.rs,error.rs,dto/updates.rs,dto/error.rs}`.

## `POST /updates/rollback {confirm: true}`
- **One code path.** The route asks through `control::request_rollback`: the `Rollback` intent, then the graceful shutdown. `main.rs` turns that into `request.json` and `EXIT_ROLLBACK`, and the supervisor runs the rollback journal that `lodestar rollback --update` runs (`journal::begin` and `journal::finish`, reason `manual`). The test fault `child:rollback` now calls the same function, so the binary tests exercise the route's path from the intent on. There's no second implementation.
- **The confirmation** follows `POST /usage/clear`: no `confirm: true` is `428 confirmation_required`, because it's a Danger-zone action (§10.10.7). Same session and same-origin JSON rules as the other routes. No fresh password, for the reason `updates.rs` already gives.
- **Refusals:** `409 rollback_unavailable`, with `error.reason` set to one of:
  - `not_supervised`;
  - `image_mode` (§2.13's image mode updates by pulling the image, not in place);
  - `busy`: a check or an install holds the one-check lock, or a switch or restart was asked for;
  - `no_previous_version`: `active` doesn't name the running version;
  - `snapshot_missing`: the running version migrated the store (`migration.json`), no `pre-v<from+1>` snapshot of it is left, and the store isn't still at `from`.

  A fixture or Windows answers `409 updates_unavailable`, as every other route does.
- **The route's check is cheap, and the supervisor's is the real one.** The route looks for the snapshot file (`journal::kept`) and doesn't verify it. Step 2 of the journal verifies it in the supervisor (settle, `quick_check`, schema), which can take minutes on a large store, and it does that once, not twice. A refusal there keeps the running version and raises the existing `rollback_refused` notice. The route also leaves the image-schema check to step 2, because only the image's own build knows the schema it reads.
- **Accepted means `202`** with the status. The engine keeps the one-check lock until the process exits, as a switch does (B-update-5's first review), so nothing checks, stages or installs before the restart. It publishes `restarting` with the version it restores. The torrents a rollback loses (`probation`'s count, when it has one) go in the request, as `lodestar rollback` gives none.
- **Crash safety of the route's entry.** Before the graceful shutdown writes `request.json`, the route writes nothing under `<data>/bin` (tested). A crash there changes nothing, and the next start offers Roll back again. `request.json` is bound to the run and consumed on read (`control::take`, already tested), so a crash between it and the journal leaves nothing half-done either. From step 2 on, the journal finishes at the next start. A binary test kills the supervisor right after each journal step (2 to 7) of a requested rollback, and each finishes as `manual` with the snapshot restored.
- **Revocations survive.** The journal never writes `trust.json`. Unit and binary tests check that its bytes are unchanged after a rollback that crashes at each step (§12.2: "no rollback can undo a revocation").

## `GET /updates`: `rollback.available` is "can roll back"
- **The brief asked for `can_roll_back` and its reason.** `RollbackInfo` already had `available` ("whether Roll back is offered"), which until now was always false. It now carries the truthful value, and `rollback.reason` (new) says why not. Adding a second boolean with the same meaning would let them disagree. `reason` is always sent but isn't `required` in the schema yet, as `installing` wasn't, so the Updates screen's fixtures still type-check. S-updates-4 reads `rollback.available` and `rollback.reason`. **Runner: this is the field name S-updates-4's brief should use.**

## The error envelope's `reason`
- **`error.reason`** (optional, a stable snake_case code) sits beside `code` when the code has several causes: `install_unavailable` and `rollback_unavailable` for now (`ApiError::reason`). The message is unchanged and still names the reason in parentheses.
- **The web client** carries it on `ApiError.reason`, the way it carries `section`. The Updates store reads `e.reason`, and the regex that parsed "(reason)" out of the message is gone.

## The download's overall timeout
- **The writer is joined before the `.part` file is removed,** on every path. Before, the 30-minute timeout dropped the download's future with the writer thread still running, so the file could be created or written after its removal. Now the deadline bounds the hops and the streaming separately (`timeout_at`), and the writer is always awaited. A test holds the writer past the deadline and checks that it had finished, and its file was gone, when the download returned.

## Tests against a loopback source
- **What "binary-level" means here.** The artifact's bytes come over real HTTP from a loopback server, through the real reqwest body reader (`download::Guarded::open` with the download-client policy), and run through the engine's whole install pipeline, files included. The allowlist still sees the signed GitHub URLs, and only where they're fetched from changes, as a DNS override would. The `lodestar` process itself isn't used: making it reach loopback would need a debug seam that bypasses the host allowlist, and this slice doesn't add one.
  - Wrong hash, wrong size and another target's bytes each fail as `download_mismatch`; an oversized body as `download_too_large`. A manifest with no artifact for this target fails as `no_artifact`, before any download. Each leaves `<data>/bin` as it was.
- **The log over an install:** a failed attempt, then a good one through a redirect whose URL carries a signature and a credential. The capture names `update.available` and `update.install_failed` with `download_mismatch`. No URL, host, query, credential or loopback address appears. No new catalogue events were added.
