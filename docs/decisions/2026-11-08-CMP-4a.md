# CMP-4a decisions (companion supervisor)

Slice CMP-4a of `docs/plan/2026-11-06-v06-companions.md` (§4, the orphans design point, §5 Q3 as decided by `docs/owner-decisions.md` §2.47, Q7); architecture §11, §12.2, §18.10. Every entry is a choice the brief left to the slice (`docs/owner-decisions.md` §2.33). None loosens Q3 or Q7 or changes an owner number: the Q7 numbers are `supervise::Timings::default()`, checked by a unit test.

- **API for CMP-5 and CMP-6.** `Supervisor::new(data_dir, hook, timings).await` first runs the orphan cleanup (one supervisor per data folder: a second would kill the first's companions as orphans), then `add(Companion)` starts one task per companion, `status(id)` gives a `tokio::sync::watch` receiver of `Status { state, restarts, last_exit }`, `logs(id)` the `LogRing`, `restart(id)` is what you do after Needs attention, `remove(id)` stops one, and `shutdown()` stops all. Dropping the `Supervisor` aborts its tasks, and every child is spawned with `kill_on_drop`, so a cancelled supervisor leaves no task or companion behind. `Timings` has public fields so tests can shorten them; shipped callers use `Timings::default()`.
- **States:** `Starting`, `Running`, `Unhealthy { failures }`, `BackingOff { delay }`, `NeedsAttention(CrashLoop | Refused(code))`, `Stopped`, each with a stable `code()`. A spawn that can't succeed as configured (Lodestar is root or an administrator, the executable isn't a regular file, a bad env name) goes straight to `NeedsAttention(Refused(code))` instead of burning the crash budget; other spawn failures count as crashes.
- **Refinements of Q7, the runner's to accept (§2.19):** a run of 5 min or more resets the backoff; health restarts count as crashes; the pidfd is taken at kill time, not stored. Each is detailed below.
- **Restart rules (Q7 applied):** the delay is 1 s doubled per crash in a row, capped at 5 min. A run that lasted at least the cap (5 min) resets the doubling. Three failed health checks in a row stop the companion (deadline, then kill) and count as a crash, so a companion that never becomes healthy also ends in Needs attention. Five crashes inside 10 min set `NeedsAttention(CrashLoop)`; `restart` clears the crash history and the backoff. Health checks start one interval after a start, and each is bounded by the interval.
- **Dependency order:** `add` refuses a companion whose `depends_on` isn't added yet, so the insertion order is a dependency order; `shutdown` stops in reverse, one at a time, each bounded by the 10 s deadline plus 5 s to reap after the kill plus 1 s for the output readers. A task that overruns is aborted (which kills its companion).
- **A companion that won't die** within the 5 s after its kill keeps its record, so the init's hook and the next start still find it. The group is signalled right after the leader's wait returns, before the record goes and before the output readers are awaited.
- **Process groups (Unix):** each companion leads its own process group (`Command::process_group(0)`, safe, no `pre_exec`), so stops and kills reach what it starts (FlareSolverr's browser). The group gets SIGTERM, then SIGKILL after the deadline, and SIGKILL again once the leader has gone or its task is dropped; the group's id stays reserved while any member lives, so only members can be hit. The init's hook also kills its adopted children in a recorded companion's group. On Windows the Job Object (CMP-4b) does this. A work child killed in the microseconds between a spawn and its record leaves that companion unrecorded; CMP-4b's Job Object covers Windows, and the window is stated here rather than closed.
- **Graceful stop:** SIGTERM on Unix, plus the companion's `Stop` request (an adapter's shutdown call, for CMP-5/CMP-8a to supply) if it has one. Windows has no signal Lodestar can send without `unsafe`, so there a companion without a `Stop` is killed at once rather than waiting out a deadline nothing can meet.
- **Environment:** Unix gets only the template's variables. Windows gets `SystemRoot`, `PATH` (`%SystemRoot%\System32`, `%SystemRoot%`, `%SystemRoot%\System32\Wbem`), `TEMP`/`TMP` (`home\temp`) and `USERPROFILE`/`APPDATA` (`home`), then the template's. `EnvName` accepts `[A-Za-z_][A-Za-z0-9_]{0,63}` and refuses `LD_*`, `DYLD_*` and the Windows base names on every platform, so a template can't change how the program loads or replace the base.
- **Working directory:** `<data>/companions/<id>/home/`, 0700 on Unix (tightened if it exists looser), each level created with `create_dir` and checked by `symlink_metadata` to be a real directory. CMP-2's sweep touches only version, staging and pointer names, so `home` is safe there.
- **Executable:** an absolute path whose `symlink_metadata` is a regular file. CMP-5 passes `Install::executable(version, entry.executable)` (CMP-2, #600); `PATH` is never searched.
- **Privilege:** Unix refuses when the effective uid is 0. Windows asks PowerShell 5.1 (by absolute path) whether the identity is `SYSTEM` or an enabled member of Administrators; only a definite answer is cached, and an answer it can't read refuses (`privilege_unknown`) until a later start asks again. `SpawnSpec::allow_privileged` always exists (so struct literals compile alike in every build) but is honoured only under `cfg(test)` or the crate's `testing` feature, because CI runners are root or elevated; shipped callers set `false`, and a release ignores it.
- **PowerShell off the async path:** spawns and the start-up cleanup run on Tokio's blocking pool (`spawn_blocking`), and every PowerShell call is killed after 30 s, so a hung PowerShell can't stall a runtime worker or make shutdown unbounded. `SpawnSpec`'s `Debug` prints env names only.
- **CMP-4b hook:** the `AfterSpawn` trait gets `&tokio::process::Child` (pid, and the raw handle on Windows) right after spawn, before the companion is recorded or supervised; an error kills it.
- **Log ring:** 1 MiB per companion, charged as each line's bytes plus 32 (roughly its own memory, so a flood of empty lines stays within the cap); control characters (C0 except tab, DEL, C1, and so ESC) are each replaced by a space before a line enters it, so they still separate words for the whole-word match of short secrets; a line is cut at 8 KiB and the rest of it dropped. Known secrets of 6 bytes or more are replaced wherever they appear; shorter ones as whole tokens only (between bytes that can't be part of a word), so none is skipped. Common shapes: the value after `password`, `passwd`, `pass`, `pwd`, `apikey`, `token`, `accesstoken`, `secret`, `clientsecret`, `sid` and `session` followed by `=` or `:` (case-insensitive, `-` and `_` ignored in the key), and the whole rest of the line after `Authorization`, `Proxy-Authorization`, `X-Api-Key`, `Cookie` and `Set-Cookie`. Reads are joined into lines before redaction. Matches are found as byte spans over the raw line (for a long line, a window 512 bytes past the cut), and the output is built only from raw text before the cut, so a secret up to 512 bytes that straddles the cut leaves no prefix, however much earlier replacements shortened the line.
- **Pidfile format:** one file per companion, `<data>/companions/run/<id>.json`, `{"format":1,"pid":…,"start":…,"exe":"…"}`, `deny_unknown_fields`, at most 8 KiB, created new (`create_new`, `O_NOFOLLOW`, 0600) in a 0700 folder checked to be a real directory. `start` is clock ticks since boot (`/proc/<pid>/stat` field 22) on Linux and `Process.StartTime` as a FILETIME on Windows; `exe` is `/proc/<pid>/exe` (with a ` (deleted)` suffix dropped, since the start time still pins the process) or `Process.Path`. Other platforms have no identity, record nothing and never kill.
- **Who a record may name (runner's review):** never pid 1 or below (a group kill of 1 is `kill(-1)`), Lodestar itself, its parent or its process group (on Windows, pids up to 4 and Lodestar itself); and only a program whose canonical path is under `<data>/companions/`, so the identity check is also an authorisation check and a planted record can't name an arbitrary program. A group is killed only when `/proc/<pid>/stat` shows the process leads it. Records are read with `O_NOFOLLOW | O_NONBLOCK` and checked on the open handle, so a FIFO in a record's place can't hang start-up, and only `.json` names count toward the 64-record limit. No companion may be called `run`, the records folder's name (`reserved_id`).
- **"A pidfd where the kernel has one"** is used for the kill rather than stored: a pidfd can't outlive the process holding it, so a file can't carry one. The cleanup opens a pidfd, then checks start time and executable, then signals through the pidfd, so a pid reused after the open isn't hit. Without pidfds (kernels before 5.3) it falls back to `kill(2)` after the same check. On Windows the kill runs in the same PowerShell call as a second start-time check, on one process handle opened first.
- **The init hook** (`crates/lodestar/src/update/supervisor.rs`, Linux only): after each work child exits, `kill_adopted_companions` calls `pidfile::kill_adopted(data_dir, own pid)`, which kills a recorded companion only if it also is the init's own child now. The init is single-threaded and reaps only in its own loop, so nothing is reaped (and no pid reused) between that check and the kill. It doesn't remove records; the next work child's `Supervisor::new` does.
- **Reaping:** the supervisor runs in the work child and waits only on its own children by pid (Tokio's `Child`); it never waits on any child, so it can't race the init's reaper. Record removal happens only after the companion was reaped.
- **The fake companion is the test binary itself,** run filtered to its `fake_companion` test with `FAKE_MODE` in its environment. That needs no shell script, no extra Cargo target and builds on Windows. The plan's required test stands in for the init by making the test process a subreaper and calling the init's own hook. The hook's call site in `update/supervisor.rs` isn't exercised by a test: `crates/lodestar/tests/` isn't this slice's to edit, so it's left to CMP-G's orphan test.
- **No log events.** As CMP-1 and CMP-2 did, errors and states carry codes and CMP-5 logs them.
- **Dependencies:** `tokio` gains `process`, `macros` and `io-util`, and `rustix` (Unix) gains `process`; dev-only `tokio` gains `process` and `signal`. All are already in the lockfile; no new crate and no `test-util`.
