# SRC-12b decisions (plugin kit `fetch_stream`, redacting `Request` Debug)

Slice session, 2026-11-04. Architecture §18.1, §18.4, §18.7; follows `2026-11-04-SRC-12.md` (its "Follow-up (runner, before SRC-G)") and #414's review.

- **Streaming is a second method on `Fetch`, with a default.** `Fetch::fetch_stream(req, limits)` returns a `StreamResponse`: status, headers and a `BodyStream` read a chunk at a time with `next_chunk`. The default calls `fetch` and hands the buffered body out in 64 KiB chunks, so fixtures (`Replayer`), `NoEgress` and every existing implementation keep working unchanged, within `MAX_BODY` and their own timeout. `Arc<T>` forwards it, so a `Kit`'s `Arc<dyn Fetch>` reaches the real implementation. No new dependency: `BodyStream` is a small trait in place of `futures::Stream`.
- **Plugins stream through `Client::poll_stream(unit, req, limits)`.** It has the same gates as `poll` (poll interval, the unit's own hold, the host's token, a block refused at once) and records the head as a poll's answer. It enforces the limits itself on every chunk, whatever the `Fetch` does, so an implementation that ignores them can't exceed them:
  - **Time.** `timeout` covers the whole exchange from sending to the last chunk. `idle` bounds the wait for the headers and for each chunk, so a reply that stalls fails then, not at the end of `timeout`. The deadline is checked before each read, so a stream that is always ready can't outrun it. Time the caller spends between reads (waiting for the pipeline to take keys) counts toward `timeout` but not toward `idle`.
  - **Bytes.** A `Content-Length` over `max_bytes` fails before any body is read. A body that grows past it fails at the chunk that crosses it; that chunk is never handed out.
  - **Fail closed, and fused.** Every limit fails with `HttpError::Transport`. Once a stream has failed, every later read returns the same error without touching the transport.
  - **Back-off.** A body failing part way (a reset, a timeout, too large) backs the host off, as a buffered body's failure does today; a kill switch's abort (`EgressDown`) doesn't. A stalled or failed head is recorded as a poll's failure.
  - **Nothing is read ahead.** A chunk is fetched only when the caller asks for the next one, so the kit holds at most the chunk in hand.
- **The real egress streams too** (runner, 2026-11-04: ownership widened to `egress.rs`, `egress_tests.rs` and `integrations/src/net.rs` for this). Without it the kit would stream only in tests, since `PluginEgress` read every body whole through a client whose 30 s total timeout also covers the body.
  - `GuardedClient::exchange_stream` (net) sends as `exchange` does, through the same `send` (address classes before and after DNS, the route's checks, no redirects), but sets the request's own timeout to the caller's in place of the client's (connecting stays capped at 10 s) and returns a `StreamBody` that reads within a byte limit. **`net` holds both to its own ceiling** (`STREAM_CEILING_BYTES` 1 GiB, `STREAM_CEILING_TIMEOUT` one hour) whatever the caller asks, so the bound doesn't rest on the kit alone. A `Content-Length` over the limit is refused at the head. `exchange` and every existing caller are unchanged; the request building is shared.
  - `PluginEgress::fetch_stream` goes through the same admission as `fetch` (endpoint policy, kill-switch gate, the paced refusal while down; factored out as `admit`) and the same error mapping (`failed`: policy refusals, a re-probe on a failed connection). **The in-flight abort covers the body:** each chunk read races the route's state, so a route that goes down while a body is being read ends it with `EgressDown`. A body read that fails on a checked route is re-probed and reads as the kill switch's error when the route is down. That probe doesn't publish a new state, since the body doesn't hold the egress; the monitor, or the next request, does.
- **The limits are the plugin's own, held to a ceiling.** `StreamLimits { max_bytes, timeout, idle }`, clamped to `STREAM_CEILING` (1 GiB, one hour, a two-minute idle wait) and `STREAM_FLOOR` (one second for both waits), with `idle` never longer than `timeout`. The plugin declares them as a constant and passes them on each call. **Deviation from the brief's "taken from the manifest":** a field on `Policy` would mean editing `manifest.rs`, every plugin's `Policy` literal and the host's (none owned by this slice); since plugins are compiled in, a plugin constant is as fixed as a manifest field, and the kit's ceiling is what bounds it. Moving it onto `Policy` later is additive.
- **The full scrape streams: 256 MiB, ten minutes, a one-minute stall** (`full_scrape::STREAM`). 256 MiB is the parser's own byte cap (`tracker_scrape::full::LIMITS`, SRC-12) and room for the largest public trackers' replies; ten minutes reads 256 MiB at about 450 KB/s. The window's close still cuts a scrape shorter when it comes first: the stream's timeout is the lesser of the two, and the whole attempt (pipeline waits included) stays inside the window's deadline. Each chunk is fed to the parser and its keys emitted before the next is read, so the plugin's memory stays the parser's fixed heap plus one chunk. `CHUNK` is gone; the chunk size is the transport's (or 64 KiB from a buffered `Fetch`).
- **`Request` and `Response` print no secrets.** Both have hand-written `Debug`: method or status; the URL as scheme, host and port only (`net::redact`: the path, query and fragment, where passkeys and API keys sit, and any user name or password are elided; a URL that doesn't parse is elided whole); every header name, but a value only for an allow-list of plainly harmless headers (`SHOWN_HEADERS`: content type, user agent, `Retry-After` and similar), so `Cookie`, `Set-Cookie`, `Authorization`, `Proxy-Authorization`, `X-Api-Key` and any header nobody thought of print `<redacted>`; `Location` as a redacted URL; and the body as its length only. An allow-list rather than a deny-list, so a new credential header fails closed. `StreamResponse`'s `Debug` follows the same rules.
- **Flat-memory test without a counting allocator** (the workspace forbids `unsafe`, as in SRC-12). `crates/sources/tests/fetch_stream.rs`, alone in its binary, streams 512 MiB through `poll_stream` and checks resident memory after every chunk on Linux (growth under 16 MiB; it grows by the whole body if chunks are kept, checked by hand). On every platform, the unit test `a_large_stream_is_never_read_ahead` checks after each of 4,096 chunks that the server has produced exactly what the caller has read. All timing tests run on tokio's paused clock with no fixed sleeps; the only sleeps pace the fixture server.
