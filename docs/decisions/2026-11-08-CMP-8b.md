# CMP-8b decisions

Companion auto-configuration through each companion's API (plan `docs/plan/2026-11-06-v06-companions.md` §4 CMP-8b, Q8, Q18, Q19; architecture §18.7, §18.10). These are the slice's decisions under §2.33. None loosens an owner decision, the SSRF guard or detection's scope. The runner flags them to the owner (§2.19).

## Shape
- **`configure::{qbittorrent, prowlarr}` implement CMP-0's `Configure`.** `configure::configurator(id)` returns the adapter for a catalogue id, like `detect::detector`. gluetun has none. FlareSolverr is CMP-12's (Q21) and isn't wired here.
- **Plan, then apply.**
  - `plan` reads the companion's state and lists the `SettingKey`s that differ from the wanted state. It writes nothing; a test checks that planning sends only the sign-in and GETs.
  - `apply_plan` writes only what the plan lists, in a fixed order. A key the adapter doesn't know is refused before anything is sent.
  - Every write sets a value outright, so applying and then planning again gives an empty plan (tested for both adapters). An empty plan sends nothing.
- **A plan's keys are per setting, not per value.** `SettingKey` is a `&'static str`, so categories are one key, `downloads.categories`. `apply` reads the categories again and creates or edits only those that differ.
- **Logging (`log_events.rs`):** three events, carrying the companion id, a setting's or step's name and a code. They never carry a value, a URL, a body or a credential; a test captures every line and checks.
  - `companions.config_applied` (info): one per applied setting.
  - `companions.config_failed` (warn): the step (`plan`, `apply`, a setting, `lodestar.settings`) and `reason`, the error's own word.
  - `companions.config_handed_over` (info).

  They're registered in the `lodestar` catalogue golden, `event-names.ts` and the en/zh messages, as CMP-0a did. The web bundle grows only by those three message pairs: the on-demand "Settings logging event names" chunk goes from 13,169 B to 13,292 B gzipped, inside its 13.3 KB budget, so the strings are kept short.

## `ConfigureInput` (additive, runner-approved under §2.33)
- **New fields, each a closed or validated type:**
  - `origin: Origin`;
  - `route: Option<Route>`;
  - `webui: Option<WebUiBind>`;
  - `downloads: Option<Downloads>`;
  - `username: Username`, CMP-3's type, defaulting to its `lodestar`.

  `None` leaves that part of the companion as it is. Builder methods set each field. `ConfigureInput::new(credentials)` keeps its signature, so CMP-0's tests and fakes are unchanged.
- **Consent can't be skipped (brief item 6).**
  - `new` alone leaves the origin `Origin::Unstated`. Both adapters, and `hand_over`, refuse it with `Refused(NOT_CONFIRMED)` before anything is sent.
  - A caller states one of three origins:
    - `.installed(InstallReceipt)`: Lodestar installed it. **Only this crate mints a receipt** (`pub(crate)`, for CMP-5's manager from its own state row; `for_tests` under the `testing` feature only), and it's bound to a target. So no caller can claim an install it didn't make for a detected companion on a fixed target, which is where #610's review put the risk. Refused for an entered URL, since Lodestar never installs at one.
    - `.confirmed(Confirmation)`: a detected or entered companion you confirmed.
    - `.guided(Confirmation, temporary)`: a guided install you confirmed.
  - **A `Confirmation` is bound to one `Target`.** `Confirmation::of(target)` must equal the target configured, or the call is refused. A confirmation for loopback can't be spent on an entered URL.
  - Consent is checked first in `plan` and in `apply`, even for an empty plan. A test drives every refused combination against a live fake server and asserts that it saw nothing.
  - **What the type can't do:** a `Confirmation` is still a claim the caller makes; CMP-5g makes one only from its confirmation endpoint. Container-name targets are trusted only under Docker's embedded DNS (#610's security review); that check stays CMP-5g's.
- **`Route`** is this crate's own closed type, so CMP-8b doesn't depend on CMP-4b (#608). CMP-5 maps CMP-4b's route onto it.
  - `Route::Direct`;
  - `Route::Interface(InterfaceName)`: 1–64 of `A–Z a–z 0–9 _ . : -`;
  - `Route::BindAddress(BindIp)`: not unspecified, multicast or broadcast;
  - `Route::Socks5(Socks5Proxy)`: a `SocketAddr` with a specific address and a non-zero port. It matches `lodestar_sources`' `Egress::Socks5 { proxy: SocketAddr }`; there's no proxy credential, because the sources' egress has none.

  **Q8:** a kind the companion can't follow is refused with `Refused(ROUTE_UNSUPPORTED)` before anything is sent, never applied as direct. qBittorrent refuses SOCKS5, and Prowlarr refuses an interface or an address.
- **`WebUiBind::{Loopback, ContainerNetwork}`** → `127.0.0.1` or `*`.
  - Each is accepted only for the target it keeps reachable: loopback for a loopback target, `*` for a container target. Inside a container, `*` means the container's own interfaces, which only Docker's network reaches.
  - An entered URL may be another machine, so neither is set there (`Refused(BIND_UNSUITED)`). Lodestar never binds a remote qBittorrent to its own loopback and locks itself out, and never binds a native one to every address on the LAN.
- **`Downloads`** holds a save path and up to 16 categories.
  - The save path is a CMP-0 `HostPath`, as the companion sees it (`/downloads` in its container), with `HostPath`'s system-folder refusals.
  - Each category is a `CategoryName` (1–64 of `A–Z a–z 0–9 _ . -` and inner spaces, no leading `.`) and an optional `HostPath`. Names are unique.
  - Windows paths for CMP-11's native qBittorrent aren't accepted yet. CMP-11 adds them.

## The session cookie (`adapter.rs`, additive)
- **`ProbeRequest::session_cookie(&'static [CookieName])`** names the cookies an adapter accepts, from its own constants. A `CookieName` is an exact RFC 6265 token (`CookieName::new("SID")`) or a prefix followed by one to five digits (`CookieName::numbered("QBT_SID_")`).
  - `CompanionHttp` reads only `Set-Cookie` headers. It hands back the first cookie whose name matches and whose value passes `cookie_value_ok` (1–512 bytes of letters, digits and `_ - . + / = % :`).
  - It comes back as `name=value` in a `Secret`, from `ProbeResponse::session_cookie()`. No other header is read or exposed.
  - The adapter sends it back itself as its `Cookie` header, a sensitive header. `CompanionHttp` still keeps no cookie jar.
- **`ProbeResponse` and `ProbeRequest` get hand-written `Debug`.** It shows the method, path, header names and the body's length, never the body (a sign-in form, Prowlarr's host settings) or the cookie; `HeaderValue`'s `Debug` was already redacted. `ProbeResponse`'s `PartialEq` is written out too, because of the `Secret` field.
- **qBittorrent's cookie is `SID` up to 5.1 and `QBT_SID_<WebUI port>` from 5.2** (`webapplication.cpp` `SESSION_COOKIE_NAME_PREFIX` at `release-5.2.0`). Inside a container the WebUI port can differ from the target's, so any digits match. A custom `WebUI\SessionCookieName` (up to 5.1) gives a sign-in with no session, which is a protocol error; Lodestar's own installs never set one.

## `Method::Put` (`adapter.rs`; approved by the runner, 2026-11-08)
- **Prowlarr's host settings take only `PUT`.** Its `HostConfigController` has `[RestPutById]` and no POST route. So `adapter::Method` gains `Put`, with `ProbeRequest::put(body)`, and `CompanionHttp` gains one match arm.
- `Method` isn't `#[non_exhaustive]`; the only match on it outside tests is that arm.

## qBittorrent (WebUI API v2)
Checked on 2026-11-08 against upstream `release-4.6.3`, `release-5.0.3`, `release-5.1.2` and `release-5.2.0`: `src/webui/api/authcontroller.cpp`, `appcontroller.cpp`, `torrentscontroller.cpp` and `src/webui/webapplication.cpp`. The catalogue pins no version, and the unpinned linuxserver.io image follows the current release, so every line from 4.6 is supported. They agree on the endpoints and preference keys; 5.2 changed the sign-in and the status of writes.
- **Sign-in:** `POST /api/v2/auth/login`, a form of `username` and `password`.
  - Up to 5.1: `200 Ok.` with `SID` is a session, and `200 Fails.` is `Unauthorized`.
  - From 5.2 (`loginAction` sets no result, which `webapplication.cpp` answers `204`): `204` with `QBT_SID_<port>` is a session, and `401` (`APIErrorType::Unauthorized`) is `Unauthorized`.
  - Writes answer `200` up to 5.1 and `204` from 5.2; both are success. A test runs a whole guided configuration against a 5.2-mode fake.
  - **A `403` is a ban after failed sign-ins:** `Refused(BANNED)`, never retried.
  - No `Origin` or `Referer` is sent. qBittorrent's cross-site check passes a request that carries neither.
- **Reading:** `GET /api/v2/app/preferences` and `GET /api/v2/torrents/categories`.
- **Writing:**
  - `POST /api/v2/app/setPreferences` with `json=` holding only the listed keys;
  - `POST /api/v2/torrents/createCategory` or `editCategory` with `category` and `savePath`.
- **Wanted state:**
  - `webui.bind_address` → `web_ui_address`;
  - `webui.local_auth` → `bypass_local_auth`, always `false`, so a process on the same machine must sign in too;
  - `downloads.save_path` → `save_path`;
  - `downloads.categories`;
  - `network.interface` → `current_network_interface`;
  - `network.bind_address` → `current_interface_address`;
  - `webui.password` → `web_ui_password`, for a guided install.

  A direct route sets both network keys empty. An interface sets the name, with the address empty (any address on it). A bind address sets the address, with the interface empty.
- **Write order:**
  1. categories;
  2. the preference batch;
  3. the new password;
  4. the WebUI address, last, because qBittorrent restarts its WebUI when it changes.
- **Guided installs (Q19).**
  - The stored credential (CMP-3's generated password, which the caller stores before applying) is tried first. If it's refused, the temporary password is tried.
  - If the temporary one signs in, the plan lists `webui.password`. `apply` signs in with the temporary password first, sets the stored one, then **signs in with the new password before it counts as done**. If that sign-in is refused, `Refused(PASSWORD_NOT_TAKEN)` is returned, so the temporary password is never left in place quietly.
  - A run costs at most one failed sign-in, well under qBittorrent's default of five before a ban.
  - A retry after a crash works whichever password is in place.
  - A plan listing `webui.password` is refused unless the origin is guided.
- **Parsing:** the bounded reader (`lodestar_sources_feeds::json`).
  - **Preferences:** depth 4, 4,096 values, 1 KiB per kept string. The five compared keys are required, each once and of its type. A key with an escape fails the parse.
  - **Categories:** the same caps. An escaped name is passed over, because it can't be one of Lodestar's plain-ASCII names. A repeated name fails the parse.
  - Paths compare ignoring one trailing `/`, and addresses compare as parsed `IpAddr`s.
- **Bounds:** 10 s and 256 KiB per request. Preferences run to about 12 KiB.

## Prowlarr (API v1)
Checked on 2026-11-08 against upstream `develop`: `src/Prowlarr.Api.V1/Config/HostConfigController.cs` and `HostConfigResource.cs`, and `src/NzbDrone.Common/Http/Proxy/ProxyType.cs`.
- **The key** goes as `X-Api-Key`, a sensitive header, and never in the URL (tested). `401` is `Unauthorized`.
- **Reading:** `GET /api/v1/config/host`. The parse needs `id` 1 and `proxyEnabled`, `proxyType`, `proxyHostname` (may be `null`) and `proxyPort` (0–65535), each once and of its type, with depth 1 (a flat object) and 512 values; any other number must be a whole number in `i64`.
- **Writing:** `PUT /api/v1/config/host/1` with **the whole object back**.
  - `SaveHostConfig` saves every property it's sent, so a partial object would reset the rest.
  - The object goes only to the same Prowlarr it came from, on the same target, with the listed proxy fields changed. It passed the bounded parse first, and is then read with `serde_json` (already a dependency) for the round trip. Nothing of it is kept, logged or shown.
  - The round trip includes Prowlarr's own `apiKey` and password hash, as Prowlarr's UI does. They go back to the API that sent them and nowhere else.
- **Echoing GET is safe (runner's condition on `Method::Put`; upstream `develop`, checked 2026-11-08):**
  - `NzbDrone.Core/Configuration/ConfigFileProvider.cs`, `SaveConfigDictionary`: skips `ApiKey` explicitly and writes only values that differ, so the echoed key, bind address and port write nothing.
  - `HostConfigController.GetHostConfig` returns the stored hash as `password` and `""` as `passwordConfirmation`. `IsMatchingPassword` passes when the hash equals the stored one, and `NzbDrone.Core/Authentication/UserService.cs` `Upsert` rehashes only `if (user.Password != password)`. With no user, `Upsert` isn't called.
  - `NzbDrone.Core/Configuration/ConfigService.cs`, `SaveConfigDictionary`: skips nulls and unchanged values.
  - **The round trip is exact.** The parse accepts only a flat object (depth 1) whose numbers are all whole numbers in `i64`, so `serde_json` can't reinterpret any field. A test checks that the PUT body is GET's object with exactly the planned proxy fields changed.
- **Wanted state (Q8: SOCKS5 only):**
  - For a direct route: `proxy.enabled` off. Nothing else changes, so the old proxy fields stay for you to see.
  - For SOCKS5: `proxy.enabled` on, `proxy.type` `socks5` (compared without case), `proxy.hostname` the route's address, `proxy.port`, and `proxy.bypass_filter` (`proxyBypassFilter`) empty. A filter would send the hosts it names on the direct route, which Q8 forbids.

  Proxy credentials and `proxyBypassLocalAddresses` aren't touched: local addresses aren't the internet. With no route, nothing is planned and nothing is sent.
- **Bounds:** 10 s and 64 KiB per request.

## `ConfigSink` and `hand_over`
- **`ConfigSink`** is the trait `crates/lodestar` implements in CMP-5g. It has two methods, both async:
  - `download_client(DownloadClientEntry { companion, target, username, password, category })`;
  - `indexer_manager(IndexerManagerEntry { companion, target, api_key })`.

  Both take closed types: a `CompanionId`, a `Target`, CMP-3's `Username`, a `Secret` and a `CategoryName`. **The sink seals the credential under its own context**, because CMP-3's sealed value opens only under `companion:<id>:<field>`.
- **`configure::hand_over(sink, companion, target, input)`** builds the entry after a successful `apply`.
  - It checks consent as configuring does.
  - It takes the credential from the input's `Credentials`, never from a companion's answer.
  - The download client's category is the first configured one.
  - A sink failure is `Refused(SINK_REFUSED)`.
- **No dependency on `crates/pipeline` or the settings code:** `cargo tree -p lodestar-companions` lists neither.

## Fixtures and tests
- **Fixture layout:** `crates/companions/fixtures/{qbittorrent,prowlarr}/configure/`, each with a README. These are the **starting state** of stateful fake servers in `tests/configure.rs`, which change their copy as writes arrive. That's how idempotence and partial configuration are tested. CMP-8a's recorded-exchange layout replays fixed answers and can't show a write taking effect.
  - qBittorrent's `preferences.json` is about 80 of 5.0.3's keys with linuxserver.io's defaults.
  - Prowlarr's `host.json` is `HostConfigResource` with a fresh install's values.

  Both are reconstructed from upstream source, since the catalogue pins no versions yet.
- **Covered:**
  - first configuration, already configured and partly configured;
  - a refused credential and a ban;
  - the temporary password replaced, and a qBittorrent that ignores the new one;
  - each adapter's unfollowable route, and unsuited WebUI bindings, refused before sending;
  - every unconfirmed origin, refused before sending (plan, apply and `hand_over`);
  - another companion's plan refused;
  - hostile answers: oversized, malformed, an HTML page, a silent server (the client's 10 s deadline), a sign-in without a usable cookie, and Prowlarr's `id` other than 1;
  - no secret in any request line, error or captured log line.

  Each parser has a totality property test and a round-trip property test.

## Left as they are, with reasons
- **A guided Prowlarr** has no temporary secret: the key you paste is the stored credential (CMP-3's `accept_pasted`). `.guided(confirmation, temporary)` is qBittorrent's; Prowlarr ignores the temporary value, so CMP-5g uses `.confirmed(…)` for Prowlarr.
- **`editCategory` resets a category's own download-path setting.** Upstream builds the options from the parameters it gets. It's only reached for a category with one of Lodestar's names whose save path differs, and the plan you confirm lists `downloads.categories`.
- **qBittorrent's subnet whitelist** (`bypass_auth_subnet_whitelist_enabled`) isn't changed: it's your network's choice, and Lodestar signs in either way. `webui.local_auth` closes only the same-machine bypass.
- **Each guided plan before the apply costs one failed sign-in.** qBittorrent bans after five by default. CMP-5g plans once per confirmation, and after a successful apply the companion's origin is `confirmed`, so the stored password signs in first.
- **`hand_over` isn't tied to a successful `apply` by type.** CMP-5g calls it only after `apply` returns `Ok`. A proof value would add a type for one call site.
- **`adapter.rs` imports the input types from `configure`.** They're CMP-8b's and configuration-only; moving them to `adapter.rs` would make CMP-0's file the home of every adapter's inputs.
