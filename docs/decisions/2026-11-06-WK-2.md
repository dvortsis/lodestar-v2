# WK-2 decisions (`lodestar worker`)

Plan `docs/plan/2026-11-06-v06-workers.md` §4.3 WK-2 and Q2; architecture §19.6, §13; builds on `docs/decisions/2026-10-23-V6-cluster2.md` and `docs/decisions/2026-11-06-WK-1.md`.

## The command
- **`lodestar worker --join <url> --token-file <path|->` joins, saves, then runs.** It doesn't exit after joining: in a container the same process goes on to connect. Without `--join`, `lodestar worker [--data <dir>]` runs from the saved credentials. `--token-file` needs `--join`; `--join` alone works only with `LODESTAR_TOKEN` (below).
- **`--join` takes `https://host:port`, `host:port` or either without a port** (8091, §19.2), and `[v6]` for IPv6. `http://` is refused with its own message (the cluster port only speaks TLS), as are paths, queries, user names and any other scheme. The parsed `host:port` is saved to `<data>/cluster/coordinator` (`LWA1`, one `addr` line, written atomically) and parsed again when read. Unit and property tests cover the parser.
- **The data folder is `--data`, else the config's data directory** (`LODESTAR_DATA_DIR`). The credentials are V6-cluster2's `<data>/cluster/credentials`, sealed with `<data>/secrets.key`.
- **A coordinator's data folder is refused** (it holds `lodestar.db`): a worker's key rotation must never rotate the coordinator's `secrets.key` without the coordinator's own re-seals.
- **One worker per folder:** `<data>/cluster/worker.lock`, held with the standard library's file lock (`File::try_lock`, no new dependency) for the whole run. A second copy, or `--rotate-key` while the worker runs, is refused. The OS drops the lock if the process dies.
- **`--data` is the folder privileges drop for.** Running as root with PUID/PGID, the drop takes ownership of the data folder; for `lodestar worker --data <dir>` that's `<dir>`, not `LODESTAR_DATA_DIR`, so the worker can write its lock, key and credentials there.
- **The address is saved before the credentials.** "Joined" means the credentials file exists, so a crash between the two leaves only an address, and the next start joins again.
- **`--token-file -` on a terminal says what to do** ("paste the join token, press Enter, then Ctrl-D"): it reads to the end of input.
- **A new `--join` replaces saved credentials only once the new ones are granted.** A refused token leaves the folder as it was, and when the folder is already joined the message says to start it without `--join` to keep that identity.
- **Exit status:** 0 for a local stop (SIGTERM, Ctrl-C) and a finished drain; 1 for a revocation, an expired certificate, a refused token, another protocol version or a replaced session, each with one line saying what to do. Privileges drop to PUID/PGID as for the other commands that write the data folder.

## The token (plan Q2, answered: owner §2.47)
- **A file or stdin, as V6-cluster2 decided, and never argv.** No flag takes the token itself.
- **A first join may take it from `LODESTAR_TOKEN`** (the owner accepted Q2's recommendation; runner, 2026-11-06T23:15Z), for the container templates. Only while the folder has no credentials: once it's joined, the variable is ignored and the worker prints a warning to remove it from the container's settings. The address comes from `--join` or `LODESTAR_JOIN`, which the Unraid template already names (the address isn't secret). A blank variable counts as unset; `--token-file` wins over the variable, with a line saying the variable was ignored. The worker's copy of the value is zeroed once parsed; the process environment itself still holds it, as Q2 accepted.
- **The coordinator side already enforces the rest:** a token is single-use (redeemed once, `JoinError` otherwise), bound to the worker name it was made for (the grant carries that name) and lasts 15 minutes (`JOIN_TOKEN_TTL_SECS`). The in-process tests show a reused and an expired token both refused with the one message.
- **It reaches no output.** Every line the worker prints is fixed text plus a worker name, an address, a path or a number. `JoinToken` and `Credentials` print no secret through `Debug`, a malformed token's error names only what's wrong, and every join refusal is the same sentence (`worker::REFUSED`): expired, already used or not this coordinator's. The tests grep the worker's output, the coordinator's log and (on Linux) a file-joined worker's `/proc/<pid>/cmdline` and `environ` for the token and for its secret part alone.

## The session (`worker/session.rs`)
- **Reconnect back-off:** capped exponential with equal jitter, 1 s doubling to a 2-minute step, each wait between half and all of its step (random from the OS source). It resets once a session is up. Waits are `tokio::time` sleeps; a test checks the exact waits on paused time with the jitter fixed.
- **What stops it, and what reconnects:** `Stop(Revoked)`, a `Renew` refused as revoked or expired, and a certificate past its end (checked before each dial and every minute) stop it at once; so do `VersionMismatch`, `IdentityMismatch`, `Replaced` (another copy of the same credentials connected) and `Drained`. `Protocol`, `HeartbeatTimeout`, `Shutdown`, a closed connection and a failed dial reconnect. A revoked worker that's offline can't be told apart from an unreachable coordinator (the TLS handshake is simply refused), so it keeps retrying at the cap until its certificate expires.
- **Renewal at half-life, then an immediate reconnect.** The coordinator's sweep checks the certificate a session was opened with, so a session left on the old certificate would be stopped as `Revoked` when that one expires (72 h), and the worker would wrongly stop. After a renewal the worker saves the new credentials and connects again at once on them, without back-off. `TooSoon` waits the hour; any other failure retries after 10 minutes. A failed save keeps the new credentials in memory and is retried each minute; the old ones on disk still work until they expire. `Welcome.renew_now` (a CA being rotated out) renews at the first check.
- **A stop the coordinator calls `Revoked` is reported as expired when the certificate has run out**, for the same reason.
- **Drain:** the runtime finishes its work and returns the outcomes, the session reports them (≤ 1,024 per batch) and says `Drained`; the coordinator re-grants any lease left out and stops the session with `Drained`. A drain asked again after a reconnect drains again.
- **`Hello` reports only the core count** for now; RAM, external IPs, companions and egress are WK-10's.

## Secrets-key rotation
- **`lodestar worker --rotate-key` (worker stopped) is the worker's rotation** (runner, 2026-11-06T23:14Z; flagged to the owner under §2.19): `SecretStore::rotate`, `Credentials::reseal`, `SecretStore::retire_old_keys`, under the folder lock, so it's refused while the worker runs (tested). Without a command the reseal would have no caller in the binary.
- **The old key is retired only once the reseal is written and verified:** the file opens and its key is sealed with the new primary key. A crash after any step leaves credentials that open (both keys are kept until the retire), and running it again finishes the job. The test rotates, reseals, retires and opens with only the new key, simulates a crash after each step, and shows that skipping the reseal strands the credentials. It prints no key material.
- **Each save reads `secrets.key` again**, so a renewal never seals with a key an earlier rotation replaced.

## Output
- **Plain stderr lines (`lodestar worker: …`), not catalogued log events.** Like the other CLI commands, the worker prints its status; adding events would touch the binary's log catalogue, its golden file and the web's event names, which other slices own now. Catalogued `worker.*` events (connected, reconnecting, renewed, stopped) belong with the worker's status page and metrics.

## Notes for later slices
- **WK-3:** add `mod have;` in `worker/mod.rs`. The have-filter key and snapshots arrive as `WorkerEvent::Snapshot` and the `HaveSnapshot`/`HaveDelta` messages; route them from `Work::event` or give the session a branch for them.
- **WK-10:** add `mod runtime;` and `mod budget;` in `worker/mod.rs`, and replace `session::Idle` with the runtime behind `session::Work`. `Work::event` gets `Assign`, `Regranted`, `Hints`, `Snapshot`, `Reverify` and `Accepted`; `Work::drain` returns the outcomes to report. The runtime needs the `WorkerSession` for claims, reports and `committed`, so expect to widen the trait (or hand the runtime a cloneable handle). **The idle worker holds what it's re-granted:** batch-0 `Grants` arrive without a claim, and heartbeats keep those leases alive while it stays connected, until a drain or a stop hands them back. That's harmless while no remote worker claims anything, but it's the runtime's job once it lands. Fill `Hello`'s capabilities too. **A drain or a renewal blocks the session loop while it runs:** `drive` awaits them inside a `select!` arm, so neither a shutdown nor the event queue is read until they return (a renewal waits at most the 15 s reply timeout). Harmless while idle; a long drain should run beside the event loop.
- **WK-18:** the templates can pass `LODESTAR_JOIN` and `LODESTAR_TOKEN` and run `lodestar worker` with no flags: the first start joins, later starts ignore the token with a warning. Don't pass `--join` with `--token-file` on every start: that always joins, and a spent token then fails with the one refusal message (exit 1). Give the worker a volume of its own for its data folder (the default is `LODESTAR_DATA_DIR`). **A drained worker exits 0, and the coordinator keeps it draining until it's resumed**, so under `restart: unless-stopped` it restarts, is drained again and exits again, over and over. Either the template's restart policy, or a later decision that a drained worker stays connected and idle, should handle that.
- **WK-19 (the workers chapter, the runner's):** document `lodestar worker` (join with `--token-file` or `-`, or `LODESTAR_TOKEN` and `LODESTAR_JOIN` for a first join; remove the token afterwards), `--data`, what each stop message asks for (join again after a revocation or an expired certificate), and `lodestar worker --rotate-key` with the worker stopped.
- **For the cluster library (runner):** a session whose certificate expires is stopped as `Revoked`. A distinct reason (`Expired`) would let a worker say so without checking its own clock. WK-2 works around it, so nothing is blocked.
