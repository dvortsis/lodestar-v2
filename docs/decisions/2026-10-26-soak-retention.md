# Snapshot retention follow-up decisions (local slice)

- **Deletion evidence is independent of fetch holds.** Store migration V12 adds `snapshot_deletions (hash, at)` and an atomic torrent-delete trigger. It retains only swarm hashes and when they were deleted, never titles or sealed names. Expiry, manual release, rule release and refetch eligibility do not consult or clear it. This refines owner decisions §2.16–2.17 and §2.21 without extending sealed-name retention.
- **Use hash identity across snapshots.** Numeric torrent IDs are not sufficient across rollback histories. The trigger records the canonical hash and any truncated v2 alias at `unixepoch()`; deleting a hash again moves its time forward (`max`). Snapshot cleanup uses the existing alias-aware lookup.
- **The backfill keeps only plausible deletions.** Migration seeds quarantine and tombstone hashes at each hold's own time (the later of the two when both exist), and skips any hash that is live again by its v1 hash or v2 alias, so a live torrent with a leftover hold isn't purged from snapshot copies. Evidence already lost on older builds cannot be reconstructed by this migration.
- **A row matches only snapshots taken up to a day after it.** A journal row is looked up in a snapshot only when `taken_at <= at + TAKEN_MARGIN` (one day, the margin `VACUUM INTO` already gets for holds). A hash deleted and then fetched again stays in snapshots taken more than a day after the deletion: those copies hold the live torrent, not the deleted one. Incremental passes use the same per-snapshot marks as holds, so an hourly pass looks up only rows added since the last one.
- **The journal is capped at the rollback window.** Every pass drops rows older than `RETAIN_SECS + TAKEN_MARGIN` (91 days): such a row matches only snapshots taken more than 90 days ago, which have expired. This holds whatever else fails, so the journal is bounded by 91 days of deletions and §2.21's "nothing deleted outlives 90 days" still holds.
- **Acknowledgement trims the journal early, per row.** A pass with no failed purge and no failed unlink drops the rows it read, matched on `(hash, at)` so a deletion added or moved forward during the pass stays. With no snapshots left and no failure, the journal is cleared. A failed purge, lock error, failed unlink or restart keeps the rows until the next good pass or the cap.
- **A snapshot of an unknown schema doesn't hold the journal back.** This build can never purge such a file, so keeping rows for it would only grow the journal; it is still deleted at 90 days, which ends what it holds. It gets no per-snapshot mark, so each pass looks at it afresh and warns.
- **A snapshot with an unreadable modification time is deleted.** Its age can't be shown to be inside the 90-day window, and the journal no longer keeps rows past that window, so keeping it would keep deleted data indefinitely. The safe bound is to treat it as expired, with a warning in the log. In practice this is a pre-1970 or out-of-range timestamp that `VACUUM INTO` never sets. A snapshot dated ahead of the clock is matched against every journal row and hold, as its time says nothing of when it was taken.
- **Preserve existing snapshot rules.** Secure deletion, checkpoints, snapshot modification times, 90-day expiry and ordinary hold semantics remain in place. A current-format snapshot also contains its own deletion journal and trigger, so the rows the purge deletes there are journaled in the snapshot too; a rollback to it keeps them. Historical schemas need only their existing torrent tables for hash matching. Applying a restored snapshot's journal on rollback is a recorded follow-up (I3).
- **Validation.** Rust tests cover the V11-to-V12 backfill (times, merged holds, live v1 and v2 hashes skipped), a hybrid delete journaling both hashes and a repeat delete moving the time, the no-snapshot and failed-unlink paths, an unknown-schema snapshot acknowledging and taking no mark, the one-day match window and a refetched hash, the 91-day cap under a failing pass, an unreadable modification time, expiry/release, a locked snapshot followed by restart and retry, old schemas and differing IDs. Each new test was checked to fail with its fix reverted. The `trigger_cost` bench has an arm with both triggers.
