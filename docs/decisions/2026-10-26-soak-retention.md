# Snapshot retention follow-up decisions (local slice)

- **Deletion evidence is independent of fetch holds.** Store migration V12 adds `snapshot_deletions` and an atomic torrent-delete trigger. It retains only swarm hashes, never titles or sealed names. Expiry, manual release, rule release and refetch eligibility do not consult or clear it. This refines owner decisions §2.16–2.17 and §2.21 without extending sealed-name retention.
- **Use hash identity across snapshots.** Numeric torrent IDs are not sufficient across rollback histories. The trigger records the canonical hash and any truncated v2 alias; snapshot cleanup uses the existing alias-aware lookup. Migration seeds extant quarantine/tombstone evidence before it can expire. Evidence already lost on older builds cannot be reconstructed by this migration.
- **Acknowledge successful cleanup, not elapsed time.** Every pass includes pending journal hashes regardless of incremental hold timestamps. Only a pass with no failed/skipped snapshots acknowledges the hashes it read. Unknown schemas, lock errors, failed expiry deletion and process restarts retain obligations. With no remaining snapshots and no errors, the journal can be cleared. A later deletion arriving during cleanup is not removed by bulk acknowledgment.
- **Preserve existing snapshot rules.** Secure deletion, checkpoints, snapshot modification times, 90-day expiry and ordinary hold semantics remain in place. A current-format snapshot also contains its own deletion journal; historical schemas need only their existing torrent tables for hash matching.
- **Validation remains explicit.** Source-level SQLite checks exercise V1–V12 SQL, atomic trigger rollback and V11 hold backfill. Rust regressions cover expiry/release, a locked snapshot followed by restart/retry, old schemas and differing IDs. Rust execution and migration/rollback smoke tests await actual collector completion. This is prepared source, not deployment approval or acceptance.
