# SRC-13b decisions (torrent-cache host wiring)

Slice session, 2026-11-05. Runner brief SRC-13b; the steps are in `docs/decisions/2026-11-05-SRC-13.md`, "What the wiring slice (SRC-13b, runner) must do". The #467 review items come from `docs/decisions/2026-11-05-X-source-adult.md`. Architecture §18.2 enrichment #3, §18.5, §18.7. This file supersedes SRC-13's "the plugin stays unregistered" and its note that the lease-free entry belongs to another slice.

- **The plugin is registered** (`crates/lodestar/src/torrent_cache.rs`, `services.rs`). It's built at every start from its saved settings, off by default, and listed on the Sources screen. Its feed runs only while it's enabled at that start (`Pipeline::torrent_cache_feed`). In fixture mode no plugin gets egress, as before.
- **Consent covers the configured hosts: the endpoints come from the config, in `crates/sources-plugins/src/torrent_cache.rs`** (the brief's first option). Each `TorrentCache` builds its own `Manifest`: `MANIFEST` with one `https` endpoint per configured host, sorted and listed once each. SRC-4's `consent::version` already digests the manifest's endpoints. So `need`, `need_in`, `Control::update_source` and the start's check cover exactly the listed hosts, with no change to `crates/sources/src/consent.rs`. The consent dialog (`GET /sources`) lists them too.
  - A new host, a changed host, a port other than 443 that's added or changed, or an emptied list asks again. An acknowledgement given while the list was empty covers no host. A changed path on the same host doesn't ask again, because the same third party is contacted.
  - The ports are included because the manifest's endpoint text is what the dialog shows. The egress host list (`host_key`) ignores ports.
  - The manifest's endpoint list is `&'static`, so it's leaked once per plugin built: at most 8 short strings per start.
  - **OPEN, for the slice that adds the settings write path (the runner's call).** SRC-4's version digests the endpoints with 64-bit FNV-1a. Its comment says that isn't a security boundary because the manifest is compiled in. With endpoints from the config, that no longer holds: someone who can change the cache list could, in principle, pick a list whose digest collides with the acknowledged one. Today nothing can write the list. Changing the digest to SHA-256, or storing the acknowledged list in the `Ack` and comparing it exactly, needs either a new dependency for `lodestar-sources` or a change to the `Ack` format. That belongs with the write path, so it isn't done here.
  - Tests: `a_new_or_changed_host_asks_again_and_an_unchanged_list_doesnt` and `the_manifest_lists_the_configured_hosts_as_https_endpoints` (plugin crate), and `a_saved_acknowledgement_covers_only_the_hosts_it_was_shown` (host, through `need_in` as the start runs it).
- **The egress gets the plugin's own endpoints.** `SourcePlugin::endpoints()` is a new trait method (`crates/sources/src/plugin.rs`). It defaults to `Endpoints::manifest(manifest.endpoints)`, so every other plugin is unchanged. The pipeline's `egress::build` uses it. While it's `None` (no cache listed), the client gets an empty pinned host list, so nothing is reachable. `SourceStatus` gains `auto_dns` from the same endpoints, so the Sources screen's SOCKS5 warning follows what the plugin really uses (local DNS for user-entered hosts).
- **Saved settings: `SourceSetting::Config`** (`sources.config.<plugin>`, `crates/store/src/sources.rs`). It holds the settings form's JSON, read at start (`saved_config`). Missing, unreadable or refused settings give an empty list, never an error, and nothing about them is logged. A purge drops them with the other settings.
  - **There's no write path yet.** No API takes plugin settings today: `PATCH /sources/{id}` has no config field. Until a follow-up adds one (SRC-15b's backend, or a SRC-13c; the runner's call, asked 2026-11-05), the list stays empty and the plugin is inert. A settings change applies at the next start, as egress and schedules do, and a host change then switches the plugin off until it's acknowledged again.
- **Feeding the queue** (`crates/lodestar/src/torrent_cache.rs`, `run`):
  - **Unverified items:** one `Cursor` page every 60 s (`PAGE_EVERY`), never more keys than the lane has room for (`Queue::room`, new). So in normal running nothing is dropped, rather than being dropped and counted. The first page comes one interval after the start. Each key becomes `Lookup::new(key, Why::Unverified, false)`, and the cursor skips private items.
  - **User interest:** the API's existing `ApiEvents::interest(id)` hint (the top search hits, a detail view) also goes to the cache feeder, through a bounded queue that never waits. The feeder reads what the id may look up from the store (`lodestar_pipeline::torrent_cache::interest`), never from the caller:
    - an unverified item: its key, private when the item is, or when a torrent stored under the key is `private_source` or BEP 27 private;
    - a stored torrent only when its file list is partial (an import), private when it's `private_source` or BEP 27 private;
    - a complete torrent or an unknown id: nothing, so no lookup.
  - A key interest already queued isn't queued again; the set is forgotten at 4,096 keys.
  - Only a key that was queued is remembered, so a hint dropped on a full lane can come again.
  - End-to-end test: `interest_in_a_private_item_or_torrent_never_reaches_a_cache` (host) runs the real plugin over a recording fake cache. Hints for a private item, a `private_source` partial torrent, a BEP 27 one, a complete one and an unknown id reach no request; only the public partial torrent's key is asked.
- **Judging** (`lodestar_pipeline::torrent_cache::judge_task`). The pipeline's own task takes each file from the feed and runs `judge_sealed` on the blocking pool, with its own `Preparer` and the filter's current rules. `judge_sealed` is `judge` that also seals a quarantined name for its review, as the writer seals a fetched one. A `Refused` is counted and dropped there. `Held` now carries the sealed name and `adult_hold`. `prepare_one` stays private to `worker.rs`, which ENR-1 owns, so `judge`'s duplicate of it stays, as SRC-13 had it.
- **Through the always-adult mask.** The writer's lease-free entry goes through `Writer::judge`/`source_adult`, as a fetched result does. A file whose key an always-adult source's unverified item (or stored torrent) holds is judged again as adult and stored Adult. Test: `an_always_adult_sources_item_stays_adult_through_a_cache`.
- **The writer's lease-free entry** (`Writer::commit_cache`, beside the pool's `Results`):
  - **`Store`** goes through the same transaction, re-judge and promotion as a fetched result. It carries a lease the coordinator never issued, which names the plugin as its only finder (`Committing::lease_free`, `leased: false`). So:
    - an unverified item under the key is promoted under its own id (§18.5);
    - a stored partial import is upgraded;
    - the row gets the plugin's source bit. That bit is the stored provenance: the API names it by the manifest's name, "Torrent cache".
  - **It isn't the crawl's.** It never enters the funnel, the crawler gate or the writer's own `stored` count, and never ends a lease. Its row is flagged `IMPORTED`, as a refetch's is, so `rollup --repair` keeps it out of the crawl's cohorts too. A new row's discovery time is the commit's, and a promotion's is the item's first sighting. Its counts are `WriterStats::torrent_cache`.
  - **Once it's stored,** the file's trackers, comment and creation date (`Verified::claims()`, `Verified::provenance()`) go through `unverified::ingest` as that source's claims on the torrent, judged as any source's claims are. They're never sent for a file that was held or refused, and storing them isn't counted as a rediscovery (no gate exclusion, rollup, scrape hint or hot-column touch). If the process stops between the two, those claims are lost, and the torrent itself is kept.
  - **Rules that changed since judging:** the writer judges again, as for a stale worker verdict. A `Held` judged under older rules is dropped unwritten (counted `stale`). An unverified item's key comes up again with the cursor's next round; a partial import's only with new interest. Test: `the_writer_judges_a_stale_cache_file_again`.
  - **`Held`** is written as a held ingest verdict is. Intake is told before the write. Then the hold is written (tombstone or quarantine, rule id, evidence and the sealed name of a quarantine), in one transaction with removing the unverified item under the key (`refile_unverified`) or a torrent stored under it (`hold_claims`). Test: `a_held_cached_file_is_never_stored_and_its_item_goes`.
- **The crash window from the #467 review is closed in the store** (`AdultMark`, `Store::set_adult_mark`). The writer sets its always-adult sources and the Adult content-type code on its connection at start. Then `Store::write` and `Store::promote` mark for the backfill (`parser_ver = 0`), in their own transaction, every row they store or touch that such a source has found and that isn't stored Adult. If `adult_by_source` never commits, the backfill finds the mark and applies the same correction. When it does commit, its enrichment write clears the mark. A row with your own Not adult correction isn't marked, since the adult step leaves it alone and nothing would clear the mark. With no always-adult source registered (today), the mask is empty and nothing is read.
  - Tests: `a_write_marks_rows_an_always_adult_source_found` (store), and `a_crash_before_the_adult_step_leaves_the_row_marked_for_the_backfill` (writer, which skips the step after the commit as a crash would).
- **`Writer::judge` and `source_adult` run on the blocking pool** (the #467 nit). They're free functions over `&Store`, called through `spawn_blocking` with the store moved in and back, with no behaviour change. An empty batch skips the hop.
- **The status page shows the plugin's `Stats`** (`/api/status` `torrent_cache`, and a "Torrent cache" section on the status page) beside the pipeline's counts: received, stored, promoted, already stored, held, refused, stale and errors. It shows no hash and no name.
- **Politeness: SRC-13's numbers are confirmed, unchanged** (§2.26 numbers; the runner flags them under §2.19). That's one lookup a minute per cache, one request every 10 s per host, back-off from a minute to six hours, and 256-lookup lanes. With the feeder paging only into free room, the lanes don't overflow in normal running. At most about 1,440 lookups a day reach any one cache, interest first. A large unverified backlog therefore takes weeks to go through (100,000 items at one a minute is about 70 days), which is the intended trade: a third party's free service, and each lookup tells it a hash. A faster drain would need more caches, not a shorter interval.
