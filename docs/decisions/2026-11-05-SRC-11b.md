# SRC-11b decisions (Sonarr and Radarr webhooks)

Slice SRC-11b of `docs/plan/2026-11-01-v06-sources.md`. It covers architecture §18.2 (rank 17, the "Sonarr/Radarr webhooks" half), §18.7 (`private_source`) and §12 (security), and the plan's §5 Q9 (runner: a per-integration token, constant-time compare, size caps). The code is `crates/api/src/webhooks.rs` (the routes), `crates/sources-plugins/src/arr.rs` (the parser, the mapping and the plugin), their tests and fixtures, and `fuzz/fuzz_targets/arr_webhook.rs`.

## The inbound route
- **`POST /api/v1/webhooks/{integration}`, `sonarr` or `radarr`.** The route names the app; the body's own `instanceName` is never trusted for that.
- **The token comes as HTTP Basic auth's password or as `Authorization: Bearer`.** Sonarr's and Radarr's webhook connection has Username and Password fields (Basic auth) on every version; custom headers only on recent ones. The username is ignored. **A query-string token is never read**: proxies and access logs keep URLs (§12.1). Two `Authorization` headers, a value over 256 bytes, or any other scheme hold no token.
- **One answer for every failure to authenticate: `401 login_required`, the same body as a missing session** (with its `setup_required`). No token, a malformed one, a wrong one, none made yet, another integration's and an unknown integration all get it. **A store that can't be read is `503 webhooks_unavailable`, never "no token"** (self-review): a transient SQLite error mustn't fail the real app's right token or spend its address's attempts. That code, rather than a webhook-specific one, also keeps the route inside the existing route-contract tests (`tests/openapi.rs`: every non-open route answers a stranger with `login_required`).
- **Only a token of the right shape is checked, and a wrong one spends a failed check** from the per-IP bucket API keys use (`Auth::key_failures`, 10 then one every 6 s), logs `auth.key_refused` (kind `webhook_token`, reason `wrong`, `unset` or `unknown_integration`, the client only), and logs `auth.rate_limited` once when it empties the bucket, as the key guard does. An empty bucket is `429 rate_limited` with `Retry-After`. A value of the wrong shape can't be a guess at a 256-bit token, so it spends nothing; it costs one header parse.
- **No I/O before authenticating** (self-review). The two token hashes are cached in `Webhooks`, read from the store on the first call and kept current by the token routes. Each token change writes the store and updates the cache in one step under the store's lock (runner review), so two changes can't interleave between write and cache: a removed token can't stay valid in the cache, and cache and store always agree. A version counter keeps a first read that raced a token change from being cached. Without the cache, every random well-formed token cost a blocking-pool hop and the shared user-data lock, and rotating addresses would make that unlimited.
- **Then, in order:** `503 webhooks_unavailable` if the host hasn't wired a sink; `413 webhook_too_large` from `Content-Length` before reading, and again while reading (`to_bytes` with the cap), at 256 KiB (a read failure with a declared length is the connection's: `400 webhook_unreadable`); the integration's own bucket; then the sink. The body is never read before the token checks out.
- **Rate: a burst of 120 calls, one a second after that, per integration** (a §2.26 kind of number, the runner's; flagged under §2.19). Sonarr sends one Download call per imported file, so a long season pack (an anime cour of 100 episodes) bursts that many; an RSS sync can grab a few dozen releases at once.
- **A real event that's dropped still answers `200 {"found": false, "dropped": true}`** (self-review): over the rate, the source off, or the pipeline full. Sonarr and Radarr record every non-2xx answer as a notification failure and disable the connection for escalating periods, up to hours, so an error here would silence every later grab. The drop is counted (`refused`) instead. **Only the app's Test call is answered with an error while the source is off** (`503 source_off`), so the Test button shows it; a body that isn't an event is `400 malformed_webhook`, which a real app never sends. A find or an event with nothing to find is `200 {"found": true|false, "dropped": false}`. Counts per integration since start: `GET /webhooks` `found`, `ignored`, `malformed`, and `refused`, which is every authenticated call not delivered: over the rate, the source off, the pipeline full, a body over the cap (`413`) or one that couldn't be read.
- **Nothing from the request is logged.** The module logs nothing itself; `api.request` logs the route template (`/api/v1/webhooks/{integration}`) and status only, never a header, the URI or a body.
- **OpenAPI:** the route is documented under the session scheme, like the feed route, because `openapi.rs` gives every path outside its `OPEN` list the session requirement and `tests/openapi.rs` checks that. Its description says it takes the integration's token instead. **Handoff (shared file, runner's call):** a `webhookToken` security scheme in `openapi.rs` for this path.

## Tokens
- **`lsw_` and 43 characters of base64url: 32 bytes from the operating system's RNG**, the same strength and alphabet as API keys (§12). There's no public prefix: one token per integration, so the integration is the lookup key.
- **Stored as SHA-256 only**, as 64 hex digits in the `settings` table under `webhooks.<integration>.token_sha256`, through the user-data store. No migration is needed, and no other subsystem reads that prefix: the settings registry reads `settings.*` only, and settings export is the registry's.
- **Compared in constant time** (`ct_eq`: an XOR-fold over all 32 bytes behind `black_box`, `#[inline(never)]`). When no token is stored, the presented hash is compared against a fixed stand-in, and an unset token never matches, so both paths do the same work. A unit test counts `ct_eq` calls on every path (a test that it's used, not a timing test).
- **Made with the fresh password** (`POST /webhooks/{integration}/token`, §20.11, as `POST /keys` does). A new token replaces the old at once. It's in that response only, with `Cache-Control: no-store`; `GET /webhooks` says only `token_set`. **Removed without one** (`DELETE …/token`): it only takes access away, as revoking a key does. Both are session-only, same-origin JSON.

## The plugin and parser (`arr.rs`)
- **Id `arr_webhooks`, kind Discovery, consent None, risk Low, no endpoints, off by default.** It sends nothing, so no egress, no HTTP and the strict default caps. Consent None (a toggle) because nothing leaves the machine, and the token made under `/webhooks` is the setup. One plugin for both apps: they share the shape, and the token is per integration.
- **Push, not poll.** While it runs, the plugin lends its `Emitter` to the shared `Inbox`; the inbox puts each find on it with `try_emit` (never waits, a full pipeline is dropped and counted by the emitter). When the run ends, however it ends, a guard takes the emitter back, and the inbox answers `Off`, so a source turned off accepts nothing and keeps nothing. The guard is tied to its run: an old run ending after a newer one started leaves the newer one's emitter in place (self-review).
- **Bounded reading, never a whole-tree parse:** SRC-9's `lodestar_sources_feeds::json` reader, at most 256 KiB, depth 16, 20,000 values, any array longer than 1,000 elements refusing the body (runner review: the reader's over-long flag was ignored at first), and a kept string's raw length checked against 4 KiB before it's copied. A body that isn't UTF-8, isn't one JSON object, has text after it, or breaks a cap is `Malformed` whole and counted (`Inbox::malformed`); nothing half-read is used. The caps' reasons are on `arr::LIMITS`.
- **What's read:** `eventType`, `downloadId`, `release.releaseTitle` and `release.size`, the series' (Sonarr) or movie's (Radarr) `tvdbId`, `tmdbId` and `imdbId`, and the imported file's `sceneName` as a fallback title. A repeated field keeps its first usable value (an over-long or undecodable first string leaves it open; for `size`, the first number, which a later non-number doesn't clear); a field of the wrong type is skipped. A Download that carries the `release` object (Sonarr 4, Radarr 5) claims the release's size and title.
- **The key is `downloadId` when it's 40 hex digits** (a torrent client's id, any case). A Usenet client's id isn't one, so its events find nothing (`200 {"found": false}`). Only Grab and Download events find a key; Test and every other event type are ignored.
- **The claims:** the release title (cleaned of control, bidi and zero-width characters, cut to the claims' name limit; an over-long one is dropped and the scene name stands in), the release size within 1 B to 1 PiB, and the catalogue ids. **An imported file's size isn't used**: Sonarr imports a season pack one file at a time, and one file's size isn't the release's.
- **The client's category isn't claimed (deviation from the brief's list).** Neither app's webhook body carries the download client's category, and `Claims` has no category field. The catalogue ids (`tvdb` for Sonarr, `tmdb`/`imdb` for both) say what it is instead. **Handoff:** a category claim, if SRC-3's claim search wants one.

## §18.7
- **Every find is `private_source`**, with no peers, no external reference, no publish date, no trackers, no files and no publisher. The release came through the user's own indexers, which may be private trackers, and a public lookup would leak its hash (BEP 27). The pool refuses private keys to DHT `get_peers`, PEX and public announces (`crates/sources/tests/pool.rs`), and exports and feeds leave `private_source` rows out (`crates/api/tests/export.rs`, `alerts.rs`). This slice's tests check the flag and the empty public fields on every find: the fixtures, two property tests and the fuzz target.
- **The end-to-end leak test across output surfaces is deferred to SRC-G (deviation from the brief; the runner's call).** The plugin isn't registered with the pipeline here (no owned line in `services.rs`), and neither `crates/api` nor `crates/sources-plugins` can reach the other's test harness without a new dev-dependency. SRC-G's `tests/safety.rs` will cover this plugin once the runner adds SRC-11b to SRC-G's deps in `runner/slices.yaml`; that file doesn't exist yet.
- **Never kept:** the indexer's name (it can name a private tracker), the download client, file paths, URLs, `applicationUrl` and `instanceName`.

## Handoffs
- **Wiring (SRC-14 or the host slice):** build `ArrWebhooks`, register it with the pipeline, and add `Webhooks::new(sink).layer()` to the API router, where the sink maps `webhooks::Integration` to `arr::App` and `arr::Delivery` to `webhooks::Delivered` (a few lines in `crates/lodestar`). Until then the route answers an authenticated call with `503 webhooks_unavailable`. Nothing is wired in `services.rs` here (the brief owns no line there).
- **Settings → Sources (SRC-15b):** a webhook panel that makes the token (with the password), shows it once with the URL to paste, and shows the counts.
- **User docs:** a how-to for connecting Sonarr and Radarr (Settings → Connect → Webhook, URL, the token as Password), once the panel exists.

## Tests
- `crates/sources-plugins/tests/arr.rs`: each app's Grab and Download fixture, Test, Usenet and other events, malformed bodies (empty, not an object, trailing commas and text, control characters, bad UTF-8, bad numbers, depth, value count, size, and the size cap's edge), field caps and cleaning, the manifest, the inbox only delivering while the plugin runs (and the plugin stopping within a second), a full pipeline answering `Busy` rather than blocking, an old run ending late without disconnecting a newer one, a Download carrying its release, and two property tests. No fixed sleeps: waits are `wait_for` on a condition.
- `crates/api/tests/webhooks.rs` with goldens `tests/golden/webhooks_*.txt`: tokens made with the password and shown once, every failure the same 401 and never reaching the sink, a query-string token ignored, the body caps before and while reading, malformed bodies counted, each integration's rate, the per-address failure bucket, replacement and removal, the cache following token changes, an unreadable store answering 503 without spending attempts, a long Basic username, and the dropped-call answers (200 for real events, 503 for a Test while off). Unit tests in `webhooks.rs` cover the token format, the `ct_eq` use count, header parsing and a Basic-auth round-trip property.
- **Fuzz:** `arr_webhook` (seeds in `fuzz/seeds/arr_webhook/`). Run here for 120 s on nightly: 9,534,560 runs, no failure. The runner review's two parser fixes (the first size wins; an over-long array refuses the body) came after that run; CI's 60 s run of the target covers them.
