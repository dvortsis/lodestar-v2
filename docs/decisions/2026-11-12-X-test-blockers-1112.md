# X-test-blockers-1112 decisions

- **A WireGuard handshake that never completed is its own leak-test outcome: `fail wireguard_handshake_never_completed`** (meaning: check the VPN credentials, for example an expired PIA key, then that the endpoint is reachable, since an unreachable endpoint also never completes one). The tester's run failed with only generic lines although the kill switch held. Reason: the report has to say why.
  - **How it's detected:** gluetun stays unhealthy for the whole wait, and its VPN interface has received 0 bytes. The counter is read up to five times, 2 s apart, because gluetun's VPN restarts recreate the interface: "no handshake" needs at least one successful read, and every read 0. It's read from `/sys/class/net/<if>/statistics/rx_bytes` by the capability-free probe container in gluetun's namespace. `wg show <if> latest-handshakes` would need `NET_ADMIN`, and gluetun may run WireGuard in userspace, where `wg` can't see the device. A counter that can't be read, or isn't 0, keeps the old `fail tunnel_healthy`: an unreadable counter is never read as "no handshake".
  - **It's still a failure, never a pass.** The final line stays `fail leak_test`, so start-block stops as before and passes the line on as it is. The tunnel-up checks that a dead tunnel can't answer (`ipv4_through_tunnel`, `tcp_literal_up`, `dns_up`, `tunnel_recovers`) report `skip`, never `ok`. Both kill-switch phases still run and judge their captures, so a real leak is still reported as a leak beside the handshake line.
  - The grammar's `fail <name>` lines can't carry prose, so the operator-facing wording ("WireGuard handshake never completed (check the VPN credentials)") lives in the name and the script's comment. Mapping step lines to sentences in `steps/run.py` is outside this slice.
- **The portable restart test reads the new copy's `app.serving` from the console or `lodestar.jsonl`, whichever shows it first.** On a saturated 4-vCPU Windows host the copy, at below-normal priority, served about 28 s after the restart, but its file log hadn't flushed by the 90 s deadline. What the test proves is unchanged: the old process exited with 80, the new copy's `app.serving` names the same port, `/healthz` answers there, and the old session still signs in (the same store). The 90 s deadline stays, with no fixed sleep. The earlier restart fixes, which are in the relaunch wait in `src/windows`, are untouched.
- **The bitmagnet PostgreSQL fixtures keep autoanalyze from running mid-import**, which fixes the `batches_are_bounded_by_count_and_memory` flake (#768, #774). The runner added this item. An autoanalyze that lands mid-import commits a transaction, and that moves the cluster snapshot `quiet()` compares between batches, so the read is refused with `NotQuiescent`. Two tables trigger one:
  - **The fixture's own tables:** the test's bulk inserts are over their autoanalyze threshold. They now turn autovacuum off (`WITH (autovacuum_enabled = false, toast.autovacuum_enabled = false)`).
  - **The shared catalog `pg_catalog.pg_database`:** every fixture's DROP and CREATE DATABASE counts toward its threshold, and a table's storage options can't reach a catalog (the runner's review, B1). `Fixture::new` now runs `ANALYZE pg_catalog.pg_database` right after it creates the database, so no autoanalyze of it is due while the test reads.
  - **Measured** on a local PostgreSQL 16 with `autovacuum_naptime = 1`: 3 failures in 15 runs before any change; 4 in 50 plus 1 more with the tables' option alone (the review); 0 in 80 with both. `quiet()` is unchanged.
  - **The product side is flagged, not changed:** a real source freshly restored by IMP-0 gets one autoanalyze pass, and it can be refused once while that runs. That's the conservative reading of "not quiescent", so nothing changes (runner, 2026-11-12).
