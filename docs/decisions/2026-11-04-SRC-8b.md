# SRC-8b decisions (RSS parser reads a bare `<infohash>`)

Slice SRC-8b, a follow-up to SRC-8 (`docs/decisions/2026-11-02-SRC-8.md`), for Academic Torrents (architecture §18.2). Its feed, `https://academictorrents.com/rss.xml`, gives each item's hash only as a plain `<infohash>` element in no namespace. Its guid and link are `/details/<hash>` pages and it has no magnet, so SRC-8's parser skipped every item as `no_hash`. SRC-10d (the plugin) builds on this.

- **`rss.rs` reads a no-namespace `<infohash>` child of an `<item>` or an `<entry>`.** The value goes through SRC-8's `hash()` unchanged:
  - v1 is 40 hex digits (either case) or 32 base32 characters, and v2 is 64 hex digits;
  - surrounding whitespace is trimmed, and CDATA and character references work as in any field;
  - all-zero hashes are invalid;
  - a present but invalid or empty value skips the item as `bad_hash`, even when a magnet is good, as for `nyaa:infoHash`.
- **The name is matched exactly, by namespace URI as SRC-8 decided.** `infohash` in no namespace counts; `infoHash`, `InfoHash`, a prefixed `<at:infohash>` and an `<infohash>` under a default namespace don't.
  - Inside an Atom entry it needs `xmlns=""`, because Atom's default namespace would put it in Atom's namespace, and Atom has no such element. That's the trivially symmetric reading the brief asked for. No Atom feed is known to carry it.
  - Academic Torrents binds `xmlns:academictorrents="https://academictorrents.com"` on its root but doesn't use the prefix, so that URI isn't tracked.
- **Precedence: `nyaa:infoHash`, then the bare `<infohash>`, then the first magnet.** The existing sources keep their place, and the new one sits between them.
  - **The first source present decides.** A source after it only adds the other hash version when the two agree on the version they share: SRC-6's `merge` rule, which SRC-8 already used between `nyaa:infoHash` and a magnet. A later source that disagrees, or is invalid, is ignored, as a disagreeing magnet always was.
  - So a valid `nyaa:infoHash` wins over a conflicting or invalid bare `<infohash>`, and a bare `<infohash>` wins over a conflicting magnet. An invalid first source still skips the item.
  - **Why the existing rule and not `bad_hash`:** the parser already had a conflict rule (first source wins, later ones merge in when they agree), and the brief asked to follow it where one exists. No known feed carries two hash elements. Either way the kept hash is the feed's own claim, as every `Item` field is.
  - **A repeated `<infohash>` is read once, and the first wins.** That's SRC-8's rule for every repeated field: a repeat costs nothing and can't spoil the item. A bad first one isn't replaced by a good repeat.
- **No new state or caps.** The element is one more field slot (`Option<Option<Hashes>>` per item), collected under the existing text cap (`max_text`, 64 KiB). The depth, element, item and byte caps are unchanged. A value over the text cap skips the item as `over_cap`.
- **Academic Torrents' `<size>` (bytes) and `<category>` aren't read.** They're in no namespace, and SRC-8 reads size and category only from Nyaa's namespace. Reading them is outside this slice; SRC-10d can raise it if the plugin needs them.
- **Tests:**
  - `tests/fixtures/rss/academictorrents.xml` is a recording of the real feed made on 2026-11-04 through the proxy. It keeps the channel and five of the 30 items as served (one has an `&amp;` in its title), with each description replaced by a placeholder. The descriptions are long third-party prose that the parser doesn't read.
  - `tests/rss_bare_hash.rs` has golden cases for valid, uppercase, base32, v2, wrong-length, zero, empty and repeated values, and for precedence against `nyaa:infoHash` and magnets.
  - `tests/rss_props.rs` adds the element to the fragment soup and to the read-back property, and a differential property: any value in a bare `<infohash>` gets the same verdict as the same value in `nyaa:infoHash`.
  - `fuzz/fuzz_targets/rss.rs` runs the same differential check, with the fuzz input (up to 4 KiB, escaped) as the value.
