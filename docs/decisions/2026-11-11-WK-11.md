# WK-11 decisions (the worker's spool)

The worker's bounded on-disk spool (architecture §19.6, workers plan WK-11, owner wkq1): `crates/pipeline/src/spool.rs` (the segment format and folder), `crates/lodestar/src/worker/spool.rs` (spooling, replay and the lease-count check), small hooks in `worker/runtime.rs` and `worker/session.rs`, the `--rotate-key` reseal in `worker/mod.rs`, the fuzz target `worker_spool` and the metric rows in `docs/metrics.md`.

**Shared edits outside WK-11's owns, approved by the runner (2026-11-11):** `SecretStore::seal_bytes`/`open_bytes` in `crates/integrations/src/secret.rs`; the Q7 refusal in `crates/pipeline/src/remote.rs`; the `runtime_config.spool` line in `crates/lodestar/src/cli/worker.rs`; and the `late_refused` wording in `docs/metrics.md`. **WK-11b** takes lease correction (below).

## The format
- **Append-only segments** in `<data>/spool`, named `<seq>.lsp` (16 hex digits, oldest first). Header: magic `LSP1`, version 1, three zero bytes, the worker id, the segment's seq, its creation time, and a checksum. Then frames: `len u32`, `sum u64`, the sealed body. Integers are little-endian. The module docs have the byte layout.
- **One record per frame:** a `Results` or `Counters` payload exactly as encoded for the wire (WK-8's note: spooled as encoded), with its batch id, when it was spooled, and the key and fencing token of each lease it carries. Nothing else. A record holds no peer address (§18.7, §19.6), and the names inside a payload stay sealed under the wire key, which the worker never writes down (WK-8).
- **Checksums find damage; the seal is the defence.** `sum` is SipHash-1-3 under a fixed key, over the header or over a frame's `len` and body. It spots a torn or damaged frame without opening it. Each body is sealed with the worker's `SecretStore` (XChaCha20-Poly1305) for the context `worker-spool/v1:<worker>:<seq>`, so a record moved into another segment or another worker's spool doesn't open.
- **Bounded reads.** Every length is checked against the bytes left and its cap before anything is allocated: a frame ≤ 1 MiB, ≤ 1,024 leases (a `Results` batch's record cap), a payload ≤ 512 KiB (`MAX_OPAQUE`). A segment is read whole, but never more than 8 MiB plus one frame, since it closes at 8 MiB.
- **Torn and damaged segments.** A final frame cut short, failing its sum, or followed only by zeros (a file grown before its data landed) is a torn write: dropped and counted, never half-used. A bad frame with more after it stops that segment there: the records before it are used, none after, and it's counted as damaged. A segment whose header doesn't read, or that names another worker (a folder that joined again under a new id), is removed when the spool opens. **Damage is counted, not logged:** a new log event needs its message pair in `web/` (the logging settings' catalogue), which no WK-11 path owns. The spool already returns the segment's file name and the part that failed (`Damage`, never a byte of it), so the event is a one-line follow-up for a slice that owns those files.
- **Decoders are fuzzed** (`fuzz/fuzz_targets/worker_spool.rs`: segments and record plaintexts). Property tests cover the record round trip, every cut of a record, and a segment cut anywhere giving back exactly its whole frames.

## Sealing (owner wkq1)
- **With the worker's own `SecretStore`** (`<data>/secrets.key`), through a new byte seal (runner-approved shared edit): `SecretStore::seal_bytes(context, &[u8])` and `open_bytes(context, &SealedSecret) -> Zeroizing<Vec<u8>>`.
  - It uses the same XChaCha20-Poly1305 format and key ids as `seal`, so `rotate`, `retire_old_keys` and `needs_reseal` apply unchanged. No existing function, behaviour or byte changed, and no dependency was added.
  - **The two kinds of seal can't open as each other.** The byte seal's associated data is the header, a 0xFF byte, then the context. No UTF-8 text context (all of `seal`'s) contains 0xFF, so a spool record never opens as a credential `Secret`, and a credential never opens as a spool record, whatever the two contexts. Tests cover both directions, the round trip, a wrong context, and a rotation.
  - **Plaintext** goes in and comes out in `Zeroizing` buffers, and nothing prints it. A seal is refused above `SecretStore::MAX_BYTES` (1 MiB); a record's largest plaintext (a 512 KiB payload with 1,024 leases, about 541 KiB) is checked against it at compile time.
- **`--rotate-key` reseals the spool before the retire** (WK-2's note). The old file's blocks aren't zeroed by the rename. What they hold is sealed under the key the rotation then retires, so it no longer opens, subject to the §2.17 limits below. After the credentials are resealed, every segment holding a record sealed under an old key is rewritten whole under a temp name, synced and renamed over the old one, which is closed (the worker is stopped: its lock is held). The old key is retired only once no spool record needs it; otherwise the rotation fails and both keys stay. Test: `rotate_key_reseals_the_spool_before_the_retire`.

## Writes
- **A segment is created atomically:** its header goes to `<seq>.tmp`, which is synced, put into place, and the folder synced on Unix. A crash leaves no segment or an empty one; leftover temp files are removed at open.
- **Files are never written or removed through a link** (the security review's L1).
  - A stale temp file is removed first, and the new one is created with `create_new`, as `Credentials::save` does.
  - A new segment is linked into place, which fails if its name is taken, so a live segment is never overwritten. Only a reseal renames over the segment it rewrites.
  - Removal looks before it opens (`symlink_metadata`). A link or anything else that isn't a regular file is unlinked without being opened, and on Unix the file opened must be the one looked at (device and inode). A planted link's target is never zeroed.
- **Private on Unix** (L2): the folder is 0700 (narrowed if it exists), and segments and temp files are 0600, whatever the umask. Windows inherits the private data folder's ACL.
- **The sequence never wraps** (L3): only `.lsp` and `.tmp` names number the spool, the counter stops at its last value (a new segment is then refused, counted as an error, and the batch stays in memory), and a new segment never replaces a file of its name.
- **A leftover that can't be removed at open** (another program holds it) is skipped and counted (`leftovers`), and the next start tries again; the spool still opens.
- **Appends are durable at a bounded cadence:** the runtime syncs at the end of each round of spooled batches, and the spool syncs any append made a second or more after its last sync. A crash loses at most the unsynced tail, which reads as torn.
- **A failed sync closes the segment** (counted, `sync_failures`), so nothing more is appended to a file whose writes may not have landed. The record whose append triggered it isn't refused: its frame is written, and refusing it would spool it twice.
- **Windows:** nothing is renamed over a file that's open, and every handle is closed before a file is renamed or removed. The worker never appends to a segment from an earlier run, so no segment is open in two places. Windows has no folder sync. NTFS journals the rename's metadata, but flushes its log lazily, so a power cut just after a segment is created can lose the rename. The segment's frames are then in `<seq>.tmp`, which is removed at the next open: only records the coordinator never acknowledged are lost, never an acknowledged one.
- **A segment closes** at 8 MiB or after an hour. That bounds what a replay holds in memory, and lets a segment wholly past the age cap be dropped by its header alone.

## The caps (owner wkq1)
- **At most 1 GB (10⁹ bytes) on disk and 24 h per record, the defaults and the ceilings.** `Caps::new` lowers a larger value to the ceiling and raises a smaller one to a floor (32 MiB, four segments; one hour, a segment's span), below which the spool would drop what it's meant to keep. There's no setting yet. The bytes count headers and sealed frames as they are on disk.
- **Full:** a batch that would pass the byte cap isn't written (counted). It stays in memory and goes out on the next session, and the pool pauses, session or not, until a replay brings the spool back under half its cap (the half stops it flapping at the edge).
- **Old:** a record whose batch was made more than 24 h ago (the worker's clock) is dropped and counted when read, never replayed.
- **The wall clock** (the runner's review, I4):
  - **Set back:** a record or segment stamped more than 60 s ahead of now (the coordinator flags a clock more than 60 s off, §19.3) is dropped as past its cap. A clock set back can't keep a sealed name on disk past 24 h.
  - **Jumped forward** (a machine with no clock battery starts at its last saved time, then NTP corrects it): everything spooled before the jump can be dropped early as old, and counted. **A known limit:** it loses records the coordinator never acknowledged, never one it did, and their leases expired long before.

## What is spooled
- **`Results` batches only.** The format carries `Counters` too (`Kind::Counters`), but the worker sends none yet. Outcomes (losses) stay in memory, as before: a worker restart loses the unsent ones. Their leases then expire on the coordinator and are granted again, and WK-11b's reconciliation returns them sooner.
- **A record's age runs from when its batch was made,** just after its records were sealed, not from when it was spooled (the runner's review, I2). A batch held in memory first (in flight across midnight, refused for now, or kept while the spool was full) keeps its own time, so the 24 h cap counts from the seal.

## The counts
- **Drops are counted once:** a torn tail or damage the first time a segment is read, and a record too old once per record, even when a lost session has a segment read again. A segment removed whole by its age counts its records as old without opening them.
- **The records gauge** counts frames: restored at open from the frames' lengths, raised on append, and lowered by a segment's frames when it's removed. It never drifts with what was dropped.
- **A segment that can't be read or removed** (deleted outside the worker, or held open by another program on Windows) is set aside until the next start and counted as an error, so it never holds up the segments after it or keeps the byte count high.
- **The spool is opened by the session task on a blocking thread,** before it handles any batch. One that won't open is counted (`WorkerSpool::unavailable`), and the runtime keeps batches in memory as before.

## While no session is up
- **The pool stays paused, as WK-10c decided** (runner, 2026-11-11, under §2.26) from WK-5's rule (the coordinator re-plans the per-IP shares without this worker at once). The spool takes what was in flight when the session went, and what the fetches already under way and the prepare stage still finish. It opens no new fetch offline, even though §19.6 says a worker "keeps harvesting". The reasons: a worker fetching on its old share after a re-plan could break same-IP politeness, and every lease it holds expires on the coordinator after 10 minutes and is granted elsewhere, so most of what it fetched would come back stale. **A refinement of §19.6, flagged (§2.19).** The DHT keeps only its routing whenever no session is up (WK-10c).
- **Full, with a session up** (a reconnect at the cap, before the replay makes room): nothing new is claimed (counted as `held_back`), the pool stays paused, and the DHT keeps only its routing, as with no session (the runner's review, B1). All three resume once the replay brings the spool under half its cap.
- **Without a spool** (`runtime::Config::spool` is `None`), unaccepted batches stay in memory, as before.

## Replay
- **On a new session, in order:** one segment at a time, oldest first. Each record is sent under a fresh outer batch id. The coordinator matches `Accepted` by the outer id only, and its idempotency is by token (WK-9), so ids from an earlier process can never collide with live ones. A refusal for now (`accepted: false`) is sent again on the retry tick. Replay shares the session with live results; heartbeats run on the session driver's own timer, so replay never holds them up.
- **A segment is removed once every record in it is accepted** (`accepted: true`, whatever the commit decided, WK-9).
- **A missed session change is still seen:** the runtime bumps a generation on every connect and disconnect, and the session task resets what it has in flight whenever the generation moved, even if the session watch changed twice while it was busy.
- **Replay twice = once.** Records accepted from a segment are remembered by frame position for the process's life, so a segment read again after a lost session sends only the rest. One resent anyway (its `Accepted` lost with the session) is stale on the coordinator: committed once, harvested once, and the funnel reconciles (`replay::a_replay_twice_counts_once`). The worker's own counters are kept straight too: "fetched" counts a batch once whether it was sent or spooled, and "processed" counts each accepted record once.
- **Removal is secure delete as owner §2.17 asks of the store:** the segment is overwritten with zeros, synced, closed, then unlinked. **What that does and doesn't give:**
  - On a hard disk with ext4, XFS or NTFS, it overwrites the blocks in place.
  - **On an SSD** the drive's flash translation layer writes the zeros to new cells and only marks the old ones stale. Their contents stay readable to someone with the raw flash until the drive's garbage collection or a TRIM erases them.
  - **On copy-on-write or snapshotting file systems** (btrfs, ZFS, APFS, LVM or Unraid pool snapshots, a VM's disk snapshots) the overwrite lands in new blocks, and any snapshot keeps the old ones. So does ext4 with `data=journal`.
  - **On Windows**, a Volume Shadow Copy or File History copy keeps the old file. A very small file can live inside the MFT itself, where the overwrite does reach it. SSDs behave as above.
  - **The seal is what protects a copied or recovered segment.** Its records are sealed with the worker's secrets key, and the names inside them are sealed again under a wire key that's never on disk. Rotating the worker's secrets key (`--rotate-key`) after the spool is empty makes any copy left behind unopenable once the old key is retired, subject to the same limits on the old `secrets.key` file.

## The wire key across a day boundary
A record sealed under day N's wire key and replayed after the day turns: **the coordinator keeps the keys it already opens (today's and yesterday's, WK-8, plus the next day's from 23:00Z, WK-10b); it keeps no older one, and nothing is requeued for it.**
- **Why that's enough:** a worker seals only while its clock is on the key's day (WK-8), and the spool drops a record more than 24 h after its batch was made (just after the seal) by the same clock, and drops one stamped ahead of the clock. A record sealed on day N is therefore replayed on day N or N + 1, and the coordinator opens both. A key kept longer would sit in memory past anything a 24 h spool can hold.
- **Why not requeue:** by the time such a record could matter, its lease (10-minute TTL) has expired on the coordinator, which has already put the key back for a re-grant. Requeueing from the worker would add a protocol path that re-fetches nothing new.
- **The edges, counted, not silent:** a batch can be made a moment after its records were sealed, so one sealed just before midnight can be stamped just after it. And a clock up to 60 s off (beyond that the coordinator flags it, §19.3) can put the replay of a record sealed just before midnight on day N + 2 by the coordinator's clock. Either way, a record replayed in the last moments of its 24 h can fall on day N + 2 by the coordinator's clock. It then doesn't open: it's counted as `remote_records_total{outcome="unopened"}` and ends `Invalid` (WK-9c). Its lease had expired long before, so no key is stranded.

## Coordinator refusal (plan Q7)
- **WK-9's `Standing` check refuses late results** (earlier epoch) from a worker that is quarantined, revoked or purged, and any record leased before the worker's last purge. A revoked worker can't open a session, so it can't replay at all.
- **A current-epoch record from a quarantined worker was committed** (found by `replay::a_refused_workers_replay_is_refused_whatever_the_epoch`, which fails on WK-9's code). **Now refused whatever the epoch** (runner-approved edit in `crates/pipeline/src/remote.rs`). `Standing::refuses_late` is checked before the epoch split; the name stays, so WK-13's implementation is unchanged. It's counted as `late_refused`. A record of this run that is still under the worker's lease goes back to wait for a re-grant, with its cohort kept and no loss counted, so the key isn't stranded with a refused worker. **A refinement of WK-9's behaviour, flagged (§2.19).**

## Lease counts after a replay
- **Detected and counted.** Once a replay drains, the session asks for a heartbeat at its next upkeep (each minute) and compares the leases the runtime holds with the coordinator's count (`HeartbeatAck.leases`). The difference is counted (`worker_spool_lease_drift_total`). It's a `Work` hook (`reconcile`, `reconciled`), which does nothing for other work.
- **Corrected in WK-11b** (runner, 2026-11-11). Per-worker renewal (V6-cluster2) keeps a lease alive that the worker no longer knows, after an outcome lost with a connection or a worker restart. In WK-11b the worker lists its tokens when the counts differ, and the coordinator returns the unlisted leases for re-grant and counts the drift. That needs a protocol message in `crates/cluster`, so it isn't in this PR.

## Wiring
- **`lodestar worker` uses the spool** in `<data>/spool`, sealed with `<data>/secrets.key`, at the default caps (`SpoolConfig::for_layout`, one runner-approved line in `crates/lodestar/src/cli/worker.rs`). A spool folder that can't be created stops the worker with a one-line message, like the credentials. One that is created but then fails to open runs the worker without a spool, as before WK-11 (unaccepted batches stay in memory, and the heartbeat's `spool_bytes` reads 0).
