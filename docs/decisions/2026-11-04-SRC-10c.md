# SRC-10c decisions (Internet Archive plugin)

**HOLD: nothing may register or enable this plugin until the Q2 terms and robots check is recorded (plan §5 Q2, owner §2.28).** The check is owed by the runner or the owner (this slice's sandbox had no route to archive.org). It must confirm, and record here:
1. the Archive's terms of use and `robots.txt` as they read today, for `advancedsearch.php`;
2. whether the terms' "scholarship and research" wording fits a general search index of new items. If that is grey, it goes to the owner;
3. the query syntax: `format:"Archive BitTorrent"`, the `btih` field and `sort[]=publicdate asc`;
4. the measured intake of torrent-bearing items an hour, and the delay between `publicdate` and the torrent, behind the 6-hour lookback and the 20-page cap.

Slice SRC-10c of `docs/plan/2026-11-01-v06-sources.md` (§4.2). It covers architecture §18.2 rank 6 and §18.7, and follows the pattern in `crates/sources-plugins/README.md`. The parser is SRC-9's (`docs/decisions/2026-11-02-SRC-9.md`).

- **Consent class: None** (§18.7 table: "Mainline DHT, Internet Archive, …: a toggle"). The manifest says `Consent::None`, risk Low, off by default. No account, no credential, no user-entered address. The manifest has one endpoint, `https://archive.org`, and egress is narrowed to it (`Endpoints::manifest`).
- **Q2 (ToS and robots) check, per endpoint.**
  - **Endpoint used:** `GET https://archive.org/advancedsearch.php` (the documented search API, `https://archive.org/advancedsearch.php`), JSON output. It is the only endpoint the plugin requests.
  - **Terms:** the Archive publishes this API for programmatic use, and its terms of use allow automated access through its documented interfaces at a reasonable rate. The plugin sends no more than 1 request/s, names no user, and never fetches content, `.torrent` files or details pages.
  - **robots.txt:** as recalled (not read today, see below), the file disallows only the site's control and report paths. `/advancedsearch.php` isn't among them. The plugin also never crawls: it makes one fixed API request per poll.
  - **Not verified live.** This slice's sandbox had no route to archive.org (the proxy answered 403 to `CONNECT`), so the terms page and `robots.txt` were not re-read today. The statements above are from memory of the Archive's published documentation, not a reading. **The runner should have someone re-read the terms and `robots.txt` before the v0.6 gate (SRC-G).** If either now forbids this use, that is a grey case for the owner (Q2), and the plugin stays off. It is off by default either way.
- **Rate limit (Q4, accepted):** at most 1 request/s to the host (`per_host`: one token, 1 s), with `since` cursors so a poll fetches only what is new.
  - **Polls:** at least an hour apart (`min_poll_interval` 3,600 s). A user can slow this, never speed it up.
  - **Catch-up:** a full page (500 rows) is followed at once by the next, through `Client::send`, so the per-host rate spaces the pages one second apart. At most 20 pages (10,000 items) a poll.
  - **Back-off:** 60 s up to 6 h. A 429 or 5xx on the first request backs the poll's unit off through the limiter (the `Retry-After` is honoured, tested with a value over the poll interval) and the next poll tries again. On a follow-up page (sent with `Client::send`) it blocks the host instead and the poll ends with what it has found; the cursor is already saved. It is not an error.
- **Cursor (Q4).** The newest `publicdate` seen (Unix seconds, decimal ASCII) is kept under the plugin-state key `since` (`PluginState`, SRC-0).
  - **Each poll asks for items from 6 hours before the cursor, inclusive** (`publicdate:[… TO *]`), and reads pages 1, 2, … of that one query. Two reasons (fresh review):
    - An exclusive bound with a moving cursor loses any item that shares a second with the last row of a full page. `publicdate` has one-second precision and the order inside a second is arbitrary. Paging one fixed query by `page=N` can't split a second.
    - An item is public from its `publicdate`, but its Archive torrent appears only after the Archive's derive step, which I believe can take hours for large items. A cursor with no lookback would never ask for it again. The lookback re-reads the last 6 hours each poll, and the pipeline drops keys it already has. **The 6 hours is a guess** (it can't be checked from this sandbox). The runner should have it checked against the live Archive before SRC-G, along with the Q2 reading below.
  - **Saved after a page's finds are sent.** A restart repeats at most the lookback window and a page, and never skips one.
  - **First run, or an unreadable or implausible cursor** (not digits, before 2001-07-02, more than a day ahead): start 24 hours back. The plugin follows what is new. It never backfills the Archive; that is an importer's job.
  - **The cursor only follows items that were kept.** A page of skipped items (no `btih`, a bad hash, over a cap) doesn't stop the poll: the next page is still read. If every item in the window is skipped, or the local clock is more than a day behind (every date is implausible), the cursor stays and each poll reads the same window, at most 20 pages an hour. It doesn't loop or run faster.
  - **Throughput and the resume point.** A poll reads at most 20 pages × 500 rows = 10,000 items. If it reads all 20 full, it saves a resume point (state key `resume`: the last row's date, at least one second past the query's start). The next poll starts there, inclusive and without the lookback, and carries on past those rows. A poll that ends on a short page clears it, and polls go back to cursor minus lookback. Without this, a 6-hour window holding 10,000 or more items (a bulk ingest, or about 1,430 an hour) would be read from its start at every poll and the cursor would never get past it (runner's review). A catch-up moves 10,000 items an hour, so a backlog beyond that is worked off over several polls rather than lost. Rows that all share one second can't be split, but the resume point moves a second at least, so it can't repeat. The real intake rate is unmeasured (HOLD item 4).
  - **The cursor never runs ahead of the page's own time:** a date up to a day ahead is believed as a claim but moves the cursor no further than "now" (runner's review).
- **The request** is fixed text plus the cursor's digits (`search_url`): `format:"Archive BitTorrent" AND publicdate:[<from> TO *]`, fields `identifier, btih, title, item_size, mediatype, collection, publicdate`, sorted by `publicdate asc`, 500 rows, `page=N`. Nothing in a request comes from an answer.
- **Distribution: `Singleton`**, although §19.5 lists Internet Archive as `sharded(unit)` (per collection). This plugin follows the whole Archive's new torrent-bearing items with one global cursor, which doesn't split into collection units without a cursor each. A later slice can shard it.
- **Parsing:** SRC-9's `archive_org::parse_each` only, with its default caps and the item cap set to twice the rows asked for (`PAGE_LIMITS`). This slice parses no untrusted text of its own. The key comes only from the parser's `Hashes` (a v1 `btih`).
- **Nothing else is fetched:** no `.torrent`, no details page, no metadata call. The replayer fails any other request.
- **Claims map** (every claim is Low confidence, unverified, through SRC-2):

  | Claim | From the parser's typed item | Dropped when |
  |---|---|---|
  | name | `title` | (the parser already cleans and caps it) |
  | size | `item_size` | 0, or over 1 PiB |
  | ids | `archive-org:<identifier>` | no valid identifier |
  | ids | `archive-mediatype:<type>` | no media type |
  | ids | `content-type:<type>` for `movies` → video, `audio` and `etree` → music, `texts` → ebook, `image` → images, `software` → software | any other media type |
  | ids | `archive-collection:<id>` per collection (at most 16, from the parser) | |
  | files | `files` (path, size), where an item lists them | a search answer lists none |
  | provenance | external reference `https://archive.org/details/<identifier>` (built by the parser from a validated identifier, never fetched); `published_at` from `publicdate`, else `addeddate` | a date before 2001-07-02 or over a day ahead |

  Not kept: descriptions, subjects, uploaders and reviews (the parser never reads them; an uploader is a person, §18.7), download counts, and any `.torrent` link. `private_source` is never set: the Archive is public.
- **Files are mapped but a search answer gives none.** `to_found` maps `files` for metadata items (the parser handles them), and the tests cover it. The plugin doesn't fetch the metadata API: one request per item would multiply the request rate and the brief asks for the search poll. A later slice can add it behind the same mapping.
- **Fixtures are hand-written** in the shape of `advancedsearch.php` answers (the parser's own golden fixture shows the shapes), with made-up identifiers and hashes and open-licence titles. This session had no route to archive.org to record from. Replace them with scrubbed recordings when one is available; the tests don't change. The plugin takes its clock from `ArchiveOrg::with_clock` in tests, so the request URLs in the fixtures are stable.
- **Shared-file edits:** none beyond the one `pub mod archive_org;` line in `crates/sources-plugins/src/lib.rs`. The plugin isn't wired into `services.rs` or the pipeline (the runner's, per the brief).
- **The HOLD at the top is also a condition for SRC-G.** A grey result goes to the owner; the plugin stays off by default either way.
- **Not tested:** a failed cursor save (ignored on purpose: the next poll repeats a window) and shutdown while a follow-up page waits for the host's token (the wait sits inside the same `select!` as every other await, as for Nyaa).
