# X-op4-polish decisions (operator test gaps and wording)

This is a follow-up to OP-4 (#655), from the non-blocking items of the runner's delta review. It adds to `docs/decisions/2026-11-11-OP-4.md` and supersedes none of it. It loosens no owner or security decision and changes no owner-set number.

- **An unset `OPERATOR_BOT_USER_ID` makes the sweep escalate before it fails.** Without the bot's ID nothing can be attributed, so the sweep lists nothing. It posts a best-effort escalation ("nothing was checked this run") and fails the job, as an API error does. It disables nothing, because no bot action was seen.
- **What failing closed on an incomplete sweep costs.** OP-4 counts a list that runs past 10 pages within the lookback as a trip: an escalation, then `operator-wake.yml` disabled.
  - So anyone who can post more than 1,000 comments, or cause as many issue events, within the 130-minute window can disable `operator-wake.yml`.
  - That costs availability only: no session starts, and nothing is exposed.
  - The owner re-enables the workflow (GitHub → Actions → operator-wake → Enable) after a look at the escalation. The runner accepted the trade.
- **The ledger's page cap, in precise terms.** Once the workspace holds more than 5,000 sessions (50 pages of 100), archived ones included:
  - `apiclient.pages()` raises `ApiError`, so each wake answers "the bridge failed (ApiError)", not a named ledger reason;
  - that happens after the operator lock and `claude-lock.json` are read, but before any App token is minted or a session created;
  - the lock is still released.

  OP-4's decisions file says what the owner does then: delete old sessions, never the most recent one.
- **Tests now cover two handlers in the bridge:**
  - the handler after the lock catches a `Refusal` (a malformed `claude-lock.json`, or no session ID returned) and answers it;
  - a failed `user.interrupt` in the crash path still leads to the "bridge failed" escalation and the archive.

  Each was mutation-checked, and so was the new sweep guard.
