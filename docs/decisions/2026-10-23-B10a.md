# B10a decisions (#111)

CRUD for user items, collections and saved searches (`/api/v1`, tag `library`). No owner decision is changed.

- **Lists are bare arrays** where the brief shows them (`GET /collections`, `GET /user-items/labels`, `GET /saved-searches`); paged lists are objects (`items` + `next_cursor`, `entries` + `next_after`).
- **Collection paging** uses `?after=<n>`, the number of shown entries to skip, and returns `next_after` (null on the last page); see the position bullet below for why it isn't the store's raw position.
- **Counts follow `?hidden=`.** `GET /collections`, `GET /collections/{id}` and the labels endpoint take `hidden` (default false, as search). Write responses (`POST/PATCH` on a collection, add, remove, reorder) count with `hidden=false`.
- **Reorder with entries the client can't see.** The list must name every entry shown by default once, and may also name filter-hidden ones. Adult-while-hidden entries and filter-hidden ones it didn't name keep their slots. Without this, a collection holding a hidden Adult torrent could never be reordered (`stale_order` forever).
- **Remove by hash skips** hashes that are unknown, not in the collection or not shown, so a withheld torrent's presence isn't revealed.
- **Store `Invalid` → `422 invalid_value`.** The field is picked from the store's rule text (labels, note, name, query → `q`, sort); the message repeats the rule, never the value.
- **`note: ""`** (or only whitespace) is a `422` on `note`; only `null` clears it.
- **Saved search `alert` and `rss` are required** on create; `channels` start at 0 and are never changed by the API.
- **`position` and `next_after` are places among the entries shown**, not the store's raw positions, and `after` means "skip this many shown entries". Raw positions are dense after a reorder but leave gaps for appended or removed ones, so exposing them would show how many entries were withheld (§20.9). The cursor of `GET /user-items` names the last row returned, never a withheld one, for the same reason (the withheld rows are read and skipped again).
- **Saved-search `alerts`, `unread` and `last_alert_at` count alerts on shown torrents only**, recounted from the store's alerts. The store counts every alert, Adult ones included, and §20.9 says the preference applies to Alerts. This departs from the brief's "from the store as given" and is flagged for the runner. B9's alert list should apply the same rule.
- **Reorder has no 500-hash cap** (the cap is for add and remove); an empty list is valid only when no entry is shown.
- **`DELETE` also calls `same_origin_json`**, as every write does, so clients send `Content-Type: application/json` on it.
- **Known follow-up:** `GET /collections` and `GET /user-items/labels` read two rows per mark while holding the reader lock that search shares. User data is small, but a very large library would block searches during the scan; batching the lookups is a later optimization.
- **For B9:** the store's `unread_total` (the nav badge) still counts alerts on Adult torrents while hidden, and this PR's saved-search counts don't. The badge and B9's alert list must use the same shown-only rule (§20.9).
- **Size:** the PR is over ~1,500 lines because the three resources share the visibility helpers in `user_items.rs`, and splitting them would split the content-safety review.
