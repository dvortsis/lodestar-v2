## For the runner to flag to the owner (§2.19)
- **start-block accepts the Legal Notice and sets the admin password itself.** The plan's Lane L steps 2–4 assume a person over `ssh -L`; under the operator there's none.

  - **It accepts only the notice version the screen rules name** (`notice_version`). If Lodestar serves another version, it refuses (`notice_version`) and never calls setup, so a changed notice is never accepted silently. The version is pinned in a reviewed rules commit.
  - **The runner's answer (2026-11-11Z): yes, with the pin.** The runner flags it to the owner as "the fleet accepts Legal Notice version N on test VMs on your behalf". The current version on `main` is 4 (`crates/api/src/legal.rs`), so the first rules file pins `"notice_version": 4`.
  - **A changed notice is a stop:** start-block prints `count notice_version_served <n>` and `count notice_version_pinned <m>`, then `fail notice_version`. It never retries and never accepts anyway (tested).
  - **Setup goes to Lodestar on gluetun's loopback only** (`http://127.0.0.1:8090`, from a throwaway container in its namespace), never a public address.
  - **The token and the password never appear** in step output, the Docker argv, copy-off or the bucket. Tests plant both: in the VM script's run, and in a live act run whose fake VM prints them. The password file is 0600, and copy-off's scrubber never mounts it (tested with a planted password in the block directory).
- **A new pinned image for the collector, the analyzer and the scrubber:** `python:3.12.12-alpine3.22`. Its multi-arch index digest is `sha256:848ba4413eb897e225159b8fc1b02094576cbae4aa73fc13142608ae2c8c0e32`, read from Docker Hub's registry on 2026-11-11Z, with the content type confirmed as an OCI image index. `block-lib.sh` holds it and the probe image's pin. A test rejects a tag.
- **The collector reaches Docker only through a proxy** (the runner's decision, 2026-11-11Z, option (b); it rejected mounting the socket into the collector).
  - **Why the collector needs Docker at all:** `collect.py --mode docker` makes these calls:
    - it inspects Lodestar's container (its identity, network mode and image), and gluetun's as its network parent;
    - it inspects the image (the digest);
    - `HEAD …/archive` checks for a `config.toml`;
    - one-shot stats, only as a fallback;
    - `POST …/stop` (`--stop`).
  - **The proxy:** `docker-proxy`, HAProxy 3.2.25 LTS (`haproxy:3.2.25-alpine3.24`, multi-arch index digest `sha256:5d97434a423c2533cfeb42874d45cf6d69a840b60334582dfbfd5008e94c80be`, built 2026-09-29Z and read from Docker Hub 2026-11-11Z; 3.2.26 was under two weeks old).
    - It's the only service that mounts `/var/run/docker.sock`, read-only.
    - It runs with `network_mode: none`, `cap_drop: ALL`, a read-only root and `no-new-privileges`, as the image's own non-root `haproxy` user, with the socket's group added.
    - It serves a unix socket in `proxy-sock/`, a folder only the collector mounts (read-only, `--docker-socket /sock/docker.sock`).
  - **The config (`steps/vm/docker-proxy.cfg`) is rendered with exact IDs.** `block-lib.sh` reads Lodestar's container ID, its image ID and gluetun's ID on the host, and checks each is 64 hex. It allows only these, each with an optional `/v1.NN` prefix; everything else is 403:
    - `GET /containers/(lodestar|<id>)/json`;
    - `GET /containers/<gluetun id>/json`, the parent inspect collect.py makes, which the runner's list didn't name: read-only, and only gluetun's ID;
    - `GET /images/sha256(:|%3A)<image id>/json`;
    - `HEAD /containers/<id>/archive`;
    - `GET /containers/<id>/stats` with `stream=false`;
    - `POST /containers/<id>/stop`.
  - **When it's rendered:**
    - at start-block, once Lodestar is up;
    - at each arm switch, after the new Lodestar container starts and before its collector does.
    Each arm needs a recreated container with a new ID, so the config is never re-rendered while a collector runs (the stub enforces that).
    - Within a segment, a recreated Lodestar gets a new ID that the proxy denies, and the collector's identity check fails closed, as it does today.
    - The proxy is removed at the block's end (arm-switch after segment 4, and copy-off).
  - **Tested without Docker:**
    - the rendered policy against the allowed shapes and a table of 34 hostile ones: `_ping`, `version`, `exec`, `create`, `attach`, `logs`, `events`, `PUT` or `GET` on archive, another 64-hex ID, gluetun's stop, path traversal, encoded slashes, case, a doubled slash, other methods and a malformed version;
    - **where `haproxy` is installed** (this session had 2.8): `haproxy -c` on the rendered config, and a real HAProxy in front of a fake engine, answering 200 or 403 with nothing denied reaching the engine. CI has no HAProxy and pulls no images, so it runs the policy test alone;
    - compose mounts the socket only into the proxy, and no script gives it to any other container.
  - **The residual:** the collector can stop Lodestar's container, which is its job. A later CR-COL slice may move collect.py to host-written snapshots (option (c), logged by the runner as a follow-up).
- **The collector container** otherwise has `--cap-drop ALL`, `no-new-privileges` and a read-only root. It holds no credential but Lodestar's password, and every mount is read-only except its own evidence folder (tested). The runner approved its image on 2026-11-11Z. ## The screen-rules file (`infra/fleet/steps/screen-rules.json`, read at the rules commit)
- **`run start-block <vm> <rules-commit>`** reads it at that commit with `git show`, never from this checkout. act has already checked the commit is an ancestor of `main`.
- **Exactly these keys:**
  - `version` (1);
  - `screen` (`[a-z0-9-]{1,40}`);
  - `lodestar_image`: `ghcr.io/dvortsis/lodestar-v2@sha256:<64 hex>`. Pinned by digest, in the one repository the project publishes; a tag or another repository refuses;
  - `lodestar_commit` and `spec_commit` (40 hex each). Both must also be ancestors of `main`. `spec_commit` is the collector's `--spec-commit`;
  - `treatment` (`adm`, `utp` or `route`);
  - `segment_hours` (2 or 3, the screen's rule 3);
  - `notice_version`.
  Anything else, a boolean where a number belongs included, refuses with a fixed reason (`steps/rules.py`).
- **The same commit gives `collect.py` and `analyze_cr.py`.** What runs as root on the VM, and what judges it, are both fixed before the screen starts (screen rule 2).
- **No rules file is committed yet.** The runner commits one per screen, and start-block refuses ("the rules commit has no screen rules") until then.

## The durable block marker (`/var/lib/lodestar-block/marker`)
- **Written by start-block before Lodestar or any collector starts.** It holds `block=<run id>`, `segment=<1–4>` and `state`, and is replaced atomically (written to a temporary file, synced, then renamed).
- **Only two things remove it:** the block's own end (arm-switch after segment 4) and copy-off.
- **Every mid-block check reads it as well as `docker ps`,** so a block stopped between segments still counts as mid-block. That closes the arm-switch gap from #652's review. The checks are the leak test, start-block, `renew-vpn`'s restart, the outage watcher's exit and vm-status.
- **Fail closed:** a block path that isn't a plain directory (a file, or a symlink), or a directory that can't be listed, reads as `unknown`.
  - The leak test, start-block, arm-switch and copy-off refuse (`block_check`).
  - deliver-pia leaves the tunnel alone and escalates (exit 32). Its message now says "Docker or the block marker".
  - The watcher keeps running.
- **A failure after the marker leaves the block recorded:** a changed notice, a failed pull, the API not answering or the collector not starting. Every other check then sees a block until copy-off ends it.
  - **Once Lodestar has started, a failing start-block or arm-switch stops it** (`docker stop -t 60`), so nothing crawls after a stop.
  - copy-off refuses only while a collector runs. A Lodestar left running alone (a failed step, or a collector that died) is stopped first, so a block that went wrong can always be ended (tested).

## start-block
- **In order:**
  1. the arguments, re-validated on the VM;
  2. no block recorded or running, failing closed;
  3. **the leak test in this same run.** start-block requires both its exit 0 and its final line `ok leak_test`; anything else stops it (`leak_test_passed`) before the marker, the pulls or compose;
  4. the marker;
  5. a past block's directory moved aside (kept, never wiped). **start-block refuses (`evidence_copied`) while that block's evidence hasn't been copied off**: copy-off leaves a `copied` stamp, so a second screen in one session can't strand the first screen's evidence;
  6. the tools staged from the rules commit, the compose file installed, and a fresh data directory and a fresh witness directory;
  7. the two pulls by digest;
  8. Lodestar alone on segment 1's arm (`--no-deps --force-recreate`, so a stopped container from a past block, still pointing at the old gluetun, is never reused);
  9. **its network parent checked** (`container:<gluetun's id>`, plan Lane L);
  10. the API up, the setup done, and segment 1's collector started. **"Started" means its `run.json` exists with `network.gluetun_network_parent: true` while it still runs** (plan Lane L), within 120 s; a collector that exits at its preflight fails `collector_started`;
  11. the outage watcher.
- **The leak test's recovery recreates gluetun** from the current `wg0.conf` in the same run, which is what OP-3a's renew-vpn rule relied on.
- **Detached:** collectors run as `lodestar-collector-<segment>` containers (`--restart no`, `--oom-score-adj -500`). The watcher runs as a transient systemd unit. The step returns once segment 1's collector is running.
- **Every wait has a deadline:** the leak test (600 s), the pulls (300 s, 120 s and 120 s), compose (240 s), the proxy (about 200 s), the API (180 s), the token (90 s) and the collector's start (120 s). The step's timeout is 2,400 s; the session, with its lock wait and margin and the SSH retries, still fits act's 50 minutes (tested).
- **The restart witness is on the host** (`./witness` beside `./data`, bind-mounted at the image's `/var/lib/lodestar-witness`; CR-SPEC 2.3, plan 0e). A recreated container at each arm switch is then a resumed start, and the analyzer's `witness_host_mounted_outside_data_dir` check holds. It's fresh per block, and the collector guards its filesystem read-only (the self-review's blocking finding).

## The arms and the collector (plan Lane L and the cloud screen)
- **ABBA:** segments 1 and 4 are the control, 2 and 3 the treatment.
  - The treatment's one switch is `true` or `false`: `LODESTAR_DHT_COORDINATED_ADMISSION`, `LODESTAR_DHT_UTP` or `LODESTAR_DHT_ROUTE_BACKOFF`.
  - `LODESTAR_DHT_SAFE_RESTART=true` for the whole block.
  - compose.yaml passes these four by bare name, so a switch the caller doesn't set stays unset in the container, at its shipped default. A test pins the list.
- **The collector,** once per segment:
  - `--mode docker --run-kind ab --treatment <t> --intensity balanced --stop --rehearsal --baseline-hours <segment_hours>`, with `--commit` and `--spec-commit` from the rules and a new `--root` per segment;
  - the plan's checklist flags, with next-run times three days out (after any fleet's 44 h);
  - on Worker, the 12/8/4 GiB storage guardrails from Lane K.
- **Never `--require-gluetun` or `--leg gluetun`** (the CR-SPEC kinds refuse both). The network-parent check stands in for them, as the plan says.
- **Not built:** the post-block observer collector (Lane L "After the block"). A screen doesn't need it; a later slice can add it.

## arm-switch
- **It waits, bounded at 15 minutes, for the running segment's `result.json`** and for its collector to have stopped. The operator runs it shortly before a segment ends.
- **Then:**
  - it requires reason `baseline_window_complete`, otherwise `segment_complete`. The block stays recorded and copy-off ends it: the screen's stop or void;
  - Lodestar must be stopped (the collector's `--stop`);
  - after segment 4 it ends the block (the marker goes and the watcher stops);
  - otherwise it records the next segment in the marker first, then starts Lodestar alone on the next arm (gluetun isn't recreated; safe restart makes it a resumed start), checks the network parent, and starts the next collector;
  - it reports `switch_seconds`, timed from `result.json`'s mtime.
- **Step timeout 2,100 s.** With the session's lock wait and margin it's 2,220 s; with the SSH retries, inside act's 50 minutes (tested). Each collector mounts only its own segment's evidence folder read-write.

## The outage watcher (plan 0e)
- **`watcher.sh` runs as a transient systemd unit, `lodestar-outage-watcher`, with `RuntimeMaxSec=44h`.** start-block starts it. The `outage-watcher` step restarts it if it has stopped, and reports `skip` if it's running. It needs a recorded block.
- **What it follows:** gluetun's container events (`die`, `kill`, `stop`, `restart`, `oom`, `health_status: unhealthy`) and its log (`restarting VPN`, `unhealthy`, `[vpn] stopping`), each follower restarted every 10 minutes and when it ends (so a recreated gluetun is followed again).
- **On an outage** it counts it in `$BLOCK/outages`. It writes a `link_outage` note at once through `docker exec` into the running segment's collector (`collect.py note`), at most one per 30-second burst and 500 in all. Between segments no collector runs: the outage is counted, with no window to note it in.
- **It never stops or restarts anything.** The plan's stop condition makes the segment invalid, and the analyzer judges that. It prints nothing and exits when the marker is gone.
- **For the first cloud run:** confirm that gluetun v3.41.3's log lines match the patterns.

## copy-off and the scrubber
- **copy-off refuses while Lodestar or a collector runs** (fail closed on Docker), and when there's no evidence.
- **On the VM, in a throwaway container:** `--network none`, `--cap-drop ALL`, a read-only root, and only the evidence, `block.env`, the tools and the two counters mounted read-only (never the password). In it, `scrub.py collect` runs `analyze_cr.py segment` on each segment, writing the reports outside the evidence, and scrubs the result. The document comes back as one `evidence <base64>` line.
- **The control plane takes that line out before the grammar parse,** decodes it, and scrubs it again with main's `scrub.py`. Then it puts it through `apply.OwnedS3` (so with `ExpectedBucketOwner`) at `fleet/<run>/copy-off-<vm>.json` in the private evidence bucket. Nothing is printed: the report says only "evidence stored in the private bucket", or why not.
- **The allow-list:**
  - from `result.json`: reason, stop mode, state, sample count, end time, elapsed seconds, finalization, the memory counter, network-parent changes, and the shutdown's exit fields;
  - from the segment report: kind, treatment, rehearsal, window, verdict and its reasons, each check's rule, name, result and effect (never its `detail`), the image digest and switches, the numerator's window rates, the worst hour, latency p95, fetch counts, peak memory, CPU and the note categories.
  - **Fixed vocabularies are enums:** `role`, `treatment`, `arm`, `kind` and `verdict`; the two start times are a number or a UTC time only.
  - **Each value must also have its field's shape:** a number, a boolean, a fixed-vocabulary word (`[a-z][a-z0-9_]{0,63}`, never 16+ hex), a UTC time, a rule number, a commit or a digest.
  - Free text, addresses, IDs, server names, hostnames, the region and every unnamed field are dropped.
  - Tested with fake private values in allowed and unallowed places; the second pass is stable.
- **Then it ends the block** (the marker goes and the watcher stops). It can run again; that copies the same evidence and reports `skip block_ended`.
- **Not to a comment:** the plan's "scrubbed aggregates go to the runner as a result comment" waits for the runner. The brief puts the evidence in the private bucket only.
