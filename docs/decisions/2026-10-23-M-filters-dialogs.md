# M-filters-dialogs decisions, part 1: the change flow and the password (2026-10-23)

The client half of §20.10–§20.11's preview, warning and password protocol, and B17's 18+ confirmation. None changes an owner decision; every guardrail stays on the server (the flow never judges a change: `confirm`, the warning and every number are the server's). Part 2 (CSX-5, Block this, reveal) adds its own file.

1. **Poll cadence.** A preview job is polled every 250 ms for its first 2 s, then every second (§20.10's target is under 5 s). Polls of a superseded or cancelled preview are aborted and their answers ignored; the job's start request is never aborted, so a job started for an abandoned preview is named and cancelled, and doesn't hold one of the server's four slots.
2. **A job 404 restarts the preview once** (its result is kept 10 minutes, or it was evicted from the 64 kept); a second 404 fails.
3. **Retry is offered only where repeating can help:** the network (status 0), 408, 429 and 5xx. A refusal the server will repeat for the same change (400, 404, 409 `floor_locked`, 422) shows the server's message with Close only. Retry always starts from the preview.
4. **A 429 `rate_limited` without `Retry-After` waits 60 s** (the brief's figure). The password route sends no `Retry-After`; the login bucket refills one attempt every 12 s, so 60 s is conservative where M-auth's sign-in form uses 12 s. The countdown is text (its moving digits hidden from screen readers, the wait read once as it started); the Apply button stays focusable and `aria-disabled` meanwhile, and nothing is sent until it ends. The lock belongs to the flow, not the screen: a variant, a Retry or a re-preview that asks for the password again comes back still locked.
5. **"Changed" means the warning text, `confirm`, any preview or Neutralize number, or the floor entries differ** between the assessment shown and the one a 428 carries. Either way a 428 needs a new confirm; nothing is re-sent automatically.
6. **Exposure summary layout.** One table, each `Preview` field on its own labelled row in a fixed order (released from quarantine now, dropped torrents fetched again, stored torrents no longer hidden/demoted/flagged, removed from the locked floor, caught in the last 30 days, of those by the core, projected per day). Never a total: §20.10's one-line "would release 37 items (2 caught by the core)" needs a sum of fields the server keeps apart, so the rows stand alone. With `estimate`, each value is `≈` and a note says the numbers come from names only. "What changed" uses the same rows, previewed beside applied.
7. **Progress is "phase, done of total"**, not a percentage: standards §4 says the client never computes percentages, so the live region says "Previewing: Checking quarantine, 400 of 1,000" (at most every 2 s) and a native `<progress>` shows the bar.
8. **Initial focus:** the dialog's title while previewing and in review (the summary is read before Apply), the password field in `confirm` (its `aria-describedby` is the warning, so the warning is read first), Cancel in the 18+ dialog. When the state changes, focus moves to the password field (entering `confirm`), the "What changed" section (`done`) or the error (`failed`); otherwise it stays where it was. On close, focus returns to what had it when the dialog opened.
9. **Esc, the close button or a click outside while applying** keep the dialog open until the answer is in, then close it (§10.13), as the brief says. `onapplied` still fires for a change that applied, so the screen behind it can say so. `onclose` fires for every close, including when the flow closes on its own (a job cancelled elsewhere, a sign-out).
10. **"Shadow for N days" is a variant, not a separate apply.** It re-previews the change with `shadow_days` (only for `add_rule`, `update_rule`, `add_override`), the primary button then reads "Shadow for N days", and "Apply now instead" re-previews without it. A shadowed weakening change still gets its warning and password if the server says so.
11. **The flow exposes `retry()`** beyond the brief's interface (the failed state's Retry needs it), **`done` carries `previewed`** (the assessment that was shown, for "What changed"), and **`createAdultConfirm()` also exposes `open` and `answer()`** for `AdultConfirmDialog`. **`setShowAdult` returns `{ ok: false }` with `error` optional**: absent when the user cancelled.
12. **The 18+ dialog's wording:** what turning it on does (adult torrents in Search, Discover, Alerts and Insights; Torznab, Stremio and export keep their own settings, off by default) and "Turn this on only if you're 18 or older." The button is "Show adult content". `409 set_by_environment` says "Set by LODESTAR_SHOW_ADULT; change it in the container template."
13. **zh:** short labels only (buttons, the password label, the countdown, the action names); the rest falls back to English until translated. The server's `warning` and error `message` are English-only (backend follow-up below).

## Backend follow-ups (named, not filled in on the client)
- `Assessment` has no per-item breakdown by layer, rule, media category, source or network, and no sealed names for core-caught items (§20.10).
- No CSX-5 "contradiction with CS-1/CS-8" flag (§20.5.5).
- `Preview` has no "matches now" count for strengthening rules (Block this uses `/search`'s `total`).
- No payload signature or release group on search hits or detail (Block this tiers 2–3).
- The warning is one English sentence string: send it as a code and parameters so the client can translate it.
- `SettingsPatch` is `Record<string, never>` in the OpenAPI document; `setShowAdult` casts its body once.
