# CMP-5g-3 decisions

Supervised companions at serve: the supervisor behind `manager::monitored`, Q18's `companions.<id>.egress` setting, and real restart, logs and regenerate (plan `docs/plan/2026-11-06-v06-companions.md` CMP-5g, Q12, Q18, Q19; architecture §18.7, §18.10; `docs/owner-decisions.md` §1.7.2). These are the slice's decisions under §2.33. None loosens an owner decision or a security decision. The runner flags them to the owner (§2.19).

## Serve
- **Wiring order:** the manager opens first and takes the companion lock. Only then is the supervisor built (CMP-4b's sandbox, CMP-4a's supervisor, CMP-8a's guarded `CompanionHttp`), because building it kills companions an earlier run left behind (its pidfiles). A second process that finds the lock held never kills anything. The manager is opened with a late-bound `Wiring`, which refuses `not_wired` until both the supervisor and CMP-8b's `Api` are set.
- **Then recovery, then starts:** every companion recovery finds installed is started in one background task, one at a time, each through `Manager::start` (start, health, CMP-8b's configure, as every start the manager makes). Serve doesn't wait for them. A failed start is logged as `companions.install_failed` with step `start`, like CMP-5's `open` and `recover`, rather than a new event and its messages.
- **Unwired stays** for the CLI (`lodestar companion install` still refuses `not_wired`: the runner's call for CMP-5, unchanged), inside a container (nothing is native, Q17), and when the supervisor can't be built (logged, step `supervise`). Then restart, logs and regenerate answer `not_wired` as before.
- **Shutdown** (#619 N3): `Companions::shutdown` stops following `integrations.clients` and starting companions, then stops each supervised companion, each bounded by the supervisor's stop. It runs after the pipeline's shutdown, so no plugin is still using one. A start racing shutdown is refused (`shutting_down`), checked again under the supervisor's lock.

## Q18: `companions.<id>.egress`
- **A raw `settings` row, not a registry entry.** It holds exactly a source's `sources.egress.<plugin>` text (`direct`, or `socks5 <host> <port> <auto|proxy|local>`), read with the pipeline's own `EgressSetting::decode`. The registry entry the slice allowed isn't needed: nothing in this slice edits it, and as a raw row under `companions.` a settings import can't write it (only registry sections are imported). CMP-9a's screen edits it through its own route; the new value applies at the next start or restart.
- **Set once, from the plugin it serves:** the first time a companion is started (an install's start is its first), with no row yet, the plugin's saved egress is saved as the companion's: the download-client source (`download_clients`) for qBittorrent, the Prowlarr plugin for Prowlarr and FlareSolverr. After that the plugin's changes don't move it: it's the companion's own, editable on its screen (Q18's wording). An uninstall leaves the row, so a reinstall keeps your choice.
- **Fails closed:** a row that doesn't decode, or an unreadable plugin route (which isn't saved), builds a route that's down for good (`setting_unreadable`), never direct. A store that can't be read, or a companion that serves no plugin, gets no route, and isn't started (`no_route`).
- **Each start builds its route afresh** (`manager::Routes`, implemented by `CompanionRoutes`) through a factory of its own, with the route kept fresh by `manager::monitored` (CMP-5's #608 follow-up) at the pipeline's probe interval (15 s). The client it builds may reach nothing (`Endpoints::manifest(&[])`): only its probe is used, since the companion makes its own connections.
- **CMP-8b configures the companion for the same route:** `Api`'s route is the one the last start was built with (`Route::Direct`, or `Route::Socks5` at the resolved proxy address). A route that can't be described (unreadable, a proxy name that didn't resolve) gives none, but such a route is down for good, so the companion never runs to be configured.
- **What a companion can follow is unchanged** (CMP-4b's `Follows`): with a source's two route kinds, Prowlarr follows direct or SOCKS5; qBittorrent follows direct only, and a SOCKS5 setting refuses it (`cant_follow_route`, "Can't follow your VPN setting"), never runs it direct (Q8). qBittorrent's interface and bind-address routes need a setting shape sources don't offer yet (SRC-5's DNS concern).
- **No SOCKS5 credentials:** CMP-8b's `Socks5Proxy` is an address only, so the companion's own proxy setting carries none, and the route's probe only connects.

## The snapshot follows the supervisor
- After every start the manager makes (install, update, serve's start, restart, regenerate, a rollback's restart of the previous version), it follows the supervisor's state into the snapshot CMP-10's gate reads: backing off, held for its route, needing attention or stopped is unhealthy. Running again after one of those is healthy once a health check passes (`Run::healthy`), since the supervisor says running as soon as it has spawned it. A start, or failed checks the supervisor hasn't acted on yet, change nothing; it restarts a companion after Q7's three, which then shows.
- **One follower per run:** each start and stop the manager makes begins a new run, and a follower publishes only for its own, checked and published under one lock. So a stopped run's last state never overwrites a newer one.
- **A failed health check is still followed:** a companion held for its route (a VPN that's down) is supervised but not running; it's unhealthy now and healthy once its route is up and it passes a check, without a restart.
- **And configured once it runs** (self-review B1): a start that failed its health check skipped CMP-8b's configuration, so a companion released later would run with whatever bind or proxy its own file held (#608's re-assert). The follower configures it, under the companion's slot and only for the current run, before it shows healthy; if that fails, the companion is stopped and shows unhealthy (Q8), and a restart tries again. **For the runner:** between the gate's release and that configuration, a companion runs for the few seconds a health check and the configuration take on its last-written settings. That window first becomes reachable in CMP-5g-3, which is the first slice to start companions (#660's review); nothing reaches it while every catalogue pin is null. X-cmp-egress-prelaunch closes it (`docs/decisions/2026-11-11-X-cmp-egress-prelaunch.md`).
- **Serve's start leaves a companion that's already running alone** (self-review I4): an install, restart or regenerate that ran while the starter was waiting on another companion has started it already.

## Restart, logs, regenerate
- **For a companion Lodestar installed only** (its journal): any other answers `not_installed`, before the supervisor is asked. Restart and regenerate answer once they've begun (the API's `202`) and run in a task of their own that holds the companion's slot, as an install does; dropping the request doesn't stop them. They're refused `busy` during an install or any other operation on it (the slot, or a journal with an operation in it).
- **Restart:** stop, then start and configure again, on the route as set now. **Bounded:** the stop by the supervisor's stop deadline, then the start, the health wait (`HEALTH_DEADLINE`, 120 s) and the configuration by `LIVE_DEADLINE` (5 min), after which it's `timed_out`. Its failure is logged with step `restart`.
- **Logs:** the supervisor's 1 MB ring for the companion, already redacted with its credentials before each line went in, redacted again by `Service` with the credentials stored now. It's empty until the companion has been started in this run of Lodestar, and kept after it stops, until it starts again, so you can read why it stopped.
- **Regenerate** (CMP-6's contract: never reads the old value): stop; a new credential's sealed row is stored, then written into the companion's own config file (CMP-3's writers, which keep every other line); start and configure with it. The row is written first, as at install (#611). **Every start writes the stored credential into the file again** before it launches (the writers keep every other line), so a crash between a regenerate's row and its file heals at the next start (#653-3's self-review I3). A file that can't be written puts the old sealed row back, so the row and the file agree; the start after it then fails the same way, so nothing runs on a file Lodestar couldn't write. Its failure is logged with step `regenerate`; a failed put-back as reason `rollback_failed`.
  - **Not handed over:** this build doesn't hand a companion Lodestar installed to Integrations or the Prowlarr source (only guided ones are, CMP-5g-2), so there's nothing there to update. When that hand-over lands, regenerate must redo it in the same step.
- **#621 N3:** `Supervised::healthy` fails at once while the companion's route is down (it's held, not running) instead of polling for 120 s. A route not checked yet is still waited for.

## #653's final review (carried)
- **L4: a guided companion's credential is never rotated.** Regenerate, like restart and logs, refuses `not_installed` for a companion you added, even when its credential's provenance is `generated` (a guided qBittorrent's replaced password, which it uses now). Rotating it would need CMP-8b's apply and the `Sink`'s save in the same step; without them the stored password would match neither qBittorrent nor Integrations. Tested over the real `Service`: the supervisor is never asked, the sealed row is unchanged, and reveal still shows the password. Rotating a guided credential through apply and hand-over is a follow-up candidate, not queued.
- **N7:** `target_changed`'s message says to reveal the password, then forget the companion and add it again, as `generated_pending`'s does.
- **N8:** `guided.rs`' module doc says four kinds of rows (target, origin, applied, provenance).
- **N9:** CMP-5g's decisions file says a stored URL is `EnteredUrl`'s normalised form, not as typed.
- **For CMP-9a (recorded in CMP-5g's file and here):** before forgetting a companion whose credential is generated, the forget screen warns that it's the password qBittorrent uses and offers reveal first. The API only says so after the fact (`credential_in_use`).
