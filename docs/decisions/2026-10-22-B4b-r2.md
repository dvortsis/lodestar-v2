# B4b-r2 decisions (#104)

Follow-ups from #87's review. These refine `2026-10-22-B4b.md` (§9's `/events`, §20.9). They supersede B4b's "`max_id` moves on with the next event, which always carries the newest watermark", and refine `architecture.md` §16's B4 entry (`{added, max_id}`; "`max_id` is never stale"), which now holds only while Adult is shown.

- **`max_id` is null while Adult is hidden** (runner, 2026-10-22). Torrent ids are sequential, so any real id sent beside an exact `added` shows, in its gap from the last one, how many hidden torrents arrived. Sending the newest *visible* id was tried first. It hid only the newest hidden torrents, not those between two visible ids, so it was dropped.
  - **Shape:** `TorrentsEvent.max_id` is `Option<i64>`. The key is always present, `null` while hidden, the same style as `crawler`'s `dht_nodes`.
  - **Shown:** unchanged. Each event carries the newest id, Adult included.
  - **Cost:** none today. Nothing acts on `max_id`; W5's client only folds it across a hidden tab's backlog, and now keeps a null from the newer event. A later "what's new" feature uses the newest id the client has seen in its own results, or a cursor, not an id from the stream.
  - **Search unchanged:** B4b's `catch_up_counted` now returns a `CatchUp { added, adult_added, replayed }` struct (exported), in place of the tuple; there's no visible-id field.
- **Events made while Adult was shown are withheld once it's hidden.** Each `torrents` event in the ring is tagged with the visibility it was made under. Every event is checked when it's handed to a client, replayed (`Last-Event-ID`) or live. While Adult is hidden, one made while it was shown becomes `resync {reason: "visibility"}`, one for a run of them, so the client refetches. With this, no frame a client gets while Adult is hidden carries a `max_id` or a count that included Adult.
  - **Checked at hand-off, not at subscribe:** this also covers a reconnect that subscribed just before the setting changed.
  - **Tagging over a broadcast `resync` on every toggle:** turning Adult off costs nothing for clients that hold no such event.
  - **The other direction:** events made while hidden are replayed unchanged after Adult is turned on. They undercount and carry no id, but reveal nothing.
  - **What it can't reach:** frames already queued to a socket, up to 16 per client plus TCP buffers, were checked while Adult was still shown. Nor can it reach events a hidden browser tab has already received and folded into its backlog. So the future "N new" consumer must reset its count when the Adult setting changes.
  - **The client keeps its place:** after a `visibility` resync it keeps `Last-Event-ID`, as after `lagged`, since the stream carries on. A drop then resumes from the last event it received instead of jumping to live (`web/src/lib/state/events.svelte.ts`).
- **`ResyncReason` gains `visibility`** (`openapi.json`, `schema.d.ts` regenerated).
- **The swap's Adult count is tested end to end.** `ServingConfig` gains a test-only (`#[cfg(test)]`) `hold_at_swap` point, after the old live indexer stops and before the new index's last catch-up. Torrents stored there, classified in the same transaction as the pipeline's writer does, are announced only by the swap's own report, so `the_swap_reports_its_adult_torrents` checks its `adult_added` exactly.
