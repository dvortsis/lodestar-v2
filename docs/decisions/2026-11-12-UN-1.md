# UN-1 decisions

Prowlarr's Newznab results stored as usenet items (UN-0's `unverified_items` rows, `network = 4`). This is v0.7's usenet tier (`docs/plan/2026-11-05-v07-m7.md` §5, Q13; architecture §18.6, §18.7). Off by default. Nothing in the UI or API shows these items yet: SRC-3b indexes them, and UN-3 and UN-4 expose them.

## The switch
- **`usenet` in the Prowlarr source's settings,** a boolean that defaults to `false` (`CONFIG_SCHEMA`, `Config::with_usenet`). With it off, nothing changes: Usenet indexers aren't polled, as before.
- **Prowlarr only.** Jackett has no Usenet indexers, so `usenet: true` with `manager: jackett` is refused ("Usenet results need Prowlarr").
- **Saved only when on.** `Config::to_json` writes `"usenet": true` only when it's on, so every form saved before UN-1 reads back byte for byte.
- **The manifest still lists `bt` only.** `GET /sources` shows a plugin's networks, and the API shows nothing about usenet until UN-3. UN-3 or UN-4 adds `usenet` to the manifest when the results become visible.

## What's polled
- **Prowlarr's enabled Usenet indexers** (`protocol: usenet`, with RSS) join the indexer list when the switch is on. They get the same `t=search` RSS request, with the API key in the `X-Api-Key` header (never in a URL), and the same agent count.
- **Each Usenet indexer is polled at most hourly** (`USENET_POLL_EVERY`, 24 API hits a day), not every 15 minutes like a torrent indexer. Newznab indexers count API hits per day (free accounts often get 100 or fewer), and Sonarr and Radarr share the quota, so the torrent schedule's 96 a day could use it up. The list itself is still read every 15 minutes, and torrent indexers are unchanged. **For the runner (§2.26):** this is a new number beside Q4's 15 minutes.
- **`MAX_INDEXERS` (500) is shared by both protocols,** in the manager's list order. A user with more than 500 enabled indexers who turns usenet on could see some torrent indexers fall past the cap. That's unlikely in practice.
- **The poll budget goes in list order.** With more than about 40 busy Usenet indexers, the last ones in the list get none of a poll's 4,096. They're polled again an hour later, but the same ones lose out each time. A later slice can rotate the starting indexer.
- **A Usenet indexer's page keeps only Newznab items** (SRC-6's `Kind::Usenet`). A torrent-shaped item on it is ignored, and a Newznab item on a torrent indexer is ignored as before.

## The NZB link is never stored (the slice's title rule)
- **Prowlarr's NZB link is dropped as soon as the item is parsed** (`to_usenet`). It carries Prowlarr's API key in its query, and the indexer's API key inside its encrypted `link=` parameter. The link is read only to check it isn't the GUID. No type that carries a result (`UsenetFind`, the `Found` it becomes, the stored claims) ever holds it, so no `Debug`, `Display`, log line or stored byte can show it, redacted or not.
- **No send reference is stored (runner, 2026-11-12, security).** Every usenet find is private, and L3 stores no external reference for a private find, on every network. Some indexers' GUIDs, and Prowlarr's, are the API-key download link itself, so plugin-side checks alone mustn't decide what's kept. A usenet item is stored with its key (the indexer id and the GUID, hashed), its title and its other claims, and nothing that names the GUID in the clear. **So UN-1's items aren't sendable yet:** see the open owner question.
- **Only a GUID that can't fetch anything keys an item** (`usenet_guid`). Otherwise the result isn't stored at all. The GUID is hashed into the key and isn't stored itself. A GUID is SRC-6's `external_ref` form, which already takes credentials (`apikey`, `r`, `i`, `token`, …), user info and fragments out of an http(s) URL. On top of that, the GUID must be:
  - 1–1,024 bytes (UN-0's `USENET_MAX_PART`);
  - never equal to the link;
  - never holding the manager's API key, in any case, or a credential word (`apikey`, `api_key`, `passkey`, `token`, `password`, `secret`);
  - either an opaque id (letters, digits and `.:_-`), or an http(s) details page that:
    - has no user info or fragment;
    - isn't on the manager's host and isn't a manager download;
    - has no path segment that fetches (`api`, `getnzb`, `download`, `dl`, `nzb`, `get`, `rss`, `sendnzb`) and no `.nzb`;
    - has no query but a single non-empty `guid=` (NZBGeek's `geekseek.php?guid=…`);
  - **never a dashed UUID** (bare or `urn:uuid:`). The *arr RSS parsers make one up (`Guid.NewGuid()`) for an item with no `<guid>`, a new one on every poll. Such an item would be stored again on every poll, crowding the cap, and send could never find it again. Newznab's own GUIDs are undashed hex or a details page.
- **The key depends on the parser's form of the GUID** (SRC-6's `external_ref`). A later change to that normalisation would re-key the items it touches, which then come back as new items beside the old ones until the cap ages those out. SRC-6's owner should treat the form as stable, or bump the key's version tag (`lodestar.usenet.v1`) with a re-key.
- **A title holding the manager's key is refused too.** The indexer's own key isn't known to Lodestar, so it's kept out by shape: Prowlarr hides it inside the encrypted `link=` parameter, which is never kept.
- **The tests:** a fixture whose links carry both keys runs through the plugin, a real pipeline and a file-backed store. Every stored claim's text, every byte of the store's files and every log line (with every pipeline, filter and integrations event on) are scanned for either key, the poster, `/download`, `getnzb`, `link=` and `t%3Dget`.

## The mapping (ENR-9's rule)
- **The claims are version 3:** a details section beside the name, size and ids. Per ENR-9, a row with a details section holds no description or publisher, and none is set.
  - **title:** the claimed name (required; SRC-6's cleaned title, at most 1,024 bytes);
  - **size:** 1 byte to `MAX_SIZE` (1 PiB), or none. SRC-6 parses sizes as `u64`, so an overflowing value is no size rather than a wrapped one;
  - **category:** `Details::source_category`, the most specific Newznab id the item names (the first one that isn't a multiple of 1,000, like `2040` Movies/HD; otherwise the first one), in decimal;
  - **posted date:** `Details::posted_at`, from `pubDate`, believed from 1980-01-01 (`USENET_MIN_POSTED`) to a day past now and at most ENR-9's `MAX_POSTED_AT`. The same value is the provenance's `published_at`;
  - **external ids:** the feed's imdb, tmdb and tvdb, which the claims' clamp keeps only in ENR-9's forms;
  - **provenance:** the posting date and `Confidence::Low`, with no external reference (L3). The indexer is part of the item's key.
- **The poster is dropped: it's never read.** SRC-6's parser doesn't keep `newznab:attr name="poster"`, so it never reaches the plugin. A Newznab poster is often an email address, and ENR-9 has no field for a person. The fixture's poster (an email in the attribute and in the description) is checked against the stored bytes and the logs.
- **The newsgroup isn't kept yet.** SRC-6's parser doesn't read `newznab:attr name="group"`, and `crates/sources-feeds` isn't UN-1's. `Details::newsgroups` stays empty, and the indexer is the item's provenance. **Follow-up:** the parser could keep `group` (checked with `newsgroup_ok`), so the plugin can fill `newsgroups`.
- **Every text is judged before storage.** The pipeline judges a usenet item's name and details texts with the same rules as any claim (`judge_usenet`), with no hash. A judged item's text is the title on its own and joined with the category, at most `USENET_MAX_JUDGED` (4 KiB); a test checks it with the pipeline's own `judged_len`.
- **A held verdict stores nothing.** Any hold (the floor, the core, a pack or your rule) drops the item and is counted as `held` (runner), though nothing is written. No tombstone or quarantine row is written, since the store has no hold for a usenet key (see the known gaps).
- **`private_source`.** Every usenet `Found` is `private_source` (`Found::usenet`), and the store marks every usenet row private (UN-0), whatever the indexer's privacy. So a private indexer's items keep `private_source`, and so do a public one's. Every later outward gate (UN-3's send, search, exports) reads the row's `flags::PRIVACY`, which both marks set.

## Bounds
- **`USENET_PAGE_BYTES` = 2 MiB per Usenet page,** checked before parsing. A larger answer is refused whole and retried next poll. A page of 100 Newznab results is about 100–300 KiB.
- **`USENET_PAGE_ITEMS` = 100 results kept per page** (the `PAGE_SIZE` asked for). `USENET_PAGE_LIMITS` lets the parser read up to 1,000 `<item>`s, so a long page is still checked to its end.
- **`USENET_POLL_ITEMS` = 4,096 results emitted per poll** of the whole indexer list, shared by every agent. The rest wait for the next poll. That's the store's `MAX_USENET_BATCH` and about 40 busy indexers' newest pages.
- **Parsing is strict.** The parser is SRC-6's (bounded, fuzzed, no DTD). The plugin adds no panic, unwrap or truncating cast: the clock is read with `i64::try_from`, dates are range-checked with saturating arithmetic, and sizes are range-checked. Property tests feed hostile bytes and hostile titles, GUIDs, sizes, dates and categories.
- **The ingest judged-bytes budget** (`2026-11-07-runner-followups.md`): a poll judges at most 4,096 × 4 KiB = 16 MiB, and a writer batch (256 finds) at most 1 MiB, against the 150 MB worst case that budget is sized for.

## Outside the brief's owns (runner, 2026-11-12)
UN-1 needed an ingest path for usenet finds, which `main` didn't have. The runner approved these edits, and refused keeping a usenet reference in `store_claims`:
- **`crates/sources/src/plugin.rs`:** `Found.usenet: Option<[u8; 32]>`, set only by `Found::usenet(indexer, guid, strategy)`, which builds UN-0's `UsenetKey` and marks the find `private_source`. Such a find's `key` holds only a writer-map key (the usenet key's first 20 bytes, so maps keyed by it keep finds apart), never a swarm hash. Nothing else changes for other finds. A unit test checks the constructor sets `private_source`.
- **`crates/pipeline/src/lib.rs`, the intake:** a usenet find goes only to the writer's claims path. It's never claimed, leased, sent to the fetch pool or peer finding, and never checked as a hash. With no claims, it's refused. It isn't counted as a harvested key (`HARVESTED`), which `docs/metrics.md` defines for hashes: it has none, and it's sent again on every poll, so counting it would lower Prowlarr's yield on Insights. The end-to-end test checks that a usenet find reaches none of the coordinator, the pool, touches or the held set, and isn't counted as harvested.
- **`crates/pipeline/src/unverified.rs`:**
  - **ingest:** a usenet find has no adult section and no identification, never looks up a stored torrent, and is judged by `judge_usenet`. If it's kept, it's written with `Network::Usenet` and its 32-byte key.
  - **`store_claims`:** unchanged for the reference (L3 stores none for a private find, usenet included; `tests/claim_trackers.rs` has a usenet case). A usenet find also gets no trackers.
  - **`judge_item` (requirement 4, follow-up 651):** a usenet item is judged by its claims, never by its key's length. Any hold removes it and holds nothing. A unit test re-judges a stored usenet item and keeps it, then removes one whose claims match a new rule.

## The cap's cost (UN-0's heads-up, requirement 5)
Measured with `usenet_cap_cost_at_one_million` (`tests/prowlarr_usenet.rs`, `--ignored`, release build), at 1M BitTorrent unverified items plus the usenet items shown, with this plugin's sizes. The writer stores a poll in batches of 256 finds (`PipelineConfig::batch_max`), so a full poll of 4,096 results is 16 adding writes.

| Store | Usenet items | One 256-find write, median (max) | A 4,096-result poll |
|---|---|---|---|
| in memory | 100k | 14 ms (16 ms) | 0.23 s |
| in memory | 1M, at the cap | 109 ms (184 ms) | 1.86 s |
| file, container disk | 100k | 16 ms (58 ms) | 0.37 s |
| file, container disk | 1M, at the cap | 128 ms (203 ms) | 2.30 s |

- **It's material.** At the cap, each adding write spends about 95–110 ms more than at 100k inside the single writer's transaction, matching UN-0's ~160 ms estimate. A full poll then holds the writer for about 2 s on a fast disk, and likely several seconds on a NAS, every 15 minutes, while the DHT and every other source wait behind it.
- **Writes stay off by default,** so this costs nothing until a user turns the switch on and the tier grows toward 1M.
- **Proposed to the runner, not done here (the store isn't UN-1's):** an index on `unverified_items(network, id)` in SRC-3b's migration, so the eviction reads the lowest usenet ids directly instead of sorting them, plus a kept per-network count (a row in a small counts table, updated in `put_one` and the purge paths), so the count runs only past the cap. Either removes most of the cost; together, the per-write cost should fall back to about the 100k figure.

## Known gaps, named, not fixed
- **No store-level hold for usenet keys** (from rv-748, beside follow-up 651). A held item isn't stored, but nothing remembers it: the next Prowlarr poll brings it back, and it's judged and dropped again. That costs one judgement per poll per held result, and nothing held is ever stored. A hold for usenet keys needs a store change (a table keyed by the 32-byte key, or V12's 20-byte checks widened), so it's SRC-3b's migration or a later store slice.
- **Undecodable usenet claims read `claims_private = false`** (rv-748, `store/src/unverified.rs`, about line 1349). It's moot while every usenet write sets flags 3, which UN-0's `put_one` does whatever the caller says. The re-judge sweep removes an item whose claims don't decode anyway.
- **Usenet items aren't sendable until UN-3** (runner). No reference is stored, so nothing yet says which Prowlarr result an item is. UN-3 designs where its reference lives.
- **`torznab::Item`'s derived `Debug` prints its `link`** (in `crates/sources-feeds`, with credentials taken out but the encrypted `link=` parameter kept). The plugin never formats an `Item`, and drops the link before any type it builds. **Follow-up** for SRC-6's owner: give `Item` a `Debug` without the link and the GUID.

## Open owner question: where send's reference lives
- **What breaks without one:** UN-3's send must ask Prowlarr for the result again. The stored key is a one-way hash of the indexer id and the GUID, so neither can be read back. The title alone is ambiguous: several results share one, and the right indexer isn't known.
- **The proposed narrow rule, not built here:** a usenet-only stored field with its own allowlisted shape, `usenet:<indexer id>:<guid>`. Its GUID would be one the plugin's `usenet_guid` accepts, and the store or pipeline would check that shape again centrally. That central check would refuse:
  - a query other than one `guid=`;
  - user info, a fragment or a credential word;
  - a fetching path segment or `.nzb`.

  It would live outside `provenance.external_ref`, so L3 stays as it is for every reference. It needs the owner, because it relaxes what a private row may name, and a store field (SRC-3b's migration or UN-3).
