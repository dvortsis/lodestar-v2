# S-snapshots decisions

Owner-delegated decision (2026-10-23; deciding factors UX and performance): migration snapshots `<db>.pre-v<N>[.<k>].db`, and the `<db>.before-rollback-<time>.db` copies a rollback keeps, get the live store's purge and are deleted after 90 days. This closes the gap `2026-10-22-runner-secure-delete.md` left open ("migration snapshots, whose retention is with the owner") for owner decisions §2.16 and §2.17; it extends architecture §7 and §12 (`crates/store/src/snapshots.rs`).

- **When:** on the writer's hourly purge tick (`PURGE_EVERY`), right after `purge_filter`, with the same `now` and `hits_before` (`Store::purge_snapshots`). Only a file-backed writable `Store` runs it; in-memory and read-only stores do nothing.
- **What is purged, per schema version the snapshot holds** (read from its `schema_migrations`, not its name):

  | Snapshot schema         | Torrents the live store deleted                                           | Quarantine expiry, sealed names, filter hits | Query log                             | API keys, saved searches, collections                       |
  | ----------------------- | ------------------------------------------------------------------------- | -------------------------------------------- | ------------------------------------- | ----------------------------------------------------------- |
  | v1–v3                   | deleted (children cascade)                                                | no such tables                               | no such table                         | no such tables                                              |
  | v4–v9                   | deleted (children cascade)                                                | purged as live                               | no such table                         | no such tables                                              |
  | v10                     | deleted (children cascade, alerts, marks and collection entries included) | purged as live                               | rows the live store pruned or cleared | rows deleted live go (by id); keys revoked live are revoked |
  | none, or newer than v10 | skipped, warning logged                                                   | skipped                                      | skipped                               | skipped                                                     |

  A file that isn't a readable database is skipped with a warning too. Either way it's left byte for byte and still expires at 90 days. `Plan::KNOWN_THROUGH` has a test that fails when a migration is added, so the next migration has to say what its schema means here.

- **Quarantine, as live:** rows past `expires_at` go, an expired adult hold becomes a tombstone (never replacing a floor rule's), and filter hits older than `hits_before` go. The SQL mirrors `purge_filter`; an equivalence test runs both on the same rows and compares the tables. **Also, a sealed name the live store no longer holds is cleared** (`sealed = NULL`): a hold released or confirmed since the snapshot was taken. The row itself stays, so a restored snapshot still refuses the hash until its own expiry.
- **Deleted torrents, by hash:** every live deletion (`delete_torrents` for abuse reports and confirmations, and the adult relabel's refile) leaves the hash in `cs_hashes`, `tombstones` or `quarantine`. A snapshot torrent stored under a held hash is deleted. A snapshot can end up stricter than live (a hash held by an imported CS-1 list whose torrent the live store still has), never laxer.
  - **Confirmed and reported CS-1 entries (origin 0 and 1) are looked up in every pass, whenever they were recorded.** `add_cs_hashes` keeps an imported entry's old `added_at` when you report it, so a time window would miss a torrent reported after the snapshot whose hash an older list import already had. They come from your own actions, so they're few.
  - **Imported entries, tombstones and quarantine are looked up only when recorded since the snapshot was taken** (less a 1-day margin for a long `VACUUM INTO`). An older one can't have a torrent in the snapshot: tombstones and quarantine are written with the time of the deletion (`INSERT OR REPLACE`).
  - **After a full pass, later passes look up only holds recorded since the last one**, less 10 minutes for a hold that committed on another connection just after it. The mark is in memory on the writer's `Store`, per snapshot path and modification time, so each start (and a new or replaced file) gets one full pass. **A full pass also runs once a day, and whenever `now` is before the last pass's:** a hold recorded with a time older than the mark less the margin (the clock stepped back, or the machine slept between reading the time and committing) is then found within a day, not only at the next restart. Measured with 200k tombstones and a 20k-torrent snapshot: about 0.9 s per snapshot on every hourly tick before; about 1 s once after a start, then about 8 ms per tick.
- **V10's query log:** the live store prunes it oldest first (`prune_query_log`) or clears it, so a snapshot row older than the live log's oldest `(at, id)`, or every row when the live log is empty, is one the live store deleted. **V10's API keys, feed tokens, saved searches and collections** have AUTOINCREMENT ids, so a snapshot row whose id the live store has issued (at or below its `sqlite_sequence`) but no longer holds was deleted there, and goes from the snapshot (a saved search takes its alerts and feed tokens, a collection its entries, by cascade). A key revoked live gets the same `revoked_at` in the snapshot, so a restore can't bring back a key or token you deleted or revoked. A row with an id above the live sequence (a snapshot newer than a store rolled back since) is left: nothing says it was deleted. **Edits** (a renamed or changed search, marks, labels and notes on torrents, which are keyed by torrent and kept only while non-empty) leave no record to match, so they go with the snapshot at 90 days, as the brief allows.
- **No pre-images:** the purge sets `secure_delete`, switches the snapshot to WAL (which only writes new pages, where the rollback journal would hold copies of the old ones, sealed names included), commits with `BEGIN IMMEDIATE`, runs a TRUNCATE checkpoint and switches back to the rollback journal, so the snapshot ends as one file, as `VACUUM INTO` wrote it. A snapshot with nothing to purge isn't written at all. **A WAL left by a purge interrupted between commit and checkpoint** is folded in at the next purge, and by `lodestar rollback` (`snapshots::settle`) before it checks and copies a snapshot, so a restore never brings back pre-purge content.
- **The snapshot's age is its modification time.** `VACUUM INTO` sets it when the snapshot is taken, and the purge puts it back after each write. Why not something else: a sidecar file is one more file per snapshot for users to see and for crashes to orphan; the live store's `schema_migrations.applied_at` is wrong after a rollback and re-upgrade (it dates an older snapshot to the new upgrade); a field inside the snapshot would change a file that must restore as it was taken. `lodestar rollback` already showed the modification time. **Limits:** a copy that doesn't keep modification times (`cp` without `-p`, some backup tools), or a crash between a purge's write and the time being put back, restarts that snapshot's 90 days. Both only keep a snapshot longer, never delete one early.
- **Expiry is a plain unlink** of the snapshot and any `-wal`, `-shm` or `-journal` beside it, at 90 days to the second. A side file that can't be deleted is a warning of its own; the snapshot still counts as deleted. Overwriting first doesn't reach the old blocks on copy-on-write filesystems or SSDs, so it would only cost a write of the whole file. Each deletion is logged at info level.
- **A running rollback keeps its snapshot.** `lodestar rollback` holds M6-cli's store lock from before it reads the snapshot until the restored file is in place, and the lock refuses while any connection has the store open and stops the server from opening it meanwhile. The purge runs only on an open writer connection, so the two can't overlap. A test holds the real `StoreLock`, shows `Store::open` fails, and that the snapshot survives. B-update's journaled rollback (§12.2) keeps every process off the store the same way.
- **The window is fixed at 90 days (`snapshots::RETAIN_DAYS`), not a setting.** A `snapshots.retain_days` setting would have to reach the writer through `WriterConfig` and the services wiring, outside this slice's files. It's a small follow-up if the owner wants it.
- **One name parser:** `snapshots::list` and `parse_name` in `crates/store`; `lodestar rollback` and `stats` map that list (adding the size).
- **`lodestar rollback`** lists each snapshot's date, age and deletion date ("deleted after …", or "past the 90-day window, deleted once Lodestar runs" for one the server hasn't removed yet, which can still be restored), and the copies earlier rollbacks kept ("kept by a rollback"), which can be restored by name to undo a rollback. `lodestar stats` counts both in its snapshot count and size.
- **Not covered:** `lodestar backup` folders are the user's to keep.
