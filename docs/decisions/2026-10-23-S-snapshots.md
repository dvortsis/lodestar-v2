# S-snapshots decisions

Owner-delegated decision (2026-10-23; deciding factors UX and performance): migration snapshots `<db>.pre-v<N>[.<k>].db` get the live store's purge and are deleted after 90 days. This closes the gap `2026-10-22-runner-secure-delete.md` left open ("migration snapshots, whose retention is with the owner") for owner decisions §2.16 and §2.17; it extends architecture §7 and §12 (`crates/store/src/snapshots.rs`).

- **When:** on the writer's hourly purge tick (`PURGE_EVERY`), right after `purge_filter`, with the same `now` and `hits_before` (`Store::purge_snapshots`). Only a file-backed writable `Store` runs it; in-memory and read-only stores do nothing.
- **What is purged, per schema version the snapshot holds** (read from its `schema_migrations`, not its name):

  | Snapshot schema | Torrents the live store deleted | Quarantine expiry, sealed names, filter hits |
  |---|---|---|
  | v1–v3 | deleted (children cascade) | no such tables |
  | v4–v9 | deleted (children cascade) | purged as live |
  | none, or newer than v9 | skipped, warning logged | skipped |

  A file that isn't a readable database is skipped with a warning too. Either way it's left byte for byte and still expires at 90 days. `Plan::KNOWN_THROUGH` has a test that fails when a migration is added, so the next migration has to say what its schema means here.
- **Quarantine, as live:** rows past `expires_at` go, an expired adult hold becomes a tombstone (never replacing a floor rule's), and filter hits older than `hits_before` go. The SQL mirrors `purge_filter`; an equivalence test runs both on the same rows and compares the tables. **Also, a sealed name the live store no longer holds is cleared** (`sealed = NULL`): a hold released or confirmed since the snapshot was taken. The row itself stays, so a restored snapshot still refuses the hash until its own expiry.
- **Deleted torrents, by hash:** every live deletion (`delete_torrents` for abuse reports and confirmations, and the adult relabel's refile) leaves the hash in `cs_hashes`, `tombstones` or `quarantine`. A snapshot torrent stored under any held hash recorded since the snapshot was taken (less a 1-day margin for a long `VACUUM INTO`) is deleted. Older held hashes can't have a torrent in the snapshot, so they aren't looked up, which keeps the hourly cost to the holds of the last 90 days. A snapshot can end up stricter than live (a hash held by an imported CS-1 list whose torrent the live store still has), never laxer.
- **No pre-images:** the purge sets `secure_delete`, switches the snapshot to WAL (which only writes new pages, where the rollback journal would hold copies of the old ones, sealed names included), commits with `BEGIN IMMEDIATE`, runs a TRUNCATE checkpoint and switches back to the rollback journal, so the snapshot ends as one file, as `VACUUM INTO` wrote it. A snapshot with nothing to purge isn't written at all.
- **The snapshot's age is its modification time.** `VACUUM INTO` sets it when the snapshot is taken, and the purge puts it back after each write. Why not something else: a sidecar file is one more file per snapshot for users to see and for crashes to orphan; the live store's `schema_migrations.applied_at` is wrong after a rollback and re-upgrade (it dates an older snapshot to the new upgrade); a field inside the snapshot would change a file that must restore as it was taken. `lodestar rollback` already showed the modification time. **Limits:** a copy that doesn't keep modification times (`cp` without `-p`, some backup tools), or a crash between a purge's write and the time being put back, restarts that snapshot's 90 days. Both only keep a snapshot longer, never delete one early.
- **Expiry is a plain unlink** of the snapshot and any `-wal`, `-shm` or `-journal` beside it, at 90 days to the second. Overwriting first doesn't reach the old blocks on copy-on-write filesystems or SSDs, so it would only cost a write of the whole file. Each deletion is logged at info level.
- **A running rollback keeps its snapshot.** `lodestar rollback` holds M6-cli's store lock from before it reads the snapshot until the restored file is in place, and the lock refuses while any connection has the store open and stops the server from opening it meanwhile. The purge runs only on an open writer connection, so the two can't overlap. A test holds the real `StoreLock`, shows `Store::open` fails, and that the snapshot survives. B-update's journaled rollback (§12.2) keeps every process off the store the same way.
- **The window is fixed at 90 days (`snapshots::RETAIN_DAYS`), not a setting.** A `snapshots.retain_days` setting would have to reach the writer through `WriterConfig` and the services wiring, outside this slice's files. It's a small follow-up if the owner wants it.
- **`lodestar rollback`** lists each snapshot's date, age and deletion date ("deleted after …", or "past the 90-day window, deleted once Lodestar runs" for one the server hasn't removed yet, which can still be restored). `lodestar stats` already showed the count and total size.
- **Not covered:** `lodestar.before-rollback-<time>.db`, the copy of the store a rollback keeps, is a full copy kept until the user deletes it, and gets neither the purge nor the expiry. `lodestar backup` folders are the user's to keep. Both are named in the PR as follow-ups.
