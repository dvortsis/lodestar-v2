# P-v06-workers decisions (planning: remote workers v1)

Planning slice P-v06-workers, 2026-11-06. The plan is `docs/plan/2026-11-06-v06-workers.md`. Docs only: these are planning choices the runner accepts or changes in review. The questions marked **owner** in the plan's §5 (Q1, Q2) aren't decided here.

## Slicing
- **22 `WK-*` slices, about 14,400 lines, every one ≲ 900 lines** (plan §4). Build-plan P4 said "about 6 PRs"; that counted the two merged cluster PRs and four large ones. The ≲ 1,500-line bar and the multi-session rules (owner §2.24) split them further. The ids are `WK-*` because `W0`–`W9` are taken in `runner/slices.yaml`.
- **The first slice unifies the lease tables (WK-0), before any wiring.** The inventory found two `LeaseTable`s: `ClusterServer`'s and the pipeline's `Coordinator`'s. Wiring remote workers onto both would let one key be granted twice and break §19.3's exactly-once. WK-0 also owns `proto.rs` and adds every v1 message and field (peer hints, the hint relay, chunked filter-snapshot and re-verification messages), plus an inbound sink, a grant-admission hook and a send/broadcast API in `server.rs`, so no later slice edits either file. The self-review found several slices needing protocol changes that no slice owned.
- **Codecs live where their types live.** `Results`, `Counters` and the filter snapshot go in `crates/pipeline/src/wire/`, because the pipeline already depends on the store, classify and filter types they carry; `crates/cluster` stays free of them. The have-filter and `Assign` codecs go in `crates/cluster`. The spool's format goes in `crates/pipeline` so the fuzz crate reaches it.
- **Docs and packaging don't gate WK-G** (WK-18, WK-19); the v0.6 tag needs them. **Quarantine and purge actions move to WK-13,** so the rest of the API (WK-14) needs only WK-5 and leaves the critical path. The critical path is eight merges.

## Scope (runner's calls, each a plan §5 question)
- **v1 places only the DHT and fetch and prepare on workers** (Q9). Build-plan P6 (v0.8) already defers singleton, account and overlay placement. This plan also defers `sharded(unit)` plugins, politeness token leases, singleton failover and the placement column in Settings → Sources: a refinement of §19.1/§19.5, flagged to the owner (§2.19). §19.8's global-politeness check becomes "no capped plugin is ever placed on a worker"; WK-G lists how v1 checks each §19.8 test.
- **No signed `Update` offers or Update action in v1** (Q13). They need the §18.10 catalogue (Track K). Version skew is refused cleanly. Flagged (§2.19).
- **The raw info archive (minus `pieces`) is sent only when `archive_raw` is on** (Q8). It's off by default and adds ~0.3–1 KB (architecture §3); the ≤ 3 KB median is gated at defaults, and the median with it on is reported.

## Store
- **One migration, `torrent_worker`, rows only for remote workers** (plan §3, Q10). Purge-by-worker and quarantine (§19.4, §19.7) need provenance, and none is stored today. A single-machine install writes no row. It takes the next free number in the §0.7 queue (V15 is reserved for CR-3).
- **No holder column on `fetch_queue`.** A coordinator restart starts a new lease epoch, so every old token is stale; keys are re-granted. Results from an earlier epoch follow Q7's **late-result rule**: committed if the key is neither stored nor held, never counted as harvested again, cohort and sources from the coordinator's own record, and a `late_result` correction beside any terminal outcome already counted, so the funnel still reconciles. A 24 h spool isn't thrown away after an update. This narrows §19.8's "stale-token results are ignored" for earlier epochs only: a refinement of §19.3/§19.8, flagged to the owner (§2.19).
- **The worker dimension is a `dim` code** in the existing rollup tables, not a column.

## Numbers and defaults (runner, §2.26)
- **Worker fetch-pool cap 50,000 keys** (Q5): 34–46 MiB (690 B per key from the soak, 0.95 KB from r3's observed step), inside an estimated 209 MiB worker at 10M stored (234 MiB during a filter swap); measured in WK-10 before it's fixed. The 200k default would take 132–190 MiB on its own.
- **The worker budget is 256 MB plus the have-filter beyond its 10M size** (Q6, decided under owner §2.26 as a size budget serving performance; flagged, and the owner can veto). The filter has to be the coordinator's exact bits, and `capacity_for` sizes it at 2× the stored count: 25 MB at 10M, 125 MB at 50M, twice that during a swap. A flat 256 MB would cap the corpus a worker can serve. The gate runs at 10M, where everything fits in 256 MB; above 64 MB the worker swaps in place instead of holding two copies.
- **Outbound bytes queued to the coordinator capped at 8 MiB** (WK-7). The session queue of 256 messages could otherwise hold 256 MiB of 1 MiB frames.
- **The cluster port isn't bound until workers are allowed** (Q3). A tightening; the default number stays 8091.
- **The local worker keeps direct calls on the one lease table** (Q4), sharing the lease, fencing and accounting code but not the `Link`. A refinement of §19.2's "one code path", flagged to the owner (§2.19).
- **The protocol freezes at 1.0 when WK-G merges** (Q11).

## Found while inventorying
- **The Unraid worker template passes the join token in an environment variable** (`LODESTAR_TOKEN`), which V6-cluster2 ruled out (file or stdin only). Loosening that is the owner's (Q2). WK-2 builds the file and stdin forms either way.
- **The have-filter is keyed with `RandomState` on purpose,** so peers can't choose hashes that collide in it, and a copy can't answer on another machine. WK-3 keeps it keyed: SipHash-1-3 under a random 128-bit key per filter, sent only in the snapshot over mTLS and never logged. `siphasher` (already in `Cargo.lock`) becomes a direct dependency of `crates/pipeline`, approved in WK-3's brief.
- **The coordinator sends the file-tree dictionary to workers** (WK-8), versioned. Blobs name their dictionary id and the commit refuses an unknown one, so a worker never builds blobs the store can't read.
- **CR-3 owns `crates/pipeline/**`**, which overlaps most WK slices. If it launches during this epic, the runner narrows its owns or orders the slices.
- **`crates/pipeline/src/have.rs` is also owned by CR-5** (Track C, unmerged). The runner orders WK-3 against it.
