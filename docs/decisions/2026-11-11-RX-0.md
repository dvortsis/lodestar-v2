# RX-0 decisions

The regex parser and trigram plan (plan `docs/plan/2026-11-05-v07-m7.md` RX-0; architecture §8, §3). `crates/search/src/regex.rs` is pure: it parses a user's pattern into a trigram plan and touches no index. Nothing calls it yet; RX-1 wires `/…/` queries, the prefilter and the verifier. None of these decisions loosens an owner decision or a security decision. The runner flags the ones marked **(refinement)** to the owner (§2.19).

## Parser
- **`regex-syntax` `=0.8.11` parses**, pinned exactly (standards §2). The runner approved it for RX-0 on 2026-11-11, as the v0.7 plan proposed. It was already in both lockfiles through tantivy's `regex`, so no new crate enters the tree. A hand-written parser for untrusted input would be more attack surface than the one `regex` itself uses, which is fuzzed upstream and has a nest limit.
- **The syntax is `regex`'s, minus what it can't do anyway:** no look-around and no backreferences (both `regex_syntax` errors, so `regex_syntax`). That's what RX-1's verifier compiles, so the planner and the verifier agree on the language.
- **Case-insensitive by default** (`CASE_INSENSITIVE`); `(?-i)` turns it off. Name search is case-insensitive everywhere else in §8, and §8's own example `/S0[1-9]E\d+/` is meant to find `s01e02`. `Pattern::verify_pattern()` spells the flag out (`(?i)…`) so the verifier compiles exactly what was planned. **(refinement)**
- **Only the `i` flag is allowed.** `m`, `s` and `R` mean nothing on a one-line name, `x` changes how the rest of the pattern reads, `U` only changes greed, and `u` off would allow non-UTF-8 matches the planner doesn't model. Refusing them is the conservative choice; any of them can be allowed later without breaking a saved query.

## Limits
All are checked before the work they guard grows, and each refusal is a `RegexError` with a stable `Reason::code()` (`regex_*`):

| Limit | Value | Code | Checked |
|---|---|---|---|
| Empty pattern | — | `regex_empty` | first |
| Pattern length | 512 bytes | `regex_too_long` | before parsing |
| Nesting: each group, class, repetition, alternation and concatenation level counts | 16 (about five levels of nested `(x)+y`) | `regex_too_deep` | while parsing (the parser's nest limit) |
| Syntax-tree nodes, class items included | 256 | `regex_too_many_nodes` | on the tree, before translation |
| One repetition count | 100 | `regex_repeat_too_large` | on the tree |
| Nested repetition counts, multiplied | 1,000 | `regex_repeat_too_large` | on the tree |
| Alternatives in one alternation | 32 | `regex_alternation_too_wide` | on the tree |
| Flags other than `i` | — | `regex_flag_not_allowed` | on the tree |
| Case-folding cost of all the classes (`\pL`, `[a-z]`, brackets, …), modelled on what `regex-syntax` does | 4,600,000 units (two `\p{Any}`) | `regex_class_too_large` | on the tree, before translation |
| Estimated compiled size: each class item's ranges (1 for a literal) × the enclosing repetition counts | 50,000 | `regex_too_large` | on the tree, before translation |
| Ranges in one translated class | 4,096 | `regex_class_too_large` | backstop while planning; real classes stay under ~1,600 |
| Plan nodes | 256 | — (weakened, see below) | while planning |

- **Why these values.** Torrent names are a few hundred characters at most, and §8's query string is 2,048 bytes; a 512-byte pattern with 256 parts covers every realistic search. The nest limit matches the query parser's `MAX_DEPTH` (16); the parser counts each group, repetition, alternation and concatenation level, so that's about five levels of nested `(x)+y`. 100 per count and 1,000 multiplied bound the repetition itself. **(refinement)**
- **Case folding is charged for exactly what `regex-syntax` folds** (runner reviews of #717: B1, B2, B3; runner §2.26 call). Patterns are case-insensitive by default, and folding is the costly step of translation: in the first review, 73 `\p{Any}` in 511 bytes took about 300 ms, and as long again for `regex` to compile. Two rounds of simpler rules (charge each class's codepoints; then charge negated items their complement and bracket items per level) each left a shape through at 150–700 ms, so the budget now follows `regex-syntax` 0.8.11's own folding (`hir/translate.rs`, `hir/mod.rs`) instead:
  - **What gets folded.** A Unicode property item folds its un-negated set, so `\P{Any}` folds all of `\p{Any}`. Each bracket folds its whole set before negating it, nested brackets included. Each set operation folds both operands. Perl classes (`\w`, `\D`, `\S`) are closed under folding and are never folded on their own; a bracket around them folds them with its set. ASCII items (`[:alpha:]`) fold their un-negated set too. The bracket's sets are built case-sensitively from each item's own text, which costs microseconds. A set with a part already folded (a property or ASCII item, a nested bracket, a set operation) is widened by every cased character, which bounds what the translator actually holds; a set of only literals, ranges and Perl classes is exactly the translator's and is charged as it is.
  - **What a fold costs.** `regex-syntax` skips a range with no cased character after one binary search; any other range is walked codepoint by codepoint. Up to the fold table's last key (U+1E943) each step is a binary search, about 10 steps' worth (23 ns against 2–3 ns past it). Each cased character found adds images that are sorted and merged, about 15 steps' worth. Calibrated in a release build at 0.1–2.5 ns a unit across `\p{Any}`, wide ranges, letter classes and brackets.
  - **Which characters are cased** comes from std's case mappings, scanned once up to U+1FFFF. A test checks this covers every character the pinned `regex-syntax` folds, and that nothing past the scan folds.
- **What this allows and refuses.** Two `\p{Any}` or `\P{Any}` fit the budget, and a third doesn't. So do six `[\x{80}-\x{FFFF}]`, two `[\S]`, four `[\D]`, two `[[^a]b]`, two `[\D--a]`, 27 `[_\pL]` and 56 `\pL`. Brackets around the fold table's whole span (`[[[\x{41}-\x{1E943}]a]a]`) are accepted three levels deep and refused at four, so the review's eight-deep shape is refused. Cheap folds stay cheap (I3): `[\W_]` walks no cased character, so `S\d\d[\W_]E\d\d[\W_]` is accepted (up to 18 copies, then the node limit) and `[\W_]` 62 times (then the compiled-size limit). `[\w--\d]`, `[\pL&&\p{Greek}]` and `[\pL~~\pN]` are accepted 13–26 times. The B2 decision to refuse `[\D--a]` outright no longer applies: it's charged its real cost like any other set operation (runner, 2026-11-12, I3: "tell me which you chose"; chosen: relieve them, since the model costs them accurately). Standalone `\w` and `\W` are bounded only by the compiled-size estimate (62).
- **Re-measured, and audited by search.** The slowest accepted patterns known parse in about 9–12 ms (release build, best of five to nine, on a shared 4-core machine): `[\w.-]` 51 times (the runner's reviewer measured 11–12 ms), two `[[^a]b]`, two `\p{Any}` at the baseline, and the shapes a randomized search over about 195,000 accepted patterns found (`[a-z\S][a-z\S]`, `[\x{0}-\x{10FFFF}ſ]{2,9}` twice, all at the baseline): nested brackets of every item kind, fold-table ranges, set operations, `(?i:…)`/`(?-i:…)` groups and repetitions, each repeated up to the length limit. The runner's bound is ≤ 50 ms. `crates/search/tests/regex_plan.rs` pins each boundary above (accepted, and one more refused) and times the accepted ones against a generous deadline.
- **The compiled-size estimate** is the plan's "compiled size" limit, made before translation: a class item weighs its range count (Unicode `\w` is about 770), times the counts of the repetitions around it. `\w{60}` passes; `(\w{10}){100}` and `\pL{100}`, which `regex` refuses at its 10 MiB default, are refused here with `regex_too_large`. It's an estimate, so RX-1 keeps `regex`'s own size and DFA limits and maps their refusal to `regex_too_large` as well.
- **The plan's size is bounded by weakening, not refusal.** Past 256 nodes an AND drops conjuncts (keeping the smallest) and an OR becomes "no constraint". Both only let more names through to the verifier, so no match is lost, and a valid pattern is never refused because its plan is large. Intermediate sets (exact strings, prefixes, suffixes) are capped at 32 strings of 64 characters the same way, so planning is linear in the tree's size.

## The plan
- **Cox's algorithm** ("Regular Expression Matching with a Trigram Index", the Code Search technique §8 names): each sub-pattern carries either its exact strings or its prefixes, suffixes and a plan; concatenation adds the grams across each join, alternation ORs. Repetitions multiply out to at most four copies, then `x{n,}` is planned as `x{n-1}` then `x+`.
- **Grams fold as the analyzer does.** `name_trigram`'s analyzer cuts the name into three-character windows and lowercases each character on its own (tantivy's `LowerCaser`, which skips the final-sigma rule). The plan uses the same folding, so `ΣΟΦ` needs `σοφ`, and a case-insensitive `s` needs `s` or `ſ` (the long s matches `s` case-insensitively but lowercases to itself). The property test checks soundness against the real analyzer.
- **`Plan::All` means no prefilter** (`.*`, `\w+`, anything shorter than three characters); `Plan::Nothing` means nothing can match (`[^\s\S]`). Whether a verify-only pattern is refused over a large corpus, and at what threshold, is RX-1's (plan RX-0 note), since it depends on the index.
- **No matching engine is built here.** The time-budgeted verifier with `regex`'s size and DFA limits is RX-1's.

## Tests and fuzzing
- Unit tests in `regex.rs` cover each planning rule and each refusal at and just inside its limit. `crates/search/tests/regex_plan.rs` holds golden plans for typical searches and a property test: for generated balanced patterns (concatenations, alternations, repetitions and `(?-i:…)` groups over leaves with awkward case foldings), random strings each pattern matches (sampled from its translation, inside random text) always pass the plan under the real `trigram_analyzer`. The worst-case patterns that drive the plan to its caps get the same soundness check. In review, an independent run checked 936,000 matching strings, confirmed by the `regex` crate itself, with none unsound.
- **`fuzz/fuzz_targets/regex_plan.rs`**: no panics, no parse slower than a second, plans within the cap, grams of three folded characters, a deterministic plan that spelling out the default flags doesn't change, and `All`/`Nothing` only as a whole plan.
- **Shared edits the runner approved:**
  - a `fuzz/README.md` row for the target, and seed patterns under `fuzz/seeds/regex_plan/` (typical searches, patterns at each limit, and negated classes);
  - the `regex-syntax` entry under `lodestar-search` in `fuzz/Cargo.lock`, which the tracked lockfile was missing;
  - a fix for a chance failure in WK-10c's `logging::refs` test, which banned the substring `0707` in a random reference (about once in 13,000 runs) and now checks that a reference isn't the hash's own bytes.
- **No `ci.yml` edit was needed.** The fuzz matrix is computed by `.github/scripts/ci_changes.py` from `fuzz/fuzz_targets/*.rs`, and the target runs whenever `lodestar-search` changes.

## For RX-1
- **Q10(a)'s marker term must be ORed into every plan.** If the trigram field is capped to a prefix of the name, a name longer than the cap may match past it, so RX-1 must run `marker OR plan` (never the plan alone), or the prefilter stops being a superset.
- The module is `crate::regex`, so inside `lib.rs` the `regex` crate needs the `::regex` path once RX-1 adds it.
- Verify with `Pattern::verify_pattern()`, compiled with Unicode on and no other flags, and the plan's grams looked up in `name_trigram` exactly as `Plan::grams()` lists them.
- The plan is sound only if `name_trigram` is filled from the same text the verifier matches (the stored `name`, unnormalized), through `trigram_analyzer`.
- **Grams depend on the toolchain's Unicode tables.** `char::to_lowercase` is std's, so a Rust update that changes case mappings changes grams: the index's grams and the planner's must come from the same tables, so such an update needs a `TOKENIZER_VERSION` bump.

## X-rx0-nits (rv-717-e9350c1d N1–N5)
A follow-up slice for the last review's nits. No bound loosened, and every charge is still at or above the work it stands for.
- **N1: the ASCII item's own fold is charged.** `[:alpha:]` folds its un-negated ASCII set before negating, about 1.5k units at most; that's now charged like a property item's.
- **N3: a bracket of only literals, ranges and Perl classes is charged exactly.** Before it, the translator has folded nothing, so its set is the bracket's case-sensitive set, and widening it by every cased character over-charged it: `[^/]` cost about 75,000 units and so allowed 60 brackets; it now costs 1, and the node limit holds it (127). A test checks, for a set of such brackets, that the set charged equals `regex-syntax`'s own case-sensitive translation, and that nothing was folded before. A set with any folded part (property or ASCII item, nested bracket, set operation) is still widened. Two boundaries moved: `[[^a]b]` and `[b[^a]]` from one to two (each folds one full span, measured 4.6 ms; two take about 9–10 ms, the baseline), `[\w--\d]` from 18 to 26, and `[\W_]` from 40 to 62.
- **N4: lookups below U+0041 count as in the table** (`lo = 0`): the folder binary-searches them too.
- **N2, N5:** one set of timing claims (about 9–12 ms, slowest `[\w.-]`×51) in the code, the test and this file; Perl classes are "never folded on their own"; the module doc is rewrapped.
