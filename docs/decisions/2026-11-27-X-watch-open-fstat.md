# X-watch-open-fstat decisions (#1140)

Follows #1104's review: `Folder::open` (`crates/lodestar/src/watch.rs`) checked the watch folder's **path** and then opened it, so a parent swapped in between made the checks describe another folder. Checks now describe the folder that was opened. Behaviour, error kinds, catalogued events and messages for a normal folder are unchanged; no check is loosened. Four edge cases now come out differently, all stricter or equal:
  - The same directory reached through two bind mounts, as both the watch folder and the data directory, is now refused as `inside_data_dir`. The path check passed it, because the paths differ.
  - A folder Lodestar can list but not enter is now `unreadable`, not `subfolder_create_failed`.
  - A folder removed between the open and the check is now `unreadable`, not `missing`.
  - On Windows, a share whose file index changes between opens now fails closed: the watch reports `unreadable` rather than reading.

- **Unix: one open, then everything through the handle.** The path check (`folder_problem`) still runs first, so its reasons (`not_absolute`, `missing`, `link` and the rest) come out as before. The folder is then opened `O_DIRECTORY | O_NOFOLLOW` as before, and its type and the data-directory rule are checked again through that handle: the folder's real place is found by `..` from the handle (`fstatat(fd, "../../…")`, device and inode, at most 1,024 levels), never from a path. The data directory is opened and walked the same way; if it can't be opened, the path check alone decides, as it did. A walk that fails is `unreadable`. The listing (`Dir::read_from(fd)`), each entry's type and shape (`fstatat(fd, name, AT_SYMLINK_NOFOLLOW)`) and the `added/` and `failed/` checks and creation now go through the handle too; reads, renames and removals already did. Why: a check made through the handle is about the folder that's read, whatever the path names later.
- **Windows: identity re-checks, since there are no handle-relative calls without `unsafe`.** The folder is still held open without delete sharing, so it can't be renamed or deleted during the poll. After it's held, the path checks run again and the path must still name the held folder by volume serial and file index (`same-file`, already a dependency). That's checked again:
  - after `added\` and `failed\` are held;
  - after each listing;
  - before each read opens the file, after it's opened and after it's read;
  - before each move and each removal.

  On a mismatch, a read leaves the file for a later poll (`wait`). A listing, move or removal stops the poll as `unreadable`, and the file stays where it is. **What's left on Windows:** each check looks at the path at one moment, so a parent junction pointed elsewhere and then pointed back around a path-based call (an open, a link, a removal) isn't detected. The checks just before and after the call both pass. The check made just before each call narrows the window to that call alone. Closing it needs handle-relative calls, which Windows has only through `unsafe`. Only a folder layout the operator made allows it, and the operator sets the path (the finding is low).
- **The start check opens the folder as a poll does.** When the watch is applied, the folder is checked by opening it, not by its path alone. Otherwise an aliased mount (above) would log `watch.started` and then `watch.disabled reason=inside_data_dir` on the first poll. `added/` and `failed/` are made at that point rather than on the first poll, a few seconds later.
- **The `..` walk stats `../`, `../../` and so on from the handle; it doesn't open each parent.** Opening `..` for reading needs read permission on every parent, which a folder Lodestar can only pass through (mode `711`) doesn't give, and `O_PATH` is Linux-only. A folder moved while it's walked can give a chain that mixes before and after. The walk then describes where it is now or was a moment ago, and the poll after checks it again.
- **Parent links are still followed, as before.** The rule is unchanged: only the folder's own entry, `added/`, `failed/` and the files can't be links. A parent swapped for a link after the open changes nothing for that poll. The next poll opens the path again and follows it.
- **Where the race tests live.** `Folder` is private, and the binary opens the folder again on every poll, so the swap tests are unit tests in `src/watch.rs` (Unix and Windows). `Folder::open_with` calls a test hook between the path check and the open, and between the open and the checks after it. A test swaps the folder or a parent there and shows that the later check refuses it. `tests/watch.rs` adds a served-binary test: a folder swapped for a file and then for a link is refused with each reason, and the other folder is never read or written.
