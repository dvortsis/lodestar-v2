# B-update decisions, part 5a: installing

Ported on 2026-11-01 (B-update-5) from the paused old-lineage branch onto `main` after F-updater (#198, `2026-10-30-F-updater.md`); written 2026-10-24 as `B-update-r5a`, carried forward here with the port's changes in the last sections. Part 5a makes the update engine install (architecture §12.2 "Downloading" and "Installing"). It builds on part 4's engine (`2026-10-23-B-update-r4.md`). Roll back from the API, the binary-level fake-source test and "trust survives a rollback" are part 5b. The code is in `crates/lodestar/src/update/{download,install,engine}.rs` and `crates/api/src/{updates.rs,dto/updates.rs}`.

## The download
- **Where from:** the pin's URL, then each redirect through the check's allowlist (`https`, the default port, no credentials, `github.com`, `objects.githubusercontent.com` or `release-assets.githubusercontent.com`), at most 5. A 404 is an error here, unlike the check's first hop. The request is the check's: `User-Agent: Lodestar-Updater` and nothing that identifies the installation.
- **Where to:** `<data>/bin/<version>.part`, created new (`O_NOFOLLOW`, 0600), so a planted file or link is refused, never written through.
- **Checks as it goes:** bytes are counted (one past the pinned size stops it) and hashed. After fsync, the SHA-256 and size must be the pin's. Anything else removes the file.
- **Stale `.part` files** are removed when the next download starts. One download at a time, under the one-check lock, and no resume.
- **Timeout:** 30 minutes for the whole download (256 MiB at about 1 MB/s). The guarded client keeps its public-address policy.

## Staging
- **`<version>.tmp/`** gets the binary (moved from the verified `.part`, 0700), plus `manifest.json` and `manifest.json.minisig` as fetched. Each file is fsynced, then the folder; it's renamed to `<version>/`, and `<data>/bin` is fsynced.
- **An overlay is inert until the supervisor names it in `active`,** so a crash leaves at most a `.tmp` folder, which the next stage replaces.

## The install pipeline
- **One task, holding the one-check lock** (a manual check meanwhile is `429`, and a second Install now is `409 install_unavailable` with reason `busy`). The steps:
  1. The policy's Install now rules again (a queued version may have been skipped since).
  2. Nothing else in the way: a rebuild under way is `rebuild_running`. An import can't run while `serve` holds the store, so there's no import probe.
  3. The last check's envelope verified again against the trust state and the clock now (a damaged `trust.json` is `trust_damaged`, an expired manifest `not_current`).
  4. The pin for this build's target.
  5. Room on `<data>/bin`'s disk: the binary, the release's `reindex_bytes`, the store's size when it migrates (its snapshot), and 64 MiB. Otherwise `no_space`.
  6. The download, then staging.
  7. The staged folder verified as the supervisor will (`overlay::verify`: the signature against the embedded keys, the binary's hash and size). A failure removes it (`bad_overlay`).
  8. The envelope verified once more (§12.2 "At install time").
  9. The switch intent and the graceful shutdown (`Restart::global().request()`), which `main.rs` turns into `request.json` and `EXIT_SWITCH`. The supervisor then verifies again, writes `pending` and `active`, and starts the new version.
- **A failure** publishes `failed` with its code and logs `update.install_failed` (a static code, never a URL). The running version carries on. An automatic install that failed isn't tried again until the next check.
- **Capability:** `not_built_yet` is gone. `can_install` is true when no reason applies.
- **`dev_build`** comes from `Context::dev`, set in `start()` from the build channel, so tests can install.

## `POST /updates/install {version, when, confirm_manual}`
- **`when: "now"`** starts the install and answers `202` at once; progress is on the `updates` topic. **`when: "window"`** queues it in `updater.json` (`queued`); the schedule installs it at the window's next opening, skipping the wait, and answers `202`.
- **Refusals:**
  - `404 unknown_version`;
  - `409 version_skipped`;
  - `409 install_unavailable`, its reason a stable code: a capability reason, `not_candidate`, `not_current`, `upgrade_path` or `busy`;
  - `422 manual_confirmation_required`, for a release with manual steps without `confirm_manual: true` (§2.19, the B17 pattern).
- **`GET /updates`** gains `installing: {version, when} | null`: the install under way, else the one queued.

## Automatic installs
- **The schedule wakes** for the next check, a queued install at the window, or the policy's next automatic install (`Plan::next`, at its `installs_at`), whichever comes first. A queued version comes before the policy's.
- **Every automatic install waits for the window** (§2.13), security fixes included; Install now doesn't.

## Events (`updates` topic)
- **An install:**
  - `waiting_window` (queued);
  - `downloading` with `bytes_done`/`bytes_total`, at most once a second, plus the first and the last;
  - `verifying`, `installing`, `restarting`;
  - or `failed` with the code.
- **After the switch:** the new version publishes `checking_health` at start while its `pending` names it, then `done` when its self-test passes.
- **After a rollback:** the restored version publishes `rolled_back` once for the newest history entry, remembered in `updater.json` (`rolled_back_seen`).

## History
- **When probation passes,** the new version appends `installed` (from `pending`'s previous version) before removing `pending`. A restored version's entry is the rollback journal's.

## Logging
- One new catalogue event: `update.install_failed` (`Warn`, its `error` a stable code).

## Changes on the port, against F-updater (DUR-26)
- **Install writes go through F-updater's acknowledged writer.** `queued` and `rolled_back_seen` are `updater.json` fields, so they're written with `Engine::write_updater` under the updater mutex (temporary file, fsync, rename, folder fsync), off the async workers. **Queuing (`when: "window"`) is acknowledged only once durable:** a failed write is `500 updates_not_saved`, nothing is queued, and the old file stays. Clearing the queue after an install and recording `rolled_back_seen` are best effort: one left queued is held back (next point) and refused as `not_candidate` once that version runs; an unsaved `rolled_back_seen` announces `rolled_back` again at the next start.
- **An unreadable `updater.json` is never written over by an install** (F-updater: only a saved pause or resume replaces it). Queuing is then `409 install_unavailable` with reason `updater_unreadable`; Install now still works (it writes nothing there). The `rolled_back_seen` mark isn't saved.
- **The hold.** Automatic installs come from `policy::plan`, which carries F-updater's `held_in_process` (`Block::Held`), so a failed pause holds them in this process too. Install now and a version queued by hand aren't automatic and, like a durable pause, the hold doesn't apply to them (§12.2: Install now skips the window, wait, level and pause).
- **No retry loop.** The engine remembers the version of the last install, failed *or* switching, and the schedule doesn't start it again (queued or automatic) until the next check. Before, only a failure was remembered, and a queued version that failed wasn't, so a queue that couldn't be cleared could retry at once.
- **Staging refuses a version that isn't an overlay name** (`layout::parse_version`: canonical, no build metadata), so a folder name is never a path. `install::stage_with` takes a step hook; a test crashes it before each of its seven steps and checks that nothing is ever active and that staging again finishes it.
- **`installing` in `GET /updates`** is always sent but not `required` in the schema yet, so the Updates screen's fixtures (S-updates, in flight) type-check; S-updates can make it required when it wires Install now.
- **Log event `update.install_failed`** is `Warn` and is labelled in the Logs settings' messages (`web/src/lib/features/settings/logging/`), which the catalogue test requires of every event; outside this slice's files, named in the PR.
