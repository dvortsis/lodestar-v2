# ENR-steam: Steam app list, streamed parser, local name match, plugin

Slice ENR-steam (architecture §18.2, §18.7). Choices the spec leaves open,
made by the slice session on 2026-11-16Z for the runner to confirm.

## No title leaves the install (owner rule)
- The plugin fetches Steam's whole list of games, page by page, folds each
  page into a local index (folded name to app ids) and drops the page. Every
  `lookup` is answered from the index. A request holds fixed parameters and
  the paging cursor (`last_appid`, a Steam app id from the previous page)
  only.
- `tests/steam.rs` shows five lookups make one list fetch (two pages) and no
  request URL or body holds any word of any title.
- The list is fetched again at most once per 24 h (`REFRESH`). A failed fetch
  keeps the old index and waits 1 h (`RETRY`) before the next try; with no
  index yet the lookup is an error (never cached as a miss). One lookup
  refreshes (a `tokio::sync::Mutex` held for the refresh only); the index
  itself sits behind a short `std::sync::Mutex` never held across a request.
  While a refresh runs, other lookups answer from the old index, or, with
  none yet, wait for the one fetch.
- A refresh can outlast the identify runtime's lookup timeout, which drops
  the lookup's future. The cursor and the names folded so far stay in the
  index, so the next refresh resumes at the cursor rather than at page 1.
  `retry_at` is set before each request and cleared once its page is
  folded: a lookup cancelled mid-request waits `CANCELLED` (a minute); one
  cancelled between pages resumes at once. A real error replaces that wait
  with `RETRY` (an hour) and drops the partial list. A partial list started
  more than `REFRESH` ago is dropped rather than resumed. A missing or bad
  key fails at once with no wait, since nothing was sent. Moving
  the refresh out of the lookup path into a task the plugin owns is left to
  the runner (the identify runtime has no hook for plugin-owned tasks yet).
- The match carries no year: the list has none, so the item's own year
  isn't echoed back as if Steam had confirmed it.
- Matching: titles compared folded (lower case, letters and digits, runs of
  anything else one space), the same fold as Wikidata. Exactly one app with
  the name is a match (id scheme `steam`, the app id); two or more is no
  match. The list has no years, so confidence is 70.

## Which API
`ISteamApps/GetAppList/v2` (keyless) has been retired by Valve in favour of
`IStoreService/GetAppList/v1`, which needs a Steam Web API key and pages with
`last_appid` / `max_results` (up to 50,000). The plugin uses the latter with
`include_games=true` and every other type off (kinds: games only) and
`max_results=10000`.

- **Account class**, off by default. One declared credential, `api_key`
  (Secret, required), read from the per-source store on each refresh, never
  from config. A key that isn't 32 hex digits is refused before anything is
  sent.
- **Key in a query string is a risk** (URL logs, proxies). The key is sent in
  the `x-webapi-key` header, never in the URL (that Valve accepts the header
  is from the slice's knowledge, not checked against current docs; a refusal
  reads "Steam refused the Web API key" and leaks nothing);
  a test checks the URL never holds it. Errors carry fixed text only.
  If Valve stops accepting the header, the fallback (a `key=` parameter) must
  not be added without redacting the egress URL log first.

## Bounds (untrusted input)
- Per page: 4 MiB, depth 8, 200,000 JSON values, 12,000 apps, name at most
  256 bytes, trimmed, no control characters; a bad app is skipped and counted.
  Only a whole page (`Page::whole`) is used; a cut-short page fails the
  refresh.
- Per refresh: at most 60 pages, 300,000 apps and 32 MiB of bodies. Names
  are kept twice (folded, up to 1.5 times longer, and as written) with about
  100 B of map overhead per app, so one index is at most about 110 MiB, and
  the peak during a refresh (old index plus the partial one) about 250 MiB,
  inside the §3 RSS budget. The cursor must move
  forward or the refresh fails (no endless paging). The index of ~200,000
  games is a few tens of MiB at most.
- Parsing runs on the blocking pool. Property tests over arbitrary bytes and
  mutated seeds (`crates/sources-feeds/tests/steam.rs`) and the fuzz target
  `fuzz/fuzz_targets/steam.rs` check no panics and the caps.

## Pacing
One request a second per host, no burst; back-off a minute up to 6 hours after
a 401/403/429/5xx. A refresh is about 20 pages a day, far below Valve's
100,000 calls a day.

## Terms (owner §2.28; Steam Web API Terms of Use)
These values come from the slice's knowledge of the terms; they weren't
re-read live in this slice. **Before the plugin is switched on,** the slice
that does it re-reads them and adjusts `steam::TERMS` (and the 100,000 calls
a day figure) if they changed.

- `background_walk: true`: the whole list is fetched regardless of items;
  nothing per item is sent.
- `redistribute: false`: Steam data is used inside Lodestar only.
- `retention: Retention::DEFAULT`.
- `attribution`: "Data from Steam", <https://store.steampowered.com>; the
  terms forbid implying Valve's endorsement, and the credit names the source
  only. Constants `SENDS`, `ATTRIBUTION`, `ATTRIBUTION_URL` are there for the
  Sources row; `Manifest` has no field for them yet (for the runner).
- `adult_marker_required: false`: the list carries no adult marker. The
  runtime never asks about items Lodestar has already marked Adult, but
  Steam does list adult-only games, so an unmarked item can still match
  one: matches may include such titles (allowed by the ENR-terms opt-out).
