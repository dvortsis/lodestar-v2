# CMP-11 decisions

qBittorrent on Windows as a guided install, then detection and configuration (owner cq4: `docs/owner-decisions.md` §1.7.2's one exception; plan `docs/plan/2026-11-06-v06-companions.md` CMP-11, Q4; architecture §18.10). These are the slice's decisions under §2.33. None loosens an owner decision or a security decision. The runner flags the refinements marked **(refinement)** to the owner (§2.19).

## Lodestar never downloads or runs the installer
- **The owner's answer is stricter than the plan's Q4 (a) draft.** The draft had Lodestar verify the pinned installer and offer it through your browser. Under cq4 as briefed, Lodestar fetches nothing: it shows qBittorrent's own page (`https://www.qbittorrent.org/download`), the pinned version and its SHA-256, and the steps. You download, check and run it yourself.
- **How that holds in code:**
  - The catalogue's Windows artifact is `"archive": "installer"`. CMP-5's manager already refuses an installer (`guided_only`) before any fetch, and `tests/manager.rs` covers that refusal on a Windows host.
  - `windows_qbittorrent` holds no HTTP client for a download and builds no command line. Its `Guide` shows only `DOWNLOAD_PAGE`, never the pin's own URL.
  - No SourceForge or FossHub host is added to the entry's fetch `hosts` (runner, 2026-11-11).

## The catalogue entry
- **`{"platform": "windows", "arch": "x86_64", "archive": "installer", "executable": null, "pin": null}`** on the qBittorrent entry, awaiting its pin like every other artifact.
- **The format can't hold this pin yet.** A native block has one `release` folder (the userdocs GitHub folder) and every pin URL must sit inside it, on the entry's fetch hosts. The official installer isn't on GitHub. A per-artifact release folder for installers, kept off the fetch hosts, goes to **CMP-13**, which owns the pin tool and the catalogue format (runner, 2026-11-11).
- **`tests/catalogue.rs`:** the builtin check now expects the Windows installer (no executable, awaiting its pin) beside the Linux binaries.

## The guide (`Guide`, `Step`)
- **Six steps, each with a stable code** for the UI's own messages (`download`, `check_sha256`, `install`, `turn_on_webui`, `set_password`, `connect`), and English text filled from the catalogue:
  1. download from the official page;
  2. check the SHA-256 with PowerShell's `Get-FileHash`, and delete the file if it doesn't match;
  3. run the installer (its administrator prompt is the installer's, not Lodestar's);
  4. turn on the WebUI bound to `127.0.0.1` on the catalogue's `webui` port (8080);
  5. set a user name and password, leaving "Bypass authentication for clients on localhost" off;
  6. find it in Lodestar and paste the password once.
- **Unpinned, no checksum is shown or claimed** (runner, 2026-11-11). There's no version and no `check_sha256` step, and the download step points to the official page alone.
- **Detection is CMP-8a's,** unchanged: loopback `8080` is already one of the fixed probes (Q12). The address shown is `http://localhost:8080`.

## The version gate (`WindowsQBittorrent`)
- **Registered for qBittorrent on Windows** in `configure::configurator` (`cfg(windows)`), wrapping CMP-8b's adapter. Every configuration then passes it: the guided path's plan and apply, and anything later.
- **(refinement) The pin's range is the pinned version and later patch releases of the same `major.minor`.** `5.0.3` accepts `5.0.3` to `5.0.x`. It refuses `5.0.2` (it may lack the pin's fixes) and `5.1.0` (Lodestar hasn't checked CMP-8b's adapter against it). An exact match would refuse every patch update you install. The bounds come from the pin's version, never its checksum.
- **Checked signed in, before anything is written.** The version endpoint answers only with a session, so the gate signs in through CMP-8b's own sign-in (`signed_in_version`, a `pub(crate)` addition to `configure/qbittorrent.rs`, approved by the runner). The plan runs CMP-8b's plan first, so a wrong password still costs one refused sign-in, then the gate. The apply checks again before the first write, so a qBittorrent updated between the plan and the apply is caught.
- **It fails closed:**
  - `awaiting_pin` while the installer is unpinned;
  - `qbittorrent_version_unsupported` outside the range;
  - `Protocol("version")` for an answer outside the version grammar.
- **The plain message** (`WindowsQBittorrent::explain`, `Unsupported`'s `Display`) names the version found and the pinned one, both Lodestar's own parsed `Version`s. It says to install the pinned version from the official page, or to wait for an update. Nothing qBittorrent sent is shown. Wiring the text to the API's refusal message is the screen's (CMP-9b) or CMP-11b's; the code is stable now.

## Windows save paths (`WindowsPath`, `SavePath`)
- **`Downloads` takes a `SavePath`:** CMP-0's `HostPath` as before, or a `WindowsPath` for this qBittorrent. `Downloads::new` takes either (`impl Into<SavePath>`). This is the only change to CMP-8b's path check.
- **Two shapes, backslashes only:**
  - a drive path, `X:\folder…`;
  - a UNC share, `\\server\share…`, where the server is a DNS name or IPv4 address.
  - A `/` anywhere is refused rather than normalised, so no mixed spelling can name another folder.
- **Each folder** is ASCII letters, digits, `-`, `_`, `.` and an inner space. It's never empty, `.` or `..`, and never ends in `.` or a space, which Windows strips (`.. ` is `..`). That set also keeps out:
  - `:` (alternate data streams);
  - `~` (8.3 names such as `PROGRA~1`);
  - `$` (`C$`, `ADMIN$`);
  - `%` (environment variables), wildcards and quotes;
  - anything outside ASCII (full-width dots, best-fit mappings).
- **Refused:**
  - `\\?\`, `\\.\` and `\??\`;
  - every relative form (`C:folder`, `\folder`, `folder`);
  - device names in any case, with an extension or spaces before it (`CON`, `PRN`, `AUX`, `NUL`, `COM0`–`9`, `LPT0`–`9`; `nul .txt` is the null device too);
  - a drive's root;
  - `Windows`, `Program Files*`, `ProgramData` (Lodestar's own data), `System Volume Information`, `Recovery`, `Boot`, `PerfLogs`, and everything below them;
  - `Users` and `Users\<name>` themselves, and a profile's `AppData` and dot folders.
  - At most 247 bytes: `CreateDirectoryW`'s limit without `\\?\`.
- **(refinement) With a Windows save path, a category has no path of its own** (`NotAbsolute`). Categories' paths are `HostPath`s, which mean nothing on Windows. qBittorrent then saves a category in a folder of its name under the save path. A Windows path per category can follow if the screen needs one.
- **Compared as Windows does:** qBittorrent may report `C:/Users/me/Downloads/`. A Windows save path is compared without case, with either separator and without a trailing one, so an unchanged folder isn't rewritten. It's written as given, in backslashes.

## The hand-over and the credential
- **The hand-over is the guided path's own** (CMP-5g, X-cmp-native-handover): after the apply, `configure::hand_over` writes the `lodestar-qbittorrent` entry through the sink, which seals the password. Nothing new is needed for Windows, and the test runs it end to end through the gate.
- **The password you paste** reaches the gate only as a `Secret` in `ConfigureInput`, and goes out only in CMP-8b's sign-in form body (and, for the generated one, the single password write). It's never in a URL, a header, an error, a log line or `Debug`. `WindowsQBittorrent`'s `Debug` shows the companion id alone.

## Tests (`crates/companions/tests/windows_qbittorrent.rs`, the module's unit tests)
- **The catalogue and the guide:**
  - the builtin installer awaits its pin, and its guide claims no checksum;
  - a pinned test catalogue shows the version, file and SHA-256, and only the official page.
- **The gate, over an in-process fake qBittorrent 5.0** (no sockets or timers):
  - a supported version is configured and handed over with the generated password;
  - older and newer versions are refused before any write, and their messages name both versions;
  - a version changed between the plan and the apply is refused at the apply;
  - unpinned and unreadable versions are refused;
  - a wrong password costs one sign-in;
  - on Windows, `configure::configurator` is the gate.
- **The password** isn't in a log line (the hand-over event is, so the check isn't vacuous), a path, a header or `Debug`. It's only in the sign-in and password-write bodies.
- **Hostile paths:** traversal, trailing dots and spaces, `\\?\`, `\\.\`, `\??\`, device names, forward and mixed separators, relative forms, streams, short names, admin shares, variables, wildcards, Unicode, NUL, IPv6 servers, roots, system and profile folders, and the length limit. A Windows save path is compared and written as Windows does.
- **Not here:** CMP-5g's guided tests in `crates/lodestar` run on Windows too. Their fake answers the version only without a session, and the builtin catalogue is unpinned, so with the gate registered they need a version answer and a Windows-pinned test catalogue. The runner approved that edit once #692 merges; until then this PR doesn't touch that file.
