# ENR-2b decisions (ThePornDB response parser)

Slice ENR-2b of `docs/plan/2026-11-04-v06-rulepacks.md`. It covers architecture §20.9 (adult enrichment from ThePornDB: studios, performers, scene ids, release dates) and the bounded-parser bar of §18.9. The parser feeds ENR-4 (the ThePornDB plugin). It holds to the safety rules SRC-6 and SRC-9 set (`2026-11-01-SRC-6.md`, `2026-11-02-SRC-9.md`) and reads JSON with ENR-2a's shared reader, `crates/sources-feeds/src/json.rs`, which it uses unchanged.

- **`tpdb::parse_each(body, &Limits, emit)`** is a pure function from bytes to matches, in `crates/sources-feeds/src/tpdb.rs`. It returns a `Page`: kept, `Skipped` by reason, the `Stop` reason and a search page's `meta.total`. `tpdb::parse` collects the matches with the default caps. No I/O; ENR-4 fetches.
- **Two shapes, matched by the root's `data` key**, so one call parses whichever endpoint the plugin asked:
  - a search page (`/scenes`, `/movies`, `/jav`): `data` is an array of items, `meta.total` the count;
  - a lookup (`/scenes/{id}`, `/scenes/hash/{hash}`, `/movies/{id}`): `data` is one item.
  - A miss (`{"data": []}`, `{"data": null}`, or an error object such as `{"message": …}`) gives no match and no stop. ENR-4 reads the HTTP status for errors; the message text is the service's and isn't kept.
  - The first `data` and `meta.total` win; repeats are skipped, as SRC-9's fields are.
- **No `serde_json`, no new dependency** (plan, "New dependencies"). Every cap holds while reading.
- **Errors stop the read, always** (#422's review). `json`'s `Stop` doesn't latch: after an `Err` the cursor sits mid-token. Every read in `tpdb.rs` propagates its `Err` with `?`; nothing swallows one. `a_mid_value_error_stops_the_parse` checks that a broken literal, number, escape, trailing comma, missing colon or cut string mid-item stops the parse there: earlier items are kept, the broken item and everything after it are not. `null` and booleans are read as `peek` then `skip`.
- **Fields kept: only what the enrichment claims can store** (plan ENR-0, §20.9):
  - **kind** from `type`: `Scene`, `Movie` or `JAV` (ASCII case aside), else `None`. **The service has no VR type or flag**; VR appears only as a tag, and tags aren't read. The classifier's own VR words (§20.9, as built) still decide `adult_kind`. JAV is its own kind rather than folded into Scene, so ENR-0 or ENR-1 can decide how to store it with nothing lost.
  - **id**: the item's `id`, a string of 1–64 ASCII letters, digits and `-` (the service's UUIDs are 36 bytes) or a non-negative integer up to 20 digits, kept as its digits. `_id` is ignored. Missing skips the item (`no_id`); present but not valid, `null` included, skips it (`bad_id`). The id is the only way to link a match back, so an item without one is useless.
  - **title**: trimmed, hidden characters removed, cut to `MAX_TITLE` (1,024 B) on a character boundary, as every feed title is. Empty is `None`.
  - **studio**: `site.name`, trimmed and cleaned the same way. Over `MAX_NAME` (256 B) it's dropped, not cut. `site.network` and `site.parent` aren't read: a network isn't the studio.
  - **release date**: `date` kept as written when it's exactly `YYYY-MM-DD` and a real calendar date (years 1–9999). Anything else is `None`. It stays a string so ENR-0 picks the encoding.
  - **performers**: each entry's top-level `id` (same rule as the item's) and `name` (cleaned, ≤ `MAX_NAME`, dropped rather than cut: a cut name may be someone else's). An entry missing either, or not an object, is dropped and the list marked `truncated`. `parent` isn't read, even its name: it's the service's canonical record, which carries the personal fields.
- **Performers come back beside the match, not inside it** (plan Q4 is open). `Found { matched, performers }`: a caller that mustn't keep them takes `found.without_performers()`, or sets `max_performers: 0` and the parser never decodes a name.
- **No personal fields, ever** (plan Q5). Everything not listed above is passed over with `skip`, which scans without decoding or copying: descriptions, images, URLs, tags, hashes, markers, directors, and every performer's `bio`, `extra`/`extras` (birthdays, birthplaces, measurements, ethnicity, aliases and the like), images and `parent`. `no_personal_fields` runs every fixture, each carrying such fields as `SENTINEL-…` values and a birth date, and asserts none appears in the output. ENR-4 requests nothing extra either way; the parser simply can't return those fields.
- **Caps.** As in SRC-6 and SRC-9, structural caps stop the parse with a `Stop` reason and keep the finished matches; field caps skip the one item and count it. A half-read item is never used.

  | Cap | Default | Over it | Why this value |
  |---|---|---|---|
  | `max_bytes` | 8 MiB | stop (`Bytes`); the prefix is parsed | A 25-item search page with performers is about 100–300 KiB, a 100-item page under 2 MiB. Half the `Fetch` contract's 16 MiB body, since enrichment answers are much smaller than feeds |
  | `max_depth` | 16 | stop (`Depth`) | SRC-6's. The deepest path is about 8 (`root > data > item > performers > performer > parent > extras > links`); the parser reads to 5 |
  | `max_values` | 500,000 | stop (`Elements`) | JSON values, containers included. A dense 100-item page is well under 100,000; 8 MiB of `0,` is 4 M |
  | `max_items` | 500 | stop (`Items`) | Items in `data`, kept or skipped. The service pages at 25 by default and ENR-4 asks for far fewer |
  | `max_array` | 10,000 elements | skip the item | Any array inside an item, `performers` included. SRC-9's value; real tag, hash and performer lists have dozens |
  | `max_text` | 64 KiB raw | skip the item | SRC-6's. Only strings the parser decodes are measured; a long description is skipped unread |
  | `max_performers` | 64 | keep the first ones, set `truncated` | No real scene has close to this many; a movie compilation might. 0 reads none |

  Per-field limits: `MAX_ID` 64 B, `MAX_NAME` 256 B, `MAX_TITLE` 1,024 B. ENR-0 may set its own `MAX_*`; these are no larger than any reasonable choice, and ENR-0 can only narrow them.
- **Fixtures are synthetic, from public docs** (`crates/sources-feeds/tests/fixtures/tpdb/`, with a README saying so). This session had no account, API key or network route to the service, so the answers follow ThePornDB's public API documentation and schema examples, with made-up names (`Example Performer One`), nil-style UUIDs and `*.example` URLs. **Recording real fixtures, with keys scrubbed, moves to the plugin slice, ENR-4** (and ENR-5 for StashDB). If a real answer differs from the documented shape, ENR-4 adds it as a fixture and fixes the parser in the same PR. This narrows the plan's ENR-2b gate ("golden fixtures recorded from each service") as the runner's brief directed.
- **Tests** (`crates/sources-feeds/tests/tpdb.rs`): goldens on the five fixtures; each cap at its exact value and one under (bytes, depth, values, items, array, text for every decoded field, performers); the mid-value error rule; field rules (first value wins, wrong types, invalid ids and dates, hidden-character names, BOM, non-UTF-8); property tests that arbitrary bytes and JSON fragments never panic or break a cap, and that generated items are read back exactly while spoiled ones (a lone surrogate, an over-long array or string after the kept fields, a bad id) leave no trace of their title, studio, performers or id; and the fuzz target's checks over 100,000 mutated fixtures.
- **Fuzz target `fuzz/fuzz_targets/tpdb.rs`**, seeded from `fuzz/seeds/tpdb/` (the fixtures). The first byte picks tight caps, as `archive_org`'s does. It ran 10 minutes clean locally (PR description has the numbers).
