# ENR-1 decisions (adult enrichment runtime)

Slice ENR-1 (runner brief, 2026-11-05T06:05Z). Spec: plan `docs/plan/2026-11-04-v06-rulepacks.md` (the ENR-1 bullet; Q2, Q3, Q11, Q13, Q15), owner decisions (rule-pack Q2 and Q3), architecture §18.1, §18.7, §20.5, §20.9, and `2026-11-05-X-source-adult.md` (the always-adult mask).

- **The plugin contract** (`crates/sources/src/enrich.rs`). An enrichment service implements `AdultEnricher`: its manifest and policy, the form it wants (`QueryForm::Name` or `Parsed`), and `lookup(kit, query)`. A `Query` is the only thing a plugin is ever given about an item, and it can hold only the display name or the parser's site, date and title. It has no field for an info hash, files, trackers or anything about the install, so the "never sent" list (Q2) is the type's shape, not a convention. Its `Debug` prints lengths only. The parser has no `site` field today; `Parsed` reads one if a later parser adds it, and otherwise sends the title and date.
- **The runtime runs as a source of its own** (`AdultEnrichSource`, `crates/pipeline/src/adult_enrich.rs`, a `SourcePlugin`). The pipeline registers, enables, stops and purges it like any other source, and gives it its kit (the client behind its egress and kill switch, and its `source_state`) and its emitter under its own source id. So enabling it needs its Account credentials (SRC-4), and a purge removes its claims (§18.1), with no new path.
- **One gate, `adult_enrich::check`, before every lookup**, user interest or background, right before the plugin is called. It reads every fact now and decides through `eligible`:
  - **Eligible:** "Show adult content" on (Q11); the plugin's kill switch not tripped (SRC-5); its source enabled; its consent condition met (`consent::need_in`); a stored torrent (an unverified item's id isn't one); classified Adult in the store, or found by an always-adult source through `AdultSources` alone, unless you said Not adult.
  - **Never:** a swarm hash tombstoned or quarantined (`held_among`) or on the floor's or a dropping list (`blocked_hash`); the `HIDDEN` flag; a drop, quarantine or hide verdict from the filter **as it is now**, judged on both readings as `source_adult::judge` does, so a rule added since the item was stored can't be outrun by the refile; a `private_source` key.
  - **Stricter than the plan (runner's call, §2.19):**
    - A BEP 27 private torrent (`flags::PRIVATE`) is never looked up either. Its name comes from a private tracker's swarm, and Q2's spirit is that private content never leaves.
    - A partial import (`FILES_PARTIAL`, from another indexer's database) doesn't count as verified, so it isn't looked up until its metadata has been fetched and hashed. A full `.torrent` import is verified: its info dict hashes to the key.
  - **A torrent marked to be classified again** (a rules change or a newer parser, `parser_ver` outdated) waits until the backfill has redone it, since its stored type may be stale: after a new Not adult rule it would otherwise still be sent.
  - The plugin-wide conditions are read first; while one fails, nothing is read about the item. The `content-type:adult` claim is never read, as X-source-adult requires.
- **Never a file name** (Q2). The name form sends the torrent's own name. The parsed form parses the torrent's name alone, never with its files: when a name says nothing useful, the classifier takes the title from the largest file or the top folder, and that title must not leave. A name the parser can't use (ambiguous, or resolved from the files) sends nothing (`NoQuery`) (#480 review).
- **What is sent and when** (Q15). User interest (`Interest::opened`, for the detail drawer; a bounded queue of 64) goes first and doesn't count against the daily cap. The background backfill pages stored torrents by id, at most 5,000 lookups a UTC day, with a cursor and the day's count in `source_state`. Every lookup is at least 1 s after the last, and the source's policy holds the per-host rate to one request a second with no burst (`adult_enrich::capped`), so a lookup that makes several requests is still within Q15. A background page reads up to 1,024 stored ids and keeps only those stored as adult or found by an always-adult source; a page with none waits 50 ms before the next, so a round over a large store is a light, steady load. A round rests a day before it starts over.
  - **No item loses its place.** When the day's budget is spent, or a plugin-wide condition fails (Show adult content off, the kill switch, the source off, no consent), the item goes back to the front of the queue and the runtime waits. The cursor saved in `source_state` is the last id dealt with, never past one still queued.
- **Caches** (Q15) live in the plugin's `source_state`: 128 bucket keys under `enr1/` (an eighth of a plugin's 1,024 keys), each holding up to 4,096 `(torrent id, expires)` entries, so about half a million. A hit lasts 30 days and a miss 7. A full bucket drops what expires soonest. A lost or unreadable bucket only means an item is asked again, which the caps bound. `StoreState` is the `source_state`-backed `PluginState` the host gives the kit; it runs each call off the async threads. The plugin is handed the same client but a state that refuses every key under `enr1/`, so it can't reset the caps or caches.
- **Results go through SRC-2's filter-before-storage path.** A match is emitted as claims (the ENR-0 section only) on the torrent's key under the plugin's source id, so it reaches the writer's `unverified::ingest` like every claim. The key never leaves the install: it's only how the writer finds the torrent. A section the claims limits can't keep counts as a failure, never as an empty discovery (which intake would read as a sighting).
  - **`ingest`** keeps a section only for a key that's a stored torrent, never through a private source. It stores it with `put_claims` on the torrent, not as an unverified item and not as a sighting: the source didn't find the key, the runtime asked about it. So it isn't counted as a rediscovery and doesn't set the source's bit on the torrent.
  - **`unverified::judge_in` judges the section's text (Q3), stricter only:** the title, the studio, each performer and the scene id (its `-`s read as spaces, since a slug can carry the title), each alone and all together, and the torrent's verified name with each of them and with all of them. Each is judged as adult, since only Adult items are looked up, so the Adult-only core's thresholds apply. The texts are extra items: a hit adds a hold and nothing can cancel one. They're never a counter-signal, because no exception or rule judging the torrent's own name ever sees them. A core hit holds every swarm hash and deletes the torrent, as for any claim (SRC-2). Any other rule drops the source's claims and holds nothing (#383). `store_claims` now carries the section into the store.
  - **The refile sweep** (`refile_step`, Claims phase) judges stored enrichment claims the same way, with the torrent's name, whenever the engine changes.
  - **A section from another plugin** would be judged and kept the same way. Plugins are compiled in, and a section can only add a hold or pin a kind on an item that's already adult. Accepting sections only from sources whose manifest has `Kind::Enrichment` needs a field in `unverified::Ctx` that the writer fills, so it's a runner follow-up (`writer.rs`).
- **A match pins the adult kind** (`enrich::apply_matches`, ENR-6's `classify_enriched`, Q13). Right after the claims are stored, `ingest` classifies the torrent again with its stored match. Only a torrent stored as adult is classified there, so nothing becomes adult and nothing needs judging or holding in that write. Any other is marked for the backfill, which judges and holds as usual. The backfill (`enrich_ids`) reads the stored match too, so a newer parser keeps the kind. A match never makes an item adult, never un-adults one, and filtering never judges the matched result (§20.7). The correction, rule or always-adult source that made it adult keeps its confidence of 100; otherwise detection's, with the match at 99. A section without a kind pins nothing. When more than one source matched, the first by source id wins.
- **Cancellation.** A lookup in progress races the source's shutdown and is dropped when it fires, and the run ends. Waiting for room in the emitter does the same.
- **What isn't done here, and why:**
  - **For ENR-7:** rate-limit `Interest::opened` at the API. The queue is bounded (64) and every lookup is paced, but user-interest lookups don't count against the daily cap, so a script opening drawers could keep the service busy.
  - **Host wiring.** Nothing builds an `AdultEnrichSource` yet. ENR-4 and ENR-5 add the plugins; the host (owned by SRC-13b now) builds the source with its own store connection, the live filter, the always-adult mask, `Switches` (the `content.show_adult` watch and the plugin's `EgressLive` route state) and a `StoreState` kit, and hands `Interest` to the detail API (ENR-7).
  - **`worker.rs` is unchanged.** Prepare classifies a fresh fetch, and a fresh fetch has no stored claims to read: a lookup needs a stored torrent. The exception is a partial import's upgrade, where the commit writes prepare's record at the current enrichment version. The backfill doesn't pick that row up again, so the kind pin is lost until a parser or rules change. The fix is one line in `writer.rs` (mark a refetched row with an adult claim for enrichment), which this slice may not edit. It's a runner follow-up.
  - **Deferred matches wait for the next backfill pass.** `apply_matches` marks a torrent for the backfill when it isn't stored as adult yet, or when the rules moved under the batch. The backfill runs once per start and whenever the classification rules change. Raising the writer's re-enrich flag from here needs `writer.rs`.
  - **The generation is read after the rules.** `apply_matches` runs inside `ingest`, whose engine the writer took before the batch, so a rules change landing in between can be written under the new generation with the old rules. `with_match` only writes rows that are and stay adult, so this can only keep an item adult (stricter), but its kind and junk score can be stale until the next pass. It's stricter for safety but looser for privacy: the write can clear a re-classification mark, so an item a new Not adult rule covers can keep being looked up until the next rules change. ENR-1b fixes it. Passing the generation or the `Handle` from the writer fixes it: the same runner follow-up.
  - **A match counts as harvested.** Intake (`pipeline/src/lib.rs`, outside this slice) adds `HARVESTED` for every emitted discovery, so matches are counted under strategy 202. They aren't rediscoveries and don't set the source's bit. Leaving them out of the harvest is a runner follow-up in `lib.rs`.
- **Tests** (`crates/pipeline/tests/adult_enrich.rs`, plus unit tests in `adult_enrich.rs` and `sources/src/enrich.rs`):
  - a property test over stored items and switches, run through the live runtime: the plugin gets exactly the eligible items. Items: the floor's list, hidden, a hide, drop or quarantine rule, `private_source`, BEP 27 private, a partial import, Not adult, unverified (a real item id, which shares the torrents' id sequence, so an opened drawer could send one), and adult by detection or by the always-adult mask. Switches: Show adult content, the kill switch, enabled, consent;
  - a tombstoned or quarantined swarm hash is never looked up;
  - a file name is never sent, in either form, including a vague name whose title would come from a file;
  - a torrent pending re-classification waits;
  - the parsed form with no title sends nothing;
  - a core-held item with a perfect match stays held;
  - no request carries the info hash, as hex or raw bytes;
  - the plugin stops after shutdown, waited for as a condition with a 10 s deadline;
  - the refile sweep judges enrichment claims when the rules change, for a core hit and for your rule;
  - an always-adult item is eligible once verified, and an unverified one isn't;
  - the parsed form sends only the parser's fields;
  - a match pins the kind;
  - a match for a key that isn't stored is refused;
  - the daily cap and the miss cache hold;
  - shutdown ends the run while it skips refused items;
  - the plugin can't reach the runtime's state keys;
  - the policy is held to one request a second.

  No fixed sleeps.
