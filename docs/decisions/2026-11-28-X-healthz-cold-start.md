# X-healthz-cold-start decisions

A large store answered `/healthz` only after `prepare()` had scanned every stored hash into the have-filter (about 14 s at 10M on the test VM). `serve` binds the HTTP listener once `Pipeline::start` returns (`crates/lodestar/src/services.rs`), so the scan held up `/healthz`, the UI and search. These decisions take the scan off the start. Architecture §5 (the have-filter) and §19.3 (the intake) are affected; `/healthz`'s contract is not.

- **The fill runs on a blocking thread after the start; the intake waits for it (the brief's option (a)).** `prepare()` makes the filter `Have::filling`. `Pipeline::start` then spawns the fill over its own read-only connection (`Store::open_reader`) and returns. The intake's first step is to wait for `Have::filled`, so no discovery or claim is admitted before every stored hash is in. Sources back up on the bounded channels meanwhile, as they do when the pool is busy. Why (a) rather than (b), checking each "no" against the store: (a) delays crawling by the fill itself, a few seconds at 10M (see the numbers below), and once a start, while (b) would add a store read per new key on the intake's hot path and a second code path to keep right. The runner's default.
- **While filling, the filter reads as holding every hash and as never full.** `Have::contains` answers "yes" until `mark_filled`, so no reader can take a "no" from a half-filled filter. The intake never asks then. The writer's own reads (flood counting, claim notes) treat a key as stored, which only undercounts, as a false positive already does. `Have::is_full` answers "no" until then, so the writer's `rebuild_have` can't swap a new filter in under the fill, which writes into the filter it started with (`Have::replace` debug-asserts it). A rebuild still needed runs on the first commit after the fill.
- **No hash is lost.** The fill is a single statement, so a single read snapshot. A hash committed after the snapshot began isn't in it, but the writer inserts every hash it commits, after the commit, so it's in the filter either way. Bits only get set, so the fill's inserts and the writer's mix safely (both are atomic ORs).
- **Fill inserts skip the WK-3 observer** (`Have::fill`). The workers' filter is built from the store itself. Before this slice the fill ran before an observer could be set. Now an observer set during the fill would otherwise be sent every stored hash as a delta.
- **A failed fill is tried again; the filter is never marked filled early.** A read error is logged as the new `pipeline.have_fill_failed` (Error, with its `attempts`), and the fill is tried again after 1 s, doubling to at most 60 s, until the pipeline stops. The fill holds a receiver of the intake's stop signal, which `Pipeline::shutdown` sends (and a dropped pipeline closes), and checks it before each try and every second of the wait. So a `Monitor` kept after the stop doesn't keep it trying. `pipeline.have_rebuild_failed` stays the writer's rebuild only. **The trade-off:** before this slice a store that couldn't be scanned failed the start, loudly. Now `/healthz` says `ok`, the UI and search are up, and crawling waits while the event repeats. A transient error (a locked or busy database) now recovers on its own; a lasting one (a corrupt row) is seen in the log, not as a failed start.
- **The filter is sized from the exact count, while the count is still taken.** `count(*)` stays in `prepare()` for `Monitor::torrents()` (see below), so `capacity_for(count)` is exact and costs nothing more. `Store::torrent_bound` (`max(id) - min(id) + 1`, two seeks of the rowid b-tree, so no scan) is added for X-healthz-count-async, which takes the count off the start. It's a correct upper bound: ids are distinct integers, so every row fits in the range. But it tracks the shared `id_seq` (unverified and overlay items take ids from it too) and keeps deleted rows' gaps, so it can be several times the count. That slice weighs the larger filter.
- **The workers' filter isn't built while the coordinator's fills** (`crates/lodestar/src/cluster/serve.rs`, `Stored::filled`). `have_step` sizes that build from `Have::len()`, which is partial during the fill. A worker reconnecting after a restart would otherwise get a filter at its minimum size, overfilled by the scan, and so mostly false positives. The build waits for the fill and is then sized from the whole set.
- **The `pipeline.starting` log's `stored` field is now the torrent count,** not `Have::len()` (swarm hashes), since the filter may still be filling then.
- **Remote workers wait for the fill too** (`crates/pipeline/src/remote.rs`, granted). `RemoteSink`'s `GrantAdmission::admit` grants no lease while the coordinator's filter is filling (`RemoteIntake::wait_for_fill`). A worker without a filter of its own would otherwise claim and fetch stored keys during the fill, for as long as a failing fill lasts. So "crawling waits" holds for the whole fleet.
- **A shutdown during the fill can wait for the rest of the scan,** about 5 s at 10M, as the old blocking start did. The scan is one statement, and the stop is checked before each try and during the wait between tries, not between rows.
- **An in-memory store (tests) is still filled synchronously in `prepare()`:** it has no path to open a second connection.
- **`/healthz` is unchanged.** It stays the constant `ok` it was. It now answers as soon as the listener is bound, while the fill may still be running. Nothing in `crates/api`, the Dockerfile or the user docs changes. `crates/lodestar` changes only in the cluster's worker-filter guard (below) and the new event's catalog entry.
- **`PipelineConfig::fill_gate`** (hidden, tests only) runs on the fill thread after the scan and before `mark_filled`, so a test can hold the fill and catch an early mark. `Have::waiting` counts the tasks waiting for the fill, so a test can see the intake parked on it.

## Measured (`bench/examples/cold-start.rs`)
A synthetic store of 10M torrents (one in eight hybrid, so 11.25M swarm hashes) in a cloud container. "Cold" means the OS page cache was dropped before the run, as after a reboot; "warm" means the next run.

| | Start (first `/healthz`) | Fill done (crawling starts) |
|---|---|---|
| Before, cold | 5,294 ms | the same: the start waited for it |
| Before, warm | 4,189 ms | the same |
| After, cold | 943 ms | 5,990 ms |
| After, warm | 65 ms | 4,332 ms |

At 2M: before 529–581 ms warm, after 128–153 ms warm (fill done at 708–802 ms).

- **What's left of the cold start is `count(*)`,** which still runs in `prepare()` for `Monitor::torrents()` (`stats.stored_torrents`, the `lodestar_torrents` gauge). It takes about 1,000 ms cold and 60–80 ms warm here. The id bound takes 0 ms. The test VM took about 14 s before, 3–4× this container, so the cold count there is likely 3–4 s: above the ~2 s goal, though most of the 14 s is gone.
- **Moving the count to the fill thread is deferred** (runner, 2026-11-28) to the follow-up slice X-healthz-count-async. Keeping the count exact means pinning the fill's read snapshot in `prepare()`, before the writer starts. The count would then be unknown until it lands, which changes a documented contract: `stats.stored_torrents` is "nullable: no" in `docs/metrics.md`, and the change would touch the OpenAPI type, the web schema, the UI's null handling and the gauge's reporting. That belongs in its own reviewed slice.
- **Crawling starts slightly later than the old start finished,** because the fill now shares the machine with the rest of the start. It's still one scan, as before.

For the 10M check on the test VM (the runner's, after merge): `cargo run --release -p lodestar-bench --example cold-start -- 10000000 <DIR>`, run twice on the same `DIR` (the first run builds the store). Read `start_ms` (time to the first `/healthz`) and `filled_ms` (until crawling starts) from the second run. The goal is a `start_ms` of about 2 s or less.
