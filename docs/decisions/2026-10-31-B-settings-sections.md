# B-settings-sections decisions (part a: the four sections and sealed secrets)

- **Four new settings sections, in display order after `search`:** `trackers`, then `integrations`, `notifications` and `insights` after `content` (§10.10.8). The registry's index now has 14 sections. The connection tests, clear usage data and send to client follow in part b.
- **Secrets are sealed in the settings table, not kept elsewhere.** A secret field's saved value is the JSON string `"sealed:<hex>"`: the integrations `SecretStore`'s XChaCha20-Poly1305 seal (§18.10) with the context `settings.<section>.<field>`, so a value copied onto another field doesn't open. This is what `Registry::register`'s old refusal ("until saved values can be sealed") was waiting for. No store schema change.
  - The key file (`secrets.key` in the data directory) is opened the first time a secret is saved or read, so an install that never saves one never creates it.
  - A value that doesn't open (the key file lost or replaced, a value never sealed) is skipped at start with `settings.saved_ignored` (`reason=not_sealed`), never fatal: the field falls back to its default, and the user enters it again.
  - An empty secret (`""`) resets the field, like `null`, so the form never shows **Set** for nothing.
  - **A secret never follows its endpoint to another server.** A patch that moves the endpoint (`Section::SECRET_ENDPOINTS`: the Torznab key with its URL, the ntfy token with its URL, the SMTP password with its host, port and security mode, so a downgrade to no encryption asks for it again; a client's password with its `url`'s scheme, host and port and its `kind`) without sending the secret again resets the secret. So a session that changes where a client points can't make Lodestar send the saved password there. Another path on the same server keeps it. A URL is compared by its `http(s)` scheme, host and port; any other value (an SMTP host such as `fd00::25`, a port, a mode) is compared whole, never parsed as a URL. An email login whose password was reset this way is refused until the password is entered again.
  - **A key rotation must re-seal these records too, and through the same store.** The registry opens its own `SecretStore` over `secrets.key` and keeps it for the life of the process; the cluster coordinator has its own. Nothing rotates the key yet. Whoever wires `SecretStore::rotate` shares one store between them (or reloads the registry's) and adds the settings rows to the re-seal step before `retire_old_keys`; otherwise the registry would keep sealing with a retired key.
- **List items can hold secrets (`Field::secret_keys`).** A download client's password lives in its item of `integrations.clients`, because the list has any number of clients. Only each item's secret is sealed, in place, with the context `settings.<section>.<field>.<item id>.<key>`; the rest of the list is plain JSON. Losing `secrets.key` (a database restored without it) loses the passwords, not the clients. Backups should keep `secrets.key` with the database.
  - `GET` returns each item without its secret keys, and the new `SettingValue.secrets_set` (left out when empty) lists the ones set as `<item id>.<key>`, so the form can show **Set · Replace · Remove** per client (§10.10.4).
  - On save, an item whose `id` matches a saved one keeps its secret when the key is left out or `null`; `""` removes it. Changing an item's `id` drops its secret.
  - A secret-holding field, list or not, is left out of export and skipped (`reason: "secret"`) on import, so the client list isn't portable yet. Exporting it without passwords is a possible follow-up.
- **Refinements of the owner's decisions, for the owner to see (§2.19):** `""` removes a list item's secret (a client's password), as `null` resets a field; and query logging's Privacy dialog asks no duration, because its retention (at most 30 days) bounds it.
- **The Torznab URL can't carry the key:** a query with `apikey` or `api_key` is refused ("Put the API key in its own field"), as credentials in a client's address are, so the key is always sealed.
- **A failure to seal names no path:** the client gets a fixed message, and the log line names the field with `reason=key_unavailable`.
- **Undo can't bring a secret back** (it's write-only): after Undo, a replaced password stays the new one. S-settings-2b's Undo copy shouldn't promise otherwise.
- **Notification values are checked by the senders themselves at save:** the section builds each set-up channel's ntfy, Discord, email or webhook sender, which refuses without a request what delivery would refuse (a URL that isn't Discord's, an ntfy URL with no topic, a token over plain HTTP to a public host, a login sent unencrypted, a loopback address).
- **Secrets in memory:** a section holds them as `SecretText`, whose `Debug` is `***`, and `Entry`'s `Debug` names the section only. They're plain `String`s otherwise (not zeroed), like the integrations crate's configs before they're wrapped in `Secret`.
- **Notifications are one of each channel, flat fields** (`ntfy_*`, `discord_url`, `email_*`, `webhook_*`), not a list: §10.10.8 names one ntfy, one Discord, one email and one webhook, and flat fields render from the schema. The ntfy topic URL, the Discord and webhook URLs, the ntfy token and the SMTP password are secrets: each URL is the only thing keeping its channel private (the integrations crate treats them as `Secret` too).
  - **Routing** is three lists of channels: `route_alerts`, `route_updates` (Updates' "Notify me", §12.2) and `route_health`. A route to a channel that isn't set up is skipped at delivery, not refused at save, so clearing a channel never fails on its routes.
- **Integrations:** `clients` (at most 8; `id`, `name`, `kind`, `url`, `username`, `password`, `category`, `save_path`, `paused`), `default_client` (an id, or empty for the first), and one Torznab endpoint (`torznab_url`, `torznab_api_key`). Addresses must be `http(s)` with a host and no credentials in them (they belong in the sealed fields). Where an address may point is the SSRF guard's decision when it's used, not the save's: download clients may reach loopback and notification channels may not (§9 integrations decisions).
- **Trackers maps onto `config.toml`'s `[scrape]`** (`scrape`, `trackers`, `dht_scrape`, `interval_secs`, `http_interval_secs`), restart-only, with 0 for the automatic intervals. `LODESTAR_SCRAPE_ENABLED` locks `scrape`; it was read by `Config::load` but missing from `config::ENV_VARS`, so its source showed as the file's. It's added there. Errors name a tracker by position, never by URL. The list is a public scrape list: it's returned and exported like any setting, so a private tracker's passkey URL doesn't belong in it. The intervals' bounds (0–86,400 s) and the list's (1,000) are wide, so a `config.toml` value doesn't fall outside the schema. Per-tracker health is reported state (Insights → Index), not a setting.
- **Insights:** `digest` (off, daily, weekly; off by default), `digest_day`, `digest_hour` (0–23, default 3, the quiet hour of §10.9.7), `digest_channels` (email, ntfy, Discord, RSS), `query_logging` (**off by default**, `x-danger: privacy`; its dialog says what's recorded and asks no duration, since retention bounds it) and `query_retention_days` (1–30, default 30: §10.9.5's 30 days is the most, and a shorter window is allowed).
- **No `config.toml` keys or variables for integrations, notifications or insights.** Credentials belong in the app, where they're sealed; adding file keys for the rest would mean new `Config` tables for values nothing reads from the file yet.

## What S-settings-2b's screens bind to
- **Remove a secret** (a field's, or a client's password) runs as its own confirmed `PATCH` from the field's menu, not as part of Save (§10.10.7's Destructive row): `null` for a secret field, `""` for a client's `password`.
- **Integrations:** `GET/PATCH /settings/integrations`. `clients` is an array of objects (a hand-built list of client cards; the schema's item `password` is `writeOnly`), with `secrets_set` for each card's password state. `default_client` is a select over the clients' ids. `torznab_url` and `torznab_api_key` (secret field) render from the schema. **Test connection** posts the card's values to `POST /settings/test` (`kind: download_client` today; `torznab` in part b).
- **Notifications:** `GET/PATCH /settings/notifications`, groups `ntfy`, `discord`, `email`, `webhook` and `routing`; generated from the schema. **Send test** comes in part b (`kind: ntfy | discord | email | webhook`).
- **Trackers:** `GET/PATCH /settings/trackers`, groups `scrape` and `cadence`; generated. Health per tracker comes from the scraper's own state, not this section.
- **Insights & digest:** `GET/PATCH /settings/insights`, groups `digest` and `usage`; generated, with the Privacy dialog on `query_logging` (§10.10.7). **Clear usage data** comes in part b.
- New message keys the screens need: `settings.<section>.label/.help`, `settings.<section>.<field>.label/.help` for every field above, `settings.<section>.<field>.keywords` for `trackers.scrape`, `integrations.clients`, `insights.digest` and `insights.query_logging`, and the groups `settings.group.{scrape,cadence,download_clients,torznab,ntfy,discord,email,webhook,routing,digest,usage}`.
