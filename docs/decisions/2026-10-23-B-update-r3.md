# B-update decisions, part 3 of 5: trust, check and policy

Part 3 adds the pure pieces the update engine is built on (architecture §12.2): the `updates` settings section, the install window, the policy, `trust.json`'s file handling and the signed check's fetch. The runner split the brief's part 3 into three PRs to keep each under ~3,000 lines (3/5 this one, 4/5 the engine and the API, 5/5 installing).

**Nothing here is reachable yet, except the settings section.** No engine calls the check, the policy, the window or the trust file until 4/5, which wires them into `serve --child` behind `/updates`; they're `allow(dead_code)` until then. Landing them first keeps the untrusted-input path (the release source, redirects, the trust state) reviewable on its own, with its own tests. The settings section is live: it can be saved and is checked, but nothing follows it yet.

The code is in `crates/lodestar/src/update/{check,policy,window,trust_file}.rs` and `crates/lodestar/src/settings/updates.rs`.

## The `updates` settings section

- **Fields and defaults:** `mode` off, `level` fixes, `security_fixes` auto, `channel` stable, `wait_days` 3 (0–14), `window` `03:00-05:00`, `allow_reindex` true, `notify_before` false, `notify_after` true, `notify_failure` true. The same keys are in `config.toml`'s `[updates]`, and every `LODESTAR_UPDATES*` variable is in `ENV_VARS`. All fields apply live.
- **`security_fixes` is a sentinel (§2.19):** no field may be nullable, so `auto` means on under `auto` and off under `notify`. It never applies under `image` or `off`. `GET /updates` gives the effective value.
- **`image` only on a container:** refused unless `deployment_here()` is Docker or Unraid, in the app and in `config.toml` or `LODESTAR_UPDATES` alike (a start with it elsewhere fails with the reason).
- **The window:** `HH:MM-HH:MM`, 00:00–23:59, wrapping midnight when its end is earlier. A start equal to its end is refused. It's form format `time-range`, new in the settings vocabulary.
- **Notify me is stored only.** Delivery waits for the notification channels to be stored (follow-up).

## The install window and the time zone

- **jiff `=0.2.38`** (published 2026-10-06), `default-features = false`, features `std`, `tz-system` and **`tzdb-zoneinfo`**. The last one is a refinement of the brief: without it a `TZ=Europe/Berlin` name can't be resolved, only `/etc/localtime`. It reads the system's zoneinfo directory and adds no dependency. Licence Unlicense OR MIT. The stripped binary's size change is measured in 4/5, where the engine first links it; here nothing calls it, so the linker drops it.
- **No zone found:** the window is in UTC, and `/updates` says so (`window_zone: "UTC"`).
- **DST:**
  - A boundary inside a spring-forward gap, or exactly at its start, is the transition itself: the first moment the clock reads past the gap. jiff's own "compatible" choice would be as late as the gap is long.
  - A window that the gap swallows whole (02:00-03:00 when 02:00 jumps to 03:00) doesn't happen that day, and the next opening is the day after. So an opening is at most a day away, or two on that one day.
  - A repeated autumn hour counts on both passes. The window is open whenever the local clock reads inside it. The next opening or closing is the first moment after now that this changes, so from the first pass it can be a re-entry, or a brief close, on the second. It's found by trying each whole minute and each zone transition, the only moments the local minute can change, for up to three days.
  - The tests use POSIX rules (Central Europe and the US), scanning both changes every 10 minutes. They need no zoneinfo.

## The check

- **The source:** `https://github.com/<owner>/<repo>/releases/download/update-manifest/<channel>.json`, from `CARGO_PKG_REPOSITORY`, which must be `https://github.com/<owner>/<repo>`; otherwise the error is `no_release_source`. **The rolling `update-manifest` release is a contract for E-M6's `release.yml`:** one asset per channel (`stable.json`, `beta.json`, `nightly.json`), each the envelope `lodestar_update` verifies. A 404 from the manifest URL itself means nothing is published for the channel yet; it's not an error. A 404 after a redirect (an expired asset link) is an error.
- **How:** `GuardedClient` with `NetPolicy::notification(false)` (public addresses only), 10 s to connect and 60 s for the whole fetch, every hop included, each hop through `send`.
  - Redirects (301, 302, 303, 307, 308) are followed by hand, at most 5. Every hop must be `https`, on the default port, without credentials, to `github.com`, `objects.githubusercontent.com` or `release-assets.githubusercontent.com`.
  - A hop URL may carry a query, because GitHub's signed asset URLs do, and it's never logged. The manifest URL and artifact URLs still refuse one (`url_ok`).
  - Bodies are read through `read_limited` at the envelope's 512 KiB.
- **What it sends:** `User-Agent: Lodestar-Updater` set on the request, overriding the client's versioned agent; no cookie, no conditional header, no query, no body. A test reads the built request's headers.
- **When** it runs (every 6 hours at a random minute, `POST /updates/check` at most once a minute), and fixture mode, are the engine's: 4/5.
- **Then** (4/5): `lodestar_update::check` against `trust.json`, and the forward-only write of the next trust state.
- **Egress settings (§5)** don't exist yet; the check takes them when they land (follow-up).

## `trust.json`

- Written by `TrustState::merge` (forward-only), temporary file, fsync, rename and a folder fsync. An unchanged state isn't rewritten.
- **The floor (§12.2):** the embedded statements and the statements of every installed overlay count whether or not the file exists. A stale `trust.json` (restored from a backup) therefore can't forget a revocation an overlay carries. Each statement is checked against the recovery key as it's added, so an overlay's statements need no trust in the overlay. 4/5 reads them from each overlay's manifest, which needs no binary copy.
- **Missing:** rebuilt from the floor, with high-water marks from the newest overlay manifest of each channel.
- **Found:** raised to the same floor, statements and marks both. A restored file can't re-accept a manifest older than an installed overlay's.
- **A rebuild that fails, or overlay statements that disagree with the file:** treated as damaged. Nothing is written that could lower a mark.
- **Damaged, or unreadable for now:** installs are blocked (`trust_damaged`) and the file is never overwritten. The check still runs from the floor rebuilt with the overlays, so releases and notices show and an overlay's revocations hold. Only when the overlays disagree with the chain is it the embedded statements alone.

## The policy

- A pure function, table-tested:
  - **Candidates:** not withdrawn, newer than the running version, not in `skipped`.
  - **Automatic installs** also need: `mode` auto, a level within `level`, no manual steps, `allow_reindex` when the release reindexes, its wait over, updates not paused, a current manifest, and an installation that can install.
- **Security fixes** skip the level and the wait, and under `notify` they're the one automatic install. **They still wait for the window (§2.19, §2.13),** and never skip manual steps.
- **The upgrade path:** a release whose `min_from` is above the running version reports `upgrade_path` with `via`, the newest reachable release, which is what installs.
- **Install now** (5/5's route) skips the window, the wait, the level and a pause. It never installs a skipped, withdrawn or unreachable release.
- **Capability reasons:** `not_supervised`, `dev_build`, `noexec` (statvfs on `<data>/bin`), `not_writable`, `package_managed`, `image_mode`, `trust_damaged`, `channel_unavailable`, `not_built_yet`.
  - **`package_managed`** is `LODESTAR_DEPLOYMENT=package`. No packaging sets it yet; it's for a distribution package.
  - Under any reason, Install automatically behaves as Check and notify.
