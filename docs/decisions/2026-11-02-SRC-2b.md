# SRC-2b decisions: saved-search alerts for promoted torrents

Slice SRC-2b closes the gap `2026-11-02-SRC-2.md` left ("The percolator: a known gap until SRC-2b"). A promoted torrent keeps its unverified item's id, which is below the search index's watermark and every saved search's, so the percolator's forward run (`(watermark, through]`) never reaches it. Architecture §8 ("Saved searches → alerts") and §18.5. No schema change.

## The durable source
- **`reindex_log` is never pruned** (V3 keeps every row, and nothing deletes them), so the percolator can always read the entry `promote` writes. That part of the runner's candidate design holds.
- **But `reindex_log` can't tell a promotion from a relabel, an enrichment or an upgrade** (SRC-2's note). Consuming it alone would alert on old torrents that newly match after a reclassification. Those aren't arrivals.
  - A permanent "promoted" flag bit wouldn't fix that: a later relabel of a promoted torrent writes another entry for the same id, and telling the promotion entry from it needs a per-id lookup in a log with no index on `torrent_id`.
  - A new table would need a V15 migration, and every migration snapshots the whole store first (`pre-v<N>.db`).
- **So `promote` marks its own entry, in `settings`** (`saved::queue_promoted`): one row per kept promotion, `percolator.promoted.<reindex_log seq, 20 digits>`, valued with the highest saved-search id at that moment. It's written in the promotion's own transaction, so a promotion is never stored without its row.
  - `settings` already holds other subsystems' state under their own prefixes (`settings.rs`). Nothing reads all of `settings`, and snapshots copy only `floor.%`.
  - **The rows are the cursor:** the percolator deletes the rows it covered in the same transaction as their alerts. A crash before that commit replays them; nothing is skipped. No in-memory queue.
  - **Bounded:** one row per promotion not yet percolated. Verification caps promotions at about 13 a second (SRC-2), and a run takes 256.

## Percolating a promoted id once
- **When:** after the forward run's saved searches, on what's left of the same budget, before live queries. The percolator takes rows whose `reindex_log` seq the serving index has committed (`SearchIndex::reindex_watermark`: the lower of the torrent and file indexes), then refreshes its reader, so the promoted document is searchable when it's matched.
- **Against which searches:** active ones (not paused) that existed when it was promoted (id at or below the row's value; saved-search ids are `AUTOINCREMENT`) and whose watermark is at or above the id. A search still below the id meets it in its own forward range, so it isn't run twice.
- **How:** `percolate` itself, over the one-id range `(id - 1, id]`. It's the same exact-tier query, so the forward run's rules hold.
- **Dedupe by (search, torrent):** `alerts` is unique on the pair and the insert ignores a repeat. So a promoted id the forward run also saw, or a row replayed after a crash, alerts once.
- **Recorded as the forward run is:** `Store::record_promoted` checks each search is still active with the same AST, as `record_percolation_unchanged` does, then inserts the alerts and deletes the rows up to the last one matched, all in one transaction. No watermark moves.
- **A merged promotion (`Promoted::Merged`) doesn't alert.** It adds no torrent: the stored one was already percolated when its own id was indexed. A merge isn't queued.
- **Visibility is the forward run's:** a held hash stores nothing (`Promoted::Held`), so it isn't queued. A torrent deleted later (a quarantine, a hold) has its alerts cascade away, or isn't in the index when its row is matched. A hidden one may be recorded but isn't listed or announced, which is how `alerts` already treats hidden torrents (B8).
- **No backfill:** a search created after the promotion has a higher id than the row's value, so it's passed over. That's the forward run's rule (a new search starts at the index's watermark).
- **Paused searches** get nothing for a promotion percolated while they're paused, as the forward run moves a resumed search past what arrived meanwhile.
- **A search that fails in the index** is passed over for that row, which is still consumed, so one bad query can't hold the queue. (The forward run retries a failed search's range; here a retry would block every promotion behind it.)
- **Restarts:** the rows survive; the next run after start takes them once the index has applied their entries.
- **A rebuilt index** commits the log's head before its ids reach a promoted one. So does an indexing backlog. A row whose id is above the index's id watermark waits, so it's never matched against an index that doesn't hold it yet.
  - **It waits without spinning** (runner review, #392). A waiting row doesn't set the run's `more`, so the task sleeps until the next commit or the idle poll. Tested in `a_row_the_index_has_not_reached_waits_without_spinning`.
  - **`more` is set only** when the budget stopped a row or a full batch was finished.
- **Progress is guaranteed** (runner review). A run's first row always finishes under its own token, whatever the forward run left of the budget, so busy runs can't stall the queue. A later row that the budget stops is matched again from scratch next run. Its partial matches are dropped, never recorded.
- **Waking:** the commit hook reports only commits that add torrents, and a promotion's commit only replays `reindex_log`. So an idle percolator also runs every `promoted_poll` (10 s). On a busy instance the next crawler commit wakes it first. Each idle run reads two short queries when there's nothing to do.
- **An unreadable saved search** (a query this build can't parse) gets nothing for the rows percolated while it is unreadable. The forward run keeps its place; here, keeping it would hold every promotion behind it.
- **`file:(…)` clauses** match against the file index, as the forward run's do.
  - The file index can lag the torrent index's ids: after a crash between their commits, it loses its documents. It then takes the log's head at once, and its ids start again.
  - So a row waits until **both** indexes' id watermarks have reached its id, not just the lower of their log seqs (runner re-review). Otherwise a promoted torrent would be matched without its files, a `file:` search would miss it, and the row would be consumed.
  - Tested in `a_row_the_file_index_has_not_reached_waits`, which fails without the check.

## Alert order: newest recorded first (self-review, then the runner, #392)
A promoted torrent's alert is new but its torrent id is old. So every place that took "newest" to mean "highest torrent id" now uses the alert id. Before SRC-2b, alerts were recorded in torrent-id order, so the two orders agreed; existing stores see no change.
- **Pruning** keeps each search's newest recorded alerts. Pruning by torrent id would delete a promoted alert at the next hourly prune whenever its search already held 1,000 alerts.
- **Lists, pages and the RSS feed** (`Store::alerts`, `shown_alerts`, the summary's last-alert time) order by alert id, descending.
  - The API's page cursor is now the last row's alert id. It stays opaque to clients, so the web needs no change.
  - A cursor handed out before the upgrade (a torrent id) is read as an alert id. The next page then restarts near the top, which is harmless.
  - Why it matters (runner review): the web marks a search read through its top row's alert id (`mark_alerts_read`: every alert with `id <= through`). Under torrent-id order, a promoted alert was either marked read unseen, or, when it was the only new one, left the badge stuck at 1.
  - Now the top row is always the newest recorded alert, so marking read through it covers everything.
- **Cost:** no index orders a search's alerts by id, so each page read sorts all of that search's alerts. Adding an index would need a migration.
  - A search usually holds about `keep` (1,000) alerts after the hourly prune. But a run records up to 1,000 per search, so a broad search during an import catch-up can hold many more until the next prune.
  - A list page sorts them once, which is fine.
  - The saved-search summary (`visible_alerts` in `crates/api/src/saved.rs`) paged through every alert 200 at a time and sorted again for each page. The runner measured 10.2 s for 100k alerts, against 0.06 s under the old order. It now reads them in one pass, with one sort.
- **The SSE `alerts` event's `max_id` stays the highest *torrent* id among the alerts it reports.** For a run that only had promotions, that's an old id. The event's `alert` field already carries the newest alert id, which is what marking read uses.
- Tested in `a_promoted_alert_is_the_newest_for_listing_pruning_and_reading` (a store test in which alert-id order differs from torrent-id order).

## Cost and fairness
- **A batch is at most 256 rows,** each one `percolate` call of one-id ranges, then one short write transaction.
  - The budget is shared with the forward run and checked before each search. Rows after the first overrun it by one search at most.
  - The first row runs under its own token, so a run can overrun the budget by that whole row: every due search for one id. That's roughly 20 ms per 1,000 saved searches (the batch measurement below), more when a `file:` clause's file set isn't cached.
- **Reported per run:** `alerts.run` (Debug) gains `promoted` (rows percolated) and `promoted_ms` (what the batch took). New alerts go through `alerts.found` and the SSE `alerts` topic as the forward run's do.
- **The writer pays one `settings` insert per kept promotion,** in the transaction it already runs.
- **Measured** (`promoted_batch_cost`, ignored test, release build, this container): a full batch of 256 promoted torrents against 20 saved searches over a 10,000-torrent index took **108 ms**, including the transaction that recorded its 2,560 alerts (10 of the searches matched every row). That is about 0.4 ms a row, well inside the 2 s budget.
- **No new metric:** the percolator exports none yet. Its counts are in the log.
