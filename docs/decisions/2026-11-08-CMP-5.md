## State and journal
- **Files, not settings rows (brief).** Each managed companion has `<data>/companions/<id>/state.json`, format 1: `installed` (the version that passed health) and `op` (the operation under way: `install`, `update` or `remove`, the version it installs, and the last step it finished). No store table, no migration (Q10). Credentials stay in CMP-3's `settings` rows.
  - **Inside the companion's folder,** so uninstall removes it with everything else, and nothing outside that folder is written.
  - **Written atomically,** as CMP-3's files and CMP-2's pointer are: a new temporary file (0600 on Unix), fsync, rename, then a best-effort folder fsync.
  - **Read strictly:** no links, at most 4 KiB, unknown fields refused, and a version must round-trip `Version::parse`.
  - **The pointer stays the truth** for what runs (CMP-2). Recovery reads both.
- **The state machine.** Steps in order: `begun`, `staged` (fetched, verified, extracted), `credentials`, `files`, `committed` (the pointer), `healthy` (started and passed health), `configured` (CMP-8b's plan and apply). Each step's effect happens first, then the journal records it. So a crash can leave a step's effect done but unrecorded, and recovery allows for that: it reads the pointer, not only the step.
  - **The commit point is `configured`.** Recovery rolls an operation that stopped before it back: an update to the version it replaces (`Install::rollback` if the pointer had moved, then `sweep`), a first install to nothing (credential rows deleted, then `Install::remove`). One that got to `configured` is rolled forward, which only deletes the previous version. This is how "a crash leaves the old version or nothing" holds while the last step, a delete, can still fail.
  - **Update skips `credentials` and `files`.** The companion's own credential and config are kept across versions. The previous version is stopped just before the commit, and the pointer keeps it as `previous` until the new one is `configured` (Q6).
  - **Remove** journals `begun` → `stopped` → `forgotten` (credential rows deleted), then removes the folder. A crash during a removal you confirmed is finished at start-up.
  - **No record but a folder:** with no pointer, it's a first install that crashed before its journal (or a removal that had already deleted the record), and the folder is removed. Credential rows are left alone: neither path left any of ours, and a detected companion's must survive. With a pointer, it's left alone and reported (`no_record`), and `install` refuses it the same way.
  - **Recovery runs first:** at serve, before anything could start a companion, and in each `lodestar companion` command.
- **One operation per companion.** The manager holds a slot per id, and a second call gets `Refusal::Busy`. A journal with an unfinished operation also refuses until recovery has run.
- **One journal writer per data folder, across processes** (self-review; runner's conditions: an OS advisory lock, released by the OS when the process dies, working on Windows, from `std` or the lockfile). `Manager::open` takes an exclusive lock on `<data>/companions/.lock` with std's `File::try_lock` (Rust 1.89: `flock` on Unix, `LockFileEx` on Windows; no new dependency) and holds it for the manager's life. A second process gets `Refusal::Busy`. Without the lock, a serve started during a long `lodestar companion install` would run recovery and roll back the install in flight. Serve that finds the lock held turns companions off for that run. The CLI checks the store is free first, then holds the lock for the whole command.
- **The commit point is recorded durably.** A step is copied into the in-memory record only after `state.json` holds it. So a failed write at `configured` reports a failure, and recovery rolls it back, rather than reporting success for an install the next start would undo.

## Confirmation and refusals
- **`InstallToken { id, version, sha256 }`** is the confirmation (CMP-6 carries it from the API). The manager compares it with the entry's current pin for this host, version and SHA-256, and refuses anything else (`confirmation_mismatch`). `Manager::offer(id)` gives what to show first: name, version, SHA-256, size, licence and the version it replaces.
- **The CLI has no `--yes` for install.** `lodestar companion install <id>` prints the offer and the exact command, then exits 3. `--sha256 <hex>` must be the shown hash. `remove` prints exactly what it deletes, then exits 3 without `--yes`.
- **Typed refusals** (`Refusal::code`):
  - `native_in_container` (Q17): a container is detected from any of `LODESTAR_DEPLOYMENT=docker|unraid`, Docker's `/.dockerenv`, Podman's `/run/.containerenv`, a container cgroup (v1), or `container=` in PID 1's environment (LXC, systemd-nspawn). That's stricter than About's detection, where the variable can say otherwise.
  - `unsupported_platform`;
  - `awaiting_pin` and `no_build`;
  - `guided_only`: the Windows installer, CMP-11's;
  - `no_launch_profile`;
  - `confirmation_mismatch`, `busy`, `already_current` and `not_installed`;
  - `credential_present`: a credential row exists for a companion Lodestar didn't install, a detected or guided one, so a first install never overwrites a key you pasted.
- **Nothing runs unverified.** The flow fetches only through CMP-1, with the pin looked up from `(entry, platform, arch)`, never passed in. It calls `verify::upstream(pin)` exhaustively before extraction and starts only `Install::executable` of a staged version.

## Effects behind traits
- **`Run::ready()`** is asked before an install begins, so nothing is downloaded for a start that can't happen. `Unwired` (serve and the CLI until CMP-5g) answers `not_wired`.
- **`Rows`** (credential rows; `forget` deletes exactly the rows `Removal` lists, one per `Field`; `crates/lodestar`'s `StoreRows` writes each one in one committed transaction), **`Run`** (start, health, stop) and **`ApiConfigure`** (CMP-8b) are trait objects, so the tests fake them. `Supervised` (CMP-4a's supervisor in CMP-4b's sandbox, each companion behind `egress::add`) and `Api` (`configurator(id)`, plan then apply) are the real ones.
- **`Downloader::new(Guarded)`** keeps CMP-1's rule that shipped code downloads only through the guarded client. `Downloader::any` exists only under `testing`.
- **The install receipt** (#611) is minted by the manager, inside this crate, after the commit and a passing health check, and handed to `ApiConfigure`. A fake can receive one but can't mint one.
- **Fault points** (`Manager::crash_at`, `testing` only) stop the flow before or after each step's effect, as a crash would. The tests restart with a new manager and check the disk, the journal and the credential rows.

## Launch profiles
- **qBittorrent:** `--profile=<home>` and `--webui-port=<port>`; its config is `<home>/qBittorrent/config/qBittorrent.conf`.
- **Prowlarr:** `-nobrowser -data=<home>`; its config is `<home>/config.xml`.
- **Others** (FlareSolverr, CMP-12) refuse with `no_launch_profile`.
- **A bare binary** (qBittorrent on Linux) is staged under the companion's id, `.exe` on Windows, the same name for every version, so a rollback finds the previous one. This needed `Install::stage_binary` in CMP-2's `layout.rs` (a shared edit, told to the runner): `stage` only extracts zip and tar.gz, so nothing could stage the `binary` kind CMP-0 added. It copies at most the pin's size, creates the file new (0700 on Unix), fsyncs it, and renames the folder in as `stage` does.

- **The binary's name comes from the companion's id, not the pin URL** (a refinement of the runner's condition that the name come from the entry's declared executable, else the pin URL's last segment). The catalogue requires `binary` artifacts to declare no executable, so the fallback would always apply, and a pin URL's file name can change between releases. The previous version must keep its name for a rollback to find it, which the id guarantees. Either way the name goes through the catalogue's `RelPath` (one component, `[A-Za-z0-9._-]`, no `..`, Windows device names refused, 255 bytes at most), and `stage_binary` refuses more than one component before writing anything. It stages only the file CMP-1 verified, capped at the pin's size. Tests cover hostile names, an interrupted stage swept away, and no partial `<version>/` left by a failure.

## Carried follow-ups
- **Route freshness (#608):** `manager::monitored(egress, every)` runs `PluginEgress::monitor` in a relay task and forwards its states on a channel of its own. When the monitor returns, the channel says `Down`. When the task is aborted or panics, it closes, and the gate reads that as down too. When every receiver is gone, the relay stops, along with its probing. CMP-5g must build each `Supervised` route with `monitored`: a raw `PluginEgress::watch()` would bring the stale-`Up` problem back. So a dead monitor can no longer leave a stale `Up` releasing the companion. Tested on Linux with a real `lo` route.
- **Bind and proxy re-asserted on every start (#608):** each start the manager makes (install, update, the restart after a rollback) runs CMP-8b's plan and apply afterwards. Restarts the supervisor makes on its own after a crash don't. The setting persists in the companion's own file, and a crash isn't a change of setting.
- **Config writers and linked parents (#608):** before writing a config file, the manager creates each folder below home one at a time and refuses one that is a link or not a directory (`config_path_link`), with the companion stopped. It's checked by path rather than by `openat2(RESOLVE_NO_SYMLINKS)`, since CMP-3's writers take a path. The companion isn't running then, so nothing can swap a folder between the check and the write.
- **`setsid` grandchildren (#608): handed to CMP-G.** A companion's child that calls `setsid` leaves the process group, so a hold's stop (which signals the group) misses it on Linux. A cgroup would catch it, but the shipped unit doesn't delegate one (CMP-4b). Windows' Job Object already catches it. CMP-G's orphan tests should cover it.
- **The credential row is stored before the password changes (#611):** in a managed install, the row is written and committed in the `credentials` step, before the config file that uses it. Guided installs (`PasswordChange`) are CMP-5g's.
- **`ProbeResponse` (#610)** is never logged: the manager logs only codes and labels.
- **Log events:** `companions.installed`, `companions.install_failed`, `companions.rolled_back`, `companions.removed` and `companions.recovered`. They carry the catalogue id, the pinned version (a `&'static` label from the compiled-in catalogue), a step name and a code; never a path, URL or credential. They're registered in the logging golden, `event-names.ts` and the en/zh messages.

## What's left for CMP-5g (and why)
- **Starting installed companions at serve, and Q18's `companions.<id>.egress` setting.** Neither is in this slice's brief. Serve runs recovery and publishes the snapshot, but builds the manager with `Unwired`, which refuses every start. Nothing runs until CMP-5g hands in the supervisor and each companion's route, so nothing runs on a route nobody chose (Q8).
- **So `lodestar companion install` refuses with `not_wired` in this release,** before anything is downloaded. `list`, `remove` and `compose` work. Whether a server-stopped CLI install should start, health-check and configure the companion in its own short-lived supervisor is the runner's call for CMP-5g.
- **The snapshot for CMP-10:** `Manager::snapshot()` is a `watch` of `Snapshot { companions: [{ id, version, health }], download_clients }`. CMP-10 isn't on `main`, so it's exposed in `crates/lodestar/src/companions.rs` with a `TODO(CMP-5g)` to hand it on as `PipelineConfig::companions`. `download_clients` follows `integrations.clients` (runner decision).
- **CMP-10's contract** (#616, runner):
  - the snapshot gains `external_client` and `external_indexer` (an `integrations.clients` entry; a Prowlarr/Jackett source endpoint the user set);
  - it's handed on as `PipelineConfig::companions: Some(rx)`;
  - after a successful configure and hand-over, the Prowlarr source is restarted or its config supplied again.

  All of this is CMP-5g's, since it lands after CMP-10. This slice's `Snapshot` has `download_clients` for now.
- **Remote workers keep `PipelineConfig::companions: None`** (the runner's lean, checked here): the worker runtime (`crates/lodestar/src/worker/`) starts no pipeline and builds no source plugins (only its tests start a coordinator's pipeline, with none), so there's nothing for the gate to hold.
- **The secret-row filter** (CMP-3's `is_secret_row` in export, settings import and support bundles) is still unwired. Those paths are outside this slice.

## Launcher hook
- **`launcher_main()` runs first in `main`**, before `thp::apply`, argument parsing, config or logging, as `if let Some(code) = launcher_main() { exit(code) }`. It's compiled only on Linux. Elsewhere the hook is absent and the sentinel argument is clap's usage error, as CMP-4b requires.
- **Test:** `crates/lodestar/tests/companion_launcher.rs` runs the binary with the sentinel and no plan. It expects exit 120 and `launcher_bad_plan`, with a broken config that isn't read and a data folder that isn't created. It's a new file outside the brief's paths, because `CARGO_BIN_EXE_lodestar` reaches integration tests only (told to the runner).
