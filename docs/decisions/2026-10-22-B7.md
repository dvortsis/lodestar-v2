# B7 decisions (#102)

Slice B7 (`docs/build-plan.md`), building §8 "Suggest/typeahead comes from the term dictionaries and the parsed-title FST. 'Did you mean' uses fuzzy terms", §9 `suggest` and §10.4's autocomplete, smart chips and "Natural phrasing". No schema change: the index stays v5.

## `/suggest`

- **`GET /api/v1/suggest?q=&pos=&limit=&hidden=`**, behind the session. `pos` is the caret in characters (the end by default; past the end is `400 bad_pos`), `limit` is clamped to 1–20 (8 by default), `hidden` is `/search`'s. A query over 2,048 bytes is `400 query_too_long`.
- **Items:** `{kind, text, insert, replace: {start, end}, count?}`. `replace` is a character range of `q` (end exclusive) that `insert` takes the place of, so the client never tokenises the query. A leading `-`/`!` stays outside it. `count` is the number of torrents the item would find among those the search may show; it's absent for field names, categories and "did you mean".
- **Order:** `did_you_mean`, `chip`, `field`, `value`, `title`; duplicates (same range and insertion) dropped; at most `limit`.
- **The token at the caret** is found by a lenient copy of the query lexer (`suggest/caret.rs`): the same splits (whitespace, brackets, quotes, `|`), but an unclosed quote runs to the end and brackets needn't balance. `file:(…)` groups are tracked, and inside one only what a file clause takes is offered (`name`, `path`, `ext`, `size`, ext values and chips). The query language has no escape character, so a backslash is literal, as in the lexer.
- **Field names** come from `query::FIELDS` (made `pub(crate)`, with `field`, `near_field`, `tag_value`, `is_field_name`, `is_plain_word` and `edit_distance`), never a second list. Fields that arrive later (`seeders:` …) aren't offered.
- **Values** come from the field's term dictionary (`tag` as `key:value`, `ext`), prefix-matched, ordered by document frequency, then counted under the base query and dropped at 0. Flags offer `yes`/`no` with counts; `cat:`/`bytes:` offer the fixed category names without counts. In a list (`ext:mkv,mp`) the last value is completed.
- **Titles** come from the title FST (below), inserted as `title:"…"` phrases. They need two folded characters. The title being typed may be the last one to six plain words before the caret (longest first), a quoted phrase, or a `title:` value.
- **Smart chips** reuse the recognisers: the release parser read the way the query parser reads a tag value (`res`, `codec`, `hdr`, `audio`, `lang` from three letters), the extension table (not bare numbers), content type names, and years 1900–2099. Only forms that parse back to themselves are offered, at most two. **A chip is the token's value alone:** read as `A [token]`, the title must stay `A` and the only field set must be the chip's (with the channels an audio codec carries, `dd5.1`), the field holds one value (not a list: `ita.eng` reads as `en, it`), the token doesn't split on `.` `-` `_` `+` into two pieces that each chip on their own (`x264.x265`; `h.264`, `dts-hd.ma` and `dd5.1` still chip), and it has no non-ASCII space. An extension chip needs a letter: `300`, `007` and `720` are numbers. So a pasted release name (`Naruto.S01E02.1080p`, `x265,naruto`, `naruto\u{3000}1080p`) is no chip and keeps its text, in `/suggest` and in natural phrasing.
- **"Did you mean":** an unknown field one edit from a known one (the parser's rule, so `Re:Zero` stays text) always; and, when the whole query finds fewer than 10 torrents (the stem fallback's line), the closest term of the `text` dictionary for each rare (< 10 documents) ASCII word among the two words nearest the caret (each costs a fuzzy walk of every segment's dictionary, so a long query of misspellings stays within budget): 1 edit under 6 letters, else 2, fewest edits then most documents, checked to exist under the base query. The word being typed (the caret at its end) isn't corrected: it is a prefix, and titles it starts are offered instead.
- **Cancellation:** the work runs on the blocking pool under the request's token (cancelled when the client disconnects) with a 2 s budget (`503 suggest_timeout`); counts check the token as they go.

## Visibility

- **Every count and existence check runs `search::base_query`**, the query `/search` runs: filter-hidden torrents only with `hidden`, Adult only with "Show adult content". So no value, chip or "did you mean" word that only hidden or Adult torrents carry is offered.
- **Titles** carry four counts in the FST (neither, Adult, hidden, both), and a request adds up the classes it may see, so a title only hidden or Adult torrents carry has 0 and isn't offered. Because the FST can be a build behind, every title is also counted against the index under the base query before it's offered. That count runs up to the FST's count or 1,000 torrents, whichever is less (past 1,000 the FST's count is shown), so a keystroke never walks a big title's whole match list. A title with no visible match isn't offered, and the count shown is never more than the visible matches. So a torrent hidden, reclassified Adult, deleted or purged since the last build stops counting at the index commit that records it.
- **That check is a phrase match** (`title:"…"`), not an exact-title one. Until the next build (one rebuild cycle, below), a title whose own torrents are gone is still offered when another visible title contains it as a phrase. Its text is then part of a visible title anyway, and its count is the visible matches'. An exact check would need the titles stored in the index (a schema change) or a per-build set of removed ids.
- **Sealed names** (§20) live only in `quarantine`, never in `torrents` or the index, so they can't be offered. A test quarantines an indexed torrent and checks its title disappears. A title quarantined after the last build stays in the in-memory set until the next build, but the existence check means it's never offered.

## The title FST (`suggest/titles.rs`)

- **Shape:** one `tantivy_fst::Map` (already in the tree through tantivy) from `fold(title) \0 display` to four 16-bit counts. `fold` is NFKD, marks removed, lowercase, every run of other characters one space; `display` is the most used spelling. Effective and alternative titles are both indexed, each once per torrent; titles over 160 folded bytes are skipped.
- **Ranking:** by count (then folded title). A prefix with at most 4,096 titles is scanned; every wider prefix has its best 24 per visibility precomputed at build time, so a lookup never scans more than 4,096 keys.
- **Lives beside the index, in memory:** each `SearchIndex` holds its own `Titles`, so a B5b rebuild/swap starts a fresh set for the new directory when its live indexer starts; the old one's builder exits with it. It isn't persisted (no new on-disk format): a restart rebuilds it, and until the first build finishes there are no title suggestions (fields, values, chips and "did you mean" still work). An older-schema index serving during a rebuild has no live indexer, so no titles until the swap.
- **When its live indexer stops** (a swap or shutdown), the set stops following the store, so an index on its way out never rebuilds again. Leases holding it still read the last set.
- **Rebuild rule:** the live indexer starts it (`Titles::follow`, with its store's path) and reports each commit (`Titles::committed`). One builder thread per set rebuilds from its own read-only store connection, then waits at least 60 s or ten build times, whichever is longer, and rebuilds again if anything was committed meanwhile. It never runs on the commit path. **A purged torrent's title** stops being offered at the commit that removes it from the index (the existence check) and leaves the FST within one cycle: at most max(60 s, 10 × build time) plus one build after that commit.
- **It reads `torrent_parsed` directly** (`t.flags`, `t.content_type`, `p.data`) through `Store::connection()`, in id order, 20,000 records per query. Each query is its own read, so the build never holds one read transaction for its whole length (8.5 s at 1M), which would hold back WAL checkpoints. A `Store::for_each_enrichment` would be the cleaner home; the store crate isn't this slice's. The builder's connection uses `StoreConfig::default()`: the live indexer gets only a `Store`, which doesn't expose its config (only `mmap_size` matters to a reader).
- **Tested through the real swap:** an index serving during a B5b rebuild offers titles from its own set, and after the swap the new directory's index has a different set, built when its live indexer starts.

## Natural phrasing (`natural.rs`, `GET /parse?natural=true`)

- `/parse` with `natural=true` adds `natural: {ast, canonical, chips: [{text, from}], text}` beside the strict parse (unchanged, so a syntax error is still a 400). It's a proposal; nothing applies it.
- **Explicit syntax is kept as written.** The input is split the way the query lexer splits it, and only runs of plain words go through the rules: tokens the parser reads as themselves, apart from their neighbours, outside brackets and not `NEAR` operands. Everything else is copied verbatim: negations (`-x265`, `!cam`), fields and lists (`res:1080p`, `ext:mkv,avi`), phrases, operators and groups. So `-cam 4k` is `-cam res:2160p` and `4k movies OR 1080p tv shows` is `res:2160p type:movie | res:1080p type:tv`. Input the strict parser rejects isn't read; `/parse` answers it with the syntax error. A property test checks that every syntax token's parsed node is in the proposal whenever it's in the strict parse.
- **Rule-based and deterministic,** reading at most 512 bytes and 32 tokens (words, operators and brackets) (`400 natural_too_long`). The rules cover:
  - resolutions, codecs, HDR, audio and languages (the chip recognisers), and extensions (preferred when a word is both, as with `flac`);
  - content types, including plural words;
  - years, year ranges, decades, and `after`/`since`/`before`/`until` years;
  - size and file-count comparisons, and `between … and …` sizes;
  - recency (`today`, `this week`, `last 3 days`, `recent`);
  - seasons and episodes, subtitles, and `without`/`no` before any of them.
- **Per top-level AND group** (the parts between top-level `OR`s): a rule on a field the group's own syntax names anywhere, in brackets too (`-(type:tv) tv shows`), is left as text, so natural phrasing never contradicts or widens it (`-type:tv tv shows`, `res:1080p 4k` stay as typed). Keyword values of one field merge across the group's runs (`movies -x tv shows` is `type:movie,tv -x`), but not across an explicit `AND`, which asks for all of them (`movies AND tv shows` is `type:movie type:tv`). A property test checks the structure: the proposal is the strict parse with each run replaced by its reading, nested ANDs flattened. Another checks no plain word is lost: each is kept as text, read by a rule, or a linking word.
- **Within a run,** values of one field merge into one clause (`movies and tv shows` is `type:movie,tv`). Linking words next to a recognised word are dropped, articles only before one (so `the office` keeps its `the`), and request words (`find`, `show me`) at the start. Every other plain word stays as text, untrimmed when trimming would make it syntax (`NEAR,`), leave nothing (`!`) or take a bracket off one side only (`Naruto[1080p]`). **A known limit:** audio and extension words read as clauses wherever they stand, so a title word like the `dts` in `the dts story` becomes `ext:dts`; the preview shows it before anything is applied.
- **Over the brief's example:** the brief writes `size:>10GB`; the proposal is `size:>=10GB` (next point).
- **Sizes are inclusive** (`over 10gb` is `size:>=10GB`), since a byte either way means nothing and the canonical renderer prints `>10GB` as a byte count; **years and file counts keep the strict sense** (`after 2010` is `year:>=2011`).
- Golden tests cover 91 phrasings, the syntax cases included. Property tests check that the output always parses to its own AST and renders back to its canonical text, and that explicit syntax survives.

## Budget

- **`/suggest` p95 < 15 ms** is gated by `search-bench --gate` at 200k torrents for seven classes: title prefix, two-letter prefix, field value, smart chip, did you mean (one typed word), did you mean (32 misspelt words), and field name.

| p95           | title prefix | two letters | field value | chip | did you mean | 32 words | field name |
| ------------- | ------------ | ----------- | ----------- | ---- | ------------ | -------- | ---------- |
| 200k (gated)  | 2.2 ms       | 3.1         | 0.9         | 1.7  | 1.7          | 2.9      | 3.8        |
| 1M (reported) | 10.3         | 3.3         | 1.6         | 4.1  | 9.5          | 13.2     | 3.8        |

- **Memory at 1M torrents.**
  - The set holds 601,507 distinct titles: **25.8 MB** (the FST plus the precomputed rankings, about 43 B per title). It builds in 5.3 s, so the rebuild interval there is 60 s.
  - The bench samples RSS during the build: about +88 MB at its peak. A swap holds the old set and the new one while the new one builds: about +132 MB at its peak.
  - The allocator keeps freed memory, so these are upper bounds. At 200k the figures are 5.8 MB, +35 MB and +49 MB.
  - The build keeps one buffer per spelling (`fold \0 display`, the final key's form) with four counts, and merges spellings after sorting. That's about 30% less than aggregating keys and spelling lists apart (+126 MB before).
- **The 10M plan** (budget: RSS under 1 GB, §3).
  - The set itself would be about 260 MB, but a build would peak around +0.9 GB, too much beside the index.
  - Above about 2M distinct titles, the build goes to two passes. The first counts hashed folded keys (8 B key, 4 B count). The second aggregates only titles more than one torrent carries, the ones typeahead most needs; how many that keeps is to be measured on a real crawl.
  - Persisting the FST (an on-disk format, so the runner's call) is the alternative.
  - This is a follow-up; nothing at the current scale needs it.
