# B7 decisions (#102)

Slice B7 (`docs/build-plan.md`), building §8 "Suggest/typeahead comes from the term dictionaries and the parsed-title FST. 'Did you mean' uses fuzzy terms", §9 `suggest` and §10.4's autocomplete, smart chips and "Natural phrasing". No schema change: the index stays v5.

## `/suggest`

- **`GET /api/v1/suggest?q=&pos=&limit=&hidden=`**, behind the session. `pos` is the caret in characters (the end by default; past the end is `400 bad_pos`), `limit` is clamped to 1–20 (8 by default), `hidden` is `/search`'s. A query over 2,048 bytes is `400 query_too_long`.
- **Items:** `{kind, text, insert, replace: {start, end}, count?}`. `replace` is a character range of `q` (end exclusive) that `insert` takes the place of, so the client never tokenises the query. A leading `-`/`!` stays outside it. `count` is the number of torrents the item would find among those the search may show; it's absent for field names, categories and "did you mean".
- **Order:** `did_you_mean`, `chip`, `field`, `value`, `title`; duplicates (same range and insertion) dropped; at most `limit`.
- **The token at the caret** is found by a lenient copy of the query lexer (`suggest/caret.rs`): the same splits (whitespace, brackets, quotes, `|`), but an unclosed quote runs to the end and brackets needn't balance. `file:(…)` groups are tracked, and inside one only what a file clause takes is offered (`name`, `path`, `ext`, `size`, ext values and chips). The query language has no escape character, so a backslash is literal, as in the lexer.
- **Field names** come from `query::FIELDS` (made `pub(crate)`, with `field`, `near_field`, `tag_value`, `is_field_name`, `is_plain_word` and `edit_distance`), never a second list. Fields that arrive later (`seeders:` …) aren't offered.
- **Values** come from the field's term dictionary (`tag` as `key:value`, `ext`), prefix-matched, ordered by document frequency, then counted under the base query and dropped at 0. Flags offer `yes`/`no` with counts; `cat:`/`bytes:` offer the fixed category names without counts. In a list (`ext:mkv,mp`) the last value is completed.
- **Titles** come from the title FST (below), inserted as `title:"…"` phrases. They need two folded characters. The title being typed may be the last one to six plain words before the caret (longest first), a quoted phrase, or a `title:` value.
- **Smart chips** reuse the recognisers: the release parser read the way the query parser reads a tag value (`res`, `codec`, `hdr`, `audio`, `lang` from three letters), the extension table (not bare numbers), content type names, and years 1900–2099. Only forms that parse back to themselves are offered, at most two.
- **"Did you mean":** an unknown field one edit from a known one (the parser's rule, so `Re:Zero` stays text) always; and, when the whole query finds fewer than 10 torrents (the stem fallback's line), the closest term of the `text` dictionary for each rare (< 10 documents) ASCII word: 1 edit under 6 letters, else 2, fewest edits then most documents, checked to exist under the base query. The word being typed isn't corrected while it starts a title.
- **Cancellation:** the work runs on the blocking pool under the request's token (cancelled when the client disconnects) with a 2 s budget (`503 suggest_timeout`); counts check the token as they go.

## Visibility

- **Every count and existence check runs `search::base_query`**, the query `/search` runs: filter-hidden torrents only with `hidden`, Adult only with "Show adult content". So no value, chip or "did you mean" word that only hidden or Adult torrents carry is offered.
- **Titles** carry four counts in the FST (neither, Adult, hidden, both), and a request adds up the classes it may see, so a title only hidden or Adult torrents carry has 0 and isn't offered. Because the FST can be a build behind, every title is also checked against the index under the base query before it's offered: a torrent hidden, reclassified Adult, deleted or purged since the last build stops being offered at the index commit that records it.
- **Sealed names** (§20) live only in `quarantine`, never in `torrents` or the index, so they can't be offered. A test quarantines an indexed torrent and checks its title disappears.

## The title FST (`suggest/titles.rs`)

- **Shape:** one `tantivy_fst::Map` (already in the tree through tantivy) from `fold(title) \0 display` to four 16-bit counts. `fold` is NFKD, marks removed, lowercase, every run of other characters one space; `display` is the most used spelling. Effective and alternative titles are both indexed, each once per torrent; titles over 160 folded bytes are skipped.
- **Ranking:** by count (then folded title). A prefix with at most 4,096 titles is scanned; every wider prefix has its best 24 per visibility precomputed at build time, so a lookup never scans more than 4,096 keys.
- **Lives beside the index, in memory:** each `SearchIndex` holds its own `Titles`, so a B5b rebuild/swap starts a fresh set for the new directory when its live indexer starts; the old one's builder exits with it. It isn't persisted (no new on-disk format): a restart rebuilds it, and until the first build finishes there are no title suggestions (fields, values, chips and "did you mean" still work). An older-schema index serving during a rebuild has no live indexer, so no titles until the swap.
- **Rebuild rule:** the live indexer starts it (`Titles::follow`, with its store's path) and reports each commit (`Titles::committed`). One builder thread per set rebuilds from its own read-only store connection, then waits at least 60 s or ten build times, whichever is longer, and rebuilds again if anything was committed meanwhile. It never runs on the commit path. **A purged torrent's title** stops being offered at the commit that removes it from the index (the existence check) and leaves the FST within one cycle: at most max(60 s, 10 × build time) plus one build after that commit.
- **It reads `torrent_parsed` directly** (`t.flags`, `t.content_type`, `p.data`) through `Store::connection()`, one sequential scan. A `Store::for_each_enrichment` would be the cleaner home; the store crate isn't this slice's.

## Natural phrasing (`natural.rs`, `GET /parse?natural=true`)

- `/parse` with `natural=true` adds `natural: {ast, canonical, chips: [{text, from}], text}` beside the strict parse (unchanged, so a syntax error is still a 400). It's a proposal; nothing applies it.
- Deterministic and rule-based, at most 512 bytes and 32 words (`400 natural_too_long`). Rules: resolutions, codecs, HDR, audio, languages (the chip recognisers), extensions (preferred when a word is both, as `flac`), content types with plural words, years, year ranges and decades, `after`/`since`/`before`/`until` years, size and file-count comparisons, `between … and …` sizes, recency (`today`, `this week`, `last 3 days`, `recent`), seasons and episodes, subtitles, and `without`/`no` of any of them. Values of one field merge into one clause (`movies and tv shows` is `type:movie,tv`). Linking words next to a recognised word are dropped, articles only before one (so `the office` keeps its `the`), and request words (`find`, `show me`) at the start. Every other word stays as text: a word the parser wouldn't read as itself (`-cam`, `OR`) becomes a one-word phrase.
- **Sizes are inclusive** (`over 10gb` is `size:>=10GB`), since a byte either way means nothing and the canonical renderer prints `>10GB` as a byte count; **years and file counts keep the strict sense** (`after 2010` is `year:>=2011`).
- Golden tests cover 44 phrasings; a property test checks the output always parses to its own AST and renders back to its canonical text.

## Budget

- **`/suggest` p95 < 15 ms** is gated by `search-bench --gate` at 200k torrents for six classes (title prefix, two-letter prefix, field value, smart chip, did you mean, field name). Measured p95 at 200k: 1.7–4.0 ms; at 1M: title prefix 10.6, two-letter prefix 3.8, field value 1.9, smart chip 5.4, did you mean 9.2, field name 5.0 ms (all reported, the 1M run isn't gated).
- **Memory at 1M torrents:** 601,507 distinct titles, **25.8 MB** (FST plus precomputed rankings, about 43 B per title), built in 8.5 s, so the rebuild interval there is 85 s. At 200k: 141,602 titles, 5.8 MB, 1.5 s. Building holds the aggregated titles in a hash map (roughly 100 B per title) on its own thread while it runs. At 10M torrents the set would be about ten times larger; persisting it or keeping only titles more than one torrent carries are the levers if that's too much.
