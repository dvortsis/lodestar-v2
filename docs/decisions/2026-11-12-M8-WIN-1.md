# M8-WIN-1 decisions (#777)

- **Service mode watches the installed MSI service; it never launches or stops it.** `cr0-soak.ps1 -ServiceName Lodestar` attaches to the service process, records its PID and start time on every sample, and leaves it running. Reason: G-v1-windows is the owner's soak of the MSI in service mode (plan OQ3), which the child-process collector could not measure.
- **The CR-0 build record is not used in service mode; the evidence binds to the service's binary by SHA-256 only** (runner, 2026-11-12). The collector hashes the executable named by the service's ImagePath (never recording the path) at attach and on every sample. The upgrade record carries the hash before and after, and the analyzer's `build_binding` check fails if any sample's hash differs from the attach hash or no hash was recorded. The upgrade check fails unless the after-upgrade hash equals the bound hash and differs from the before hash. The binding changes only through that recorded upgrade event.
- **The file-version half of the binding was dropped because the exe has none.** `lodestar.exe` has no VERSIONINFO resource, so a file version is always null. `lodestar --version` prints Cargo.toml's base version, so a release candidate prints `1.0.0` and two RCs look alike. The collector records that output (`service_reported_version`, and the upgrade's `from_version`/`to_version`) as information only; nothing compares it.
- **What is lost against the CR-0 build record:** no check that the binary was built from a named source commit, and no check that the embedded UI's `index.html` hash matches the build. `-Commit` is recorded but not verified. `release.yml` publishes no checksum for `lodestar.exe` itself, so the runner takes `lodestar.exe` from the RC's portable zip (after checking the zip against the signed `SHA256SUMS`), hashes it, and compares it with `service_image_sha256`. It does the same for `from_image_sha256` against the last release's zip, since nothing else shows the upgrade started from that release (`from_version` is information only). The CI MSI smoke (`release.yml`, `/healthz`) covers the embedded UI.
- **A restart can't be proved from the samples alone.** A restart ends the collector's loop before it takes another sample. So `service_restart` passes only if there are samples, the run finished (`baseline_window_complete`, `service_detached`, `finalization_complete`, `result.samples` equal to the sample count), every sample has a service identity, and PID, start time and the `start_time_seconds` metric stayed constant. An unfinished, truncated or aborted run fails it. A service that exits ends the run with the fixed reason `service_process_exited`.
- **Order: upgrade first, then the 24 h soak on the RC, then uninstall** (plan OQ3 leaves the order open). The soak thus measures the upgraded service. "Kept" data after a default uninstall counts as clean, as the user guide says the uninstaller leaves it; `REMOVE_DATA=1` is the other accepted policy.
- **A service attached after its start-up pause has ended starts the baseline at the first sample.** A first sample with `dht_sample_suppression_seconds` 0 counts as "ended", or the baseline would never start. A restarted service may pause for up to 6 h, so the run is about 32 h.
- **`MEMORY_FIT` and its numbers are unchanged;** a test asserts them. Old evidence without the new fields reports `absent`, not `fail`; an unreadable `lifecycle.json` fails.
- **Shared edit (runner-approved):** `docs/soak/tools/test_cr0_collector.ps1` parses the changed scripts and tests the attach path, service identity, image path and hash, torrent count, version strip, upgrade and uninstall records (with real temporary files and folders for the data, hash and existence checks), and lifecycle merge. `Save-SoakUpgrade` requires a valid previous binary hash, start time and torrent count.
- **Time zone withheld.** In service mode `run.json`'s `timezone` is `withheld`, so the owner's zone isn't sent (`docs/owner-decisions.md` §2.35).
- **Not run here:** `pwsh` is not available in the build container. CI's `soak collector (Windows)` job runs `test_cr0_collector.ps1`, which now parses `cr0-soak.ps1` and `cr0-common.ps1` and exercises the upgrade, uninstall, torrent-count, version, identity and image helpers with their Windows calls replaced. Not covered by any test: the service-mode branches inside `cr0-soak.ps1`'s main loop beyond parsing, and the real CIM, process and `msiexec` calls.
