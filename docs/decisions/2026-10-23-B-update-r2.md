# B-update decisions, part 2: the supervisor and rollback

`lodestar serve` on Unix is now the supervisor of a `serve --child` that does the work (architecture §12.2). The code is `crates/lodestar/src/update/`. Nothing stages an overlay outside tests until part 3, so in practice the supervisor runs the image's own code as its child.

## `<data>/bin`
- **The folder:** created 0700, refused if it's a symlink, not a folder, or owned by another user. Its owner is checked, and its mode set, through a descriptor opened `O_NOFOLLOW | O_DIRECTORY`. On a share or drive without Unix owners (SMB, NTFS, exFAT) the refusal says to mount it with the process's `uid` or set `PUID` to its owner.
- **Files:** every one is written by temporary file (`O_NOFOLLOW`, 0600), fsync, rename, then a folder fsync. It's read through `O_NOFOLLOW | O_NONBLOCK` and must be a regular file, so a FIFO can't hang a read. State files are capped at 256 KiB when written, and a larger one read is damage. Overlay folders are named by canonical strict versions without build metadata, never paths.
- **Who writes what:**

  | File | Writer |
  |---|---|
  | `.lock` | supervisor (`flock`, for its life); `lodestar rollback --update` |
  | `active` | supervisor |
  | `pending` | supervisor; the child only deletes it |
  | `rollback.json`, `halted.json` | supervisor |
  | `skipped` (reasons `failed`, `manual`; at most 64 entries) | supervisor |
  | `<version>/` (`lodestar`, `manifest.json`, `manifest.json.minisig`) | part 3's updater; tests here |
  | `<version>/migration.json`, `probation.json`, `request.json` | child |
  | `history.json` | supervisor (rollbacks); part 3 (installs, clear) |
  | `trust.json`, `updater.json`, `skipped` (reason `user`) | part 3 |
- **Two writers never run at once.** The supervisor writes only while no child runs. The one exception is `probation.json`, which only the child writes.

## Control channel (§12.2 "must resolve")
- **Reserved exit codes:** `EXIT_RESTART` 80, `EXIT_SWITCH` 81, `EXIT_ROLLBACK` 82 **(§2.19)**. They stay clear of 0–3, clap's 2, a panic's 101 and 128 + n.
- **The request file:** before exiting with a code, the child writes `request.json` with its own `run_id` (16 random hex digits per start). A reserved code without a matching request is an ordinary exit, or a failed attempt in probation. The request is consumed either way.
- **`LODESTAR_SUPERVISOR`:** `{pid, run_id, version, image_version, notices}`, at most 4 KiB. It isn't a setting, so it's not in `config::ENV_VARS`. `serve --child` checks that `getppid()` is the `pid`. If not, it serves, but nothing counts as supervised: no probation and no supervised restart. Part 3 reports that as `not_supervised`.
- **The child's version:** a release child's version is its own build's. A debug build takes the hint's `version`, so the tests can run one binary as several versions.

## Probation
- **Attempts:**
  - One attempt is charged in `pending` (fsynced) before each start.
  - It's refunded only when the child exited after a stop the supervisor forwarded (`TERM`, `INT` or `QUIT`), or after a valid `EXIT_RESTART`.
  - **A hard kill of the supervisor in between leaves the attempt charged.**
  - Three failed attempts roll back. A version found with its attempts used up at start (a kill landed between the third failure and the journal) is rolled back then, never started a fourth time.
  - A start that fails (`ENOEXEC`, `ETXTBSY`, a missing loader) is a failed attempt, like a crash, so it ends in a rollback, not in a loop under the restart policy.
  - If the charge can't be written, the attempt still counts in memory for this run, and the supervisor says so.
- **Time limits:**
  - The deadline is cumulative: `used_ms` adds up the time spent starting across attempts, up to 5 minutes. A child that hasn't written `probation.json` yet counts as starting, so a child that hangs before it beats fails too.
  - While `probation.json` says `migrating`, the time doesn't count toward the deadline. Beats every 10 s; 5 minutes without one fails.
  - Every limit is measured on the supervisor's monotonic clock (round 1). The child's beat timestamp only shows that a beat happened, so a wall-clock jump can't fail or extend an attempt.
  - **The migration cap is 6 hours (§2.19, a new number).**
  - A probation failure stops the child: SIGTERM, 30 s, SIGKILL.
- **`pending` can't be written** (a full disk, for example): nothing switches. The current version restarts with `pending_unwritable` in the hint's notices.
- **Passing:**
  - The child deletes `pending` and `probation.json` once its self-test passes.
  - The self-test checks four things: the store opened with its migrations (`Services::start` returned), a fixed query against the index, the HTTP port bound and the DHT up unless it's off, and `/healthz` green, retried until the deadline.
  - Once that child has exited, the supervisor keeps `active` and its previous version and deletes older overlays (it writes only while no child runs).
  - A self-test failure asks for the graceful shutdown, and the child exits 1.
- **`Store::max_id` doesn't exist.** The child reads `max(id)` on a read-only connection of its own for `baseline_max_id`, then `stored_since` every 60 s and at shutdown.

## The rollback journal
- **The steps** are §12.2's, implemented in `journal.rs`. The journal is rewritten and fsynced after each step.
- **The snapshot** is used only when `<failed>/migration.json` exists and the newest `pre-v<from+1>` snapshot settles, passes `quick_check` and reads as schema `from`. Its SHA-256 is recorded when the journal is written, before the restore. The restore source must be a regular file.
- **No verified snapshot after a migration: refused (round 1, blocking).** With `migration.json` but no snapshot that verifies, a rollback goes ahead only while the store still reads as schema `from`. Each migration step commits with its `schema_migrations` row, so that means none committed. Otherwise, or if `migration.json` can't be read, it's refused, nothing is written and `active` stands: the previous version couldn't read the store.
  - After every attempt failed, a refusal writes `halted.json` with the reason (`refused`), and the supervisor exits 1 at every start until a newer image replaces both versions.
  - After `EXIT_ROLLBACK`, the running version keeps running, with `rollback_refused` in the notices. The attempt is refunded.
  - `lodestar rollback --update` refuses with exit 3, before it asks.
- **The child records the migration or doesn't start (round 1).** If listing the snapshots or writing `migration.json` fails, `serve --child` logs `update.migration_unrecorded` and exits 1 before `Services::start`, so nothing migrates unrecorded. That's a failed attempt. The child now starts logging before this step, so the update events reach the log file.
  - **A store whose schema can't be read fails closed too (round 2).** If the store exists but `serve --child` in probation can't read its schema, it exits 1 the same way, rather than guessing there's nothing to migrate.
- **Back to the image, the store must be one the image reads (round 2).** Whatever `migration.json` says, a rollback to `image` is refused if the store it would leave is past this build's `latest_schema_version()`: the restored snapshot's `from`, or else the store as it is. It's also refused if that schema can't be read. This catches a migration nothing recorded. A rollback to another overlay can't be checked this way, because only that version knows its schema.
- **Journal validation:** a journal in another `format`, or with `steps_done` outside 2–6, can't be read, and nothing starts. The same applies to `pending` in another format: it's damage.
- **A damaged `pending` starts a fresh probation (round 2, runner decision under §2.19).** If `pending` can't be read, or is in another format, the supervisor rewrites it as a fresh probation of `active`'s version (`kind: install`, attempts 0) before anything runs, so its migration is recorded and its self-test runs. With no `active` it's removed. If it can't be rewritten, nothing starts. If `history.json` shows a rollback to `active`'s version, or can't be read, the repair is `kind: restored` instead, so failing halts. One level of rollback, never two (round 2, the runner's security check). **Flag to the owner:** this replaces round 1's "runs without probation".
- **Step 2 runs on a blocking thread** while signals are watched, because verifying the snapshot takes minutes on a large store. `pending` is no longer removed first: step 6 rewrites it, and nothing reads it while the journal exists.
- **Only the snapshot this migration took counts (self-review).** `migration.json` is written before the store opens, so it lists the `pre-v` snapshots that already exist (`before`). The journal never restores one of those, even if it verifies. An attempt that failed before its own `VACUUM INTO` (a full disk) leaves the store alone, instead of restoring an earlier upgrade's snapshot and losing weeks of data. The journal's restore also accepts only a `pre-v` name (`snapshots::parse_name`).
- **Lost torrents** count from the first attempt's `baseline_max_id`: a later attempt keeps it. A rollback that restores nothing records 0.
- **Step 6 also writes `pending` for the restored version** (`kind: restored`), before the journal is deleted in step 7. A crash before step 8 (the start) then keeps the restored version's probation. §12.2 lists that as step 8.
- **A stop signal during a rollback** finishes the current step and leaves the journal; nothing starts. The journal runs on a blocking thread while the supervisor keeps watching signals. Docker's 10 s stop timeout is shorter than the 30 s grace; the journal makes that safe.
- **A failed restore** (the snapshot is gone and the store doesn't match its hash) keeps the journal, starts neither version, and prints where things stand.
- **One level, once per failed version:**
  - A restored version that fails its three attempts writes `halted.json` and exits 1, naming both versions.
  - While `halted.json` exists the supervisor prints the error and exits 1, unless this image is newer than both versions. The message says the file can be deleted to try again once the cause is fixed.
  - **A version in `skipped` with reason `failed` is never installed again (§2.19)**; part 3 enforces it. A manual rollback writes reason `manual`, which the supervisor refuses the same way. A `user` entry never replaces either.
  - An unreadable `skipped` refuses every switch and stops step 6, rather than starting a fresh list that forgets earlier entries.
  - A newer image drops the entries at or below its version, and the list keeps at most 64 entries, oldest dropped first.
- **`lodestar rollback --update` (§2.19):** server stopped. It takes the lock (held: exit 3), finishes a journal in progress or rolls `active` back with reason `manual` and lost torrents unknown, and starts nothing. `active` must be newer than this image (round 1); in probation, `pending`'s `index_before` is used. Before a new rollback it says what happens (which snapshot is restored and that torrents stored since are lost, or that the store is kept) and asks, like plain `rollback`: `--yes`, or a typed "yes" on a terminal; no terminal and no `--yes` is refused. It keeps no `before-rollback` copy: the restore is a rename, as the supervisor's is.
- **Every store opener refuses while `rollback.json` exists:** `serve --child`, `import-bitmagnet`, and the CLI (already). On Unix, the supervisor finishes the journal first; one it can't read stops it.

## Overlays
- **What runs:**
  - With no `active`, or one not newer than this build, the supervisor runs its own code.
  - When nothing is in flight, it then removes `active` and every overlay it's at least as new as: a newer image wins.
  - Otherwise it verifies the active overlay with `lodestar_update::overlay` against the embedded keys (part 1), with no expiry check.
- **When verification fails:**
  - A key revoked by this build's embedded statements is refused; the supervisor runs its own code.
  - A definitive failure renames the folder `<version>.bad` (kept for diagnosis) and runs its own code with the `bad_overlay` notice. Definitive means a file missing, a symlink or not a regular file, a bad signature or hash, or too large. This build's own problems (its target isn't shipped, its built-in keys don't load) aren't the overlay's, so they keep it (round 2).
  - Any other I/O error keeps the overlay. The image runs this time with the `overlay_unavailable` notice, and the overlay is checked again at the next start (round 1).
  - If the store was migrated past what this build reads, `Store::open`'s `SchemaTooNew` refuses without harm.
- **Versions only go up (round 1).** `plan` refuses an `active` that isn't newer than its version-valued `previous`. A switch must go to a version newer than the running one, and `rollback --update` needs an `active` newer than the image.
- **What runs (round 1):**
  - On Linux the overlay's binary is copied into a memfd. It's sealed against writes, growing, shrinking and further seals, then that copy is hashed and verified, and it's what runs (`/proc/self/fd/<n>`).
  - `MFD_EXEC` is asked for first, so `vm.memfd_noexec` doesn't block it. It costs the binary's size in memory while the child runs (about 40 MB).
  - Without a memfd (an old kernel, a seccomp policy), the `O_NOFOLLOW` descriptor is hashed and run, and the supervisor says so. Elsewhere the path runs.
  - The binary read is capped at `MAX_ARTIFACT_SIZE` + 1.
  - The image's own code starts as `/proc/self/exe` on Linux. **Version skew avoided:** on a host where a package upgrade replaces the binary while the supervisor runs, the child is still the supervisor's own version, the one it reports and compares overlays with. The new binary takes over at the next supervisor start.
- **Previous index directories are not kept through probation.** B5b's cleanup deletes older *complete* index directories once the new one is complete; it keeps only newer ones. After a rollback, the restored version rebuilds its index from the store while serving, which §12.2 allows. Keeping them needs a change in `crates/search` (follow-up, recorded by the runner). **What a user sees:** after a rollback from a version that changed the index format, the previous version rebuilds its index in the background while it serves (§12.2), and search results are incomplete until that finishes. That takes about an hour at 10 million torrents (§8's rebuild window), less for smaller stores; the Overview and status pill show the rebuild's progress meanwhile. A rollback from a version that kept the index format loses nothing here.

## The supervisor process
- **Order at start:** after `privdrop::run` (still single-threaded) and the config load, it takes the lock (held: "another Lodestar is using this data folder", exit 3). It then finishes a journal, honours `halted.json`, and chooses what to run. The loop runs on a current-thread tokio runtime.
- **What it never does:** open the store for writing, read `trust.json`, start the log file, or touch the network. A rollback reads the store's schema, and the snapshot's, read-only, and renames the snapshot over the store.
- **A stop that meets a request (round 2):** if the child exits with a reserved code and a valid request just as a forwarded stop arrives, the stop wins and the supervisor exits 0. Its child shut down cleanly; the request is dropped.
- **`ps`** shows the child as `lodestar` (`arg0`), not `/proc/self/fd/<n>`.
- **A child subreaper on Linux** (`PR_SET_CHILD_SUBREAPER`), so orphans are reparented to it and reaped even when it isn't PID 1 (systemd, a shell).
- **A stop signal while it stops a child** (the 30 s grace) is remembered: it then exits rather than restarting or rolling back.
- **A forwarded stop** (`TERM`, `INT`, `QUIT`) that the child outlasts by the grace period becomes SIGKILL (round 1).
- **The child stops with the supervisor:** on Linux `serve --child` sets `PR_SET_PDEATHSIG` to SIGTERM, then checks `getppid()` again, in case the supervisor died first (round 1).
- **A deadline that races a pass:** if probation stops the child just as it cleared `pending`, the version is kept and started again, instead of exiting with the stop's status (round 1).
- **The child's arguments** are built from what was parsed: `--config <path>` when one was given, then `serve --child`. The environment is inherited. `serve --child` on Windows is refused with exit 2.
- **`skipped` is read too:** a switch to a version skipped with reason `failed` or `manual` is refused, beside part 3's own check.
- **A bad or revoked overlay** stays in `active`, so every start says so again (`bad_overlay`) until a newer image or part 3's next install replaces it. That's deliberate: refusing it must be visible, not a one-off line.
- **The lock and part 3's updater:** the supervisor holds `.lock` for its life, so the updater in the child takes `<data>/bin/install.lock` while it downloads and stages. Only the supervisor reads or writes `active` and `pending`, and the updater's switch goes through `EXIT_SWITCH`. An unsupervised `serve --child` (no matching parent) installs nothing (`not_supervised`).
- **Console output:** its own lines are `supervisor:` prefixed. It also writes the PUID/PGID report through a console-only `tracing` subscriber, because the child starts unprivileged and has nothing to report.
- **As init:** it forwards `TERM`, `INT`, `HUP`, `QUIT`, `USR1` and `USR2`, and reaps every child (`waitpid(-1, WNOHANG)`) on `SIGCHLD` and every second. Children are spawned with `std::process::Command` and never waited on through `Child::wait`.
- **Exit:** outside probation it exits with the child's status, 128 + n for a signal.

## Composition with B2c's restart
- **Under `--child` with a verified parent:** `Restart::global()` reports `method: "supervised"` and is available (`RestartMethod::Supervised`, new).
- **After the graceful shutdown:** a requested restart writes `request.json` and exits 80 instead of calling `reexec()`. The supervisor starts the same version again and refunds the attempt.
- **What's unchanged:**
  - A signal still wins.
  - `reexec()` stays for an unsupervised run (`serve --fixture`).
  - The temporary-fixture refusal is unchanged.
  - The address timer's revert restarts the same way.
- **Part 3's switch and rollback** go through `control::set_intent`: `main.rs` turns the intent into the request and its code.

## Debug-only test overrides
`update/testing.rs`, read from `LODESTAR_UPDATE_TEST` only under `cfg(debug_assertions)`; every accessor returns `None` otherwise:
- `trust_root`: test public keys;
- `version`: a pretend image version;
- `target`;
- `probation_ms`, `stall_ms`, `migration_cap_ms`, `grace_ms`;
- `beat_ms`: the migration heartbeat;
- `max_binary`: a smaller cap on an overlay's binary (round 2);
- `fault`, a list: `journal:<k>` (exit after step k), `journal:slow`, `overlay:io` (a transient verification error), and `child:<what>@<v>` with `crash`, `hang`, `ignoreterm`, `selftest`, `stall`, `migrate=<s>`, `restart`, `switch=<version>`, `rollback`, `orphan` or `unrecorded`.
- `trust_root.statements`: the key statements the test "build" embeds.

`/security-review` checks that none of these reaches a release build.

## Threat model and residuals (round 1)
- **The child is as trusted as `<data>` itself.** It runs as the same user and can write `<data>/bin`. A compromised child can therefore write `active`, `pending` or `skipped` between the supervisor's writes. That's equal to write access to the data folder, which is control of the install already (the config, the store, `seal.key`). The supervisor's checks stop accidents and damage, not that user.
  - The runner has asked the owner about a separate supervisor UID.
  - What the checks still guarantee: only a binary verified against the embedded keys runs as an overlay; versions only go up; a rollback never restores a snapshot that isn't this migration's own; and nothing starts while a journal is unfinished.
- **The residuals:**
  - Without a memfd, a writer holding the overlay's binary open could change it between the hash and the exec.
  - Off Linux the path runs, so a swap in between is possible.
  - A `serve --child` started by hand doesn't take `.lock`; only the supervisor and `rollback --update` do. Two servers on one data folder are already prevented by the store's own lock, and an unsupervised child installs nothing.
- **Nightlies:** `LODESTAR_VERSION` must be set for a nightly build. Without it, every nightly reports `CARGO_PKG_VERSION`, versions don't go up, and switches between nightlies are refused (E-M6/#92 above).

## Windows (`cfg(not(unix))`)
- **What exists here:** no supervisor and no `--child`; `rollback --update` says it isn't available. `serve` there still refuses while a journal exists.
- **What E-M6's `lodestar update-helper` reuses:**
  - `lodestar-update`'s verification;
  - the `pending`, `rollback.json` (`journal::Journal`) and `history.json` formats;
  - `<data>\updates\` for the cached MSI;
  - the service set to manual start during a rollback;
  - M6-win's exit codes;
  - Authenticode checked only when the artifact carries a signature;
  - the `Restart::global()` hook in `windows/service.rs` (still M6's).
- **From P-release's review:** the Windows service reports Running before it opens the store, so an MSI downgrade over a newer schema installs and then stops with `SchemaTooNew`. The helper's rollback must restore the store before it relies on the old MSI. That is the same order as journal steps 4 and 6 here.
