# B-update decisions, part 2: the supervisor and rollback

`lodestar serve` on Unix is now the supervisor of a `serve --child` that does the work (architecture §12.2). The code is `crates/lodestar/src/update/`. Nothing stages an overlay outside tests until part 3, so in practice the supervisor runs the image's own code as its child.

## `<data>/bin`
- **The folder:** created 0700, refused if it's a symlink, not a folder, or owned by another user. Every file is written by temporary file (`O_NOFOLLOW`, 0600), fsync, rename, then a folder fsync, and read with `O_NOFOLLOW`. Overlay folders are named by canonical strict versions without build metadata, never paths.
- **Who writes what:**

  | File | Writer |
  |---|---|
  | `.lock` | supervisor (`flock`, for its life); `lodestar rollback --update` |
  | `active` | supervisor |
  | `pending` | supervisor; the child only deletes it |
  | `rollback.json`, `halted.json` | supervisor |
  | `skipped` (reason `failed`) | supervisor |
  | `<version>/` (`lodestar`, `manifest.json`, `manifest.json.minisig`) | part 3's updater; tests here |
  | `<version>/migration.json`, `probation.json`, `request.json` | child |
  | `history.json` | supervisor (rollbacks); part 3 (installs, clear) |
  | `trust.json`, `updater.json`, `skipped` (reason `user`) | part 3 |
- **Two writers never run at once.** The supervisor writes only while no child runs. The one exception is `probation.json`, which only the child writes.

## Control channel (§12.2 "must resolve")
- **Reserved exit codes:** `EXIT_RESTART` 80, `EXIT_SWITCH` 81, `EXIT_ROLLBACK` 82 **(§2.19)**. They stay clear of 0–3, clap's 2, a panic's 101 and 128 + n.
- **The request file:** before exiting with a code, the child writes `request.json` with its own `run_id` (16 random hex digits per start). A reserved code without a matching request is an ordinary exit, or a failed attempt in probation. The request is consumed either way.
- **`LODESTAR_SUPERVISOR`:** `{pid, run_id, version, image_version, notices}`, at most 4 KiB. It isn't a setting, so it's not in `config::ENV_VARS`. `serve --child` checks that `getppid()` is the `pid`. If not, it serves, but nothing counts as supervised: no probation and no supervised restart. Part 3 reports that as `not_supervised`.
- **The child's version:** a release child's version is its own build's. A debug build takes the hint's `version`, so the tests can run one binary as several versions.

## Probation
- **Attempts:**
  - One attempt is charged in `pending` (fsynced) before each start.
  - It's refunded only when the child exited after a stop the supervisor forwarded (`TERM`, `INT` or `QUIT`), or after a valid `EXIT_RESTART`.
  - **A hard kill of the supervisor in between leaves the attempt charged.**
  - Three failed attempts roll back.
- **Time limits:**
  - The deadline is cumulative: `used_ms` adds up the time spent starting across attempts, up to 5 minutes. A child that hasn't written `probation.json` yet counts as starting, so a child that hangs before it beats fails too.
  - While `probation.json` says `migrating`, the time doesn't count toward the deadline. Beats every 10 s; 5 minutes without one fails.
  - **The migration cap is 6 hours (§2.19, a new number).**
  - A probation failure stops the child: SIGTERM, 30 s, SIGKILL.
- **`pending` can't be written** (a full disk, for example): nothing switches. The current version restarts with `pending_unwritable` in the hint's notices.
- **Passing:**
  - The child deletes `pending` and `probation.json` once its self-test passes.
  - The self-test checks four things: the store opened with its migrations (`Services::start` returned), a fixed query against the index, the HTTP port bound and the DHT up unless it's off, and `/healthz` green, retried until the deadline.
  - The supervisor then keeps `active` and its previous version, and deletes older overlays.
  - A self-test failure asks for the graceful shutdown, and the child exits 1.
- **`Store::max_id` doesn't exist.** The child reads `max(id)` on a read-only connection of its own for `baseline_max_id`, then `stored_since` every 60 s and at shutdown.

## The rollback journal
- **The steps** are §12.2's, implemented in `journal.rs`. The journal is rewritten and fsynced after each step.
- **The snapshot** is used only when `<failed>/migration.json` exists and the newest `pre-v<from+1>` snapshot settles, passes `quick_check` and reads as schema `from`. Its SHA-256 is recorded when the journal is written, before the restore.
- **Step 6 also writes `pending` for the restored version** (`kind: restored`), before the journal is deleted in step 7. A crash before step 8 (the start) then keeps the restored version's probation. §12.2 lists that as step 8.
- **A stop signal during a rollback** finishes the current step and leaves the journal; nothing starts. The journal runs on a blocking thread while the supervisor keeps watching signals. Docker's 10 s stop timeout is shorter than the 30 s grace; the journal makes that safe.
- **A failed restore** (the snapshot is gone and the store doesn't match its hash) keeps the journal, starts neither version, and prints where things stand.
- **One level, once per failed version:**
  - A restored version that fails its three attempts writes `halted.json` and exits 1, naming both versions.
  - While `halted.json` exists the supervisor prints the error and exits 1, unless this image is newer than both versions.
  - **A version in `skipped` with reason `failed` is never installed again (§2.19)**; part 3 enforces it.
- **`lodestar rollback --update` (§2.19):** server stopped. It takes the lock (held: exit 3), finishes a journal in progress or rolls `active` back with reason `manual` and lost torrents unknown, and starts nothing.
- **Every store opener refuses while `rollback.json` exists:** `serve --child`, `import-bitmagnet`, and the CLI (already). On Unix, the supervisor finishes the journal first; one it can't read stops it.

## Overlays
- **What runs:**
  - With no `active`, or one not newer than this build, the supervisor runs its own code.
  - When nothing is in flight, it then removes `active` and every overlay it's at least as new as: a newer image wins.
  - Otherwise it verifies the active overlay with `lodestar_update::overlay` against the embedded keys (part 1), with no expiry check.
- **When verification fails:**
  - A key revoked by this build's embedded statements is refused; the supervisor runs its own code.
  - Any other failure renames the folder `<version>.bad` (kept for diagnosis) and runs its own code with the `bad_overlay` notice.
  - If the store was migrated past what this build reads, `Store::open`'s `SchemaTooNew` refuses without harm.
- **Optional hardening done:** on Linux the binary is hashed from an `O_NOFOLLOW` descriptor, and that same descriptor runs (`/proc/self/fd/<n>`). Elsewhere the path runs. The residual is a swap between the check and the start, which needs write access to `<data>`, and that is full control already.
- **Previous index directories are not kept through probation.** B5b's cleanup deletes older *complete* index directories once the new one is complete; it keeps only newer ones. After a rollback, the restored version rebuilds its index from the store while serving, which §12.2 allows. Keeping them needs a change in `crates/search` (follow-up, recorded by the runner). **What a user sees:** after a rollback from a version that changed the index format, the previous version rebuilds its index in the background while it serves (§12.2), and search results are incomplete until that finishes. That takes about an hour at 10 million torrents (§8's rebuild window), less for smaller stores; the Overview and status pill show the rebuild's progress meanwhile. A rollback from a version that kept the index format loses nothing here.

## The supervisor process
- **Order at start:** after `privdrop::run` (still single-threaded) and the config load, it takes the lock (held: "another Lodestar is using this data folder", exit 3). It then finishes a journal, honours `halted.json`, and chooses what to run. The loop runs on a current-thread tokio runtime.
- **What it never does:** open the store, read `trust.json`, start the log file, or touch the network.
- **Console output:** its own lines are `supervisor:` prefixed. It also writes the PUID/PGID report through a console-only `tracing` subscriber, because the child starts unprivileged and has nothing to report.
- **As init:** it forwards `TERM`, `INT`, `HUP`, `QUIT`, `USR1` and `USR2`, and reaps every child (`waitpid(-1, WNOHANG)`) on `SIGCHLD` and every second. Children are spawned with `std::process::Command` and never waited on through `Child::wait`.
- **Exit:** outside probation it exits with the child's status, 128 + n for a signal.

## Composition with B2c's restart
- **Under `--child` with a verified parent:** `Restart::global()` reports `method: "supervised"` and is available (`RestartMethod::Supervised`, new).
- **After the graceful shutdown:** a requested restart writes `request.json` and exits 80 instead of calling `reexec()`. The supervisor starts the same version again and refunds the attempt.
- **What's unchanged:**
  - A signal still wins.
  - `reexec()` stays for an unsupervised run (`serve --fixture`).
  - The temporary-fixture refusal is unchanged.
  - The address timer's revert restarts the same way.
- **Part 3's switch and rollback** go through `control::set_intent`: `main.rs` turns the intent into the request and its code.

## Debug-only test overrides
`update/testing.rs`, read from `LODESTAR_UPDATE_TEST` only under `cfg(debug_assertions)`; every accessor returns `None` otherwise:
- `trust_root`: test public keys;
- `version`: a pretend image version;
- `target`;
- `probation_ms`, `stall_ms`, `migration_cap_ms`, `grace_ms`;
- `fault`: a list of `journal:<k>`, `child:crash@<v>`, `child:hang@<v>` and `child:selftest@<v>`.

`/security-review` checks that none of these reaches a release build.

## Windows (`cfg(not(unix))`)
- **What exists here:** no supervisor and no `--child`; `rollback --update` says it isn't available. `serve` there still refuses while a journal exists.
- **What E-M6's `lodestar update-helper` reuses:**
  - `lodestar-update`'s verification;
  - the `pending`, `rollback.json` (`journal::Journal`) and `history.json` formats;
  - `<data>\updates\` for the cached MSI;
  - the service set to manual start during a rollback;
  - M6-win's exit codes;
  - Authenticode checked only when the artifact carries a signature;
  - the `Restart::global()` hook in `windows/service.rs` (still M6's).
- **From P-release's review:** the Windows service reports Running before it opens the store, so an MSI downgrade over a newer schema installs and then stops with `SchemaTooNew`. The helper's rollback must restore the store before it relies on the old MSI. That is the same order as journal steps 4 and 6 here.
