# B12 decisions (API keys, feed tokens, rate limits, password confirmation, proxy-header auth)

Architecture §12, §12.1, §20.11, §10.10.6–§10.10.8, and the B8 and M-auth decision files. No owner decision is reversed or loosened. The refinements the runner flags to the owner (§2.19) are marked **(§2.19)**.

- **"Reveal" is replaced by Regenerate (§2.19).** §10.10.7 lists "reveal or regenerate an API key" as password-confirmed. Only a key's SHA-256 is stored (B8), so it can't be shown again. The secret appears once, in the create or regenerate response. Regenerate makes a new secret for the same name, kind, scopes, feed and expiry, and the old one stops working at once. It gets a new id and prefix: the store has no "replace the hash" call, and the new row exists before the old one is deleted, so a failure leaves both keys working rather than neither. A revoked or expired key can't be regenerated (409 `key_inactive`); make a new one instead.
- **One key format:** `lsk_<8>_<43>` for an API key and `lsf_<8>_<43>` for a feed token, 56 characters. `<8>` is 8 random characters of `A-Z a-z 0-9`, and with the tag it's the public prefix the store finds the row by. `<43>` is 32 bytes from the OS RNG (`SysRng`), unpadded base64url. The store gets the prefix and the SHA-256 of the whole string. The tag lets a user, or a secret scanner, tell what a leaked string is.
- **Scopes** are bits: `SEARCH` 1 (the JSON search API, read-only), `TORZNAB` 2, `FEEDS` 4 (every feed). An API key needs at least one. A feed token always has `FEEDS` alone, and optionally belongs to one saved search. A route opts in to one scope; a key reaches it only with that bit.
- **Which changes need the password.** Creating or regenerating a key or token, changing proxy auth, and signing out other sessions all need it (§10.10.7). Revoking and deleting don't: they only take access away, like strengthening a filter. Each confirming route checks its other fields first, so a bad value is answered before the 428.
- **The fresh-password primitive** is `auth::require_fresh_password` (blocking) and `auth::confirm_fresh_password` (async). A missing password is `428 confirm_required` with `field: "password"` and spends no attempt. A wrong one is `401 bad_password`. Attempts share the login bucket (burst 5, one per 12 s, §16 M2). `filters.rs` keeps its inline 428 until B15 adopts this; the messages differ, and the codes and fields match.
- **Presenting a key:** `Authorization: Bearer`, `X-Api-Key`, or `?apikey=` (Torznab). A feed token comes only as `?token=`, and only on feed routes. A key presented the wrong way fails. The same secret in two forms is fine; two different ones are refused. A session (cookie or proxy header) is checked first.
- **Every bad secret answers the same:** malformed, unknown prefix, wrong secret, revoked, expired, or the wrong kind for how it came are all `401 bad_api_key`. A valid key without the route's scope is `403 key_scope`. A key used to write (any method but GET and HEAD) is `403 key_read_only`, and a `Set-Cookie` a handler adds to a key request is dropped.
- **Limiters**, each a token bucket:
  - **Login, setup, password change and fresh password:** per IP, burst 5, one per 12 s (unchanged).
  - **Failed key checks:** per IP, burst 10, one per 6 s, separate from login. When it's empty, even a valid key from that address waits. `429` with `Retry-After`.
  - **Requests per key:** burst 300, then 5 a second (18,000 an hour), with `Retry-After`. A Prowlarr sync or a season search sends tens of requests, so polling never meets it. Sessions aren't key-limited, so the UI's search-as-you-type can't hit it.
  - **Memory:** each map holds at most 10,000 entries (IPs or key ids). When it's full, entries that have fully recovered are forgotten. If it's still full, newcomers share one overflow bucket. This bounds memory under a flood of addresses, where before the login map could grow past its cap.
  - Login 429s still send no `Retry-After`, so M-auth's bodies are unchanged; the client's 12 s default stays right.
- **Proxy-header auth (§12), off by default.** The settings are trusted proxies (IPs or CIDRs, at most 64), the user header (default `Remote-User`) and optional allowed users (at most 64). They're saved in `auth.json` under `proxy`, which is left out while it's the default, so older files load unchanged.
  - The header signs a request in only when proxy auth is on, setup is done, and the **TCP peer** is a trusted proxy. The header must hold exactly one user name of 1–256 bytes with no control characters, on the allowed list if there is one. From any other peer the header is ignored. Cookies keep working.
  - **Refused settings:** a `/0` range (it would trust every address), turning it on with no trusted proxy, and headers that carry something else (`Cookie`, `Authorization`, `Host`, `X-Forwarded-For`, `X-Api-Key` and the like).
  - **IPv4-mapped IPv6** peers and entries (`::ffff:10.0.0.1`) count as IPv4, so a dual-stack listener matches IPv4 lists.
  - A hand-edited `proxy` section that fails these checks loads as off, with a warning naming only the bad field.
- **`ClientIp` behind a trusted proxy** is the rightmost `X-Forwarded-For` address that isn't a trusted proxy. Several header lines are read in order, and at most 16 entries of at most 64 bytes each are read from the right. An entry may be quoted, bracketed or carry a port. **A bad entry ends the walk at the peer, rather than being skipped.** The brief said "skipped", but the entries right of the client are written by the trusted proxies, which only write valid ones, so a bad one there means something is wrong. Skipping it would let the walk reach entries the client wrote. With proxy auth off, every proxy header is ignored, the forwarded address included.
- **Recovery:** `LODESTAR_PROXY_AUTH=off`, read in `services.rs` where `Auth::load` runs, turns proxy auth off for that run without changing the saved settings. `GET /auth/proxy` reports `forced_off: true`, so the Security screen can say why. It isn't in `config::ENV_VARS`, which lists settings-registry variables; this one is an auth switch, not a setting.
- **What B2c's keep-or-revert timer needs:** before applying a `PUT /auth/proxy`, take `Auth::proxy()`. If nobody confirms from a signed-in session within 5 minutes, call `Auth::set_proxy(previous)`. That call asks for no password, because the user already confirmed the change. Today a proxy change can't lock anyone out of a cookie session, so the timer matters only when B2c adds proxy-only modes.
- **Signing out other sessions** (`POST /sessions/revoke-others`) rotates the session key, as a password change does, and returns a new cookie for this browser. Trusted-proxy sessions aren't cookies, so they're unaffected.
- **At most 500 keys and tokens,** revoked ones included (409 `too_many_keys`), so the list and the per-key map stay small.
- **`ApiState.user_data`** is a read-write `Store` connection opened in `services.rs`, shared with B10a. The guards find it, with the `Auth`, in the request extension `router()` adds (`SessionAuth::of`).
- **Never logged or echoed:** secrets, their hashes (`Debug` of `Minted`, `Presented`, `Secret`, `CreatedKey` and the request DTOs redacts them), `Authorization` and `X-Api-Key` values, `apikey` and `token` values, and the proxy user header. A log-capture test runs every flow and checks for each one, plus the password and the session cookie.
