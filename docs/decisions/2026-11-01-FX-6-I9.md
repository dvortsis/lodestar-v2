# FX-6-I9 decisions (#350)

M5 design review finding I9: brushing the Size histogram wrote `size:1073741824..4294967295` into the query bar while the chip said "1.00 GiB to 4.00 GiB".

- **The canonical printer writes byte bounds in IEC units** (`KiB`, `MiB`, `GiB`, `TiB`), choosing the largest one that divides the value exactly; otherwise it writes plain bytes (§10.12's one formatter). It wrote `KB`/`MB`/`GB`/`TB` before. Every parser version reads both spellings as 1024-based. Counts (`files:`, `year:` …) keep plain numbers.
- **One-sided bounds one byte short of a unit, or one byte past it, print in their exclusive form.** `hi` = 16 GiB − 1 prints as `size:<16GiB`, and `lo` = 4 GiB + 1 prints as `size:>4GiB` (it was `size:>=4294967297`). The parser has always read `<x` and `>x`, so this text is safe to store.
- **The brush keeps its bound one byte short.** Histogram bins are `[lo, hi)` and query ranges are inclusive (`web/src/lib/features/search/facets/bins.ts`), and `brushOfRange` relies on the bound to light the right bins. Moving it to `4GiB` would add torrents of exactly 4 GiB and light the next bin.
- **New syntax `a..<b`: a range whose top stops short of `b`.** It's a refinement of the §8 query language, for the runner to flag to the owner (§2.19). `..<0` and an empty `..<` are errors. The arithmetic is checked, so `u64` edges can't overflow. Because `range()` is shared, counts and shares read the form too (`year:2019..<2021`), though nothing prints it for them. `docs/query-language.md` documents it.
- **Two-sided ranges don't print `..<` yet (content safety; runner's ruling after a security review).** Filter rules, `unless` queries, classification rules, allow entries and override scopes store canonical text. `crates/filter/src/load.rs` skips a stored row it can't parse, and a rollback keeps the store. So a hide, drop or quarantine rule written with `..<` would be skipped by the release before this one, which loosens filtering. The plan has two stages:
  - **Stage 1 (this PR):** the parser reads `a..<b`; the printer never writes it. A brushed range prints as `size:1GiB..4294967295`. Tests check this: a property test asserts that printed byte ranges never contain `..<`, and an API test stores a brushed range through every filter writer and reads plain text back.
  - **Stage 2 (one release after this one ships):** the two-sided arm prints `a..<b` again. A rollback goes back one version, and that version already reads the form.
- **I9 is only partly fixed until stage 2.** Units are readable wherever a bound is exact and on one-sided bounds. A brushed range's upper bound still shows in bytes.
- **Other stored text is unaffected.** Saved searches run from their AST JSON, the percolator runs ASTs, nothing writes `query_log` in production yet, and old URLs parse to the same AST. Nothing compares stored text with newly printed text.
- **The e2e mock printer is unchanged.** `web/e2e` checks the facet rail against a TypeScript stand-in for `/api/v1/parse` that prints bytes. It tests the AST edits, not the server's text, so this PR changes no web files. The stale OpenAPI example (`size:>=10GB` in `crates/api/src/dto/search.rs`) is queued as a separate follow-up.
