# ENR-2a decisions (shared bounded JSON reader)

Slice ENR-2a of `docs/plan/2026-11-04-v06-rulepacks.md` (§4.3, architecture §18.9). It moves the JSON reader SRC-9 wrote inside `archive_org.rs` (`docs/decisions/2026-11-02-SRC-9.md`) into `crates/sources-feeds/src/json.rs`, so ENR-2b (ThePornDB) and ENR-3 (StashDB) reuse the audited reader instead of copying it. No behaviour changes.

- **What moved, unchanged:** the tokenizer (whitespace, `eat`, the strict RFC 8259 string and number grammar, the literals), the depth and value counters with their stops (`Stop::Depth`, `Stop::Elements`, `Stop::Malformed`), the iterative `skip` with its `max_array` report, escape decoding (`decode`, `hex4`) and the end-of-document check. The code is the same code, line for line; only who owns the cursor changed.
- **What stayed in `archive_org.rs`:** everything IA-specific. The `Draft` and `FileDraft` state, the shapes, the string-or-array `strings`/`first` helpers, `count` and `digits`, and the field validators. `archive_org::Limits` keeps all eight fields and its defaults. It hands `max_depth`, `max_values`, `max_array` and `max_text` to the reader as `json::Limits`.
- **The API: a `Reader` plus a `Walk` trait.** `Reader` holds the cursor and the counters. `Walk::object` and `Walk::array` are trait methods, so a parser that holds a `Reader` implements `Walk` (one `json()` accessor) and its callbacks get the whole parser, item state included, as SRC-9's did. That kept the archive code's shape as it was, which makes the move reviewable as a move.
- **`Reader::text` returns the fault instead of spoiling an item.** It counts the value, reads the string, and returns `Ok(Err(TextError::OverCap))` over `max_text` (raw bytes, checked before decoding) or `Ok(Err(TextError::Malformed))` for a lone surrogate. The read goes on either way, as before. `archive_org` maps them onto its `Bad::OverCap` and `Bad::Malformed`, exactly where it spoiled the item before. The reader has no notion of an item: what a fault spoils is each parser's choice.
- **Who counts values:** `object`, `array`, `skip` and `text` count their own. `string` and `number` don't, because `string` also reads keys (which aren't values). A parser reading a number as a value calls `value()` first, as `archive_org::count` already did.
- **`json` is a public module.** The fuzz target and the integration tests use it from outside the crate. It's a building block for this crate's parsers, not for other crates: nothing outside `crates/sources-feeds` should read untrusted JSON with it instead of going through a parser that caps items and fields.
- **SRC-9's unit tests moved with their code where they test the reader.** `decodes_escapes` stays in `archive_org.rs` (importing `json::decode` and `json::hex4`) and is repeated in `json.rs`; no assertion changed. `archive_org_golden.rs`, `archive_org_limits.rs`, `archive_org_props.rs` and `fuzz_targets/archive_org.rs` are untouched and pass.
- **No behaviour change, checked differentially.** Before committing, a throwaway test (not committed) compiled SRC-9's `archive_org.rs` beside the new one and compared every emitted item and the whole `Page` (`Debug` output, byte for byte) on 10 million mutated fixtures (2.4 million of them with items) and 10 million random byte strings, half with `LIMITS` and half with tight caps picked as the fuzz target does. They matched on every input.
- **New tests for the reader's own API:**
  - unit tests in `json.rs`: every RFC 8259 refusal (trailing commas, single quotes, leading zeros, bare `.5`, `1.`, `1e`, `+1`, `NaN`, raw control characters, bad escapes, text after the root, input cut short), the depth cap counting open containers only, the value cap not counting keys, `max_array` reported and not stopped (including `0`), the text cap on raw bytes, raw keys, and a callback that reads nothing failing as `Malformed`;
  - `tests/json_props.rs`: any generated document reads back exactly (strings decoded, keys raw, numbers as written), with and without `\u` escapes; each structural cap holds exactly (stop iff the document's depth or value count is over it, `skip` reports an array over `max_array` iff the longest is); the text cap is on raw bytes; on any input, walking with `object`/`array`/`text` stops with the same `Stop` as `skip`; a million open brackets stop at the cap without recursion.
- **Fuzz target `fuzz/fuzz_targets/json.rs`.** The first byte picks tight caps. On any input, walking and skipping agree on the stop, and a stop is one of the three kinds. **It also checks against `serde_json`** (already a dependency of the fuzz crate, not of `sources-feeds`): whatever `serde_json` accepts, the reader accepts with wide caps and reads to the same tree. The reverse doesn't hold by design: the reader only scans a lone surrogate escape, and accepts numbers `serde_json` can't fit in an `f64`. CI's fuzz matrix lists `fuzz/fuzz_targets/*.rs` itself. No seeds directory was added (`fuzz/seeds/` isn't in this slice's paths); `fuzz/seeds/archive_org/` makes a good starting corpus.
