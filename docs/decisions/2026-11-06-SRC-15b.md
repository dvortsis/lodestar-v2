# SRC-15b decisions (Sources: consent dialogs and purge)

Slice SRC-15b of `docs/plan/2026-11-01-v06-sources.md`. It covers architecture §18.7, §18.8 and §10.10.7, owner decision §2.49, and the runner's narrowing of the slice (2026-11-06T21:30Z).

## What ships, and what moves to SRC-15c

- **Ships:** the External, Restricted and Overlay consent dialogs, the purge flow, and a strings test for all four approved texts.
- **Moves to SRC-15c (runner, 2026-11-06T21:30Z):** the Account dialog and the generated config forms. The API doesn't expose what they need. A plugin declares no credential spec, `config_schema` isn't in `GET /sources`, and there is no purge preview count. The runner adds them in the new slice X-sources-api-spec.
- **Until SRC-15c lands, an Account source keeps SRC-15a's "needs setup" state.** Its toggle stays off and there is no credentials UI. The Account text is already in en.json and zh.json, and the strings test checks it through `consent.ts`, so SRC-15c only has to place it in a dialog.

## The dialogs

- **The text is the approved text.** It is `docs/decisions/2026-11-02-SRC-4.md` "Draft consent texts" with owner §2.49's Account change. en.json holds it once. `consent-approved.fixture.ts` is a separate copy, and `dialogs.test.ts` fails when the two differ.
- **zh is a translation.** The English text is the approved one; the Chinese strings have not been approved by the owner and need a native review.
- **Fill-ins:**
  - `{hosts}`: the distinct host names of `Source.endpoints`. The row still lists the full addresses, as SRC-15a does.
  - `{egress}`: the label of `egress.setting.route` ("direct connection", "SOCKS5 proxy", "bound network interface"). An unset route reads as direct.
  - `{network}`: the first entry of `Source.networks` that isn't `bt`, else the source's name. A source with several networks shows the first only; the manifest has no display name for a network (follow-up for X-sources-api-spec).
- **The UI never decides that consent is satisfied.** A dialog opens when the row's own `needs` or `password_required` says so, and it sends `enabled: true` with `consent` and the `consent_version` the server gave, plus `password` for Restricted and Overlay. Whatever the server answers is shown: the new row when it takes the change, or the refusal.
- **The X-consent-gate-052 refusal** (`400`, `field: "enabled"`, reason `CONSENT_GATE_REASON`) is shown with the server's own reason, then "Nothing was changed". The dialog stays open and the source stays off. Today the server refuses External, Restricted and Overlay this way. Lifting the gate is the separate Opus follow-up. The tests cover the refused path and an accepting server.
- **Restricted and Overlay** start with focus on Cancel and ask for the password every time (SRC-4's tightening of Q13). A wrong password (`401`) clears the field.
- **`SourcePatch.password` isn't in `openapi.json`** (it is never serialized in Rust). The screen's `EnableBody` adds it in the client. Follow-up: list it in the schema.

## Purge

- **The server asks for the admin password on every purge** (`428 confirm_required`, `401`), so the dialog does too. This is stricter than §10.10.7 and plan Q13 ("no password"). The runner confirmed the server's rule (2026-11-06T21:30Z) and settles the docs.
- **No count before the run.** §10.10.7 wants the exact count and size before the user commits, but the API has no preview. The dialog names the categories (claims, unverified items, credentials and settings, the consent record) and shows the `PurgeJob` counts after the run. X-sources-api-spec adds the preview count; SRC-15c shows it.
- **Progress** polls `GET /jobs/{id}` every second until the job leaves `running` and `paused`. The result comes from the job's own state.

## `consent::text_version`: no change

- **Account needs no bump.** An Account source's consent is given by saving credentials, not by an acknowledgement. No ack record exists for it, and `text_version(Account)` is 0, so it is never compared. Changing the Account text therefore changes nothing for an enabled source.
- **External, Restricted and Overlay** are unchanged since `f3222361` (§2.49), so no bump is needed either.

## Size gate

- **The dialogs load on first use** through one hop, `dialogs-root.ts`, so their preload lists stay out of the screen's chunk (as `body.ts` does for the screen). Their chunks import the SourcesScreen chunk, which holds the modules they share with it, so `web/.size-limit.mjs` gets what `filtersLater` has: a `sourcesLater` exemption in `staticHits`, those files in the Sources first view's `stop` list, and a "Sources dialogs (on demand)" entry.
- **Numbers:** the dialogs measure 35.6 KB gzipped, limit 36 KB. The Sources first view was already at 29.97 KB of its 30 KB. The loader, the dialogs' state and the Purge button add 0.57 KB, so it measures 30.54 KB and its limit is 30.9 KB (a 0.9 KB raise). Both are runner calls under §2.26 and are flagged in the PR.
- **A slow chunk:** the toggle puts itself back, nothing is sent, and the dialog opens when its code arrives. If the code can't load, the screen says it couldn't reach Lodestar.

## Errors the server sends

- **A refused `enabled`** carries the server's own sentence (`"The setting wasn't saved: …"`, code `invalid_setting`). The dialog shows it as it is, then "Nothing was changed". That covers the consent gate and "purge it again to finish".
- **A wrong password** is `401 bad_password`. Any other `401` (an expired session) isn't called a wrong password.
- **A changed notice** (`409 consent_required`) reloads the list, so the next try sends the new version.
- **Network names:** the API sends `bt_i2p`, `ed2k`, `ipfs` and `usenet`. The text shows I2P, eD2k, IPFS and Usenet.
