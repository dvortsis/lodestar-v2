# M6-win decisions (#98)

Slice M6-win (build plan P3 [M], architecture §11). Code in
`crates/lodestar/src/windows/`, one hook in `main.rs`, and `SO_LINGER(0)` in
`crates/peer-wire/src/fetch.rs`.

## Service entrypoint
- **Name and image path.** The service is `Lodestar`. The installer registers
  `"<install dir>\lodestar.exe"`, optionally with `--config <path>` (an
  optional `serve` is accepted too). No subcommand marks a service start.
- **How a service start is recognised.** `main` first calls `windows::hook()`.
  It parses the arguments without exiting (`Cli::try_parse_from`). Only a
  serve command line (no command or `serve`, with an optional `--config`) goes
  further: when stdin isn't a terminal, it asks the SCM
  (`StartServiceCtrlDispatcher`). An ordinary run gets
  `ERROR_FAILED_SERVICE_CONTROLLER_CONNECT` at once and carries on as before.
  - A console run never asks the SCM.
  - `healthcheck`, `backup` and other commands never ask it either, even from
    a scheduled task or a child process with no console.
  - The CLI (M6-cli) needs no service subcommand.
  - The later `update-helper` (§12.2) is a separate process, which this
    doesn't preclude.
- **Data.** `%ProgramData%\Lodestar` unless `LODESTAR_DATA_DIR` or the config
  file sets one. The service runs from that folder, so relative paths in the
  config land there. Without `--config`, the config file is `config.toml` in
  that folder (or in `LODESTAR_DATA_DIR`).
- **Controls.** Stop, Shutdown and Preshutdown all trigger the same graceful
  shutdown as Ctrl+C.
  - The service reports Running as soon as it has registered, because opening
    a large store can outlast the SCM's start wait and `/healthz` already says
    when it's ready.
  - The control handler reports StopPending itself, at once, so a stop during
    start is acknowledged. A stop while the store is still opening ends the
    start: `Services::start` is raced against the stop.
  - While stopping, the service reports a new checkpoint every 5 s (wait hint
    30 s), so a long final commit isn't taken for a hang.
- **Exit codes.**
  - A clean stop reports `NO_ERROR`.
  - A stop on an error reports service-specific code 1, so the recovery
    actions the MSI configures apply.
  - A start refused because the data folder isn't safe reports
    service-specific code 3, the CLI's "refused for safety". Nothing was read
    or written, so there's no log line; `sc query Lodestar` shows the code.

## The data folder's permissions (§11, §12)
- **The problem.** `%ProgramData%` lets every local user read, and create
  folders and files. A folder created there inherits that: `Users` get
  `(OI)(CI)(RX)` and `(CI)(WD,AD)`. The 0600 modes on `auth.json` and the
  other secret files are Unix-only. So in `%ProgramData%\Lodestar`, any local
  user could:
  - read `auth.json` (the session key) and forge an admin session;
  - read the setup token in the log, and the database;
  - before the first start, plant a `config.toml`, an `auth.json` or a `logs`
    junction that the service would then use.
- **The fix.** Before anything in the folder is read or written, at every
  start, the service makes sure it's private (`windows::acl`). The workspace
  forbids `unsafe`, so it reads security descriptors with PowerShell's
  `Get-Acl` (SDDL, which isn't localised), and sets them with `icacls`, and
  reads its own SID with `sc showsid`, all by absolute path.
  - **Private means all of these.**
    - **The folder's owner** is `SYSTEM` or `Administrators`, as the
      installer makes it (not even the service). An owner can always rewrite
      the ACL, so a private-looking DACL on a folder a user owns isn't
      private.
    - **The DACL** is protected (nothing inherited from `%ProgramData%`), and
      its allow entries are only for those two and the service's own SID
      (`NT SERVICE\<name>`). Shared service accounts
      (LocalService, NetworkService) and other services' SIDs are refused:
      many services run as LocalService, and any of them could otherwise
      read `auth.json`.
    - **Parsed strictly.** Flags may only be `P` (required), `AI` and `AR`. A
      NULL DACL (`NO_ACCESS_CONTROL`) is refused. Entries may only be allow
      (`A`, for those SIDs) or deny (`D`); object, conditional and any other
      entry types are refused, as is anything unparsed.
    - **Every entry directly in the folder** is owned by `SYSTEM`,
      `Administrators` or the service, and **nothing anywhere beneath it** is
      a link, junction or other reparse point. An entry a user owns, or a
      link, could have been planted before the folder was private.
  - **A missing folder** is created with its final ACL in one step (.NET
    `Directory.CreateDirectory` with a `DirectorySecurity`, through Windows
    PowerShell 5.1), so no handle can be opened while it's still open to
    Users. Under Constrained Language Mode that call isn't allowed. Lodestar
    then creates the folder and takes it over, and the inspection that
    follows catches anything added in between.
  - **A folder that isn't private** is taken over only while it's empty: owner
    `Administrators` (when the account may set it) and the protected ACL. It
    then has to pass the inspection again.
    - Only the folder is changed, never what's beneath it (no `/T`).
    - `icacls /L` acts on a link itself, never its target. A user who swaps
      the folder for a junction between the inspection and the take-over
      can't redirect the change, and the second inspection refuses the link.
  - **Otherwise it refuses**, with code 3, untouched:
    - a folder that is a link;
    - a folder that isn't private and holds anything;
    - a folder holding a link or an entry someone else owns.
  - **Folders an administrator chooses.** The default folder is used, and so
    checked, only when it's where the config or the data lives. With
    `--config` or `LODESTAR_DATA_DIR` pointing elsewhere, and a `data_dir`
    elsewhere, it isn't created or required. A folder an administrator
    chooses keeps the permissions the administrator gave it.
- **What remains.**
  - A hard link in the folder to a file `SYSTEM` or `Administrators` owns
    shows that owner. Since 2019, Windows needs write access to a file to
    create a hard link to it, so a user can only link files they could
    already change.
  - Owners deeper than the top level aren't inspected: such entries can
    only be put there through a top-level entry, which is. Links are looked
    for at every depth.
- **The installer applies the same rules** (`packaging/windows/
  secure-datadir.ps1`, recorded in `docs/decisions/2026-10-22-P-release.md`,
  which points here). **The two must stay in step:** a change to one is a
  change to both.
  - The service also takes over an empty folder that isn't private, where
    its account may; the installer re-applies its ACL instead.
  - The `.lodestar-secured` marker is a hint only. The service writes it once
    the folder passes, so a reinstall over existing data finds it. Nothing
    trusts it: both check owners, the ACL and links whether it's there or
    not.
- **For P-release (the MSI), required (#92 does all of it).**
  - Create `%ProgramData%\Lodestar` empty, owned by Administrators, with
    inheritance removed and full control for `SYSTEM`, `Administrators` and
    `NT SERVICE\Lodestar`.
  - Create the folder with that ACL in one step, so no handle is opened in
    the window with the inherited one.
  - If the folder already exists with a foreign owner, stop and ask rather
    than adopt it.
- **The service account: `NT SERVICE\Lodestar`, a virtual account, as the
  MSI (#92) installs it.**
  - LocalSystem is the most privileged account on the PC. A bug in a program
    that parses untrusted network input (the DHT, the peer wire, metadata)
    would hand an attacker the whole machine.
  - A shared account like LocalService would let every other service running
    as it read `auth.json`. The virtual account's own SID keeps the folder to
    Lodestar alone.
  - It has no password to manage, and no rights beyond the folder the
    installer grants it.

## Logging under the service
- A service has no console, so it logs to `<data>\logs\lodestar.log` (plain
  text, the console format). This is where the first run's setup token
  appears, and why the folder's ACL matters.
- The file rotates once at 16 MiB to `lodestar.log.1`, so the folder never
  holds more than 32 MiB. A failed rotation keeps appending rather than
  dropping lines.
- This is a stand-in until §12.1's structured `lodestar.jsonl` and the Windows
  Event Log output exist (the §12.1 logging slice).
  - Until then, a log level saved in Settings applies to the service only at
    its next start. The live reload handle is private to `settings::log`,
    whose `init` writes only to stderr.
  - A follow-up there (an `init` that takes a writer) fixes it.

## Below-normal priority
- On by default for the service and for `lodestar serve` on Windows.
  `LODESTAR_PRIORITY=normal` turns it off. (`config.toml` keys are
  `config.rs`'s to add; an environment variable needed no shared change.)
- The workspace forbids `unsafe`, so the priority is set by running
  `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe` by absolute
  path, the way the key file's ACL uses `icacls`. It runs on a background
  thread so it doesn't delay the start.
- **The trade-off, accepted for now:**
  - An unsigned program (Windows builds ship unsigned, owner 2026-10-23) that
    starts `powershell.exe` at every start is the kind of thing EDR products
    and Defender's behaviour rules flag.
  - Under AppLocker or PowerShell's Constrained Language Mode, the command can
    fail. That failure is logged as a warning, and Lodestar runs at normal
    priority.
  - The alternative is one `SetPriorityClass` call. That needs `unsafe`, and
    an exception to the workspace's ban is the owner's call, not this
    slice's.

## Ephemeral-port warning
- At start, Lodestar reads the IPv4 and IPv6 TCP dynamic ranges and the
  excluded (reserved) ranges inside them through `netsh`. Translated labels
  are handled by taking the numbers after the colons.
- **Threshold.** It warns when the available ports are fewer than
  `2 × max_sockets + 2048`.
  - With `SO_LINGER(0)`, a closed fetch holds no port, so the steady need is
    about one port per open socket.
  - Twice that covers sockets still connecting or closing, and the tracker
    and integration clients. 2,048 is left for the rest of the PC.
  - Windows' default range (16,384) suits every preset. The XP-era 1025–5000
    range suits Balanced but not Aggressive. A Hyper-V reservation that takes
    most of the default range warns at any preset.
- **The fix.** The warning gives the `netsh int ipv4|ipv6 set dynamicport tcp
  start=… num=…` command.
  - The suggested range is Windows' default when that's enough. Otherwise
    it's the needed size plus the reserved ports, rounded up to 1,024 and
    ending at 65535.
  - It tells the reader to check the excluded ranges again afterwards, since
    Hyper-V and WinNAT can reserve more.
  - It also suggests lowering the intensity or `max_sockets` instead.
- The dashboard's "ephemeral-port pressure" exception (§10.9) is later work.
  `windows::ports` is the logic it can reuse.

## SO_LINGER(0)
- **This widens §11.** §11 lists `SO_LINGER(0)` "for failed handshakes". This
  slice sets it on every outbound peer TCP connection (`peer-wire` `fetch`),
  on Windows.
  - Failed handshakes alone don't fix the problem the brief names: thousands
    of successful short fetches a minute, each leaving its port in TIME_WAIT
    for 120 s.
  - Nothing is in flight when a fetch ends: the metadata has arrived or the
    fetch has failed, and Lodestar sends nothing after it. So the reset loses
    nothing. The peer sees a RST instead of a FIN, which BitTorrent clients
    treat as an ordinary disconnect.
- Windows only, because there's no measurement elsewhere. Linux's default
  range is larger (28k ports), and macOS holds TIME_WAIT for 30 s, not 120 s.

## mmap delete-retry: already covered
- Index directories are renamed and deleted with backoff retries, and
  whatever is left is retried at the next start (B5a/B5b,
  `search/rebuild.rs`).
- Tantivy's own segment GC keeps a file it couldn't delete in its managed list
  and retries it at the next GC. It expects that failure on Windows.
- Hot columns are in-memory atomics, not mapped files (§16, M4). SQLite
  manages its own mapping.
- So this slice adds no delete-retry code.

## For P-release (the MSI): the rest
- **Service.**
  - Install it as `Lodestar`, start type Automatic (Delayed Start), account
    `NT SERVICE\Lodestar` (above).
  - Set failure actions to restart, with `FailureActionsOnNonCrashFailures`,
    so exit codes 1 and 3 count. A code-3 refusal will keep failing until an
    administrator fixes the folder, so cap the restarts.
  - `PreShutdownDelay` (`SERVICE_CONFIG_PRESHUTDOWN_INFO`) of 60 s, which
    #92 sets. The service accepts Preshutdown, but Windows 10 1703 and later
    wait only 10 s by default, which can cut the final commit short.
- **Firewall.** Rules scoped to the program (`lodestar.exe`):
  - the DHT port, for the protocols Lodestar listens on there (UDP for the
    DHT and uTP);
  - the Private profile only, by default;
  - the UI port is not opened to the network unless the user chooses to.
- **Defender exclusion.** Opt-in, explained, and removed on uninstall (§11).
- **Uninstall.** Stop and delete the service, and remove the firewall rules
  and the exclusion. Keep `%ProgramData%\Lodestar` unless the user asks to
  remove their data.
