# M6-win: Windows runtime

Slice M6-win (build plan P3 [M], architecture §11). Code in
`crates/lodestar/src/windows/`, one hook in `main.rs`, and `SO_LINGER(0)` in
`crates/peer-wire/src/fetch.rs`.

## Service entrypoint
- **Name and image path.** The service is `Lodestar`. The installer registers
  `"<install dir>\lodestar.exe"`, optionally with `--config <path>` (an
  optional `serve` is accepted too). No subcommand marks a service start.
- **How a service start is recognised.** `main` first calls `windows::hook()`.
  When stdin isn't a terminal, it asks the SCM (`StartServiceCtrlDispatcher`);
  an ordinary run gets `ERROR_FAILED_SERVICE_CONTROLLER_CONNECT` at once and
  carries on as before. A console run never asks. This keeps the CLI (M6-cli)
  free of a service subcommand, and the later `update-helper` (§12.2) is a
  separate process, which this doesn't preclude.
- **Data.** `%ProgramData%\Lodestar` unless `LODESTAR_DATA_DIR` or the config
  file sets one. The service runs from that folder, so relative paths in the
  config land there. Without `--config`, the config file is `config.toml` in
  that folder (or in `LODESTAR_DATA_DIR`).
- **Controls.** Stop, Shutdown and Preshutdown all trigger the same graceful
  shutdown as Ctrl+C. The service reports Running as soon as it has
  registered, because opening a large store can outlast the SCM's start wait
  and `/healthz` already says when it's ready. While stopping it reports
  StopPending with a checkpoint every 5 s (wait hint 30 s), so a long final
  commit isn't taken for a hang.
- **Exit codes.** A clean stop reports `NO_ERROR`. A stop on an error reports
  service-specific code 1, so the recovery actions the MSI configures apply
  (P-release should set "restart" with `FailureActionsOnNonCrashFailures`).
- **Account.** Not decided here: the MSI (P-release) chooses it. The
  recommendation is the virtual account `NT SERVICE\Lodestar` with modify
  rights on `%ProgramData%\Lodestar`, rather than LocalSystem.

## Logging under the service
- A service has no console, so it logs to `<data>\logs\lodestar.log` (plain
  text, the console format). This is where the first run's setup token appears.
- The file rotates once at 16 MiB to `lodestar.log.1`, so the folder never
  holds more than 32 MiB. A failed rotation keeps appending rather than
  dropping lines.
- This is a stand-in until §12.1's structured `lodestar.jsonl` and the Windows
  Event Log output exist (the §12.1 logging slice). Until then a log level saved in Settings
  applies to the service at its next start: the live reload handle is private
  to `settings::log`, whose `init` writes only to stderr. A follow-up there
  (an `init` that takes a writer) fixes it.

## Below-normal priority
- On by default for the service and for `lodestar serve` on Windows.
  `LODESTAR_PRIORITY=normal` turns it off. (`config.toml` keys are
  `config.rs`'s to add; an environment variable needed no shared change.)
- The workspace forbids `unsafe`, so it's set through
  `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe` by absolute
  path, like the key file's ACL through `icacls`. It runs on a background
  thread so it doesn't delay the start.

## Ephemeral-port warning
- At start, Lodestar reads the IPv4 and IPv6 TCP dynamic ranges and the
  excluded (reserved) ranges inside them through `netsh`. Translated labels are
  handled by taking the numbers after the colons.
- **Threshold.** It warns when the available ports are fewer than
  `2 × max_sockets + 2048`. With `SO_LINGER(0)`, a closed fetch holds no port,
  so the steady need is about one port per open socket. Twice that covers
  sockets still connecting or closing and the tracker and integration clients,
  and 2,048 is left for the rest of the PC. Windows' default range (16,384)
  suits every preset. The XP-era 1025–5000 range suits Balanced but not
  Aggressive. A Hyper-V reservation that takes most of the default range
  warns at any preset.
- **The fix.** The warning gives the `netsh int ipv4|ipv6 set dynamicport tcp
  start=… num=…` command: the default range when that's enough, else the
  needed size plus the reserved ports, rounded up to 1,024 and ending at 65535.
  It also suggests lowering the intensity or `max_sockets` instead.
- The dashboard's "ephemeral-port pressure" exception (§10.9) is later work.
  `windows::ports` is the logic it can reuse.

## SO_LINGER(0)
- Every outbound peer TCP connection (`peer-wire` `fetch`) gets an abortive
  close on Windows. Nothing is in flight when a fetch ends, so the reset loses
  nothing.
- Windows only, because there's no measurement elsewhere. Linux's default
  range is larger (28k ports), and macOS holds TIME_WAIT for 30 s, not 120 s.

## mmap delete-retry: already covered
- Index directories are renamed and deleted with backoff retries, and
  whatever is left is retried at the next start (B5a/B5b, `search/rebuild.rs`).
- Tantivy's own segment GC keeps a file it couldn't delete in its managed list
  and retries it at the next GC. It expects that failure on Windows.
- Hot columns are in-memory atomics, not mapped files (§16, M4). SQLite
  manages its own mapping.
- So this slice adds no delete-retry code.
