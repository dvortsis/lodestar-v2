# X-thp-off decisions (#434, transparent huge pages off for the worker)

Runner brief X-thp-off, 2026-11-04 (Track R, the r4 contingency, memory fix 3; auto-approved under owner §2.33). Architecture §11 (the binary and its allocator) and §12.2 (the supervisor and its `--child`). Follows `2026-11-04-X-merge-policy.md` and the owner's soak memory review (#425, §2 point 2).

## Why
- **Soak r4 (rc.3, baseline hour about 17, read-only host reads):** the worker (`lodestar serve --child`) had RssAnon 492 MiB, of which AnonHugePages was 212 MiB (44%). RssFile was 14 MiB, so it isn't the index's mmaps.
- **The live heap is flat.** X-merge-policy measured the whole indexing path at about 2.7 KiB retained per torrent at a soak-sized corpus, with a flat dhat live heap. r4's provisional slope was about 19 KiB per torrent. So the growth is retained or inflated pages, not live data.
- **The mechanism:** mimalloc v3 defaults `allow_thp` to 1 and advises `MADV_HUGEPAGE` on its large OS allocations. With the host's THP mode at `always`, or at `madvise` given that advice, khugepaged collapses sparsely used 2 MiB ranges of the arenas into huge pages. Each collapse makes the whole 2 MiB resident, so resident memory grows while the heap doesn't. That fits r3 and r4's slow climb and their steps.

## What changed
- **`prctl(PR_SET_THP_DISABLE, 1)` first thing in `main`** (`crates/lodestar/src/thp.rs`, called before `windows::hook`, argument parsing, the privilege drop and any thread). Linux only; other systems compile it to nothing. Through rustix's safe `thread::disable_transparent_huge_pages`, since the workspace forbids `unsafe`.
  - **It's process-wide:** the kernel keeps the flag on the address space (`MMF_DISABLE_THP`), not the calling thread, whatever rustix's doc comment says. The unit test checks it from a second thread.
  - **It reaches the worker:** the flag is inherited across `fork` and kept across `execve`, so the supervisor's `--child`, a re-exec (`system::restart::reexec`) and every maintenance command carry it. The worker also calls `thp::apply` itself.
  - **It covers every heap.** SQLite, C zstd and ring allocate through musl's mallocng (or glibc's malloc), not mimalloc, because mimalloc's `override` feature is off (#425 §2 point 2). The prctl covers those too. From the call on, no mapping gets a new huge page, whether made before it or after (khugepaged included), and the kernel ignores `MADV_HUGEPAGE`. Huge pages already faulted in before `main` stay until they're freed; at that point there are hardly any. **This is the switch that takes effect.**
- **`MIMALLOC_ALLOW_THP=0` in the worker's environment** (`crates/lodestar/src/update/supervisor.rs`, `Supervisor::spawn`), on Linux only: the supervisor also runs on macOS, which has no THP. mimalloc initialises before `main`, because the Rust runtime allocates first, and setting the option from Rust (`mi_option_set`) needs `unsafe`. So it can only reach a process about to start. With it, the worker's mimalloc stops advising `MADV_HUGEPAGE` (v3 `prim.c`). It also calls `PR_SET_THP_DISABLE` itself (v3 `prim.c`), so it would hold even if the first switch failed. **It covers only mimalloc.** Both are kept, because together they cost one syscall and one environment variable (runner, 2026-11-04).
- **Not `libmimalloc-sys`'s `no_thp` feature.** It removes the `MADV_HUGEPAGE` call at compile time. That would take away the escape hatch for mimalloc, it would still leave the C heaps and the kernel's `always` mode to the prctl, and it needs a `Cargo.toml` change this slice doesn't own.
- **The supervisor itself** gets only the prctl: it was started before Lodestar could set its environment. It's small and single-threaded until it spawns the worker.
- **Which switch takes effect is read from the sources, not measured apart.** The measurement's "off" arm sets both. The prctl alone covers every heap and every mapping, and the kernel checks it before any `MADV_HUGEPAGE` advice, so it decides on its own. The mimalloc option adds nothing the prctl doesn't already do, beyond saving the advice syscalls.
- **Problems are printed, never fatal.** If the prctl fails (no such kernel feature, a seccomp filter), Lodestar prints one line to stderr and starts as before: THP only costs memory.

## The escape hatch
- **`LODESTAR_THP=allow`** restores the previous behaviour: neither switch is touched. The value `off` (or unset or empty) is the default. Any other value keeps THP off and prints a warning naming the value, so a typo can't silently turn it back on. The supervisor prints the warning; its worker, which inherits the value, doesn't repeat it. Case and surrounding space are ignored.
- **In the default mode, the worker's `MIMALLOC_ALLOW_THP` is always 0,** even if the operator set another value in the container. `LODESTAR_THP=allow` is the only supported way back.
- **It isn't a setting** and stays out of `config::ENV_VARS`, like `LODESTAR_SUPERVISOR`. It's read once at start, so it can't change at run time and isn't shown in Settings.
- **Under `allow`, an inherited flag is left as it is.** If something above Lodestar already disabled THP (a container runtime, a parent process), `allow` doesn't clear it.
- Documented in `docs/user/appendix-b-settings-reference.md`, beside `LODESTAR_LOG`.

## Measurement
Local, in a cloud container on 4 cores. **Its THP mode booted as `madvise`.** It was set to `always`, the owner's Unraid setting, for every run below. The container's kernel, memory and khugepaged pace still differ from the owner's host. The harness sets each arm from outside: "on" is as before, and "off" sets `PR_SET_THP_DISABLE` and `MIMALLOC_ALLOW_THP=0` before exec, which is what the worker now gets. A 1 s sampler reads `Anonymous` and `AnonHugePages` from `/proc/<pid>/smaps_rollup`, and `THP_enabled` from `status`.
- **Harnesses:**
  - X-merge-policy's `mem-merge` (`ingest default 20000 --docs 1`), from its branch at `c506450`, because it isn't on `main` yet. It gives 20,000 synthetic torrents at 1 document per commit, both tantivy writers, every torrent inserted into SQLite through the store's zstd file-tree codec, and its slope column (the least sample per 250 torrents).
  - `bench/examples/mem-ingest.rs` (`20000 200`), for the whole ingest pipeline (intake, writer, SQLite, hot columns, live index). It commits in batches, not 1 document per commit.
- **Runs:** two arms ran at once, on and off side by side, to share the noise.

- **Slope units:** `mem-merge` slopes are MiB per 1,000 torrents, the OLS fit from 2,000 torrents on, with its 95% CI. `mem-ingest` slopes are that harness's own second-half figure, in KiB per torrent.
- **Note on "Anon at 20k":** for `mem-merge` it's the harness's own figure, the least `Anonymous` sample after each commit in the last 250-torrent row (so a merge in flight doesn't count). For `mem-ingest` it's `Anonymous` at the end of the run.
- **The switch works.** Every "off" process read `THP_enabled: 0` and had no huge pages at any sample. Every "on" process had up to 118–192 MiB of them, about a third of its anonymous memory on average.
- **The full pipeline holds 57–68 MiB less with THP off** at 20k torrents (`mem-ingest`, gnu and musl), and its baseline is 12 MiB rather than 26–28 MiB.
- **The growth slope isn't separable here.** In `mem-merge`, the runs within an arm spread as widely as the arms differ, as X-merge-policy found (its arm D2, `MIMALLOC_ALLOW_THP=0` in `madvise` mode, looked like A). At 20k torrents, over minutes, khugepaged has little time to collapse ranges. The soak's climb took hours. `mem-ingest`'s second-half slope is higher with THP off (1.5 against 1.0 KiB per torrent on gnu, 1.1 against 0.4 on musl), but from a lower start. With huge pages on, its memory is already resident early, so less of the growth shows later. One run per arm can't tell those apart. **So the harness confirms the mechanism and the level, not r4's slope.** Soak r5 is the acceptance.
- **Performance is unchanged within noise.**
  - Ingest: each off run took as long as its on pair (gnu 1,120 / 981 s against 1,119 / 972 s; musl 743 / 774 s against 720 / 777 s).
  - Search and commit latency during ingest (`mem-merge latency default 5000`, musl, one process at a time, 2 runs per arm): commits p50 26.5–27.3 ms, p95 46.9–48.4 ms off, against 25.6–27.2 ms and 48.1–48.3 ms on. Search p50 0.08–0.09 ms, p95 0.24 ms off, against 0.09 ms and 0.24–0.25 ms on.
- **Not covered:** the real network fetch path (DHT and peer wire), and the owner's kernel.

## Tests
- **Unit (`thp.rs`):** unset, empty and blank are off; `allow` and `off` in any case and with surrounding space; any other value is off and reported, trimmed; only the off mode adds `MIMALLOC_ALLOW_THP=0` to the worker's environment; on Linux, `disable` sets the flag and a second thread sees it.
- **Integration (`crates/lodestar/tests/thp.rs`, Linux):** starts the real binary as the supervisor and finds the worker once it has exec'd (its `environ` holds the supervisor's hint). It checks `THP_enabled` in `/proc/<pid>/status` for both, which reports the flag `PR_GET_THP_DISABLE` returns (that prctl can only read the caller's own flag). It also checks the worker's environment. Three cases: the default (both disabled, `MIMALLOC_ALLOW_THP=0` set), an unknown value (disabled), and `allow` (both enabled, no mimalloc variable). The `allow` case is skipped if the test process itself already has THP disabled. All waits poll with a 60 s deadline.

## Delta note
- **This is a process-level change.** It doesn't alter any data structure, format or budget. It changes what the kernel and the allocator do with the same allocations.
- **The local harness shows the mechanism, not the soak.** The container's THP mode differs from Unraid's, and the harnesses don't exercise the real network fetch path. **Soak r5 is the acceptance:** AnonHugePages in the worker's `smaps_rollup` should read near 0, and the RssAnon slope is the judge.
