# X-sec-S8-01 decisions (#869)

S8-01 (important), data folder file modes. The detail stays with the runner (`docs/security/v1/README.md` §5); this file records only what the code now does.

## What the code does
- **The data folder is owner-only on Unix (0700).** So every store, index and snapshot file under it is closed to other users, whatever mode each file gets.
  - **A folder Lodestar creates** is made so: `crates/lodestar/src/data_dir.rs` (`ensure`) creates any missing parents with the default mode and the folder itself 0700.
  - **An existing folder Lodestar's user owns** is made so at start (`data_dir::secure`, from `Services::start`), the same way `logging/file.rs` already treats the logs folder. The change goes through a descriptor opened without following a link, so a symlinked data folder is never changed.
  - **A folder another account owns** is never changed. If its group or others have any access, the start logs one warning, the catalogued event `system.data_dir_open`. The user guide (3.7, "Keep the data folder owner-only") gives the command to run as that account.
- **No process-wide umask.** Outputs and companion files are written for other apps' users to read, for example Unraid containers under other user IDs. A global umask would break them.
- **Files outside the data folder that hold the same data:**
  - **Backups:** `lodestar backup --to <folder>` already writes a new 0700 folder. The store copy in it is set to 0600 once written, and the other files are created 0600. Nothing changes there.
  - **Everything else:** every other store, snapshot, rollback and index path sits inside the data folder (the store, the index, the pre-migration snapshots, rollback's kept copy and `vacuum`'s staged copy all derive from it), so the folder's mode covers them.
- **Windows is unchanged.** The installed service's folder is already limited by its ACL. A non-default folder isn't ACL-checked, which `update/layout.rs` already documents.
- **The store crate isn't touched.**

## Tightening a folder Lodestar's user owns (the runner's call)
- **Why:** Docker creates a missing bind-mount folder as root with 0755, so Lodestar never creates it. That covers the Unraid template, the fleet's `./data` and the README's `-v "$PWD/data:/data"`. The PUID hand-over then gives it to Lodestar's user and leaves it 0755. Without this step, the main platform would get a warning on every start and no fix.
- **What it changes on upgrade:** an existing data folder that Lodestar's user owns and that's open to its group or others becomes 0700 at the first start. The runner flags this to the owner, because it changes existing installs.
- **Who is unaffected:** a folder another account owns is never changed, only warned about.

## The hand-over checks the owner without read access
- **The hand-over reads the folder's owner through an `O_PATH` descriptor** (`privdrop.rs`, `chown_data_dir`), which needs no read access. A folder already the target account's is never opened for reading. Only a folder that must be walked and chowned is opened for reading, through that same descriptor.
- **Why:** under `cap_drop: ALL` with only CHOWN, SETUID and SETGID kept, as `packaging/docker/README.md` and the fleet's compose file run it, root has no DAC_OVERRIDE. It can't open an owner-only folder it doesn't own for reading. Without this, a 0700 `/data` (a new named volume on the new image, or a bind mount someone tightened) would stop the container at start.
- **No capability is added.**
- **Tested:**
  - a unit test of the decision;
  - a test that an owned folder with no read access at all (mode 0) still passes, which fails with the old read-open when run as a normal user;
  - the release smoke now also starts the image with `--cap-drop ALL --cap-add CHOWN --cap-add SETUID --cap-add SETGID` on a new named volume.

## The packaging, before and after
- **Before** (checked before choosing):
  - **Docker image** (`packaging/docker/Dockerfile`): it starts as root only to apply PUID/PGID, then hands `/data` to PUID:PGID (default 65532) and drops root (`privdrop.rs`). It shipped `/data` empty, owned by 65532 and created with `mkdir -p`, so 0755. A new named volume copied that mode, and a bind mount kept the host's.
  - **Unraid template** (`packaging/unraid/lodestar.xml`): `/data` is a bind mount of `/mnt/cache/appdata/lodestar`, with PUID 99 and PGID 100. Docker creates a missing host folder as root with 0755, and the start then hands it to 99:100.
  - **systemd:** the unit already creates the folder owner-only (`StateDirectoryMode=0700`, `UMask=0077`).
- **After:**
  - **The image ships `/data` as 0700** (`install -d -m 0700 /out/data`), and a new named volume copies it.
  - **Bind mounts and existing volumes** are handed to Lodestar's user at start, then tightened as above.
  - **Lodestar's user can always open the folder:** it owns it after the hand-over, which no longer needs read access. Unraid's appdata backup plugin runs as root.
- **Approved additions to the brief's paths:**
  - `privdrop.rs` (`chown_data_dir`) and `update/layout.rs` (the supervisor's `Bin::open`) call `data_dir::ensure` instead of `create_dir_all`.
  - The hand-over's owner check reads through `O_PATH`.
  - The Dockerfile line and the release smoke's hardened container.

## The warning is a catalogued log event
- **The start's warning is `system.data_dir_open`** (Warn, with the folder's path), because first-party code logs only through `log_event!` with a catalogued event.
- **Adding it touched the event catalogue** (`crates/lodestar/src/logging/events.rs`) and its golden (`settings/golden/logs_catalog.txt`, re-blessed).
- **It also touched the web app's generated event names** (`npm run event-names`) and the event's English and Chinese name and help (`web/src/lib/features/settings/logging/messages/`).
- **These files are outside the brief's paths,** but the logging rules require them for any new event. The change is only the one event.
