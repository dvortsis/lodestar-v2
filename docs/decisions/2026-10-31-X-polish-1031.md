# X-polish-1031 decisions

Optional findings from the B-search-recovery (#266), B-refetch-funnel (#267) and send (#273) reviews. No schema, index format or API type change.

## Saved refetches (supersedes part of `2026-10-31-B-refetch-funnel.md`)
- **A saved key is a refetch, and dropped at start, only when its strategy code is 200 and it's either under `REFETCH_COHORT` or from a peer finder** (`saved_refetch`, `crates/pipeline/src/lib.rs`). Refetches were always queued under the first enabled peer finder, so the source still catches a queue saved before `REFETCH_COHORT`. A plugin that isn't a peer finder and uses 200 as its own strategy code keeps its saved keys. This replaces "Saved refetches are matched by strategy code 200". Tests: `a_saved_refetch_is_matched_by_code_and_owner`, `a_saved_refetch_is_queued_afresh_from_the_store`.
- **The Insights floor skips saved refetches** (`queue_floor`, `crates/lodestar/src/insights.rs`): a refetch saved by an older build, under a real hour, no longer holds that hour's sealing back for one start. Any key with strategy code 200 is skipped here, not only a peer finder's: at worst a day seals before such a key resolves, and its late count lands on the open day, as with any key past the floor.

## Recovery caching (supersedes "Counts aren't cached" in `2026-10-31-B-search-recovery.md`)
- **A cached empty first page keeps its `recovery` beside it** (`RecoveryCache`, `crates/api/src/search.rs`), keyed by the cursor fingerprint of the user's query and visibility. It's read only while the result cache serves the same page entry: that entry's key covers everything the counts depend on, and the counts ran on its lease. So it's invalidated as the page is (any commit, the ttl, an eviction).
- **Only complete recoveries are kept.** One the 20 ms deadline cut short is counted again on a repeat, as before, so a loaded moment doesn't freeze missing counts until the next commit. A search the result cache doesn't keep (`file:(…)`) or bypasses (`explain`) keeps none either.
- **Bounded at 1,024 entries,** process-wide: when full, those of retired pages go first, then all. Each holds the clause texts and reduced ASTs of at most 8 clauses.
- **Tests:** `recoveries_are_kept_beside_their_cached_page`, `recoveries_are_bounded`, and end to end `a_commit_recounts_a_cached_recovery` (`crates/api/tests/search_recovery.rs`).

## Bench
- **`search-bench` gains a zero-result table:** each class with a word nothing matches appended, searched under the default visibility, then the recovery pass on its lease, at most 100 queries per class, gated at p95 ≤ 20 ms (`RECOVERY_BUDGET`). A pass the deadline cut short took at least 20 ms, so it counts against the gate. A class with one clause plus the word (browse everything) has nothing to remove and isn't timed.

## Send failures (item 8, added by the runner after #273)
- **An HTTP-status refusal keeps its own message on `POST /send`,** for every client: "The address answered HTTP 500: it isn't this client's API." Only a refusal without a status reads as qBittorrent's possible duplicate, or as "The client refused the torrent." for the others. The runner asked to narrow the qBittorrent arm; the generic refusal arm after it would have replaced the message too, so it's narrowed by the same check (`send_failure`, `crates/api/src/settings/send.rs`). Test: `an_http_status_isnt_read_as_a_refused_torrent`.
