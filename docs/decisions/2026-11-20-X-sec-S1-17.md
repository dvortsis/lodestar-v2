# X-sec-S1-17 decisions

S1-17 (low), surface 1, the DHT reply path. The detail stays with the runner until the fix has merged; this file records only what the code now does.

## What the code does
- **Reply values are budgeted per source.** A get_peers leg and a peer request each still keep at most 64 distinct values (`MAX_VALUES`). They're now filed under the source of the responder that sent them: an IPv4 /24 or an IPv6 /48, the same `limits::source` grouping CR-LOOKUP-END uses.
  - **Where:** `Values` in `crates/dht/src/node/lookup/values.rs`, used for a leg's values (`Lookup::absorb`, `Lookup::on_response`) and a request's (`PeerRequest::peers` in `actor.rs`, filled per reply and merged from each leg as it finishes).
- **The rule (the runner's call on the approach; the exact rule is this slice's):** max-min fair.
  - While there's room, every value goes in, so one responder answering alone can still fill all 64, as before.
  - Once full, a value from a source holding fewer values than the largest holder takes the place of that holder's newest value. A value from the largest holder, or from a source as large, is dropped.
  - So `n` sources that each send enough end with about `64 / n` each.
- **Unchanged:** the 64-value cap, a reply's own 64-value read, CR-LOOKUP-END's `ENOUGH_VALUES = 8` and `VALUE_RESPONDERS = 2`, the ledger's value counts, and the streaming path.
- **No new switch.**

## Tested
- `lookup/values.rs`: the budget shared between sources, the first values of a source kept, a value held once, merging keeps each value's source, and a property test that the cap is never exceeded and a source under its fair share never loses a value.
- `lookup.rs`: a leg's values are shared between sources within the cap, and one source alone still fills the leg.
