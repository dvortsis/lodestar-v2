# P-release: packaging choices

Slice P-release (architecture §11, §12.2; build-plan P3). Choices the brief left open:

- **Where the jobs live.** In `release.yml` as `package-*` jobs, behind a `package-gate` job. On pull requests the gate passes only for `packaging/**`, `release.yml`, `Cargo.toml`, `Cargo.lock`, a crate manifest, `rust-toolchain.toml`, or the `full-ci` label. Tags, nightly and manual runs always run. The workflow path filter gained `packaging/**`; labels are read on the next push, as in #90.
- **Linux builds** use the Dockerfile's recipe (cargo-zigbuild 0.24.0, the same pinned zig wheel, stripped release profile), so tarball and image binaries match. `aarch64` is cross-built and not run, as in the Docker job.
- **Version names.** Tags give `X.Y.Z[-pre]`. Nightly is `<Cargo version>-nightly.<date>`, other runs `<Cargo version>-dev.<sha>`. The MSI version is the part before any `-`.
- **MSI with cargo-wix and no `Cargo.toml` change.** `cargo wix --include packaging/windows/main.wxs` with `--no-build`; the licence RTF is generated at build time. WiX 3 (cargo-wix's target).
- **Service.** Installed as `LocalService`, start type manual, data folder set in the service's registry `Environment`, until M6-win adds the service entrypoint and sets the start type to automatic. The smoke test runs the binary directly.
- **Firewall.** `8090/tcp` for the private profile only; `6881/udp` for all profiles (DHT needs inbound from the internet). The `6881/tcp` peer port is reserved and unused today (operations.md §4), so no rule yet.
- **Defender exclusion** is a custom action behind `DEFENDER_EXCLUSION=1` (a checkbox on an added Options page, default off). It is removed again on uninstall. Failure never fails the install.
- **Uninstall keeps `%ProgramData%\Lodestar`**; `REMOVE_DATA=1` deletes it.
- **Signing** is `packaging/windows/sign.ps1`, driven by secrets `WINDOWS_CERT_PFX_BASE64` and `WINDOWS_CERT_PASSWORD`; it skips with a notice when they are absent. Checksums for the MSI are written after signing.
- **Releases.** Tags create (or update) a **draft** GitHub release via `gh`, with tarballs, MSI, zip, per-file `.sha256` and a combined `SHA256SUMS`. Prerelease tags are marked prerelease. Nightly: workflow artifacts only (14 days).
- **Not done:** macOS tarballs, winget, the tray icon, and release-manifest signing (B-update).

## Release signing: environments and owner setup (runner decision, owner-delegated 2026-10-23)

- `package-windows` (the only job that reads signing secrets) runs in the `release` environment on `v*` tags and in the `nightly` environment on nightly and manual runs. Pull requests use no environment and so see no secrets. `package-release` (creates the draft release) runs in `release`. A tag build therefore waits for the owner's approval before signing and before the draft release; that gate is intended.
- Each environment holds its own secrets. Windows Authenticode today: `WINDOWS_CERT_PFX_BASE64`, `WINDOWS_CERT_PASSWORD` (skipped when absent). Release-manifest signing is B-update's.
- **For B-update:** use two keys. `RELEASE_SIGNING_KEY` (in `release`) signs stable manifests; `NIGHTLY_SIGNING_KEY` (in `nightly`) signs nightly ones. Public keys go in `packaging/keys/`; installs trust the nightly key only on the Nightly channel (§12.2), so a leaked nightly key cannot sign a stable update.
- **Owner setup (GitHub → Settings → Environments):** (1) `release`: deployment branches and tags = tag rule `v*`, required reviewer = the owner; (2) `nightly`: deployment branches = `main` only, no reviewer; (3) generate both keypairs and add `RELEASE_SIGNING_KEY` to `release` and `NIGHTLY_SIGNING_KEY` to `nightly`; add the Windows certificate secrets to both once certificates exist. GitHub creates each environment unprotected on first use, so do (1) and (2) before the first tag.
