# P-release: packaging choices

Slice P-release (architecture §11, §12.2; build-plan P3). Choices the brief left open:

- **Where the jobs live.** In `release.yml` as `package-*` jobs, behind a `package-gate` job. On pull requests the gate passes only for `packaging/**`, `release.yml`, `Cargo.toml`, `Cargo.lock`, a crate manifest, `rust-toolchain.toml`, or the `full-ci` label. Tags, nightly and manual runs always run. The workflow path filter gained `packaging/**`; labels are read on the next push, as in #90.
- **Linux builds** use the Dockerfile's recipe (cargo-zigbuild 0.24.0, the same pinned zig wheel, stripped release profile), so tarball and image binaries match. `aarch64` is cross-built and not run, as in the Docker job.
- **Version names.** Tags give `X.Y.Z[-pre]`. Nightly is `<Cargo version>-nightly.<date>`, other runs `<Cargo version>-dev.<sha>`. The MSI version is the part before any `-`.
- **MSI with cargo-wix and no `Cargo.toml` change.** `cargo wix --include packaging/windows/main.wxs` with `--no-build`; the licence RTF is generated at build time. WiX 3 (cargo-wix's target).
- **Service.** A native `ServiceInstall` in the component keyed by `lodestar.exe` (a component keyed by a registry value made Windows Installer skip it), account `NT SERVICE\Lodestar` (its own virtual account, not LocalSystem or the shared LocalService), delayed-automatic start, `ServiceConfig` for pre-shutdown (60 s), failure actions when the process returns an error, and the unrestricted service SID; restart twice 60 s apart, then none until the counter resets after a day. A deferred `sc privs` action leaves it only `SeChangeNotifyPrivilege` and `SeIncreaseWorkingSetPrivilege` (no SeImpersonate or SeCreateGlobal). The smoke test starts the real service, polls `/healthz` on 8090, checks the marker and `logs\lodestar.log`, stops it, and checks that an upgrade keeps service, data and ACL.
- **Firewall.** `6881/udp` for the private profile only. The web port `8090/tcp` (private profile) is opt-in (`WEB_FIREWALL=1`, a checkbox, off by default): the M6-win decision (level 2) says the UI port isn't opened to the network unless the user chooses, which wins over the brief's "firewall rules for the web port". Both rules are scoped to `lodestar.exe`. Public-profile DHT would reach more of the network; users on a Public-profile network can change the rule. The `6881/tcp` peer port is reserved and unused today (operations.md §4), so no rule yet.
- **Defender exclusion** is a custom action behind `DEFENDER_EXCLUSION=1` (a checkbox on an added Options page, default off). It is removed again on uninstall. Failure never fails the install.
- **Uninstall keeps `%ProgramData%\Lodestar`**; `REMOVE_DATA=1` deletes it.
- **Signing** is `packaging/windows/sign.ps1`, driven by secrets `WINDOWS_CERT_PFX_BASE64` and `WINDOWS_CERT_PASSWORD`; it skips with a notice when they are absent. Checksums for the MSI are written after signing.
- **Releases.** Tags create (or update) a **draft** GitHub release via `gh`, with tarballs, MSI, zip, per-file `.sha256` and a combined `SHA256SUMS`. Prerelease tags are marked prerelease. Nightly: workflow artifacts only (14 days).
- **Not done:** macOS tarballs, winget, the tray icon, and release-manifest signing (B-update).

## Release signing: environments and owner setup (runner decision, owner-delegated 2026-10-23)

- `package-windows` (the only job that reads signing secrets) runs in the `release` environment on `v*` tags and in the `nightly` environment on nightly and manual runs. Pull requests use no environment and so see no secrets. `package-release` (creates the draft release) runs in `release`. A tag build therefore waits for the owner's approval before signing and before the draft release; that gate is intended.
- Each environment holds its own secrets. Windows Authenticode today: `WINDOWS_CERT_PFX_BASE64`, `WINDOWS_CERT_PASSWORD` (skipped when absent). Release-manifest signing is B-update's.
- **For B-update:** use two keys. `RELEASE_SIGNING_KEY` (in `release`) signs stable manifests; `NIGHTLY_SIGNING_KEY` (in `nightly`) signs nightly ones. Public keys go in `packaging/keys/`; installs trust the nightly key only on the Nightly channel (§12.2), so a leaked nightly key cannot sign a stable update.
- **Owner setup (GitHub → Settings → Environments):** (1) `release`: deployment branches and tags = tag rule `v*`, required reviewer = the owner; (2) `nightly`: deployment branches = `main` only, no reviewer; (3) generate both keypairs and add `RELEASE_SIGNING_KEY` to `release` and `NIGHTLY_SIGNING_KEY` to `nightly`; add the Windows certificate secrets to both once certificates exist. GitHub creates each environment unprotected on first use, so do (1) and (2) before the first tag.

## Checksums and their signature (for the user guide)

- **File:** one `SHA256SUMS` per release, attached to the GitHub release beside the tarballs, MSI and zip (`sha256sum` format: `<hash>  <file name>`). Each file also has its own `<name>.sha256`.
- **Signature:** `SHA256SUMS.minisig`, a minisign signature made by the `package-release` job with the **release key** (`02910813433E81E0`, `packaging/keys/lodestar-release.pub`), only on `v*` tags in the `release` environment. The job verifies it against the public key before attaching it. It is attached only if the `RELEASE_SIGNING_KEY` secret (and optional `RELEASE_SIGNING_KEY_PASSWORD`) exists; until the owner adds it, the release has `SHA256SUMS` without `.minisig`, and the job prints a notice.
- **Nightlies** are workflow artifacts with per-file `.sha256` only; they are not signed. A nightly signature (key `NIGHTLY_SIGNING_KEY`, `nightly` environment) comes with B-update's nightly channel.
- **User verifies** (public key from `packaging/keys/lodestar-release.pub` in the repository):
  - `minisign -V -p lodestar-release.pub -m SHA256SUMS` (add `-x SHA256SUMS.minisig` if the files are in different folders)
  - Linux: `sha256sum --check --ignore-missing SHA256SUMS`
  - Windows: `(Get-FileHash .\<file> -Algorithm SHA256).Hash.ToLower()` and compare with the line in `SHA256SUMS`

## M6-win review requirements (#98)

- Data folder: created with inheritance removed (see the next section for the exact ACL). Smoke checks that inheritance is off and no Users/Everyone entry exists.
- Firewall: program-scoped, DHT UDP, Private profile. Defender exclusion opt-in and removed on uninstall (already so).

## Service account and data-folder ACL, agreed with M6-win (#98)

- The service runs as `NT SERVICE\Lodestar` (virtual account, no password), not LocalSystem or the shared LocalService. The MSI creates `%ProgramData%\Lodestar` empty and sets the same ACL as `windows/acl.rs`: inheritance removed; full control for SYSTEM (`S-1-5-18`), Administrators (`S-1-5-32-544`) and `NT SERVICE\Lodestar`. It does not write `.lodestar-secured`. The MSI's ACL is what the service verifies.
- `packaging/windows/secure-datadir.ps1`, run by the MSI after the service is registered, creates the folder with its security descriptor in the same call, so it never has ProgramData's inherited rights. The install stops, with a message in the install log, if the folder already exists and is a link, is owned by anyone but SYSTEM, Administrators or the service, holds files without the `.lodestar-secured` marker, or contains a link. A reinstall over data kept from an earlier install (marker present) re-applies the ACL.
- Pre-shutdown delay is set to 60 s (the service's `PreshutdownTimeout` registry value, written by a custom action, since WiX 3 has no attribute for it); it takes effect once the service accepts the pre-shutdown control (M6-win).
- The earlier registry `Environment` value for the service was dropped: the service finds its default data folder itself.
- Not yet checked on a real service start: the smoke test runs the binary directly until M6-win merges.

Marker is a hint only: an existing non-empty folder is trusted only if its ACL is protected and allows only SYSTEM, Administrators and the service, and every top-level entry has one of those as owner. These are the same rules as the service's start-up check in `crates/lodestar/src/windows/acl.rs` (#98; see `docs/decisions/2026-10-22-M6-win.md`), and the two must stay identical. The smoke test checks each refusal.

## Release builds leave out `fixture`

Tarballs, MSI and zip are built with `--no-default-features --features web`, so `serve --fixture` (B16 test data, about 690 KB) isn't in them. Both smoke tests fail unless `serve --fixture` answers "no fixture backend". The Dockerfile gets the same flags (a scope exception the runner approved: `rand_chacha` ships via `fixture`, a licence-inventory gap), and the Docker smoke job has the same check.

The service SID (`service-sid.ps1`, SHA-1 of the upper-cased name, UTF-16LE, five little-endian words) is tested in CI against `NT SERVICE\TrustedInstaller` = `S-1-5-80-956008885-3418522649-1831038044-1853292631-2271478464` by `test-service-sid.ps1`.

## Data-folder script, security review round (M6-win)

- A folder owned by the service's own SID counts as trusted (the service creates a missing folder under that owner), alongside SYSTEM and Administrators.
- An existing **empty** folder that isn't private (inherits from ProgramData, or lets anyone but SYSTEM, Administrators or the service in) is removed and created fresh with its final descriptor, as SYSTEM, rather than re-ACLed in place: a handle opened while it was open to others (WRITE_DAC) would keep its rights. If removal fails (something holds it open), the install stops with a message. A non-empty non-private folder is still refused. After any create, the script checks owner and ACL, in case someone created the folder in between.
- The link scan fails closed (`-ErrorAction Stop`). The private-ACL check ignores NULL DACLs and object ACEs because the ACL is re-applied afterwards.

- The data-folder script runs as SYSTEM, so its log never goes to a name another user could have prepared in `C:\Windows\Temp`: it creates a new `lodestar-secure-<guid>` folder (SYSTEM and Administrators only) and a `CreateNew` file inside. File names in messages are reduced to printable ASCII and `::` is broken up, so a name can't pose as a workflow command. The folder is left behind for diagnosis; it is small and only admins can read it.

## Review round (fresh Opus reviewer) and what changed

- Release step fix: the file list is a bash array; a missing `SHA256SUMS.minisig` no longer stops the draft release. Per-file `.sha256` files are attached, as the READMEs say. A re-run never touches a published release.
- Downgrades and same-version upgrades are allowed (`MajorUpgrade AllowDowngrades`, `AllowSameVersionUpgrades`): nightlies and a release share an MSI version, and §12.2 rolls back by reinstalling the previous MSI.
- The install folder can't be changed (an error action stops any folder but `C:\Program Files\Lodestar`): SYSTEM runs scripts from it and the service runs the program from it.
- The Defender exclusion is added after the data folder is secured, with a rollback that removes it. The data folder is re-checked on Repair too.
- Signing secrets are visible to the two `sign.ps1` steps only, from the `release` and `nightly` environments, not as repository secrets.
- `DATAFOLDER` became the private Id `DataFolderDir`; the service-SID type step must succeed; a junction planted between the existence check and the create is caught.
- Known and left: `CreateServiceRollback` deletes a service named Lodestar even if the create failed because one already existed (only reachable after a failed earlier install); the actions that pin third-party `taiki-e/install-action`, `dtolnay/rust-toolchain` and `Swatinem/rust-cache` by tag follow `ci.yml` and no longer see any secret; the smoke test checks the DHT rule's profile but not its port or program, and has no junction-refusal case.

## Runner review round 1 (fix) and where it landed

- No install-folder choice: the wizard goes licence, options, ready, and any other `INSTALLFOLDER` is an error. The SYSTEM scripts stay in the MSI's install folder, which under Program Files inherits admin-only write; running them from a temp copy or the Binary table was not added. Say if that is still wanted.
- Same-version upgrades and downgrades allowed; the sc.exe rollback that could delete an existing service is gone with the sc.exe service actions.
- Web port rule opt-in, signing secrets only in the two signing steps, `dtolnay/rust-toolchain`, `Swatinem/rust-cache` and `taiki-e/install-action` pinned by SHA in the package jobs, no shared cache on tag builds, `persist-credentials: false`, no choco fallback, tag must equal the Cargo version, `--clobber` only on a draft, CR stripped from `SHA256SUMS`.
- `secure-datadir.ps1`: a link is refused after create, and the new folder must be new (a few seconds old), not one that already existed. An empty folder owned by someone other than SYSTEM, Administrators or the service is refused, not replaced.
- `REMOVE_DATA=1` runs `remove-datadir.ps1`, which refuses links and deletes with .NET, not `rmdir /s /q`.
- Not done (optional): extra systemd hardening (not this slice's file), `WixQuietExec64`, an `.cmd` that removes inheritance on the portable `data` folder (the README tells people to unpack inside their user folder instead).
