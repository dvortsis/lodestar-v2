# B9 decisions (percolator, alerts over SSE, RSS per saved search)

Architecture §7, §8 ("Saved searches → alerts", "Indexing"), §9, §10.8, §12, §12.1, §18.7 and §20.9, with the B4, B5a and B17 entries of §16 and the B4b, B5c, B8, B10a, B12 and B16 decision files. No owner decision is reversed or loosened, and no owner number changes (§1.6.3's 5 s is met and measured below). The refinements the runner flags to the owner (§2.19) are marked **(§2.19)**.

## Percolation
- **Exact tier only (§2.19).** A saved search percolates as `SearchIndex::query` compiles it, never with the stem fallback. An alert is then a torrent the search's own first page could show, and the fallback's "fewer than N exact matches" rule has no meaning for a range of a few new ids.
- **One searcher snapshot per run, through the post-filter path, with no lease and no result cache.** The id range `(watermark, end]` is a `RangeQuery` ANDed with the compiled query; the lifted fast-field ranges still apply in the collector. No visibility clauses: an alert is stored for every match (B8) and the read side decides what's shown.
- **A range never passes the snapshot.** Each run caps `through` at the highest id in its snapshot (the `id` column's maximum per segment). A commit is reported only after the reader reloads, so this normally changes nothing; it guarantees a run on a stale reader can't move a watermark past torrents it couldn't see.
- **Numbers (§2.19):** a per-run budget of **2 s** (checked between searches), a per-search range cap of **100,000 ids** per run, and **`keep` = 1,000** alerts per saved search, both per run (the highest ids) and in `prune_alerts`. 1,000 is a few weeks of a broad search at today's ingest and well past what the list and the feed show. A run cut by the budget or the cap is followed by another at once; one with nothing left waits for the next commit.
- **Most behind first:** `percolation_due` is sorted by (watermark, id) in the task, so a budget never starves the search furthest behind.
- **Cost follows the new data, not the index.** A search reads only the segments whose `id` column range can overlap its `(watermark, end]`, so a run after a commit reads the newest segments. Inside a scan the token is checked every 4,096 documents too (`CHECK_EVERY`), once a search has completed in the run, so one heavy search can't overrun the budget by much and every run that starts a search finishes at least one.
- **At most 1,000 saved searches** (paused ones included): creating one more is `409 too_many_saved_searches`. Every one runs against every commit's new torrents, so the count bounds that work. (A runner-requested change to `crates/api/src/saved.rs`'s create, B10a's file.)
- **A search paused or edited while a run is under way gets nothing from it.** The percolator records through `Store::record_percolation_unchanged`, which re-reads `paused` and the AST inside the transaction and leaves a search alone (no alerts, no watermark move) unless it's still active with the AST the run matched. The AST, not `updated_at`, is compared: `updated_at` has one-second resolution, so an edit in the same second would pass. An edited search runs the range again with its new query (B8: an edit keeps the watermark). `record_percolation` itself is unchanged, since `bench/` and B10a's tests call it.
- **Logged once:** a search whose stored query this build can't read is logged once per process, not every run. A search that fails in the index is logged by id alone: Tantivy's errors can carry query terms.
- **Not yet scoped to the range:** `file:(…)` clauses build their torrent-id set from the whole file index, and its cache key changes with every commit, so each run rebuilds it. Scoping the file search to the new range is left to the percolation benchmark below.
- **Several range ends, several transactions.** Searches capped at different ends are recorded with one `record_percolation` per end, each its own transaction. Each search's hits and watermark still move together.
- **An unreadable stored AST is skipped, not moved past.** It's counted, logged by id, and kept at its watermark, so once its query is saved again it catches up from where it was (capped, like any catch-up).
- **Pruning runs at start and hourly,** never per commit, because a prune that deletes scrubs the WAL (§2.17).
- **Fixture mode never starts the task** (`fixture::unless_offline` on its stop receiver): it adds no hook sink and reads nothing, so the manifest's alert counts hold.
- **Shutdown:** the percolator stops after the search (`Handles::shutdown`), so the indexer's last commit can still be recorded.
- **Measured:** with 200 active saved searches and the real commit cadence (2 s), a torrent inserted into the store is an alert after **≈2.07 s** (three runs: 2.06–2.08 s). About 2 s of that is the commit interval; percolating 200 searches over the new range and recording it takes tens of milliseconds. The test asserts under 5 s. It runs on a small index, so it shows the cadence and coalescing, not the cost of 200 broad queries over a corpus-sized index. **Follow-up for the next `bench/` brief:** a percolation benchmark at corpus scale (about 10M torrents) with 200 and 1,000 saved searches, including `file:(…)` and regex queries, measuring commit-to-alert and per-run cost.

## SSE
- **`AlertsEvent` gains `notify`** (the search's `alert` flag), so the UI notifies only for searches that asked to and otherwise just refreshes counts. `matched`, `alert` and `max_id` count only alerts on torrents shown now (`shown_row`); a search whose new alerts are all withheld sends no event.
- **`EventHub::alerts(event, adult_shown)`** publishes through `publish_tagged`, so an event counted while Adult was shown is replaced by one `resync` for a client while Adult is hidden, replay included, as `torrents` events are.

## The API
- **`GET /saved-searches/{id}/alerts`:** `{ items: [{ id, created_at, read, torrent }], next_cursor }`, newest first, limit 1–200 (clamped, as B10a's lists). **The cursor is the last row returned**, a shown torrent's id, never a withheld one (B10a's rule; the brief's "last row read" is read that way, since a cursor naming a withheld row would reveal it).
- **`POST /alerts/read { saved_search?, through }`** marks every unread alert with an id up to `through` read, withheld ones included: the user can't see those, and counting or skipping them would reveal them. It returns `{ ok: true }` with no count.
- **`GET /alerts/unread`** is the store's new `unread_shown(hidden_type)`, which replaces the uncalled `unread_total`. It's `withheld(.., hidden_ok = false, adult)` in SQL (a classified torrent of Adult's code while hidden, or `flags::HIDDEN`), and a test checks the two agree for every kind of torrent either way. The badge equals the sum of B10a's per-search `unread`.
- **Notification channel bits** (`alerts::channel`, persisted in `saved_searches.channels`, append only): webhook 1, ntfy 2, Discord 4, email 8. Nothing sends on them yet. Sending waits for a notifications settings section (the API keeps `channels` untouched until then, B10a), and anything that sends must check the fixture gate.

## RSS (`GET /feeds/{id}`)
- **Who reaches it:** a session, a feed token for this search, an all-feeds token, or an API key with `feeds` (B12). Another search's token, a search without `rss`, an unknown id and a path id that isn't a number all give one body, `404 feed_not_found`. A revoked or malformed token is B12's `401 bad_api_key`, and a key without `feeds` is B12's `403 key_scope`: the guard answers those before the handler runs, and neither reveals anything about saved searches.
- **What it holds:** up to 50 of the newest alerts on shown torrents, leaving out private-source ones before counting (§18.7: private results stay local; they still show in the app's own list and events). The renderer drops `private_source` items as well.
- **The list and the feed select in SQL** (`Store::shown_alerts`, the badge's rule plus `PRIVATE_SOURCE` for the feed, `ORDER BY torrent_id DESC LIMIT`). Walking the alerts row by row with two lookups each, under the reader lock search shares, would scan a mostly-withheld search's whole history on every poll.
- **The feed's Adult rule (§2.19): `content.show_adult`.** §20.9 gives outputs (Torznab, Stremio, export) their own adult settings; a feed follows the app's setting, as the brief says, because it shows your own saved search's alerts, the same list the Alerts screen shows. A per-output feed setting can come with the notifications section.
- **Links (§2.19):** the guid is the info-hash; an item links to `{origin}/t/{hash}` and the channel to `{origin}/alerts/{id}`. The origin is the request's `Host`, accepted only as a host or IP and an optional port and normalized through `Url` (`rss::feed_origin`); anything else gives `http://localhost`. It's `https` only when proxy-header auth is on, the TCP peer is a trusted proxy, and it sends exactly one `X-Forwarded-Proto: https`.
- **The magnet enclosure:** `RssItem.magnet` (`RssMagnet { info_hash, name, size }`) is rendered only as `magnet:?xt=urn:btih:<40 hex>&dn=<percent-encoded name>`, escaped with `escape_into`, typed `application/x-bittorrent` with the size as its length. A hash that isn't 40 hex digits leaves the enclosure out. Item titles now go through `clean_line` in `render` itself.
- **Inert in a browser:** `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`.
- **No `Host`** (HTTP/2 sends `:authority`): the request target's authority is used, under the same check.
- **Caching:** `lastBuildDate` is the newest included alert's time (the search's creation time when empty), so an unchanged feed is byte-identical. A strong `ETag` is the first 128 bits of the body's SHA-256. `If-None-Match` compares weakly (RFC 9110), so a `W/` prefix still matches and gets a 304 with the same headers. `Cache-Control: private, max-age=60`, `Referrer-Policy: no-referrer`.
- **No secret leaves:** the token and any query string never appear in a link, a body, a header, an error or a log. A log-capture test runs every feed outcome with real tokens.

## Scope
- **`pub mod alerts`** rather than `mod alerts` in `crates/api/src/lib.rs`: the binary's percolator calls `alerts::announce`.
- **`mod percolator;` in `crates/lodestar/src/main.rs`**, the binary's module list, beside the `services.rs` lines the brief names.
- **`magnet: None`** in `crates/integrations/tests/rss.rs`, so its `RssItem` literals compile with the new field.
