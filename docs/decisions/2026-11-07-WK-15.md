# WK-15 decisions (Insights worker dimension, marginal gain, fleet summary)

Architecture §19.7 and §10.9; workers plan WK-15 and Q12; owner §1.6.4 (Insights budgets). Shared-file edits beyond the brief's list were approved by the runner before they were made (2026-11-07), and are listed at the end.

## What's counted, and where
- **The per-worker rows on `main` couldn't carry Discover, Fetch or marginal gain.** Metric 17 (`BY_WORKER`, WK-9b) holds only what remote workers send: rediscovered, dropped, scraped and DHT scrapes. Nothing recorded per worker the keys granted to it, its commits or its losses, or whether a second worker had claimed a key another held.
- **New metric code 18, `WORKER_LEASES`** (`crates/pipeline/src/rollups.rs`). dim = the worker id (0 = the built-in worker). Keys: 0 granted, 1 marginal, 2 committed, 3 lost, and, for remote workers, 4 rediscovered and 5 dropped (`lodestar_pipeline::marginal::key`). Kind: Sum.
  - **Why keys 4 and 5:** Discover first read remote workers' rediscovered and dropped from metric 17. That's up to 256 packed rows an hour under WK-9b's caps, and it broke the 50 ms budget even with the grouping done in SQL (Discover range=all 49 ms on hourly rows, 69 ms compacted). So the remote intake (`remote.rs` `counters()`) also sums those two counters per worker into metric 18, at 2 rows per worker per hour, and the page reads metric 18 only (runner-approved).
  - They're written only for counters `Admit` has accepted, in the same place and with the same value as the metric-17 write. So a refused counter, or the part of one over its row's cap, adds to neither.
  - **The key list, 0–5, is append-only.** Keys 4 and 5 duplicate metric 17 so Insights reads stay within budget; **metric 17 stays the source of truth.**
  - `worker_totals_match_the_packed_rows` checks the two agree per worker. It covers hours across the window, a worker with only dropped rows, refused counters and a capped row.
  - A sealed day can't reach `Admit`, whose window is 24 hours. Reading metric 18's sealed days is checked at the API, by `sealed_cached_and_compacted_days_read_alike`.
  - **It's an on-disk meaning:** append-only, never reused or renumbered. The code list's module comment now says so for every code.
  - **It's written by the coordinator only:** keys 0–3 from its lease events, and keys 4 and 5 from counters `Admit` already let in. No worker can name it in its `Counters`: it isn't in `FROM_WORKERS`.
  - No migration: it's a new `metric` value in `rollup_hour` and `rollup_day`.
- **The logic is computed at intake, in `crates/pipeline/src/marginal.rs`.** The coordinator's `FunnelEvents` passes the authority's events to it: `harvested` → granted, `lost` → lost (with marginal), and `serving` → start counting. `Coordinator::complete` and `complete_for` count commits (with marginal). It belongs at intake, not in a store query: which worker claimed which key exists only while the key is in flight, and the store keeps no per-key worker record (WK-12's `torrent_worker` is for remote workers only).
- **`Lease::finder: Option<WorkerId>`** (`crates/cluster/src/leases.rs`): the worker the key was first granted to.
  - It's set at a fresh grant and cleared under the authority's lock the first time any other worker claims the key, while held or while waiting for a re-grant.
  - It's kept across re-grants, and `None` for a lease restored from an earlier run.
  - Claim and grant answers are unchanged.
  - The `Lease` literals in `remote.rs` (a late result's lease) and `writer.rs` (two tests and the lease-free claims path) set `None`.
  - **Why it's on the lease:** the first draft used an event after the lock plus a map in `marginal.rs`. Self-review found two cross-thread races there: a claim's event could run before the grant's, or after the commit's, and either way a shared key kept its count. The map's size at its cap was also understated (86 MB, not 48 MiB). Deciding under the lock removes both the races and the map.
- **`LeaseEvents::serving()`** is a default no-op, called once per authority after the lock is released, from `serve_remote`. The cluster server calls that whenever it's built on the authority, which happens at every start while workers are allowed. Counting starts there, so it survives restarts. The first draft's latch, the first grant to a remote worker, reset at each start and dropped every worker's counts until one happened.

## Marginal gain (Q12)
- **Definition:** for each worker, its finds that **nothing else claimed while they were in flight**. That includes the built-in crawler's claims (runner, 2026-11-07): the local intake claims through the same authority. It's an approximation of §19.7's "new keys per hour that no other worker would have seen", labelled ≈ in the API. A key found again only after its commit is a rediscovery and doesn't count against it.
- **Counted when the lease ends, not at the grant.** Q12's "counted at grant" assumed the count could be taken back later, but a take-back after the lock can't be ordered against the grant or the end. So a lease that ends, committed or lost, with its finder still set counts 1 for the finder, at the key's discovery hour.
  - Keys still in flight aren't counted yet, so the latest hours fill in as their leases end.
  - A lease restored across a restart isn't counted: its finder is unknown, so the view can only under-count.
  - If a lease expires and the key is re-granted without a claim (`regrant_pending`), the finder keeps the credit and the new holder counts the commit or loss.
  - This is the runner's question (Q12), refined here and flagged (§2.19).
- **Granted** is counted at the grant, for the holder. **Committed and lost** are counted at the lease's end, for the worker holding it then.
- **A late result** (plan Q7, `restore_if_free` then `complete_for`) is one more lease end for its worker, as `LATE_RESULTS` is one more terminal row in the funnel. So a worker's Fetch `by_worker` can show more endings than its grants.

## Memory and parity
- **No state.** Everything is decided from the lease the authority hands over, so `marginal.rs` holds no key, and nothing grows with the torrents in flight. `Lease` gains 8 bytes.
- **Single-machine parity (§19.8):** nothing is counted until a cluster server serves, so a single machine writes no metric-18 row.
- With workers allowed but none joined yet, the built-in worker's 4 rows an hour are written. The stage pages still leave `by_worker` out of the JSON until a remote worker has counted something in the range, so their bytes are unchanged; the stage goldens pass as they were.
- `leases_through_the_coordinator_reconcile` puts 3,000 leases through grants, claims by other workers, expiries, take-overs, commits and losses. It checks that each worker's grants and ends reconcile and that marginal is exactly the finds no one else claimed. `a_lease_keeps_its_finder_until_another_worker_claims_it` covers the flag in the cluster crate.

## The API
- **Discover and Fetch gain `by_worker[]`** (`crates/api/src/insights/stages.rs`, `crates/api/src/dto/insights.rs`).
  - **Discover:** `worker`, `granted`, `marginal`, `rediscovered`, `dropped`.
  - **Fetch:** `worker`, `committed`, `lost`.
  - The list starts with the built-in crawler (0), then remote workers by id. It's left out unless a remote worker counted something in the range. On Fetch, a worker that only sent counters (no lease ended) isn't listed.
  - The built-in crawler's rediscovered and dropped are the fleet's totals less the remote workers' keys 4 and 5, so the breakdown adds up to the KPI. A range reaching back before this change credits remote workers' older counters (in metric 17 only) to the built-in crawler. That's transitional.
  - Fetch's `reason` filter doesn't narrow `by_worker`: metric 18 counts losses without their reason. The field's doc says so.
  - `previous` (Compare) doesn't carry it.
- **Metric 18 is read as window totals,** over `read_metric`'s spans but grouped by (worker, key) in SQL (`RollupBy::DimKey`): compacted days from `rollup_day` plus stragglers, sealed days from the sealed-day cache, and the rest hour by hour. Reading it bucket by bucket brought a year of compacted days back row by row and pushed Fetch at range=all to 57 ms. 18 is added to `SUMMED`, so `warm` fills the cache at start as it does for the others. `sealed_cached_and_compacted_days_read_alike` checks that a day read live, then from the cache, then compacted, gives the same per-worker numbers.
- **No new store query.** The brief allowed one in `crates/store/src/insights.rs`. The existing `rollup_sums`, `rollup_day_sums` and straggler reads already group by (dim, key) through the primary key. A grouped query over metric 17's packed keys was written and measured, and dropped with the change to keys 4 and 5.
- **The fleet summary is `GET /insights/workers/summary`** (`crates/api/src/insights_workers.rs`, signed in, not admin-only, since everyone sees the pill). It returns `{fleet: null}` with no worker joined or no cluster. Otherwise `fleet` has:
  - `workers` = online + draining. Both are doing work: a draining worker is still fetching its leases.
  - `online`, `draining`, `paused` and `offline` as disjoint counts. Paused and offline (disconnected) workers aren't in `workers`; they're shown apart so the pill can say so.
  - `stored_per_hour`: torrents the whole fleet newly stored, the built-in crawler's included, in the last full UTC hour. It's read exactly as the overview's `ingest_per_hour` (metric 4, `STORED`), not from metric 18, which a fleet of paused or offline workers may not have written. 0 for a measured hour without one, null for an unmeasured hour.
  - States are counted with an exhaustive `match`, so WK-13's `quarantined` must be placed when it's added.
  - The plan doesn't say how the pill counts states; this is the runner's call, flagged here (§2.19).

## Privacy
- **Counts only, per worker.** No per-worker field anywhere in the API names a torrent, an infohash, a worker's name or an address. `by_worker` entries are numbers under fixed names, and the summary has no id at all.
- **Private-source and remote-unverified torrents** reach Insights only as part of these counts, as they do in every other Insights number. `marginal.rs` never holds, writes or returns a key.
- The tests check that every `by_worker` entry is numbers only, under the expected names, and that the summary carries no worker name, address or id.

## Budgets (owner §1.6.4)

The after fixtures add metric 18's 52 rows an hour (4 keys for the built-in worker, 6 for each of 8 remote ones) on top of WK-9b's worst case. The pages' read paths didn't change after these runs: the review's fixes changed only how rows are written and the summary.
