# WK-15 decisions (Insights worker dimension, marginal gain, fleet summary)

Architecture §19.7 and §10.9; workers plan WK-15 and Q12; owner §1.6.4 (Insights budgets). Shared-file edits beyond the brief's list were approved by the runner before they were made (2026-11-07), and are listed at the end.

## What's counted, and where
- **The per-worker rows on `main` couldn't carry Discover, Fetch or marginal gain.** Metric 17 (`BY_WORKER`, WK-9b) holds only what remote workers send: rediscovered, dropped, scraped and DHT scrapes. Nothing recorded per worker the keys granted to it, its commits or its losses. Remote claims go through `LeaseAuthority::claim_batch` inside the cluster server, so the pipeline never learned that a second worker had claimed a held key either.
- **New metric code 18, `WORKER_LEASES`** (`crates/pipeline/src/rollups.rs`). dim = the worker id (0 = the built-in worker). Keys: 0 granted, 1 marginal, 2 committed, 3 lost (`lodestar_pipeline::marginal::key`). Kind: Sum.
  - **It's an on-disk meaning:** append-only, never reused or renumbered. The code list's module comment now says so for every code.
  - **It's written by the coordinator only,** from its lease events, never from a worker's `Counters`. `Admit` still refuses it: it isn't in `FROM_WORKERS`.
  - No migration: it's a new `metric` value in `rollup_hour` and `rollup_day`.
- **The logic is computed at intake, in `crates/pipeline/src/marginal.rs`.** The coordinator's `FunnelEvents` forwards the authority's events to it: `harvested` → granted, `lost` → lost, and the new `claimed_elsewhere`. `Coordinator::complete` and `complete_for` count commits. It belongs at intake, not in a store query: which worker claimed which key exists only in memory while the key is in flight, and the store keeps no per-key worker record (that's WK-12's `torrent_worker`, for remote workers only).
- **`LeaseEvents::claimed_elsewhere(key, lease, claimer)`** (`crates/cluster/src/leases.rs`) is a default no-op. It's called after the lock is released, as `harvested` is, once for each claim on a key in flight under another worker: one it holds, or one waiting for a re-grant after its lease expired or was evicted (`lease` is that earlier lease). The holder's own repeated claim never calls it. Claim and grant semantics and return values are unchanged.

## Marginal gain (Q12)
- **Definition:** for each worker, the keys first granted to it that **nothing else claimed while they were in flight**. That includes the built-in crawler's claims (runner, 2026-11-07): the local intake's claims go through the same authority and fire the same event. It's an approximation of §19.7's "new keys per hour that no other worker would have seen", labelled ≈ in the API. A key found again only after its commit is a rediscovery and doesn't count against it.
- **Counted at the grant** (as Q12 says): +1 at the key's discovery time, and −1 in that same hour the first time another worker claims it. So each hour nets out, and a range's sum is never below 0 once its take-backs have landed. A worker's marginal is credited to the worker the key was **first** granted to. If its lease expires and the key is re-granted to another worker without a claim (`regrant_pending`), the finder keeps the credit and the new holder counts the commit or loss.
- **Committed and lost** are counted at the lease's end, for the worker holding it then.

## Memory and parity
- **Bounded by live leases.** `marginal.rs` keeps one entry per key in flight (about 48 bytes each): who it was first granted to, the hour, and whether it was claimed elsewhere. Every terminal path ends an entry:
  - commits through `Coordinator::complete`/`complete_for`;
  - losses through `LeaseEvents::lost`, which covers `lost` and every `report` with a loss. Every `report` call on `main` passes one.
  - A hard cap, `MAX_TRACKED` = 2²⁰ (about 48 MiB), lies far above the fleet's in-flight leases (the built-in pool's 200,000 plus each worker's pool cap). Past it a grant is still counted as granted but not as marginal, so the view can only under-count.
  - The map lives in memory only, so it's gone at shutdown.
- **Expiry:** an expired or evicted lease's key isn't finished. It waits in the authority for a re-grant, still in flight, and a claim for it then is exactly what marginal gain has to notice. So its entry stays until that key's next lease ends, and the map's bound is the authority's in-flight count (held plus waiting). The runner asked for removal on expiry; this is the reason it doesn't happen there. `churn_leaves_nothing_behind` puts 10,000 leases through grants, claims elsewhere, expiries, re-grants, commits and losses, and asserts the map is empty after every round.
- **Single-machine parity (§19.8):** nothing is counted and no key is held until the first grant to a remote worker, which only a serving cluster server makes. On a single machine metric 18 gets no row, the map stays empty, and the stage pages' `by_worker` is left out of the JSON, so their bytes are unchanged (the stage goldens pass as they were). Keys granted to the built-in worker before the first remote grant aren't tracked; they're counted only as they end.

## The API
- **Discover and Fetch gain `by_worker[]`** (`crates/api/src/insights/stages.rs`, `crates/api/src/dto/insights.rs`).
  - **Discover:** `worker`, `granted`, `marginal`, `rediscovered`, `dropped`.
  - **Fetch:** `worker`, `committed`, `lost`.
  - The list starts with the built-in crawler (0), then remote workers by id. It's left out when no worker counted anything in the range.
  - The built-in crawler's rediscovered and dropped are the fleet's totals less the remote workers' metric-17 counts, so the breakdown adds up to the KPI.
  - Fetch's `reason` filter doesn't narrow `by_worker`: metric 18 counts losses without their reason. The field's doc says so.
  - `previous` (Compare) doesn't carry it.
- **Both metrics are read through the stage pages' existing `read_metric`,** so sealed days come from the sealed-day cache and compacted ones from `rollup_day`. 17 and 18 are added to `SUMMED`, so `warm` fills the cache at start as it does for the others. `sealed_cached_and_compacted_days_read_alike` checks that a day read live, then from the cache, then compacted, gives the same per-worker numbers.
- **No new store query.** The brief allowed one in `crates/store/src/insights.rs`. The existing `rollup_sums`, `rollup_day_sums` and straggler reads already serve metric 17 and 18 by (dim, key) through the primary key, so none was needed.
- **The fleet summary is `GET /insights/workers/summary`** (`crates/api/src/insights_workers.rs`, signed in, not admin-only, since everyone sees the pill). It returns `{fleet: null}` with no worker joined or no cluster. Otherwise `fleet` has:
  - `workers` = online + draining. Both are doing work: a draining worker is still fetching its leases.
  - `online`, `draining`, `paused` and `offline` as disjoint counts. Paused and offline (disconnected) workers aren't in `workers`; they're shown apart so the pill can say so.
  - `committed_per_hour`: the whole fleet's commits, the built-in crawler's included, in the last full UTC hour, read from metric 18 like the overview's `ingest_per_hour`. 0 for a measured hour without one, null for an unmeasured hour.
  - The plan doesn't say how the pill counts states; this is the runner's call, flagged here (§2.19).

## Privacy
- **Counts only, per worker.** No per-worker field anywhere in the API names a torrent, an infohash, a worker's name or an address. `by_worker` entries are numbers under fixed names, and the summary has no id at all.
- **Private-source and remote-unverified torrents** reach Insights only as part of these counts, as they do in every other Insights number. `marginal.rs` holds keys in memory while they're in flight, and never writes or returns one.
- The tests check that every `by_worker` entry is numbers only, under the expected names, and that the summary carries no worker name, address or id.
