# X-cmp01-fix decisions

- **CMP-01 (important, companions; detection and requests on loopback) fixed in part.** Its detail is held under `docs/security/v1/README.md` §5 until a release with the fix is published. This file says only what the code now does. The managed path's first configuration is not covered by this part: the first follow-up below is the fix for it, and has to land before the first managed pin (the runner's condition).

## Calls
- **One loopback address a port** (architecture §18.10; plan `2026-11-06-v06-companions` Q12). `CompanionHttp` sends a loopback target to `127.0.0.1`. It looks on `::1` only when nothing listens on `127.0.0.1` and the request is a bare probe: a `GET` with no header, no body and no query, which is what detection and the health check send.
- **`127.0.0.1` keeps a port for good.** Once it has answered on a port, every later request to that port goes to it alone, a bare probe included, for as long as the `CompanionHttp` lives. A failure that only follows an accepted connection (an over-long answer, an unreadable one) counts as an answer.
- **A port found on `::1` is remembered as that only until `127.0.0.1` answers.** Every later request to the port, bare or not, still asks `127.0.0.1` first, and an answer there takes the port. So a companion that starts listening on `127.0.0.1` has the port from the next request on, with no wait for a health probe.
- **A request that carries anything goes only where a probe found the companion.** Any header (a key, a cookie), body or query makes a request not bare, whatever its values: a session cookie travels as a plain header, so the rule doesn't depend on the value being marked secret. Before any probe, such a request stops at `127.0.0.1`. With the port remembered on `::1`, it asks `127.0.0.1` first and goes on to `::1` only when nothing listens there.
- **A companion that listens on `::1` only still works,** within one `CompanionHttp`: a probe finds it there, and its requests follow.
- **The memory is each `CompanionHttp`'s own.** Lodestar builds three today (the health watch, the guided path and the managed path), and each starts with none.
- **A request whose headers can't be sent is refused before any address is asked,** so it never counts as an answer from one.
- **Container and entered-URL targets are unchanged.**

## What this leaves, stated as behaviour
- **While nothing listens on `127.0.0.1` for a port, whatever first answers a bare probe on `::1` is taken as the companion there,** and requests that carry something go to it for as long as `127.0.0.1` still isn't listening when each is sent.
  - **A managed companion's first configuration falls inside this.** Lodestar binds a managed companion to `127.0.0.1`, and waits for it with a bare probe every second until one answers. An answer from `::1` in that time counts as ready, and the configuration that follows goes wherever `127.0.0.1` isn't yet listening. Asking `127.0.0.1` first narrows it to the time before the companion listens; it doesn't close it. The first follow-up does.
  - **The health checks don't bound it.** They run every 30 seconds on the managed and watch instances, and the guided instance probes only when a guided detection runs.
- **An entered URL that names `localhost` is resolved by the system,** to either loopback address (`::1` often first on Windows), and doesn't go through the per-port rule above. Second follow-up.
- **After a restart, a hand-run companion on `::1` only is not found by a request that carries something until a bare probe has run on the same `CompanionHttp`.** Detection and the health check send one; a guided step that begins with a keyed request does not.
- **A hand-run companion that moves from `127.0.0.1` to `::1` while Lodestar runs** isn't found again until Lodestar restarts.

## Tests
- `crates/companions/tests/detect.rs`, against real listeners on both loopback addresses of one port, each held for the whole test:
  - `only_a_bare_probe_looks_on_ipv6_loopback`;
  - `ipv4_loopback_keeps_the_port_once_it_has_answered`: 127.0.0.1 answers once and stops listening, its port then held closed; a bare probe and a request with a body are both refused there, and nothing reaches `::1`;
  - `ipv4_loopback_takes_a_port_found_on_ipv6`: the first request after 127.0.0.1 starts listening goes to it, though it carries a body.
  They need `::1`; where it can't be bound they say so and, on CI, fail, as `loopback_falls_back_to_ipv6` already does.
- `crates/companions/src/detect/mod.rs`: what counts as bare, how a port's address is remembered and replaced, and what shows a listener, without sockets.
- `a_port_is_held_closed_once_its_listener_is_gone` runs the helper the second test rests on, on machines without IPv6 too.
- **Not run where they were written:** the build container has no IPv6 at all, so the three dual-loopback tests ran only on CI. The unit tests and the helper's test ran locally.

## Follow-ups
- **Tie a managed companion's requests to the supervised process** (runner; before the first pin): a request that carries a credential goes out only while the supervisor holds the child it started on that port. It needs the supervisor (`crates/companions/src/supervise/**`, `manager.rs`), outside this slice's owned paths.
- **Entered loopback hosts** (runner adds the slice): an entered URL naming `localhost` or a loopback address goes through the same per-port rule, or `localhost` resolves to `127.0.0.1` only.
- **A `127.0.0.1`-only `CompanionHttp` for the managed path, and one shared instance** (runner; with the slice above): managed companions never listen on `::1`, so their client shouldn't look there; and one instance for the watch, the guided path and the managed path would let a probe by any of them serve the others. Both need `crates/lodestar/src/companion_wiring.rs` and `companions.rs`, outside this slice's owned paths.
- **The exact-input regression test** lands after the release with the fix (`docs/security/v1/README.md` §5).
