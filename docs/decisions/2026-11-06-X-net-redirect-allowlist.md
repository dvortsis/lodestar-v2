# X-net-redirect-allowlist decisions

Runner brief, 2026-11-06T04:16Z, from the review of #521 (X-sources-low). It tightens behaviour, so it's the runner's call, flagged to the owner under `docs/owner-decisions.md` §2.19. It refines the SSRF guard's redirect rule (§12) recorded with X-integrations.

- **A cross-origin redirect keeps an allow list, not a deny list.** `GuardedClient::send_following` (`crates/integrations/src/net.rs`) used to drop only `Authorization` and `Cookie` on a 307/308 to another origin. It now keeps only `CROSS_ORIGIN_HEADERS` and drops every other header the request set. A webhook or notifier that later carries `X-Api-Key`, `X-Auth-Token`, `Proxy-Authorization`, a secret in ntfy's `Tags`, or any header a user configures can no longer forward it to whatever origin a redirect names. An allow list fails closed: a credential under a name nobody thought of is dropped too.
- **The list is the sources egress list, unchanged:** `accept`, `accept-language`, `content-type`, `content-length` and `user-agent` (`CROSS_ORIGIN_HEADERS` in `crates/sources/src/egress.rs`). They describe content and the body, and can't carry a credential. `crates/integrations` keeps its own copy, with a comment naming the sources list, rather than depend on `crates/sources` for five strings.
- **No additions.** The brief allows a header only if a current caller needs it across origins and it can't carry a credential. None qualifies:
  - the webhook's `X-Lodestar-Delivery` and `X-Lodestar-Schema` repeat the payload's `id` and `schema_version`, so a receiver behind a cross-origin redirect still has both;
  - ntfy's `Title`, `Tags`, `Priority` and `Click` can carry what the user typed (the brief names a secret in `Tags`), and a cross-origin redirect away from an ntfy server is unusual. The message body still arrives; those extras are lost on such a hop. A user whose ntfy server redirects should configure the final URL.
- **"Origin" is scheme, host and port** (`Url::origin`), as before: a change of port alone is another origin. Everything else is as it was: 307/308 only, the `https`→`http` refusal, `MAX_REDIRECTS`, the per-hop address checks, and a same-origin hop keeping every header.
- **Tests** (`net.rs`): a 307 and a 308 to another host on the same port, and to the same host on another port, each assert at the landing server that `Authorization`, `Cookie`, `Proxy-Authorization`, `X-Api-Key`, a custom header and `X-Lodestar-Delivery` are gone, that nothing outside the allow list (and `Host`) arrived, and that the allow-listed headers and the body did. A same-origin 307 (relative) and 308 (absolute) keep every header. A unit test pins that the filter keeps exactly the list, a repeated header included. The servers record each request before answering, so the assertions need no waits.
