# V6-cluster1: cluster CA, mTLS and one-time join tokens

Remote workers v1, PR 1 of 6 (`docs/build-plan.md` P4; architecture §19.2, §19.6, §12). Everything is in `crates/cluster`; nothing is wired into `lodestar serve` or `lodestar worker` yet (V6-cluster2 does that).

## Keys and certificates
- **Ed25519 everywhere** (CA, coordinator and workers). rustls' ring provider supports Ed25519 and P-256 equally for TLS 1.3 and in webpki; Ed25519 has no per-signature nonce to get wrong, deterministic signatures and the smallest keys and certificates.
- **No new package.** Certificates are written by a small DER encoder for one fixed layout (`x509.rs`) and signed with ring. rcgen would have added rcgen, yasna, pem and time-formatting crates for three certificate shapes. Lodestar only writes certificates; all parsing and verification is rustls-webpki's. The direct dependencies added to `lodestar-cluster` (`ring`, `rustls`, `subtle`, `zeroize`) and the path dependency on `lodestar-integrations` (for the secrets key) were all already in the lockfile.
- **Shapes:** the CA has `basicConstraints` CA:TRUE pathlen 0 and `keyUsage` keyCertSign + cRLSign, both critical. The coordinator's leaf has EKU serverAuth and the DNS name `coordinator.cluster.lodestar.invalid`; a worker's has EKU clientAuth and `<name>.worker.cluster.lodestar.invalid`. The EKUs stop a worker's certificate posing as the coordinator (tested).
- **Workers verify the coordinator against that fixed name,** not the host they dialled. Workers reach the coordinator by IP, LAN name or overlay name alike; the pin is the cluster CA.
- **Lifetimes:** CA 10 years. Leaves 72 hours, renewed at half-life, so a worker offline for the whole 24-hour spool window (§19.6) still reconnects without rejoining. Leaves are backdated by **5 minutes** of clock skew; §19.3 already flags a worker past 60 s.
- **The worker makes its own key pair** and sends only the public key (§19.6: "the worker creates a key pair and the coordinator signs its certificate"). The brief's "the worker gets its cert and key" is read as "gets its certificate for its key": the private key never crosses the wire. Renewal can rotate the worker's key the same way.
- **Worker ids** are allocated at redemption (`cluster.next_worker`, from 1; 0 is `WorkerId::LOCAL`).

## mTLS
- **TLS 1.3 only**, ring provider, no system roots anywhere. The cluster port speaks two ALPN protocols, chosen from the ClientHello with rustls' `Acceptor` (`CoordinatorTls::config_for`): `lodestar-cluster/1` requires a worker certificate; `lodestar-join/1` takes none and may only redeem a token. Anything else, or both, is refused before the handshake.
- **Every cluster handshake** checks, under one read lock of the live trust state: the chain to a trusted cluster CA (webpki: signature, validity, EKU), then that the certificate's SHA-256 is **one the coordinator issued and hasn't revoked**. A valid chain the coordinator never issued (a leaked CA key, a lost record) is refused too.
- **Revocation** is the `revoked` flag on each issued-certificate record; `revoked_serials()` lists them. It applies from the next handshake, and `CoordinatorTls::identify` re-checks it on an open connection; closing connections that are already open is V6-cluster2's (§19.8: "within one heartbeat"). Revoked records are dropped once the certificate has expired, since webpki refuses it from then on anyway.
- **Rotation** (`rotate_ca`): a new CA signs every new and renewed worker certificate at once, and the old CA stays trusted for **7 days**. The coordinator keeps presenting a certificate from the **old** CA until the overlap ends, so workers that haven't renewed yet still recognise it; renewal grants carry both CAs. A renewing worker is told to renew early (`PeerIdentity::renew_now`). When the overlap ends (`maintain`), the coordinator moves to a certificate from the new CA and forgets the old CA and everything it signed. The switch waits for any open join token that pins the old CA (at most 15 minutes). A worker that was offline for the whole week must join again.

## Join tokens
- `lsj1` + 122 base32 characters: an 8-byte id, a **256-bit secret**, the **SHA-256 of the CA certificate** the coordinator presents, and a 4-byte checksum (so a typo reads as "mistyped", not as an untrusted coordinator). Parsing is strict (one spelling besides case) and property-tested: arbitrary text never panics, random well-formed text is refused, every one-character change is refused.
- **15-minute expiry, single use, bound to the worker name** given when it was created; at most 64 open at once. A name with a live certificate can't get a token or redeem one until that worker is revoked.
- **Stored only as a hash**: SHA-256 over a domain label, the id and the secret (256 random bits need no slow hash), compared with `subtle` in constant time. The token text exists only in what `create_join_token` returns; `JoinToken` never prints and is zeroed on drop.
- **Until the secret matches, every refusal is "unknown"**, so a guess learns nothing. After it matches: already used (a replay), expired, or name in use. The protocol should send one "token refused" answer for all of them.
- **Spending is atomic:** the used mark, the new certificate's record and the next worker id are written in one transaction. Spent records stay until their expiry, so a replay reads as "already used", across restarts too; after that it reads as unknown.
- **First join without a man in the middle:** the join connection trusts only a chain to the CA whose fingerprint is in the token, and the coordinator sends that CA's certificate in its chain. A different CA, or the real CA's (public) certificate in front of a leaf signed by another key, is refused (tested).

## Persistence
- **Coordinator: the store's `settings` table**, under `cluster.` (no migration; B8 owns M5's). Records are versioned (`v1`), space-separated lowercase hex; the layout is in `coordinator.rs`'s module docs. One transaction per operation. An unknown or malformed `cluster.` record refuses to load rather than being guessed at.
- **Private keys** (CA, coordinator) are sealed with the install's existing secrets key (`lodestar_integrations::SecretStore`, XChaCha20-Poly1305, `secrets.key` outside the database), with the certificate's fingerprint in the context so a sealed key can't be moved to another record. A copy of the database alone holds no usable key (tested). `SecretStore` key rotation needs the cluster records re-sealed; that hook is V6-cluster2's, when the binary owns both.
- **Worker: `<data>/cluster/credentials`**, a small versioned text file (mode 0600 on Unix), written atomically, with the key sealed by the worker's own `SecretStore`.

## Secrets and logs
- The crate logs nothing. `JoinToken`, `KeyPair`, `Credentials`, `Coordinator` and `CoordinatorTls` print no key material or token text (tested), and no error carries any.
- Key material is zeroed where we hold it (`Zeroizing` PKCS#8 bytes, token bytes, the hex passed to the sealer). ring's expanded Ed25519 key and the copies rustls keeps for signing aren't, which is as far as those crates allow.
