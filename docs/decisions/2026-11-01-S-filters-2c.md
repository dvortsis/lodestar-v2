# S-filters decisions, part 2c: "Block this…" in a result's menu and the detail drawer

Completes S-filters (§20.2 "Block this…", §20.9, §20.10, §20.11). Part 2b measured the hooks and moved them here (`2026-10-31-S-filters-2b.md`).

- **Where it shows.** A result's More menu gets a third item, **Block this…**, after Copy info hash (keyboard: Shift+F10 or the menu key on a row, then End or the arrows). The detail drawer and `/t/[hash]` share `DetailActions.svelte`, so both get a **Block this…** button beside Copy magnet. Both open the flows' existing `BlockThisDialog`; nothing in `filters/flows/**` changed.
- **What it pre-fills: only what the view shows.** The dialog gets the torrent's hash, its v2 hash and its raw name, nothing else (no title, files, trackers or category). The list row shows the raw name on its second line when it differs from the title, and the drawer shows it in its summary. A card (Cards density, which uses the same More menu) shows only the title, so there the raw name's words first appear in the dialog, before anything is sent. The raw name is passed, not the title, because the phrase tier's rule is `name:"…"` and matches raw names. The dialog shows the rule's query before the preview, so the v2 hash it adds is on screen too. Search results and the drawer list only torrents the server lets the viewer see (withheld and, with "Show adult content" off, adult torrents never reach them, §20.9), so the dialog can't show a name the view couldn't.
- **The drawer acts on the torrent shown when Block this… was pressed, and only while it's shown.** If the drawer moves to another torrent or loses it, or visibility is invalidated (e.g. "Show adult content" turned off), while the flows load the press is dropped (same rule as Copy magnet). Once the dialog is open, the same events close it, so it never keeps showing a name the view no longer may.
- **Only an added rule.** The entry points start nothing themselves: `BlockThisDialog` builds `addRule({ query, action })`, previews it, and applies it through the flow. Cancel and Esc send no change; a refused apply shows the server's message (the flow's `failed` state). There's no shadow, Undo, exception or removal path from here.
- **One door into the flows: `features/filters/flows-door.ts`.** Every consumer that starts a filters change loads them through `import('…/flows-door')` and then `load()`: the Filters screen (its change dialog, the change flow, the override editor and the reveal dialog), the result menu, the drawer and `/t`. `load()` imports `flows-root.ts`, which re-exports the flow components and `createChangeFlow`. That makes `flows-root.ts` the flows' only dynamic-import root from these views, so the bundler keeps the flows and the overlay code they bring in one on-demand group. It no longer regroups them with a chunk that the Filters screen imports statically, which is what broke 2b. The door is a separate small module because a dynamic import's preload list sits in the importing chunk (X-alert-search-headroom). So Search results, the drawer and `/t` each pay for one small import, and the ~0.5 KB list is fetched with the door on the first press. Appearance's 18+ dialog and the wizard's pack step (`PackStep.svelte`, `flow.svelte.ts`) still import their one flow module directly: they're outside this slice, and neither brings in the dialogs. Moving them behind the door, and adding their views to the guard, is a follow-up.
- **A guard.** `.size-limit.mjs` reads the chunk graph (`modulesIn`) and fails, before measuring, if the Filters first view, Search results, the detail drawer or `/t` contains any `filters/flows/**` module or `flows-root.ts`. Checked by importing `flows/block.ts` statically in `DetailActions.svelte`: the size step failed naming the drawer and `/t`.
- **A walk that reaches the door as on demand stops there** (`FLOWS_DOOR` in `walk` and `ownChunk`). Without the stop, the entries that collect what loads later would subtract the flows' modules as if already loaded, and so leave out modules the view shares with them. A first draft showed that hole: "Detail sections" dropped Banner, Input and Svelte's input bindings (−2.2 KB), and "Settings controls" dropped Radio (−0.5 KB). The door is now on demand in `detailLazy` and `settingsOnDemand`, and both entries match `main` to the byte. A walk that reaches the door as part of a first view walks on, so the view counts the flows and the guard names it. Whether an import is on demand is declared in the entry's list, as for every other lazy chunk; the graph can't tell a press from a mount-time import.
- **The door has its own entry, "Filters flows door (on demand)", 0.58 KB** (measured 0.53 KB + 10%), as Save search's loader does. "Filters dialogs (on demand)" now measures from `flows-root.ts`. It now also counts the change flow (`flow.svelte.ts`, `machine.ts`, 2.15 KB), which the Filters first view counted before, although it only loads on the first change. It also counts `BlockThisDialog` and its radio field. No limit was raised. That entry has 104 B of headroom (34,296 / 34,400 B). The next slice that adds to the flows has to find bytes, or the runner decides under §2.26.

- **Not done here (follow-ups):** after a successful `hide`, the torrent stays in the current results and the drawer until the next search or refetch (no `onapplied` refresh at either entry point). A failed load of the door in the drawer does nothing visible; the result menu shows the error toast. A toast in the drawer would bring the toast store into its first view, and it has 230 B of headroom.
