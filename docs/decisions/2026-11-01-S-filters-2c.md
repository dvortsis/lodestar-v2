# S-filters decisions, part 2c: "Block this…" in a result's menu and the detail drawer

Completes S-filters (§20.2 "Block this…", §20.9, §20.10, §20.11). Part 2b measured the hooks and moved them here (`2026-10-31-S-filters-2b.md`).

- **Where it shows.** A result's More menu gets a third item, **Block this…**, after Copy info hash (keyboard: Shift+F10 or the menu key on a row, then End or the arrows). The detail drawer and `/t/[hash]` share `DetailActions.svelte`, so both get a **Block this…** button beside Copy magnet. Both open the flows' existing `BlockThisDialog`; nothing in `filters/flows/**` changed.
- **What it pre-fills: only what the view shows.** The dialog gets the torrent's hash, its v2 hash and its raw name, nothing else (no title, files, trackers or category). The row shows the raw name on its second line, and the drawer shows it in its summary. The dialog shows the rule's query before the preview, so the v2 hash it adds is on screen too. Search results and the drawer list only torrents the server lets the viewer see (withheld and, with "Show adult content" off, adult torrents never reach them, §20.9), so the dialog can't show a name the view couldn't.
- **The drawer acts on the torrent shown when Block this… was pressed.** If the drawer moves to another torrent, or visibility is invalidated, while the flows load, the press is dropped (same rule as Copy magnet).
- **Only an added rule.** The entry points start nothing themselves: `BlockThisDialog` builds `addRule({ query, action })`, previews it, and applies it through the flow. Cancel and Esc send no change; a refused apply shows the server's message (the flow's `failed` state). There's no shadow, Undo, exception or removal path from here.
- **One door into the flows: `features/filters/flows-door.ts`.** Every consumer that starts a filters change loads them through `import('…/flows-door')` and then `load()`: the Filters screen (its change dialog, the change flow, the override editor and the reveal dialog), the result menu, the drawer and `/t`. `load()` imports `flows-root.ts`, which re-exports the flow components and `createChangeFlow`. That makes `flows-root.ts` the flows' only dynamic-import root from these views, so the bundler keeps the flows and the overlay code they bring in one on-demand group. It no longer regroups them with a chunk that the Filters screen imports statically, which is what broke 2b. The door is a separate small module because a dynamic import's preload list sits in the importing chunk (X-alert-search-headroom). So Search results, the drawer and `/t` each pay for one small import, and the ~0.5 KB list is fetched with the door on the first press. Appearance's 18+ dialog and the wizard's pack step still import their one flow module directly: they're outside this slice, and neither brings in the dialogs.
- **A guard.** `.size-limit.mjs` reads the chunk graph (`modulesIn`) and fails, before measuring, if the Filters first view, Search results, the detail drawer or `/t` contains any `filters/flows/**` module or `flows-root.ts`. All four views stop at the door when measured (`filtersDoor`).
- **The door has its own entry, "Filters flows door (on demand)", 0.58 KB** (measured 0.53 KB + 10%), as Save search's loader does. "Filters dialogs (on demand)" now measures from `flows-root.ts`. It now also counts the change flow (`flow.svelte.ts`, `machine.ts`, 2.15 KB), which the Filters first view counted before, although it only loads on the first change. It also counts `BlockThisDialog` and its radio field. No limit was raised. That entry has 104 B of headroom (34,296 / 34,400 B). The next slice that adds to the flows has to find bytes, or the runner decides under §2.26.
