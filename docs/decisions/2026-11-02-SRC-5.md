# SRC-5 decisions (per-plugin egress and kill switch)

Slice SRC-5 of `docs/plan/2026-11-01-v06-sources.md`. It covers architecture §18.4 (per-plugin egress), §18.7 ("every external connection goes through the plugin's egress setting"), §5 (VPN-first deployment, proxying) and §12 (the SSRF guard). Every source plugin's HTTP client comes from `lodestar_sources::egress::EgressFactory`, starting with SRC-7.

## The factory and the client
- **`EgressFactory::build(plugin, &Egress, Endpoints)` returns a `PluginEgress`, which is the plugin's `Fetch`** (SRC-0's seam). It goes into the plugin's `Kit`, behind the plugin's `HostLimiter`, so pacing and back-off work as SRC-0 set them.
- **It never fails.** A route that can't be used (an interface by name off Linux, an invalid name, unreadable credentials) gives a client whose kill switch is down for good. The reason shows in its status and every request is refused.
- **The reqwest client stays in `crates/integrations`.** `GuardedClient::with_route` builds it, and `GuardedClient::exchange` sends one request from plain values (method, URL, headers, body) and reads the body within a limit. So `crates/sources` doesn't depend on reqwest, and `crates/integrations/clippy.toml`'s ban on unchecked `send`/`execute` still covers every request.
- **Bounds:**
  - the request timeout is 30 s by default, clamped to 1–120 s, connect included (connecting is capped at 10 s);
  - bodies are read up to SRC-0's `MAX_BODY` (16 MiB) and refused past it;
  - response headers are capped by hyper's defaults (100 headers, about 400 KB);
  - redirects are never followed by the `Fetch` (SRC-0); `send_following` follows at most 5.

## Routes (`Egress`)
- **Direct:** the routing table. No kill switch, because there's nothing to check.
- **Bind address:** every socket binds to the address before connecting.
  - **Only destinations of the bound address's family are connected to.** hyper-util binds a socket only when the destination's family matches the bound address; a socket of the other family would connect unbound, over the default route. So a v4 bind drops v6 answers, and a v6 literal fails (and the reverse).
  - **Windows only.** Windows' strong host model makes a bound address pin the interface that owns it. On Linux the routing table still picks the interface: an address left on a downed VPN interface (`ip link set wg0 down` keeps it) would send packets out of the default route while the address check stays good. So on Linux the plugin's egress is down with `BindAddressOnLinux` ("on Linux a bind address doesn't keep traffic on the VPN; choose the interface by name"). `GuardedClient`'s `Route::BindAddress` itself works on both, and the tests use it on Linux to prove the socket is bound.
- **Interface:** `SO_BINDTODEVICE`, through reqwest's `interface()`, so packets can leave only through that interface. Both families are bound.
  - **Linux only.** Elsewhere the client is down with `Unsupported` ("choosing a network interface by name works only on Linux; choose the interface's address instead"). Windows users choose **Bind address** with the VPN adapter's address. macOS isn't a supported platform.
  - Linux 5.7 or later lets an unprivileged process set `SO_BINDTODEVICE`; the Docker image runs as root anyway.
  - The name is checked as Linux's `dev_valid_name` does: 1–15 bytes, not `.` or `..`, no `/`, `:`, whitespace or control characters. So the name is also safe as one path segment under `/sys/class/net`.
- **SOCKS5:** reqwest's `socks` feature (approved in the plan; it adds no crate, because hyper-util already carries the SOCKS code). `Proxy::all` sends both schemes through the proxy, with no `NO_PROXY` list, after `no_proxy()` has turned system proxies off.
  - **The proxy's address is a literal `SocketAddr`.** It's infrastructure the user chose, so it isn't checked against the destination policy. A name would be resolved through the guard, which would refuse a proxy on the LAN or inside the tunnel. SRC-14 resolves a name the user enters before it reaches the factory.
  - **No fallback.** When the proxy is down, connections fail; nothing goes direct (tested).

## DNS on the interface and bind-address routes
- **Names are resolved by the system resolver, outside the route.** Only the HTTP sockets are bound; `getaddrinfo` sends its queries wherever the system's DNS settings say. When the VPN interface isn't the default route, the LAN or ISP resolver sees which hosts a plugin contacts. The connection itself still goes only through the route, or fails.
- **Who this affects:** the usual setups (a container whose whole network is the VPN, `network_mode: service:gluetun`, or a VPN that also sets the system's DNS) resolve through the tunnel anyway. A per-plugin interface beside a non-VPN default route doesn't.
- **The private choice:** SOCKS5 with proxy DNS (the default) keeps lookups in the tunnel. A resolver bound to the interface (a DNS client of our own) is possible later; it's beyond this slice.
- This is a statement against §18.7's "every external connection goes through the plugin's egress setting" for DNS lookups. Flagged to the runner for the owner, with the `HTTPS_PROXY` note below.

## SOCKS5 and DNS
- **Default: the proxy resolves names (`socks5h`, `SocksDns::Proxy`).** No lookup leaves outside the tunnel, which is why people use a proxy. The guard can't see the address the proxy connects to, so it checks what it can:
  - IP literals, against the policy;
  - names that are plainly local, refused unless the policy allows that class: the metadata names (`metadata.google.internal`, `metadata`, `instance-data`, `instance-data.*`) as metadata, which is never allowed; `localhost` and `*.localhost` as loopback; and single labels, `.local`, `.lan`, `.home.arpa` and `.internal` as private;
  - the plugin's host list, when it has one.

  **What isn't covered:** a public-looking name the proxy resolves to an address on its own network, and rebinding on the proxy's side. The proxy's network decides what such a name reaches. Tested: the stub sees the name, and the local resolver isn't called.
- **`SocksDns::Local` (`socks5`):** Lodestar resolves through the guard, refuses the name if any answer is disallowed, and sends the proxy a checked address. The lookup leaves outside the tunnel. Tested: the stub sees an address, and a loopback answer under a public-only policy is refused before the proxy is asked.
- **IP literals reach the guard's resolver in local-DNS mode** (reqwest resolves them like names, IPv6 in brackets). The guard now checks a literal against the policy without calling the inner resolver.

## Kill switch
- **It's always on for a non-direct route.** §18.4 calls it "optional". The brief requires that a chosen route never falls back to direct, and a kill switch that's off would mean exactly that fallback. **Refinement (runner's call, §2.19):** choosing a route is the opt-in, and there is no "route, but fall back" setting.
- **Before each request** the route is checked:
  - **Bind address (Windows):** a UDP socket binds to the address, which succeeds only while it's assigned.
  - **Interface:** `/sys/class/net/<name>/flags` exists and has `IFF_UP`.
  - **SOCKS5:** a TCP connection to the proxy succeeds within 5 s. A good answer is trusted for 10 s; a down route is re-checked on every request.

  A request that fails to connect or times out re-checks at once, so the status catches up. Probes run one at a time, so a slow good answer can't overwrite a newer bad one.
- **The probe isn't the safety; the socket is.** Tests build each route with a probe that always says up and show the bound socket still fails closed: a bind to an unassigned address, and a device that doesn't exist, never reach the server.
- **In flight:** each request races the route's state. When it turns down, the request is abandoned with "egress went down: …". `PluginEgress::monitor(every)` probes on a timer; the host spawns one per plugin with a non-direct route (SRC-14 wires it). Without the monitor, new requests are still refused.
- **Observable per plugin:**
  - `PluginEgress::status()` gives the route kind, the state (`Unchecked`, `Up`, or `Down(reason)`), and `EgressCounters`: answered, kill-switch refusals, kill-switch aborts, policy refusals, transport failures and trips (changes to down);
  - `watch()` gives the live state.

  The counters follow `IntegrationMetrics`' pattern (atomics and a snapshot). `docs/metrics.md` gains the series names. **Nothing emits them yet:** rendering them in the Sources API and `/metrics`, and spawning `monitor`, are gates for SRC-14.

## Endpoint policy (§12)
- **`Endpoints::manifest(&manifest.endpoints)`:** for built-in public endpoints. Public addresses only (`NetPolicy::notification(false)`), and only the declared `http`/`https` hosts, each over its declared scheme (an `https` endpoint isn't fetched over `http`). Hosts match exactly, through SRC-0's `host_key`, so subdomains aren't included; the port isn't checked. A host that isn't listed is refused before any lookup.
- **`Endpoints::user_entered(policy)`:** for URLs the user enters. The guard's policy for that kind of endpoint (for example `download_client()` for a LAN indexer), with any host. `only_hosts` narrows it.
- **The policy applies after DNS resolution and on every hop:**
  - every answer is checked, and a name with any disallowed answer is refused whole;
  - every new connection resolves again, which catches rebinding (tested end to end);
  - each redirect is a new request through the same checks (tested: a redirect to the metadata service, to link-local, and to a name that resolves to the metadata service).
- **`send_following(client, req)`:** follows at most 5 redirects, each through the plugin's `Client`, so each hop is paced too.
  - 307 and 308 keep the method and body. 301, 302 and 303 become a `GET` without a body; `HEAD` stays `HEAD`.
  - `https` → `http` and non-http schemes are refused.
  - `Authorization`, `Cookie`, `Proxy-Authorization` and `X-Api-Key` are dropped when a hop changes origin.

  `GuardedClient::send_following` (307/308 only, three hops) is unchanged for notifications.
- **Errors name an address class or a rule, never a URL.** A policy refusal or a kill-switch refusal is `HttpError::Transport` with fixed text, so SRC-0's limiter backs off as for any transport failure.
  - **Follow-up for SRC-14's brief:** a separate `HttpError` variant, so a kill-switch refusal doesn't count against the source's host. Today a VPN outage backs the plugin's hosts off, up to the back-off ceiling. `http.rs` is outside this slice.

## Credentials
- **`EgressCredentials::socks5(source)`** is the boundary to SRC-4's per-source credential store, which seals with `SecretStore`. It returns `Option<SocksAuth>`, read once when the client is built. A store error leaves the route down (`CredentialsUnavailable`).
- **`SocksAuth` holds the user name and the password as `Secret`s** (zeroized on drop). The user name counts as secret, because some VPN providers use the account number.
  - `Debug` on `SocksAuth`, `Socks5Route`, `Route`, `PluginEgress` and `EgressStatus` prints neither.
  - reqwest errors are mapped without their text, as the guard already did, and reqwest's proxy matcher strips the user info before anything prints the proxy.
  - Each must be 1–255 bytes (RFC 1929). hyper-util writes the lengths unchecked, so a longer value is refused (`CredentialsUnavailable`) rather than desynchronising the handshake.
  - **Not zeroized everywhere:** reqwest keeps a copy in its proxy URL `String` for the client's life, outside `Secret`'s zeroize-on-drop.
  - Tested: a password with `@ : / %` round-trips to the stub, and no error or `Debug` string contains it or the user name.

## `HTTPS_PROXY`
**Plugins ignore `HTTPS_PROXY`, as the guard already did.** A proxy that resolves names itself would bypass the guard. §2.28's acceptance covers blocklist fetches only, so this is a separate statement for plugins:
- the per-plugin SOCKS5 route is the supported proxy;
- a VPN that routes the whole container still applies.

Flagged to the runner for the owner.
