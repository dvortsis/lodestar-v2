# WK-5 decisions (`Assign` v1 and placement)

WK-5 follows plan `docs/plan/2026-11-06-v06-workers.md` §4.3 and Q5/Q9, and architecture §19.5 and §19.2. None of these points loosens an owner decision or changes an owner-set number. Q9's deferral of `sharded(unit)` and token leases was already flagged in the plan.

## The `Assign` payload (`crates/cluster/src/assign.rs`)
- **A fixed layout, not postcard.** The payload is one version byte, then 55 bytes, little-endian (`ASSIGN_V1_LEN` = 56). It has no length field and no collection, so decoding allocates nothing.
  - **Unknown versions:** refused before any other byte is read. A v2 payload of another length still reads as "unknown version".
  - **Wrong length:** refused before any field is read.
  - **Every field is checked** before an `Assignment` is returned. Unknown role bits are refused, and a DHT-less payload must carry a zero shard, so a payload that decodes re-encodes to the same bytes (property test and fuzz target).
- **The payload carries the revision too.** `Assignment::from_message` refuses a payload whose revision differs from the message's. Revision 0 with an empty payload is the server's greeting ("nothing assigned yet") and decodes to `None`.
- **Its own `ShardSpec` and `Intensity`.** `lodestar-cluster` doesn't depend on `lodestar-dht`, so the payload has its own shard type. It checks exactly what `Shard::new` checks. `crates/lodestar/src/cluster/placement.rs` converts it (`dht_shard`: the full shard becomes `None`, WK-4's "no shard"). This adds no `Cargo.toml` edit.
- **The budget's shape:** CPU share (1–1000 ‰), RAM, upload and download in kB/s, with 0 meaning no cap beyond the defaults. §19.5 names the budget but not its fields. WK-10 applies them and WK-14 sets them. A field may change until WK-G freezes protocol 1.0 (Q11).
- **Pool cap:** 50,000 keys by default (Q5). The payload is refused above 1,000,000, so a bad value can't size a worker's pool past any memory budget.
- **Roles:** DHT, fetch and prepare bits. In v1, fetch and prepare are always set ("everywhere"). There is no plugin field: v1 can't place a source plugin on a worker (Q9).

## Placement (`crates/cluster/src/placement.rs`)
- **Prefixes are split fleet-wide, slots per IP.** Every DHT member gets one contiguous run of the 256 target prefixes, in member order: the coordinator first, then by worker id. So no two members walk the same prefix and together they cover all 256.
  - **Members sharing a public IP** split its 8 BEP 42 slots round-robin.
  - **A member alone on its IP** keeps all 8.

  This reads the plan's two sentences ("same IP splits slots and prefixes"; "different IPs keep all slots and get a share of prefixes") as one rule that satisfies both, and the gate's "no overlap, full cover".
- **The coordinator's own DHT is one member of its IP.** With no worker it gets `ShardSpec::FULL` and one install's limits, so single-machine behaviour doesn't change (§19.8). A coordinator with its DHT off isn't a DHT member, but it still counts for connections.
- **Caps:** at most 8 DHT members per IP (one per slot) and 256 in the fleet (one prefix each). Members past those caps run fetch and prepare only.
- **Grouping:** members that share any reported address (an IPv4-mapped address counts as its IPv4 address) are one group, transitively.
- **Reported addresses are hints** (runner, 2026-11-07T00:26Z). `Hello` already caps them at `MAX_EXTERNAL_IPS` (8) in `validate`; `tests/placement.rs` checks it.
  - **A worker that reports more than one address** may leave through any of them, so it's planned in the coordinator's group. It's also grouped with everyone who shares one of its addresses.
  - **A worker that reports none**, or any member whose address is unknown, puts the whole fleet in one group. That's stricter than "into the coordinator's group", the fallback the runner set: an unknown worker could share any member's address, not only the coordinator's, so only one group for everyone keeps the per-address sums. It's slower until the addresses are known, never less polite.
  - **A lying worker can only hurt politeness from its own address.** Workers are joined by the admin and authenticated over mTLS, so this isn't a trust boundary. WK-G measures the per-address sum.
- **Connections per peer IP (today 2, the fetch pool's `per_ip`).** An IP's N members are split into ⌈N/2⌉ groups. A peer IP belongs to exactly one group, chosen by an unkeyed FNV-1a of the address (`peer_ip_bucket`, the same on every machine). Only that group's members dial the peer, and their limits sum to 2: one member gets 2, two members get 1 each. So per peer IP, the fleet behind one address opens at most 2 connections. Every member keeps at least 1 connection for the peers in its bucket.
- **BEP 51 intervals:** each of an IP's k DHT members waits k × the interval a remote node asks for, so together they sample a node no more often than one install does.
- **Only public addresses count.** These say nothing about where a remote peer sees a member from, so they're dropped (`is_public`, with a table test):
  - IPv4: private (RFC 1918), CGNAT (100.64/10), loopback, link-local, `0/8`, reserved (240/4), broadcast, multicast, benchmarking (198.18/15), IETF protocol (192.0.0/24) and the documentation ranges;
  - IPv6: loopback, unspecified, multicast, unique-local, link-local, site-local (fec0::/10), documentation (2001:db8::/32) and discard-only (100::/64).

  6to4, Teredo and NAT64 forms aren't unwrapped: they count as the public address they are (runner, 2026-11-07T02:04Z). A member left with none is unknown. Otherwise an honest worker that reports its LAN address would be planned on its own IP and double the connections from the shared NAT address.
- **A draining worker stays a member** until it disconnects. It runs no DHT and gets no new work, but it's still fetching the keys it holds (§19.6), so it keeps its IP's per-peer share. Dropping it at `Drain` would give the others its share while it still uses it.
- **Revisions are numbered from the coordinator's clock** (`Planner::starting_at`, seeded with Unix ms by `Placement::new`). A restarted coordinator's plans are still newer than any a worker applied, so "apply only a newer revision" works across restarts.
- **The cost of the per-peer split.** With 3 or more members on one IP, each may dial only the peer IPs in its own bucket. A key whose peers all hash to other buckets can't be fetched by its holder. Small swarms make this common. It's the price of the per-address sum. WK-10 should hand such a lease back early (a `Lost` outcome under a new loss code, or an early release) rather than hold it until expiry.
- **Dual-stack workers.** Reporting an IPv4 and an IPv6 address counts as "several addresses", so such a worker is planned with the coordinator and loses its full slots. v1 keeps this conservative rule (runner, 2026-11-07T00:55Z).
- **The runner accepted** both the whole-fleet grouping for an unknown address (stricter than the coordinator-group fallback it first asked for) and treating non-public addresses as unknown (2026-11-07T00:55Z).
- **Pins:** a worker's DHT pinned off keeps fetch and prepare. It still shares its IP's per-peer connections, but not its BEP 51 interval, since it doesn't sample.
- **Settings and pins are kept apart:** `set_settings` changes budget, intensity and pool cap and keeps the pin.
- **Pins and settings outlive a session.** They're kept per worker id, apart from membership, so a worker whose link drops for a heartbeat timeout rejoins with its pin and budget, not the defaults (runner's review). They can be set while a worker is away (no plan is made until it's back). `forget` drops them: WK-14 calls it on revoke or removal.
- **At most 4,096 remote workers** (`MAX_WORKERS`) per planner, so every per-IP count fits the payload's `u16`s. A join past it is ignored.
- **Re-planning:** every join, leave, drain, pin, setting, coordinator-address change and dictionary or filter version change makes a new plan. Each plan has a new revision, and every member's assignment carries it.

## Coordinator side (`crates/lodestar/src/cluster/placement.rs`)
- **Membership:** a worker is a member while it's connected and not draining, with the addresses in its `WorkerStatus`. The built-in worker is the coordinator itself.
- **`sync` sends every member its current assignment each time it's called.** It doesn't send only on a change: a worker that reconnects between two syncs is greeted with the server's empty `Assign` and would otherwise stay idle. The payload is 56 bytes. A full queue is reported and retried on the next sync.
- **`runs_on_worker(Distribution)` is false for every variant.** `ShardedKeyspace` is the DHT's, and the DHT is built in, not a plugin. The match is exhaustive, so a new variant has to be decided there.
- **Single machine:** nothing here opens the PKI or binds anything. With no worker joined, nothing is planned or sent.

## For later slices
- **WK-10 (worker runtime):**
  - Apply an `Assignment` only if its revision is newer.
  - Restart the DHT node when the shard changes (WK-4: a shard is fixed for a node's lifetime).
  - Apply `politeness` to the fetch pool: dial a peer IP only if `connections_to(ip) > 0`, up to that many.
  - Multiply the BEP 51 wait by `bep51_interval_scale`.
  - Apply the same to the coordinator's own DHT and pool, from `Placement::coordinator()`.
  - **Tighten before loosening.** A plan may loosen a member's limits (a worker left; the number of peer groups changed, which moves peers between buckets). Apply a tighter share at once, and close connections the new share forbids. A worker that loses its session must stop its DHT and stop opening connections at once: the coordinator re-plans without it and widens the others' shares, so a worker still running on its last assignment would break the per-address sum. In-flight fetches may finish.
  - **Revisions** order plans from one coordinator. They're numbered from its clock, so a newer coordinator's are newer; a worker still resets its "last applied" on a `Welcome` from a coordinator whose clock went backwards.
  - `set_coordinator_ips` comes from the coordinator's DHT address vote. **A coordinator with its DHT off never learns its address**, so every plan treats the fleet as one IP: polite, but at most 8 DHT members and split slots for everyone. A second source is needed (the fetch pool's peer-reported address, or a `[cluster]` setting); WK-10 or WK-1's config owner adds it.
  - **The `serve` hook is WK-10's** (runner, 2026-11-07T00:55Z; the runner adds `crates/lodestar/src/cluster/serve.rs` to WK-10's owns), so nothing sends `Assign` before something handles it. What it calls, and when:
    1. **At start:** build one `Placement::new(coordinator_dht)` beside the `ClusterServer`. It opens nothing, so build it whether or not workers are allowed.
    2. **On every cluster tick while a server runs:** `placement.sync(&server.snapshot(), &server)`. Retry the workers in `Synced::full` on the next tick (nothing else to do). When `Synced::replan` is `Some`, apply `replan.coordinator` to the coordinator's own DHT (restarting it when the shard changes) and fetch pool.
    3. **On the coordinator DHT's address vote:** `set_coordinator_ips(ips)`, and apply the returned plan's coordinator share as in step 2.
    4. **From WK-14 and WK-8:** `pin`, `set_settings` and `set_versions`; their plans go out on the next tick.
  - **External IPs reach the coordinator only in `Hello`** (`WorkerStatus::external_ips`, which `sync` reads). A worker should know its public IP before `Hello`, for example after its DHT's first address vote, and reconnect when it changes. Otherwise it's planned as unknown: polite, but the whole fleet is one group.
- **WK-G: IPv6 neighbours.** BEP 42 masks an IPv6 address to its top /64, so two members on one /64 with different addresses are planned as separate IPs, keep all 8 slots each and mint the same id prefixes. Politeness still holds, because the fetch pool counts exact peer IPs and remote nodes rate-limit by exact address. Grouping IPv6 members by /64 for slots goes with the per-family refinement below.
- **WK-G (the per-address measurement):** a refinement to evaluate is grouping per address family. A remote peer sees a worker's IPv4 and IPv6 addresses as different addresses, so a dual-stack worker needn't share the coordinator's group. The runner flags it to the owner as a §2.19 refinement.
- **WK-14 (workers API):** pins go through `Placement::pin` (`DhtPin::Auto`/`Off`), revoke and removal through `Placement::forget`; budget, intensity and pool cap through `set_settings`, which clamps the pool cap to 1–1,000,000 and the CPU share to 1–1000 ‰.
- **WK-8:** announce the dictionary and filter-snapshot versions through `Placement::set_versions`. Their bytes travel in WK-0's snapshot chunks.
