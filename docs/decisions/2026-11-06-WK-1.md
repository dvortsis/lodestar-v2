# WK-1 decisions (the cluster port in `lodestar serve`)

Plan `docs/plan/2026-11-06-v06-workers.md` §4.3 WK-1 and Q3; architecture §19.2, §19.6, §12; builds on `docs/decisions/2026-11-06-WK-0.md`.

## Off until allowed (plan Q3, a tightening)
- **`[cluster] enabled` is "Allow workers", off by default.** While it's off, `serve` binds nothing, opens no store connection or secrets key for the cluster and creates no `cluster.` rows: a single-machine install has no cluster port, CA or keys (§19.6 "created on first use"). The default port number stays `8091` (`listen = "0.0.0.0:8091"`, §19.2). The real-binary test `tests/cluster_serve.rs` proves both halves; `cluster/serve.rs`'s unit tests prove it in-process, including that not even `lodestar.db` or `secrets.key` is touched.
- **The port follows a switch, not only the config.** `ClusterHandle::set_allowed` turns it on or off in a running `serve`, so Settings → Workers (WK-14, WK-16) only has to call it and save its own setting. WK-1 doesn't save the switch: the config decides at start. Off stops every session (`Stop(Shutdown)`) and closes the port; leases remote workers held stay in the lease authority and expire as any silent worker's do (WK-9 hands parked keys to the built-in worker). Nothing is deleted: the CA and the workers' certificates are kept, so the same workers reconnect when it's on again.
- **The port is bound before the PKI is opened**, so a taken port creates no CA. At start, a bind or PKI failure fails `serve` with the reason (`cluster port (bind): binding cluster.listen …: Address in use`), as other bad configuration does. A later change that fails is logged (`cluster.start_failed`, with a fixed error kind) and counted, and serving goes on.
- **A fixture (`serve --fixture`) never opens the port**, whatever the config: a fixture is served offline.
- **No environment variable** for `[cluster]` yet. Settings → Workers is where the plan has users turn it on (Q3); a `LODESTAR_CLUSTER_*` variable can follow with the packaging slice (WK-18) if a template needs one.

## Config validation (from #538's review)
- Every `[cluster]` number is checked at load, with a `cluster.<key>: <value> is outside <low>..=<high>` error: `max_skew_ms` 1,000–3,600,000 (the server takes `max_skew_ms.abs()`, which panics on `i64::MIN`; zero or negative would flag every worker), `handshake_timeout_secs` 1–120, `max_pending` 1–4,096, `max_pending_per_ip` 1–`max_pending`, `session_queue_mib` 1–256. Heartbeat (5 s), lease TTL (the authority's, 10 min) and the rest keep the protocol's values; they aren't settings.
- `listen` port 0 takes a free port and logs it (`cluster.listening`), for tests.

## Wiring
- **The PKI runs on its own store connection and the install's `secrets.key`** (`SecretStore::open_or_create` in the data directory, the same file the settings registry seals with). The server's own heartbeat tick reloads the PKI, runs `Coordinator::maintain` hourly, sweeps revoked and silent sessions and re-grants expired leases (V6-cluster2), so `serve` adds no tick of its own.
- **The server is built with `ClusterServer::with_hooks` on `Monitor::lease_authority()`** (WK-0), so remote and local grants share one table and one funnel. `StoredKeys` is a read-only connection's `Store::find`; a read that fails counts as not stored (one extra fetch at worst; the commit refuses a duplicate) and is counted. `InboundSink` and `GrantAdmission` stay unset until WK-9: `Results` and `Counters` are refused (`accepted: false`), so a worker's spool would keep them.
- **Shutdown order:** the cluster port stops before the pipeline, so no remote session outlives the pipeline's save.

## Secrets-key rotation
- **`ClusterHandle::reseal` is the cluster's step between `SecretStore::rotate` and `SecretStore::retire_old_keys`.** It stops the server first: the running server's in-memory secrets copy predates the rotation, and its hourly upkeep (renewing the coordinator's certificate) would otherwise write a key sealed with the old secrets key after the reseal, which `retire_old_keys` would then strand. It then seals the CA, previous CA and coordinator keys with the key file's new primary key (`Coordinator::reseal`) and serves again on the key file as it is now. With no cluster PKI it does nothing and creates nothing (`Ok(false)`). The test rotates, reseals, retires, then opens the PKI with only the new key: same CA, and a joined worker still connects.
- **`serve` has no rotation flow yet** (nothing calls `SecretStore::rotate`), so the hook is in place but not called. Whichever slice adds rotation calls it, with the settings registry's and the source credentials' re-seals, before retiring.

## Metrics (`docs/metrics.md` "Cluster port")
- 20 `lodestar_cluster_*` families: whether it's allowed and listening, connected workers, handshakes, leases held and waiting, sessions, pre-auth refusals by reason, joins, grants, re-grants, busy denials, stale reports, revocations, protocol and version errors, skew flags, PKI errors, start failures and store-check errors. They render on every install (all 0 while off), and counters are summed over every server the process built, so turning workers off and on never sends them backwards. No series carries a worker name, address or certificate.

## Files edited outside the slice's first `owns` (told to the runner)
- `crates/lodestar/Cargo.toml`: `lodestar-cluster` and `lodestar-metainfo` as dependencies (workspace crates already in the binary through `lodestar-pipeline`; no new package).
- `crates/lodestar/src/http.rs`: one `AppState` field and one `render` call in `/metrics`, where every series is assembled.
- `crates/lodestar/src/logging/events.rs`: three events (`cluster.listening`, `cluster.closed`, `cluster.start_failed`, component Workers) in the binary's catalogue, which every event must be registered in.
