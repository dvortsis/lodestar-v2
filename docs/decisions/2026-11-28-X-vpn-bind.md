# X-vpn-bind decisions (PR pending)

Owner §2.85 (D8): the VPN is optional and works with any provider, with system-wide VPNs and with VPNs in other containers. Plan `docs/plan/2026-11-26-fastest-1.0-proposal.md` §4.6. This slice is A: the binding, the pause and the API. The settings screen, the "VPN down" wording and its glossary entry are slice B (`X-vpn-bind-ui`, runner, 2026-11-28).

## The setting
- **`dht.interface` in `config.toml`, and only there in this slice** (runner, 2026-11-28). The settings form renders every field the Settings API lists, so a field there would show at once, unlabelled. X-vpn-bind-ui adds the Settings field (`crawler.interface`, restart-required) with its strings.
- **Unset or empty (the default) means any route, and that path is unchanged.** No socket goes through `socket2` that didn't before, no guard is made, no task runs and no lookup changes. A name such as `wg0` or `tun0`, or on Windows the adapter's name ("WireGuard Tunnel"), limits the crawl to that interface.
- **It takes effect at the next start** (runner, Step 0). Every crawl socket is bound at start, and the file is read only then.
- **No environment variable.** One can come with D-vpn-guide if the templates want it.
- **Validation (user input):**
  - **Linux and elsewhere:** the kernel's own rule (`dev_valid_name`): 1–15 bytes, visible ASCII, no `/` or `:`, not `.` or `..`.
  - **Windows:** friendly names: 1–256 characters, no control characters, no leading or trailing space.
  - The name is only ever a socket option, one `/sys/class/net/<name>/` path segment, or a string compared with the system's adapter list. It never reaches a shell.
  - `config.toml`'s load checks it with `Interface::parse`, so a bad name fails the start before anything binds.
- **A specific `dht.bind` address with an interface is refused at load, on every platform** (runner, review of #1167). On Linux the address could belong to another interface, and the pinned socket would then send through the VPN carrying it; Windows binds the interface's own address anyway. `0.0.0.0` and `[::]` are the only binds allowed with an interface.

## Windows: refused until X-vpn-bind-win (runner, review G)
- **On Windows a set `dht.interface` fails the start**, naming the setting and saying Windows support is pending. Unset (any route) is unchanged there. Nothing on `main` may run with the setting on Windows while a route around the interface is open (the fail-closed rule).
- **Why:** binding a socket to the interface's address leaves Windows' weak-host send path open. An adapter with forwarding enabled, or Internet Connection Sharing, lets a packet with the VPN's source address leave by another interface. Closing it needs `IP_UNICAST_IF` / `IPV6_UNICAST_IF` (the interface's index; network byte order for IPv4, host order for IPv6) on every crawl socket. No crate in the tree wraps them without `unsafe`, and the workspace forbids `unsafe`. The runner has asked the owner whether to allow one small, Windows-only `unsafe` `setsockopt` in `crates/network-policy`, as `crates/store` has for its SQLite reads (§2.35).
- **X-vpn-bind-win** (follow-up slice): if the owner allows it, it sets both options on every crawl socket (a failure is a refused pin: fail closed), tests them with a `getsockopt` read-back and a byte-order unit test, and lifts the gate. If not, Windows stays refused and the guide says so.
- **The Windows design behind the gate stays compiled and tested**, so the follow-up only lifts it: the address bind and per-family check, `WSAEADDRNOTAVAIL` tripping the guard, adapter lookup through `if-addrs`, and HTTP trackers off (reqwest gives no hook to pin its sockets, so they'd be skipped and counted like host-named ones).
- Tested: the refusal on every platform (`crawl_interface_on(true)`), and through the real entry point on Windows.

## Binding (fail closed)
- **Linux: `SO_BINDTODEVICE`** (`socket2::Socket::bind_device`), set on every crawl socket before it binds or connects. The kernel then routes the socket's packets only through that device, ignoring the routing table, and fails the send when the device is gone.
  - **Kernel and privileges:** since Linux 5.7 an unprivileged process may set it on a socket that isn't bound yet, which is how `iface::pin` is always called. Lodestar's container drops root and every capability at start (`privdrop`, PUID/PGID), so this unprivileged path is the one that has to work. Unraid 6.12+ (kernel 6.1) and current Docker hosts have it.
  - **Older kernels** need `CAP_NET_RAW`, which the drop removes. There every pin fails with `EPERM`. The DHT plugin logs `pipeline.vpn_pin_failed` (Error) once and puts the guard on **hold**: the crawl stays "VPN down" (`bind_failed`) through every check, without flapping up between attempts, while the plugin retries from 2 s, doubling to a minute. A start that works releases the hold. Only a pin's own failure counts: `Guard::pin` marks its errors (`iface::pin_failure`), and `is_refused` matches that mark, so a bind's own `EACCES` (a port below 1024) or a port in use stays the DHT source error it was before. Each retry reads the guard's generation before it starts, so a link that changes during the start makes that node stale at once. It never falls back to an unpinned socket. Tested: `pipeline/tests/vpn_hold_retry.rs` (its own binary, so the pin counter counts only its attempts) waits for two retries past the first attempt and finds `bind_failed`, no node and one trip.
- **Both: one address per family, and a family the interface lacks has no socket** (runner, security review of #1167). A check reads the interface's addresses (Linux: `getifaddrs` through `if-addrs`, Windows: the adapter list) and keeps the lowest of each family, skipping link-local and unspecified ones; an interface with none is down (`no_address`). A socket of a family the interface has no address of fails its pin (`NoFamily`): on Linux it would otherwise leave through the tunnel carrying another interface's source address (the LAN IPv4, or the real global IPv6). The DHT skips that family's socket and binds the other; a dial or UDP scrape of that family fails without touching the guard. An HTTP scrape is pinned by `SO_BINDTODEVICE` alone (reqwest has no per-socket hook), so the scheduler skips an HTTP tracker whose address is of a family the last check found no address of (`Guard::has_family`; the job counts as `skipped`), and the pinned client follows no redirect, since one could name such an address (runner, delta review of c896368c).
- **A pin while the guard has the interface down is refused, on Linux too** (runner, delta review of c896368c). Callers check the state and then pin, so a drop in between would otherwise get a socket; with a device that's up but has no address (`no_address`), its packets would carry another interface's source address. The refusal (`is_while_down`) isn't a hold: the DHT goes back to waiting for the interface, and it doesn't trip the guard again. `if-addrs` is now a dependency on Linux too (same exact pin; it uses `libc` there, and our code stays free of `unsafe`).
- **Windows (behind the gate): bind to the interface's own address.** The strong host model (the default since Vista) sends a packet with that source address only through the interface that owns it, as SRC-5 already relied on (#380). Pins read the guard's last check (`Guard::pin`), so no socket lists the adapters again; the check itself runs every 2 s on the blocking pool. Adapter names match without regard to case, as Windows does. 
  - **The weak-host send path is why Windows is gated** (above).
  - The adapter is found by its friendly name through `if-addrs` (=0.15.0, MIT or BSD-3-Clause; runner-approved, first for Windows, then for Linux's address check). Our code stays free of `unsafe`. CI's advisory check covers it on every target, and its licence texts ship (`web/licenses/rust.json`).
- **Elsewhere (macOS, the BSDs):** unsupported. Every pin fails, so the crawl stays down (`unsupported`).
- **The socket is the safety, not the probe.** Tests give a guard a probe that wrongly says "up" for a missing interface, and show that no fetch, scrape or DHT packet reaches the test server. The probe only decides when to pause and when to try again.

## Every socket the crawl opens
| Socket | Where | With an interface |
|---|---|---|
| DHT UDP, one per `[dht].bind` address | `dht/src/node/mod.rs` `bind` | Pinned; a missing interface fails `Node::start`. A send error that says the interface is gone trips the guard at once (`actor.rs`). |
| uTP (CR-4, `dht.utp`) | rides the DHT's sockets through `utp::SharedPort` | Covered by the DHT pin. `dht/tests/vpn_bind.rs` shows a pinned node's uTP reaching a peer from the DHT's own port. With an interface set the port is made re-attachable (`SharedPort::reattachable`; `Node::shutdown` detaches it), so a node made again after the interface returns attaches its fresh sockets; the same test shows the second node's uTP leaving from its own new port. Without one it's the plain port, attached once and lock-free as before (`detach` does nothing to it). |
| Peer-wire TCP dials | `peer-wire/src/fetch.rs` `dial` | Pinned (`pinned_dial`); refused without a packet while the guard is down. A failed dial that says the interface is gone trips the guard. |
| UDP tracker scrapes | `tracker-scrape/src/udp.rs` | Pinned; nothing is sent while the guard is down, and a socket from before a return is made again. |
| HTTP tracker scrapes | `tracker-scrape/src/http.rs` `client_through` | Linux: reqwest's `interface()` (`SO_BINDTODEVICE`), with certificates checked as every routed client checks them (`lodestar_integrations::tls::http_client_config(&Route::Interface(..))`). **Windows and elsewhere: off.** reqwest gives no hook to pin its sockets, and binding the interface's address alone leaves Windows' weak-host send path open (runner, review G). So with an interface set the client isn't built, HTTP trackers aren't scheduled, and they're counted with the host-named ones in `pipeline.vpn_trackers_skipped`. |
| BEP 33 scrapes | the DHT node | Covered by the DHT pin. |
| Route probe (CR-4 `route_backoff`) | `peer-wire/src/route.rs` | Left unpinned on purpose: a UDP `connect` sends nothing. With an interface set it can't make a packet leave either, since the dials it gates are pinned. |
| `UtpSocket::bind` (its own UDP socket) | `utp/src/socket.rs` | Not a crawl socket: only examples and tests use it. Unchanged. |

**Unset path changes:** none on the hot paths. `SharedPort::new` is still the lock-free, attach-once port; `Node::shutdown` calls `detach`, which does nothing to it.

**Not crawl traffic, so not covered:** the web UI and API listener, the cluster's coordinator and workers, companions, notifications, updates, the torrent cache, Prowlarr and the other source plugins (each source has its own egress setting, SRC-5).

**Workers:**
- **The built-in worker inside the main process is covered.** Its fetch stages use the pipeline's own fetcher (`PeerWireFetcher(config.fetch)`, which carries the guard), its DHT is the pinned plugin, and its pool is the one the VPN hold pauses.
- **A remote worker (`lodestar worker`) can't limit its crawl until `X-vpn-bind-worker` lands** (runner, 2026-11-28). Its own `config.toml` can carry `dht.interface`, but nothing in the worker honours it yet, so a worker with it set **refuses to start** and says why, rather than crawl by the normal route with the setting ignored. A worker without it keeps today's routes. That follow-up adds the same fail-closed bind.

## Detecting the interface going
- **A `Guard` checks every 2 s** (`iface::CHECK_EVERY`, the same as peer-wire's `PROBE_EVERY`).
  - **Linux:** `/sys/class/net/<name>`: `IFF_UP`, `operstate` not `down`, `lowerlayerdown`, `notpresent` or `dormant` (tunnels report `unknown`), no `carrier` of 0, and its `ifindex`. This is SRC-5's rule.
  - **Windows:** an adapter with that name, operationally up, with an address.
- **Immediately on a socket error** (`Guard::trip`): `ENETDOWN`, Linux's `ENODEV`, or Windows' `WSAEADDRNOTAVAIL` (the main sign there that the bound address went) marks the guard down at once, without a probe, and wakes `run` for a check on the blocking pool. That check decides: gone stays down; there, or made again, is up under a new generation, so every socket is made again. A trip never blocks the async path it's called from, and a burst of such errors marks it down once.
  - **A deviation from the approved design, accepted by the runner (review of #1167):** on Linux `EADDRNOTAVAIL` doesn't trip the guard. It's also what running out of ephemeral ports gives under heavy dialing, and one such dial shouldn't stop the crawl.
- **One check at a time:** checks hold a probe lock, so an older probe's answer can't overwrite a newer one's, and a check that a trip overtook doesn't bring the interface back up on its own answer.
- **Each return is a new generation.** A device deleted and made again (WireGuard and OpenVPN do this on reconnect) has a new index, and a socket pinned to the old one stays dead, so sockets are made again. A changed index or address while up also counts as a return.
- **Down means:**
  - the crawler is paused through `Control`'s VPN hold, beside the setup hold. The user's own pause setting is left alone, and is applied again when the interface returns;
  - the DHT plugin stops its node (state saved) rather than pausing it, so it doesn't even answer other nodes;
  - the fetch pool starts nothing, and dials are refused before any packet;
  - the scrape scheduler's jobs are skipped (`Outcome::Skipped`, not a failure against the tracker);
  - `GET /crawler` gives `state: "vpn_down"` and `interface: {interface, state: "down", reason}`. The stats page's `crawler.reason` gives `vpn_down`.
- **Up again:** the DHT node starts on fresh sockets from the saved state, the hold lifts, and the user's setting applies.
- **Down at start:** nothing binds. The pipeline's pool starts paused, the DHT plugin waits, and `pipeline.vpn_down` (Error) is logged with the reason. An interface that goes down after the pipeline starts but before `Control` takes over is held the same way: `Control::start` pauses the pool and the DHT explicitly (review of #1167), since its state already reads paused and no later change would.
- **Consumers of the new codes:** no web code, golden or metric reads `crawler.state` or the stats page's `crawler.reason` as a closed set today (the web only reads `crawler.paused`), so `vpn_down` breaks nothing before slice B shows it. The generated `schema.d.ts` gains the value and the `interface` field; one web fixture gains `interface: null`.
- **Events:** `pipeline.vpn_down` (Error, with the reason code), `pipeline.vpn_up` (Info), `pipeline.vpn_pin_failed` (Error), and once per start with a count, `pipeline.vpn_trackers_skipped` and `dht.bootstrap_names_skipped` (Info). Each VPN pause and resume is also a `pause` or `resume` row, as any pause is, so Insights draws the gap.
- **Metrics:** `lodestar_crawl_interface_up` (gauge) and `lodestar_crawl_interface_trips_total` (counter), only with an interface set (`docs/metrics.md`). `/metrics` is open by existing policy; these two say only whether the VPN is up and how often it went, never the interface's name or addresses (a test checks the name doesn't appear). The runner flags this to the owner.

## DNS: no lookups outside the interface (runner, 2026-11-28)
The runner withdrew the earlier "stated limit": the owner's leak protection (§2.85) covers DNS too. **With an interface set, the crawl sends no name to the system resolver.** That resolver asks wherever the system's DNS settings say, which can be outside the tunnel. A DNS client pinned to the interface was rejected for now: it's a new untrusted parser, it can't reach the loopback resolvers gluetun and Docker use, and Windows resolver discovery needs `unsafe` or another dependency. It stays a later option for getting hostname trackers back.

**Every name lookup in the crawl path, and what it does with an interface set:**
| Lookup | Where | With an interface |
|---|---|---|
| DHT bootstrap routers (`lookup_host`) | `dht/src/node/actor.rs` `resolve`, at each node start | Not called. `literal_bootstrap`: with the default list, the built-in addresses of its routers (`BOOTSTRAP_LITERALS`); with a list the user set, only its IP-literal entries (an empty list stays empty). Skipped names are logged once per start with a count (`dht.bootstrap_names_skipped`). |
| UDP trackers (`lookup_host`) | `tracker-scrape/src/udp.rs` | Not called. Only a tracker named by address is asked; a named one fails with `Resolve`, no packet sent. |
| HTTP trackers (reqwest's resolver; `DenyResolver`'s `lookup_host`) | `tracker-scrape/src/http.rs` | `client_through` installs `NoLookups`, which refuses every name. IP-literal URLs never reach a resolver. No redirect is followed at all. |
| Tracker list (the scrape scheduler) | `pipeline/src/health/service.rs` `through_interface` | A tracker named by host isn't scheduled at all; the count is logged once per start (`pipeline.vpn_trackers_skipped`). |
| Peer dials, uTP, the route probe, BEP 33 | `peer-wire`, `utp`, `dht` | No lookups: they take addresses only. |
| `dht.bind`, `dht.interface` | `config.rs` | Parsed, not resolved. |

- **First start with no saved table:** with the default bootstrap list the node joins through the built-in router addresses; with a list of the user's, through its IP-literal entries only. If none answers, `crawler.dht.bootstrapped` stays false and the node keeps trying those addresses (the usual bootstrap rounds). It never looks a name up. The guide should tell users to add IP-literal bootstrap nodes (`dht.bootstrap` entries written as a peer address and port) if that happens.
- **The router addresses** are the long-standing ones for router.bittorrent.com, dht.transmissionbt.com, router.utorrent.com and dht.libtorrent.org. They're used only with an interface set. The owner checked their A records on 2026-11-28 (relayed by the runner); dht.transmissionbt.com has two, so the list has five. The ports are the routers' published ones. A stale address costs only a failed join: IP-literal `dht.bootstrap` entries still work and the node keeps retrying.
- **The cost (runner flags it to the owner):** with an interface set, every tracker named by host is skipped, and nearly all public trackers are. So tracker scrape health is mostly gone while the interface is set. Swarm counts still come from BEP 33 scrapes over the DHT. Getting them back means a resolver reached through the interface, (a) above.
- **Tests:** the DHT and the scrapers count what they send to the system resolver (`lodestar_dht::node::lookups`, `lodestar_tracker_scrape::lookups`).
  - With an interface set, a node start with a name among its entries and scrapes of host-named UDP and HTTP trackers send none, and those trackers are never reached.
  - Without an interface, the same name is looked up (the control).

## What's proven where
- **Linux CI (unprivileged):**
  - `network-policy`: a missing interface fails the pin with `ENODEV`. A TCP socket pinned to another interface can't reach a loopback server that the routing table would reach through `lo`; one pinned to `lo` can. That shows the pin overrides the routing table.
  - `dht`: uTP goes out from the pinned DHT socket, before and after a rebind.
  - `dht`, `peer-wire`, `tracker-scrape`: each constructor goes through the pin (the pin counter, and `ENODEV` for a missing interface). With a lying probe, no packet reaches the test server and the guard trips. Pinned to `lo`, each works.
  - `pipeline`: down at start holds the crawl with a reason code and runs no DHT node. Up resumes and starts the node, down stops it, and the next up starts a new one. A user's pause outlasts the hold. An interface gone before `Control` starts is held. Scheduler and client: host-named trackers aren't asked, and jobs are skipped while down or under a stale generation.
  - `lodestar`: `dht.interface`'s checks at load, a remote worker refusing to start with it, the status page's `vpn_down` reason, and the two metrics. `api`: `GET /crawler` with `state: "vpn_down"` and its `interface` (a golden).
  - The guard's state machine (generations, trips, `run`'s polling) on a scripted probe, with condition waits of at least 10 s.
- **Windows CI:** everything compiles and the platform-neutral tests run: the name rules, the guard, and the VPN hold with the DHT pinned on both OSes (a probe giving loopback's address on Windows). The Linux-only socket tests are `cfg(target_os = "linux")`.
- **Not proven in CI:**
  - The DHT actor's trip on a failed send (`actor.rs`): the actor's tests send through real loopback sockets, which don't fail that way. The trip itself is `Guard::trip`, tested.
  - Windows' address binding against a real VPN adapter. CI has none, and the strong-host-model argument is SRC-5's.
  - A real interface flap (dummy or veth). It needs `CAP_NET_ADMIN` and the `ip` tool, which CI's unprivileged runners don't have, so no such test was added. The flap path is covered by the scripted-probe tests and by the device-deleted case (`ENODEV`).
  - The crawl rounds on the host measure that "Any" keeps today's performance.
