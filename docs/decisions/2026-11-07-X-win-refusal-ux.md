# X-win-refusal-ux decisions (#PR)

- **The service's refusal exit code carries the customer bit: `0x20000003` (536870915), not `3`** (runner's call). The SCM looks a bare service-specific code up in Windows' own messages, so `3` read as "The system cannot find the path specified" and `1` as "Incorrect function". With the customer bit set, Windows shows the number and looks nothing up. A Win32 code such as 5 ("Access is denied") was rejected: it sends people off to loosen permissions, the opposite of the fix. Codes other than refusals get the same bit (`service::scm_code`); 0 stays 0.
- **A refusal goes to the Application event log as event 3 from the source `Lodestar`,** as well as `%SystemRoot%\Temp\lodestar-service.log`. The MSI registers the source (`EventSource` component, .NET's `EventLogMessages.dll`). Only `acl::secure_dir`'s refusals go there, never config errors: the Application log is readable by every local user, so it gets paths, SIDs, account names and commands, never a secret or the config file's text.
- **A refusal names the account and the exact fix.** When the folder's one problem is one extra Allow entry for a user account (`S-1-5-21-` and four numbers, not a domain group RID 512 to 527), the message names it (`DESKTOP-1\alex (S-1-5-21-…)`), gives `icacls "<dir>" /remove:g *<SID> /T /C` and says Repair fixes it if that is your own administrator account. Anything else (a group or well-known SID, a second account, a Deny entry, inheritance, a user-owned folder or top-level item, a link) gets the move-the-contents-away advice, which no longer suggests deleting the folder before its contents are safe.
- **Owner §2.52 implemented in `secure-datadir.ps1`:** an install or Repair re-secures an existing, marked folder whose one problem is the installing administrator's own Allow entries: it removes that SID's granted entries from the folder and everything in it (`icacls /remove:g /T /C`, after the recursive link scan), then applies the ACL. Every other defect still stops the install, that entry plus anything else included, and the scan still fails closed (trap, exit 2).
  - **The SID comes only from a real administrator:** the MSI passes `-InstallerSid [UserSID]` only when `AdminUser` is set, with `MSIUSEREALADMINDETECTION=1` so Windows Installer doesn't set `AdminUser` for every user on a per-machine install.
  - **Deny entries are never repaired,** even the administrator's own: a Deny is not what Explorer's Continue adds, and removing one changes who is kept out.
  - Tested on real folders in `test-secure-datadir.ps1` (release workflow, before the MSI is built) and end to end in `smoke.ps1` (refusal code, event, a refused Repair with a second account, then a Repair that works).
- **`logging.event_log_errors` is wired, not hidden** (runner's call). On the Windows service, error lines go to the Application log as event 1, at most 10 a minute, with one line counting any more. They are read from the ring as `/logs` reads it, so the file mask and setup-token redaction already apply, and then every data value and untyped field is shown as `[hidden]` too, because the Application log is readable by local users while the log folder isn't. That is stricter than the file log, never looser. The forwarder runs on its own task and a writer thread, so it never holds up logging; after a failed write it stops, notes why once in the temp log, and tries again after the next settings save. Turned off, it sends nothing; turned on again, only what comes after. The refusal path writes whatever the setting is, once per start.
- **The troubleshooting chapter** (section 6.2) now gives the new code beside the old one, the Event Viewer entry, Repair as the recommended fix for your own account, and the `icacls` command. A new row in section 6.1 covers the Windows Firewall Public network profile: set a trusted home network to Private, and never add the Public profile to Lodestar's rules.
