# X-win-refusal-ux decisions (#597)

- **The service's refusal exit code carries the customer bit: `0x20000003` (536870915), not `3`** (runner's call). The SCM's event 7024 looks a bare service-specific code up in Windows' own messages, so `3` read as "The system cannot find the path specified" and `1` as "Incorrect function". With the customer bit set, Windows looks nothing up; event 7024 may show only the raw code (`%%536870915`), and the guide points to Lodestar's own log for the reason. A Win32 code such as 5 ("Access is denied") was rejected: it sends people off to loosen permissions, the opposite of the fix. Every non-zero code gets the bit (`service::scm_code`); 0 stays 0.
- **A refusal names the account and the exact fix,** in `%SystemRoot%\Temp\lodestar-service.log` as before. When the folder's one problem is one extra Allow entry for a user account (`S-1-5-21-` and four numbers, not a domain group RID 512 to 527), the message names it (`DESKTOP-1\alex (S-1-5-21-…)`), gives `icacls "<dir>" /remove:g *<SID> /T /C` and says Repair fixes it if that is your own administrator account. Anything else (a group or well-known SID, a second account, a Deny entry, inheritance, a user-owned folder or top-level item, a link) gets the move-the-contents-away advice, which no longer suggests deleting the folder before its contents are safe. The built-in Administrator and Guest, which SDDL writes as `LA` and `LG`, are spelled out through Windows first. Names in the message lose control characters, quotes and bidirectional marks and overrides, and the reason itself loses control characters and every Unicode format, line-separator and paragraph-separator character (Cf, Zl, Zp) (item names in it are whoever could write the folder's choice); the name lookup waits at most 5 s, then the SID goes alone.
- **The Windows Event Log is deferred to the owner** (runner's call, withdrawing its earlier approval). Legal Notice §5 lists every place Lodestar keeps data outside the data folder, and `legal_facts.rs` holds it to "no code writes to the Windows Event Log". The Application log is readable by every local user, so writing refusals or errors there is a change to the notice, which is the owner's to make, not a UX slice's. Nothing in this PR writes to it and the MSI registers no event source. The runner puts the question to the owner for a follow-up slice.
- **`logging.event_log_errors` is hidden** (runner's call). It never did anything. The server keeps the field, so settings files and exports an earlier version saved still load and still pass the section's schema. The UI no longer shows it, on any deployment.
- **Owner §2.52 implemented in `secure-datadir.ps1`:** an install or Repair re-secures an existing, marked folder whose one problem is the installing administrator's own Allow entries. Every other defect still stops the install, that entry plus anything else included, and the scans still fail closed (trap, exit 2).
  - **Who counts as the installing administrator:** the MSI always passes `-InstallerSid [UserSID]`, and the script uses it only for a user-account SID (as above, matched case-sensitively, ASCII digits only, nothing after the last digit) that isn't already trusted and that is a direct member of the local Administrators group. If membership can't be read, it refuses. This replaces gating on `AdminUser` (runner's call): a per-machine install sets `AdminUser` for every user, and with `MSIUSEREALADMINDETECTION` a Repair started from Control Panel under UAC doesn't get it, so the recommended fix would never have worked. An administrator only through a group, or with a work or school (Entra ID, `S-1-12-1-`) account, is refused by Repair. When the folder's only extra entries are that installing account's own and a read-only check of everything inside finds nothing else, the refusal is a message of its own, "Repair can't fix this for your account", with the `icacls` command (printed only for a plain ASCII path; otherwise it points to the guide) (runner's call, §2.26). The guide's manual step keys on that message, so a Repair refusal that found anything else never sends anyone to `icacls`. The guide never has an administrator run text from a log: standard users can create folders in `C:\Windows\Temp`, so it reads only logs in folders owned by SYSTEM or Administrators, and its `icacls` step works out the administrator's own SID itself.
  - **Lock first, then check everything.** While the entry is there, that account's unelevated processes can change the folder. So the script first removes the account's granted entries everywhere with `icacls /remove:g /T /C /L` (with `/L` a link is changed itself, never followed). Then, with nobody else able to change anything, it checks again that the folder is a real, private folder, and that everything inside, at every depth, is a real file or folder owned by SYSTEM, Administrators or the service, with plain Allow entries for only those three plus OWNER RIGHTS and CREATOR OWNER (as `acl::log_folder_private` allows on the service's logs folder). Entries are read raw on every path that keeps a folder (`Get-NotPrivateReason` ends with the raw check, so a reinstall or Repair without the administrator's entry is covered too, and so are the folder itself before and after the lock and everything inside), as `check_entries` in `acl.rs` reads them: a NULL DACL or any entry that isn't a plain Allow refuses. "Raw" means read with `GetNamedSecurityInfo` (`dacl-check.ps1`, a small Add-Type helper compiled in the log's private folder, never the world-writable temp folder) and kept as a `RawSecurityDescriptor`. .NET's own view can't be used: `Get-Acl` builds a `CommonSecurityDescriptor`, which drops object entries (OA, OD) from a file's access list altogether, so even its binary form lacks them, and it shows callback entries (XA, XD) as unconditional Allows or Denies. `Set-Acl` would then write the object entries away instead of the install refusing them. The folder's own owner is checked again too.
  - **The lock doesn't close handles opened before it.** A process that opened the folder with DELETE or WRITE_DAC while the administrator's entry was there keeps that access, and `Set-Acl` goes by path. So the script records the folder's file ID at the start, and just before `Set-Acl` checks that the path still has that file ID and is a real folder, not a link; otherwise it refuses. The gap left is `Set-Acl`'s own call, by path; only the administrator's own unelevated processes could use it, which the owner's rule accepts. Closing it with a handle-based `SetSecurityInfo` (`FILE_FLAG_OPEN_REPARSE_POINT`) is the follow-up X-win-repair-handle-acl. A refusal after the lock leaves the folder more private than before.
  - **Follow-ups (runner):** X-win-repair-handle-acl (above); X-win-deep-check-reinstall, a deep check of everything inside on every reinstall or Repair of a non-empty folder, so files planted between the manual `icacls` and the next start are caught; X-win-temp-log-owner, `temp_log` refusing a pre-created `lodestar-service.log` owned by anyone but SYSTEM, Administrators or the service. Also noted by the runner: `test-secure-datadir.ps1` runs only in `release.yml`.
  - **Deny entries are never repaired,** even the administrator's own: a Deny is not what Explorer's Continue adds, and removing one changes who is kept out.
  - Tested on real folders in `test-secure-datadir.ps1` (release workflow, before the MSI is built: `Get-DaclProblem` on descriptors built in memory, an object entry among them, which .NET's own view would drop; on disk, written natively: a non-member account, groups, Deny, a second account, inheritance, user owners at the top and deep inside, a file open to Everyone, conditional entries inside and object and conditional entries on the folder where Windows stores them, a junction, malformed, lower-case, non-ASCII-digit, space-padded and newline-ended SIDs, no marker; the manual-fix message only for a non-member or a work or school account with nothing else wrong) and end to end in `smoke.ps1` (refusal code and message, a refused Repair with a second account, then a Repair that works).
- **The troubleshooting chapter** (section 6.2) gives the new code beside the old one and what event 7024 shows, points to Lodestar's own log for the reason, recommends Repair for your own account and gives the `icacls` command, also for an administrator through a domain group or a work or school account. It says "older versions" for the old code, so it holds whether or not the change is backported. `docs/architecture.md` §12.1 no longer says errors go to the Event Log (runner-approved shared edit). A new row in section 6.1 covers the Windows Firewall Public network profile: set a trusted home network to Private, and never add the Public profile to Lodestar's rules.
