# Runner secure-delete decisions (#81)

Owner decision §2.17 (deleted data is overwritten).

- **`PRAGMA secure_delete = ON`** on every store connection, so freed pages in the main file are zeroed. FAST isn't enough: it leaves freed overflow pages, which hold large values, in the freelist.
- **The WAL is scrubbed after deletes.** Every delete path (`purge_filter`, `release`, `release_many`, `release_rules`, `delete_torrents`, and `set_enrichments_at` for the Is-adult relabel) runs a PASSIVE checkpoint, then a TRUNCATE checkpoint that waits at most `SCRUB_WAIT` (100 ms). If a reader's snapshot keeps it busy, `scrub_pending` is set and the next delete, or the hourly purge on any connection (`PURGE_EVERY`), finishes it. The shutdown checkpoint also truncates.
- **Every write transaction in `crates/store` uses `begin_write` (`BEGIN IMMEDIATE`).** A deferred transaction that reads first gets SQLITE_BUSY at once if another connection holds the write lock (a scrub's checkpoint, or simply another writer), because SQLite doesn't run the busy handler for a read-to-write upgrade. Ingest batches were lost this way. IMMEDIATE waits up to the busy timeout instead and costs nothing measurable (300 × 50 inserts, same time within noise). Existing write-first transactions are still deferred, which is safe (the busy handler runs for them), but **new write transactions should use `begin_write`** so the rule needs no case analysis.
- **Not covered, by design:** the WAL while a scrub is pending (until the retry or shutdown); Tantivy segment files, which keep deleted torrents' names until a merge (a follow-up force-merges them); migration snapshots `*.pre-vN.db`, purged and kept 90 days (`owner-decisions.md` §2.21); and filesystem-level remnants (copy-on-write, snapshots, SSDs), which an application can't control.
