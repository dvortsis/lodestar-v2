# UP-1 decisions: the watch folder

Brief: runner, 2026-11-12 (`briefs/UP-1.md`). Spec: plan `docs/plan/2026-11-05-v07-m7.md` §4.3 (UP-1) and §6 ("Folder watch adds no network surface"); architecture §3 and §18.7; UP-0's `docs/decisions/2026-11-12-UP-0.md`.

## The same path as an upload
- **Every file goes through `local_torrent::Uploads::submit`**, the queue the upload route uses: the same read, the floor's hash list first, then the full filter, then the writer's lease-free entry. Nothing is written to the store directly, and nothing bypasses the judge. A held or floor-blocked file is never stored. A `private=1` file gets both privacy bits, as an upload does.
- **The provenance source is UP-0's built-in `upload`.** A watched file and an uploaded file are the same act: the user handing Lodestar a file. A second source would split the same thing across two ids, and sources are a bounded bitmask (64).
- **No network surface:** no new route. The section is served by the existing `/settings` routes; its screen is UP-2's.

## The setting (`crates/lodestar/src/settings/watch.rs`)
- **Section `watch`:**
  - `folder`: an absolute path; empty, the default, turns the watch off.
  - `after`: `move` (the default) or `delete`.
- **Saved in the app only.** No `config.toml` key or `LODESTAR_*` variable backs it yet, so `config.rs` and `ENV_VARS` are unchanged. `LODESTAR_WATCH_DIR` for Docker is the runner's follow-up X-watch-env, with the same checks.
- **It applies live.** `watch::follow` subscribes to the section, checks the folder again each time it changes and at start, and restarts the poller.
- **The path is normalised first:** rebuilt from its components, so a trailing separator or `.` is dropped (fresh self-review, blocking). On Unix `lstat` and `O_NOFOLLOW` resolve a last component written `link/`, so without this a link written that way would pass every check. Tested, and the test fails without the fix.
- **Checked when loaded, saved values included,** by `Section::check`: empty or absolute, nothing about the disk (rv-765 B1). The registry runs this on every saved value at start and drops one that fails, so a disk check here dropped a folder on a share that mounts after Lodestar starts, and the watch stayed off for the whole run. Tested: save, restart with the folder gone, and the setting stays, the watch reports `missing`, then resumes once the folder is there.
- **Checked when saved,** by `Section::confirm`, which only a patch or an import runs: there, a directory, and not itself a link or reparse point (its own entry is read without following it). This check runs on the request's thread. It's a user action, so a hung mount slows only that save.
- **Checked when applied and again on every poll,** by `folder_problem` with the data directory, so a folder swapped for a link, or for one inside the data directory, after it was saved is never read: the folder is not the data directory, not inside it, and doesn't hold it, compared once both are resolved (`canonicalize`, so `..` and links in the parents can't hide it).
  - Neither check sees the data directory, so a folder inside the data directory saves and then shows as disabled with `inside_data_dir`. It fails safe: nothing is ever read from it.
  - **UP-2 must show that reason next to the field** (runner's note in UP-2's brief).
- **A bad folder pauses the watch with one fixed reason,** never the path: `not_absolute`, `missing`, `not_directory`, `link`, `inside_data_dir`, `holds_data_dir`, `subfolder_link`, `subfolder_not_directory`, `subfolder_create_failed`, `unreadable`, `too_many_stuck`.
  - It's logged as `watch.disabled` when it starts or changes, and `watch.started` is logged when it clears; never once per poll.
  - **The folder's checks run on every poll.** A folder that fails one (inside the data directory, a link, not a directory) stays off, with its reason, for as long as it fails, and nothing is read. **Every problem but `too_many_stuck` is re-checked this way,** so a share that mounts after Lodestar starts, or a folder the user fixes, resumes without a save or a restart (fresh self-review). Nothing is read while it's paused.
  - `too_many_stuck` holds until the setting changes or Lodestar restarts.
  - On Unix, opening the folder maps `ENOENT` to `missing`, `ENOTDIR` to `not_directory`, `ELOOP` to `link`, and anything else (such as `EACCES`) to `unreadable`.

## Polling (`crates/lodestar/src/watch.rs`)
- **Every 10 s** (`POLL_EVERY`; the plan's minimum is 5 s). No filesystem-event dependency, so it works on Docker bind mounts and SMB.
- **Bounded each poll** (§2.26 numbers, the runner's call):
  - `MAX_SCAN` = 10,000 `.torrent` names kept, and `MAX_LIST` = 200,000 directory entries read. Only `.torrent` names count against the first, so other files and folders that stay in the folder (a Downloads-style folder, say) can't hide a new torrent (fresh self-review; tested). A folder of a million entries costs one bounded listing per poll, not a stall.
  - `MAX_SUBMIT` = 32 files read and submitted. That's about 190 a minute, without letting a dropped folder starve the crawl's share of the judge. One file is held in memory at a time, so at most 8 MiB.
- **Resumes in order.** Candidates are sorted by name, and each poll starts after the last file it took, wrapping round. So a big folder drains in order and a name that sorts early can't starve the rest. The test fills the folder with `MAX_SUBMIT` + 8 files, then adds one that sorts first.
  - **What's left of starvation:** with over 10,000 `.torrent` names, or over 200,000 entries, those the listing doesn't reach wait until taken files leave the folder. Taken files do leave it; at most 1,024 stay stuck.
- **The file work runs on the blocking pool:** the listing and the classification of each entry in one call, then each read, move and delete, and the folder check when the setting is applied (rv-765 O3). Nothing in the watch blocks the runtime on a slow SMB mount; the save check above is the one exception.

## Safe file handling
- **Only regular files directly in the folder whose name ends in `.torrent`** (ASCII case-insensitive, and more than just `.torrent`). Subfolders, `added/` and `failed/` included, are never entered. Other names and a directory called `x.torrent` are left alone.
- **Nothing is followed.**
  - **Unix:** the folder is opened `O_DIRECTORY | O_NOFOLLOW` once per poll, and every step that acts on a file goes through that handle: `openat(… O_NOFOLLOW | O_NONBLOCK)` to read, `mkdirat`, `renameat` and `unlinkat` to create the subfolders, move and delete. The listing and each entry's type (`symlink_metadata`, never following) are only hints for what to try; the handle decides. A folder replaced by a link between polls stops the watch with `link`.
  - **Windows:** a file is opened with `FILE_FLAG_OPEN_REPARSE_POINT` and refused if its handle says it's a reparse point (a symbolic link, junction or mount point). The listing reads each entry without following it.
    - **Moves never overwrite:** a hard link at the target (`std::fs::hard_link`, which fails if anything is there), then the original removed. `std::fs::rename`, which replaces a target, is never used (runner, 2026-11-12).
      - Where hard links aren't there (FAT, exFAT, some SMB shares), the move fails and the file joins the never-read-again set, reported once.
      - Before the link is made, the file is opened for delete. If that fails (another program holds it without delete sharing, or it's read-only), the move fails with no link made. A removal that still fails afterwards takes the new link back. So a retried move never leaves extra names in `added\` or `failed\` (rv-765 I1).
      - **A link entry isn't moved at all on Windows** (a hard link to a link isn't defined the same way everywhere). It stays where it is, is never read, and is counted once as failed. It's remembered in a bounded set of its own (1,024), **which never holds the watch**: junctions need no privilege to make, so counting them toward `too_many_stuck` would let anyone who can write to the folder turn the watch off (rv-765 I3; tested with `mklink /J`). Past 1,024, a further one is counted again each poll and nothing worse.
      - Should Lodestar stop between the link and the removal, both names are left, and the next poll may submit the file again. That's harmless: the store keeps one torrent per info hash.
    - **The folder, `added\` and `failed\` are held open for the whole poll** without delete sharing (`FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT`, share read and write only), and each is checked through its handle to be a directory and not a reparse point (rv-765 I2). While they're held, none of the three can be renamed, deleted or replaced by a junction. So the path-based listing, reads and moves of that poll act on the folders that were checked, and the earlier race (a junction swapped in for `added\` or `failed\` between the check and the move) is closed too. No new dependency and no `unsafe`. Tested: renaming the folder or `added\` fails while a poll holds them.
      - **What's left:** a parent of the watch folder is still resolved by path, so someone who can rename the folder's parents could point the path elsewhere between polls. The next poll checks the new folder from scratch (shape and data-directory rule) before reading anything, as on Unix.
    - **No hard-link check on Windows:** `nlink` is checked on Unix only, because the link count isn't available on stable Rust on Windows. So on Windows a hard link to a file elsewhere is read like any file (it needs access to that file to make).
    - **Windows cloud and dedup files** (OneDrive placeholders, deduplicated files) are reparse points, so they're link entries: they stay where they are, never read (rv-765 I3).
- **Checked through the handle, not the name.** After opening, `fstat` must show:
  - a regular file;
  - the size and modification time it was listed with;
  - on Unix, exactly one link: a hard link to a file elsewhere goes to `failed/` as `linked`, so the watch never reads a file that lives outside the folder;
  - within the cap.

  It's then read through `take(cap + 1)`. **A file swapped for a link between the listing and the open is refused** (`O_NOFOLLOW` returns `ELOOP`, which goes to `failed/` as `link`). The swap test does exactly that between `entry` and `read`.
- **The cap is `local_torrent::MAX_BYTES`, 8 MiB, as for an upload.** A file listed over it goes to `failed/` as `too_large` on first sight, without being opened. The test makes it unreadable as well, so any read would show as `unreadable`.
- **It's read once it's complete:** its size and modification time match on two polls in a row. A file another program holds open isn't a failure; it's tried again on a later poll. That covers a Windows sharing or lock violation, `EBUSY`/`ETXTBSY`/`EAGAIN` on Unix (SMB locks show this way), and a file that vanished.
- **On Unix a link entry is moved, never followed:** `renameat` moves the link itself into `failed/` as `link`, and its target is untouched (tested). On Windows it stays where it is (above).

## Afterwards: never read twice
- **Accepted files go to `added/`; everything else goes to `failed/`, named `<stem>.<cause>.torrent`.** The causes are `malformed`, `refused` (the floor), `held` (the filter), `failed` (judging panicked), `too_large`, `link`, `linked` and `unreadable`.
  - **`held` gets its own name, not a subfolder.** One `failed/` folder is easier to find in a file manager, and the cause in the name tells the user why without any log.
- **Delete mode deletes accepted files only.** A failed file still goes to `failed/`, so the user can see what didn't go in. This is stricter about keeping things, and costs nothing.
- **`added/` and `failed/` are created without following links** (`mkdirat` on Unix), and checked again before every move. If one is a link or isn't a directory, the watch stops with `subfolder_link` or `subfolder_not_directory`, and nothing is moved into it (tested).
- **Never overwrite.**
  - On Linux and macOS the rename is `renameat2(RENAME_NOREPLACE)`. A filesystem without the flag (some network mounts) falls back to a check and then `renameat`, as do other Unix systems and Windows.
  - A name clash gets `-1`, `-2` and so on, up to 1,000 tries, before the move counts as failed.
- **A file that can't be moved or deleted** (a read-only mount, say, or one another program holds open during the move) is remembered in a bounded set by name, with its size and modification time and why it was failed. It's never read again; **its move is retried quietly on every poll** (not counted, not logged), so one that was only briefly locked goes on to `added/` or `failed/` (fresh self-review).
  - It's reported once, as `watch.stuck` with the set's size, never per poll. That covers a link that can't be moved too (tested).
  - A file that has changed since (a new file under the same name) is forgotten from the set and judged afresh. One still over the cap stays stuck under its name however it grows, so a growing oversize file can't fill the set.
  - When the set reaches `MAX_STUCK` (1,024; a §2.26 number), the watch stops with `too_many_stuck`. Nothing is evicted and read again. **Every path into the set checks the cap** (rv-765 B2). A problem with `added/` or `failed/` found while putting a file away (one swapped for a link, or a share's hiccup) **stops the poll at that file**, so the rest aren't read while they can't be put away. Tested with `failed/` swapped for a link during a poll: one file is remembered, nothing more is read, and the rest are taken once it's fixed.
  - **A name that leaves the folder is forgotten** (rv-765 O1): when a poll's listing is whole (read to its end, not cut by `MAX_SCAN` or `MAX_LIST`), remembered names it doesn't show are dropped, so a stuck file the user removed by hand never counts toward the cap (tested). The listing's own names decide, not the entries that could be looked at, so a name whose entry couldn't be read on one poll isn't forgotten (rv-765 P1).
  - A retried move that finds a problem with `added/` or `failed/` stops the poll too (rv-765 P3).
  - On Windows a link entry is left alone only when its own entry says it's a link. Any other refusal, such as a share without hard links, makes it stuck as usual (rv-765 P2).
  - **`too_many_stuck` clears only when the folder changes or is cleared, or on a restart** (rv-765 O4): a change to `after` alone keeps the watcher's memory, the hold included. UP-2 should say so next to the reason.
  - The set lives in memory, so a restart forgets it. After a restart a stuck file is read once more, then stuck again. **That's the one re-read**, bounded at one per stuck file per restart, and recorded here.
  - A change to the section that keeps the same folder (only `after` changed, say) keeps the set and the rest of the watcher's memory, so it re-reads nothing (tested). A different folder starts afresh.
- **If the pipeline stops taking uploads** (it's shutting down), the poll stops and the file stays where it is, untouched.

## Recorded, not changed (rv-765 optional notes)
- **O2, a transient read error:** an open or read error other than busy, gone or a link (`EIO`, `ENOTCONN`, `ESTALE` on a flaky share) still sends the file to `failed/` as `unreadable`, unjudged. A retry needs a per-file count of polls; that's left for the runner, since the file is kept and can be put back.
- **O6, a bind-mount alias of the data directory:** the data-directory rule compares resolved paths, so two bind mounts of the same host folder (at `/data` and `/watch`) pass it. The data directory holds no `.torrent` files, so the only effect is `added/` and `failed/` appearing there. Comparing device and inode numbers would close it; left for the runner.

## Nothing from the file in logs or status
- **The events** are `watch.started`, `watch.stopped`, `watch.disabled` (with `reason`), `watch.took` (with the `added`, `failed` and `errors` counts) and `watch.stuck` (with the `stuck` count). They're in the `lodestar-watch` catalogue, component `Sources`, with one line in `logging::CATALOGUES`.
- **None carries a file name or a path.** Names in a user's folder are often torrent titles, adult ones included. The unit test that fills the stuck set and the served-binary test both check that no name reaches the log.
- **No in-app status yet:** UP-2 adds the screen and its status API, and these events are what it shows until then.

  - The process's panic hook still logs the caught panic as `app.crash` ("Lodestar crashed"), with its location only. The hook (`settings/log.rs`) isn't this slice's to change, so the line overstates what happened. Recorded as a follow-up.

## For the guide (a docs slice, after UP-2)
- **Docker:** bind-mount a host folder into the container, for example `/mnt/user/torrents/watch` to `/watch`, and set the watch folder to the container path, `/watch`.
  - Lodestar runs as `PUID`/`PGID` (`99`/`100` in the Unraid template; `65532` in the plain image). The folder must be writable by that account, because Lodestar creates `added/` and `failed/` inside it and moves files there.
  - A folder Lodestar can't write to shows as off with "couldn't create added/failed" (`subfolder_create_failed`).
- **The folder must not be the data folder (`/data`), inside it, or hold it.**
- **What the subfolders mean:**
  - `added/` holds files Lodestar took and stored.
  - `failed/` holds files it didn't. The word before `.torrent` says why: `malformed` (not a .torrent it can read), `held` (your filter or the safety rules hold it), `refused` (on the safety list), `too_large` (over 8 MiB), `link` or `linked` (a link, not a file), `unreadable`, `failed` (an internal error).
  - Both are safe to empty.
- **Timing:** files are picked up within about 20 seconds of being complete. A file still being copied is left until it stops changing.
- **SMB/NAS shares work;** a file locked by another program waits. A share that isn't mounted yet shows the watch as off until it is, then it resumes on its own.
- **Windows:** links, junctions, OneDrive files that aren't downloaded, and deduplicated files stay where they are and are never read. Each is counted once as failed.
- **Windows:** while a poll runs (a moment every 10 s), the watch folder can't be renamed or deleted. An antivirus or sync tool that holds the folder can make a poll show the watch as off with "unreadable"; it resumes on the next poll once the tool lets go.
