# UP-1 decisions: the watch folder

Brief: runner, 2026-11-12 (`briefs/UP-1.md`). Spec: plan `docs/plan/2026-11-05-v07-m7.md` §4.3 (UP-1) and §6 ("Folder watch adds no network surface"); architecture §3 and §18.7; UP-0's `docs/decisions/2026-11-12-UP-0.md`.

## The same path as an upload
- **Every file goes through `local_torrent::Uploads::submit`**, the queue the upload route uses: the same read, the floor's hash list first, then the full filter, then the writer's lease-free entry. Nothing is written to the store directly, and nothing bypasses the judge. A held or floor-blocked file is never stored. A `private=1` file gets both privacy bits, as an upload does.
- **The provenance source is UP-0's built-in `upload`.** A watched file and an uploaded file are the same act: the user handing Lodestar a file. A second source would split the same thing across two ids, and sources are a bounded bitmask (64).
- **No network surface:** no new route. The section is served by the existing `/settings` routes; its screen is UP-2's.

## The setting (`crates/lodestar/src/settings/watch.rs`)
- **Section `watch`:**
  - `folder`: an absolute path; empty, the default, turns the watch off.
  - `after`: `move` (the default) or `delete`.
- **Saved in the app only.** No `config.toml` key or `LODESTAR_*` variable backs it yet, so `config.rs` and `ENV_VARS` are unchanged. `LODESTAR_WATCH_DIR` for Docker is the runner's follow-up X-watch-env, with the same checks.
- **It applies live.** `watch::follow` subscribes to the section, checks the folder again each time it changes and at start, and restarts the poller.
- **Checked when saved,** by `Section::check`: absolute, there, a directory, and not itself a link or reparse point (its own entry is read without following it).
- **Checked when applied,** at start and on every change, by `folder_problem` with the data directory: the folder is not the data directory, not inside it, and doesn't hold it, compared once both are resolved (`canonicalize`, so `..` and links in the parents can't hide it).
  - `Section::check` sees only its own section, not the data directory, so a folder inside the data directory saves and then shows as disabled with `inside_data_dir`. It fails safe: nothing is ever read from it.
  - **UP-2 must show that reason next to the field** (runner's note in UP-2's brief).
- **A bad folder disables the watch with one fixed reason,** never the path: `not_absolute`, `missing`, `not_directory`, `link`, `inside_data_dir`, `holds_data_dir`, `subfolder_link`, `subfolder_not_directory`, `subfolder_create_failed`, `unreadable`, `too_many_stuck`. It's logged once as `watch.disabled`. A disabled watch stays off until the setting changes or Lodestar restarts.

## Polling (`crates/lodestar/src/watch.rs`)
- **Every 10 s** (`POLL_EVERY`; the plan's minimum is 5 s). No filesystem-event dependency, so it works on Docker bind mounts and SMB.
- **Bounded each poll** (§2.26 numbers, the runner's call):
  - `MAX_SCAN` = 10,000 directory entries looked at. Enough for any folder a person fills; a folder of a million entries costs one bounded listing per poll, not a stall.
  - `MAX_SUBMIT` = 32 files read and submitted. That's about 190 a minute, without letting a dropped folder starve the crawl's share of the judge. One file is held in memory at a time, so at most 8 MiB.
- **Resumes in order.** Candidates are sorted by name, and each poll starts after the last file it took, wrapping round. So a big folder drains in order and a name that sorts early can't starve the rest. The test fills the folder with `MAX_SUBMIT` + 8 files, then adds one that sorts first.
  - If more than 10,000 entries are present, the ones the listing doesn't reach that poll are reached as taken files leave the folder.
- **The file work runs on the blocking pool:** the listing and the classification of each entry in one call, then each read, move and delete. Nothing blocks the runtime on a slow SMB mount.

## Safe file handling
- **Only regular files directly in the folder whose name ends in `.torrent`** (ASCII case-insensitive, and more than just `.torrent`). Subfolders, `added/` and `failed/` included, are never entered. Other names and a directory called `x.torrent` are left alone.
- **Nothing is followed.**
  - **Unix:** the folder is opened `O_DIRECTORY | O_NOFOLLOW` once per poll, and every step that acts on a file goes through that handle: `openat(… O_NOFOLLOW | O_NONBLOCK)` to read, `mkdirat`, `renameat` and `unlinkat` to create the subfolders, move and delete. The listing and each entry's type (`symlink_metadata`, never following) are only hints for what to try; the handle decides. A folder replaced by a link between polls stops the watch with `link`.
  - **Windows:** a file is opened with `FILE_FLAG_OPEN_REPARSE_POINT` and refused if its handle says it's a reparse point (a symbolic link, junction or mount point). The listing reads each entry without following it. Moves are path-based (no `windows-sys` in the binary, and no `unsafe`), each re-checked first. **The residual race:** a link planted in place of `added/` or `failed/` between the check and the move. It needs write access to the folder, which already lets that person do anything the watch could.
- **Checked through the handle, not the name.** After opening, `fstat` must show:
  - a regular file;
  - the size and modification time it was listed with;
  - on Unix, exactly one link: a hard link to a file elsewhere goes to `failed/` as `linked`, so the watch never reads a file that lives outside the folder;
  - within the cap.

  It's then read through `take(cap + 1)`. **A file swapped for a link between the listing and the open is refused** (`O_NOFOLLOW` returns `ELOOP`, which goes to `failed/` as `link`). The swap test does exactly that between `entry` and `read`.
- **The cap is `local_torrent::MAX_BYTES`, 8 MiB, as for an upload.** A file listed over it goes to `failed/` as `too_large` on first sight, without being opened. The test makes it unreadable as well, so any read would show as `unreadable`.
- **It's read once it's complete:** its size and modification time match on two polls in a row. A file another program holds open isn't a failure; it's tried again on a later poll. That covers a Windows sharing or lock violation, `EBUSY`/`ETXTBSY`/`EAGAIN` on Unix (SMB locks show this way), and a file that vanished.
- **A link entry is moved, never followed:** `renameat` moves the link itself into `failed/` as `link`, and its target is untouched (tested).

## Afterwards: never read twice
- **Accepted files go to `added/`; everything else goes to `failed/`, named `<stem>.<cause>.torrent`.** The causes are `malformed`, `refused` (the floor), `held` (the filter), `failed` (judging panicked), `too_large`, `link`, `linked` and `unreadable`.
  - **`held` gets its own name, not a subfolder.** One `failed/` folder is easier to find in a file manager, and the cause in the name tells the user why without any log.
- **Delete mode deletes accepted files only.** A failed file still goes to `failed/`, so the user can see what didn't go in. This is stricter about keeping things, and costs nothing.
- **`added/` and `failed/` are created without following links** (`mkdirat` on Unix), and checked again before every move. If one is a link or isn't a directory, the watch stops with `subfolder_link` or `subfolder_not_directory`, and nothing is moved into it (tested).
- **Never overwrite.**
  - On Linux and macOS the rename is `renameat2(RENAME_NOREPLACE)`. A filesystem without the flag (some network mounts) falls back to a check and then `renameat`, as do other Unix systems and Windows.
  - A name clash gets `-1`, `-2` and so on, up to 1,000 tries, before the move counts as failed.
- **A file that can't be moved or deleted** (a read-only mount, say) is remembered in a bounded set by name, size and modification time, and skipped from then on.
  - It's reported once, as `watch.stuck` with the set's size, never per poll.
  - When the set reaches `MAX_STUCK` (1,024; a §2.26 number), the watch stops with `too_many_stuck`. Nothing is evicted and read again.
  - The set lives in memory, so a restart forgets it. After a restart a stuck file is read once more, then stuck again. **That's the one re-read**, bounded at one per stuck file per restart, and recorded here.
- **If the pipeline stops taking uploads** (it's shutting down), the poll stops and the file stays where it is, untouched.

## Nothing from the file in logs or status
- **The events** are `watch.started`, `watch.stopped`, `watch.disabled` (with `reason`), `watch.took` (with the `added` and `failed` counts) and `watch.stuck` (with the `stuck` count). They're in the `lodestar-watch` catalogue, component `Sources`, with one line in `logging::CATALOGUES`.
- **None carries a file name or a path.** Names in a user's folder are often torrent titles, adult ones included. The unit test that fills the stuck set and the served-binary test both check that no name reaches the log.
- **No in-app status yet:** UP-2 adds the screen and its status API, and these events are what it shows until then.

## rv-753 follow-ups (UP-0's files)
- **N3, a panic while judging fails one file:**
  - `local_torrent::task` catches a panic per upload (`catch_unwind`) and answers it with the new `Outcome::Failed`, counted in `UploadStats::failed`. Nothing from that file reaches the writer, and the next upload or watched file is judged as usual.
  - The preparer is kept: each prepare call compresses in a fresh zstd frame, and nothing else in it changes while preparing, so nothing a panic leaves behind is read by a later call. No `writer.rs` edit.
  - **Over HTTP** a failed upload is answered `400 malformed_torrent` (`crates/lodestar/src/upload.rs`), the nearest existing cause, so the API's codes are unchanged. **In the watch** it goes to `failed/` as `failed`.
  - Tested in `local_torrent`'s unit tests (a judge that panics on one body; the next upload is stored) and in the watch's.
- **N2:** `alerts.rs` has a unit test that `feed_xml` leaves out each `PRIVACY` bit and keeps the public torrent.
  - The SQL mask and the Rust check are the same rule, so no test can tell one from the other without changing the code. The test pins the behaviour.

## For the guide (a docs slice, after UP-2)
- **Docker:** bind-mount a host folder into the container, for example `/mnt/user/torrents/watch` to `/watch`, and set the watch folder to the container path, `/watch`.
  - Lodestar runs as `PUID`/`PGID` (`99`/`100` in the Unraid template; `65532` in the plain image). The folder must be writable by that account, because Lodestar creates `added/` and `failed/` inside it and moves files there.
  - A folder Lodestar can't write to shows as off with "couldn't create added/failed" (`subfolder_create_failed`).
- **The folder must not be the data folder (`/data`), inside it, or hold it.**
- **What the subfolders mean:**
  - `added/` holds files Lodestar took and stored.
  - `failed/` holds files it didn't. The word before `.torrent` says why: `malformed` (not a .torrent it can read), `held` (your filter or the safety rules hold it), `refused` (on the safety list), `too_large` (over 8 MiB), `link` or `linked` (a link, not a file), `unreadable`, `failed` (an internal error).
  - Both are safe to empty.
- **Timing:** files are picked up within about 20 seconds of being complete. A file still being copied is left until it stops changing.
- **SMB/NAS shares work;** a file locked by another program waits.
