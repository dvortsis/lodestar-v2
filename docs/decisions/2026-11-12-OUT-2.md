# OUT-2 decisions: Settings → Outputs

Slice OUT-2, 2026-11-12 (UTC). Brief `briefs/OUT-2.md` (runner-state). Spec: architecture §10.10, §10.10.7, §10.10.8, §20.9; `docs/decisions/2026-11-11-TZ-0.md`; `docs/decisions/2026-11-11-OUT-0.md`.

- **"Reveal the key" means shown once, at create or regenerate, behind the password (runner, 2026-11-12; flagged to the owner).** TZ-0's Torznab key is an ordinary B12 API key with the `torznab` scope. B12 keeps only a hash of each key, so nothing on the server can show an existing key again. Storing the key so it could be revealed later would weaken a security decision, which is the owner's to make, and nobody has asked for it.
  - So the screen lists Torznab keys by name, prefix, status and dates, never by secret.
  - **Create** and **Regenerate** ask for the password in Security's own dialog (§10.10.7, the Security row) and show the new secret once in Security's reveal dialog, unchanged. That dialog says it's the only time Lodestar shows the secret.
  - **Regenerate** names what breaks: the app finds nothing until the new key is pasted into it.
  - **Revoke** asks a plain question, as on Security (B12).
- **One key per app, named for the app (runner, 2026-11-12).**
  - The new key's name is pre-filled with the first of Prowlarr, Sonarr, Radarr, Lidarr and Readarr that no active Torznab key uses, and stays editable.
  - Keys made here have only the `torznab` scope, TZ-0's safe choice.
  - Keys with other scopes as well are listed, because they work, and marked "Also has other access", with a link to Security → API keys.
- **The Torznab address** is `<the browser's origin>/api/v1/torznab/api`, with Copy. Its help line says to use the address the app reaches Lodestar at, if that's different (another computer or container), and which indexer type to add in Prowlarr, Sonarr and Radarr.
  - The screen also carries TZ-0's Sonarr hint: add categories 5000 and 5045, or shows without a resolution in their name, and 4K shows, aren't found.
- **`content.export_adult` applies at once with the 18+ confirmation, like "Show adult content" on Appearance (B17), not staged.** The field is a `content` setting, and turning any adult field on needs `confirm_adult`; the server refuses it otherwise.
  - Outputs is a hand-built screen with no Save, and the setting's only consequence is the next export. So it behaves as Appearance's switch does: the question first (focus on Cancel), then the change; turning it off asks nothing; Undo is turning it off.
  - The dialog is Outputs' own, worded for exports. It says bitmagnet will look each adult torrent up on the DHT.
- **The bitmagnet export is a plain download link** (`GET /api/v1/export?format=bitmagnet`, `download`), so the browser writes the file to disk as it streams and nothing holds it in memory.
  - A download's response headers aren't readable, so the screen finds its job as the newest bitmagnet export in `GET /jobs` started at or after the click (5 s of slack). It polls once a second until the job finishes, or gives up after 30 s and links to Jobs.
  - It shows the server's counts. A capped export (`truncated`) gets a warning that the file isn't complete, which OUT-0's file can't say itself, having no trailer. A cancelled or failed export says to delete the file.
  - Pause, resume and cancel stay on the Jobs screen.
- **What's always left out is said in one plain sentence:** private sources and private trackers, hidden, unverified, and blocklisted or removed torrents, with Adult left out unless included. The screen also shows a `curl` line for bitmagnet's import address.
- **Size (§10.1):** Outputs' icon and purpose line, its 18+ dialog and Security's key flows are on demand.
  - The flows load through `outputs/key-flows.ts` by `import()`. Imported statically from a second screen, the bundler moved them into the chunk every Settings view loads, which cost every view about 1.2 KB.
  - `.size-limit.mjs` lists Outputs' on-demand modules as it does Companions', with two new entries: parts 27 KB (measured 25.7 KB) and icon and purpose 1 KB (measured 0.66 KB).
  - **The registry entry pays for itself (runner, 2026-11-12).** Registering the screen first cost every Settings first view about 96 B, and three budgets with no headroom went over by under 100 B. The runner approved +0.1 KB for Filters and Sources, but refused to raise "Settings section", which is already past §10.1's 45 KB. It asked for at least 62 B to be recovered instead.
  - The registry's eager glob now imports only each `screen.ts`'s default export (`import: 'default'`, with `export default screens` added to `settings/screens/screen.ts`). That drops one module-namespace object per screen from the shared chunk.
  - Net, every Settings first view is about 88 B smaller than before OUT-2, Outputs' entry included. So no budget is raised, Filters' and Sources' included.
  - `collect` now takes each module's default export (a screen or a list), and its tests say so.
- **The registry tests** (`shell/screens.test.ts`, `shell/SettingsShell.test.ts`) list every screen, so they gain `outputs` between Integrations and Notifications, its place in the Connections group.
