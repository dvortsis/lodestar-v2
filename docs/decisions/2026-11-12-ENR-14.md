# ENR-14 decisions (Wikidata parser and plugin)

Slice ENR-14 (runner brief, 2026-11-12). Spec: plan `docs/plan/2026-11-05-v07-m7.md` (ENR-14 row, "may land before the cut, inactive", Q5 and Q12), `docs/decisions/2026-11-12-ENR-10.md`, `2026-11-06-ENR-9.md`, `2026-11-06-ENR-9b.md`, `2026-11-07-runner-followups.md`, architecture §18.1, §18.2, §18.7 and §18.9.

## Terms and usage policy (owner §2.28), checked 2026-11-12
- **How it was checked:** this session's network couldn't reach Wikimedia's own hosts (`www.wikidata.org`, `www.mediawiki.org`, `foundation.wikimedia.org` didn't resolve), so the policies were read through web search results quoting them, on 2026-11-12. Read them again directly when a session can reach them, and record any difference in a new decisions file.
- **What was checked, and what the plugin does:**
  - **User-Agent policy** (Wikimedia Foundation; also the Wikimedia APIs access policy). Every request needs a User-Agent of the form `<client>/<version> (<contact>) <library>/<version>`; the contact may be a URL of a relevant website, a user page or an email. A client without one may be blocked without notice. **The plugin sends `Lodestar/<version> (<the project's repository URL>) lodestar-sources-plugins`** (`wikidata::USER_AGENT`): the project's own URL, built from the workspace's `repository` field, the same for every install. It never carries a user name, an email, a host name or anything about the install (brief). The repository URL holds the maintainer's GitHub name: that's the project's public identity, the same for everyone, not the user's.
  - **Robot policy and rate limits** (Wikitech robot policy; the Wikimedia APIs rate-limits page, marked new in 2026 and subject to change). Clients that don't sign in: one request at a time, under 5 a second; any client: at most 3 at once; over a limit, HTTP 429. **The strictest applies:** one request at a time (`Policy::max_agents` 1, the runtime runs one lookup at once), **at most one request a second with no burst** (the plan's cap for Wikidata, §2.26), back-off from 60 s to 6 h after a 429 or 5xx through the plugin's host limiter.
  - **API etiquette** (MediaWiki Action API): send requests in series, not in parallel; non-interactive work sends `maxlag`, and on a `maxlag` refusal waits the answer's `Retry-After`. **Every request sends `maxlag=5`**, since the background walk is non-interactive and an opened item is fine to wait. A `maxlag` refusal is an API error object on a 200, which the host limiter doesn't see, so **the plugin holds itself**: after any API error it sends nothing for the answer's `Retry-After` (60 s when there's none, at least its 2 s interval, at most an hour), and each lookup meanwhile fails at once as "on hold" (`an_api_error_holds_for_its_retry_after`). The lookup isn't cached, so the item is asked again later. That's the backoff ENR-10's N3 left to the first plugin that needs it, kept in the plugin so `identify.rs` is unchanged.
  - **No bulk scraping through the API.** (The runner's reading, 2026-11-12: the stricter one. Q12's 100,000 is a ceiling, not a target; lookups go interest first, and the background walk only at this polite rate.) Wikidata's data-access guidance points bulk use at the weekly dumps, not the API. The plugin sends one search and one entities request per lookup, only for items the runtime finds eligible (user interest first, then the capped background, Q12), and asks for at most five items. At one request a second and two requests a lookup, a plugin makes at most about 43,000 lookups a day, under Q12's 100,000. **Open question, flagged to the owner by the runner:** whether a background walk over a whole index through the API counts as "bulk", for which Wikimedia points to the dumps. A dump-based local match (as ENR-steam does for Steam) would answer it fully; it's not in this PR.
  - **What a lookup costs the service:** one search answer (a few KiB) and, only for the results named by the title, one entities answer with their statements (a well-known film is a few hundred KiB; the cap is 8 MiB). The plugin drops every search result whose label, alias or matched text isn't the title before fetching anything, so a word-in-a-longer-title hit costs nothing more. At the 43,000-lookup ceiling and a few hundred KiB a match, a fully busy install would move several GB a day; in practice user interest and the cache keep it far below. This belongs with the open "bulk" question.
  - **Licensing.** Structured data in Wikidata's item, property and lexeme namespaces is CC0 (public domain): no attribution is required, so none is stored or shown. Descriptions and other page text aren't read at all.
- **No API key, no account.** Wikimedia's 2026 limits ask heavy clients to sign in for higher limits; the plugin doesn't, so it stays at the unauthenticated, strictest level and stores no credential.

## Off by default, External class
- **The manifest:** `wikidata`, an Enrichment source, Consent `External`, endpoint `https://www.wikidata.org` only, `enabled_by_default: false`, never always-adult, never finds private. Nothing is sent until you enable it and acknowledge its endpoint (§18.7); `tests/wikidata.rs` `off_by_default_nothing_is_sent` runs it under ENR-10's runtime with the source registered but not enabled, and nothing reaches the wire.
- **Eligibility is ENR-10's, as is** (`identify::check`): never a `flags::PRIVACY` item (private source, BEP 27 or unverified), held, hidden or Adult-off; only Q5's parsed title, year and kind. The plugin adds no gate of its own and is handed nothing else. `a_private_item_is_never_sent` opens two private torrents before a public one: exactly the public one's two requests go.
- **Kinds: Movie and TV only.** The cross-ids the brief names (IMDb, TMDB, TVDB) are film and series ids, and the kind check below is written for them. Music, books and games are the later plugins' (MusicBrainz, Open Library, IGDB).
- **Wired into the host, off** (runner, 2026-11-12: ENR-10 assigned the wiring to ENR-14). `services.rs` registers `IdentifySource` with the Wikidata plugin beside the other sources: its own store connection, the live filter, ENR-10's default `Config` (Q12's 100,000 a day as a ceiling; the plugin's 2 s interval keeps it to about 43,000), and the always-adult sources the store has registered (this run's or an earlier one's, matched to the catalogue), so an item only one of them found is never sent. It registers off (`enabled_by_default: false`), and in this build it can't be switched on at all: a start switches off any source whose consent class isn't `None` (`control::consent_text_approved`, as for Prowlarr and the torrent cache). So the plan's "may land before the cut, inactive" holds.
  - **The gate's kill switch reads as not tripped in the host** (`EgressEnforced`; runner, 2026-11-12: accepted as a follow-up). The plugin's egress client refuses every request while its route is down (SRC-5), and the plugin turns that into a failed lookup, so nothing leaves the install either way. The cost is that a down route spends lookups from the day's count.
  - **User interest isn't wired yet:** the detail drawer doesn't call `Interest::opened`, so only the background walk runs once enabled. That's API and UI work (ENR-12/ENR-13).
  - `catalogue.rs` lists the manifest (one line, which its test requires of every module), and `crates/lodestar/src/ops.rs`'s test list of every plugin's policy gains its line.

## What is sent (Q5)
- **At most two requests a lookup, both fixed templates** (`search_request`, `entities_request`):
  - `GET https://www.wikidata.org/w/api.php?action=wbsearchentities&search=<title>&language=en&uselang=en&type=item&limit=5&format=json&maxlag=5`;
  - `GET …?action=wbgetentities&ids=<Q…|Q…>&props=labels|aliases|claims&languages=en|mul|de|es|fr|it|ja|ko|pt|ru|zh&format=json&maxlag=5`, only for the search results whose label, alias or matched text folds to the title (`wikidata_match`: the novella the search also finds isn't fetched).
- **The title is one URL parameter**, encoded by the `url` crate's form encoder, so no character in it can add a parameter or change the action (`a_hostile_title_is_one_parameter`). The ids in the second request are only what `Qid::parse` accepted (`Q` and digits) and are written back from the number. **The query service (SPARQL) isn't used:** the entity and search APIs cover the need, and no query language is ever built.
- **The year isn't sent.** It's only used locally to choose among candidates. Neither is the kind. The headers are `Accept` and `User-Agent`, nothing else.

## The parser (`sources-feeds/src/wikidata.rs`)
- **On the shared bounded JSON reader**, like ENR-2b's. Pure, no I/O, no panics, no unwraps, no truncating casts (a year goes through `u16::try_from`). **Linear time:** repeats are found with a bitmask over the keys a part reads (`Keys`) and a scan of what's kept (at most the count caps), never a list of every key seen; the self-review measured the first draft's list at minutes for an 8 MiB answer of unknown keys. `many_unknown_keys_are_read_in_linear_time` reads 300,000 of them whole. The plugin parses the entities answer on the blocking pool anyway, so even a slow parse never holds a runtime thread.
- **The caps, as named fields of `Limits`:**
  - `SEARCH_LIMITS`: 256 KiB, depth 16, 20,000 values, 10 results, 16 texts per result, 1,000 elements per array. A search answer for five results is a few KiB.
  - `ENTITY_LIMITS`: 8 MiB, depth 32, a million values, 5 entities, 64 labels and aliases per entity, 256 statements read per entity, 20,000 elements per array, 4 KiB per decoded string. An item's statements are most of an entities answer, and a well-known film's are a few hundred KiB; depth 32 is well past a statement's references.
  - Past the entity or result cap the parse stops (`Stop::Items`); past the label or statement cap the rest are passed over undecoded and the entity says `truncated`. `max_array` holds for every array, read or passed over: one over it spoils its entity or result (over cap).
- **Strict shape:** an answer counts only when `Page::whole()`: read to its end, the root key asked for in the right type, no `error`, no repeated or escaped root key, no trailing bytes and nothing skipped. In a part that's read, a key with an escape, a repeat of a key it reads (a field, a label's or alias's language, a read property, an entity's id), a missing `"type": "item"` (unless the entity is `missing`), a wrong type, an unknown snak type or rank, a snak naming another property, a label whose `language` isn't its key, or a time that isn't `±Y…Y-MM-DDThh:mm:ssZ` with a precision spoils the entity. Everything outside the read parts (descriptions, sitelinks, other statements, qualifiers, references) is skipped undecoded, and repeats of keys that aren't read don't matter. An empty map may come as `[]` (PHP's empty array), and only empty.
- **To confirm against real answers** (the fixtures are hand-written): the `[]` form, and an id redirected between the search and the fetch, which the parser reads as malformed if `wbgetentities` keys it by the requested id with the target's `id`. A failure there is a failed lookup, never a wrong match.
- **What it keeps:** item ids, labels and aliases (hidden characters removed, trimmed, at most `MAX_TITLE`), and seven properties: P31 (instance of), P345 (IMDb), P4947 (TMDB movie), P4983 (TMDB TV), P4835 (TVDB series), P577 (publication date) and P580 (start time). A `novalue`, `somevalue` or deprecated statement keeps nothing; a time coarser than a year, before year 1 or after 9999 keeps no year.
- **Ids:** an item is `Q` and 1–20 digits with no leading zero that fit a `u64`. IMDb keeps only titles (`tt` and 7 digits, or 8–10 with no leading zero), so a person's `nm` id never survives; TMDB and TVDB are 1–20 digits with no leading zero. The store's `id_ok` checks them again when the claims are clamped.

## Choosing a match (`wikidata::choose`)
- **One item must agree on all three:** its kind (an instance of one of the listed film or series classes, or holding that kind's TMDB or TVDB id), a label or alias equal to the title after folding (lower case, letters and digits, runs of anything else one space), and the query's year among its publication or start years when the query has one. **None, or more than one, is no match:** it never guesses (`wikidata_candidates`: the year picks one Dune; with no year, the two films tie).
- **Confidence:** 90 with a matching year, 70 without one. Both stay under ENR-10's `MAX_PLUGIN_CONFIDENCE` (95).
- **The answer:** `wikidata:Q…`; `imdb:` and the query kind's `tmdb:` (and, for TV, `tvdb:`) only when the item holds exactly one value, so two disagreeing values name nothing; the English label, else the `mul` one, as the canonical title; the other labels and aliases, with their language, as alternative titles; no genres (Wikidata's genres are items, which would need a third request); the year. ENR-10's `into_claims` clamps it again.

## Judged before storage
- **Nothing here judges text.** Every title goes into ENR-10's claims, and the writer's ingest judges each alone, joined and with the torrent's names (ENR-9b). `an_answer_is_judged_and_a_held_one_is_not_stored` runs the plugin's real answer through `unverified::ingest`: clean, it's stored; when its German title completes a child-safety pattern with the torrent's name, the hash is held and nothing is stored.

## Errors
- **Status first:** 200 is parsed; 429 is "limiting requests", and the host limiter holds the host, so the next lookup fails at once without a request ("on hold"); a 3xx is never followed; anything else, or a transport failure such as a timeout, is "the request failed". A 200 that's an API error object (such as `maxlag`) is "answered with an error", and holds the plugin for its `Retry-After`. A 200 that isn't `whole` is "wasn't understood". **None of them is a miss**, so none is cached as one, and no error holds the service's text.
- **A hung request** is ENR-10's `lookup_timeout` (60 s), already tested there.

## How to add the next plugin
For ENR-tmdb, ENR-tvdb, ENR-mb and the others. Copy Wikidata's shape; change only what the service needs.
1. **Files to copy:**
   - `crates/sources-feeds/src/<name>.rs`: the parser, on `json.rs` (or `quick-xml` for AniDB). One `parse_*` function per answer shape, returning the kept values and a `Page` with `whole()`.
   - `crates/sources-plugins/src/<name>.rs`: a unit struct implementing `identify::Identifier`, its `MANIFEST` (Enrichment, its consent class, its one endpoint, off by default), its `POLICY` (the plan's rate cap, `HostRate` with no burst, back-off 60 s to 6 h), `kinds()`, `min_interval()` (its cap times the requests a lookup makes), fixed request builders, `ok_body` and `usable` for errors, and `choose`.
   - The `mod` lines in both `lib.rs` files and one line in `catalogue.rs`.
   - `crates/sources-feeds/tests/<name>.rs`, `crates/sources-plugins/tests/<name>.rs`, `crates/sources-plugins/fixtures/<name>/` with a `README.md`, `fuzz/fuzz_targets/<name>.rs` with its `fuzz/Cargo.toml` `[[bin]]`, `fuzz/README.md` row and `fuzz/seeds/<name>/`.
   - `docs/decisions/<date>-ENR-<name>.md` with the ToS check first.
2. **Caps to set, all named** (and enforce each on what's read, not only on what's skipped): bytes per answer; depth; values; items (results or entities); texts per item (titles, aliases); statements or fields read per item; elements per array; bytes per string. Pick each from the service's documented answer sizes and say why in the decisions file.
3. **Rules to keep:** linear time (repeats found with a bitmask over the known keys and a scan of what's kept, never a list of every key; a large answer parsed on the blocking pool); fetch details only for results the title names; after an API error on a 200 (which the host limiter doesn't see), hold for its `Retry-After`; a request from a fixed template with the title as one encoded parameter (and a fixed query string for GraphQL, never built from text); only Q5's title, year and kind, and send no more of them than the service needs; ids parsed strictly to the known kinds; a broken answer is an error, never a miss; no service text in an error; no unwraps or truncating casts; one item must agree, or no match; a credential (Account class) read on each lookup from `Credentials` and sent in a header, never the URL.
4. **Tests to have:** a body of hundreds of thousands of unknown keys read whole; repeats of read keys spoiling; an API error's hold; a match; no match; several candidates; the request's exact parameters and headers; hostile text stays one parameter; the caps (count and bytes); garbage, oversize and truncated answers; a timeout; a 429 backing off through the host limiter; a redirect not followed; requests paced at the cap; the manifest (consent, off by default, endpoints); and under ENR-10's runtime: off by default nothing is sent, a private item never sent, and the real answer judged by `unverified::ingest` with a held text not stored. Paused tokio time or condition waits of at least 10 s; recorded fixtures only.
