# ENR-11 decisions

Slice ENR-11: identification answers reach the index and the query language (alternative and canonical titles, ID terms, `imdb:`, `tmdb:` and the other ID fields, and Torznab's ID parameters). Spec: architecture §6 and §8, `docs/decisions/2026-11-12-ENR-10.md`, `docs/decisions/2026-11-16-ENR-terms.md` and `docs/decisions/2026-11-11-TZ-0.md`. Built while the runner was paused, by a session standing in for it at the owner's word (2026-11-24). The refinements below are the runner's call under §2.19 and are flagged to the owner.

## What search may serve
- **One rule for every answer search indexes, the same as the effective title's (`identify::stored_title`):** a version 3 claims row whose details hold a match confidence; from a source that didn't find the torrent; not through a private source (`torrent_claims.flags = 0`, ENR-9b); on a torrent that isn't `flags::PRIVACY`; and from a source whose terms record (`enr10/terms`) allows passing answers on. A missing or unreadable record doesn't. `Store::served_identifications` is that rule, in `crates/store/src/identify_sweep.rs`. Its terms reader is held to `identify::may_redistribute` by a property test over every record (`tests/enrichment.rs`). Reason: an ID or title from a source whose terms forbid redistribution would be passed on through search, Torznab and export (ENR-terms).
- **Adult documents get no IDs and no catalogue titles, and neither does a document with no classification record.** Every enrichment source today is a general catalogue, and the Adult rules (hidden by default) shouldn't depend on what a catalogue says. An unclassified document has nothing to enrich yet and is reindexed once it's classified.
- **IDs are kept only for the enrichment schemes** (`claims::ENRICHMENT_SCHEMES`) and only in `claims::id_ok`'s form. Anything else in a row is dropped, not indexed.

## Titles
- **At most 8 titles from answers per torrent** (`MAX_IDENTIFIED_TITLES`, the slice's cap), after the torrent's own titles. Order: higher match confidence first; then the canonical title before alternative ones; then English (`en`, `en-*`) or no language, then `und`, then other languages; then by source id and the row's own order. Titles equal to one already indexed, ignoring case, are skipped and don't count. Reason: the first titles kept are the ones most likely to be what a user types, and the cap keeps the index inside its budget.

## Fields and terms
- **The term is `scheme:value`, the same as the field name** (`imdb:tt0111161`), not the plan's `id:imdb:…` prefix. The query printer already writes a tag as `TagKey::as_str()`, so one spelling serves the field, the term and the AST. The terms sit in the existing `tags` field, so no schema or generation change.
- **Eleven fields, one per enrichment scheme:** `imdb`, `tmdb`, `tvdb`, `anidb`, `anilist`, `mbid`, `olid`, `igdb`, `discogs`, `steam` and `wikidata`. `olid` is beyond the slice title's list; it's an enrichment scheme already (OpenLibrary, §18.2), and leaving it out would make its IDs unsearchable.
- **Values are read leniently and stored in one form:** `imdb:111161` is `tt0111161`, numeric IDs drop leading zeros, and case doesn't matter. A value that isn't an ID of that scheme is an error naming the form expected. ASCII only, at most 64 bytes.
- **ID clauses are search-only:** filter rules refuse them (`mentions_provenance`), like `source:`. Whether an ID is there depends on which sources ran and their terms, which a filter rule shouldn't depend on.
- **The field catalogue lists them as keywords, not facetable.** Typing `a` in the query bar now suggests `anidb:` and `anilist:` among the fields (`suggest_unicode_caret` golden). The web labels them by catalogue name ("IMDb ID").

## Torznab
- **`imdbid`, `tmdbid` and `tvdbid` are now read** (they were refused with `203`, TZ-0) and become `imdb:`, `tmdb:` and `tvdb:` clauses beside the rest of the request. A malformed value or a repeat is `201`; an empty value counts as absent, as before. `rid`, `tvmazeid`, `traktid`, `doubanid` and `tvrageid` are still refused with `203`.
- **Caps advertise them unconditionally:** `tv-search` is `q,season,ep,tvdbid,imdbid,tmdbid` and `movie-search` is `q,imdbid,tmdbid`. Inferred reason: Sonarr and Radarr fall back to a title search when an ID search finds nothing, so an install with no identification source still answers. This supersedes TZ-0's "caps doesn't advertise them" for these three.

## The sweep
- **Torrents enriched before this slice are backfilled by a bounded, resumable sweep** (`Store::identify_sweep_step`, at most 1,024 claims rows a step), as the runner's notes ask (SB-6 contract: no generation, no corpus walk). It logs each torrent holding a version 3 row that isn't through a private source to `reindex_log`; the cursor and end live in `settings` under `identify_sweep.` and are written in the same transaction as the step's entries, so a restart goes on where it stopped. The end is fixed at the first step; later answers reach the index through the backfill (ENR-10).
- **Nothing calls the sweep yet.** No identification plugin is wired into the host, so no install holds answers today. The slice that wires them in calls it at start, next to `identify::sweep_recorded` (ENR-terms precedent). The runner adds this to that slice's notes.

## For later slices
- **Host wiring:** call `identify_sweep_step` until done, and add the "results may be incomplete" notice for ID clauses while it runs (it needs `crates/api/src/search.rs`, which SRC-3b owns).
- **UI review 02 §5.5:** autocomplete showing the matched title for `imdb:` and `tmdb:` values; rows saying "matched an alternate title"; the +N badge collapse.
- **Torznab docs and the *arr setup guide** name the ID parameters once a source can fill them.
