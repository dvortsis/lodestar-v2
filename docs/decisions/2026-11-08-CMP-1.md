# CMP-1 decisions (companion fetch and verify)

Slice CMP-1 of `docs/plan/2026-11-06-v06-companions.md` (§4, §5 Q2, Q16); architecture §12.2 "Checking" and "Downloading", §18.10. Every entry is a choice the brief left to the slice (`docs/owner-decisions.md` §2.33). None loosens a plan rule or changes a Q16 number.

- **The rules are the updater's** (`crates/lodestar/src/update/download.rs`), re-implemented in `fetch.rs` rather than shared: `crates/companions` must not depend on `crates/lodestar`, and moving `hop_allowed` into a shared crate wasn't needed, because the companion check differs anyway (the entry's own host allowlist, not the updater's). The same `MAX_HOPS` (5), redirect statuses (301, 302, 303, 307, 308), `https`-only hops with no port and no user information, the writer thread joined before a failed file is removed, and stable error codes that never carry a URL.
- **Allowlist per hop:** a host must be on **both** the entry's `hosts` and the catalogue's `DOWNLOAD_HOSTS`. The catalogue already makes the first a subset of the second; checking both again at download time costs nothing, and a test catalogue can't widen it.
- **Download folder:** `<data>/companions/.downloads/<id>_<version>.part`. A companion id must start with a letter, so `.downloads` can never be a companion's own folder (CMP-2's layout is `<data>/companions/<id>/`, and its sweep stays out of it). `_` is in neither an id nor a version, so `qbittorrent_…` files can't be confused with a `qbittorrent-x_…` companion's. The folder is created `0700` on Unix; neither it nor `<data>/companions` may be a link. On Windows it inherits the data folder's ACL, as CMP-3's files do.
- **The `.part` file** is created with `create_new` (and on Unix `O_NOFOLLOW` through `rustix`, mode `0600`), opened read-write so the writer thread hands the same handle back after the fsync. That companion's earlier `.part` and `.verified` files (names `<id>_<version>.<ext>` with a valid version) are removed at the start of each download, a link of that name included, never followed. Other companions' files stay.
- **On success** the file is renamed `<id>_<version>.verified` and returned as `fetch::Verified`: the open handle, rewound, plus its path, size and SHA-256. It implements `Read + Seek`, so it is CMP-2's `extract::Archive` as it is; `discard()` deletes it after extraction. CMP-5 wires the two together.
- **One download per companion at a time:** a process-wide set of companion ids; a second download of the same companion while one runs fails at once with `download_busy`. Lodestar runs one process per data folder, so a file lock isn't needed.
- **Timeouts, sized for 512 MiB:** `OVERALL` 60 minutes (512 MiB at about 150 KB/s, the updater's 30 minutes for its 256 MiB at the same rate), `IDLE` 60 s between chunks, as the updater. `fetch_limited` takes other limits, which only tests use.
- **Byte cap:** the pin's size, and never more than `MAX_ARTIFACT_SIZE` (512 MiB) even if a pin said otherwise. One byte past it stops the download before that chunk is written.
- **Route:** the caller hands in a `GuardedClient`, wrapped by `fetch::Guarded::new`, which refuses a client whose policy is anything but public addresses only (`NetPolicy::notification(false)`). `fetch::client(route)` builds that client through the route the caller passes (Lodestar's egress setting, §5), with a per-request timeout of `OVERALL`. Nothing here builds a direct client of its own. The SSRF guard sees every hop, since each hop is a separate `send`. CMP-5 passes the same egress route the updater uses.
- **Request:** `GET`, `User-Agent: Lodestar-Companions`, nothing else. reqwest adds only `accept: */*` and `host`; the client keeps no cookies and sends no referer. A test checks the exact header set on every hop over real HTTP, including after a redirect that sets a cookie.
- **Verification:** `verify::matches` compares the size and the SHA-256 (the latter in constant time) and always evaluates both. A mismatch removes the file and returns `download_mismatch`.
- **Upstream signatures (Q2):** `UpstreamSig::None` and `UpstreamSig::VerifiedAtPin` need nothing beyond the SHA-256 at run time. `verify::minisign(file, key, sig)` checks a minisign signature with `lodestar_update::minisign` after the pin matched, and `fetch::fetch_signature` fetches a `.minisig` through the same hop rules within 1 KiB. **The catalogue can't name a minisign key today** (runner told, 2026-11-08). For it to, a later slice adds to `catalogue.rs`, in CMP-0's style:
  - `upstream_sig: {"kind": "minisign", "public_key": "<the minisign public key's base64 line>", "sig_url": "https://<one of the entry's hosts>/…/<file>.minisig"}`, with `public_key` parsed by `PublicKey::from_base64` and `sig_url` validated as an `HttpsUrl` on the entry's hosts, both at catalogue load;
  - an `UpstreamSig::Minisign { key, sig_url }` variant, which CMP-5 checks with `fetch_signature` and `verify::minisign` before extraction.
  No v0.6 companion publishes minisign signatures, so nothing goes unchecked meanwhile.
- **The minisign check reads the file whole** (at most the pin's size), because `lodestar_update::minisign::PublicKey::verify` takes the message rather than its BLAKE2b-512 prehash. When the catalogue variant lands, a streaming `verify_prehashed` in `crates/update` would remove that; flagged to the runner.
- **No log events.** As CMP-2 did, the errors carry codes and CMP-5 logs them. Nothing here logs a URL.
- **Tests over real HTTP, not TLS:** like the updater's download tests, the network tests use a real HTTP/1.1 server on loopback, reached through a real `GuardedClient` by a source that keeps each hop's path and query and changes only where it's fetched from. `GuardedClient` has no way to trust a test certificate authority, and adding one is outside this slice. The allowlist, the cap, the hash and the headers are all checked on the catalogue's `https` URLs. `Guarded::unchecked` (only under `cfg(test)` or the `testing` feature) lets that client reach loopback.
- **Dependencies:** `lodestar-update`, `reqwest` (`=0.13.5`, no default features), `tokio` (`rt`, `sync`, `time`) and, on Unix only, `rustix` (`fs`), all already in the lockfile; `tempfile` for tests. No new crate.
