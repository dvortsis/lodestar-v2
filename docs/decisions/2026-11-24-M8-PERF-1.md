# M8-PERF-1 decisions (10M bench mode: search-bench)

The second of two PRs for M8-PERF-1 (the first was #780, M8-PERF-1a, `docs/decisions/2026-11-12-M8-PERF-1a.md`). This one adds `search-bench --dataset DIR`: every §3 latency row at 10M, the Insights rows, steady-state RSS, new torrent → searchable under ingest, cold start and low-resource mode, all in 1a's JSON report. It also does the review items #780 left to it: RSS with a live indexer running, starved-ingest rows, decimal RSS budgets, cold start after a build, the Insights mirror and argument checks. Nothing outside `bench/` changed; the 50k and 200k CI gates are unchanged (below).

## The dataset key
- **The same key as 1a:** `{format: 1, generator: synth::VERSION (1), seed, torrents}`, from `--seed` and `--torrents`. `search-bench` opens it with `dataset::open_or_build`, so a mismatched folder is refused before anything is written, naming both keys, and a missing one is built. Nothing in this PR changes what a seed generates or how a dataset is built, so neither version moves.

## The rows and how each is measured
- **Every CI table, on the dataset:** keyword, browse, regex (RX-1's class, gated at 500 ms), `/search`'s lease and first page with the deep cursor page and the count estimates, collapse (reported for G-v07-scale, never gated), zero-result recovery, broad file clauses cold and warm, facets and suggest. Each p95 becomes a row with a stable id (`search.<class>.p95`, `search.api.<class>.p95`, `search.recovery.…`, `facets.…`, `suggest.…`) against its §3 budget. Swarm data is loaded from the store with `Store::load_hot`, as the server starts without a snapshot, instead of being derived from the seed. `--no-hot` and `--only` are refused with `--dataset`, since either would leave rows out of a report a gate reads.
- **Insights (`insights.{overview,stages}.{24h,7d,30d,all}.p95`, < 50 ms):** the store reads the API makes for a range's first open, with no cache: for the overview, the range and the period before it (day tables below the compaction boundary, hourly rows above, recent cohorts raw, as `read_period` does), the "now" reads from the stall window, the yield baseline's cohorts and the events; for the stage pages, every summed metric and the searchable gauge, by day below the boundary. Mirrored in the bench because the API crate is only a dev-dependency here. The sealed-day cache isn't used, so this is the slow case. `all` is the dataset's year of rollups.
- **Steady-state RSS (`rss.steady.max`, `rss.steady.median`):** on the scratch copy, as a server holds memory: the index with hot columns, the title set, and a live indexer at its production settings following a trickle ingest of 4 torrents a second. One pass of a mixed keyword, browse and facet load warms the caches, then the load runs for `--steady-secs` (60) while a sampler reads `VmRSS` every 250 ms. The highest sample is gated, the median reported. The process's earlier tables stay resident, so the figure errs high.
- **Decimal RSS budgets:** "< 1 GB" is 1,000,000,000 bytes and RQ8's "< 512 MB" is 512,000,000, the stricter reading. The row is in MB with a budget one byte under, so a row's `value <= budget` is the strict `<`.
- **Low-resource (`--low-resource`):** the file-clause rows and the regex row are `off` (RQ8: not offered in that mode), RSS is gated at 512 MB, and the ingest rows' live indexer runs with a 64 MB heap, the one cache the bench can shrink. The product's missing switches (trigram field, file index, caches and merge threads) are `unavailable` rows, so a low-resource report stays `incomplete` until a slice adds them, as in 1a.

## What "new-to-searchable" measures
- **Idle (`nrt.idle.max`, < 5 s):** the CI gate's check, unchanged: on the scratch copy, a live indexer at `LiveConfig::default()`; 10 rounds each store one new torrent and time from the insert returning until the index's document count includes it. Gated on the slowest round.
- **Under ingest (`nrt.ingest.max`, < 5 s; `nrt.ingest.p95` and `nrt.ingest.rate` reported):** the same live indexer while a background thread inserts `--ingest-rate` (100) new torrents a second, paced by elapsed time. `--nrt-rounds` (50) probe torrents are stored among them; each is timed from its insert returning until `SearchIndex::find_hash` finds its info-hash, polled every 5 ms with a 120 s give-up. That's the commit and reader reload a search would see; it doesn't include the crawler's metadata fetch or enrichment. Gated on the slowest round, as the idle check is: §3 says "< 5 s" with no percentile.
- **Starved ingest:** if the ingest reached less than 90% of the rate asked, a busy machine flattered the latency, so both latency rows are `unmeasured` with the rate in the reason, and the verdict is `incomplete`. The rate reached is always reported. No crate hook was needed: the public `LiveIndexer` and `find_hash` give the time.

## What "cold start" measures
- **`cold_start.<cache>.open` and `.first_query`, reported (§3 sets no number):** the first thing the run does, before anything else in the process opens the dataset: open the store reader and the index, load the hot columns from SQLite, then answer the UI's first page (everything, newest first, 50) and load its rows. `open` is the time to the index being ready, `first_query` to the page's rows. `<cache>` is `page-cache-dropped` when `--drop-caches` ran as root (sync, then `drop_caches=3`), else `page-cache-as-found`, a lower bound. `--drop-caches` without root adds an `unmeasured` row saying so.
- **After a build:** when this process built the dataset, its files are in the page cache and its memory is the build's, so cold start and steady-state RSS are `unmeasured` ("run again to measure") and the verdict is `incomplete`. Run `search-bench` in a fresh process after the build.

## The report and the gate
- Rows go into 1a's report (`dataset::report`, tool `search-bench`). A run that stops with an error still writes the report, with a `run` row `unmeasured`. With `--dataset`, `--gate` exits 1 unless the verdict is `pass`.
- **Argument checks:** the dataset-only flags (`--low-resource`, `--steady-secs`, `--ingest-rate`, `--nrt-rounds`, `--drop-caches`) are refused without `--dataset`, `--dataset` with `--dir` is refused, and zero rounds, rate or seconds are refused, so the CI gate's command can't change by accident.

## The CI gates are unchanged
- Without `--dataset`, every table runs as before, prints the same lines and gates the same budgets. The rows are collected but never printed, and `--json` is optional. `size-report` isn't touched.
- The PR description has the dry run of `search-bench --torrents 200000 --gate`, `main`'s bin against this branch's.

## Refinements flagged (§2.19)
1. **Decimal RSS budgets:** "< 1 GB" and "< 512 MB" are read as 10⁹ and 512 × 10⁶ bytes, the stricter of the two readings.
2. **Cold start is reported, not gated,** since §3 sets no number for it.
3. **A starved ingest makes the new-to-searchable rows `unmeasured`** below 90% of the rate asked: the threshold is the bench's.

## Not run here
- **No 10M run:** it needs about 25 GB and hours; G-v1-10m runs it on the dedicated runner (M8-PERF-3). The mode is proved at 1,200 torrents in `bench/tests/dataset.rs`: every row prefix is present, the budgets are right, low-resource rows are `off` and `unavailable`, `--gate` fails a non-pass verdict, a run that builds the dataset leaves cold start and RSS `unmeasured`, the dataset's digest is unchanged after the runs and the scratch copy is gone.
