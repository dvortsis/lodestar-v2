# GS-0 decisions (the `payload_sig` producer and `sig:`)

Spec: `docs/plan/2026-11-05-v07-m7.md` §3 and §5 "GS-0"; architecture §6 "Grouping/dedup" and §8; build-plan Track M7; the population contract (`docs/decisions/2026-11-04-SB-6.md`).

- **One hash, in `classify`.** `lodestar_classify::payload::payload_sig` (file list) and `payload_sig_of_sizes` (content sizes, any order) compute what `filter::payload_sig` computed before, byte for byte: the same seed, `fmix64` and length mix. Goldens taken from the old code pin six values in both crates, and a property test checks the moved function against a verbatim copy of the old one. `filter::payload_sig` keeps `PayloadSig { sig, specific }` and CS-8a's specificity rule on top, so CS-8a, SP-4 and every stored CS-8 key are unchanged. `fmix64` is copied into `classify` as a private function: `classify` can't depend on `filter`.
- **The producer.** `TorrentDoc::new` computes the signature from the store's file tree (non-padding sizes), and `to_document` writes it to SB-6's `payload_sig` field (u64, indexed and fast). A torrent with no content files has none. `population::GENERATIONS["payload_sig"]` is now 1: every existing index walks its torrents under SB-6's backfill and reports the field partial until the walk completes. A blue/green rebuild writes it for every torrent, so a fresh index is complete at once.
- **`sig:` syntax.** `sig:` takes exactly 16 hex digits (the whole `u64`, any case), or a 40-hex info hash or magnet link, as `hash:` reads them. The AST is `{"op":"sig","sig":"<16 or 40 lowercase hex>"}`. A shorter value is an error: "sig: use all 16 hex digits of a payload signature, or paste an info hash (40 hex digits)". The error never echoes the value. **Refinement, accepted by the runner and flagged (§2.19, §2.33): this departs from architecture §8's 8-digit example `sig:7a9f3c12`,** which is refused rather than read as a prefix. An 8-digit prefix collides too often to name one payload, and it can't be one term lookup (§6). `docs/query-language.md` shows the 16-digit form.
- **`sig:<info hash>` is "same payload as this torrent", itself included.** The hash's signature is read when the query's weight is built, from the snapshot the query runs on, so a lease's later pages read the same answer and the result cache (keyed by generation) never serves a stale one. The query is that torrent's hash term OR its signature's term. **A withheld reference looks unknown** (B13's rule, `docs/decisions/2026-10-22-B13.md`): the reference counts only if it passes the request's own visibility clauses (`hidden:no`, `verified:yes` and `-type:adult` while Adult is hidden, the top-level clauses `api::search::base_query` adds), so a torrent a filter rule hid, or an Adult one while Adult is hidden, resolves to no signature. The query then matches only that torrent, which the same clauses remove, exactly as an unknown hash. A test checks that `sig:`, `-sig:`, `x | sig:` and `item sig:` answer the same for both. **Alerts too (the runner's option (a), the strictest that fits):** percolation runs saved searches without a request's visibility (B8), so a saved query containing `sig:<info hash>` runs with the default visibility added (`Node::with_default_visibility`: `hidden:no`, `verified:yes`, `-type:adult`). A hidden, unverified or Adult reference then resolves like an unknown hash and alerts nothing. Percolation doesn't know whether the saving account shows Adult, so Adult references never resolve there. Such a query's alerts also leave out hidden, unverified and Adult clones, which reading them would hide anyway. The 16-digit form names no torrent and runs as saved. Live queries carry their own visibility clauses, which `sig:` reads as `/search` does. Tests cover a hidden reference, an Adult reference and a visible one, each against an unknown hash. A torrent whose own document doesn't carry a signature yet (the walk hasn't reached it), or has no content files, matches only itself, never nothing. An info hash no indexed torrent has matches nothing.
- **Partial while backfilling, not a prefilter.** **Refinement, accepted by the runner and flagged (§2.19):** the brief says the pasted-hash form is "resolved through `SearchIndex::prefilter`". `sig:` is a clause the user asked for, like `source:`: it matches the documents that carry the field, and `Node::population_fields` names `payload_sig`, so `/search` returns it in `incomplete_fields` (`fields_incomplete`) while the field isn't Ready. It never answers "no match" without saying the field is partial. `SearchIndex::prefilter` stays the gate for *narrowing* another query by the field, which is GS-1's use (siblings' identical payloads), so no prefilter ever reads an unpopulated `payload_sig`.
- **Filter rules refuse `sig:`,** as they refuse `verified:`, `source:` and `network:`. `Node::mentions_provenance` now names it too, so the filters API answers `provenance_in_rule` (its message names `sig:`), and `filter::load::rule_query` treats a stored rule with it as unreadable. Otherwise the judge would call it no match, and a negated one (`-sig:…` in an Always-allow) would match every torrent. The matcher and the reference matcher still call it no match, for any path that reaches them. Rules block payloads through CS-8 keys. **Flagged as a follow-up:** a rule could match the 16-digit form against the item's own files (`classify::payload::payload_sig`), but the pasted-hash form needs the store.
- **The field catalogue lists `sig:`** with value type `hash` and `=` only, so the Builder offers it as a hex value, with no new value type. The web client labels the new AST op as its query text (`clauses.ts`), as it does provenance, until the UI gives it words. `FieldKind::Later` stays for the next field announced ahead of its milestone; none uses it now.
- **Size (`size-report --torrents 50000`):** the torrent index goes from 446.7 to **476.6 B per torrent (+29.9 B)**, within §3's 512 B. Of that: terms 19.1 B (one nearly unique `u64` term each), fast column 8.0 B, postings 2.5 B. That's above the plan's ~16–20 B estimate. The runner accepted it under §2.26. 35.4 B of headroom is left, and **GS-2, RX-1 and ENR-11 must each run `size-report --torrents 50000` and stay inside it** (plan Q10). The field's norms (1.0 B, SB-6's `INDEXED` numeric option) were already there before GS-0. A future schema bump could drop them.
- **Tests that played "a producer ships"** with `payload_sig` at generation 1 now use this build's generation + 1 (`index.rs`, `rebuild.rs`), or `group_key`, which still has no producer (`tests/index.rs`). They test the same contract.
