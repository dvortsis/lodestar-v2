# PK-cli decisions (PR pending)

`lodestar settings get|set|reset` on the stopped store (architecture §10.10.6 "Recovery without the UI", §11, §12; M6 gap-audit plan rows 29, 32, 110, 179 and Q2). Nothing here loosens an owner decision: the command can change less than the app can.

- **The API's rules, not a copy of them.** The command locks the store (`cli/lock.rs`), copies its `settings.` rows into an in-memory store, loads the real `settings::Registry` over that copy and saves through `SettingsApi::save`, exactly as `PATCH /settings` does: types, bounds, each section's `check`, `confirm` (the adult confirmation), revisions and sealing. The rows that changed are then written back to the locked store in one transaction. The copy is needed because the registry takes a `lodestar_store::Store`, and the store lock's exclusive connection can't be shared with a second one. A refused change writes nothing. Like the server's own load, it also writes back what `Registry::load` tidies (the old `general.log_level` moved, a field that's become read-only removed).
- **Refusals, from the code** (`set` only; a test in `cli/settings.rs` holds the lists to the registry's schema):
  - **Secrets** (schema `writeOnly`, whole or in a list's items): `integrations.clients` (each client's `password`), `integrations.torznab_api_key`, `notifications.ntfy_url`, `notifications.ntfy_token`, `notifications.discord_url`, `notifications.email_password`, `notifications.webhook_url`. Refused outright, before the value is parsed, so it's never checked, echoed or logged. Reading one from stdin or a 0600 file was the other option; refusing is smaller, and a secret is never a recovery need (the address and the DHT are). `get` prints a secret field as `(set)` or `(not set)`, and a list's items without their secret keys plus which are set, as the API returns them.
  - **`x-danger: security`:** none today. Refused by the tag, so a later field that needs the password again is covered without a change here.
  - **`x-danger: privacy`:** `insights.query_logging`, `logging.data`, `logging.data_until`, `logging.kinds`, `logging.peer_activity_until`, `logging.change_details_until`, `logging.console_detail`. Refused **whatever the value**, not only when turning on: telling on from off for a radio, a deadline and a list would be a second copy of the UI's rules, and `reset` turns each one back off (the defaults are off).
  - **Adult content:** turning on any `content` field (`show_adult`, `torznab_adult`, `stremio_adult`, `export_adult`). Detected as the registry's own `NeedsConfirmation` refusal, since the command never sends `confirm_adult`; turning one off is allowed. No CLI 18+ confirmation is added (Q2: that would be the owner's call).
  - Not refused: `x-danger: disruptive` fields (`network.http_bind`, `network.dht_port`, `network.dht_enabled`, `search.enabled`, `updates.channel`). Their UI dialog only explains the effect, and the address and the DHT are what recovery is for. The `*_allow_private` notification switches stay settable too: the UI has no confirmation for them either, and whoever can run the command can write the data folder anyway.
- **Exit statuses.** 3 (refused for safety, nothing changed): the store is open, an update rollback is in progress (`refuse_during_update_rollback`, which covers `bin/rollback.json`), a secret, a security or privacy field, or adult content. 2 (bad arguments): an unknown section or field, a read-only field, one an environment variable sets, `null` (use `reset`), or a value the API refuses, with the API's own message (`ApiError::from(SettingsError)`). 1: no store, or a failed save. `--help`'s AFTER_HELP already says this. `settings` returns its own `ExitCode` rather than `util::Failure`, which has no "bad arguments" case.
- **`get`** prints the value and its source (default, config.toml, saved, or the environment variable), and for a saved value what applies without it (the file's value or the default, with which). It doesn't print the built-in default under a `config.toml` value: the plan's "its default" is read as "what a reset gives", the useful fact in a recovery.
- **A secret the save resets is named.** Moving a secret's server (`notifications.email_host`, `email_port`, `email_security`, `integrations.torznab_url`) resets the saved secret through the registry's `SECRET_ENDPOINTS`, as the API does. The UI shows that as the fields reload; `set` prints `Also reset <field>` with a pointer to the app, since it can't set a secret back.
- **Values.** The argument is parsed as JSON (`true`, `30`, `["a"]`, `"text"`); anything that isn't JSON is taken as text, so `0.0.0.0:8080` needs no quotes. A string that looks like JSON is quoted (`'"30"'`). Hyphen values (`-1`, "until turned off") are allowed.
- **`reset --all`** resets every field the registry shows as saved through one batch (revisions go up), then removes the `settings.<section>.<field>` rows it doesn't show: a value an environment variable hides, which would otherwise come back when the variable goes, and one this build has no field for. Their sections' revisions go up too. `config.toml`, the environment and every key outside `settings.` (filter, floor, pack and subscription state, §20) are untouched.
- **Keep or revert** (`system/address.rs`): a `set` or `reset` of `network.http_bind` that goes through, and every `reset --all`, removes a pending `system.keep_or_revert.http_bind` record in the same transaction, which is what the UI's Keep stores. Refusing instead was the alternative, but the record exists precisely when the operator may be locked out, and the person at the machine running the command is a stronger confirmation than a session on the new address. Left in place, a record whose `new` equals the address the operator just set would revert it at the next start (`decide`'s `Revert` or `Bind` with a deadline), and a stale `serving` would keep `lodestar healthcheck` probing the old address. Only `http_bind` has a record kind today; the table in `cli/settings.rs` takes a later kind.
- **Runs as PUID/PGID** (`privdrop::Scope::DataDir`, like the other store commands), `get` included: it takes the same lock, and reading a sealed value can create `secrets.key` if it's missing, as the server's load would.
- **`worker` placeholder: moot.** `lodestar worker` is the real command on `main` (`cli/worker.rs`, WK-2: `--join`, `--token-file`, `--rotate-key`), so no placeholder is added (plan row 179, Q4).
