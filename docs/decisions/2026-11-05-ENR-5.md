# ENR-5 decisions (StashDB plugin)

**HOLD: nothing may register or enable this plugin until all of these are done.**
1. **The Q2 terms and robots check for StashDB's API is owed by the owner** (plan §5 Q2, owner §2.28). This slice's sandbox had no route to the service and no account. The check must confirm, and record here: (a) the API terms of use and `robots.txt` as they read today for `https://stashdb.org`; (b) that a general-purpose index sending a release name per lookup, at most one request a second and 5,000 background lookups a day (Q15), fits those terms (if it's grey, it goes to the owner); (c) that the request and answer shapes below match the live API, since the fixtures are hand-written and were never recorded: the `ApiKey` header, `POST /graphql`, `searchScene(term, limit)`, the `release_date` field name (older stash-box versions had only `date`), and what `searchScene` returns for a name that matches nothing (an empty list, or a loose best guess: the plugin takes the top result as the match).
2. **Host wiring is a later slice.** Nothing builds `AdultEnrichSource` yet: the host builds it with its own store connection, the live filter, the always-adult mask, its `Switches` and a `StoreState` kit, wraps this plugin's policy in `adult_enrich::capped`, and hands `Interest` to ENR-7's API.
3. **Precondition for registration: the hand-written fixtures are replaced by recordings from the live service, keys scrubbed** (ENR-3 passed this to ENR-5; plan ENR-3 gate). Recording needs an account and a key this slice didn't have.

Slice ENR-5 of `docs/plan/2026-11-04-v06-rulepacks.md` (runner brief, 2026-11-05). Spec: architecture §18.1, §18.7, §20.9, plan Q2, Q4, Q5, Q15, and the contract in `2026-11-05-ENR-1.md`; the parser and query documents are ENR-3's (`2026-11-04-ENR-3.md`). It mirrors ENR-4 (`2026-11-05-ENR-4.md`).

- **Not registered, not enable-able.** `crates/sources-plugins/src/stashdb.rs` is one `pub mod stashdb;` line in `lib.rs` and nothing else: no entry in `crates/lodestar/**`, no registry, nothing in Settings. `StashDb::need` shows what enabling would ask for.
- **Manifest.** Id `stashdb` (never renamed), `Kind::Enrichment`, **Account** consent, `enabled_by_default: false`, `always_adult: false`, risk Medium, priority Low, one endpoint: `https` to `stashdb.org`, so egress is narrowed to that host over https, public addresses only. `distribution: coordinator` (the policy default). No user-entered address, so no other stash-box instance can be reached (ENR-3 left that for a later base-URL parameter).
- **Policy (Q15).** One request a second per host with no burst, and a back-off of a minute up to six hours. The runtime already paces lookups, counts the daily cap and the caches, and holds the same per-host rate with `capped`, so the plugin has no second limiter: its requests go through the kit's `Client::send`, which applies the host limiter and records a 429's `Retry-After`.
- **API key.** The `api_key` credential in SRC-4's sealed store (the config schema marks it `writeOnly`; there are no other settings). It's read through the `Credentials` trait on each lookup, so a key dropped by a purge stops working at once and no copy outlives the call. It goes in StashDB's `ApiKey` header and nowhere else: not the URL, not the GraphQL body. It's only accepted if it's 1–2,048 ASCII letters, digits or `-_.|` (StashDB's are JWTs), so it can't break out of the header. No error, `Debug` string or log line holds it; a test runs a distinctive key through 401, 403, 429, 500, a cut body, an HTML body, a GraphQL error, a good body and a 302, against a service that echoes the key into its body and headers. A missing key, an unreadable one and an invalid one each fail before any request, with a message that names none.
- **The request is the name and nothing else.** One `POST https://stashdb.org/graphql` with the body `{"query": SEARCH_SCENE, "variables": {"term": <display name>, "limit": 1}}`: ENR-3's fixed document, with the name as a GraphQL variable, never spliced into the text. Built by `stashdb::search_request` from `Query::Name`, the only thing the runtime gives a plugin about an item. The plugin asks for the name form, so the parsed form is refused without a request (as ENR-4). No info hash, file name, tracker or install detail can reach it. It never uses the fingerprint query (fingerprints are of files, Q2) or `FIND_SCENE`, and asks for no performer id or personal field (the document selects none, and the parser can't return one: Q4, Q5). The exact header list is `Accept`, `Content-Type`, `ApiKey`, and a test asserts it.
- **Redirects are refused.** The client doesn't follow one; a 302 with an off-host `Location` is one request ending in "StashDB's request failed" and a test checks that exactly one request went out.
- **The answer** is read with ENR-3's `stashdb::parse_each` under `ANSWER_LIMITS` (its default caps, with items cut at 1 and performers at the section's 64). **Only the top result is used** (`limit: 1` asked, `max_items: 1` enforced): if it can't be read, the answer is an error, never the second-best guess, which could pin another scene's performers on the torrent (Q4).
  - **Mapping to ENR-0's section:** scene id, kind (always `Scene`: stash-box has no movie type and VR is a tag the claim doesn't read), title, studio name (the studio id isn't kept), release date (the fuzzy year, month or day kept as said), and **performer names** in the service's order, with `performers_truncated` as the parser reports (Q4 allows names on the item they belong to; no id, no personal field). A scene id the section's rule refuses is an error (it can't happen: the parser keeps UUIDs).
  - **Errors read the HTTP status.** 200 is read; **401 or 403** is "StashDB refused the API key" (no key echoed, no service text); **429**, or the host being held after one, is "StashDB is limiting requests; backing off" (a retry within the hold sends nothing and says "on hold after a refusal or a rate limit", since the limiter holds the host after a 401/403 too); any other status or a transport failure is a plain failure. The service's message text is never read or kept; GraphQL `errors` are only counted by the parser.
  - **A broken answer is an error, never a miss.** Every 200 body, match or miss, first passes a strict structural read (`shape`): within the parser's byte cap, one whole JSON document with no trailing bytes, a root object whose `data` is an object with a `searchScene` list, no `findScene` key (ENR-3's parser reads `findScene` too, so a `findScene` scene would otherwise be taken as the match), and no non-empty GraphQL `errors`. The read is a derived serde struct, so a repeated `data` or `searchScene` is refused rather than read two ways. A match needs the parser's top scene to be `searchScene`'s first entry (same id); a miss needs `searchScene == []`, no parser stop and no skipped scene. So an answer that stops the parser, skips a scene, is cut anywhere, has trailing bytes, or carries any `errors` entry (even beside a readable top scene, whose cast may be missing, and even after the parser's early stop at a second item) is "not understood", and the runtime doesn't cache it as a 7-day miss. `data: null`, a missing or non-list `searchScene` and a `findScene`-only answer are errors. The `Page` flag in `sources-feeds` (HOLD item 4) is still the long-term fix; this check is the stopgap.
- **The filter still applies in full.** `lookup` returns a `Lookup` to the runtime and nothing else; storing is the runtime's, through `adult_enrich`'s `judge_in`. The plugin has no path around it, and it can only run for an item that gate passed. The "blocklist applies" end-to-end test is ENR-G's (and SRC-G's `tests/safety.rs`), since it needs the pipeline, which this crate doesn't depend on. Here a test checks the section is within the claim limits unchanged, so intake has nothing to cut.
- **Fixtures** (`crates/sources-plugins/fixtures/stashdb/`) are hand-written and synthetic, made from ENR-3's. Not recorded: see HOLD 1c and the README there. Each exchange carries the exact request body the plugin must send.
- **Tests** (`crates/sources-plugins/tests/stashdb.rs`): fixture replay of a match and a miss; the request is a POST of the fixed document with the name and limit variables, the key header only, the exact header list, no URL query; only the name form is answered; 401, 403, 429 (with the hold and the retry after it), 500, a cut body, an HTML body and a GraphQL error each end in the right outcome; the top-result-only rule; answers not understood are errors and clean misses are no match; property tests that arbitrary and mutated bytes never panic and any match fits the claim limits; a missing or invalid key fails before a request; enabling without a key is refused (`consent::need`); the manifest, policy, floors and schema; no `Debug`, request or error holds the key or the name; the redirect and key-leak tests above; a lookup in flight can be dropped; two lookups are at least a second apart; and no shipped manifest is both Enrichment and always-adult. No live network, no fixed sleeps (paused clock).
