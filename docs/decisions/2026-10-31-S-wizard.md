# S-wizard decisions: first-run wizard, part 1

Part 1 of the slice (§10.10.10, §3 "Cold-start reality", §12.2): the shell at `/welcome` and steps 3, "How it works", 4, 5, 8 and 9. Part 2 adds 6, 7 and the rule-pack step.

- **Part 2 slots.** `wizard/steps.ts` lists the steps in order and names where the rest go (`SLOTS`): **6 Import from bitmagnet** and **7 Download client** after Storage & retention, and the **rule-pack step** (§20.6, packs pre-checked) after them, before Updates. Adding one is a new entry in `STEPS` and a loader in `WizardPage.svelte`; nothing else moves. Part 1 shows no placeholder for them, so a visitor never sees a step that can't be used. Progress numbers count the steps shown (3, 4, …), so the list has no gap until those steps land.
- **`/welcome` keeps the auth check and replaces the links page.** `WelcomePage` still does the setup-required, signed-out, retry and no-focus-steal handling, and renders the wizard once signed in. The page heading is now "Finish setting up", with each step's own heading below it. The old "Go to Search / Review settings" links moved to the Done step, which is where the brief wants them.
- **Steps 1 and 2 are listed as done** (they happen in `/setup`), using the existing `auth_setup_step_*` messages.
- **Progress** is `{ step, done, skipped }` in `sessionStorage` (`lodestar.wizard`), wrapped in try/catch, so a reload resumes and blocked storage only loses the resume. Anything unreadable starts at the first step. Nothing else in the app reads it.
- **Chunks.** The first view is the shell, the progress list and the page's auth check. Each step is its own dynamic import, loaded when it opens; the three form steps share the Settings engine's own lazy parts. If a chunk fails to load the shell says so and offers a reload (a failed module can't be retried). Their sizes are gated by a second entry, "Wizard steps (on demand)".
- **The engine is used as it is.** Steps 4 and 5 are `SettingsForm` (no save bar, no leave guard, no ⌘S) with `SettingField`s, so previews, validation, locks and errors are the engine's. **Save and continue** calls `form.save()`; it moves on after a save or when nothing changed (no request). A refused, conflicting, invalid or unreachable save leaves the step where it is with the engine's error summary or notice; the server's value stays the saved one and nothing is shown as saved. **Skip** never touches the form: no request, and the staged edit is dropped with the step.
- **Intensity** shows `crawler.intensity`. **Storage & retention** shows `storage.archive_raw` and `storage.mmap_mib`: the schema has no retention field yet (the only one, `insights.query_retention_days`, belongs to query logging). A retention field joins the list when the server adds one.
- **Updates (step 8)** uses the engine's form for `updates.mode` but a hand-built radio group, since the Settings screen for Updates isn't merged and its labels don't exist. Off, Check and notify, Install automatically; the server's current value is the only one selected (Off by default); "Container image updates" appears only when it is the current value, never as a choice. The step says plainly that checking contacts GitHub (§12.2). A value set by `LODESTAR_UPDATES` shows locked (disabled, with the variable named). "Fixes only is labelled recommended" (§10.10.10) is not implemented: the brief says to preselect nothing beyond the current value, and `updates.level` isn't part of this step.
- **Network check (step 3).** Reads `GET /network/check` every 5 s while `reachable` is `null`, one request at a time (the next read is scheduled when the last answer arrives), until it knows or 12 minutes have passed (the server measures for 10). It stops when the step unmounts and aborts the request in flight. **Retest** is the 30 s-limited `POST`; a `429 rate_limited` shows "You can retest once every 30 seconds" with the server's `Retry-After` when it sent one, and keeps the last answer. When the port isn't reachable the step lists the router port forward and the VPN case, and says Lodestar works either way.
- **"How it works"** is a static inline SVG of four numbered boxes with arrows, `aria-hidden`, and the four stages as an ordered list, which is its text equivalent. It sets the §3 expectation: the index grows over days and weeks. No numbers are quoted, since §3's are rough estimates.
- **The wizard changes no content-safety setting in part 1.** Only `crawler.intensity`, `storage.*` and `updates.mode` are ever sent.
- **Sizes.** The `/welcome` first view has its own entry at measured + 10%; the step chunks have one. No other entry is touched (Alert, Search results, Alerts and the Results toolbar are not changed by this slice; their sizes were checked before and after).
- **Messages.** `wizard_*` in `features/wizard/messages/{en,zh}.json`, both filled.
- **Review round (self-review).**
  - **Fixes only.** "Install automatically" now says it installs fix releases (Fixes only, recommended) and that the level is in Settings → Updates. Nothing extra is preselected; this follows §10.10.10 and the owner's §2.13 (this replaces the earlier bullet that dropped it).
  - **DHT off** is final for the network step: no polling, no progress, no port-forward help; the step says the DHT is off.
  - **Restart.** A saved field that needs a restart is remembered in the progress and Done says "Restart Lodestar to apply".
  - **Load failures.** Save and continue does nothing, and doesn't mark the step done, while the step's settings haven't loaded; Skip waits until the step has loaded.
  - **Accessibility.** The network step has one small polite region that changes only with the verdict. The Updates options and error are linked with `aria-describedby`.
  - **`SLOTS`** in `steps.ts` is documentation for part 2 and is not used by the shell yet.

## Engine access through `form/embed.ts` (runner ruling, §2.26)
- **`settings/form/embed.ts`** is the one door onto the form engine for `shell/SectionForm.svelte` and the wizard's steps (the runner widened this slice's ownership to that file and SectionForm's engine import lines). It re-exports what SectionForm used, plus `SettingsForm` and `SettingField`. A second consumer reaching the engine through other paths split its chunk (Settings section +1.37 KB); going through one module cut that to +0.14–0.22 KB. The wizard imports it statically from the step chunk.
- **Accepted as measured by the runner**, against a fresh build of `main` 064f69c (gz KB): Settings first views +0.14–0.22 (Settings section 43.31 → 43.53, Notifications 43.31 → 43.49, Language 42.97 → 43.15, Insights 43.05 → 43.23, Integrations 42.55 → 42.74, Logging 42.46 → 42.64, Appearance 27.66 → 27.81, Filters 32.45 → 32.60, Security 29.79 → 29.94, Keyboard 34.70 → 34.84); Settings section chunks 41 → 43 (static imports of SectionForm, preloaded in parallel); CSS 19.93 → 19.97 of 20 KB; Alert 45.40 → 45.44; Alerts 25.73 → 25.76; Search results 42.74 → 42.75; Results toolbar 4.29 → 4.30. No limit changes. New entries: Welcome route 14.85 (limit 16.5), Wizard steps 32.88 (limit 36.9).
- **Risk for the next slice:** CSS has about 30 B of headroom under its 20 KB limit.
- **Outside the brief's owned paths** (approved by the runner): `web/e2e/support/routes.ts` (the welcome smoke heading), `web/e2e/.update-snapshots` (marker: regenerates the welcome baselines, removed after), `settings/form/embed.ts` and SectionForm's engine imports.

## Part 2: download client and rule packs (S-wizard-2)
- **Step 7, Download client** (optional) shows `integrations.clients` with Settings' own client cards (`screens2/ClientsWidget`), so **Test connection** is the cards'. qBittorrent is named as the recommended client. Skip sends nothing; Continue saves through the engine's multi-section patch; a client setting that could not be read never marks the step done (same load guard as part 1). The cards are loaded with a dynamic import of the module Settings itself loads that way, and the step registers it as the field's widget; a static import of `LazyWidget` or `GroupedForm` split the Settings connection screens' chunks (+0.55 KB).
- **Rule-pack step** (after step 7, before Updates). The five packs come from `GET /filters`, each with one plain line (no adult content is named), all pre-checked when no pack is on (§20.6, owner §2.8). If any pack is already on, the server has a stored choice: the step shows the server's state instead, a pack that is on is checked and disabled (the wizard only turns packs on), and it says the rest is in Settings → Filters & Safety.
- **Applying.** Continue turns the checked, not-yet-on packs on one at a time, each as a `pack_switch` change through the change flow: the preview job first, then apply. The wizard applies a change itself only when the preview says it neither weakens anything nor needs a confirmation. Anything else (a warning, a password, `weakening`) is cancelled, nothing is applied, and the step says to use Settings → Filters & Safety. No password UI is in the wizard. A failed or refused apply stops at that pack, shows the server's message, re-reads `GET /filters` so the screen shows what the server has, and doesn't mark the step done. Skip, or Continue with none checked, sends nothing, so packs stay off.
- **Chunk rule for the flows.** The step imports `filters/flows/flow.svelte` dynamically (a module the Filters screen already loads that way), builds the `pack_switch` change as a typed literal and words an error from the server's message. Importing the flows' index, `changes.ts` or `errors.ts` made a second consumer of the dialogs' chunks (Filters dialogs +0.59 KB), the same effect `filters/screens/ops.ts` documents.
- **Step 6 (import from bitmagnet)** stays a hidden slot (`SLOTS.import` in `steps.ts`); online import is deferred (B-import-server-2).
- **CSS.** The part-2 files add no utility classes. A word in a comment ("card") made Tailwind generate daisyUI's `.card` (+147 B), so avoid component and utility names in comments and strings.
- **Sizes** (gz KB, fresh `main` 81738ec → branch): CSS 19.96 → 19.96; Welcome route 14.84 → 15.20 (limit 16.5); Wizard steps (on demand) 32.97 → 48.74, limit 36.9 → 53.6 (measured + 10%, as the brief allows for this entry); the Settings first views and Alert move by ≤ 0.02 KB, none over a limit.
- **Stored choice, as far as the API tells.** `GET /filters` has no "chosen" flag, so "the server has a stored choice" means at least one pack is on. If packs were turned off before, all five are pre-checked again. After a partial failure the packs still off keep the user's checks, so Continue tries them again. A change whose preview carries a warning, needs a confirmation or weakens anything is never applied by the wizard.
