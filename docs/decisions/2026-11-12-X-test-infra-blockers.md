# X-test-infra-blockers decisions

Blockers 2 and 3 from the cloud tester (2026-11-12): the PIA key step failed for us-brooklyn, and the AWS Windows test instance never reached SSM. Both are scripts the owner and the tester run; this PR changes and tests them offline only.

- **The PIA certificate name check takes any DNS hostname, lowercased** (`infra/pia-bridge/vm/pia-wireguard.sh`, stage 13). The old `^[a-z0-9.-]{1,253}$` rejected names with capitals. The new check: labels of `[a-z0-9-]`, 1–63 bytes, no leading or trailing hyphen, at most 253 bytes, after lowercasing. Names match without case in DNS and in curl's certificate check, so lowercasing changes nothing the server sees as identity.
  - **Why it stays strict:** the name goes into `--connect-to` and the URL. `:`, `/`, `@`, `_`, whitespace, control and non-ASCII characters are all still refused. The script now runs with `LC_ALL=C`, so `[a-z]` means ASCII in every locale.
  - **jq checks the characters before bash sees them:** `$(...)` drops NUL bytes, so `"a\u0000b"` would have become `ab`. The same check covers the server address.
  - **Not confirmed against the live list:** the brief forbids fetching PIA's server list, and nothing in the repo records us-brooklyn's name. The fix assumes the failing character is a capital. If it's something else, stage 13 now says which check failed (no server list, not JSON, region missing, no WireGuard server, address not IPv4, name not a string or not a hostname), with the rejected name, bounded and printable only, for the tester to report.
- **Stage 15 reports why addKey failed, on stderr only.** It prints the HTTP status (`000` for no reply), and PIA's `.status` and `.message` when the reply is a JSON object: control and non-ASCII characters stripped, cut to 32 and 200 bytes, the token and private key masked. The reply is capped at 64 KiB (`--max-filesize`). Never the reply itself. Exit code stays 15. `curl --fail` is gone from that call so a refusal's body is readable; success now needs a 2xx status **and** `"status": "OK"` (before, any non-error status with OK passed).
  - `deliver-pia` still discards all output (PIA's replies carry the exit address), so this helps a person running the step by hand. Stage 13 prints the same kind of line.
- **The AWS Windows instance gets a public IPv4 at launch** (`Deploy-AwsWindows.ps1`). Its subnet has an internet gateway but `MapPublicIpOnLaunch=false`, and no NAT gateway or VPC endpoints, so it couldn't reach SSM. `--subnet-id` and `--security-group-ids` became one `--network-interfaces` entry: `DeviceIndex=0`, the same subnet and group, `AssociatePublicIpAddress=true`, `DeleteOnTermination=true`. The runner's preferred fix. A public IPv4 is a small new charge (AWS bills about $0.005 an hour per address), far below a NAT gateway or endpoints, which would be the owner's call; the plan the human reads before typing the phrase now shows it.
  - **The security group must have no inbound rules.** Before the launch, dry run included, one read-only `describe-security-groups` call counts the group's inbound rules. Any rule, a failed call, or an answer that isn't exactly one row for that group refuses the launch. A public address is only safe while nothing can connect in; SSM is outbound only. The check runs once, before the launch: a rule added later isn't caught, so the runbook says to keep the group free of inbound rules.
  - Every existing guard stays: the typed phrase, the expiry policy, state tracking, the dry run, and the refusal while any Lodestar instance is active. `tests/Test-DeployAwsWindows.ps1` checks them against a stub AWS CLI.
- **`LodestarRestrictedEC2` couldn't be checked.** The policy lives only in the live account (`docs/operations/lodestar-cloud-assets.md`), not in `infra/aws/**`. RunInstances already creates a network interface in the approved subnet and group, so the resources the policy sees are the same. Whether it conditions on `ec2:AssociatePublicIpAddress` is unknown: the owner's `-DryRun` answers that, and an `UnauthorizedOperation` there means the policy needs the owner's change. The runbook says so.
- **The new PowerShell test isn't in CI yet.** CI's infra job runs "no script that can reach a cloud", and this test runs the deploy script itself (against a stub, on a PATH with no real AWS CLI, with AWS's config files pointed at nothing). Wiring it in means editing `ci.yml`, which this slice doesn't own; that's the runner's call. The PIA tests run in CI already (`infra/fleet/run_tests.sh`).
