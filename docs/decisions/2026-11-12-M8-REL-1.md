# M8-REL-1 decisions: `relevance` scores an existing store and index

Slice M8-REL-1 (plan `docs/plan/2026-11-06-m8-hardening.md`, OQ2 and RQ2; `docs/decisions/2026-11-06-runner-planning-wave-answers.md`). Spec: architecture §8, §17; build-plan §0.6. It builds on `docs/decisions/2026-10-22-R-relevance.md`, which still holds for the committed set.

## `--data-dir PATH`
- **The judgments folder comes from `--dir`, which `--data-dir` requires.** The folder holds `judgments.txt` and `baseline.txt` and has no `corpus.txt`. The default `--dir` is the committed corpus set, whose keys aren't hashes, so `--data-dir` without `--dir` is refused rather than failing on line 3.
- **Keys are v1 info hashes: 40 hex digits, either case, stored lowercase.** A v2-only torrent is keyed by the first 40 digits of its v2 hash, because that's what the store keeps in `torrents.info_hash`. A hybrid torrent is keyed by its v1 hash. The first 40 digits of its v2 hash aren't looked up (the store's `info_hash_v2` has no index a lookup could use at 10M rows), so a hybrid keyed that way counts as not in the store, and the format doc says so. A 64-digit v2 hash is refused with its own message, for the same reason.
- **The grammar is otherwise the existing one.** Malformed hashes, a duplicate judgment (after lowercasing) and unknown grades are errors with a line number. Three things are now stricter in both modes: a grade must be followed by a space (`3abc` isn't grade 3 for `abc`), an empty `=` line is an error (it used to clear the rationale, so a second `=` slipped through), and in hash mode a grade line must name a torrent. A leading UTF-8 byte-order mark, which Windows editors add, is skipped. The committed judgments have neither, and their output is byte-identical.
- **A judged torrent the store doesn't hold is left out of that query's grades.** It's counted: "N judged torrents not in this store". If that leaves a query with nothing graded above 0 that it had before, or with no judgment at all (only `x` torrents, all missing), the query is skipped and counted too. Scoring it would give NDCG 1 for a query that tested nothing. Why: the set measures ranking over what was crawled, not crawl coverage.
- **Strictly read-only.**
  - The store is opened as a SQLite URI with `mode=ro&immutable=1` and a read-only connection. No `-wal` or `-shm` is created, and nothing is locked or written. Opening a WAL-mode store read-only without `immutable` would create both.
  - **A `lodestar.db-wal` or `lodestar.db-shm` is refused, whatever its size.** SQLite removes both when the last connection closes cleanly. Either one means a server is running or stopped without closing the store, and `immutable` would read past the log. This also catches a server with search turned off, which holds no index lock, and one that hasn't written yet (an empty `-wal`).
  - The index is opened only when `index/v{schema}-t{tokenizer}/meta.json` and its `files/meta.json` exist, so `SearchIndex::open` creates no index. No writer is taken.
  - **A tantivy reader does briefly lock `.tantivy-meta.lock`** in each index folder while it opens its segments, opening the file for writing and creating it if missing. So an index without that file is refused rather than given one. An index on a read-only mount (Docker `:ro`, a snapshot) can't be opened; the error says to score a writable copy.
  - The test compares every file's size and mtime before and after a run and a `--write-baseline`.
  - **No new API in `crates/store` or `crates/search`.** It uses `lodestar_store::rusqlite`, `latest_schema_version` and `SearchIndex::open`.
- **Refused while a server holds the directory.** The server holds an exclusive lock on `index/.lock` (`lodestar_search::rebuild`'s `lock_root`) and its writers' `.tantivy-writer.lock` files. Each one that exists is opened read-only and locked shared (`File::try_lock_shared`, the same `flock`/`LockFileEx` tantivy uses). A busy lock refuses the run. The locks are held until the run ends. A lock file that doesn't exist isn't created, since creating it would change the directory and nobody can hold it.
  - **A server started during a run isn't kept out of the store.** It opens and may migrate the store before it reaches the index lock this run holds, and with no `index/.lock` yet nothing stops it at all. Every store read happens while opening, so once they're done the store's size, mtime and side files are checked again, and any change refuses the run.
- **Another schema is refused, never migrated.**
  - The store's `max(version)` in `schema_migrations` must equal `latest_schema_version()`.
  - The index must be this build's `v{SCHEMA_VERSION}-t{TOKENIZER_VERSION}`. The refusal lists the versions it found.
- **The search path is the committed suite's:** a `Lease`, its first page of 50, and `without_hidden()` plus `-type:adult`. No hot columns are loaded, so the swarm and freshness priors don't apply, as in the committed suite. The scores mean the same thing in both modes.
  - **The clock is a day after the store's newest `discovered_at`,** as the corpus's is a day after its last torrent, so a run over the same store ranks the same.
- **On a real store only the first page is checked for forbidden results.** The committed suite stops when a query matches 50 or more, so its check sees every match. Pilot data matches far more, and reading every page isn't what `/search` shows.
- **The baseline fingerprints the judgments, not the store.** `inputs` is FNV-1a of `judgments.txt` with line endings normalised. Two lines are added: `store_torrents` (the store's torrent count) and `index` (the index version, e.g. `v7-t1`). A 10M store's contents aren't hashed. `--gate` fails when the judgments, the count or the index version changed since the baseline. The committed set's `baseline.txt` format is unchanged.

## `--held-out`
- **It needs `--data-dir`** and prints only: the scored query count, NDCG@10, MRR, recall@50, the count of queries with a forbidden result, the not-in-store count and the skipped count.
  - **The forbidden count is a refinement on the brief's list.** It's an aggregate that names nothing, and hidden Adult appearing is a correctness failure the owner should hear about.
  - The skipped count is likewise an aggregate.
- **No per-query output, ever.** `--worst`, `--all`, `--gate` and `--write-baseline` are refused with it (exit 2). `--gate` is refused because plan RQ2 says the held-out score is reported, not gated, and a gate has no baseline it may write.
- **It writes no file. `--write-baseline` is refused outright,** rather than allowed outside the checkout. Telling "outside the repository" apart reliably (symlinks, worktrees, a checkout under the data directory) is more code than the case is worth, and the owner's ask is aggregates only.
- **Its errors name a line number, never the line.** Judgment errors give the line and a fixed message. A query that fails to parse or search gives "judgments.txt:N: the query failed". A panic hook replaces any panic message with a fixed one.
- **The judgments file is capped at 16 MiB** in both modes (the baseline is read under the same cap), and the parser is tested on 20,000 random files: it never panics, and a redacted error is only its line and a fixed message. The old parser split the tag at byte 1, which panicked on a multibyte first character. That's fixed.

## Structure
- The new code is in `bench/src/bin/relevance/judgments.rs` (the parser, moved from `relevance.rs` and made generic over corpus keys and hashes) and `bench/src/bin/relevance/data_dir.rs` (the read-only open).
- The rest stays in `relevance.rs`. Moving the corpus, measure and baseline code too would have doubled the diff, with no change in behaviour, past the slice's size budget.
- `bench/README.md` isn't this slice's file, so the format is documented in the module docs. M8-DOC-1's `docs/relevance.md` is where it belongs for users.
