# P-v06-companions decisions

Planning slice for E-v06-companions. The plan is `docs/plan/2026-11-06-v06-companions.md`. Docs only; nothing here is built. Each choice below is the planner's unless it says the runner made it in review of #516. Questions that belong to the owner are in the plan's §5 (Q1–Q5, Q15, Q20, Q21) and are not decided here.

- **One new crate, `lodestar-companions`** (architecture §13 already names `crates/companions/`). Every Opus core piece (catalogue, fetch and verify, extraction, credentials, supervisor) gets its own files in it, so wave 2 runs four slices at once with only `lib.rs` `mod` lines shared.
- **Twenty-one `CMP-*` slices, about 13,900 lines, none over ~1,200** (CMP-6, of which ~400 is regenerated OpenAPI). CMP-0 also defines the adapter traits and the closed input types, so the supervisor, the adapters and the templates can run at once. The supervisor is split into the concurrency core with orphan cleanup (CMP-4a) and the platform limits and egress hook (CMP-4b). The install flow (CMP-5) stays one slice because it's one state machine that crashes must leave consistent.
- **The guided Docker/Unraid path is its own slice, CMP-5g** (runner, review of #516): owner §1.7.2 asks for "automatic detection and configuration" after a guided install, and no slice built the endpoints, the watch loop for unsupervised companions, or the adapter wiring.
- **Compose and template generation and both adapter slices on Opus, stricter than build-plan Track K's [S] marks** (plan Q14; CMP-7 by the runner in review). Compose output runs under a root-equivalent `docker compose`, so it is built only from CMP-0's closed input types, with `serde_json`-quoted YAML scalars and `quick-xml` for Unraid, and no hand-written escaping. Detection (CMP-8a) probes a URL you enter and reads untrusted responses; auto-configuration (CMP-8b) writes generated credentials into third-party APIs through a sink `crates/lodestar` provides (CLAUDE.md: security-sensitive code and untrusted input are never delegated).
- **No migration** (plan §3, Q10): per-companion state and sealed credentials go in `settings` rows, the #367 pattern the rule-pack plan also used. The migration queue is unchanged.
- **Each owner question changes one slice:** Windows qBittorrent is CMP-11 (Q4); FlareSolverr, opt-in only, is CMP-12 (Q21, runner in review); the unit's hardening question gates CMP-G and any unit change in CMP-4b (Q20, runner in review). Q1 and Q15 gate CMP-0, Q2 CMP-1 and CMP-13, Q3 CMP-4a and Q5 CMP-6. CMP-0 also carries `ext:v051-soak-verdict`.
- **Q3 states its consequence** (runner in review): companions run as Lodestar's own account can read `secrets.key`, the database and the auth file. The recommendation is a same-account sandbox (Landlock on Linux; a restricted token or AppContainer on Windows if a safe wrapper exists), with a plain warning where it can't apply.
- **Orphaned companions are a design point with a gate** (runner in review): pid and start-time records with orphan kill at start-up, and the init kills the companions it adopts when the work child dies (CMP-4a, CMP-G).
- **"Verified at pin time" is a checked claim:** CMP-13's pin-refresh tool verifies upstream OpenPGP signatures and writes the pins, and CI refuses pins it didn't produce (runner in review; plan Q2).
- **A companion's route is its own setting** (plan Q18), seeded from the egress of the plugin that needs it and built through `lodestar_sources::PluginEgress` handed in by `crates/lodestar`, so `crates/companions` never depends on `crates/pipeline`.
- **Guided installs never put a secret in a generated file** (plan Q19): you paste the companion's own key or temporary password once, and Lodestar seals it and replaces the temporary password. gluetun's VPN keys stay placeholders you fill in; Lodestar never stores them.
- **Only CMP-9b's two mount lines wait for SRC-15b** (runner in review): the chip component lives in `web/src/lib/features/companions/`, the wizard option is its own slice (CMP-9c), and nothing else in the epic waits on `ext:owner-q1`.
- **Recommended deferrals, accepted by the runner and flagged to the owner** (§2.19): managed-container mode past v0.6 (Q11), and native VPN beyond the existing egress settings (architecture §5 and §14 put embedded WireGuard in v1.x). Both narrow scope without loosening any owner decision: §1.7.2 asks for guided installs on Docker and Unraid, which the plan builds.
- **Recommendations stricter than the spec, the runner's call** (§2.19): no LAN scanning in detection (Q12); a companion that can't follow the egress route doesn't start (Q8); native installs refused inside containers (Q17); an unanchored second read on CMP-0, CMP-1, CMP-2 and CMP-G.
- **`/security-review` on every slice but CMP-D** (runner in review): CMP-D is docs only, an exemption from standards §7. Its replacement check is that the guide follows §18.10: no Docker socket, ports on the internal network, `service:gluetun`, and the WebUI never exposed.
- **Numbers proposed under §2.26 and accepted by the runner:** supervision backoff, crash and health thresholds and the 1 MB log ring (Q7); download and extraction caps (Q16).
- **The plan doesn't edit `runner/slices.yaml` or `runner/dashboard.yaml`** (brief): §4.1 gives the slice lines, the eight `ext:owner-cq*` conditions, the `CMP-*` placement rule and the `CMP-G` gate entry for the runner to add.
