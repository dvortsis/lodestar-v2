# P-v06-companions decisions

Planning slice for E-v06-companions. The plan is `docs/plan/2026-11-06-v06-companions.md`. Docs only; nothing here is built. Each choice below is the planner's, for the runner to accept or change in review. Questions that belong to the owner are in the plan's §5 (Q1–Q5) and are not decided here.

- **One new crate, `lodestar-companions`** (architecture §13 already names `crates/companions/`). Every Opus core piece (catalogue, fetch and verify, extraction, credentials, supervisor) gets its own files in it, so wave 2 runs four slices at once with only `lib.rs` `mod` lines shared.
- **Sixteen `CMP-*` slices, about 11,100 lines, none over ~1,000.** The supervisor is split into the concurrency core (CMP-4a) and the platform limits and egress hook (CMP-4b). The install flow (CMP-5) stays one slice because it's one state machine that crashes must leave consistent.
- **Two model assignments stricter than build-plan Track K's [S] marks** (plan Q14). Auto-configuration (CMP-8b) moves to Opus, because it writes generated credentials into third-party APIs (CLAUDE.md: security-sensitive code is never delegated). Detection (CMP-8a) stays Sonnet only because it reuses existing bounded readers (`integrations::clients::qbittorrent`, `sources-feeds` `json.rs`); a new parser would be split out to Opus. Compose and template generation (CMP-7) stays Sonnet with `/security-review` for its escaping.
- **No migration** (plan §3, Q10): per-companion state and sealed credentials go in `settings` rows, the #367 pattern the rule-pack plan also used. The migration queue is unchanged.
- **The narrower option is built where an owner question is open, and the gate waits** (plan Q4): the slices build guided qBittorrent on Windows; CMP-G depends on `ext:owner-cq4`, so nothing ships before the owner answers. Q1, Q2, Q3 and Q5 each gate the slice whose design they set.
- **Recommended deferrals, for the runner to confirm and flag to the owner** (§2.19): managed-container mode past v0.6 (Q11), and native VPN beyond the existing egress settings (plan §2 "Not in this plan"). Both narrow scope without loosening any owner decision: §1.7.2 asks for guided installs on Docker and Unraid, which the plan builds.
- **Recommendations stricter than the spec, the runner's call** (§2.19): no LAN scanning in detection (Q12); a companion that can't follow the egress route doesn't start (Q8); native installs refused inside containers (Q17); `/security-review` on every slice but the two display and docs slices, and an unanchored second read on CMP-0, CMP-1, CMP-2 and CMP-G.
- **Numbers proposed under §2.26** (performance and UX, flagged): supervision backoff, crash and health thresholds and the 1 MB log ring (Q7); download and extraction caps (Q16).
- **The plan doesn't edit `runner/slices.yaml` or `runner/dashboard.yaml`** (brief): §4.1 gives the slice lines, the five `ext:owner-cq*` conditions and the `CMP-G` gate entry for the runner to add.
