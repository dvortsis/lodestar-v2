# X-search-files-6 decisions

§3's "File-level query joined to torrents < 150 ms" row at 10M, continued from X-search-files-5 (#505). This slice closes two of the three clauses #505 left (`file:(ext:mkv,mp4,avi -path:sample)` and `file:(size:>100MB)`) under the runner's design call (§2.26, 2026-11-05), and reports a design for the third (`file:mkv`), which needs a schema bump the brief doesn't allow without the runner. The gate's query mix and numbers are unchanged. **At 10M the gate was met at 5d6141ca on this machine: cold p95 93.6 ms (gate 150), warm p95 29.5 ms (gate 30), from 116.8 and 46.3 ms on `main` on the same store and machine. The final head is unmeasured at 10M** (the runner's review round changed the path's guards; the container can't hold a fresh 10M store beside the build, and the runner queues the rerun for G-v1-10m and the reference runner). The warm margin was half a millisecond, and `file:mkv` is now the slowest clause.

## Extensions less rare words (brief item 1)
- **The shape (`compile::negated_words`):** a `file:(…)` clause of one extension atom (`ext:a,b`, or `ext:a | ext:b`) and one or more negated words not on the title (`-path:sample`, `-sample`, `-name:x`), in any order. Other shapes stay as they were.
- **The answer:** a torrent matches when one of its covered files has an extension and none of the words. So it's the **candidates**, the torrents with any `{ext}:{code}` term (`file_ext_bucket`, which follows smart coverage exactly, #505), less the **bad** torrents: those with a covered file of the extensions that has a word (the suspects) and none without. On the torrent index that's `file_ext_bucket` matching `(a|b):[0-9]+` and not `id` in the bad set (`compile::negated_query`), scored as #505's bucket clauses are (`torrent_level`).
- **The bad set (`files::bad_torrents`):** the file pass computes it in place of the whole clause.
  - **Suspects** come from each segment's files with an extension and a word. Tantivy's intersection is led by the words' postings, so it reads about as many files as the words have, not the extensions'.
  - **Rescue by neighbours:** a torrent's files are normally adjacent documents (added together), so each suspect torrent's run of documents around its suspect file is checked for a file with an extension and no word, seeking that clause forward only (`files::undecided_in`). In the synthetic corpus 60% of movie folders (about 4.5% of all torrents, ~450k at 10M) have a `Sample/` file, and nearly all of them have the film beside it, so almost every suspect is rescued here without a lookup.
  - **The exact check:** the suspects the neighbours don't rescue (cached per segment, `{clause}@undecided`) are checked on all of their files wherever they sit (the file index's `torrent` terms, `TermSetQuery`), so the answer never depends on document order or on which segment a file landed in. What's left is the bad set, cached for the file snapshot (every segment and its deletes in the key), so a warm query reads it whole instead of redoing the exact check. Tests: `tests/files.rs` `the_cached_bad_set_follows_new_torrents_and_deletes` covers one handle with a new sample-only torrent committed and then a store delete (no new segment); it fails with a constant key. `files::negated_props::a_cached_bad_set_follows_a_delete` fails with the delete count left out of the key. Through the public path a delete only removes torrents, and those leave the torrent index too, so there a stale entry is harmless.
  - **Cost guard (the runner's review):** more than 256 undecided suspects that are also more than 1/1024 of the extensions' files (`files::UNDECIDED_RATIO`, `UNDECIDED_FLOOR`) send the clause to the file index whole. A word under the ratio whose suspects are mostly truly bad would otherwise cost more there. Measured on a fresh 200k corpus (cold best, words' path against whole): a release group's name (`-sparks`, `-flux`, `-rarbg`, `-yify`, `-tigole`: every file of ~2,800 torrents) took 22–25 ms cold and 9–11 ms warm on the words' path, against 8–12 and 2 ms whole. At the final head, on another fresh 200k store, they run whole, at 6.4–6.9 ms cold and 2.0–2.3 ms warm, the suspects' pass included. `-path:sample`, `-sample`, `-path:extras`, `-path:screens`, `-grp` and `-ncop01` keep the words' path, at 1.8–3.5 ms cold (6.4–8.1 whole) and 1.4–1.6 ms warm. `-1080p` and `-x265` are over the ratio there and run whole.
  - The brief asked for the second step to run on the file index restricted to the suspects' ids. It does, for the undecided ones; looking up all ~450k suspects by id first would read their files through 450k `torrent` terms on every cold query (not measured at 10M: it was judged from the counts before the build), so the neighbour pass decides most of them first. Same answer, by construction and by test.
- **The threshold (`files::NEGATED_RATIO`, 8):** the words' path runs only when their terms' documents (summed over the target fields and segments, deleted ones included, the terms `word_query` reads: the word's units and compounds) are at most an eighth of the extensions'. The first push counted every token, parts included (`f5` → `f5`, `f`, `5`), so an alphanumeric word was never rare enough; the 10M per-word numbers below were taken then, so `-1080p`, `-720p` and the like may take the words' path now, subject to the cost guard. Otherwise the clause runs on the file index whole, as before. Measured at 10M (cold best, the clause's torrents identical on both paths): `-path:sample` and `-sample` (over `ext:mkv,mp4,avi`) and `-path:extras` (over `ext:mkv`) take the words' path, at 84–97 and 45 ms; `-path:subs`, `-1080p`, `-720p`, `-hevc` and `ext:srt -en` are over the ratio and run whole, at 102–122 ms (38 ms for `srt`), as on `main`. On `main`, `-path:sample` measured 133.7 ms cold. Warm, both paths take 21–30 ms, the cached sets being small either way. Only one ratio (8) was measured. The words over it ran slower on the whole path (102–122 ms) than those under it on theirs (84–97 ms), so a looser ratio might pay off; that needs one more run at 10M.
- **Population:** the path needs `file_ext_bucket` Ready in the snapshot (`bucket_terms_ready`), as #505's bucket clauses do; while it isn't, the clause runs on the file index whole.
- **Not while the file index lags (the self-review's finding, made race-free in the runner's review):** the file index lags the torrent index only when it's rebuilt or recreated behind it (a crash leaves it ahead: it commits first). #505's bucket clauses may then find a torrent early, since they only find true matches; this shape would let in false ones, as the bad set would miss the lagging torrents' files. So the path runs only when the file index's `last_id` has reached the torrent index's.
  - **Where the watermarks come from:** `PopView::last_ids`, set at open and by the writer after both readers reload, and read in `compile_at` before the file searcher is taken. That searcher therefore holds at least what they say. The first round read each index's `meta.json` after taking it, and `Side::commit` writes the meta before it reloads, so a query could pair a caught-up meta with the stale snapshot (the runner's blocking finding). Reading the view also drops two `meta.json` parses a query. If `Indexer::commit` fails after both commits reached disk, the view keeps its older values until the next successful commit. That's conservative: the clause runs whole and is never wrong.
  - **What's left:** a torrent committed while a query is in flight (after its file pass, before its torrent search) can match by its candidates alone for that one query, where `main`'s path misses it for that query. Both are transient.
  - **Tests:** `index::population_tests::a_stale_file_snapshot_never_meets_the_words_path` commits the file index without a reload, as `Side::commit` does before its reload, and fails with the first round's check. `tests/files.rs` `negated_words_wait_for_a_lagging_file_index` covers the recreated file index.
- **Tests:**
  - `tests/files.rs` `negated_words_answer_as_the_file_index_does`: the same torrents, order and scores as the file index for a torrent whose only video is a sample, one with both kinds, `sample` in the name rather than a directory, a compound word (`web-dl`), an absent word, a word too common for its postings (`common`, which takes the fallback), two words, `ext:a | ext:b`, the words first, beside a word, a range or another file clause, in an alternative and negated, over a pack whose small images coverage leaves out and a hidden video. It also checks which path each word takes. It fails if the bad set is taken to be all the suspects (no rescue at all). Its torrents' files are adjacent, so it doesn't tell the neighbour pass from the exact check; the property test below does.
  - `files::negated_props::bad_torrents_are_exact` (property test): the bad set is exactly the torrents with a live file of the extensions that `main`'s evaluator (the whole clause through `torrent_ids` on the file index) doesn't find, and exactly the brute-force ones. It covers `path:`, unfielded and `name:` words, two words, one or two extensions, a torrent's files spread over documents and segments, torrents re-indexed partway (files deleted, some added again later), cold and from the cache. The cost guard sends a bad set to the whole clause, and a stopped token stops it with `Cancelled`. It fails if the exact check is skipped.
  - The differential test's corpus is now several segments (a few torrents a commit). Non-adjacent files arise only from a re-index, which the property test covers.
  - `tests/files.rs` `a_generation_1_index_backfills_the_new_codes`: an index at generation 1 opened by this build backfills both fields. Bucket and negated-word clauses answer from the file index meanwhile and from the new terms afterwards, the same torrents throughout.
  - `compile::negated_tests::negated_words_takes_only_its_shape`: the shapes refused (two extension atoms, words only, a phrase, a prefix, a positive word, a range beside it, a negated alternative).
  - `bucket_clauses_fall_back_while_their_terms_are_backfilled` now includes this shape: while `file_ext_bucket` backfills it answers as the file index does.
- **An index without `id`** (none opens: it's in every schema since v1) matches nothing for this clause, rather than the candidates unfiltered.
- **Stopping and errors:** the neighbour pass checks the token every 4,096 steps (suspect files and run documents), and so does the exact check, a segment at a time. A stop returns `Cancelled` or `OutOfTime` as the whole-clause path does. Any other error is logged (`FILE_SEARCH_FAILED`), and the clause runs on the file index whole.
  - #505's `bucket_terms_answer_as_the_file_index_does` forced its reference onto the file index with a never-matching exclusion, which is now this shape; it adds an always-matching atom (`Node::All`) instead, the same files.

## Finer size codes (brief item 2)
- **The floors (`files::code_floors`):** `size_bucket`'s floors (each power of two and 1.5 times it), plus 5, 10, 20, 50, 100, 200 and 500 of each binary unit (B, KB, MB, GB, TB, PB, EB; 1 and 2 of a unit are powers of two already). A file's code is its floor's index twice, plus one above the floor, as #505's split. So a decimal-looking bound such as `size:>100MB` (100 × 2^20) or `size:<=500MB` is whole codes and reads no file; 1,000 MB, 700 MB and other values still have edges, checked in the file index.
- **Why this split:** measured on 200,000 synthetic torrents, it adds about 10% to the bucket terms (`file_bucket` 5.15 → 5.67 terms a torrent, `file_ext_bucket` 6.91 → 7.74). Eight sub-codes per power of two would double them (10.35 and 14.81) and still leave 100 MB off a floor. The file index's `size_bucket` is unchanged.
- **Population, not schema:** the codes are what `file_bucket` and `file_ext_bucket` hold, so both move to generation 2 in `population::GENERATIONS` (SB-6's contract): an index built by #505 backfills them from the store, resumably, and until the walk completes every bucket clause and the negated-word path run on the file index (#505's `bucket_terms_ready`), so results stay true. No `SCHEMA_VERSION` bump. **Upgrade cost for an existing v7 index:** the backfill re-indexes every torrent in the background while the index serves, rewriting the torrent index only (the file index's documents and the file-set caches are untouched). That's less than a rebuild; not measured. The branch's full build of both indexes ran at 2,476 torrents a second here, about 67 min for 10M on 4 cores, an upper bound.
- **Tests:** `codes_are_ordered_and_hold_their_sizes` (property: every size has one code, a larger size never a smaller one, and its code's range holds it), `a_code_plan_covers_exactly_its_range` (property, now over the new floors too: a range's whole codes and edges cover exactly the range, edges within one code and never a whole one, at most two), and `floors_split_ranges_into_whole_codes` (binary and decimal floors, an edge between floors). `tests/files.rs` probes every code floor too, and its differential test adds ranges at, beside and between decimal floors.

## `file:mkv`, a word that's also an extension (brief item 3): not built, a design for the runner
- **What the tokenizer emits:** every file name with an extension emits the extension as a token (`a.mkv` → `a`, `mkv`; `x.mp4` → `mp4` whole and `mp`, `4` parts; `F.WEB-DL.mkv` → … `mkv`). So `file:mkv` is the ext-mkv torrents (from `file_ext_bucket`, exact) ∪ the torrents with `mkv` in a file whose extension isn't `mkv`, or in a directory.
- **Why it isn't closed here:** the second part's postings are `name:mkv` and `dir:mkv` on the file index, and `name:mkv` holds every `.mkv` file: reaching the few others means walking them all, which is the 166 ms. No existing field leaves the extension token out.
- **The runner's ruling: v8 is deferred.** The clause is about 95 ms cold, under the 150 ms gate, and a v8 would make every v0.5.1 user rebuild in full. Design A is preferred over B. It's bundled with the next slice that needs v8 anyway, or taken at G-v1-10m, measured on the reference runner first. A must also drop the extension's split tokens (`mp`, `4`) from `name`, and keep phrase and word matches unchanged (`file:"sample mkv"`, `file:mp`), with a differential test.
- **Design A (preferred, v8):** index a file's name without its extension token in the file index (the token stays in `ext`), and answer a word that is a valid extension as `ext` candidates ∪ the rest. The file index shrinks by about one posting a file (not measured; at most one posting a covered file, about 30 per torrent at 10M, saved from `name`); `file:mkv` would cost about a lone extension's time plus the rest's postings (`file:(ext:mkv)` measures 11.3 ms cold at 10M). Phrases ending in an extension (`file:"sample mkv"`) need rewriting to keep matching. A `SCHEMA_VERSION` bump to v8, acceptable only before the v0.5.2 cut.
- **Design B (v8):** a torrent-index marker term on torrents whose `paths` differ from their file documents' words (paths truncated at `MAX_PATH_TOKENS`, or files coverage leaves out), so an unfielded `file:word` is `paths:word` off the marked torrents, plus the file index for the marked ones. Under 1 B a torrent on the torrent index, but the marked torrents' part still needs a file-index field to avoid the walk, and `paths` holds a single-file torrent's name. More moving parts than A.

## Measured at 10M
- **Method:** #505's. One 10M corpus built in this container (4 cores, 15 GiB) with `main` at a7778e71 and benched with `search-bench --torrents 10000000 --only "broad file"`. Then the index was deleted and rebuilt from the same store with the branch, and benched the same way. Cold means the file-set cache was emptied before each query; the OS page cache stayed warm. **This machine ran faster than #505's.** `main` measured cold p95 116.8 ms here, where #505 measured 228.4 ms for the same code, so `main` already met the cold gate here. Compare within this table, not across PRs. The branch's run stored the bench's 10 NRT torrents a second time, and they already existed (the generator's seed is fixed, so they're the same torrents), so its final NRT check reported "never indexed". That comes from reusing the store, not from this change: `main`'s run on the same store passed it.

## What's left
- **Nothing for the gate on this machine,** but the warm p95 (29.5 ms) is within half a millisecond of its gate, and a slower machine (#505's measured `main` at twice this one's cold p95) may miss it.
- **`file:mkv`** (95 ms cold, about 26 ms warm) is now the slowest clause of the mix. Design A, with v8, is deferred (above).
- **The final head at 10M** is unmeasured: the runner queues the rerun (cold, warm and NRT on a fresh store) for G-v1-10m and the reference runner. It should include a release-group word (`-rarbg`, `-sparks`): the cost guard was measured only at 200k, and its limit grows with the corpus. On a fresh 200k store at the final head, the CI bench passes (cold p95 4.19 ms, warm 2.68 ms) and so does NRT (max 2.03 s).
- **Decimal bounds off the floors** (`size:>700MB`, 120 ms) still check their edge code file by file. They're not in the gate's mix.
