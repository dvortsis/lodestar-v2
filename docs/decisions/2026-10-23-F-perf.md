# F-perf decisions (#110)

Filter engine speed-ups, hostile-input bounds, and the budget's reference runner (architecture §20.4, §20.8; owner decisions §1.6.6, §2.19). Supersedes the reference-runner choice in `2026-10-22-filter-budget.md`; everything else there stands.

- **The 50 µs budget is now held on an AMD EPYC 7763, the most common hosted runner** (owner, 2026-10-23: "Go with whatever makes for the best user experience"). #97 held it on the fastest runners seen as a stopgap, since today's code then ran 52 µs at 10% on a 7763. Users run Lodestar on NAS and desktop CPUs, so the budget should hold on hardware like theirs.
  - **`CALIB_REF_NS` = 10.7 µs**, by #97's rule: the lowest `calibration:` line (fastest pass) of the 7763 runs seen. #97's four 7763 jobs (120136591749, 120136592052, 120136592177, 120136592216) each had a fastest pass of 10.7 µs. `calibrate`, `torrents` and `COMMON` are unchanged since.
  - **What the gate now means for users:** a torrent is judged against the core, every pack and 10,000 of your rules in under 50 µs on one core of a 2021 server CPU, so one such core keeps up with over 20,000 torrents a second on filtering alone. Recent desktop CPUs are as fast or faster per core; many NAS CPUs are slower, and the 7763 is closer to them than the fastest runners were. A Xeon 6973P-C, about 1.5× faster, now reads its times 1.5× higher, so the gate is that much stricter there. The budget is unchanged; what it holds grows by the mixed set below.
  - **The speed range stays 0.4–2.0×.** Runners seen now take 0.67× (Xeon 6973P-C) to about 1.1× (an Intel build VM) the reference's time.
- **Every rule shape is held to the budget (owner-delegated, 2026-10-23; `docs/owner-decisions.md` §2.21).** The owner had the runner decide open questions with UX and performance as the deciding factors, and the runner decided that NEAR, negation, fuzzy, prefix and `title:` rules count, not only the shapes the cheap check can reject.
  - **The held mixed set:** of every 100 rules, 10 on common words (the 10% case), 1 NEAR, 2 negations, 2 fuzzy words, 3 prefixes and 1 `title:` word, all on words the set has so the narrowing can't rule them out, and the rest as before (keywords, phrases, groups, narrowed keywords, alternatives). **Why that mix:** most rules people write and lists ship are words, phrases and groups; each expensive shape is a few per cent of a large rule set, and the 10% on common words keeps the held stress case in it. The runner proposed the first four proportions; `title:` was added at 1% so the set has every shape.
  - **Each shape at 10% of rules is measured and reported**, not held, so its cost stays visible: NEAR (two common words always further apart than its window, 32 variants), negation (a common word without `mkv`, which every torrent has), fuzzy (made-up words, half within one edit, half two), prefix (hundreds of different prefixes, each starting like a common word) and `title:` (a common word no title has).
  - **Matching is unchanged.** Every speed-up below answers exactly what the full match answers, so §2.21's fallback (a Filters UI warning instead of weaker matching) isn't needed for these shapes at 10%. B15 may still warn about NEARs wider than eight positions or `title:` phrases, which take the full match (see "Not covered").
- **Gates on the rule index (§20.8 "Narrowing").** Each index entry carries one more clause every match needs, checked from numbers the torrent has once while its rules are marked: its size (`size:`), a file's size reachable (`file:(… size:…)`), one tag, a prefix's first characters, or a phrase's first two tokens in a row. A rule whose gate fails isn't marked, so it's never read.
  - **Why:** at 10% a torrent met about 400 rules, and the cheap check turned nearly all of them away at about 30 ns each, mostly cache misses reading the compiled rule. Rules met per torrent fell from 394 to 46 at 10%, and from 785 to 49 at 25%.
  - **Soundness:** a gate is one of the cheap check's own answers, on a clause an AND needs, so it turns a rule away only where the cheap check would. The matcher's reference property test asserts that on every generated query and torrent.
  - **Tried and dropped:** the cheap check laid out flat in one array per rule set. It cut no misses (they were in the torrent's own key tables), and it ran 2 µs slower.
- **More gates, for the shapes the cheap check couldn't decide (§2.21).** A gate may also answer exactly from the torrent's distinct token texts, compared byte for byte, so it still says *no* only where the full match must. The reference property test now holds every gate to the full match.
  - **A negated word anywhere** (`x264 -1080p`): the rule is turned away when the torrent has the word, unless it's a CSX-5 neutralized word, which never counts.
  - **A prefix:** turned away unless some token text starts with it, read from the texts sorted by the key of their first characters.
  - **A fuzzy word:** an edit drops at most one of the word's characters, so a text within the distance lacks at most that many of them, and so do all texts of its length together. The rule is turned away when no length within the distance has enough of its characters.
  - **A NEAR:** turned away when its words never came within its window (below).
  - **A `title:` word:** turned away when the titles don't have it.
  - **Rules sharing a gate clause** (`-sample`, the same prefix) get its answer once per torrent.
- **NEAR nearness, recorded by the key scan.** For the token texts the rule set's NEAR words use, and only for the pairs some NEAR asks about (its first word's against each other word's), the scan records the closest two came in one text, up to eight positions. A NEAR's places within its window always have a token of each that close (two ends `gap` apart, or a shared position), so a pair never that close rules the NEAR out. Pairs no NEAR asks about, words outside the rule set's, and windows wider than eight are left to the full match. A join's compound sits at the previous word's first position but is seen after that word's later parts (a joined camelCase word like `xYz-dl` or `eAC-3` splits), so the scan keeps occurrences three positions further back than the window. A property test holds what it records to the tokenizer's own positions, every pair within the window at most that far apart; others pin compounds, pairs no rule asks about, and recording on hostile names. (The self-review found the first version kept none further back, which missed joined camelCase words.)
- **Words and prefixes anywhere are answered from the distinct token texts** where that decides them (a whole form or the one part there, or a part missing), so a negation no longer tokenizes every path.
- **Switched-off rules are left out of the index.** A switch changes the list, which rebuilds the index, so marking no longer reads a switch per rule. A bit filter in front of the key map spares the map most of a torrent's texts, which no rule names.
- **Less work per torrent:**
  - The key scan adds a token text's starts and lowercase copy only when the text is new, and remembers eight folders (four deep), so a season's episodes and subtitles, which alternate between two folders, no longer rescan the folder name for each file.
  - The core remembers four folders' tokens the same way (property-tested against reading every path whole), and keeps its buffers between torrents.
  - The vocabulary starts with room for a typical torrent's texts.
- **Hostile names stay near-linear (§6):**
  - **Phrases** looked up each next word by scanning the whole text, so a name repeating a word thousands of times cost its square. A tokenized text now keeps its tokens by position (a counting sort, built once on first use), and a phrase looks each next word up there.
  - **NEAR** lists each word's places once, in order, and every place of the first word finds the nearest place of every other word by binary search: the text's length times its logarithm, whatever the slop (at most 50). Before, the windowed search sorted the text's tokens again for every rule, and scanned each window.
  - **The key scan of non-ASCII text** read each position's tokens by scanning them all; it now reads runs of a sorted list.
  - **Hash collisions in the vocabulary** are chained, so a crafted full 64-bit collision costs its own chain rather than a scan of every text. The tables themselves still use the unsalted term hash as their bucket hash (`IdHasher`, unchanged here), so a name crafted for colliding low bits can slow their inserts; seeding that hasher is a follow-up.
  - **Bounds are tested by counting steps, not time** (`crate::work`, compiled away outside tests): on names four times as long, phrases, NEAR and the non-ASCII scan take about four times the steps, and under 40 n log n. The previous phrase and NEAR search is kept as a test reference, and a property test holds the new one to it.
- **Not changed:** what any rule matches. The compiled matcher's reference property test and the new ones pass unchanged.
- **Not covered, left to the full match:** NEARs wider than eight positions (`words + slop - 1`), NEARs and phrases in `title:`, and fuzzy words and prefixes in `title:`. Each costs a full match per torrent that has its words.
- **Follow-ups (not in this slice's files):**
  - §20.8's "How the rules stay cheap" doesn't describe gates or the position index yet; this file does.
  - The only fuzz target reaching the filter (`lists`) exercises the core, not rules, NEAR or phrases. A rules fuzz target would need `fuzz/`, which this slice doesn't own.
