# IMP-5 decisions: imported records out of crawl-yield Insights; import annotations

Imports add thousands to millions of records in minutes. They aren't crawl discoveries (§10.9.3; IMP-4's "Imported cohorts keep their origin"), so this slice keeps them out of every crawl-yield series, counts them apart, and annotates the trend so a step is explained, not hidden. No schema change: everything reads V13's tables and the `events` table as they are.

## What already held (confirmed, with tests)
- **The import write path writes no rollup and no cohort.** `commit_import_batch` touches records, membership, quality, provenance, filter hits and the job; nothing in `rollup_*` or `cohort_*`. Test: `an_import_writes_no_crawl_rollups` (`crates/store/tests/import_insights.rs`).
- **The Searchable stage, end-to-end yield's numerator and time to searchable were already crawl-only.** `record_searchable` counts an imported id in `NEWLY_SEARCHABLE` under `key` 1 and in `insights_state.imported`, and never in the Searchable cohort stage or the delay histogram (B11a). Discover's harvests and Understand's `STORED` rollup are written by the crawler's pipeline only.

## A gap this PR doesn't close: the start-time refetch of partial imports
- **At each server start the pipeline queues up to 50,000 `FILES_PARTIAL` hashes (imports with incomplete file lists) for re-fetching** (`crates/pipeline/src/lib.rs`, `strategy::REFETCH`), under a cohort of the start hour.
- **Those fetches go through the funnel like a crawl's:**
  - the worker records PeerFound and Fetched;
  - the coordinator records the losses;
  - the writer records Stored, even when the row is `Existing`.
- **So the start hour's cohort shows fetched, stored and lost counts with no matching harvest** (the restored lease records none). `stages.fetch` and the Fetch stage's trend (`FUNNEL_EVENTS` `Fetched`) count them too.
- **Yield isn't inflated:** the numerator, cohort Searchable, never counts an import. Conversions and loss shares for that hour are skewed.
- **The fix is in the pipeline,** which this slice doesn't own: skip funnel recording for `REFETCH` leases, or give them a cohort the funnel doesn't read. The runner decided (option 1) to land IMP-5 with the gap recorded here and queue the follow-up slice **B-refetch-funnel**: `REFETCH` leases skip funnel recording in the worker, coordinator and writer, with a test that a refetch moves no cohort or `FUNNEL_EVENTS` row. Until it merges, these events land in the start hour's funnel.
- **Removing an import never rewrites a final cohort** (§10.9.3): imported rows have no cohort, and the delete trigger only adds to `REMOVED` by event time and takes the row off `insights_state.imported`. Test: the removal half of `an_import_annotates_its_start_finish_and_removal` compares every cohort row before and after.

## What changed
- **"New searchable" is crawled only.** `kpi.new_searchable`, `trend[].searchable`, `previous.kpi.new_searchable`, `segments.by_content_type`/`by_group`, Understand's `newly_searchable` and type lists, and Index's `new_searchable` (KPI and trend) now read `NEWLY_SEARCHABLE` key 0 only. This reverses `docs/metrics.md`'s "imports included" for `kpi.new_searchable`, as the brief asks: an import's million records would otherwise read as a crawl spike in the headline number and its delta. The contract doc is updated in this PR.
- **Imports get their own fields, additive only:**
  - `kpi.new_searchable_imported`, `previous.kpi.new_searchable_imported`, `trend[].searchable_imported`;
  - Index's `kpi.new_searchable_imported` and `trend[].new_searchable_imported`;
  - `kpi.searchable_crawled` = `kpi.searchable` − `kpi.imported` (at least 0), so the client never subtracts (standards §4). "Searchable torrents" stays the whole index, split into "Crawled" and "Imported".
- **The mechanism is the existing key split, read apart.** No new counter and no extra write: the overview reads `NEWLY_SEARCHABLE` by (hour, key) and (dim, key) instead of by hour and by dim (a new `RollupBy::DimKey`), and sealed and compacted days by (day, dim, key). The ingest path is unchanged, so its cost is 0. The read reads up to twice the `NEWLY_SEARCHABLE` rows, a small part of what an overview reads.
- **Measured** with `a_year_of_rollups_answers_within_budget` (`cargo test --release -p lodestar-api --test insights a_year_of_rollups`), its fixture now holding imports in every hour (the worst case for the split), against `main` with the same fixture. The figures are below. The §3 budget is +≤ 5% p95 on reads and −≤ 2% on ingest; ingest has no new work.

**Result (2026-10-31, a shared cloud runner, release build):**

- **Ingest does no new work:** the write path is unchanged. The import transitions write one `events` row each, and removal steps one row update.

## Annotations (§10.9.2's events)
- **The store writes them in the job's own transaction,** into `events`, so they're as durable as the transition and need no reader of the job table at request time. Codes (persisted, append only), after `lodestar_pipeline::event`'s 1–5:
  - `6` `import_started`: the job moved past `ready` (phases may skip forward, so one change can write both `6` and `7`);
  - `7` `import_finished`: it stopped writing records, by moving to `indexing` or by being cancelled or failed after it began. Completing after indexing writes nothing more: the records were all written at `indexing`, and that's when the step starts once the server indexes them;
  - `8` `import_removed`: its records were taken back.
  - **`lodestar_pipeline::event`'s next code must be 9.** That file belongs to another slice; a unit test in `crates/api/src/insights.rs` asserts the import codes come after the pipeline's last one.
- **`detail` is `key=value` words, from the job row:** `job` and `source` always; `new` and `merged` on `import_finished` (the job's counters then); `removed` on `import_removed`. The API parses them into `annotations[].import {job, source, new, merged, removed}`, null for other kinds, and keeps `text` as the raw detail.
- **A removal in many steps is one annotation.** The first step that deletes a torrent inserts it, at that step's time; later steps within the hour add to its `removed`. A removal resumed later starts a new annotation, so each `REMOVED` spike has a marker near it. A step that only drops provenance or candidates writes nothing: it changes no Insights series. `remove_import_job_records` takes no time argument, so the event is stamped with SQLite's `unixepoch()`, as the delete trigger stamps `REMOVED`.
- **Pause and resume aren't annotated:** they don't change what's in the store.

## Novel against already known (master plan H3)
- **`import_finished` carries `new` (records the job stored new) and `merged` (records the store already had, merged as provenance).** That's the overlap an operator needs after importing into a data folder that already crawled. Test: an import of four records, one already crawled, annotates `new=3 merged=1`.

## The gate counters (master plan F14)
- **Confirmed, no code change: imports never reach `metadata_new_verified_total{origin="network"}` or `searchable_new_total{origin="network"}`.** `lodestar import` writes through `Store::commit_import_batch` in its own process with the server stopped (IMP-4b), never through the writer that feeds `GateStats`. A later network fetch of an imported torrent is `Inserted::Existing`, which the writer counts as `already_stored`. Test: `a_fetch_of_an_imported_torrent_is_not_new_to_the_gate`.
- **`origin="import"` and `"recovery"` stay reserved and unrendered** (`docs/metrics.md`): nothing in the server process counts them, and a series that's always 0 would read as "no imports". The import's own counts are its job's, on the annotation. When a later slice routes imports through the running server's writer (IMP-4b's "Left to a later slice"), it counts them under `origin="import"` and renders the series then.

## What the screens should show (the UI follow-up)
- **Overview KPI "Searchable torrents":** the total, with "Crawled" and "Imported" beneath it (`kpi.searchable_crawled`, `kpi.imported`).
- **"Searchable torrents" Δ (`kpi.searchable_delta`) isn't split:** it's the whole index's change, imports included. When an `import_finished` marker falls in the range, say the change includes an import.
- **"New searchable in range":** the crawled count. When `kpi.new_searchable_imported > 0`, a secondary line "+ N imported" (`formatCount`), never added into the headline or its delta.
- **Movement chart:** the crawl's line as now. Imports either as a separate, visually quieter series (`trend[].searchable_imported`) or not drawn, but never stacked into the crawl's line. Import annotations as markers: "Import started", "Import finished: N new, M already known", "Import removed: N deleted", with counts through `formatCount`.
- **Index stage:** "New searchable" crawled, with "Imported" beside it from `new_searchable_imported`. The removed series includes an import's removal, and the `import_removed` marker explains its spike.
- Strings go in Insights' `messages/{en,zh}.json`, worded per `docs/ui-glossary.md`.
