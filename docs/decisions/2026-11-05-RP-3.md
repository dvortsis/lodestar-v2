# RP-3 decisions: the packs API (PR to be numbered)

Plan `docs/plan/2026-11-04-v06-rulepacks.md` §4.3 "RP-3"; architecture §20.7, §20.8, §20.10, §20.11. Builds on RP-0 (`2026-11-04-RP-0.md`: versions, shadow, `upgrade::accept`), RP-1 (`2026-11-04-RP-1.md`: the corpora) and RP-2 (`2026-11-05-RP-2.md`: overrides). No migration; one new `settings` row. Any doubt was resolved as weakening.

## `GET /filters`
- **Per pack:** `version`, the pack's rules at the versions this build ships (`MW-4@1 MW-1@1 …`, RP-0's `Manifest::pack_version`; a pack has no number of its own), and `changelog`, the compiled-in `CHANGELOG.md`.
- **Per rule:** `version` (as built), `applied` (as this install accepted; null when not known or never applied), `pending` (the version in shadow), `action` (what applies now: the base action, or the override's where it applies), `base_action` (RP-2's `base_action`), `base_changed` (the override's `changed`), and the override.
- **The override's key is now `pack_override`,** not `override`, so it can't be read as one of the CSX-5 Override entries (`overrides`), as #465's review asked. Nothing in `web/` read it yet; RP-2's API test follows the rename.
- **`pending_pack_versions`:** each pending rule with its applied and pending versions, the combined recorded direction (null: no record), and the changelog entries after the applied version up to the pending one, newest first. **`pack_conditions`:** RP-0's `packs.*` labels and RP-2's unreadable-override labels, for the Filters & Safety notice. **`packs_seeded_over_rules`:** RP-0's report.

## Accepting pending versions (`accept_pack_versions {rules, versions?}`)
- **`rules` names pack rules or packs,** at most 22 (every pack and rule), and `versions` at most 22 too; a pack stands for its pending rules. A rule with nothing pending is 409 `not_pending`, an unknown id 400 `unknown_pack`, an empty list 400 `no_rules`.
- **Strengthening only when** every accepted version's combined direction is `widens` or `action-heavier`, nothing is in doubt for the rule (RP-0's `in_doubt`), and its shadow results agree (RP-0's `acceptance_strengthens`). Anything else, `narrows`, `action-lighter`, `mixed`, no record, a shadow disagreement, a state in doubt, or shadow results that couldn't all be read, is weakening: the effect warning and the password.
- **The password confirms named versions.** The assessment gives `pack_versions` (`RULE@version`); a confirmed acceptance must send them back as `versions` (400 `pack_versions_needed` before the password is read, as `held_needs_version` does). Apply reads the acceptance again under the store lock: one that weakens by then without the password, or whose versions aren't the ones sent, is 409 `changed_since_preview`.
- **The impact** (`pack_acceptance`, per rule): torrents only the new version holds, only the applied one, both with a heavier or lighter action, disagreements, and the holds left for review. The preview's `caught_30d` is what the accepted versions hold in the replay window. Its release counts stay 0: nothing is released.
- **Undo never undoes an acceptance** (RP-0): it isn't in `rule_set_prev`. The warning says so.

## Shadow results, from `filter_hits` (no pipeline change)
- **Ingest already logs both sides:** the pending version as a shadow hit of its rule where it holds, the applied version as an ordinary hit where the rule decides. Per torrent in the replay window, the heaviest of each is its `PackShadow`. The writer persisting `PackShadow` itself (RP-0 left it to RP-3) wasn't needed.
- **Only hits from while the shadow ran count, and that survives restarts** (self-review, blocking). `filter.packs.shadow_since` records, per pending `RULE@version`, the highest `filter_hits` id when the API first sees that version pending, at its start or after a change. Only hits with a higher id count. It's a row id, not a time, so pack state still keeps no time (§20.8), and entries for versions no longer pending are dropped. Until one is recorded, every hit in the window counts: a hold only the applied version made then reads as a disagreement, which is weakening. A first version anchored to process start or the first shadow hit (this PR's first head) lost the evidence at every restart, so a mislabelled `widens` with no shadow hits could pass without the password after a container restart.
- **What counts as shadow evidence** (runner, #478). For a pending `RULE@version`, its evidence is the rule's `filter_hits` rows in the replay window with an id above its `shadow_since` entry, read per torrent hash. A shadow hit is the pending version's side and an ordinary hit is the applied side. The edges:
  - **First seen pending before any hit:** the entry is the table's highest id then, 0 when it's empty, so every later hit counts.
  - **A restart:** the entry is kept; nothing is lost or re-anchored. The pipeline starts judging just before the API's start records a new entry, so the first moments of a new build's hits can fall before it. That's less evidence, never stale evidence.
  - **A store restored from Undo:** Undo never changes versions (RP-0) and `shadow_since` isn't in its snapshot. An Undo that switches the rule off drops its entry. One that switches it back on leaves it pending (restoring "on" records nothing, RP-0), and a fresh entry starts then. While the rule was off it logged no hits of either side.
  - **A downgrade:** nothing is pending (RP-0), so the entry is dropped. The upgrade back starts a fresh one.
  - **A pending version that changes** (a build with `MW-2@3` while `MW-2@2` waited): `MW-2@2`'s entry is dropped and `MW-2@3`'s starts then, so the older version's shadow hits never count as the newer one's.
  - **No entry yet** (a version first seen now): every hit in the window counts until the next change or start records one.
  - **Hit ids reused** (runner, #478, blocking). `filter_hits.id` isn't AUTOINCREMENT, so once the table empties (the 30-day purge on a store idle for a month) new hits reuse ids from 1, and "after the anchor" would drop them. So each entry also holds a fingerprint of the anchor's own hit row (FNV-1a over its columns; it records nothing of its own): `MW-2@2 <id>:<fingerprint>`. The evidence is in doubt when the anchor's row holds a different hit, which catches a refill past the anchor. It's also in doubt when the anchor's row is gone while lower ids exist, which catches a refill below it. An anchor that aged out takes every lower id with it, so that alone is no doubt. A version in doubt is recorded as `MW-2@2 ?` at the next change or start, and stays so until it's accepted with the password or the pending version changes. (The runner's rule, `max(id)` below the anchor, is the second case; the first was added because a table refilled past the anchor between two checks would pass it.)
  - **A `shadow_since` row or line that doesn't read** (runner, #478, blocking): every pending version without a readable entry is in doubt, and is written back as `?`, so the evidence lost with the row is never treated as none. It's reported in `pack_conditions` as `packs.shadow-unreadable`, together with any `?` entry. A version in doubt makes its acceptance weakening.
- **Shadow agreement can hold with no evidence, by RP-0's design:** an acceptance seconds after the start, or of a version whose torrents haven't come by yet, has nothing to disagree with. The recorded direction then decides, and RP-1's corpus in CI checks that record against examples.
- **An applied hit counts as the applied versions' own action.** It means they matched, whatever action an override gave it, so the comparison is of the base rule's two versions, as RP-2 says. A heavier override no longer reads as a disagreement.
- **Shadow hits are kept.** This PR's first head deleted accepted rules' shadow hits so that the next version wouldn't read them (runner-accepted). The recorded start id excludes them anyway, so the deletion is gone and `filter_hits` keeps its replay-window counts.
- **Only rules that are on are pending** (self-review): a rule or pack that's off runs no shadow, and switching it on records its current version (RP-0), so it's left out of `pending_pack_versions`, the per-rule `pending` and acceptance (409 `not_pending`).
- **Known limits, each failing toward weakening:** the applied side is only seen where its rule decided, so an applied-version hold under a stronger rule's decision is invisible (that torrent stays held by the stronger rule); holds logged by the unverified-retry and enrichment paths carry no shadow hit and read as applied-only; more than 1,000,000 hits of one rule, or a hit whose action doesn't read, puts the results in doubt.

## The review queue
- **Holds acceptance leaves for review:** for a weakening acceptance, each quarantine or tombstone row of the accepted rule whose hash has no shadow hit (the new version isn't shown holding it). A strengthening one leaves none: its record and shadow say the new version holds what the old one did. A hold with no shadow evidence is listed too: one older than the shadow, or a hybrid torrent's second swarm hash (hits are logged under the first). Listing more only asks for a look; it releases nothing.
- **Written before the acceptance it's for** (runner, #478). The acceptance writes in a transaction of its own inside `crates/filter` (`upgrade::accept`), which this slice doesn't own, so the two can't share one. If the review write fails, nothing is accepted. If the acceptance then fails, the row is put back as it was. Either way nothing is released.
- **Stored in one `settings` row,** `filter.packs.review`, one `RULE-ID <hash>` per line, newest first. No time, author or reason (§20.8); not in Undo. `GET /filters/queue` and `GET /filters/tombstones` entries gain `pack_review`. Accepted by the runner on #478.
- **A hard cap of 200,000 lines,** written and read: as many holds as one acceptance reads (100,000 quarantine and 100,000 tombstone rows), so one acceptance never loses a line to it. A longer row, however written, reads only the first 200,000 (runner, #478).
- **A row that doesn't read fails closed** (#357; runner, #478): nothing is marked for review from it, the queue and tombstone pages and every change keep working, and every hold stays held, because the row only ever marks holds and never releases one. It's reported in `pack_conditions` as `packs.review-unreadable`, and the next acceptance that leaves holds for review replaces it. A line that doesn't read, or lines past the cap, are reported under the same label rather than dropped silently.
- **The warning gives the number actually marked.** When there are more holds than one acceptance reads (100,000 of each kind), it says that those past them stay held but aren't marked.
- **Pruned at every start, and after a change that can end holds** (a release, *False positive*, *Confirm*, an acceptance, Undo, or any change that released holds), to the holds that still exist. A hash nothing holds (an expiry or a purge) stays in it at most until the next start, and no page lists it meanwhile. Pruning is best effort: it runs after the pack conditions are recorded, and its failure never fails a change. It's skipped when the holds can't all be read at once (over 100,000 of either).

## Re-confirming an override (`confirm_pack_override {rule, base?}`)
- **The stored override's action and `unless`, bound to the version that applies now,** through RP-2's `set_pack_override` path: weakening exactly when the override weakens the rule as it now is (a paused one always does), then the password and `base` (`pack_override_needs_base`, `changed_since_preview` when the base moved). One that weakens nothing (a strengthening override whose base changed) needs neither. Only a changed override can be confirmed (409 `pack_override_current`), and only one that reads (409 `pack_override_unreadable`: set it again in full). It's in the Undo snapshot, as setting one is.

## `GET /filters/fixtures`
- **Gains `packs`:** RP-1's report against the engine's manifest, per rule its version, must-match and must-not-match counts, failing examples, versions whose recorded direction the corpus doesn't show (`direction_disagreements`) and known gaps (`gaps`), plus the precision corpus's size and failures, `failures` as readable lines, `passes`, and `error` when the corpus doesn't load. Known gaps don't fail `passes`, as in CI; they show per rule so RP-6 can show them. The built-in manifest's report is fixed for a build, so it's run once and cached. The core part is unchanged.
