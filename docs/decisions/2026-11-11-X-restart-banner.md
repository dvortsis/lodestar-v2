# X-restart-banner decisions

The restart banner, Restart now and the restart flow (§10.10.6) in `web/`. The backend was already built.

- **Review shows saved values only.** `GET /system` sends `restart_required` as field names, and `GET /settings/{section}` sends the saved value; no endpoint sends the running value. Review lists each pending field with its label and saved value and says it applies after the restart. Nothing is invented. A `running` value on `SettingValue` would need a Rust change; if the owner wants the two-column view, that is a follow-up slice. A secret shows "set", never its value. Refines §10.10.6's "running and saved values"; flagged to the owner (§2.19).
- **The banner is not in any Settings first view** (runner, 2026-11-11: no first view over 45 KB). The Settings shell carries one empty `<div id="restart-slot" class="contents">`. The chrome's restart watch (started after the first interaction, or 30 s after load) asks `/system` (every 15 s on a Settings screen, once a minute elsewhere), and when a change waits for a restart it loads `RestartBanner.svelte` and mounts it into that slot, again after each visit to Settings. One slot in the shell covers every Settings screen and the Overview, so the Overview needs no mount of its own. The banner can therefore appear a moment after the screen shows (once the page has been used). The slot reserves no space (`contents`) and the banner mounts as one unit; its polite live region is in the page empty and gets its text on the next frame, so a screen reader announces it.
- **Review's list, the dialog, the Restarting page and "Keep this address?" are further on-demand chunks** behind one `door.ts`, so the banner carries one small preload list. The count in the banner goes in as a plain whole number, not through `$lib/format` (0.8 KB gzipped the Settings views don't otherwise carry). Counts above 999 can't occur in practice.
- **Budget (`web/.size-limit.mjs`, runner-approved shared edit, flagged to the owner under §2.19).** The slot adds about 20 B to a Settings first view; only the Filters screen's limit moves (31.14 → 31.2 KB, +20 B measured; accepted by the runner under §2.26). Two new on-demand entries, measured beyond a Settings section's first view: "Restart banner (on demand)" 3.15 KB, limit 3.5 KB; "Restart flow (on demand)" 26.59 KB (the dialog, Review with the form engine it reads, the Restarting page, the prompt), limit 29.3 KB; both measured + ~10%.
- **The status pill's "Restart needed" shows over the calm states only** (crawling, idle, paused). A stall, a rebuild, a failed rebuild or a lost connection still win, because they need attention sooner. The pill asks `/system` once a minute; the Settings banner shares the same store and refreshes every 15 s, on focus and on each Settings navigation.
- **Waiting for the server.** The first `/healthz` probe waits 1 s, then backs off 1 s × 1.5ⁿ up to 5 s, and gives up at 2 minutes. An answer counts as the new run once the server was seen down, or, when it never was (a fast restart), once `GET /system`'s `started_at` has changed, so the old process still shutting down isn't taken for the new one. If `restart_required` is still non-empty after the reload (an environment variable pins a value), the page says so and offers Reload.
- **The HTTP address follows the backend.** The dialog shows `address_change.url` while the state is `awaiting_restart`. After the restart the page probes the new origin's `/healthz` (an opaque `no-cors` answer is enough), then goes to its `/settings`, where `awaiting_confirmation` shows "Keep this address?" with the countdown from `deadline`, Keep (`POST /system/address/keep`) and Go back (`POST /system/address/revert`). A revert that answers `restarting: true` returns the UI to `previous_url` through the same Restarting page. This matches §10.10.6: the backend's states are `awaiting_restart`, `awaiting_confirmation` and `reverted`, and the timer is the server's.
- **The e2e spec is `web/e2e/restart.routes.test.ts`,** not `restart.spec.ts`: no Playwright project matches `.spec.ts`; `*.routes.test.ts` runs in `core`. The give-up runs on Playwright's test clock.
- **A restart in progress belongs to the store, not to the dialog that began it** (found in self-review). A refresh that finds nothing pending any more must not unmount the Restarting page before it reloads, so `restart.waiting` holds it and pauses `/system` refreshes while it is set. When the countdown reaches 0:00 unanswered, the UI hands over to the Restarting page on the previous address, because the server reverts and restarts by itself.
- **A server that binds every interface sends a placeholder, not a URL** (`http://<this host's address>:9000/`, or `0.0.0.0`). The UI replaces it with the host the browser reached it by, for the dialog, the prompt and the probe. With a new address and no `started_at` to compare, an answer counts only once the old address was seen down or the server's own estimate has passed.
- **The Restarting page is a modal:** it moves out of the page's `<main>` to the body and makes everything else `inert` while it shows.
- **Outside the brief's "Owns", for the status pill's new state, named in the PR for the runner to confirm:** the shell messages (`shell_status_restart*`), `Chrome.svelte` (one effect starting the `/system` watch), `status.ts`, `status.svelte.ts` and `shell.test.ts`.
- **The e2e harness answers `/system` with nothing pending by default** (`web/e2e/support/test.ts`, a shared file; runner-approved, kept to that one default). The documented `/system` example lists a change waiting for a restart, which the pill now shows as "Restart needed", so the shell specs that expect the crawler state failed on it. The restart specs set their own `getSystem`.
- **Follow-ups:** the banner learns of a save within 15 s (a hook in the form's save path would make it instant); "Keep this address?" shows on Settings routes only.
