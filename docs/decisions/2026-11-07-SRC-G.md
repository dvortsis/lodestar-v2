## How the suite tests it
- **Real plugins, real pipeline.** Each plugin runs on its own recorded fixture through `FakeCtx`, with no network, exactly as its contract tests run it. A relay then hands its finds, unchanged, to a real `Pipeline`, filter and store. The relay keeps the plugin's manifest (id, kinds, `finds_private`, `always_adult`). It opens only the consent class and the default switch so it runs; consent has its own test on the real manifests. The fixture harness is in `crates/sources-plugins/tests/support/plugins.rs`, which the bench includes too.
- **The plugin kinds.** There are nine:
  - Academic Torrents, Internet Archive, Nyaa and Sukebei (feeds);
  - Prowlarr, with a public and a private indexer;
  - qBittorrent and Transmission (the download-client lister);
  - the full scrape (keys only);
  - the Sonarr/Radarr webhooks (each parsed body goes through the plugin's own mapping).

  The DHT has no fixture, so its own test relays key-only finds under its real manifest: a floor hash is refused at intake and never reaches a peer finder, and a clean key does. The three enrichment kinds (torrent cache, ThePornDB, StashDB) answer lookups about keys already found, so they find nothing to inject. Their blocklist paths are covered where they live:
  - `crates/pipeline/tests/torrent_cache.rs`: `a_cs_pattern_name_is_held_never_stored`, `a_name_your_rules_drop_is_held`, `a_key_on_the_floors_hash_list_is_refused_before_preparing`, `a_hold_added_after_a_key_was_queued_refuses_it_as_held`.
  - `crates/pipeline/tests/adult_enrich.rs`: `the_refile_sweep_judges_enrichment_claims`, `a_held_swarm_hash_is_never_looked_up`, `a_core_held_item_with_a_perfect_match_stays_held`. The enrichment runtime isn't wired (ENR-G).
- **The injection is drawn from each plugin's own finds.** Its first key goes on the floor's hash list. The first other find with a two-word name becomes a core pattern hit (its two words become the stand-in child-role and sexual terms). Every other key is the clean control.
  - **The floor hash is refused at intake** in both rounds (the intake count covers every floor find) and never stored; the floor is the permanent hold.
  - **The named key is held:** quarantined under a `CS-` rule, with the name kept only sealed.
  - **A second sighting of each is refused.**
  - **The clean keys are stored as unverified items** and never as torrents, so nothing was promoted.
  - **A user Drop rule added after storage** removes the first clean key, and any other clean key its word names. The test adds that rule only once every find is with the writer, so only the re-judge sweep can apply it.
  - **No check is silently skipped.** Every kind must give a name to block, a clean control and a rule word, or the test fails. The one exception is the full scrape: its finds are keys only, so it gets the floor hash and the clean control but no name block and no re-judge.
  - **Webhook fixture:** the recorded bodies repeat two keys. A third is the download body re-keyed in the test.
- **No fixed sleeps.** Every wait polls a condition for at least 10 s, and the plugins run on a paused clock. The blocklist test was run 30 times alone, then 30 times as six copies at once on four cores, with no failure.

## `private_source`: the outputs and the lookups
- **New in this gate:** a key found only by a private source (the download clients, the webhooks, Prowlarr's private indexer) is stored with `private_source` and `claims_private`, and keeps no tracker and no outside link. One private find in each private kind is given a tracker and a details link before it's relayed, so that check can fail; `crates/pipeline/tests/claim_trackers.rs::a_private_finds_external_ref_and_trackers_are_not_stored` pins the same rule at the writer. It never reaches a public peer finder, whether it came with claims or bare. A spy peer finder in the real pipeline records every key it's asked about. The public control key is sent only once intake has taken every private find and handed the bare sightings to the pool. The control then reaches the finder, and none of the private keys did. A public indexer's finds from the same manager stay public.
- **The outputs, each already filtered on the stored flag and tested.** This gate shows plugin finds arrive with that flag:
  - RSS feeds: `crates/api/tests/alerts.rs::the_feed_shows_shown_public_alerts_with_magnets`, `crates/api/tests/provenance.rs::a_feed_never_names_a_source`, `crates/integrations/tests/rss.rs::a_caller_cant_leak_a_private_item_through_the_renderer`.
  - Notifications (ntfy, Discord, email, outbound webhook): `crates/integrations/src/notify/mod.rs::private_items_are_withheld`, `webhook.rs::delivers_the_versioned_payload_without_private_items`.
  - Send to client: `crates/api/tests/send.rs::only_visible_torrents_are_sent_each_with_its_result`.
  - Export: `crates/api/tests/export.rs::what_search_hides_and_private_sources_are_never_exported`, `crates/api/tests/provenance.rs::an_export_carries_no_provenance`.
  - Keys and tokens never reach search or provenance: `crates/api/tests/provenance.rs::keys_and_tokens_never_reach_provenance`. There's no guest or shared view.
  - Logs: at the default preset no key is printed, in either case of hex (`log_scan.rs` checks every key the plugins found).
- **The public lookups:**
  - DHT `get_peers` and announce: `crates/sources/tests/pool.rs::private_keys_never_reach_peer_finders`, and this gate's pipeline test.
  - Partial refetch at start: `crates/pipeline/tests/refetch_private.rs::private_partials_never_reach_public_peer_finding_across_a_restart`.
  - The torrent cache: `crates/sources-plugins/tests/torrent_cache.rs::no_lookup_exists_for_a_private_key`, `crates/pipeline/tests/torrent_cache.rs::the_cursor_never_offers_a_private_source_key`.
  - Adult enrichment: `crates/pipeline/tests/adult_enrich.rs::no_ineligible_item_is_ever_handed_to_a_plugin`.
  - Tracker scrapes: `crates/store/tests/swarm.rs::lanes_skip_private_torrents`.
  - Trackers and outside links aren't stored for private finds: `crates/pipeline/tests/claim_trackers.rs::a_private_finds_external_ref_and_trackers_are_not_stored`.
- **NOT-YET-BUILT: Torznab and Stremio.** Neither is routed. `torznab_and_stremio_outputs_are_not_built_yet` fails as soon as either is routed in `crates/api` or `crates/lodestar`, until that slice adds its leak test and lists it there.
- **Observations, not failures (for the slices that own them):**
  - **PEX:** the extended handshake always advertises `ut_pex` (`crates/peer-wire/src/message.rs:59-64`). Lodestar never sends PEX, and the peers it receives are unused. A private key is never fetched from a public peer, so nothing private is shared. BEP 27 still asks a client not to advertise PEX for a private torrent. That's a peer-wire change (#579's paths, outside this slice).
  - **Hash log kind:** with the time-limited, opt-in "hash" kind on, `pipeline.lease_missing` (Warn) prints a key whatever its source. The user chose to see hashes, so this is within §12.1. Hiding private-source keys even then would be a logging refinement.
  - **Notifications:** nothing builds alert notifications from the store yet. Whoever wires them must map `PRIVATE_SOURCE` into `NotificationItem::private_source`, and should add an end-to-end test.
  - **Health interest gate:** its test (`crates/pipeline/tests/health.rs`) uses `REMOTE_UNVERIFIED`, not `PRIVATE_SOURCE`. Both are in `flags::PRIVACY`, so the code covers it. A `PRIVATE_SOURCE` case would pin it.

## Consent
- **New in this gate:** every plugin in `catalogue::manifests()` (11 manifests) is registered with its real consent class. The test does four things:
  - It seeds each source Enabled first, as an earlier build or a restored backup could. About half are seeded under an older plugin version (`0`), so the start after an upgrade is checked too.
  - At the start, every source whose class isn't None is switched off before it runs.
  - Each such source is then refused `enabled: true` through `Control::update_source` for every consent class named, every version (none, empty, the current one) and with or without the password. Nothing is written.
  - The None-class webhooks stay on. For each class that acknowledges a text, an acknowledgement of the previous `text_version` doesn't cover the manifest, so it asks again.
- **The other paths, already tested:**
  - **PATCH through the router:** `crates/lodestar/src/ops/tests.rs::no_class_can_be_enabled_past_its_condition`.
  - **The real binary:** `crates/lodestar/tests/consent_gate.rs`.
  - **First registration in one write:** `crates/pipeline/tests/control.rs::first_registration_is_one_write_so_a_crash_cant_leave_a_gated_source_on`.
  - **A start after a stale or changed acknowledgement:** `control.rs::a_restart_switches_off_a_source_whose_condition_no_longer_holds`, `ops/tests.rs::a_restart_ignores_a_stored_acknowledgement_and_a_new_text_asks_again`.
  - **A changed address list asks again:** `crates/sources/src/consent.rs::a_new_text_or_endpoint_list_asks_again`.
- **Settings import and the config file can't reach a source's state.** Import reads only registry sections, and none has a source key (`crates/lodestar/src/settings/portable.rs`). The config file only adds or leaves out the DHT (class None, `dht.enabled`). There's nothing to bypass there. The settings-import case is covered by `crates/lodestar/src/ops/tests.rs::no_class_can_be_enabled_past_its_condition`.
- **A manifest version bump alone doesn't ask again**, and it shouldn't: an acknowledgement covers the class, the text version and the address list (`consent::version`), which is what the user was shown.
- **Hardening note for whoever owns `crates/store/src/sources.rs`:** `update_source_secrets` accepts any `Option<SourceState>`, `Enabled` included. Its only caller passes `Disabled`, and the start switch-off would catch any slip. A guard like `set_source_state`'s would make the store refuse it itself.

## No profiles
- **Schema:** every table and column of the latest schema is checked for address-like names (ip, addr, peer, port, node, endpoint, remote, client, user and similar). Each allowed exception is named with what it holds:
  - `swarm.dht_peers` and `swarm.dht_seeds`: aggregate counts;
  - `user_items`: the operator's own marks on torrents.

  A new column with such a name fails the test until it's reviewed and listed. `source_state.value` is an opaque plugin blob. No plugin in `crates/sources-plugins` stores a peer there (their state is cursors and last-attempt times), but a schema check can't see inside it.
- **Logs:** the test runs in its own binary (`tests/log_scan.rs`), because the sink and the event switches are global to the process. It installs a capturing sink and turns on every event the pipeline, filter, DHT, peer wire and integrations declare. It then relays every plugin's finds plus one key fetched from a refusing local peer. Every record is rendered with every kind except the opt-ins shown, peer addresses and hashes included. No line shows the peer beside a torrent; the failed fetch shows the hash and `peer=[hidden]`. The real-binary canary (`log_canary.rs`) covers the outputs: file, ring, stream and download.

## The full scrape and `PrivateTrackers`
- **Unwired, as required.** The binary's code builds no `FullScrape`. The scan reads every shipped line of `crates/lodestar/src` (and of `crates/api/src`, for Torznab and Stremio). It leaves out only `#[cfg(test)]` modules, brace-matched, and a self-test checks that code after an item-level `#[cfg(test)]` is still seen. `StaticPrivateTrackers` doesn't appear in it, and the binary doesn't enable the plugins' `testing` feature. The test fails the moment `FullScrape` is built in `crates/lodestar/src`, unless three things hold: the binary has its own `PrivateTrackers` implementation, the settings text has the §2.37 wording, and the user guide has it too.
- **Blocker for wiring (owner §2.37):** neither text exists yet.
  - The settings description (`full_scrape::CONFIG_SCHEMA`) says "public trackers that allow a full scrape … Never a private tracker", but nothing about trackers whose published rules forbid scraping.
  - `docs/user/` doesn't mention the full scrape at all.

  The wiring slice must add both. **Proposed text** (runner, 2026-11-07, asked for exact sentences to copy):
  - **Settings description** (`CONFIG_SCHEMA`'s `trackers.description`): "Announce addresses of public trackers whose published rules allow a full scrape, such as https://tracker.example/announce. Don't add a tracker whose rules forbid scraping, and never a private tracker."
  - **User guide** (the full-scrape section of `docs/user/05-use-lodestar.md`, when the plugin ships): "Add only public trackers whose published rules allow a full scrape. Lodestar can't read a tracker's rules for you: if a tracker's rules forbid scraping, or you can't find them, don't add it. Never add a private tracker."
  - The test looks for "published rules" in the schema, and for "full scrape" and "published rules" (any case) anywhere under `docs/user/`. Whether the lookup fails closed (an error counts as private) is for the wiring PR's review; the test only checks that the binary has its own implementation.
- **A note for the store-backed lookup:** private finds' trackers are stripped before storage (`claim_trackers.rs`), so "does a private torrent list this host?" can't be answered from claims. The lookup needs its own record of private trackers, or it has to fail closed.

## The overhead benchmark
- **What it measures:** the real ingest path, as `examples/mem-ingest.rs` does: pool, fetch, prepare, writer and SQLite on disk, with the live search index following it, which is §3's "commit + index". It stores 20,000 synthetic torrents once alone, and once with every plugin kind's fixture finds flowing through the same writer. Those finds are re-keyed so each is new, at one claim per two torrents, into a store already holding 200,000 unverified items, so each insert pays the duplicate check against a full table. It takes the best of three each way, in release, in this sandbox (4 cores). The figure is the time until every torrent is committed and indexed.
- **The numbers** (torrents/s):

  | Run | Sources off | Sources on | Change |
  |---|---|---|---|
  | Commit only (before the review) | 1,262 | 1,176 | −6.8% |
  | Commit + index, run A | 1,266 | 989 | −21.9% |
  | Commit + index, run B | 1,178 | 811 | −31.1% |

  The breakdown (`sources_overhead_breakdown`, commit + index, best of three): off 1,088; 200,000 unverified items only (the duplicate check) 975; the claims only 1,111; both 1,041.
- **Reading:** this host measured the same "off" setup at 1,088 to 1,266/s, a spread of ±10–15%, with its baseline at the budget line. The duplicate check against a large unverified table may cost about 5–10%. The claim batches show no cost beyond the noise. No measurement here separates the effect from the noise, so the budget is **not decided**, rather than passed or failed. The runner has the numbers (2026-11-07). The ignored `sources_overhead` asserts the budget and should be re-run on the §2.20 reference CPU or the soak host before the v0.6 gate is closed.
- **Not a budget:** §3 sets no separate overhead percentage for sources; its "−≤ 2%" is the reporting overhead. The runner isn't setting one now (2026-11-07). The percentages are for information.
- **Search latency isn't measured.** No source writes to the search index in v0.6. Unverified items are indexed by SRC-3b, after v0.6, and the only search-side change is SRC-3's default `verified:yes` clause.

## e2e
- **Filename:** `web/e2e/sources-gate.routes.test.ts`, not the plan's `sources.spec.ts`. The Playwright config only runs `*.routes.test.ts`, `*.keyboard.test.ts` and `*.fixture.test.ts` (and a few named files), so a `.spec.ts` would never run. The `routes` suffix puts it in the `core` project with the OpenAPI mock.
- **What it checks:**
  - The External, Restricted, Overlay and Account sources each show their class and "Needs setup".
  - Their switch opens the class's dialog and sends nothing.
  - The None-class DHT has no consent badge and runs.
  - A source an earlier build acknowledged is sent to the server, and the server's `invalid_setting` refusal leaves its switch off, with "Nothing was changed."
  - An unverified result carries the Unverified badge and a verified one doesn't.
