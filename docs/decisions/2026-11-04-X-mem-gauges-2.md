# X-mem-gauges-2 decisions

The runner's follow-up to X-mem-gauges (#433, merged as `b4fb3f87`) before soak r5: three fixes from the merge review. These are still metrics and tooling only (delta class B/C). This file amends `2026-11-04-X-mem-gauges.md` only where it says so.

- **A negative SQLite count is absent, not 0.** `sqlite3_memory_used` and `sqlite3_memory_highwater` return a signed 64-bit count. #433 mapped a negative one to 0. That broke the slice's own rule: a gauge that can't be read is absent, never 0, because a 0 would read as "SQLite holds no memory". `lodestar_store::memstats` now returns `Option<u64>`, and a negative count leaves `mem_sqlite_bytes` or `mem_sqlite_highwater_bytes` out of `/metrics`. SQLite never reports one in practice, but a gauge that could show a false 0 shouldn't exist. The two `unsafe` reads and their `allow`s (owner-decisions §2.35) are unchanged.
- **The analyzer's refusal uses the gate's rows.** `memory_attribution` claimed to refuse a restart by the same check as `memory_fit`, but it built the process and identity sets from usable rows only. The gate counts every baseline row in the window, because a failed metrics read still names its process. A restart seen only in failed reads was refused by the gate and passed by the attribution section. Both now check the same rows: every baseline row for the process and its identity, usable rows for the start time. Only usable rows are fitted, as before.
- **The attribution table stays one table.** The "other heap is an approximation" note was printed between the other-heap row and the segment rows. That ended the Markdown table, so the segment rows rendered as stray text. The note now follows the last row.
- **Branch:** this PR's branch is `slice/X-mem-gauges`, restarted from `main` after #433 merged, not `slice/X-mem-gauges-2`. The session that builds it may push only to its designated branch. The PR title carries the `X-mem-gauges-2:` id the runner asked for.
