# ENR-12 decisions (detail API: "Identified as")

Slice ENR-12 (runner brief, 2026-11-12). Spec: architecture §6 and §10.5; `docs/decisions/2026-11-12-ENR-10.md` (what is stored, `ResolvedVia`, `stored_title`, the notes to ENR-12); `2026-11-06-ENR-9.md` and `-ENR-9b.md` (the v3 details, judged before storage); ENR-7's adult-enrichment section (#491) for visibility.

## The section
- **`identified_as` on `GET /torrents/{hash}`**, an `IdentifiedAs` with:
  - `alternatives`: each plugin's stored answer (canonical title, year, ids, alternative titles, genres, confidence, source);
  - `resolved_via`.
- **Absent, never null or empty, when there's nothing to show**, as `adult_enrichment` is. The OpenAPI property is a plain reference that isn't required. A caller can't tell from the field alone whether an answer exists.
- **Each plugin's row is one alternative**, the surest first, ties to the lower source id. That's `identify::stored_title`'s order.
- **`chosen` marks the answer whose title the record shows, and only when it does:** the stored record is resolved via a plugin, and this is the surest answer with a canonical title. Today ENR-10's own lookups never resolve a title, so no answer is chosen; marking the surest one anyway would tell ENR-13 that the title came from TMDB when it didn't (self-review).
  - It's decided over every stored answer before any is left out for this caller. So when the chosen one's source is withheld, no answer is marked: a caller never sees another answer promoted in its place. Its absence says only that an unshown answer exists, never whose.
  - Rows with an adult section are skipped. `stored_title` doesn't skip them, but a row can't hold both: the clamp and the mapping drop details beside an adult section (ENR-9b).
  - The API re-implements `stored_title`'s rule rather than calling it, because `lodestar-api` doesn't depend on the pipeline outside its tests.
- **An answer is ENR-10's own rule:** a claims row from a source whose bit isn't in the torrent's `sources` (it didn't find it), not through a private source, with a details section that holds a match confidence. A feed that found the torrent and sends a canonical title isn't an answer, so it never shows here.

## Visibility, stricter where unsure (brief requirement 1)
- **No section** when the torrent is any of these:
  - hidden;
  - held (a tombstone or quarantine on a swarm hash);
  - private in any way (`PRIVACY`: a private source, BEP 27, or a remote worker's unconfirmed private bit);
  - Adult by its stored type, or found by an always-adult source (see the gap below).
- **Why stricter than the detail view:** ENR-10 never looks those up, so an answer on one is stale, and Adult goes only through ENR-1's section (Q5). The Adult rule holds whatever "Show adult content" says, so a torrent classified Adult after it was answered never shows the answer. A `private_source` torrent therefore names no enricher at all.
- **Sources:** the admin session sees every answer with its source. Any other caller sees only answers from a source known to be public (`Catalogue`: not account class, finds not private, a plugin this build runs).
  - The rest are left out without a trace, as provenance leaves out private sources.
  - An account-class enricher's answer is the admin's only, as ENR-7 does for its Account-class services.
  - Today the route is session-only (§12), so only the admin reaches it. The public rule is unit-tested so that a later key-scoped route inherits it.

- **The always-adult rule fails closed** (runner, 2026-11-12). The detail route learns the always-adult sources only from the `DrawerInterest` extension. While the host hasn't installed it, the mask is unknown, not "none", so no torrent can be confirmed not to be an always-adult source's find, and **no "Identified as" section shows at all**. With it installed, a torrent an always-adult source found shows none.
  - **The gap this closes in the binary today:** the host doesn't install `DrawerInterest` yet, so its mask would have read as 0. An always-adult find is normally reclassified Adult (`adult_by_source`), and the stored-Adult rule covers that. Without failing closed, two cases would have shown: the window before that reclassification lands, and a torrent you marked Not adult.
  - **Follow-up X-always-adult-detail-mask** (runner): `always_adult` on `ops::Source` and the host side, before ENR-13 ships the drawer, so the section can show in the binary. Its reviewer checks ENR-7's section for the same gap. No `dto/ops.rs` or host change here.

## Stored text only (brief requirement 2)
- **Nothing is judged at read time.** Every text was judged before storage (ENR-9b), and the refile re-judges stored rows when the rules change.
- **Bounded again, defensively:**
  - lists cut to the stored caps: 32 alternative titles, 16 genres, 32 ids;
  - an alternative title with an invalid language or empty text is skipped;
  - ids kept only when `id_ok` accepts them, so only the closed schemes;
  - each text cut on a character boundary to its stored limit;
  - the confidence capped at 100;
  - a year outside 1–9999 dropped.
- **`resolved_via`** comes from the stored record, and only as a listed method (`ResolvedVia::ALL`: files, folder, structure). A stored `plugin` reads as null here (ENR-10, runner 2026-11-12). The answer that resolved the title is still shown, marked `chosen`. No `detail_via_plugin` or `labels.ts` entry; the slice that makes `plugin` fire adds them.

## rv-750's N6 and N7 (`pipeline/src/identify.rs`)
- **N6: `Config::lookup_timeout` is clamped** in `IdentifySource::new`, to between twice the plugin's own per-host interval (its `Policy`, floored as its client floors it; at least 1 s) and 5 min.
  - The floor gives a lookup time to wait for its first request's token and send it. A shorter timeout would expire in the token wait and charge a host that never got a request (self-review). With the default STRICT policy (one request per 10 s) the floor is 20 s.
  - 5 min is ample: a lookup is a few requests at the plugins' rate caps, and AniDB's one per 2 s is the slowest. A hung plugin holds the runtime no longer than that.
- **N7: a timed-out lookup is recorded as a failure in the plugin's client limiter** (`HostLimiter::record`), on each host in its manifest's endpoints. The client never saw an answer, so nothing else records it, and the host now backs off as any failing host does. This is what N3's backoff will build on.
  - **Only a host that's ready is charged** (self-review, blocking). A lookup that starts while its host backs off waits in the client's gate and sends nothing. Charging that host again would push the back-off out with every lookup, up to the 6 h ceiling, and no request would ever reach the host to clear it.
  - A plugin with no endpoints records nothing.
  - Charging every endpoint is stricter than charging the one host the plugin was waiting on, which the runtime can't know.

## Known limits (runner, review of #760)
- **`chosen` can go stale.** It reads the stored record, which the backfill rewrites. Between a new, surer answer and the backfill reaching the torrent, `chosen` marks the answer the record still shows, not the surest.
- **N6's floor** uses the plugin's policy as its client floors it with the default user limits. A host that sets slower user limits than that can still time a lookup out in a token wait. The ready-only rule then charges the host once, not on every lookup.
- **`resolved_via` null never means "from the name".** It's also null for a plugin's title and an unreadable record (the OpenAPI says so). ENR-13 renders every field as plain text with bidi isolation (runner, ENR-13's brief).
