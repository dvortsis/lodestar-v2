# X-filter15-fix decisions

FILTER-15, blocking: the store's write path for holds. The detail stays held under `docs/security/v1/README.md` §5.

## Calls
- **A held decision in a write deletes the stored torrent with the hold** (runner, by message). `Store::write` deletes every stored torrent under a hash a held decision covers, in the same transaction as the hold, and logs it for the search indexer. Every other hold path already did this.
  - `Written.deleted` returns the ids. A row the batch stored and then deleted is counted as blocked, not stored, and a sighting of one isn't a rediscovery.
  - Ids are never reused, so hot-column slots left behind are never read again, as with `delete_torrents`. The searchable-deleted rollup is the store's own delete trigger, so it counts these rows too.
- **A commit that fails keeps its holds.** The writer queues the holds the batch decided (not a promotion's, which its own transaction wrote) and writes them again through `Store::write`, one transaction each, so each deletes the stored torrents under its hashes. Every waiting hold is tried on each pass, so one that keeps failing never holds up the rest; only the failures wait out a backoff. It tries once more at a clean stop. A cache's holds that fail to write join the same queue. A waiting hold is replaced only by a newer one of the same kind, rule and adult flag whose hashes cover all of its own, so the same hold failing again keeps one entry. Any other hold waits beside it and both are written. Holds are never merged, so no hash is ever written under another hold's rule, kind or sealed name, and the store's precedence decides between them.
  - A hold queued for retry is written whatever happened since, a rule removed or an item released included: that errs on the safe side.
  - Known limit: the queue is kept in memory. A hold still failing at a clean stop, or one queued when the process dies, is lost. Its torrent stays stored until something judges that hash again: a refetch, the crawl or a source finding it, or a rule change's refile. The start-up sweep has already run once by then, so it doesn't catch it.
- **A hold in a write deletes every stored torrent under its hash**, whether the hash is a torrent's own v1 hash or another's truncated v2 hash. So do a retried hold, which goes through the same write, the start-up sweep, the claims and cache holds (`Store::hold_claims`) and the abuse delete (`Store::delete_torrents`).
- **A fetch under a hash held since it was judged is never stored** (runner, by message). The write reads the hold tables in its own transaction, one indexed lookup per swarm hash, for each torrent the pipeline fetched (`WriteBatch::prepared`). A held one is neither inserted nor merged into a stored row: it comes back as `Inserted::Held`, and the writer counts it blocked. So a hold another path writes after the writer judged a result, which the writer's set in memory doesn't know of yet, still keeps it out.
- **A held hash is never queued for a refetch.** `partial_hashes` leaves out a key held under either swarm hash, so held keys no longer take the start-up refetch's places.
- **A one-time sweep at start-up** (`Store::sweep_held_stored`) deletes every stored torrent under a hash that's already held, before the refetch queue is built. It walks the tombstone and quarantine tables in key order, 2,000 hashes per short transaction, so the write lock is never held for long on a store with a long history. The marker `store.held_sweep` is set with the last batch, so it runs to the end once and never again; a stop before that runs it again, which deletes nothing twice. It needs no schema change or migration.
- **How long a deleted row can stay in search.**
  - A results page (`/search`, Torznab) reads each hit's row from the store and leaves out one that's gone, so a deleted torrent never appears in a page served after the write returns.
  - Counts and facets read the index, which drops the document at its next commit: within the live indexer's commit interval (2 s by default), but only once the indexer has caught up with the store's re-index log. Under a backlog, that takes longer.
  - Typeahead's title suggestions are rebuilt at most every 60 s, or every ten build times if that's longer, so a deleted title can still be suggested until the next rebuild. Tightening that isn't in this slice.

## Not in this slice
- Other hold paths are outside this slice; the runner tracks them by id.

## Tests
- **Store** (`crates/store/tests/held_write.rs`):
  - a held write deletes the stored torrent under either swarm hash, and a decision that doesn't hold leaves it;
  - a partial row is deleted;
  - a write that fails after the delete keeps neither the hold nor the delete, nor a re-index entry;
  - `partial_hashes` leaves held keys out;
  - the sweep runs once, and covers thousands of holds across its batches;
  - the claims hold, the unverified refile and the abuse delete take both rows under a hash shared as one torrent's v1 and another's truncated v2;
  - a stale batch with a fetch held since judging marks only what it stored;
  - a fetch under a hash held since it was judged is neither stored nor merged.
- **Writer** (each fails without the fix):
  - a drop rule and a quarantine rule added since the torrent was stored, on a remote worker's result;
  - the built-in worker's CS-0a verdict;
  - a refetch of a partial import that the core holds;
  - a torrent newly found by an always-adult source;
  - a cache's file held at commit;
  - a promoted torrent held later;
  - a failed commit's holds written again, and a hold that keeps failing not holding up the next;
  - a hash held after judging, unknown to the writer's set, never stored;
  - the retry queue replaces a hold only with a newer one of its rule covering all its hashes, and the same hold failing again keeps one entry;
  - a newer hold under another rule never takes over a waiting hold's other hashes (a floor or kept hold, or one pattern rule under another).
  - a row the batch stores and its own hold deletes is counted blocked, and the have-filter never learns it.
- **Start-up** (`crates/pipeline/tests/held_startup.rs`): a partial row under a held hash is deleted at start and never refetched; a partial row whose refetched list is too large to judge is held under CS-0a and deleted. It fails without the start-up sweep.
- **Search** (`crates/api/tests/held_search.rs`): `/search` and Torznab leave the torrent out as soon as the held write returns; its count and facets follow once the index commits.
