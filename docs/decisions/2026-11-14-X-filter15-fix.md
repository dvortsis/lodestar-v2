# X-filter15-fix decisions

FILTER-15, blocking: the store's write path for holds. The detail stays held under `docs/security/v1/README.md` §5.

## Calls
- **A held decision in a write deletes the stored torrent with the hold** (runner, by message). `Store::write` deletes every stored torrent under a hash a held decision covers, in the same transaction as the hold, and logs it for the search indexer. Every other hold path already did this.
  - `Written.deleted` returns the ids. The writer doesn't count a sighting of one of them in the same batch as a rediscovery.
  - Ids are never reused, so hot-column slots left behind are never read again, as with `delete_torrents`. The searchable-deleted rollup is the store's own delete trigger, so it counts these rows too.
- **A commit that fails keeps its holds.** The writer queues the holds the batch decided and writes them again, one transaction each, with `Store::hold_claims`, which deletes the stored torrent too. It waits out a backoff after each failure, and tries once more at a clean stop. A cache's holds that fail to write join the same queue.
  - Known limit: the queue is kept in memory. A hold still failing at a clean stop, or one queued when the process dies, is lost. Its torrent stays stored until something judges that hash again: a refetch, the crawl or a source finding it, or a rule change's refile. The start-up sweep has already run once by then, so it doesn't catch it.
- **A hold deletes every stored torrent under its hash**, whether the hash is a torrent's own v1 hash or another's truncated v2 hash.
- **A held hash is never queued for a refetch.** `partial_hashes` leaves out a key held under either swarm hash, so held keys no longer take the start-up refetch's places.
- **A one-time sweep at start-up** (`Store::sweep_held_stored`) deletes every stored torrent under a hash that's already held, before the refetch queue is built. The marker `store.held_sweep` is set in the same transaction, so it runs to the end once and never again. It needs no schema change or migration.
- **How long a deleted row can stay in search.** A results page reads each hit's row from the store and leaves out one that's gone, so a deleted torrent never appears in a page served after the write returns. Counts and facets read the index, which drops the document at its next commit: within the live indexer's commit interval (2 s by default) once it has caught up with the store's re-index log.

## Not in this slice
- **An import over a stored torrent** (`crates/store/src/import.rs`) is reported to the runner, not changed here. Hash-rule holds on a stored hash belong to X-filter03-fix.
- **The suggested `store/src/filter.rs` and `crates/filter` polish from #857's review** is outside this slice's files. It's left for the slices that own them.

## Tests
- **Store** (`crates/store/tests/held_write.rs`):
  - a held write deletes the stored torrent under either swarm hash, and a decision that doesn't hold leaves it;
  - a partial row is deleted;
  - a write that fails keeps neither the hold nor the delete;
  - `partial_hashes` leaves held keys out;
  - the sweep runs once.
- **Writer** (each fails without the fix):
  - a drop rule and a quarantine rule added since the torrent was stored, on a remote worker's result;
  - the built-in worker's CS-0a verdict;
  - a refetch of a partial import that the core holds;
  - a torrent newly found by an always-adult source;
  - a cache's file held at commit;
  - a promoted torrent held later;
  - a failed commit's holds written again.
