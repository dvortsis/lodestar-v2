# X-utp-backoff decisions (the X-utp-backoff PR)

The follow-up to `2026-11-08-runner-followups-3.md` §2: the uTP retransmission timer backed off without limit across timeouts separated by progress, and the reset-on-progress fix was rejected because it breaks Karn's rule. Affects `crates/utp` only (the peer-wire transport, architecture §6); no wire format, setting or owner-set number changes.

- **Timeouts separated by progress grow the backoff only to 4× (`PROGRESS_BACKOFF_CAP = 2`), and never shrink it.** Consecutive timeouts with nothing acknowledged in between still double up to `MAX_RTO` (60 s), so a dead path backs off exactly as before. Only a round-trip sample from a first transmission resets the backoff (Karn, RFC 6298 §5). Why 4×: it stops the compounding on a lossy link (each lost resend used to double the next timer), while a round trip that jumps to up to 4× the old timeout is still outlasted by the next new packet, which then gives a sample. A bigger jump grows the backoff through consecutive timeouts, which the cap doesn't touch. The new Sim test `a_round_trip_jump_costs_few_retransmissions` bounds this: after the round trip jumps from 20 ms to 1.8 s, 20 one-packet messages cost at most 3 resends (2 in the test). Reset-on-progress costs 40 there.
- **A lost retransmission is fast-retransmitted from selective ACKs.** Each transmission now records its order among all our transmissions. The oldest unacknowledged packet counts as lost once three packets *sent after its latest transmission* are selectively acknowledged, whether or not it was a resend. Before, only first transmissions could be fast-retransmitted, so every lost resend waited for a backed-off timeout. Three duplicate ACKs still count only for a first transmission: they may answer packets sent before the resend. The selective-ACK count is now taken only when the ACK's hole is our oldest packet, which is the only case where the mask describes it. LEDBAT still halves at most once per round trip.
- **A timeout counts towards `MAX_TIMEOUTS` unless the peer answered with a window too small for our oldest unacknowledged packet.** It used to count only when the peer was silent, so a peer that kept sending (data or bare ACKs) but never acknowledged our data held the connection open for ever, resending at `MAX_RTO`. Now any timeout with nothing acknowledged since the last one counts, except when the peer was heard advertising a window smaller than that packet: that's flow control, and we keep probing, as TCP's persist timer does. The test is against the packet waiting, not a fixed one-MSS threshold, so a peer can't dodge the count by advertising a window that fits our packet but stays under the MSS. A peer that really keeps its window shut can hold a connection for as long as the application keeps its stream (a dropped stream still expires after `Config::linger`), as with TCP. Memory stays bounded either way (the send buffer).
