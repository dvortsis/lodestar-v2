# ENR-0 decisions (claim encoding version 2)

Plan `docs/plan/2026-11-04-v06-rulepacks.md` §3 and §4.3 (ENR-0); owner §2.37 (plan §5 Q2–Q5); architecture §18.5, §20.9. The layout is in the module docs of `crates/store/src/claims.rs`.

- **Version 2 is version 1 plus one optional section, and only that.** Bit 6 of `present` (reserved in version 1) says the adult-enrichment section follows the ids. The version byte must agree with that bit: a version 1 blob holding a section, or a version 2 blob without one, is refused. So each value has exactly one blob version, and the plain layer stays canonical across both. `decode_plain` reads both; `Claims::version` says which a value takes. Unknown versions (0, 3 and up) are still refused.
- **The writer emits version 1 whenever there's no section** (brief). Claims without enrichment keep the exact bytes, and so the hashes, they had before ENR-0. A golden SRC-1 blob generated from `origin/main` is committed in the tests and as a fuzz seed, and it decodes to the same value and re-lays to the same plain body.
- **What the section holds:** the service's scene id, an optional kind, title, studio name, release date, performer names, and `performers_truncated`. Nothing else:
  - **No performer id** (runner call, flagged under §2.19). It's the key that would link a person across items, which Q4 rules out. ENR-2b and ENR-3 keep names only.
  - **The studio's name only** (runner call). ENR-2b reads no studio id, and ENR-3's isn't needed.
  - **No birth date, description or other personal field** (Q3, Q5). A performer is a bare `String`, not a struct that could grow an id, and a test names every field of the section, so adding one fails to compile.
  - **`performers_truncated`** (runner call): the parsers degrade rather than spoil, so a cut list says so.
- **Caps** (named `MAX_*`, chosen to cover ENR-2b's and ENR-3's parser caps, so a parsed match always fits):

  | Field | Cap | Covers |
  |---|---|---|
  | Scene id | 1–64 ASCII letters, digits and `-`, `MAX_SCENE_ID` | ENR-2b's `MAX_ID` (64: letters, digits, `-`); StashDB UUIDs (36) |
  | Title | 1,024 bytes, `MAX_SCENE_TITLE` | the parsers' `MAX_TITLE` |
  | Studio | 256 bytes, `MAX_STUDIO` | the parsers' `MAX_NAME` |
  | Performers | 64 names, `MAX_PERFORMERS` | both parsers' default `max_performers` |
  | Performer name | 256 bytes, `MAX_PERFORMER` | the parsers' `MAX_NAME` |

  A caller that reads more performers than 64 keeps the first 64 and sets the flag (`lodestar_sources`' clamp does).
- **The scene id is only letters, digits and `-`,** the characters both parsers produce. ENR-7 builds the scene's link from it (StashDB's `link()` is the page URL and the id), so a corrupt or crafted stored row must not be able to carry `/`, `?`, `#`, `%` or `.` into that URL.
- **Nothing rides along beside a section.** Claims with an adult section hold no description, publisher or external ids: the encoder refuses them (`Limit("enrichment claims")`) and so does the decoder (`Malformed`). Without this, a mapping could still store a scene description in `description` (against Q3) or a performer id in `ids` (against Q4) on the same row. Enrichment results are their own `torrent_claims` rows under the enrichment source's id (plan §3), so they lose nothing. `lodestar_sources`' clamp clears those three fields when it keeps a section. The name, size, files, trackers and provenance stay allowed (ENR-4/ENR-5 may put the scene's page in `external_ref`).
- **Release dates may be a year, a year and month, or a full date** (refinement of the brief's `YYYY-MM-DD`, flagged under §2.19). StashDB states partial dates (ENR-3's `Date`); keeping only full ones would throw away a year it gives. `ReleaseDate` can only be built valid (year 1–9999, month 1–12, a real day of that month, a day only with a month), prints and parses `YYYY`, `YYYY-MM` or `YYYY-MM-DD` exactly, and is stored as 4 fixed bytes, so there's one encoding per date.
- **Kind is optional and one of scene, movie or VR** (plan §4.3, ENR-6). ThePornDB's answer can have no known type, so the kind can be absent. ThePornDB's `JAV` has no kind of its own here: ENR-4's mapping decides (scene is the natural fit). ENR-6 pins only scene, movie and VR.
- **The section's text counts toward `MAX_TOTAL`** (about 17 KiB at its caps). That keeps `MAX_PLAIN` and `MAX_STORED`, and V14's `CHECK` on `torrent_claims.data`, unchanged: no migration (plan Q9). The section's framing (under 150 bytes) fits the existing slack, and the worst-case tests show it.
- **One type, not a mirror.** `lodestar_sources` depends on `lodestar_store`, so it re-exports `AdultEnrichment`, `AdultKind` and `ReleaseDate` instead of copying them. The two can't disagree on what a section may hold. `lodestar_sources::Claims::clamp` bounds the section by degrading, not spoiling: an over-long or empty studio or performer name is dropped, not cut (a cut name may name someone else), and a dropped performer sets `performers_truncated`. A section with an invalid scene id is dropped whole, since a cut id points at another scene.
- **No wiring** (brief). `pipeline::unverified::store_claims` (SRC-2's mapping) passes `adult: None` until ENR-1 extends `unverified::judge` so the core judges the section's text before it's stored (Q3). Until then no enrichment reaches the store through the pipeline. An enrichment-only discovery would store an empty version 1 row until then; no plugin emits one before ENR-4/ENR-5.
- **Edits outside the brief's owned paths,** each one line: `crates/pipeline/src/unverified.rs` (the `adult: None` above; ENR-1 owns this file next), `crates/store/tests/unverified.rs` and `crates/store/tests/unverified_props.rs` (`adult: None` in exhaustive `Claims` literals the new field breaks), and `fuzz/README.md` (the `claims` row now describes version 2).
- **`Debug` shows lengths and counts only**, as for the rest of the claims: the section names people.
