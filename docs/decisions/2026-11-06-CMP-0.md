# CMP-0 decisions

The companion catalogue, its format and the crate's contracts (plan `docs/plan/2026-11-06-v06-companions.md` §4.3, CMP-0). These are refinements, decided by the slice and flagged to the owner by the runner (owner §2.19). None of them loosens an owner decision.

- **Every v0.6 artifact and image ships unpinned.**
  - **What:** each entry carries its structure: platforms, archive kinds, hosts, image names, ports, health and templates. Every `pin` and `digest` is `null`.
  - **Effect:** an unpinned artifact or image can't be installed or rendered. `Entry::installable` and `Container::pinned_digest` return `None`.
  - **Why:**
    - Pins are CMP-13's output. Plan §4.3 says "every `catalogue.json` pin came from CMP-13's tool", and CMP-13's CI rejects pins the tool didn't produce.
    - This session's network can't reach github.com or the registries, so any pin written here would be unverified.
    - An unpinned catalogue is the fail-safe state: nothing runs until a pin checked against upstream lands (§18.10, owner §2.46 cq2).
- **Validation is stricter than plan §4.3 lists.** The plan names `https` only, per-entry host allowlists, size caps, unique ids and supported platforms. The catalogue also checks:
  - **Hosts:** the entry's hosts must also be in a code-level `DOWNLOAD_HOSTS` list, and images must come from `REGISTRIES` (`lscr.io`, `ghcr.io`, `docker.io`, per owner §2.47 cq6). Adding a host is then a code change with its own review.
  - **URLs:** no port, user information, query, fragment or percent-encoding.
  - **Archives:**
    - the archive kind must match the URL's file name;
    - executables stay inside the archive, and end in `.exe` exactly on Windows;
    - installers are Windows-only.
  - **Pins:** all pins in an entry share one version, and a SHA-256 of one repeated digit is refused as a placeholder.
  - **Ports and health:**
    - ports are `1024` and up;
    - only a download client may publish (`p2p`) a port;
    - the health check uses an internal TCP port.
  - **Needs:**
    - `challenge_solver` requires `opt_in` (owner §2.47, Q21);
    - `vpn_route` is container-only, because the native VPN is v1.x (plan §2).
- **A fourth archive kind, `binary`.** The plan lists `zip|tar.gz|installer`. But the userdocs static `qbittorrent-nox` (owner §2.47 cq6) is published as a bare executable, not an archive, so `binary` means "the downloaded file is the program". CMP-2 installs it without extracting.
- **`upstream_sig` takes two forms:** `none` or `verified_at_pin` with the upstream key's OpenPGP fingerprint. That records what CMP-13 checked at pin time (owner §2.46, cq2). A run-time minisign form is left for when a companion publishes minisign signatures. None do today.
- **Template ids are a closed enum.** The ids are `qbittorrent_conf`, `prowlarr_config_xml`, `compose_service` and `unraid_template`. An id with no writer behind it is refused when the catalogue is parsed. The config-file templates need `native`; the compose and Unraid ones need `container`.
- **gluetun's health is left to CMP-8a.** gluetun's control-server routes and their authentication vary by version, so its entry has no `health` until CMP-8a's recorded fixtures settle the endpoint. That's a one-line shared catalogue edit.
- **The crate is registered with the binary's logging now.** A new workspace crate needs a `logging::TARGETS` line (`targets_cover_every_crate`). Its catalogue needs a `logging::CATALOGUES` line (`every_declared_catalogue_is_registered`). So CMP-0 adds both, plus `lodestar-companions` to `crates/lodestar/Cargo.toml`. These are three shared one-line edits, requested from the runner before they were made.
- **The only event so far is `companions.catalogue_invalid`.**
  - It's an `Error`-level event, required (it can't be turned off), and carries only the rule's code.
  - Errors name the rule and a location built from the code's own field names and indexes, never catalogue text, so they're safe to log and show.
