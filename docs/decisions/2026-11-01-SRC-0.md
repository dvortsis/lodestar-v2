# SRC-0 decisions (plugin contract v2)

Slice SRC-0 of `docs/plan/2026-11-01-v06-sources.md`. It covers architecture §18.1, §18.4 and §18.9.

- **The v2 manifest fields live in `Policy`, beside `Manifest`.** `SourcePlugin::policy()` returns it, and its default is `Policy::STRICT`. Politeness caps, the JSON-schema config, `distribution` and default schedule windows all go there.
  - Why: `Manifest` is built as a static struct literal in `pipeline/src/dht.rs`, `lodestar/src/services.rs` and several tests. A new field would break every one, and the DHT plugin had to stay unchanged.
  - A plugin that declares nothing gets the strictest settings: coordinator only, no full scrapes, one request per host every 10 s, polls at most every 15 min, and back-off from 30 s to 6 h. Approved by the runner, 2026-11-01.
- **Caps are hard.** `Policy::limits(&UserLimits)` takes the stricter side of every part: the longer poll and request interval, the smaller burst, the smaller daily scrape quota, and the longer back-off floor and ceiling. `Limits::within` is the check, and a property test covers any caps against any user settings.
- **Declared caps have global floors** (`manifest::floors`). A plugin's own declaration is trusted no further than these, so a zero interval or zero back-off can't become a request storm (§18.9). `Limits::floored` applies them in `Policy::limits` and again in every `HostLimiter` constructor, whatever built the `Limits`. A property test covers arbitrary declared caps, zeros and extremes included. The floors, set by the runner (§2.26):
  - at least 1 s between requests to one host, and a burst of at most 4;
  - at least 60 s between polls of one unit (the strictest Q4 rate is download clients at ≥ 1 min);
  - a back-off base of at least 1 s, and a ceiling at least the base;
  - at most 1 full scrape per tracker per day (BEP 48, §18.1).
- **`Policy` literals are written `Policy { caps: …, ..Policy::STRICT }`,** so a field added later takes the strict default instead of breaking the build or loosening anything.
- **One exception to the owned paths:** a single line in `crates/pipeline/src/lib.rs` (`kit: lodestar_sources::Kit::default()`) at the `SourceCtx` literal. Approved by the runner, 2026-11-01.
  - `SourceCtx` gains `kit: Kit`, which holds the plugin's `PluginState` and its HTTP `Client`. The client is a `Fetch` behind the plugin's `HostLimiter`, so a plugin gets no raw `Fetch`.
  - `Kit::default()` is in-memory state, `NoEgress` (every request fails with `HttpError::NoEgress`, so nothing leaves the machine) and `Policy::STRICT` caps.
  - SRC-1, SRC-4 and SRC-5 replace it per plugin with `Kit::for_plugin`: the store-backed state, SRC-5's client and the plugin's own policy.
- **The discovery event is `Found` with two new boxed options:** `claims` and `provenance`. A bare DHT key pays two null pointers and nothing else. `Discovery` and its literals are unchanged.
  - The event has no `network` field yet. Keys are still `InfoHash`, and the network tiers (§18.6) add it with their own key types.
- **Claims are bounded at the contract boundary.** The `Emitter` clamps every event's claims and provenance before it leaves the plugin.
  - The limits: name 1 KiB, files 10,000, path 4 KiB, trackers 64, IDs 32, description 64 KiB, publisher 256 B.
  - One event's claims also hold at most 1 MiB of text in all. Every other field fits in about 200 KiB at its own limit, so the budget bounds the file list, and files past it are dropped. Without it one event could carry about 40 MB.
  - Control characters, NUL and bidi overrides aren't stripped here. Display escaping and the filter pipeline own that.
  - Clamping releases the memory it cuts (`shrink_to_fit`). Parsers cap as they read rather than relying on the clamp (SRC-6 and later, as the `claims` module docs say).
  - Clamping trims; it never rejects. It doesn't replace the child-safety filter, which still runs on every claim before storage (§18.7, §20.1).
- **`PluginState` is async** (it returns `BoxFuture`), so the store-backed version can go through the writer. It offers get, set, remove and compare-and-set.
  - Both implementations enforce the same limits: keys 1–128 B, values ≤ 64 KiB, ≤ 1,024 keys per plugin. A plugin that passes against `MemoryState` then fits in `source_state` (SRC-1).
- **The per-host limiter is GCRA** (a token bucket of `burst` refilled one per `interval`). In any span of time `t`, one host gets at most `burst + t / interval` requests.
  - Back-off after the n-th consecutive failure is drawn from `[full, 1.5 × full]` and capped at `max`, where `full = min(max, base × 2^(n−1))`. So the stated floor, `base`, is real. The jitter is splitmix64, seeded per limiter.
  - The limiter tracks at most 1,024 hosts and forgets idle ones to make room. An idle host has a full bucket, isn't blocked, has no scrapes in the last 24 h, and either has no failures or failed more than one back-off ceiling ago. Forgetting one loses nothing: it starts over as a first failure would. A full map of busy hosts makes a new host wait (`WaitReason::Hosts`).
  - An answer is never dropped for want of room. `failure` and `block` always record against the host, even past 1,024: a host that answered held a token a moment ago. The map shrinks back as such hosts go idle.
  - **SRC-12 will need per-plugin caps.** A full scrape across thousands of trackers outgrows both 1,024 limits (`MAX_HOSTS` and the `PluginState` keys). That slice raises them per plugin, through `Policy`, rather than globally.
  - **The poll gate is the path plugins poll through, not an enforcement point.** `Client::poll(unit, &Request)` waits on `HostLimiter::try_poll` (one poll per unit per effective poll interval, covered by a property test) and then sends. A plugin could still poll through `Client::send`. What catches that is each plugin's contract test, which checks poll spacing from the replayer's timestamps: the pattern for SRC-7 in the `testing` module docs.
  - **The host key is the host the client connects to.** It comes from the WHATWG parser in the `url` crate, the one reqwest uses (approved by the runner; it was already in the lockfile).
    - IPv4 in any spelling (`127.1`, `0x7f000001`, `2130706433`, `::ffff:127.0.0.1`) is one key, and IPv6 is compressed.
    - Domains are lower-case punycode without a trailing dot.
    - Schemes other than http(s) are `BadUrl`.
    - So `http://evil.example\@nyaa.si/` is paced as `evil.example`, where it really goes.
  - SRC-5 should check the same key against the manifest's endpoints and the SSRF guard.
- **"Blocked by source"** applies on 401, 403, or a 429/503 that carries `Retry-After`. Nothing goes to the host until the block ends.
  - The block lasts the source's `Retry-After` (delta-seconds, capped at 24 h), but never less than the next back-off delay. When the source gave no `Retry-After`, it lasts the back-off ceiling.
  - A refusal also counts as a failure, so a source answering `Retry-After: 0` every time still escalates to the ceiling.
  - The HTTP-date form of `Retry-After` reads as absent, and the back-off covers it.
  - **Refinement:** "until the next window" is read as that time. Schedule windows are a separate gate, which the scheduler applies (see below).
  - A 429 or 5xx without `Retry-After`, or a transport error, backs off instead. Any other answer, 404 included, resets the back-off.
- **The daily full-scrape quota** is per host over a rolling 24 h. A quota of 0 never grants.
  - **The limiter's state is in memory and resets on restart,** because `Instant` can't be persisted. A cap that must survive restarts is persisted by the plugin in `PluginState`, as wall-clock time. That covers BEP 48's one full scrape per tracker per day: SRC-12 stores each tracker's last full scrape time and checks it before calling `try_full_scrape`. The poll interval works the same way: a feed plugin stores its last poll time where a restart-loop would otherwise poll early.
- **Schedule windows** are minutes since local midnight, and a window may wrap past midnight. Turning the clock into a minute of the day belongs to the scheduler (SRC-4/SRC-14), not to this crate.
- **`Fetch` is the HTTP seam.** SRC-5 implements it with reqwest and the plugin's egress. Plugins send only through the `Client` in their `Kit`, which takes the host's token, sends, and feeds the answer into the back-off. No client is built here.
  - **A `Fetch` never follows redirects.** It returns the 3xx, so any next hop goes back through the `Client`: paced for its own host and checked against egress.
  - **A `Fetch` reads at most `MAX_BODY` (16 MiB) of body** and fails past that.
  - **Streaming comes later as an additive `Fetch::fetch_stream`** with a default implementation, so implementations written now keep compiling. SRC-12's multi-megabyte full scrapes need it, and that slice may raise the fixture cap.
- **`testing` is always compiled** (it doesn't sit behind the `testing` feature, which stays the crawler simulator's), so plugin crates can use it from their own tests.
  - `FakeCtx` wires a `SourceCtx` to channels, with HTTP answered by any `Fetch` (usually the `Replayer`).
  - `Running::stop_within` is the cancellation gate: the plugin returns `Ok` within `STOP_WITHIN` (1 s) of shutdown. It counts the longer of clock time and real time, so neither a long timer nor blocking work passes on a paused clock.
  - Every harness wait (`next`, `wait_for`, `stop`) gives up after 10 s of real time, however far tokio's paused clock runs meanwhile. A plugin's 15-minute poll then needs no special timeout in tests.
  - The harness re-checks in clock steps that grow from 50 ms (to 1 s in `wait_for`). Hours-long back-offs then finish in a few thousand cheap iterations, even on slow runners.
  - The fixture layout is documented in the module docs for SRC-7 to build on: zero-padded `NNN.http` plus `NNN.body`, matched strictly, with `finish()` reporting skipped or unmatched exchanges. `Replayer::load` replays in order. `Replayer::load_unordered` takes the first unplayed match, for plugins that query several indexers in parallel.
  - Fixtures are capped at `MAX_BODY` (16 MiB) per file.
- **Left as documented:** empty claimed file paths are kept (the filter pipeline judges them), and the HTTP-date form of `Retry-After` reads as absent.
- **Schedule windows are `&'static [Window]`,** the manifest's defaults. Windows a user sets (SRC-14) need an owned form, which that slice adds when it stores them.
