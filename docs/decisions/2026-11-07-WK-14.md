# WK-14 decisions (the workers API)

WK-14 follows plan `docs/plan/2026-11-06-v06-workers.md` §4.3 and architecture §19.6, §19.7, §10.10.7, §12 and §18.7. It builds on WK-1 (the cluster port), WK-5 (placement) and #560's delta review. No owner decision is loosened and no owner-set number changes. The §2.19 refinements are listed at the end; the runner flags them to the owner.

## The endpoints (`crates/api/src/workers.rs`, `dto/workers.rs`)
- **Admin only.** Every route sits behind `auth::protected`, which accepts a session and nothing else. API keys (any scope), feed tokens and a bare proxy header get 401, and the test checks all three on every route. Writes need same-origin JSON.
- **`GET /workers`** joins three sources: the server's fleet snapshot, the certificates on record (for names, and for workers that haven't connected since this start) and the saved settings. Revoked workers aren't listed. Live values (clock offset, CPU, RSS, spool, counters, last seen) are `null` until the worker has spoken to this coordinator.
  - **Left out, not faked:** version, uptime, egress, assigned shards, per-minute throughput and quarantine. Later slices fill them.
  - **External IP** is the worker's own reported egress (§19.7). No peer address, certificate material or token appears in any response.
- **`POST /workers/tokens`** returns the `lsj1` token once (201, `Cache-Control: no-store`). It comes with the cluster address and ready-to-copy commands:
  - the CLI reads the token from stdin (`--token-file -`), never from argv (WK-2);
  - `docker run` and compose pass `LODESTAR_JOIN` and `LODESTAR_TOKEN`, as WK-2 and WK-18 decided;
  - Unraid and Windows get text.

  The address's host is the request's `Host`, kept only if it's a plain DNS name or IP literal; anything else becomes `<this-server>`, so nothing odd lands in a shell line. The port is the cluster port's.
- **No way to read a token back:** only its hash is stored (V6-cluster1). The binary hands the API the one copy (`NewToken`, whose `Debug` hides it and whose text is overwritten on drop), and no error variant carries one. The tests scan every other route's body, every refusal and the captured log for the token and for its secret part.
- **Ids:** `{id}` is a `u32`. A non-number is 400. Worker 0 (the built-in worker, the coordinator itself) and any id the coordinator doesn't know are `404 unknown_worker`.
- **PATCH ranges** are checked in the API before the binary is called. An out-of-range value is `422 out_of_range` with the field, matching the API's `422 bad_body` for a body that doesn't fit. The ranges:
  - `budget.cpu_permille` 1–1000;
  - `budget.ram_mb` 0–1,048,576;
  - `budget.up_kbps` and `budget.down_kbps` 0–10,000,000;
  - `pool_cap` 1–1,000,000 (`MAX_POOL_CAP`).

  0 means no cap beyond the defaults (WK-5). Unknown fields are refused.
- **Other refusals:**
  - `409 workers_off` (a token while "Allow workers" is off);
  - `409 worker_offline` (drain needs a session);
  - `409 name_in_use` and `409 too_many_tokens`;
  - `400 bad_name` (the same rule as `valid_worker_name`, checked again by the coordinator);
  - `409 too_many_workers` (#560 item 4).
- **Single machine:** without the workers extension, or with workers off, `GET /workers` is `{ "allowed": false, "workers": [] }` and every action is 404. Nothing is opened or written: no PKI, no `workers.` rows (tested).

## The glue (`crates/lodestar/src/cluster/ops.rs`)
- **`Workers`** implements `WorkersApi` over `ClusterHandle` and the one `Arc<Placement>`. The API crate sees only DTOs.
- **Saved settings** (#560 item 1):
  - **Storage:** one `settings` row per worker, `workers.prefs.<id>`, as versioned JSON: the pin, intensity, budget, pool cap and pause.
  - **Not under `cluster.`:** `cluster/serve.rs` treats any `cluster.` row as "the PKI exists" (runner, 2026-11-07).
  - **On restart:** settings are re-applied to the planner at open.
  - **Bad rows:** a row that doesn't parse, or is out of range, is skipped with `workers.prefs_skipped` (Warn), and the worker gets the defaults.
  - **Revoke** deletes the row, so rows can't outlive their workers.
  - **Not exposed:** the settings registry reads and writes only `settings.` keys, so no generic settings route lists or writes these rows.
- **Revoke** calls `ClusterServer::revoke_worker`. That refuses the certificates, takes the leases back and stops the session before it returns. Only then does it call `Placement::forget` (#560 item 2, in that order). The response gives the certificate and lease counts and `gone_within_secs` (one heartbeat, 5 s).
  - Tested end to end with a real in-process coordinator and a joined worker. The worker's session ends with `Stop(Revoked)` in less than one heartbeat, the worker leaves the list, and it can't reconnect.
- **Pause** (runner, 2026-11-07, option (a)) is the cluster server's:
  - **What it does:** a paused worker keeps its session and its leases. Its claims are denied as if draining, and no re-grant goes to it. Nothing is sent to it, and it is never turned into a drain.
  - **Survives a reconnect** (the server's per-worker state outlives sessions).
  - **Survives a coordinator restart:** it's saved in the row, and a follower task re-applies saved pauses to every new `ClusterServer` (one is built each time workers are turned on). `ClusterServer::pause` marks a worker before it connects. The follower checks every 100 ms, and every API call re-applies too.
  - **Shown distinctly** from draining; when both are set, draining shows. Resume ends both.
- **Drain** needs a connected worker (`409 worker_offline`), as `ClusterServer::drain` says. It isn't saved: it stands across reconnects in the server, not across a coordinator restart.

## Placement fixes from #560's delta review
- **Item 2:** `Placement::forget` now also tombstones the id, so a fleet snapshot taken before the revocation can't rejoin it with the defaults. A revoked id can never reconnect, because its certificates are refused. WK-5's `a_reconnecting_worker_keeps_its_pin_and_budget` assumed one could, and now checks that it isn't planned again.
- **Item 3:** a join refused at `MAX_WORKERS` no longer records the worker's addresses, so the next sync tries again once there's room (`Planner::is_member`). It's logged as `workers.join_refused` (Warn) once per worker until it joins or leaves. The test uses `Planner::limit_members(3)`: filling 4,096 members costs 4,096 re-plans, which took 21 s.
- **Item 4:** `Placement::pin` and `set_settings` return `Err(PrefsFull)` when no settings can be kept for that worker (`Planner::can_store_prefs`, asked under the same lock). The API answers `409 too_many_workers`.
- **Item 5:** `is_public` also refuses `2001:2::/48` (benchmarking) and `3fff::/20` (documentation), with boundary cases in its table test.
- **Each fix has a test that fails without it.** Reverting each fix alone fails `a_forgotten_worker_isnt_rejoined_by_an_older_snapshot`, `a_join_past_the_cap_is_retried_once_there_is_room`, `a_pin_with_no_room_is_refused_out_loud`, `is_public_refuses_every_special_range` and (with `persist` a no-op) `settings_and_pauses_survive_a_coordinator_restart`.

## Log events (`crates/lodestar/src/logging/events.rs`, component Workers)
- `workers.join_refused` (Warn): `worker` (the id).
- `workers.prefs_skipped` (Warn): `worker`.
- `workers.token_created` (Info): no fields. This is the admin audit line, and the token is never logged.
- `workers.revoked` (Info): `worker` and `leases`.

The runner asked for the worker's `name` on these. They log the id instead. The name is admin text, and the log has no data kind for it: `Label` takes only static text, and `Name` is the torrent-name kind, which a privacy mask would hide. Settings → Workers shows id and name side by side. Pause, resume and drain have no audit events (optional in the runner's answer). The en/zh names were added, `logs_catalog.txt` re-blessed and `event-names.ts` regenerated.

## The web client's typing limit (`web/src/lib/api/client.ts`, runner, 2026-11-07)
- **What failed:** with the four body-less action POSTs in `schema.d.ts`, svelte-check reported "Expression produces a union type that is too complex to represent" at the first `api.post` it checked (`features/alerts/api.ts`). Main's schema checked clean.
- **Cause:** while a call's path `P` is still being inferred, `RequestOptions<O>` is evaluated with `O` = the union of every POST operation. `Params`, `Part` and `BodyPart` were distributive conditional types, so `Part<'path'> & Part<'query'> & BodyPart` became a cross product of three per-operation unions, about N³ members. Main sat just under TypeScript's 100,000-member limit.
- **Fix:** the four conditionals are non-distributive (`[O] extends [{…}]`). For a single operation the types are identical. `client.types.test.ts` gains `@ts-expect-error` cases (wrong body type, missing path params, unknown path, a typed PATCH body), so the types can't widen silently. A cast at the call site didn't help (the union is built before the body is checked), so `alerts/api.ts` is unchanged.

## For WK-10 (worker runtime)
- **The planner is `Workers::placement()`:** the one `Arc<Placement>`, built in `services.rs` with `coordinator_dht = dht is on`. Use it rather than a second one, or saved pins and budgets won't reach the plan. The `sync` contract is WK-5's: on every cluster tick, `placement.sync(&server.snapshot(), &server)`, retry `Synced::full`, and apply `replan.coordinator` to the coordinator's DHT and pool.

## For WK-13 (quarantine, release, purge)
- **Routes and methods:** add one route each in `workers::routes()` and one method each on `WorkersApi`, where the `// WK-13` comment is. Purge is a Danger zone action like revoke.
- **Quarantine reuses `paused`** (`ClusterServer::pause`) and adds its own flag. `release` clears the quarantine with `ClusterServer::unpause` only if the admin hadn't paused the worker separately; the saved row's `paused` is the admin's pause. Add `quarantined` to `dto::workers::WorkerStatus`.

- **When purge forgets a worker,** delete its `workers.prefs.<id>` row as revoke does (runner's condition).

## §2.19 refinements (the runner flags these to the owner)
1. **Pause is a server flag**, distinct from drain. The worker keeps its session and leases and isn't told; it's re-applied within 100 ms to a newly built cluster server.
2. **Worker settings rows live under `workers.prefs.`** outside the settings registry: not exported or imported with settings.
3. **Audit events log the worker id, not its name.**
4. **Out-of-range PATCH values are 422** (the API's `bad_body` convention), not 400.
5. **The join commands carry the request's `Host`**, sanitized, with the cluster port.
