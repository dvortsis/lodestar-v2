# M8-NET-E2E decisions

The in-process DHT test network (architecture §17): `crates/crawler-sim/tests/e2e_search.rs`, helpers in `tests/e2e/`.

- **Loopback, not the simulator's network.** The test runs 50 real `lodestar_dht` nodes on 127.0.0.1 UDP, as `crates/dht/tests/network.rs` does, and real TCP fake peers (`lodestar_peer_wire::testing::FakePeer`). The simulator's in-memory socket (`lodestar_dht::node::testing::start`) can't be used here. The production DHT plugin (`lodestar_pipeline::DhtSource`) binds real UDP, and the brief wants the production plugin inside the production `Pipeline`. Using the simulator would mean rewriting the plugin's wiring in the test, which copies production logic. Loopback also suits what runs downstream: SQLite, the live indexer thread and the axum router all run on real time, which tokio's paused clock can't drive.
- **What's real and what's the test's:**
  - Real, with production settings:
    - the crawler: `DhtSource` in `Pipeline::start`, with the peer-wire fetcher, `PoolConfig::default()` and the shipped content filter;
    - the store: `Store::open` in a temp data dir;
    - the index: `Serving::open_or_rebuild` with `LiveConfig::default()`'s poll and commit cadence;
    - search: `/api/v1/search` through `lodestar_api::router`, called with `tower::ServiceExt::oneshot` after a real first-run setup and sign-in.
  - The crawler's DHT config differs from `Config::default()` in four places only: it binds loopback, bootstraps from the test network, sets `allow_private` (loopback is private), and sets `sample_start_delay: 0`. Without that last one, a start with no restart proof suppresses sampling for 6 h (CR-0d). The fetcher also sets `allow_private`.
  - The index writer heap is 64 MiB, not 256 MiB. That's the configurable `search.heap_mib`, at a test's size.
  - `gate_follows_index` stays off, as no crawler gate is wired.
  - The test's own parts:
    - the 50 network nodes: real nodes that don't sample themselves, so the crawler is the only sampler;
    - the fake peers;
    - a bare KRPC client. It does what a BitTorrent client does: an iterative `get_peers` lookup from the bootstrap node, then `announce_peer` to the 8 closest nodes it found, with their tokens.
- **The clock (runner, 2026-11-12, decision C).** §17 reads "harvest → fetch → store → index → search … within 5 s", and the owner's §1.6 budget is "new torrent → searchable < 5 s". Neither covers how long the DHT takes to show the crawler a hash. So each hash's 5 s runs from the crawler's first sighting of it to `/search` first returning it. The runner flags this definition to the owner (§2.19).
  - The first sighting is read in process from the DHT's own `dht.key_harvested` event, through a test log sink. Only the crawler samples, and a sample harvest is reported once per node and hash, so a hash's first `sample` event is the crawler's.
  - `/search` is polled, so the measured time only errs long.
  - Harvest has its own deadline: every served hash must be harvested within 30 s of its peer serving. There's no bar on it, since its tail is the sampler-frontier finding below.
  - The network joins and the install is prepared first. The peers then start serving and are announced to each hash's 8 closest nodes (BEP 5), and then the crawler starts. Starting the crawler first was measured and rejected (option 1, below).
- **What's asserted:**
  - all 16 known torrents (8 peers × 2) are returned by `/search` under their own hash, with the size and file count of the dict their peer served, each within 5 s of its harvest;
  - the search wait's deadline is 40 s, so a miss reports how long it took;
  - a forged peer (`Behavior::WrongData`) is rejected: a `HashMismatch` failure is counted, and nothing is stored or searchable;
  - a hash the network was asked about but no peer has is queued and looked up (an attempt spent), and is never stored or searchable;
  - the writer stored exactly the 16.
  - The test writes one line to the real stderr, past libtest's capture, with each hash's time, the max and the harvest times, so CI logs keep them for a passing run.
- **Seeded:** names, sizes and file lists come from one SplitMix64 seed, the same on every OS. Node ids and packet timing are real, so assertions are order-free and nothing is compared to a golden.
- **Dev-dependencies, runner-approved 2026-11-12 under standards §2:** `lodestar-api`, `lodestar-bencode`, `lodestar-pipeline` and `lodestar-search` (workspace crates); `axum`, `tower` (util) and `serde_json` at the versions and features `lodestar-api` uses, so `Cargo.lock` gains no package or version; `lodestar-peer-wire`'s `testing` feature. tokio gains `rt-multi-thread` and `net` for this crate's tests only; no other package's tokio changes. `tempfile` was approved too but isn't used: a small drop guard keeps the data dir.
- **Sampler frontier, a production yield finding (runner follow-up X-sampler-frontier, Track C):**
  - BEP 51's frontier refills only from the crawler's routing table (`sample_tick`, when it falls under `LOW_FRONTIER`). With K = 8 buckets, a 50-node network doesn't fit, so some nodes enter the frontier late. It's what delays harvest; it doesn't touch the per-hash bar.
  - Evidence: in a run that missed, 9 of 18 hashes were harvested at 1.1 s and the other 9 at 10.1 s. No query timed out and no reply was dropped. In 20 runs before decision C, every miss of the then from-serving bar was this tail.
  - No production code changes in this slice.
- **Option 1 measured and rejected (runner asked for it).** The crawler joined first, then the clients looked up and announced: 13 of 20 runs passed, and two never fetched some hashes within 20 s.
  - Nodes the crawler had sampled before the peers served were on their ≥ 60 s BEP 51 cooldown.
  - Correction: the two stalls were first put down to a passive GetPeers harvest racing the announce. Under decision C's topology, where no such race can happen, the same stall recurred, on hashes in the same keyspace region (d4/d7/e2/ef/f1). So they're the lookup-convergence bug below, not a separate race.
- **A production lookup-convergence bug blocked this slice, fixed by X-dht-lookup-converge (#756, merged as 0a70c788).** The fix parks lookups until the bootstrap settles, and refreshes the far keyspace once after joining (`docs/decisions/2026-11-12-X-dht-lookup-converge.md`). Before it, in about 1 run in 10, one known hash is harvested about 80 ms after the crawler starts, and its `get_peers` lookup completes with no peers. The key then waits out the pool's 120 s `retry_backoff`.
  - There were no DHT timeouts, throttling, denials or send errors, and all 18 lookups were answered.
  - The network holds the values: on the stall, the 8 nodes closest by id to the stuck hash each return the peer to a direct `get_peers`. An iterative BEP 5 lookup from the bootstrap node finds all 8 of them.
  - So the crawler's lookup ends without reaching them. It started with a routing table of about 25 nodes, with about 18 lookups launched together.
  - Reproducer: run `cargo test -p lodestar-crawler-sim --test e2e_search` in a loop. A failure reads "1 of 16 missing: [… (harvested: true)]", with the key queued at 1 attempt. Seen on d4b3… (Kestrel 01) and a76b… (Harbor 04), with seed `0x4c4f_4445_5354_4152`. Node ids are random, so the stuck hash varies.
- **Measured after the fix (Linux container, 20 runs on `main` at or after 0a70c788):** 20 passed, with no flake.
  - Per-hash harvest → searchable: each run's max was 2473–3976 ms, with 17 of 20 under 3.01 s, inside the 5 s bar.
  - T0 → harvest: every served hash by 2.08 s, mostly at 70–90 ms and about 1.07–1.09 s, a few at 2.07–2.08 s.
  - The 6–10 s sampler-frontier tail didn't appear in these 20 runs. It may be rarer now that every network node refreshes its far keyspace on joining, but X-sampler-frontier still stands, and harvest keeps its 30 s deadline with no bar.
- **Measured under decision C before the fix (Linux container, 20 runs):** 18 passed, with per-hash harvest → searchable at 1445–3406 ms (each run's max 1978–3406 ms). The 2 failures were the lookup bug. T0 → harvest was mostly 70–95 ms, the rest at about 1.1 s, with a sampler-frontier tail of 2–3 s and once 6.1 s and 9.1 s.
- **Where the time goes in a run that passes:**
  - harvest: by 0.1–1.1 s, as the sampler runs on the 1 s DHT tick;
  - fetches: they start on the next tick, two at a time on 127.0.0.1 (`per_ip = 2`), and everything is stored by 2.3–3.4 s;
  - indexing: the live indexer commits on a ~2 s cadence.
  - Together, the 1 s tick and the ~2 s commit grid put a clean run at about 4.0 s from T0, and each hash's harvest → searchable at about 1.5–3.4 s.
