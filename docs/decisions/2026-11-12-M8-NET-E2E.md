# M8-NET-E2E decisions

The in-process DHT test network (architecture §17): `crates/crawler-sim/tests/e2e_search.rs`, helpers in `tests/e2e/`.

- **Loopback, not the simulator's network.** The test runs 50 real `lodestar_dht` nodes on 127.0.0.1 UDP, as `crates/dht/tests/network.rs` does, and real TCP fake peers (`lodestar_peer_wire::testing::FakePeer`). The simulator's in-memory socket (`lodestar_dht::node::testing::start`) can't be used here. The production DHT plugin (`lodestar_pipeline::DhtSource`) binds real UDP, and the brief wants the production plugin inside the production `Pipeline`. Using the simulator would mean rewriting the plugin's wiring in the test, which copies production logic. Loopback also suits what runs downstream: SQLite, the live indexer thread and the axum router all run on real time, which tokio's paused clock can't drive.
- **What's real and what's the test's:**
  - Real, with production settings:
    - the crawler: `DhtSource` in `Pipeline::start`, with the peer-wire fetcher, `PoolConfig::default()` and the shipped content filter;
    - the store: `Store::open` in a temp data dir;
    - the index: `Serving::open_or_rebuild` with `LiveConfig::default()`'s poll and commit cadence;
    - search: `/api/v1/search` through `lodestar_api::router`, called with `tower::ServiceExt::oneshot` after a real first-run setup and sign-in.
  - The crawler's DHT config differs from `Config::default()` in four places only: it binds loopback, bootstraps from the test network, sets `allow_private` (loopback is private), and sets `sample_start_delay: 0`. Without that last one, a start with no restart proof suppresses sampling for 6 h (CR-0d). The fetcher also sets `allow_private`.
  - The index writer heap is 64 MiB, not 256 MiB. That's the configurable `search.heap_mib`, at a test's size.
  - `gate_follows_index` stays off, as no crawler gate is wired.
  - The test's own parts:
    - the 50 network nodes: real nodes that don't sample themselves, so the crawler is the only sampler;
    - the fake peers;
    - a bare KRPC client. It does what a BitTorrent client does: an iterative `get_peers` lookup from the bootstrap node, then `announce_peer` to the 8 closest nodes it found, with their tokens.
- **The timeline.** The network joins and the install is prepared first: store, index, API and setup. The clock starts when the fake peers start serving. They're announced (about 40 ms), then the crawler starts. Starting the crawler first was tried and rejected (runner, 2026-11-12, option 1, below).
- **What's asserted:**
  - all 16 known torrents (8 peers × 2) are returned by `/search` under their own hash, with the size and file count of the dict their peer served, within 5 s of the peers starting to serve;
  - the wait's own deadline is 20 s, so a miss reports how long it took;
  - a forged peer (`Behavior::WrongData`) is rejected: a `HashMismatch` failure is counted, and nothing is stored or searchable;
  - a hash the network was asked about but no peer has is queued and looked up (an attempt spent), and is never stored or searchable;
  - the writer stored exactly the 16.
  - The test writes one line to the real stderr, past libtest's capture, with the measured time and the counters behind it, so CI logs keep the time of a passing run.
- **Seeded:** names, sizes and file lists come from one SplitMix64 seed, the same on every OS. Node ids and packet timing are real, so assertions are order-free and nothing is compared to a golden.
- **Dev-dependencies, runner-approved 2026-11-12 under standards §2:** `lodestar-api`, `lodestar-bencode`, `lodestar-pipeline` and `lodestar-search` (workspace crates); `axum`, `tower` (util) and `serde_json` at the versions and features `lodestar-api` uses, so `Cargo.lock` gains no package or version; `lodestar-peer-wire`'s `testing` feature. tokio gains `rt-multi-thread` and `net` for this crate's tests only; no other package's tokio changes. `tempfile` was approved too but isn't used: a small drop guard keeps the data dir.
- **Sampler frontier, a production yield finding (runner follow-up X-sampler-frontier, Track C):**
  - BEP 51's frontier refills only from the crawler's routing table (`sample_tick`, when it falls under `LOW_FRONTIER`). With K = 8 buckets, a 50-node network doesn't fit, so some nodes enter the frontier late.
  - Evidence: in a run that missed, 9 of 18 hashes were harvested at 1.1 s and the other 9 at 10.1 s. No query timed out and no reply was dropped. In 20 runs of the final topology, every miss of the 5 s bar was this tail.
  - No production code changes in this slice.
- **Option 1 measured and rejected (runner asked for it).** The crawler joined first, then the clients looked up and announced: 13 of 20 runs passed, and two never fetched some hashes within 20 s. A client's lookup passes through the crawler before its announce exists. The crawler harvests the hash passively with no peers, its own lookup comes back empty, and the key waits out the pool's 120 s `retry_backoff`. That's production behaviour too, and a second candidate for the follow-up. Nodes the crawler sampled before the peers served were also on their ≥ 60 s BEP 51 cooldown.
- **Where the time goes in a run that passes:**
  - harvest: by 0.1–1.1 s, as the sampler runs on the 1 s DHT tick;
  - fetches: they start on the next tick, two at a time on 127.0.0.1 (`per_ip = 2`), and everything is stored by 2.3–3.4 s;
  - indexing: the live indexer commits on a ~2 s cadence, so searchable times cluster at about 4.0, 6.0 and 8.0 s.
- **Measured times, from CI:** _to be filled in from the PR's CI logs (Linux, macOS, Windows)._
- **M8-CHAOS-1 builds on this harness.** The `Cargo.lock` chain is NET-E2E → CHAOS-1 → PERF-2.
