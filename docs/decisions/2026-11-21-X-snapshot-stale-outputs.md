# X-snapshot-stale-outputs decisions (#1031)

Slice session, 2026-11-21Z, from #1013: the `settings-bp2560-riverstone-dark` baseline lacked the Outputs nav item (OUT-2) and the snapshot test still passed; the light 2560 baseline lacked it too. A whole nav row could go missing with no test failing.

## Why it passed

- **The 2560 baselines are compared in PR runs.** The `bp2560-riverstone-{light,dark}-{comfortable,compact}` projects are in the matrix (`testMatch` is `smoke.test.ts` and `states.test.ts`), and the e2e workflow's "playwright (core, matrix, sample, motion, keyboard)" job runs all of them. Only the regeneration run (the `web/e2e/.update-snapshots` marker) compares nothing.
- **The pixel tolerance is the hole at that size.** `expectPageSnapshot` uses `maxDiffPixelRatio: 0.001`. At 2560 the shot is the viewport, 2560 × 1440 = 3,686,400 px, so 3,686 differing pixels are allowed. I ran the stale dark baseline (git 17c8f30d3, no Outputs row) against the regenerated one with the row (fb6eede05) through Playwright's own comparator (`toMatchSnapshot`, anti-aliased pixels excluded, as in CI): **3,746 pixels differ, 60 over the 3,686 allowed (1.6 %)**. Whether the missing row fails is decided by anti-aliasing noise, which is how it passed. The row costs few pixels because the 2560 shot cuts the navigation off at 1440 px, so only some of the rows that shift up are in the picture. At 1920 × 1080 the allowance is 2,074 px and at 1366 (full page, 1366 × 1487) 2,031 px, so the same row fails there with a margin of about 1.8×. The 2560 shots are the weak spot.
- **The stale baselines are already regenerated.** #1028's regeneration (60fa30d3a) regenerated both `settings-bp2560-riverstone-{dark,light}-comfortable` baselines for the page frame, and both now show Outputs. No PNG changes in this PR.

## The fix: a DOM assertion (runner call, §2.26)

- `web/e2e/smoke.test.ts` gains "smoke settings navigation: every registered screen has a link". It runs in every matrix project (28: 320 to 2560 px, light and dark, comfortable and compact); the sample-theme and reduced-motion projects skip it, since theme and motion can't change which links exist. It visits `/settings` (the overview shows the navigation at every width; a section's page hides it below 1024 px) and requires a visible link in the "Settings sections" navigation for every registered screen, and no link without a screen.
- **The screen ids come from the registry files on disk** (`src/lib/features/**/screen.ts`, read with `fs`, the same files `screens.ts` globs). Every `id:` in those files is a screen id, matched whatever the order of the keys or the quotes; a file whose `id:` count differs from what was read (an id written as a constant, say) throws, so a shape the test can't read fails loudly instead of shrinking the list. A new screen needs no list edit and a retired one needs none either: the test only requires that it read at least 10 ids and no repeats, so an empty read can't pass. The link match is exact on the path (`/settings/<id>`, with or without `?density=`), so one id that is a prefix of another can't match two links.
- **No tolerance change.** A tighter global `maxDiffPixelRatio` would make the 2560 shots flake; the assertion covers the navigation row, which is what failed.
- **Conditional screens.** The registry has no visibility rule: a `Screen` has no condition field, and `SettingsShell.svelte` shows every registered screen (the section filter only narrows the list). So no exception exists to name today, and the test says so in its header: a screen that gets a visibility rule must be named in the test with its reason.

## Proof (mutation, reverted)

Changing Outputs' `group` to an invalid one (so `isScreen` drops it from the navigation) fails the new test in **all 14 comfortable matrix projects**, 320 to 2560 px, light and dark, each with "the outputs screen's link": bp320, 390, 768, 1024, 1366, 1920 and 2560. The compact projects were mutated at 320 and 2560 px (4 of 14): they fail the same way. With the change reverted, the test passes in all 28 matrix projects. (The 14 existing `smoke settings` screenshot comparisons fail on a cloud machine's local render, as `web/e2e/README.md` warns; CI's baselines are authoritative.)

The slice's `owns` in `runner/slices.yaml` gains this file (runner-approved). Its title still says "stale 2560 px baselines regenerated": #1028's regeneration had already done that, so no PNG changes here.
