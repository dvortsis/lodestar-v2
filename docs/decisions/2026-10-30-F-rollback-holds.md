# F-rollback-holds decisions

Builds on `2026-10-30-F-rollback-journal.md` (#241). It closes the gap that file left under "Not covered: holds", and O1 and O2 from its review. It refines BB-1, the deletion guarantee (owner decisions §2.16, §2.17, §2.21), the content-safety holds (§20.3, §20.5.2) and the locked floor (§2.7) for `lodestar rollback` (architecture §12). Nothing here loosens a hold, the floor or BB-1, or changes an on-disk format: rows are written to the existing tables as they are. **Flagged to the owner (§2.19) as content safety,** with the limits listed at the end.

- **A rollback keeps the holds recorded after the snapshot.** In the same transaction as #241's purge, `snapshots::carry_holds` merges the current store's `cs_hashes`, `tombstones` and `quarantine` into the copy's, wherever both schemas have them (V4 adds all three). Before this, the held torrents left the copy but the restored store no longer refused them, so a later crawl could fetch and index again what the safety core blocked after the snapshot.
- **Imported CS-1 entries are carried too, not only your own.** Entries from `blocklist.files` would come back anyway, since they're synced into the store at every start (`lodestar::floor::sync_files`). But an entry a floor-marked list dropped and you chose to keep (`resolve_pending_floor` without `remove`) is stored as an import that no source writes again. Carrying them all is stricter, never laxer. An imported entry the copy's floor manifest doesn't know stays blocked, and can be removed in the app with Remove CS-1, like any entry.
- **Blocklist subscriptions are carried too.** Lists subscribed to in the app live only in the store (`subscriptions`, `subscription_data`, V6), so a list added after the snapshot, a floor-marked one above all, would otherwise vanish with the rollback. That would remove locked floor entries without the app, the warning or the password (§2.7). `snapshots::carry_lists` merges them by URL:
  - a list only the store has is added with its data;
  - a list both have keeps the copy's data (its next refresh is due), and is floor-marked or switched on if either copy has it so;
  - a list only the copy has stays;
  - a floor-marked list's pending removals (`floor.pending:list:<id>`) come along under the copy's id, and stay blocked until they're settled in the app.

  A copy before V6 has no subscription tables. There, the entries of the store's floor-marked content lists, both applied and pending removal, are added as imported CS-1 entries instead.
- **Conflicts keep the stronger hold, then the later one.**
  - A CS-1 entry is merged as `add_cs_hashes` merges it: your own confirmation or report outranks an import, and its time stays.
  - For tombstone and quarantine rows, the floor's rules (`CS-1a`, `CS-1b`, `CS-8a`) outrank an adult hold, and an adult hold outranks any other. An adult hold is the one filtering can't rebuild, and an adult hold's expiry never replaces a floor tombstone. Between equals, the later `at` wins, and the current store's on a tie. The whole row comes from the winner.
  - A hold only the copy has stays: **a release made after the snapshot is undone by the rollback**; release it again.
  - **A hash both tombstoned and quarantined keeps only the tombstone,** unless the quarantine is an adult hold. Otherwise the quarantine's expiry would release the hash from the running filter's held set while the tombstone still stands. The rollback makes that easy to reach: released since the snapshot, then fetched again and dropped. A running store can reach it too, through `purge_filter` returning every expired non-adult hash as released; that's raised with the runner as a follow-up outside this slice.
- **Quarantine stays sealed.** Rows are copied byte for byte; nothing is unsealed. The copy's quarantine purge then runs over the merged rows, as the store's own tick would: an expired adult hold becomes a tombstone, other expired holds go, and a sealed name the current store no longer holds is cleared.
- **The whole journal and every hold apply to a rollback's copy (O1).** `purge_for_restore` now matches every journal and hold row by hash, whenever it was recorded (`since = i64::MIN`), not only those from a day before the snapshot's modification time. A snapshot copied without keeping its time (`cp` without `-p`) looks as if it was taken after deletions it still holds, so the window would let a deleted torrent back. The cost: a torrent deleted and then legitimately fetched again since is removed from the copy too, and can be fetched again. A large imported list makes the rollback slower; it's a one-off. The hourly snapshot purge keeps its window (`2026-10-23-S-snapshots.md`): it only scrubs, and never makes a snapshot the store.
- **Limits, inherent to restoring an older store, for the owner's flag:**
  - **Rolling forward from a store before V12 can bring back what it deleted (O2).** Such a store keeps no deletion journal, so rolling it forward (undoing a rollback to a schema before V12, say) has no record of what it deleted since the copy it restores was taken. Its holds still apply and are carried.
  - **A rollback to a schema before V4 drops every hold.** That copy has no hold tables, and nothing is added to its schema: the held torrents still leave it, but the release it belongs to has no content filter, and once it's upgraded again its hold tables start empty. Carrying the holds after that upgrade would need the next start to know a rollback happened, so it's raised with the runner as a follow-up.
  - **Your other filter settings go back to the snapshot's:** core switches, your rules, the override list, exceptions and *Always allow*. A rule switched on since can be off again, and an exception deleted since can be back. Unlike holds, these have no "stronger" side to merge to. The user guide's rollback page should tell the user to check Filters after a rollback; that's raised with the runner for the docs.
- **Tests:**
  - a rollback with holds recorded after the snapshot keeps every one, and the restored store's filter state (which intake refuses from at start) refuses the reported hash and holds the tombstoned and quarantined ones;
  - each conflict rule is pinned, the time tiebreak included;
  - lists, floor marks and pending removals are carried, and before V6 as CS-1 entries;
  - a copy dated a month after its deletions still loses them;
  - the journal row is merged when the store doing the rollback is older;
  - dropping any one table's merge, the tombstone-over-quarantine rule or the list carry fails a test.
