# ENR-4 decisions (ThePornDB plugin)

**HOLD: nothing may register or enable this plugin until both of these are done.**
1. **The Q2 terms and robots check for ThePornDB's API is owed by the owner** (plan §5 Q2, owner §2.28). This slice's sandbox had no route to the service and no account. The check must confirm, and record here: (a) the API terms of use and `robots.txt` as they read today for `https://api.theporndb.net`; (b) that a general-purpose index sending a release name per lookup, at most one request a second and 5,000 background lookups a day (Q15), fits those terms (if it's grey, it goes to the owner); (c) that the request and answer shapes below match the live API, since the fixtures are hand-written and were never recorded, including what `parse` returns for a name that matches nothing (an empty list, or a loose best guess: the plugin takes the top result as the match). **Precondition for registration:** a `Page` flag in `sources-feeds` saying the root `data` key was seen, to replace the plugin's byte scan (below).
2. **Host wiring is a later slice.** Nothing builds `AdultEnrichSource` yet: the host builds it with its own store connection, the live filter, the always-adult mask, its `Switches` and a `StoreState` kit, wraps this plugin's policy in `adult_enrich::capped`, and hands `Interest` to ENR-7's API.

Slice ENR-4 of `docs/plan/2026-11-04-v06-rulepacks.md` (runner brief, 2026-11-05). Spec: architecture §18.1, §18.7, §20.9, plan Q2, Q4, Q5, Q15, and the contract in `2026-11-05-ENR-1.md`; the parser is ENR-2b's (`2026-11-04-ENR-2b.md`).

- **Not registered, not enable-able.** `crates/sources-plugins/src/tpdb.rs` is one `pub mod tpdb;` line in `lib.rs` and nothing else: no entry in `crates/lodestar/src/services.rs`, no registry, nothing in Settings. `Tpdb::need` shows what enabling would ask for.
- **Manifest.** Id `tpdb` (never renamed), `Kind::Enrichment`, **Account** consent, `enabled_by_default: false`, `always_adult: false`, risk Medium, priority Low, one endpoint: `https` to `api.theporndb.net`, so egress is narrowed to that host over https, public addresses only (`Endpoints::manifest`). `distribution: coordinator`. No user-entered address.
- **Policy (Q15).** One request a second per host with no burst, and a back-off of a minute up to six hours. The runtime already paces lookups and counts the daily cap and the caches (`adult_enrich`), and holds the same per-host rate with `capped`, so the plugin has no second limiter: its requests go through the kit's `Client::send`, which applies the host limiter and records a 429's `Retry-After`. Polls aren't used (`Client::poll` is for feeds).
- **API key.** The `api_key` credential in SRC-4's sealed store (the config schema marks it `writeOnly`; there are no other settings). It's read through the `Credentials` trait on each lookup (a deliberate departure from that trait's "asked at start" note, since an enricher has no start), so a key dropped by a purge stops working at once and no copy outlives the call. It goes in an `Authorization: Bearer` header, never in the URL. It's only accepted if it's 1–256 ASCII letters, digits or `-_.|`, so it can't break out of the header. No error, `Debug` string or log line holds it (tests check each outcome with a distinctive key). A missing key, an unreadable one and an invalid one each fail before any request, with a message that names none.
- **The request is the name and nothing else.** `GET https://api.theporndb.net/scenes?parse=<display name>&per_page=5`, built by `tpdb::search_request` from `Query::Name`, the only thing the runtime gives a plugin about an item. The plugin asks for the name form, so the parsed form (which today carries only a title and a date) is refused without a request. No info hash, file name, tracker or install detail can reach it; it never calls `/scenes/hash/{hash}` or any by-id endpoint, and asks for no performer id or personal field (the parser can't return one anyway: Q4, Q5). `parse` is the service's documented search from a release name; **this is the first thing the owner's check must confirm against the live API** (HOLD item 1c).
- **The answer** is read with ENR-2b's `tpdb::parse_each` under `ANSWER_LIMITS` (its default caps, with items cut at 50 and performers at the section's 64). **Only the top result is used** (`max_items: 1`): if it can't be read, the answer is an error, never the second-best guess, which could pin another scene's performers on the torrent (Q4).
  - **Mapping to ENR-0's section:** scene id, kind (Scene and JAV are `Scene`; Movie is `Movie`; the service has no VR flag, so the classifier's own VR words still decide that), title, studio (`site.name`), release date, and **performer names** in the service's order, with `performers_truncated` as the parser reports (Q4 allows names on the item they belong to; no id, no personal field). A scene id the section's rule refuses is no match.
  - **Errors read the HTTP status.** 200 is read; **401 or 403** is "ThePornDB refused the API key" (no key echoed, no service text); **429**, or the host being held after one, is "ThePornDB is limiting requests; backing off" (the limiter keeps the hold, so a retry within it sends nothing and says "on hold after a refusal or a rate limit", since the limiter holds the host after a 401/403 too and doesn't say which); any other status or a transport failure is a plain failure. The service's message text is never read or kept.
  - **A broken answer is an error, never a miss.** A 200 whose root isn't an object, that stops the parser, or whose every item was skipped is "not understood", so the runtime doesn't cache it as a 7-day miss. Only an answer with a `data` key that parsed cleanly to nothing (`{"data": []}`, `null`) is no match; an object without `data` (the service's error object on a 200) is an error. **Accepted gap:** the parser doesn't report whether it saw `data`, so the plugin scans the root object for its first `data` key (tracking strings and nesting) and takes a miss only if the value starts a list, an object or `null`; `{"message": "data"}`, a nested `data`, `{"data": "x"}` and `{"data": 5}` are errors. The `Page` flag in `sources-feeds` is the proper fix and a precondition for registration.
- **The filter still applies in full.** `lookup` returns a `Lookup` to the runtime and nothing else; storing is the runtime's, through `adult_enrich`'s `judge_in` (the section's text is judged against the child-safety core and the user's rules before it is stored, `2026-11-05-ENR-1.md`). The plugin has no path around it, and it can only run for an item that gate passed. **The brief's "blocklist applies" test is deferred to ENR-G (and SRC-G's `tests/safety.rs`):** it needs the pipeline, which this crate doesn't depend on. The cross-plugin end-to-end test through the real filter is ENR-G's (it needs the pipeline). Here, a test checks the section is within the claim limits unchanged, so intake has nothing to cut.
- **Fixtures** (`crates/sources-plugins/fixtures/tpdb/`) are hand-written and synthetic, made from ENR-2b's. Not recorded: see HOLD 1c and the README there.
- **Tests** (`crates/sources-plugins/tests/tpdb.rs`): fixture replay of a match and a miss; the request is the name and the key header only (path `/scenes`, two query parameters, no hash, performer, file or tracker, key not in the URL); only the name form is answered; 401, 403, 429 (with the hold and the retry after it), 500, a cut body and an HTML body each end in the right outcome; answers not understood are errors, and clean misses are no match; property tests that arbitrary and mutated bytes never panic and any match fits the claim limits; a missing or invalid key fails before a request; enabling without a key is refused (`consent::need`); the manifest, policy, floors and schema; no `Debug`, request or error holds the key or the name; a lookup in flight can be dropped; two lookups are at least a second apart. No live network, no fixed sleeps (paused clock).
