# ENR-9 decisions (claim encoding v3)

Slice ENR-9 (runner brief, 2026-11-06T16:55Z). The spec is `docs/plan/2026-11-05-v07-m7.md` §4.3 "ENR-9": architecture §6, §18.1 and §18.5, owner §2.37, §2.46 and §2.47. Version 3 lands **inactive**: it decodes, and nothing writes it. The sources→store mapping (`pipeline/src/unverified.rs`) stores `details: None` until ENR-10 judges the section before storage, as it does for the adult section.

## The layout
- **Version 3 is version 1 plus a details section, and only that.** This mirrors how ENR-0 made version 2.
  - `present` bit 7 says a details section follows the ids. With bit 7 taken, every bit of `present` now names a field, so the next top-level field needs a new layout.
  - A blob is version 3 exactly when it has a details section. Claims without one keep their version 1 bytes and hashes.
  - `decode` refuses version 0 and versions 4 to 255. It also refuses any blob whose section doesn't match its version byte.
- **One section a row.** Claims that hold an adult section can't also hold a details section, and both sides refuse it (`enrichment claims`).
  - Each enrichment result is its own row under its plugin's source id (plan §3).
  - General enrichment never handles Adult items (Q5, `2026-11-06-runner-planning-wave-answers.md`).
  - So the two sections never need to share a row. Keeping them apart also keeps the adult section's "nothing rides along" rule simple.
  - This is stricter than the plan requires. It can be loosened later without breaking any stored blob.
- **The fields, as the plan lists them** (`store::claims::Details`, re-exported by `lodestar_sources`). Each one is optional or a list:

  | Field | Limit |
  |---|---|
  | `source_category` | 1–256 bytes, kept as the feed spells it |
  | `posted_at` | zigzag Unix seconds |
  | `newsgroups` | ≤ 8, each 1–128 bytes, RFC 5536 names |
  | `alt_titles` | ≤ 32, each 1–512 bytes, each with a language |
  | `canonical_title` | ≤ 1,024 bytes |
  | `genres` | ≤ 16, each 1–64 bytes, normalised |
  | `year` | 1–9999 |
  | `match_confidence` | 0–100 |

  - **The plan's "per-plugin confidence" is `match_confidence`**, a percentage on each row. A plugin's claims are their own row, so this is per plugin. It says how well this match fits. `Provenance::confidence` keeps its existing meaning: how far the source is trusted at all.
  - **ENR-11 ranks alternative titles by this row-level value**, then breaks ties by language preference.
  - **The order of the optional values is fixed:** category, posting time, canonical title, year, confidence. The section's `flags` byte has bits 0–4 for these, and bits 5–7 must be zero. The three lists follow.
  - **A section that claims nothing is refused.**
- **Canonical stored forms**, so that one value has one body:
  - **Language tags are stored in lower case.** BCP 47 tags compare without case (RFC 5646 §2.1.1).
    - Only the tag's shape is checked: `-`-separated subtags of 1–8 letters or digits, the first 2–8 letters, at most 35 bytes. The registry isn't consulted, so a tag added later still fits.
    - `und` means the language isn't known.
  - **Genres are normalised.** There are no ASCII capitals, no control characters, and words are separated by single spaces.
    - `lodestar_sources` lower-cases with full Unicode and folds all Unicode whitespace.
    - The store's check uses only properties that can't change: ASCII case, ASCII whitespace and `Cc` controls. So a Unicode update can never make a stored genre invalid, which a Unicode whitespace check could have done.
  - **No list may repeat an entry.** An alternative title's entry is its (language, title) pair.
  - **Newsgroups are never cut or re-cased**, because either could turn a name into another group's. A bad name is dropped instead.
- **The section's in-memory size counts toward `MAX_TOTAL`** (`Details::charged_len`): its text, plus 256 bytes for the section, 48 for each alternative title and 24 for each newsgroup or genre.
  - These charges are fixed numbers rather than `size_of`, so any blob one build accepts, every build accepts. Compile-time asserts keep them at least as large as the real sizes.
  - This keeps `unverified::MAX_ROW`'s bound on `decoded_size` true without changing `MAX_ROW`.
  - It costs at most about 2.4 KiB of the file list's room on an enriched row.
  - `MAX_PLAIN` and `MAX_STORED`, which the schema's `CHECK` holds, are unchanged. The section's ~150 bytes of framing fit in the existing slack, and tests cover the worst case.

## IDs stay in v1's `ids` (plan §4.3)
- **Beside a details section, `ids` hold only enrichment ids.** Both sides check this (`enrichment ids`). Version 1 claims keep accepting any scheme, as before.
  - The schemes are `imdb`, `tmdb`, `tvdb`, `anidb`, `anilist`, `mbid`, `olid`, `igdb`, `discogs`, `steam` and `wikidata` (`ENRICHMENT_SCHEMES`).
  - Each value has one spelling (`id_ok`), and no id may appear twice.
- **The value forms**, chosen so that no id names a person:

  | Scheme | Form | Refused |
  |---|---|---|
  | `imdb` | `tt` and 7 digits (zero-padded), or 8–10 digits with no leading zero | `nm` person ids, and a second spelling such as `tt00111161` |
  | `tmdb`, `tvdb`, `anidb`, `anilist`, `igdb`, `steam` | 1–20 digits, no leading zero | |
  | `mbid` | a lower-case UUID | |
  | `olid` | `OL` + digits + `M` or `W` | authors (`…A`) |
  | `discogs` | `r` or `m` + digits | artists |
  | `wikidata` | `Q` + digits | `P` and `L` ids |

  - **What the format can't tell apart:** a MusicBrainz or Wikidata id for a person has the same shape as one for a work. ENR-10's enricher contract writes ids for works only.
  - **Numeric ids may exceed `u64::MAX`** (up to 20 digits). ENR-11 must treat them as strings, or refuse the few it can't parse.
- **The schemes are closed only where a details section is.** An enrichment row with ids alone would store as version 1, with any scheme. So **ENR-10 always writes a non-empty section** (at least `match_confidence`), which brings every enrichment row under these rules. The runner carries this into ENR-10's brief.
- **The Newznab feed's own ids follow the same rules (UN-1).** UN-1 normalises them, for example adding `tt` to a bare IMDb number. Ids in schemes that aren't on the list, such as TVRage, are dropped.

## No personal fields
- **A row with a details section holds no description or publisher.** Both sides refuse them (`details claims`), as the adult section's rows do.
  - A plugin's overview can name the cast, and a Newznab `poster` is often an email address.
  - So UN-1 can't store a poster beside its v3 fields, and ENR-10 can't store an overview.
  - The rule is set now, because tightening it after v3 rows exist would make them undecodable.
- **The section describes a work, never a person** (owner §2.37, plan §4.3).
  - It has no field for cast, crew, an author, an uploader or a poster's address.
  - `Debug` shows counts and language tags, never titles, groups or genres.
  - A test lists every field, so adding a new one fails there first. A new field needs a new layout, and the owner if it could hold a personal detail.

## Clamping (`lodestar_sources::Claims::clamp`)
- **Free text is cut on a character boundary:** the category, the canonical title and each alternative title.
- **What can't be cut without changing its meaning is dropped:** a language tag, a newsgroup or an id. A tag is lower-cased first.
- **Duplicates are dropped, then each list is cut to its count.** An out-of-range year or confidence becomes `None`.
- **When nothing remains, the section is dropped.** A section left empty is never stored.
- **When claims came with an adult section, the details section is dropped**, whether or not the adult section itself is kept.
- **Beside a kept section:**
  - The description and publisher are dropped.
  - Only enrichment ids stay, each once. An MBID is lower-cased first.
  - The ids are filtered before the list is cut to 32, so invalid ids can't crowd out valid ones.
- **A property test checks clamp and store against each other.** Whatever a source sends, the clamped claims encode, round-trip, and are version 3 exactly when a section survives. Clamping twice changes nothing.
