# File-query resource follow-up decisions (local slice)

- **Bound retained file-ID results separately.** `FileSetCache` has an 8 MiB estimated allocation budget and retains the existing 4,096-entry ceiling. It charges vector capacity, key capacity, Arc storage and a conservative estimate of hash-table bucket capacity. Least recently used entries leave first; oversized results remain usable by their requesting query but are not retained. Clearing releases table capacity too. This is a new internal cache budget, not a change to an owner-set RSS target or the outer result-cache configuration (§8).
- **The cache limit is not a query-memory limit.** Active queries/leases can retain results after eviction, and compilation still allocates the current result vector and sorting workspace. Scale/peak-memory acceptance is deferred; an 8 MiB retained cache does not establish the 1 GiB process budget.
- **Cancellation reaches cold compilation.** Lease creation, stem fallback and facet recompilation pass the existing token through file enumeration. Checks happen before work, between segments, every 4,096 visited documents, before/after sorting, and before retention. Cancellation and deadline expiry propagate distinctly instead of becoming the empty-result fallback used for file-index errors. Sorting itself remains non-interruptible between its surrounding checks.
- **Keep existing public compilation behavior.** The existing synchronous compilation APIs use an uncancelled token; token-aware request paths use the fallible internal compiler. No HTTP contract or dependency changes.
