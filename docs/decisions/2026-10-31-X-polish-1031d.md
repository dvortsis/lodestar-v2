# X-polish-1031d decisions

Optional findings from the #290 and #292 reviews. Nothing is loosened: a classification re-queue stays pending in as many cases as before, and past the cap it marks more torrents, never fewer. No schema, wire, setting or log-event change.

- **`classify.requeue_pending` is capped at 64 distinct query texts; past that it becomes one full re-mark** (`crates/api/src/filters.rs`, #290 O1).
  - **Why 64:** the value stays a few KiB, and it's read and rewritten under the store lock on every rule change. 64 is far above what an admin changes between starts with search off. Past it, marking everything costs less than remembering every text.
  - **Stored under its own key, `classify.requeue_all` = `1`** (runner, on review). The collapse sets it and deletes the list key in one transaction. No query text can be read as it or clear it. Below the cap the list stays deduped.
  - **While it's pending:** a push is covered by it, a single text's clear leaves it, and with search on a rule change still marks its own matches at once.
  - **Clearing:** only `resume_requeues` at a start with search on runs it. It marks ids 1 to `Store::max_id` with one range UPDATE per `MARK_CHUNK` of ids, the same statement as `mark_unenriched_after` with an upper bound. That's one chunk per store lock, with the shutdown checked between chunks. A per-id UPDATE would take hours on a 10M–50M imported library. It clears only once every chunk is done, with no shutdown and no rule change (`class_gen`) since it began: the same terms as a text entry. The clear removes both keys, since the full re-mark covers any list beside it. A torrent stored after `max_id` was read is enriched under the rules in force by then.
  - **A downgrade only delays it.** An older binary doesn't know `classify.requeue_all`, so it never overwrites or clears the key, and it keeps its own list beside it. The next start of a binary that knows the key runs the full re-mark, which covers that list, and then clears both.
  - **A collapse caused by a refused removal stays** (`remove_class_rule`, "rule not found"). The drop never clears a full re-mark, which is deliberately conservative.
- **The soak report's memory columns say what they measure** (`docs/soak/tools/analyze_cr0.py`, #292). "Peak RSS (MiB)" is renamed "Peak working set (MiB)", since in Docker mode it's the cgroup working set, page cache included. A "Peak private (MiB)" column comes from `private_bytes` and reads unknown when the rows don't carry it. The JSON keeps `rss_max_mib` for older consumers and adds `private_max_mib`. The "RSS change" column is unchanged, since the brief named only the peak. Committed evidence reports aren't regenerated.
