# SRC-13 decisions (torrent-cache enrichment)

Slice session, 2026-11-05. Architecture §18.2 enrichment #3, §18.5, §18.7; v0.6 sources plan §4.2 SRC-13 and §5 Q3 and Q8; `docs/owner-decisions.md` §2.37 (Q3).

- **Two modules, joined by the host.** `lodestar_sources_plugins::torrent_cache` fetches and checks; `lodestar_pipeline::torrent_cache` chooses what may be looked up and judges what came back. Neither crate depends on the other, and the brief owns only these two files, so the host joins them. **Host wiring is SRC-13b (runner, 2026-11-05; its steps are at the end of this file):** register the plugin from its saved config with its `endpoints()`; feed its `Queue` from the pipeline's `Cursor` and from user interest; hand each `Verified` to `torrent_cache::judge`, and send an `Admitted` to the writer as verified metadata (the prepare stage's `Results`, with provenance "torrent cache") and a `Held` to the writer's hold path. `Admitted` doesn't carry provenance or the out-of-info claims yet: the host attaches `Verified::provenance()` and `Verified::claims()`, and `created by` and web seeds wait for claim fields (below). The writer needs a lease-free entry for metadata that didn't come through the pool; that change is in `writer.rs`/`worker.rs`, which this slice doesn't own. **Until that slice lands, nothing stores what a cache returns.**
- **Never a `private_source` hash, held three ways (§18.7).** `Lookup::new` returns `None` for a private key, and a request can only be built from a `Lookup` (`TorrentCache::request`), so no request exists for one. The pipeline's `Cursor` skips private items before they reach the queue. The plugin's tests show a private key turning into no lookup and no request; the pipeline's show the cursor never offering one.
- **Only user interest and unverified items (Q3).** `Why` has exactly those two cases. Interest has its own lane and is looked up first. The crawl's own keys are never offered: BEP 9 fetches them anyway, and each lookup tells a third party what you want.
- **Off by default, External consent, the list starts empty (Q3).** The manifest is `Consent::External`, off by default, with no built-in endpoints; SRC-4's `need` asks for the class's consent to be acknowledged before it's enabled. **The acknowledgement must cover the configured cache hosts (runner, review of #458), and today it can't.** SRC-4's version digests the manifest's `&'static` endpoint list, which is empty here, so an acknowledgement would cover nothing, and adding a host would never ask again. (`full_scrape` and `prowlarr` aren't precedents: their classes are None and Account, which have no endpoint acknowledgement.) The plugin framework has no way for a plugin's endpoints to come from its config, so **the plugin stays unregistered** (it isn't in any host list) until SRC-13b makes the acknowledgement cover the configured hosts, so that adding or changing one asks again (step 1 below). `endpoints()` is `None` while the list is empty, so nothing can be reached, and the plugin fails "needs setup" before any request.
- **No suggestion ships until the owner checks one (Q2, owner).** Q3 asks for suggestions to be shown; owner's rule §2.28 lets a source ship only once its recorded ToS check allows automated access. This session had no network to read any cache's terms, so `SUGGESTED` and the form's `examples` are empty; a test keeps the two equal and checks each suggestion against the config rules. **For the owner's queue (via the runner):** check iTorrents' terms (`https://itorrents.org/torrent/{HASH}.torrent`) or name another cache to suggest. Adding one is a one-line change.
- **Templates.** `{hash}` (lower-case hex) or `{HASH}` (upper case), exactly once, after the host. https only: the hash is the private part, and plain http would show it to every hop. No user name, password or fragment; public addresses only (`NetPolicy::notification(false)`, as `full_scrape`); at most 8 caches, 512 bytes each, none repeated. Errors name the rule, never the value.
- **Politeness (chosen by this slice; §2.26 numbers for the runner to confirm and flag under §2.19).** Each cache is one poll unit: at most one lookup a minute per cache (the kit's poll floor), one request every 10 s per host, back-off from a minute to six hours. About 1,440 lookups a day per cache at most: a third party's free service, and it caps how much any one cache learns. Coordinator only, so remote workers don't multiply it. Lanes hold 256 lookups each; a push past that is dropped and counted, and the cursor offers it again next round (`VERIFY_ROUND_SECS`, six hours, as SRC-2's verification cursor). A key held by several unverified rows is offered once per page.
- **Caps on bytes and time.** Bodies are streamed (`Client::poll_stream`) under 8 MiB, 30 s for the whole reply and 10 s for any wait; a larger declared length fails before the body is read. Parsing uses `lodestar-metainfo` (fuzzed) with the whole-file cap at the same 8 MiB, and half its default bencode values (1,000,000) and files (100,000). Redirects aren't followed: a cache that redirects to a mirror fails that lookup and the next cache is asked. A cache backing off or blocked is passed over for that lookup, not waited out, so one cache's six-hour back-off can't hold up every lookup behind it (counted as `skipped`).
- **The info dict is judged as BEP 9 delivers it (runner, review of #458).** A `.torrent`'s top-level `encoding` key isn't covered by the hash, and `TorrentFile::parse` lets it steer how non-UTF-8 names decode, so a cache could garble a GBK or Shift-JIS name past the name rules and still verify. The plugin keeps the info dict's raw span (`TorrentFile::raw_info`, a small `lodestar-metainfo` addition the runner approved, with its own test) and parses `Info` from it with no hint; the pipeline's `judge` takes those raw bytes, parses them hint-free and stores them (`prepare(info, Some(raw))`) exactly as the worker does a fetched dict. Tests: the same info dict under two `encoding` values gives one `Info`, and a rule on the hint-free name still holds a file whose `encoding` key lies.
- **The hash check (Q8).** A file is used only when its info dict's SHA-1 is the key, or its truncated SHA-256 for a v2 key; anything else is counted as mismatched and the next cache is asked. A `Verified` can be made only after that check; the pipeline's `judge` checks it again.
- **The full filter before storage (SRC-2's path).** `judge` mirrors the worker's `prepare_one` for a BEP 9 fetch: the floor's hash list, preparing (the raw dict archived as a fetched one is), enrichment, then `judge_classified` with your classification rules. It differs in one way: a drop or quarantine verdict comes back as `Held`, never as something to store, so a host that wires it can't store a held name by mistake. The code is duplicated rather than shared because `prepare_one` is private to `worker.rs`; a later slice that owns it can make both call one function.
- **What the fields outside the info dict become.** Trackers (only for a torrent not marked `private`, and only addresses with no user name, query or passkey-shaped path segment, and none on a literal LAN, loopback or link-local address, since the file outside the info dict is the cache's to change) and the comment (also dropped for a `private` torrent, whose comment often names its tracker) become claims; `creation date` (2001–2100) becomes provenance `published_at`, at Medium confidence, since those fields aren't covered by the hash. Web seeds and `created by` have no claim field yet; adding one is the claims format's owner's call. They stay on `Verified::torrent()` for the host.
- **Content encoding.** The kit has no gzip decoding, so a cache that always gzips its replies fails the parse and is counted invalid. None is assumed here; a later slice can add `Accept-Encoding` support in the kit if a cache needs it.
- **Nothing that can be logged shows a hash.** `Lookup`'s and `Verified`'s `Debug` leave out the key and the file, and neither module logs anything.

## What the wiring slice (SRC-13b, runner) must do
1. **Before registering the plugin, make its External acknowledgement cover the configured cache hosts** (runner, review of #458). Either let a plugin's consent endpoints come from its config, or bind the ack's version to the config's host list, so adding or changing a host makes the server ask again. Test both cases. Then build the plugin from its saved config (`Config::from_json`), register it, and give its egress `TorrentCache::endpoints()`. While that's `None`, no endpoint is reachable.
2. Feed its `Queue` from two places:
   - the pipeline's `Cursor`, paged a flush at a time, with each key made into `Lookup::new(key, Why::Unverified, false)`;
   - user interest (a search hit, a saved search, a detail view), with `Lookup::new(key, Why::Interest, private_source)`.
   **`private_source` comes from the store, never from the caller (runner):** the unverified row's flag or the stored torrent's flags for that key. A key the store doesn't know isn't looked up. Add an end-to-end test that an interest lookup for a private torrent or item never reaches the plugin's fetch.
3. Take each `Verified` from the plugin's channel and call `torrent_cache::judge(engine, preparer, v.key(), v.info_raw(), now)` with the current filter engine and the store's preparer.
4. Add a lease-free entry to the writer, beside the pool's `Results`:
   - `Judged::Store(Admitted)` commits as verified metadata. The provenance is `torrent_cache::PROVENANCE` and the plugin's source bit, and `Verified::claims()` and `Verified::provenance()` are stored as that source's claims.
   - It promotes an unverified item holding the key, keeping its id (§18.5).
   - The writer judges again if `Admitted::version` is behind the engine.
5. `Judged::Held` goes to the writer's hold path, as a held ingest verdict does (tombstone or quarantine, rule id and evidence only). `Judged::Refused` is counted and dropped.
6. Show the plugin's `Stats` on the status page.
