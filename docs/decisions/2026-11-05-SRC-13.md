# SRC-13 decisions (torrent-cache enrichment)

Slice session, 2026-11-05. Architecture §18.2 enrichment #3, §18.5, §18.7; v0.6 sources plan §4.2 SRC-13 and §5 Q3 and Q8; `docs/owner-decisions.md` §2.37 (Q3).

- **Two modules, joined by the host.** `lodestar_sources_plugins::torrent_cache` fetches and checks; `lodestar_pipeline::torrent_cache` chooses what may be looked up and judges what came back. Neither crate depends on the other, and the brief owns only these two files, so the host joins them. **Host wiring needed (the sources wiring slice, or SRC-14):** register the plugin from its saved config with its `endpoints()`; feed its `Queue` from the pipeline's `Cursor` and from user interest; hand each `Verified` to `torrent_cache::judge`, and send an `Admitted` to the writer as verified metadata (the prepare stage's `Results`, with provenance "torrent cache") and a `Held` to the writer's hold path. The writer needs a lease-free entry for metadata that didn't come through the pool; that change is in `writer.rs`/`worker.rs`, which this slice doesn't own.
- **Never a `private_source` hash, held three ways (§18.7).** `Lookup::new` returns `None` for a private key, and a request can only be built from a `Lookup` (`TorrentCache::request`), so no request exists for one. The pipeline's `Cursor` skips private items before they reach the queue. The plugin's tests show a private key turning into no lookup and no request; the pipeline's show the cursor never offering one.
- **Only user interest and unverified items (Q3).** `Why` has exactly those two cases. Interest has its own lane and is looked up first. The crawl's own keys are never offered: BEP 9 fetches them anyway, and each lookup tells a third party what you want.
- **Off by default, External consent, the list starts empty (Q3).** The manifest is `Consent::External`, off by default, with no built-in endpoints; SRC-4's `need` asks for the endpoint list to be acknowledged. `endpoints()` is `None` while the list is empty, so nothing can be reached, and the plugin fails "needs setup" before any request. `SUGGESTED` (one entry, iTorrents) is shown in the form's `examples`, never in its `default` (`[]`).
- **Q2 for the suggestion (owner).** Owner's rule §2.28: a plugin ships only if its recorded ToS check allows automated access. This session had no network to read iTorrents' terms. Sent to the runner for the owner's queue: check them, or drop the suggestion. The list stays the user's either way; nothing depends on the answer but `SUGGESTED`.
- **Templates.** `{hash}` (lower-case hex) or `{HASH}` (upper case), exactly once, after the host. https only: the hash is the private part, and plain http would show it to every hop. No user name, password or fragment; public addresses only (`NetPolicy::notification(false)`, as `full_scrape`); at most 8 caches, 512 bytes each, none repeated. Errors name the rule, never the value.
- **Politeness (runner, §2.26 numbers, flagged under §2.19).** Each cache is one poll unit: at most one lookup a minute per cache (the kit's poll floor), one request every 10 s per host, back-off from a minute to six hours. About 1,440 lookups a day per cache at most: a third party's free service, and it caps how much any one cache learns. Coordinator only, so remote workers don't multiply it. Lanes hold 256 lookups each; a push past that is dropped and counted, and the cursor offers it again next round (`VERIFY_ROUND_SECS`, six hours, as SRC-2's verification cursor).
- **Caps on bytes and time.** Bodies are streamed (`Client::poll_stream`) under 8 MiB, 30 s for the whole reply and 10 s for any wait; a larger declared length fails before the body is read. Parsing uses `lodestar-metainfo` (fuzzed) with the whole-file cap at the same 8 MiB. Redirects aren't followed: a cache that redirects to a mirror fails that lookup and the next cache is asked.
- **The hash check (Q8).** A file is used only when its info dict's SHA-1 is the key, or its truncated SHA-256 for a v2 key; anything else is counted as mismatched and the next cache is asked. A `Verified` can be made only after that check; the pipeline's `judge` checks it again.
- **The full filter before storage (SRC-2's path).** `judge` mirrors the worker's `prepare_one` for a BEP 9 fetch: the floor's hash list, preparing (without archiving the raw dict, as importers do), enrichment, then `judge_classified` with your classification rules. It differs in one way: a drop or quarantine verdict comes back as `Held`, never as something to store, so a host that wires it can't store a held name by mistake. The code is duplicated rather than shared because `prepare_one` is private to `worker.rs`; a later slice that owns it can make both call one function.
- **What the fields outside the info dict become.** Trackers (only for a torrent not marked `private`, and only addresses with no user name, query or passkey-shaped path segment) and the comment become claims; `creation date` (2001–2100) becomes provenance `published_at`, at Medium confidence, since those fields aren't covered by the hash. Web seeds and `created by` have no claim field yet; adding one is the claims format's owner's call. They stay on `Verified::torrent()` for the host.
- **Content encoding.** The kit has no gzip decoding, so a cache that always gzips its replies fails the parse and is counted invalid. None is assumed here; a later slice can add `Accept-Encoding` support in the kit if a cache needs it.
