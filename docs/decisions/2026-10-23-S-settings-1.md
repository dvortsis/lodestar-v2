# S-settings-1 decisions

The Settings route, shell and registry (§10.10.2, §10.10.8), Overview, restart and search (parts 2 and 3 add to this file in their PRs). Items marked **(§2.19)** refine an owner decision and are for the runner to flag; none loosens one.

## Part 1: route, shell and generated screens

### Registry
- **The registry is resolved against the schema** (`buildRegistry(index)` → `{ screens, get, fieldsFor, screenOf, doubleClaims }`), not a set of free functions: `screenOf` and the interim screens need the index, so `fieldsFor(screen, index)` is a convenience over it. A registered screen shows before the index arrives; a generated screen waits for it.
- **The Keyboard fallback claim** (`keyboard` → `preferences` / `keyboard`) is a constant in `registry.ts` with a `TODO(shortcuts)`; it only applies to a registered screen whose id is `keyboard` and that declares no `sections`.
- **Interim screens** take the id and title of the section (`/settings/logging`), group `preferences` for `preferences` and `content`, `system` otherwise; `preferences` is instant, everything else staged. A section whose id is already a registered screen's id gets no interim screen (dev error).
- **A screen with `sections` all `preferences` is instant,** so S-appearance's generated groups get the right mode without a new field.
- **Discovery** also accepts a default export of a screen or an array, deduplicating one object exported twice (S-keys exports `screen` and default). An unknown `group` or a repeated id is skipped with a dev error.

### Messages and the 45 KB budget (owner, 2026-10-23: never raised)
- **Server messages load per section** (runner answer 1): `form/message-map.gen.ts` now writes `form/message-map.ts` (a loader per unit) and `form/message-map/<unit>.ts`; `loadSettingMessages(sections)` in `form/messages.ts` resolves before a form mounts. `common` holds the group headings and each section's label and help, so the navigation and Overview need no section's fields. `settingText` reads what is loaded and is undefined for the rest (the field name stays the fallback, so the engine's tests are unchanged). The generator formats its output the way Prettier does (tabs, no trailing comma, wrapped past 100 columns) without depending on it. Hub edits: `form/message-map.gen.ts`, `form/messages.ts`, `form/index.ts` (one export) and their tests.
- **`settings_ui_*` keys are never server keys** and are skipped by the generator.
- **The `data` group** is worded "Data" for General's data folder and Logging's data kinds; per-section group keys in `groupFields` remain an engine follow-up.

### Screens
- **Advanced's open state is remembered per screen** under `lodestar.settings.advanced.<screen>` as the list of open group ids (a group has its own disclosure). A deep link, search, the error summary, or Show changed only opens one without remembering it.
- **Show changed only opens every Advanced that holds a changed field,** since a changed advanced value hidden behind a click defeats the filter.
- **Show changed only lives in `?changed=1`** and is kept in component state (`replaceState` moves the address bar, not `page.url`), following `page.url` on a real navigation.
- **Layout CSS uses `@media (min-width: 64rem)`** (= `--breakpoint-x-large`) in component `<style>` blocks instead of `@variant x-large`: svelte-check warns on the at-rules, as the engine's decisions noted.
- **Icons per screen:** Crawler `gauge`, Network & VPN `network`, Storage & retention `hard-drives`, Search & ranking `magnifying-glass`, General `sliders`; the shell's `gear` for any screen without one.
- **The group headings in the navigation are `<h2>`s** inside the `<nav>`; the screen's `<h1>` follows in the manuscript column.
- **Network's lockout dialog** is this screen's `form.gate('disruptive', …)` and loads on the first disruptive save. `dht_port` and `dht_enabled` alone use the preview's warnings, else a sentence of the screen's own.
- **The reachability panel** refreshes every 30 s while the page is visible and again when it becomes visible; its code loads when Network opens.

## Part 2: Overview, restart banner and the address check

- **The layout fetches `/system` once** and refreshes it on every `settings` event and resync; the Overview, the badges, the banners and the restart flow all read it. Attention items are computed by a lazily loaded module once `/system` and the schema are in, and again after each refresh; a newer run supersedes an older one.
- **The Overview's own rows** are: a restart waiting (`restart`), the DHT port unreachable (`problem`, from `GET /network/check`; the port is the configured `dht_port`, else the one others see), an address awaiting confirmation (`problem`) and an address reverted (`notice`). Each registered screen's `attention(ctx)` adds more, run in parallel and isolated; ordered problem, restart, notice, then by screen order. A failed network check leaves its row out and the page says so once.
- **"Changed from default" is the server's list counted per screen** (`system.diagnostics.changed` → `screenOf(name)`); the client adds nothing up beyond that tally, and the link is `/settings/<id>?changed=1`.
- **Badges** come from the same items: "{n} problem(s)" (a problem wins) and "Restart needed" for a screen holding restart-pending fields; the count is in the link's accessible name ("Network & VPN, 1 problem") through a visually hidden suffix.
- **The skeleton shows after 300 ms** of waiting, so a fast answer never flashes.
- **The banners and the restarting state are one lazily loaded chunk** brought in only when there is something to show, so they never count against the Settings routes' first view.
- **Restart now asks first** (`ask()`, Cancel focused: "Crawling pauses for about {estimate}"), then `POST /system/restart`, then a full-page "Restarting…" state. It polls `/healthz` 1 s doubling to 8 s for 2 minutes; **an answer from `/healthz` alone isn't proof**, since the old process answers until it shuts down, so it also needs `/system.started_at` to differ from the one before the restart (a `401` or any non-5xx answer from `/system` counts as up, as the session may be gone). After 2 minutes it says what to check (the container's logs, `lodestar healthcheck`) with Try again. Restart-pending fields are checked by the reload itself: the banner is still there if anything still waits.
- **Where Lodestar can't restart itself the banner says how,** by `deployment.kind` (container for Docker and Unraid, the Windows service, the portable build), else the server's `restart.hint`; a `409 restart_unavailable` shows the server's message.
- **A pending address change** (`awaiting_restart`) makes the restart poll the new address (`new URL('/healthz', url)` with `mode: 'no-cors'`; any answer is up), then `location.assign(new URL('/settings/network', url))`. Only `http:` and `https:` addresses are followed; anything else is shown as text with "Open it yourself". `awaiting_confirmation` is a banner on every Settings page with Keep (`POST /system/address/keep`) and Go back (`POST /system/address/revert`, then the restart flow toward `previous_url`); a `409 no_address_change` refreshes `/system`. The countdown is hidden from screen readers, and the banner is announced once with a sentence that doesn't change.
- **Review** lists each waiting field, its screen as a link and the saved value (`GET /settings/{section}`); the running value isn't in the API.

## Part 3: search, config.toml, backup and reset

- **Search** is in-house: NFD with combining marks dropped and `toLocaleLowerCase`, word prefixes (plus a plain substring for Han, Kana and Hangul, which have no spaces), every word of the query must match, ranking label > keywords, `config.toml` key, `LODESTAR_*` name > group > help, an exact label first. The index (every field, screen title and hand-built `search()` entry) and the results load on the first focus; the box itself is the only eager part. Values are fetched once per open for the sections the results are in.
- **No match** links to `{system.repository}/tree/main/docs/user` in a new tab (runner answer 5); with no repository known there is only the sentence.
- **`/` focuses the box** through a `settings` key scope pushed by the layout.
- **View as config.toml** lists saved values that aren't at their default, never a `writeOnly` field. A setting with no `x-config` key (only the app saves it) appears in the environment block only. The environment block has scalars only: lists and maps come from `config.toml`; a value with a space, quote, `#`, `$` or backslash is double-quoted.
- **Export** is a plain `fetch` of `GET /settings/export` (the typed client reads JSON, the answer is TOML), saved as `lodestar-settings.toml`. **Import** checks the 64 KiB size before sending; the dry run and the apply use the generated types; Undo sends one `PATCH /settings` with each change's `from` where it came from the app (`db`), else `null`, guarded by the revisions after the import, and is offered for 10 s.
- **Reset all** leaves Preferences alone and skips read-only and `writeOnly` fields (a saved secret is removed only through its own confirmation, §10.10.7). It counts `source === 'db'` values first and says so when there are none.

## Follow-ups
- **Backend:** per-section group keys or a distinct `x-group` for `data`; no "hides config.toml" flag; no running value for restart-pending fields; no egress/VPN, retention, hot/cold paths or backup-schedule fields; no `default` per property (from the engine); no backups yet, so the Overview has no "no backup in 14 days" row.
- **UI:** the Keyboard screen onto the engine and its `sections`/`icon` in `screen.ts`; the engine's instant-mode lazy split; Settings entries in the command palette and the status pill's "Restart needed" (`lib/shell`).
