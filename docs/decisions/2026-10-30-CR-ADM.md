# CR-ADM decisions (PR pending)

Bounded admission, wakeup and backpressure between the fetch pool and the DHT actor (DUR-02–04; master plan H2, `docs/decisions/2026-10-30-master-plan.md`). It meets the "Candidate backpressure contract" in `docs/plan/2026-10-27-crawler-experiment-protocol.md`. This is the Phase 1 design; the code waits for the runner's OK. Everything here is behind one switch that is off by default. No cap, timeout or rate changes: the pool's `max_lookups` (256), the actor's 32 owned requests, `lookup_wait` (30 s), `retry_backoff` (120 s), `LOOKUP_DEADLINE` (25 s) and the 64-query budget all stay.

## Today's path (`origin/main` at `ac20c916`)
1. The pool sends a key due a lookup while `lookups < max_lookups` (256). `on_discovery` and the back-off timer call `request_peers` directly; only `dispatch` drains `lookup_backlog`. A new arrival therefore takes a free position ahead of keys already in the backlog.
2. `request_peers` `try_send`s one `PeerRequest { key, admit }` to every finder channel (the DHT plugin's, 1024 deep). The plugin forwards it with `NodeHandle::request_peers`, which `try_send`s onto the actor's 64-deep command channel. If that's full, `admit` is dropped.
3. The actor admits while `get_peers_queue.len() + active_get_peers < 32`. Otherwise it answers `None`, with the precedence caller-closed, paused, capacity. It starts queued requests on its 1 s maintenance tick. One owned request runs one lookup leg per family under one owner id, with `remaining = families.len()`. The legs share a 3-RPC in-flight budget and the 64-query cap. The slot frees when the last leg finishes (`finish_lookup`, `remaining == 0`).
4. The pool polls its admission receivers every 25 ms. A refusal (`None`) or a lost acknowledgment (closed) ends the request unaccepted: `lookup_unaccepted` goes up, no attempt is used, and the key backs off for `retry_backoff` (120 s). The freed position goes to the next key at once. At saturation the pool re-asks a full actor about every 25 ms per position, which is the 95.5M-rejections-against-111k-admissions shape in CR-0 (#189). Meanwhile backed-off keys are evictable, so 98.86% of evictions come before an accepted lookup.

## The permission unit is the logical request
- **One permit per logical pool request per finder, covering every address-family leg.** The actor's slot is already the logical request: `dht_peer_active`/`dht_peer_queued` count "logical owned requests, across configured families; combined cap 32" (`docs/metrics.md`). The pool's attempt is also per logical request: the first accepted finder consumes it.
- **Why not one per family leg, with both families accepted.** On a dual-stack node, a request runs a v4 leg and a v6 leg under one owner.
  - *Partial grants.* Per-leg permits would allow a half-granted request (v4 yes, v6 no). That request either waits holding one permit, which can deadlock with other half-granted requests, or runs one family and still consumes a full attempt.
  - *Returns without a free slot.* The v4 leg usually finishes first. Returning its permit while the v6 leg runs would let a new request in while the owner slot is still occupied. The actor would refuse it on capacity, which is the churn this slice removes.
  - *A changed baseline.* A 32-leg budget is 16 dual-stack requests but 32 single-stack ones, so the screen would also be testing a smaller cap (H1, CR-1c's subject).

  One permit per logical request returns exactly when the actor frees the slot, whichever leg finishes last. Test (Phase 2): a dual-stack fixture where both legs are accepted, and each leg order holds one permit until the second leg ends.
- **The permit is a token held where the slot is held.** Each credited finder gets a `tokio::sync::Semaphore` with `lodestar_dht::PEER_REQUEST_CAPACITY` (the actor's existing 32, now exported) permits. An `OwnedSemaphorePermit` travels in the request: `PeerRequest.permit`, then the actor's queue entry, then its `PeerRequest` struct. Dropping it returns the credit. One request can't return it twice, and losing the request can't leak it. Every terminal boundary drops the request, so each returns its permit (table below). The token adds no new dependency: both crates already use tokio, and `lodestar-dht` still doesn't depend on `lodestar-sources`.
- **Multiple finders.** A request is sent when it holds a permit from every open, credited finder. A finder without credits (none in production) is asked as today. Production has one finder (the DHT), so this is one permit per request.

## Bounds, wakeup and fairness
- **Waiters live in the pool and cost no task, future or socket.** A waiter is an entry in `LookupQueued`, so the count is bounded by `max_pending` (200,000): at most one live waiter per entry. Each semaphore has at most one waiting future, the pool's wakeup. The actor's own queue stays inside its 32. There is no actor-side waiter list, so nothing can grow without bound there.
- **The queues hold no stale garbage.**
  - There are two FIFOs, `interactive` (interest keys) and `background`. Copies made stale by eviction or state changes are skipped when popped, as `lookup_backlog` does today.
  - Each FIFO is compacted when it grows past 2 × its live waiters + 1,024, the `admitted` pattern.
- **Grant rule:**
  - A key due a lookup gets a permit at once only when one is free *and* both FIFOs are empty. Otherwise it joins the back of its FIFO.
  - The rule covers new arrivals, restored keys and back-off retries alike, so none overtakes a key already waiting. Today's direct send from `on_discovery` is the indefinite advantage the brief forbids.
  - Requeued work goes to the front of its FIFO: a refused or unacknowledged send, and accepted work the actor dropped on pause. That work has already waited its turn.
- **Bounded interactive bursts:**
  - Interactive waiters are served first, but at most `INTERACTIVE_BURST = 4` in a row while background waiters exist. The next grant then goes to background.
  - Background therefore gets at least 1/5 of the permits under any interest load. Interest gets at least 4/5 while it has waiters.
  - Background is FIFO by the time a key started waiting, across sources. Per-source fairness of retention is DUR-09's candidate, not this one.
- **Wakeup and coalescing:**
  - The pool's `select!` gains one arm: `acquire_owned()` on the finder's semaphore. It's armed only when the switch is on, the pool isn't paused, a live waiter exists and the pool holds no unused permit.
  - It resolves only when a permit is returned: no polling, no timer, no spin.
  - On wake, `dispatch` uses that permit, then `try_acquire_owned()`s in a loop, granting one waiter per permit until permits or waiters run out. Any number of returns between two turns of the loop are coalesced into one drain.
  - A woken permit with no live waiter left (all evicted meanwhile) is dropped at once and counted as `unused`.
- **Refusals cost no attempt, no back-off and no spin:**
  - A request that held permits can still come back `None` (paused, or a legacy un-owned `GetPeers` taking a slot; no production caller sends those) or closed (the command channel was full or closed, the acknowledgment was lost, or the plugin stopped).
  - Under the switch, it is requeued at the front with no attempt used, `lookup_unaccepted` counted as today, and **no `retry_backoff`**.
  - The finder is held for `REFUSAL_HOLD = 1 s` (one actor tick) before the pool asks it again. Without the hold, a refusal would hand the permit straight back to the same waiter: a spin.
  - The hold doesn't escalate, and the next accepted admission clears it. So a run of refusals costs at most one request per finder per second, and recovery starts on the first free permit: no permanent back-off.
- **The lookup timer starts at the send, never during the wait.** Waiting is not an attempt and is never charged to `lookup_wait`. A waiting key leaves the wait only by a grant, by peers arriving (it becomes `Ready`), or by eviction.
- **Not in this switch: the actor's 1 s start latency.** The actor still starts queued requests on its tick, so a returned permit can turn into a running lookup up to 1 s later. Both arms have this. Starting at admission would change lookup latency, H1's variable, and mix two causes in one screen. It's recorded here as a candidate for CR-1c, not done.

## Who returns permission at each terminal boundary
"Returns" means the holder drops the permit. The boundary label is the one the new counters use.

| Boundary | Holder at that moment | Returned when | Counter (`boundary`) |
|---|---|---|---|
| Finder channel full or closed at `try_send` | pool | at once; the request never left | pool `finder_full` / `finder_closed` |
| Command channel full or closed (plugin → actor) | `NodeHandle::request_peers` | at once; it drops the command with `admit` | dht `handoff_failed` |
| Actor refuses (caller closed, paused, capacity) | actor `on_command` | before it answers `None` | dht `refused` |
| Acknowledgment lost (`admit.send` fails) | actor | at once; nothing queued | dht `ack_failed` |
| Caller cancels while queued (receiver dropped: pool timeout, eviction, peers arrived, entry lost) | actor queue | on the next command or tick (`retain` of closed callers) | dht `cancelled_queued` |
| Pause drops queued owned requests (CR-0f) | actor queue | in `SetPaused(true)` | dht `paused` |
| Caller cancels while active (same causes) | actor `PeerRequest` | when the last leg is reclaimed in `finish_if_due`/`finish_lookup`, at most one tick | dht `cancelled_active` |
| Completion, including empty results and the 25 s deadline | actor `PeerRequest` | in `finish_lookup` when `remaining` reaches 0 | dht `completed` |
| Peers arrive while the lookup runs; fetch success or failure | n/a | the permit went back at completion or cancel, above; fetching never holds one | — |
| Eviction or loss of a waiting key | none held | nothing to return; the waiter is skipped when popped | — |
| Woken permit with no live waiter | pool | at once | pool `unused` |
| Shutdown or drain | actor queue and `PeerRequest`s; pool's unused permit | the actor drains them after its loop, before #216's `finish()`; the pool drops its own permit on exit | dht `shutdown`, pool `unused` |

- **Why the permit stays with the actor until it reclaims a cancelled request:** that request's RPCs are still in flight and its slot is still counted. Returning the permit earlier would let the pool send work that the actor refuses on capacity. The actor reclaims it within one tick, so no permit outlives an eviction by more than that.
- **Conservation, asserted in every Phase 2 fixture:** pool grants = Σ pool returns + Σ dht returns + permits in use. After drain, permits in use = 0 and `available_permits() == 32`. The existing `assert_peer_ownership_drained` and the pool's `lookups == 0` hold too.
- **A late acknowledgment from an old generation can't attach to a replacement entry:**
  - *Receivers die with their request.* Evicting or losing an entry removes its `Request`, which drops its admission and completion receivers. An acknowledgment sent to them has no reader, and the actor sees the caller closed.
  - *Replacement entries are new requests.* A new lifetime with the same hash creates a new `Request` with fresh receivers.
  - *Generations are unique across lifetimes.* Today each entry's `generation` starts at 0, so a timer left behind by an evicted lifetime can match a replacement entry's generation and expire its lookup early. This is a pre-existing defect. Under the switch, generations come from one pool-wide counter, so a new lifetime never reuses an old one's.
  - *Owner ids stay unique in the actor.* The existing `next_request` skip, tested by `cancelled_same_hash_retry_ignores_the_old_wire_response`.
  - Off, numbering is unchanged, so the goldens stay byte-identical. Making the fix unconditional is the runner's call, after checking it leaves the goldens unchanged.

## Waiting is not an attempt
- **Cancellation while waiting sends nothing and leaves nothing.** A waiter has sent no request and holds no permit. Eviction removes the entry, and the FIFO copy is skipped. `fetch_admission_wait_cancelled_total{reason="evicted"}` counts it. Peers arriving make it `Ready` (`reason="peers"`).
- **Cancellation after admission releases both legs exactly once.** Both legs check the shared owner's closed reply, and the permit is dropped once, when the owner record is removed at `remaining == 0`. The completion goes to a closed receiver and counts in `dht_peer_cancelled_total` only, as today.
- **Retries stay distinguishable from arrivals.** Every wait and grant carries `kind`:
  - `arrival`, from a discovery or a restored queue;
  - `retry`, from the back-off timer, or interest raised during back-off;
  - `requeue`, after a refusal, a lost acknowledgment or a pause drop.

  `fetch_retry_unaccepted_total` keeps its meaning.
- **No permit is kept after eviction** beyond the actor's one-tick reclaim (table above).

## Pause and resume (CR-0f's order is kept)
- **Pause, still pool first:** the paused pool disarms its wakeup and grants nothing, and waiters stay queued at no cost. Already-sent requests then go one of three ways:
  - queued at the actor: dropped by `SetPaused(true)`, so the permit returns (`paused`) and CR-0f's `requeue_cancelled` puts the key back with no attempt used;
  - running: they finish and answer as today;
  - in flight to a paused actor: refused, so the permit returns (`refused`) and the key is requeued with no back-off.
- **Resume, still DHT first, then the pool** (`apply_paused`, #200): the pool re-arms only on its own `SetPaused(false)`. That arrives after the DHT's change, so the first grants reach a running actor. Even if a refusal slipped through, it would cost one 1 s hold, not 120 s.
- **No change to `crates/pipeline/src/control.rs`.** Phase 2 adds a switch-on test that a resume causes no paused refusals.

## Closed finder, shutdown and drain
- **A closed finder:** `try_send` returns `Closed`, so the permit returns (`finder_closed`) and that finder is marked closed for good: it is never woken for or asked again. With no open finder left, keys take today's no-finder path (`lookup_unaccepted`, back-off).
- **Shutdown with waiters:**
  - The pool's loop exits and drops its unused permit and every `Request`. Waiters are saved in the snapshot with their attempts unchanged; a waiter never used one.
  - The actor drains its queue and active requests after its loop, counting `shutdown`, then runs #216's `finish()` unchanged.
- **Composes with #216.** #216 changes `Actor::new` (the `proof` field), the start of `maintain`, its save condition and suppression gauge, `sample_tick`, and the `save()`/`finish()` split. This slice touches different spots:
  - `on_command`'s `RequestPeers` and `SetPaused` arms;
  - the queue entry type and `PeerRequest`;
  - `finish_lookup`'s owner removal;
  - one drain call just before `actor.finish()` in `run`.

  The only adjacent line is that call, and it is added after #216 merges.

## Metrics
New series, apart from the existing ones, which keep their meaning. The existing ones are `dht_peer_admitted_total`, `dht_peer_rejection_reasons_total`, `dht_peer_ack_failed_total`, `dht_peer_command_*`, `fetch_finder_*`, `fetch_lookup_unaccepted_total`, `fetch_retry_unaccepted_total` and `fetch_evicted_service_total`. All new series are zero, or absent, with the switch off. The `docs/metrics.md` text, added as a new section after "Hardened baseline diagnostics":

> ## Coordinated admission (CR-ADM, 2026-10-30)
>
> Present only with `dht.coordinated_admission` on ([the decision](decisions/2026-10-30-CR-ADM.md)). A permit is one logical peer request's slot at one finder, covering every address family; there are 32 per finder. These are event counts, not unique hashes, network attempts or cohort conversion. The existing admission counters keep their meaning.
>
> | Series | Meaning |
> |---|---|
> | `fetch_admission_waits_total{kind}` | A key due a lookup that joined the permission queue instead of being granted at once. `kind` is `arrival` (a discovery or a restored key), `retry` (after back-off) or `requeue` (after a refusal, a lost acknowledgment or a pause drop). |
> | `fetch_admission_wait_cancelled_total{reason}` | Waiters that left without a request: `evicted`, or `peers` (peers arrived first). No network attempt is made. |
> | `fetch_admission_wakeups_total` | Times a returned permit woke the pool. One wakeup can grant several waiters. |
> | `fetch_admission_grants_total{kind,class}` | Permits granted to a request, by `kind` as above and `class` `interactive` or `background`. |
> | `fetch_admission_refusals_total{reason}` | Requests that held permits but weren't accepted: `refused` (the actor answered no; its reason is in `dht_peer_rejection_reasons_total`) or `unacknowledged` (the handoff or acknowledgment was lost). Neither uses an attempt or a back-off. |
> | `fetch_admission_holds_total` | 1 s holds on a finder after a refusal. |
> | `fetch_admission_permit_returns_total{boundary}` | Permits returned in the pool: `finder_full`, `finder_closed`, `unused`. |
> | `dht_peer_permit_returns_total{boundary}` | Permits returned in the actor: `completed`, `cancelled_queued`, `cancelled_active`, `paused`, `refused`, `ack_failed`, `handoff_failed`, `shutdown`. |
> | `fetch_admission_waiters{class}` | Live waiters now. |
> | `fetch_admission_permits_in_use` | Permits held now, across finders. |
>
> At any moment, `fetch_admission_grants_total` = the sum of both `…permit_returns_total` series + `fetch_admission_permits_in_use`. A gap means a leaked or duplicated permit.

- **Where they live:** the pool counters go in `PoolStats` and the dht ones in `Stats`, both exported where the existing `fetch_*`/`dht_peer_*` series are (`crates/lodestar/src/metrics.rs`). That file is a shared-file edit, so the PR names it for the runner.

## The switch
- **`dht.coordinated_admission`, a bool, off by default.**
  - It's set in `config.toml` (`[dht] coordinated_admission = true`) or with `LODESTAR_DHT_COORDINATED_ADMISSION=true`, read at start. A bad value is a config error.
  - It's not in the Settings UI or the runtime settings registry; changing it needs a restart.
  - It follows `dht.safe_restart`'s precedent (#216). It sits under `[dht]` because the DHT is the only peer finder and the actor is the permission's authority.
- **Plumbing:**
  - `Config::pipeline_config()` sets `PoolConfig::coordinated_admission`.
  - The pipeline (`crates/pipeline/src/lib.rs`, where finder channels are made) creates one semaphore per peer-finder source when it's on, and passes it in a new `PoolIo::finder_credits` parallel to `peer_finders`.
  - The DHT plugin forwards `PeerRequest.permit` with a new `NodeHandle::request_peers_with(hash, admit, permit)`. `request_peers` stays and passes `None`.
  - CR-SIM gains `Switches { coordinated_admission }`, which `apply` writes into `PoolConfig`. The sim wires semaphores as the pipeline does.
- **Off is today's behaviour exactly:** no semaphore, `permit: None` everywhere, no new branch taken in the pool or actor, generation numbering unchanged, and the new counters stay 0. The three CR-SIM goldens (`healthy`, `high-latency`, `admission-pressure`) must stay byte-identical, which proves the switch inert (CR-SIM's convention).
- **Release:** it isn't in v0.5.1 unless the release delta review says so.

## Phase 2 tests (planned)
- Pool and actor unit tests, on tokio's paused clock or with conditions on ≥ 10 s deadlines, and no fixed sleeps:
  - saturation;
  - recovery after saturation, with no back-off left;
  - pause/resume while waiting and while admitted;
  - cancel while waiting and while admitted, on dual stack;
  - a closed finder;
  - drain and shutdown with waiters;
  - interactive bursts against background progress;
  - a stale timer against a replacement entry.
- The protocol doc's three replays with the switch off and on: A/B/C/A rejection churn, retained A through its retry deadline, and accepted-and-held A under arrivals. Each asserts ownership drain and permit conservation.
- **A CR-SIM screen:** `admission-pressure` with the switch on, against its baseline over `SCREEN_SEEDS`. The report gives rejections, accepted lookups, useful service before eviction, and stored/searchable, judged against the measured 20–28% noise floor. It is re-checked at the production pool defaults, as CR-SIM requires for that scenario.
