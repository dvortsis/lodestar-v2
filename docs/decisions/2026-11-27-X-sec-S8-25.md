# X-sec-S8-25 decisions (S8-25, important; surface plugin TLS)

- **Certificate verification follows the connection's route** (`crates/integrations/src/tls.rs`, `verification_for`). One rule for every routed client: the plugin HTTP client (`GuardedClient::with_route`, which companions' fetches also use), the plugin WebSocket client (`crates/sources`, `Roots::Platform`) and the IRC client (`crates/sources-irc`, `Roots::Platform`). A server's own CA (`Roots::Only`) is unchanged: webpki over just those roots, as before.
  - **`Route::Direct`:** the operating system's verifier (rustls-platform-verifier), unchanged. A direct connection already uses the OS default network, so the OS's own trust decisions, its enterprise roots and its revocation checks stay as they were. Every client built with `Route::Direct` is untouched; a client built on another route (plugin HTTP, and companion downloads when Lodestar's egress setting is a route) takes the self-contained verifier below.
  - **Any other route** (a bound address, a bound interface, a SOCKS5 proxy with either DNS mode): **webpki in this process**, over the bundled Mozilla roots (`webpki-root-certs`) plus every root in the OS store that webpki can use (`rustls-native-certs`, read once per process from local storage), with no revocation lists. Validation is a computation on the certificates the server sent. Why: a routed connection then behaves the same on every platform, as it already did on Linux, and its verification depends only on its own handshake.
  - **Why both root sets:** the bundled set gives the same trust on every platform, and a Docker image without a CA bundle still verifies; the OS store keeps a root the user added on purpose (a private indexer's CA) working off the direct route.
- **Per platform, on a routed connection:**
  - **Linux, Docker and Unraid:** the same as before in effect (the platform verifier was already webpki over the OS roots there); the bundled roots are added.
  - **Windows:** webpki over the bundled roots and the Windows ROOT store's roots, instead of the Windows certificate verifier. Revocation isn't checked on these routes; the bundled set covers the public web CAs.
  - **macOS:** webpki over the bundled roots and the keychains' roots, instead of the macOS trust evaluation. Revocation isn't checked on these routes.
- **Trade-off, recorded:** off the direct route a revoked but unexpired certificate is accepted, as on Linux before this change. A direct connection keeps the OS's revocation checking.
- **Dependencies:** `lodestar-integrations` takes `rustls-platform-verifier =0.7.1`, `rustls-native-certs =0.8.5` and `webpki-root-certs =1.0.10` directly; all three were already in `Cargo.lock` at these versions (through rustls-platform-verifier), so no new crate enters the build. `lodestar-sources` and `lodestar-sources-irc` drop their direct `rustls-platform-verifier` dependency and verify through `lodestar_integrations::tls`.
- **Tests:** every non-direct route selects the self-contained verifier (`tls::tests`, `ws::tests::the_default_roots_verify_by_route`), a routed `GuardedClient` reports it, the verifier checks chain and name, and an IRC client over a bound address verifies with its own roots (`a_routed_client_verifies_with_its_own_roots`).
- **User guide:** a paragraph in section 8.6 (revision 3.5) says how certificates are checked on a routed connection.
