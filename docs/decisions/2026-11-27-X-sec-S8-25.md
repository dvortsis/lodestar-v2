# X-sec-S8-25 decisions (S8-25, important; surface plugin TLS)

- **Certificate verification follows the connection's route** (`crates/integrations/src/tls.rs`, `verification_for`). One rule for every routed client: the plugin HTTP client (`GuardedClient::with_route`, which companions' fetches also use), the plugin WebSocket client (`crates/sources`, `Roots::Platform`) and the IRC client (`crates/sources-irc`, `Roots::Platform`). A server's own CA (`Roots::Only`) is unchanged: webpki over just those roots, as before.
  - **`Route::Direct`:** the operating system's verifier (rustls-platform-verifier), unchanged. The OS's own trust decisions, its enterprise roots and its revocation checks stay as they were. Every client built with `Route::Direct` is untouched; a client built on another route (plugin HTTP, and companion downloads when Lodestar's egress setting is a route) takes the self-contained verifier below.
  - **Any other route** (a bound address, a bound interface, a SOCKS5 proxy with either DNS mode): **webpki in this process**, over every root in the OS store that webpki can use (`rustls-native-certs`, read once per process from local storage), with no revocation lists. Why: one verifier for routed connections, the same on every platform.
  - **Why the OS store's roots only:** a root the user added on purpose (a private indexer's CA) keeps working off the direct route. A bundled Mozilla set (`webpki-root-certs`, `webpki-roots`) is CDLA-Permissive-2.0, which the shipped-licence list (owner's decision §2.12, `web/licenses/allow.json`) doesn't allow, so none is added. The Docker image's distroless base ships the Debian CA bundle.
- **Per platform, on a routed connection:**
  - **Linux, Docker and Unraid:** the same as before in effect (the platform verifier was already webpki over the OS roots there).
  - **Windows:** webpki over the roots in the Windows ROOT store (current user and machine), instead of the Windows certificate verifier. Revocation isn't checked on these routes. A server whose root Windows hasn't yet put in that store is refused on these routes until it has.
  - **macOS:** webpki over the keychains' roots, instead of the macOS trust evaluation. Revocation isn't checked on these routes.
- **Trade-off, recorded:** off the direct route a revoked but unexpired certificate is accepted, as on Linux before this change. A direct connection keeps the OS's revocation checking.
- **Dependencies:** `lodestar-integrations` takes `rustls-platform-verifier =0.7.1` and `rustls-native-certs =0.8.5` directly; both were already in `Cargo.lock` at these versions (through rustls-platform-verifier), so no new crate enters the build. `lodestar-sources` and `lodestar-sources-irc` drop their direct `rustls-platform-verifier` dependency and verify through `lodestar_integrations::tls`.
- **Tests:** every non-direct route selects the self-contained verifier (`tls::tests`, `ws::tests::the_default_roots_verify_by_route`), the roots a routed `GuardedClient` hands reqwest's `tls_certs_only` are exactly that set (`net::routed_roots`), the verifier checks chain and name, and an IRC client over a bound address verifies with its own roots (`a_routed_client_verifies_with_its_own_roots`).
- **User guide:** a paragraph in section 8.6 (revision 3.5) says how certificates are checked on a routed connection.
