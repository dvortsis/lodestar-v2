# X-sec-S8-25 decisions (S8-25, important; surface plugin TLS)

- **Certificate verification follows the connection's route** (`crates/integrations/src/tls.rs`). `verification_for` chooses the verification and `client_config` builds the TLS configuration. Every client that takes a route builds its TLS from `client_config`:
  - the plugin HTTP client (`GuardedClient::with_route`), which hands the whole configuration to reqwest; companion downloads also use this client;
  - the plugin WebSocket client (`crates/sources`, `Roots::Platform`);
  - the IRC client (`crates/sources-irc`, `Roots::Platform`);
  - the tracker scrape client, when it is bound to an address (`crates/tracker-scrape`).

  A server's own CA (`Roots::Only`) is unchanged: webpki over just those roots, as before.
  - **`Route::Direct`:** the operating system's verifier (rustls-platform-verifier), unchanged, with the OS's own trust decisions, enterprise roots and revocation checks. Every client built on `Route::Direct` is untouched, and so is the tracker scrape client when it isn't bound.
  - **Any other route** (a bound address, a bound interface, or a SOCKS5 proxy with either DNS mode): webpki over the roots in the OS store (`rustls-native-certs`, read once per process, on a blocking thread from the plugin egress), with no revocation lists. With no usable root, the client or connector isn't built. Why: one verifier for routed connections, the same on every platform.
  - **Why only the OS store's roots, for now:** a bundled Mozilla set (`webpki-root-certs`) is CDLA-Permissive-2.0, which `web/licenses/allow.json` doesn't list. Widening that list is left to the runner and the owner. If it is widened, adding the bundled set is a two-line change in `tls::roots`. The Docker image's distroless base ships the Debian CA bundle.
- **Per platform, on a routed connection:**
  - **Linux, Docker and Unraid:** effectively unchanged, since the platform verifier was already webpki over the OS roots there.
  - **Windows:** webpki over the roots in the Windows ROOT store (current user and machine), instead of the Windows certificate verifier.
    - Only the ROOT store is read: the Disallowed store and Windows policy constraints don't apply on these routes.
    - Revocation isn't checked.
    - A server whose root Windows hasn't yet added to that store is refused on these routes until it has been added.
  - **macOS:** not a shipped target (`web/licenses/rust.json` lists Linux musl and Windows), so not described here.
- **Trade-off:** off the direct route, a revoked but unexpired certificate is accepted, as on Linux before this change. A direct connection keeps the OS's revocation checking. This refines a security decision, so the runner should flag it to the owner (`docs/owner-decisions.md` §2.19).
- **A refused certificate is named:** the HTTP client reports `NetError::Certificate` ("the server's certificate isn't trusted"), instead of the generic connect failure.
  - It comes from rustls' certificate errors inside reqwest's error chain, and the plugin status shows it.
  - Download clients, notifications and companion detection treat it as they treat an unreachable host.
  - The WebSocket client already says "the server's certificate wasn't accepted", and IRC stops with `Stop::Certificate`.
- **Dependencies:**
  - `lodestar-integrations` takes `rustls-platform-verifier =0.7.1` and `rustls-native-certs =0.8.5` directly. Both were already in `Cargo.lock` at these versions, so no new crate enters the build.
  - `schannel` (MIT), which `rustls-native-certs` uses to read the Windows ROOT store, now ships on Windows (`web/licenses/rust.json`). It was already in the lock.
  - `lodestar-sources` and `lodestar-sources-irc` drop their direct `rustls-platform-verifier` dependency.
  - `lodestar-tracker-scrape` takes `lodestar-integrations`.
- **Tests pin the wiring**, each on the configuration or connector that is actually built:
  - `tls::tests`:
    - every non-direct route gets a webpki configuration, checked by a match with no wildcard arm;
    - with no roots there is no configuration and no routed `GuardedClient`;
    - a routed HTTP client that trusts only the test CA reaches the test server, which the OS verifier would refuse;
    - the same client using the OS-store roots reports `NetError::Certificate`.
  - The plugin egress (`a_routed_sources_http_and_websocket_tls_verify_self_contained`): a routed source's HTTP client and WebSocket connector both use webpki, and a direct source's don't.
  - IRC (`a_routed_tls_config_verifies_self_contained`): checks the connector that `spawn` uses.
  - Tracker scrape (`a_bound_client_verifies_as_routed_clients_do`).
- **User guide:** section 8.6 (revision 3.5) explains how certificates are checked on a VPN or proxy route, and what to do on Windows when a certificate isn't trusted.
