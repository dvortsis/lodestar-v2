# CR-gate-hash-mismatch decisions (#236)

Supersedes the `failed_verification` entry of [CR-gate-metrics](2026-10-30-CR-gate-metrics.md), which counted protocol and handshake violations as failed verification and kept hash mismatches inside `fetch_failures_total{kind="invalid"}`. Neither holds any more: the gate metric reports failed verification apart from other losses (build-plan §0, owner G2).

- **Option A: the cause travels beside `Loss`, nothing new is persisted.** `peer-wire` gains `FailureKind::HashMismatch`, and only `Error::HashMismatch` maps to it; `Handshake` and `Protocol` stay `FailureKind::Invalid`. The funnel's `From<FailureKind> for Loss` maps both `HashMismatch` and `Invalid` to `Loss::Invalid` (6), so `cohort_hour.reason` gets no new code. A v0.5.1 rollback reads the same codes it always did, so there's no unknown-code path to prove, and Insights, its CSV and the zh strings don't change. Option B would add a persisted code for a distinction the gate needs and the Insights funnel doesn't, and would carry rollback risk for nothing.
- **The signal is the loss's cause, passed to `Funnel::lost`.** `Funnel::lost(key, cohort, source, loss)` gains `cause: Option<FailureKind>`: the key's last fetch failure, but only when that failure is what `loss` is (`Loss::from(kind) == loss`). A key evicted, blocked or given up after a hash mismatch carries `None`; it was lost to something else. The default impl still records only `loss`. `WorkerFunnel::lost` counts `Excluded::FailedVerification` when the coordinator accepts the loss, `loss == Loss::Invalid` and `cause == Some(FailureKind::HashMismatch)`; before, it checked only the loss. Passing the kind rather than a bare flag keeps the decision in the gate, where the metric is defined, and costs one copy of an enum.
- **`lodestar_metadata_excluded_total{reason="failed_verification"}` narrows to hash mismatches** (owner §2.25): a key counts when its last fetch failure before the pool gave it up was metadata whose SHA-1 didn't match the info hash. (That failure may predate the key's final lookup, as with `Loss::Invalid` before.) A protocol or handshake violation as that last failure is still a funnel `invalid` loss, and like other lost keys it's only in `fetch_lost_total{reason="invalid"}`, no longer in `failed_verification`. The excluded series are diagnostics beside the numerator, not a denominator, so the gate's number doesn't move. This is a runner refinement of how the gate metric is measured, not of a number the owner set (§2.19); flagged to the owner.
- **Fetch-failure labels gain `hash_mismatch`, additively.** The pool's `failures` array, `lodestar_fetch_failures_total{kind}` (docs/metrics.md), `/api/status` `fetch.failures`, the `fetch.failed_summary` log event (a new `hash_mismatch` field, appended after `oversize`) and the per-attempt `fetch.failed` event's `error` value (refines [B-log1b-r5](2026-10-24-B-log1b-r5.md)'s value list) all split it out of `invalid`. Every index and code is append-only: `HashMismatch` is the last `FailureKind`, index 6, and nothing is renumbered. The logs catalogue golden lists an event's field kinds, not its fields, so it doesn't change. The soak analyser's allowlist (`docs/soak/tools/analyze_cr0.py`) gains the label, so the new series isn't dropped from soak reports. Dashboards that read `invalid` see it drop by the hash-mismatch share; the sum over all kinds is unchanged.
- **CR-SIM goldens.** The only value change is `HashMismatch=0` appended to each `failures:` line. Re-blessing for it also wrote out zero counters that `run.rs` already printed and the comparison ignored: CR-ADM's `admission_*` and `dht_permit_returns` in all three goldens, and #232's `peer_queued_dropped_*` in `healthy` and `high-latency`. Every added line is `=0`, and no existing value moves (runner follow-up from the #236 review).
