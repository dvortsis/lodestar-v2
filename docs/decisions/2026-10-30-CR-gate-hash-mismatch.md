# CR-gate-hash-mismatch decisions (#TBD)

- **Option A: the cause travels beside `Loss`, nothing new is persisted.** `peer-wire` gains `FailureKind::HashMismatch`, and only `Error::HashMismatch` maps to it; `Handshake` and `Protocol` stay `FailureKind::Invalid`. The funnel's `From<FailureKind> for Loss` maps both `HashMismatch` and `Invalid` to `Loss::Invalid` (6), so `cohort_hour.reason` gets no new code. A v0.5.1 rollback reads the same codes it always did, so there's no unknown-code path to prove, and Insights, its CSV and the zh strings don't change. Option B would add a persisted code for a distinction the gate needs and the Insights funnel doesn't, and would carry rollback risk for nothing.
- **The signal is the last failure's kind, passed to `Funnel::lost`.** `Funnel::lost(key, cohort, source, loss)` gains `last: Option<FailureKind>`: the pool's `last_failure` for that key, `None` for losses that aren't fetch failures (`NoPeers`, `Blocked`, `Evicted`, `GaveUp`). The default impl still records only `loss`. `WorkerFunnel::lost` counts `Excluded::FailedVerification` when the coordinator accepts the loss and `last == Some(FailureKind::HashMismatch)`, instead of `loss == Loss::Invalid`. Passing the kind rather than a bare flag keeps the decision in the gate, where the metric is defined, and costs one copy of an enum.
- **`lodestar_metadata_excluded_total{reason="failed_verification"}` narrows to hash mismatches** (build-plan §0, owner G2): a key counts when the last attempt before the pool gave it up returned metadata whose SHA-1 didn't match the info hash. A protocol or handshake violation on the last attempt is still a funnel `invalid` loss, and like other lost keys it's only in `fetch_lost_total{reason="invalid"}`, no longer in `failed_verification`. The excluded series are diagnostics beside the numerator, not a denominator, so the gate's number doesn't move. This is a runner refinement of how the gate metric is measured, not of a number the owner set (§2.19); flagged to the owner.
- **Fetch-failure labels gain `hash_mismatch`, additively.** The pool's `failures` array, `lodestar_fetch_failures_total{kind}` (docs/metrics.md), `/stats` `fetch.failures`, and the `fetch.failed_summary` log event (a new `hash_mismatch` field, appended after `oversize`) all split it out of `invalid`. Every index and code is append-only: `HashMismatch` is the last `FailureKind`, index 6, and nothing is renumbered. The logs catalogue golden lists an event's field kinds, not its fields, so it doesn't change. The soak analyser's allowlist (`docs/soak/tools/analyze_cr0.py`) gains the label, so the new series isn't dropped from soak reports. Dashboards summing `invalid` see it drop by the hash-mismatch share; the sum over all kinds is unchanged.
