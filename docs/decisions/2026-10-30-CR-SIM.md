# CR-SIM decisions (PR pending)

- **Candidates are screened in a deterministic simulation of the real code, not a model of it (master plan, "Crawler program"; §5, §18.4).** `crates/sources/tests/sim` runs the real DHT node actor and the real fetch pool. They are wired as `crates/pipeline/src/dht.rs` wires them, in tokio's paused clock on a current-thread runtime, against a scripted network and scripted metadata peers. The same seed gives a byte-identical report, so CI asserts on goldens. Screening filters candidates before the live A/B runs; it never replaces them.
- **A dev-only `testing` cargo feature carries the seams (§5).** `lodestar-dht` and `lodestar-sources` gain the feature, enabled only through their own dev-dependencies, the pattern `peer-wire` and `tracker-scrape` already use. No production build enables it; `cargo tree -p lodestar -e features` shows it absent. Under it:
  - the actor runs on an in-memory socket (`node::testing::start`) with a seeded RNG;
  - the actor's maps and sets and the pool's request map become B-trees, because their iteration order reaches scheduling. A fixed hasher was tried and rejected: hash-table layout varies with SIMD width (x86_64 vs arm64) and std releases, and changing only the hash keys moved every golden. Production keeps the randomly keyed std hash tables for hash-flooding resistance.
  - `Node::start` and the simulator share one private `Node::spawn`, so the command channel, stats and shutdown wiring can't drift between them.
- **Production-neutral refactors the seams need (§5):**
  - **The clock:** the node's timekeeping uses `tokio::time::Instant` instead of `std::time::Instant`. At runtime they are the same clock unless a test pauses it.
  - **The sockets:** they sit behind a `SendSocket`/`RecvSocket` enum whose only production variant is UDP.
  - **The RNG:** it is created in `Node::start` and passed into the actor, instead of inside it.

  No behaviour, rate, cap or timeout changes.
- **Three baselines and a switch convention (master plan H1, H2).** The baselines are `healthy`, `high-latency` (H1) and `admission-pressure` (H2). Each candidate adds its runtime switch to `Switches` in `scenario.rs`, default off. With the switch off, every golden must stay unchanged; that proves the switch is inert. Golden counters are an explicit list, and new zero-valued counters are ignored, so adding a counter doesn't break that proof. The 60-minute stress run and the noise measurement are `#[ignore]`.
- **A/B screening uses several seeds.** Measured noise floor, seeds 1–8, stored metadata over 10 simulated minutes:
  - healthy: mean 433, range 396–515 (27.5%);
  - high-latency: mean 287, range 263–322 (20.6%);
  - admission-pressure: mean 294, range 262–325 (21.5%).

  A candidate counts as screened in only when it clears that spread, not on one seed.
- **Known limits, recorded so no screening result is over-read:**
  - IPv4 only, with no inbound passive queries, uTP, NAT or kernel buffer limits;
  - routing is approximated on numerically sorted ids;
  - discoveries skip the intake have-filter, and "stored" means "reached the writer".

  Goldens rely on `Ord` iteration and the simulator's own SplitMix64, not on platform hashing.
