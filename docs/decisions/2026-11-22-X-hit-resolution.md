# X-hit-resolution decisions

Slice `X-hit-resolution`, the Resolution half of UI review I15 (runner records r13, decided by the runner in r14 under `docs/owner-decisions.md` §2.26). It follows `2026-11-22-X-search-toolbar.md`, which added the table's Raw name column and deferred Resolution here.

- **`SearchHit.resolution` is the release parser's value, read from the stored record (runner's choice, A).** `string | null`, always sent, `required` in the OpenAPI schema like the sibling nullable fields (`title`, `resolved_via`), so the generated `schema.d.ts` reads `resolution: string | null`. Its values are `Resolution::as_str` (`crates/release-parser/src/lib.rs`: `480p`, `576p`, `720p`, `1080i`, `1080p`, `1440p`, `2160p`, `4320p`; `4k` and bare numbers are canonicalised before storage), which is exactly the string the index holds as the `res:` tag (`crates/search/src/doc.rs`) and the one `res:` canonicalises a typed value to (`query.rs` `tag_value`). A later click-to-filter can send `res:<value>` as it is. Null means the name gives none, the torrent isn't classified yet, or this build can't read its stored record. `docs/metrics.md` §7.1 has the row.
- **No extra read, no parsing in the API or the web.** The route already loads and decodes each hit's classification record (`search::enrich`) for the title, type and junk fields; the resolution is one more lookup in that decoded record. The table renders the string as it comes.
- **Every `SearchHit` carries it.** `enrich` is shared, so compare, user items, alerts, collections, Discover and siblings hits have the field too, with the same values and null rule. The export is unchanged: CSV and NDJSON write the fixed `ExportField` list, which doesn't include it (adding it there is a separate decision about the export format).
- **Table column `res`, "Resolution" / "分辨率" (`search_table_col_res`).** Placed after Type. No sort: the API has none for it, so the header is plain. Text, start-aligned, sized to its content (at most five characters). Null shows "—", like the Type column next to it: no shared "not known" message exists, and the runner asked for no new key just for that.
- **Saved column choices (runner).** A choice saved before a column existed keeps its columns as they were and gets the new column hidden. That was the Raw name rule, and it's now one list (`ADDED` in `columns.ts`: `raw`, `res`). With no saved choice, or one that already knows `res`, Resolution shows. A choice saved after Raw name but before Resolution keeps Raw name as chosen, shown or hidden, and gets Resolution hidden.
- **Size.** The table chunk grows by about 60 B (6.12 → 6.18 kB gzipped, limit 6.5 kB). No code goes into the Results chunk. Its one byte-level change is the table chunk's content-hashed filename inside its lazy `import()`, which changes with any edit to the table (see the PR for the measurement and the runner's call on it).
