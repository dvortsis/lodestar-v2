# X-soak-docker-memrule decisions

Flagged to the owner under `docs/owner-decisions.md` §2.19: this changes how a soak guardrail measures memory in Docker mode. It applies only to runs started with a collector from after this merges; the current rc.2 Unraid run keeps the collector it started with. The 1 GiB and five-sample numbers are unchanged, and the binding memory gate (`MEMORY_FIT`, `docs/decisions/2026-10-30-CR-0-acceptance.md`) is untouched.

- **In Docker mode the 1 GiB × 5 stop rule judges the cgroup's `anon`, not its working set** (`docs/soak/tools/linux/collect.py`). The working set (`memory.current − inactive_file`, as `docker stats` shows) is charged with page cache from the container's own SQLite and index reads, which sits in `active_file`. So the old rule counted cache, not process memory. The Windows collector judges `WorkingSet64`, which ReadFile cache doesn't charge to the process, and native Linux mode judges `VmRSS`; `anon` is the Docker figure closest to both. On the rc.2 soak the working set reached 1,071 MiB while `anon` sat near 800 MiB.
- **This refines the plan's stop-rule line for Docker mode.** `docs/soak/2026-10-25-CR-0.md` says the run stops on "working set above 1 GiB for five samples"; for Docker runs that now reads as cgroup `anon`. Native runs, and Docker samples without `anon` (for example cgroup v1 hosts read through the Docker API), still use the working set. The analyzer's `rss_max_mib` is still the working-set maximum, which this PR doesn't own.
- **`anon` alone, nothing added.** `kernel_stack`, `sock` and `shmem` aren't added: nothing here shows they matter for Lodestar, and the brief asked for the simple, conservative choice. One field keeps the rule easy to check and matches `private_bytes`, which the analyzer's memory gate already fits. If a later soak shows a large `shmem` or `sock` charge, a new decision can add it.
- **A new reason, `process_memory_over_1GiB_for_five_samples`,** so evidence from the two rules can't be confused. Native mode and the fallback keep `rss_over_1GiB_for_five_samples`. Both are in `analyze_cr0.py` `STOP_REASONS`. A streak that mixes anon and fallback samples is reported under the reason of the sample that tripped it.
- **Missing `anon` fails safe:** that sample is judged on the working set, as before, and `events.log` notes the fallback once. The check is never skipped.
- **`run.json` records the basis** as `settings.memory_stop_basis` (`anon` in Docker mode, `rss` in native mode).
- **The working set stays as evidence.** It's recorded every sample as before. In Docker mode `events.log` notes once when it first passes 1 GiB, and `status.json` and `result.json` carry `working_set_over_1GiB_samples`. It never stops the run.
