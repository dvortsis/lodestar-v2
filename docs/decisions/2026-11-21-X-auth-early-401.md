# X-auth-early-401 decisions

The runner's call (UX, owner decision §2.26; flagged under §2.19), from the #999 review. A 401 that lands before the shell installs its auth handlers no longer leaves a broken page. `GET /auth` is never cached.

## What changed

- **An early 401 is kept and replayed once** (`web/src/lib/api/client.ts`).
  - The shell installs the 401 handler lazily, after an `import()` in `onMount`. A signed-out visitor's first request, or an expired session's, can fail before that. Until now `loginRequired()` dropped such a 401, so the page stayed broken and the Settings draft keeping never ran.
  - Now the first one is kept, as a closure that calls `loginRequired` again with its path and options (whether setup or the Legal Notice is due). A 409 `notice_required` is kept the same way. Re-calling the same function makes the filters apply again for free. The runner suggested this form because it is the smallest one tried.
  - **Why this lives in `client.ts`:** the 401 lands before the shell's lazy auth module loads, so nothing else can catch it.
  - Installing a handler replays it once. The usual filters run again at that moment: the auth endpoints, and the sign-in and setup pages, judged by where the browser is at install.
  - A request that works before the install drops it, because the session is proven. The public `GET /auth` and `/logout` don't count, as before.
  - **Bounded:** one entry, and the first wins. A 401 from an auth endpoint is never kept.
  - Nothing changes after install: one redirect until a request works, as before.
  - An uninstall keeps nothing. A 401 during the gap is kept for the next install.
- **`GET /auth` sends `Cache-Control: no-store`** (`crates/api/src/auth/http.rs`), signed in or not. The web UI decides from a fresh answer whether the session is live: the sign-in pages' load check, and X-session-draft-keep's draft-block probe. A cached `logged_in: true` could otherwise lift that block after a Sign out. No other header changed, and the OpenAPI document is unchanged, since it doesn't list response headers for this route.

## Tests

- `client.test.ts`:
  - an early 401 is sent on once after install, and not again on a second install;
  - a success before install drops it, but the public `GET /auth` doesn't;
  - auth endpoints are never kept;
  - nothing is sent on when the browser is on `/login` or `/setup` at install;
  - several early 401s replay the first, once;
  - an early notice 409 replays with `noticeRequired`;
  - the uninstall gap.
- Mutation check. Each of these fails a test:
  - no replay (5 fail);
  - replay that skips the filters (1);
  - no auth-endpoint filter before keeping (3);
  - `sessionOk()` not dropping the entry (1);
  - the last 401 winning instead of the first (1).
- `crates/api/tests/api.rs` `auth_status_is_never_cached`: `no-store`, signed out and signed in.
