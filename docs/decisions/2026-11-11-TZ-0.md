# TZ-0 decisions: the Torznab server (#715)

The Torznab endpoint, `GET /api/v1/torznab/api` (plan `docs/plan/2026-11-05-v07-m7.md` §4.3 TZ-0; architecture §9, §18.2 Outputs, §18.7, §18.9, §20.9, §12). The code is `crates/api/src/torznab.rs` and `crates/api/src/torznab/`; the tests are `crates/api/tests/torznab.rs`. These are runner-level refinements (§2.19), flagged to the owner, who can veto them. None loosens an owner or security decision. Two of them make the plan stricter.

## Exclusions
- **Every §18.7 privacy bit is left out, not only `private_source`** (stricter than the plan). Torznab leaves out `flags::PRIVACY`: a private source's find, a BEP 27 `private=1` torrent, and a remote worker's row whose private bit isn't verified yet. A magnet for a BEP 27 torrent has the download client look the hash up on the DHT, which BEP 27 forbids. The other privacy gates (scrapes, Send to client) already refuse the same set.
  - **Counts:** the index query carries `-flag:private -flag:private_source`, so totals and pages leave them out.
  - **Rows:** every stored row is checked again on the full bit set, because the index can lag and has no term for `REMOTE_UNVERIFIED`.
  - **A page fills itself past rows the stored check leaves out** (self-review I1). The lease is read on from where the page stopped, at most 4 more times (`MAX_REFILLS`), so a page comes back short only when the results run out. Sonarr and Radarr stop paging at the first short page, so a short page would hide everything after it. The response's `offset` stays the one asked for. A refilled page can repeat an item on the next page, and the apps de-duplicate by `guid`.
  - **A total can count a remote row whose private bit isn't verified yet** (WK-9, until WK-13 re-verifies it), because the index has no term for it. The row is never served, and the total is one high. An index term would be a search change, not TZ-0's.
- **Unverified items are never served** (plan Q17), whatever the request says. The search's AST is built from the parameters and never parsed as query language. So `q=verified:no`, `q=flag:hidden` or `q=type:adult` is only words, and search's own `base_query` adds `verified:yes`.
- **Hidden torrents are left out.** Your filters apply: hidden by a rule is never served, and Torznab has no `hidden=true`.
- **Held and blocklisted items** are never stored (the CSAM floor, held verdicts), so nothing can find them. G-v07 carries the fixtures through every output.
- **Adult appears only with `torznab_adult`** (§20.9). Torznab reads its own setting through a `TorznabAdult` extension, once per request, the same pattern as `export::ExportAdult`.
  - "Show adult content" doesn't apply.
  - Without the extension, Adult is never served, which fails closed.
  - Each row's stored class is checked again, as search does.
  - **The wiring** (runner, 2026-11-11): `settings::content::follow_torznab` follows the setting, and the server layers it next to `export_adult` in `crates/lodestar/src/services.rs` (after #709 merged, as the runner approved). The setting's help no longer says "Not used yet"; `settings_index.txt` is regenerated for that line.

- **The outputs tripwire lists Torznab as covered** (runner, 2026-11-11). `crates/sources-plugins/tests/safety.rs::torznab_and_stremio_outputs_are_not_built_yet` fails once an output is routed until its slice adds a `private_source` leak test. Its `COVERED` now holds `"torznab"`, naming `crates/api/tests/torznab.rs::private_hidden_and_unverified_are_never_served` and `::stored_rows_decide_when_the_index_lags`. Each puts a `private_source` row in the store and asserts it's never served, the second with an index that doesn't know the flag. Stremio stays uncovered for OUT-1.

## Parameters (all untrusted)
- **Bounds** (runner numbers under §2.26):
  - the query string at most 4 KiB and 64 parameters;
  - `q` at most 256 bytes and 32 words;
  - `cat` at most 32 ids of up to 6 digits;
  - `season` up to 4 digits, `ep` up to 4 digits or a daily `MM/DD`;
  - `limit` from 1 and capped at 100 (default 100, as caps says);
  - `offset` up to 9 digits.
- **An offset past search's 10,000 window** (`MAX_WINDOW`, §8) returns an empty page with the true total, not an error. *arr apps page until a short page, and an error would mark the indexer as failing.
- **Unknown parameters are ignored.** Newznab clients send many (`extended`, `o`, `attrs`, `year`, …).
- **A parameter read twice is refused (`201`)**, rather than one copy picked.
- **ID parameters with a value are refused (`203`)**: `imdbid`, `tmdbid`, `tvdbid`, `rid`, `tvmazeid`, `traktid`, `doubanid` and `tvrageid`. Ignoring one would answer an ID search with whatever else matched. Caps doesn't advertise them, and ENR-11 adds them. An empty value counts as absent, because some clients send `imdbid=`.
- **Control characters are removed** from `q`. Invalid percent-decoded UTF-8 is replaced, not trusted. Error descriptions are fixed strings: they name the parameter and never echo its value.
- **A daily episode** (`season=2024&ep=01/15`, Sonarr's form) becomes the phrase `2024 01 15` on name and paths. Any other non-numeric `ep` is a `201`.
- **Without `cat`, a mode searches its own categories**: `tvsearch` 5000, `movie` 2000, `music` 3000 and `book` 7000. `search` searches everything. An explicit `cat` replaces the mode's.
- **Requested categories this server doesn't list find nothing.** A mix of listed and unlisted categories finds the listed ones.

## The search
- **It's search's own path:** `base_query` over the AST, a `Lease` of the index serving now, its ranking and its total. There's no fork of ranking or counts.
  - Words match name and paths (`TextField::Any`), as plain words do in the query language.
  - With no words, results are newest first (`Sort::Discovered`), which is what an RSS poll expects. With words, they're by relevance.
- **No result cache and no cursors:** Torznab pages by offset only. The search is cancelled when the client goes away, as `/search` is.
- **Results don't count as user interest** (scrape priority) and aren't added to the Serve rollups. Those measure people searching, and an *arr app polls on its own schedule.

## The category map
- The map is in `torznab/categories.rs`, which documents it as a table. In short:
  - movie 2000 and tv 5000, each with SD, HD and UHD subcategories from the parsed `res`;
  - music 3000 and audiobook 3030;
  - software 4000 and game 4050;
  - Adult 6000, with photos as 6060;
  - ebook 7020 and comic 7030;
  - images, video, other and anything not classified yet in 8000 and 8010.
- **An item lists under its parent and its subcategory, when one applies.** A parent request finds every item of its subcategories.
- **A movie or show with no parsed resolution is in 2000 or 5000 only**, so a client gets exactly what it would label the item as. Unlisted Newznab ids (Console, Anime 5070 and so on) find nothing.
- **Sonarr's default categories are 5030 and 5040,** so with them a TV item with no parsed resolution, and a UHD one (5045), isn't found (self-review I3). The how-to for connecting Prowlarr, Sonarr and Radarr should tell people to add 5000 (and 5045) in Sonarr, and OUT-2's settings screen, which shows the Torznab URL and key, could carry the same hint. TZ-0 ships no user docs: the runner's D-outputs-guide writes that page (below). The categories aren't guessed instead, so a client never gets an item under a label it doesn't have.
- **Caps always lists 6000 XXX,** whatever `torznab_adult` says. Prowlarr syncs an indexer's categories when it's added, so caps that changed with a setting would leave the apps' category lists stale. With the setting off, a 6000 search finds nothing.

## The documents
- **Results are RSS 2.0 with the `torznab` namespace**, one page per response:
  - the channel's `title`, `description` and `link`. RSS 2.0 requires the link. It's `/`, the instance's own web UI as a constant relative URL, and never built from the request's `Host` (X-tz0-polish, runner, 2026-11-12);
  - `torznab:response offset total` for the page;
  - for each item: `title` (the torrent's name, which *arr apps parse as a release name), `guid` (the info hash), `pubDate` (discovery time, RFC 822 UTC), `size`, `link` and `enclosure` (the magnet link), `category`, and the `torznab:attr`s `category`, `size`, `files`, `infohash`, `magneturl`, `seeders`/`peers`/`grabs` (only once scraped: never-scraped counts aren't claimed as 0), `downloadvolumefactor=0` and `uploadvolumefactor=1` (public swarms).
- **Magnet links only.**
  - A link carries the v1 hash, a hybrid's v2 multihash as well, or only the multihash for a pure v2 torrent. It also carries `dn`, the name percent-encoded and cut at 256 bytes on a character boundary.
  - It has no trackers: none are stored for DHT finds.
  - Nothing written back carries the key: the only link to this server is the channel's constant `/`, and there are no absolute URLs at all.
- **The XML writer** (`torznab/xml.rs`) builds each document in memory. A document is bounded by 100 items, so it isn't streamed.
  - **It's hand-written, a departure from the plan** (`docs/plan/2026-11-05-v07-m7.md` line 126 said the Torznab writer uses the existing `quick-xml`). The reasons:
    - element and attribute names are this module's constants, so nothing needs a general writer;
    - every value goes through one escaping function, which also removes what XML 1.0 forbids, so no value can skip it;
    - no CDATA is ever written.
    `quick-xml` is a dev-dependency only, used to parse the output back. The same plan line's quick-xml for ENR-anidb is a *parser*, which this doesn't change.
  - Element and attribute names are constants.
  - Every value is escaped: `& < > " '` become entities, and no CDATA is written, so `]]>` stays text.
  - `Cc` control characters, C0 and C1, are removed. Tab, LF and CR become a space.
  - U+FFFE and U+FFFF are removed, and so are the bidirectional overrides and isolates (U+202A–U+202E, U+2066–U+2069) and U+FEFF, so a hostile name can't display reversed in an *arr app.
  - **The bidi marks are kept** (U+200E LRM, U+200F RLM, U+061C ALM; X-tz0-polish, 2026-11-12). They can't reorder text the way overrides and isolates can. Real Hebrew and Arabic release names use them to render correctly, and removing them would garble those titles. "Can't display reversed" is the overrides' and isolates' doing.
  - A property test and the integration test check this. The test parses every response twice: with its own strict XML 1.0 reader and with `quick-xml` (`=0.42.0`, already in the lockfile, a dev-dependency only: runner, 2026-11-11).
- **Caps** advertises `search`, `tv-search` (`q,season,ep`), `movie-search`, `music-search`, `audio-search` and `book-search` (`q`), `limits default=100 max=100`, and the category tree. The integration test pins it byte for byte. It names no version, so the document doesn't tell anyone which build is running.

## Auth and errors
- **The API's own key guard** (`auth::key_or_session` with `scope::TORZNAB`):
  - the stored hash in constant time;
  - one answer for every bad key;
  - the per-IP failed-check bucket;
  - the per-key request bucket (the rate limit per key the plan asks for);
  - read only, and no cookies.
- **A session also gets in,** so a signed-in browser can check the feed.
- **The guard's JSON refusals are rewritten as Torznab error documents** by a layer outside the guard. The HTTP status and `Retry-After` stay the same. The description is fixed per status, and the JSON message isn't carried over.
  - 401 → `100` "Incorrect user credentials";
  - 403 → `102` "Insufficient privileges: use an API key with the Torznab scope";
  - the notice gate's 409 → `102` "Insufficient privileges: accept the Legal Notice in the Lodestar web UI first". Only a signed-in browser can meet the gate, because keys skip it, so the fix for that caller is to accept the notice (X-tz0-polish, 2026-11-12);
  - 429 → `500` "Request limit reached";
  - 405 → `202` "No such function";
  - 503 → `910` "API disabled";
  - anything else → `900` "Unknown error".
- **Parameter errors are `400`** with their Newznab code. Search off is `503` with `910`. A search that fails is `900` with its status, logged as internal errors are.
- **Errors keep real HTTP statuses, not 200.** Newznab doesn't specify a status. Sonarr, Radarr and Prowlarr report a 401 or 429 by status, and a cache or proxy then never stores an error as a feed.
- **Not in OpenAPI.** The plan doesn't put Torznab there; it's specified by Torznab itself. Its tests are its contract.

## For the user guide (D-outputs-guide, runner, 2026-11-11)
Facts the "Connect Prowlarr, Sonarr and Radarr" page needs, as built:
- **The URL** is `http(s)://<host>:<port>/api/v1/torznab/api`. In Prowlarr, add it as a *Generic Torznab* indexer, with that URL and the key; in Sonarr and Radarr directly, it's a *Torznab* indexer with the same two values. Check the app's API path field against the real app when writing the page.
- **The key** is an API key with the **`torznab`** scope (Settings → Security). A key with other scopes as well works, but the safe choice is a key with only `torznab`, one per app, so one can be revoked alone. The key is sent as `apikey=` in the URL, which the request log never records; it never appears in a response.
- **Sonarr's default categories (5030, 5040) miss TV whose resolution wasn't parsed (listed under 5000 only) and UHD (5045).** Tell people to add 5000 and 5045.
- **Radarr's defaults** (2000 and its subcategories) already include 2000, so nothing is missed. Music apps (Lidarr) use 3000, book apps (Readarr) 7000, 7020 and 3030.
- **Adult:** Torznab serves Adult only when `torznab_adult` is on (the `content` settings section, an advanced field, with the 18+ confirmation), separately from "Show adult content". Adult items list under 6000 XXX (6060 for image sets); an app finds them only if 6000 is in its categories too.
- **What never appears:** private-tracker and Usenet finds (`private_source`), BEP 27 private torrents, unverified items and anything your filter rules hide. Results are magnet links, so the download client needs DHT on.
- **Limits:** at most 100 results per page; too many failed key checks from one address, or more than 300 requests in a burst from one key (5 a second after that), get `429` with a `Retry-After`, which the apps show as a rate limit.
