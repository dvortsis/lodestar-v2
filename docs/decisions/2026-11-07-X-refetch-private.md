# X-refetch-private decisions

- **The finding.** At every start, the pipeline queues imports whose file list is partial for refetch through the first enabled peer finder, with `private_source: false` (`crates/pipeline/src/lib.rs`, the start's partial-refetch block). The keys came from `Store::partial_hashes`, which selected `flags & FILES_PARTIAL != 0` with no privacy filter. `FILES_PARTIAL | PRIVATE`, `FILES_PARTIAL | PRIVATE_SOURCE` and `FILES_PARTIAL | REMOTE_UNVERIFIED` are all real states. So a private partial import was sent to public DHT and PEX lookups after every restart, which §18.7 and BEP 27 forbid. The refetch also made later finds no safer: a private source's find merged into the queued public refetch stays public, because the pool keeps an entry private only while every find is private (`e.private &= ...`).

- **The fix: filter in the query.** `partial_hashes` now also requires `flags & flags::PRIVACY = 0`, so it never returns a BEP 27 private torrent, a private source's find or an unverified remote row.
  - **A private unverified item under the hash counts too.** `partial_hashes` also skips a row that has an unverified item flagged private (`unverified_items.flags & 1`) under either swarm hash. `Store::insert` leaves such an item in place beside a public import, and `docs/decisions/2026-11-06-X-tcache-recheck.md` already treats that key as private. The torrent cache's `Gate::check` and the writer's `stored_private` apply the same rule, so the start's refetch now agrees with them. The lookup uses the `(network, key)` unique index.
  - **Why the query, not `private_source: true` at the queue.** A private refetch has nowhere to go: the only place it's queued is a public peer finder. Carrying the key as private would leave it in the pool doing nothing, using up part of the 50,000 cap (`PARTIAL_REFETCH`). Filtering in SQL is simpler, and provably safe because nothing is queued at all. It also means the cap counts only keys that can actually be refetched.
  - **The name stays `partial_hashes`.** It has one caller in production, the start's refetch, and its doc comment now states the guarantee. That kept the change out of other slices' test files.
  - **Private partial imports stay partial.** Their file lists are never fetched from the public swarm. Upgrading them through a private source (a client's own copy, say) is not built; that would be a separate slice.
  - **Public parity.** Public partial imports are refetched exactly as before: same order (oldest first), same cap, same queue entry.

- **The audit** covers every construction of `QueuedKey`, `Found`, pool entries, `FetchedKey`, `Results` and `Interest`, and every literal `private_source: false`, in `crates/pipeline/src/**` and `crates/sources/src/**` on `main` 8979a9b7. Only the start's refetch was wrong.

- **Tests**, each failing without the fix:
  - `crates/store/tests/partial_privacy.rs`: a store with public, `PRIVATE_SOURCE`, BEP 27 (`info.private` and the bare `PRIVATE` bit) and `REMOTE_UNVERIFIED` partials returns only the public one. Four older private partials don't use up a cap of 1. Public partials still come back oldest first. A public partial that has a private unverified item under its hash is left out, and one that has a public item is kept. A hybrid partial whose truncated v2 hash alone has a private item is left out, and a public hybrid partial is kept.
  - `crates/pipeline/tests/refetch_private.rs`: the real pipeline, started twice on the same database file. A recording peer finder, with a fake peer that serves every torrent, is asked only for the two public imports. The private partials stay partial, and none of them is in the saved fetch queue afterwards.

- **v0.5.1 exposure and backport.** `release/v0.5.1` has the same refetch (`lib.rs:913-922`) and the same unfiltered `partial_hashes`. There, `FILES_PARTIAL` rows come only from the bitmagnet importer, and that importer copies bitmagnet's `private` column into the BEP 27 bit. So a BEP 27 private torrent that bitmagnet indexed with a partial file list is looked up on the public DHT after every v0.5.1 start. v0.5.1 has no private sources, so `PRIVATE_SOURCE` and `REMOTE_UNVERIFIED` partials can't exist there. The practical risk is low: bitmagnet itself found those hashes on the public DHT. Lodestar never announces them, but it does send `get_peers` for them and then connects to the peers it finds over the peer wire, where PEX can apply. It is still a BEP 27 violation. **Recommendation:** backport the query filter (and the store test) to any later v0.5.x patch release. It isn't a straight copy: v0.5.1 has no `flags::PRIVACY` or `REMOTE_UNVERIFIED`, so the mask there is `PRIVATE | PRIVATE_SOURCE`. v0.5.1 has no `unverified_items` table, so the unverified-item check is left out there. It doesn't justify a release on its own. The runner and the owner decide on releases.
