# B-log1b decisions, part 2a of 4 (#156): API, auth and the setup token

Architecture §12 and §12.1, owner's decisions §2.11 and §2.19, and the B-log1, B-log2 and B12 decision files. Part 1 is `2026-10-23-B-log1b.md` (#148). No owner decision is reversed or loosened, and no security or content-safety decision is weakened. The refinements the runner flags to the owner (§2.19) are marked **(§2.19)**.

- **Part 2 is split in two (2a and 2b), so the slice is four PRs (§2.19).** Each stays near the ~1,500-line guideline. 2a is the API, auth and the setup token, with the canary's positive controls. 2b is the `lodestar` crate's sweep (`services.rs` with the bounded shutdown, `system/**`, `windows/**` with the service's runtime wiring, `fixture.rs`, `insights.rs`, `main.rs`) and `filter/lists.rs`. Part 3 becomes 4 of 4.
- **An `AUTH` catalogue** (`crates/api/src/auth/log_events.rs`, `lodestar-api-auth`, component `Auth`). Every field is a `Client` (the address the limiter keys on: the TCP peer, or behind a trusted proxy the forwarded client, as B12 resolves it) or a fixed label. Nothing a user typed is a field: not a password, a key, its prefix or its hash, a feed token, a proxy user name or a header. A unit test holds that only clients and labels are declared.
  - `auth.setup_complete` (no fields), `auth.sign_in`, `auth.password_changed`, `auth.sessions_revoked`: Info.
  - **`auth.sign_in_failed`** (Warn) covers every failed password check, with `action` (`sign_in`, `setup`, `confirm`, `password_change`) and `reason` (`bad_password`, `bad_token`, `weak_password`, `not_set_up`, `setup_done`). A confirmed change that succeeds logs its own event, so a successful confirmation logs nothing more.
  - **`auth.rate_limited`** (Warn), `limit`: `password` (the login bucket), `key_checks` (failed key checks) or `key_requests` (a key's request bucket). **For key checks it's logged once, by the failed check that uses an address's last attempt;** while the address stays limited its requests log nothing more, neither a refusal nor the limit. A password attempt that's refused for the limit logs it each time (folding takes repeats from one address).
  - **Floods (§2.19, recorded):** before this PR these paths logged nothing. A client rotating source addresses (IPv6 privacy addresses in one /64, or many LAN hosts) gets a fresh bucket per address, so each bad key logs one `auth.key_refused` line that folding can't merge (the address differs). Each costs the client a request and the server a key lookup; a password attempt costs an Argon2 run. The file's size cap and rotation bound the disk; a per-network limiter is a follow-up if that proves noisy.
  - **`auth.key_refused`** (Warn). Every refusal comes after the failed-check limiter, `read_only` included (runner's review of #156): a limited address logs nothing more, whatever it sends. `kind` (`api_key`, `feed_token`, or `unknown` when it didn't parse) and `reason`: `malformed` (not a key, or two different ones in one request), `wrong_form`, `unknown`, `revoked`, `expired`, `wrong_kind`, `scope`, `read_only`. The response is unchanged: one answer for every bad secret (B12). Unit tests send each case through the real guard on a temp store with a capture sink and check every reason, and that no part of any secret is logged; `wrong_kind` can't be reached through the API (the store's key always has the kind its tag says).
  - **`auth.proxy_changed`** (Info): `enabled` and how many ranges are trusted, never the allowed users or the header (B12). Logged on a successful `PUT /auth/proxy`. A per-request proxy sign-in isn't logged: it would be a line per request, and `api.request` already gives the client.
  - The configuration warnings: `auth.proxy_settings_invalid` (`field`, the setting's name), `auth.proxy_override_ignored`, `auth.proxy_wide_range`, and `auth.proxy_forced_off` (from `services.rs`, where `LODESTAR_PROXY_AUTH=off` applies). `auth.key_use_unrecorded` replaces `guard.rs`'s plain line.
  - **Not built here:** key create, regenerate and revoke events. Their call sites are in `crates/api/src/keys.rs`, which this slice doesn't own. Follow-up: declare `auth.key_created`, `auth.key_regenerated` and `auth.key_revoked` (`kind`, `scopes` as a count, never the name, prefix or secret) in the `AUTH` catalogue and call them from `keys.rs`'s three handlers.
- **`auth.setup_token` comes through the catalogue.** `services.rs` logs it with `SetupToken` and the bind address as `Listen`. The console line still reads `… enter setup token XXXX-XXXX-XXXX-XXXX address=…`, the token right after the message (`tests/serve.rs`, the canary and the user guide read the word after `setup token`). **The address is the bind address as it is** (`0.0.0.0:8191` under Docker), where the plain line said `http://<this host's address>:8191/` (§2.19). A friendlier label could be leaked once at start, as `request_log` does for templates; the brief's `Listen` keeps the event's fields typed instead. The user guide only asks for the token. **For the docs follow-up (S-logs):** the token's line shows the bind address as it is (`0.0.0.0:8191` under Docker), not `http://<this host's address>:8191/`, so the guide should say to use the host's own address; and with the console set to JSON, the token is in `fields.token.value`, not after the words; the guide's step 2 describes the text format.
- **The plain-line special case is retired** (B-log2's note): the ring no longer looks for `setup token ` in untyped messages, since nothing writes one. History and redacted downloads still redact it in older files (`view.rs`), with a test that writes an older plain line into the file and reads it back redacted.
- **`api.request` (§2.19: route templates only)** (`crates/api/src/request_log.rs`): one `axum::middleware::from_fn` layer in `lodestar_api::router`, added after the routes and both fallbacks, so it sees the matched route and the final status (a guard's 401 included). Debug, `default_on: false`.
  - Fields: `method` (the standard methods, else `other`), `route`, `status` (a count), `took_ms` (`Size`) and `client` (`Client`: the TCP peer from `peer_ip`, never a forwarded-for header).
  - **`route` is axum's `MatchedPath`**, the template with the nest prefix (`/api/v1/torrents/{hash}`); a request no route matched is `unmatched`. Never the raw path, the query or any header, so no hash, search query, `apikey` or `token` value can reach it. The URI isn't logged at all.
  - **`'static` without an unbounded leak:** each distinct template is leaked once into an interned set, capped at 512 (the router has about a hundred routes); past the cap a template logs as `other`. The `MatchedPath` is cloned (an `Arc`) before the request runs, so an event that's off copies nothing.
  - **It needs axum's `matched-path` feature,** added to `crates/api/Cargo.toml`'s axum features with the runner's approval (2026-10-23). `Cargo.lock` is unchanged: the feature adds no crate.
  - Logged when the response starts, so `/logs/stream`, `/events` and downloads log once, at open, never per frame.
  - **It sees only what reaches `lodestar_api::router`.** A request refused by a layer outside it (the binary's web routes, its static files, anything `http::router` answers before nesting `/api/v1`) logs no `api.request`.
  - **Its rate under Build 3's rule:** the UI with the live log open makes a few requests a second (polling, the stream, search-as-you-type), so at (d)'s cost it's far under 1% of a core, but at about 300 bytes a line, more than about one request a second over a day passes the file's 18 MiB daily share. It stays `default_on: false` (Detailed), as the runner decided; it doesn't swamp Detailed by 10×, so not `Trace`.
- **`auth.setup_complete`'s message is `auth: setup complete; …`** because `crates/api/tests/keys.rs` (another slice's test) looks for `setup complete` in what its capture sees. The prefix doubles on the console (`auth.setup_complete: auth: setup complete; …`); a follow-up for that test's owner can let it read `Setup complete; …`.
- **The canary's positive controls.** Run 4 (both servers) now asserts the lines that must appear, in the console and the file, in the same runs that assert no secret appears: `auth.setup_token`, `auth.setup_complete`, `auth.sign_in`, `auth.sign_in_failed` (with the client and `bad_password`), `auth.password_changed`, `auth.key_refused` (a bad key as `Authorization: Bearer`, `X-Api-Key` and `?apikey=`, and a bad feed token on a feed route, each answered 401, both kinds logged), `auth.proxy_changed` (on, one trusted range), `auth.sessions_revoked` (its new cookie absent), and `api.request` by template for requests carrying `?apikey=` and `?token=`, with neither value, nor `q=`, in any request line. A refused feed request's line carries 401, an unmatched route's carries `unmatched`, and its path and query appear nowhere. The console is matched by the whole id (`auth.sign_in: `), so `auth.sign_in` isn't found inside `auth.sign_in_failed`. **The brief's "proxy sign-in" control is the setting turned on** (`auth.proxy_changed`): a sign-in through the proxy's header isn't its own event (a line per request), and `api.request` carries its client.
