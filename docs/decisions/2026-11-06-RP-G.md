# RP-G decisions: the rule-pack gate

Plan `docs/plan/2026-11-04-v06-rulepacks.md` §4.3 "RP-G"; architecture §20.6–§20.11; owner §2.20, §2.21. RP-G adds tests only: no runtime code, no migration, no owner decision, security or content-safety decision, or owner-set number changes. It closes RP-5's item "Not in CI yet" (`docs/decisions/2026-11-05-RP-5.md`, Measurements): SP-4's set at its cap is now in the budget CI runs. One finding is for the runner (the flooded commit, below).

## What the gate runs
- **Corpora** (`crates/filter/tests/packs_gate.rs`):
  - Every pack corpus and the precision corpus pass one rule at a time, as RP-3 serves them (`Corpus::run`). Direction checks agree, and no known gap is listed.
  - **The shipped counts are floors**, so losing an example is a regression: per rule, the `match` and `miss` examples the corpora have today (MW-2 11/6, FK-2 10/5, UC-1 7/5, the rest 3 or 4 each), and 38 precision items. Every stateless rule must have a floor, so a new rule can't skip it. Adding examples needs no edit. Removing one needs the floor lowered in the same PR, where review sees it.
  - **With every pack on together, behind the shipped child-safety core**, on a fresh install: every `match` example is held at least at its rule's own action, and no precision item is held by anything. RP-1's corpus runs each rule alone with empty core lists, so this is the first run of the packs as an install runs them.
  - **On an install an earlier build set up** (seeded at version 1, every pack on), the same run holds. The rules added after RP-0 are in shadow only (never applied before acceptance). Six precision items are still held by MW-2@1 and FK-2@1 (four music production packs, two short-episode series): the false positives their version 2 guards fix (RP-1b). That's intended: a narrowing version takes the password to accept, and until then the older version keeps holding. The gate pins those six, each held only by a rule whose pending version lets it through. Once everything pending is accepted, the install behaves as a fresh one.
- **Upgrade without release** (same file), on the real build: MW-2 and FK-2 at version 1 applied, version 2 built.
  - They stay pending across a restart (`ensure_seeded` never seeds again), a rule of yours added, and another rule switched off and on (which records only that rule's version).
  - Overrides made against version 1 apply unchanged until acceptance.
  - Accepting releases nothing. The review queue, tombstones, filter hits and exceptions are compared row for row before and after, here and through the API (`accepting_through_the_api_releases_nothing`).
  - **Limit:** the held rows name hashes with no stored torrent behind them, since these tests have no ingest path to store one. A future acceptance that re-judged held torrents would find nothing to re-judge here, so this proves acceptance writes nothing to those tables, not that a re-judgment would keep them. Today `upgrade::accept` writes only the pack-version rows, and the release path is `release` with its own warning and password.
  - After acceptance, MW-2's lighter override (weakens) is paused and MW-2 applies as built. FK-2's heavier one (strengthens) is kept and flagged as changed. An override on a rule nothing pending touches still applies. A restart keeps all of it.
- **Guardrails through the API** (`crates/api/tests/packs_gate.rs`, outside the brief's listed paths; see below). Every operation the packs added that weakens is checked: an override lighter than the rule's action, one with an `unless`, one on SP-4, removing a heavier override, accepting MW-2@2 or FK-2@2 (which narrow) or the malware pack whole, and confirming an override the acceptance paused. So is every older operation aimed at a rule the packs added: turning SC-2, MW-6, UC-1 to UC-3, SP-3 or SP-4 off, turning the unauthorised-copy pack off, and an exception to any of them (by query, and SP-4 by payload). For each one:
  - its preview says it weakens and shows a warning;
  - without the password, apply returns 428 `confirm_required`;
  - with a wrong password, it returns 401 `bad_password`;
  - after either refusal, the rule set and the engine version are unchanged;
  - with the password, and the `base` or `versions` the preview asked to be sent back, it applies.
  - **`new_since_rp0` matches every `Change` variant by name**, so an operation added later doesn't compile here until it's classified. One example of each operation marked new is kept by hand beside the scenarios, and the test fails unless the scenarios cover each of them: whoever marks a new arm adds its example.
  - Strengthening forms of the same operations need no password: a heavier override, turning SP-4 on, accepting SP-4. So a guard that asked for the password on everything couldn't pass.
- **E2E** (`web/e2e/packs.routes.test.ts`). The mock keeps the pack state between requests, so each apply changes the next `GET /filters`. The run:
  - views both pending versions, their changelogs and the corpus badges;
  - accepts SP-4 without a password and sees it leave the notice;
  - sets a heavier override and sees base beside yours;
  - makes two weakening changes, a lighter override and accepting MW-2@2. Each asks for the password. A wrong one shows the error and changes nothing. The right one is sent with the previewed `base` or `versions`.
  - axe runs on the screen, the notice and the dialog.

## The budget (`crates/filter/tests/props.rs`, `budget`, the `filter budget` CI job)
- **What's added.** Every engine case runs with every pack on at the versions a fresh install applies, not at `PackVersions::default()`, which is the unseeded interim mode. SP-4's set is filled to its cap, 1,000,000 signatures, and shared as the writer shares it. Each held case is timed twice:
  - as prepare judges (`Engine::judge`);
  - as the writer judges the commit again through RP-4's entry point, at its worst (`Engine::judge_at_commit`): SP-3 at its demote level, so every torrent pays the second judgment, and SP-4 looked up as the writer does (payload signature, then one map read).
  - Many of the budget's torrents share a payload, so 479 of 512 are clones. SP-4 decides 105 of them at commit; other packs already hide the rest in prepare. A pre-check asserts that every clone is decided by SP-4 or was already hidden, and that SP-4 decides at least a tenth of the set, so the at-commit timings include the inherit path.
- **Pending versions in shadow.** The held sets (1%, 10%, mixed) are timed again, both ways, on an install an earlier build set up. Eight versions are pending there and judged in shadow: MW-2, MW-6, FK-2, SP-3, SP-4, UC-1, UC-2 and UC-3.
- **The CI job is unchanged.** It already runs `budget`, and the new cases are inside it, so no workflow line changed.
- **The overrides and neutralized cases** stay on the mixed set, as on `main`, and keep `main`'s rule: they don't assert that no rule of yours decides (with words neutralized, a negation rule matches).
- **Pack overrides in the budget** are now built with `current_base` against the versions that apply, rather than a hard-coded base 1. On a fresh install MW-2 and FK-2 apply version 2, so a base of 1 would have read as changed. The case asserts all four apply, none changed or paused.

This session's container: an Intel Xeon @ 2.30 GHz, not in `ENGINE_SPEED`, so scaled by the calibration (7.19 to 7.21 µs, 0.69× the reference). Release build, two runs. Reference-runner µs per torrent:

Every held case is under 50 µs. **The headroom is thin:** the tightest, mixed with five words neutralized at commit, is 48.5 µs, 3% under. Before RP-G, the same container measured mixed at 47.1 and neutralized at 49.2, at the interim versions (`PackVersions::default()`). The at-commit judgment costs about what prepare's does, plus 0.5 µs at most for the payload signature and SP-4's lookup at the cap.

### For the runner: a flooded or cloned commit's two judgments
- **The budget is per judgment**, as RP-4 set it (#495): "a flooded commit gains a second judgment, which is under the engine's 50 µs budget". RP-G holds each judgment.
- **Together, the two cost 86.2 to 86.4 µs** reference (59.4 µs here) at 10,000 rules, mixed: prepare's judgment, then the writer's again. The budget reports it, not held.
- **Who pays it:** every commit the writer judges again (`writer.rs`, `at.any()`). That's a flood's commits from its 20th near-duplicate in an hour on (SP-3's demote level), and, since RP-5, **every commit whose payload signature is in SP-4's set**. A clone wave can be larger than a flood.
- RP-4's runner accepted the second judgment under §2.26 on #495, when it measured 3.1 µs with few rules. At 10,000 rules it nearly doubles the commit's judgment.
- **Not loosened, not changed:** the per-judgment gate holds. If the runner reads §1.6.6's "50 µs per torrent" as per commit, a flooded or cloned commit is over it. A fix belongs in `writer.rs` or `engine.rs`: reuse prepare's verdict for everything but the pack layer. Neither is in this slice's paths.

## Outside the brief's listed paths
- **`crates/api/tests/packs_gate.rs`** (new): the brief asks for the guardrails "through the API", and `crates/filter` can't depend on `crates/api`, so the test lives in the API crate. It's a new file, and no other slice owns it.
- **`web/e2e/packs.routes.test.ts`, not `web/e2e/packs.spec.ts`:** Playwright's projects match `*.test.ts` names (`playwright.config.ts`), so a `.spec.ts` file would never run. A `routes` name puts it in the `core` project, which CI runs, without editing the shared config.
- **`runner/slices.yaml`:** RP-G's own entry, `owns` updated to the files above.
