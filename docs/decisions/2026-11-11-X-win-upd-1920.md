# X-win-upd-1920 decisions

This slice makes the MSI updater handle error 1920 from a held `lodestar.exe`, and adds the follow-ups from #663's review. The brief is from the runner, dated 2026-11-11. The review is `reviews/rv-663-cb9fdeb6.md`. This file supersedes the "What's left to a holder of `lodestar.exe`" bullet in `2026-11-11-X-win-upd-bounds.md`.

No new privilege, trigger or principal is added beyond §2.47's Q13 row. The helper reads one more file it already writes: the `msiexec` log in staging.

## 1920 from a held file: retried, bounded, never skipped at once
- **The case:** a local user holds `lodestar.exe` open with share mode 0 through StartServices (review item 1). The window is wider than #663's decisions file said:
  - `IMAGE_WAIT` never refuses, so a hold taken at any time before the copy works, as long as it lasts until the MSI's `ServiceControl Start="install" Wait="yes"`. No race is needed.
  - The SCM can't open the image, so Windows Installer reports error 1920, rolls the install back, and `msiexec` exits 1603.
  - Before this slice, the forward install's version was then skipped for good, and a rollback's reinstall halted.
- **How it's told apart (`msi::held_open`):** the exit code must be 1603, and the run's own log must show error 1920 for this service.
  - The forward log is `msiexec.log` and the rollback's is `msiexec-rollback.log`, both in staging, opened as themselves (never through a link).
  - Each is removed right before its run, so a run that fails before it writes a log never reads an earlier run's 1920.
  - A log path outside staging is never read.
- **The log is untrusted input:**
  - Only its last `LOG_TAIL` (1 MiB) is read, from an even offset.
  - The encoding comes from the file's own first two bytes: Windows Installer's UTF-16LE byte-order mark is kept in front of a tail that starts past it. Without a mark, a tail is read as UTF-16LE only when its first 64 units have the ASCII NUL pattern, otherwise as lossy UTF-8.
  - One fixed pattern is matched per line, with no regex. The number 1920 must follow a word and be followed by `. `, and the service's name must come after it: `Error 1920. Service 'Lodestar' …`, or `Fehler 1920. Der Dienst "Lodestar" …`.
  - **Where language still matters:** a UTF-16 log works in any language, because the mark decides. An ANSI log in a non-UTF-8 code page with a non-Latin word before `1920` decodes to U+FFFD, which isn't a letter, so the 1920 is missed. That fails safe: it's an ordinary failure, as before this slice. Windows Installer writes UTF-16 logs, so this is the unusual case.
  - **Tests:**
    - Fixtures: UTF-16 with and without the mark, a tail that starts on either byte, a long Cyrillic UTF-16 log, UTF-8, German, another service's 1920, another error, the number inside another number or after a non-word, a garbled log, and a 1920 before the tail.
    - Property tests: any bytes give an answer and never a panic, and a 1920 line among any printable lines is found in both encodings.
    - All fixtures are synthetic. A real `msiexec` 1920 log can't be produced on a CI runner.
- **A forward install** that fails this way answers `install_blocked`, a new outcome code, instead of `install_failed`.
  - Windows Installer has already rolled it back, so the journal goes, the old service is started, and nothing is skipped.
  - `blocked.json` in staging, which only the helper writes, records the version, the request and the attempts so far. The helper's next run tries that same request again even though `handled.json` names it. That's the one exception to "a request is acted on once", and it's bounded.
  - **In practice that run is the boot run.** The service starts the task only after it writes a new request.
  - **One retry per blocked attempt:** a retry first clears the request from the record and keeps the count. So a retry that ends any other way isn't repeated at every boot: a refusal, a busy Installer, a stale manifest. If the record can't be saved, there's no retry, and if the blocked attempt's own record can't be saved, it's an ordinary failure, skipped, so the bound always holds.
  - **The user's skip wins:** no retry once `<data>\bin\skipped` lists the version, and then the record goes. The service can write that file, but it can only stop a retry, and a list that can't be read stops it too.
  - The `MAX_BLOCKED`-th (3rd) failure in a row is an ordinary one: the version is skipped as `failed`, and `result.json`'s `detail` and the Event Log give the plain reason ("couldn't start the Lodestar service … 3 times in a row; error 1920: another program may hold lodestar.exe open, or the version doesn't start").
  - An install that succeeds, or that fails any other way, ends the count. A busy Installer (1618) leaves it as it is.
  - The count is per version, not per request, so a new request can't reset it. That matters because a release whose service really doesn't start also gives 1920. The bound still skips such a release, two attempts later than before.
- **A rollback's reinstall** that fails this way is a `rollback_pending` retry, not a halt.
  - The count is `blocked` in the journal, a `#[serde(default)]` field that an older helper ignores and then halts as before.
  - The step's state is saved, and the service is disabled and stopped again before the run returns. The marker stays.
  - The next run hands the reinstall to a fresh copy.
  - The `MAX_BLOCKED`-th failure in a row halts, with the reason in the recovery text.
- **The code chosen:** a new `install_blocked`, not an existing code. `installer_busy` means "another install was running, nothing changed", and this case isn't that: the install ran and was rolled back. Nothing parses `result.json`'s outcome (it's display only), so a new code breaks nothing.

## The #663 review items
- **Item 3, the recovery text after a journal that couldn't be saved:**
  - A step's save that fails is now `Stop::Journal`, and its halt carries `Cause::Journal`.
  - Its recovery text says "the rollback's journal couldn't be saved, so it stopped there" (with "the store may be half restored" or "the store was restored before it did"). It no longer blames the reinstall.
  - Tested by turning the journal into a folder right after the restore.
- **Item 4, `remove_marker`'s early return:** no marker means no lock is taken and nothing waits. Tested on the drop path with `.lock` held throughout: `take_lock` never makes a busy pass.
- **Item 5, the Windows-only wiring:**
  - A Windows-only unit test calls `boot_time` (a plausible past time, stable within the slack), `installer_idle` (answers within its wait) and the real parent lock (holds the wait, and its drop frees it).
  - `tests/update_windows_msi.rs` checks that `--run-msi` refuses outside staging.
  - The spawn mapping in `Windows::msiexec` still has no test of its own: making `msiexec` itself fail to spawn isn't feasible on a CI runner.
- **Item 6, PowerShell:**
  - `boot_time`'s CIM query has `-OperationTimeoutSec 30`, and a test pins it.
  - `Windows::powershell_command` is now the one setup every script uses: `authenticode()`, `boot_time` and `installer_idle`. It runs powershell from System32 with no profile, no `PSModulePath`, no window and no `LODESTAR_*` variable.
- **Item 7:** `the_wait_for_the_parent_is_bounded` now has a budget of 20 s. Once the parent lets go, the test uses the real clock, and Windows may hold a lock it was just given back for seconds.

## Item 2: a 3010 that never takes effect, then offered again (investigated, recorded as a residual)
- **What happens:** after the forward bound ends a 3010 whose replacement never took effect (`install_interrupted`), nothing is skipped, so the service offers `to` again.
  - Windows Installer has already registered `to` as installed (the files were left for the restart).
  - So the next `msiexec /i` of the same package is likely a maintenance run that exits 0 without replacing `lodestar.exe`.
  - The helper then judges probation on what's running, which is still `from` and healthy, and reports `installed` for `to`. The journal goes, and the service, still `from`, offers `to` again.
  - Windows installs are Install-now only today, so each pass of the loop is a re-offer the user must click. Each one stops and starts the service once, and `from` keeps serving. No version is wrongly skipped and nothing is lost.
- **Why it isn't fixed here:**
  - The fix is to refuse to report `installed` when the run that judges finds `from` still on disk after a 0. In the real helper that run is always the program on disk.
  - But the helper's tests run `msiexec` inline with the program on disk left as `from` and expect `installed`. A correct fix means reworking most of the install tests, well past "small".
  - **Residual:** a follow-up slice should add that check, skip `to` with a plain reason ("Windows Installer reports it installed, but the program on disk is still `from`: repair or reinstall by hand"), and move the install tests to model the program on disk.
- **The other half of item 2 is accepted as #663's review says:** two clock corrections of more than 60 s within one boot can end the forward wait early, and `to` then misses probation.

## Residuals
- **Item 2's loop:** above.
- **The forward retry runs only when the helper runs again** (at boot, or when the service starts the task), and only while `request.json` and the staged MSI are still in place. If the service removes the request, the next Install starts a new request, and the per-version count carries over.
- **A holder who is there at every attempt** still gets the version skipped after `MAX_BLOCKED` attempts. That's bounded and visible in the Event Log. The boot run usually comes before any user signs in, so a boot-time retry gets past a user's hold.
- **The boot retry checks only the skip list.** It doesn't check the user's mode (Off) or a pause. Windows installs today are Install-now only, so a retry repeats an install the user asked for. When install windows (owner §2.13) reach Windows, the boot retry must also wait for the window and honour mode and pause. The runner flags this.
- **`install_blocked` shows the service's `install_failed` notice** (`check.rs`, not owned here), so the user isn't told it will retry at boot. That's for `check.rs`'s owner.
- **A 1920 from a version that did run** (it migrated the store, then didn't reach Running in time) starts `from` on the migrated store with no restore, whether it's skipped or retried. This predates the slice and is noted for the rollback's owner.
