# LEGAL-1r decisions (release/v0.5.1, rc.4)

LEGAL-1r builds the Legal Notice (owner decision §2.38; `docs/decisions/2026-11-04-X-legal-docs.md` "Slices") for `release/v0.5.1`'s setup screen, so v0.5.1 opens with it. The owner chose this scope on 2026-11-05: rc.4 = the memory fixes plus this. The fuller LEGAL-1 (main's wizard step) and the packs on by default ship in v0.5.2. Every point below is a runner-level refinement under §2.19, flagged to the owner.

## Server
- **`legal::NOTICE_VERSION` is 2, not 1.** The notice's own heading says "Version 2 · 2026-11-04", and section 10 tells the reader that "the version and date are at the top". A constant of 1 beside a text that says 2 would leave the API and the screen disagreeing about which notice was accepted. A unit test ties the constant to the heading. No install has accepted any version yet, so starting at 2 costs nobody a second showing.
- **The text is built in from `crates/api/src/legal/notice.md`, a copy of `docs/legal/legal-notice.md`.** The Docker build copies only `crates/`, so `include_str!` can't reach `docs/`. A unit test fails when the two differ, and another rejects Markdown the in-app renderer doesn't handle (raw HTML, tables, images, numbered lists).
- **The accepted version lives in `auth.json` (`notice_version`), not the settings database.** The admin password is in `auth.json`, so this is the only way "the same transaction as the admin password" holds: setup writes both in one atomic file replace (`write_private`). Every later change (`change_password`, `rotate_sessions`, `set_proxy`) carries it forward. `lodestar backup` already copies `auth.json`, so a restore keeps it. A missing field (an install set up on rc.1 to rc.3) means "not accepted".
- **`POST /setup` takes `notice_version`.** If it's missing or not the current version, the answer is `409 notice_required` (golden `setup_notice_required`, `setup_notice_stale`), and nothing is claimed. The check comes after the rate limiter and the token check, so a refusal spends an attempt like any other refusal and tells someone without the token nothing new. `Auth::setup` (tools and tests) accepts the current version; `Auth::setup_with_notice` is what the route calls.
- **The gate: every session route answers `409 notice_required` until the current version is accepted** (golden `error_notice_required`). It's enforced in the one session check that `protected`, `require_session` (`/api/status`) and the key guard's session branch all share. A session is still a session: sign-in succeeds, `GET /auth` reports `notice_required: true` (only to the signed-in caller), and with no session the answer stays the 401. That's the narrowest server-side gate on the release code: no new session state, no change to cookies, Argon2, the login bucket or the lock order.
- **Two new routes.**
  - `GET /legal/notice` is open, so the setup screen can show the notice before a session exists. The notice is public text.
  - `POST /legal/accept {version}` is the one session route the gate lets through, behind its own session-only guard. It's same-origin JSON like every write, needs no password, and records only the current version (`409 notice_required` for a stale one, golden `legal_accept_stale`). Accepting again is a no-op.
- **API keys and feed tokens aren't gated.** They're for connected apps (*arr, feed readers) that can't read a notice, and the admin who created them meets the gate at their next sign-in. Gating them would stop every integration on the upgrade to rc.4 before anyone had signed in. On this branch keys reach only the feed route.
- **Raising `NOTICE_VERSION` shows the notice again; an editorial change that leaves it alone doesn't.** Pending means `stored < current`. Tests cover both, using `Auth::with_notice_version` to raise the version across a restart.
- **Unchanged:** the login, setup, password and confirm limits (5 per IP, then 1 every 12 s), the key-failure and per-key buckets, the save-lock order, cookie flags and the 401's `setup_required`. `crates/api/tests/legal.rs` re-checks the login limit with the notice pending.

## UI
- **Setup has three steps:** setup token, Legal Notice, admin password. The notice step shows the rendered notice in a scrolling, focusable region and a required "I have read the Legal Notice" checkbox. Continue refuses until it's ticked, and the submit refuses too if the tick is somehow missing. Setup sends the version it showed. If a different build answers `notice_required`, the form goes back to the notice step with the new text and the tick cleared.
- **The sign-in gate is on the sign-in page, not a new route.** A 409 `notice_required` from any request goes to `/login?next=…` through the same handler as a 401, keeping the session. There the page shows the notice and an "I have read it, continue" button instead of the password form, then goes on to `next`. Signing in on a pending install hands over to the gate directly.
- **About:** `/settings/about` was the "not available in this build" page on this branch. It's now a static page with one section, Legal, showing the notice. The other About content arrives with the Settings screens.
- **Rendering:** the notice is parsed into nodes (`features/auth/markdown.ts`) and rendered by Svelte, never through `{@html}`. Only `https:` links become links, and they open with `rel="noopener noreferrer"`.
- **A new layout token, `--notice-max-height` (50dvh),** caps the scrolling box. It's in `docs/design-tokens.md` §7. There was no fitting token, and arbitrary values are banned.
- **Messages:** en and zh keys for the labels only. The notice body is English, as §2.38 decides.
- **About's strings (`auth_about_*`) live in the auth messages, not the settings messages,** for two reasons:
  - `settings_*` keys are the settings form's field map, which a test keeps in step with the server;
  - reusing the shell's "About" and "Search" labels split the shell's message chunk and pushed the Alert route and the lazy search results over budget.

  For the same reason, the sign-in gate's "changed again" line is its own key rather than setup's.
- **The live-updates stream treats `409 notice_required` like a 401:** it hands over to the sign-in page and resumes once a request works again.
- **The `/status` page** (`crates/lodestar/src/status.html`, the server's own status page) no longer has its own setup form: that form couldn't show the notice. It links to the web UI's `/setup` instead. A pending notice shows a link to the sign-in page's gate, and a 409 makes it re-check rather than report "Can't reach the server."
- **The soak collectors are unaffected:** `docs/soak/tools/linux/collect.py` and the Windows scripts read only `/healthz`, `/metrics` and `/`, which need no session.
- **`Auth::with_notice_version` stays `pub` and `#[doc(hidden)]`,** like `Auth::without_refill`: the integration tests in `crates/api/tests/` are a separate crate, so `#[cfg(test)]` can't reach them, and a test-only Cargo feature would be a new shared-manifest change for one helper. It only changes which version this process shows; nothing in the server calls it.

## The notice text on v0.5.1
The notice and the operator guidance were written against `main`. This slice checked them against this branch, and so did the legal session (X-legal-docs). The runner authorised the release-copy edits below on 2026-11-05. Where the two checks disagreed, this branch's code decided: for example, pausing is in Insights, not Settings.

**`docs/legal/legal-notice.md` (and the built-in copy):**
1. The italic status line at the top is deleted. It said the in-app step wasn't built, and this PR builds it.
2. §2: "and magnetico" is deleted. Only `lodestar import-bitmagnet` exists.
3. §2: the download-client hand-off clause is deleted ("and, if you set one up, hand it to a download client of your own; …"). No hand-off exists.
4. §2: "pause it in Settings after setup" → "pause it from the Insights page after setup". There are no Settings screens in this build.
5. §3: the filters paragraph is replaced with the legal session's wording.
   - The five packs are named (malware, lures, fakes, spam and scams; junk is a ranking score, not a pack). They're off until turned on.
   - This version has no Settings pages, so those controls and **Show adult content** are set in the configuration file, through environment variables or through the API.
   - The unauthorised-copy pack, the packs on by default and the setup review are gone; they ship in v0.5.2.
6. §5: the API-key bullet → "API keys you issue, which Lodestar keeps as hashes, never in clear; this version stores no credentials for other services, because it connects to none".
   - The relayed wording said "keyed hashes in a file outside the database". On this branch, keys are plain SHA-256 hashes in the database's `api_keys` table (`crates/api/src/keys.rs` `mint`, `crates/store/src/api_keys.rs`), so that clause was deleted and reported to the runner.
7. §5: "Credentials are encrypted at rest …" → "Lodestar holds no stored credentials for other services in this version."
8. §5: the backup sentence names "the key that unseals quarantined names" (`seal.key`) instead of "the key that unlocks stored secrets".
9. §5: the notification channels (ntfy, Discord, email, webhooks) are deleted. Nothing sends on them.
10. §5: the Diagnostics sentence is deleted. There's no Diagnostics panel; the data is only in `GET /system`.
11. §5: ", and which you can clear" (the query log) is deleted. Nothing clears it.
12. Kept as written, and checked on this branch:
    - "and again whenever its version is raised": this PR does that;
    - the Peer activity log kind, off by default (`crates/api/src/dto/logs.rs`);
    - "saved searches" (`crates/api/src/saved.rs`).

**`docs/legal/operator-guidance.md`,** copied from #447:
