# UN-2 decisions

The SABnzbd and NZBGet adapters that send a usenet item to a Usenet download client (architecture §18.6, §18.10; `docs/plan/2026-11-05-v07-m7.md`). Nothing calls them yet: UN-3 adds "Send to SABnzbd/NZBGet", and UN-1 produces the items.

## The interface (`clients/usenet.rs`)
- **A trait of its own, `UsenetClient`, next to the torrent `DownloadClient`.** An NZB isn't a magnet or a `.torrent`, and none of `DownloadClient`'s options apply: save path, file selection, batch, listing. The trait has three methods:
  - `add_nzb(&Nzb, &NzbOptions) -> JobId`: the NZB's bytes in, the client's job id out;
  - `test() -> UsenetInfo`: the version, plus what the credentials may do (`Access`), for the settings screen;
  - `categories() -> Vec<Category>`: the existing `Category` type, with no save paths.

  There's no download listing and no history scraping (brief).
- **`ClientError` is reused unchanged.** Every usenet failure maps onto an existing variant (`Auth(..)`, `Rejected`, `Protocol`, `InvalidRequest`, `Timeout`, `Unreachable`, `Blocked`), so UN-3 handles both client families the same way.
- **`UsenetConfig` and `connect_usenet`,** like `ClientConfig` and `connect`. They're for UN-3 to build an adapter from stored settings. The credentials are `Secret`s, and `Debug` shows the redacted URL only.
- **`NzbOptions`:** an optional category, an optional priority (low, normal, high, force; `None` is the client's default) and `paused`.
- **Shared edit:** `clients/mod.rs` gains only the three `pub mod` lines. The types live in the new `clients/usenet.rs` (see "Shared files").

## Bytes, never a URL (runner, §2.33)
- **Lodestar sends the NZB's bytes,** never the indexer's link:
  - SABnzbd gets `mode=addfile`, a multipart upload;
  - NZBGet gets `append` with base64 content.

  No adapter calls SABnzbd's `addurl` or appends a URL to NZBGet.
- **Why:** a Prowlarr or Newznab NZB link carries the indexer's API key (`…&apikey=…`). A client that fetches a URL keeps it in its queue, its history and its logs, where any other user or tool of that client can read it, and keeps it after Lodestar forgets the item. UN-1 never stores the link (UN-0). UN-3 rebuilds it from the indexer id and GUID at send time, fetches the NZB itself through the guarded egress, and hands the bytes to this adapter. The key then never leaves Lodestar.
- **NZBGet also reads any `append` content that starts with `http://` or `https://` as a URL to fetch.** Base64 never starts that way (it has no `:`), so uploaded bytes can't be taken for a URL.

## Bounds
- **`MAX_NZB_BYTES` = 16 MiB, checked in `Nzb::new`.** An `Nzb` can't be built over the cap, so an oversize one never reaches the network.
  - **Why 16 MiB:** it's the `.torrent` cap (`MAX_TORRENT_FILE`) and the list cap (`MAX_LIST_BYTES`), so every upload to a client has one ceiling. An NZB lists each article's message id at ~100 bytes per article of ~750 KB, so 16 MiB covers a release of about 100 GB. That's well past a 4K remux; season packs that big are normally split into one NZB per episode.
  - NZBGet's base64 makes that request ~21 MiB. Each upload's timeout grows with its size, as qBittorrent's does (`upload_timeout`).
- **`Nzb::new` also refuses** an empty file, and one with no `<nzb` element in its first 64 KiB. That catches an indexer's HTML or JSON error page served as a 200 before it's sent to the client.
- **The file name is cleaned:**
  - the path goes, so `../x` becomes `x`;
  - quotes and control characters go;
  - it's cut to 200 characters;
  - it always ends in `.nzb`, so SABnzbd never treats it as an archive (`.zip`, `.rar`, `.7z`) to unpack.
- **Every answer is read within a cap:** 1 MiB (`MAX_ANSWER`) for each SABnzbd answer and for NZBGet's `version` and `append`, and 4 MiB (`MAX_CONFIG`) for NZBGet's `config`. Category lists keep at most 10,000 names (`MAX_CATEGORIES`).
- **Answers are parsed strictly:**
  - **SABnzbd:** `status` must be a boolean. `nzo_ids` must hold exactly one id of 1–64 ASCII letters, digits, `_` or `-`. A field of the wrong type fails the whole answer.
  - **NZBGet:** `result` must be an integer in `i64`, so a float, a string or a 30-digit number fails to parse, and one outside `1..=i32::MAX` (NZBGet's ids are `int`) is refused. `0` or less is NZBGet's refusal (`Rejected`). An echoed `id` must match the request's.
- **A reflected credential is scrubbed.** Before an answer is parsed, every copy of SABnzbd's key, or NZBGet's password and user name, is replaced with `***` (secrets of 4 bytes or more). A reverse proxy whose error page echoes the request body can't then put the key into a `Rejected` reason.
- **Error text is bounded.** A client's own reason goes through `client_reason` (one line, at most 200 characters). An unexpected status becomes `HTTP <n>: <reason>`. The rest are `&'static str`.
- **Fuzzing:** two new targets, `sabnzbd_answer` and `nzbget_answer`, since the crate's other answer parsers have one (`client_list`). Each module also has a proptest that its parsers never panic.

## Credentials
- **SABnzbd's API key and NZBGet's user name and password are `Secret`s.** No log line, error or `Debug` carries them. A query string in the configured URL (`?apikey=…`, pasted from a browser) is dropped, and the URL is only ever printed through `redact`.
- **SABnzbd's key goes in the `POST` body,** never in the query string. SABnzbd merges body and query parameters (CherryPy's `kwargs`, `interface.py`) and has no header for the key. Every call is a `POST` (a form, or multipart for `addfile`), so the key stays out of URLs, proxies and SABnzbd's access log.
- **NZBGet gets HTTP Basic, the header marked sensitive** (reqwest's `basic_auth`). The adapter never puts credentials in NZBGet's `/user:pass/jsonrpc` path, which would land in logs.
  - Empty credentials send no header, for an NZBGet without a password.
  - A user name with a `:` is refused, because Basic splits at the first one. So is a `user:password` over 192 bytes: NZBGet decodes Basic credentials into 257 bytes and refuses longer base64 (`WebServer.cpp`), then drops the request without answering, which would look like a network failure.
- **NZBGet's `config` answer holds the client's own passwords** (`ControlPassword`, `ServerN.Password`) for the control user. It's the only way to list categories. So:
  - the parser keeps only the `CategoryN.Name` values, and skips every other value with `IgnoredAny`, unread;
  - the adapter's copy of the answer is zeroized once parsed. The HTTP stack's own buffers, and the copies `read_limited` leaves as it grows, aren't, so this narrows the window rather than closing it.
- **`test` tells the kind of key apart.** SABnzbd's `mode=auth&key=…` (no key needed, changes nothing) answers `apikey`, `nzbkey` or `badkey`.
  - The NZB key can add (access level 1) but not list categories: `get_cats` is level 2 and answers 403 `API Key Incorrect`. `UsenetInfo::access` says `AddOnly`, so the settings screen can explain why categories are missing.
  - NZBGet's add-only user can call `version` and `append` only, so its `access` is `Unknown`; `categories` then fails with the client's `Access denied`.

## Network
- **Every request goes through `GuardedClient` with `NetPolicy::download_client()`,** as the torrent adapters' do: loopback and private addresses are allowed; link-local, metadata and reserved ones aren't.
  - The URL is checked when the adapter is built, so a refused address fails when the setting is saved.
  - Redirects are never followed: any 3xx is `Protocol("the client redirected")`, since the target would get the key or the NZB in the body. A test shows the target receives nothing.
  - Each request has a timeout (default `CLIENT_TIMEOUT`, 15 s).
- **No new egress path,** and no `reqwest` client of the adapters' own.

## Error mapping
| Answer | Error |
|---|---|
| SABnzbd 403 `API Key Incorrect` / `API Key Required`, or an empty 403. With `api_warnings` off, SABnzbd also sends the address and host-name refusals below empty, so the settings screen should say "check the key, `inet_exposure` and `host_whitelist`". | `Auth(BadCredentials)` |
| SABnzbd `mode=auth` → `badkey` | `Auth(BadCredentials)` |
| SABnzbd 403 `External internet access denied` (outside `inet_exposure`) | `Auth(AddressRefused)` |
| SABnzbd 403 `Access denied - Hostname verification failed` (`host_whitelist`) | `Auth(OriginRefused)` |
| SABnzbd `{"status": false, …}`; with `error`, its text | `Rejected` |
| NZBGet HTTP 401 (wrong user name or password) | `Auth(BadCredentials)` |
| NZBGet JSON-RPC `error` (`Access denied`, `Invalid parameter (…)`) | `Rejected(message)` |
| NZBGet `append` → 0 or less | `Rejected("the client refused the NZB")` |
| Any 3xx | `Protocol("the client redirected")` |
| Unparseable, oversize or wrong-type answer | `Protocol` |

## Versions followed
- **SABnzbd 4.5.5** (the latest 4.x tag), from its source: `sabnzbd/api.py` (`_api_table` access levels, `report`, `_api_addfile`, `_api_auth`) and `sabnzbd/interface.py` (`secured_expose`, `check_apikey`, the `_MSG_*` texts).
  - The develop branch (5.0, on Starlette) keeps the same modes, key levels and refusal texts.
  - Priorities are -1, 0, 1 and 2, and -2 is "paused", which replaces the priority. So a paused add keeps the category's default priority (recorded in `NzbOptions::paused`).
- **nzbget-ng v24.8** (the latest 24.x), from its source: `daemon/remote/XmlRpc.cpp` (`DownloadXmlCommand`, `BuildResponse`, `BuildErrorResponse`, the add-user check) and `WebServer.cpp` (`CheckCredentials`, `SendAuthResponse`).
  - **Checked against v26.3:** it only adds an optional trailing `autoCategory` to `append`. The nine v13+ parameters this adapter sends are unchanged.
  - Priorities are -50, 0, 50 and 900 (low, normal, high, force).
  - NZBGet finds `method` and `params` by searching the request text, so the body is serialized with `id`, `method` and `params` in that order (a struct, not a map), and a test pins it.
  - **v24.8's string scanner (`WebUtil::JsonNextValue`) ends a string early at two adjacent escapes.** It skips one escaped character but doesn't re-check the next for `\`. v26.3 fixed it. A category such as `a""b` would shift every later `append` parameter, so `NzbOptions` refuses `"` and `\` in a category, for both clients. The file name has neither (it's cleaned), and base64 has no escapes.
- **The fixtures aren't live recordings.** The sandbox refused to run the downloaded clients, and the runner said not to try. So each answer in `tests/fixtures/usenet_clients/` was built from those source lines, NZBGet's checked against v26.3, and each file's `recorded_from` says so (runner, 2026-11-12). Re-recording against running clients is a follow-up for whoever has them.

## Memory
- **A 16 MiB NZB is copied a few times on its way out:** about 58 MiB at the peak for NZBGet (the bytes, the base64 string and the serialized body), and about 32 MiB for SABnzbd (the bytes and the multipart part's own copy). Sends are one at a time, at a user's click, so this is accepted. Streaming the body would need a `Bytes` part or a hand-written JSON writer, which isn't worth it at this cap.
