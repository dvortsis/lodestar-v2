# CR-gate-metrics decisions

The crawler gate's metric (`docs/owner-decisions.md` §2.25, master plan "Crawler program"). The thresholds stay the owner's to confirm. These entries decide only how the gate is measured; the runner flags the hidden-rows entry to the owner (§2.19).

- **The numerator is `searchable_new_total{origin="network"}`.** The owner's definition ends at "committed as stored and searchable", so the stored count (`metadata_new_verified_total`) is a diagnostic for index lag, not the gate.
- **Counted at commit points, never at fetch.** The writer (`crates/pipeline/src/writer.rs`) counts new, already stored, filtered, quarantined, rediscovered, duplicate and store failed, from what the store's `Inserted` says. The prepare stage counts floor refusals and unusable metainfo. Failed verification is counted where the pool's terminal loss ends the lease (`WorkerFunnel::lost`). Reason: a per-attempt count would count retries, and it couldn't tell new from already stored.
- **The brief's "rediscovered (already stored)" is split in two:** `already_stored` (fetched and verified, then found in the store) and `rediscovered` (a stored torrent sighted again, never fetched). They mean different things for the crawler.
- **`failed_verification` is the pool's give-up reason, `Loss::Invalid`.** It counts keys whose final attempt was invalid: a hash mismatch, or a protocol or handshake violation (peer-wire's `FailureKind::Invalid` covers all three). A key that failed on one peer and then timed out on another is in `fetch_lost_total{reason="timed_out"}`. Per-attempt failures stay in `fetch_failures_total{kind="invalid"}`. Carrying hash mismatch separately through the pool's terminal loss is a follow-up (runner, 2026-10-30).
- **A new row counts even if its lease went stale between the fencing check and `complete`.** The store says it's new, and a later delivery of the same key reads as `already_stored`, so it's still counted once. `writer_stored_total` keeps its old boundary; the two can differ by that rare race.
- **Rows a rule hides, demotes or flags count as new and searchable** (refines §2.25's "filtered-out items"; flagged to the owner). They're stored and indexed, and an `Action::Hide` pack only takes them out of default results; Adult rows hidden by the content setting are the same. "Filtered out" means held back from the store: a drop (`filtered`) or a quarantine (`quarantined`). If the owner wants hidden rows out of the numerator, a `hidden` breakdown can be added without changing the others.
- **"Searchable" is the serving index's commit hook** (`Committed::max_torrent_id`), wired in `crates/lodestar/src/services.rs` beside the Insights recorder's hook (runner's decision, 2026-10-30). There's no search-crate change. The hook already reports the watermark after every commit, including the gap report after a failed reload, and it outlives index swaps. A rebuild's own commits don't report; the next live commit covers their ids. `PipelineConfig::gate_follows_index` is set when a serving index exists, so ids are handed over from the writer's first commit. An index commit between `Pipeline::start` and the hook's `add()` is counted late, at the next commit with `docs_added > 0`, never lost. `services::gate_tests` checks the wiring end to end with a real serving index.
- **First seen is the lease's `discovered_at`**, the existing per-key state. For keys restored from the fetch queue, whose `discovered_at` is the old cohort hour, it's clamped to this run's start. There's no new per-key map.
- **Bounded hand-off for latency:**
  - The writer `try_send`s `(id, first seen)` on a 4,096-entry `sync_channel`, which is lock-free.
  - The index commit drains it into a queue of at most 65,536 entries (24 bytes each, about 1.5 MiB), evicting the oldest. Then it counts the ids at or below its watermark.
  - The queue's lock is taken once per index commit, on the indexer's thread, and nothing else contends for it.
  - At either bound, only the latency is lost: the drop is counted in `discovery_to_searchable_dropped_total`, and the record is still counted searchable once a commit passes the highest id dropped. A record dropped while a commit runs may be counted one commit early.
  - A row the index committed before the writer handed it over is counted as searchable at once.
- **A record can be counted one index commit late.** One handed over while a commit is draining waits for the next commit that adds documents, so its latency includes that wait. Counts are never doubled or lost. If crawling stops just then, the count waits for the next commit.
- **Whole-second resolution.** Discovery times are unix seconds, so the lowest bucket is 1 s. The 5 s search budget (§3) sits on a bucket bound.
- **`origin` has one value, `network`.** Imports and recovery never go through the writer's fetch path today. Their label values are reserved for when they're counted, rather than rendered as zeros that look measured.
