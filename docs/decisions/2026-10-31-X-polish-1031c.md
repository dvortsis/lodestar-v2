# X-polish-1031c decisions

Optional findings from the #283, #278 and #279 reviews. No schema, wire or setting change; one new error code and one internal `settings` key.

- **A segment's failed file scan stops its siblings** (`crates/search/src/files.rs`, #283). `torrent_ids` keeps a local `AtomicBool` beside the executor call; `scan_segment`'s checks read it as well as the token. The first real error is the one reported, since the executor reports the first by position, which may be a sibling's stop. A cancel or deadline still wins over it. The bitset choice's size hint is commented as an estimate for `size:` ranges (tantivy 0.27's range doc set returns `num_docs / 10`), and the scan test pairs parts to segments by their first id, not by position. `2026-10-31-X-search-files-2.md` gains one line: the 10M measurement must include concurrent cold queries, because cold scans share the file pool's ≤ 4 threads.
- **Only the server's shutdown stops a classification re-queue, and a stopped one is redone at the next start** (`crates/api/src/filters.rs`, #278). `FiltersApi::shutdown` is a `CancelToken` that `services.rs` cancels when the graceful shutdown starts; no deadline stops a re-queue, as before. Before a rule is added or removed, its query is appended to a pending list (`settings` key `classify.requeue_pending`, a JSON list) under the same store lock, and the entry is removed once the re-queue's marks are in. A stop or failure anywhere after the rule change leaves the entry. At every start, `services.rs` runs `FiltersApi::resume_requeues` in the background: it redoes each pending re-queue, so a new Is-adult rule's existing matches are marked once the server is running again. Marking twice is harmless: a torrent is enriched once more. A request the shutdown cuts short gets `503 server_stopping`. The shutdown is checked between steps and between mark chunks, and inside the file-index scans. The torrent-index search, `SearchIndex::matching_ids`, takes no token, and it's outside this slice's paths, so it runs to its end. An unreadable pending value is started afresh rather than blocking rule changes, since nothing could be recovered from it.
- **The hint order's bound holds however the clock reads** (`crates/dht/src/node/hints.rs`, #279). `compact_order` now keeps at most one entry per live hint: a slot taken and recaptured at the same `Instant` left entries that all matched it, so `retain` couldn't drop them and every capture could rescan. After a compaction at most 2 × `HINT_CAPACITY` entries remain, so at least 2 × the cap captures pass before the next. This is the same bound the brief's `next_compact` option gives, and it also bounds the deque. Tested by `recaptures_at_one_instant_stay_bounded`, with two keys alternating so the brief's "skip a repeat of `order.back()`" alternative wouldn't catch it.
- **Tests wait on conditions only:** none of the new tests sleeps.
