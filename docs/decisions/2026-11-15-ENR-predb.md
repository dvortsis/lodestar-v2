Slice ENR-predb (API lane, 2026-11-15). Spec: plan `docs/plan/2026-11-05-v07-m7.md` (ENR-predb row, §6 Q4 and Q5), owner §2.47 (v0.7 Q4: yes for PreDB, at most 1 request a second, user interest first, the slice recording its terms check), architecture §18.2 and §18.7. ## Terms check (owner §2.28), 2026-11-15
- **Which PreDB HTTP sites still run and publish an API** (checked on 2026-11-15T23:20Z, and the API page's text re-read from the site's own script on 2026-11-16T00:10Z; a one-record search then answered in the shape below):
  - **predb.net** runs, and publishes a public JSON API at `https://api.predb.net/` with a documentation page (`https://predb.net/api-documentation/`, "Last updated 08.08.2025"). `predb.de/api` now redirects there.
  - **predb.ovh**, whose API many tools used, no longer resolves.
  - **predb.me** and **predb.club** serve web pages only; neither publishes an API or terms for one.
- **Chosen: predb.net**, the one site that still runs and publishes an API for this use. One fixed endpoint, not a configurable one: no other site offers an API to put on an allow-list today. A later slice can add one, with its own terms check.
- **What predb.net's API page says**, and what the plugin does:
  - It welcomes automated use: "A lot of users were crawling our website … We think that this is ok and we want to make it easier for you all, so we decided to create an API." No key, no account.
  - "Treat this API respectfully, it runs on a simple server with limited resources. Your IP will be blocked if you overload the API." **Rate limit: 30/60s.** The owner's cap is at most one a second; the site's is stricter, so **one request every two seconds, no burst** (`HostRate::every(2 s)`, `min_interval` 2 s), one request a lookup, back-off from a minute to 6 hours after a 429 or 5xx, and a 60 s hold (or the answer's `Retry-After`) after an error answer on a 200.
  - "Don't use the API to create your own DB. It makes more sense to import another dump." **The plugin never walks the database:** it searches only for a title the runtime hands it (user interest first, then the capped background, Q12), one page of at most 100 records, and keeps only what it matches. That's lookup, not a mirror. Q12's 100,000 lookups a day can't be reached at 30 a minute (43,200 a day at most); in practice user interest and the cache keep it far below.
  - Results are limited to 100 pages; the plugin reads page 1 only.
  - No attribution is asked for, so there's no `ATTRIBUTION` constant. The site's own disclaimer says it hosts no copyrighted content; the plugin reads release names and metadata only, never NFOs or files.
  - `robots.txt` on predb.net allows all agents but a list of SEO crawlers; the API host has none.
- **User-Agent:** `Lodestar/<version> (<the project's repository URL>) lodestar-sources-plugins` (`predb::USER_AGENT`), the same for every install; nothing about the user or their host.
- **Read again before the plugin is switched on**, with the fixtures re-recorded from the live service (as ENR-14's condition says for every External plugin).

## Off by default, External class
- **The manifest:** `predb`, an Enrichment source, Consent `External`, endpoint `https://api.predb.net` only, `enabled_by_default: false`, never always-adult, never finds private. No account, so not the Account class; no credential.
- **Eligibility is ENR-10's** (`identify::check`): never a `PRIVACY`, held, hidden or Adult item. `a_private_item_is_never_sent` checks it under the runtime.
- **Kinds: Movie and TV.** The title-then-year (or season) reading of a scene name below is written for them. Music, games, software and books name their releases differently (`Artist-Album-…`, `Title.v1.2-…`); they can follow once local matching exists, since it doesn't depend on reading the title.
- **No host wiring**, as for ENR-14: listed in the catalogue only. It's switched on with the slice that lifts the External consent gate, with the Legal Notice's line (owner, §2.33).

## What is sent (Q5)
- **One request a lookup, a fixed template** (`search_request`): `GET https://api.predb.net/?type=search&q=<title> <year>&limit=100`, with the headers `Accept` and `User-Agent` only.
- **`q` is the parsed title folded** (lower case, letters, digits and single spaces) **and the year** when the query has one. That's less than Q5 allows (no kind is sent), and folding means no character of it can reach predb.net's parameter syntax (its `-` exclusions or `,` lists) or another parameter (`a_hostile_title_is_one_parameter`). The year is sent because predb.net searches from the start of a release name, and the year narrows a page of 100 newest records to the right film.
- **Never the info hash, the torrent's name, its files, sizes or CRCs.** `a_private_item_is_never_sent` checks the one request's URL holds none of the torrent name's other words.
- **`SENDS`** (`predb::SENDS`) says this in plain words for the Sources row (UI review 02 §5.5). `Manifest` has no field for it: the runner's follow-up, as for the other lane plugins.

## The parser (`sources-feeds/src/predb.rs`)
- **On the shared bounded JSON reader**, like ENR-14's. Pure, no I/O, no panics, no unwraps, no truncating casts. **Linear time**: repeats found with a bitmask over the six record keys and two root keys; `many_unknown_keys_are_read_in_linear_time` reads 300,000 unknown keys whole.
- **The caps** (`SEARCH_LIMITS`): 256 KiB, depth 6, 5,000 values, 200 elements per array, 2 KiB per decoded string, 100 records. A page of 100 records is about 30 KiB.
- **Strict shape:** an answer counts only when `Page::whole()`: read to its end, `"status": "success"`, `data` an array when present, no repeated or escaped root key, no trailing bytes, and no record spoiled. A record is spoiled by a wrong type, a repeated or escaped key it reads, a `pretime` that isn't an integer, or a missing `release` or `pretime`. **One exception:** a well-formed record whose name isn't a scene name (printable ASCII, no spaces, 1–255 bytes) is dropped and counted (`foreign`) but doesn't spoil the answer, since the service may hold such rows and one shouldn't stop every lookup of that title.
- **Empty search:** `"status": "success"` with no `data` (predb.net sends a `message` instead). **Error:** `"status": "error"` on a 200; its `message` is never read.
- **What it keeps** (`PreRelease`): the release name; `pretime` as Unix seconds UTC, kept only from 1980-01-01 to 2100-01-01 (`MIN_PRETIME`, `MAX_PRETIME`), else `None`; the section when it's printable ASCII of 1–64 bytes; the nuke state; the nuke reason (cleaned, at most 255 bytes) only when the state isn't clean; the genre (cleaned, at most 64 bytes). The id, file count, size, group, links and NFO are never read.
- **Nuke state**, predb.net's `status`: 0 clean, 1 nuked, 2 unnuked, 3 deleted ("delpre"), any other number `Unknown`. Read from the site's own front end, which labels them so.

## The pre claim's shape (for IRC-3)
- `PreClaim { release, pretime, section, nuke, reason }` (`sources-plugins/src/predb.rs`): the release name as the scene wrote it, its pre time in Unix seconds UTC, its section (the scene's own category string, such as `X264-HD`), its `Nuke` state (`Clean`, `Nuked`, `Unnuked`, `Deleted`, `Unknown`) and the reason. IRC-3's pre lines (name, section, time, nuke/unnuke) map to the same fields; `Nuke` and the bounds live in `sources-feeds::predb` so both can share them.

## Matching
- **Local matching is what pre data needs, and the runtime can't do it yet.** A pre time, section and nuke state belong to one release, so they can only be claimed for a torrent whose own name equals a release name. ENR-10's `Query` carries only the parsed title, year and kind (Q5), by design, and its `Identification` has no field for pre data. The brief's rule holds: **nothing more is sent to get it.** So this slice builds:
  - `pre_for(name, releases)`: the one release whose name equals the torrent's name (ASCII case ignored); none, or two records of that name that disagree, is nothing. Pure, run inside the install; `name` is never sent.
  - `PreDb::releases(kit, query)`: the same one request as a lookup, returning the parsed records, so the runtime can call `pre_for` with the torrent's name locally.
- **What `lookup` answers today:** the work the releases agree on. A release agrees when its folded name starts with the folded title followed by the query's year, or, for a series, a season (`s01`, `s01e02`). A longer title that starts the same way never agrees. With no year asked, agreeing releases of two different years are no match (it never guesses). The answer has no id (PreDB has none for a work), the year, up to three of the agreeing releases' genres, and confidence 75 with a year, 55 without (lower than the databases': a scene name's title is read from its start, not stated).
- **Follow-up for the runner (local pre claims):** to store pre data, the runtime needs (1) a way to hand a plugin's raw answer back to a local step that knows the torrent's name and file names, never sending them (for example, an `Identifier` method that returns a local matcher, or `IdentifySource` calling `PreDb::releases` then `pre_for` itself); and (2) somewhere to store it: `Details` (`crates/store/src/claims.rs`) has `source_category` (fits the section) and `posted_at` (Unix seconds, but defined as a usenet post time), and nothing for the nuke state or reason. A new `Details` field set (pre time, nuke, reason) is an on-disk format change, so it's a core slice of its own, not this one. IRC-3 needs the same.

## Errors
- As ENR-14's: 200 is parsed; 429 is "limiting requests" and the host limiter holds the host; a 3xx is never followed; anything else or a transport failure is "the request failed"; an error answer on a 200 holds the plugin for its `Retry-After` (60 s if none, between 2 s and an hour); an answer that isn't whole is "wasn't understood". None of them is a miss, and no error holds the service's text.

## Terms (ENR-terms)
ENR-terms (#962) gave every identify plugin a `Terms` and an adult marker on its answers. PreDB's choices (`predb::TERMS`), from predb.net's API documentation page as read above, within the owner's v0.7 Q4 answer (at most one a second, user interest first):
- **`background_walk: false`.** The API page says "Don't use the API to create your own DB", and Q4 says user interest first. Lookups stay on the items you open.
- **`redistribute: false`.** predb.net publishes no licence for its data, so nothing clearly allows passing its answers on. They stay in Lodestar's own UI.
- **`retention: Retention::DEFAULT`** (180 days). The API page asks for no shorter.
- **`attribution`:** "PreDB.net", linked to `https://predb.net/`. The API page asks for no credit; the link is a courtesy.
- **Adult marker: the scene section.** predb.net gives each release its section, and the scene files adult releases under `XXX` (`XXX`, `XXX-0DAY`, `XXX-IMGSET` and the like). An answer whose agreeing releases include one in such a section, or one whose name carries the `XXX` tag as a whole word, is `adult: Some(true)`, and the runtime refuses it (`predb::marked_adult`, `an_xxx_section_is_marked_adult_and_refused`).
- **Every other answer is `None`, not `Some(false)`.** A non-`XXX` section (`X264-HD`, `TV-X264`) is where the pre was sorted, not a statement that the work isn't adult: sections are assigned by each site's pre bots, with no fixed list, and an unknown or missing section says nothing. So **`adult_marker_required: false`**: requiring a marker would refuse every answer, and the gate that matters is the runtime's, which never looks up an Adult item. The plugin answers films and series only.
