# P-m8 decisions (#515)

The planning slice for E-M8, build-plan P7 ("M8 hardening → 1.0"). The plan is `docs/plan/2026-11-06-m8-hardening.md`. These are the plan's own structural choices, made under owner §2.19. Every product question (OQ1–OQ6, RQ1–RQ7) stays open in plan §5 until the owner or the runner answers it; none is decided here. No owner decision, security or content-safety decision, or owner-set number is changed.

- **Three id families: `M8-*` for build and review slices, `R-v1-cut` for the release cut (as `R-rc3-cut`), `G-v1-*` for gates.** No collision with existing prefixes (`SEC-`, `REL-`, `PERF-` were checked and are free, but the `M8-` prefix keeps the whole epic recognisable on the dashboard). Gates follow `G-v051` and `G-v06-crawler`.
- **Gates measure; they never fix.** Each gate slice owns only `docs/gates/v1/<gate>/**`. A finding becomes an `X-*` slice the runner adds (plan §4.4), so a gate's evidence is never on a head that its own fix changed.
- **The security review is split into eight surfaces plus a method slice (M8-SEC-0),** by trust boundary rather than by crate: network parsers and crawler; API, auth and web; sources and importers; content safety; update and supply chain; cluster and companions; integrations, logs and privacy; store, host, packaging and `unsafe`. Each is about one reviewer's context. Reviews own only their report, so up to four run at once with no owns conflict.
- **Reviews start when their surface's epics are merged, not at the RC.** Reviewing at the RC would put eight reviews and their fixes on the critical path after the cut; reviewing stable code earlier and running one delta review in G-v1-security costs less wall-clock time.
- **Unfixed findings are not committed in detail.** The repo is public and v0.5.1 is released. The plan's default (plan §4.3 M8-SEC-0, §5 OQ6) lists unfixed findings by id and severity only; where the detail is held is the owner's choice (OQ6), since it needs GitHub settings only the owner has.
- **The real-data relevance set is split in two.** A committed set of openly licensed real names is gated in CI; a held-out set on the owner's pilot data is judged and run on the import host, and only aggregate scores leave it. This keeps owner data and copyrighted or adult names out of the public repo (owner-decisions §3 repository visibility; owner §1.8) while still measuring ranking on real data, as build-plan §0.6 asks. Routed to the owner (OQ2).
- **Proposed, owner question OQ1: the 10M gates move to a dedicated machine, not the PR CI** (owner §1.6.3 says "enforced as CI benchmark gates"; a scheduled and dispatched workflow is still CI). The 200k regression gates stay in `ci-ok`. The 10M runs so far varied by about ±50 % between cloud containers (`docs/decisions/2026-11-05-X-search-files-5.md`), so they can't gate. A self-hosted runner on a public repo is a security choice, so the host and its lockdown go to the owner (OQ1).
- **Chaos tests live in `crates/crawler-sim`.** That crate exists so the DHT and sources testing seams are enabled only in tests; the multi-worker harness needs the same seams. The harness is frozen after M8-CHAOS-1, and later targets add helper files by `#[path]`, so M8-CHAOS-2/3/4 can run at once with disjoint owns.
- **The in-process DHT network test (§17) is its own slice (M8-NET-E2E)** with no worker dependency, so it can start early and M8-CHAOS-4's parity check builds on it.
- **Two gates not named in P7 are proposed:** a 24 h Linux Docker soak on the RC (OQ4, owner's host) and a 1.0 design review (§17 lists "a `design-review` pass with no blocking findings"; G-m5's review predates M6–v0.8's screens). The Linux soak needs the owner's host, so it's an owner question; the design review is within §17 as written.
- **The 50M gate isn't re-run for 1.0 by default** (RQ3, runner): build-plan §0.6 already says a later producer re-checks only the budgets it affects.
- **The Windows soak's bar reuses CR-0's memory rule** (`docs/decisions/2026-10-30-CR-0-acceptance.md`, already in `analyze_cr0.py`): CR-0 was a 24 h Windows soak the owner accepted, so the plan asks the owner only to confirm it for 1.0 (OQ3) rather than inventing a number.
- **Gates on the RC dispatch their workflows on `release/v1.0`.** GitHub runs scheduled workflows on the default branch only, so "nightly on the RC" can't happen; the theme, chaos, fuzz and 10M gates use `workflow_dispatch` with the RC ref.
- **The cut, the rc tag and the 1.0 tag are separate** (runner's review of #515). `R-v1-cut` cuts `release/v1.0`; the owner's `v1.0.0-rc.<n>` tag is `ext:owner-v1-rc` (`auto: tag:`), which every RC gate depends on directly, so the gates run in parallel rather than behind one RC gate; `ext:v1-tagged` follows a green `G-v1`, as `ext:v051-tagged` follows `G-v051`, so no gate depends on its own outcome.
- **A full-CI-on-the-RC gate (`G-v1-ci`)** maps §17's first bullet: `ci.yml`, `web.yml`, `e2e.yml` and `release.yml` dispatched on the RC head. `ci.yml` and `web.yml` don't run on `release/*` pushes, so M8-CI adds `workflow_dispatch` to `web.yml`.
- **Every slice with no other unmet dep carries `ext:v051-soak-verdict`,** so the dashboard doesn't show it as ready before the soak verdict. There is no `pull_forward` field; RQ1 says when they launch.
- **G-v1-10m names every owner-set and §3 number** (plan §4.3), the component size budgets, regex, Insights and the worker budgets included, so none is dropped by omission. `search-bench` lacks the regex and Insights rows, so M8-PERF-1 adds them. Low-resource mode has no figures anywhere, so the plan proposes them (RQ8, runner, flagged).
- **A design review before the RC (M8-DR),** with G-v1-design as a delta on the RC, so design fixes don't land after the cut.
- **`Cargo.lock` is chained, not shared in parallel:** M8-NET-E2E → M8-CHAOS-1 → M8-PERF-2, the three slices that add dependencies.
- **Security surfaces widened** (runner's review): the query language, tokenizer, release-name parser and query cost go to M8-SEC-2 (denial of service through the API); M8-SEC-3 waits for E-v08's Nostr and Lemmy parsers; M8-SEC-5 covers every workflow's permissions and secrets, the self-hosted runner and `status-connector-deploy`; M8-SEC-1 fuzzes all 27 targets for an hour each (runner's call).
- **The re-run rule after the RC** (RQ4) is a table from what a fix touches to the gates it re-opens; a docs-only change, M8-DOC-4 included, re-opens none.
- **Brief rule kept:** this slice doesn't edit `runner/slices.yaml` or `runner/dashboard.yaml`. Plan §4.1 holds the entries ready to paste and the new `ext:` conditions (`owner-m8-q1`..`q6`, `bench-runner`, `windows-soak-host`, `unraid-soak-host`, `owner-v1-rc`, `v1-tagged`).
- **Checked:** every dep names an id in `runner/slices.yaml` or the plan (except the running `X-search-files-6`, noted in plan §4.1); no two slices that can run at once share an owned path (checked with a script over the YAML block); every slice is estimated at ≤ 1,500 changed lines.
