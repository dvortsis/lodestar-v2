# LEGAL-1 decisions (main: the Legal Notice as a setup-wizard step)

LEGAL-1 brings LEGAL-1r's Legal Notice (`release/v0.5.1`, #457; `docs/decisions/2026-11-05-LEGAL-1r.md`) to `main`, and puts the notice into main's first-run wizard as its own step (owner §2.38, §2.40; `docs/decisions/2026-11-04-X-legal-docs.md` "Slices"). It ports the behaviour, not the commits. Every point below LEGAL-1r doesn't already decide is a runner-level refinement under §2.19, flagged to the owner.

## Server: what is the same as v0.5.1
- **Same stored field.** The accepted version stays in `auth.json` as `notice_version`, written in the same atomic replace as the admin password at setup (§2.40's runner addition), so the database schema doesn't change. The version itself is raised to 3 on `main` (below), so a v0.5.1 install sees the new notice once.
- **Same gate.** Every session route answers `409 notice_required` (golden `error_notice_required`) until the current version is accepted. It's enforced in the one session check that `protected`, `require_session` (`/api/status`) and the key guard's session branch share, so it covers proxy sessions too. `GET /auth` reports `notice_required` only to a signed-in caller. `POST /setup` refuses a missing or stale `notice_version` after the rate limiter and the token check, and claims nothing. `GET /legal/notice` is open. `POST /legal/accept {version}` is the one session route the gate lets through.
- **Not gated:** API keys, feed tokens and any route a token reaches through `key_or_session` or `feed_token` (the alert feeds on `main`), and the Sonarr and Radarr webhook calls SRC-11b (#459) added (`POST /webhooks/{integration}`, which carries its own token). The admin who made them meets the gate at their next sign-in, and an upgrade mustn't stop a connected app first. The webhook token routes (`/webhooks`, `/webhooks/{integration}/token`) need a session, so they meet the gate. `crates/api/tests/legal.rs` covers both (`webhooks_are_not_gated`).
- **A pending session cookie beside a valid API key gets 409.** The key guard checks the session first (`auth/guard.rs`), as LEGAL-1r does: a browser with the notice pending is a browser, whatever else it sends. A connected app sends only its key and is never gated.
- **Every route is checked, not a sample** (runner, after the security review): `tests/legal.rs` `every_route_but_the_allowed_ones_meets_the_gate` walks every path and method in the router's own `/openapi.json` with a pending session and expects `409 notice_required`, except for `PENDING_ALLOWED`: `GET /auth`, `POST /setup`, `/login`, `/logout`, `GET /legal/notice`, `POST /legal/accept`, `GET /openapi.json` and the webhook call `POST /webhooks/{integration}`. A future route that skips `protected` fails CI.
- **Accepting is logged** (runner): `auth.notice_accepted`, at info, with the client address and the version; the record carries the time. Never the session, the cookie or anything typed. Setup's acceptance is part of `auth.setup_complete`. The logs catalogue golden, the event list and its en/zh names follow.
- **SRC-17a (#462)** sets `Access::Session` in the session guard once `check_session` passes, so the notice check comes first and a pending session never gets the private-source access it marks.
- **Streams:** `/events` and `/logs/stream` go through `protected`, so a pending notice refuses them at open. Their heartbeat re-checks the cookie only. That's enough: the notice can only become pending again when the version constant changes, which needs a restart, and a restart ends every stream.
- **Unchanged:** the login, setup, password and confirm limits, the key-failure and per-key buckets, the save-lock order, cookie flags and the 401's `setup_required`. `crates/api/tests/legal.rs` re-checks the login limit with the notice pending.
- **A malformed version fails closed:** a non-number in `auth.json` stops the load rather than reading as "accepted".

## The notice text on main
- **Built in from `crates/api/src/legal/notice.md`,** a copy of `docs/legal/legal-notice.md` on `main` (the Docker build copies only `crates/`). The unit tests from LEGAL-1r stay: the copy matches the published file, the heading's "Version N" matches the constant, and the text uses only what the in-app renderer handles.
- **The status line at the top of `docs/legal/legal-notice.md` is deleted.** It said the in-app step was still being built; this PR builds it. X-legal-docs' session is done, so this PR owns the file (runner); the version bump and the one content edit are below.

## The wizard step
- **The Legal Notice is the wizard's first step** (§10.10.10 gains a step before "1. Setup token"). It runs in `/setup`, before there's a session: Legal Notice, then the setup token, then the admin password. The server takes all three in one `POST /setup`, which sends the version the step showed.
  - Why first and not between the token and the password (LEGAL-1r's order): the brief asks for it first, X-legal-docs asks for it "before first use", and the notice is public text, so showing it before the token proves nothing about who's at the screen. A wrong token returns to the token step with the box still ticked; a `409 notice_required` (a newer build answered) returns to the notice step with the new text and the box cleared.
- **Registration.** `/setup`'s steps are listed in `wizard/steps.ts` as `SETUP_STEPS = ['legal', 'token', 'password']`, one line, beside `STEPS`, the post-setup list. `STEPS` can't hold the notice: its steps run after setup, with a session, and the notice must be accepted before setup can claim the instance. `SetupForm` draws its stepper from `SETUP_STEPS`, and the wizard's progress lists them as done and numbers its own steps on from them (Network check is now step 4).
- **`wizard/LegalStep.svelte`** shows the notice through LEGAL-1r's `NoticeBox` (rendered from Markdown into nodes, never `{@html}`; only `https:` links become links, with `rel="noopener noreferrer"`), in a scrolling, focusable region of the `--notice-max-height` token's height, and the required "I have read the Legal Notice" box, unticked by default. It saves nothing itself. Continue refuses until the box is ticked, and the submit refuses too if it's somehow missing.
- **No layout shift.** The notice is the first thing setup shows, so it can't move the page when it arrives (the boot-shell CLS gates): the box has a fixed height (`--notice-max-height`, now a height rather than a cap, and `50svh` so a phone's address bar showing or hiding doesn't resize it mid-read), the loading line holds the same box, the checkbox is drawn at once and stays disabled until the notice is there, and the notice waits for the UI font's Latin face (preloaded; at most 2 s, `notice.ts` `FONT_WAIT_MS`) so its lines don't reflow on the font swap.
- **Focus:** on first paint nothing is moved; returning to the step (Back, or a changed notice) puts focus on the notice region once it has loaded, so a keyboard user can scroll it and then Tab to the box.
- **Messages:** the step's labels are `wizard_step_legal` and `wizard_legal_*` in `wizard/messages/{en,zh}.json`. The shared parts (the region's name, loading and retry, the sign-in gate) keep LEGAL-1r's `auth_notice_*` keys in `auth/messages`. The notice body is English only (§2.38). LEGAL-1r's `auth_setup_step_notice`, `auth_notice_intro`, `auth_notice_confirm` and `auth_error_notice_*` keys aren't ported; the step's own keys replace them.

## Sign-in gate, About and the status page
- **The notice is fetched outside the API client** (`notice.ts`): it's an open route, so its answer proves nothing about a session, and through the client it would mark a signed-out `/setup` visitor (or a pending gate) as signed in, which also skipped the account's language and region refetch after a real sign-in. It still reads errors through the client's envelope parser.
- **Headings nest under the screen's own.** The renderer takes a `level`: the sign-in gate (no screen heading names the notice) keeps `#` → h2 and `##` → h3; the setup step and About, whose h2 already says "Legal Notice" or "Legal", get `#` → h3 and `##` → h4.
- **The sign-in gate** is LEGAL-1r's, with one change: when signing in hands over to it, focus moves to the notice once it has loaded (as the setup step does), so keyboard and screen-reader users aren't left on a removed button. Otherwise unchanged: a 409 `notice_required` from any request goes to `/login?next=…` and keeps the session; the page shows the notice and "I have read it, continue", which posts `/legal/accept` and goes on to `next`. The live-updates stream treats the 409 like a 401.
- **About → Legal** is a new section in main's existing About screen (§10.10.13), before Licences and credits. "Show the Legal Notice" loads it on demand (its own chunk, like Diagnostics and the licence list) with its version, and a link to `docs/legal/operator-guidance.md` in the build's repository. Its keys are `settings_about_legal_*` in the About part's messages. LEGAL-1r's static About page and its `auth_about_*` keys aren't needed on `main`.
- **The server's `/status` page** loses its own setup form, as on the release: that form couldn't show the notice. It links to the web UI's `/setup`, and a pending notice links to the sign-in gate.

## NOTICE_VERSION is 3 on main (runner, 2026-11-05)
- **Why.** `main`'s notice differs in substance from the copy v0.5.1 users accept at version 2 (LEGAL-1r's release corrections). It describes what that build doesn't do: (1) the rule packs on by default and the unauthorised-copy pack; (2) handing a magnet link to a download client; (3) credentials for integrations, stored sealed with a key outside the database; (4) the notification channels (ntfy, Discord, email, webhooks), which contact the internet; (5) the Diagnostics panel in Settings → About and a query log you can clear. X-legal-docs says a change to what Lodestar requests, stores or sends raises the version, so the runner decided (a) on 2026-11-05: bump in this PR.
- **What changed.** `legal::NOTICE_VERSION` is 3 and the notice's heading reads "Version 3 · 2026-11-05" (a unit test ties the two). The stored field is unchanged (`auth.json` `notice_version`), so a v0.5.1 install, which stored 2, sees the new notice once at its next sign-in, and accepting stores 3 there. `auth.rs` `a_v0_5_1_install_sees_version_3_once` and `tests/legal.rs` `a_v0_5_1_install_sees_the_new_notice_once_at_login` cover it.
- **The one content edit** (runner's instruction): the packs-on-by-default sentence loses its "(planned)" marker and says what RP-DEF (#454) ships: on by default for a new data folder, while an upgraded install keeps its packs as they were. The unauthorised-copy pack stays "(planned)" until RP-UC merges. No other wording changed.
- **A factual deletion (runner, after review):** section 3 listed "junk" among the rule packs, but `main` has five packs (malware, lures, fakes, spam, scams); junk is a ranking score, as LEGAL-1r's release correction says. The word is deleted; nothing else changes and the version stays 3.
- **Release notes:** `main` has no v0.5.2 draft yet (`docs/releases/` holds v0.5.0 and v0.5.1), so the line "v0.5.1 users see the updated notice once" waits for it; it's in the PR description for whoever writes the notes.

## Size budgets (runner, §2.26)
The gate has to live in the shared API client and the events client (a 409 `notice_required` hands over to the sign-in gate), which adds 20–60 B gzipped to every route. Measured on the tree with `main` (SRC-15a) merged, three entries went over; each limit is raised by its residue rounded up to 64 B, the rule SRC-15a used:
- Settings FiltersScreen (first view): 31.08 KB against 31.07 KB, now 31.14 KB.
- Settings NotificationsScreen (first view): 45.09 KB against 45.07 KB, now 45.14 KB.
- Detail sections (on demand): 37.54 KB against 37.52 KB, now 37.59 KB.

**The §10.1 45 KB route cap is exceeded** by the Notifications screen's first view, by SRC-15a's and LEGAL-1's stacked residues (45.14 KB). The runner flags it to the owner (§2.19). About → Legal loads on demand with its own entry, "Settings about Legal Notice (on demand)" (measured 3.07 KB, limit 3.3 KB), so About's first view and its other parts keep their budgets.
