# UP-0 decisions: `.torrent` upload through one raw-body route

Brief: runner, 2026-11-12 (`briefs/UP-0.md`). Spec: `docs/plan/2026-11-05-v07-m7.md` §5 and §4.3 UP-0; `docs/architecture.md` §3, §12, §18.7; owner §2.37.

## Step 1: the exception as it will be built (restating plan §5)
The owner took the runner's recommendation (§2.37). This is that recommendation, term by term, as UP-0 builds it. Every difference from §5 is named under "Differences from §5" so it can go to the owner.

1. **One route, raw body.**
   - `POST /api/v1/torrents/upload`, in `crates/api/src/upload.rs`, mounted with one line in the api router. It doesn't use the JSON extractor.
   - `Content-Type` must be `application/x-bittorrent` exactly (ASCII case-insensitive; no parameters, no `;charset=`). Anything else, a missing header and `multipart/form-data` included, is `415 unsupported_media_type`, checked before the body is read.
   - No multipart parser, no filenames, no form fields, no query parameters. One request carries one file; the body is the file.
2. **The same guard as JSON writes.**
   - The route sits behind `auth::protected`, the guard every JSON write uses: a session cookie, or trusted-proxy auth where it's on (`logged_in`), and the accepted Legal Notice. No new auth path.
   - **API keys can't upload.** The route isn't under `key_or_session`, and no `KeyScope` grants it. A request with only an API key gets the same `401 login_required` as one with nothing.
   - **Same-origin:** the rule `same_origin_json` applies (`extract.rs` ~194): an `Origin` whose host differs from `Host` is `403 cross_origin`. `same_origin_json` itself can't be called, because it also demands `application/json`, so `upload.rs` applies the same Origin/Host comparison itself (`extract.rs` is not edited, per the plan).
3. **Bounded.**
   - **Body cap 8 MiB** (8,388,608 bytes), a §2.26 number the runner may raise to 32 MiB. A `Content-Length` over the cap is `413 body_too_large` before any byte is read; a body without one, or that lies, is read through a length-limited reader that stops at cap + 1 and answers the same 413. Nothing is parsed until the whole body is in and under the cap.
   - Parsed with `metainfo::TorrentFile::parse_with` and its existing limits (depth, list lengths, string lengths, file counts). No new parser.
   - One file per request (the body is the file; there's nothing else to parse).
   - **Its own rate-limit bucket, per client IP, separate from the login limiter:** a burst of **30**, then **1 a second** (3,600 an hour), at most 10,000 tracked IPs (the same cap the other limiters use). Over it is `429 rate_limited`. The bucket is spent before the body is read, so a refused request costs no parse. Reason: a user dropping a folder of torrents sends one request per file, so a burst of 30 covers a typical drop; at 8 MiB a request, 1 a second bounds parse and judge work to well under one core. These two are §2.26 numbers.
4. **Nothing stored but what a BEP 9 fetch would store, plus the out-of-info-dict claims.**
   - The info hash comes from the raw info-dict bytes, as `metainfo` derives it for a fetched info dict (v1, v2 and hybrid alike).
   - The stored record is what the verified-file path stores for a fetched info dict, with provenance "upload".
   - Out-of-info-dict keys become claims: `announce` and `announce-list` through X-claim-trackers' guard; `creation date`, `created by` and `comment` judged by the core like any claim text (stricter only). `url-list` (and `httpseeds`) is dropped and never fetched (§18.7). Every other top-level key is dropped.
   - **The raw file is dropped** after parsing unless the info-dict archive setting is on, and then it stores what the archive stores for a fetched torrent: the info dict minus `pieces` (`docs/architecture.md` §3). The rest of the file is never kept.
   - **`private=1` in the info dict makes it `private_source`** (BEP 27): its hash never reaches the DHT or any DHT-facing path (no sample, no `get_peers`, no announce, no harvest re-sighting).
5. **The same judgement as any metadata.** SRC-13b's verified-file path (`pipeline/src/torrent_cache.rs` `Feed` → `judge_sealed` → the writer's lease-free entry), floor hash list first, then the full pipeline. **A held verdict is never stored;** a floor-blocked one never is either. The new code is `crates/pipeline/src/local_torrent.rs`; `writer.rs` is not edited.

**Errors name the cause without echoing the file:** `unsupported_media_type` (415), `body_too_large` (413), `rate_limited` (429), `cross_origin` (403), `login_required` (401), `malformed_torrent` (400), `refused` (422, the floor or the pipeline turned it away) and `held` (422). No name, path, tracker, comment or other text from the file appears in a response or a log line; the info hash may.

## Differences from §5
- **No `Sec-Fetch-Site` check of its own.** §5 calls the rule "`same_origin_json`'s Origin/Sec-Fetch-Site rule", but `same_origin_json` checks only `Origin` against `Host`. UP-0 copies what JSON writes actually do and adds **one stricter step: `Sec-Fetch-Site: cross-site` is also `403 cross_origin`**. Stricter only, so it loosens nothing; named so the owner sees it.
- **A request without `Origin` is allowed, as for JSON writes.** That matches `same_origin_json`. It's safe here for the same reason: `application/x-bittorrent` isn't a CORS-safelisted type, so a cross-site page can't send it without a preflight the server doesn't answer, and an HTML form can't send it at all.

Nothing else differs: one route, raw body, session/proxy guard, no API keys, the 8 MiB cap, `parse_with`'s limits, a separate bucket, the verified-file path, held never stored.
