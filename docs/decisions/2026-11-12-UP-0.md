# UP-0 decisions: `.torrent` upload through one raw-body route

Brief: runner, 2026-11-12 (`briefs/UP-0.md`). Spec: `docs/plan/2026-11-05-v07-m7.md` §5 and §4.3 UP-0; `docs/architecture.md` §3, §12, §18.7; owner §2.37.

## Step 1: the exception as it will be built (restating plan §5)
The owner took the runner's recommendation (§2.37). This is that recommendation, term by term, as UP-0 builds it. Every difference from §5 is named under "Differences from §5" so it can go to the owner.

1. **One route, raw body.**
   - `POST /api/v1/torrents/upload`, in `crates/api/src/upload.rs`, mounted with one line in the api router. It doesn't use the JSON extractor.
   - `Content-Type` must be `application/x-bittorrent` exactly (ASCII case-insensitive; no parameters, no `;charset=`). Anything else, a missing header and `multipart/form-data` included, is `415 unsupported_media_type`, checked before the body is read.
   - No multipart parser, no filenames, no form fields, no query parameters. One request carries one file; the body is the file.
2. **The same guard as JSON writes.**
   - The route sits behind `auth::protected`, the guard every JSON write uses: a session cookie, or trusted-proxy auth where it's on (`logged_in`), and the accepted Legal Notice. No new auth path.
   - **API keys can't upload.** The route isn't under `key_or_session`, and no `KeyScope` grants it. A request with only an API key gets the same `401 login_required` as one with nothing.
   - **Same-origin:** the rule `same_origin_json` applies (`extract.rs` ~194): an `Origin` whose host differs from `Host` is `403 cross_origin`. `same_origin_json` itself can't be called, because it also demands `application/json`, so `upload.rs` applies the same Origin/Host comparison itself (`extract.rs` is not edited, per the plan).
3. **Bounded.**
   - **Body cap 8 MiB** (8,388,608 bytes), a §2.26 number the runner may raise to 32 MiB. A `Content-Length` over the cap is `413 body_too_large` before any byte is read; a body without one, or that lies, is read through a length-limited reader that stops at cap + 1 and answers the same 413. Nothing is parsed until the whole body is in and under the cap.
   - Parsed with `metainfo::TorrentFile::parse_with` and its existing limits (depth, list lengths, string lengths, file counts). No new parser.
   - One file per request (the body is the file; there's nothing else to parse).
   - **Its own rate-limit bucket, per client IP, separate from the login limiter:** a burst of **30**, then **1 a second** (3,600 an hour), at most 10,000 tracked IPs (the same cap the other limiters use). Over it is `429 rate_limited`. The bucket is spent before the body is read, so a refused request costs no parse. Reason: a user dropping a folder of torrents sends one request per file, so a burst of 30 covers a typical drop; at 8 MiB a request, 1 a second bounds parse and judge work to well under one core. These two are §2.26 numbers.
4. **Nothing stored but what a BEP 9 fetch would store, plus the out-of-info-dict claims.**
   - The info hash comes from the raw info-dict bytes, as `metainfo` derives it for a fetched info dict (v1, v2 and hybrid alike).
   - The stored record is what the verified-file path stores for a fetched info dict, with provenance "upload".
   - Out-of-info-dict keys become claims: `announce` and `announce-list` through X-claim-trackers' guard; `creation date`, `created by` and `comment` judged by the core like any claim text (stricter only). `url-list` (and `httpseeds`) is dropped and never fetched (§18.7). Every other top-level key is dropped.
   - **The raw file is dropped** after parsing unless the info-dict archive setting is on, and then it stores what the archive stores for a fetched torrent: the info dict minus `pieces` (`docs/architecture.md` §3). The rest of the file is never kept.
   - **`private=1` in the info dict keeps it from every DHT-facing path** (BEP 27): no scrape, no cache lookup, no refetch, no get_peers. As built, this is the store's BEP 27 mark, not `private_source`: see "As built" below.
5. **The same judgement as any metadata.** SRC-13b's verified-file path (`pipeline/src/torrent_cache.rs` `Feed` → `judge_sealed` → the writer's lease-free entry), floor hash list first, then the full pipeline. **A held verdict is never stored;** a floor-blocked one never is either. The new code is `crates/pipeline/src/local_torrent.rs`; `writer.rs` is not edited.

**Errors name the cause without echoing the file:** `unsupported_media_type` (415), `body_too_large` (413), `rate_limited` (429), `cross_origin` (403), `login_required` (401), `malformed_torrent` (400), `refused` (422, the floor or the pipeline turned it away) and `held` (422). No name, path, tracker, comment or other text from the file appears in a response or a log line; the info hash may.

## Differences from §5
- **No `Sec-Fetch-Site` check of its own.** §5 calls the rule "`same_origin_json`'s Origin/Sec-Fetch-Site rule", but `same_origin_json` checks only `Origin` against `Host`. UP-0 copies what JSON writes actually do and adds **one stricter step: `Sec-Fetch-Site: cross-site` is also `403 cross_origin`**. Stricter only, so it loosens nothing; named so the owner sees it.
- **A request without `Origin` is allowed, as for JSON writes.** That matches `same_origin_json`. It's safe here for the same reason: `application/x-bittorrent` isn't a CORS-safelisted type, so a cross-site page can't send it without a preflight the server doesn't answer, and an HTML form can't send it at all.

Nothing else differs: one route, raw body, session/proxy guard, no API keys, the 8 MiB cap, `parse_with`'s limits, a separate bucket, the verified-file path, held never stored.

The runner confirmed step 1 on 2026-11-12 (both differences accepted: (a) is stricter only, (b) is exactly the guard JSON writes have).

## As built
Refinements the runner decided on 2026-11-12, recorded here for the owner (§2.19):

- **A `private=1` upload is stored with BEP 27's `flags::PRIVATE`, not `PRIVATE_SOURCE`** (a refinement of plan §4.3's "is `private_source`").
  - The writer's lease-free entry, which the brief requires, hard-codes `private_source: false` for a file that came through no lease (`crates/pipeline/src/writer.rs:293`) and reads only `stored_private` at commit (`writer.rs:1854`). Setting `PRIVATE_SOURCE` would need a `writer.rs` edit, which the plan rules out.
  - `PRIVATE` is set by the store's own prepare step from the info dict (`crates/store/src/lib.rs:1598`). It's in `flags::PRIVACY` (`lib.rs:126`), the mask every §18.7 gate refuses: scrapes (`swarm.rs`'s `NEVER_SCRAPED`, the health scheduler), cache lookups (`torrent_cache::Gate`), refetches (`partial_hashes`), ENR-1, Send, export and Torznab.
  - `crates/pipeline/tests/local_torrent.rs` uploads a private hybrid and checks the public paths: it's never offered for a scrape, a refetch or a cache lookup (by either hash), and ENR-1 refuses it as private. `crates/lodestar/tests/upload.rs` shows Torznab never serves it on a running instance.
  - **A private torrent's trackers and comment are dropped**, as SRC-13's `Verified::claims` drops them: a private tracker's announce address holds the uploader's passkey, and its comment often names the tracker. The pipeline test scans every table to check that the tracker's address is stored nowhere.
- **`created by` is dropped.** `sources::claims::Claims` has no field for it, and SRC-13 dropped it for the same reason (`docs/decisions/2026-11-05-SRC-13.md`). `url-list` (and every other top-level key) is dropped too, never fetched (§18.7).
- **`creation date` becomes `Provenance::published_at`** when it falls in SRC-13's believable range (2001-07-01 to 2100), at Medium confidence, since nothing outside the info dict is covered by the hash. **`comment` becomes the `description` claim.** The writer judges both at `ingest_found`, as it judges a cache's.
- **Trackers** pass X-claim-trackers' guard (`lodestar_integrations::net::public_tracker_url`) plus the torrent cache's own rules (no query, fragment or passkey-shaped path segment, at most 512 bytes), in the guard's form. The writer's claim check runs on them again before they're stored.
- **The archive is the existing path.** The info dict goes through `torrent_cache::judge_sealed`'s `preparer.prepare(info, Some(raw_info))` (`crates/pipeline/src/torrent_cache.rs:376`), the same call a fetched dict takes. When `archive_raw` is on, the store keeps `info_without_pieces(raw)` (`crates/store/src/lib.rs:1231`, `crates/metainfo/src/info.rs:587`), so `pieces` is dropped, exactly as for a BEP 9 fetch. There's no second form.
- **Counters.** Commits go through the writer's lease-free entry, so stored and held-at-commit uploads are counted in `WriterStats::torrent_cache` with the cache's. `local_torrent::UploadStats` counts uploads received, accepted, malformed, refused and held at judging. It isn't exported to `/metrics` yet, so there's no `docs/metrics.md` row. **Follow-up (runner):** split the writer's counters by source once a slice owns `writer.rs`.
- **The Origin–Host comparison is repeated** in `crates/api/src/upload.rs`, because `same_origin_json` also demands `application/json` and `extract.rs` isn't edited. The `the_origin_rule_agrees_with_json_writes` table test runs the same cases through both and asserts that they agree, apart from the stricter `Sec-Fetch-Site: cross-site`. **Follow-up:** one shared helper, once a slice owns `extract.rs`.
- **No Origin is allowed, as for JSON writes,** for the reason above: `application/x-bittorrent` isn't a CORS-safelisted type, so another site's page can't send it without a CORS preflight, which the server never answers with permission; and an HTML form can only send `application/x-www-form-urlencoded`, `multipart/form-data` or `text/plain`.
- **The rate bucket** is keyed on the same resolved client address as the login limiter (`extract::ClientIp`: behind a trusted proxy, the forwarded client, never the proxy). It has its own limiter (`upload::Limiter`), not the login one's `Buckets`. When the table of 10,000 addresses is full, only buckets that have fully refilled are forgotten (the same state as a new bucket, so nothing is reset). If it's still full, an address with no bucket is refused, and no existing bucket is ever evicted. The table test covers this.
- **At most 4 requests read a body or wait on the pipeline at once** (`upload::IN_FLIGHT`). A request past that waits, unread, for a turn; a test holds it to that. Each turn has a **60 s read deadline** (`upload::READ_DEADLINE`, `408 body_timeout`), so stalled clients can't keep every turn (fresh self-review). With the pipeline's own queue (4) and judge (1), and requests whose client left after sending, about 9 bodies (72 MiB) are held at most, plus a held file's info dict waiting in the writer's channel. These are new performance bounds, so they're the runner's call under §2.26.
- **Order of refusals:** the session guard (401, or 409 until the notice is accepted), then the content type (415), then the origin (403), then the rate bucket (429), then a declared length over the cap (413). The body is read only after that, through the limit (413 once it passes 8 MiB, `408 body_timeout` after 60 s, `400 bad_body` if the connection fails). It's then judged.
- **What a 202 means.** The upload has been read and judged storable, and handed to the writer. The writer judges it again at commit if the rules have moved on (stricter only). A file already stored gains the upload as a source. The answer carries the primary info hash and whether it's private, and nothing from the file.
- **The `upload` source** is a built-in source registered at every start (`Pipeline::start_with`), as imports register theirs. It's the torrent's provenance and a search `source` term. It isn't a plugin and has no Sources-screen row.
- **If a judgment panics, the judge task ends,** as the torrent cache's does. Every later upload then answers `503 uploads_unavailable` until a restart, and nothing is stored from the file that panicked. The proptest and the fuzz target cover `read`; `judge_sealed` is the cache's, already fuzzed.
- **`GET /torrents/upload`** now answers 405 (with a session) instead of the detail route's `400 bad_hash`. The static segment takes precedence over `{hash}`.
