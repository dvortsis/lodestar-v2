# X-watch-search-wait decisions (#1166)

On #1161's CI (ubuntu-latest), `crates/lodestar/tests/watch.rs`, `a_served_instance_takes_files_from_its_watch_folder`, timed out at its search wait: for over a minute after the good file was taken, a search for `Watched Cut` never answered `"total":1`. `main` was green and a re-run passed. These decisions change only the test; no product code and no spec section is affected.

- **The most likely cause, not a confirmed one: the test joined the live DHT and matched on words a crawled torrent can share.** The servers ran with the DHT on (`LODESTAR_DHT_PORT=0` is an ephemeral port, not off), so on a GitHub runner each one joins the live DHT for the test's run (about 90 s, up to about 3 minutes) and stores real torrents. The search was for two common words (`Watched Cut`) and required exactly one result. One crawled torrent matching it makes `total` 2, and the wait fails for its whole minute. Locally the failure doesn't reproduce: one run and eight parallel runs beside four CPU hogs all found the file within 13 ms, but this container has no UDP egress, so it never joins the DHT. The failed attempt's raw log couldn't be read, and the test didn't print the server's log anyway. Nothing else in the path (watch, `Uploads::submit`, the writer's lease-free entry, the live indexer committing every 2 s, the response's plain-number `total`) explains a miss of over a minute.
- **The old check had a substring weakness.** It looked for the text `"total":1` in the response, so `"total":12` passed too: ten or more matches hid a wrong count. The check now parses the JSON.
- **The servers run with the DHT off** (`LODESTAR_DHT_ENABLED=false`, as `cluster_serve.rs` does; runner, 2026-11-28). The watch doesn't need the DHT, and a CI test shouldn't depend on internet traffic it doesn't control. Checked: with the DHT off, the watch's takes are still stored, indexed and found, and all four tests pass.
- **Each searched torrent carries a token no other torrent has** (`Qzvxkr`, `Qzvxst`), and the search is for that token alone.
- **The wait is stricter, not looser.** `until_found` waits, with the same 60 s deadline and 200 ms poll and no fixed sleep, for a 200 whose JSON has `total` exactly 1 and one hit whose `name` is the torrent's exact name. The log check now also proves the torrent's name stays out of the log.
- **A timeout explains itself.** It fails with the last search response, `GET /api/v1/system` and the server's log, so if the cause was something else (an indexer retry, a failed store write), the next failure names it.
