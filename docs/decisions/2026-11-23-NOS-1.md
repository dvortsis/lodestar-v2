# NOS-1 decisions (#1101)

BIP-340 Schnorr signature checks for Nostr events (`crates/sources-feeds/src/nostr_sig.rs`), per plan `docs/plan/2026-11-06-v08.md` Q-r2 and its NOS-1 entry, architecture §18.5 and §18.9. Pure and unused until NOS-3 (plan §5.4: lands early, inactive).

- **Dependency:** `k256 = "=0.14.0"`, `default-features = false`, `features = ["schnorr"]` (plan Q-r2; approved in the brief). RustCrypto's pure-Rust secp256k1: no C, no build script, no `links`, so it builds on Windows as on Linux. 0.14.0 is the newest release. Without default features there's no ECDSA signing, `std`, `getrandom`, PKCS#8 or precomputed tables. It adds 14 crates to both lockfiles: `base16ct` 1.0.0, `cpubits` 0.1.1, `crypto-bigint` 0.7.11, `der` 0.8.3, `ecdsa` 0.17.0, `elliptic-curve` 0.14.3, `ff` 0.14.0, `group` 0.14.0, `k256` 0.14.0, `primefield` 0.14.0, `primeorder` 0.14.0, `sec1` 0.8.1, `signature` 3.0.0 and `wnaf` 0.14.1. All are `Apache-2.0 OR MIT` (`ff` and `group` write it `MIT/Apache-2.0`), inside `web/licenses/allow.json`; `web/licenses/rust.json` is regenerated for them. `ecdsa` and `der` come in because k256's `sha256` feature turns on `ecdsa-core/digest`; nothing here calls them.
- **sha2: no second version.** k256 0.14.0 depends on `sha2` 0.11 and `digest` 0.11, so it resolves to the workspace's one `sha2 =0.11.0` and `digest` 0.11.3 (`cargo tree -d` shows no duplicate). The plan's condition (a second `sha2` only if no k256 release uses 0.11) doesn't arise. k256 0.13.x would have pulled `sha2` 0.10 beside it, one reason for 0.14.0.
- **Only the verifier is used in shipped code.** `nostr_sig::verify` is `VerifyingKey::from_slice`, `Signature::from_slice` and `VerifyingKey::verify_raw`: k256 does the curve maths, nothing is hand-rolled. `verify_raw` hashes the message as BIP-340 says (any length, not pre-hashed), so the event's 32-byte id is the message, as NIP-01 states. The tests also use k256's `SigningKey` to make synthetic events.
- **`bool`, not `Result`.** Failure has one meaning (drop the event), and k256's error is deliberately opaque, so `verify` and `event_signed` return `bool` (`#[must_use]`). The relay-message entry point, `parse_signed`, returns `Result<Message, Rejected>`: `Rejected::Refused(nostr::Refused)` for whatever `nostr::parse` refuses, `Rejected::BadSignature` for an `EVENT` that fails. A separate reason lets NOS-3 count forged events apart from malformed ones.
- **Where the check is wired:** `nostr_sig::parse_signed` is `nostr::parse` plus the signature check, and is the function NOS-3 calls for each relay message. `nostr.rs` is unchanged: nothing outside its tests calls `nostr::parse` yet, so a wrapper drops failures without widening this slice's files or changing NOS-0's `Refused`. Order: the id is recomputed first (cheap, and an edited event fails there), then the signature. `event_signed` trusts `Event::id`, which `nostr::parse` has already recomputed; its doc says so.
- **Hostile input is a plain `false`:** a key that isn't an x coordinate on the curve (or is ≥ p), `r` ≥ p, `s` ≥ n, an all-zero or all-ones signature. No `unwrap`, no panic, no `unsafe`. One deliberate difference from BIP-340's letter: k256 refuses `r = 0` and `s = 0` at parse. No point has x = 0, so `r = 0` can't verify anyway; `s = 0` verifies only for a signature nobody can produce without breaking SHA-256. Both are drops either way.
- **Tests (`crates/sources-feeds/tests/nostr_sig.rs`):** BIP-340's `test-vectors.csv`, all 19 rows (0–18) including the 10 that must fail, transcribed unchanged from `github.com/bitcoin/bips` at commit `fdcd8024595bc1e97db73883e716dbb91627c371` (master on 2026-11-23), file SHA-256 `34c9d1d9c3a88d524bc80778540dc43f8306ec249a7485293063c376db851c2d`. BIP-340 is licensed BSD-2-Clause (its code BSD-2-Clause OR MIT OR CC0-1.0); the source and licence are noted at the table. Rows with a secret key also check k256's signer, which the synthetic events use. Then edge values (r = p, p + 1, 0, 2^256 − 1; s = n, n + 1, 0, 2^256 − 1; keys 0, p, 2^256 − 1 and an off-curve x); property tests that arbitrary bytes and messages never panic and that flipping any one of the 1,024 bits of id, signature or key fails a valid signature; and synthetic NIP-35 events signed with a fixed test secret: kept when signed, dropped when signed by another key than the one claimed (a forged publisher), when a signature digit changes or the key is off the curve, refused as `IdMismatch` when the content changes. No real key and no real relay data: the plan's "plus real events" is met by the NIP-01 reading below and the vectors, as the runner's brief asked for synthetic events only.
- **Cost (plan: "verification cost is measured"):** about 61 µs per signature in a release build on the development machine (WSL2, one core), so ~16,000 events a second per core. `verify_cost` in the test file measures it; it's `#[ignore]`d, run by hand with `--release -- --ignored --nocapture`, and not a gate. A relay flood stays bounded by NOS-2b's message caps and NOS-3's rate caps (§18.4).
- **NIP revisions (NOS-0 asked NOS-1 to record them):** `nostr-protocol/nips` `master` at `bec0fc89e75645e77a06d145598246efca844457` (2026-11-16). NIP-01 last changed in `98b57cf3e76f5de64a563350d437328e5d7a8f73` (2026-11-05): signatures are BIP-340 over secp256k1, `sig` is the signature of the id, and its seven content escapes are the ones NOS-0 implements. NIP-35 last changed in `e6552476aa2e5ca7256be572a9aa226ec8a022ee` (2024-09-03), the tags NOS-0 reads.
