# CMP-3 decisions (companion credentials)

Slice CMP-3 of `docs/plan/2026-11-06-v06-companions.md` (§3, §4, §5 Q5, Q10, Q13, Q19); architecture §12, §18.7, §18.10. Every entry is a choice the brief left to the slice (`docs/owner-decisions.md` §2.33). None loosens a plan rule.

- **Encodings.** qBittorrent's WebUI password is 32 bytes from the OS RNG as unpadded URL-safe base64: 43 characters of `A–Z a–z 0–9 - _`, which neither `qBittorrent.conf` quoting nor a form body changes. Prowlarr's `ApiKey` is **16** bytes as 32 lowercase hex digits. The brief asks for "32 bytes" and also for "32 lowercase hex characters, matching Prowlarr's own format"; those can't both hold, and the format wins: 128 bits from the OS RNG, more than the 122 random bits of the GUID Prowlarr generates itself. Nothing is seeded from time or a PRNG (`getrandom::fill`).
- **Rows and contexts** are the plan's: `settings` key `companions.<id>.secret.<field>`, sealing context `companion:<id>:<field>`, with fields `webui_password` and `api_key`. No migration (Q10).
- **Rotation.** `credentials::reseal_rows` is step 2 of `SecretStore`'s rotation for these rows: it reseals every row sealed with an old key and returns them for the caller to commit before `retire_old_keys`. It derives the context from the row key, so a field added later reseals too. A row under `companions.<id>.secret` whose key doesn't parse fails the call rather than being stranded by the retirement.
- **Secret-row filter.** `credentials::is_secret_row` is true for any key under `companions.<id>.secret`, well formed or not, so it fails closed. The export, settings-import and support-bundle filters live in `crates/lodestar` and `crates/store`, which this crate can't reach; **CMP-5** wires `is_secret_row` into them beside SRC-4's `sources.secret.` rule and adds the test there.
- **The secret wrapper** is `lodestar_integrations::secret::Secret`, not a new type: `Debug` prints `Secret(***)`, it zeroes its memory on drop, and it has no `Display` at all, which is stricter than a redacted `Display`. Buffers that hold a credential (an existing `config.xml`, RNG output, the written XML) are `zeroize::Zeroizing`; `zeroize` is already a workspace dependency, pinned `=1.9.1`, as the brief's item 5 anticipates.
- **API for later slices** (no UI, no endpoints here):
  - `generate(store, key)` creates and seals a credential and returns the row and the plaintext once. It is also **Regenerate** (CMP-6): it never reads or returns the credential it replaces.
  - `accept_pasted(store, key, secret)` (Q19) validates and seals a pasted value and returns only the row. Pasted API keys are 32 hex digits, upper case allowed and kept as given. Pasted passwords are 6–128 characters of printable ASCII with no space at either end.
  - `replace_temporary_password(store, key, sealed)` (Q19, CMP-8b) returns the temporary password to sign in with and a newly generated one.
  - `open(store, key, sealed)` is for CMP-8b's configuration and CMP-6's password-gated reveal only.
  - `config_files::write_qbittorrent(path, username, password)` and `write_prowlarr(path, api_key)` are for CMP-5's managed installs, before first start. `qbittorrent_conf` and `prowlarr_config` are the pure forms. Guided installs never get a file written, and nothing here writes a compose service or template.
- **qBittorrent username:** `lodestar` by default, rather than qBittorrent's well-known `admin`. Usernames are 1–64 characters of `A–Z a–z 0–9 . _ -`, so they need no escaping in Qt's INI format.
- **qBittorrent's file** is read as Qt reads INI files: `/` and `\` are the same separator, `[General]` (any case) is the root, and a key may carry its section as a prefix (`Preferences\WebUI\Address` under `[General]`). Qt matches keys and sections case-sensitively on Unix and case-insensitively on Windows, so a key or section that differs from ours only in case is refused: on Linux qBittorrent wouldn't read it, and on Windows it would shadow ours. The first occurrence of each of our three keys is rewritten in place, keeping its spelling; later duplicates are dropped. A missing key goes after the last entry of the first `[Preferences]` section, or into a new `[Preferences]` section at the end. The password is written as qBittorrent writes it: `WebUI\Password_PBKDF2="@ByteArray(<salt>:<hash>)"`, PBKDF2-HMAC-SHA512, 100,000 iterations, a 16-byte salt from the OS RNG.
- **Prowlarr's file** follows Prowlarr's own reader, which takes each key from `Descendants(key)` and resets it (a new `ApiKey`, `BindAddress` back to `*`) unless it finds exactly one. So `ApiKey` and `BindAddress` may appear only as children of the root, and a nested `<Config>` is refused too.
- **Malformed existing files are refused, never overwritten.** The writer refuses a file that is a symlink or not a regular file, is over 1 MiB, isn't UTF-8 or holds NUL. For `qBittorrent.conf` it also refuses a lone CR, any other control character but tab (Qt and Rust disagree on whether `\v` and `\f` are whitespace, which could move a section boundary), a line continuation (an odd run of `\` at a line end, outside a comment), an unbalanced unescaped `"` on a line (Qt lets a quoted value run on past the newline), a key or section name with any byte outside `A–Z a–z 0–9 _ - . / \` and space (Qt's writer percent-encodes the rest, and Qt cuts a line at an unquoted `;`, so `[Preferences ; old]` is `Preferences` to it; `[%General]` is the one exception), an empty section name (Qt names `[]` `/`, not the root), text after a section header other than a `;` comment, a key or section differing from ours only in case, and an unterminated section header. For `config.xml` it refuses a DOCTYPE, XML that isn't well formed, a root other than a single `<Config>` without attributes (a namespace would hide it from Prowlarr), text outside it, `ApiKey`, `BindAddress` or `Config` anywhere but their own place, and markup inside `ApiKey` or `BindAddress`. A refused file is left exactly as it was. The runner's review (Qt 6.12 `QSettings` over about 63,000 generated files) found the `;` and `[]` cases; the property tests' oracle now models both. The rewritten `qBittorrent.conf` text is held in zeroized buffers, since it may carry other plaintext secrets (`Network\Proxy\Password`), and the existing file is read through a handle checked to be the regular file inspected (same device and inode on Unix), so a symlink swapped in after the check is refused. Each case either has no unambiguous safe edit or could hide one of our keys from the writer.
- **Atomic writes.** The writer creates a temporary file with `create_new` in the same folder, then writes it, fsyncs it and renames it over the target. On Unix it also fsyncs the folder, best effort as `SecretStore` does for its key file: the rename has already happened, so failing there would wrongly report the file as unwritten. The temporary file is created with mode `0600`. On Windows the file inherits the companion folder's ACL; there's no new ACL code. The folder must already exist: CMP-5 creates it. **For CMP-5:** the file is `0600` and owned by Lodestar's account. A managed companion runs under that same account (plan Q3, owner §2.47), so it can read and rewrite the file. Anything that runs a companion under another uid has to chown the file first.
- **The golden tests use a fixed salt** through `PasswordHash::with_salt`, which exists only under `cfg(test)` or the crate's `testing` feature, never in a release build. qBittorrent compatibility is checked against its own documented default hash for `adminadmin`, plus a vector computed independently with Python's `hashlib.pbkdf2_hmac`.
- **Base64 and hex are encoded in a few lines in `credentials.rs`** (tested against the RFC 4648 vectors) rather than through a new `base64` dependency, which the brief didn't approve. Encoding only; nothing is decoded.
