# X-dht01-fix decisions

- **DHT-01 (blocking, network; the DHT node) fixed.** Its detail is held under `docs/security/v1/README.md` §5 until a release with the fix is published. This file says only what the code now does.

## Calls
- **Pings to queriers have a budget of their own** (§5). A node that queries us isn't put in the routing table until it answers a ping of ours, since its address may be spoofed. Those pings now draw on their own bucket first, then on the query rate as every query does:
  - **rate:** 5% of the query rate (`VERIFY_SHARE`): 2.5, 10 and 50 a second at Low, Balanced and Aggressive, with a burst of one second's worth;
  - **outstanding:** at most 1/16 of the outstanding-query cap awaiting an answer at once (`VERIFY_OUTSTANDING_DIV`): 16, 64 and 256.
- **Past either, the querier just isn't verified this time.** It is still answered, within the reply rate as before; a later query from it gets another chance. The refusal counts in `dht_throttled_total`, as any query the budget refuses does, so no metric is added.
- **The total stays inside the query rate.** The new bucket is taken before the shared one, never in place of it, so the node sends no more than it did: the politeness caps of §5 are unchanged, and what inbound traffic can't spend stays with lookups, sampling and scrapes.
- **The policy check runs before the budget.** An address the network policy or the blocklist refuses costs nothing from either bucket.
- **Both follow the intensity,** and a change of intensity starts the new bucket full, as it does the others.
- **Not behind a switch.** The crawler rule (new behaviour off by default until a live A/B shows it wins) is for changes meant to raise the yield. This one closes a blocking finding and only lowers what the node sends, so it is on.

## What it may change in a crawl
- Queriers were the cheapest way into the routing table. At Balanced the node now verifies at most 10 of them a second where it could have spent the whole query rate on them. On a quiet table that is still far more than the table can take (8 a bucket); on a busy node the table is mostly full and `would_accept` already declines most queriers. So no change in the 24 h mean is expected, but it isn't measured.
- **Follow-up (runner):** compare `dht_throttled_total` and the routing-table size against the last soak in the next one, before the crawler gate's 24 h run.

## Tests (`crates/dht/src/node/verify_tests.rs`)
- `queriers_spend_only_their_share_of_the_query_rate`: far more queriers than the whole query rate, at once: at most the share is sent, the rest of the query rate is untouched, and a lookup's query still goes out.
- `queriers_hold_only_their_share_of_the_outstanding_cap`: with no rate limit at all, at most the share is outstanding; an answered or timed-out ping gives its place back.
- `the_share_follows_the_intensity`.
- Each of the first two fails with the budget check removed.

## Follow-ups
- **The exact-input regression test** lands after the release with the fix (`docs/security/v1/README.md` §5).
- **One network taking the whole share.** A single /24 can use all of the verification budget, so other queriers wait. Only table freshness is at stake, never the crawl's budget. A per-network split (as `ExternalIp` does for votes) would close it; left out to keep this change small.
