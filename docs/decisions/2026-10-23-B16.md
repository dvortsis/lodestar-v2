# B16 decisions (fixture backend)

`lodestar serve --fixture [DIR]` and the data set behind it (build plan §1.3 seam 2, P1 "v0.5 exit"). No owner decision is reversed or loosened.

## The data set

- **Built only through public store, pipeline and search APIs** (`bench::fixture::build`): insert, `enrich_stored`, the indexer's `catch_up`, then `WriteBatch` for swarm and Insights rows and the M5 store calls for user data. That's the sequence `search-bench` uses, so a fixture stays valid across migrations. Hot columns aren't written; the server loads them from the store.
- **`auth.json` and `seal.key` come from the server's first start, not the builder.** `lodestar-bench` doesn't depend on `lodestar-api`, and `bench/Cargo.toml` is #48's to edit. The auth file's format belongs to the API, so the server creates it the usual way.
- **Every name is invented** (`runner/standards.md` §4b). `synth::Generator` uses real release-group names (RARBG, YIFY, SubsPlease…), a real repacker's file names and real private-tracker tags. `fixture::sanitize` swaps them for invented ones as whole tokens in names, paths, the v2 file tree and `source`, and a test checks 3,000 generated torrents. `synth.rs` is unchanged, so the size and search benches still measure the same stream.
- **Adult is mostly detected from names** (`XXX`, `Hentai`), so a re-enrichment by a newer parser keeps it. One torrent is Adult only by an Is adult correction, stored with `set_correction` and enriched with `enrich_corrected`, as the API applies one.
- **Filter-hidden is the `HIDDEN` flag set at insert**, as `crates/api/tests/discover.rs` does. No filter rule or hit is recorded, so the Filters screens show no hits for these torrents.
- **Content types in the manifest come from the stored classification,** which is what the index is built from. Every other number comes from the specification. The build fails if a hand-specified torrent's type isn't the one specified, so a classifier change that moves one shows up there. The generated torrents' types follow the classifier.
- **Sources:** `dht` (id 0), `bitmagnet` (1, the imports) and `fixture-private-feed` (2, the `PRIVATE_SOURCE` torrents). Imports have no cohorts. Private torrents (the `private` flag or `PRIVATE_SOURCE`) never get a swarm row (§18.7).
- **Time model.**
  - Every timestamp is an offset from the anchor, the build time rounded down to the hour.
  - The first run is 35 days before it (`first_run_at`), so the pipeline's 30-day warm-up flags `BACKFILL` on torrents discovered in its first 30 days, as live ingest would.
  - The crawler is paused for six hours at 7 d and at 24 h, and stopped for six hours at 72 h. Nothing is harvested, discovered or stored then. "24 h", "7 d", `discovered:<7d` and cohort finality therefore give the manifest's numbers for six hours after the anchor, and the gaps show up as pause, resume, stop and start annotations.
  - Cohorts that ended 72 h or more before the anchor are final. The rest have keys in flight (`in_progress > 0`).
- **Event-time counters follow intake:** `HARVESTED` counts every key received (the cohort's first harvests plus `REDISCOVERED` and `DROPPED`), as the pipeline counts it. Imports get no `STORED` counter, since `import-bitmagnet` stores outside the pipeline.
- **The manifest's flags, sizes, file counts, names and hashes come from the specification and the info dicts it wrote.** The build fails if the store holds anything else.
- **Funnel shape.** Per cohort, harvested = searchable + losses + in progress. Stored and searchable equal the torrents discovered in that hour, because the index holds every torrent. Losses are deterministic per hour, and every reason occurs.
- **Swarm buckets in the manifest are cumulative** (`≥1` counts every torrent with 1 or more) and are counted over the default browse set, with never-scraped counted separately. The API serves `buckets` as `null` until M4 indexes the swarm. #48 should confirm the cumulative reading when it fills them.
- **Two hand-written JSON writers,** for the manifest and for the saved searches' ASTs. `lodestar-bench` has no `serde_json`, and its manifest can't gain one here. Output is deterministic with keys in a fixed order. The binary's test parses each AST back with serde and compares it with `parse(query)`.
- **`FORMAT` (now 1) names the data set.** Bump it whenever the data or the manifest changes. A folder with another format is refused, not rebuilt over.

## The server

- **Behind a default-on `fixture` feature.** Stripped, as the Docker build ships it, the data set adds 692,608 bytes (+2.8%, about 265 KB gzipped) to the release binary, above the brief's 300 KB. (Unstripped, with line tables, it's 3.3 MB.) It stays on by default so `cargo test --workspace` runs the fixture tests. Release builds can opt out with `--no-default-features --features web`, and the Docker smoke image can use `web,fixture`; that's a packaging follow-up (P-release). A build without the feature keeps the flag and refuses it with exit status 2. `crates/lodestar/tests/fixture.rs` runs only with the feature.
- **Fixture mode is logged at WARN** ("fixture mode: test data in …, not a real install"), so it shows even with `LODESTAR_LOG=warn`. Reusing a folder more than six hours after its anchor warns that the windows have drifted and to rebuild. Exposing `fixture: true` on `/system` is a follow-up.
- **A fixture is marked twice:** `fixture.json`, and a `fixture_format` setting in the store holding `FORMAT`. The store is checked read-only (`immutable=1`, nothing written beside it), so a stray `fixture.json` can't make a real data folder count as a fixture.
- **`serve --fixture` is a flag on `serve`** (`Command::Serve { fixture: Option<Option<PathBuf>> }`). A bare `lodestar` still runs a normal `serve`.
- **The folder is checked before anything is written or logged.** Absent or empty means build. A `fixture.json` of this format beside `lodestar.db` means reuse. Anything else is refused with exit status 3 ("refused for safety: nothing was changed"), the same status the maintenance commands use.
- **PUID/PGID are dropped for the fixture's folder, after that check.** `main.rs` skips its own drop for `--fixture`, and `fixture::serve` runs the same drop (`Scope::DataDir`) with the fixture folder as the data directory, still single-threaded. The real data directory is never chowned, and a refused folder is never touched.
- **Config.** `--config` is read if given. `data/config.toml` and `$LODESTAR_DATA_DIR` never are, because they belong to a real install. Then:
  - the data directory is the fixture's;
  - the DHT, blocklist files and subscriptions are off, and search is on;
  - the bind is `127.0.0.1:8090` unless the file or `LODESTAR_HTTP_BIND` sets one. A non-loopback bind gets a warning.
  - `LODESTAR_DHT_ENABLED` and `LODESTAR_HTTP_BIND` are marked as set in the environment, so the settings registry shows them read-only, labelled as set by those variables (a fixture-only label would need a settings change outside this slice). A value saved in the app can't turn the DHT on or move the server, even in a reused folder.
- **The blocklist refresher stops before its first step** through one `services.rs` line, `crate::fixture::unless_offline(...)`. In fixture mode it hands the refresher a stop signal whose sender is gone. The refresher's first await reads the store, so it returns before it could download anything. A subscription added in the app is never fetched. Any later service that reaches out must check the same `fixture::OFFLINE` gate; #48's tracker scraper is the next one, since every fixture swarm row falls due a few hours after the anchor.
- **The fetch pool runs but never fetches** (the brief says it "never starts"; it's built as in every `serve`, with nothing to fetch). With no DHT there is no peer finder, and no fixture torrent is a partial import. The test checks the fetch and lookup counters stay at 0 and that no DHT source or `dht-state.bin` appears.
- **Sign-in:** the setup token is printed as on any first start. `LODESTAR_FIXTURE_PASSWORD`, if set, claims the instance through `Auth::{load, setup_token, setup}` before the server starts. There's no built-in default password, and the password must pass the usual strength check. A reused, already-claimed folder keeps its password, and an ignored `LODESTAR_FIXTURE_PASSWORD` is logged.
- **Each `serve` adds its own events.** The pipeline records a start and a stop on every run, after the fixture's events. The manifest lists the fixture's events only.
- **A reused folder keeps its anchor.** Absolute counts, facets, cohort numbers and hashes still match the manifest. The relative windows only hold within six hours of the anchor, so rebuild for screenshots.
