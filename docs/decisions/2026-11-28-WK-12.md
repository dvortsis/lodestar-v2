# WK-12 decisions (#PR)

Store migration V17: worker provenance (`torrent_worker`), the commit write, purge-by-worker and the snapshot purge (architecture §19.4, §19.7, §7; owner decisions §2.17, §2.21; workers plan Q10). The runner approved the design at step 0 and ruled on its questions (2026-11-28T18:16Z). V17 was assigned at the migration slot; SRC-3b and PL-8 take V18 and V19.

## V17: `torrent_worker`
- **A side table, not a `torrents.worker` column (plan Q10, refining §18.5).** `torrent_worker (torrent_id INTEGER PRIMARY KEY REFERENCES torrents (id) ON DELETE CASCADE, worker INTEGER NOT NULL CHECK (worker BETWEEN 1 AND 4294967295)) STRICT`, plus `torrent_worker_worker (worker)`. A row exists only for a torrent a remote worker prepared, so a single-machine install writes nothing (parity), and `torrents` keeps its width. Every deletion path, the snapshot purge's included, needs nothing new, because rows go with their torrent.
- **`u32`, not §18.5's `u16` (runner refinement, flagged to the owner under §2.19).** It matches `WorkerId(u32)` and `cluster.next_worker`, so no id can be truncated onto another worker's.
- **The CHECK refuses 0.** No row means the built-in worker, an import or a row from before V17. Purging "worker 0" is refused too (`Error::Invalid`), so it can never read as purging local torrents.
- **No backfill.** Nothing before V17 recorded the worker, so there is nothing to backfill from. See "Rows from before V17" below.
- **Holds no names.** `snapshots::Plan::KNOWN_THROUGH` is now 17, and V17 joins the V15–V16 plan unchanged.

## The commit write
- **In the commit's own transaction,** so a crash can't leave a remote row that the purge can't find:
  - `WriteBatch::prepared_by` holds the worker for each of `prepared`, in order. It's empty when all are local; any other length is refused with nothing written. It defaults to empty, so no other `WriteBatch` literal changes.
  - `Store::promote_from(…, worker)` records promotions; `promote` delegates with 0.
  - The writer passes the authenticated session's `Results.worker` (WK-9), never a field a worker sends.
- **What records the worker:** a row whose info-derived columns that worker's record wrote. That is a new row, or a `FILES_PARTIAL` import the record upgraded (`upgrade_partial` now says whether it did).
  - An already complete row seen again keeps its provenance. Held, refused and existing-but-not-upgraded rows record nothing.
  - A later upgrade by another worker replaces the row's worker: provenance follows whoever last wrote the metadata.
- **Cost:** one keyed insert per remote torrent, none per local one.

## Purge-by-worker (`crates/store/src/workers.rs`)
- **`Store::purge_worker_step(worker, limit)`** runs one `BEGIN IMMEDIATE` transaction over at most `MAX_WORKER_PURGE_STEP` of that worker's torrents, lowest ids first, and returns `{deleted, done}`.
  - It needs no cursor: deleted rows take their `torrent_worker` rows with them, so each step reads the next ones, and a job stopped between steps carries on where it was.
  - It's idempotent once `done`.
  - WK-13 runs it as a `/jobs` job.
- **A deletion goes the way every other one does,** in the same transaction:
  - a `reindex_log` row, so the search indexer drops the document;
  - V11's `torrents_removed` trigger, so the rollups count it as removed;
  - V12's `snapshot_torrent_deleted` trigger, so its hashes are journalled and the snapshot purge takes it out of every snapshot (§2.21);
  - `ON DELETE CASCADE` for its child rows;
  - `secure_delete`, then `scrub_wal` (§2.17).
- **Untouched:**
  - holds: tombstones, quarantine, `cs_hashes`, and the worker's floor reports, which `Store::purge_worker_floor` already removes for WK-13;
  - the fetch queue, which records no holder (WK-13 evicts live leases);
  - the worker's Insights rows (metrics 17 and 18, dim = worker): WK-13's, with the sealed-day cache (runner ruling Q2);
  - every torrent without that worker's row.
- **A purged torrent's claims go with it (runner ruling Q3).**
  - The worker-prepared metadata is untrusted, so the whole row goes, claims and all, as `delete_torrents` does.
  - The key returns only through rediscovery: it stays in the have-filter, so a sighting takes the false-positive path and is fetched and judged again by a worker in good standing.
  - Another source's claim lands as an unverified item if that source reports the key again.
  - `Store::worker_torrents(worker)` returns `{torrents, with_claims}`, so the purge preview can say how many claims go with them (tested).
- **Step size (runner ruling 6): `MAX_WORKER_PURGE_STEP` = 1024.**
  - Measured with a release build on this machine (4-core Xeon @ 2.10 GHz). The store held 1M torrents (717 MB) with 500-byte file blobs, a v2 hash on every 10th, claims on every 8th, and every 4th a remote worker's (`crates/store/tests/workers.rs` `purge_step_time`). Five steps per size:

    | Step | Median | Max |
    |---|---|---|
    | 256 | 43 ms | 395 ms (first step only, after the 700 MB fill) |
    | 512 | 86 ms | 96 ms |
    | 1024 | 143 ms | 162 ms |
    | 2048 | 260 ms | 283 ms |
    | 4096 | 442 ms | 479 ms |

  - That's about 0.11 ms per torrent. 4096 holds the write lock for about 450 ms and 2048 for just over 250 ms, so 1024 keeps a step at about 150 ms, well inside the 250 ms the runner set: the writer's latency comes first.
- **Worker ids are never reused (runner ruling 5).**
  - `crates/cluster/src/coordinator.rs` `spend_token` takes `cluster.next_worker` and writes it plus one (`checked_add`) in the same `IMMEDIATE` transaction. Nothing lowers it, and revoke doesn't touch it.
  - It starts at 1 only in `Coordinator::create`, which runs only when the store has no `cluster.` row, and `open` refuses other cluster rows without a CA.
  - `settings` and `torrent_worker` live in the same file, and a rollback restores both together. So every `torrent_worker` id is below `next_worker` in any state the store can be in, and a new worker can't inherit an old one's rows.

## Rows from before V17 (runner ruling Q4)
- **No released build commits remote-worker results.** v0.5.1, the only tag, has the cluster crate's library but no intake, cluster port or `lodestar worker` mode.
- **`release/v0.5.2` can, but isn't tagged** (checked at 114bb625a, 2026-11-28). It has `crates/lodestar/src/cluster/{serve,intake}.rs` and `pipeline/src/remote.rs`, and it attaches the intake while "Allow workers" (`[cluster] enabled`, default off) is on.
  - A store that v0.5.2 wrote with workers on would hold remote rows (they carry `REMOTE_UNVERIFIED`) with no `torrent_worker` row, which purge-by-worker can't reach.
  - No backfill is possible: nothing recorded which worker wrote them.
- **So the store can purge them on their own (runner ruling 4, option c, 2026-11-28):**
  - `Store::unattributed_remote_torrents()` gives the preview's counts (`{torrents, with_claims}`).
  - `Store::purge_unattributed_remote_step(after, limit)` purges them in the same bounded steps, by the same deletion path. It returns `next`, the cursor for the following step, or `None` when the pass is done.
  - "Unattributed remote" means `REMOTE_UNVERIFIED` with no `torrent_worker` row, so built-in-worker, imported and attributed rows are never touched. A row WK-13's re-verification has cleared of the bit leaves the set.
  - `torrents` has no index on `flags`, so the step reads its candidates before taking the write lock, then deletes each only if it still qualifies, checked in the write transaction. The lock covers the deletes alone, and the scope stays exact.
  - **A cursor for this step only (runner refinement of ruling 4, 2026-11-28T18:52Z, flagged to the owner with the `u32` choice).** Without an index, a cursor-free step would rescan past every kept row each time, which is quadratic on a big store. The step walks the primary key instead (`AND t.id > ?after`). `purge_worker_step` stays cursor-free: its index ends in the id.
  - **One pass is complete.** After V17, every remote row is attributed in the same transaction that writes it, so no unattributed row can appear behind the cursor; the set only shrinks. The test runs a full sweep, commits an attributed remote row, and shows that a second sweep from 0 finds nothing (`unattributed_remote_rows_are_purged_alone`).
  - WK-13 decides how to offer it. The runner handles the v0.5.2 side separately.

## Upgrade and downgrade
- **Up:** the existing migrate path takes `<db>.pre-v17.db` before any write. V17 is additive and runs in about 1 ms, so the snapshot is the whole cost:

  | Store | V17 with snapshot | Migration alone |
  |---|---|---|
  | 1M torrents, 304 MB | 0.67 s | 1.1 ms |
  | 2M torrents, 608 MB | 1.30 s | 1.2 ms |

  (`schema.rs` `v17_migration_time_on_1m_and_2m_stores`, release build, same machine.)
- **Older builds refuse a V17 store untouched:** V12–V16 code paths and their read-only checks return `SchemaTooNew`, and the file, its folder and its bytes are unchanged (`older_builds_refuse_a_newer_store_untouched`).
- **Down:** the update rollback restores the pre-V17 snapshot, which a V16 build opens and writes. Migrating up again reapplies V17 with a second snapshot (`v17_upgrades_a_v16_store_and_comes_back_after_a_rollback`).
