# M8-SEC-0 decisions (#786)

`SECURITY.md` and `docs/security/v1/README.md`, from owner-decisions §2.47 (M8 OQ6) and plan `docs/plan/2026-11-06-m8-hardening.md` §4.3–§4.4. Each bullet is a refinement for the runner to flag to the owner (§2.19); none loosens a security or content-safety decision. One question goes to the owner, through the runner (the third bullet).

- **"Until the fix ships" means until a release with the fix is published, not until it merges.** §2.47 says details are held "until the release ships"; the plan's §4.3 says reports list "fixed ones in full". A fix on `main` still leaves every user of the last release exposed, so a report records a finding in full only after the release. Stricter than either reading. (`docs/security/v1/README.md` §5)
- **The held detail never goes on `runner-state` either.** That branch is in the public repository, so briefs for fix slices name the finding's id and component only, and the detail travels by `send_message` and the owner's draft advisory. Slice ids and titles in `runner/slices.yaml` follow the same rule. (§5)
- **A fix PR ships general tests; the exact-input regression test waits for the release.** §2.47 says fix PRs go without a proof of concept until the release ships, and the input that triggers a flaw is one. So the fix PR's tests assert the invariant (bounds, properties, authorization on every path) and the exact-input test lands in a post-release disclosure slice, tracked by id. This keeps CLAUDE.md's tests-with-the-code rule as far as the owner's rule allows. **Question for the owner, through the runner:** may the exact-input test ship in the fix PR instead? That would loosen §2.47, so it stays the strict default until the owner answers. (§5 step 5)
- **Who writes the post-release record:** a runner-added disclosure slice after each release (for example `X-sec-disclose-v1`) owns the held rows in `docs/security/v1/*.md`; `SD-*` findings live in `docs/gates/v1/security/`, which `G-v1-security` owns. Without it, held rows would never be updated, because the review slices are done by then. (§5 step 6)
- **`/security-review` is a supplementary pass.** It reads a branch's diff, and a surface review reads code already on `main`, so the manual entry-point read is the review and the command is pointed at the surface's paths or at an unpushed scratch branch. (§2 step 5)
- **Severity for security, read from standards §5:** an attacker within the review's threat model breaking a spec guarantee is blocking; a precondition the threat model doesn't grant, missing defence in depth, or an inherited gap is important; polish has no plausible exploit. Ties go up; any child-safety-core finding is at least important; only the owner can accept or downgrade a blocking or important finding. (§3)
- **Content-safety findings stay partly held after release:** their full record describes the class and the fix, never evasion terms or patterns beyond what the shipped rules publish, and never real material. Stricter than §2.47; it follows the Legal Notice §9's rule on synthetic examples. (§5)
- **Long fuzz runs happen in the review session's container, not in GitHub Actions.** CI's `fuzz` job uploads crash inputs as public artifacts and libFuzzer prints them in the log, so a crash first seen there counts as disclosed, and a held crash input never goes into `fuzz/seeds/` or a corpus. `ci.yml` is unchanged here. **Follow-up for the runner:** decide whether the `fuzz` job (and M8-CI's long-run workflow) should stop uploading crash artifacts and print only the target and a hash; that would be a small Sonnet-safe CI slice, reviewed by Opus. (§2 step 6)
- **Fix slices' `owns` name the component or crate, never the flawed file,** because `runner/slices.yaml` is public. (§5)
- **Finding ids** `S<surface>-<nn>`, `SD-<nn>` for the RC delta review and `SVR-<nn>` for outside reports, never reused. `SRC` was avoided because `SRC-*` already names source slices. (§4)
- **`SECURITY.md` promises no response time, no safe-harbour terms and no bounty,** because the owner set none; it names no email address (§2.47). It does promise reporters credit in the published advisory, and that polish-rated reports may become public after they're told; both are the runner's calls. Supported versions: the latest release only, since nothing in the plan back-ports fixes. Each is the owner's to change.
- **Scope in `SECURITY.md`** mirrors the eight review surfaces, and sends reports about indexed material to the Legal Notice §9, as `docs/decisions/2026-11-04-X-legal-docs.md` already decided.
