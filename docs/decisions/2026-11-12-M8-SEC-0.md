# M8-SEC-0 decisions (PR pending)

`SECURITY.md` and `docs/security/v1/README.md`, from owner-decisions §2.47 (M8 OQ6) and plan `docs/plan/2026-11-06-m8-hardening.md` §4.3–§4.4. Each bullet is a refinement for the runner to flag to the owner (§2.19); none loosens a security or content-safety decision.

- **"Until the fix ships" means until a release with the fix is published, not until it merges.** §2.47 says details are held "until the release ships"; the plan's §4.3 says reports list "fixed ones in full". A fix on `main` still leaves every user of the last release exposed, so a report records a finding in full only after the release. Stricter than either reading. (`docs/security/v1/README.md` §5)
- **The held detail never goes on `runner-state` either.** That branch is in the public repository, so briefs for fix slices name the finding's id and component only, and the detail travels by `send_message` and the owner's draft advisory. Slice ids and titles in `runner/slices.yaml` follow the same rule. (§5)
- **A fix PR's regression test ships with it.** §2.47 says fix PRs describe the fix without a proof of concept; CLAUDE.md requires tests with every change. The method keeps both: the test asserts the behaviour that now holds and its name and comments say nothing about the exploit. **Question for the runner:** confirm this reading, or tell the reviews to hold the test back to a follow-up PR after the release. (§5 step 5)
- **Severity for security, read from standards §5:** an attacker within the review's threat model breaking a spec guarantee is blocking; a precondition the threat model doesn't grant, missing defence in depth, or an inherited gap is important; polish has no plausible exploit. Ties go up; any child-safety-core finding is at least important; only the owner can accept or downgrade a blocking or important finding. (§3)
- **Content-safety findings stay partly held after release:** their full record describes the class and the fix, never evasion terms or patterns beyond what the shipped rules publish, and never real material. Stricter than §2.47; it follows the Legal Notice §9's rule on synthetic examples. (§5)
- **Finding ids** `S<surface>-<nn>`, `SD-<nn>` for the RC delta review and `SVR-<nn>` for outside reports, never reused. `SRC` was avoided because `SRC-*` already names source slices. (§4)
- **`SECURITY.md` promises no response time, no safe-harbour terms and no bounty,** because the owner set none; it names no email address (§2.47). Supported versions: the latest release only, since nothing in the plan back-ports fixes. Each is the owner's to change.
- **Scope in `SECURITY.md`** mirrors the eight review surfaces, and sends reports about indexed material to the Legal Notice §9, as `docs/decisions/2026-11-04-X-legal-docs.md` already decided.
