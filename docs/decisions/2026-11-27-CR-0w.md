# CR-0w decisions (#1134)

Removes the start wait (owner §2.77, `docs/decisions/2026-11-15-owner-no-start-wait.md`). Before this slice a first start, and every restart whose proof failed, sampled no one for about six hours, and a version-1 snapshot carried a blanket gate into its first run on a newer binary (#1118's upgrade path). Now every start samples as soon as the DHT has bootstrapped, and only per-node restrictions carry over a restart.

## What the code now does
- **No start suppresses sampling** (`crates/dht/src/node/proof.rs`). A first start, a failed or missing proof, a corrupt, stale or old snapshot, a busy lock and a failed invalidation all sample at once. A start that can't resume restores nothing. The reason (`first_start`, `dirty`, `no_witness` …) stays as a diagnostic in `dht_sample_suppression_reason`.
- **No blanket gate, anywhere.**
  - A run writes `gate` as 0 in every snapshot it commits.
  - A resumed run drops any gate it restores, so a version-1 snapshot written by an older binary resumes its restrictions and samples at once (`an_old_snapshots_gate_is_dropped`).
  - A late invalidation landing adds nothing; before, it waited for this run's start + H and passed that on.
  - X-split-resume-gate's fallback gate goes too. If a snapshot's spill filter can't be rebuilt (the sampler's filter is already in use, which a fresh run's never is), its cooldowns are dropped and nothing waits for them (`a_filter_that_cant_be_rebuilt_is_dropped_without_a_gate`). `Sampler::restore_spill` still returns the last lost end; the proof ignores it. Its doc comment in `sampler.rs`, which says the proof gates on it, is outside this slice's owns: a follow-up for the next slice that edits `sampler.rs`.
- **The one hold left: `START_HOLD`, 10 s.** An on-run holds samples for at most 10 s after its epoch while its lock and start work land, so a resume's restrictions are in the table before its first sample. Past 10 s it samples whatever the proof says. A resume that lands after the run reserved a sample restores nothing and reports `locked` (`a_busy_lock_is_retried_and_nothing_is_touched_meanwhile`); one that lands before, however late (a paused crawler, `harvest.sample` off, a start job landing in the shutdown drain), still resumes (`a_run_that_hasnt_sampled_resumes_after_the_hold`, the drain test at 30 s). The rule keys on that flag, not on time, so the sampler is only ever seeded before its first sample: seeding over a sample in flight, or into a spill filter already in use, is a state `sampler.rs` doesn't take (its `restore` asserts it in debug builds). The cost of a late landing is re-asks, as for a failed proof. The start work reads at most about 32 MiB and lands in under a second on a working disk; the DHT's own bootstrap takes seconds too, so the hold rarely delays a first sample. Off-runs, legacy runs (no data directory) and lockless filesystems never hold. Inside the hold a busy lock is retried every tick, so a predecessor that lets go at about 8 s still hands over a resume (`a_lock_freed_late_in_the_hold_still_resumes`); after it, the retry backs off to a minute as before.
- **`H` stays** as the horizon for in-flight samples sealed at shutdown and as the snapshot's bound, as the owner's record says.

## Safe restart on by default
- **`dht.safe_restart` defaults to `true`** (`crates/lodestar/src/config.rs`). `false` in the file or `LODESTAR_DHT_SAFE_RESTART=false` turns it off; then nothing is restored, and sampling still starts at once.
- **`sample_start_delay` no longer turns the proof off.** It was CR-0d's I5: any override made an off-run. Now it's only a fixture's delay from the epoch, in every mode, and `None` (production's value) means no delay instead of `H`. So the six-hour default goes without the side effect the owner's record warned about (`Some(0)` would have turned safe restart off for every run).
- **On Windows, the service now creates `%ProgramData%\Lodestar-witness` on every install by default**, since that folder follows the switch (`crates/lodestar/src/windows/service.rs`). Docker and systemd already set `LODESTAR_DHT_WITNESS_DIR`.

## The three cases the owner's record left to this review
- **Crash loops: a one-minute guard** (the runner's call, §2.19, under §2.77's "if there are no repercussions for re-asks"; this replaces the self-review's "no guard", which had Docker's backoff wrong).
  - **The cadence it prevents:** Docker resets its restart backoff after any run of 10 s or more, so a container crashing about 12 s in restarts about every 12 s, indefinitely. Each run starts from the same `dht-state.bin` routing table and asks the same first nodes again, about five times a minute against the sampler's 60 s interval floor.
  - **The guard:** if the previous marker is `dirty` and its `at_ms` is less than 60 s before this start, sampling holds until `at_ms` + 60 s (`CRASH_LOOP`). The dirty marker is written at a run's start (S4), so this means "the last run lived under a minute", and a loop then samples at most about once a minute. The hold is capped at 60 s, so a clock that stepped back can't stretch it.
  - **Who never waits:** a first start, a clean restart, and an ordinary crash after more than a minute up (`a_crash_loop_samples_at_most_once_a_minute`: a marker 20 s old holds until +60 s, one 90 s old doesn't). Off-runs write no dirty marker, so they aren't guarded; nor is a crash loop on a filesystem without locks, whose runs never read or write the marker (`lockless`). The cap is tested (`a_stepped_back_clock_cant_stretch_the_crash_loop_guard`: a marker stamped an hour ahead holds for at most a minute).
  - **No format change:** the dirty marker already carries `at_ms`. It reports as `dht_sample_suppression_reason{reason="dirty"}` with `dht_sample_suppression_seconds` above 0.
- **`invalidate_failed`: samples at once, commits only once the write lands.** A resumed run whose marker and witness writes fail keeps what it restored and samples; the writes are retried with backoff as before. At shutdown it commits only if one landed (`a_run_that_never_invalidates_samples_but_never_commits`). If none did, the older clean marker stays on disk, so a later start may resume from the older snapshot without this run's restrictions, or read `snapshot_mismatch` because `dht-state.bin` changed. Either costs re-asks, never a wait, and never shortens a restriction a snapshot holds. When the write lands late, the reason becomes the start's own (`resumed`, …) instead of staying `invalidate_failed`, since nothing waits on it any more. An unreadable marker still counts only once the marker itself is overwritten (runner review B1).
  - **This keeps what the resume restored,** where the owner's record says a failed proof samples "with no restored restrictions". The proof itself held; only the write that retires the old marker failed, and keeping the restrictions only avoids re-asks. Flagged below.
  - **An off-run** (§6.13) likewise samples before its `off` marker lands. If it never lands, the older clean marker stays; the next on-run then reads `snapshot_mismatch` (the off-run saved `dht-state.bin`) or resumes the older snapshot. Re-asks, never a wait.
- **`locked`: at most `START_HOLD`.** A busy lock at start usually means the previous process is still committing (an in-process restart, or a container that overlaps its successor), so the 10 s hold, with its retry every tick, often ends in a resume. After it, the run samples, keeps retrying the lock (backing off to a minute) and writes nothing while locked out. Once it gets the lock it runs S0–S4; if it has sampled by then it restores nothing and keeps reporting `locked`, otherwise it resumes. A locked-out run never commits.

## The restart format (for the runner's review)
- **Unchanged.** Versions 1, 2 and 3 of the snapshot, the marker and the witness are as X-sec-S8-27 left them: restored spill sections stay read-only, new inserts use fresh keys. The `gate` key stays in every version and is written as 0; decode still checks it against the horizon, so a corrupt gate still fails the resume. An older binary reading a snapshot from this one sees no gate.

## Metrics
- **`dht_sample_suppression_seconds` is kept and reads 0** once the start work lands, at most 10 s before that, and at most 60 s in a crash loop; a fixture's start delay can still make it larger in tests. `stats.sampling_blocked` (derived from it in `crates/lodestar/src/ops.rs`) is therefore null except during the hold. Help text in `crates/lodestar/src/metrics.rs` and `docs/metrics.md` match, and `dht_sample_full_seconds_total`'s stale gate text (from X-split-resume-gate's follow-ups) is fixed.
- **`dht_sample_suppression_reason` keeps its 18 labels** as the restart outcome. The `dht.restart_check` log event keeps `mode=suppress` for a run that restored nothing, so log readers don't break.

## CR-SIM restart goldens
- **`restart-honoured.txt` is re-recorded.** Leg 1 is now a first start that samples at once for its 20 minutes, instead of sitting out 6 h then sampling 20 minutes; the run asserts its first sample within 60 s and the gauge at 0. Leg 2 is therefore a clean restart after an unproven run, and samples at once with no gate. The leg-1 line drops `suppression=` and `samples_in_suppression=`; `restart_cost` now compares leg 1's 20 minutes against leg 2's first 20 (it compared leg 1's first hour of suppression, always 0, with leg 2's hour). Every number after the header changes, because leg 1 now runs at a different time against a network that keeps its state.
- **`restart_without_safe_restart_samples_at_once` replaces `restart_without_safe_restart_suppresses_in_full`:** leg 2 with the switch off restores nothing, samples within a minute, reads 0, and re-asks some of leg 1's nodes early (`sampled_before_expiry` above 0): the cost the owner accepted.

## §2.19 refinements, for the runner to flag to the owner
- `START_HOLD`: a new 10 s bound on an on-run's start, where the owner's record said "sample as soon as the DHT has bootstrapped".
- The one-minute crash-loop guard (the runner's call; above).
- A late invalidation landing now reports the start's own reason.
- `invalidate_failed` keeps the restrictions its resume restored, rather than restoring nothing.
- A resume that lands after the run sampled restores nothing.
- The Windows service creates its witness folder by default.
