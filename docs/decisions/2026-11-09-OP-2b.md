## For the runner to flag to the owner (§2.19)
- **The bridge is written from the plan, not imported (the runner agreed).** The plan says the logic comes from the owner's `provision_pia.py`, "reviewed and imported". That file lives on the owner's Windows host; it isn't in the repo or in runner-state. So `infra/pia-bridge/` follows the plan's §4 spec and PIA's public manual-connections flow (`github.com/pia-foss/manual-connections`). If the owner shares the file, a follow-up can compare the two.
- **A new `pia-delivery` secret, `STATE_BUCKET_OWNER` (approved by the runner):** the state bucket's 12-digit account ID. It's for `ExpectedBucketOwner`, which deliver-pia passes on its S3 call (the runner's note). The cloud-fleet jobs' S3 calls (OP-2's lock store and backend, which pia-fence and pia-release reuse) don't pass it yet. Adding it there needs the control bucket's owner as a `cloud-fleet` secret too; that's left as a follow-up for the runner. Setup step 6 gains it beside its four secrets. It's a secret, not a variable, because account IDs never reach a public log (plan §3).
- **`PIA_SERVERS` is JSON:** `{"main": "<PIA region ID>", "worker": "<PIA region ID>"}`.
  - The region IDs are the `id` values in PIA's server list, for example `ca_toronto`.
  - Exactly one entry per role, each `[a-z0-9_-]{1,64}`.
  - The two must differ, or the job refuses.
- **The PIA secret is JSON** `{"username": "...", "password": "..."}`. Anything else is refused.
- **Residual: write access to `fleet.json` equals reading the PIA login.** deliver-pia sends the login to whatever address and host key `fleet.json` names, so anyone who can write `fleet.json` can receive it. That's `LodestarFleetOperator`, which by design can't read the secret itself. The shape checks below stop a malformed record, not a well-formed hostile one. The guards are the same as for any control-plane change: `fleet.json` is written only by `fleet.yml` at `main`, through that role.
- **`renew-vpn` rewrites `wg0.conf` but doesn't restart gluetun.** A running tunnel keeps its old registration until OP-3's steps restart the container. The OP-3 brief should include that restart.
- **Where `wg0.conf` goes:** `/home/lodestar/lodestar/secrets/wg0.conf`, root:root 0600. That's the directory cloud-init creates and the path `pia-example/compose.vpn.yaml` mounts (`./secrets/wg0.conf`). Dockerd runs as root, so the bind mount reads a root-only file.

## The chain (plan §3, "Delivery runs inside the lock")
- **act keeps the lock** after a successful `up` or `run renew-vpn <vm>`. It writes `deliver=true` to its job outputs. Every other command, and every refusal or failure, releases the lock as before.
- **pia-fence** (cloud-fleet, 4 min) runs just before deliver-pia, which can't reach the control bucket (the runner's note). It re-parses the comment and checks four things:
  - it is a first attempt;
  - this run still holds the lock (`fence`);
  - `fleet.json` is readable and records a fleet;
  - the fleet isn't overdue or mismatched.
  If any check fails, the job fails and deliver-pia is skipped. On success it passes the lease's end (`expires_at`, a UTC timestamp, nothing private) to deliver-pia as a job output.
- **deliver-pia** (pia-delivery, 30 min; next section) **refuses unless the lease has at least 25 minutes left** when it starts. That's its worst case: one cloud-init wait, one step and the close, with the targets in parallel. Queue time before the job, or a wait on its environment, comes out of the lease. So a delivery can't outlive the lock it runs under, whatever the runners' backlog.
- **pia-release** (cloud-fleet, 5 min, `always()`) releases the lock whatever deliver-pia did: failed, skipped or cancelled. It uses `FleetLock.release`, a conditional delete that succeeds only while the lock still holds this run's ID. If the delete itself fails, it reports and escalates, and the lock expires on its own. **Its `if:` reads no repository variable**, so changing one mid-chain (a stop, a cleared channel) can't strand the lock; the conditional delete is what keeps it safe.
- **If act can't write its `deliver` output,** it releases the lock itself and says nothing was delivered, so pia-release isn't needed.
- **Timeouts:** 50 + 4 + 30 + 5 = 89 minutes, under the lock's 90, and a test checks the sum. The lease check above, not this sum, is what bounds deliver-pia.
- **Re-runs:** every chain job requires `run_attempt == 1`, in its `if:` and again in code. A re-run has a different run ID, so it can neither fence nor release the original chain's lock; that lock expires on its own.
- **Residual: rule writes aren't fenced inside deliver-pia.** deliver-pia writes its rule sets while the chain holds the lock, but it can't re-check the lock between writes. If the reaper pre-empts mid-delivery (an emergency), the reaper's own sweep and deliver-pia's writes can interleave. The reaper is going `down` then anyway. A job rule left behind is a well-formed `/32` that the next sweep removes, and the hourly audit catches anything else.

## deliver-pia (plan §4)
- **Its own gates, and they read nothing from act's output except `deliver`.** The job's `if:` repeats the checks: created event, a PR, channel PR, bot ID, `main`, first attempt, pia-fence succeeded and `OPERATOR_STOP != 'true'`. The script re-parses the comment through the same `gate()` that act uses. `up` delivers to every role; `run renew-vpn <vm>` delivers to that VM (the enum `main` or `worker`). Anything else delivers nothing.
- **Dry-run** reports "would deliver the PIA login to …" and reads no secret.
- **Targets and pins come only from `fleet.json`:**
  - each target's address, host key, fingerprint and firewall ID, each shape-checked:
    - the address is one dotted IPv4 address, not loopback, link-local, multicast, unspecified or reserved;
    - the host key is exactly one ed25519 key line (so no extra or wildcard line can reach `known_hosts`);
    - the firewall ID is digits;
  - the recorded fingerprint must match the host key;
  - the pinned commit must be an ancestor of `main` (the checkout has full history);
  - a tombstone, an expired fleet or an unfilled slot is refused.
- **Secrets are read with boto3,** in-process, through `LodestarPiaDelivery` (`apply.oidc_session` now takes the role's environment name). Every value is masked as soon as it's read, before any other use:
  - the raw secret string;
  - the PIA username and the password;
  - the firewall token;
  - each `PIA_SERVERS` region;
  - the runner's address;
  - every line of `FLEET_SSH_KEY`.
  Masks go one line at a time, with GitHub's `%` escaping. Nothing is written to `GITHUB_ENV` or `GITHUB_OUTPUT`.
- **Its own `/32`.** The runner's address comes from `checkip.amazonaws.com`. The answer must be exactly one IPv4 address inside `/meta`'s Actions ranges, or the job refuses and opens nothing. There's no fallback, and tests cover two addresses, an empty answer, IPv6, a CIDR and junk.
  - The job reads every target firewall's rule set first.
  - On each one it then sweeps stale job rules (OP-2's `audit.sweep`; `actions: read`) and adds `job-<run>-<attempt>` (`audit.open_rule`) in the same whole-rule-set write.
  - In a `finally` it closes the rule again and sweeps stale job rules once more (plan §3: at the start and in the cleanup). If closing fails, it escalates, and the next sweep removes the rule. Report lines are posted even when an exception is on its way out.
  - **Residual:** a cancelled or timed-out job gets about 7.5 s between SIGINT and SIGTERM, which may not be enough to close the rule. It then stays open until the next sweep, at most an hour, as plan §3's accepted residual for a lost runner.
- **The firewall token can't read `/account`** (it's scoped to Firewalls only), so there's no EUUID check here. The account binding is that every firewall ID from `fleet.json` must be a `lodestar`-tagged firewall this token can see; `linode.py` refuses any other.
- **SSH:**
  - **Identity:** user `lodestar` (root login is off), `-F /dev/null`, `BatchMode`, `StrictHostKeyChecking=yes`.
  - **Host key:** a per-target `UserKnownHostsFile` holding exactly `<address> <pinned key>`, with `GlobalKnownHostsFile=/dev/null` and ed25519 only.
  - **Key file:** `FLEET_SSH_KEY` written to a 0600 file in a 0700 temporary directory, removed afterwards.
  - **Output:** the remote side's stdout and stderr go to `/dev/null`, because PIA's API answers with the exit address. Only exit codes come back.
  - **Retries:** exit 255 (SSH itself: the rule not applied yet, or the host key) is retried for up to 2 minutes; any other result isn't.
  - **The targets run in parallel** (they boot together), each in one session bounded at 14 minutes.
- **`sudo -n` and its scope (the runner asked).** `sudo -n` relies on cloud-init's rule for `lodestar`, `ALL=(ALL) NOPASSWD:ALL` (`infra/akamai/terraform/cloud-init/ubuntu24.yaml.tftpl`, OP-2's file, unchanged here). That's broader than the VM step needs. It isn't narrowed in this PR for three reasons:
  - OP-3's steps (the leak test, the block start, the arm switch, copy-off) run Docker and system commands under the same user and key, so a rule naming only this step would break them;
  - whoever holds `FLEET_SSH_KEY` already has the control plane's full access to these disposable VMs;
  - the file belongs to the Terraform slice.
  **For the runner:** narrowing it to the commands OP-2b and OP-3 actually run fits once OP-3's step list is fixed. The SSH key itself never leaves the two environments' secrets.
- **What crosses SSH, and how:**
  - **The command line** is a fixed string: `sudo -n bash -c '<bootstrap>'`.
  - **stdin** is a tar built in memory: the VM step, PIA's CA, `login.json` and `region`, all mode 0600 or 0700 and owned by uid 0. The login is never in argv, the environment or a file on the runner.
  - **The bootstrap, in order:**
    1. It waits up to 8 minutes for cloud-init (`cloud-init status --wait`). Delivery follows `up` within minutes, before cloud-init's final stage has installed jq and wireguard-tools and made the secrets directory. If `boot-finished`, the three tools or that directory are still missing, it exits 20, and the report says "the VM isn't ready".
    2. It takes a per-VM `flock` on `/run/lodestar-pia.lock` (empty) for up to 3 minutes, or exits 21. So a retried session waits for an orphaned earlier step instead of sharing or deleting its directory.
    3. It recreates `/run/lodestar-pia` at 0700. It traps EXIT to delete it, and HUP, INT and TERM to exit, so EXIT runs.
    4. It unpacks stdin and runs the step under `timeout -s TERM 150` (exit 124).
  - **A dropped session doesn't signal the remote side:** there's no PTY, so sshd sends no SIGHUP, and the step writes nothing that could raise SIGPIPE. The orphan runs to its 150-second bound, and its traps then delete the login.
- **Afterwards, a second SSH checks that `/run/lodestar-pia` is gone,** whether or not the step succeeded. After a lost session (exit 255, or the session timing out) it polls for up to 200 seconds, past the orphan's own bound, before deciding. "NOT clean" or "unchecked" escalates. OP-3's leak test checks again before any crawl.
- **Reports are fixed strings plus role names,** for example "deliver-pia: main: delivered; /run clean". The exit code says whether every target was delivered and checked clean.

## The VM step (`infra/pia-bridge/vm/pia-wireguard.sh`)
- **PIA's manual-connections flow:**
  1. a token from `api/client/v2/token`;
  2. the region's WireGuard server from `serverlist.piaservers.net/vpninfo/servers/v6`;
  3. a fresh key pair from `wg` (cloud-init installs wireguard-tools, jq and curl);
  4. `addKey`, against the server's name (`--connect-to` the listed address) with `--cacert` PIA's CA.
- **No secret on a command line on the VM either.** The username, the password and the token reach curl only as `name=<file` or `name@file`, and jq reads the login from its file. A test runs the step with a stub curl that records its argv, and checks that none of the three appear.
- **Fail closed on every field:** the region ID, the login's shape, the server's address and name, both WireGuard keys, the port and the peer address are each validated before use. So a hostile server-list or API answer can't inject a line into `wg0.conf` (tested with a newline-and-`PostUp` server key).
- **`wg0.conf`:**
  - **Interface:** the peer address `/32` and the private key.
  - **Peer:** the server key, `AllowedIPs = 0.0.0.0/0`, the endpoint pinned to the server list's IPv4 address, and keepalive 25.
  - **No `DNS` line:** gluetun does its own DNS.
  - **Written** to a `mktemp` file in the same directory (0600 under umask 077), made root-owned with `chown -h`, then renamed into place.
- **Cleanup:** the step has its own EXIT trap (it deletes the work directory and any temp file) and turns HUP, INT and TERM into exits (a cancelled job, or the bootstrap's timeout). Tests cover success, two kinds of failure and a hangup sent to the process group, and each test checks that the login is gone. The IPv4 checks accept octets above 255; curl then fails, and nothing can be injected.
- **PIA's CA** is committed as `vm/pia-ca.rsa.4096.crt`, from PIA's repository. Its SHA-256 fingerprint is `1F:D2:56:58:…:BB:FC:9D:70`, and it expires 2034-04-12. A test pins the file's hash, so it can't change silently.
- **Why WireGuard:** the plan's reasoning stands. WireGuard uses the password once, while OpenVPN keeps it for every reconnect.
