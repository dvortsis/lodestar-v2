# RP-2 decisions: pack-rule overrides (PR to be numbered)

Plan `docs/plan/2026-11-04-v06-rulepacks.md` §3, §4.3 "RP-2", Q8 and Q9; architecture §20.1, §20.6 "as built", §20.7, §20.8, §20.11. Builds on RP-0's version state (`packs::upgrade`) and RP-DEF (`docs/decisions/2026-11-05-RP-DEF.md`). No migration (Q9).

- **What an override is.** An action of `flag`, `demote`, `hide` or `drop` in place of the rule's own, plus an optional `unless` query read as your rules' `unless` is: as the torrent is, with no neutralized words taken out. It never changes what the rule matches. `quarantine` isn't offered, since the plan lists the four (§4.3), and the API refuses it with 400 `unknown_action`. A stored row with `quarantine` from a later build still reads. An override of a rule that's switched off, or whose pack is, does nothing.
- **Storage.** One `settings` row per overridden rule, `filter.pack_override:<RULE-ID>`, holding lines `1` (the format), the base version, the action's name, then optionally the `unless` text (which may hold newlines, so it comes last). It records no author, time or reason. `RuleSet.pack_overrides` reads every row with that prefix as stored, and a value that isn't text stays as its bytes, so an unreadable row is still unreadable after an Undo. `replace_rule_set` deletes and rewrites them with the other rule layers. The Undo snapshot (`rule_set_prev`) gains `pack_overrides` (`{rule, text}` or `{rule, hex}`). A snapshot from before RP-2 has none, and restores none, because that set had none. A row for a rule this build doesn't know is kept in the store and ignored.
- **The base version.** An override is bound to the version this install applied when it was set (`RuleState::applied`). While the version state is in doubt for the rule (`PackVersions::in_doubt`: both rows lost, rows that differ, skipped, unknown or downgraded), the base is `0`, which never counts as unchanged. At every load, an override is **changed** ("changed since you edited", §20.8) when its base isn't the version applied now, or the state is in doubt.
- **Weakening and strengthening (Q8).** Against what applies now, setting an override weakens when it has any `unless`, or its action is lighter than what applies. That is the rule's own action (the heaviest of the versions that apply), or the current override's when it's heavier. So lowering a `drop` override back to `hide` on a hide rule asks for the password. Removing an override weakens only when it applied an action heavier than the rule's own. Weakening gets the effect warning and the password; strengthening gets neither. A weakening override can't be set while the rule's version state is in doubt (409 `pack_rule_in_doubt`): nothing could check it later. A strengthening one can, bound to `0`.
- **When the base changes.** A changed override that still doesn't weaken the rule as it now is keeps applying, as "at least this action": the stronger of it and the rule's. A changed override that weakens the rule as it now is **pauses**, and the rule applies as built. Weakening is judged against the new version, not the one it was made for. So a `hide` override that needed no password on a hide rule pauses once a version that drops is accepted (it would now lighten it), and a `hide` override on a rule whose new version only demotes keeps applying. Re-confirming is setting it again with the password, which binds it to the new version. RP-3 may add a dedicated op over the same path.
- **Fail closed (#357).** A row whose parts don't all read (the format, base, action or `unless`) keeps of its action and the rule's the stronger, and drops its `unless`. A row whose action doesn't read, or whose format this build doesn't know, leaves the rule as built. Each is listed in `Engine::unreadable` as the new `RowKind::PackOverride` (`/metrics` `filter_rows_unreadable{kind="pack_override"}`, failing closed, so the Insights exception is an error). The filters API records it in `filter.stand_ins` as `packs.override.<RULE-ID>`, with the pack conditions (`StandIns::with_packs`), not as a stand-in whose holds are re-judged (`StandIns::reconcile` skips the kind). Its stand-in only ever holds by the rule's own action or by a heavier action you set, so it has no holds of its own to undo. Marks are re-judged by the ordinary rule-change sweeps.
- **Unaccepted versions still never drop.** Where a version no record shows accepted applies (the interim mode), an "at least" override's action is held at most at quarantine, as RP-0 holds the version's own.
- **The `changed_since_preview` race (§20.7).** The assessment reads the rule set, versions and override from the store, in the preview and again under the store lock in apply. A change previewed as strengthening that weakens by apply (a version accepted in between) is refused with 409 `changed_since_preview`. A weakening override confirmed with the password must send back the assessment's new `pack_base` as `base` (400 `pack_override_needs_base` before the password is read, as `held_needs_version` does). Apply refuses one whose base has moved since with 409, because the password confirmed it against a rule that no longer applies.
- **Precedence** stays the pack layer's: the floor, CSX-5, the core, your exceptions (an exception to the rule still releases from it), *Always allow* and your rules decide first, and the strongest pack or list action still wins. The pending version's shadow result still compares the base rule's two versions, so RP-3's acceptance preview isn't skewed by an override.
- **Holds made before** the override stay as they are, as for a changed rule of yours (`update_rule`). A weakening override's preview counts the rule's holds and 30-day decisions, as `update_rule` does. Releasing goes through *Release* and *False positive*.
- **API.** New ops are `set_pack_override {rule, action, unless?, base?}` and `remove_pack_override {rule}`, both in the Undo snapshot. The assessment gains `pack_base`, and `GET /filters` gains an `override` per pack rule (`action`, `base`, `changed`, `paused`, `unless`, `unreadable`). `openapi.json` and `schema.d.ts` were regenerated. RP-3 takes these files over.
- **Outside the brief's listed paths** (shared edits, each the least the change needs): `crates/api/src/log_events.rs` (the two ops' arms in the existing opt-in `filters.change_detail` text: rule, action, `unless`; no new event); `docs/metrics.md` (the new `pack_override` kind of `filter_rows_unreadable`); `crates/api/tests/pack_overrides.rs` (the API gates through the router; RP-3's `filters_packs.rs` doesn't exist yet). The pipeline's `filter_note` logs the new load note as kind `other`, and its owner can name it.
