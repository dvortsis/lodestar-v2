# SRC-12 decisions (BEP 48 full scrape)

Slice session, 2026-11-04. Architecture §18.1, §18.2 rank 16, §18.4, §18.7; v0.6 sources plan §4.2 SRC-12 and §5 Q2.

- **The parser is a push parser over bytes** (`tracker_scrape::full::Parser`), fed chunks with `feed` and closed with `finish`. It holds one dictionary key (32 bytes), a `failure reason` capped at 1 KiB, a nesting stack and one batch of hashes, all sized by its limits, so its heap is fixed whatever the reply (`Parser::heap_bytes`, checked after every chunk of the 50 MB test). Caps: 256 MiB, 4 million entries, 1 KiB per entry, depth 8, batches of 1,024.
- **Malformed entries are skipped; broken bencode ends the parse.** An entry whose key isn't 20 bytes, whose value isn't a dictionary, or whose value is over the entry cap is skipped and counted. A byte that isn't bencode can't be skipped by a streaming parser, so it fails. The keys of entries completed before the failure are still emitted, since each came from a whole entry. Each `feed` call hands over every key it completed before returning.
- **Duplicates aren't removed.** That would need memory growing with the reply. The pipeline merges repeats.
- **The plugin uses the body the kit's `Fetch` returns, up to its 16 MiB `MAX_BODY`.** The kit has no streamed body yet (`crates/sources/src/http.rs` names a later, additive `fetch_stream`). Until it does, a tracker whose full scrape is over 16 MiB fails that day's attempt. The plugin already feeds the body to the parser in 64 KiB chunks and emits each chunk's keys before the next, so streaming changes only that loop. **Follow-up for the kit's owner:** add `fetch_stream`.
- **At most one full scrape per tracker per day, held three ways.** The plugin's state keeps the last attempt per host (`last:<host>`, Unix seconds), so a restart doesn't reset the cap. The kit's quota `max_full_scrapes_per_day: 1` and a 24-hour poll interval guard it in-process. The attempt is recorded before the request is sent, so a failure, a refusal or a crash mid-reply still uses the day. An unreadable state skips the scrape.
- **The window is 01:00–07:00 in the user's time zone,** checked by the plugin through a `Clock` (Unix time plus a UTC offset). The kit doesn't enforce schedule windows yet. A request that hasn't started by the window's end is dropped (a timeout to the window's close). The host has to pass the user's UTC offset to `SystemClock`; with none it is UTC.
- **Private trackers are refused twice.** At setup: no query, no fragment, no user name, and no path segment of 16 or more letters and digits (where private trackers put passkeys). Before every scrape: a `PrivateTrackers` lookup, answered by the host from the store ("does a `private` or `private_source` torrent list this host?"). An error counts as private. **Host wiring needed:** the store-backed `PrivateTrackers` and the plugin's registration are the host's (SRC-G or the sources wiring slice).
- **Public addresses only.** Trackers must be http or https (UDP has no full scrape), follow the announce → scrape convention, and not be literal LAN, loopback or link-local addresses. Egress is `Endpoints::user_entered(NetPolicy::notification(false))` narrowed to the configured hosts. One tracker per host, because the daily cap is per host.
- **What a key carries.** The tracker's announce URL as a `trackers` claim at Medium confidence ("an indexer's own record"), no name, size or external reference, and never `private_source`. The counts in each entry aren't kept: the scrape scheduler measures swarms itself.
- **Manifest.** `full_scrape`, discovery, Low risk (§18.2), consent External, Low priority by default (§18.4 groups full scrapes with importers), Singleton distribution (each worker taking its own daily scrape would break the cap), off by default.
- **Q2, the ToS check per tracker class.** For this slice the runner decides and flags to the owner (§2.19):
  - *Public trackers that allow it.* A full scrape is part of the tracker protocol (BEP 48: a scrape with no `info_hash` asks for every torrent), made for automated clients. A tracker that doesn't allow it answers with a `failure reason` or an error, and the plugin tries again no sooner than the next day. Lodestar ships no tracker list; the user names each tracker.
  - *Public trackers whose published rules forbid scraping.* Not detectable by the plugin. The settings help text says to list only trackers that allow a full scrape.
  - *Private trackers.* Never scraped (above): their rules forbid it and their addresses carry passkeys.
- **The flat-memory test doesn't use a counting allocator.** The workspace forbids `unsafe`, which a `GlobalAlloc` needs. It checks the parser's own heap after every chunk (exact, on every platform) and the process's resident memory on Linux (growth under 4 MiB over 50 MB). `dhat` (as `bench/tests/mmap_retention`) would need a new dev-dependency and its own CI job; not needed for a parser whose state is fixed-size.
