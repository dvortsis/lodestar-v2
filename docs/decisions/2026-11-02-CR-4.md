# CR-4 decisions (uTP wiring and IPv6 coverage)

Crawler candidate 6 (build plan §0; master plan Part A2, hypothesis H3: peer reachability and transport), and the fix for S04, the transport setting that had no runtime effect. Implementation plan §10: "uTP wiring is a separate measured slice … IPv6 route backoff requires route-level evidence, not peer timeouts." Politeness caps, timeouts, rates, the per-IP limits and the metadata size cap are untouched. No store schema change, no `crates/cluster` or §19 worker-protocol change, no BEP 33.

## What existed
X-utp (#51) built `crates/utp` (BEP 29, LEDBAT, a fuzzed parser, bounded buffers, a per-IP connection cap) and `FetchOptions::{transport, fallback_to_tcp, utp_fallback_after, utp}` in `crates/peer-wire`, with `UtpSocket::with_sink` / `feed` and `classify` as the shared-port hook. **The hook was never wired**: the DHT handled every datagram as KRPC, nothing built a uTP socket, and `FetchOptions::transport` was always TCP.

## The switches
- **`dht.utp`, a bool, off by default.** `[dht] utp = true` in `config.toml` or `LODESTAR_DHT_UTP=true`, read at start; a bad value is a config error. Not in the Settings UI.
- **`dht.route_backoff`, a bool, off by default.** `[dht] route_backoff = true` or `LODESTAR_DHT_ROUTE_BACKOFF=true`, the same way.
- **Refinement (§2.19): two switches, not one.** uTP and the route backoff move different things, so each A/B can switch one alone, as Part A asks for every candidate. The brief asked for "a runtime switch".
- **Off is today's behaviour exactly.** `dht::Config::utp` is `None`, so `Actor::on_datagram` passes every datagram to `on_packet` unchanged and `Node::start` clones no socket; `FetchOptions` keeps `transport: Tcp`, `utp: None`, `route_backoff: false`, so `fetch_any` returns through the same TCP branch as before. Proof: `without_utp_a_utp_datagram_is_malformed_krpc_as_before` (a uTP SYN on the DHT port still counts as malformed KRPC), `utp_and_route_backoff_are_off_unless_asked_for`, and the four CR-SIM goldens, which this PR doesn't change. The new counters that count with the switches off (`fetch_family_*`, `fetch_no_route_total`) only observe; nothing reads them.

## uTP in metadata fetches (`dht.utp`)
- **Shared port, wired.** `services` makes a `lodestar_utp::SharedPort` (new: a `UtpSocket` whose sink is attached later) and hands its socket to the fetch options and the port to the DHT config. `Node::start` attaches clones of its sending sockets (a `DualSink`, by family), and the receive loop sends every datagram `classify` calls uTP to `feed`, after the same blocklist check KRPC gets. Bencode (`d…`) and anything unclassified still go to KRPC. `crates/dht` now depends on `lodestar-utp`.
- **The existing policy, unchanged:** `transport: Utp`, `fallback_to_tcp: true`, `utp_fallback_after` 2 s, all inside the same overall deadline. Per-IP limits (the pool's), timeouts, the metadata size cap, MSE and the blocklist apply identically, because they sit above or inside `fetch` whatever the transport. uTP's own per-IP connection cap (#51) adds to them.
- **Per family:** `UtpSocket::reaches` (new, from `PacketSink::reaches`) says whether the shared port has a socket for a peer's family. A family the DHT didn't bind (IPv4-only by default) goes straight to TCP instead of waiting out a uTP connect that can't open.
- **One node per port.** `SharedPort::attach` takes effect once and holds the DHT's send handles for the process's life; `Node::start` refuses a port already attached, so a later in-process DHT restart (none exists today) must make a new `SharedPort`.
- **Counting:** with `dht.utp` on, uTP datagrams are counted in `dht_utp_in_total` (or `dht_denied_total`), not `dht_packets_in_total`.
- **Incoming uTP connections stay ignored:** no listener, so a SYN from a stranger costs one parse and an `unknown` count.
- **The Settings `transport` section is labelled honestly, not connected.** Saved settings override `config.toml` and the environment (`Registry::effective_config`), so a value someone saved in the UI would silently decide an A/B arm, and turning uTP on for users before the A/B would skip the measurement Part A requires. The section stays stored-only, its labels keep "(not active yet)", and its module doc now names `dht.utp`. If the A/B adopts uTP, a later slice connects the setting (and drops the env switch or makes it win).

## IPv6 coverage (`dht.route_backoff`)
- **Local evidence only, from a probe.** Before a fetch dials, `Routes::routed` asks the local routing table with a UDP `connect` to the peer's address. That sends nothing, and fails as "network unreachable" only when no local route exists. A bind failure for the family (IPv6 disabled gives `EAFNOSUPPORT`) also counts as no route. The answer is cached per family for 2 s (`PROBE_EVERY`).
  - While the probe says no route, fetches to that family fail at once as `unreachable`. No attempt is counted; `fetch_route_skipped_total` counts the skip.
  - Peer timeouts, refusals, resets and a remote router's ICMP never decide anything.
  - A TCP `ENETUNREACH` is only counted (`fetch_no_route_total`), because a remote router's "net unreachable" for one dead prefix aborts a connect with the same error.
- **Recovery takes seconds.** When a route comes back (a VPN or gluetun reconnect), the first fetch after the 2 s cache expires sees it. There's no doubling window.
  - This replaces the first design: a 30 s backoff doubling to 15 min, triggered by a confirmed TCP `ENETUNREACH`. The runner's review found it could stall every fetch for up to 15 min after a tunnel came back.
  - Tests: `a_route_that_comes_back_is_seen_within_one_probe_interval`, `an_unrouted_family_is_skipped_until_its_route_returns`.
- **The same probe guards uTP.** With `dht.utp` on, a family with no local route goes straight to TCP. It doesn't spend `utp_fallback_after` (2 s) of a fetch slot on a uTP connect that can't open, which matters for a host with an IPv6 socket but no IPv6 route.
- **With both switches off, none of this runs.** There's no probe and no lock on a TCP connect's success; a failed connect only bumps the `ENETUNREACH` counter.
- **Expected effect: about zero.** A local `ENETUNREACH` already returns at once, so skipping the dial saves a syscall and a few microseconds of a fetch slot. The switch makes per-family behaviour explicit and measurable; it isn't a throughput win. **Baseline gate:** run the A/B only if a baseline shows `fetch_no_route_total{family="ipv6"} > 0`.
- **Not changed:**
  - the DHT's lookups (the plan notes they start on family 0);
  - which address families are bound;
  - how peers are admitted.

  This slice measures fetches per family; the DHT's own family balance is a separate question.

## Metrics (`docs/metrics.md`, "uTP and address families")
#51's names are reused: `fetch_{attempts,success,connect_timeouts}_total{transport}` and `utp_{retransmits,connection_timeouts}_total`, which now render when `dht.utp` is on (the `FetchStats` holds the socket). New: `fetch_family_{attempts,success}_total{family}`, `fetch_no_route_total{family}`, `fetch_route_skipped_total{family}`, `fetch_route_probe_down_total{family}`, the `fetch_route_down{family}` gauge and `dht_utp_in_total`. A uTP connect refused by uTP's own connection table (`QuotaExceeded`, nothing sent) isn't counted as a uTP attempt, so a full table can't inflate the uTP share; it still falls back to TCP.
- **Refinement (§2.19):** family is a separate series, not a second label on #51's series, so existing queries and the transport series' shape don't change.

## CR-SIM screen: not possible; live A/B proposed
CR-SIM replaces the fetch layer with a scripted `Fetcher` whose outcome is a hash of (seed, peer, hash): there is no transport, no socket and no route below it, and the network is IPv4 only (its README). Neither switch can change a simulated outcome, so a screen would be two identical arms. The goldens run unchanged as the off-path check.

**Proposed live A/B** (build plan §0.5 protocol, one switch per experiment, the other crawler switches fixed in both arms):
1. **uTP:** 6 h ABBA, at least two repetitions, switching only `LODESTAR_DHT_UTP`. Primary: verified searchable per minute (`searchable_new_total{origin="network"}`). Discovery: fetch success per peer tried (`fetch_success_total` summed over transports, over `fetch_attempts_total{transport="tcp"}` plus uTP attempts that didn't fall back). Guardrails: `utp_retransmits_total`, `utp_connection_timeouts_total`, `dht_timeouts_total` (uTP shares the DHT socket's buffers), `dht_throttled_total`, RSS and the fetch latency. uTP data now runs through the DHT actor's receive loop, which CR-0 found saturated, so also guard on the actor's capacity and admission counters: `dht_sample_deferred_total`, `dht_peer_rejection_reasons_total{reason="capacity"}`, `dht_peer_admitted_total` / `dht_peer_rejected_total` and `fetch_admission_refusals_total`. Check it's on: `dht_utp_in_total` and `fetch_attempts_total{transport="utp"}` rise in the "on" arm and stay 0 in the "off" arm.
2. **Route backoff:** gate on a baseline with `fetch_no_route_total{family="ipv6"} > 0`. If it's 0, skip the experiment. Otherwise run ABBA on `LODESTAR_DHT_ROUTE_BACKOFF`, with the primary metric as above and `fetch_route_skipped_total` and `fetch_route_probe_down_total` as the mechanism. The predeclared expectation is no measurable effect.
3. Predeclare the thresholds from the CR-0 baseline's variance before the run.
