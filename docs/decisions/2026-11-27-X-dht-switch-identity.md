# X-dht-switch-identity decisions (#1146)

The running binary now reports which crawler switches it runs with, so round 1's collector records each arm's effective values instead of guessing compiled defaults from the environment (`docs/plan/2026-11-27-revised-path-to-100.md` §5.1, §5.2 item 1). No switch default, preset or behaviour changes.

- **Name and shape: `lodestar_dht_switch{switch}`, a gauge, 1 on and 0 off** (`docs/metrics.md`, "Crawler switches"). One family with one label follows the existing labelled-gauge pattern (`dht_sample_suppression_reason{reason}`) and keeps the collector's read to one family. The label value is the `[dht]` key's name, so the series, the config key and the `LODESTAR_DHT_*` variable all map one to one.
- **13 series, always all rendered:** the 12 crawler switches (`coordinated_admission`, `responder_hints`, `streaming_peers`, `target_prefixes`, `utp`, `lookup_end`, `preset_slots`, `hint_first`, `sampler_cooldown_split`, `sample_backoff_escalate`, `soft_timeout`, `route_backoff`) and `safe_restart`. The names match `crates/lodestar/src/config.rs` and the plan's §6.1 table exactly. The label set is a fixed array in code (`config::Dht::switches`), never input.
- **One source for the values.** `Dht::switches` reads the resolved `[dht]` fields that `Config::dht_config` and `Config::pipeline_config` build the crawler from, and `services` takes it from the same effective `Config` it starts the DHT and pipeline with. A test checks it against the built `dht::Config`, pool and fetch options, so a new mapping that drifts fails. The environment isn't parsed a second time.
- **Set once at start; constant for the process.** None of these switches is in the Settings UI, so the value can't change without a restart. It's rendered by the serving process even with `dht.enabled = false`, where it still shows what the config resolved.
- **`safe_restart` is the config value.** The restart proof runs when it's on (`dht_config().restart` is set); whether this run resumed is `dht_sample_suppression_reason`'s job, not this gauge's.
- **The intensity preset is left out.** It isn't a start-time constant: the settings can change it at runtime (`settings::crawler::follow_intensity`), so a start-time gauge could disagree with the running preset. The collector reads it from the settings API, as the brief allows.
- **Wiring outside the listed files.** The gauge is registered in `http.rs`'s `/metrics` handler (a new `AppState::switches` field) and filled in `services.rs` where `AppState` is built: the "metrics wiring" the brief names. No other code in those files changes.
