## Dependencies (Q13)
- **`zip` 9.4.2, `default-features = false`, feature `deflate-flate2` only.** MIT. `zip-rs/zip2`, the maintained successor of the original `zip` crate, with regular releases through 2026. Only stored and deflate entries can be read; bzip2, zstd, lzma, xz, deflate64, PPMd, AES and the legacy methods aren't compiled in, so an entry using one is refused as corrupt. It adds `typed-path` (MIT OR Apache-2.0), `constant_time_eq` (CC0-1.0 OR MIT-0 OR Apache-2.0) and, through `zeroize`'s features, `zeroize_derive` (Apache-2.0 OR MIT), all on the licence allowlist. Its lockfile entries also bring `nix` 0.31.3 and `cfg_aliases` 0.2.2 (both MIT); neither is built for a shipped target, so `web/licenses/rust.json` doesn't list them.
- **`tar` 0.4.46, `default-features = false`** (no `xattr`). MIT OR Apache-2.0. Maintained in `composefs/tar-rs`, its long-standing home. It adds `filetime` (MIT/Apache-2.0). Only its reader's header parsing is used: never `unpack`, which applies the archive's own paths, modes and links.
- **`flate2` 1.1.10** with the `rust_backend` feature, already in the lockfile for other crates. Pinned exactly like the crate's other dependencies.

## Names
- **Printable ASCII only.** A name with a control byte, a non-ASCII byte or one of `<>"|?*` is refused. That's stricter than the brief, and it makes normalisation exact: there is no Unicode normal form to compute (no normalisation crate is needed), and case-folding is ASCII lower-casing, which is what NTFS, APFS and ext4's case-folding agree on for ASCII. Prowlarr's archives, the only v0.6 zip and tar.gz entries, are all ASCII.
- **Normalisation:** one trailing `/` marks a directory; one leading `./` is dropped (what `tar -C dir .` writes), and a bare `./` is the root and is skipped. Every other `.` component is refused, as are empty components, `..`, a leading `/`, `C:`-style drive letters (`c:x` included), `//host` UNC prefixes and backslashes. Windows device names (`CON`, `PRN`, `AUX`, `NUL`, `COM0`–`COM9`, `LPT0`–`LPT9`, `CONIN$`, `CONOUT$`, `CLOCK$`) are refused with any extension and with spaces before it. Caps: 255 bytes a component, 64 components, 1,024 bytes a name.
- **Duplicates** compare by the ASCII-lower-cased, `/`-joined name. A directory created because a later name needed it may be listed afterwards; listed twice, or a file and a directory with one name, is a duplicate. A child whose parent's case differs from an earlier spelling goes into the folder on disk (the first spelling), so nothing depends on the filesystem's case rules. A create that still finds its name taken (an 8.3 short-name alias on NTFS, say) is refused as a duplicate.
- **The executable must match the catalogue's spelling exactly,** as written on disk. A file that only folds to it is refused as missing, since on a case-sensitive filesystem it's another file.

## Kinds, modes and caps
- **Zip modes are read from the raw external attributes.** The `zip` crate's `unix_mode` clears setuid, setgid and sticky bits and ignores the Unix half on a DOS-made entry, so it can't refuse them. Any non-zero upper 16 bits are taken as a Unix mode, whatever system the entry claims: a symlink type refuses as a link; any type but none, regular or directory refuses as special; any of `0o7000` refuses. A directory needs both the trailing `/` and an empty body.
- **Tar:** regular files and directories only. Symlinks and hard links refuse as links; devices, FIFOs, contiguous and sparse files and unknown types as special. pax global headers (`git archive` writes one) carry no file and are skipped, but counted as entries. Each entry's mode is checked for `0o7000`.
- **A size mismatch refuses.** An entry whose bytes written differ from its header's size is refused (`size_mismatch`), and the zip reader stops at the claimed size and then fails the CRC, so a header that lies small is refused too. The 2 GiB cap counts bytes as they're written, never a claim: one byte past stops it.
- **The ratio is checked as bytes are written, per entry and for the archive, with a 64 KiB floor (runner, confirmed above).** Output up to 64 KiB, per entry or in all, isn't refused for its ratio alone: a small file of one repeated byte can pass 100:1 honestly, and deflate and gzip framing make the ratio of a few kilobytes meaningless. Beyond it every byte is checked against 100:1. The denominators come from what was really read, never from a header or the caller: the archive's is its length, measured by seeking to its end; a zip entry's is the bytes read from the archive while it's decoded, plus the 8 KiB the zip reader may have read ahead (its header's compressed size could be inflated up to the archive's length); a tar.gz entry's is the compressed bytes read during it, plus the 32 KiB the gzip reader may have read ahead. This keeps Q16's 100:1 for anything that matters.
- **Everything a tar.gz decompresses is bounded, not only file bodies** (self-review). The tar parser reads GNU long names (`L`, `K`) and pax records (`x`) whole into memory, and skips the bodies of pax global headers (`g`), before an entry reaches the writer. A guard between the gzip decoder and the parser counts every decompressed byte, and the writer shares its count of file bytes with it. **Whatever isn't a file body (headers, long names, pax records, padding, skipped bodies) is capped on its own at 64 MiB** (20,000 tiny files need about 40 MiB), plus one 64 KiB copy buffer in flight; the 2 GiB total and the ratio against the compressed bytes read apply on top. So a header's body is never more than about 64 MiB, whatever the total or the ratio would still allow. **Peak memory under the cap is about 150–200 MB:** the parser's buffer can double past 64 MiB while it grows, and the name is copied once more (`path_bytes().into_owned()`). Runner's review: an earlier version bounded it only by the total, and a 1 GiB long name behind an incompressible file peaked at 1.14 GB; the reviewers measured 145 MB after the fix, refused.
- **Folders a name creates count toward the 20,000 entries** (runner's review). A deep name creates up to 63 folders the archive never listed; each is counted when it's created, so entries plus created folders stay within the cap and a small archive can't create millions of folders.
- **An encrypted zip entry refuses as `encrypted`,** read from the entry's raw view, since the zip reader fails such an entry before it can be named.
- **The gzip trailer is read** after the tar's end (at most 1 MiB of padding), so a bad CRC or length past the last entry still refuses the archive. Only the first gzip member is read; bytes after it are ignored, as `gzip` itself does with trailing garbage.
- **A zip's index is read under a byte budget** (runner's call, after two reviews). The `zip` crate allocates for every central-directory record it reads while opening an archive; a 205 MB zip of 4 million records took about 774 MB more memory before its count could be checked. An earlier version read the end-of-central-directory records first and checked their counts, but mirroring the crate's search rules left gaps: zip64 is also taken when the directory's size or offset is `0xFFFFFFFF`, the crate tolerates trailing bytes past the longest comment, and it scans for another zip64 record when the first fails. So that precheck is gone. Instead, **the reader refuses (`too_large`) once opening has read more than the 64 MiB overhead budget**, whatever the crate's rules; a legitimate 20,000-entry directory is a few megabytes. The budget ends once the archive is open, and the 20,000-entry cap is then checked on the count. **Peak memory is about four times the budget, about 250 MB** (round-3 review: a 63 MiB index of 1.35 million minimal records opens, is refused as `too_many_entries`, and peaks at about +254 MB); the runner kept the 64 MiB budget rather than add a limit. Separately, zip 9.4.2 reserves up to about file_len/47 index slots up front: about 1.7 GB of reserved, mostly untouched virtual memory for a 512 MB crafted zip64 (the reviewer measured +15 MB RSS for 11.4 million claimed entries). That's harmless on Linux; on Windows it's committed memory and matters only near the commit limit. A later option is the crate's streaming `ZipIterable`. Then, `validate_header_consistency()` checks every local header against the index, that none is missing and that no entries overlap. Tar is checked entry by entry.

## Writing
- **No `O_NOFOLLOW` constant is needed.** Every file is opened with `create_new` (`O_CREAT|O_EXCL` on Unix, `CREATE_NEW` on Windows), which fails on anything already at the name, a dangling symlink included, so it can never write through a link. Every directory is one this extraction created, below a staging folder it created with `create_dir` (which fails if anything is there), so no path traverses anything else. This avoids a `rustix` or `libc` dependency and `unsafe`.
- **Modes are set through the handle** (`fchmod`) after the file is written, so the umask can't change 0644 or 0755. Directories are set to 0755 at the end, after an `lstat` check. Windows inherits the companion folder's ACL; there's no ACL code.
- **Durability:** each file is fsynced; at the end each directory is fsynced, deepest first, then the staging folder; after the rename, the companion folder. Windows can't open a directory with `std`, so its directory fsyncs are skipped, as in the updater.

## Errors
- **`ExtractError`** is a closed enum: `Refused { refusal, entry }`, `Corrupt`, `NotAnArchive`, `StagingInTheWay`, `Io(ErrorKind)` and `Cleanup { cause, kind }` (extraction failed and so did removing the staging folder; the next stage or sweep removes it). `Refusal` has one variant per rule, each with a stable `code()`. The parser's own messages are dropped, since they can quote the archive; the only archive text kept is `EntryName`: at most 96 bytes, every byte outside printable ASCII shown as `?`.
- **No sweep after an fsync that failed** (round-3 review). If the folder's fsync fails after the pointer's rename, the rename may not survive a crash, and the old pointer could come back naming a version a sweep had just deleted. So nothing is swept then; the fsync error is the leftover, and a later sweep on a durable pointer finishes the job.
- **`Switched`** is what `commit`, `rollback` and `prune_previous` return (runner's review): once the pointer is renamed into place the switch has happened, so it's a success; the folder's fsync after the rename, or deleting what's no longer named, can still fail (on Windows a running program's files can't be deleted), and that error is returned in `leftover` for CMP-5 to log, and a later `sweep()` finishes the job. Before, the step returned an error after the pointer had moved, and a retried rollback then failed with `NoPrevious`.
- **`LayoutError`** wraps `ExtractError` and adds `OutsideRoot`, `AlreadyStaged`, `NotStaged`, `NoPrevious`, `NoCurrent`, `BadPointer` and `Io(ErrorKind)`.
- **No log events in this slice.** A new event needs its names and help in the logging screen's messages (`web/`), outside this slice's paths, and the steps are CMP-5's to report. **Note for CMP-5:** log `ExtractError::code()` and `LayoutError::code()` (stable, closed labels) for each failed step; never the `Display` text or the `EntryName`.

## The install layout and the API CMP-5 calls
- **The "current" pointer is a small JSON file,** `<data>/companions/<id>/current`: `{"format":1,"current":"5.0.3","previous":"5.0.2"}`, read strictly (`deny_unknown_fields`, format 1, versions that parse and re-print the same, at most 4 KiB). It's written by a new `current.tmp`, fsync, rename over `current`, fsync of the folder. A rename over a file is atomic on Windows (`MoveFileExW` with replace) as on Unix, so no symlink or junction is needed, and a crash leaves the old pointer or the new one. A damaged pointer is reported (`BadPointer`), never guessed or rewritten.
- **The API, on `layout::Install`:**
  - `open(data_dir, id)` creates and checks the folder; `existing` checks it without creating it;
  - `stage(version, kind, archive, executable)` extracts into `<version>.staging/` and renames it to `<version>/`; a stale staging folder is removed first if it's a plain directory, and an existing `<version>` (even a link) refuses;
  - `commit(version, executable)` points at it and keeps the old current as `previous`; `<version>/` must be a real folder holding the catalogue's executable as a regular file, so a partial folder is never committed;
  - `rollback()` points back to `previous` and deletes the rolled-back version;
  - `prune_previous()` deletes `previous` once the new version is healthy;
  - `sweep()` deletes version and staging folders the pointer doesn't name, `*.deleting` tombstones and a leftover `current.tmp`, and nothing else (so other slices' files in the folder are safe). CMP-5 runs it at start;
  - `remove()` deletes the whole folder, **the pointer first** (and fsynced), then each child through `delete` (folders by way of a tombstone), then the folder. A crash or a locked file partway through (the companion running, antivirus) never leaves `current` naming a half-deleted version; with no pointer, `sweep` takes every version folder (runner's review); plus `pointer()`, `version_dir()` and `executable()`.
- **Versions compare by their text** in the layout (runner's review): `Version` equality is numeric (`1` = `1.0`), but `1` and `1.0` are different folders, so `commit` and `sweep` compare `as_str()`.
- **A folder is deleted by renaming it to `<name>.deleting` first,** then removing it (runner's review). A crash partway through leaves only a tombstone that `sweep` takes, never a partial `<version>/` that looks staged.
- **I/O errors aren't read as "not staged":** `commit` and `rollback` return them; only "not found" means not staged.
- **`open` checks `<data>/companions` before creating `<id>`,** so a linked `companions` never gets a folder made inside its target.
- **Only one previous version is kept.** A second commit without a prune makes the old current the previous and deletes the one before it.
- **Deletion:** the folder and `<data>/companions/` must be real directories (not links), and the folder's canonical path must equal the canonical data folder joined with `companions/<id>`. That's checked when the folder is opened and again before every delete. Everything deleted is a direct child of the folder or the folder itself, removed with `std::fs::remove_dir_all`, which never follows a symlink or a junction (it's race-safe on Unix and Windows) and removes a link found inside as a link.
- **Windows links:** a junction or directory symlink found where a real folder must be refuses; one found inside is removed with `remove_dir`, which removes the link. The tests make junctions with `mklink /J`, which needs no privilege, so Windows CI covers this; symlink tests are Unix-only because creating one on Windows needs a privilege.
- **One caller per companion.** Every changing step takes `&mut self`; CMP-5 holds one `Install` per companion and serialises its steps. There's no lock file.
- **The state row is CMP-5's** (plan §3): it mirrors the pointer. If they ever disagree, the pointer on disk is what runs.

## Notes for later slices (runner's review; no code here)
- **There's no way to reinstall the current version in place.** `stage` refuses an existing `<version>/` (`AlreadyStaged`), `sweep` keeps the current one, and `remove()` removes everything. CMP-5's repair path must either install another version or remove and install again.
- **On Windows, `<data>/companions` spelt in another case breaks the canonical-path match:** `canonicalize` returns the case on disk, so the check refuses (`OutsideRoot`). It fails safe; CMP-5 should create the folder through `Install::open` only.
- **A V7 (pre-ustar) tar regular entry whose name ends in `/` is refused** (an empty-named file). That's safe, and accepted.
- **CMP-5 logs** `ExtractError::code()`, `LayoutError::code()` and a `Switched::leftover`'s code.
- **The tar.gz ratio counts headers and long names as output,** since the guard sees everything the parser decompresses. A valid tar.gz of very deep names, whose headers compress far better than its files, can be refused at about 109:1. It fails safe; CMP-5 reports it as `ratio`.
- **`sweep` removes any `*.deleting` child of `<id>/`,** whatever is before the suffix: the name is the layout's own tombstone, and nothing else should use it.
- **`remove()` fails safe on a child it can't name or tombstone.** A direct child of `<id>/` whose name isn't UTF-8, or is 247 bytes or more (so `<name>.deleting` passes 255), makes `remove()` fail and leaves the uninstall unfinished. CMP-5 reports it; nothing Lodestar writes there has such a name.
