# PK-win-soak-ci decisions

- **What the stress covers:** merges and segment garbage collection in both indexes (torrents and files) on a real `MmapDirectory` behind `retry_dir.rs`, through the public API only (`SearchIndex::open`, `Indexer`, `Lease`, `SearchIndex::search`). One writer makes 240 commits of 1–4 torrents with tantivy's default merge policy. Four reader threads take a lease on each commit, hold up to four across 1–24 later commits (so across merges that retire their segments), page each again before dropping it, and also search the current searcher. It asserts that no commit, merge or collection fails; a held lease returns what it returned when taken; every committed torrent is found alone by a lease taken after its commit, the corpus count never falls below what was committed, and once the run settles every torrent is found alone by its own word; merges land (tantivy only logs a failed merge, so the final segment count must be under a tenth of the commits; locally it's 2 per index); and, once every lease is gone and the writer commits again, each folder holds only the files of the segments its own `meta.json` lists, plus `meta.json`, `.managed.json` and the two locks. The mmap cache gauge (`SearchIndex::mmap_cache_entries`, X-mmap-cache-prune) must then equal the live non-empty segment files in each folder; empty files are never mapped. On Windows at least one retired segment must also have outlived a later commit's collection (a delete that failed while a map was held), or the run tested nothing there; elsewhere that count is 0, because a mapped file can be unlinked. Architecture §11.
- **What it doesn't cover:** hot columns are RAM arrays, not mmaps, so only merge/GC applies (plan `docs/plan/2026-11-06-m6-gap-audit.md` rows 57 and 119). A `Lease` pins only the torrent index's searcher, so long-held maps are on torrent segments; the file index's are held only between a commit's collection and its reader's reload, which still makes those deletes fail and retry on Windows. The title FST, an index swap during a rebuild (`rebuild.rs`, which keeps a retired index open until its last lease) and a crash between a failed delete and the next collection are outside it; recovery has its own tests.
- **No timing assertions, no fixed sleeps.** The work is fixed by a seeded generator. Readers wait on a condvar for the next commit with a 60 s deadline. The writer shuts down with `Indexer::finish`, so no merge finishes after settling has looked. Settling then commits, waits for merges, commits again and re-checks, until a 60 s deadline. A failed read of `meta.json` while a merge replaces it is retried until the same deadline. Each failure message says what it saw.
- **Settling commits twice per round.** `Indexer::finish` reloads the readers after waiting for merges, but the collection inside the merges ran before that reload, so on Windows it can still miss files the old searcher mapped. A second, empty commit runs the collection and the prune against the reloaded readers. The test prints how many rounds it took.
- **CI:** a `windows-gc-stress` job on `windows-latest` runs `cargo test -p lodestar-search --test windows_gc_stress -- --test-threads=1 --nocapture` in the test profile (opt-level 1), one cold build rather than a release one; the summary line it prints shows how many retired segments outlived a collection. It's in `ci-ok`'s `needs`, so it's required where it applies. It reuses the `mmap_retention` output of `.github/scripts/ci_changes.py`, which is true for a change to `lodestar-search` or to anything the bench crate builds (the search crate's dependencies among them), and on `main`, nightly and `full-ci`. That's a small superset of "the search crate and the test", and it avoids a change to `ci_changes.py`. The test also runs in the workspace `test` job on Linux and Windows.
- **Job time:** measured on this PR's CI run and reported in the PR description.
