# SRC-1 decisions: store migration V14 for Sources

Slice SRC-1 of `docs/plan/2026-11-01-v06-sources.md` (§3, §4.2). It covers architecture §18.5, §7 and §20, and owner decisions §2.16, §2.17 and §2.21.

## Number and timing
- **The migration is V14.** The runner assigned it (runner-state `migration_order`: V12 `release/v0.5.1`, V13 imports on `main`, V14 SRC-1, V15 CR-3). This is the plan's §5 Q12 swap: CR-3 takes the next number after this one. The plan writes "V15" for this migration throughout; read it as V14.
- **Migrations on `main` before the v0.5.1 tag are allowed** (owner, §2.28). v0.5.1 ships V12, so its build refuses a V14 store cleanly, as it refuses V13 (test below).

## V14: what it adds
Additive only: three tables, one index and three triggers. No existing table, column or trigger changes. `torrents` gains nothing.

- **`unverified_items (id, network, key, source_id, sources, flags, claims, first_at, last_at)`**, `UNIQUE (network, key)`, STRICT, a rowid table (claims run to a megabyte).
  - `id` comes from `id_seq` and is kept on promotion (§18.5).
  - `network` 0 is clearnet BitTorrent (§18.6), whose `key` must be a 20-byte swarm hash. Other networks get 1–64 bytes; none exists yet.
  - **Two columns beyond §18.5's sketch, both needed for §18.1's purge:**
    - `sources`, a bitset as in `torrents`, so a purge can tell an item only one source found from one others found too. A `CHECK` keeps `source_id`'s bit set.
    - `flags`, with two marks (§18.7):
      - "found only through private sources", sticky the safe way as on `torrents`: a public sighting clears it, a private one never sets it;
      - "its claims came through a private source". A public sighting of the key doesn't clear this one; only public claims replacing them do. One source can cover private and public indexers (Prowlarr), so the source id can't tell. Private claims hold private-tracker names and tracker URLs with passkeys, and must never leave the instance (self-review).
  - **`source_id` is the source whose claims `claims` holds.** One item holds one source's claims:
    - the first source's claims are kept, and only that source's newer claims replace them;
    - another source finding the same key adds its bit, and its claims wait until promotion (its next poll then writes `torrent_claims`);
    - after a purge takes the owner's claims, `claims` is `NULL` and `source_id` moves to a remaining finder, whose next claims take the row.
    - Why: per-source claims for unverified keys would need a second claims table without a foreign key. Feeds repeat their items, so little is lost.
  - **A new item needs claims.** Bare keys stay a capped verification queue, not rows (§18.5); `put_unverified` returns `Put::Bare` and writes nothing.
- **`torrent_claims (torrent_id, source_id, flags, data)`**, primary key `(torrent_id, source_id)`, cascading on torrent delete (§18.5). `flags` 1 marks claims that came through a private source, set from the sighting that wrote them and carried over on promotion; SRC-17, exports and Torznab leave them out. A rowid table, plus an index `(source_id, torrent_id)` so a purge deletes one source's claims in bounded chunks.
- **`source_state (source_id, key, value)`**, the store side of SRC-0's `PluginState`. A table, so state commits in the same store as the items (plan §3, silent in §18.1). The limits match SRC-0's: key 1–128 bytes, value ≤ 64 KiB, ≤ 1,024 keys per source. The `CHECK`s hold the first two; the store API holds the third. Plugin state holds no names, so no purge or snapshot rule touches it beyond a source purge.
- **Every `source_id` references `sources (id)`.**

## The claim encoding (`crates/store/src/claims.rs`)
- **It's an on-disk format and an untrusted-input parser.** It's a version byte, a codec byte (raw or zstd), then a plain body. The layout is in the module docs.
- **The store owns its own `Claims` model.** It mirrors `lodestar_sources::Claims` and `Provenance` with the same limits. `lodestar_sources` depends on the store, so the types can't be shared; SRC-2 maps one onto the other.
  - Provenance (external reference, publish time, confidence) is stored with the claims. "Found by: Nyaa", with a link to the item, needs it (SRC-17), and the format is cheapest to settle now.
- **The decoder trusts nothing:**
  - every length and count is checked against its limit before anything is reserved, and a count is refused if what's left can't hold that many entries;
  - text in all is ≤ 1 MiB, as SRC-0 clamps it;
  - zstd reserves what the frame declares, never more than `MAX_PLAIN` (1.14 MiB), and the stored blob is ≤ `MAX_STORED`, a number the schema's `CHECK` repeats (a test keeps them equal);
  - varints are minimal and ≤ 64 bits; unknown field bits, flag bytes, confidence values and versions are refused; strings are UTF-8; nothing may follow the last field.
- **The plain body is canonical:** an accepted body re-encodes to the same bytes. The fuzz target and the property tests check this.
- **`encode` refuses claims outside the limits** (`Claims::check`), so the store never writes a blob its own decoder would refuse. Callers clamp first (SRC-0's `Claims::clamp`).
  - `MAX_PLAIN` counts 13 bytes of framing per file: a path of 128 bytes or more needs a 2-byte length. The first draft counted 12, so the largest claims could exceed it (self-review, blocking). A test now builds that worst case, compressible and not, and the encoder returns an error rather than ever writing past the bound.
- **Zstd is used only when it makes the blob smaller.** No dictionary: typical feed claims are about 170 B, and a trained dictionary is a later optimisation if the size measurement asks for one.
- **`Claims`', `ClaimedFile`'s and `ExternalId`'s `Debug` print no text,** only lengths and counts, so a claim a rule holds can't reach a log line. Store errors about claims carry no text either.
- **A blob that doesn't decode is surfaced as `unreadable`,** not as an error, so the re-judge sweep can drop it rather than wedge on it. It can't be judged, so it can't be kept.

## Content safety
- **Nothing is written under a held hash.** `put_unverified`, `put_claims` and `promote` all refuse a hash in `tombstones`, `cs_hashes` or `quarantine`, checking both hashes of a hybrid. The filter engine's checks (SRC-2) come before these calls; these are the store's own guard.
- **A hash that enters any of the three tables later** fires a V14 trigger (V13's pattern), which:
  - journals the hash into `snapshot_deletions` when an unverified item held it;
  - deletes that item;
  - deletes the claims of any torrent under the hash, by v1 or truncated v2 hash.
  - The `torrent_claims` deletion isn't journalled: those claims belong to a torrent, and the snapshot purge already deletes a held hash's torrents, whose claims cascade.
- **No trigger on `torrents` inserts.** IMP-1 measured V13's at up to four index probes per crawler insert. A crawled hash that's already unverified is promoted by writer code (SRC-2). If a torrent is stored under the hash first, `promote` merges instead (`Promoted::Merged`), so nothing is duplicated either way.
- **Tests cover every path:** a hold through each table (each written the way the store writes it), a truncated v2 hold reaching a hybrid's claims, and a held hash refused by `put_unverified`, `put_claims` and `promote`.
- **Deleted names leave the file.** `secure_delete` is on, and every API that deletes names (re-judging, purges, a refused promotion) runs the WAL scrub after. A file-level test checks a purged name is in neither the database nor the WAL.

## Store API (`crates/store/src/unverified.rs`)
- **`put_unverified`:** one transaction per batch. Returns `New`, `Existing`, `Torrent` (a stored torrent holds the key: it gains the source's bit and `torrent_claims`, and is made public on a public sighting), `Held` or `Bare`.
- **`put_claims`** stores or replaces a source's claims on a torrent, with their private mark. **`torrent_claims`** reads them.
- **`promote(id, &PreparedTorrent)`:** one transaction. Only verified metadata promotes (§18.5): `t.verified` false is `Error::Invalid`.
  - **Keeps the id.** `insert_new` takes the next id from `id_seq`, so the call points the sequence at the item's id for that one insert and puts it back. The item's id came from the sequence and was never a torrent's, so it's unique.
    - This avoids editing `lib.rs` beyond the module lines, which this slice doesn't own. A later store slice can replace it with an `insert_new` that takes an id.
    - It refuses (`Corrupt`) an item id that isn't below the sequence's next id, so a damaged sequence can never be moved backwards and an id reused.
  - **When a torrent already holds the hash** (`Promoted::Merged`), it gains the item's sources and claims, and an import's partial file list gets the fetched one, as `commit_one` does.
  - The torrent gains the item's `sources`, the fetching source's bit, `first_source` (the item's `source_id`), the earlier discovery time, and the item's claims.
  - It stays private-source only if both the item and the fetch were.
  - A key the torrent doesn't hold is `Error::Invalid`. A held hash deletes the item (journalled) and stores nothing.
  - **The promoted id goes into `reindex_log`.** It's below the search index's id watermark, which would otherwise never see it.
  - **Handoff to SRC-2/SRC-3, because a promoted id sits below every id watermark:**
    - the search indexer's re-index path must handle an id it never indexed;
    - the percolator (saved-search alerts) and the hot columns must pick it up;
    - **Insights:** `record_searchable` counts ids above the index watermark, so it never counts a promoted torrent as newly searchable, while V11's `torrents_removed` trigger does count its later deletion. Until SRC-2 counts promotions (newly searchable, time to searchable, the day tables), a promoted torrent that is later purged or held puts the rollups one off. The purge test reconciles torrents that were never promoted.
  - A promotion isn't a deletion, so nothing is journalled.
- **The re-judge store API** (SRC-2 adds the sweep, as #280 did for candidates):
  - `unverified_after(after, limit)` and `claims_after((torrent, source), limit)` are keyset pages.
    - Each is capped at `MAX_PAGE` (1,024) rows and stops once its decoded text passes `PAGE_TEXT` (8 MiB).
    - **So a page holds at most about 9 MiB** however large the claims are. A test checks a page of 1 MB claims stops early.
  - `refile_unverified` and `refile_claims` write a batch in one short transaction. They're **cancellable:**
    - like `refile_import_candidates`, they ask `current()` inside the transaction and write nothing when the rules moved on;
    - the sweep can stop between any two pages.
  - A removed item is journalled. A decision passed with it is written as ingest writes one: a filter hit, and a hold on the hashes when it holds.
  - `refile_claims` removes claims. A decision that doesn't hold leaves the torrent alone, since a stored torrent is judged on its verified metadata by the existing refile path. **A decision that holds also deletes the torrent** and logs it for the index, as `set_enrichments_at` does, so nothing stays stored under a held hash (self-review, blocking).
  - **The rule for SRC-2:** a claim that hits the floor or a CS pattern always carries a hold. A claim removed without a hold isn't journalled, so older snapshots keep it until they expire (below).
- **`purge_source(source, cursor, limit)`** (§18.1, §18.9). Chunked: one transaction per step over at most `MAX_PURGE_STEP` (4,096) rows, so SRC-14 runs a purge of millions as a `/jobs` job that can stop between steps. The stages, in order:
  1. **Unverified items:** deleted (journalled) when only this source found them. Otherwise the bit is cleared, and the claims too when they were this source's.
  2. **Every claim this source made.**
  3. **Torrents:** deleted when only this source found them. Each goes into `reindex_log`, and V12's trigger journals it and V11's trigger counts it as removed in Insights, so the rollups reconcile (tested). Torrents others found too lose the bit.
  4. **The plugin's state, and the persisted fetch-queue keys the source queued**, so a fetch queued before it was disabled can't store a torrent under its bit afterwards. **Handoff to SRC-14:** drop the pipeline's in-memory queue entries for the source too, before the purge job starts.
  - **The source must be disabled or purged first** (`Error::Invalid` otherwise), so nothing it finds meanwhile slips past the purge.
  - `first_source` is left on kept torrents: it records history, and ids are never reused (§16).
  - **A kept item or torrent stays public** even when its only public finder was the purged source. That's the sticky direction already chosen: a purge doesn't make anything private again.
  - **Not covered by the snapshot purge:** claims deleted from rows that survive stay in older snapshots until those expire at 90 days. That's the same as edited searches or notes (`snapshots.rs`). The cases:
    - a source purge's claims on torrents others found too;
    - a source purge's claims on unverified items others found too (set to `NULL`);
    - claims `refile_claims` or `refile_unverified` removes **without** a hold.
    - The first two are data-management actions, not safety deletions. The third is why floor and CS claim hits must always hold (the SRC-2 rule above): every hold deletes the item or torrent in snapshots, and claims go with it. Journalling claim deletions by `(torrent_id, source)` would need a second journal; it isn't worth it while holds cover safety.
- **`plugin_state`, `set_plugin_state` and `compare_and_set_plugin_state`** implement SRC-0's contract. The `PluginState` implementation over them (it's async, through the writer) is wiring for SRC-2 or SRC-4.

## Snapshots
- **`Plan::KNOWN_THROUGH` is 14.** A V14 snapshot also drops unverified items whose hash the live store deleted, purged or holds (`PurgeReport::unverified`). Torrent claims cascade when the purge deletes the torrent.
- **Tested:** a held item, a purged item, and a deleted torrent's claim all leave a V14 snapshot, while an unrelated item stays.

## Measurements
Both are `#[ignore]` tests, so they can be re-run. Release build, this session's container.

- **Space per row** (unchanged by the `flags` columns, which store 0 in no bytes), with typical feed claims (a 45-byte name, a size, three files, a tracker, a publisher and a GUID), measured with SQLite's `dbstat` over 100,000 rows:
  - claim blob: **170 B** on average;
  - `unverified_items`: **248 B per row**, including its `UNIQUE (network, key)` index;
  - `torrent_claims`: **210 B per row**, including the primary-key and source indexes.
  - Run: `cargo test --release -p lodestar-store --test unverified space_per_row -- --ignored --nocapture`.
- **Migration time on a 1M-torrent store.** No 1M fixture exists, so the test builds one: a V13 store with 1,000,000 torrents and their file rows, 304 MB.
  - V14 with its pre-migration snapshot: **0.8–2.1 s** over two runs, nearly all of it the `VACUUM INTO` snapshot.
  - The migration alone: **2–10 ms** over two runs (2.1 s and 0.8 s with the snapshot). It creates empty tables and triggers, so its cost doesn't grow with the corpus; the snapshot does, as for every migration.
  - Run: `cargo test --release -p lodestar-store --lib v14_migration_time -- --ignored --nocapture`.
