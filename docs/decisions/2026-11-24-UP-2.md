# UP-2 decisions: upload drop zone and watch-folder settings

Slice: UP-2 (`runner/slices.yaml`). Spec: architecture §10.14 and §10.3; UI review 02 §5.3 (`docs/review/2026-11-13-ui-ux/02-skills-pass-and-future-modules.md`); the runner's UX call on Retry (`docs/decisions/2026-11-14-runner-ui-review-placement.md`); UP-0 (`docs/decisions/2026-11-12-UP-0.md`) and UP-1 (`docs/decisions/2026-11-12-UP-1.md`).

## Where it lives
- **A Settings screen, `/settings/import`, titled "Add torrent files", in the Crawling group** (after Companions: the registry puts an id it doesn't list last in its group). It registers itself through `features/upload/screen.ts`, so no route file is added. The screen holds both the drop zone and the watch folder's fields.
  - UI review 02 §5.3 puts the watch folder in Settings → Sources "as its own row". Sources is another slice's screen; one screen for both ways of adding files keeps UP-2 inside its paths, and a Sources row can link here later.
  - **The overflow menu's Import item** (§10.3, held in `nav.ts` until a screen existed) now opens it, labelled "Add torrent files" as the review names it, first in the menu as §10.3 lists it.
- **Not built here, follow-ups:** the item on the empty Search state, and a drop anywhere on the Search page. Both are in the Search route, whose 45 KB budget can't be raised; they belong to the slice that owns that route.

## The upload part
- **One request per file, one at a time, in the order picked.** `POST /torrents/upload` takes one raw file per request (UP-0). Sending in turn keeps a pick from racing past the server's rate limit and keeps the result list in order.
- **Limits named before upload:** "Up to 30 files at a time, each at most 8.00 MiB".
  - **30 files per pick** is the server's rate-limit burst (`upload::RATE_BURST`), so a whole pick goes through on a fresh allowance. A pick over 30 is refused whole, with the number chosen and the limit, and nothing is sent: taking the first 30 silently would leave the person guessing which ones were left.
  - **8 MiB** is `upload::MAX_BYTES`. A larger file is marked "Over 8.00 MiB, too large" and never sent.
  - **A file not named `.torrent`, or empty, is "Not a torrent file"** without being sent. The server still judges every file it gets.
- **Results per file:** Added (with "Open" to its page, `/t/<hash>`; "Added, private" for `private=1`), Not a torrent file, Held by filters, Refused by the safety floor, too large, and the retryable ones: too many uploads (with the server's `Retry-After`), Lodestar isn't taking uploads, couldn't send, not sent yet. Counts sit above the list, and a screen-reader line announces them when a pick finishes.
  - **"Already in the index" isn't shown.** The upload route answers `202` for a torrent the index already has, exactly as for a new one, so the browser can't tell them apart. Follow-up for the API (outside this slice's paths): an `already_indexed` flag on the `202`, which this screen would then show.
- **Retry (the runner's call):** a file that failed because of the server or the connection gets Retry, and "Retry failed files" retries them all. A refusal about the file itself (not a torrent, held, refused, too large) gets none: sending it again would get the same answer. A rate limit or "not taking uploads" stops the rest of the pick, which waits as "Not sent yet" for Retry instead of failing the same way file by file.
- **The whole screen takes a drop,** not only the zone, so a file let go beside the zone is added instead of opened by the browser. The zone's Choose files button is the way in without a mouse.
- **Leaving the screen stops the queue** and aborts the request in flight.

## The upload request's headers (`/security-review`)
- Exactly `Content-Type: application/x-bittorrent` and `Accept: application/json`, with the file as the body. No multipart, so the file's name and path never leave the browser (the limits line says so).
- `credentials: 'same-origin'`: the session cookie goes only to this origin. The browser adds `Origin` and `Sec-Fetch-Site`, which the route's same-origin check reads; the page never sets them.
- `redirect: 'error'`: a redirect is refused rather than followed with the file's bytes; `cache: 'no-store'`.
- A `401` goes to the shell's sign-in handler like every other request.
- The answer is trusted only as far as its shape: refusals are read by their `code`, never by showing the server's message, and an `info_hash` that isn't 40 hex digits is dropped before it's used in a link. File names are shown as text inside `<bdi>`, so direction marks in a name can't reorder the row.

## The watch folder
- **Its two fields render on the form engine**, taken through its one door (`form/embed.ts`) as the section form and the wizard take it, so saving, conflicts, the draft and an environment lock work as on every other screen. Not through `GroupedForm`: reaching it without `SectionScreen` split the connection screens' shared chunk and added ≈ 0.5 KB to three of their first views. When `LODESTAR_WATCH_DIR` lands (X-watch-env, #1104), the engine shows the field read-only with its "Set by" line, with nothing to change here.
- **The reason beside the field:** a save can't see the data folder (`Section::check`), so a folder inside it saves and then is never read. The screen reads General's data folder (`general.data_dir`) and compares the two paths by their parts, as typed, showing "Off: this folder is Lodestar's data folder or inside it…" or "…the data folder is inside this folder…". It resolves no links and gives up on `..`, so it can miss a case the server catches, never invent one; the server stays the authority.
- **What the screen can't show yet:** the watch's live state (on, paused and why, last scan, counts, "Still being written", the failed files with Retry). Nothing in the API reports it: UP-1 only logs `watch.disabled` with its reason. The screen says how the watch works (every 10 s, a file still being copied is left until it stops changing, `added/` and `failed/` with the reason in the name, move a failed file back to retry it) and links to Logs for why it's off. Follow-up for the runner: a watch-status endpoint (problem code, last poll, counts, files pending a re-read, the `failed/` list) and a Retry that moves a failed file back, then this screen shows them.
- **Settings search doesn't list the watch fields,** only the screen by its title. Listing them needs a generated screen's purpose module or the find index's list of field screens, both shared files with their own size budgets; left as a follow-up.
- **Labels:** the `watch` section's field labels and help (`settings_watch_*`, `settings_group_watch`) are added to the settings messages, which UP-1 left without them because the section had no screen.

## Size (web/.size-limit.mjs)
Every Settings page loads the screen registry and the group headings, so a new screen costs every first view something. Kept as small as the patterns allow:
- **The entry forwards through `body.ts`** (as Sources, Jobs and Blocklists do), so the body's preload list stays out of the registry's chunk: the entry measured 81 B there instead of 134 B. Like theirs, `upload/body.ts` needs its name in the `securityLoader` pattern of `.size-limit.mjs`, or the walk counts its 337 B in every first view.
- **The overflow menu's item has its own label** (`upload_menu_item`, same words as the title). Sharing the title put that one message in a chunk of its own, fetched by every Settings page.
- **The screen loads its watch part without Settings' `Lazy`**, and the watch part shows its own loading and failure lines: reaching one of the form's shared status messages without the rest split them into two chunks on every first view.
- **The drop zone has a 1 px border** (`border`), not a dashed 2 px one: those two classes were new to the global stylesheet, whose budget can't grow.
- **The watch part loads after the upload part paints** (the engine, ≈ 21 KB of the screen's 52.8 KB). With it measured as on demand, like the connection screens' and Logging's later parts, the screen's first view is about 35 KB. That needs `WatchFolder.svelte` in the hand-built screens' on-demand list with an entry of its own, and `UploadScreen: ['watch']` in `bodyMaps`: both `.size-limit.mjs` edits, left to the runner.
