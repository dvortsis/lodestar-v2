The purge job, `Pool::drop_source` and the snapshot scrub follow in 14b-2, after R-mem-triage merges; 14b-2 adds its own file (`2026-11-02-SRC-14b-2.md`). It covers architecture §12 (the SSRF guard) and §18.7 (egress), and closes SRC-14a's handoff on `EgressDown` pacing.

## IPv4-mapped proxy addresses are judged as IPv4
- **`[::ffff:0.0.0.0]`, `[::ffff:224.0.0.1]` and `[::ffff:255.255.255.255]` are refused as proxy addresses,** like the IPv4 addresses they carry. A connection to a mapped address goes to that IPv4 address, so `::ffff:0.0.0.0` reaches this machine, as `0.0.0.0` does.
- **Each of the three checks converts with `to_ipv4_mapped()` first:**
  - the API parser (`lodestar_api::ops::parse_proxy`);
  - the stored value (`EgressSetting::decode`, through `proxy_host_ok`);
  - the factory (`usable_proxy`, for literals and for every answer a name resolves to).
- Mapped forms of usable addresses (`::ffff:127.0.0.1`, `::ffff:192.168.1.10`) are still accepted in all three (runner, #399 N4).
- Tested in all three: `parse_proxy`'s refusal list, `egress_settings_round_trip_and_refuse_junk`'s cases, and `a_proxy_by_name_resolves_once_and_an_unusable_one_stays_down` (mapped literals, and a name that resolves only to mapped unusable addresses).

## A route-level delay after `EgressDown` (SRC-14a's I1 handoff)
- **A refusal before sending, while the route is down, comes back after a delay:** 1 s (`DOWN_DELAY_MIN`), doubling with each refusal in a row, up to 30 s (`DOWN_DELAY_MAX`). A sequential retry loop therefore gets at most one attempt per delay through its egress, however fast it retries.
- **It ends early when the route comes up** (the kill switch's state changes to Up), so a recovering VPN costs no extra wait. The refusal is still returned, and the plugin's next request goes through.
- **A request that the route lets through resets the streak.** That includes one that then fails at the host.
- **Only the refusal before sending is paced.** An abort in flight or a dead route found on re-probe returns at once. The plugin's next attempt meets the refusal, which is paced.
- **The delay is per plugin, not per request.** Concurrent requests each wait, and the streak is shared.
- **Bounded:** no wait exceeds 30 s, and a dropped future (the plugin's shutdown) ends it.
- `HttpError::EgressDown`'s plugin contract now says that egress paces refusals. A plugin still waits its poll interval.
- Tested in paused time: `refusals_while_down_are_paced_and_bounded` (1, 2, 4, 8, 16, 30, 30 s; cut short at 5 s when the route comes up; back to 1 s after a request goes through).

## Rate limits and 5xx back off the poll unit, not the host
- **`Client::poll(unit, …)` records the answer with `HostLimiter::record_poll`:**
  - a 429, or a 503 with `Retry-After`, **blocks the unit**;
  - a 5xx, or a 429 without `Retry-After`, **backs off the unit**;
  - the unit's block or back-off is checked after its poll is taken, as a host's is, so a plugin that retries a blocked unit at once (Nyaa's loop does) is still paced by the poll interval. A blocked unit's poll fails with `HttpError::Blocked`.
  
  Before this, one Prowlarr indexer that rate-limited us blocked the whole manager for up to 24 h (`MAX_RETRY_AFTER`).
- **Host-wide failures stay on the host:**
  - a transport failure (connect, reset, timeout);
  - a 401 or 403, which is a key the whole host refuses.
  
  They back off or block every unit on it, as `record` does for `send`.
- **A normal answer resets both** the unit and the host.
- **Two different units failing in a row** (a 5xx or a rate limit, with no normal answer between) **back off the host too** (fresh review, important). A manager that's down behind a reverse proxy is then asked once per back-off step, not once per indexer per step. The same unit failing again stays on that unit. Tested: `different_units_failing_in_a_row_back_the_host_off`.
- **A host-wide `Retry-After` is honoured on the host** (runner, #399 B1, blocking). When two different units in a row both answer with `Retry-After`, the host is blocked until the earlier of the two times, so one unit's long `Retry-After` can't stretch the host's block. A manager, or a proxy in front of it, that answers everything `429 Retry-After: 3600` is asked once per window, not once per unit. Tested: `a_host_wide_retry_after_blocks_the_host`.
- A unit's own state lives in the limiter's host table under `unit <id>`. A host key never holds a space, so the two can't collide.
  - Units are made within `MAX_HOSTS`, and forgotten when idle, as hosts are.
  - When the table is full, the answer goes on the host, the safer side (fresh review, important). A manager can't grow the table by rotating indexer ids.
  - Tested: `units_stay_within_the_table`.
- `Client::send` (no unit) is unchanged: everything stays on the host.
- Tested: `a_poll_units_rate_limit_and_5xx_stay_on_the_unit` and `host_wide_failures_in_a_poll_stay_on_the_host`.
- **A precondition for Prowlarr (SRC-7):** its plugin must poll each indexer as its own unit through `Client::poll`, so a rate-limited indexer stops only itself. It already does (`prowlarr.rs`).
  - **Handoff to SRC-7:** it also polls the manager's own indexer list as the unit `"indexers"`. A 429 there is the manager's own API refusing us, so that request should go through `Client::send` (paced by the host) rather than `poll`. Until then, the two-units rule above backs the host off once the indexers fail too. `prowlarr.rs` isn't this slice's to edit, and the plugin isn't registered.

## More Prowlarr preconditions (runner, #399 review, deferred)
- **N1:** a unit's block doesn't cover `Client::send` to the same host. A plugin that mixes `send` and `poll` on one host can reach a blocked unit's resource through `send`.
- **N3:** units share the `MAX_HOSTS` table with hosts. A manager that lists more than 1,024 indexers can fill it, and its answers then fall back to the host (the safe side, above), which stalls its own plugin.
- Both matter only once Prowlarr is registered; the runner is tracking them.

## IPv6 forms that carry IPv4, beyond mapped (fresh review, polish, left)
- The proxy checks convert only IPv4-mapped addresses, as the brief prescribes. The SSRF guard's `net::classify` also decodes IPv4-compatible (`::a.b.c.d`), NAT64 and 6to4 addresses (`embedded_v4`), so `[::224.0.0.1]` passes the proxy check.
- None of these reaches this machine: `::` is refused as unspecified, and `::1` is loopback, which is allowed for a proxy anyway.
- **Handoff:** exposing `embedded_v4` from `crates/integrations` (not this slice's path) would let all three checks share one rule.
