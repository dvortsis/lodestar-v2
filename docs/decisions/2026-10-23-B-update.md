# B-update decisions, part 1: the trust core

The new crate `crates/update` (`lodestar-update`) is the pure verification core of §12.2: minisign, the documents, the key chain, the trust state and the three entry points. It changes no behaviour yet; parts 2 (the supervisor and rollback) and 3 (the check, install, policy and API) use it. **`crates/update/README.md` is the format contract** for E-M6's `release.yml` and the weekly re-sign.

- **A library crate, pure.** No tokio, no network, no clock, no logging: callers pass bytes and the time. It has to be a library so `cargo fuzz` can reach the parsers (`crates/lodestar` is a binary). Dependencies, all already in `Cargo.lock` and pinned exactly: `ring` 0.17.14 (Ed25519), `blake2` 0.11.0 (minisign's prehash), `sha2` 0.11.0, `base64` 0.22.1, `semver` 1.0.28, `serde`, `serde_json`; `proptest` 1.11.0 for tests. Not `minisign-verify` (its own curve code) and not OpenPGP: the key IDs in `packaging/keys/` are minisign key numbers.
- **minisign is written to the format** (`src/minisign.rs`): the 42-byte public key, the four-line signature file (≤ 1 KiB, comments ≤ 512 bytes of printable UTF-8, tab allowed because minisign's default trusted comment has one), strict base64, and all three checks (key number, signature over the prehash, global signature). Both real `.pub` files decode to their documented IDs, and `tests/vectors/minisign/` holds a key, signatures and a key statement made with the real minisign 0.11 tool.
- **Only prehashed `ED` signatures are accepted (§2.19).** Legacy `Ed` (`minisign -l`) is refused. Prehashed is minisign's default since 0.10 and what #92's `minisign -S` writes; accepting one form only removes a downgrade choice.
- **Verify, then parse, with one read ahead (§2.19).** Bodies are the exact signed bytes, and nothing in one is used before its signature verifies. The exception: when a manifest's or freshness statement's signature names a key the installation doesn't know yet (it was offline across a rotation), its `statements` array is read first. Each statement is its own recovery-signed document, verified before its own body is read; nothing else from the unverified body is used, and the document then verifies under the key those statements lead to. The brief puts the statements inside the signed bodies, and an installation that missed a rotation has no other way to learn the new key.
- **Strict JSON, typed bodies.** UTF-8, no BOM, no unknown or duplicate fields, integers only, and a `type` per body (`lodestar-manifest`, `lodestar-key`, `lodestar-freshness`), so one kind can't be read as another and `SHA256SUMS.minisig` can't pass as a manifest. A manifest `format` above 1 is `newer_format` ("needs a newer Lodestar"), read before the strict parse so a format-2 manifest's new fields don't hide the reason.
- **Caps are refusals, never truncation:** envelope 512 KiB, manifest body 384 KiB, freshness 64 KiB, statement 2 KiB, trust state 256 KiB; 64 statements, 64 releases, 8 artifacts per release, notes 16 KiB, versions strict semver ≤ 64 bytes and unique, URLs `https` ≤ 512 bytes on the download allowlist, `sha256` 64 lower-case hex, `size` 1 B to 256 MiB, the three shipped targets. Base64 length is checked before decoding.
- **Details the brief left open, chosen here:**
  - Times are Unix seconds, `date` included; `min_from` and `notes_url` may be null or left out.
  - Release versions carry no build metadata (`+…`), which semver doesn't order.
  - One artifact per target and kind in a release.
  - **A new target needs a new manifest format,** because older versions refuse an unknown `target`. The brief fixes the target list; publishing a new triple (macOS, say) means a format bump.
  - `notes_url` follows the artifact URL rules (https, no query or fragment) but on any host.
  - A statement's `cosig` is checked for form only: it's never sufficient, so verifying it could only add a way to fail.
  - **A key can't be used twice.** A statement whose key (or key number) has been in the chain before, under any role or as the recovery key, is refused. This keeps a revoked key from being brought back and makes a key's role unambiguous.
  - **A document carries the whole chain, from `seq` 1, in ascending order.** A publisher can't know a verifier's sequence, and an older supervisor verifies an overlay from its embedded statements alone, so a tail would strand it; a list that doesn't start at 1 is a gap. Statements at or below the current sequence must equal the accepted ones byte for byte (the body; a re-signature of the same body is the same statement).
  - **Adding a nightly or freshness key is a one-time choice:** as generation 0 or by a statement, never both (the key would count as reused).
  - Key statements from trusted copies (embedded, `trust.json`, verified overlays) aren't held to the clock again; only statements arriving in a fetched document get the 1-day check, so a clock that later runs behind can't undo accepted ones.
- **The same-timestamp rule (§2.19).** A manifest at the high-water mark's timestamp is accepted only with the same body SHA-256 (a refetch); a different body at the mark is refused.
- **Freshness marks are per channel (§2.19),** each with the freshness body's SHA-256 under the same rule. §12.2 names one mark, but a single one would refuse the other channel's statement after a channel switch. The digest (`fresh_sha256`, a field the brief's list didn't have) lets the six-hourly refetch of the same freshness statement pass while a different statement at the same time is refused.
- **A rotation's reset leaves no digest,** so a manifest dated exactly at the rotation's timestamp passes; anything older is refused.
- **A refused freshness statement doesn't refuse the manifest.** The manifest still counts (and moves the high-water mark); only its currency is affected, and the refusal is reported (`freshness_refused`, or `freshness_unavailable` while no freshness key exists).
- **`revoked` in `trust.json` is additive** (runner review). On load every statement is re-verified in sequence and `seq` must agree, or the state is `trust_damaged`; `revoked` is not compared. Each build unions its stored entries with the revocations its own generation 0 implies, because builds can differ in generation 0 (a nightly key added later): a version without that key, after a rollback or with an older image, must still load the file and keep the newer build's revocation, and a newer build must load an older build's file. Extra entries only refuse more. Revoked keys are stored as full key lines, not key IDs, because a key number is chosen by whoever makes the key.
- **Marks more than a day ahead of the clock count as damage,** not a freeze until that date: every mark is a verified timestamp accepted at most a day ahead.
- **The chain is capped at 64 statements over its life** (the document cap; a document carries the whole chain), and accepted statements are stored normalised (body, recovery signature with a fixed untrusted comment, no cosig), so `trust.json` always fits its 256 KiB and can't be padded by whoever carried a statement.
- **Forward only.** `TrustState::merge(old, new)` needs `new`'s statements to extend `old`'s. With a higher sequence, `old`'s marks take only the resets of the statements `new` adds (as `advance` applies them), then each mark is the later of the two, so a check that started from a stale state can't lower a channel the rotation doesn't govern (runner review). With the same sequence, `old` stays unless no mark is lower. `trust.json` refuses a channel named twice.
- **A rotation's reset is intended.** A release or nightly rotation lowers that role's channels' high-water marks to the statement's timestamp, and a freshness rotation the freshness marks, so a client that a leaked key froze with a manifest dated up to a day ahead recovers once the rotation lands. Only the new key can sign at or after the reset.
- **Generation 0 never changes.** `crates/update/keys/` holds copies of the release and recovery `.pub` files (the Docker context has only `crates/`) and an empty `statements.json`. After a rotation the `.pub` in `packaging/keys/` changes but the embedded copy stays: the statements carry the change. A test fails unless each `packaging/keys/*.pub` is its role's current key in the embedded chain, so a nightly or freshness key published there without being embedded fails the build. The owner's first nightly and freshness keys are added as generation 0 (copy the `.pub`, change one `None` in `src/keys.rs`) by default.
- **Until the nightly and freshness keys exist,** Nightly checks fail with `no_nightly_key` (notice `channel_unavailable`) and freshness statements are refused with `no_freshness_key` (notice `freshness_unavailable`). Neither is silent.
- **`overlay()` takes any key that has ever signed for a channel role,** then judges revocation: revoked by the embedded statements is refused (`revoked_key`); revoked only by a later statement (the overlay's own here; part 3 also checks `trust.json`) returns `revoked_later` for the notice.
- **`Error::Ahead` means the clock is behind.** It's only returned after a signature verified, so part 3 maps it to `clock_behind`. `clock_ahead` is raised when a check succeeds but the newest manifest isn't current; part 3 must tell that apart from `manifest_lapsed` (the publisher stopped re-signing), for example by how far past expiry the clock is.
- **For part 3:** a damaged `trust.json` needs a documented way out: rebuild from the floor when only the marks fail (`marks_plausible`), and a documented delete otherwise (the floor and overlays then rebuild it). `ClockAhead` currently covers any check whose manifest isn't current; part 3 tells a freeze (the publisher stopped re-signing) apart from a wrong clock.
- **For part 3, too:** `overlay()`'s `revoked_later` sees only the overlay's own statements; the updater also checks `TrustState::revokes` against `trust.json`. Every write of `trust.json` goes through `merge` against the state on disk, so two checks can't lose a mark.
- **The test signer** (`src/testing.rs`) uses fixed seeds, marked TEST ONLY, and is compiled only for this crate's tests or with the `testing` feature (the fuzz target, and later crates' dev-dependencies). No shipped build enables it, and none of its keys is trusted outside a test's own `Embedded`.
- **The vectors** are 33 envelopes in `crates/update/tests/vectors/check/`, regenerated with `LODESTAR_BLESS=1`; a generated envelope that differs from its file fails, so the format can't drift unnoticed.

## For later parts and E-M6
- **The `release.yml` contract** is `crates/update/README.md`: an envelope per channel with the signed manifest and, from the weekly re-sign, a freshness statement; every manifest after a rotation carries the chain; prehashed signatures only. The owner's statement steps are in `packaging/keys/README.md`.
- **The Windows helper (E-M6)** reuses `check`, `install` and `overlay` unchanged.
