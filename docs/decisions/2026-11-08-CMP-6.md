# CMP-6 decisions

The Companions API, admin only, and the Companions row in `/system` (plan `docs/plan/2026-11-06-v06-companions.md` CMP-6 and Q5; architecture §12, §18.10, §10.10.13; `docs/owner-decisions.md` §2.47). These are the slice's decisions under §2.33. None loosens an owner decision or a security decision. The runner flags them to the owner (§2.19).

## Routes
- **Admin only.** Every route is inside `auth::protected`: a signed-in session. Lodestar has one admin, so "not the admin" means any other caller: no session, an API key (header, bearer or `apikey` query), a feed token, or a proxy header from an untrusted peer. Each gets `401`, and the binary is never asked. `crates/api/tests/companions.rs` checks every route this way.
- **`GET /companions` and `GET /companions/{id}`** return the same row: the catalogue entry, the installed version and health, the version an install or update would fetch, the refusal code when it can't be installed here, the stored credential fields (names only), and the templates it offers.
- **Install and update share one route.** `GET /companions/{id}/install` is the manager's `offer`: version, SHA-256, size, licence, and `replaces` for an update. `POST` takes `{version, sha256}`, compares them with the offer (the SHA-256 trimmed and lower-cased, so a pasted hash in upper case counts), and refuses anything else with `409 confirmation_mismatch` before the manager is asked. The manager compares the token with the pin again. This mirrors `lodestar companion install --sha256`. A separate update route would add nothing: the manager decides from the journal whether it's an install or an update.
- **The removal confirmation echoes only the id** (security review note b): a removal has no artifact to pin. Plan line 162's entry, version and SHA-256 are for installs, which echo both.
- **Remove** is `GET /companions/{id}/remove` (exactly what it deletes) and `POST` with `{confirm: "<id>"}`. A confirmation that doesn't name the companion is `409 confirmation_mismatch`. The folder is named relative to the data folder (`companions/<id>`), not by its absolute path, so no response carries a path on this machine. The credential rows are named by their `settings` keys.
- **Templates** are `POST /companions/{id}/template` with `{kind: compose|unraid, config_dir, downloads, network, puid, pgid, route, gluetun_container}`. Defaults match the CLI. Each value goes through CMP-0's input types and CMP-7's checks; a refusal is `400` with the field and the rule's code. On a native Unix install, Lodestar's own data folder (resolved through links) is passed as a data folder, so a template can't mount it. If it can't be resolved, the template is refused (`500`, logged as `data_folder`) rather than generated without the guard. On Windows the data folder is a drive path, which no template host folder (always a `/` path) can name, so none is passed. Nothing is stored.
- **Error codes are the manager's own** (`not_wired`, `busy`, `native_in_container`, `awaiting_pin`, `no_build`, `guided_only`, `already_current`, `not_installed`, `credential_present`, `folder_in_use`, `no_launch_profile`, `no_template`), at `409`, with a fixed sentence each. `unknown_companion` and `no_credential` are `404`. A failed step is logged by its code and answered as the generic `500`. No response or log line carries a path, a URL or a credential.
- **Without the manager** (a fixture, or companions off for the run because the lock is held or the catalogue is invalid), every route is `503 companions_unavailable`. Each route documents it.

## Credential reveal (Q5, exactly the plan row)
- **`POST /companions/{id}/credentials/{field}/reveal`** with `{password}`: the fresh-password check (§20.11; `428 confirm_required`, `401 bad_password`, `429 rate_limited`) runs before the id or field is looked at. Then the binary opens that one sealed row with CMP-3's `credentials::open`. The value is in that response alone, with `Cache-Control: no-store`; `Debug` on the DTO and on `Revealed` hides it.
- **Logged as `companions.credential_revealed`** (Info, Companions): the catalogue id, the field name and the client address. Never the value. The event lives in the API crate's catalogue because the route is where the reveal happens. It's registered in the logging golden, `event-names.ts` and the en/zh messages.
- **Only a companion Lodestar installed has a revealable credential** (self-review B1). The Q5 row is about seeing a *generated* credential, and plan §4.3 says a pasted key or temporary password is never echoed back. So the reveal and Regenerate answer `404 no_credential` unless the manager's snapshot (filled from each journal by recovery) shows Lodestar installed that companion. A guided qBittorrent's replaced, generated password (CMP-5g) needs a provenance marker before it can be revealed; that's CMP-5g's to add, and the runner's to approve.
- **`Service::installed` keys on the snapshot: a companion with `version.is_some()`** (security review note a). Today only the manager publishes into the snapshot, and only for companions it installed, so that means "Lodestar installed it". The types can't yet express a companion that's in the snapshot with a version but wasn't installed by Lodestar (`Present` carries no provenance), so there's no test for that case. **CMP-5g must move this guard onto the manager's own install record** (its journal) before detected companions enter the snapshot with a version. That's in CMP-5g's notes.
- **Exports, backups and support bundles** are outside this slice. The reveal is the only route that opens a credential; CMP-3's `is_secret_row` filter stays unwired in those paths (CMP-5's carried follow-up).
- **"Regenerate" offered beside it** is `POST …/regenerate`. It needs the companion stopped, its config file rewritten and the companion started again, which only CMP-5g's supervisor can do, so it answers `not_wired` until then. It checks the credential is stored first (`404 no_credential`), and it never reads the old value. It doesn't ask for the password: the plan row asks for it on the reveal only, and a regeneration shows nothing.

## Built for CMP-5g's wiring
- **`CompanionsApi`** (in `crates/api`) is the handlers' trait. `crates/lodestar/src/companions.rs`'s `Service` implements it over the `Manager`, the store's credential rows and the secrets file the manager seals with (`manager_with` returns both, so there's one `SecretStore`).
- **`Live`** is what only a running supervisor can do: restart, recent output and regenerate. `Unwired` implements it with `not_wired`, and it decides `not_installed` for what it doesn't run. CMP-5g hands in its supervisor for `live` and for the manager's `Run`; nothing else changes.
- **Until then, every action is refused with `not_wired` before anything is downloaded.** The manager checks the confirmation, then asks `Run::ready()`, then claims the slot and downloads. `crates/companions/tests/manager.rs` confirms it with a pinned catalogue: an install with a `Run` that isn't ready is refused with `not_wired`, nothing is fetched, and no folder, journal or credential row is left. That test lives with the manager because the binary can't load a catalogue other than the compiled-in one: CI's guard keeps `lodestar-companions/testing` out of `lodestar`'s dependency tree, dev-dependencies included. The binary's own tests use the compiled-in catalogue, where nothing is pinned yet.
- **Logs are redacted again** with the companion's own stored credentials (CMP-4a's `Redactor`), whatever the supervisor's ring already did, and sent with `no-store`.

## `/system`'s Companions row
- **`count`** is how many companions Lodestar installed (from the manager's snapshot), **`state`** is `on` when any is, otherwise `off`. With companions off for the run, `state` is `off` and `count` is null. Detected companions join the count when CMP-5g adds them to the snapshot.
