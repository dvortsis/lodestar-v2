# FX-3 decisions (Keyboard preferences apply at once)

From the M5 design review (`docs/review/2026-11-01-m5-design-review.md`).

- **B3: Keyboard applies at once, with "Saved. Undo".** Save and Cancel are gone. Each toggle or remap applies to the registry straight away and saves through the `preferences` section with `if_revision`, one save at a time, each with the revision the last one returned (Appearance's queue). The status line and Undo match Appearance. Undo is a change of its own and isn't itself undoable. Undo inverts only that change's own delta, laid over the server's current map, so it never reverts another device's change merged in after a stale revision, or an earlier change that failed. After Undo, focus moves to the control the change was made with, because the Undo button removes itself (Appearance has the same gap; it's outside FX-3's paths, so it's flagged to the runner). This supersedes the interim Save/Cancel noted in `2026-10-23-S-keys.md` (§10.10.1 "Two save models").
- **B3: a remap that collides keeps the Swap / Cancel prompt.** `ShortcutsField` already calls `onchange` only on Swap, so nothing is sent until Swap is chosen; Cancel sends nothing (unit and keyboard e2e tests check both).
- **B3: the stale-revision merge, kept and made automatic.** With no Save to press again, a `stale_revision` reloads the section and re-sends once. The re-send carries only this change: the switch if this change touched it, and for remaps the change's own adds, changes and removals laid over the newer map (the same `rebase` as before). A second stale gives up, shows the newer settings and says it couldn't save, so a stale revision never overwrites newer settings. Deviation from the Fix: the report says "keep the stale-revision merge" without saying when it runs. Before, it re-ran when you pressed Save again; with nothing to press, it now re-sends once by itself. The stale message now reads "Changed in another tab or device too; both changes were kept."
- **B3: a refused save goes back.** A 422, a lock (409) or a failure re-reads the section and puts the screen and the registry back to the server's current values. The screen's own older copy could otherwise undo a change `boot.ts` had already applied from another device. That means the row a 422 names shows its saved key along with the server's message. Before this change it kept the unsaved edit to fix and Save again; now nothing is pending, so the screen shows what's actually saved.
- **I8 (Keyboard part):** the screen's `<h1>` uses `text-title` (`shortcuts.css`), the step the report picks for every Settings screen.
- **Strings:** the unused `shortcuts_save`, `shortcuts_cancel` and `shortcuts_nothing_to_save` keys are removed. `shortcuts_saved` now reads "Saved." and `shortcuts_undo` is added, both matching Appearance (en and zh, in the feature's own `messages/`). `shortcuts_save_failed` now matches Appearance's "Couldn't save that change…".
