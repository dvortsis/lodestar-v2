# SB-6b decisions

Follow-ups to SB-6's population contract (`docs/decisions/2026-11-04-SB-6.md`) from the runner's review of #415. They land before any producer raises a generation.

- **The swap never drains a population walk.** Its last catch-up, with no live indexer running, loops only while new torrents or `reindex_log` entries are left (`rebuild.rs` `swap_catch_up`). Before, it looped on `catch_up`, which counts backfilled torrents, so a `.building` directory resumed by a build with other generations ran its whole walk at the swap. A walk still open then advances at most one bounded batch per step there, and the new live indexer finishes it, with the field reported `Backfilling` until it does. `Rebuild::step` reports `backfilled` apart from `replayed`; the rebuild's progress counts it in `replayed`, as the live indexer's counters already do: a field of its own would mean editing `RebuildProgress` literals in `crates/lodestar/src/http.rs` and `crates/api/src/search.rs`, outside this slice. Whoever owns those can split it out if the rebuild banner should show the backfill on its own line.
- **A field name no index has is `Missing`,** not `Ready`, so a misspelled tracked field fails closed: `prefilter` never narrows by it. Names are checked against the index's own schemas, `file.<name>` against the file index's.
- **When both indexes walk, they walk in lockstep** from the lower cursor: each torrent is read from the store once and written to each index whose walk covers it, and only that torrent is held at a time. Metadata comes from untrusted peers (up to 16 MiB info dicts), so caching a batch of loaded torrents for the second walk could hold gigabytes; lockstep holds one.
