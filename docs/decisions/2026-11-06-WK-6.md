# WK-6 decisions (#539)

The `Results` and `Counters` payload codecs, `crates/pipeline/src/wire/` (architecture §19.2, §19.4, §19.8, §3; plan `docs/plan/2026-11-06-v06-workers.md` §4.3 and Q8).

- **A hand-written varint layout, not postcard.** Every byte is defined in the module docs, integers must be in their shortest form, and unknown flag bits refuse the record. Each payload therefore has one canonical form: whatever decodes re-encodes to the same bytes, which the fuzz target and property tests check. No new dependency. The frames that carry the payloads are still postcard and zstd (§19.2); these bytes are their opaque body.
- **Versioned and all-or-nothing.** The first byte is the format version (1). The decoder reads only that version and refuses the whole payload on any error, so a batch is never half-used. The pinned v1 bytes are in `crates/pipeline/tests/fixtures/wire/*.hex`; changing them needs a version bump. **A new payload version needs a protocol major bump, or a payload version in `Hello`'s capabilities that the coordinator checks:** `Hello` refuses only a different protocol major (`lodestar_cluster::proto`), so without one a worker on another payload version would join and then have every batch refused.
- **Bounds.** The payload is capped at the cluster protocol's opaque-body cap (`proto::MAX_OPAQUE`, 512 KiB) before anything is read. Every count is checked against its cap (1,024 records, 8,192 counters) and against what the bytes left could hold. Every length is checked against its cap (name 16 KiB, raw name 4 KiB, `torrent_extra` 64 KiB, composition 1 KiB, enrichment record 16 KiB; blob and raw dict only by the payload) before allocation. The encoders apply the same checks, so an over-cap batch is an error for the worker to split, never a frame the coordinator refuses.
- **`pieces` is never encoded, and that is checked on both sides.** `Prepared` has no `pieces` field. Both sides refuse a raw dict or `torrent_extra` that isn't a canonical bencoded dict without `pieces` (`info_without_pieces(b) == b`).
- **What a record carries:** the key (as a flag saying whether it is `info_hash` or the truncated v2 hash, so a record can't name a key that isn't one of its swarm hashes); the v1 and v2 hashes; the fencing token; the prepared row, file-tree blob (codec plus dictionary id, an id only with zstd), `torrent_extra` and enrichment; the sources the worker saw; the fetch time; the worker's action and rule-set version; the classification-rule fix; and the private-source and always-adult marks. A batch has an id (for idempotent replay, §19.2, WK-11) and no key twice.
- **What it leaves out (a refinement of the §19.4 list, flagged under §2.19):**
  - **The worker id.** The coordinator takes it from the authenticated mTLS session, never from bytes the worker chose.
  - **The first source.** The coordinator's lease holds it (§19.3).
  - **The decoded file list and the in-memory `Classification`.** The coordinator re-judges every remote result (§19.4, `writer.rs`). It rebuilds both from the blob and the name (WK-9), so the verdict never rests on a classification the worker supplied, and the file list isn't sent twice. What is stored must not rest on it either: see the enrichment requirement for WK-9 below.
  - **The verdict's rule reference and evidence.** Only the action and the rule version go; WK-8 adds what its marks need (plan §4.2 gives it a line in `wire/mod.rs`).
- **The row is what a local `Preparer` could have produced.** Each of the five row integers must fit an SQLite integer (`≤ i64::MAX`). A larger one would fail the coordinator's whole write transaction, so one bad record could make a whole batch fail every time it's sent. The torrent flags may only be those derived from the info dict (`PRIVATE`, `V2`, `HYBRID`, `PADDING`, `SYMLINKS`, `SINGLE_FILE`, `WARNINGS`). `V2` must be set exactly when there's a v2 hash, and `HYBRID` exactly when that hash's truncation isn't `info_hash`. A worker can't set `HIDDEN`, `DEMOTED`, `FLAGGED`, `IMPORTED`, `BACKFILL`, `FILES_PARTIAL` or `PRIVATE_SOURCE`: those are the coordinator's, and a filter mark without its `filter_hits` row couldn't be explained (§20). A dictionary id is never negative, and an empty `torrent_extra` (`de`) is refused, since `Preparer` leaves it out. A raw name must decode to `name` under its encoding, and is kept only when the name isn't plain UTF-8, as `Preparer` does.
- **Enrichment is range-checked always and fully checked for this build's version.** The content type must be a known code and the junk score at most 100. With this build's `ENRICHMENT_VERSION`, the composition and record must also decode and agree with the hot columns. Another version passes the codec: `Hello` refuses only a different protocol major, so a worker one parser bump behind is normal, and refusing its enrichment would refuse every batch it sends. **Passing the codec doesn't make it safe to store:** WK-9 must not store a worker's enrichment as sent, of any version (below).
- **Counters** carry `(hour, metric, dim, key, value)` in strictly ascending key order. The encoder sorts and sums duplicates; the decoder refuses unordered or repeated keys. Only metrics that aggregate as a sum are admitted: the `SEARCHABLE` gauge can't be added up, and an unknown code is refused. Each delta (and each sum within a batch) must be in `1..=2^40`, and each hour in `0..=i32::MAX`. **These bound one batch only.** Across batches, a worker can add up to 2^40 to the same row again and again: `rollup_hour.value` is a STRICT INTEGER summed as `value + excluded.value`, so after about 2^23 such batches the sum leaves the integer range and every later write to that row fails. Worker-chosen hours and keys also make up to 8,192 new rows per batch, against the rollups budget (owner §1.6.4: ≤ 50 MB a year). The intake's rules below close both. Which of those metrics a worker may send (never `HARVESTED`, which the coordinator counts at grant, §19.3) is also the intake's rule.
- **Size (§19.8 budget, plan Q8).** Golden corpus: `crates/pipeline/tests/fixtures/wire/corpus.txt`, 40 real-shaped torrents with invented names (single-file videos, seasons, albums, software, packs and a 2,048-file dataset). Each record is encoded alone in a batch, header included, and before frame compression. Results:
  - **`archive_raw` off (the default, gated ≤ 3 KB):** median 365 B, p95 710 B, max 1,491 B.
  - **`archive_raw` on (reported):** median 660 B, p95 21,572 B. The uncompressed raw dict of the large packs dominates the p95; frame zstd shrinks it.
  - **Both figures are conservative in one way and generous in another.** The test store has no trained file-tree dictionary, which makes the blob larger. The corpus's patterned file names compress better than real ones, which makes it smaller. The median is set by single-file torrents, whose cost is mostly the name and the hashes, so the margin to 3 KB is wide either way.
- **Requirements on the intake (WK-9, with WK-8 for the dictionary).** The codec checks shape, not truth, and can't see the coordinator's state. A record or counter that passes it can still lie, so WK-9 must do these per record or counter, before the commit:
  - **Store the coordinator's own enrichment, never the worker's (content safety).** Search's `type:adult` term and `adult:` tags come from the stored enrichment (`crates/search/src/doc.rs`). A worker that sends content type Movie for adult content, with a matching classification fix, would otherwise have it shown with "Show adult content" off. Today `rejudge` re-enriches only when the fix differs (`writer.rs`), and re-verification samples only 0.5% (WK-13). So for **every** remote record WK-9 must do one of two things. Either it stores the enrichment it rebuilds with `enrich_infos` from the name and the rebuilt file list, which it already needs for the re-judge. Or it refuses the record when the worker's content type or adult kind differs from the rebuilt one. That covers every enrichment version: one from another version is rebuilt the same way, not kept until the background re-enrich, so no record is stored with a worker's classification even briefly. The codec carries no hook for this, since the rebuild needs the coordinator's classifier and rules.
  - **Bound what counters can do to the rollups.** Accept only hours within a window around the coordinator's own clock, after correcting for the worker's offset. Accept only dims and keys from each metric's own domain (the strategy, stage and loss codes `rollups::metric` documents). Cap or saturate what a row accumulates, so no sum leaves the integer range.
  - **Take provenance from the lease.** For a leased record, `sources` and `private_source` merge with the coordinator's lease, which is authoritative (§19.3, Q7), not as the worker sent them (`writer.rs` keeps them today). `metadata_at` is corrected by the worker's clock offset (§19.3).
  - **Check the row's counts.** `size` and `file_count` must match the rebuilt file list; a mismatch refuses the record.
  - **An unknown dictionary id** fails `Store::write` for the whole transaction (`Error::Corrupt`). Check it against the coordinator's dictionaries per record (WK-8's gate) and refuse that record alone.
  - **Decompressing a worker's blob** to rebuild the file list is capped only by the store's 1 GiB per blob (`compress::MAX_DECOMPRESSED`). Up to 1,024 small blobs in one 512 KiB payload could each claim that much, so the intake needs a far tighter cap derived from metainfo's file and path limits.
  - **A raw dict sent while the coordinator's `archive_raw` is off** is dropped, not stored: Q8 follows the coordinator's setting.
  - **Swarm hashes other than the key** (a hybrid's other hash) come from the worker. The flag checks above stop a record claiming a v2 hash without being a hybrid, but not one naming another stored torrent's v2 hash. A remote record matching a stored torrent only by a non-key hash shouldn't upgrade that torrent.
  - **An `Action::Drop` on the wire** is accepted for now. WK-8 (plan Q1) decides whether a drop may ever be sent.
- **Fuzzing.** `fuzz/fuzz_targets/cluster_results.rs` covers both decoders, seeded with the pinned payloads (`fuzz/seeds/cluster_results/`). It ran 10 minutes clean with `-malloc_limit_mb=64` before the PR. Running it needs `lodestar-pipeline` as a dependency of the fuzz crate (one line in `fuzz/Cargo.toml` and its entry in `fuzz/Cargo.lock`), which WK-8's target reuses. The runner approved these four paths for WK-6 (2026-11-06): the `[[bin]]` and dependency lines in `fuzz/Cargo.toml`, `fuzz/Cargo.lock` as cargo regenerated it (one `lodestar-pipeline` entry, no new external package), one `fuzz/README.md` row and the two seeds. They are in WK-6's `owns` in `runner/slices.yaml`.
