# WK-6 decisions (PR pending)

The `Results` and `Counters` payload codecs, `crates/pipeline/src/wire/` (architecture §19.2, §19.4, §19.8, §3; plan `docs/plan/2026-11-06-v06-workers.md` §4.3 and Q8).

- **A hand-written varint layout, not postcard.** Every byte is defined in the module docs, integers must be in their shortest form, and unknown flag bits refuse the record. Each payload therefore has one canonical form: whatever decodes re-encodes to the same bytes, which the fuzz target and property tests check. No new dependency. The frames that carry the payloads are still postcard and zstd (§19.2); these bytes are their opaque body.
- **Versioned and all-or-nothing.** The first byte is the format version (1). The decoder reads only that version and refuses the whole payload on any error, so a batch is never half-used. The pinned v1 bytes are in `crates/pipeline/tests/fixtures/wire/*.hex`; changing them needs a version bump.
- **Bounds.** The payload is capped at the cluster protocol's opaque-body cap (`proto::MAX_OPAQUE`, 512 KiB) before anything is read. Every count is checked against its cap (1,024 records, 8,192 counters) and against what the bytes left could hold. Every length is checked against its cap (name 16 KiB, raw name 4 KiB, `torrent_extra` 64 KiB, composition 1 KiB, enrichment record 16 KiB; blob and raw dict only by the payload) before allocation. The encoders apply the same checks, so an over-cap batch is an error for the worker to split, never a frame the coordinator refuses.
- **`pieces` is never encoded, and that is checked on both sides.** `Prepared` has no `pieces` field. Both sides refuse a raw dict or `torrent_extra` that isn't a canonical bencoded dict without `pieces` (`info_without_pieces(b) == b`).
- **What a record carries:** the key (as a flag saying whether it is `info_hash` or the truncated v2 hash, so a record can't name a key that isn't one of its swarm hashes); the v1 and v2 hashes; the fencing token; the prepared row, file-tree blob (codec plus dictionary id, an id only with zstd), `torrent_extra` and enrichment; the sources the worker saw; the fetch time; the worker's action and rule-set version; the classification-rule fix; and the private-source and always-adult marks. A batch has an id (for idempotent replay, §19.2, WK-11) and no key twice.
- **What it leaves out (a refinement of the §19.4 list, flagged under §2.19):**
  - **The worker id.** The coordinator takes it from the authenticated mTLS session, never from bytes the worker chose.
  - **The first source.** The coordinator's lease holds it (§19.3).
  - **The decoded file list and the in-memory `Classification`.** The coordinator re-judges every remote result (§19.4, `writer.rs`). It rebuilds both from the blob and the name (WK-9), so the verdict never rests on a classification the worker supplied, and the file list isn't sent twice. The stored enrichment is still the worker's as sent (`rejudge` re-enriches only when the classification fix differs); WK-9 decides whether to compare it with what the coordinator rebuilt, and WK-13's re-verification sampling checks it.
  - **The verdict's rule reference and evidence.** Only the action and the rule version go; WK-8 adds what its marks need (plan §4.2 gives it a line in `wire/mod.rs`).
- **The row is what a local `Preparer` could have produced.** Each of the five row integers must fit an SQLite integer (`≤ i64::MAX`). A larger one would fail the coordinator's whole write transaction, so one bad record could make a whole batch fail every time it's sent. The torrent flags may only be those derived from the info dict (`PRIVATE`, `V2`, `HYBRID`, `PADDING`, `SYMLINKS`, `SINGLE_FILE`, `WARNINGS`). `V2` must be set exactly when there's a v2 hash, and `HYBRID` exactly when that hash's truncation isn't `info_hash`. A worker can't set `HIDDEN`, `DEMOTED`, `FLAGGED`, `IMPORTED`, `BACKFILL`, `FILES_PARTIAL` or `PRIVATE_SOURCE`: those are the coordinator's, and a filter mark without its `filter_hits` row couldn't be explained (§20). A dictionary id is never negative, and an empty `torrent_extra` (`de`) is refused, since `Preparer` leaves it out.
- **Enrichment is range-checked always and fully checked for this build's version.** The content type must be a known code and the junk score at most 100. With this build's `ENRICHMENT_VERSION`, the composition and record must also decode and agree with the hot columns. Any other version is kept as sent: `Hello` refuses only a different protocol major, so a worker one parser bump behind is normal, and the store re-enriches any `parser_ver` but its own in the background (`Store::unenriched`). Refusing it would refuse every batch from such a worker.
- **Counters** carry `(hour, metric, dim, key, value)` in strictly ascending key order. The encoder sorts and sums duplicates; the decoder refuses unordered or repeated keys. Only metrics that aggregate as a sum are admitted: the `SEARCHABLE` gauge can't be added up, and an unknown code is refused. Each delta (and each sum) must be in `1..=2^40`, so adding deltas in the rollups can't overflow, and each hour in `0..=i32::MAX`. Which of those metrics a worker may send (never `HARVESTED`, which the coordinator counts at grant, §19.3) is the intake's rule (WK-9), not the codec's.
- **Size (§19.8 budget, plan Q8).** Golden corpus: `crates/pipeline/tests/fixtures/wire/corpus.txt`, 40 real-shaped torrents with invented names (single-file videos, seasons, albums, software, packs and a 2,048-file dataset). Each record is encoded alone in a batch, header included, and before frame compression. Results:
  - **`archive_raw` off (the default, gated ≤ 3 KB):** median 365 B, p95 710 B, max 1,491 B.
  - **`archive_raw` on (reported):** median 660 B, p95 21,572 B. The uncompressed raw dict of the large packs dominates the p95; frame zstd shrinks it.
  - **Both figures are conservative in one way and generous in another.** The test store has no trained file-tree dictionary, which makes the blob larger. The corpus's patterned file names compress better than real ones, which makes it smaller. The median is set by single-file torrents, whose cost is mostly the name and the hashes, so the margin to 3 KB is wide either way.
- **Left to the intake (WK-9, with WK-8 for the dictionary).** The codec can't see the coordinator's state, so these are WK-9's to handle per record, before the commit:
  - **An unknown dictionary id** fails `Store::write` for the whole transaction (`Error::Corrupt`). Check it against the coordinator's dictionaries per record (WK-8's gate) and refuse that record alone.
  - **Decompressing a worker's blob** to rebuild the file list is capped only by the store's 1 GiB per blob (`compress::MAX_DECOMPRESSED`). Up to 1,024 small blobs in one 512 KiB payload could each claim that much, so the intake needs a far tighter cap derived from metainfo's file and path limits.
  - **A raw dict sent while the coordinator's `archive_raw` is off** is dropped, not stored: Q8 follows the coordinator's setting.
  - **Swarm hashes other than the key** (a hybrid's other hash) come from the worker. The flag checks above stop a record claiming a v2 hash without being a hybrid, but not one naming another stored torrent's v2 hash. A remote record matching a stored torrent only by a non-key hash shouldn't upgrade that torrent.
  - **An `Action::Drop` on the wire** is accepted for now. WK-8 (plan Q1) decides whether a drop may ever be sent.
- **Fuzzing.** `fuzz/fuzz_targets/cluster_results.rs` covers both decoders, seeded with the pinned payloads (`fuzz/seeds/cluster_results/`). It ran 10 minutes clean with `-malloc_limit_mb=64` before the PR. Running it needs `lodestar-pipeline` as a dependency of the fuzz crate (one line in `fuzz/Cargo.toml` and its entry in `fuzz/Cargo.lock`), which WK-8's target reuses. The runner approved these four paths for WK-6 (2026-11-06): the `[[bin]]` and dependency lines in `fuzz/Cargo.toml`, `fuzz/Cargo.lock` as cargo regenerated it (one `lodestar-pipeline` entry, no new external package), one `fuzz/README.md` row and the two seeds. They are in WK-6's `owns` in `runner/slices.yaml`.
