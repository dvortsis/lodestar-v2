# X-rusqlite-041 decisions

Runner brief X-rusqlite-041, 2026-11-21: close RUSTSEC-2026-0459, which `deny.toml` had ignored since X-ci-advisories as "narrowed, not closed" (review by 2026-12-13). This is a security dependency fix.

## What changed

- **rusqlite 0.40.2 → 0.41.1** in `crates/store` and `crates/sources-importers`, with the same features: `bundled`, plus `hooks` and `limits` for the importer.
  - `Cargo.lock` holds exactly one rusqlite (0.41.1) and one libsqlite3-sys (0.39.1). No other crate names rusqlite directly; the rest reach SQLite through the store.
  - The bundled SQLite moves from 3.53.2 to 3.54.1.
  - rusqlite 0.41 declares Rust 1.89, the workspace's `rust-version`.
- **The ignore is gone.** `deny.toml`'s `ignore` list is now empty. `cargo deny --locked check advisories` (cargo-deny 0.20.2, CI's pin and command) prints `advisories ok`.
  - **Control:** the same `deny.toml` against `main`'s lockfile fails with RUSTSEC-2026-0459. So the bump, not a change to the check, is what closes it.
- **The one code change the bump needs** is in `crates/sources-importers/src/magnetico.rs`. rusqlite 0.41's `Connection::progress_handler` takes `&mut self`, so `harden` takes `&mut Connection`, and the Magnetico source's connection is bound `mut`.
  - The handler, its 10,000-step interval and its stop conditions (a cancel, or the batch deadline) are unchanged.
  - Nothing else in the workspace needed editing.
- **`unsafe` is unchanged.** lodestar-store's SQLite memstats, the workspace's one `unsafe` exception, calls `sqlite3_memory_used` and `sqlite3_memory_highwater` through `rusqlite::ffi`. Those compile unchanged against libsqlite3-sys 0.39, so the exception isn't widened, and there's no new `unsafe` anywhere.

## The advisory, re-read

- **The vulnerability:** CVE-2026-119375 (GHSA-72w2-rjgg-q729). SQLite before 3.54.0 can return uninitialized page-cache memory when a process opens a database together with a `-wal` whose page size differs from the database's. A crafted pair of files can make ordinary queries return stale bytes from the process's memory.
- **The fix:** libsqlite3-sys 0.39.0 and 0.39.1 bundle SQLite 3.54.0 and 3.54.1, which fix it (patched `>= 0.39.0`).
- **Not used here:** the `bundled-sqlcipher` feature is still affected in 0.39 (SQLCipher bundles SQLite 3.53.4), and Lodestar doesn't use it. A build against a system SQLite would take the system library's exposure; Lodestar's builds use `bundled`.
- **The importer's `-wal`/`-journal` refusal stays, as the brief requires.** With the fix, a crafted `-wal` can no longer expose memory, so the stat check is no longer the advisory's mitigation. It's still needed for what it was named for (`quiescent`, `Refusal::NotQuiescent`):
  - a non-empty `-wal` or a `-journal` means magneticod may still be writing, or left an unfinished transaction;
  - SQLite would replay that `-wal` even on a read-only open, so the import could read a database other than the one checked.

  It's still a stat, not atomic with SQLite's read. That's acceptable for a quiescence check, which is what it now is.

## The on-disk format, shown unchanged

There's no checked-in fixture database, so two scratch programs outside the repo, one built against each revision's `lodestar-store`, checked it both ways:

- **The programs:** each opens a store with `Store::open` and `StoreConfig::default()`. In `write` mode it inserts three torrents (v1, a hybrid v2 with a file tree, and another v1, with raw info dicts). It then prints the count, each row (id, name, info hash, size, pieces, files), `PRAGMA user_version`, `PRAGMA integrity_check` and every `sqlite_master` entry.
- **A database written by `main`** (rusqlite 0.40.2, SQLite 3.53.2) **opened by this branch** (0.41.1, SQLite 3.54.1) prints output identical to what `main` printed: the same 3 rows, `integrity_check` `ok`, and the same 101 schema objects.
- **The reverse:** a database written by this branch, opened by `main`'s build, also prints output identical to its writer's. A rollback reads it. The two writers' schemas are identical.
