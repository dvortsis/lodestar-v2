# F-updater decisions (DUR-26)

Contract for updater acknowledgment semantics, as `docs/plan/2026-10-27-persistence-and-import-audit.md` ("Updater acknowledgment semantics (DUR-26)") requires before implementation. Refines architecture §12.2 and `docs/decisions/2026-10-26-soak-updater-order.md`, whose "best-effort persistence" bullet this supersedes. No install, rollback, policy-eligibility, scheduling or UI change.

## API contract
- **A fixed persistence-failure code: `updates_not_saved`, HTTP 500.** `UpdatesError::NotSaved` in `crates/api/src/updates.rs`, in the existing `{ "error": { "code", "message" } }` envelope. The code is the stable key the UI localizes. The message is one fixed English sentence: "Lodestar couldn't save this change, so it may not survive a restart. Check that its data folder has free space and can be written, then try again." It never carries a path, an OS error or any I/O text; the cause goes to the log by error kind only. 500 because the request was valid and the server failed to persist it; a distinct code (not `internal`) so the UI can say what happened. Not 503: that already means "no update engine".
- **Routes that return it:** `POST /updates/pause` (pause and resume, `days: 0`), `POST /updates/skip` and `POST /updates/history/clear`, whenever the state file they change couldn't be written, flushed or renamed into place (or removed, for history). `POST /updates/check` doesn't: a check that can't save its timestamps still succeeded as a check (below). `skip`'s existing `409 bin_unavailable` stays for "no `<data>/bin` at all". A pause or resume with no `<data>/bin` is `updates_not_saved` (it used to be acknowledged in memory only, the bug this slice fixes).
- **A process-only hold: `policy.held_in_process: bool`** (required, false normally). True after a failed pause, until a later explicit pause or resume is saved. While true, every release carries `blocked_by: { code: "held" }` and none is `eligible`, so automatic installs are held in this process. `policy.paused_until` keeps showing the last *durable* pause only; the hold is never shown or written as a durable pause. The UI says the pause wasn't saved and that updates are held only until Lodestar restarts.
- **Unsaved check timestamps: notice `check_not_saved`.** When a check's `checked_at`/`next_check_at`/`error` couldn't be written, `status` still shows them (the schedule must not check back to back), and `notices` gains `check_not_saved` so they're never presented as persisted.
- **Unsupported platforms unchanged.** Windows and fixtures keep `unavailable` and `409 updates_unavailable` on every write. No in-memory imitation of updater support; `held_in_process` is false there.

## Engine semantics
- **One serialized mutation path.** Under the existing updater mutex: clone the last durable `updater.json`, apply the mutation, write it atomically (temporary file, write, fsync, rename, folder fsync), and only then publish it as durable and acknowledge. Any failure returns the typed error and leaves the durable state, and the file on disk, as they were. `skip` and `history/clear` run under the same mutex, so concurrent writes never interleave.
- **Failed pause:** the request fails with `updates_not_saved` and the hold turns on. **Failed resume:** fails, keeps the durable pause and any hold. **A later successful pause or resume** is a new, separately acknowledged outcome and clears the hold. Nothing retries a failed save in the background, so no failed request is ever acknowledged later.
- **Background check timestamps** use the same writer. On failure they stay as transient values overlaid on the durable state; the next durable write starts from the durable state, so a transient check can never overwrite a durable pause, and a successful check write clears the overlay.
- **Folder fsync failure counts as a failed save.** After the rename the new file may be visible but not durable; reporting success would claim durability we don't have. A pause that fails this way may still be found on disk after a restart, which errs toward paused.
- **Fault injection for tests:** the atomic write takes a private step hook (write, flush, rename) so tests fail each step against the real file sequence, including a half-written temporary file that's never loaded.
