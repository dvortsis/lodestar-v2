# F-updater decisions (DUR-26)

Contract for updater acknowledgment semantics, OK'd by the runner on 2026-10-30 with three changes (folded in below: no-bin pause, the hold in the policy function, the folder-fsync residual), as `docs/plan/2026-10-27-persistence-and-import-audit.md` ("Updater acknowledgment semantics (DUR-26)") requires before implementation. Refines architecture §12.2 and `docs/decisions/2026-10-26-soak-updater-order.md`, whose "best-effort persistence" bullet this supersedes. No install, rollback, scheduling or UI change, and no policy-eligibility change beyond the hold.

## API contract
- **A fixed persistence-failure code: `updates_not_saved`, HTTP 500.** `UpdatesError::NotSaved` in `crates/api/src/updates.rs`, in the existing `{ "error": { "code", "message" } }` envelope. The code is the stable key the UI localizes. The message is one fixed English sentence: "Lodestar couldn't save this change, so it may not survive a restart. Check that its data folder has free space and can be written, then try again." It never carries a path, an OS error or any I/O text; the cause goes to the log by error kind only. 500 because the request was valid and the server failed to persist it; a distinct code (not `internal`) so the UI can say what happened. Not 503: that already means "no update engine".
- **Routes that return it:** `POST /updates/pause` (pause and resume, `days: 0`), `POST /updates/skip` and `POST /updates/history/clear`, whenever the state file they change couldn't be written, flushed or renamed into place (or removed, for history). `POST /updates/check` doesn't: a check that can't save its timestamps still succeeded as a check (below). **No `<data>/bin` at all is `409 bin_unavailable`** on pause and resume as on skip (runner): it's a capability gap that retrying won't fix, nothing installs without `bin`, so it turns on no hold. The old in-memory-only acknowledgement is gone either way.
- **A process-only hold: `policy.held_in_process: bool`** (required, false normally). True after a failed pause, until a later explicit pause or resume is saved. While true, every release carries `blocked_by: { code: "held" }` and none is `eligible`, so automatic installs are held in this process. **It's enforced where eligibility is decided** (runner): `update::policy::plan`, through `Inputs::held_in_process` and `Block::Held`, the single function `/updates` uses and the install path (B-update 5/5) must call, so 5/5 inherits the hold. A held release has no `installs_at`, and `Plan::next` is `None`. `policy.paused_until` keeps showing the last *durable* pause only; the hold is never shown or written as a durable pause. The UI says the pause wasn't saved and that updates are held only until Lodestar restarts.
- **Unsaved check timestamps: notice `check_not_saved`.** When a check's `checked_at`/`next_check_at`/`error` couldn't be written, `status` still shows them (the schedule must not check back to back), and `notices` gains `check_not_saved` so they're never presented as persisted.
- **An unreadable `updater.json` fails closed (refinement under owner-decisions §2.19: OK'd by the runner on 2026-10-30, which flags it to the owner).** A file that's there but can't be read at start (damage, a permission problem after a restore, EIO) may hold a pause, so the engine doesn't start unpaused: `held_in_process` is true, notice `updater_unreadable`, log event `update.state_unreadable` (error kind only), and a check's times stay in memory rather than writing over the file. Only an explicit pause or resume that's saved replaces the file and ends the hold; the notice's documentation says so, so the Updates screen (S-updates, not built yet) can tell the user what to do. The next start then reads the new file normally (tested). Before, the first check after such a start erased the pause, the same lost-pause outcome DUR-26 is about.
- **An unreadable skip list stays damage, not a failed save:** `POST /updates/skip` keeps its old `500 internal` for it, so `updates_not_saved` and its "free space" advice mean only a failed write.
- **History clear with no `<data>/bin` stays `200`:** there's no history to clear, so nothing was refused.
- **Unsupported platforms unchanged.** Windows and fixtures keep `unavailable` and `409 updates_unavailable` on every write. No in-memory imitation of updater support; `held_in_process` is false there.

## Engine semantics
- **One serialized mutation path.** Under the existing updater mutex: clone the last durable `updater.json`, apply the mutation, write it atomically (temporary file, write, fsync, rename, folder fsync), and only then publish it as durable and acknowledge. Any failure returns the typed error and leaves the durable state, and the file on disk, as they were. `skip` and `history/clear` run under the same mutex, so concurrent writes never interleave.
- **Failed pause:** the request fails with `updates_not_saved` and the hold turns on. **Failed resume:** fails, keeps the durable pause and any hold. **A later successful pause or resume** is a new, separately acknowledged outcome and clears the hold. Nothing retries a failed save in the background, so no failed request is ever acknowledged later.
- **Background check timestamps** use the same writer. On failure they stay as transient values overlaid on the durable state; the next durable write starts from the durable state, so a transient check can never overwrite a durable pause, and a successful check write clears the overlay.
- **Folder fsync failure counts as a failed save.** After the rename the new file may be visible but not durable; reporting success would claim durability we don't have. **The residual, accepted by the runner:** the renamed file may still be found after a restart. A pause that fails this way errs toward paused. A *resume* that fails this way may come back resumed after a restart, the opposite of "a failed resume keeps the durable pause"; in this process the pause is kept, and the response already says the change may not survive a restart. It needs the rename to succeed and the folder fsync alone to fail, which is rare. Tests cover both directions. **Skip and history clear share the residual, and show it at once:** those files aren't cached but read from disk, so a skip or clear refused this way is already in effect in this process too. The routes' `500` descriptions say so ("may already be in effect"), and a test covers it.
- **Fault injection for tests:** `Bin::write_acknowledged` and `Bin::remove_acknowledged` take a step hook (`layout::Step`: write, flush, rename, folder fsync) so tests fail each step against the real file sequence; a failed write leaves half the temporary file before failing. Production passes `|_| Ok(())`. The supervisor's own writes (`Bin::write`, `pending::skip`) are unchanged.
- **Logging:** a new event `update.state_unsaved` (Warn) logs the file's name and the error's kind (`StorageFull`, `PermissionDenied`, …), never a path or OS text; `update.state_unreadable` (Warn) logs the kind for an unreadable `updater.json` at start.
- **One snapshot per response:** `status()` reads the durable pause and the hold once and passes them to `policy::plan` (`Engine::plan_with`), so `held_in_process` and the releases' `held` blocks always agree.
- **Check timestamps are saved off the async workers** (the write fsyncs under the mutex), through the engine's `blocking` helper.
- **Nonzero selected Unix test counts (the spec's last fixture):** the runner extended this slice's ownership to one step in `.github/workflows/ci.yml`: in the `test` job on Linux, after `cargo test --workspace`, `cargo test -p lodestar --bin lodestar update:: -- --list` must list at least one test. Locally on Linux the updater selection runs 85 tests (`update::`), 27 of them in `update::engine`.
- **Unix only.** The engine and these tests compile only on Unix; Windows tests assert the unavailable capability (`update::unavailable`), not persistence.
