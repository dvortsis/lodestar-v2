# S-updates decisions (Settings → Updates, part 1)

Spec: `docs/architecture.md` §10.10.14, §12.2. No owner decision is changed. Everything below is a runner-level refinement, named in the PR description (`docs/owner-decisions.md` §2.19).

- **A hand-built screen, not the form engine.** The `updates` settings section holds `mode`, `level` and `security_fixes`, but the screen needs the server's effective state (`GET /updates`) beside them, a confirmation per action, and per-control reset to the server's value after a refusal. It reads and writes the section itself (`GET`/`PATCH /settings/updates`, with `if_revision`), and a field set by an environment variable or read-only is disabled with the variable named.
- **Control state is the server's.** A refused or failed change puts every radio and toggle back on the server's value and shows an error; "up to date" appears only when the last check's `state` is `ok` with a `checked_at`, otherwise "not checked yet" or the check's error code. Nothing is preselected: Off stays Off, and the screen says that checking contacts GitHub.
- **Security fixes toggle** shows `policy.security_fixes` (the effective value); before the server has said, the mode's default (on under automatic, off under Check and notify). It is hidden under Off and Container image updates.
- **Container image updates** is offered when `GET /system` says `deployment.kind` is `docker` or `unraid` (or when it is already the saved mode).
- **Notices:** `revoked_key`, `trust_damaged`, `clock_behind`, `clock_ahead`, `updater_unreadable`, `check_not_saved`, plus `policy.held_in_process` (the third F-updater notice), and the other codes `GET /updates` documents (`pending_unwritable`, `bad_overlay`, `manifest_lapsed`, `channel_unavailable`) get a plain line each. `rolled_back` is explained in the status area from the newest rolled-back history entry.
- **Dates use `Intl` directly (`updates/time.ts`)** rather than `$lib/format`: importing the format module from a Settings screen splits the chunk that Discover, Detail and `/t/[hash]` share and cost them 138–160 B each (the same reason as Security's `date.ts`).
- **Clear history** (`POST /updates/history/clear`) is included, behind the same confirmation dialog, since the API exists and the history table is on the screen.

## Slots left for part 2 (and what is missing)

- **Install now:** the API has no install request (`/updates` has `check`, `pause`, `skip`, `history/clear` only). The button is not rendered, so damaged trust data trivially cannot offer it; when the endpoint exists, the button goes beside Check now and must stay hidden while `trust_damaged` is a notice or the capability reason.
- **Advanced** (channel dialog, wait, window, index rebuilds, notification choices), **Roll back** in the Danger zone, the Overview's Needs attention entries, the status pill's "Updating…", the restart overlay and the wizard's Updates step hookup.
- The install progress list is driven by the `updates` SSE topic (`downloading` → `checking_health`); the byte progress (`bytes_done`) is not shown yet.

## Sizes (gzip, measured)

- Updates first view: 33.68 KB (limit 45 KB, 11.3 KB headroom). Release notes and history: 2.91 KB on demand (limit 3.2 KB). Icon and purpose line: 722 B (limit 0.8 KB).
- Other Settings first views grow by the registry entry only: 115–123 B each (title in en and zh, `iconLoad`, `about`, `load`).
- No limit was raised. Alert, Alerts, Search results and Results toolbar moved 2–6 B because chunk hashes in the preload lists changed with the new chunks; no code was added to their chunks.
