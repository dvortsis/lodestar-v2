# P-v06-rulepacks decisions

The planning slice for the second half of E-v06-sources: curated rule packs and ThePornDB/StashDB enrichment (build-plan P4 "Filters"). The plan is `docs/plan/2026-11-04-v06-rulepacks.md`. These are the plan's own structural choices, made under §2.19. Every product question (Q1–Q15) stays open in plan §5 until the runner or the owner answers it; none is decided here. No owner decision, security or content-safety decision, or owner-set number changes.

- **Two id families: `RP-*` for packs, `ENR-*` for enrichment.** They share no files and can be scheduled and gated separately (RP-G, ENR-G). `ENR-*` is generic enough for later enrichment plugins; v0.7's TMDB and friends can take `ENR-9` onwards.
- **The packs stay compiled in.** They're Rust today (`crates/filter/src/packs.rs`), and the signed release manifest (§12.2) covers them. The plan adds versions and changelogs on top rather than turning packs into a data format, which would mean a new parser of signed, untrusted input and a trust model the owner hasn't chosen. Whether a between-release channel is wanted is plan Q1, for the owner.
- **`packs.rs` becomes a `packs/` module in RP-0,** so SP-3, SP-4 and the overrides each get a file of their own. The engine slices still share `packs/mod.rs`, `engine.rs` and `writer.rs`, so they're chained (RP-0 → RP-2 → RP-4 → RP-5) rather than run in parallel. That costs wall-clock time on the pack path, but it's cheaper than conflicts in the filter engine, which is correctness-critical and has the owner's 50 µs budget.
- **No migration, proposed** (plan §3, Q9). Everything fits existing tables: `settings` rows as #367 did (`filter.stand_ins`), V14's `torrent_claims` and `source_state`. V15 stays reserved for CR-3 (runner-state `migration_order`), and no whole-store snapshot is taken for this epic.
- **Enrichment results are stored as claims, with claim encoding version 2** (ENR-0). Claims already have purge, snapshot purge, `secure_delete`, filter-before-storage and the refile sweep (SRC-1, SRC-2, SRC-14b). A separate table would have to rebuild each of those guarantees.
- **ENR-1 depends on SRC-13,** the first enrichment plugin, so the enrichment hook into the pipeline is designed once. ENR-1 must not edit `crates/pipeline/src/writer.rs`, which RP-4 and RP-5 own in turn.
- **SP-3 is judged in the writer only.** Its rate state depends on order, and prepare runs in parallel on workers (§19.4), so judging it in prepare would make verdicts depend on timing.
- **FK-3 stays out of v0.6** (plan Q6, for the runner): it needs TMDB release dates, a v0.7 enrichment (§18.3).
- **Routing.** Q1–Q5 go to the owner: Q1 is a signing and trust choice, Q2 a privacy one, and Q3–Q5 are content-safety and adult-content scope, as the brief asks. Q6–Q15 are the runner's (UX, performance, store design, numbers under §2.26). Owner §2.28 covered only the questions open on 2026-11-02, so it doesn't answer these.
- **Brief rule kept:** this slice doesn't edit `runner/slices.yaml` or `runner/dashboard.yaml`. Plan §4.1 holds the entries ready to paste, and the three new `ext:owner-rpq*` conditions the runner adds.
