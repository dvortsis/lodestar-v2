# P-v06-rulepacks decisions (#412)

The planning slice for the second half of E-v06-sources: curated rule packs and ThePornDB/StashDB enrichment (build-plan P4 "Filters"). The plan is `docs/plan/2026-11-04-v06-rulepacks.md`. These are the plan's own structural choices, made under §2.19. Every product question (Q1–Q16) stays open in plan §5 until the runner or the owner answers it; none is decided here. No owner decision, security or content-safety decision, or owner-set number changes.

- **Two id families: `RP-*` for packs, `ENR-*` for enrichment.** They share no files and can be scheduled and gated separately (RP-G, ENR-G). `ENR-*` is generic enough for later enrichment plugins; v0.7's TMDB and friends can take `ENR-9` onwards.
- **The packs stay compiled in.** They're Rust today (`crates/filter/src/packs.rs`), and the signed release manifest (§12.2) covers them. The plan adds versions and changelogs on top rather than turning packs into a data format, which would mean a new parser of signed, untrusted input and a trust model the owner hasn't chosen. Whether a between-release channel is wanted is plan Q1, for the owner.
- **`packs.rs` becomes a `packs/` module in RP-0,** so SP-3, SP-4 and the overrides each get a file of their own. The engine slices still share `packs/mod.rs`, `engine.rs` and `writer.rs`, so they're chained (RP-0 → RP-2 → RP-4 → RP-5, with RP-5 also after RP-3 for the release hook) rather than run in parallel. That costs wall-clock time on the pack path, but it's cheaper than conflicts in the filter engine, which is correctness-critical and has the owner's 50 µs budget.
- **A pack change in a release is a pending change, not applied at start.** §20.10 (owner §1.8.7) names "accepting a signed update" among the changes previewed before they take effect. Packs are code, so the release keeps the previous version of each changed rule beside the new one: the old one applies, the new one runs in shadow for the preview, and acceptance switches them. Applying on start instead would loosen §1.8.7, so it isn't offered.
- **A rule an install has never applied is pending as well,** so an upgrade that adds SP-3, SP-4 or SC-2's own id is previewed and accepted like a version bump (runner review of #412). Fresh installs and the wizard take current versions.
- **Each pack-rule version records its direction** (widens, narrows, heavier or lighter action, mixed), checked against the corpus and the shadow results. Only a recorded widening or heavier action is accepted without the password; anything unknown counts as weakening. An applied version whose code is gone fails closed: the current version applies, every hold is kept, and its narrowings wait as weakening.
- **A weakening override pauses when its base rule changes.** The password confirmed it against a rule that no longer exists, so it waits for a fresh confirmation (§20.11); strengthening overrides keep applying. This keeps plan Q8 within the runner's remit.
- **SP-3 and SP-4 run inside the engine's precedence, without changing `filter::Item`.** `Item` is built at about 25 sites, one of them in a file another wave-3 slice owns; an engine entry point from the writer keeps CSX-5, exceptions, *Always allow*, switches and "strongest action wins" in force.
- **No `serde_json` for the adult-enrichment parsers.** `crates/sources-feeds` reads JSON with its own bounded reader so caps hold while reading (SRC-9); ENR-2 moves it into a shared `json.rs`.
- **No migration, proposed** (plan §3, Q9). Everything fits existing tables: `settings` rows as #367 did (`filter.stand_ins`), V14's `torrent_claims` and `source_state`. V15 stays reserved for CR-3 (runner-state `migration_order`), and no whole-store snapshot is taken for this epic.
- **Enrichment results are stored as claims, with claim encoding version 2** (ENR-0). Claims already have purge, snapshot purge, `secure_delete`, filter-before-storage and the refile sweep (SRC-1, SRC-2, SRC-14b). A separate table would have to rebuild each of those guarantees.
- **ENR-1 depends on SRC-13,** the first enrichment plugin, so the enrichment hook into the pipeline is designed once. ENR-1 must not edit `crates/pipeline/src/writer.rs`, which RP-4 and RP-5 own in turn.
- **SC-2 gets its own id** (plan Q16, for the runner): today it's folded into SC-1, so §20.6's per-rule toggle can't reach it.
- **SP-3 is judged in the writer only.** Its rate state depends on order, and prepare runs in parallel on workers (§19.4), so judging it in prepare would make verdicts depend on timing.
- **FK-3 stays out of v0.6** (plan Q6, for the runner): it needs TMDB release dates, a v0.7 enrichment (§18.3).
- **Routing.** Q1–Q5 go to the owner: Q1 is a signing and trust choice, Q2 a privacy one, and Q3–Q5 are content-safety and adult-content scope, as the brief asks. Q6–Q16 are the runner's (UX, performance, store design, refinements, numbers under §2.26). Owner §2.28 covered only the questions open on 2026-11-02, so it doesn't answer these.
- **Brief rule kept:** this slice doesn't edit `runner/slices.yaml` or `runner/dashboard.yaml`. Plan §4.1 holds the entries ready to paste, and the three new `ext:owner-rpq*` conditions the runner adds.
