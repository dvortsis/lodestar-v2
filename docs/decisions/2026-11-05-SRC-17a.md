# SRC-17a decisions (PR to follow)

The API fields SRC-17's UI renders: provenance on the detail view, `verified` and a source on search hits, and `source`, `verified` and `network` facets (architecture §18.5–§18.8; `docs/plan/2026-11-01-v06-sources.md` SRC-17).

- **Who counts as the admin (§18.7).** A private source's name and its claims are shown to the signed-in session (or the trusted proxy's user) only. `/search`, `/facets` and `/torrents/{hash}` are session-only today (`auth::protected`), so the admin is the only caller they answer. Their handlers still read the request's `Access`, and fail closed: `auth::protected` now puts `Access::Session` in the request as `key_or_session` already did, and a request without one counts as public. So a handler called as a function, or a route mounted without a guard, never shows private data, and when a later slice puts these routes behind `key_or_session` for the `search` scope, an API key or feed token is a public caller at once. Exports and feeds already leave `private_source` torrents out, and neither carries a source or claim field; there's no Torznab server in this build yet.
- **What's private.** For a public caller, a source is left out (and `withheld` set) when any of these is true:
  - the torrent is `private_source` (found only through private sources), which covers all its sources;
  - the source's consent class is `account` (Prowlarr, Jackett, private-tracker announces, your own download clients: "results local-only", §18.7);
  - its class isn't known, because this build doesn't run the plugin or no pipeline is served. This fails closed.

  A public source's claims that came through a private source are withheld on their own (`claim` null, `withheld` set); the source's name stays. A source's visibility depends only on the torrent and the source's class, so a hit's source and the detail view always agree. The admin sees every source and claim, with `private` set on any of the above.
- **Display names come from the running plugins' manifests** (`GET /sources`' `name`), read once per pipeline and kept, because manifests are fixed for the life of the process and listing them takes the writer's lock. A source the build doesn't run shows by its manifest id.
- **First seen per source.** The store records one discovery time per torrent and which source was first (`torrents.first_source`), not a time per source, and this slice changes no schema. So `first_seen_at` is the discovery time for the first source and null for the others. A per-source time needs a migration and isn't scheduled.
- **Claim differences are bounded.** Name, size and file count only, each null when the source didn't state it or it agrees; names are cut to 1,024 bytes (the claims limit). Names are compared byte for byte, so a feed's tidied title ("Some Show S01" against "Some.Show.S01.1080p") is a difference: the UI shows a name difference as information, not as a warning. Claimed file counts may include padding files the verified count leaves out. A claimed file list cut at the 10,000-file limit is "at least that many", so it doesn't count as a mismatch against a bigger torrent. Claimed file lists are never returned.
- **`verified` and `source` on hits are `/search`'s only.** Other lists that embed a hit (collections, alerts, Discover's Newest, user items, compare, exports) leave both out (absent, not null), so their responses and goldens don't change. `verified` is always true today: `torrents` holds verified metadata only, and unverified documents (SRC-3b) have no stored row to serve a hit from.
- **The `verified` facet counts `no` while the search hides it.** The default `verified:yes` sits in the user's part of the query (SRC-3's `base_query`), so it's the facet's own selection and disjunction removes it: the UI can show how many unverified items "Show unverified" would add. Its `yes` value is `selected` even when the user didn't type it; the UI knows the default is on when its own query names no `verified:` clause. To keep that from costing a second full pass on every request, when `verified:yes` is the facet's only selection the extra pass counts only the `verified:no` documents, and `yes` is the shared pass's count.
- **`verified` and `network` count their default as the rest.** Documents indexed before SRC-3 carry neither field and are all verified `bt` (the same reading `compile.rs` uses), so `yes` and `bt` are the documents without another value. `source` has no such default; while its backfill runs, its facet says `partial` (a new `TermFacet` field, false for every other facet).
- **`source` facet values are manifest ids**, which is what `source:` takes; `source_names` maps each listed id to its display name. A public caller never sees a private source's value: a withheld value counts as an unlisted one, wherever it ranked, in `other` and `distinct`, as a number without a name.
- **Scope beyond the brief's list.** The facet counting lives in `crates/search/src/facets.rs` (approved by the runner, 2026-11-05). `crates/api/src/auth/http.rs` gains the one line that puts `Access::Session` in a protected request. The golden fixture (`crates/api/tests/golden.rs`) now registers two sources and one feed claim, so the detail and search goldens show provenance. Two web test fixtures gained the new required fields so `npm run check` stays green.
