# WK-9 decisions (coordinator intake: results under fencing, late results, hints)

Plan `docs/plan/2026-11-06-v06-workers.md` §4.3 WK-9 and Q7; architecture §19.3, §19.4, §19.5, §18.7, §10.9.3. Builds on WK-0 (`2026-11-06-WK-0.md`), WK-1 (`2026-11-06-WK-1.md`), WK-6 (`2026-11-06-WK-6.md`) and WK-7 (`2026-11-06-WK-7.md`).

**This is the first of two PRs (runner, 2026-11-07).** It covers results intake, fencing, content safety, late results, hints, `RECENT_COMMITS` and the worker's held-set prune. **WK-9b** completes §4.3: counters into the rollups with `dim = worker` (and the Insights budgets re-checked with it), grant backpressure through WK-0's `GrantAdmission`, and remote and waiting leases in `fetch_queue` (with WK-1's "leases after off"). Until WK-9b, a `Counters` payload is refused (`accepted: false`, so the worker's spool keeps it), no admission hook is set, and the fetch queue holds the built-in worker's keys only, as before.

## The intake (`crates/pipeline/src/remote.rs`)
- **One `RemoteIntake` per pipeline** (`Monitor::remote()`), built at start beside the built-in worker's stages. When "Allow workers" opens the port, `serve` attaches it to the server (`crates/lodestar/src/cluster/intake.rs`): the server's `InboundSink` is a `RemoteSink`, with the store check, each worker's measured clock offset and the workers' standing.
- **Remote results reach the writer through the built-in worker's own channel.** The writer already re-judges every result whose worker isn't the built-in one (`writer::judge` → `rejudge`), so the commit path is the same: one transaction, the authoritative blocklist, promotion, rollups and indexing. The intake hands it a `Results` it rebuilt; nothing the worker sent goes in unchecked.
- **The sink never blocks a session.** `results` puts the payload on a queue of 16 (`INTAKE_QUEUE`, each ≤ 512 KiB) and answers at once; a task decodes and rebuilds on the blocking pool, then waits on the writer. A full queue answers `accepted: false`, and the worker sends the batch again later.
- **Every batch that was read is answered `accepted: true`,** including one that didn't decode and one whose records were all stale or refused (requirement 7, coordinator side). Only a full queue answers "later". An undecodable batch can't end its leases (its keys are unknown); they last while the worker heartbeats, as any held lease does. WK-10's encoder applies the codec's own checks, so a well-behaved worker never sends one.
- **Shutdown:** the pipeline lets go of the intake's writer and pool senders first (`RemoteIntake::close`), so the writer's input closes when the built-in worker's does. The cluster port already stops before the pipeline (WK-1).

## Fencing (§19.3, §19.8)
- **A record whose token isn't the sender's current lease is dropped and counted as stale** (`LeaseAuthority::held(worker, key, token)`). The worker id is the authenticated session's (WK-6), never the payload's. A resend read before the first copy's commit ended the lease reaches the writer too; the writer's own fence stores it once and ends the lease once (`stale_and_guessed_tokens_commit_nothing`).
- **Remote commits end leases through `LeaseAuthority::commit`, holder-checked (requirement 4).** The writer's one new entry point, `Writer::end_lease`, replaces its three lease-ending calls (stored, refused by a stopped source, blocked) and routes a remote result through `Coordinator::complete_for` / `lost_for` (`LeaseAuthority::commit` / `report`). The built-in worker's path calls exactly what it called before (`complete`, `lost`).
- **Outcomes end leases in the server**, as WK-0 built (`report` for `PeerFound`/`Lost`, `held` for `Fetched`): stale-token outcomes change nothing. The sink's `outcomes` stores nothing.

## Content safety (requirement 1)
- **The coordinator stores the enrichment it rebuilds, for every remote record, of any version.** It decodes the file list from the blob, then runs `enrich_infos` on the name and that list, and stores that record and its hot columns; the classification the writer judges with is rebuilt the same way. The worker's enrichment bytes are never stored, so search's `type:adult` term and `adult:` tags (built from `Enriched::data`, `doc_enrichment`) follow the coordinator's verdict. WK-6's alternative (refusing a this-version record whose decoded type differs) isn't used: rebuilding is never wrong and costs one classification per record. The worker's verdict, rule fix, rule version and always-adult mark are dropped; the writer judges again and finds an always-adult source from the lease's sources (`source_adult`).
- **Test:** `a_worker_cannot_store_adult_content_as_non_adult`: a worker sends adult content with a this-version Movie record (it passes the codec), and another with an older version's undecodable bytes; both are stored with this version's record, which decodes as Adult with an adult kind, and the Adult hot column. Search's indexer can't be used from the pipeline's tests (search depends on the pipeline); it reads exactly these bytes.

## What else is rebuilt or checked (requirement 3 and WK-6's list)
- **`sources` are the lease's** (its sources and its first source); the worker's bitset is ignored. **`private_source` is the lease's:** private when every source of the lease is a private one (`finds_private`), as the pool decides it for the built-in worker (every finder private). The worker's flag is ignored.
- **`metadata_at` is corrected by the worker's measured offset and kept between the key's discovery and now.**
- **`size` and `file_count` must match the rebuilt file list** (non-padding sizes and count, as `Preparer` derives them); a mismatch refuses the record.
- **The blob must name a dictionary the coordinator has** (`Preparer::has_dict`), else the record alone is refused, before `Store::write` could fail the whole transaction.
- **Decompression is capped (approved store edit).** `Preparer::decode_files(blob, max, max_components)` reads zstd as a stream through `take(max + 1)`, so no more than the cap is ever produced; the decoder's window is capped at what `max` needs (at least 1 MiB, since a dictionary widens a small blob's window; 16 MiB for the largest blob), so a frame that asks for zstd's default 128 MiB window is refused before it's allocated. Per record the byte cap is `min(info_size + 4 KiB, 16 MiB)` (`info_size` is the worker's word; metainfo's 16 MiB info-dict cap bounds it); per batch, 64 MiB decompressed in total (`BATCH_BLOBS`). A refused blob is charged its whole cap, so a batch of bombs costs its budget once, not 1,024 caps. A record over either is refused alone.
- **The decoded shape is capped too (from the self-review).** `filetree::decode` copies each directory's path into every child's, so a blob of a few hundred KB (a chain of 60,000 nested directories) would ask for about 1.8 × 10⁹ path components. `decode_files` first reads the blob's shape (`filetree::shape`, new and read-only: counts, depth and total components, with no path built) and refuses a tree deeper than metainfo's 64, with more than its 200,000 files, or with more components than the batch has left (`BATCH_COMPONENTS`, 2,000,000: metainfo's bencode item cap, which one largest torrent fits; about 150 MB of decoded file lists at most). `filetree::decode` and every local path are unchanged. `shape` is one linear pass over the blob with no recursion (a directory's depth is its parent's plus one, parents first), one byte per directory. Tests: depth 64 is accepted and 65 refused, 200,000 files accepted and 200,001 refused, the component budget exact to one, a 60,000-deep chain of under 300 KB refused with no path built (`decode_files_refuses_a_tree_over_its_shape_limits`), and the budget per record and per batch (`path_components_are_budgeted_per_record_and_per_batch`). The `remote_blob` fuzz target checks `shape` against `decode` on every input.
- **A raw dict is dropped while the coordinator's `archive_raw` is off** (plan Q8).
- **A hybrid's other hash is the worker's word:** a record whose non-key swarm hash names another stored torrent is refused, so it can't upgrade or merge into that torrent.
- **A record refused for its content ends its lease once, as `Invalid`** (holder-checked `report`), so the funnel gets its terminal row and the key isn't stranded.
- **`Action::Drop` on the wire** stays accepted (WK-8 decides), and is ignored: the writer judges again.

## Late results (plan Q7, a runner refinement flagged under §2.19)
- **A token from an earlier epoch** (its high 32 bits below this run's start) is a late result. It's committed only when its key is **neither stored nor in flight** (leased to anyone, or waiting for a re-grant), through the same rebuild and re-judge, under a lease rebuilt from the coordinator's own record of the key: the fetch queue this run started from (cohort, first source, strategy), never the worker's. The lease is restored, not granted: **never "harvested" again.** A key with no record in that queue is dropped as stale.
- **Refinement:** "in flight" includes a key waiting for a re-grant, not only one held, which Q7's "held by any worker" leaves open. Stricter: a waiting key will be fetched again by whoever gets it.
- **Checked and leased in one step** (`LeaseAuthority::restore_if_free`, from the self-review): the late result's lease is made only if the key is still neither held nor waiting, under the authority's lock. An expiry, a claim or a second feed in between makes the record stale; it never takes over a waiting lease, and the correction is never counted twice. `a_late_lease_never_takes_over_a_key_expired_in_between` injects that interleaving step by step and shows the old check-then-`restore` losing the waiting lease.
- **Who may send one.** Any authenticated worker may commit a late result for any key in the start's queue that is free, including one the built-in worker held before the restart: Q7 allows it, since the key is neither stored nor held, and the result is rebuilt and re-judged like any other. It bypasses the claim and the have-filter (the store check stands in for them). **For WK-9b and WK-13:** grant backpressure doesn't apply to late results, and quarantine is what stops a misbehaving worker's.
- **The funnel correction.** Such a key's first lease ended with a terminal outcome (after the restart the built-in worker held it; it isn't stored, so that lease ended lost), and the late result ends a second lease with another. Each commit counts one `LATE_RESULTS` row (rollup metric 16, by discovery cohort, dim = the key's first source), so **harvested = Σ terminal − `LATE_RESULTS` + in flight** (`late_results_follow_q7` checks it across a stored, a waiting and two late keys).
- **Refused outright:** any late result from a worker that is quarantined, revoked or purged, and **any** result (late or not) fetched before that worker's last purge, through the `Standing` trait (`refuses_late`, `last_purge`), tested with a fake. Until WK-13 fills it, `NoStanding` refuses nothing; a revoked worker can't connect anyway. A current-epoch record refused this way ends its lease once (as `Invalid`), so the key isn't stranded once the worker forgets it (`a_purged_record_ends_its_lease`).
- **The purge cutoff compares the record's fetch time,** the worker's `metadata_at` corrected by its measured offset, both of the worker's making. That suits an honest replay; a hostile worker is stopped by `refuses_late` and by revocation. **For WK-13:** if a purge doesn't evict the worker's live leases, compare against the lease's grant (the token's sequence) instead.
- **The record's bound (runner, 2026-11-07).** The map is built only when "Allow workers" is on at the start (`PipelineConfig::remote_workers`, from `[cluster] enabled`): with workers off, nothing is held or written. It holds the start's fetch queue, which the pool caps at `max_pending` (200,000 keys), at about 30 bytes a key (the key, its cohort hour, source and strategy: exactly what the start restored), so about 6 MB at the cap. It never grows after the start: each key is removed when its late result is committed, and the whole map is dropped 25 h after the start (`LATE_FOR_SECS`: a spool's 24 h, owner §2.17, plus an hour). Tests: `the_start_queue_is_kept_only_with_workers_allowed` and `the_start_queue_is_kept_only_while_a_spool_can_hold_a_result` (the drop, on the clock it's given).
- **Until WK-9b** puts remote leases in the fetch queue, a remote lease from before a restart has no record there, so its late result is stale (a key the built-in worker held before the restart does have one: see "Who may send one").
- **What stopping leaves:** a batch taken off the queue but not yet handed to the writer when the pipeline stops is dropped, its leases (and a late result's correction) as a crash would leave them; the cluster port stops first, so this is at most one batch.

## Peer hints (requirement 5, §18.7)
- **Every relay filters with `lodestar_network_policy::allows`** on top of WK-0's `usable_hint`: the server's remote-to-remote relay in `claim()`, `ClusterServer::relay_hints`, hints for the built-in worker (`RemoteSink::local_hints`, into its pool as a peer reply) and the built-in worker's hints for a key a remote worker holds (intake's `Held` arm → `RemoteIntake::relay_local`). A private find's peers stay with the built-in worker.
- **`ServerConfig::hints_allow_private` is false, with no way to turn it on.** No private-address setting reaches `serve`'s cluster config (the DHT's `allow_private` is a test and simulator field). **For WK-14/WK-16:** if a LAN-only fleet ever wants private-address hints, this is the switch, and it should follow the DHT's and fetch's own private-address setting, not become a new knob.
- **Hints are never stored:** `hints_are_filtered_and_never_stored` reads every file in the data folder after a relay and finds no hint address, in text or as bytes.

## `RECENT_COMMITS` (requirement 6)
- **A key → sequence-number map** (`crates/cluster/src/leases.rs`). A re-commit takes a new slot, and an old queue entry evicts its key only if it is still that key's latest commit; every commit counts in `commit_seq`. Before, a re-commit kept its first slot, so a claim racing the second commit could be granted and harvested again once the first slot rolled over. `a_re_commit_keeps_its_place_in_the_recent_commits` fails on the old code (checked by reverting it).

## The worker's held set (requirement 7, worker side)
- **A key reported `Fetched` whose commit doesn't come within the lease TTL is dropped from the held set** (a new token for the key, after a re-grant, starts the wait again) (`crates/cluster/src/client.rs`, at each heartbeat, on the session's clock). Its batch was lost or never accepted; the worker no longer counts it or takes hints for it. Keys still being fetched aren't pruned (the worker's pool cap bounds them, plan Q5). `an_unanswered_fetched_key_is_pruned_after_the_ttl` uses an injected clock and fails with the prune removed.

## Notes for later slices
- **WK-9b:** `Admit` (domains, an hour window after offset correction, per-row and per-day caps), `BY_WORKER` rows, `GrantAdmission` on the writer's fill, `fetch_queue` rows for remote and waiting leases, parked keys to the built-in worker while no server runs, and the Insights budget numbers. - **WK-10:** report `Fetched` only once the result is in the outbound queue, and call `committed` on `Accepted { accepted: true }`; the held-set prune covers a lost answer. Filter hints with `allows` again before dialling (WK-0). The funnel's `PeerFound` and `Fetched` stages for a remote key aren't counted on the coordinator yet: the worker's own funnel counts them, and WK-9b/WK-10 decide how they reach the coordinator's cohorts.
- **WK-11:** a replayed spool batch is answered like any other: committed if still current or late and admissible, else stale; `accepted: true` either way, so the segment can go. A replay from a quarantined, revoked or purged worker, or older than its last purge, is refused by the same `Standing` check.
- **WK-12:** the commit write (`torrent_worker`) hooks in where `Writer::end_lease` is called for a stored result; `Results.worker` is the authenticated session's.
- **WK-13:** implement `Standing` (`refuses_late` for quarantined, revoked or purged workers; `last_purge`) and hand it to `intake::attach`.
- **WK-15:** read late results (metric 16) beside the funnel's terminal rows, so a cohort reconciles.
