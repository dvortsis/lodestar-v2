# WK-10a decisions (the coordinator's cluster tick)

WK-10 is split in three (runner, 2026-11-07T19:01Z, §2.33): **WK-10a**, this PR (the coordinator's tick in `crates/lodestar/src/cluster/serve.rs`); **WK-10b**, the worker runtime core; **WK-10c**, the worker's sharded DHT, budget and heartbeat stats, and the measured RSS breakdown (Q6). The brief's gates are split the same way: this PR has none of the worker's gates. It builds on WK-3 (`2026-11-07-WK-3.md`), WK-5 (`2026-11-07-WK-5.md`), WK-8 (`2026-11-07-WK-8.md`), WK-9c (`2026-11-07-WK-9c.md`) and WK-14 (`2026-11-07-WK-14.md`), and follows each one's "for WK-10" notes on the coordinator side.

## The tick (`serve.rs`)
- **One tick per served cluster server, every second (`TICK`).** It starts with the server and is aborted before the server shuts down. Each tick runs these steps in order:
  1. A worker whose session is new gets both snapshots from chunk 0 (`WorkerSnapshots::forget`).
  2. Placement brings membership in line and queues each member's assignment (`Placement::sync`). Workers that were full are retried on the next tick.
  3. The open wire keys follow the day (below).
  4. The workers' have-filter syncs, and is rebuilt on a blocking thread when it's due.
  5. The filter and dictionary snapshots are read and installed on a blocking thread when they're due, then synced.
- **The one planner.** `Wiring::placement` is the `Arc<Placement>` that `services.rs` builds before `Cluster::start` and hands to `Workers::open` too (WK-14's note), so saved pins, budgets and pauses reach the plan the tick sends. Prefs saved before this PR reach a worker with its first `Assign`.
- **No fleet, no work beyond placement.** `Wiring::fleet` (the stored set, the filter engine and the seal key) is `None` in tests that don't need it. Then no have-filter, snapshot or wire key is built. `serve` always passes one. As before, nothing is built until a remote worker connects (§19.8). Before that, the observer on the coordinator's `Have` costs one atomic load per insert (WK-3).
- **The have-filter's observer is set once per process,** the first time a server is built (`Have::observe` takes one). One `WorkerFilter` lives as long as the process, across "Allow workers" off and on.
- **The rebuild** runs on its own read connection on a blocking thread, with `Have::len()` (swarm hashes) as the stored count (WK-3). A second one never starts while one runs. A failed scan keeps the old filter and backs off (WK-3's note): 1 s, then doubling to 5 minutes, reset by a success. So a failing store isn't scanned in full on every tick. A panic in the scan is caught and becomes an error inside `WorkerFilter::rebuild`, so its own "rebuilding" flag clears and the old filter stays; a drop guard clears the tick's flag however the blocking task ends (#592's review, N5). `WorkerFilter::rebuild` itself also clears its flag and the half-built filter if its sizing or allocation unwinds (a drop guard in `cluster/have.rs`, from the delta review).
- **Snapshots:** the active dictionary's id is read from `settings` (the store's `file_dict` row) and its bytes by that id. `Store` caches the active dictionary when a connection opens, so the tick's long-lived reader can't use `active_file_dict` (the review found that a newly trained dictionary was otherwise rebuilt every second and never sent). The same id makes the due check and the build agree. When a build is due, the read, the encode and the decode check all run on a blocking thread. That keeps the async threads and the sink free at the caps (tens of MiB).
  - `WorkerSnapshots` is taken out of its slot for that time, and the blocking half puts it back itself. So a tick aborted mid-install (Allow workers off, a reseal) can't leave the process without snapshots.
  - Acknowledgements that arrive meanwhile wait in the tick's queue and are applied afterwards; stale ones are ignored by version and sequence.
  - Every tick ends by handing the installed versions to `Placement::set_versions` (an unchanged pair is a no-op), so a change made while the snapshots were out of their slot, an aborted tick's install included, still reaches the plan (#592's review, N1).
  - A failed snapshot read backs off as a failed rebuild does (N2).
- **A new session restarts that worker's snapshots from chunk 0, and only its** (WK-8; #592's review, B1). `WorkerStatus` now carries the live session's id (`session`, unique and counting up for a server's life; runner-approved edit to `crates/cluster/src/server.rs`). The tick keeps each worker's id from the last tick and calls `forget` for a worker whose id changed, so a reconnect between two ticks is seen, as a certificate renewal's is (each worker reconnects at half-life, every 36 h). Another worker's transfer is never touched. The first version of this PR restarted every worker's transfer whenever the session count rose more than the new workers explained, which a renewal would have turned into a fleet-wide resend every 36 h.

## Snapshot acknowledgements (the inbound sink)
- **`serve.rs` wraps the pipeline's `RemoteSink`** in its own `InboundSink`. Results, counters, outcomes, re-verification replies and local hints go to the intake as before. Without an intake, results and counters are refused, as the trait's default does.
- **Have-filter acknowledgements go straight to `WorkerFilter::ack`,** which takes only its own mutex and queues messages (WK-3's contract: the sink must not block).
- **Filter and dictionary acknowledgements are queued for the tick,** at most 16 waiting per worker (`ACKS_PER_WORKER`: twice the two kinds' windows of four), in a queue sized for every planned worker (4,096 × 16). Past its share, one worker's acknowledgements are dropped and counted (`cluster_snapshot_acks_dropped_total`). So a worker that floods acknowledgements can't block the server's session tasks or take another worker's room. Its own transfer then restarts after its stall. The counts are cleared when a new server is built, since the old queue goes with the old server.

## Wire keys, and WK-9c's choice
- **The keys sealed records open with are set when the server is built,** before any tick, and again when the coordinator's UTC day changes (`follow_keys`). They are today's and yesterday's (`filter::wire_keys`). A record that a worker spooled before a coordinator restart opens from the first result on. The keys are the intake's own `Attached::keys`.
- **What holds:** a worker never seals under a key the coordinator lacks. It only ever holds a key the coordinator built (the filter snapshot carries it, keyed by the coordinator's own day), and refuses to seal past that key's day by its own clock (`Judge::judge_at`: `NotReady`). On the coordinator, the keys change on the same tick as the snapshot (step 3 runs before step 5).
- **What doesn't hold yet, and the runner's decision (2026-11-07T20:55Z, #592's review B2), which WK-10b implements:** `Judging` turns `NotReady` into `Loss::Blocked`. So every worker throws away its fetched work at each UTC midnight until the new snapshot arrives (plus any clock skew), and once WK-10c tombstones `Blocked` keys, it would tombstone legitimate keys for good.
  1. **`NotReady` is never `Loss::Blocked`.** On the worker, a result refused for a missing snapshot or a day boundary is kept and judged again when the fresh snapshot arrives, within WK-10b's queue limits (or the spool's, WK-11). One that can't be kept is released for a re-grant under a distinct reason that doesn't tombstone. `Blocked` stays reserved for the floor: CS-8a and hash-list drops.
  2. **The coordinator pre-sends the next UTC day's wire key and its snapshot** ahead of midnight (from about 23:00Z), so workers judge at 00:00Z with no gap. That's a `serve.rs` change, approved for WK-10b.
  3. **Tests:** no loss across a midnight crossing with the snapshot pre-sent; a late snapshot is retried, not dropped; and `NotReady` never produces `Blocked`.
- A record that doesn't open under a known key, or whose inside doesn't match its header, still ends its lease as `Invalid` (WK-9c). Neither WK-9c option (accepting tomorrow's key at the coordinator, or requeueing a record refused for an unknown key) is taken: the pre-sent snapshot does both jobs.

## Logs and metrics
- **Three events** (runner-approved, item d):
  - `cluster.have_at_cap` (warning) is said once each time the have-filter turns full at its largest size, with the stored count (WK-3).
  - `cluster.snapshot_failed` (error) is said for each failed build. Its error is a fixed kind that names the cap (`TooLarge`/`Invalid`'s name), never a rule. A failed store read (`store`) is said once when reads start failing and again only after one has worked, so an unreadable store doesn't log every second.
  - `cluster.tick_failed` (error) is said once if the tick task ends in a panic (#592's review, N7). A watcher task waits on the tick and aborts it when it's aborted itself. Its abort guard is made before the watcher is spawned, so aborting the watcher before it first runs still ends the tick; with the guard made inside the watcher (this PR's second round), an early abort detached the tick, which then kept running against the shared state after its server stopped (the delta review). Its message and help both say the tick resumes when the cluster port reopens: Allow workers turned off and on, a key reseal, or a restart.
  - Not tested end to end: `cluster.have_at_cap`, whose filter would have to reach `MAX_FILTER_BITS`. Its latch is the same three lines as the store-failure one, which is tested.
- **Their web names:** `event-names.ts` (regenerated with `npm run event-names`) and the `en`/`zh` messages. `event-labels.test.ts` requires a name and help line in both languages for every catalogued event, so the messages are part of "the one web file" the runner approved. None of it is under `web/e2e`.
- **Seven series** in `docs/metrics.md` ("The cluster tick"):
  - counters: have rebuilds and their failures, snapshot installs and their failures, dropped acknowledgements;
  - gauges: the have-filter's bytes, and whether it's at its cap.

## WK-2 nits
- **`ci.yml`'s root-only worker tests** run with `--exact` and check `test result: ok. 2 passed` as a fixed string. Before, `2 passed` also matched `12 passed`.
- **A hand-set `LODESTAR_TOKEN_IGNORED`:** when only the marker says a token was set (the image `prepare` started again), each warning now also says "If LODESTAR_TOKEN isn't set, remove LODESTAR_TOKEN_IGNORED instead". So it's right in both cases. A real `LODESTAR_TOKEN` keeps the old lines.
- **A non-UTF-8 `LODESTAR_TOKEN` isn't stripped** before the worker runs: `std::env::var` doesn't see it. It's left as is. Such a value can't be a token, so it's never redeemed, and the join reports it as unset.

## Tests (`serve.rs`)
- `a_worker_gets_its_assignment_every_snapshot_and_a_new_dictionary`: over TCP and mutual TLS, with the pipeline's intake. It checks:
  - the keys are set before any tick;
  - the assignment, the have-filter, the filter snapshot and a trained dictionary arrive, paced by acknowledgements;
  - the assignment names both versions;
  - a newly trained dictionary is sent and built once, not on every tick (counted over three more ticks).
- `a_session_that_restarted_between_ticks_gets_the_snapshot_again`: the tick is stepped by hand, so a reconnect with no tick in between is certain. It fails without the session check.
- `a_reconnect_restarts_only_that_workers_transfer` (B1): A reconnects between two ticks and gets chunk 0 again. B's finished transfer isn't resent: a dictionary trained afterwards is the marker on B's snapshot queue, and no filter chunk comes before it. It fails with the old restart-everyone logic.
- `an_install_aborted_midway_keeps_the_snapshots`: the install's blocking half is parked on the reader's lock, the tick is aborted, and the snapshots come back and install. The next tick hands their version to placement (N1).
- `store_failures_are_said_once_and_rebuilds_back_off`: its rig sets the rebuild's back-off to an hour and the reads' to zero, so nothing depends on the runner's speed (N3). Also `retries_back_off_and_reset`, `the_sink_queues_snapshot_acks_per_worker_without_blocking`, `the_open_keys_follow_the_day` and `without_a_fleet_only_placement_runs`.
- From the delta review: `aborting_the_watcher_ends_the_tick_before_and_after_it_runs` (it fails with the guard made inside the watcher), `a_panicking_tick_is_said_once`, and `a_panicking_scan_keeps_the_old_filter` (failure counted, both flags clear, the old filter stays, the next rebuild runs). `retries_back_off_and_reset` checks "not due" with an hour's back-off.
- Every wait is on a condition with a 20 s deadline; none sleeps a fixed time.
