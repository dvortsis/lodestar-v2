# PK-win-upd-2 decisions: the MSI install through the update helper

The MSI now installs a new version through a SYSTEM helper, as the owner approved M6 Q13 (`docs/owner-decisions.md` §2.47; the decision is the plan row in `docs/plan/2026-11-06-m6-gap-audit.md` §5 Q13). The code:
- the service side in `crates/lodestar/src/update/windows/check.rs` and `msi.rs`;
- the helper in `windows/helper.rs`;
- the command in `cli/update_helper.rs`;
- the task in `packaging/windows/main.wxs`.

Calls marked "runner" are the runner's under §2.19; the owner can veto them.

## The task
- **`Lodestar update helper`,** registered by the MSI after the service exists (so its SID resolves), again on Repair and upgrade, and removed on uninstall. Exactly the Q13 row:
  - **runs as** SYSTEM (`S-1-5-18`), highest rights;
  - **runs only** `%ProgramFiles%\Lodestar\lodestar.exe update-helper`;
  - **when:** one trigger, at boot, plus on demand (`AllowStartOnDemand`). One instance at a time (`IgnoreNew`), two hours at most;
  - **who:** the task's descriptor is `D:P(A;;FA;;;SY)(A;;FA;;;BA)(A;;FRFX;;;<NT SERVICE\Lodestar>)`, so the service may read and start it (`schtasks /Run`), nothing more.
- **Registered by the program itself** (`update-helper --register-task`, which the MSI runs as SYSTEM through `WixQuietExec64`). That keeps the definition as plain code with tests (`msi::task_xml`), and Windows CI registers it under a test name and reads it back (runner).
  - The XML reaches PowerShell on stdin, never as script, with `-ExecutionPolicy Bypass` as the MSI's other scripts have.
  - The flag refuses unless the program is the installed one.
- **`AllowDowngrades="yes"` stays** in `main.wxs`. The helper never asks for a downgrade (rule 4 below), and PK-win-upd-3's rollback needs it.
- **A rolled-back upgrade from a version before this one** leaves the task registered, pointing at a program without the command. It fails harmlessly at boot until the next install.

## The service's side
- **Install is offered** (`capability.can_install`) for the MSI only, when:
  - the data folder is the service's default, which it checks at every start (`data_folder_unchecked` otherwise);
  - the build isn't a dev build;
  - `skipped` can be read.

  An unknown kind answers `install_kind_unknown`. The portable build answers `not_built_yet` until PK-win-portable-upd.
- **`POST /updates/install`** with `when: now` applies Install now's rules (`policy::install_now`, with nothing incapable), the manual-steps confirmation, and the pin from a current manifest. It then answers at once, with `installing` set, and in the background:
  1. downloads the MSI to `<data>\bin\<version>.part` (`download.rs`, now on Windows too);
  2. hands it over in `<data>\updates\`: earlier leftovers removed, the envelope it checked (byte for byte), the MSI, then `request.json` last, so the helper never sees a request without its files;
  3. starts the task.
- **`when: window`** answers `not_built_yet`. Nothing installs automatically on Windows: the policy still treats `auto` as Check and notify (runner).
- **The service has no rights beyond its virtual account,** and the helper trusts none of what it leaves (Q13 rules 1 and 3).
- **The helper's answer** (`<data>\updates\result.json`) shows as the `install_failed` notice when it didn't install a newer version. It's display only, since the service can write that file too.
- **`/updates` contract:** no shape change. `capability.reason` and `notices` are strings. The new codes are `install_kind_unknown`, `data_folder_unchecked` and `install_failed`, and the DTO's descriptions (X-updates-api-text's files) don't list them yet. Nothing is regenerated.

## The helper's rules (Q13)
- **Its own facts first.** The build's version must parse: `update/mod.rs`'s fallback to 0.0.0 would make every version newer (#630 review item 2). The program must be `%ProgramFiles%\Lodestar\lodestar.exe`.
- **Only a checked data folder** (#630 item 1). The helper reads no config and no `LODESTAR_*` variable. `--config` is refused, and the data folder is always `%ProgramData%\Lodestar`. It must pass the ACL check the service runs at start (`windows::acl::verdict` with the service's SID).
- **Pinned folders, no deletes** (from the self-review). The helper never deletes or replaces anything in the data folder by a path it checked once:
  - `<data>` and `<data>\updates` are opened as themselves (`layout::pin_dir`: `FILE_FLAG_OPEN_REPARSE_POINT`, the handle's attributes checked, no `FILE_SHARE_DELETE`) and held for the whole run. `<data>\bin` is pinned the same way by `Bin`. So neither folder can be swapped for a junction or a mount point after the check.
  - Its only writes there are `result.json` (temporary file and rename, beneath the pinned `updates`) and, after a failed install, `skipped` under `.lock`.
  - The service cleans `updates\` before its next hand-over.
- **Each request once.** `request.json` carries a new random id. The helper records the id in staging (`handled.json`) before acting, whatever becomes of the request, so a boot run never repeats an install nobody is watching. A retry is a new Install.
  - The file isn't Unix's `pending`, which is a probation record PK-win-upd-3 keeps in `<data>\bin`.
- **Rule 1, copy then verify.** The envelope and the MSI are copied into `incoming\` in the staging folder, and only the copies are read after that. The MSI's copy must be the pinned size and SHA-256, and `msiexec` installs that copy, so a file swapped after the copy is never run.
- **Rule 2, the staging folder** is `%ProgramFiles%\Lodestar\updates` (runner). The helper creates it with a protected DACL for SYSTEM and Administrators only, and checks it before every use. A folder that isn't private is refused. It sits under Program Files, where other users can't create anything, not under `%ProgramData%`, where anyone can squat a name. Architecture §12.2 had the previous MSI in `<data>\updates\`; Q13 superseded that. The layout:
  - `incoming\`: this run's copies;
  - `trust.json`: the helper's own trust state;
  - `handled.json`: the last request id;
  - `current\` and `previous\`: the MSI installed last and the one before, each with `pins.json` (version, channel, SHA-256, size), for PK-win-upd-3's rollback;
  - `msiexec.log`.
- **A damaged staging `trust.json`** blocks every install (`trust_damaged`). An administrator deletes it, and it's rebuilt from the embedded floor.
- **Rule 3, untrusted input.** The request (at most 4 KiB, unknown fields refused, a canonical version, a hex id) and the envelope (`MAX_ENVELOPE`) are opened as themselves, never through a link. The helper doesn't read the data folder's `trust.json`, `rollback.json` or `history.json`.
- **Rule 4, newer only.** The requested version must be newer than this build by semantic version. RC and nightly MSIs share their release's `ProductVersion`, which Windows Installer can't tell apart. The semver comparison decides, and `MajorUpgrade` takes the same-`ProductVersion` upgrade. The journal's rollback target is PK-win-upd-3's exception.
- **Rule 5, channel and freshness,** as the engine does it: `lodestar_update::check` against the embedded keys, the request's channel and the clock, then `lodestar_update::install` (refused when not current, withdrawn, or no MSI for this target).
  - **The channel is the service's to choose (runner, §2.19).** It comes from the request, and the manifest must be signed for exactly that channel. A compromised service could ask for Beta or Nightly over Stable, but only for a validly signed Lodestar build that's newer.
  - The trust state is the helper's own, so a validly signed older manifest is refused (`older_than_mark`) whatever the data folder's `trust.json` holds. It's saved forward-only before installing.
- **Rule 6, fixed arguments:** `msiexec /i <staged copy> /qn /norestart /l*v <staging>\msiexec.log MSIRESTARTMANAGERCONTROL=Disable`. No public property is passed. Restart Manager is off because the helper runs from the folder being upgraded, so an in-use file is replaced at the next restart (exit 3010, reported as `restart`).
- **Authenticode** (§2.23): an MSI with no signature passes, a valid one passes, anything else is refused.
- **The relaunch token** (#630 item 6): `sc`, `msiexec`, `schtasks` and the helper's own PowerShell are started by absolute path from `System32` without any `LODESTAR_*` variable. The ACL check's PowerShell (`windows::acl`) and the `reg` fallback remove the relaunch token only. The SYSTEM task's environment has no other `LODESTAR_*` variable.

## Order, the lock and outcomes
1. Check everything above, while the service keeps running.
2. Stop the service (`sc stop`, up to 2 minutes; if it doesn't stop it's started again anyway, since it may stop late), then take `<data>\bin\.lock`, waiting up to 30 s. The lock proves the service has stopped (PK-win-upd-1: it holds the lock for its whole run). If it stays held, nothing is installed and the service is started again.
3. Install. The MSI starts the new service.
4. **Exit 1618 or 1601** (another install running, Windows Installer unavailable): `installer_busy`. Nothing is skipped, and the old service is started.
5. **Any other failure** was rolled back by Windows Installer. The version is written as `failed` in `skipped` (best effort, under the lock), and the old service is started.
6. **Health check:** Running within 5 minutes and still Running at every look for 60 s. The MSI and its pins move into `current\` either way; a staging error there is logged, not a refusal, since the install happened.
   - **Unhealthy** (exit 1) is for PK-win-upd-3's rollback to take over. This slice doesn't roll back.
   - **It doesn't confirm which binary runs.** After exit 3010 the old one may until a restart. PK-win-upd-3 adds the version check its rollback needs.
- **Exit status** (Task Scheduler's last result): 0 installed or nothing to do, 1 failed, busy or unhealthy, 2 bad arguments, 3 refused. The detail is in `result.json`.

## The #630 review items
- **1. Unchecked bin, 2. unparsed build version, and 6. the relaunch token:** above.
- **3. The skip trim:** `windows::check::trim` drops the oldest `user` skips first, and never a `failed` or `manual` entry, nor the entry just added. Unlike Unix's `pending::trim`, it keeps going past 64 when only refusing entries are left (runner): a version that failed must stay refused.
  - Past `MAX_STATE` (thousands of failures), writes to `skipped` would fail and be named. That's accepted as unreachable in practice.
  - `add_skip` writes the `{version, reason}` shape.
- **4. A briefly held rename:** `layout::rename_retrying`. On Windows it retries os errors 5 and 32 only, 8 times, from 5 ms doubling to 320 ms (about 1.3 s, as `lodestar-search` does), and returns the last error. Unix calls `fs::rename`. `write_steps` (every atomic write), the helper, `msi::hand_over` and the staging moves use it.
- **5. `ProgramFiles`:** a service's environment has it. When it's missing or empty, `msi::program_files` reads `ProgramFilesDir` from the registry. The notifier's `signals` and the helper use it.

## Tests
- **On every OS:**
  - the helper installs the verified copy, after copying and before stopping the service, from staging, with the fixed arguments, keeps it with its pins, deletes nothing in the data folder, and answers in `result.json`;
  - an MSI swapped after its copy is never installed; a wrong hash, a short file and an oversize file are each `artifact_mismatch`;
  - a swapped envelope after its copy changes nothing;
  - a replayed, validly signed older manifest is refused;
  - each refusal: not newer (same, older, an RC of the same release), an unparsed build version, an unchecked data folder, a staging folder that isn't private, another channel, a stale manifest, no MSI for the target, a damaged request or signature, a bad Authenticode signature;
  - links in place of `updates`, the request, the envelope or the MSI, and an oversize envelope (Unix symlinks);
  - `.lock` held: nothing installed, the service started again, the request answered once and a new one installed; a service that won't stop is started again;
  - a failed install skipped as `failed`; a busy installer skipping nothing; exit 3010 and an unhealthy service reported; `current\` and `previous\` rotated;
  - the request parser (ids included), the fixed `msiexec` arguments and exit codes, the `ProgramFiles` fallback, the task's XML, the bounded retry, children's environments without `LODESTAR_*`;
  - 64 user skips don't push out a `failed` entry;
  - the service: Install offered for the MSI, the MSI downloaded, the envelope, MSI and request handed over and the task started; refusals (not a candidate, unknown, `window`, skipped), and no Install for an unknown kind or the portable build.
- **On the Windows CI job,** all of the above, plus:
  - `<data>` and `<data>\updates` pinned during a run (renaming either fails);
  - the staging folder created private for real, and an inherited one refused;
  - Task Scheduler taking the definition (registered under a test name and read back);
  - a briefly held file renamed over once let go (a real os error 32), and a missing source not retried;
  - a junction at the download's part path refused;
  - `tests/update_windows_msi.rs`: the real binary refuses outside Program Files and refuses `--config`, and the command is hidden.
- **The MSI build:** CI doesn't build the MSI (only `release.yml` does), so there's no WiX build check in CI. The new elements are checked to be well-formed XML. The release build compiles them, and G-m6's manual install covers them.
