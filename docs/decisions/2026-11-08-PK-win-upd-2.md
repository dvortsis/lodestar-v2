# PK-win-upd-2 decisions: the MSI install through the update helper

The MSI now installs a new version through a SYSTEM helper, as the owner approved M6 Q13 (`docs/owner-decisions.md` §2.47; the decision is the plan row in `docs/plan/2026-11-06-m6-gap-audit.md` §5 Q13). The code is in `crates/lodestar/src/update/windows/helper.rs` and `msi.rs`, the command in `cli/update_helper.rs`, the task in `packaging/windows/main.wxs`. Calls marked "runner" are the runner's under §2.19; the owner can veto them.

## The task
- **`Lodestar update helper`,** registered by the MSI after the service exists (so its SID resolves), again on Repair and upgrade, and removed on uninstall. Exactly the Q13 row:
  - **runs as** SYSTEM (`S-1-5-18`);
  - **runs only** `%ProgramFiles%\Lodestar\lodestar.exe update-helper`;
  - **when:** one trigger, at boot, plus on demand (`AllowStartOnDemand`). One instance at a time (`IgnoreNew`), two hours at most;
  - **who:** the task's descriptor is `D:P(A;;FA;;;SY)(A;;FA;;;BA)(A;;FRFX;;;<NT SERVICE\Lodestar>)`, so the service may read and start it, nothing more.
- **Registered by the program itself** (`update-helper --register-task`, which the MSI runs as SYSTEM through `WixQuietExec64`), so the definition is plain code with tests (`msi::task_xml`), and Windows CI registers it under a test name and reads it back (runner). The XML reaches PowerShell on stdin, never as script. The flag refuses unless the program is the installed one.
- **`AllowDowngrades="yes"` stays** in `main.wxs`: the helper never asks for a downgrade (rule 4 below), and PK-win-upd-3's rollback needs it.

## The helper's rules (Q13)
- **Its own facts first.** The build's version must parse: `update/mod.rs`'s fallback to 0.0.0 would make every version newer (#630 review item 2). The program must be `%ProgramFiles%\Lodestar\lodestar.exe`, judged by `windows::check::detect` with its service-account sign set.
- **Only a checked data folder** (#630 item 1). The helper reads no config and no `LODESTAR_*` variable. `--config` is refused, and the data folder is always the service's default `%ProgramData%\Lodestar`. It must pass the same ACL check the service runs at start (`windows::acl::verdict` with the service's SID): owner and DACL, and no reparse point anywhere inside. A data folder moved with `--config` or `LODESTAR_DATA_DIR` is never installed from.
- **Rule 1, copy then verify.** The envelope and the MSI are copied from `<data>\updates\` into `incoming\` in the staging folder. Only the copies are read after that. The MSI's copy must be the pinned size and SHA-256, and it's the copy `msiexec` installs, so a file swapped after the copy is never run.
- **Rule 2, the staging folder** is `%ProgramFiles%\Lodestar\updates` (runner). The helper creates it with a protected DACL for SYSTEM and Administrators only (`windows::acl::secure_dir` with no service SID) and checks it before every use. A folder that isn't private (an inherited ACL, a foreign owner, a planted link) is refused. It sits under Program Files, where other users can't create anything, rather than under `%ProgramData%`, where anyone can squat a name. The layout:
  - `incoming\`: this run's copies;
  - `trust.json`: the helper's own trust state;
  - `current\` and `previous\`: the MSI installed last and the one before, each with `pins.json` (version, channel, SHA-256, size). PK-win-upd-3's rollback reads `previous\`.
  - `msiexec.log`.
- **Rule 3, untrusted input.** The request (`<data>\updates\pending`: `{format, version, channel}`, at most 4 KiB, unknown fields refused, the version canonical) and the envelope (capped at `MAX_ENVELOPE`) are opened as themselves, never through a link. A `updates` folder that's a link is refused. The helper doesn't read the data folder's `trust.json`, `rollback.json` or `history.json`.
- **Rule 4, newer only.** The requested version must be newer than this build by semantic version. RC and nightly MSIs share their release's `ProductVersion` (`2026-11-08-PK-manifest.md`), so Windows Installer can't tell them apart. The semver comparison decides, and `MajorUpgrade` (new `ProductCode` on every build) takes the same-`ProductVersion` upgrade. The journal's rollback target is PK-win-upd-3's exception and doesn't come through this path.
- **Rule 5, channel and freshness,** as the engine does it: `lodestar_update::check` against the embedded keys, the request's channel and the clock, then `lodestar_update::install` (not current, withdrawn, no MSI for this target: refused). The channel is the service's to choose: it comes from the request, and the manifest must be signed for exactly that channel. The trust state is the helper's own, in staging, so a validly signed older manifest is refused (`older_than_mark`) even when the data folder's `trust.json` was rolled back or deleted. It's saved forward-only before installing.
- **Rule 6, fixed arguments:** `msiexec /i <staged copy> /qn /norestart /l*v <staging>\msiexec.log MSIRESTARTMANAGERCONTROL=Disable`. No public property is passed, so an upgrade keeps the options chosen at install. Restart Manager is off because the helper runs from the folder being upgraded. An in-use file is replaced at the next restart instead (exit 3010).
- **Authenticode** (§2.23, B-update-r2's reuse list): an MSI with no signature passes, a valid one passes, and anything else is refused (`Get-AuthenticodeSignature`, the path in an environment variable).
- **A clean environment** (#630 item 6): every program the helper starts (`sc`, `msiexec`, PowerShell, `reg`) is started by absolute path from `System32`, without any `LODESTAR_*` variable. That covers `LODESTAR_RELAUNCH_TOKEN`.

## Order and the lock
1. Check everything above. Nothing in the data folder is written, and the service keeps running.
2. Stop the service (`sc stop`, up to 2 minutes), then take `<data>\bin\.lock`, waiting up to 30 s for the stopped service's handle to go (PK-win-upd-1: the service holds it for its whole run). Then remove the request and the data folder's MSI, so a boot run doesn't repeat it. If the service won't stop or the lock stays held, nothing is written and the service is started again.
3. Let go of the lock and install. The MSI starts the new service.
4. **A failed install** (any exit code but 0, 3010, 1641) was rolled back by Windows Installer. The helper writes `{version, reason: "failed"}` into `skipped` under the lock, best effort, and starts the old service.
5. **Health check:** the service must reach Running within 5 minutes. The MSI and its pins move into `current\` either way. An unhealthy service is reported (`unhealthy`, exit 1) for PK-win-upd-3's rollback to take over. This slice doesn't roll back.
- **Exit status** (Task Scheduler's "last run result"): 0 installed or nothing to do, 1 failed or unhealthy, 2 bad arguments, 3 refused.

## The #630 review items
- **1. Unchecked bin, and 2. unparsed build version:** above.
- **3. The skip trim:** `windows::check::trim` drops the oldest `user` skips first and never a `failed` or `manual` entry, nor the entry just added. Unlike Unix's `pending::trim`, it keeps going past 64 when only refusing entries are left (runner): a version that failed must stay refused. The reader's 256 KiB cap holds thousands. `add_skip` writes the `{version, reason}` shape.
- **4. A briefly held rename:** `msi::rename_retrying` retries os errors 5 and 32 (Windows only) 8 times, from 5 ms doubling to 320 ms (about 1.3 s, as `lodestar-search`'s index renames do). The helper uses it for the staging moves.
- **5. `ProgramFiles`:** a service's environment has it. When it's missing or empty, `msi::program_files` reads `ProgramFilesDir` from the registry (`reg query`), so detection doesn't fail safe into refusing every MSI install. The notifier's `signals` uses the same function.
- **6. The relaunch token:** above.

## Tests
- **On every OS** (`update::windows::helper`, `msi`, `check`):
  - it installs the verified copy, after copying and before stopping the service, from staging, with the fixed arguments, and keeps it with its pins;
  - an MSI swapped after its copy is never installed, and a wrong size or hash is refused;
  - a swapped envelope after its copy changes nothing;
  - a replayed, validly signed older manifest is refused;
  - not newer (same, older, an RC of the same release), an unparsed build version, an unchecked data folder, a staging folder that isn't private, another channel, a stale manifest, no MSI for the target, a damaged request or signature, a bad Authenticode signature;
  - `.lock` held: nothing written, the service started again; a service that won't stop;
  - a failed install skipped as `failed`; exit 3010 and an unhealthy service reported; `current\` and `previous\` rotated;
  - the request parser, the fixed `msiexec` arguments and exit codes, the `ProgramFiles` fallback, the task's XML (one boot trigger, SYSTEM, one action, the descriptor), the bounded rename retry, children's environments without `LODESTAR_*`;
  - 64 user skips don't push out a `failed` entry.
- **On the Windows CI job,** all of the above, plus:
  - the staging folder created private for real, and an inherited one refused;
  - Task Scheduler taking the definition (registered under a test name, read back: SYSTEM, highest, one boot trigger, the one action, `IgnoreNew`, the service's SID in the descriptor);
  - `tests/update_windows_msi.rs`: the real binary refuses outside Program Files and refuses `--config`, and the command is hidden.
- **The MSI build:** CI's jobs don't build the MSI (only `release.yml` does), so there's no WiX build check in CI. The new elements are checked to be well-formed XML. The release build compiles them, and G-m6's manual install covers them.
