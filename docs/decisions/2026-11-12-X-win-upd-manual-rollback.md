# X-win-upd-manual-rollback decisions (part 1: the helper's side)

Architecture §12.2 says manual Roll back "is always there": the previous version, while its snapshot is kept, through the same journal. On Windows it answers `not_built_yet` today (`docs/decisions/2026-11-11-PK-guide-3.md`). This PR builds the helper's side in `crates/lodestar/src/update/windows/rollback.rs`, the slice's only owned path. Nothing calls it yet, so Roll back still answers `not_built_yet` and the user guide stays right.

## What this part decides
- **A passed probation leaves a record, `installed.json`, in the helper's staging folder.** It holds the versions (`from`, `to`), the start type before the install, and the name of the pre-migration snapshot the install took. That snapshot is chosen by the same rule as an automatic rollback's step 2. The record exists because the journal goes when probation passes, and with it the list that tells the update's snapshot from older ones. It's kept in staging, which only SYSTEM and Administrators can write, so nothing in the data folder decides a rollback (the PK-win-upd-3 rule). The next install that passes replaces it, a finished rollback removes it, and one whose `to` isn't the running version, or isn't the MSI the helper keeps as `current\` (so a hand install or an older helper can't leave one that matches later), is never used. Writing it is best effort: if the write fails, no manual Roll back is offered for that install. A stale record is removed rather than kept.
- **The snapshot is recorded while it's certainly there, and its absence refuses** (`snapshot_missing`). Without the name, a snapshot that retention deleted would look like an update that never migrated. The store would then be kept, and the previous version handed a store it can't read. `None` means the install took no pre-migration snapshot, so it didn't migrate, and the store is kept.
- **The snapshot is checked again once the service has stopped** (step 1, before the marker or the skip). The plan is read while the service runs, and the service's retention purge could delete the snapshot in between. If it's gone, the service's start type is set back, the service is started again and the journal goes: nothing was changed. Step 2 also halts if `choose` finds anything other than the recorded snapshot.
- **A manual journal counts as touched only by its `touched` field.** It starts rolling back at step 0, so a halt before step 1 (no kept MSI) leaves the service running and clears the journal, as the automatic path does before it touches anything.
- **A manual Roll back is the failed-probation rollback's five steps, unchanged.** `manual_journal` builds a journal with `from` set to the recorded previous version and `to` set to the running one, already in the rolling-back state at step 0. Its `snapshots_before` lists every snapshot there now except the recorded one. So step 2's `choose` picks exactly that snapshot, or none, and the journal format doesn't change. An older helper that resumes it after the reinstall behaves the same. Crash safety, the marker, the stop and process checks, the pins check right before `msiexec`, the copy hand-off and the halts all come from the existing code.
- **A manual journal's id starts with `manual-`** (followed by the request's 1 to 32 lowercase hex digits). Only the wording and the skip reason depend on it. The halt texts open with "Lodestar's manual rollback from X to Y" instead of "failed its health check". The version goes into `skipped` as `manual` (already a reason the user can't undo, `check::refusing`), not as `failed`. An older helper ignores the prefix and only words a halt as a failed probation's.
- **The start type put back is the one at the time of the request,** read before step 1 disables the service. `start_before` is used when it can't be read or is already disabled.
- **It refuses rather than guess:** `busy` (a journal is in place); `no_previous_version` (no record, a record for another version, `from` not older, the MSI not kept or not matching its pins); `snapshot_missing`; `io` (a record that can't be read, an unknown format, versions that don't parse, a snapshot name that isn't a pre-migration snapshot beside the store, an invalid request id). The codes match the API's existing `rollback_unavailable` reasons, except `io`.

## What's left: the follow-up slice (needs files outside this slice's owned path)
1. **Blocking for wiring: scrub the snapshot before it's restored (content safety).** An automatic rollback restores the snapshot within minutes of the update. A manual one can come weeks later, within the 90-day retention. A snapshot restored as it was would bring back source purges' credentials and consent (SRC-14b), plus hashes deleted since (Store V12's journal). That would loosen a content-safety decision. SYSTEM never opens the store, so the service must run `snapshots::purge_for_restore` on the recorded snapshot (as `lodestar rollback` does) before it asks the helper. If the snapshot can't be scrubbed, the service refuses. The helper hashes the snapshot at step 2, after the service has stopped, so it restores the scrubbed copy.
2. **The helper's request** (`helper.rs`): a `rollback` request kind that calls `rollback::manual` after `resume`, plus its `result.json` and Event Log answers.
3. **The API** (`check.rs`): `rollback.available` and `rollback.reason` from a check the service can make. The service account may not be able to read staging, so the service needs a copy of the plan it is allowed to read. Roll back then writes the request and starts the helper's task, with a confirmation that names the torrents stored since the install, which are lost.
4. **Docs:** the user guide's "automatic rollback only" (`PK-guide-3`) changes once this is wired. `check.rs`'s and `windows/mod.rs`'s `not_built_yet` comments change too.
5. **More tests** (from the self-review): a manual journal resumed through `resume` at steps 0, 2 and 4; a failed `installed.json` write; a later install replacing the record; an automatic rollback of a newer install removing it.
6. **Tests on Windows:** CI's Windows job runs these unit tests. The real service and installer path needs the owner's manual M6 check.
