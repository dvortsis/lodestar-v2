# OP-2 decisions (fleet live mode for `screen`)

The slice builds `fleet.yml`'s live mode, behind `FLEET_LIVE=true`, as the plan's OP-2 row asks (`docs/plan/2026-11-08-cloud-operator.md` §3–§4). Nothing calls a cloud in CI or locally: every live path is tested with fakes for S3, the Linode API, Terraform, `ssh-keygen`, the Actions API and `/meta`. These are the choices the plan left open, or narrowed, plus the runner's binding refinements. None loosens §4's containment or widens a credential beyond the two exact keys below.

## Layout
- **New modules** (the runner added them to the slice's owns):
  - `apply.py`: the Terraform entry point and the live backend;
  - `linode.py`: a standard-library Linode client;
  - `audit.py`: the job-rule sweep and the firewall audit;
  - `requirements-live.txt`.
- **Live mode is selected in `fleet.py`'s context:** with `FLEET_LIVE=true` it builds the live backend and the S3 lock store. Dry-run keeps the in-memory ones. Both backends share one interface (`create`, `destroy`, `finish_down`, `audit`, `set_mismatch`, …), so the command logic is the same code in both modes.
- **`run <step>` refuses in live mode with "step not built (OP-3)"** (the runner). OP-2 supplies what OP-3 needs:
  - pinned host keys, and fingerprints in `fleet.json`;
  - rule-set writes that send only the writable fields (no `version` or `fingerprint` echoed back);
  - `LiveBackend.set_job_rules`, which opens or closes a job's `/32` on every fleet firewall under the lock;
  - `known_hosts()`.

## Credentials in the job
- **Credentials are minted only after the gates.** The live backend is built on first use, so `act` runs its gates, the stop check and the main-head check before any OIDC exchange, secret read or Linode call. A refused comment or a stale re-run never holds the role.
- **No third-party action holds a credential.** The job asks GitHub for its OIDC token and calls STS `AssumeRoleWithWebIdentity` itself, in-process. So `configure-aws-credentials` isn't used, and the AWS keys never reach `GITHUB_ENV` or a log. Only Terraform's own subprocess environment gets them, with the Linode token. That environment is built from a short allowlist (`PATH`, `HOME`, the temp directories, proxy settings), never the job's whole environment, which holds the GitHub and OIDC tokens. The `act` job's timeout is 50 minutes, under the role's one-hour session.
- **The Linode token** comes from `lodestar/akamai-fleet-token` in Secrets Manager, as a bare token or JSON with a `token` field. It goes only into the Linode client's `Authorization` header and Terraform's `LINODE_TOKEN`. The live modules contain no `print`, logging or `add-mask` (a test checks), and every error is a fixed string.
- **Two owner setup additions** (the runner approved both and flags them to the owner):
  - the repository variable `OWNER_SSH_PUBLIC_KEY` (the owner's public key, beside the control plane's on each Linode);
  - the `cloud-fleet` secret `FLEET_LINODE_ACCOUNT_EUUID`.
  Live mode refuses unless every setting is present and the token's `/account` matches that EUUID. A refusal names the missing settings, never their values.
- **boto3 comes from `requirements-live.txt`:** seven pure-Python wheels, pinned by hash, installed with `--require-hashes --target` into the runner's temp directory, and only when `FLEET_LIVE=true`. `--target` also keeps clear of Ubuntu's system-Python guard.
- **Terraform 1.10.5** comes from `hashicorp/setup-terraform`, pinned by full SHA, only when `FLEET_LIVE=true`.
- **Permissions:** `act`, `reaper` and `dispatch-down` gain `id-token: write`; the reaper, the only sweeping job here, gains `actions: read`. Every action is pinned by full SHA.

## Terraform
- **`apply.py` is the control plane's own entry point.** It runs `init` with the S3 backend's `-backend-config` (the fleet's fixed key), then `apply` or `destroy` with `-lock-timeout=5m`, retrying up to three times on a held state lock, and **never `force-unlock`**. All output goes only to the private evidence bucket (`fleet/<run>/…`). `terraform output -json` holds addresses, so it isn't stored at all. The `.ps1` scripts stay phrase-only.
- **The Terraform configuration is pinned per fleet.** Later commands run Terraform from a detached `git worktree` of the fleet's pinned commit, checked again as an ancestor of `main`, so a merge mid-session can't change what runs on the Linodes.
- **Refinement for the runner to flag (§2.19):** the plan says every later command "checks out that commit". Here `fleet.py` itself runs from `main`, so gate and safety fixes apply at once. The fleet's expiry and preset are fixed in `fleet.json` at `up`. A `limits.yaml` change mid-fleet (for example a list price, which the ledger uses) does apply to that fleet.
- **Host keys** (the runner's conditions):
  - **How they're made:** fresh for each fleet at each `up`, by `ssh-keygen` in the job, then passed to Terraform as the `sensitive` variable `host_keys` and installed by cloud-init (`ssh_keys`, with `ssh_deletekeys` and no other key types generated);
  - **What's stored:** only the public halves and their fingerprints go into `fleet.json`;
  - **What's never done:** they are never printed or written to a job log or artifact, and no workflow step handles them (a test checks).
  - **The residual:** the private host keys sit in the Terraform state in the state bucket (SSE-S3, role-scoped, old versions kept 30 days) and in each Linode's user-data until `down`. That's acceptable because each key is single-use and dies with its VM, and the bucket is readable only by the owner and `LodestarFleetOperator`.
  - **Why not Terraform's `tls` provider:** it would need a new provider and lockfile hashes, and `ssh-keygen` is on every runner.
- **Firewalls:** each firewall has `lifecycle { ignore_changes = [inbound] }`, so Terraform makes the admin rule and leaves job rules to the Linode API. The same applies to the manual path: a changed admin address now needs the firewall updated by hand or recreated.
- **New output:** `fleet_hosts` (sensitive): each role's address, firewall ID and admin `/32`s.
- **Manual path:** `extra_ssh_public_keys` and `host_keys` default to empty, so it is unchanged in its own account. **It must not run in the fleet's account while `fleet.yml` runs:** the audit treats any tagged firewall it didn't record as a mismatch, and `down` deletes everything tagged `lodestar` there. The plan's setup step 1 already makes that account dedicated; OP-3's runbook says it again.
- **The fleet doesn't set `main_extra_admin_ipv4_cidrs`:** the Windows lanes are human-run (plan, "The design"), so no Windows VM needs a tunnel to Main.

## State, the tombstone, the ledger and the flag
- **`fleet.json` is never deleted** (the runner's refinement). Once `down` leaves nothing tagged in the account, `finish_down` books the spend, writes the tombstone and clears the mismatch flag.
- **The first tombstone** is written by the control plane itself, the first time it reads a missing `fleet.json` (a real 404, which only `LodestarFleetOperator` can see) while nothing tagged exists. The write is conditional (`If-None-Match`). No setup step is needed.
- **"No fleet" comes only from a readable tombstone.** Any other read result raises `FleetUnknown`: an error, a 403, unparsable JSON, or a 404 while tagged Linodes exist. Then:
  - commands other than `down` refuse;
  - the status reads "a fleet may exist";
  - the reaper skips the firewall audit and escalates, and the 44 h age reap still runs.
- **New keys,** added exactly to `LodestarFleetOperator` in OP-2a's template, with policy-test assertions: the spend ledger `fleet/spend-ledger.json` (state bucket, Get and Put) and the mismatch flag `locks/fleet-mismatch.json` (control bucket, Get, Put and Delete, plus its list prefix). **The owner updates the stack before `FLEET_LIVE=true`.**
- **The ledger** holds each month's booked fleet compute, priced from `limits.yaml`. Accrual runs to the time of `down`, not to the expiry, so a fleet that outlives it is still billed. `up`'s cap check adds the running fleet's accrued cost. A fleet that crosses a month boundary is booked in the month it went down.
  - **Accepted gap:** a `down` with no readable fleet, and an age reap, book nothing, because the preset and start time aren't known. Terraform's `max_hourly_compute_usd` and the account's AWS Budgets alert still bound it.
  - **An unreadable ledger** raises its own error. `finish_down` writes the tombstone and clears the flag before it books, so an unreadable ledger never strands the fleet. `up` refuses while the ledger is unreadable (the cap fails closed), with its own message.
- **The mismatch flag is always present** once the first tombstone is written: `{"mismatch": false}`, overwritten, never deleted. Its meaning never rests on S3 answering 404 rather than 403, and anything but a readable `false` counts as a mismatch (fail closed). Before the first tombstone the flag reads as a mismatch, and with nothing in the account the reaper's next `down` writes it.

## `down`, the reaper and pre-emption
- **`down` always sweeps.** It runs `terraform destroy`, then deletes every Linode and firewall tagged `lodestar` in the fleet's account through the API, even with no fleet recorded. Whatever fails in the Terraform phase (a held lock, a failed `git worktree`, a missing binary, an unreachable evidence bucket), the API sweep still runs. It tries every delete, then checks what's left. That covers the plan's emergency path (a state lock that doesn't free) and **`down` with no `fleet.json`**. Only a tagged resource is ever deleted, and `linode.py` refuses any other.
- **The reaper's firewall audit runs under the lock.** It sweeps stale job rules first (fenced writes), then checks each tagged firewall:
  - enabled;
  - attached only to fleet Linodes;
  - `inbound_policy` DROP;
  - exactly the recorded admin rule;
  - job rules that are ACCEPT, TCP/22, one IPv4 `/32` inside `/meta`'s Actions ranges, at most one per run.
  A stale rule is one whose run isn't queued or in progress, or started more than 90 minutes ago; the Actions API answers. The audit reads every rule set, device list and run status before its first write, so a failed read sweeps nothing.
- **An audit that can't run** (GitHub `/meta` or the Actions API failing, or a Linode error) escalates with a fixed message and is **not** counted as a mismatch: a GitHub outage would otherwise destroy every fleet. Lifetime enforcement (the expiry, the 15-minute emergency, the 44 h age reap) runs regardless, so plan §3's "enforced twice" never depends on the audit.
- **On a mismatch** the reaper records the flag, puts the "reaping" marker over its own lock, and goes down.
- **A mismatch with no fleet recorded** still goes down whenever anything tagged exists. A stale flag with nothing left is cleared.
- **The overdue emergency** (more than 15 minutes past expiry) pre-empts without waiting, as in OP-1.
- **The marker** is released only once `down` has emptied the inventory. If tagged resources remain, it stays until its own 90-minute expiry, and the run reports "tagged resources remain; escalate". `down`-only holds meanwhile through the flag or the expiry.
- **The age reap** also deletes any tagged firewall left with no device. `up` refuses while any tagged firewall exists, not only a Linode, so a leftover firewall can't make the next fleet look mismatched.

## Limits
- **`max_fleets` is removed:** one fleet at a time is enforced by `up` refusing while anything tagged exists or a fleet is recorded.
- **`limits.load` refuses values outside the plan:** a monthly cap outside (0, 40] (the owner's $40), a lifetime over 44 h, a lock over 90 minutes, a grace period over 15 minutes, or a `max_fleets` key.

## Tests
- **Fakes** stand in for every outside service.
- **Coverage:**
  - the Linode client's tag refusals and account check;
  - every audit mismatch shape, plus the sweep and opening and closing job rules;
  - the tombstone rules, and that any read error means a fleet may exist;
  - `create` recording first and fencing (it stops before `apply` when the lock is lost), and the Terraform pin;
  - `destroy` retrying a held lock, never force-unlocking, then sweeping through the API while leaving untagged resources alone;
  - `finish_down`, the reaper's mismatch path end to end, and live `up`/`run`/`down`;
  - a leak check that no address, host key, fingerprint, EUUID, bucket name or public key reaches stdout, stderr or a comment.
- **The workflow tests** pin each job's exact permissions, allow pip only as the exact live-only line, and keep secrets in `env:` of the `fleet.py` step in `cloud-fleet` jobs.
- **Cloud-init** was rendered with `terraform console` (no providers, no network) in both modes, and the YAML checked: the private host key round-trips byte for byte.
- **Test polish from the OP-2a reviews:** the `terraform init` scan now sees quoted, `.exe`, path and variable spellings; the policy audit checks each policy's `Version`.
