# OP-2 decisions (fleet live mode for `screen`)

The slice builds `fleet.yml`'s live mode, behind `FLEET_LIVE=true`, as the plan's OP-2 row asks (`docs/plan/2026-11-08-cloud-operator.md` §3–§4). Nothing calls a cloud in CI or locally: every live path is tested with fakes for S3, the Linode API, Terraform, `ssh-keygen`, the Actions API and `/meta`. These are the choices the plan left open, or narrowed, plus the runner's binding refinements. None loosens §4's containment or widens a credential beyond the two exact keys below.

## Layout
- **New modules** (the runner added them to the slice's owns):
  - `apply.py`: the Terraform entry point and the live backend;
  - `linode.py`: a standard-library Linode client;
  - `audit.py`: the job-rule sweep and the firewall audit;
  - `requirements-live.txt`.
- **Live mode is selected in `fleet.py`'s context:** with `FLEET_LIVE=true` it builds the live backend and the S3 lock store. Dry-run keeps the in-memory ones. Both backends share one interface (`create`, `destroy`, `finish_down`, `audit`, `set_mismatch`, …), so the command logic is the same code in both modes.
- **`run <step>` refuses in live mode with "step not built (OP-3)"** (the runner). OP-2 supplies what OP-3 needs:
  - pinned host keys, and fingerprints in `fleet.json`;
  - rule-set writes that send only the writable fields (no `version` or `fingerprint` echoed back);
  - `LiveBackend.set_job_rules`, which opens or closes a job's `/32` on every fleet firewall under the lock;
  - `known_hosts()`.

## Credentials in the job
- **Credentials are minted only after the gates.** The live backend is built on first use, so `act` runs its gates, the stop check and (for `up` and `run`) the main-head check before any OIDC exchange, secret read or Linode call; the reaper and `dispatch-down` refuse a re-run first. A refused comment or a stale re-run never holds the role.
- **No third-party action holds a credential.** The job asks GitHub for its OIDC token and calls STS `AssumeRoleWithWebIdentity` itself, in-process. So `configure-aws-credentials` isn't used, and the AWS keys never reach `GITHUB_ENV` or a log. Only Terraform's own subprocess environment gets them, with the Linode token. That environment is built from a short allowlist (`PATH`, `HOME`, the temp directories, proxy settings), never the job's whole environment, which holds the GitHub and OIDC tokens. The `act` job's timeout is 50 minutes, under the role's one-hour session.
- **The Linode token** comes from `lodestar/akamai-fleet-token` in Secrets Manager, as a bare token or JSON with a `token` field. It goes only into the Linode client's `Authorization` header and Terraform's `LINODE_TOKEN`. The live modules contain no `print`, logging or `add-mask` (a test checks), and every error is a fixed string.
- **Two owner setup additions** (the runner approved both and flags them to the owner):
  - the repository variable `OWNER_SSH_PUBLIC_KEY` (the owner's public key, beside the control plane's on each Linode);
  - the `cloud-fleet` secret `FLEET_LINODE_ACCOUNT_EUUID`.
  Live mode refuses unless every setting is present and the token's `/account` matches that EUUID. A refusal names the missing settings, never their values.
- **boto3 comes from `requirements-live.txt`:** seven pure-Python wheels, pinned by hash, installed with `--require-hashes --target` into the runner's temp directory, and only when `FLEET_LIVE=true`. `--target` also keeps clear of Ubuntu's system-Python guard.
- **Terraform 1.10.5** comes from `hashicorp/setup-terraform`, pinned by full SHA, only when `FLEET_LIVE=true`.
- **Permissions:** `act`, `reaper` and `dispatch-down` gain `id-token: write`; the reaper, the only sweeping job here, gains `actions: read`. Every action is pinned by full SHA. `id-token: write` is job-wide, so the two third-party actions in those jobs (`actions/checkout`, `hashicorp/setup-terraform`) could mint the job's OIDC token too. That's accepted because both are pinned by SHA, and the role's trust names only `fleet.yml` at `main` in `cloud-fleet`.
- **Re-runs:** the reaper's and `dispatch-down`'s job `if:` require `github.run_attempt == 1`, as the gates do for `act`, and both commands check `GITHUB_RUN_ATTEMPT` again before any credential is minted. A re-run replays an old event with that run's old code, so it's refused.
- **The main-head check applies only to `up` and `run`,** the commands that create or use a fleet. The kill paths (the reaper, the owner's `down`, a comment `down`) never refuse because `main` moved on: with merges landing all day, the scheduled reaper's checkout is often a commit behind by the time it runs, and refusing would skip an hour of lifetime enforcement. **Trade-off:** a kill path may run code one merge older than `main`. That's accepted because it can only destroy tagged resources and clear state, never create anything or widen access, and a refused re-run already stops the stale-event case. `status` also skips it (read-only).
- **A kill path older than the fleet's pinned commit:** if its checkout predates the commit `up` recorded (a merge landed, then `up` ran, then an older run kills), the ancestor check fails, `destroy` skips Terraform, and the API sweep does the work. That still empties the account, but it leaves Terraform's state stale (resources it thinks exist) until the next `apply` refreshes it.
- **Lock retries are idempotent:** `acquire` treats a live `run` holder with this run's own ID as acquired, so a put whose response was lost (the retry gets a 412) doesn't strand the lock for 90 minutes. The first tombstone's conditional put re-reads once when it fails, and accepts only a tombstone.

## Terraform
- **`apply.py` is the control plane's own entry point.** It runs `init` with the S3 backend's `-backend-config` (the fleet's fixed key), then `apply` or `destroy` with `-lock-timeout=2m`, retrying once on a held state lock (see Timeouts), and **never `force-unlock`**. All output goes only to the private evidence bucket (`fleet/<run>/…`). `terraform output -json` holds addresses, so it isn't stored at all. The `.ps1` scripts stay phrase-only.
- **The Terraform configuration is pinned per fleet.** Later commands run Terraform from a detached `git worktree` of the fleet's pinned commit, checked again as an ancestor of `main`, so a merge mid-session can't change what runs on the Linodes.
- **Refinement for the runner to flag (§2.19):** the plan says every later command "checks out that commit". Here `fleet.py` itself runs from `main`, so gate and safety fixes apply at once. The fleet's expiry and preset are fixed in `fleet.json` at `up`. A `limits.yaml` change mid-fleet (for example a list price, which the ledger uses) does apply to that fleet.
- **Host keys** (the runner's conditions):
  - **How they're made:** fresh for each fleet at each `up`, by `ssh-keygen` in the job, then passed to Terraform as the `sensitive` variable `host_keys` and installed by cloud-init (`ssh_keys`, with `ssh_deletekeys` and no other key types generated);
  - **What's stored:** only the public halves and their fingerprints go into `fleet.json`;
  - **What's never done:** they are never printed or written to a job log or artifact, and no workflow step handles them (a test checks).
  - **The residual:** the private host keys sit in the Terraform state in the state bucket (SSE-S3, role-scoped, old versions kept 30 days) and in each Linode's user-data until `down`. That's acceptable because each key is single-use and dies with its VM, and the bucket is readable only by the owner and `LodestarFleetOperator`.
  - **Why not Terraform's `tls` provider:** it would need a new provider and lockfile hashes, and `ssh-keygen` is on every runner.
- **Firewalls:** each firewall has `lifecycle { ignore_changes = [inbound] }`, so Terraform makes the admin rule and leaves job rules to the Linode API. The same applies to the manual path: a changed admin address now needs the firewall updated by hand or recreated.
- **New output:** `fleet_hosts` (sensitive): each role's address, firewall ID and admin `/32`s.
- **Manual path:** `extra_ssh_public_keys` and `host_keys` default to empty, so it is unchanged in its own account. **It must not run in the fleet's account while `fleet.yml` runs:** the audit treats any tagged firewall it didn't record as a mismatch, and `down` deletes everything tagged `lodestar` there. The plan's setup step 1 already makes that account dedicated; OP-3's runbook says it again.
- **The fleet doesn't set `main_extra_admin_ipv4_cidrs`:** the Windows lanes are human-run (plan, "The design"), so no Windows VM needs a tunnel to Main.

## State, the tombstone, the ledger and the flag
- **`fleet.json` is never deleted** (the runner's refinement). Once `down` leaves nothing tagged in the account, `finish_down` books the spend, writes the tombstone and clears the mismatch flag.
- **The first tombstone** is written by the control plane itself, the first time it reads a missing `fleet.json` (a real 404, which only `LodestarFleetOperator` can see) while nothing tagged exists. The write is conditional (`If-None-Match`). No setup step is needed.
- **"No fleet" comes only from a readable tombstone.** Any other read result raises `FleetUnknown`: an error, a 403, unparsable JSON, or a 404 while tagged Linodes exist. Then:
  - commands other than `down` refuse;
  - the status reads "a fleet may exist";
  - the reaper skips the firewall audit and escalates, and the 44 h age reap still runs.
- **New keys,** added exactly to `LodestarFleetOperator` in OP-2a's template, with policy-test assertions: the spend ledger `fleet/spend-ledger.json` (state bucket, Get and Put) and the mismatch flag `locks/fleet-mismatch.json` (control bucket, Get and Put only; corrected in OP-2b, see the flag's grant below). **The owner updates the stack before `FLEET_LIVE=true`.**
- **The ledger** holds each month's booked fleet compute, priced from `limits.yaml`. Accrual runs to the time of `down`, not to the expiry, so a fleet that outlives it is still billed. `up`'s cap check adds the running fleet's accrued cost. A fleet that crosses a month boundary is booked in the month it went down.
  - **Accepted gap:** a `down` with no readable fleet, and an age reap, book nothing, because the preset and start time aren't known. Terraform's `max_hourly_compute_usd` and the account's AWS Budgets alert still bound it.
  - **An unreadable ledger** raises its own error. `finish_down` writes the tombstone and clears the flag before it books, so an unreadable ledger never strands the fleet. `up` refuses while the ledger is unreadable (the cap fails closed), with its own message.
- **An `up` that fails after its first write** (keygen, the pinned worktree, init, apply, a timeout, the outputs, or the slot write) sets the flag to `true` before it re-raises. `fleet.json` already holds the expiry, so the reaper enforces it either way; the flag makes commands down-only meanwhile, and the next reaper goes down, so a half-built fleet never waits out its lifetime.
- **The mismatch flag is always present** once the first tombstone is written: `{"mismatch": false}`, overwritten, never deleted, so its meaning never rests on S3 answering 404 rather than 403. It has three readings (the runner's call, §2.26):
  - **readable `true`:** the reaper goes down;
  - **readable `false`:** nothing;
  - **unreadable** (missing, malformed or denied): commands stay down-only (fail closed), the reaper escalates "mismatch flag unreadable" and never destroys on it, and lifetime enforcement goes on.
  - **Its IAM grant** is `GetObject` and `PutObject` on the one key, with no `DeleteObject` and no list prefix: nothing deletes it, and no code needs a 404 for it.

## `down`, the reaper and pre-emption
- **`down` always sweeps.** It runs `terraform destroy`, then deletes every Linode tagged `lodestar` in the fleet's account through the API, even with no fleet recorded. Whatever fails in the Terraform phase (a held lock, a timeout, a failed `git worktree`, a missing binary, an unreachable evidence bucket), the API sweep still runs.
  - **The sweep's order:** it tries every Linode delete, then lists again. Firewalls go only if no tagged Linode is left, and then only those with no device, so a Linode that survives keeps its firewall.
  - **When anything is left,** `destroy` sets the mismatch flag, so commands go down-only and the reaper retries hourly.
  - **On the paths that have already pre-empted** (the reaper's emergency, the owner's `down`), a lock read that fails (S3) doesn't stop the sweep; losing the lock to someone else still does. That covers the plan's emergency path (a state lock that doesn't free) and **`down` with no `fleet.json`**. Only a tagged resource is ever deleted, and `linode.py` refuses any other.
- **The reaper's firewall audit runs under the lock.** It sweeps stale job rules first (fenced writes), then checks each tagged firewall:
  - enabled;
  - attached only to fleet Linodes;
  - `inbound_policy` DROP;
  - exactly the recorded admin rule;
  - job rules that are ACCEPT, TCP/22, one IPv4 `/32` inside `/meta`'s Actions ranges, at most one per run.
  - **Attachments:** each tagged Linode must sit behind exactly one firewall (`/linode/instances/{id}/firewalls`), and it must be recorded and tagged; every recorded firewall must still exist and be tagged. That catches a fleet firewall that was deleted, untagged or detached, which a check over tagged firewalls alone can't see.
  - **For the owner (the runner flags it):** Linode's newer "Linode Interfaces" attach firewalls per interface, and `/linode/instances/{id}/firewalls` may not list those. This check holds while the Terraform module attaches its firewall through the instance's `firewall_id` (legacy config interfaces), as it does now. A change to Linode Interfaces must also change this check, or it would see every fleet Linode as unprotected and go down.
  - **Stale rules:** a rule is stale when its run isn't a `fleet.yml` run at the label's attempt, isn't queued or in progress, or started more than 90 minutes ago; the Actions API answers.
  - **Failed lookups:** a lookup that fails (the Actions API erroring or denying) counts as not live, so that rule is swept (fail closed). The reaper reports "N job-rule lookups failed, so those rules were swept; escalate". The cost is a live job losing its SSH, which fails that job; a rule an attacker could keep open by making lookups fail is worse.
  - **Read before write:** the audit reads every rule set, device list and attachment before its first write.
- **An audit that can't run** (GitHub `/meta` failing, `fleet.json` turning unreadable mid-audit, or a Linode error) escalates with a fixed message and is **not** counted as a mismatch: a GitHub outage, or one failed S3 read, would otherwise destroy a healthy fleet. Lifetime enforcement (the expiry, the 15-minute emergency, the 44 h age reap) runs regardless, so plan §3's "enforced twice" never depends on the audit. With `fleet.json` unreadable the reaper still sweeps stale job rules, and skips only the comparison with recorded admin rules and firewalls.
- **On a mismatch** the reaper records the flag, puts the "reaping" marker over its own lock, and goes down.
- **A mismatch with no fleet recorded** still goes down whenever anything tagged exists. A stale flag with nothing left is cleared.
- **The overdue emergency** (more than 15 minutes past expiry) pre-empts without waiting, as in OP-1.
- **The marker** is released only on a confirmed empty inventory. If tagged resources remain, or anything unexpected is raised, it stays until its own 90-minute expiry, and the run escalates. `down`-only holds meanwhile through the flag or the expiry.
- **The age reap** also deletes any tagged firewall left with no device. `up` refuses while any tagged firewall exists, not only a Linode, so a leftover firewall can't make the next fleet look mismatched.

## Timeouts
Every Terraform call has a subprocess timeout, and a timeout counts as a failure: init 2 min, apply 12 min, destroy 5 min, output 1 min, with `-lock-timeout=2m` and 2 attempts (only a held lock is retried). A killed Terraform can leave its `.tflock` in S3. The control plane never removes it (no `force-unlock`): later Terraform runs then fail, `down`'s API sweep still runs, and the owner clears the lock.
Other calls are bounded too: each Linode, GitHub and OIDC HTTP call 30 s; each AWS call (S3, STS, Secrets Manager) 10 s to connect and 30 s to read, at most 3 attempts; `git ls-remote` 60 s; each `git worktree` call 30 s. Worst case per job, in minutes. **The assumption:** the slow parts (Terraform, the reaper's lock wait) run to their limits, and the other calls are slow but answer, at a few seconds each, not at their caps:
- **The reaper (40-minute job):** setup (checkout, Terraform, pip) 3; the lock wait 5; the audit, about 15 Linode, GitHub and S3 calls plus one Actions lookup per job rule, 4; the re-read and re-decide 1; `down`: worktree 1, init 2, two destroy attempts 10, the API sweep and re-lists 3, finish (tombstone, flag, ledger) 1; the status and escalation 1. That's 31 minutes.
- **`dispatch-down` (40 minutes):** setup 3, no lock wait and no audit, then `down` 17 and the status 1. That's 21 minutes.
- **`act` (50 minutes):**
  - `up`: setup 3, `ls-remote` 1, keygen and worktree 1, init 2, two apply attempts 24, output 1, writes 1. That's 33 minutes. (`act` never waits for the lock: it answers "busy, retry".)
  - `down`: setup 3, `down` 17, the status 1. That's 21 minutes.
- **With every call at its cap,** the reaper comes to about 44 minutes, over its 40-minute job timeout. The timeout is the fail-closed backstop: a killed reaper leaves the "reaping" marker or its lock, which expires within the lock's 90 minutes; the flag and the expiry keep commands down-only meanwhile, and the next hour's reaper carries on. Each job's timeout stays under the lock's 90 minutes (a test checks).
- **Reporting is best-effort:** a comment or status post that fails prints a fixed line and the run carries on, so a GitHub outage (which also fails run lookups) never stops enforcement. A failed lock release is reported, and the lock then expires on its own.
- **Credentials:** the role's 1-hour session outlasts both jobs.
- **Pinned worktrees** are removed after each use.

## Limits
- **`max_fleets` is removed:** one fleet at a time is enforced by `up` refusing while anything tagged exists or a fleet is recorded.
- **`limits.load` refuses values outside the plan:** a monthly cap outside (0, 40] (the owner's $40), a lifetime over 44 h, a lock over 90 minutes, a grace period over 15 minutes, or a `max_fleets` key.

## Tests
- **Fakes** stand in for every outside service.
- **Coverage:**
  - the Linode client's tag refusals and account check;
  - every audit mismatch shape, plus the sweep and opening and closing job rules;
  - the tombstone rules, and that any read error means a fleet may exist;
  - `create` recording first and fencing (it stops before `apply` when the lock is lost), and the Terraform pin;
  - `destroy` retrying a held lock, never force-unlocking, then sweeping through the API while leaving untagged resources alone;
  - `finish_down`, the reaper's mismatch path end to end, and live `up`/`run`/`down`;
  - a leak check that no address, host key, fingerprint, EUUID, bucket name or public key reaches stdout, stderr or a comment.
- **The workflow tests** pin each job's exact permissions, allow pip only as the exact live-only line, and keep secrets in `env:` of the `fleet.py` step in `cloud-fleet` jobs.
- **Cloud-init** was rendered with `terraform console` (no providers, no network) in both modes, and the YAML checked: the private host key round-trips byte for byte.
- **Test polish from the OP-2a reviews:** the `terraform init` scan now sees quoted, `.exe`, path and variable spellings; the policy audit checks each policy's `Version`.
