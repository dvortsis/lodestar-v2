# B-held-precommit decisions: no window between a new hold's commit and intake refusing it

The follow-up to `2026-10-31-B-held-exact.md` (#287), from its review's optional item 4. No schema change, no API change, no new metric or log event. Content safety is tightened, not loosened: from before any path's store commit that holds a hash until that path's reconcile, intake refuses the hash, and afterwards the set follows the store as #287 proved.

- **A pending guard in `HeldSet` (§20.3).** `HeldSet` now keeps two things under its one lock: the held set, and a count of pending marks per hash. `contains` is true for a held or a pending hash.
  - **`pend(hashes) -> Pending`** marks a batch's hashes before its store commit.
  - **`Pending::settle(held_among)`** runs after the commit, or after its rollback or failure. Under the write lock, one `CHECK_CHUNK` at a time, it asks the store which hashes it holds, inserts those, and takes one mark off every hash: #287's `insert_held` plus clearing the marks.
  - **`remove_released` only touches the held set,** never a mark, so a release's M can't make a pending hash fetchable. This meets the brief's "never removes a pending hash" in a different shape. M may remove the hash's *held* entry while the mark keeps it refused. The batch's own reconcile then reads the store after C and puts the entry back if the store holds it. Skipping pending hashes in M instead would be worse after a rollback. M would leave a held entry that the store had released, and a reconcile that only inserts would never take it out.
  - **Marks are counted, not a set,** so two in-flight batches marking one hash (the writer and a `correct`) don't clear each other's mark.
- **Why the obvious "insert before C" alone is unsafe** (as the brief says). A release's M between the pre-insert and C reads the store as not holding the hash and removes it. Intake then lets it through until the reconcile after C. A mark lives apart from the held set, and only its own batch's settle clears it, so this can't happen.
- **All four paths mark before C:**
  - **The sweep and backfill.** They decide what they hold inside `enrich.rs` and commit in the same function. New `refile_candidates_marking` and `enrich_stored_marking` call a `mark` callback with the hashes just before the store write. The old functions call these with a no-op, so other callers and tests don't change. The sweep marks every candidate it judged held, a superset of what the store ends up holding (a candidate already gone isn't held). The settle reads the store, so the extra ones aren't inserted.
  - **The ingest commit.** It marks the swarm hashes of every committing torrent whose verdict is Drop or Quarantine. Those are exactly the ones `transaction` partitions into `blocked`. It settles on the blocking thread right after `transaction`, whether that committed or failed. The blocked arm's unconditional `held.insert` is gone. Before, in the order C, S, M, I, that insert kept a released hash refused until the next start. It is now exact.
  - **`correct` (API).** It marks the refilings' held hashes before `set_enrichments_at`. Afterwards it settles against the store, whether the write landed or the generation check refused it. Its unconditional insert is gone too.
  - **Owned paths.** `crates/pipeline/src/enrich.rs` wasn't in the brief's "Own". The two `_marking` variants are the smallest hook that marks before C without changing `Backfill` (11 test constructions). The runner was told when the work started.
- **Fail closed.** `Pending` is `#[must_use]`. Dropped without a settle (a `?` return in `correct`, a panic), its hashes move into the held set. If a settle's store query fails, that chunk and every later one go into the held set, as in #287. Either way they stay refused until a release reconciles them against the store or the next start. A mark is never just dropped, and none is left behind, so pending stays bounded: one batch per writer arm (they run one at a time on the writer task) plus the API's in-flight corrections. A later release reconcile only removes them if the store doesn't hold them, so this is never loose.
- **The interleavings traced.** P is the pre-mark, C the store commit (or rollback), Q+I the settle, S a release's store delete, M its locked reconcile, V a non-release rule change. #287's 11 still hold: Q+I is #287's Q+I plus the unmark, and before P nothing changed.
  1. P, C, Q+I, then S, M: #287's case 1. **Released.** The mark is gone.
  2. P, M, C, Q+I. M reads "not held" (C hasn't run yet) and removes the old held entry, if one existed. The mark keeps the hash refused. C holds it, and Q+I reads that and inserts it. **Held**, refused throughout.
  3. P, S, M, C, Q+I. As 2: the release's delete ran before the batch's insert, so the store ends holding the hash. **Held**, refused throughout.
  4. P, S, C, M, Q+I. M reads the hash held and keeps it, and Q+I inserts it. **Held.**
  5. P, C, S, M, Q+I. M reads it released and removes the held entry, while the mark keeps it refused. Q+I reads it released and doesn't insert it. **Released** once Q+I clears the mark, which is exact.
  6. P, C, S, Q+I, M. Q+I reads it released. M removes nothing. **Released.**
  7. P, C (rolled back or failed), Q+I. The store doesn't hold the hash, unless an older hold does. Q+I inserts exactly what the store holds and clears the mark. **No pending and no held entry for a hash the store doesn't hold.** A rollback with M anywhere in between ends the same way.
  8. P, V, C. The sweep and backfill commits check the version or generation inside their transaction and refuse: this is case 7. The ingest commit and `correct` commit whatever their verdict was, and Q+I reads the store, so it's #287's case 8. **Held, as the store has it.**
  9. **Intake between P and Q+I.** `contains` is true at every point, because only that batch's settle takes its mark off. At Q+I the hash is inserted under the same lock that clears the mark, so a read never sees neither.
  10. **Two batches marking one hash.** Each mark is counted. The first settle leaves the second mark in place, so the hash stays refused until the second settle reads the store.
  11. **An error between P and Q+I** (a `?` or a panic). The `Pending` drop moves the hashes into the held set: refused, never loose.
  12. **A crash anywhere.** Marks live only in memory. At restart the set is loaded from `filter_state().held`, the same tables `held_among` reads, so after a restart the set equals the store's. A crash before C loses the uncommitted batch, and nothing holds the hash. After C, the store holds it and the reload refuses it.
  13. M and Q+I can't interleave inside each other: both take the write lock per chunk, as in #287. Exactness is per hash.
- **The cost.** Marking takes the write lock once per batch with holds. Batches with no holds skip it: the ingest path checks for an empty set, and an empty mark is a cheap lock round. Settle costs what #287's `insert_held` cost, on the same hashes or a few more (the sweep's superset).
- **Tests** (deterministic, through hooks, no sleeps):
  - `a_new_hold_is_refused_from_before_its_commit` (writer): covers the sweep, backfill and the ingest commit. A test-only `Writer::marked` hook runs right after P. It runs M with the store's pre-C answer ("not held") and asserts that the hash is still refused while its old held entry is gone. `between` runs after C, before Q+I, and asserts that every hash the store holds is refused and still pending. At the end the hash is held, no mark is left, and the set equals the store's (restart) holds.
  - `a_rolled_back_batch_leaves_nothing_refused` (writer): the rules move between the sweep's P and C, so the store refuses the write. Afterwards the hash isn't refused, no mark is left, and the set equals the store's.
  - `a_correction_relabelling_a_torrent_adult_meets_the_adult_only_core` (API) now also checks that `correct` leaves no mark and that the set equals the store's.
  - `HeldSet` unit tests cover P, M, C and Q+I step by step, a rolled-back mark, counted marks, and the fail-closed drop and failing settle.
- **#287's nits.** `CHECK_CHUNK` now sits above `HeldSet`'s doc comment, so `HeldSet` gets its doc back. #287's "Errors fail closed" bullet now says "that chunk and every later one". That is an edit to another slice's decisions file, which the brief directed.
