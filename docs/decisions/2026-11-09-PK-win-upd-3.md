# PK-win-upd-3 decisions: the MSI's probation and rollback

The update helper (PK-win-upd-2, #640) now runs probation after it installs an MSI. When probation fails it rolls back: the store first, then the previous MSI, with the service disabled meanwhile (architecture §12.2; plan Q13 rule 2; B-update-r2's store-before-MSI order). A probation or rollback interrupted by a crash or a restart is finished by the next run. The code is in `crates/lodestar/src/update/windows/rollback.rs` and `helper.rs`. Calls marked "runner" are the runner's under §2.19; the owner can veto them.

## The journal
- **`journal.json` in the helper's staging folder** (`%ProgramFiles%\Lodestar\updates`, SYSTEM and Administrators only), not `<data>\bin\rollback.json` (runner).
  - Q13 rule 2 keeps the rollback side in the SYSTEM-only folder, and nothing the service account can write decides a rollback.
  - Unix's `journal.rs` (overlay-based, `cfg(unix)`) is unchanged; its format isn't reused, because the Windows steps differ.
- **Written by temporary file and rename after each step.** On Windows the rename isn't write-through, so a power cut can bring back the step before. Every step is idempotent, so repeating it is safe.
  - A journal that can't be read refuses the run rather than guess.
- **`result.json` stays display only** (#640 security review item 4). Nothing reads it back; a test plants a misleading one and shows it decides nothing. A halt's reason stays in the journal, not in `result.json`.

## Probation
- **The `Installing` journal is written before `msiexec` runs.** It records the version installed from, the version installed, and the store's snapshot names then.
  - If those names can't be listed, the install is refused. Without the list, a rollback couldn't tell the failed version's snapshot from a months-old one.
- **Passing:** the new service reaches Running within 5 minutes and stays there for 60 s. One failure rolls back.
- **The next run tells what happened from the helper's own version.** That is the program on disk, a fact only SYSTEM and Administrators can change:
  - **still `from`, after exit 3010:** Windows hasn't restarted yet, so nothing is judged and nothing is started;
  - **still `from`, otherwise:** the install never finished. The journal goes, the service is set to automatic start and started, and the run reports `install_interrupted`;
  - **`to`:** the service is set to automatic start (a crash inside a rollback's first step can leave it disabled), started, and probation is judged;
  - **anything else:** someone installed another version by hand. The journal and the marker are dropped, and that is also how an administrator recovers from a halt.

## `--resume` is the boot run (runner)
- The task runs only `lodestar.exe update-helper`, as Q13 has it, so the boot trigger takes no other argument.
- Every run, at boot or on demand, finishes a journal first, before it reads any request. That is §12.2's `--resume`; there's no separate flag.

## The rollback
1. **Stop the service.**
   - Its start type is set to **disabled**, not manual (runner). The SCM's failure actions restart a crashed service even when it's set to manual; they can't start a disabled one. Architecture line 2889 says manual; disabled is strictly stronger.
   - The service is stopped, and nothing may still run as its account.
   - Then, under `.lock`, the marker `<data>\bin\rollback.json` is written. The store openers that call `cli::util::refuse_during_update_rollback` refuse while it exists (§12.2).
   - **Why it's in the data folder (runner's item c, corrected):** `serve` runs as the service account, which can't read the SYSTEM-only staging folder, so a marker there couldn't be seen.
   - A marker someone else plants there can only make store openers refuse. The helper never reads it, and nothing ever runs from it.
   - The service started by the SCM checks it too, before the store opens (`windows/service.rs`, runner, 2026-11-09). It reports the refusal through its existing path: `%SystemRoot%\Temp\lodestar-service.log`, and exit code 3, which the SCM records in the System event log.
   - The failed version is marked `failed` in `skipped`.
2. **Choose the snapshot** (the journal already says "rolling back", written with the start type before the first change, so a crash from here on resumes the rollback rather than judging probation again) by name alone: the earliest pre-migration snapshot the failed version took (`<stem>.pre-v<N>[.<k>].db`, one not there before the install). Its SHA-256 is recorded, hashed through a handle that never follows a link.
   - This happens after the stop, so the snapshot can't still be changing.
   - SYSTEM never opens the store. A planted snapshot gains nothing: the service account can write the store itself, and the old version checks the store when it opens it.
   - No new snapshot means the failed version never migrated, and the store is kept.
3. **The store first.** The service is stopped again and its processes checked again. Then, beneath the pinned data folder, the snapshot is renamed over `lodestar.db`: its `-wal`, `-shm` and `-journal` are removed first, and the snapshot is checked to be a regular file right before the rename. Then the marker goes.
   - A repeat that finds the snapshot gone and the store at its SHA-256 counts the step done.
   - A snapshot changed since it was chosen halts the rollback, and so does one with its own `-journal` or `-wal` beside it: it was mid-write, and SYSTEM never opens SQLite to settle it.
   - If the marker can't be removed, the step isn't recorded done, and the next run retries it.
4. **Then the previous MSI.** The service is stopped and checked again. The MSI is found by its pins (version equal to `from`, size, SHA-256) in staging's `previous\` (as the install leaves it) or `current\` (when the install was interrupted before it rotated them).
   - The pins are checked before step 1 and again right before the MSI runs. This is rule 4's one exception: the journal's rollback target with SYSTEM-held pins.
   - `MajorUpgrade AllowDowngrades="yes"` reinstalls it, logging to its own `msiexec-rollback.log` so the failed install's log stays.
5. **Back to the start type the service had before the rollback** (runner, item a), recorded in the journal before the first change. A disabled one counts as delayed automatic, since only this helper disables it. The MSI's ServiceInstall already resets it to automatic during step 4.
   - Then the service is started. The reinstalled MSI becomes `current\` again; that step counts as done once `current\` holds `from`'s pins. Then the old version's health is checked and reported (`rolled_back`, with `healthy`).

## Stops
- **Transient** (the service won't stop yet, a process lingers, `.lock` stays held, Windows Installer is busy or won't start): the journal stays, the service stays disabled, and the next run retries (`rollback_pending`).
- **Final:** the run halts, and as §12.2 says, neither version starts.
  - Before step 1 nothing was changed, and the service is left as it is.
  - **Before the rollback touched the service** (no MSI kept, or a tampered one): nothing was changed. The halt is reported and the journal is dropped, so later updates still run.
  - **After it:** the service is disabled and stopped again, in case Windows Installer's own rollback or the SCM started it. The marker stays while the store isn't restored.
  - **Every halt** writes, to the Event Log (Application, source "Lodestar update helper") and to `result.json`'s `detail`, which step stopped and why. It also says how an administrator recovers (runner, item b):
    1. read the journal and the `msiexec` logs;
    2. install the `from` MSI by hand, or restore a backup;
    3. once the store is one the installed version reads, delete the marker and the journal, then `sc config Lodestar start= delayed-auto` and `sc start Lodestar`.

    Installing a version other than `from` and `to` drops both files by itself. Neither file starts anything.
- **A refusal before the journal is reached** (the data folder fails its ACL check, the staging folder isn't private, the journal can't be read) leaves everything as it stands. In the middle of a rollback that means the service stays disabled, so neither version starts until the cause is fixed and the next run finishes. The refusal is the task's last result (exit 3).

## The first update after a manual install (runner, flagged)
- **The helper caches only MSIs it installed.** So the first update after a manual MSI install has no kept MSI for `from`: a failed probation halts before anything is changed, and leaves the new version running.
- Refusing the install instead would block every first update. Windows Installer's own cache of the installed package isn't used: it isn't a pinned, verified copy.

## §12.2 steps not done on Windows (flagged to the owner; follow-ups)
- **`history.json`** (the rollback's reason and loss count): Windows has no install history yet (PK-win-upd-1). The outcome is in `result.json` and the journal.
- **Removing the failed version's newer search-index folders** (step 5): the old version uses its own index folder, so a newer one only costs disk until a later cleanup.
- **The old version's rollback notice** (step 8) on the Updates screen: the `install_failed` notice from `result.json` covers it for now. Its own wording is the web owner's.
- **Three attempts before a rollback:** one failed probation rolls back. The Windows service has no supervisor to count restarts.
- **The self-test probation** (store open and migrated, `/healthz`, a timer that starts after migrations): probation is Running held for 60 s. The Windows service reports Running before it opens the store, so a migration that runs past 60 s and then fails isn't caught until the next run. Confirming the running version and `/healthz` needs the service to report to SYSTEM.
- **Unix's source-purge scrub** (SRC-14b) before a snapshot is restored: a restored store may hold torrents a source purge had removed, until the next purge runs.

## Accepted risk (runner, flagged)
- A compromised service account can force a one-level downgrade by failing probation (crashing during it).
  - That reinstalls the previous MSI, whose own helper may predate this slice's hardening, and marks the new version skipped.
  - It's bounded to the one previous version the helper itself installed and verified.

## #640's security review items
1. **The task's `<Command>` is quoted** (`msi.rs`). The task never depends on how a command line with a space is rebuilt. The Windows CI test reads it back quoted.
2. **The version floor on a first install.** The helper's own trust state is merged forward-only (`TrustState::merge`) with the data folder's `trust.json` when that loads.
   - The data folder's statements are taken (each verified under the embedded recovery key when the file loaded) and its channel marks, so a key rotation the service saw doesn't reset the marks.
   - Never its revocation list: an entry needs only to parse as a key, so the service could pad it, and that would land in the helper's own state.
   - Marks more than a day ahead fail the check's plausibility rule. The service can delay installs, never allow one.
   - So on a first install, a replayed older, still unexpired manifest is refused (`older_than_mark`) once the service has seen a newer one. The service can only raise the marks, within the check's plausibility bound of a day ahead, which refuses more and never less.
   - A damaged data-folder `trust.json` is ignored.
3. **The race in `secure-datadir.ps1`** between its link scan and `Set-Acl` propagation. Whether that propagation follows a junction isn't something this slice could confirm.
   - So the helper makes sure the race can't be used: before `msiexec` runs, nothing may run as `NT SERVICE\Lodestar` (`tasklist` filtered by that account). Otherwise the install is refused (`service_processes`) and the service is started again.
   - Each rollback step that changes the data folder or runs an installer checks the same.
   - A Windows CI test runs the same filter for SYSTEM, which always has processes, so a filter that silently matched nothing would show.
   - `secure-datadir.ps1` is unchanged.
4. **`result.json` display only:** above.

## Tests (every OS, and the Windows CI job)
- **A full rollback, call by call:**
  - the store is the old one when the previous MSI runs;
  - the marker is present during the restore and gone after;
  - the service is disabled until step 5;
  - the failed version is skipped;
  - the old MSI is current again;
  - the reinstall has its own log.
- **A crash at every call of the rollback is finished by the next run.** That includes the hooks after the snapshot is chosen, inside the restore (between removing the side files and the rename), and after the last rotation. The previous MSI is never reinstalled once its step is recorded.
- **Resume and probation:**
  - a crash during the install, judged by the program on disk (interrupted, or installed then judged);
  - exit 3010: no probation before the restart, judged after it;
  - a manual install drops the journal.
- **Halts:**
  - a tampered, mismatched or missing previous MSI, or one only planted in the data folder: halted before anything changes;
  - a halt after the stop leaves the service stopped on manual start;
  - a snapshot changed since it was chosen halts before the restore, keeping the marker;
  - a journal naming a snapshot that isn't beside the store halts.
- **Snapshots:** a snapshot from before the install is never restored.
- **The trust floor:**
  - a process left as the service's account blocks the install;
  - the data folder's marks refuse a replayed older manifest on a first install;
  - its revocations never reach the helper's state;
  - a damaged data-folder `trust.json` is ignored.
- **The hand-off:**
  - an install handed to the copy and finished by the next run, with nothing touched while the copy runs;
  - a rollback's reinstall handed off, with the store restored before the copy runs the old MSI;
  - the copy runs only the pending MSI (refusing one outside staging or not matching its pins, or with no pending run);
  - a failed copy never falls back to Program Files;
  - the copy is the helper's own bytes under a fresh name, with earlier copies cleaned;
  - the copy must sit in the staging folder.
- **The service:** refuses its start on the marker.
- **Windows CI:** `tasklist` counted for real.
- No fixed sleeps. The crashes are panics at a chosen call, caught.

## `msiexec` from a copy of the helper (runner, 2026-11-09; flagged to the owner)
- **Why:** the helper runs from `%ProgramFiles%\Lodestar\lodestar.exe`, the folder `msiexec` replaces. With Restart Manager off, an in-use file is only replaced at the next restart (exit 3010).
  - On a rollback, the failed version's binary would stay on disk, and the MSI's own StartServices would start it on the just-restored store, which it would migrate again. That's exactly what store-before-MSI prevents.
  - On the forward path, the old binary would run until a restart.
- **How Q13's "runs only `lodestar.exe update-helper` from Program Files" works now:** the scheduled task still runs only that. Inside the helper, each `msiexec` run (install or rollback) goes through a copy:
  1. **The run is recorded first.** The journal names the pending run: its purpose, the MSI inside staging, its log, and its pins.
  2. **The copy is made safely.** The helper checks the staging folder (its ACL as for every other write there, and that it isn't a reparse point) and pins it. It copies its own image to a fresh, unpredictable name, `run-<32 hex>.exe`: created new, never over a file or through a link, and flushed. The copy is then held open read-only, sharing only reading, and its SHA-256 must equal the running helper's own image, or nothing runs.
  3. **The hand-off.** The helper starts the copy with the one argument `update-helper --run-msi` and a clean environment, then ends. From there the copy's own running image can't be written or deleted.
  4. **The copy's run.** The copy refuses unless it sits directly in `<program files>\Lodestar\updates` under that name. It takes `msiexec.lock` in staging and waits up to 2 minutes for the program in Program Files to end. It runs only the journal's pending `msiexec`, whose MSI must be inside staging and still match its pins. It writes the exit code to `msiexec-result.json` (with the journal's id and the run's purpose), then starts the task again.
  5. **The run that follows** finishes from that answer: probation after an install, or step 5 after a rollback's reinstall.
     - A copy still running (its lock is held) means a run touches nothing.
     - A copy that died leaves no answer: an install is then judged by the program on disk, and a rollback's reinstall is handed off again.
- **Copies can't remove themselves.** The next helper run removes every `run-*.exe` in staging, except one still running.
- **A copy that can't be made or started refuses the install** (`helper_copy_failed`, nothing changed, the service started again). During a rollback it's retried on the next run. Nothing ever falls back to running `msiexec` from Program Files.
- **The CLI's hidden `--run-msi` flag** is in `cli/update_helper.rs`.
