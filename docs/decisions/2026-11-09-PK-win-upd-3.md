# PK-win-upd-3 decisions: the MSI's probation and rollback

The update helper (PK-win-upd-2, #640) now runs probation after it installs an MSI, and rolls back when probation fails. The order is the store first, then the previous MSI, with the service on manual start meanwhile (architecture §12.2; plan Q13 rule 2; B-update-r2's store-before-MSI order). A rollback or probation interrupted by a crash or a restart is finished by the next run. The code is in `crates/lodestar/src/update/windows/rollback.rs` and `helper.rs`. Calls marked "runner" are the runner's under §2.19; the owner can veto them.

## The journal
- **`journal.json` in the helper's staging folder** (`%ProgramFiles%\Lodestar\updates`, SYSTEM and Administrators only), not `<data>\bin\rollback.json` (runner).
  - Q13 rule 2 keeps the rollback side in the SYSTEM-only folder, and nothing the service account can write decides a rollback.
  - Unix's `journal.rs` is overlay-based and `cfg(unix)`. It's unchanged; its format isn't reused, because the Windows steps differ.
- **Written by temporary file and rename before each step** (`layout::write_atomic`, whose rename retries a briefly held file). A journal that can't be read halts the run rather than guess.
- **`result.json` stays display only** (#640 security review item 4). Nothing reads it back, and a test plants a misleading one and shows it decides nothing.

## Probation
- **The `Installing` journal is written before `msiexec` runs.** It records the version installed from, the version installed, and the store's snapshot names then.
- **Passing:** the new service reaches Running within 5 minutes and stays there for 60 s (PK-win-upd-2's health check). Then the journal goes.
- **After exit 3010** (Windows must restart to replace an in-use file), probation isn't judged until after the restart. The journal stays, and the boot run judges it.
- **A crash during the install** leaves `Installing`. The next run judges probation on whatever then runs, and rolls back if it fails.
- **What probation still doesn't check** is which binary answers: a service that stays Running counts as healthy. A version check needs the service to report its version to SYSTEM, which this slice doesn't add (follow-up).

## `--resume` is the boot run (runner)
- **The task runs only `lodestar.exe update-helper`, as Q13 has it, so the boot trigger takes no other argument.** Every run, at boot or on demand, finishes a journal first, before it reads any request. That is §12.2's `--resume`; there's no separate flag.
- A halted journal is reported on each run, and nothing more is tried until an administrator removes it.

## The rollback steps
1. **Choose the snapshot** by name alone: the earliest pre-migration snapshot the failed version took (`<stem>.pre-v<N>[.<k>].db`, one not there before the install). Its SHA-256 is recorded.
   - SYSTEM never opens the store, so SQLite never parses the service's file as SYSTEM.
   - A planted snapshot gains nothing: the service account can write `lodestar.db` itself, and the old version checks the store when it opens it.
   - No new snapshot means the failed version never migrated, and the store is kept.
2. **Set the service to manual start (`sc config start= demand`), stop it,** and refuse while anything still runs as its account. Then mark the failed version `failed` in `skipped` under `.lock`.
3. **The store first:** the snapshot is renamed over `lodestar.db`, with its `-wal`, `-shm` and `-journal` removed, beneath the pinned data folder.
   - A repeat that finds the snapshot gone and the store at its SHA-256 counts the step done.
   - A snapshot changed since it was chosen halts the rollback.
4. **Then the previous MSI** from staging's `previous\`. Its pins (version equal to the journal's `from`, size, SHA-256) are checked when the rollback begins, and again right before it runs.
   - This is rule 4's one exception: the journal's rollback target with SYSTEM-held pins.
   - `MajorUpgrade AllowDowngrades="yes"` reinstalls it.
5. **The service back to delayed automatic start,** and started. The reinstalled MSI becomes `current\` again.
- **Unix's source-purge scrub** (SRC-14b) before a snapshot is restored isn't done here. A restored store may hold torrents a source purge had removed, until the next purge runs. Follow-up, flagged.
- **A halt** (no previous MSI, a tampered one, the store not matching, a failed reinstall) records why in the journal. Nothing more is tried, and the service is set back to automatic start and started.

## The first update after a manual install (runner, flagged)
- **The helper caches only MSIs it installed.** So the first update after a manual MSI install has no `previous\` and can't be rolled back: a failed probation halts and leaves the new version running.
- Refusing the install instead would block every first update. Windows Installer's own cache of the installed package isn't used: it isn't a pinned, verified copy.

## #640's security review items
1. **The task's `<Command>` is quoted** (`msi.rs`). The task never depends on how a command line with a space is rebuilt. The Windows CI test reads it back quoted.
2. **The version floor on a first install.** The helper's own trust state is raised (never lowered) by the data folder's `trust.json`, when that verifies against the embedded keys (`TrustState::merge`). The raised state is saved to staging after the check.
   - So on a first install, a replayed older manifest that's still unexpired is refused (`older_than_mark`) once the service has seen a newer one.
   - The service can only raise the marks, which refuses more, never less.
3. **The race in `secure-datadir.ps1`** between its link scan and `Set-Acl` propagation. Whether that propagation follows a junction isn't something this slice could confirm.
   - So the helper makes sure the race can't be used: before `msiexec` runs, nothing may still run as `NT SERVICE\Lodestar` (`tasklist` filtered by that account). Otherwise the install is refused (`service_processes`) and the service is started again. The rollback checks the same before it touches the store.
   - `secure-datadir.ps1` itself is unchanged.
4. **`result.json` display only:** above.

## Paths beyond the brief's owns
- `crates/lodestar/src/update/windows/msi.rs`: the quoted `<Command>` (one line), plus the two test assertions that check it.
- `crates/lodestar/src/cli/update_helper.rs`: the exit-code match covers the new outcomes (`rolled_back`, `rollback_halted`, both exit 1) in place of `unhealthy`.
- `crates/lodestar/src/update/windows/mod.rs`: `pub mod rollback;`.

## Tests (every OS, and the Windows CI job)
- A failed probation restores the store, then reinstalls the previous MSI, with the service manual meanwhile. The store is the old one when that MSI runs; the failed version is skipped; the old MSI is current again.
- A crash at each rollback step (manual, stop, reinstall, automatic, start) is finished by the next run. The previous MSI is never reinstalled twice once its step is recorded.
- A crash during the install is judged by the next run.
- Exit 3010 defers probation to the boot run.
- A tampered previous MSI, wrong pins, or none at all: halted before anything runs, the store untouched, the service back on automatic start, and nothing more on the next run.
- A process left as the service's account blocks the install.
- The data folder's marks refuse a replayed older manifest on a first install.
- A planted `result.json` decides nothing.
- `tasklist` rows are counted.
- No fixed sleeps. The crashes are panics at a chosen call, caught.
