# CR-ADM follow-up decisions (#231)

These are the five optional findings from the runner's review of #228 (runner, 2026-10-30). They refine [CR-ADM](2026-10-30-CR-ADM.md). The switch is still off by default, and with it off nothing changes: the CR-SIM goldens are unchanged.

- **A partial refusal holds the finders that refused.** With more than one finder, a request one finder accepts and another refuses used to set no hold, so the refusing finder could be asked again at once. Now every finder that refuses a permitted request, or never acknowledges it, rests for the 1 s hold, whatever the others did.
  - *When:* the finder rests in the poll that first sees its answer, so a refusal seen before another finder accepts, or before the last one refuses, still holds. Each finder's answer is seen once, so no finder is held twice for one request. The request keeps only whether any finder refused, which classifies its refusal as `refused` rather than `unacknowledged` if no finder accepts, on the timer path too.
  - *Why it matters:* production has one finder (the DHT), so this only matters for future finders.
  - Test: `a_partial_refusal_holds_the_finder_that_refused`. Finder 1 refuses and the pool sees it before finder 0 accepts; the runner's review found this order unheld at 6967d0e3.
- **A permitted request no finder acknowledges before `lookup_wait` is requeued, not backed off.** It goes through the same path as an unacknowledged request: `fetch_admission_refusals_total{reason="unacknowledged"}`, a hold on the silent finders, and the key at the front of its queue with no attempt used.
  - This was chosen over the 120 s back-off because a silent finder still holds the request's permit until it deals with the request. The requeued key therefore waits for real capacity rather than a blind timer, and it can't spin: there's no permit to grant until the finder answers.
  - It also matches CR-ADM's rule that a permitted request never accepted costs no back-off.
  - Test: `an_unanswered_request_is_requeued_not_backed_off`.
- **A grant can't reach the paused or at-the-cap branch.** A `debug_assert!` in `request_peers_as` checks it. `drain_admission` only grants while the pool is neither paused nor at `max_lookups`.
- **`StatsSnapshot::peer_permit_returns` is sized by `PermitReturn::ALL.len()`,** so adding a boundary can't leave the snapshot short.
- **The dual-stack permit test now reports whether it ran.** It writes to stderr directly, which libtest doesn't capture, so the CI log shows it.
  - It skips on a host without an IPv6 loopback. This cloud container is one, so the test had been skipping here silently.
  - Whether the CI runners reach the asserts is read from this PR's CI log and stated in the PR.
