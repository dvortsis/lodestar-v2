# PK-unraid decisions (#680)

Removes the unused Hot path and Cold path fields from the Unraid templates. Brief: runner, 2026-11-11; plan Q3 (`docs/plan/2026-11-06-m6-gap-audit.md`).

- **Both fields are gone from `lodestar.xml` and `lodestar-gluetun.xml`.** Their descriptions said "Planned, not used yet", and split paths need a store change (an attached `cold.db`) that no milestone schedules. Revisit after the 10M/50M disk numbers (Track I) show whether they're needed. The worker template had neither field and is unchanged (Q4).
- **`validate.py` refuses any `Config` whose description says "not used yet",** so a field can't ship as clutter again. The Peers (TCP) field's "(planned)" stays: the port is mapped for the peer listener and costs nothing. `test_validate.py` covers it: the shipped templates pass, and each of the two templates with the old field put back is refused. The validator isn't run by CI today; adding it is a workflow change outside this slice, so it is flagged to the runner.
- **Users who already mapped `/data/hot` or `/data/cold` need do nothing.** Checked in the code:
  - `/data/hot` is where the hot-column snapshot goes: `services.rs` uses `config.data_dir.join("hot")` and there is no setting for it. A folder mapped there simply holds that snapshot, as before.
  - Removing the mapping later is safe: the snapshot is then written inside the Data folder's `hot/`. If the snapshot is missing, unreadable or stale, `open_hot` (`pipeline/src/lib.rs`) rebuilds the hot columns from SQLite and carries on. The first start after the change is slower, and nothing is lost.
  - `/data/cold` is never written; `system/info.rs` only reads the size of a `cold` folder inside Data. An empty mapped folder can stay or go.
  - `companions/src/compose.rs` `DataFolders::new` still takes hot and cold folders (its doc comment says they come from the Unraid template). Every production caller passes `DataFolders::none()`; only a test passes them. So nobody is affected; the parameters are dead API for the companions owners to drop.
  - Unraid keeps the container settings a user already saved, so an existing container keeps its mappings until the user edits it. A user who wants the tidy form can remove the two rows in Edit; they never need to move any files.
- **Architecture text this changes:** §11's "optional split paths" item (`docs/architecture.md` ~1336) and §16's adopted "optional hot/cold path split" (~1759) are deferred until Track I's disk numbers say whether they're needed, and the as-built note at ~2927 ("the Unraid template's hot and cold paths are marked 'planned, not used yet'") is stale. The `slices.yaml` CMP-7 note about hot and cold paths is stale too.
- **Chapter 2's "Hot path" subsection is removed,** and the Data section now says there are no separate folders: everything lives in Data. The github-docs lint gate passes.
- **Illustrations:** neither SVG draws the removed fields. The repo has no generator for them (they were committed whole), so the one stale value, the source stamp in `unraid-puid-pgid-illustration.svg`, was changed by hand from `lodestar.xml:30-33` to `:28-31`. The runner was told before the change; the SHOTLIST row notes it.
- **Left for the owners of these files (not in this slice's paths):** `docs/user/appendix-b-settings-reference.md` still lists the Hot path and Cold path rows (lines 11-12), `docs/operations.md:182` describes the split paths as options (PK-ops), and `docs/setup.facts.md` is generated from tag `v0.5.1` and is correct for that tag.
