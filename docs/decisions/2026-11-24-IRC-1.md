## First commit: X-irc-tag-crlf (from #1100's post-merge review, r17)
- **A tag value never holds `CR`, `LF` or `NUL`.** IRCv3's `\r` and `\n` escapes, and any of the three however they got there, become U+FFFD in `line::unescape_tag`. Replacing rather than dropping keeps words apart and shows something was there. The docs now say so, with golden and property tests. `escape_tag` still escapes them for outgoing values, so the round trip holds for every value without them.
- **908 then 904 is `Disconnect::SaslUnavailable`, not `Stop::AuthFailed`.** A 908 (`RPL_SASLMECHS`) that lists mechanisms without PLAIN means the server can't do PLAIN now; the 904 after it isn't a wrong password. It's retried with back-off, like a server that doesn't offer PLAIN in `CAP LS`. A 908 that does list PLAIN leaves the 904 a failed login. Both count only while `AUTHENTICATE PLAIN` waits for its answer: once the credentials are sent, a 904 is a failed login whatever came before it (security review).

## The definition format (plan Q7)
- **Lodestar's own format: a short text file of `key = value` lines** (`crates/sources-irc/data/announce/README.md`, with `template.def` as a complete example the tests parse). Keys: `lodestar-announce = 1` first, then `id`, `name`, `network`, `channel` (1–8), `announcer` (1–8), `announcer-host` (0–8), `pattern` (1–4) and an optional `torrent-url`. No TOML or JSON: a line format needs no new parser dependency, and it's fuzzed as it stands. Nothing is copied from another project's definitions (plan Q7).
- **No tracker definitions ship in IRC-1 (§2.19).** The plan's row says "definitions"; IRC-1 ships the format, its parser and the matcher. A shipped definition needs a person to read that tracker's published rules (owner-decisions §2.47 Q2: none for a tracker whose rules forbid announce bots) and its published announce format, and to record both. That belongs with IRC-2, the plugin that uses them; the README in `data/announce/` says so and sets the rules for adding one. Flagged to the owner.
- **A definition may be the user's, so it's untrusted input:** at most 16 KiB (a leading byte-order mark ignored), lines at most 2,048 bytes, values with no control or Unicode format character and no U+2028 or U+2029, every list capped (repeats under case mapping counted once, before the cap), every value validated (`id` `[a-z0-9-]` up to 32, a DNS host name, IRC-0's `valid_channel` and RFC 2812 nicks). Errors name the key or line number, never the text, which could hold a secret.

## Patterns
- **Regular expressions with named captures, compiled with `regex`'s limits** (plan §4 "IRC-1"): a source of at most 1,024 bytes, a compiled program of at most 128 KiB, a lazy-DFA cache of at most 128 KiB and nesting at most 32 deep. `regex` matches in time linear in the line, and a line is at most one IRC line (about 1 KB of text after Latin-1 decoding), so a hostile pattern or line costs bounded time and memory.
- **`regex = "=1.13.1"` is the one new dependency of `sources-irc`** (standards §2): the plan names it for IRC-1, and it's the version `crates/search` already pins, so no new crate enters either lock file; each lock file's `lodestar-sources-irc` entry gains one line.
- **Captures are `name` (required), `size`, `category` and `id`;** any other named capture is refused, so a definition can't invent a field IRC-2 doesn't map. They map to claims (IRC-2): `name` to `name`, `size` to `size`, `category` to the details section's `source_category` (ENR-9), and `id` only fills the URL template.
- **At most 32 definitions and 64 patterns in one `Matcher`,** so its compiled programs hold at most 8 MiB, plus at most 128 KiB of lazy-DFA cache per pattern for each thread matching at once. A matcher serves one connection; `Matcher::new` doesn't check that its definitions share a network, which is the caller's job (IRC-2 groups them by `network`).

## Matching
- **Only a `PRIVMSG` or `NOTICE` to a definition's channel from one of its announcers can be an announce;** CTCP is ignored. Channels and nicks compare under RFC 1459 case mapping, as IRC-0 does. An announcer is an RFC 2812 nick, which has no dot, so a server name can't pass for one. **An optional `announcer-host` narrows it further** (security review): when a definition names hosts, the message's host (the part after `@` in `nick!user@host`) must equal one of them exactly, ignoring case (no wildcards), so on a network where anyone can take an unused nick, taking the announcer's nick isn't enough to inject announces. It's optional because many announce channels are moderated and a tracker's bot host can change; the README recommends it where nicks aren't protected. The first definition for the channel and nick, and its first matching pattern, decide.
- **Server text is cleaned before it's matched** (IRC-0's rule for every consumer of `Events`): `line::clean_text` removes mIRC formatting (`strip_formatting`), every control character, every Unicode format character and the line and paragraph separators, turning tabs and the separators into spaces. Captured fields are trimmed of spaces. The Unicode format-character table moved from `client.rs` to `line::is_format_char` so both use one list.
- **A captured field holding `://` makes the line a `Reject::Url`,** so no URL, passkeyed or not, reaches a claim through a careless pattern. A torrent id is letters, digits, `-`, `_` and `.` up to 64 bytes, and not only dots; anything else is refused (`Reject::TorrentId`) when the template needs `{id}`, rather than escaped into a different id. The name is never cut: one over 1,024 bytes is refused (`Reject::Name`), though a line can't make one that long. A category is cut to 256 bytes on a character boundary.
- **Sizes read as trackers write them:** `B`; `KB`, `MB`, `GB`, `TB` as powers of 1,000; `KiB` to `TiB` as powers of 1,024; any case; `1,024.5` groups thousands, `1,37` and `0,500` are decimal commas. Exact integer arithmetic, rounded down. A size that doesn't read, or is over 1 PiB, is left out and the announce kept: it's a hint (§18.5). Units are taken as written, since many trackers mean GiB by "GB" but the line can't say which. A no-break space counts as a space; up to 18 fraction digits count.
- **The event-queue budget is unchanged:** the matcher holds only its compiled definitions and keeps no per-message state, so a client's worst case stays IRC-0's 4.5 MB of queued text (r17).

## Passkeyed URLs are never stored or logged
- **An `Announce` holds the torrent id, never a URL.** `Definition::torrent_url(announce, passkey)` fills the template only when the `.torrent` is about to be fetched (IRC-2: on explicit interest, sources-plan Q15) and returns a `SecretUrl`: wiped on drop, not `Clone`, no `Display`, and `Debug` prints `SecretUrl(<redacted>)`. The passkey is IRC-0's `Secret`. Every value is percent-encoded (RFC 3986 unreserved characters kept). The URL's exact length is worked out first and the buffer allocated once, so it never grows and leaves no unwiped copy of the passkey behind (security review). No URL is made when an `{id}` or `{name}` value is only dots, which would climb the path (`/dl/..`).
- **The template is `https://` only, with no user info, no placeholder in the host and a port of 1–65535,** so the definition fixes where the passkey goes and an announce can't redirect it. `Definition::torrent_url_host` gives that host before any URL is made, for IRC-2's egress check. `{passkey}` may appear once. `Debug` of a `Definition` shows only whether it has a template.
- **A template with 20 or more letters and digits in a row, or 32 or more hex digits in a run that may also hold `-` (a UUID), outside a placeholder, or such a hex run in a host label, is refused** (`DefinitionError::LiteralSecret`), because it looks like a pasted personal link, and a definition is saved in settings. Ordinary path words are far shorter; a tracker whose real path needs such a run can be written with a placeholder.
- The crate still writes no log lines.
- **For IRC-2, from the security review:** a `reqwest` error's `Display` includes the URL, so map fetch errors with `without_url()` before they're logged or shown; follow no redirects on the `.torrent` fetch (a redirect could carry the passkey elsewhere, or arrive at a URL that isn't wiped); and any `url::Url` parsed from a `SecretUrl` is a plain copy that isn't wiped, so keep it as short-lived as the request. The plugin layer's request type holds the URL as a plain `String` today; IRC-2 decides how the secret crosses it.

## Reviews and fuzzing
- **A fresh review and a security review found nothing blocking.** Their low and polish findings are fixed in the second commit: the 908 phase, dot segments, the exact buffer, the port range, `torrent_url_host`, `announcer-host`, separators in values, the UUID check, dedupe before the caps, the byte-order mark, `parse_size`'s first group and fraction digits, and tests for an over-long name (a hand-built message), a repeated `torrent-url` and a bad port.
- **`irc_announce` fuzz target:** 604,500 runs in 300 s with no crash (2026-11-24, after the fixes). A first run stopped at once on the harness itself: its fixed definition had a pattern without `id` under an `{id}` template, which the parser rightly refuses; the pattern now captures an optional `id`, so the `Reject::TorrentId` path is fuzzed too.
