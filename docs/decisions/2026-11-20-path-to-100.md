# Path to 100: crawler build order and testing (r5, #970)

**Decided by:** the owner, 2026-11-20, in a chat session: "We'll go with your recommendation. Update the master plan with the path forward and testing needed." The recommendation is `docs/reviews/2026-11-20-path-to-100-review.md`, which reviews `docs/reviews/2026-11-17-path-to-100-plan.md` and the 2026-11-16 work beside it. This file records what changed in `docs/build-plan.md` §0 and `runner/slices.yaml`. It doesn't change CR-SPEC, the gate or any owner number. The runner adds the owner's choice to `docs/owner-decisions.md`.

## What the owner chose
- **The build order follows the CR-0 ledger.** Lookup cost limits the crawler. Over CR-0's 24 h, each admitted lookup held one of the 32 slots for about 24 s and cost up to about 59 DHT queries, while fetch sockets were under 5 % busy. The build therefore goes:
  1. measure (CR-LEDGER);
  2. make lookups end on values and start on admission (CR-LOOKUP-END);
  3. ask the sampling responder first (CR-HINT-FIRST);
  4. size the slots to the preset (CR-1c);
  5. keep sampling alive through the worst hour (X-sampler-cooldown-split).

  A calibrated simulator scenario (X-crawler-sim-calibrate) screens them.
- **They are built now, in build slots, alongside the host runs.** Building doesn't use the experiment host.
- **The host order is unchanged:** CR-AB-ADM → CR-AB-4 → Checkpoint 1 → CR-AB-1 → CR-5 → CR-COMB. Checkpoint 1's inputs stay as the owner set them on 2026-11-02 (§2.27). Its report carries the measured ledger and the r5 build as the option if the projection falls short.
- **Every change gets the same testing ladder** (build-plan §0.5, "Testing each change needs"):
  1. unit and property tests on a paused clock;
  2. reply-path fuzzing and `/security-review` where untrusted input is touched;
  3. a calibrated CR-SIM screen;
  4. memory bounds and the soak screen;
  5. a cloud-lane mechanism check;
  6. the host A/B per CR-SPEC;
  7. CR-COMB.

## Runner-level refinements, flagged under §2.19
- **CR-1c depends on CR-LOOKUP-END, not on CR-AB-ADM.** Raising slots before cutting queries per lookup would hit the Balanced 200 a second first. CR-1c's default-on decision still reads CR-AB-ADM's result.
- **CR-AB-1 runs the lookup-cost switches first.** CR-1a-S, CR-1a-H and CR-1b follow only where the ledger shows they still act on the limit; a skip is recorded with its reason.
- **Cloud-lane runs check mechanism only.** They show that `W` and `q` fall, that hint answers arrive and that sampler-full time drops. They never count as a gain, which keeps the runner's existing screen rule.
- **The calendar uses CR-SPEC's two blocks per treatment (O6):** about 3 host-days each, about 20–32 host-days in all, four to six weeks with retries. The r3 calendar's 8–9 days assumed one block.

## Not changed
- The gate, CR-SPEC, the Balanced preset's 200 queries a second, the 1024 outstanding cap, BEP 51 intervals, the sampler's per-IP limits and the 60 s per-IP hint guard.
- `LOOKUP_DEADLINE` (25 s), the 64-query cap and `ALPHA` under CR-LOOKUP-END.
- Every new behaviour is behind its own switch, off by default. CR-LEDGER only adds counters.

## For the owner
- **A combined arm could save about 3 host-days.** A predeclared combined arm, for example CR-LOOKUP-END with CR-1c, changes CR-SPEC's design (rule 6.1), so it needs the owner's confirmation before any data is collected (§2.25). Nothing is planned on it until the owner answers.
