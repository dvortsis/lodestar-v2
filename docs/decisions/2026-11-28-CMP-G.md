# CMP-G decisions (#1161)

The companion gate (architecture §18.9 "Companion tests", §18.10, §12; plan `docs/plan/2026-11-06-v06-companions.md` CMP-G). It adds tests and a CI workflow only. No product code changes, and none of these decisions loosens an owner decision or weakens a security decision. The runner flags the refinements to the owner (§2.19).

- **One test per guarantee, in `crates/companions/tests/gate.rs`.** Each goes through the crate's public API the way serve wires it, and each fails if its guarantee breaks:
  1. A download that isn't the pin's (one byte changed, one short, one extra) is refused at the fetch. Nothing is extracted, no credential is made, no file is left and nothing starts. A confirmation naming other bytes is refused before anything is downloaded. The catalogue refuses, by its named rule, a signature kind this build doesn't check, an unknown field, a `verified_at_pin` without a valid key fingerprint, `none` with a fingerprint, a malformed hash, a URL off the entry's hosts and a host off the download list. `verify::minisign` refuses another key's or another file's signature; it is a library check, not on the install path yet, because no catalogue field can name a minisign key (`2026-11-08-CMP-1.md`).
  2. A managed companion is reached at `Target::Loopback` on its catalogue port. Its config file binds `127.0.0.1` before the first start, overwriting a file that bound every address. Compose keeps every port on the internal network unless you publish it: on `127.0.0.1`, or on every address (`Bind::Lan`) only when you ask. A peer port is never put on loopback, only a download client has one, and gluetun's control port is never put on your network (`LanRefused`).
  3. Direct adds nothing to the launch; SOCKS5 puts the proxy variables in it, and only loopback bypasses the proxy. Interface, bind-address and a SOCKS5 route with no proxy have no launch form, so the companion isn't started. Compose's gluetun route sends everything through gluetun, with its post-rules. **Kill switch, against the installed program:** on a SOCKS5 route that's down, the companion isn't started. That is checked over a whole start, not one instant: a direct control companion added after it to the same supervisor starts and answers, and only then is the gated one checked to be held, never run (`run` 0) and recorded nowhere. Once the route is up it runs on the proxy. It stops when the route goes down, and it's held when nothing can read the route any more.
  4. While the companion is missing, the Prowlarr source's requirement isn't met, and Prowlarr is the one suggested. The real `Supervised` refuses the installed program with no route, or with a SOCKS5 route whose proxy isn't known, before anything is spawned. An install whose start is refused that way is undone completely. Installed and healthy, the requirement is met; once removed, it isn't.
  5. The API key is sealed in its row, under its own context. In plain text it is only in the companion's own `config.xml` (0600 on Unix), which the companion needs. It's in no log event (every event of the crate is turned on and captured through a `lodestar_log` sink), no other file under the data folder (journal included), the companion's log ring (the test companion prints its own key), compose output or the `Debug` of what the API reads.
  6. An earlier run's work child is killed outright, and its companion is left running. The next `Supervisor::new` kills it before anything starts. The uninstall then removes exactly what `removal` listed, and nothing named for the companion is left under the data folder.
  7. **The install smoke:** the offer, then the install. The installed program is the archive's byte for byte, the journal is clean, and the download folder is empty. The program then runs under the real supervisor and sandbox and answers on 127.0.0.1, and the removal takes it all away. The data folder is canonicalised once, because on Windows the manager reports `\\?\` paths with 8.3 names expanded.
  8. **No catalogue override in a release:** the only constructor without `testing` is `builtin()`, over `include_str!`. `catalogue.rs` reads no file and no environment variable. `from_json`, `Downloader::any`, `fetch_from`, `fetch_limited` and `Fault` are test-only. `cargo metadata --no-deps` shows that no crate's normal dependency or feature turns `lodestar-companions/testing` on. The release workflow, the container image (`packaging/docker/Dockerfile`) and the MSI (`packaging/windows/build-msi.ps1`) build `-p lodestar` with only `--no-default-features --features web`. Nothing under `crates/*/src` names the test catalogue. CI's existing `cargo tree` check (`testing seams stay out of the binary`) covers the built graph.
- **The test companion is the gate's own test binary.** It is packed as the pinned artifact: a `.tar.gz` on Linux and a `.zip` on Windows, beside a .NET 8 `runtimeconfig.json` so that a SOCKS5 route can be launched on, as Prowlarr ships. The test catalogue is the shipped qBittorrent, Prowlarr and gluetun entries with test image digests and no pins. The gate pins Prowlarr's build for the running platform when it runs, because the hash depends on the binary. This is the `tests/supervise.rs` pattern, with no shell scripts and the same on every platform.
- **The manager's `Run` is a recorder, and the installed bytes run under the real supervisor.** The manager launches Prowlarr with its real flags (`-nobrowser -data=…`), which a test binary can't take. So the manager installs through every real step (fetch, verify, extract, credentials, config files, journal) and records the launch. The tests then start the installed executable under the real `Supervisor`, `Sandbox` (Landlock and rlimits on Linux, the Job Object on Windows) and `egress::add`, with the environment that `launch_env` builds for the route, as `Supervised::start` does. They set `allow_privileged: true`, as the other process tests do, because CI's Windows runners are administrators. **That leaves `Supervised`'s own refusal of root and administrators unasserted in CI.** `tests/supervise.rs` `root_is_refused_unless_a_test_allows_it` is `cfg(unix)` and asserts the refusal only when it runs as root, which CI's test job doesn't, and there is no Windows administrator test. The gap predates this slice; the runner opens a separate slice for that test and flags it to the owner.
- **What the gate leaves to other suites, and why.**
  - The pipeline's hold of a plugin on an unmet requirement is in `crates/pipeline` (`tests/requires.rs`). That crate depends on this one, so the gate covers the manager side: the snapshot and the requirement.
  - API responses (no credential except the reveal) are in `crates/api` (`tests/companions_egress.rs` `credentials_never_appear_in_a_response_or_a_log`, `tests/companions.rs` for the reveal).
  - There is no run-time catalogue signature, by design. Owner cq1 (a) compiles the catalogue into the release-signed binary, and cq2 checks upstream OpenPGP signatures when a pin is made. So "a catalogue entry fails its signature" is covered by the release check (item 8) and by the catalogue's refusals in item 1; the release signature itself is the updater's (§12.2) and its own tests'.
  - "After the work child is killed, no companion survives" is `tests/supervise.rs` `no_companion_survives_a_killed_work_child` (Linux, the init's hook) and `tests/limits.rs` (Windows, the Job Object). The gate's orphan test kills a work child that has neither, on purpose, to leave an orphan for the next start to find.
- **The smoke workflow, `.github/workflows/companions-smoke.yml`,** runs the gate on `ubuntu-latest` and `windows-latest`, the operating systems CI tests on. It runs on PRs that touch what the gate builds or reads, and by hand, not on every merge to `main`: CI's test job already runs the gate on both systems for any Rust change, so the workflow adds only the check that the key tests ran and passed. Folding that check into `ci.yml` instead is the runner's call. It is not inside `ci-ok`: the runner decides that. Linux arm64 isn't in the matrix, because no workflow here uses an arm64 runner.
- **Not done here:** the real-companion smoke (Q20) is not covered here; it waits on CMP-13's pins and is tracked as its own slice. That is the plan's "real qBittorrent and Prowlarr under the shipped systemd unit" smoke, Q20's input: every artifact in `crates/companions/data/catalogue.json` is still `pin: null`, so nothing real can be installed yet.
- **The artifact's size.** It is the test binary compressed. CI's `line-tables-only` debug info keeps it far under the 512 MiB cap (`MAX_ARTIFACT_SIZE`). A local build with full debug info is about 220 MB, still under the cap.
