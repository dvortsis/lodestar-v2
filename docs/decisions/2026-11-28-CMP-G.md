# CMP-G decisions

The companion gate (architecture §18.9 "Companion tests", §18.10, §12; plan `docs/plan/2026-11-06-v06-companions.md` CMP-G). It adds tests and a CI workflow only. No product code changes, and none of these decisions loosens an owner decision or weakens a security decision. The runner flags the refinements to the owner (§2.19).

- **One test per guarantee, in `crates/companions/tests/gate.rs`.** Each goes through the crate's public API the way serve wires it, and each fails if its guarantee breaks:
  1. A download that isn't the pin's (one byte changed, one short, one extra) is refused at the fetch. Nothing is extracted, no credential is made, no file is left and nothing starts. A confirmation naming other bytes is refused before anything is downloaded. A minisign signature by another key, over other bytes, or that won't parse is refused.
  2. A managed companion is reached at `Target::Loopback` on its catalogue port. Its config file binds `127.0.0.1` before the first start, overwriting a file that bound every address. Compose keeps every port on the internal network unless you publish it: on `127.0.0.1`, or on every address (`Bind::Lan`) only when you ask. A peer port is never put on loopback, and only a download client has one.
  3. Direct adds nothing to the launch; SOCKS5 puts the proxy variables in it, and only loopback bypasses the proxy. Interface, bind-address and a SOCKS5 route with no proxy have no launch form, so the companion isn't started. Compose's gluetun route sends everything through gluetun, with its post-rules. **Kill switch, against the installed program:** on a SOCKS5 route that's down, the companion isn't started. Once the route is up it runs on the proxy. It stops when the route goes down, and it's held when nothing can read the route any more.
  4. While the companion is missing, the Prowlarr source's requirement isn't met, and Prowlarr is the one suggested. The real `Supervised` refuses a companion with no route, or with a SOCKS5 route whose proxy isn't known, before anything is spawned. An install whose start is refused that way is undone completely. Installed and healthy, the requirement is met; once removed, it isn't.
  5. The API key is sealed in its row, under its own context. In plain text it is only in the companion's own `config.xml` (0600 on Unix), which the companion needs. It's in no log event (every event of the crate is turned on and captured through a `lodestar_log` sink), no other file under the data folder (journal included), the companion's log ring (the test companion prints its own key), compose output or the `Debug` of what the API reads.
  6. An earlier run's work child is killed outright, and its companion is left running. The next `Supervisor::new` kills it before anything starts. The uninstall then removes exactly what `removal` listed, and nothing named for the companion is left under the data folder.
  7. **The install smoke:** the offer, then the install. The installed program is the archive's byte for byte, the journal is clean, and the download folder is empty. The program then runs under the real supervisor and sandbox and answers on 127.0.0.1, and the removal takes it all away.
  8. **No catalogue override in a release:** the only constructor without `testing` is `builtin()`, over `include_str!`. `catalogue.rs` reads no file and no environment variable. `from_json`, `Downloader::any`, `fetch_from`, `fetch_limited` and `Fault` are test-only. `cargo metadata --no-deps` shows that no crate's normal dependency or feature turns `lodestar-companions/testing` on. The release workflow builds `-p lodestar` with only `--no-default-features --features web`. Nothing under `crates/*/src` names the test catalogue. CI's existing `cargo tree` check (`testing seams stay out of the binary`) covers the built graph.
- **The test companion is the gate's own test binary.** It is packed as the pinned artifact: a `.tar.gz` on Linux and a `.zip` on Windows, beside a .NET 8 `runtimeconfig.json` so that a SOCKS5 route can be launched on, as Prowlarr ships. The test catalogue is the shipped qBittorrent, Prowlarr and gluetun entries with test image digests and no pins. The gate pins Prowlarr's build for the running platform when it runs, because the hash depends on the binary. This is the `tests/supervise.rs` pattern, with no shell scripts and the same on every platform.
- **The manager's `Run` is a recorder, and the installed bytes run under the real supervisor.** The manager launches Prowlarr with its real flags (`-nobrowser -data=…`), which a test binary can't take. So the manager installs through every real step (fetch, verify, extract, credentials, config files, journal) and records the launch. The tests then start the installed executable under the real `Supervisor`, `Sandbox` (Landlock and rlimits on Linux, the Job Object on Windows) and `egress::add`, with the environment that `launch_env` builds for the route, as `Supervised::start` does. They set `allow_privileged: true`, as the other process tests do, because CI's Windows runners are administrators. `tests/supervise.rs` checks that `Supervised`'s own refusal of root and administrators holds.
- **What the gate leaves to other suites, and why.**
  - The pipeline's hold of a plugin on an unmet requirement is in `crates/pipeline` (`tests/requires.rs`). That crate depends on this one, so the gate covers the manager side: the snapshot and the requirement.
  - API responses (no credential except the reveal) are in `crates/api` (`tests/companions_egress.rs` `credentials_never_appear_in_a_response_or_a_log`, `tests/companions.rs` for the reveal).
  - There is no run-time catalogue signature, by design. Owner cq1 (a) compiles the catalogue into the release-signed binary, and cq2 checks upstream OpenPGP signatures when a pin is made. So "a catalogue entry fails its signature" is covered three ways: by the release check above, by `verify::upstream` being `PinOnly` for every shipped pin, and by the catalogue refusing a signature kind this build doesn't check, an unknown field, a malformed hash, a URL off the entry's hosts and a host off the download list.
- **The smoke workflow, `.github/workflows/companions-smoke.yml`,** runs the gate on `ubuntu-latest` and `windows-latest`, the operating systems CI tests on. It runs on PRs that touch the companions crate or its dependencies, on `main` and by hand. It fails if the key tests didn't run and pass. It is not inside `ci-ok`: the runner decides that. Linux arm64 isn't in the matrix, because no workflow here uses an arm64 runner.
- **Not done here:** the plan's "real qBittorrent and Prowlarr under the shipped systemd unit" smoke (Q20's input). Every artifact in `crates/companions/data/catalogue.json` is still `pin: null`, so nothing real can be installed until CMP-13's pins land. It is named to the runner as a follow-up.
- **The artifact's size.** It is the test binary compressed. CI's `line-tables-only` debug info keeps it far under the 512 MiB cap (`MAX_ARTIFACT_SIZE`). A local build with full debug info is about 220 MB, still under the cap.
