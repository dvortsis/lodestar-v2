# M8-PERF-1 decisions (10M bench mode)

The measurement tool G-v1-10m runs on (plan 2026-11-06 §4.3): a persisted dataset, every §3 latency row and size figure in a `--dataset` mode of `search-bench` and `size-report`, and one JSON report each. The 200k and 50k CI gates are unchanged (below). Nothing outside `bench/` changed.

## The dataset key
- **Key:** `{format, generator, seed, torrents}`, written to `DIR/dataset.json`. `format` is `dataset::FORMAT` (1), the build recipe: the constants, the phases and the rollups. `generator` is `synth::VERSION` (1), raised in any change to what a seed generates. All four must match; a mismatch is refused before anything is written, and the message names both keys (`Refused::Mismatch`). The torrent count is in the key so a 1M dataset is never reported as 10M. The store and search schema versions are recorded beside the key but aren't part of it. A newer search schema or tokenizer version names a new index folder (`index_dir`), so a complete dataset without one is indexed again from its store, as the server rebuilds. Every open then checks that the index holds exactly `torrents` documents and fails otherwise, so no row ever runs on an empty or partial index (`a_dataset_without_this_builds_index_is_reindexed_never_empty`).
- **Never a data directory:** a folder is used only when it's new, empty or holds a `dataset.json`, and never when it's `$LODESTAR_DATA_DIR` (`Refused::NotADataset`, `Refused::DataDir`). It's the fixture's rule (`bench/README.md`, fixture backend).
- **The build:** 20,000 torrents, a trained 112 KiB zstd dictionary, recompression, and the rest with it (`size-report`'s recipe). Then enrichment, one synthetic scrape a torrent (`size-report`'s, now `dataset::scrape_all`), a year of B11a's wide Insights hour ending at `synth::EPOCH`'s hour and compacted there (30 days kept hourly), and both indexes. The index writer uses a 512 MB heap and commits every 200,000 torrents, as `search-bench` always has and as X-search-files-5 measured 10M. An interrupted build resumes after its last finished phase. The two windows where work is done but not yet recorded are safe: training is skipped when a dictionary is already stored, and the rollups phase starts from empty Insights tables. `an_interrupted_build_resumes_to_the_same_dataset` stops after each phase and in both windows, and compares with a clean build.
- **Deterministic:** nothing reads the clock. The store stamps two bookkeeping columns with it (`schema_migrations.applied_at`, `zstd_dicts.created_at`), which nothing reads for search or size, so the build pins both to `synth::EPOCH` at the end. Two clean builds of one key then give the same SQLite file byte for byte, except the header's file change counter and version-valid-for number (bytes 24–27 and 92–95), which count checkpoints and so depend on when SQLite ran them; and the same content digest (`bench/tests/dataset.rs` `the_same_key_builds_the_same_bytes`). Tantivy names segments at random, so the indexes are compared by document count, not bytes. A resumed build is the same content, not necessarily the same bytes.
- **Read-only once built:** the rows that write (new torrent → searchable, idle and under ingest) run on `DIR/scratch`, a copy made for them and removed after them, so every run starts from the same bytes. The test checks that the digest is unchanged after both bins run. The copy needs as much free disk again as the dataset.

## Each new row's method
- **Every existing table** (keyword classes, the `/search` path and count estimates, zero-result recovery, broad file clauses cold and warm, facets, suggest) runs unchanged in `--dataset` mode and gets a report row each. In `--dataset` mode hot columns are loaded from the store's `swarm` table (`Store::load_hot`), as the server loads them without a snapshot, rather than from `synth::swarm`.
- **Regex (< 500 ms):** queries of five shapes (`/a.*b/`, `/^a/`, `/a[0-9]+/`, `/a[._ ]b/`, `/a.*(1080p|2160p)/`) over common vocabulary words, timed like keyword queries (parse, search a page of 50, load the rows). **`regex search` isn't on `main` (RX-1),** so the row probes the parser and reports `unavailable` while it refuses `/abc/`, never a pass. It times real queries once RX-1 lands, with no bench change.
- **Insights (< 50 ms, "rollups only"):** the store reads the overview's `read_period` and the stage pages make (`crates/api/src/insights.rs`, `insights/stages.rs`). They follow the API's grain rule: hourly up to 7 days and above the compaction boundary, whole days otherwise. The overview reads the range, the period before it, the current hours, the yield baseline and the events, for the UI's ranges (24h, 7d, 30d, and all, which is the year here), with no cache (a range's first open, the slow case), 50 runs each. **Refinement flagged (§2.19):** these are the handler's store reads, not the HTTP handler. Calling the handler would make `lodestar-api` a normal dependency of `lodestar-bench`, which puts every API change into the bench gates' change detection (`.github/scripts/ci_changes.py`). The composition over those rows is in memory and its size follows the hours, not the corpus. The full handler stays measured by the nightly `reporting-overhead` at 100k.
- **Steady-state RSS (< 1 GB; < 512 MB low-resource, RQ8), decimal units,** the stricter reading of the owner's figures. It runs on the scratch copy, as a server holds memory: hot columns, the title set, and a live indexer at its production heap (256 MB) following a trickle ingest of 4 torrents a second (about twice the crawler gate's 100 a minute). One pass of a mixed load (each class's queries plus three facet queries) warms it; then the load runs for `--steady-secs` (default 60) while a sampler reads `VmRSS` every 250 ms. The highest sample is gated and the median reported. The process's earlier tables stay in its memory, so the figure errs high. There's no crawler, API or recorder in the process, which the 10M gate's soak-side figures cover. A dataset built in the same process is `unmeasured` (the build's memory stays mapped), so a 10M run builds first and measures in a second invocation; cold start is `unmeasured` then too.
- **Low-resource mode:** RQ8's subset. Keyword, browse, facets and typeahead run against the default targets, the RSS budget is 512 MiB, and the file and regex rows are `off` (not offered by design, never a pass). **Refinement flagged (§2.19):** RQ8 says they're "reported as unavailable". Here `unavailable` means "this build can't yet" and keeps the verdict `incomplete`, so a mode that will never offer them uses `off`, which still isn't a pass. **The product has no low-resource switch yet** (architecture §3 describes one; no code turns the trigram field, the file index, caches or merge threads off). Each missing switch is an `unavailable` row, so a low-resource report is `incomplete` until a slice adds the switch. Told to the runner on 2026-11-12. The bench shrinks only the live indexer's heap (64 MB).
- **Sizes (`size-report --dataset`):** the four CI figures, plus store and torrent index together (≤ 1,536 B) and the all-in figure (store plus both indexes, reported against the ≈ 2.3 KB target, never gated, since the owner set it as a target). "Every 1.0 field populated" is one row per field that `SearchIndex::unpopulated()` reports. Today that's `group_key`, `group_minhash` and `name_trigram`, which have no producer yet, so the size report is `incomplete` until GS-2 and RX-1 fill them.

## What "new-to-searchable" and "cold start" measure
- **New torrent → searchable** is the time from one `Store::insert` of a probe torrent returning to `SearchIndex::find_hash` finding its info hash, polled every 5 ms with a 120 s give-up. Indexing is through a `LiveIndexer` at its production `LiveConfig`, on the scratch copy of the whole corpus, so commits and merges happen at the dataset's scale. Two rows:
  - **idle:** the CI check's 10 rounds, gated on the max;
  - **under ingest:** `--nrt-rounds` (50) probes while a second thread inserts `--ingest-rate` (100) torrents a second in batches every 100 ms through the same store. Gated on the p95 (§3's rows are p95s). The ingest is paced by elapsed time. If it reaches less than 90 % of the rate asked, all three rows (p95, max, rate) are `unmeasured`, since a starved ingest would flatter the figure. A rate of 0 is refused.
- **Cold start** is the time from the first open, before anything else in the process touches the dataset, to the first page answered:
  - `Store::open_reader`, `SearchIndex::open`, and hot columns from SQLite (the start without a snapshot, the slower path);
  - then the UI's first page (everything, newest first, 50 rows loaded).

  It's reported with and without the opens (§3 sets no number). With `--drop-caches` as root the OS page cache is dropped first, and the row id says `page-cache-dropped`. Otherwise it says `page-cache-as-found`, a lower bound.

## The JSON report
- **One object per run** (`dataset::report`), documented in `bench/README.md` "The JSON report": `report_format` 1, `tool`, `mode`, `verdict`, `machine` (cores, memory, CPU, kernel, and the dataset folder's disk kind from `/sys/dev/block`: `nvme`, `ssd`, `hdd` or `unknown`), `dataset` (the key), `git` (`$GITHUB_SHA` or `git rev-parse HEAD`, and `dirty`) and `rows`.
- **A row** is `{id, budget_row, value, unit, budget, status, reason}`, with stable ids for M8-PERF-3 to gate on. `verdict` is `fail` if any row failed, else `incomplete` if any is `unavailable` or `unmeasured`, else `pass`. `--gate` with `--dataset` exits 1 unless it's `pass`, so a missing measurement can never read as a pass.

## The CI gates are unchanged
- Without `--dataset`, both bins run as before: the same arguments, rows and budgets, and no new row is printed or gated. The new flags that only make sense with a dataset are refused without one.
- **Dry run (this container, 4 cores, not the gate's machine):**
  - `size-report --torrents 50000 --gate` on `main`'s bin and this branch's printed identical store and blob figures (948.3 B and 346.1 B) and file index (789.2 B). The torrent index read 476.0 B here against 476.2, 476.6 and 477.0 B in three runs of `main`'s own bin: Tantivy's run-to-run noise.
  - `search-bench --torrents 200000 --gate`: the same rows and hit counts, 64 PASS lines and exit 0 on both.
- `size-report`'s generate, store and scrape code moved into `dataset.rs` unchanged, so both modes share it.

## Not run here
- **No 10M run.** A 10M build needs about 25 GB and several hours. The run that counts is G-v1-10m's, on the dedicated runner (M8-PERF-3).
- **Reporting overhead at 10M** (plan §4.3's G-v1-10m list) isn't in this mode: it's the `reporting-overhead` example, which needs `lodestar-api`. Told to the runner; the example's `--torrents` can run it at 10M by hand.
- The mode is proved at 1,200 torrents in `bench/tests/dataset.rs`. Both bins run there in default and low-resource mode, and the test checks that every §3 row has a line and that the dataset is unchanged after the runs.
