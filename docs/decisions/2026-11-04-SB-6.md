# SB-6 decisions

Search `SCHEMA_VERSION` 5 → 6, M7's one bump (build-plan §1.3, Track M7), with the population contract (r3). Applies architecture §8 ("Index evolution", the torrent and file index field lists) and §18.6.

## The v6 fields (`crates/search/src/schema.rs`, `files.rs`)
- **Torrent index, defined and left empty** (no producer in this slice):
  - `verified`, `source`, `network`: keyword fields (raw tokenizer, fast), like `flag` and `tag`, so SRC-3's `verified:`/`source:`/`network:` are term lookups and the Source/Verified/Network facets (SRC-17, §18.6) read one column each. `verified` takes `yes`/`no`, `network` the §18.6 tier names.
  - `payload_sig`: u64, indexed and fast. §6 asks for a fast field and a one-term `sig:` lookup; a fast field alone would make `sig:` a column scan.
  - `group_key`: u64, indexed and fast (§8's "later `group_key`"; the clusters need both the lookup and the column). `group_minhash`: multi-valued u64 in the inverted index, one value per MinHash band, so near-duplicate candidates are term lookups. The grouping slice decides the band count; the field shape doesn't depend on it.
  - `name_trigram`: docs only (no freqs, positions or norms), tokenized by a new `trigram` analyzer (3-grams of the name, lowercased), registered on every index so any writer can open a v6 index. The regex slice fills it; a different analyzer later is a `TOKENIZER_VERSION` bump, not a schema bump. Low-resource mode (§3) leaves it empty.
- **File index, filled by SB-6's own rebuild:** `category` (keyword, `Category::as_str` of the extension, `other` without one), `pieces_root` (32 bytes, indexed, only when the torrent has one) and `size_bucket`.
  - **`size_bucket` instead of an inverted index on `size`** (X-search-files-2's proposal). Measured with `size-report --torrents 50000`: indexing `size` itself costs 307 B per torrent (219 B of terms, since almost every file size is distinct, and 88 B of postings), taking the file index to 1,061 B against §3's 800 B budget. `size_bucket` is the size's highest bit and the one below it (two buckets per power of two, at most 128, each spanning at most half its lowest size; `files::size_bucket` and `bucket_floor`). A `size:` range reads the postings of the buckets wholly inside it and checks the `size` column only in its two edge buckets, which is what X-search-files-3 needs for the cold p95. It's a refinement of the proposal that leaves the budget unchanged, so it's the runner's call (owner §2.19) and flagged in the PR.
  - **File index after SB-6: 789 B per torrent (budget 800)**, up from about 726 B: `category` 26 B, `size_bucket` about 35 B, `pieces_root` 2 B. That leaves 11 B of headroom, which later file-index work must budget for.
- **`TorrentDoc` doesn't gain fields** for the empty ones: each producer adds what it writes to `doc.rs` with its generation bump. Adding them now would only add literals other slices' tests must repeat.

## The population contract (`crates/search/src/population.rs`, new)
- **A generation per tracked field.** `population::GENERATIONS` holds this build's: 0 while no producer ships, 1 for the three file fields SB-6 fills (`file.category`, `file.pieces_root`, `file.size_bucket`). Tracked fields are exactly the ones v6 added; every older field is filled for every document by construction.
- **Recorded durably, atomically with the documents:** each index's Tantivy commit payload gains a `;pop:` part, `name=gen` per complete field and `name=gen@cursor/high` per field being backfilled, in name order. The parser is strict (canonical numbers, sorted unique names, non-empty walks) and property-tested; anything else is `Corrupt`, as for the existing watermark parts. Older payloads without `pop:` still parse.
- **When the build's generation differs from the recorded one,** the index backfills: a walk over `(0, high]`, `high` being the highest torrent id the index held when it noticed. Torrents past `high` are indexed by this build already. A field recorded at generation 0 needs no walk when this build is also at 0 (nothing to write). An index from before `pop:` walks every field with a producer. A brand-new index is complete at this build's generations.
- **The walk replays like `reindex_log`:** each torrent in the batch is deleted from the index and re-added from the store as it is now, in both indexes only where that index has a walk. It runs inside `Indexer::catch_up_counted`, after new torrents and log entries, taking what's left of the step but at least an eighth of it, so a busy crawl slows it and never starves it, and new torrents stay within the 5 s budget (§3). One pass serves every field being backfilled, since a document is rebuilt whole.
  - **"Through `reindex_log`" is read as "the way `reindex_log` entries are applied", not as writing entries into the log:** the indexer's store connection is read-only, the store is out of this slice's scope, and a cursor walk needs no write per torrent.
  - **Restarts:** the cursors commit with the documents, so work after the last commit is redone, never skipped.
  - **Deletions:** a deleted id isn't returned by the walk's read, and its documents went with its `reindex_log` entry; one deleted between the two reads is dropped.
  - **Filter changes and other edits:** they reach the index as deletes or flag marks, each with a `reindex_log` entry. The walk reads current data and the entry replays it again, so the order doesn't matter.
- **Completion:** a field is complete when its walk's cursor reaches `high`, recorded in the same commit as the last batch. Only then is it `Availability::Ready`.
- **Truthful availability** (`SearchIndex::availability`, `unpopulated`, `prefilter`), on top of `missing_fields()`:
  - `Missing`: the serving index lacks the field (an older index during a rebuild); clauses on it match nothing, as before.
  - `NoProducer`: every document lacks it.
  - `Backfilling { done, upto }`: ids up to `done` have it, `(done, upto]` may not.
  - `SearchIndex::prefilter(field, searcher, query)` (crate-internal, for M7's in-crate prefilters) returns the prefilter only when the field is `Ready` **in the snapshot it runs on**: a field that completes while the index is open records the first searcher generation of its index's reader that sees it complete, so a lease still reading a snapshot from mid-backfill never prefilters on it. A prefilter never treats an unpopulated document as "no match"; every producer's prefilter goes through it.
  - A read-only older index (another schema, serving during a rebuild) reports what its own payload records, without reconciling it with this build's generations: generation 0 is `NoProducer`, an open walk `Backfilling`. One without a `pop:` part predates the contract, when fields only came with full rebuilds, so each field it has is `Ready`. This keeps a v6 index honest while it serves during M8's v7 rebuild.
  - A backfill step that only moves a cursor (the walk's last ids were deleted, so nothing is re-indexed) still counts as pending work, so the live indexer, which commits only what's pending, commits the completed walk.
- **Not wired to the API in this slice:** `/search/state` keeps reporting `missing_fields()` as `unavailable`. Adding `unpopulated()` there (and to a query's notices when a clause names a partial field) touches `crates/api`, outside this slice's paths. The first producer slice (SRC-3) needs it and should add it.
- **Each producer slice** raises its field's generation, adds its `doc.rs` writes, and tests SB-6 → import → producer on an existing database with a restart mid-backfill (build-plan Track M7). `SearchIndex::with_generations` lets a test play the bump without editing the table.

## Blue/green (`crates/search/src/rebuild.rs`, shared)
- **v5 → v6 uses the existing rebuild:** the v5 index serves read-only, mapped by field name, with the v6 fields reported missing; the v6 index builds beside it, resumes from its watermarks after an interruption, and swaps in. Its file fields come from the store's file trees.
- **The disk high-water mark** is sampled over the whole index root at the build's start, at each build commit, after its finish and right after the swap (before the old index is deleted). It's kept as `Serving::disk_high_water()` and logged in the `search.swapped` event (`disk_high_water_bytes`), which G-rebuild-10M reads from the owner host's log. Being sampled, it can miss a short peak while background merges hold old and new segments at once; at 10M, read it beside the host's own disk metrics. It isn't on `RebuildProgress`, which other crates construct in tests; `/status` or a metric for it is a follow-up outside this slice's paths.
- **The X-mmap-cache-prune behaviour is unchanged:** both new directories are opened through `SearchIndex::open`, which prunes at open and after each commit, and the old index's directories go with its last clone.
