Migration V11, the metric aggregation kinds, daily compaction with the query log's prune, reads over both grains, `lodestar rollup --repair` and fetches by event time (architecture §7 "Insights rollups", §10.9.3, §10.17; `docs/metrics.md` §7.5, §7.7). The stage pages, `export.csv`, the overview's Compare additions and the `insights` SSE topic are part 2, in `2026-10-23-B11b-r2.md`. No owner decision is reversed or loosened, no security or content-safety decision is weakened and no owner-set number changes; the refinements below are the runner's to flag (`docs/owner-decisions.md` §2.19).

## Schema (V11)

- **`rollup_day(day, metric, dim, key, value)` and `cohort_day(day, source, stage, reason, count)`,** `STRICT, WITHOUT ROWID`, keyed like their hourly twins; `day` is Unix time / 86,400 (UTC days, `docs/metrics.md` §2).
- **`insights_state(key, value)`** holds `compacted_before_day`, `last_compaction_at`, `funnel_events_since_hour` and `imported`. A key-value table rather than one row of columns, so a later slice adds a value without a table rebuild.
- **`imported` is seeded once, by the migration,** with the same count `count_flagged_searchable(IMPORTED)` makes, and kept exact from then on: `record_searchable` adds each chunk's imports in its own transaction, and the trigger subtracts. The recorder mirrors the row after every record and every tick, so the full scan at each start is gone (B11a's follow-up).
- **`funnel_events_since_hour`** is seeded with the first whole hour after the upgrade: the upgrade's own hour is partial, so it reads as unknown too. **On a store with no history** (no torrent, cohort or rollup row) it's 0: nothing went uncounted, so a new install shows fetches from its first hour, `range=all` included.
- **The `torrents_removed` trigger** (`AFTER DELETE ON torrents`, `WHEN old.id <=` the highest `index_watermark_hour.last_id`) adds 1 to `rollup_hour` at `unixepoch() / 3600` under **code 15 `REMOVED`** (dim = content type, or 255) and takes an import off `imported`. It covers every delete path, present and future, without each one remembering to count. Hour-0 ids (indexed before tracking) count as searchable here, because they were.
- **The snapshot purge fires the trigger too** (it deletes, on a migration snapshot, the torrents the live store deleted). We keep it: in a restored snapshot those torrents did leave, its `imported` stays exact only if the trigger runs, and the searchable Δ (which counts removals) then agrees with the removals shown. They're counted at the purge's hour, not the original delete's. `snapshots.rs`' `Plan::KNOWN_THROUGH` moves to 11 so V11 snapshots keep being purged (its own comment asks every migration to do this).

### Trigger cost (the brief's measurement)

- **Measured in release** on a file store, 100k searchable torrents, median of 5: `delete_torrents` 4.62 s without the trigger, 5.79 s with it (+25%); a cached `DELETE` loop 1.24 s → 1.68 s (+35%), about 4 µs a row.
- **The delete paths now cache their statement** (runner's round, scope exception): `delete_torrents` (`filter.rs`), `set_enrichments_at` (`lib.rs`) and the snapshot purge (`snapshots.rs`) ran an uncached `tx.execute` per row, so SQLite compiled the trigger program again for every row. With `prepare_cached`, `delete_torrents` of 100k takes **2.41 s without the trigger and 2.84 s with it (+18%)**, under half the 5.79 s before.
- **The watermark lookup isn't the cost.** A trigger with only the `WHEN` clause adds about 3%; moving the watermark into an `insights_state` value the recorder maintains made no measurable difference (the subquery is one seek on `index_watermark_last_id`). The cost is the counter write itself, which any per-row trigger pays: SQLite has no statement-level triggers.
- **A filter relabel** deletes through the same per-row `DELETE FROM torrents WHERE id = ?` inside `set_enrichments_at`, so it pays the same ~4 µs a row; it wasn't timed separately.
- **Kept as is.** Bulk deletes are rare (abuse reports, a relabel), and the alternative (every delete path counting its own removals, by type, in its own transaction) moves the same writes into code that's easy to forget. A 100k delete now holds the write lock about 0.4 s longer. **The runner's decision: the trigger stays** (it covers every delete path, future retention included). **Revisit when retention lands**, since that may delete in bulk on a schedule.

## Aggregation kinds and codes

- **`lodestar_store::Aggregation { Sum, Last }`** and `lodestar_pipeline::metric::aggregation(code)`, one table naming every code: 1–12, 14 and 15 `Sum`; 13 `SEARCHABLE` `Last`; 5–9 `Sum` (#48's, not on `main` yet). A test fails if any code from 1 to `LAST_CODE` lacks a kind, or if anything but `SEARCHABLE` is `Last`.
- **A code with no kind is never compacted:** its hours stay, the recorder logs it once per run of the process, and the boundary moves past it anyway (readers of compacted days read only `Sum` metrics from the hourly stragglers, so it's never summed).
- **Code 14 `FUNNEL_EVENTS`** (dim = `Stage`, key = `Loss` or 0): the writer adds the funnel rows it flushes again by event time, at the flush hour (event time within the 5 s cadence), three lines beside `self.funnel.drain()`. `stages.fetch` and `previous.stages.fetch` read dim `Fetched`, and are **null when the window starts before `funnel_events_since_hour`**: a range only partly counted would undercount silently.

## Compaction

- **Rule:** whole UTC days that ended more than 30 days ago (`day < now_day − 30`) are folded, **never from the seal floor's day on** (the oldest cohort restored from the fetch queue, `InsightsSource::seal_floor`, while it's held): the whole day is held, both tables, since there's one boundary.
- **One day per `BEGIN IMMEDIATE` transaction** (a day is about 2,600 rollup and 700 cohort rows at B11a's density): insert at daily grain (`Sum` adds; `Last` takes the latest hour's rows of that metric), delete the day's hourly rows, move `compacted_before_day` past it, commit. A crash leaves a day fully hourly or fully daily; a repeated run folds nothing. Empty days are skipped by seeking the next hourly row, so a first run on a year makes one transaction per day with data.
- **Stragglers** (hourly rows of metrics with a kind, or cohort rows, below the boundary: a clock set back, or a backlog recorded into an old cohort) are folded the same way at the start of each run, additively, even at or after the seal floor's day (they're already behind the boundary, and folding only makes them visible at daily grain). Until then, readers read them beside the day rows (a range scan of the sparse hours below the boundary, `Store::rollup_straggler_sums`), so they show at once. A `Last` straggler replaces its day's value.
- **Budget and WAL:** a step runs for at most 1 s (each call folds at least one day first), then the recorder's loop goes on (commits keep being recorded) and the next 30 s tick continues. No read transaction spans days. On the synthetic year the WAL stayed under 40 MB (SQLite's 1,000-page autocheckpoint at 16 KB pages) and the compacted file under 50 MB.
- **When:** the recorder's tick checks `last_compaction_at`; a run starts when it's 24 h old, first checked 10 min after start. `last_compaction_at` is written in the run's last transaction.
- **After a run:** `prune_query_log(now − 30 days, 100,000 rows)` (§10.9.5's 30 days; 100,000 rows is about 5 MB at typical query lengths and far more than a month of a household's searches), its only production caller. The free pages the run added are then handed back by `incremental_vacuum` **at most 256 pages (4 MB) per tick**, so no one vacuum holds the write lock long or fills the WAL (a year's first run frees a few thousand pages).
- **The sealed-day cache** keeps only the 8–30-day band: days below the boundary are dropped from it after a step and never read into it (`warm` starts at the boundary).

## Reads over both grains

- **The boundary is read inside the overview's read transaction** (`overview_in_snapshot`), before the window is computed, and the whole build runs in that snapshot, so a compaction running beside it never double-counts or drops a day (a store test holds a reader's snapshot across every fold).
- **Days below the boundary** read `rollup_day`/`cohort_day` with one seek per (day, metric), plus the straggler range scan; the 8–30-day band from the cache; the rest hour by hour. `previous.kpi.searchable` takes the compacted day's `Last` value.
- **A window reaching a compacted day is bucketed by day** (`range.bucket: "day"`), even if shorter than 7 days. With Compare, if the previous period reaches a compacted day and the current one doesn't, both are bucketed by day so their trends line up.
- **Measured in release** on a year of rollups at B11a's density, after compaction: `24h` ≤ 2.6 ms, `7d` ≤ 8.6 ms, `7d&compare=1` ≤ 12.5 ms, `30d` (with or without compare) ≤ 8.4 ms, `all` (with or without compare) ≤ 22 ms; every response byte-identical to the one before compaction.

## Repair

- **`lodestar rollup --repair [--since <N>d]`** is offline like `vacuum`: `refuse_during_update_rollback`, then `StoreLock::acquire`, refused (exit 3) while anything has the store open. It runs `lodestar_store::repair_rollups` on the lock's own connection, which first checks the schema is this build's (a store not upgraded yet is told to start Lodestar once).
- **Window:** the last 30 days by default (`--since 30d`), `--since <N>d` up to 7,320. Hours in compacted days are repaired at daily grain into the day tables; a compacted day only partly in the window isn't compared.
- **What it rebuilds** (for cohorts and hours in the window): cohort Stored (`discovered_at` hour, `first_source`, imports excluded); `STORED` by `metadata_at` hour (dim = `first_source`, imports excluded, since the writer counts only fetched torrents); `NEWLY_SEARCHABLE` at each id's first watermark row; cohort Searchable and its histogram, with the delay taken to the watermark hour's midpoint (≤ 30 min off), never earlier than the torrent's `metadata_at`; and, the command only, `imported`.
- **The writer now counts `STORED` at `metadata_at`** (the fetch, seconds before the commit) instead of the commit time (one argument in `writer.rs`). Counted at commit, every hour boundary moved a few torrents into the next hour, and raise-only repair would then have raised the hours that lost them and kept the ones that gained them, overcounting a healthy store. Now the writer and the recount use the same hour. Rows from before this build keep the commit hour; a repair over them can raise an hour by those few boundary torrents.
- **Raise only:** a cohort cell is set only where the recount is above it (at daily grain, above the day's row plus its hourly stragglers, which the raise then absorbs, so the next compaction can't add them again); an hour's (or day's) rows of `STORED` or `NEWLY_SEARCHABLE` are replaced only where the recount's total is above the stored total (cells within it then follow the torrents' current classification); a cohort's histogram is replaced with the recount only when one of its Searchable cells is raised. A torrent deleted since never lowers a total, and a second run changes nothing (tested); a per-type or per-source cell inside a replaced hour can drop to the current classification. A raised Searchable cell replaces that cohort's whole histogram with the recount's midpoint approximations (≤ 30 min off), exact delays included. Known limit: the histogram is the whole cohort's, so after deletions in another source of that cohort its total can trail the cohort's Searchable cells by those deletions.
- **Reading:** `torrents` in id chunks of 20,000, each in its own read transaction, from the first id stored since the window (a binary search on the primary key over `metadata_at`, with an hour of slack, since ids follow storage order only roughly) or the first id the window's watermark rows cover, whichever is lower; then the raises in one `BEGIN IMMEDIATE` transaction.
- **Automatic after an unclean stop** (§7): in `services.rs`, on the writer's store before `Pipeline::start` takes it, so no live increment races it. Unclean means the newest `event::START`/`event::STOP` is a `START`; a new store has neither. It recounts the 72 h before the store's **last activity**, not before now (`Store::last_activity`: the end of the newest rollup hour, which coverage writes every 30 s, or the newest torrent's `metadata_at`; at most now), so a box that lost power Friday and starts Tuesday repairs Friday's window. That's seconds, not a full scan: at most 72 h of stored torrents (at ~10 a second, about 2.6M rows read in 20,000-id chunks) before the HTTP server binds, inside the container healthcheck's start period. It and doesn't recount `imported` (the trigger and `record_searchable` keep it transactional, so a crash can't skew it). **It can't fix** cohorts older than 72 h: keys restored from the fetch queue with an older cohort that were stored in the crash window keep that cohort's loss, until a `--since` run covers it.
- **Lost for good** (also in `lodestar rollup --help`): pre-storage counts (harvested, peer found, fetched, losses, keys reported, rediscovered, dropped, `FUNNEL_EVENTS`), coverage, gauges (`SEARCHABLE`'s snapshots) and hour-0 ids; after compaction, hourly detail older than 30 days (hour buckets, hourly finality, hourly repair).
