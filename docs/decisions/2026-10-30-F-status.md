# F-status decisions

- **The pill reads progress, not only liveness.** It adds two states, `starting` and `stalled`, on top of the crawler stream. `stalled` applies when the API names a reason (`kpi.health.reason`, `stale.reason`, or an exception of kind `writer_stalled`, `cohort_stalled` or `index_lag`), or when the Insights `ingest_per_hour` is 0 and `uptime_s` is at least 8 h, whether or not the crawler is busy (a starved pipeline reads as idle, so idle must not hide it). `ingest_per_hour` is the last full UTC hour, which can start two hours back, so 8 h = the 6 h suppression plus two hours makes the reported window lie wholly after it. Fetching that never reaches the store counts as a stall, so the fetch rate plays no part. A null rate is unknown, never a stall. The client compares and never computes a rate (`runner/standards.md` §4). An `index_lag` stall gets its own wording (storing works; search trails) and counts at any uptime. The server raises `writer_stalled` (no flush for 120 s, and the writer skips a commit with nothing pending) and `cohort_stalled` when nothing is stored, which is also what a fresh start looks like, so inside the 6 h suppression they show `starting`, not `stalled`. An idle crawler (nothing active or pending) has no writer to stall, so `writer_stalled` is ignored while idle. A starved idle pipeline carries `writer_stalled` too (the writer skips empty commits), so the stored-rate verdict (`no_progress`) is checked before a named `writer_stalled`. The constant is 6 h plus 60 s, covering the server's query timeout in the suppression.
- **Startup suppression is a client constant for now.** Nothing in the REST API exposes the remaining sampling suppression (`dht_sample_suppression_seconds` is a metric only), so the pill compares the API's `uptime_s` with 6 h. `starting` shows only while uptime is under 6 h and nothing is flowing yet; a young crawler that is storing shows `crawling`. This narrows the brief's literal "while uptime is under 6 h" so a healthy young install is not labelled "Starting"; the runner flags it to the owner (§2.19). A real API field would replace the constant.
- **Polling.** The pill asks cheap `GET /stats` every 60 s while the tab is visible (and when it becomes visible). It asks the Insights overview (a rollup query) at once when fetching is 0 or the index lags past 30 s, and otherwise every 5 minutes, because a writer can stall while fetches still count. It does not ask while paused. A null fetch rate (first minute) is not treated as odd.
- **Insights overview** shows a stalled banner above the stage strip for the server's own `cohort_stalled` and for the pill's `no_progress` verdict (which needs `uptime_s`, so it comes from the shell). An `index_lag` has its own exception, and a stale banner always comes with a writer stall, so neither adds a second warning.
- **uTP.** `transport.utp` is labelled "not active yet" in the settings messages (label and help); uTP has no runtime effect until CR-4. The Rust schema carries no label text, so no shared-file change is needed.
- **Restarts and visibility.** Kept stored-rate facts are dropped when `uptime_s` goes down (a restart) or the crawler is paused. Coming back to the tab refreshes at most once per 10 s.
- **Insights banner timing.** The `no_progress` verdict on Insights comes from the shell's pill, which exists only after the deferred chrome boots (the first interaction, or 30 s). `cohort_stalled` shows from the overview response alone. A writer stall needs no banner of its own, since the server always sets the stale banner with it.
- **Glyphs.** On phones the words are visually hidden, so the glyph carries the meaning: `starting` uses an hourglass and `stalled` a warning octagon, distinct from `connecting` (dots) and `busy`/`failed` (warning triangle). This replaces the shared `statusIcons.warning`; the warning ink still comes from `ui/status.ts`.
- **fallback_to_tcp.** `transport.fallback_to_tcp` is as inert as `transport.utp` and is labelled "not active yet" the same way.
- **Edits outside the brief's owned paths** (named for the runner): `web/src/lib/shell/progress.ts` (new), `status.ts`, `status.svelte.ts`, `Chrome.svelte` (all under `shell/`, which is owned), `web/src/lib/features/shell/messages/*`, the generated `settings/form/message-map.ts`, and the new `web/e2e/status-stalled.routes.test.ts`.
