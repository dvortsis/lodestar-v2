# F-status decisions

- **The pill reads progress, not only liveness.** It adds two states, `starting` and `stalled`, on top of the crawler stream. `stalled` applies when the API names a reason (`kpi.health.reason`, `stale.reason`, or an exception of kind `writer_stalled`, `cohort_stalled` or `index_lag`), or when the Insights `ingest_per_hour` is 0, `fetched_per_hour` is not above 0 and `uptime_s` is at least 6 h. A rate that is null is unknown, never a stall. The client compares and never computes a rate (`runner/standards.md` §4).
- **Startup suppression is a client constant for now.** Nothing in the REST API exposes the remaining sampling suppression (`dht_sample_suppression_seconds` is a metric only), so the pill compares the API's `uptime_s` with 6 h. `starting` shows only while uptime is under 6 h and nothing is flowing yet; a young crawler that is storing shows `crawling`. A real field would replace the constant.
- **The overview is asked only when `/stats` looks wrong.** The pill polls cheap `GET /stats` every 60 s while the tab is visible, and asks the Insights overview (a rollup query) only when fetching is at 0 or the index lags past 30 s. A healthy install never makes the overview call from the shell. A writer stall with fetching still above 0 is therefore seen on the Insights page (its own banner) before the pill.
- **Insights overview** shows the same stalled banner from its own response (the named reasons, or `ingest_per_hour` 0). It has no `uptime_s`, so the no-progress rule there is only the reasons plus a zero stored rate while the crawler is not paused.
- **uTP.** `transport.utp` is labelled "not active yet" in the settings messages (label and help); uTP has no runtime effect until CR-4. The Rust schema carries no label text, so no shared-file change is needed.
