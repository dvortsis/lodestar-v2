# P-v06-sources-plan decisions (#356)

Slices the v0.6 Sources epic (`E-v06-sources`, build-plan P4) into 25 `SRC-*` slices. The plan is `docs/plan/2026-11-01-v06-sources.md`; the entries are in `runner/slices.yaml`. Docs only. Nothing here reverses or loosens an owner decision, weakens a security or content-safety decision, or changes an owner-set number. The refinements below are the runner's to flag (`docs/owner-decisions.md` §2.19). The open questions are in the plan's §5, with five for the owner (Q1, Q2, Q3, Q15, and Q7, which the runner moved to the owner).

- **One migration, at the next free number** (SRC-1). CR-3, which reserved V14, has no slice and waits behind the 50M import gate (build-plan §0.6). Waiting for it would stall the whole Sources critical path, so SRC-1 takes V14 if CR-3 hasn't claimed it (plan Q12, accepted by the runner). **Flag (§2.19):** this renumbers the V14 reservation in `2026-10-30-master-plan.md`'s migration order. Build-plan §0.6's "then the other source families" means the deferred import families, not v0.6 Sources, so P4's "continues in parallel" applies. It holds `unverified_items` and `torrent_claims` (architecture §18.5) plus `source_state`, the plugin KV store. §18.1 sketches that store without saying where it lives; a table keeps cursors transactional with the items they produced. New externals: `migration-slot` (one migration PR at a time) and one per owner answer (`owner-q1`, `q2`, `q3`, `q7`, `q15`), so gated slices can't launch first.
- **No new trigger on `torrents` inserts.** V13's already costs the crawler's hot path. Unverified rows copy V13's tombstone, quarantine and `cs_hashes` trigger pattern instead, and promotion runs in writer code. V13's `import_candidates` stays import-only (plan Q16).
- **Purge follows §10.10.7:** a Danger zone confirmation with the exact count and size, and no password.
- **First registration of a plugin becomes atomic** (SRC-4). Today a crash between `register_source` (Enabled) and the follow-up disable leaves a consent-gated source on.
- **The snapshot purge covers claims and unverified items.** Both hold names, so owner §2.16, §2.17 and §2.21 apply to them as to `torrents`. This tightens; it doesn't loosen.
- **Claims and unverified items are filtered before storage, locked floor included, and re-judged after it** (§18.7, §20.1). A writer sweep copies #280's import-candidate refile (`docs/decisions/2026-10-31-B-import-refile.md`) and runs at start and whenever the filter engine's version changes. The plan names this explicitly because §18.5 describes the tier without restating it.
- **A crawled hash that's already unverified is promoted, not duplicated** (§18.5). The writer checks every new `torrents` insert (v1 and truncated v2), and SRC-2 measures that check's cost against the per-insert budget.
- **Verification fetches of unverified keys stay behind a switch, default off,** until the crawler acceptance soak ends. They share `fetch_queue` and the fetch pool (§18.4), and the v0.6 crawler gate is measured with no imports (build-plan §0.6).
- **Search fields ride the M7 `SCHEMA_VERSION` bump** (build-plan §1.3). Until then, unverified items are stored but not searchable. A new external, `m7-schema-bump`, gates SRC-3.
- **Two new crates:** `crates/sources-feeds` (pure, fuzzed parsers) and `crates/sources-plugins` (one module per plugin behind its `src-*` feature, §18.1). The Sonnet glue slices then own one file each and can run in parallel (build-plan P4).
- **AnimeTosho reuses the Torznab parser,** since §18.2 calls its feed "Torznab-style". There's no separate parser slice for it.
- **Sonarr/Radarr webhooks are their own slice (SRC-11b),** because an inbound endpoint is a new auth surface. It may slip to v0.7 without blocking the v0.6 tag.
- **Scheduler v2 is narrowed for v0.6:** per-host limits, schedule windows and per-plugin egress only. Shares per resource class and auto-balance wait for yield data (§18.4 says "v0.6+"; plan Q10).
- **The runner's answers to the plan's questions** (2026-11-01, flagged under §2.19). Accepted as recommended: Q4 (rate limits) and Q11 (a 1M dead-hash queue cap), both §2.26 numbers; Q5, Q6, Q8 (a hash-checked cached `.torrent` is verified metadata, with provenance "torrent cache" and the full filter pipeline still applied), Q9, Q10, Q13, Q14, Q16 and Q17 (the Jobs view is a Settings screen, no new route). Q12 follows P4. **Q7, the Sukebei feed, goes to the owner** as a content-safety scope decision: until the owner answers, SRC-10a ships Nyaa only and the new SRC-10e waits on `ext:owner-q7`.
