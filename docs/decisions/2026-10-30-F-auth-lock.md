# F-auth-lock decisions

Fixes items I1 and I2 from the fresh review of #178 (F-auth). I1 predates #178: every auth change wrote `auth.json` (write, file fsync, rename, directory fsync) while holding the state's write lock, so `verify`, which runs on every request, waited on the disk. On Unraid with the data directory on a spun-down array disk that is seconds, and the whole UI stalled during a password change, a sign-out of other sessions or a proxy save.

- **A save lock serialises changes; readers never wait on the disk.** `Auth` gains `save_lock: Mutex<()>`. Every change (setup, password change, sign-out-others, proxy settings) takes it, copies the state under a brief read lock, checks its preconditions against that copy, builds the next state, saves it, and only then takes the write lock for the swap. The F-auth guarantee stands: a failed save changes nothing, live or after a restart. `verify`, `client_ip`, `proxy_signs_in`, `needs_setup` and `proxy` take only the read lock, which is now never held across a save.
- **Lock order: `save_lock`, then `setup_token`, then `state`.** Each is optional; nothing takes `save_lock` while holding either of the others, and neither `setup_token` nor `state` is held across the disk or Argon2. The order is written on `State` in `auth.rs`. Setup is the only path that holds two at once: it takes the token lock and the write lock together for the swap, so nobody sees the instance claimed with its token still pending.
- **Argon2 runs before the save lock, with no lock held.** Password change checks the old password against a copy of the stored hash and hashes the new one first; then, under the save lock, it re-reads the state and goes ahead only if the stored hash is still the one it checked against. Every writer holds the save lock, so a match there still holds at the swap. Of two changes racing from the same password, exactly one wins and the other gets `bad_password`, which is true by then. Setup does the same with its token: checked and hashed first, re-checked under the save lock (`setup_done` if another setup won). The alternative, hashing under the save lock, would be simpler but would queue every other change behind two Argon2 runs; re-checking one string is cheap and keeps the check-then-act consistent.
- **Sign-in and the fresh-password check copy the hash out too.** They used to run Argon2 under the read lock. The standard library's `RwLock` lets a waiting writer block new readers, so a swap waiting behind a sign-in's Argon2 would still have stalled `verify` for that long. A sign-in that races a key rotation returns a cookie signed with the old key, which simply doesn't verify: the same outcome as signing in just before the change.
- **The save lock ignores poisoning.** It guards no data (`Mutex<()>`), so a panic in one change leaves nothing for the next to distrust; the state lock keeps its `expect`.
- **A failed directory fsync logs `auth.dir_sync_failed` once per run (I2).** The save still returns `Ok`, as F-auth decided: the new file is in place. The warning says a power cut could bring back the previous file. Once per run because the cause (a filesystem that refuses directory fsync) repeats on every save; it is a new `Warn` event in the `AUTH` catalogue with no fields, and the logs catalogue golden is regenerated.
- **Test seams are unit-test only.** `auth/hooks.rs` exists only under `cfg(test)`: a hook called where a change takes the save lock and where it starts writing, and a switch that fails the directory fsync. The lock tests (`auth/lock_tests.rs`) are unit tests for that reason, not in `crates/api/tests/`. They force each interleaving rather than hoping for it: a save held mid-write while readers and sign-ins answer within a deadline, two password changes and two setups racing past their checks, and the warning firing once over three saves. Making `commit` hold the write lock across the save again fails the reader test.
- No owner decision, security decision or owner-set number changes.
