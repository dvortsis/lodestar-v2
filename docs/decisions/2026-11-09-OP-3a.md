## P8: ExpectedBucketOwner on every cloud-fleet S3 call
- One wrapper, `apply.OwnedS3`, is the only S3 client the live backend, the evidence writer and the S3 lock store see. Each of its three calls passes `ExpectedBucketOwner`: `get_object`, `put_object` and `delete_object`. Any other method raises, so a later change can't reach S3 around it.
- So a bucket name re-registered in another account can't receive the lock, `fleet.json`, the flag, the ledger or the evidence. The owner value is validated as 12 ASCII digits.
- **The gap: Terraform's own S3 backend** (the state file and its lockfile) can't send `ExpectedBucketOwner`. Closing it needs an `s3:ResourceAccount` condition on `LodestarFleetOperator`'s policy in OP-2a's template, which is outside this slice. **For the runner:** a small follow-up to the template.

## Live `run <step> <vm>` (steps/run.py, steps/remote.py)
- It runs inside `act`, under the fleet lock, after the gates, the main-head check and the ancestor checks, as before. The steps built here are `vm-status` and `leak-test`. Every other allowed step refuses with "step not built yet (OP-3b)", except renew-vpn, which chains into deliver-pia as OP-2b made it.
- **Targets:** the VM's address and host key come only from `fleet.json`. They're shape-checked as deliver-pia does: one dotted IPv4 address that isn't loopback, link-local, multicast, unspecified or reserved; one ed25519 key line; and the fingerprint must match.
- **The step's files are read from the fleet's pinned commit** (`git show <commit>:infra/fleet/steps/vm/<file>`), never from this checkout or a comment. A fleet pinned before a step existed can't run it.
- **Its own `/32`:**
  - OP-2's `set_job_rules` opens `job-<run>-<attempt>` on the fleet's firewalls, fenced, and only for one IPv4 address inside `/meta`'s Actions ranges (checkip). `act` doesn't sweep, so it needs no `actions: read`; the reaper and deliver-pia sweep.
  - A `finally` closes the rule, whatever happened: a refusal, an SSH error, or a half-opened rule set. A rule that won't close is escalated with the step's result.
  - The close runs under the tolerant fence (as pre-empted paths do): a failed lock read (S3) doesn't leave the rule open, but a lost lock still stops it.
  - A lost lock propagates, and nothing else runs after it.
- **SSH:** the same options as deliver-pia: `-F /dev/null`, `BatchMode`, `StrictHostKeyChecking=yes`, a per-run `known_hosts` holding exactly the pin, ed25519 only, and user `lodestar` with `sudo -n`.
  - **The fixed bootstrap:**
    1. it takes **the same per-VM lock as delivery** (`/run/lodestar-pia.lock`), so a step and a delivery never overlap; a busy VM answers `fail vm_busy`, exit 21;
    2. it unpacks the in-memory tar into a fresh root-only `/run/lodestar-step`, deleted on EXIT (HUP, INT and TERM exit);
    3. it runs the step under `timeout`.
  - The session's own timeout is the step's, plus the lock wait, plus a minute. `act`'s 50-minute job covers the longest, the leak test (10 minutes).
- **The output allow-list** (the runner kept it).
  - The control side keeps only lines matching `(ok|fail|skip) <name>` or `count <name> <int>`. Names are `[a-z][a-z0-9_]{0,40}` and counts are up to 12 digits.
  - At most 64 KiB and 200 lines are read, and everything else is dropped. So a step can't put an address, a name or an ID in a log or comment, whatever it prints.
  - Tests feed it addresses, long lines, ANSI escapes, tabs, CRs, non-ASCII and a missing final newline.
  - The report is one line of fixed words, for example `run vm-status main: done; 7 ok; failed: lodestar_running; collectors_running 0, disk_free_gib 18, …`.
- **Step arguments** (none yet; start-block will have one) must be keys from the step's own list, with values in `[a-z0-9_-]{1,64}` or a 40-hex commit. Anything else is refused before SSH.
- **The FLEET_SSH_KEY and the runner's address** are masked (`::add-mask::`, line by line) and never printed.

## The VM stack (`steps/vm/compose.yaml`; the runner's Q1/Q2)
- **gluetun** is pinned by digest, with these settings:
  - PIA through the custom WireGuard provider, its firewall on (nothing sets the variable that disables it);
  - `FIREWALL_VPN_INPUT_PORTS` empty, `TZ=Etc/UTC`, `oom_score_adj: -500`;
  - `no-new-privileges`;
  - `wg0.conf` mounted read-only from where OP-2b writes it.
  **Lodestar** runs in gluetun's namespace (`network_mode: service:gluetun`) with `no-new-privileges`, no devices or ports, `TZ=Etc/UTC`, a 60-second stop grace, and **`cap_drop: ALL` with only CHOWN, SETGID and SETUID added back**, the set `packaging/docker/README.md` documents for dropping root. With NET_RAW gone, a compromised Lodestar can't send raw frames past gluetun's firewall. It starts only with the `block` profile. Its image is `${LODESTAR_IMAGE}`, which start-block (OP-3b) sets from the screen rules after validating it.
- **The only host port** is `127.0.0.1:8090:8090`, the UI on the host's loopback for `ssh -L`. Tests parse the file and assert all of this.
- **The file is read at the fleet's pinned commit,** copied into `/home/lodestar/lodestar`, and run as compose project `lodestar` with container names `gluetun` and `lodestar`. Collectors (OP-3b) are `lodestar-collector-*`.

## The leak test (`steps/vm/leak-test.sh`; plan 0d)
- **It refuses mid-block:** with `lodestar` or any `lodestar-collector-*` container running, it fails `block_running` and touches nothing. The endpoint block would cut a live crawl, and Lodestar's traffic isn't what it judges.
- **Setup:** it recreates gluetun alone (`--force-recreate`) from the committed compose file and the current `wg0.conf`, so the configuration under test is the one in force, and waits for its health check. It pulls the pinned probe image and checks the probe tools exist (`probe_tools`).
- **Tunnel up:** every probe runs from the throwaway probe container in gluetun's namespace, which Lodestar shares.
  - the IPv4 echo answers, and isn't the host's own address;
  - TCP to a literal address (1.1.1.1:443) connects. That's the positive control for the down probe;
  - IPv6 fails;
  - DNS answers through gluetun's resolver (`nameserver 127.0.0.1`).
- **Tunnel down:**
  - the WireGuard endpoint (read from the root-only `wg0.conf`, validated as IPv4 and a port in 1–65535 with leading zeros normalised, never printed) is dropped in the host's `DOCKER-USER` chain. gluetun keeps running, so its firewall is what's tested;
  - a capture runs on gluetun's veth (found from the namespace's `iflink`), excluding ARP and the endpoint's WireGuard flow;
  - the probes:
    - IPv4 by name;
    - **TCP to the literal address, which needs no DNS** (so a kill switch that leaks TCP is exercised even with DNS down);
    - IPv6;
    - DNS for **a name not asked before** (`example.net`, so gluetun's cache can't answer);
    - DNS straight to an outside resolver;
    - a UDP send.
  - Every probe must fail, and **the capture must hold zero packets**. The capture must also still be running after the last probe (`capture_alive`), and reading it back must succeed (`capture_read`). A capture that died after writing its header, or a file that can't be read, fails; it never counts as zero.
- **Recovery:** the block is lifted, and the tunnel must be healthy **and the echo must show the same exit address as before**. An EXIT trap lifts the block whatever ended the test (tested with a failing first delete).
- **It also checks `/run/lodestar-pia` is gone.** The step already holds the VM's lock, so no delivery can be running. A plain `test ! -e` is correct here; `flock -n` on a lock the step itself holds would always fail.
- **Missing tools refuse** (docker, iptables, tcpdump, ip). Every line is in the output grammar, and it ends `ok leak_test` (exit 0) or `fail leak_test` (exit 1). A failure is a stop condition: no crawl starts on that VM (OP-3b's start-block will require a passing leak test). The step timeout is 10 minutes.
- **Accepted for now:** checking the host's own IPv6 (0d's separate host check) is left to OP-3b. Stopping the gluetun container (a different case, 0d) is a runbook drill (OP-3c).
- **Tests run the script against stubs** of docker, iptables, tcpdump, ip and sleep:
  - the pass case;
  - each failure: a captured packet, IPv4 or TCP leaking with the tunnel down, no TCP with the tunnel up, IPv6 open, the exit equal to the host's address, a non-address answer, DNS not local, the probe image missing its tools, a capture that died after its header, an unreadable capture, no recovery, recovery through a different exit, a failed delete;
  - hostile `wg0.conf` endpoints, a missing config, a compose failure, a failed probe pull, a left-over login, and refusal mid-block.

## renew-vpn takes effect (the runner's item from #650)
- deliver-pia's bootstrap, after the WireGuard step, restarts gluetun (and Lodestar after it, operations §4.3), because a new `wg0.conf` takes effect only on a restart.
- **Never mid-block:** with a `lodestar-collector-*` container running, it leaves the tunnel alone and exits 30. The report says "renewed; takes effect after the block", and that counts as delivered. start-block (OP-3b) always recreates gluetun from the current `wg0.conf`.
- A failed restart exits 31 and escalates ("delivered, but restarting the tunnel failed"). Lodestar gets a 60-second stop timeout on that restart, and `docker inspect` looks only at containers.
- A gluetun that exists but isn't running is left alone. start-block brings it up from the current `wg0.conf`.
- With no stack yet (the first delivery after `up`), nothing restarts.
- Tested end to end with a stub `docker`: no stack, gluetun and Lodestar, gluetun alone, mid-block, and a failed restart.
