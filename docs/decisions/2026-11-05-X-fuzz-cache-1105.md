# X-fuzz-cache-1105 decisions

Slice session, 2026-11-05. Runner brief X-fuzz-cache-1105: the follow-up X-fuzz-1105 (#484) handed on in `docs/decisions/2026-11-05-X-fuzz-1105.md`, once SRC-13b (#479) had landed. Architecture §6 (hostile-input limits), §14 M1 (fuzzing), §18.2 enrichment #3 and §18.7.

- **The body check is a sync, I/O-free `torrent_cache::verify_body(body: Vec<u8>, lookup: &Lookup, host: &str) -> Result<Verified, Miss>`** (`crates/sources-plugins/src/torrent_cache.rs`). It's the code that was inline in the private async `TorrentCache::ask`, moved unchanged: the `.torrent` parse under `LIMITS`, `raw_info`, the info dict re-parsed with no encoding hint, then `verify`. The same caps and the same misses: `Invalid` for either parse, `Mismatch` for another hash. `ask` now fetches the body and calls it, then counts the miss as before (`Stats::invalid`, `Stats::mismatched`), so counting stays in one place.
  - **It returns a `Verified`, not the tuple X-fuzz-1105 sketched.** A `Verified` is still made only after the hash check, now in `verify_body` rather than in `ask`, so the guarantee is the same and the fuzz targets reach `Verified::claims` without a test-only constructor. `verify_body` is public: anyone holding a body and a `Lookup` can check it, and the result can only be a file whose dict hashes to the key. The caller names the host; it's only shown on the status page.
  - **The body is taken by value** and dropped once the raw dict is copied, as `ask` did, so a file near the 8 MiB cap isn't held while its dict is parsed again.
  - **Proof of no behaviour change:** the existing tests are unchanged and pass, and `the_async_lookup_and_verify_body_agree_on_the_fuzz_seeds` (`crates/sources-plugins/tests/torrent_cache.rs`) runs every `torrent_cache` seed, with the key the target picks, through the plugin's real async lookup over a fake cache and through `verify_body`. A hit gives the same key, why, v2 flag, host, file, raw dict, claims and provenance; a miss is the same kind and counted once.
- **`torrent_cache` fuzz target retargeted at `verify_body`.** It still works out the key with its own parse (and still checks `raw_info`'s span names the same swarm as the file parse), then calls `verify_body`: an unparsable body is `Invalid`, a parsed one verifies under its own hash (v2 only when it isn't the v1) and is a `Mismatch` under any other key, and a kept `info_raw` re-parses to the kept `info`. Bit 7 of the first byte now also picks `Why`. The seeds are unchanged.
- **New `verified_claims` target** for `Verified::claims` and `Verified::provenance`. An even first byte takes the rest as a whole body; an odd one builds a `.torrent` from the input around a fixed info dict (flags for `private` and `creation date`, then the comment and one tracker per `0x00`-separated segment), so the fuzzer works on the untrusted fields outside the dict rather than on reaching a valid one. It checks claims are deterministic, already clamped and only trackers and a description; trackers are the file's own in the `url` crate's form, in order, once each, within `MAX_TRACKERS` and `MAX_TRACKER_URL`, `http`, `https` or `udp` only, with no query, fragment or user name; a private dict gives no tracker and no comment; the description is a non-empty prefix of the file's comment, and a public comment is never lost; provenance is Medium with no reference and keeps `creation date` only within `MIN_CREATED..=MAX_CREATED`. 15 seeds in `fuzz/seeds/verified_claims/`: the `torrent_cache` seeds keyed by their own hash, the plugin's `hit` body, four built ones (public trackers and duplicates, the plugin tests' hostile trackers, a private dict, a comment only) and the regression input below. The target adds `lodestar-sources` (a workspace crate) and `url` at the plugins' pin `2.5.8` to `fuzz/Cargo.toml`; no new third-party crate.
- **The first crash, fixed: a tracker was kept as written, not as checked** (security; found by `verified_claims` within seconds). `public_tracker` parsed a tracker with the `url` crate and judged that reading, but `claims` kept the file's raw text. The WHATWG parser reads `http:1.1/announce^udp://127.0.0.1:6969/announce` as `http://1.0.0.1/announce^udp://127.0.0.1:6969/announce` (url 2.5.8 leaves `^` unencoded in a path; corrected by X-claim-trackers), a public host, so the raw string, with a loopback address in it that a looser parser could take as the host, was stored as the torrent's tracker. `public_tracker` now returns the normalised URL, the address that was checked, and that's what's kept and deduplicated, with `MAX_TRACKER_URL` applied to it as well. Ordinary trackers are unchanged (the fixture's `udp://tracker.public.example:1337/announce` stays as it is); a non-canonical one is stored in canonical form (`HTTPS://Tracker.Example:443/announce` becomes `https://tracker.example/announce`), which loses nothing a client needs. Regression test: `a_tracker_is_kept_as_checked_not_as_written` (plugin unit tests), and the input is the `built-normalised-tracker` seed. This tightens SRC-13's tracker rule, it doesn't loosen it, so it's the runner's call (§2.19).
- **Audit: no other place judges a tracker by one reading and keeps another** (runner, review of #491). I looked at every path that stores, dials or forwards a tracker URL from a `.torrent`, a claim or the settings:
  - **`full_scrape`** (`crates/sources-plugins/src/full_scrape.rs`, `tracker`): the user-entered address is parsed by `TrackerUrl::parse`. It keeps `TrackerUrl`'s canonical form as `announce`, and the `scrape` URL derived from that form. The public-host check (`check_url`) runs on that same scrape URL, which is what's dialed. The user name, query and passkey checks use `url::Url::parse` on the same text, and that's the parser `TrackerUrl` uses (after the same trimming). Same reading, nothing to fix.
  - **The tracker health scraper** (`crates/pipeline/src/health`) and the **settings and config checks** (`crates/lodestar/src/settings/trackers.rs`, `config.rs` `health_config`): these take only `TrackerUrl` values built from the user's own config, and dial their canonical form. Trackers from claims are never scraped.
  - **Claims from feeds and other plugins** reach the store through the pipeline's `store_claims` (`crates/pipeline/src/unverified.rs`). It filters them with `tracker_url`, a text-level plausibility check: scheme, length, a non-empty authority, and no whitespace or control characters. It makes no judgement about the host, user name or passkey, so no parse differential can slip past it. Those trackers are stored only: no magnet link includes them, no endpoint returns them, and nothing dials them (corrected by X-claim-trackers, which also puts them through a host guard before storage; see `docs/decisions/2026-11-05-X-claim-trackers.md`). The other plugins (`clients`, `arr`) claim no trackers. Nothing to fix here. `unverified.rs` is ENR-1's in any case.
  - **So `torrent_cache`'s `public_tracker` was the only tracker that was checked on a parsed reading but stored as its raw text.**
- **`fuzz/Cargo.lock`** also gains `lodestar-release-parser` under `lodestar-filter`: main's lockfile was stale there, and any fuzz build adds it.

## Campaign
Run on a 4-core cloud container, both targets at once, at this branch's head, `<target> fuzz/corpus/<t> fuzz/seeds/<t> -max_total_time=1800 -max_len=262144 -rss_limit_mb=2560 -timeout=10` (built with `cargo +nightly fuzz build -O`), from an empty corpus.

**No crashes, hangs, timeouts or OOMs in the 30-minute runs.** The one crash, the tracker differential above, came from a 30 s smoke run of `verified_claims` before the fix; both campaigns ran on the fixed code.

| Target | Time | Execs | exec/s | Seeds | Corpus (entries / bytes) | Coverage (cov / ft) | Peak RSS | Findings |
|---|---|---|---|---|---|---|---|---|
| `torrent_cache` (now on `verify_body`) | 30 min | 12.2 M | 6,772 | 22 | 2,913 / 950 KB | 5,170 / 15,229 | 508 MB | none |
| `verified_claims` (new) | 30 min | 3.2 M | 1,801 | 15 | 5,789 / 1,110 KB | 7,096 / 30,887 | 527 MB | none (after the fix) |

`verified_claims` is slower because each input is parsed twice (the target's own key parse, then `verify_body`) and `claims` parses every tracker URL. libFuzzer's length control held its inputs to about 700 bytes in this run, which is enough for the built shape's comment and a few trackers. A later campaign can give it `-len_control=0`.
