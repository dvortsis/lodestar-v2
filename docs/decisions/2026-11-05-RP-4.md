# RP-4 decisions: SP-3 flooding, judged in the writer (PR to be numbered)

Plan `docs/plan/2026-11-04-v06-rulepacks.md` §4.3 "RP-4" and Q10; architecture §20.1, §20.6, §20.8. Builds on RP-0 (versions, shadow), RP-2 (overrides) and RP-3 (shadow evidence from `filter_hits`). No migration, no new `settings` row: SP-3's state is memory only (plan §3). No owner decision, security or content-safety decision, or owner-set number changes; the numbers are the runner's (Q10).

## The rate map (`crates/filter/src/flood.rs`)
- **Q10's numbers:** flag at 20 near-duplicate names in an hour, demote at 100, at most 10,000 publishers and sources tracked, the one seen longest ago evicted (a linked list over a slab, so a commit costs O(1)).
- **The hour is 12 buckets of 5 minutes.** A count holds the names of the last 55 to 60 minutes and never one older than an hour. A clock that goes back counts in the newest bucket.
- **Near-duplicate is the release parser's title** (`class.title.release.title`), which already leaves out the episode, season, quality, source, codec and group tokens, read through the filter's own normalization (`normalize::tokens`: look-alike letters, invisible characters, case) and hashed. At most its first 32 words count. A name with no title has no signature and is never counted.
- **16 signatures per publisher.** A new one takes the slot with the fewest names in the window, the one seen longest ago among them. A flood's count keeps growing while one-off titles take turns in the other slots. Eviction only forgets names, so a count never exceeds the names really seen: SP-3 can't flag a publisher for names it didn't send.
  - **Known limit:** a flood that sends 16 or more different titles between each of its own names is forgotten each time. It has to send 16 times more names to do it, and those are its own.
- **No text is kept, and nothing grows with input.** A publisher is hashed with SipHash under keys drawn at process start (`RandomState`), so no publisher string can be chosen to land on another publisher's count. The map holds hashes and counters only (about 800 bytes a publisher, so about 8 MB at the cap; the slab grows by doubling but never past the cap). A publisher is already clamped to `MAX_PUBLISHER` bytes when its claims are read, and only hashed here.

## The rule (`crates/filter/src/packs/sp3.rs`)
- **SP-3 is one rule with two actions.** Its version's action is demote, applied from the demote level. At the flag level it's capped at flag. An override you set (RP-2) replaces both: it sets the rule's action wherever the rule matches.
- **Added after RP-0** (`ADDED_AFTER_RP0`), declared last so every other rule's index stays. It's evaluated after SP-1 in the spam pack. On a store seeded before it shipped, with the spam pack on, it's pending and runs in shadow (its shadow hits feed RP-3's acceptance preview) until accepted, or until the pack or the rule is switched off and on again. A fresh store applies it. Its first version `widens`, so accepting it needs no password. Its shadow side holds only what the applied side (nothing) doesn't, which agrees with `widens`. The sequence fixtures check this.
- **RP-1's corpus already exempts it** (`corpus::STATEFUL`). The manifest's per-rule golden marks every other item of the golden set flooded, so SP-3's row records that it matches exactly where the writer counted a level and nowhere else.

## The engine entry point (`Engine::judge_flooded`)
- **The torrent is judged again with SP-3 matching at the level counted,** through the same `judge_doc` path as every judgment. Precedence is the engine's own: the floor, then CSX-5 Override, the core with your exceptions, *Always allow*, your rules, then the pack layer, where SP-3's switches, your exception for it and your override apply, and the strongest action wins. Nothing is reimplemented beside it.
- **The adult reading is judged as the writer's other verdicts are:** an always-adult source's find (`source_adult`) or one your Is adult rule makes adult is judged as adult too, its floor first, and the stricter verdict stands.
- **The writer keeps the stricter of its first verdict and this one.** Adding SP-3 only adds to the pack layer, so this one is never weaker. The test fixture asserts that on every commit. A tie keeps the first verdict's rule.
- **Only flooded commits pay for it.** Below the flag level nothing is judged again.
- **`filter::Item` is unchanged.** `packs::Ctx` gains a `flood` level, `None` everywhere but here, so prepare's verdict leaves SP-3 out.

## The writer (`crates/pipeline/src/writer.rs`)
- **Counted at commit, in the authoritative check** (`judge`), after the first verdict and before quarantine sealing, for every commit of a torrent not yet stored (a key in the have-filter, such as a refetch or a cache's file offered again, is the same name and isn't counted again): a fetched torrent's and a torrent cache's file. Counting happens in commit order, so verdicts don't depend on prepare's timing.
- **Whom a commit counts against:**
  1. the publisher a torrent cache's claims name for the file;
  2. else the publisher in the claims of the unverified item it promotes;
  3. else that item's source, if it counts;
  4. else the lease's source, if it counts.
  An empty publisher counts as none.
- **The DHT never counts** (Q10), **and neither does an importer** (runner's call under §2.19, flagged in the PR). The sources that count are every registered source except a peer finder and an importer (`flood_counted`), read from the plugin's own kinds, not its name. The DHT is the only peer finder. An importer replays a dump's history in minutes, so its commit-time rate would flag every busy series it imports. The mask is computed once at start in `crates/pipeline/src/lib.rs`.
- **No store read in the usual case.**
  - A find only the DHT made, the crawl's usual commit, reads nothing: the unverified item is looked at only when a source that counts is among the commit's finders and the store holds unverified items (one `EXISTS` per batch, read only when a commit needs it).
  - The writer notes whom each claim it hands to the store counts against (`Claimed`: the key, and the publisher's flood-map key or the source), at most 65,536 keys, the oldest forgotten first, memory only. A commit that promotes one of them reads nothing.
  - Only a key claimed before this start, or forgotten since, costs one read of its unverified item (a measured 2.4 µs). A read that fails reads as no item.
  - A claimed item that the DHT alone fetched before any feed's sighting reached its lease isn't counted.
- **Memory only, rebuilt from nothing at start** (plan §3): a restart forgets at most one window.
- **A stored torrent judged again later** (reclassified as adult, §20.9) is judged without SP-3: the rate it was counted at is gone. A mark SP-3 set stays unless that judgment refiles the torrent with a decision of its own. The map lives in the writer and moves into its blocking judge task and back with the store, so no lock is added.
- **SP-3 is counted while it's off,** so switching it on finds the rate as it is. A flooded commit is judged again only while the spam pack and SP-3 are on.
- **A CSX-5 entry in shadow mode is logged once:** the two judgments log it with their own decision's action, and the writer keeps one entry, with the action of the decision that stands.
- **Known limits**, each erring toward not flagging:
  - A source that sends 10,000 or more distinct publisher names an hour evicts every tracked origin, so no flood reaches a level. That's inherent to a least-recently-seen map at Q10's cap.
  - A claimed item that the DHT alone fetched before any feed's sighting reached its lease isn't counted, so a flood that also spreads on the DHT can partly escape.
  - A note in `Claimed` is written as the claims are handed to the store, before the store accepts them. It can name a publisher the store's item no longer holds (a later feed's claims, a purge). That misattributes a count. It never adds one.
  - A torrent cache working through its backlog, with no publisher in its claims, counts per cache source at commit time, like a feed. Whether a cache should count like an importer is a question for the runner.
- **For RP-6's copy:** an override of SP-3 with its base action (demote) also turns the flag level into demote, because an override sets the action wherever the rule matches. `GET /filters` shows SP-3's action as demote. RP-3's acceptance preview reads an applied SP-3 hit at flag as the base action. That only matters for a future SP-3@2, and it errs strict.
- **The clock is injected in tests** (`Flooding::clock`): no test sleeps.

## Measurements
Release build, this session's container (`sp3_writer_cost`, an `#[ignore]` test in `writer.rs`; `cargo test --release -p lodestar-pipeline --lib sp3_writer_cost -- --ignored --nocapture`). Each figure is per commit, against the store's insert in batches of 256:
  - **A crawl commit** (found only by the DHT): **0.03 µs**, 1.4% of an insert (2.2 µs on this small store; SRC-2 measured 28.5 µs on a store of 1M items, which makes it smaller still).
  - **A feed's commit whose claims came this start:** **0.28 µs**, 2.0% of that commit's own writer cost (14.4 µs: the insert plus promotion's read and judgment of the claims).
  - **A torrent cache's file naming a publisher:** **0.18 µs**, 1.2%.
  - **A feed's commit claimed before this start:** **2.4 µs** (16.5%), for the one read of its item. That's over the 5% gate, for this case only, and is flagged to the runner. It's paid once per such key, while the backlog from before a restart is fetched.
  - **A flooded commit's second judgment:** **3.1 µs**, only at 20 or more near-duplicates in an hour.
  - The gate is at most 5% of the writer's per-insert cost. The test asserts it for the crawl's and a feed's commits, and they pass. It's an `#[ignore]` measurement that no CI job runs; whether to add it to one is the runner's call (`ci.yml` isn't this slice's).
- **Architecture §3** ("Coordinator ingest ≥ 1,000 new verified torrents/s", "New torrent → searchable < 5 s") still holds. A crawl commit gains a bit test. A flooded commit gains a second judgment, which is under the engine's 50 µs budget. The 50 µs filter budget isn't raised, and SP-3 isn't part of it: it isn't judged in prepare.
