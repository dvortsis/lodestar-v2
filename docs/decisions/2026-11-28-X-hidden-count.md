# X-hidden-count decisions

Slice `X-hidden-count`, the rest of P7 from the UI review of 2026-11-13 (`docs/review/2026-11-13-ui-ux/01-review.md` P7, `02-skills-pass…md:66`): "2,196 results", "2,208 torrents" and "2.2K" appeared together on Search with nothing saying what each counts. The runner decided the points marked "runner" (§2.26) and flags them to the owner (§2.19).

## What each count was
- **"2,196 results"** (toolbar): `GET /search` `total`, the matches after the default exclusions (filter-hidden, unverified, and Adult while it's hidden). Correct; unchanged.
- **"2,208 torrents"** ("Index still growing" banner, Home's "Search … torrents"): `GET /search/state` `searchable_torrents`, the serving index's `num_docs`, so every indexed torrent, the hidden ones included. The same figure as Insights' "Searchable torrents".
- **"2.2K"** (status pill, "Idle · 2.2K torrents"): the `crawler` event's `torrents`, rows in the store (`Pipeline::torrents()`), which also holds what the index hasn't committed yet. A third figure, close to the other two but not equal.

## Decisions
- **"N hidden · Show" is built here (runner).** X-search-toolbar (#1075) deferred it (its decisions file): `/search` had no hidden count, so the gap between results and searchable had nothing to explain it.
- **It counts exactly what "Show" brings back (runner; content safety, §20.9, owner §2.12).** The count runs `base_query` with `hidden: true` under the request's own Adult visibility and verified default, ANDed with `hidden:yes`.
  - It never counts Adult while Adult is hidden.
  - It doesn't count unverified torrents: "Show" (`hidden=true`) doesn't bring those back ("Show unverified" does, §18.6). The runner's first wording named unverified torrents too; counting them would break its own rule that the count match what "Show" adds, so the runner approved leaving them out.
  - Quarantined and dropped torrents are never in the index, so they're never counted. A torrent a held write deletes drops out at the next commit, as it drops out of `total`.
  - Tested through the route (`adult_visibility.rs`): an Adult torrent and a film both filter-hidden, with Adult hidden, count 1, and `hidden=true` adds exactly that one; with Adult shown, 2.
- **A follow-up request, not a field on the first page (runner).** Inline on `/search`, the second count added 28–57% to the first-page p95 for ordinary queries and about 700% for swarm queries on the bench corpus (it evaluates the user's query again in full; few hidden torrents don't make it cheaper). So:
  - **`POST /search/hidden`**, a route of its own, rather than a limit-0 form of `/search`. `/search` takes limits of 1–200, and a count-only mode there would have to fake `hits`, `total` and the rest, and keep that mode out of the result cache and cursors. The new route has a one-field response (`SearchHiddenCount`) and nothing to keep out. It takes the search's own body (`q` or `ast`, `hidden`, `tz`), so parsing, validation and auth are the search's (`request_ast`, `tz_param`, `same_origin_json`, behind the same login).
  - **Free skip.** It first counts what "Show" could reveal across the whole index: `hidden:yes` under the request's Adult visibility and verified default (`base_query`), not the raw posting list. With nothing there it answers 0 without running the query. The probe is restricted like the count itself (runner review): a raw probe would answer fast or slow depending on whether filter-hidden Adult exists, which tells a viewer with Adult hidden something it may not see. Tested: an index whose only hidden torrents are Adult answers 0 for every query while Adult is hidden.
  - **A regex that stopped early** (`regex_stopped`, out of its verify budget) gives null, as recovery's counts do: its total covers only what was verified.
  - **What "Show" adds, by definition.** The count is the `hidden=true` search's total less the search's own, each on a lease taken as that search takes it. A count of `query AND hidden:yes` on its own lease would take its own stem fallback (§8: stems below 10 exact matches), so with a few hidden matches it would count stemmed ones that "Show" doesn't add (fresh self-review). Past 100,000 matches both totals are estimates and neither search falls back to stems, so the hidden ones are counted alone there, unless that count itself stemmed (then null). Tested with a word only stems match (`movies`). Each count reads the index serving at the time, so a commit between them can move the answer by what it added, as a search a moment later would.
  - **Unverified torrents.** Nothing is indexed as `verified:no` today (`stored_verified` gives `yes` or `imported`), so no fixture can hold a hidden unverified torrent. Both counts are built with `base_query`, as the search is, which adds the verified default; the rule holds by construction.
  - **Budget.** All of the follow-up's counts share one `HIDDEN_COUNT_BUDGET` deadline (the recovery counts' 20 ms). Past it, or when the count would be an estimate, the answer is `null` and the toolbar shows nothing. On the bench corpus (200,000 torrents, CI's `search-bench`) the free skip's p95 is 0.2–1.0 ms for every query shape; the full count, forced as if hidden torrents existed, is 0.3–12 ms, and 19.9 ms for regex (19 of 300 out of time).
  - **No cache.** The result cache keys first pages and their leases; the hidden count runs on a lease of its own for another query, so keeping it there isn't cheap. A repeat search counts again, within the budget.
  - **The client.** The toolbar asks after the rows render (in the next animation frame, then asynchronously), for the query the rows answer (`results.query`), never for a query still loading, and shows the count only while the store is `ready` and not refining: a new query, whether it keeps the old rows (refining) or not (loading, or failed), hides it, so "Show" never applies to a query whose rows aren't on screen. A forced reload of the same query (a Block hid a row) names it afresh (`results.query` is a new object each answer), so the count is asked again. A newer query, sort, visibility or reload of the rows aborts the request, and an answer for rows no longer shown is dropped. A failure shows nothing. Tested in `ResultsToolbar.test.ts`, the stale answer included, and in `search-toolbar.routes.test.ts`, which holds the answer and checks the count line keeps its height.
- **The toolbar** reads "2,196 results · 12 hidden by filters · Show" (or the short form, below) while the count is above 0, and nothing extra for 0, null or a failure. The words are §20.3's and the glossary's `hidden_by_filters` ("N hidden by filters · Show"); §10.4's bare "N hidden · Show" stays junk's, for the slice that adds the default junk threshold. "Show" sets `hidden=true` (`search.setHidden`), so Back undoes it, and moves focus to the results (as Skip to results does), since the button goes with its count. The button's accessible name is "Show", described by "12 hidden by filters". Under a coarse pointer its 44 px target is padding taken back by a negative margin (and the global target rule's minimum height reset), so it adds nothing to the line's height. §20.5's "why" per item is the rows' own (their reasons), unchanged here.
- **Nothing moves when the count arrives (runner, refines §10.4's toolbar).** It arrives after the rows, so every width was measured in e2e (toolbar height, the first row's y and the Sort control's y, before and after, with "2,196 results"):
  - **Full words** ("12 hidden by filters · Show") from 56rem of toolbar width up (about 1,280 px of window and wider; the 900 and 1,024 px layouts, whose toolbar is narrower beside the rail, take the short form).
  - **Short form** ("12 filtered · Show") below 56rem; its accessible description stays the full words. The glossary records it as a short form of `hidden_by_filters`.
  - **Sort and View keep their labels as accessible names only below 46rem of toolbar** (extending the below-40rem-of-window rule), so the one-row toolbar has room for the note. Tested: both controls keep their names. It replaces the drawer's own below-38rem-of-toolbar rule, which it covers.
  - **No note** below 14.5rem of toolbar (360 px phones, where even the short form wraps the count line) and from 30 to 42rem (about 630–820 px windows, where the toolbar is one row of controls with no room left). "Show hidden" stays in Filters there.
  - Measured: 0 px vertically at 360, 380, 390, 480, 600, 630, 640, 641, 660, 680, 720, 768, 800, 830, 850, 900, 1,024, 1,366 and 2,048 px; the spec keeps 360, 390, 768, 900, 1,024, 1,366 and 2,048, and holds Sort's x too below 2,048 (128rem). A longer count (grouped, "≈ 2.4M results") is wider than the one measured and can still wrap a narrow line.
  - **Follow-up X-hidden-count-wide-shift (runner records r24):** from 128rem of window the controls follow the count (L3), so they move right by the note's width when it arrives.
- **The status pill counts searchable torrents (runner).** `CrawlerEvent` gains `searchable` (the serving index's `num_docs`, as `/stats`'s `searchable_torrents`; null with search off); `torrents` stays for other readers. The pill reads "Idle · 2.2K searchable" and shows no count while it's unknown (before: "— torrents"). `PillState.torrents` is renamed `searchable`.
- **The banner and Home say "searchable" (runner).** "Index still growing: 2,208 searchable." (as short as X-search-toolbar left it for one line at 360–390 px: "searchable" replaces "torrents"), "2,208 searchable torrents so far." and "Search 2,208 searchable torrents".
- **Two figures, each labelled.** Searchable (the index: the pill, the banner, Home, Insights) and results (the toolbar). Searchable counts every indexed torrent: filter-hidden ones, unverified ones and Adult while it's hidden included. "N hidden by filters" accounts for the filter-hidden part of the gap only.
- **Glossary.** `searchable` and `hidden_by_filters` say where each count shows and how they relate (`docs/ui-glossary.md`).
- **zh strings are machine-drafted** (`个可搜索`, `个已被过滤器隐藏`, `显示`), for the translator (W4) to confirm, like the glossary's zh column.
