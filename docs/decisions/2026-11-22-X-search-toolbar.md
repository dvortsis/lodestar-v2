# X-search-toolbar decisions

Slice `X-search-toolbar`, from the UI review of 2026-11-13 (`docs/review/2026-11-13-ui-ux/`: I2, L4, I15, P7, L3). The runner decided the points marked "runner" under `docs/owner-decisions.md` §2.26 and flagged them to the owner under §2.19.

- **One view switcher (runner, refines §10.2 "density control" and §10.4's toolbar line).** List, Compact, Table, Cards in one control replace Density (Comfortable, Compact, Cards) and List/Table, whose combinations didn't all mean something. "List" is §10.2's Comfortable: a moderate user reads "List" against "Table" more easily than "Comfortable" (it names what they see, not a spacing grade). The URL keeps `density=` and `view=`, so old links work: `view=table` wins over any density, then `density=cards`, then `density=compact`, else List. Every combination is tested (`toolbar.test.ts`). Writing a view clears both parameters and sets the one it needs.
- **The account's Appearance density sets the default view (runner, §10.10).** The order is the URL (`view=` or `density=`; `density=comfortable` is the List), then the preference, then List. The preference's three values map one to one onto the switcher: Comfortable is List, Compact is Compact, Cards is Cards. Table has no preference value, so a preference can't default to it. Settings' UI needs no change. Nothing in Search read the preference before.
  - **No URL write.** The first design wrote the preference's `density=` into a bare link; that reset the query bar mid-typing (the write navigates) and left a stale `density=` that outranked a later Appearance change. Now the URL changes only when the user picks a view; the rows, the table and the toolbar each derive the same view from the URL and `<html data-density>`. Choosing List under a Compact or Cards preference writes `density=comfortable`, or the preference would bring the old view back.
  - **Seeding and timing.** The shell sets `<html data-density>` only after the first interaction, so the toolbar chunk applies the cache the last visit left (`lodestar.appearance`) the same way when it loads, if nothing has set it. Both the panel and the toolbar read the attribute together with the URL, so a preference that arrives late takes effect with the next query and never rearranges the list on screen (CLS 0 in the e2e check at 390 and 1440 px). A first visit with a non-default preference therefore shows List until the next query. The panel and the toolbar read the query string (not the URL object), so closing the drawer, which replaces the URL with the same query, doesn't re-read the attribute either.
  - **A picked view stays in the URL and follows the nav links.** Density is URL state that links carry (§10.3, `shell/density.ts`), so a view the user picked travels with them and outranks an Appearance change they make afterwards, until they pick another. That is the existing rule for `density=`, not new; a follow-up for the runner if it surprises people.
  - **Where it lives.** `toolbar/view.ts` (`viewOf`, shared with the toolbar) and `toolbar.ts` (`viewHref`, `seedPref`). The panel derives its density from the same two inputs in `results/ResultsPanel.svelte` (three lines, net-zero in the Results chunk).
- **The view control is a native `<select>` at every width.** It costs less than the segmented control with four options, and gives type-ahead and the platform picker on phones for free.
- **Phones (below 640 px): Select and Save sit in a "More" disclosure** (a native `popover`: Tab moves through it, Escape closes it and returns focus), replacing the ARIA menu pattern first asked for. Bits UI's menu would have put about 35 kB in the toolbar chunk. Save keeps its label (X-alert-noun renames that noun later). Filters shares the toolbar's row (the rail's host is placed over the results track's top-left, below x-large), and the count moves to a line under the row. The count stays visible, so the control row is one line and the count is still read once.
- **"Still growing" stays visible (runner) and is shorter.** It says the results are incomplete. The copy is now "Index still growing: {count} torrents, +{rate}." (en; zh matches), a refinement of the §10.4 wording ("…Older content appears over time."), so it fits one line at 360 to 390 px with its 16 px icon; below 640 px it also takes caption size and tight padding, in CSS (`.rp-growing`, a class on the banner).
- **Raw name only, no Resolution (runner).** `SearchHit` has no `resolution` field and names aren't parsed client-side. The table gets a Raw name column, shown by default and only when it differs from the title (as in List); a column choice saved before this change is kept as it was (Raw name starts hidden for it). **Cards don't get the raw name here (runner, I15's card half deferred).** With it, the Search cards chunk measured 8.11 kB against its 8.01 kB limit, 97 B over, and trimming the card (the raw name as one element, shared classes) recovered only 3 B. The limit stays, so the card half is deferred to a follow-up; List and Table show the raw name (Compact never did). The API's `resolution` field is a follow-up for the runner (X-hit-resolution).
- **P7 "N hidden · Show" is deferred (runner).** Results expose no hidden count, so there is nothing to show; the runner queues the API follow-up. The toolbar has one count. The other figures come from `results/ResultsPanel.svelte:431` (the "No results" title, `searchable_torrents`, with the empty state) and `discover/DiscoverPage.svelte:82` (the compact `≈ 2.2K`, via `formatCompact`); the follow-up can reconcile them there.
- **L3 is done.** From 2,048 px the toolbar's controls follow the count instead of the track's far edge (`toolbar.css`, CSS only); checked at 2,560 px.
- **CSS placement and the Filters button.** The rail placement and banner rules live in `toolbar/toolbar.css`, not `results/results.css`: that chunk has no headroom. Below x-large the Filters host is out of flow in every state, so nothing moves when the toolbar arrives (on a slow runner the panel's first frame has no toolbar, which broke an earlier version that placed the host only once the toolbar was there). `ResultsToolbar` is alive in every state and tells `#results` how much room the host takes (`--tb-inset`: its width and a gap; `--tb-rail-h`: its height and the grid's gap, which an empty host still leaves). The region's first child (the toolbar, or an alert above it such as Details couldn't load) starts after the button; with no toolbar (the empty and cold-start states) the panel starts below it, exactly where it stood when the host was in flow, so the cold-start baselines are unchanged. `#results` stays an ordinary element (Skip to results focuses it with no rows; a keyboard test at 390 px covers it). The pasted-link layout-shift test asserts 0 below 1024 px, also with the toolbar's chunk delayed and the CPU throttled. The popover has no elevation: there is no shadow token. The Filters button stays 40 px next to 32 px controls (`facets/` is not this slice's).
- **One row holds from 390 px.** At 360 px in en the More button wraps to a second row; the row is still shorter than before, and no cheap fix (an icon button with a label) fits the toolbar's size cap. The pre-existing `?browse=1` shift (0.012 at 320 to 360 px) is the runner's follow-up. The popover has no elevation: there is no shadow token. The Filters button stays 40 px next to 32 px controls (`facets/` is not this slice's).
