# GS-1 decisions (siblings: identical payload and the same file)

Spec: `docs/plan/2026-11-05-v07-m7.md` (GS-1 row and §5); architecture §6 "Grouping/dedup" and §10.5; B13's withheld rule (`docs/decisions/2026-10-22-B13.md`, `2026-11-05-B13b.md`). Closes `TODO(M7)` in `crates/api/src/compare.rs`.

- **Identical payload: GS-0's signature, confirmed by the stored sizes.** The reference's signature comes from its stored file tree (`classify::payload::payload_sig_of_sizes`, the function `sig:` and CS-8a share). Candidates are the index's `sig:<16 hex>` matches under the request's visibility (`discover::shown`), at most 200, read best first. Each one is kept only if its stored non-padding sizes are the reference's, sorted (`same_payload`). So a signature collision never shows. The bare 16-digit form looks nothing up (GS-0), so no reference is resolved through the index.
- **The same file: v2 piece roots, from the file index.** The reference's distinct roots are looked up, largest files first, at most 64 (`SAME_FILE_ROOTS`) per torrent. The new `SearchIndex::torrents_with_pieces_roots` returns the newest 1,000 torrents (`SAME_FILE_CANDIDATES`) that have any of those roots, plus whether there were more. Its memory is bounded by the limit, and it checks the request's token before and during collection. Each candidate is kept only if its stored tree has one of those roots. v1 files carry no root, so only v2 and hybrid torrents are found. v1 per-file md5, sha1 and ed2k aren't used (plan Q18).
- **Both groups are withheld exactly as other versions are.** A candidate is dropped when the stored state withholds it from this request (`discover::withheld` with `hidden_ok: false` and the request's Adult flag), whatever the index says. A reference the drawer opened because a filter hid it still answers, as its other versions do. An Adult reference while Adult is hidden is the same 404 as an unknown torrent. Each candidate's lookups happen under the shared reader's lock, one candidate at a time. The request's `CancelToken` is checked before each search and before each candidate's lookups.
- **Typed answers, never empty-as-none.**
  - **New `Unavailable` reasons** (shared edit, `dto/discover.rs`):
    - `no_content_files`: the torrent has only padding or nothing, so it has no signature and no roots. Requirement 2: a torrent without a signature never lists the other signature-less ones.
    - `needs_v2_files`: a v1-only torrent has no piece roots.
  - **Old reasons kept:** `needs_payload_signature` and `needs_piece_roots` now mean an older index serving during a rebuild, one that lacks the field (`Availability::Missing`). `search_disabled` is unchanged.
- **Partial and capped are flags on `SiblingsResponse`, not on `HitGroup`,** so Discover's groups and their schema don't change:
  - `identical_payload_partial`: true while `payload_sig` isn't Ready (GS-0's backfill). It's the same readiness signal `sig:` reports.
  - `same_file_partial`: true while `file.pieces_root` isn't Ready.
  - `same_file_capped`: true when the roots looked up or the candidates read were bounded.

  The UI doesn't show the flags yet. That's a later UI slice; until then the groups read as "available", which is what they are. **Refinement, flagged (§2.19):** the brief allowed "an unavailable reason or a note" for v1-only torrents. This uses a reason.
- **New copy is reason codes only:** two message pairs, en and zh, in `discover/messages`, worded per the glossary.
- **Order.** Clones read best first, by search relevance and its swarm priors. Same-file candidates read newest first (the highest ids). Both list at most `MAX_SIBLINGS` (20), with `truncated` past it, as other versions do.
- **Known effect:** a single-file torrent's payload is one size. So an episode pack's equal-sized episodes, or any two torrents of one file with the same byte count, list each other as identical payloads. That's what the definition says (§6, "the sorted vector of non-padding file sizes"), and CS-8a's specificity rule doesn't apply to siblings.
