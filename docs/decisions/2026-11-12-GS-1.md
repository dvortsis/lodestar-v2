# GS-1 decisions (siblings: identical payload and the same file) (#772)

Spec: `docs/plan/2026-11-05-v07-m7.md` (GS-1 row and §5); architecture §6 "Grouping/dedup" and §10.5; B13's withheld rule (`docs/decisions/2026-10-22-B13.md`, `2026-11-05-B13b.md`). Closes `TODO(M7)` in `crates/api/src/compare.rs`.

- **Only a specific payload is matched** (the runner's refinement of plan §6's definition, under §2.26 and §2.33; flagged to the owner, §2.19). By §6, a payload is just the sorted file sizes, so a small or round one is shared by unrelated torrents (two single 1 MiB files list each other). A panel of false "identical" matches is worse than none. So the reference must pass CS-8a's specificity rule, read through the one copy of it, `filter::payload_sig(...).specific`: 50 MiB or more in all, or at least 2 files of distinctive size. A reference that doesn't gets the new reason `payload_not_specific`. Candidates are still confirmed by their stored sizes. Exact round sizes of 50 MiB or more can still match: a single 1 GiB file is specific under the rule, so equal-sized 1 GiB episodes still list each other.
- **Identical payload: GS-0's signature, confirmed by the stored sizes.** The reference's signature and specificity come from its stored file tree, through `filter::payload_sig` (on `classify::payload`, the hash `sig:` and CS-8a share). Candidates are the index's `sig:<16 hex>` matches under the request's visibility (`discover::shown`), at most 200, read best first. Each one is kept only if its stored non-padding sizes are the reference's, sorted (`same_payload`). So a signature collision never shows. The bare 16-digit form looks nothing up (GS-0), so no reference is resolved through the index.
- **A partial file list is never a payload** (the runner's ruling on review finding B1). An import that dropped files is stored with `flags::FILES_PARTIAL`, and the index signs the files that were kept, so a season pack missing an episode would otherwise look identical to a torrent that really holds those episodes. The repo already treats a partial list as not the stored truth (`identify.rs`, `torrents.rs`). So:
  - such a reference gets the new reason `partial_file_list`;
  - such candidates are dropped from identical payload, by a row check before their tree is read;
  - same file keeps them, because a root they do list is still exact.
- **The same file: v2 (size, root) pairs, from the file index.**
  - **What's looked up.** Only files of at least 1 MiB (`SAME_FILE_MIN_BYTES`), largest first, distinct, at most 64 (`SAME_FILE_ROOTS`) per torrent. This is the runner's ruling on I2, a refinement of plan §6 flagged to the owner.
  - **Why the floor.** A v2 `pieces_root` is a Merkle root over 16 KiB blocks, so it identifies content exactly at any size. The floor is for distinctiveness, as CS-8a's is: a small file (the same `.nfo`, a "downloaded from" note) is in countless unrelated torrents and would crowd out real matches.
  - **No qualifying file:** a torrent whose files with roots are all under the floor gets `payload_not_specific` for this group too.
  - **Confirmed on the pair.** Each candidate is kept only if its stored tree has one of those (size, root) pairs, so a root claimed with another size isn't the same file.
  - **Accepted risk:** a crafted torrent can still claim a real (size, root) pair. Visibility rules still apply to it, and nothing is fetched.
  - **The lookup.** The new `SearchIndex::torrents_with_pieces_roots` matches the roots in the file index, then keeps only torrents the request's visibility clauses pass, through `discover::shown(Node::All, adult)`, the one source of truth for B13's base query. Only then does it take the newest 1,000 (`SAME_FILE_CANDIDATES`), using percolation's `TopIds` collector, and say whether there were more. Withheld torrents therefore never fill the window (I1). The pairs are matched in the file index on both root and size (a fast-field range), so wrong-size claims never take a place in the window either; its memory is bounded by the limit, and it checks the request's token before and during collection, never returning a stopped collection's partial ids.
  - **Scope.** v1 files carry no root, so only v2 and hybrid torrents are found. v1 per-file md5, sha1 and ed2k aren't used (plan Q18). A v2 or hybrid torrent whose files have no usable root never reads "v1 only".
- **Both groups are withheld exactly as other versions are.** Both index lookups apply the request's visibility (`shown`), and each candidate is dropped when the stored state withholds it from this request (`discover::withheld` with `hidden_ok: false` and the request's Adult flag), whatever the index says. A reference the drawer opened because a filter hid it still answers, as its other versions do. An Adult reference while Adult is hidden is the same 404 as an unknown torrent. Each candidate's lookups happen under the shared reader's lock, one candidate at a time. The request's `CancelToken` is checked before each search and before each candidate's lookups.
- **Typed answers, never empty-as-none.**
  - **New `Unavailable` reasons** (shared edit, `dto/discover.rs`), with `payload_not_specific` above:
    - `no_content_files`: the torrent has only padding or nothing, so it has no signature and no roots. Requirement 2: a torrent without a signature never lists the other signature-less ones.
    - `needs_v2_files`: a v1-only torrent (no root, and not v2 or hybrid) has no piece roots.
    - `partial_file_list`: above.
  - **Old reasons kept, copy corrected:** `needs_payload_signature` and `needs_piece_roots` now mean an older index serving during a rebuild, one that lacks the field (`Availability::Missing`). `search_disabled` is unchanged.
- **Partial and capped are flags on `SiblingsResponse`, not on `HitGroup`,** so Discover's groups and their schema don't change:
  - `identical_payload_partial`: true while `payload_sig` isn't Ready (GS-0's backfill). It's the same readiness signal `sig:` reports.
  - `same_file_partial`: true while `file.pieces_root` isn't Ready, or while the file index lags the torrent index (the new `SearchIndex::files_caught_up`; recreated or rebuilt, its population can read Ready before it has caught up: I3).
  - `same_file_capped`: true only when the visible list itself is full (`MAX_SIBLINGS`) and the roots looked up or the candidates read were bounded. That's the runner's rule: a short list never hints at torrents it couldn't show, so withheld torrents leave no trace, not even in a flag. The API doc of `same_file_capped` says exactly this: set only when `same_file` is full and the lookup was bounded, never on a shorter list (from the fresh review's I2).

  The UI doesn't show the flags yet. That's a later UI slice; until then the groups read as "available", which is what they are. **Refinement, flagged (§2.19):** the brief allowed "an unavailable reason or a note" for v1-only torrents. This uses a reason.
- **New copy is reason codes only:** four message pairs, en and zh, in `discover/messages`, worded per the glossary.
- **Order.** Clones read best first, by search relevance and its swarm priors. Same-file candidates read newest first (the highest ids). Both list at most `MAX_SIBLINGS` (20), with `truncated` past it, as other versions do.
