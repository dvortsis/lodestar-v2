# WK-3 decisions (have-filter replication)

WK-3 follows plan `docs/plan/2026-11-06-v06-workers.md` §4.3 and Q6, and architecture §19.3, §7 and §19.8. Q6 was delegated to the runner (owner §2.46, `ext:owner-wkq3`). Its answer is the plan's recommendation: a **separate worker filter**. One point below is a refinement for the runner to flag (§2.19): the in-place rule. None of these points loosens an owner decision or changes an owner-set number.

## The keyed hash (`crates/pipeline/src/have.rs`)
- **SipHash-1-3 under a random 128-bit key per filter** replaces `RandomState`. One SipHash-1-3-128 pass over the 20 hash bytes gives `h1` (the low half) and `h2` (the high half, made odd). Hash `i` sets bit `(h1 + i·h2) mod bits`, where bit `b` is bit `b % 64` of little-endian word `b / 64`. The coordinator and every worker run the same code, so a copy that has the key answers the same everywhere. Peers still can't choose colliding hashes, because they don't know the key.
- **The key comes from the system random source** (`HaveKey::random`, ring's `SystemRandom`, which the cluster crate already uses). A failing source panics, as `RandomState::new` did before.
- **The false-positive rate is unchanged.** The coordinator's own filter keeps 10 bits and 7 hashes per key and `capacity_for` (2× stored). A property test checks it at capacity: below 1.25 % at 10 bits and 7 hashes (about 0.8 % in theory), below 3 % at Q6's 8 bits and 6 hashes (about 2.2 %), and never a false negative.
- **The key is never in `Debug` or error text.** `HaveKey` prints as `HaveKey(..)` and has no `Display`. `Bloom` prints neither its key nor its bits. `HaveError` names only the field that failed. Tests check all three. Nothing in this slice logs.
- **Runner's call (§2.33): a manual `Debug` on `ToWorker`,** so the have-filter key can't reach logs. `HaveSnapshot`, `HaveDelta`, `Update`, the `Snapshot` bytes and the `Assign` payload print only their length; every other variant prints as before. `proto.rs` is in WK-3's owns for this impl alone. `ToCoordinator` carries none of these payloads, so it keeps its derived `Debug`. A test formats each such message with a known key and checks that neither the key nor any payload byte appears.
- **Insert notifications go through `have.rs`.** `Have::observe` takes one `HaveObserver`, which is told of every insert. It's unset until WK-10 sets it, and unset costs one atomic load per insert. `writer.rs` is unchanged.
- **No rebuild notification is needed.** The coordinator's own rebuild re-reads the same stored set, and the worker filter fills and is rebuilt on its own count (below). So `Have::replace` tells nobody.
- **`crates/pipeline/src/lib.rs` gets one re-export line:** `pub use have::{Bloom, HaveObserver, new_key}`, beside `Have` (runner, 2026-11-07T03:16Z). That is all the cluster and worker code use. The module stays private.

## Wire format (`crates/cluster/src/have.rs`)
- **The header goes in `ToWorker::HaveSnapshot`.** It has a fixed little-endian layout of 70 bytes, not postcard:
  - version 1;
  - generation;
  - transfer serial (never 0);
  - the first delta sequence number after the snapshot;
  - key, 16 bytes;
  - size in bits;
  - hashes;
  - capacity;
  - count;
  - chunks.

  Q6's "bits per hash" is `bits / capacity`. The decoder works in this order, allocating nothing:
  1. It refuses an unknown version.
  2. It refuses a wrong length.
  3. It checks every field. The size is a multiple of 64 and from 64 bits to 256 MiB. Hashes are 1–16. Capacity is from 1 to the number of bits. Chunks must be exactly `ceil(bytes / 512 KiB)`.
- **The bits go in WK-0's `Snapshot` chunks.** They're of kind `HaveFilter`, with the transfer serial as `version`, and each carries at most `MAX_CHUNK` (512 KiB). Each chunk but the last is exactly 512 KiB, and the last is the rest. An `Assembly` takes them strictly in order. A chunk that is out of order, of the wrong length or with the wrong total is refused, and the caller drops the assembly. So a missing or repeated chunk never completes a filter, and a half-built one is never used.
- **Deltas go in `ToWorker::HaveDelta`.** The layout is version, generation, sequence number, a count from 1 to 26,213 (so the delta fits `MAX_OPAQUE`), then 20 bytes per key. The count is checked against the exact length before the keys are allocated.
- **A resync request is `SnapshotAck { HaveFilter, version: 0, seq: 0 }`.** No transfer has serial 0. That way, a worker that knows it lost something can ask for a fresh snapshot with an existing message.
- **Tests:** `crates/cluster/tests/have.rs` has property tests for round trips, arbitrary bytes and the order of chunks. The fuzz target is `fuzz/fuzz_targets/cluster_have.rs`.

## Q6: the worker filter (`crates/lodestar/src/cluster/have.rs`)
- **Size and rate:** the stored count plus 25 %, at least 2^20 keys. Up to 30M stored it uses 10 bits and 7 hashes per key; above that, 8 bits and 6 hashes. It's rebuilt from the store when its count passes its capacity.
- **It's built only once a remote worker is connected.** `sync` says when a build is due, and WK-10 runs `rebuild` over the store on a blocking thread. With no worker, there's no filter, no delta buffer and no observer work beyond one atomic load. That's single-machine parity (§19.8).
- **Keys inserted during a rebuild's scan aren't lost.** The new filter is published before the scan takes its read, and every insert goes into it as well as the old one. A key committed after the scan's read is still in it.
- **Snapshots are read from the live filter as they're sent,** chunk by chunk, so no per-worker copy is held. This is still correct:
  - bits are only ever set;
  - every insert after a worker's header is in a delta that follows the header;
  - the worker ORs chunks and deltas into the filter it's assembling.

  So the worker ends with every key stored before its snapshot.
- **Pacing:** at most 4 chunks (2 MiB of the 8 MiB session queue) in flight per worker, ahead of its acknowledgements. Only the next acknowledgement of the current transfer counts; one from an earlier transfer is ignored.
- **When a worker's snapshot starts over:**
  - a delta can't be queued to it (otherwise it would have a gap);
  - it sends a resync request. At most one per 5 s (`RESYNC_MIN`) starts a new snapshot; a request sooner than that waits for the next sync after it. So a faulty worker can't make the coordinator resend its filter in a loop;
  - it makes no progress for 60 s;
  - a rebuild bumps the generation (this restarts every worker's snapshot).
- **A full queue retries a header or chunk** on the next sync.
- **Deltas are numbered per generation** and go to every worker whose header went out. If more than 2^20 keys wait for a delta (no sync for a long time), they're dropped and every worker gets a fresh snapshot instead. That bounds the buffer at 20 MiB.
- **Generations and transfer serials are numbered from the coordinator's clock** (Unix ms), as WK-5's revisions are, so a restarted coordinator's are newer.
- **The writer never waits on the cluster server.** An insert takes only a small lock of its own (the filters and the keys waiting for a delta). Headers, chunks and deltas are sent under the transfer lock, which an insert never takes. Lock order: transfers, then inserts.
- **The worker filter never exceeds what a worker accepts:** `worker_params` caps the capacity at the 256 MiB header limit, and a header that wouldn't pass the worker's check is never sent.

## The worker (`crates/lodestar/src/worker/have.rs`)
- **"Might be stored", never a wrong "no."** With no complete filter, every answer is "maybe": the claim goes to the coordinator, which answers from the store.
- **A delta for the generation being assembled** goes into the new filter and into the one in use.
- **A delta out of sequence (a gap)** drops an assembly of that generation and asks for a resync, once per incident. The filter in use keeps answering.
- **The old filter stays until the new one is complete,** except above the in-place limit.
- **Refinement for the runner to flag (§2.19): "above 64 MB" is read as the old and new filters together above 64 MiB.** A worker over that limit drops the old filter at the header and answers "maybe" until the new one is complete. Q6's "above 64 MB the worker swaps in place rather than holding two copies" exists to keep the 256 MB budget flat. Reading it as the new filter alone above 64 MB would let a 62.5 MB filter at 50M hold two copies (125 MB) during a rebuild. The cost is a burst of claims the coordinator answers from the store while a large filter transfers.
- **A snapshot of the same filter refills the one in use.** A resync after a lost session, a stall or a full queue sends the same generation, key and shape. Its chunks are ORed straight into the filter in use: bits only get set, so this can't give a wrong "no". It needs no second copy and leaves no "maybe" window, even above the in-place limit.
- **The filter for a new header is allocated with no lock held,** so lookups don't wait for it. Delta sequence numbers wrap rather than overflow.
- **A new session asks for a fresh snapshot** (`reconnected`, on every `Welcome`): anything queued to the old session may be lost. The filter in use stays.
- **The property gate** is in `cluster/have.rs`'s tests. A coordinator, its `Have` and two workers run behind lossy queues that keep their order, with random stores, syncs, partial deliveries, full queues, lost sessions and rebuilds. The window is 1–4 chunks and in-place swaps are on or off. Unit tests add inserts during a rebuild's scan (also from another thread), a failed rebuild, the delta buffer's overflow and the resync rate limit. No worker ever says "not stored" for a key stored before the snapshot it holds, and once things settle every worker has every key. A deliberately broken worker that skips deltas while assembling fails the test.

## Memory under Q6
| Stored | Worker filter | Worker while a rebuild transfers | Coordinator (its own filter / worker filter) |
|---|---|---|---|
| 10M | 15.6 MB (12.5M keys × 10 bits) | it fills at 12.5M stored; the new 19.5 MB filter plus the old = 35.2 MB, under 64 MiB, so it holds both | 25 MB / 15.6 MB, plus the new 19.5 MB one while rebuilding |
| 50M | 62.5 MB (62.5M keys × 8 bits) | it fills at 62.5M stored; the new filter is 78.1 MB, and together they'd be 141 MB, so the swap is in place: 78.1 MB | 125 MB / 62.5 MB, plus the new 78.1 MB one while rebuilding |

For comparison, today's filter replicated as is would be 25 MB at 10M and 125 MB at 50M, with up to 3× during a growth swap. The filter's size steps up once, at the 30M switch to 8 bits. A 10-bit filter built at 30M (37.5M keys, 46.9 MB) fills at 37.5M stored. Its 8-bit replacement is 46.9 MB, and the two together (93.8 MB) are over the limit, so that swap is in place too.

## For WK-10 (worker runtime and serve wiring)
- **On the coordinator, at start once workers are allowed:** build one `WorkerFilter::new()` and register it with `Have::observe`. A single-machine install never needs to register it.
- **On every cluster tick while a server runs:** `filter.sync(&server.snapshot(), &server, Instant::now())`. When it returns `rebuild: true` and none is running, run `filter.rebuild(stored, |insert| store.for_each_swarm_hash(insert))` on a blocking thread with its own read connection. `rebuild` refuses a second concurrent run (`Ok(false)`).
- **The inbound sink's `snapshot_ack`** passes have-filter acknowledgements to `filter.ack(worker, ack, &server, now)`. It must not block, and `ack` takes only the filter's mutex and queues messages.
- **On the worker:** pass `HaveSnapshot` to `WorkerHave::header`, `Snapshot` chunks of kind `HaveFilter` to `chunk`, and `HaveDelta` to `delta`. Send back every acknowledgement they return. Send `reconnected()`'s request on every `Welcome`. Check discovered hashes with `might_be_stored`, and claim every "maybe".
- **Lock order:** the coordinator calls `ClusterServer::send` while it holds the worker filter's transfer lock. The server must never call into the filter with its fleet lock held. That's true today: the sink runs with no lock held.
- **Never `Debug`-log a protocol message,** as a second line of defence. `ToWorker`'s `Debug` already prints only the lengths of its opaque payloads (below).
- **A failing store:** `sync` asks for a rebuild on every tick until one succeeds. Back off between attempts.

## For WK-G
- **Measure what a snapshot costs:**
  - time and bytes for a 62.5 MB snapshot over the soak's link;
  - the burst of claims during an in-place swap at 50M;
  - the coordinator's added RSS (the worker filter, and twice that while rebuilding).
- **The 256 MiB header cap** (`MAX_FILTER_BITS`) covers the 8-bit worker filter to about 215M stored. Raise it in a v2 header if the corpus ever gets near that.
- **The header and delta layouts may change until protocol 1.0 freezes** (Q11).
- **The worker filter stays once built,** even after the last worker leaves (a reconnect would otherwise rescan the store). Consider dropping it after a quiet period.
