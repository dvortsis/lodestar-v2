# B11a decisions (Insights overview API)

`GET /insights/overview` and `GET /insights/events` (architecture §7 "Insights rollups", §10.9–10.9.4, §10.9.6, §10.17; `docs/metrics.md` §6, §7.5), the write hook that records searchable time, and the Searchable funnel stage. No owner decision is reversed or loosened, no security or content-safety decision is weakened and no owner-set number changes. The refinements below are the runner's to flag (`docs/owner-decisions.md` §2.19).

## Write path
- **The commit hook takes a second sink.** `CommitHook::add` appends sinks beside the one `set` gives (the SSE hub's); `set` and `clear` leave them alone, so B4's behaviour for the hub is unchanged. The Insights sink only `try_send`s the `Committed` into a channel of 64 and returns, so the indexer never waits.
- **A recorder task in the binary** (`crates/lodestar/src/insights.rs`), on its own `Store` connection, applies each commit through `Store::record_searchable(last_id, at, codes)`, in `BEGIN IMMEDIATE` transactions of at most 20,000 ids each. A large range (the first start after the V10 upgrade, whose hour-0 seed is old, or a swap) therefore never holds the write lock for long; all of it is credited to the hour it was recorded in, the earliest time it's known to be searchable. With search off the recorder still runs, for coverage.
  - **The range's lower end is read from `index_watermark_hour`, not passed in.** The brief sketched `record_searchable(prev_id, last_id, at)`; taking the lower end from the table in the same transaction means a repeated call, a commit the channel dropped, or a call after one that failed neither counts an id twice nor skips one. A dropped commit is covered by the next one, or by the 30 s tick, which reads the index's watermark (`IndexStats.watermark`). The same catch-up runs at start (commits made before the hook was attached) and at shutdown, after the indexer's last commit.
  - **The watermark upsert keeps `record_index_watermark`'s rules** (both columns only grow; an id at or below the highest changes nothing; an earlier hour counts in the latest). `reporting.rs` was outside this slice, so the upsert is a private helper in `insights.rs` and a property test holds the two to the same results on random sequences. B11b, which owns `reporting.rs` next, can make `record_index_watermark` call the helper.
  - **What one range writes:** for ids in `(previous highest, last_id]` (a primary-key range of `torrents`, one commit's worth): `metric::NEWLY_SEARCHABLE` at the hour written, by content type (`UNCLASSIFIED` = 255 for none yet), imports under key 1; and, unless imported, `Stage::Searchable` in the torrent's cohort (`discovered_at` hour, `first_source`) and its delay in that cohort's `metric::TIME_TO_SEARCHABLE` histogram. Ids at or below hour 0's (indexed before tracking) are never counted. A torrent with no `first_source` (stored before M1) has no cohort and stays out of the funnel.
  - **New searchable counts at the watermark row's hour,** so §10.17's "by the first `index_watermark_hour` row covering each id" holds exactly, a clock set back included.
- **New metric codes 10–13** (`crates/pipeline/src/rollups.rs`), after #48's 5–9, which is still open: `NEWLY_SEARCHABLE` (10, event time), `TIME_TO_SEARCHABLE` (11, **by discovery cohort**: `hour` is the cohort, `key` a log bucket), `COVERAGE` (12, seconds measured per hour; dim 0 indexing, dim 1 crawling) and `SEARCHABLE` (13, a gauge: the index's document count, written every 30 s with replace semantics, `Store::set_gauges`, so each hour keeps its last snapshot).
- **Time-to-searchable buckets** (`lodestar_store::log_bucket`): bucket 0 holds 0 s; bucket `b ≥ 1` holds `[1.1^(b−1), 1.1^b)` seconds. Read back as the bucket's geometric midpoint, a value is within 5% (§10.9.3 asks ≤ 10%). A property test checks it.
- **Coverage tells a gap from a zero** (§10.9.3 "missing data is a gap, not a zero (e.g. while the crawler is paused)"; the brief's "no rollup row = null, never 0" plus "a measured zero gives 0"). Without it, a quiet hour and a paused one both have no rows. Every 30 s the recorder adds the seconds since the last tick, split at hour boundaries, and only while the crawler isn't paused: crawling always, indexing too while search is on. A paused stretch therefore reads as a gap on both trend lines, even though indexing goes on; torrents it does make searchable still show, because rows win over coverage. A trend bucket with rows shows their sum; with coverage and no rows, 0; with neither, `null`. History from before this build has no coverage rows, so its quiet hours read as gaps.
- **The imported total** is the searchable torrents that were imported: one scan of `torrents` at start (`count_flagged_searchable`, over ids up to the recorded watermark, after the start-up catch-up), then what each later range adds. It's `null` until that count is in. This is the only full scan, it runs once per start on the recorder's connection, and never on the read path.
- **A crash** loses at most the last commit's rows and 30 s of coverage. B11b's `rollup --repair` restores the searchable counts from `torrents` and `index_watermark_hour`.

## Read path
- **Rollups only.** Each overview read is an indexed range scan, in one read transaction (`Store::read_snapshot`) under the reader lock on the blocking pool. Rollup sums seek the primary key once per hour (`hour = ? AND metric = ?`, a recursive hour list with `CROSS JOIN`), so a metric's cost follows the hours and its own rows, not every metric's. A store test checks every plan for a `SEARCH` and no `SCAN`.
- **Sealed days are summed once and kept in memory.** A year of hourly rows can't be read in 50 ms: every query seeks each of 8,760 hours, and §7's daily compaction is B11b's. UTC days that ended 8 or more days ago (the 72 h retry horizon with room to spare) no longer change, so their sums are read once and kept in `OverviewCache` (about 1.5 KB a day). The recorder warms them first thing at start (about 0.3 s on a year).
  - **What can still write into a sealed day, and how it's handled:** the recorder making old cohorts searchable after an index backlog drops the days from that cohort on (`forget_days_from`) and warms them again at once; keys restored from the fetch queue after a long downtime keep their old cohort, so the oldest queued cohort's day and later stay unsealed for the retry horizon after start (`InsightsSource::seal_floor`).
  - **A generation counter** guards the race between a request reading days from an older snapshot and a forget: sums read under a generation older than the cache's are used for that response only, never kept. A unit test holds the summed path to the hour-by-hour one. With them, every range answers in at most 12 ms in release on a year of rollups at about 110 rows an hour. B11b's compaction can replace them.
- **Responses are cached per (normalized query, last flush).** The key is the normalized window, the compare window, the current hour, "Show adult content", the writer's last commit (whole seconds) and a counter the recorder bumps at each write (every 30 s at least). The snapshot fields (searchable, imported, health, stale, index lag) are read for every request. At most 8 responses are kept. A cached response can trail by up to 30 s: a second commit in the same second, or a pause, resume or intensity event (written by the crawler control on its own connection) shows at the next tick.
- **Range normalization:** whole UTC hours ending with the current one up to 7 days; past that, whole UTC days (so `30d` is 30 UTC days, the current one last). `all` starts at the earliest rollup or cohort hour, but at most 20 years back, so one stray hour from a clock that was unset can't make thousands of buckets (the warm is capped the same way). `custom` rounds `from` down and `to` up to the hour (day), stops at the current hour, and is refused past 20 years. Day buckets are UTC days (`docs/metrics.md` §2). `range.bucket` is new in §7.5.

## Definitions
- **Finality** (a constant, `RETRY_HORIZON_HOURS` = 72): a cohort hour is final once it has ended with nothing in progress (harvested = stored + lost) and everything stored searchable, or once more than 72 h have passed since it ended. A UTC day in the funnel is final when all its hours are. Yield and time to searchable use final cohort hours only, so they're `null` with none.
- **`in_progress`** is harvested − stored − lost, at least 0 (a refetched partial torrent can be stored without a harvest in its cohort).
- **Stale** (`STALE_AFTER_S` = 120): more than 120 s since the writer's last commit (`WriterStats.last_commit`), or since the pipeline started when it hasn't committed. The reason is `paused` while paused (nothing to flush), else `writer_stalled`.
- **Health:** paused first; then degraded with `writer_stalled` when stale; then degraded with `index_lag` when `/stats`' `index_lag_s` is over 30 s; else running.
- **Compare:** `previous` is the window of the same length just before (`all` has none, so it's absent). It carries what Compare changes (§10.9.4: Status, trend, Serve), not the snapshot fields, so it isn't the full overview's shape. **`kpi.searchable_delta` is §6.2's "Δ vs the previous period's end", removals included:** now's searchable count less `previous.kpi.searchable`, the last `metric::SEARCHABLE` snapshot in the day before the range starts. It's null when there's no snapshot then (search off, the server down that whole day, or history from before this build), never an estimate from new searchable, which would ignore filter-rule and delete removals.
- **Stage strip:** `discover` is the cohorts' harvested counts (a cohort hour is the hour of first harvest, so it's event time too); `understand` is `metric::STORED`. `fetch` is `null` until the pipeline counts fetches by event time (cohort fetched counts are a different time base); `serve` is `null` until #48's search counters are read.
- **Serve:** every field is `null` until its counter exists (searches and latency with #48, alerts with B9, sends with the integrations' counters).
- **`ingest_per_hour`** is `metric::STORED` in the last full UTC hour, `null` when that hour wasn't measured and stored nothing.
- **`funnel_total`** is new: the funnel over the whole range, with conversions and each loss reason's share, so the client never sums cohorts. `funnel[].conversion` is new too.

## Segments
- **Shipped:** `by_content_type` and `by_group` from `NEWLY_SEARCHABLE` (event time), and `by_source` (harvested, searchable and yield by the source that found each hash first, over final cohort hours), which the cohort table supports today.
- **Groups** map content types to the composition groups of §10.18: video (movie, tv, video), audio (music, audiobook), documents (ebook, comic), software (software, game), images, other; plus adult and unclassified.
- **Adult is left out entirely while "Show adult content" is off** (§20.9, the B4 entry): no `adult` row in either list, read per request; the cache key includes the setting.
- **Deferred to B11b:** `by_strategy` and `by_ip_family` (the cohort table has no strategy or address-family dimension), and `resolved_by` (needs a resolution counter).

## Exceptions
- **Shipped:** `index_lag` (`/stats`' lag over 30 s; an error past 600 s) and `cohort_stalled` (hashes in progress in a cohort that isn't final, the crawler covered for at least 3,000 s in each of the last 2 full hours, and nothing stored in them). Both are computed whatever the range.
- **Deferred to B11b:** `yield_below_baseline`, `nat_saturation`, `ephemeral_ports`, `port_unreachable`, `scrape_bans`, `parser_confidence`, `disk_projection` and `network_path`.

## Events
- `GET /insights/events` names `restart`, `stopped`, `paused`, `resumed` and `intensity` from `pipeline::event` (unknown codes are skipped) and returns the paused spans overlapping the range: the state before the range comes from the last pause or resume before it (`Store::last_event_before`), and a span still open has `to: null`. At most 1,000 annotations, with `truncated`.
- The code-to-name tables for stages, losses, events and the metric codes the API reads live in `crates/api/src/insights.rs`; a test in `crates/lodestar` checks them against `lodestar_sources::{Stage, Loss}`, `crates/lodestar/src/metrics.rs`' loss labels and `lodestar_pipeline::{event, metric}`.

## Visibility notes
- **Adult:** the rule (§20.9, B4's entry) covers segments, so `kpi.new_searchable`, the trend and the funnel count Adult torrents while it's hidden. `kpi.new_searchable` less the segment sums therefore reveals how many Adult torrents became searchable. That's a count, never a name or a hash, and it's allowed as written.
- **Hidden by a filter rule** (`flags::HIDDEN`) still counts as searchable: those torrents are in the index and served when the user asks for hidden results.
- **Overview annotations** are capped at the oldest 1,000, like `/insights/events`.

## Budgets (§1.6.4)
- **Measured in release** on a year of hourly rollups (about 110 rollup rows and 28 cohort rows an hour, 2,000 events), each call a fresh build (never a cached response): `24h` 1.4–2.3 ms, `7d` 6.3 ms, `7d&compare=1` 11–12 ms, `30d` (with or without compare) 6.4 ms, `all` (with or without compare) 10–11 ms. The test asserts ≤ 50 ms only in release builds (CI's test profile reports them).
- **Search +≤ 5% and ingest −≤ 2% aren't benchmarked here.** The added write load is one short transaction per index commit (every 2 s or so, a primary-key range) and one coverage write every 30 s, on the recorder's own connection; reads take the reader lock for ≤ 12 ms. The `bench/` gate for the dashboard-open case is a follow-up (B11b or a perf slice).
- **The start-up import count** is one scan of `torrents` (a read transaction of seconds at 10M torrents, delaying WAL checkpoints that long), once per start.
- **The cold path:** until the start-up warm has run (it's the recorder's first step, about 0.3 s on a year), and between a forget and its re-warm, a `30d` or `all` request reads the missing sealed days hour by hour itself (about 0.25 s a year under the reader lock) and keeps them. Requests outside those windows meet the budget.
