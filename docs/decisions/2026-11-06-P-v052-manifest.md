# P-v052-manifest decisions

Planning slice, 2026-11-06. It records the v0.5.2 feature manifest (`docs/plan/2026-11-06-v052-feature-manifest.md`), the freeze build-plan §0.4 asks for before `release/v0.5.2` is cut. It is a docs-only slice: no code, and no edits to `runner/*.yaml`. Nothing here reverses or loosens an owner decision, weakens a security or content-safety decision, or changes an owner-set number.

- **D1. The baseline is the first-parent history `c3f6341a..63a2c6df`: 297 merges.**
  - `c3f6341a` is where `release/v0.5.1` split from `main` (build-plan §0.4).
  - PRs ported to the release branch (R-gauges, #357, #402, #406, #432, #433, #434, #442, #448) are listed as enabled and marked "already in v0.5.1", so the manifest stays complete and the reader can see v0.5.1's gate already covers them.
  - Why first-parent: every slice reaches `main` as one merge, so each merge maps to one PR.
- **D2. Merges after `63a2c6df` are classified by P-v052-cut, using the same classes, in its delta report.**
  - A later merge that adds a default-on behaviour, a migration or a re-soak trigger gets an addendum to the manifest before the cut. The addendum is a new decisions file plus an edit to the plan file.
  - Why: `main` takes dozens of merges a day. A freeze at the tag with no rule for the gap would let a behaviour in unlisted.
- **D3. The classes are enabled, inactive, excluded and no user-visible behaviour.**
  - **Excluded:** compiled in but unreachable. The plugin isn't registered in `crates/lodestar/src/services.rs`, the runtime isn't wired, or a `cfg` leaves it out.
  - **Inactive:** reachable, but off by a default the user or operator can change.
  - A PR that is partly on (RP-UC, RP-DEF, SRC-13c, SRC-17) is listed with the enabled behaviours, and its note says what stays off.
  - Why: the brief asks for "inactive or excluded, with how it's kept off". A feature the user can't turn on needs a different proof from one they can, so the two classes are kept apart.
  - The Nyaa, Sukebei, Internet Archive and Academic Torrents plugins (SRC-10a, 10c, 10d, 10e) have manifests that say "off by default", which could read as inactive. The manifest counts them as excluded, because `services.rs` doesn't register them, so no user can turn them on.
- **D4. Four features have no test proving they stay off (manifest §3.3, G1–G4). The runner should get them closed before the freeze.**
  - G1: the registered plugin set.
  - G2: the enrichment wiring.
  - G3: the `verify_unverified` pipeline default.
  - G4: `fixture` left out of the release tarballs and the Windows binary. The Docker image is already checked (`.github/workflows/release.yml:80-85`).

  Each needs a test or a CI check, not a behaviour change. This slice writes no code, so it records them for the runner to schedule (open question Q2).
- **D5. A V12 store upgraded straight to V14 writes one snapshot, `<db>.pre-v13.db`.**
  - It is named after the first pending migration (`crates/store/src/schema.rs:1059-1063`).
  - This confirms build-plan §0.4's file name for the upgrade smoke. The rollback check uses `lodestar rollback v13`.
- **D6. Soak legs under the delta rule (manifest §5.2 step 4, §6, Q5). Some points are the runner's call (runner, 2026-11-06, review of #520):**
  - the binding 24 h Docker soak on an upgraded v0.5.1 folder, with every pack turned on after the upgrade and the pack state recorded (runner's call);
  - the ≥ 6 h Windows run on a fresh folder;
  - a Windows run of the upgrade smoke and the rollback check on a real v0.5.1 folder (runner's call). The MSI check runs one binary twice, so it doesn't cover the upgrade;
  - each clock starts after setup completes (LEGAL-2), and on an upgraded folder after Legal Notice v3 is accepted. Until then the API answers `409 notice_required`, which the collector doesn't handle. Recommendation: the collector fails loudly on a 409.

  Why: the diff has crawler-lifecycle changes that run in the default build (the CR-0d off path's lock file, LEGAL-2's setup hold, #223's lookup generations). Upgrade-only load (the V14 migration, the v5 → v7 rebuild, re-classification) and fresh-only load (the setup hold, packs on from the first start) can't both run in one folder. The SP-3 flood map isn't a reason: it stays empty while every source is off.
- **D7. Release-note corrections are listed in the manifest (§7), not made here.**
  - `docs/releases/v0.5.2.md` isn't in this slice's paths. P-v052-cut completes it.
  - Pack overrides have a screen (RP-6, #487).
  - The webhooks keep "not connected yet" and gain "advanced: API only". The torrent-cache wording stays as it is (runner's call).
  - Two things the draft leaves out: tracker scraping is on by default (`scrape.enabled = true`, as in v0.5.1), and the setup hold.
- **D8. No owner question blocks the manifest (Q6).**
  - Packs on for new installs, the unauthorised-copy pack and the v0.5.2 placement are owner decisions already (§2.39, §2.40).
  - Crawler switches stay off under build-plan §0.4, because none has passed C8.
- **D9. No source that needs consent can be turned on in v0.5.2 (runner's call, 2026-11-06; manifest §3.4, Q4).**
  - The torrent cache's consent and its host list can be set only through the API, so nobody sees the consent wording, and the owner hasn't approved it. Accepting it that way isn't real consent.
  - The fix slice `X-consent-gate-052` (Opus, `/security-review`) lands before P-v052-cut. Until SRC-15b ships owner-approved consent text, `PATCH /sources/{id}` refuses to enable a source whose `consent::need` isn't None, and a test against the real binary proves it. The runner adds it to `runner/slices.yaml`.
  - The Sonarr/Radarr webhooks need no consent, so they stay opt-in: advanced, API only.
  - This tightens the consent rule, so it loosens no owner decision.
- **D10. The upgrade smoke allows only one count change.** That change is the torrents `CLASSIFY_VERSION` 3 → 4 re-classifies as adult. `crates/filter/src/reclassify.rs` re-judges only those; RP-UC is off on an upgraded store and MW-6 is shadow-only. Any other change in the counts fails the smoke. Earlier drafts cited a general re-judge, which doesn't exist.
