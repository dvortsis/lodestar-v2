# X-fuzz-1105 decisions (#484)

A longer fuzz campaign than CI's 60 s per target (architecture §6 hostile-input limits, §14 M1 fuzzing), over the untrusted-input parsers that merged this week and then the core parsers. Run on a 4-core cloud container, four targets at a time, `cargo +nightly fuzz run -O <t> fuzz/corpus/<t> fuzz/seeds/<t> -- -max_total_time=900 -rss_limit_mb=2560 -timeout=10` with the `-max_len` below, at `main` `ea01beb`.

## Result
**No crashes, hangs, timeouts or OOMs in any target.** No parser changed. 18 targets, 5.1 h of fuzzing in total (an extra 15 min round for the new `torrent_cache`, and 5 min on its reworked version after review, from an empty corpus), about 333 million executions.

## Decisions
- **New `torrent_cache` target over the metainfo parse with the plugin's caps, not over a reply entry point** (architecture §18.2, the torrent cache). The plugin (`crates/sources-plugins/src/torrent_cache.rs`, SRC-13) parses a cache's body inside the private async `TorrentCache::ask`, which fetches it first; there's no network-free function that takes body bytes and returns a `Verified`, and `Verified` can't be built outside the module. That file is also held by #479 (SRC-13b), so this slice doesn't split the parse out. The target runs `ask`'s steps on the bytes: `TorrentFile::parse_with(body, &LIMITS)`, `TorrentFile::raw_info`, `Info::parse_with` on the raw dict with no encoding hint, then the public `verify`. It checks that the file parse and the no-hint re-parse of `raw_info`'s span give the same v1 and v2 hashes (what `ask` relies on), and that `verify` answers `Some(false)` only for the v1 hash, `Some(true)` only for a truncated v2 hash that isn't also the v1, and `None` only for a key that is neither. The first byte picks the key, modulo 3: the v1 hash, the truncated v2 hash (v1 when there's none), or 20 bytes from the input, so the v1 match, the v2 match and the mismatch are all reached. A build-time assertion keeps `LIMITS`' file cap equal to `STREAM`'s 8 MiB byte cap. **Follow-up for the plugin's owner once #479 lands:** move the parse into a sync `fn verify_body(body: &[u8], lookup: &Lookup) -> Result<(TorrentFile, Vec<u8>, bool), Miss>` that `ask` calls, and point the target at it, so the target and the plugin can't drift. `Verified::claims` (the public-tracker filter) is also only reachable through a `Verified`, so it isn't fuzzed yet.
- **New seeds only, no corpora.** `fuzz/seeds/torrent_cache/` holds the `metainfo` seeds' `.torrent` files behind `0x00` (v1 key) and `0x02` (input key, `-mismatch`), the hybrid and v2 ones also behind `0x01` (v2 key, `-v2key`), and the plugin's `hit` fixture body; `fuzz/seeds/json/` the three Internet Archive answers behind a `0xff` byte (the target always runs its wide caps; this byte gives the second pass depth 8, 1,021 values and 3-item arrays); `fuzz/seeds/rss/` gains the Sukebei feed, the Sukebei listed-hash feed and Nyaa's malformed feed from `crates/sources-plugins/fixtures/`. Each new seed folder is smaller than the existing `metainfo` one (11,920 B of content): `torrent_cache` 3,714 B, `json` 3,639 B.
- **No new dependency.** A first version hashed the raw dict with `sha1` in the target; the self-review found that check circular (the parser hashes the same bytes) and the dependency unapproved, so it compares the two parses' hashes instead.
