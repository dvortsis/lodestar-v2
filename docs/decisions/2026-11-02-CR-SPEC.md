# CR-SPEC decisions: frozen measurement specification for crawler runs

The evidence rulebook for every live crawler run on the experiment host: the bitmagnet comparator (CR-AB-COMP), every A/B (CR-AB-*), and the CR-COMB 24 h acceptance soak that judges the v0.6 crawler gate (`docs/build-plan.md` §0.5, §0.6). CR-COL-3 implements these rules in `docs/soak/tools/`. A reviewer checks a run against them rule by rule.

**Status: frozen, pending the owner's confirmation (`ext:owner-cr-spec`).** No booked run starts before the owner confirms. After that, a rule changes only through a new decisions file merged **before** the next run it applies to, never after any data from an affected run has been seen. A run is judged by the version of this spec in force when it started.

**Owner-set numbers used, unchanged:** 24 h mean ≥ 100 verified searchable torrents per minute, no hour below 70/min, p95 discovery-to-searchable ≤ 10 min (`docs/owner-decisions.md` §2.25, `docs/build-plan.md` §0.6 under §2.26); one node, one public IP, a fresh data directory, no imports, the Balanced preset; Checkpoint 1 (§2.27). Every other number below is a measurement parameter this spec introduces, listed for the owner in [Flagged for the owner](#flagged-for-the-owner).

**Supersedes:** the "predeclare the thresholds from the CR-0 baseline's variance" step in `docs/decisions/2026-11-02-CR-4.md` ("Proposed live A/B", item 3), the same step for any other crawler A/B (CR-1b included), and the freeze list in `docs/plan/2026-10-27-crawler-experiment-protocol.md`. Rule 6.3's fixed margin replaces a per-experiment threshold.

## Definitions
- **D1. Scrape.** One collector sample of `/metrics` plus process identity, every 60 s (`SAMPLE_SECONDS`). Times are the collector's monotonic `elapsed_seconds`, never the wall clock. Series are named without the exported `lodestar_` prefix, as in `docs/metrics.md`; `fetch_lookups`, `dht_timeouts_total` and `dht_throttled_total` are the existing series defined in `crates/lodestar/src/metrics.rs` and read by `analyze_cr0.py`.
- **D2. Numerator.** `searchable_new_total{origin="network"}`, the gate's own counter (`docs/metrics.md` "Crawler gate").
- **D3. Latency series.** `discovery_to_searchable_seconds` (a cumulative Prometheus histogram: buckets `le` 1, 2, 5, 10, 30, 60, 120, 300, 600, 1800, 3600, 7200, `+Inf`; `_count` = `+Inf`; whole seconds) and `discovery_to_searchable_dropped_total`.
- **D4. Segment.** One process lifetime measured under one configuration: the comparator run, one A/B arm, or the acceptance soak.
- **D5. Block.** One sequence of four segments on one fresh data directory: ABBA, or BAAB (rule 6.1).
- **D6. T_open.** The first scrape at which `dht_sample_suppression_seconds` reads 0. For a `resumed` start this is the first scrape. `invalidate_failed` opens once its write lands, no earlier than start + 6 h; `locked` never opens.
- **D7. Verdicts.** A segment is **valid**, **invalid** (rule 6.5: its evidence can't be trusted) or **void** (rule 5: its treatment didn't take effect). Only valid segments enter an analysis.

## 1. The measured window
1. **Start.** The window's nominal start is `ws = T_open + 60 min` (the warmup). Same rule for every Lodestar run type:
   - **fresh data directory** (the first segment of a block, CR-COMB): `first_start` holds sampling for 6 h, so `ws` ≈ process start + 6 h + 60 min;
   - **resumed restart** inside a block (rule 2.3): `ws` ≈ process start + 60 min, and the warmup is also the wash-out;
   - **any other suppression reason:** the same formula; the delay is recorded.
   - **No T_open within 7 h of process start:** the segment is invalid.
2. **Comparator.** bitmagnet has no sampling suppression: `ws` = its process start + 60 min.
3. **Length.** A/B segment: 6 measured hours. Comparator and CR-COMB: 24 measured hours. The run stops after the window ends (rule 3.4 says what is reported).
4. **Boundary scrapes.** Hour `k` (k = 0, 1, …) is `[ws + 3600·k, ws + 3600·(k+1))`. Its boundary value is the **first scrape at or after** the boundary, no more than 90 s after it; otherwise the hour has a gap (rule 6.6). `t_s` is the window's start scrape (hour 0's), and the window ends at the last hour's end scrape. Every later rule measures from `t_s`, not `ws`.
5. **Hours are consecutive, not wall-clock aligned and not rolling.** Adjacent hours share one boundary scrape, so every scrape interval belongs to exactly one hour. An hour's rate is its counter delta between its two boundary scrapes, net of rule 3.2, divided by the actual minutes between them.
6. **Window mean** = (end value − start value − carry-in bound) ÷ minutes between the start and end scrapes. It is not an average of hourly rates.
7. **Startup is reported, not hidden.** The suppressed period and the warmup are published separately with their own numerator rate and the suppression reason (`dht_sample_suppression_reason`).

## 2. Carry-over between arms
1. **A fresh data directory per block,** never per segment. No data, routing state or witness from an earlier run, block or the comparator is reused.
2. **The comparator has its own booked period.** No Lodestar process runs on the host or the public IP from 12 h before its process start to its window's end, and no Lodestar window starts within 12 h after it. Its store is fresh (§0.5: separate days, never back to back).
3. **`dht.safe_restart` is `true` in every segment of a block** (`LODESTAR_DHT_SAFE_RESTART=true`), the same in both arms, so an arm switch is a clean stop and a resumed start instead of another 6 h suppression. It's a constant of the block, never a treatment.
   - **The witness must survive the switch.** `LODESTAR_DHT_WITNESS_DIR` points at a host directory outside the data directory (a bind mount on Docker, where changing an environment variable recreates the container and the default in-container witness would be lost to `no_witness`). It's fresh per block. This is a pre-run checklist item, published (rule 7.2).
   - An arm switch is a clean stop (the collector's stop path, not a kill) followed by a start with only the treatment's switch changed, within 10 minutes, well inside CR-0d's 6 h `stale` horizon.
   - A start whose reason isn't `resumed` still counts: rule 1.1 moves its window, and the reason is published.
4. **Wash-out:** the 60 min warmup after a resumed start. Keys the previous segment left in the fetch queue take this run's start as their first sighting (`docs/metrics.md`), before `t_s`, so rule 3.2 removes them.
5. **Depletion is balanced, not removed.** The store keeps what earlier segments stored, so later segments see more `already_stored` and `rediscovered`. Rule 6.2 cancels a linear drift; every segment publishes `metadata_excluded_total{reason="already_stored"}` and `{reason="rediscovered"}`.
6. **CR-COMB** runs once from a fresh directory with no restart, so `safe_restart` doesn't act (`first_start`); it's set as the build under test ships it, and recorded.

## 3. The cohort
1. **An arm's events are keys first sighted inside its window** and made searchable inside it. The instruments count at commit time, so the numerator is the commit-time delta minus an upper bound on keys first sighted before `t_s` (rule 3.2). No carry-in key counts; a few in-window keys may be discounted (conservative).
2. **Carry-in bound.** For each scrape interval `(t_i, t_{i+1}]` inside the window, let `a_i = ⌊t_i − t_s⌋` seconds and `e_i` the largest finite bucket edge ≤ `a_i` (none if `a_i` < 1). A key committed in the interval can predate `t_s` only if its latency exceeds `a_i`, so:

   `bound_i = Δ_count − Δbucket{le = e_i} (0 if no edge) + Δdropped_i`, where `Δdropped_i` counts only while `a_i` < 7200 s.

   Buckets are cumulative, so this counts each sample once. After 2 h a carry-in key needs a latency above 7200 s and lands in `+Inf`, which the first term always keeps; a dropped sample after 2 h is taken as in-window. The bound is summed per hour (rule 1.5) and over the window (rule 1.6), and subtracted from both. Hour 0 carries most of it: the gross and net counts and the bound's share are published per hour.
3. **Latency cohort:** samples whose index commit falls in the window, carry-in included. A straddler has a long latency, so keeping it can only raise the p95 (conservative for the gate; the same in both A/B arms).
4. **Window end.** A key first sighted in the window and not yet searchable at its end is outside the cohort and isn't measured after it. It's **reported, not dropped:** the end scrape publishes `metadata_new_verified_total{origin="network"} − searchable_new_total{origin="network"}` (stored, not yet searchable), `fetch_admission_waiters`, `fetch_lookups` and `dht_peer_active + dht_peer_queued`.
5. **Never in the numerator:** imports, `origin="recovery"`, and every `metadata_excluded_total` reason. They're published as separate series.

## 4. Latency coverage and the p95
1. **Coverage** = Δ`_count` ÷ (Δ`_count` + Δ`discovery_to_searchable_dropped_total`) over the window. Also published per hour.
2. **Below 98 % coverage the p95 is "not measured".** Not measured is never a pass.
3. **The pass test counts dropped samples as above the threshold.** p95 ≤ 10 min passes only if Δbucket{le="600"} ≥ 0.95 × (Δ`_count` + Δdropped). 600 s is a bucket edge, so no interpolation.
4. **Reported p95** = the upper edge of the first bucket whose cumulative delta reaches 95 % of (Δ`_count` + Δdropped), dropped counted in `+Inf`. Never interpolated.
5. **Reconciliation.** Δ`_count` + Δdropped must match the gross numerator delta within 2 %. A larger gap is missing evidence (rule 6.6).

## 5. Mechanism checks
A segment whose treatment didn't take effect is **void**, not negative. Each check compares window deltas.

1. **CR-ADM (`dht.coordinated_admission`).**
   - On: Δ`fetch_admission_grants_total` > 0, and the permit identity in `docs/metrics.md` "Coordinated admission" (grants = DHT permit returns + `finder_full`/`finder_closed` returns + permits in use) is non-zero at no more than 4 consecutive scrapes. A longer run of non-zero scrapes is a leaked or duplicated permit: the segment is void.
   - Off: every `fetch_admission_*_total` delta is 0 and `fetch_admission_permits_in_use` reads 0 at every scrape.
   - Published, both arms: `dht_peer_rejection_reasons_total{reason="capacity"}`, `fetch_admission_refusals_total`.
2. **uTP (`dht.utp`).**
   - On: Δ`dht_utp_in_total` > 0 and Δ`fetch_attempts_total{transport="utp"}` > 0.
   - Off: Δ`dht_utp_in_total` = 0, `fetch_attempts_total{transport="utp"}` absent or Δ 0, and `utp_*` series absent.
   - Published, at least CR-4's guardrails: `utp_retransmits_total`, `utp_connection_timeouts_total`, `dht_timeouts_total`, `dht_throttled_total`, `dht_sample_deferred_total`, `dht_peer_rejection_reasons_total{reason="capacity"}`, `dht_peer_admitted_total`, `dht_peer_rejected_total`, `fetch_admission_refusals_total`, peak RSS, and the fetch latency where it's exported.
3. **Route backoff (`dht.route_backoff`).**
   - **Run only if a baseline shows `fetch_no_route_total{family="ipv6"}` > 0,** summed over the windows of every valid segment with both `dht.route_backoff` and `dht.utp` off. If it's 0, CR-AB-ROUTE is a **recorded skip** (a decisions file stating the sum and the segments), not a run. On the default IPv4-only DHT bind the series is expected to be 0, so the skip is the expected outcome.
   - On: Δ`fetch_route_skipped_total` > 0. If it's 0 the switch had nothing to act on: the segment is void as **"no opportunity"**. It isn't re-run and doesn't make its block invalid; if no on-segment had an opportunity, the outcome is recorded as "no opportunity" and the switch stays off.
   - Off: Δ`fetch_route_skipped_total` = 0, and with `dht.utp` off, Δ`fetch_route_probe_down_total` = 0.
   - The predeclared expectation is no measurable effect (CR-4).
4. **The comparator.**
   - Its image is pinned by digest, and the digest is published.
   - Its store is empty at start (a fresh database and volume).
   - Its count of stored torrents rises in every measured hour.
   - Rule 2.2 holds.

   The count is a read-only count of its torrents table taken at each scrape (D1). CR-COL-3 fixes the exact query and publishes it before the rehearsal. bitmagnet has no searchable stage separate from storage and no latency histogram, so the comparator reports the mean and the hourly rates only, with no carry-in bound.
5. **Every Lodestar segment** also checks: the Balanced preset, no import job in the window (no `import_finished` annotation, and `metadata_new_verified_total{origin="import"}` not rendered), the same image digest in every segment of a block, and the switch set of rule 6.1.

## 6. Analysis
1. **Design.** Each treatment runs alone. **Every other crawler switch is at its shipped default (off) in every A/B block, except `dht.safe_restart` (rule 2.3).** A is the control (treatment off), B the treatment on, 6 measured hours per segment.
   - **At least two blocks per treatment** before any outcome (four repetitions per arm; the plan's minimum is two). Block 1 is ABBA; block 2 is BAAB and starts about 12 h out of phase with block 1, so time of day and post-start depletion fall on both arms. A third block, if needed (rule 6.3), is ABBA. Each segment's host-local start hour is published.
2. **Effect estimate.** Per valid segment, `y = ln(net window mean)`. Over all valid blocks of one treatment, fit `y` by least squares on a block intercept, a per-block linear trend in segment midpoint time, and the treatment indicator `τ`. The effect is `exp(τ̂) − 1`, a relative change in the net verified searchable rate; its 95 % CI uses the t distribution with `n_segments − 2·blocks − 1` degrees of freedom (3 for two blocks, 5 for three). With equally spaced midpoints, a block's own estimate is the plain ABBA (or BAAB) contrast; a non-resumed restart breaks the spacing, which the fit handles.
3. **Outcome** (after block 2, and after block 3 if run), first match wins:
   1. **win:** the CI's lower bound > 0 and the point estimate ≥ +5 %;
   2. **no effect:** the whole CI lies within [−5 %, +5 %] (relative: `τ` within [ln 0.95, ln 1.05]);
   3. **loss:** the CI's upper bound < 0;
   4. **inconclusive:** anything else. After block 2, run block 3; after block 3 it stays inconclusive and the switch stays off.

   Two looks at 95 % raise the chance of a false win somewhat above 5 %. That's accepted because no switch reaches the gate on an A/B: CR-COMB's 24 h soak measures the combination on its own.
   Invalid blocks don't count towards the three.
4. **Also reported, not decided on:** the same estimate for the gross numerator, the stored rate (`metadata_new_verified_total{origin="network"}`), fetch success per attempt, the p95 per arm (rule 4), each segment's worst hour, and the guardrails (rule 5.2). A guardrail that worsens with its own CI excluding 0 goes to the runner, which decides adoption under `docs/owner-decisions.md` §2.26.
5. **What makes a segment invalid.** Any of these, between process start and the window's end:
   - an interruption: a process restart, a stop, a host reboot, a container action by any plugin;
   - a counter reset: any cumulative counter decreasing, or the process identity changing;
   - host activity: an import, another crawler (Lodestar or bitmagnet) on the host or the public IP, an array or parity operation, anything the operator logs as disruptive;
   - network: a public-IP change (checked at `t_s`, at the end and at every hour boundary), or a logged link or router outage;
   - a missing host-checklist item: auto-update and backup plugins excluding the container with their next scheduled runs recorded, the host-mounted witness (rule 2.3), the Defender exclusion on Windows;
   - no T_open within 7 h (rule 1.1);
   - missing evidence (rule 6.6).
6. **Missing evidence:**
   - a required series (rule 6.10) is absent from a scrape in the window;
   - two consecutive scrapes are more than 180 s apart;
   - a boundary scrape is more than 90 s late (rule 1.4);
   - the reconciliation fails (rule 4.5);
   - the configuration identity is missing (rule 7.2).
7. **Re-runs.** Runs are never stitched: no window is assembled from two processes, two periods or two data directories.
   - An invalid segment, or a void one other than "no opportunity", makes its whole block invalid. The block is re-run in the same order from a fresh directory; the invalid block is published, with its reason.
   - An invalid comparator run or CR-COMB run is re-run in full from fresh data.
   - Re-runs come out of the ~30 % retry budget (`docs/build-plan.md` §0.7).
8. **The gate decision (CR-COMB, one valid 24 h window).** It passes only if all three hold:
   - the net window mean ≥ 100/min (rule 1.6);
   - every one of the 24 net hourly rates ≥ 70/min (rule 1.5);
   - the p95 passes rule 4.3 with coverage ≥ 98 %.

   Anything else is a fail, or "not measured" for the p95, and never a pass. The comparator's mean and worst hour are published beside it. If the host, its public IP or its network changed since the comparator ran, the comparator is re-run first (§0.5).
9. **Checkpoint 1 projection** (after the CR-ADM and uTP outcomes and the comparator). It's a projection with stated uncertainty, not a measurement (§0.5).
   - **Base `R0`:** the net window mean pooled over the control segments of the uTP experiment's valid blocks (its switches are the shipped defaults), with its 95 % CI from those segments (`n − 1` df).
   - **Gains:** `g_i = exp(τ̂_i)`, with its CI, for each treatment that won. With no winner, the projection is `R0`.
   - **Two models, both published:**
     - multiplicative: `R0 · Π g_i`; its interval sums the variances of `ln R0` and every `τ̂_i` and uses the largest t quantile among them;
     - additive: `R0 · (1 + Σ (g_i − 1))`; its interval from the delta method on the same variances, with the same quantile.

     The projected range spans both intervals.
   - **The projection used for "on track" is the lower of the two point estimates** (the additive one when every gain exceeds 1).
   - **Worst hour:** the projection × the lower of two ratios, worst hour ÷ mean: the comparator's 24 h window, and CR-0 final's measured 24 h (excluding its startup; it measured the stored rate, not searchable). 6 h arms don't bound a 24 h worst hour, so this is stated as an assumption.
   - **p95:** the largest reported p95 (rule 4.4) among the winning arms' on-segments, or among `R0`'s segments with no winner; "not projected" if any is not measured.
   - **Also published:** the comparator's mean, and the projection as a fraction of it.
   - **On track** when the projection ≥ 100/min, its worst hour ≥ 70/min, and its p95 ≤ 10 min. Otherwise the runner reports the projection and its range, the dominant limiter, the comparator's rate and the options to the owner before CR-5 (§2.27). When on track but the range's lower end is below 100/min, the runner says so in its report.
10. **Required series** (each window scrape; absence is missing evidence):
    - **every Lodestar segment:** D2's numerator and `metadata_new_verified_total{origin="network"}`, D3's histogram and dropped counter, `metadata_excluded_total`, `fetch_failures_total`, `fetch_lost_total`, `fetch_attempts_total{transport="tcp"}`, `fetch_success_total`, `fetch_family_attempts_total`, `fetch_family_success_total`, `fetch_no_route_total`, `dht_sample_suppression_seconds`, `dht_sample_suppression_reason`, `dht_peer_active`, `dht_peer_queued`, `fetch_lookups`, the `analyze_cr0.py` core counters, and the process's memory and CPU;
    - **CR-ADM segments, both arms:** the `fetch_admission_*` series and `dht_peer_permit_returns_total`;
    - **uTP on-segments:** `dht_utp_in_total`, `fetch_attempts_total{transport="utp"}`, `utp_retransmits_total`, `utp_connection_timeouts_total`; off-segments: `dht_utp_in_total` only;
    - **route-backoff segments, both arms:** `fetch_route_skipped_total`, `fetch_route_probe_down_total`;
    - **the comparator:** its torrent count (rule 5.4) and its process's memory and CPU.

## 7. Evidence each run publishes
Under the run's own `docs/soak/evidence/<slice>/` (each slice's `owns`):
1. **Aggregates and hourly snapshots only.** Per hour and over the window:
   - the numerator, gross and net, and the carry-in bound with its share;
   - the latency bucket deltas, Δdropped and coverage;
   - every mechanism and guardrail series in rule 5;
   - `metadata_excluded_total` and `fetch_lost_total` by reason, and `fetch_failures_total` by kind;
   - the per-family and per-transport fetch series;
   - peak RSS, CPU, packets/s, bytes, connects/s and open sockets;
   - the startup period (rule 1.7) and the end-of-window backlog (rule 3.4).

   **Never per-minute or per-scrape rows.** They stay in the private evidence directory on the host.
2. **Identity:**
   - the binary or image digest and the source SHA;
   - every crawler switch and the intensity preset;
   - `safe_restart`, whether the witness is host-mounted, and the suppression reason;
   - the host class and network mode class;
   - the spec version (this file's path and commit);
   - the elapsed times of process start, `T_open`, `ws`, `t_s` and the end, and the host-local start hour.
3. **Validity:** the host checklist and activity log as fixed categories with elapsed times, each rule 6.5 check with its result, and the segment's verdict (D7) with its reason.
4. **Never published:** peer or node IPs (the public IP only as "unchanged" or "changed"), ports, node IDs, tokens, infohashes, torrent or file names, and any label value outside the fixed enums CR-COL-3 validates.

## Flagged for the owner
None of these changes an owner-set number. Each is a measurement rule the owner confirms with `ext:owner-cr-spec`. O1 could read as loosening, so the runner hasn't decided it.
- **O1 (owner to decide). The 24 h gate window excludes the 6 h first-start suppression and a 60 min warmup** (rule 1.1), so the gate run lasts about 31 h, and its mean and worst hour describe sustained crawling, not a user's first day. **The alternative:** `ws` = process start with no warmup, so the 24 h include about 6 h without BEP 51 sampling; the carry-in bound is then 0 on a fresh directory. That is stricter. The startup period is published either way (rule 1.7). Recommended: exclude, because with CR-0d's `safe_restart` only a first start waits 6 h, and the A/B arms then measure the same steady state the gate does.
- **O2 (tightens).** The first-sighting cohort is enforced by subtracting an upper bound on carry-in keys (rule 3.2): each commit whose latency bucket could reach back before `t_s` (in hour 0, any latency above the time elapsed since `t_s`, rounded down to a bucket edge), every `+Inf` sample, and dropped samples in the window's first 2 h. Hour 0 carries most of it and could decide the "no hour below 70" test; its share is published per hour.
- **O3 (tightens).** The p95 isn't reported below 98 % coverage, and dropped samples count as above 10 min (rules 4.2, 4.3).
- **O4. Checkpoint 1's "reaches ≥ 100/min" uses the lower of the additive and multiplicative point estimates**, with the range always reported (rule 6.9). Requiring the range's lower end would be stricter, but with 8–12 segments per treatment it would send nearly any result to the owner.
- **O5. New measurement parameters:**
  - 60 min warmup and wash-out (rules 1.1, 2.4); no T_open within 7 h makes a segment invalid (rule 1.1);
  - 90 s boundary tolerance and 180 s maximum scrape gap (rules 1.4, 6.6); public IP checked at every hour boundary (rule 6.5);
  - dropped samples count as carry-in for the first 2 h (rule 3.2);
  - 2 % reconciliation (rule 4.5);
  - a permit-identity gap over 4 consecutive scrapes voids a CR-ADM segment (rule 5.1);
  - arm switches within 10 minutes (rule 2.3); 12 h clear of Lodestar either side of the comparator (rule 2.2);
  - a +5 % practical effect and equivalence margin, two looks at 95 % (rule 6.3);
  - two to three blocks per treatment (rules 6.1, 6.3).
- **O6. Calendar.** Two blocks per treatment are the minimum (one block's CI has 1 degree of freedom, t ≈ 12.7, so it can almost never decide). A block is about 1.5 host-days (6 h suppression, then four segments of warmup plus 6 h). That's about 3 host-days per treatment against §0.7's 2 days for CR-ADM and uTP together: roughly **4 extra host-days for those two, more for the later A/Bs**, before the 30 % retry budget. Arm switches use `dht.safe_restart` (rule 2.3), so a block pays one 6 h suppression, not four.
