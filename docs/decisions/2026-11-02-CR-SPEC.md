# CR-SPEC decisions: frozen measurement specification for crawler runs

The evidence rulebook for every live crawler run on the experiment host: the bitmagnet comparator (CR-AB-COMP), every A/B (CR-AB-*), and the CR-COMB 24 h acceptance soak that judges the v0.6 crawler gate (`docs/build-plan.md` §0.5, §0.6). CR-COL-3 implements these rules in `docs/soak/tools/`. A reviewer checks a run against them rule by rule.

**Status: frozen, pending the owner's confirmation (`ext:owner-cr-spec`).** No booked run starts before the owner confirms. After that, a rule changes only through a new decisions file merged **before** the next run it applies to, never after any data from an affected run has been seen. A run is judged by the version of this spec in force when it started.

**Owner-set numbers used, unchanged:** 24 h mean ≥ 100 verified searchable torrents per minute, no hour below 70/min, p95 discovery-to-searchable ≤ 10 min (`docs/owner-decisions.md` §2.25, `docs/build-plan.md` §0.6 under §2.26); one node, one public IP, a fresh data directory, no imports, the Balanced preset; Checkpoint 1 (§2.27). Every other number below is a measurement parameter this spec introduces; they're listed for the owner in [Flagged for the owner](#flagged-for-the-owner).

## Definitions
- **D1. Scrape.** One collector sample of `/metrics` plus process identity, every 60 s (`SAMPLE_SECONDS`). Times are the collector's monotonic `elapsed_seconds`, never the wall clock.
- **D2. Numerator.** `lodestar_searchable_new_total{origin="network"}`, the gate's own counter (`docs/metrics.md` "Crawler gate").
- **D3. Latency series.** `discovery_to_searchable_seconds` (buckets `le` 1 … 600, 1800, 3600, 7200, `+Inf`) and `discovery_to_searchable_dropped_total`.
- **D4. Segment.** One process lifetime measured under one configuration: the comparator day, one A/B arm, or the acceptance soak.
- **D5. Block.** One ABBA sequence of four segments (A, B, B, A) on one data directory.
- **D6. T_open.** The first scrape at which `dht_sample_suppression_seconds` reads 0. For a `resumed` start this is the first scrape. (`locked` and `invalidate_failed` never read 0, so they never open.)

## 1. The measured window
1. **Start.** The window starts at `ws = T_open + 60 min` (the warmup). Same rule for every Lodestar run type:
   - **fresh data directory** (the first segment of a block, CR-COMB): `first_start` holds sampling for 6 h, so `ws` ≈ process start + 6 h + 60 min;
   - **resumed restart** inside a block (rule 2.3): `ws` ≈ process start + 60 min, and the warmup is also the wash-out;
   - **any other suppression reason:** the same formula; the delay is recorded, not an error.
2. **Comparator.** bitmagnet has no sampling suppression: `ws` = its process start + 60 min.
3. **Length.** A/B segment: 6 measured hours. Comparator and CR-COMB: 24 measured hours. The run stops after the window ends (rule 3.5 says what is reported).
4. **Boundary scrapes.** Hour `k` (k = 0, 1, …) is `[ws + 3600·k, ws + 3600·(k+1))`. Its boundary value is the **first scrape at or after** the boundary. That scrape must be no more than 90 s after it; otherwise the hour is a gap (rule 6.6). The window's start and end values are the boundary scrapes of hour 0's start and the last hour's end.
5. **Hours are consecutive, not wall-clock aligned and not rolling.** Adjacent hours share one boundary scrape, so every scrape interval belongs to exactly one hour. A rate is the counter's delta between the hour's two boundary scrapes divided by the actual minutes between them.
6. **Window mean** = (end value − start value − carry-in bound, rule 3.2) ÷ minutes between the start and end scrapes. The mean is not an average of hourly rates.
7. **Startup is reported, not hidden.** The suppressed period and the warmup are reported separately with their own numerator rate and the suppression reason (`dht_sample_suppression_reason`), so a reader sees what the window excludes.

## 2. Carry-over between arms
1. **A fresh data directory per block,** never per segment. No data, routing state or witness from any earlier run, block or the comparator is reused. The witness directory (`LODESTAR_DHT_WITNESS_DIR`, CR-0d) is fresh with it.
2. **The comparator and Lodestar never share a day or a data store,** and never run back to back (`docs/build-plan.md` §0.5): each starts from fresh data on its own host-local calendar day.
3. **`dht.safe_restart` is `true` in every segment of a block** (`LODESTAR_DHT_SAFE_RESTART=true`), the same value in both arms, so an arm switch is a clean stop and a resumed start instead of another 6 h suppression. The switch is a constant of the block, never a treatment.
   - An arm switch is a clean stop (the collector's stop path, not a kill) followed by a start with only the treatment's switch changed, within 10 minutes, well inside the 6 h `stale` horizon.
   - A start whose reason isn't `resumed` still counts: rule 1.1 moves its window. The reason is published (rule 7.3).
4. **Wash-out:** the 60 min warmup after a resumed start (rule 1.1). Keys the previous segment left in the fetch queue get this run's start as their first sighting (`docs/metrics.md`), which is before `ws`, so rule 3.2 removes them from the numerator.
5. **Depletion is balanced, not removed.** The store keeps what earlier segments stored, so later segments see more `already_stored` and `rediscovered`. ABBA cancels a linear drift (rule 6.2); every segment publishes `metadata_excluded_total{reason="already_stored"}` and `{reason="rediscovered"}` so a reviewer can see it.
6. **CR-COMB** runs once from a fresh directory with no restart, so `safe_restart` doesn't act (`first_start`); it's set as the build under test ships it, and recorded.

## 3. The cohort
1. **An arm's events are keys first sighted inside its window** and made searchable inside it. The instruments count at commit time, so the numerator is the commit-time delta minus an upper bound on keys first sighted before `ws` (rule 3.2). This never counts a carry-in key towards a window; it may discount a few keys sighted just after `ws` (conservative).
2. **Carry-in bound.** For each scrape interval `(t_i, t_{i+1}]` inside the window, a key committed in it straddles `ws` only if its latency exceeds `t_i − ws`. The bound adds, per interval:
   - every histogram bucket delta whose upper edge `le` > `t_i − ws` (the `+Inf` bucket always);
   - every `discovery_to_searchable_dropped_total` increment (its latency is unknown).

   The bound is computed per hour (rule 1.5) and over the window (rule 1.6), and subtracted from both. The gross and net counts and the bound are all published.
3. **Latency cohort:** samples whose index commit falls in the window, carry-in included. A straddler has a long latency, so keeping it can only raise the p95 (conservative for the gate; the same in both A/B arms).
4. **Window end.** A key first sighted in the window and not yet searchable at its end is outside the cohort and isn't measured after it. It's **reported, not dropped:** the end scrape publishes `metadata_new_verified_total{origin="network"} − searchable_new_total{origin="network"}` (stored, not yet searchable), `fetch_admission_waiters`, `fetch_lookups` and `dht_peer_active + dht_peer_queued`.
5. **Not in the numerator, ever:** imports, `origin="recovery"`, and every `metadata_excluded_total` reason. They're published as separate series.

## 4. Latency coverage and the p95
1. **Coverage** = Δ`discovery_to_searchable_seconds_count` ÷ (Δ`_count` + Δ`discovery_to_searchable_dropped_total`) over the window.
2. **Below 98 % coverage the p95 is "not measured".** Not measured is never a pass. Coverage is also published per hour.
3. **The pass test counts dropped samples as above the threshold.** p95 ≤ 10 min passes only if Δ(bucket `le="600"`) ≥ 0.95 × (Δ`_count` + Δ`dropped`). 600 s is a bucket edge, so the test needs no interpolation.
4. **Reported p95** = the upper edge of the first bucket whose cumulative delta reaches 95 % of (Δ`_count` + Δ`dropped`), dropped counted in `+Inf`. Never interpolated.
5. **Reconciliation.** Δ`_count` + Δ`dropped` must match Δnumerator (gross) within 2 %. A larger gap is missing evidence (rule 6.6).

## 5. Mechanism checks
A segment whose treatment didn't take effect is **void**, not negative. Each check compares window deltas; each segment also publishes its full switch set (rule 7.2), and every switch other than the treatment is identical in all four segments of a block.

1. **CR-ADM (`dht.coordinated_admission`).**
   - On: Δ`fetch_admission_grants_total` > 0.
   - Off: every `fetch_admission_*_total` delta is 0 and `fetch_admission_permits_in_use` reads 0 at every scrape.
   - Also published, both arms: `dht_peer_rejection_reasons_total{reason="capacity"}`, `fetch_admission_refusals_total`, and the permit balance (`docs/metrics.md` "Coordinated admission"); a persistent gap in the balance makes the on-segment void.
2. **uTP (`dht.utp`).**
   - On: Δ`dht_utp_in_total` > 0 and Δ`fetch_attempts_total{transport="utp"}` > 0.
   - Off: both deltas 0, and `utp_*` series absent.
   - Published: the guardrails CR-4 names (`utp_retransmits_total`, `utp_connection_timeouts_total`, `dht_timeouts_total`, `dht_throttled_total`, `dht_sample_deferred_total`, the capacity rejections, `fetch_admission_refusals_total`, peak RSS).
3. **Route backoff (`dht.route_backoff`).**
   - **Run only if a baseline shows `fetch_no_route_total{family="ipv6"}` > 0:** summed over the windows of every valid segment with both `dht.route_backoff` and `dht.utp` off (the CR-ADM block's segments and the uTP block's off-segments). If it's 0, CR-AB-ROUTE is a **recorded skip** (a decisions file stating the sum and the segments), not a run.
   - On: Δ`fetch_route_skipped_total` > 0. If it's 0, the segment had no route outage to act on: it's void as "no opportunity", not a result.
   - Off: Δ`fetch_route_skipped_total` = 0, and with `dht.utp` off, Δ`fetch_route_probe_down_total` = 0.
   - The predeclared expectation is no measurable effect (CR-4).
4. **The comparator.**
   - Its image is pinned by digest, and the digest is published.
   - Its store is empty at start (a fresh database and volume).
   - Its count of stored torrents rises in every measured hour.
   - No Lodestar process runs on the host or the public IP during its day.

   The count is a read-only count of its torrents table taken at each scrape (rule D1). CR-COL-3 fixes the exact query, and publishes it before the rehearsal. bitmagnet has no searchable stage separate from storage and no latency histogram, so the comparator reports the mean and the hourly rates only, with no carry-in bound.
5. **Every Lodestar segment** also checks: the Balanced preset, no import job in the window (no `import_finished` annotation, and `metadata_new_verified_total{origin="import"}` not rendered), and the same image digest in all segments of a block.

## 6. Analysis
1. **Design.** Each treatment runs alone in ABBA blocks of 6 measured hours per segment. The minimum is one block: two repetitions per arm. A is the control (treatment off); B is the treatment on.
2. **Effect estimate.** Per segment, `y = ln(net window mean)`. Over all valid blocks of one treatment, fit `y` by least squares on: a block intercept, a per-block linear trend in segment midpoint time, and the treatment indicator. The effect is `exp(τ̂) − 1`, a relative change in the net verified searchable rate. Its uncertainty is the 95 % confidence interval from the t distribution with `n_segments − 2·blocks − 1` degrees of freedom. With one block this equals the plain ABBA contrast `½(y_B1 + y_B2) − ½(y_A1 + y_A2)`, with 1 degree of freedom.
3. **Outcome** (per treatment, after each block):
   - **win:** the CI's lower bound > 0 and the point estimate ≥ +5 %;
   - **loss:** the CI's upper bound < 0;
   - **no effect:** the whole CI lies within ±5 %;
   - **inconclusive:** anything else. Run one more block, to at most 3 blocks per treatment. After 3, it stays inconclusive and the switch stays off.
4. **Also reported, not decided on:** the same estimate for the gross numerator, the stored rate (`metadata_new_verified_total{origin="network"}`), fetch success per attempt, the p95 per arm (rule 4), the worst hour per segment, and the guardrails (rule 5.2). A guardrail that worsens with its own CI excluding 0 goes to the runner, which decides adoption under `docs/owner-decisions.md` §2.26.
5. **What invalidates a segment.** Any of these, inside its window:
   - an interruption: a process restart, a stop, a host reboot, a container action by any plugin;
   - a counter reset: any cumulative counter decreasing, or the process identity changing;
   - host activity: an import, another crawler (Lodestar or bitmagnet) on the host or the public IP, an array or parity operation, an item the operator logs as disruptive;
   - network: a public-IP change (checked at `ws`, at the end and at least hourly), or a logged link or router outage;
   - a host-checklist item missing (auto-update and backup plugins excluding the container, their next scheduled runs recorded, Defender exclusion on Windows);
   - missing evidence (rule 6.6);
   - a failed mechanism check (rule 5).
6. **Missing evidence:**
   - a required series is absent from a scrape;
   - two consecutive scrapes are more than 180 s apart;
   - a boundary scrape is more than 90 s late (rule 1.4);
   - the reconciliation fails (rule 4.5);
   - the configuration identity is missing (rule 7.2).
7. **Re-runs.** Runs are never stitched: no window is assembled from two processes, two days or two data directories.
   - An invalid segment voids its whole block. The block is re-run from a fresh directory; the invalid block is published as invalid, with its reason.
   - An invalid comparator day or CR-COMB run is re-run in full from fresh data.
   - Re-runs come out of the ~30 % retry budget (`docs/build-plan.md` §0.7).
8. **The gate decision (CR-COMB, one valid 24 h window).** It passes only if all three hold:
   - the net window mean ≥ 100/min (rule 1.6);
   - every one of the 24 net hourly rates ≥ 70/min (rule 1.5, carry-in subtracted per hour);
   - the p95 passes rule 4.3 with coverage ≥ 98 %.

   Anything else is a fail, or "not measured" for the p95, and never a pass. The comparator's mean and worst hour are published beside it. If the host, its public IP or its network changed since the comparator ran, the comparator is re-run first (§0.5).
9. **Checkpoint 1 projection** (after the CR-ADM and uTP results and the comparator). It's a projection with stated uncertainty, not a measurement (§0.5).
   - **Base `R0`:** the net window mean pooled over the control segments of the most recent valid block, with its 95 % CI from those segments.
   - **Gains:** `g_i = exp(τ̂_i)` for each treatment that won (rule 6.3), with its CI.
   - **Two models, both published:**
     - multiplicative: `R0 · Π g_i`, with its interval from summing the variances of `ln R0` and every `τ̂_i` and using the largest t quantile among them;
     - additive: `R0 · (1 + Σ (g_i − 1))`, with its interval by the same rule.

     The projected range spans both models' intervals.
   - **Worst hour:** the projected mean × the lower of (worst hour ÷ mean) in the comparator's 24 h window and in CR-0's 24 h final. 6 h arms don't bound a 24 h worst hour, so this is stated as an assumption.
   - **p95:** the largest reported p95 (rule 4.4) among the winning arms' on-segments, or "not projected" if any is not measured.
   - **Also published:** the comparator's mean, and the projection as a fraction of it.
   - **On track** when the multiplicative point estimate ≥ 100/min, its projected worst hour ≥ 70/min, and its p95 ≤ 10 min. Otherwise the runner reports the projection and its interval, the dominant limiter, the comparator's rate and the options to the owner before CR-5 (§2.27). When on track but the range's lower end is below 100/min, the runner says so in its report.

## 7. Evidence each run publishes
Under the run's own `docs/soak/evidence/<slice>/` (each slice's `owns`):
1. **Aggregates and hourly snapshots only.** Per hour and over the window:
   - the numerator, gross and net, and the carry-in bound;
   - the latency bucket deltas, Δdropped and coverage;
   - every mechanism and guardrail series in rule 5;
   - `metadata_excluded_total` and `fetch_lost_total` by reason, and `fetch_failures_total` by kind;
   - the per-family and per-transport fetch series;
   - peak RSS, CPU, packets/s, bytes, connects/s and open sockets;
   - the startup period (rule 1.7) and the end-of-window backlog (rule 3.4).

   **Never per-minute or per-scrape rows.** They stay in the private evidence directory on the host.
2. **Identity:**
   - the binary or image digest and the source SHA;
   - every crawler switch and the intensity preset;
   - `safe_restart` and the suppression reason;
   - the host class and network mode class;
   - the spec version (this file's path and commit);
   - the elapsed times of process start, `T_open`, `ws` and the end.
3. **Validity:** the host checklist and activity log as fixed categories with elapsed times, each rule 6.5 check with its result, and the segment's verdict: valid, invalid with its reason, or void with its mechanism check.
4. **Never published:** peer or node IPs (the public IP only as "unchanged" or "changed"), ports, node IDs, tokens, infohashes, torrent names or file names, and any label value outside the fixed enums CR-COL-3 validates.

## Flagged for the owner
None of these changes an owner-set number. Each is a measurement rule the owner confirms with `ext:owner-cr-spec`. The first one is a choice that could read as loosening, so the runner hasn't decided it.
- **O1 (owner to decide). The 24 h gate window excludes the 6 h first-start suppression and a 60 min warmup** (rule 1.1). The gate run therefore lasts about 31 h, and its 24 h mean and worst hour describe sustained crawling, not a user's first day. The alternative is to measure the first 24 h from process start, which includes 6 h without BEP 51 sampling, and is stricter. Either way the startup period is published (rule 1.7). Recommended: exclude, because CR-0d's `safe_restart` means only a first start waits 6 h, and the A/B arms then measure the same steady state the gate does.
- **O2 (tightens).** The first-sighting cohort is enforced by subtracting an upper bound on carry-in keys (rule 3.2), so the gate's numerator can be slightly lower than `searchable_new_total`'s delta.
- **O3 (tightens).** The p95 isn't reported below 98 % coverage, and dropped samples count as above 10 min (rules 4.2, 4.3).
- **O4. Checkpoint 1's "reaches ≥ 100/min" uses the multiplicative point estimate**, with the interval always reported (rule 6.9). Requiring the interval's lower bound would be stricter, but with 4–12 segments per treatment it would send nearly any result to the owner.
- **O5. New measurement parameters:**
  - 60 min warmup and wash-out (rules 1.1, 2.4);
  - 90 s boundary tolerance and 180 s maximum scrape gap (rules 1.4, 6.6);
  - 2 % reconciliation (rule 4.5);
  - a +5 % practical effect and equivalence margin (rule 6.3);
  - at most 3 blocks per treatment (rule 6.3).

  Each extra block costs about 2 host-days; the §0.7 calendar assumes one block per treatment plus the 30 % retry budget.
- **O6.** Arm switches use `dht.safe_restart` within a block (rule 2.3): one 6 h suppression per block instead of one per segment, which keeps the §0.7 calendar.
