# S-filters decisions, part 2a: Settings → Filters & Safety

Part 2a is the screen and release (§20.7). Part 2b adds "Block this…" in Search and the detail drawer, and the Adult facets (§20.9).

- **The screen shows the server's last answer and decides nothing.** A switch is a button whose label follows `on` from `GET /filters`; it never flips locally. Each action starts the flows' change dialog (preview, effect warning, password), and the screen reloads `GET /filters` only after the server says the change applied. A refused or failed request therefore leaves the state on screen as the server last reported it. An unreadable overview shows an error and no controls.
- **The locked floor has no control.** A core rule with `floor: true` renders a "Locked" label and no button. Nothing reads the URL, so no parameter or key can start a change. The server still refuses a floor switch-off with 409 (§20.5.6).
- **Held items show hashes, never names or thumbnails.** The review queue lists hash and rule. A sealed name opens only through `RevealNameDialog` (warning, password, no Copy). Holds marked `adult_hold` are left out unless "Show adult content" reads as on (`GET /settings/content`), and nothing says they exist. An unreadable setting counts as off. The expiry time of a hold is not shown: a relative-time label put shared format code into the Alert and Search chunks.
- **Release, False positive, Confirm, disabling a rule, adding Always allow, removing an exception or override, turning off a core rule or pack and Undo each go through the dialog.** The screen doesn't judge which ones weaken: the server says so in the preview, so Cancel sends nothing for all of them (tested for each button except the CSX-5 entry form, which is the flows' own `OverrideDialog`, tested there).
- **Added rules and Always allow take a plain text query** and the five actions. The structured editor, fixtures and diff view (§20.7 "Editor") are not part of 2a. The text query is checked by the server's preview. The CSX-5 entry uses `OverrideDialog` as is.
- **The change builders are typed literals in `screens/ops.ts`,** not imports of `flows/changes.ts`, and the flow module loads with the first change. Imported statically, those modules were placed in this screen's chunk, so every dialog a later slice loads from another screen ("Block this…" in Search) would have pulled in the whole Filters screen. The shapes match `flows/changes.ts` and are typed against the same `Change`.
- **The registry entry is as small as it can be** (id, group, title, body loader through `body.ts`). There is no `about` and no `iconLoad`: each is a lazy import whose preload list lands in the registry chunk, which Alert and Search share. This departs from the brief's "purpose line in the lazy about.ts pattern": a hand-built screen's purpose is its body's heading line, as for Integrations and Security, and the Settings filter matches the title. The navigation shows the gear. The runner can overrule this and add them back at about 60–130 B on every first view.

- **A failed reload after an apply shows a "may be out of date" banner** with Retry, because the old state could now show a rule as on that the server turned off. Adult holds and the per-rule decision counts (which include the adult-only rules) are hidden while 18+ is off, and a page holding only adult holds reads on to the next page instead of saying nothing is waiting.
