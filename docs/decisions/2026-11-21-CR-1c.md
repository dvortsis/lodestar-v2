# CR-1c decisions

Lookup slots sized to the intensity preset, behind `dht.preset_slots` (env `LODESTAR_DHT_PRESET_SLOTS`), off by default. Build-plan §0.5 "Path to 100", step 5; `docs/decisions/2026-11-20-path-to-100.md`.

**CR-1c failed its CR-SIM screen** (below), so it isn't a CR-AB-LC candidate unless the owner says so. The runner is asking the owner whether a change that raises slots needs stored per slot-second to rise, or whether per query (politeness) plus the memory bound are the right conditions. Nothing here assumes the answer.

## The caps on concurrent peer lookups today
From the pool to the wire, with the switch off. Rates and outstanding caps are Low / Balanced / Aggressive.

| Cap | Where | Value | Binds? |
|---|---|---|---|
| Pool lookups in flight | `PoolConfig::max_lookups` | 256 | No: above the actor's 32 |
| Per-finder permits (CR-ADM, `dht.coordinated_admission`) | the pool's `Semaphore(finder_capacity)` | 32 | Together with the actor's 32, which it mirrors |
| Owned requests, running plus queued | actor `MAX_GET_PEERS` (`PEER_REQUEST_CAPACITY`) | 32 | **Yes, at every preset**: CR-0's `L` = 30.3 of 32 |
| Maintenance lookups (refresh, explore, rejoin) | actor `MAX_LOOKUPS` | 16 | No: separate from peer requests |
| Queries awaiting an answer | `Intensity::max_outstanding` | 256 / 1,024 / 4,096 | No: 32 slots × `ALPHA` 3 × 2 families = 192 at most |
| Query rate | `Intensity::queries_per_sec` | 50 / 200 / 1,000 | Only at Low. 32 slots at CR-0's 59 queries per 24 s lookup ask about 79 a second; Balanced used 76 of its 200 |
| Finder channels | main 1,024; worker 32; the node's command channel 64 | | No: they hold the slots' bursts |

So the 32 slots bind at Balanced and Aggressive. At Low, the 50 a second binds about as soon.

## What changes with the switch on
- **The slots are the start preset's count:** Low **32**, Balanced **80**, Aggressive **256** (`Intensity::peer_slots`). The actor runs or queues that many owned requests (`Actor::peer_slots`, used where `MAX_GET_PEERS` was), and the pool's per-finder permits (`finder_capacity`) are the same number, so a permit is always a slot. Two other caps follow, so a burst of grants isn't refused:
  - the worker's finder channel: the pool `try_send`s to it. It's 256 with the switch on, because a worker's node takes its count from the intensity its `Assign` gives, not from the worker's file;
  - the node's command channel: 32 plus the slots, so 64 when off, as before.
- **The formula:** `S = ceil(rate · W / q_all)`, the slots at which the preset's query rate binds by Little's law.
  - Query use is `(S / W) · q_all`, so the rate binds once `S ≥ rate · W / q_all`.
  - `W` = 16.2 s and `q_all` = 43 (every query per admitted lookup) come from CR-LOOKUP-END's screen with it on. The owner paired this slice with that switch (A1), and CR-AB-ADM hasn't run yet.
  - The raw counts are 19 / 76 / 377. They're clamped to at least 32 (never fewer than with the switch off) and at most 256 (the pool's `max_lookups`), then rounded up to a multiple of 16.
  - **Cross-check against CR-0's live ledger:** `q_all` = 76 / 1.286 ≈ 59 and `W` ≈ 24 s give 81 at Balanced.
  - Each count × `ALPHA` × 2 address families (an owned request runs a leg per family) is within three quarters of its preset's outstanding cap: 192 of 256, 480 of 1,024 and 1,536 of 4,096 (tested). The actor enforces the cap either way.
- **At Aggressive the pool's `max_lookups` binds with the slots,** both at 256. Raising it isn't this slice's to decide (the runner, at launch).
- **A new slot count needs a restart.** The count is fixed for the node's run, from the intensity it starts with, as the pool's `max_sockets` already is. The rate and the outstanding cap still follow a live intensity change at once.
  - **Why:** the pool builds its per-finder semaphore once. The actor sees only permits, never the semaphore's size, so it can't resize it safely. And a pool larger than the actor's count would see refusals, each a 1 s hold.
  - **A live change down keeps the network bound:** from Aggressive to Low with 256 slots, no query goes out while Low's 256 outstanding are reached, the 768 in flight only drain, and the rate is Low's at once (`a_live_change_to_low_holds_lows_caps_with_256_slots`).
  - This is the runner's call (§2.26), confirmed at launch.
- **`dht_lookup_slots_capacity`** reports the count in use, so 32 with the switch off (`docs/metrics.md`). No new series: CR-COL-5's A1 check already reads the maximum of `dht_lookup_slots_occupied` against 32.

## What doesn't change, either way
The query rate, the outstanding cap, the 25 s `LOOKUP_DEADLINE`, the 64-query `MAX_PEER_QUERIES`, `ALPHA`, the per-IP guards, the T1 hint caps, and the 16 maintenance lookups. With the switch off, every count is 32 (or 64 for the command channel) as before: the dht suite passes unchanged, and every CR-SIM golden is byte-identical.

## Memory
The slots' state is bounded by the slot count. Per slot, the worst case is about **38 KiB**. This is an **analytic upper bound**, not a heap measurement: each structure's `size_of` times its cap, with hash-map entries counted twice for spare room (`the_slot_state_at_aggressive_is_bounded`, which fails if the structures grow past it). It counts:
- the request record;
- 64 values and their sources;
- per-source vouching: a source per query, 4 values each;
- per address family, a lookup with its 64 candidates, its own values, and 3 queries in flight;
- the queue entry.

At Aggressive's 256 slots that's at most **9.5 MiB**, against 1.2 MiB at 32. Low and Balanced are 1.2 and 3.0 MiB. Nothing new is allocated: the queue and maps are the ones there were, bounded by the count.

## WK-4 fix: ships regardless of the switch
WK-4's review item. At start, a sub-range shard keeps saved ids only if each takes its own BEP 42 slot (`sharded_ids`). The address vote (`on_external_ip`) had no such check. Ids kept without a saved public address, valid for the address the vote finds and in the shard, but two in one slot, stayed as they were. Now `fits` also rejects a repeated slot when there's a shard, and the vote re-ids them, one per slot. Without a shard, ids share slots by design (16 ids over 8 slots), and nothing changes.

It's a correctness fix, so it isn't behind the switch. Tested by `the_vote_re_ids_kept_ids_that_repeat_a_slot` (it fails with the check removed) and `without_a_shard_ids_may_share_a_slot`.

## Tests
Actor tests on tokio's paused clock (`node/preset_slots_tests.rs`):
- the documented counts and their bounds;
- per preset, on and off: exactly the count admitted and running (more than 32 at Balanced and Aggressive), the next refused, and the count unchanged through every intensity change;
- with 80 running, every permit back exactly once on each end: values, closest set, cancel, the deadline, and shutdown, running and queued alike;
- at every preset with the slots full of unanswered requests: no tick past the rate (a full bucket, then the rate) or the outstanding cap, no request past 64 queries or its deadline;
- the 64-query cap reached beside 79 other requests;
- the live change from Aggressive to Low;
- the memory bound.

Condition waits only, no fixed sleeps. Config tests cover the variable, the file key, refusal of non-booleans, and `finder_capacity` per preset.

## Screen (CR-SIM): not kept on the screen's rule
The calibrated `live-lookup` scenario, 8 seeds (`SCREEN_SEEDS`), Balanced, `dht.lookup_end` on in both arms, `dht.preset_slots` off against on. Run it with `cargo test -p lodestar-crawler-sim --test sim preset_slots_screen -- --ignored --nocapture`.

| 8-seed mean | Off | On | Change |
|---|---|---|---|
| Stored per minute | 18.64 | 39.19 | +110 % |
| Stored per slot-second | 0.0101 | 0.0085 | −16 % |
| Stored per DHT query | 0.0038 | 0.0048 | +26 % |
| `L` (slots occupied) | 30.7 of 32 | 76.8 of 80 | |
| Admitted lookups a second | 1.89 | 4.59 | +142 % |
| `W` (`W_little`) | 16.2 s | 16.7 s | none |
| `q` (lookup queries per lookup) | 19.4 | 19.8 | none |
| `q_all` | 43.0 | 29.7 | −31 % |
| `y` | 0.164 | 0.142 | −13 % |
| Lookups ending at the deadline | 56 % | 59 % | |
| Lookups ending on enough values | 32 % | 30 % | |

- **Stored per minute rose on every seed** (+17.7 to +23.1 a minute; sign test `Better`), and so did stored per query (8/8).
- **Stored per slot-second fell on every seed** (−16 %), so one of the screen's two keep conditions (build-plan §0.5) fails. **By the rule as written, CR-1c failed the screen and isn't kept.** The runner left the rule as it is after seeing the data, and put the question above to the owner.
- **The reading:** with more slots, `W` and `q` per lookup don't change, but each extra lookup is worth a little less: `y` falls, as the extra slots reach the backlog's lower-value hashes.
- **Memory, for the owner to weigh beside this:** at most about 38 KiB per slot, so 3.0 MiB at Balanced's 80 slots and 9.5 MiB at Aggressive's 256, against 1.2 MiB at 32 ([Memory](#memory)).
- **Neither cap binds yet:** about 136 queries a second (4.59 × 29.7) of Balanced's 200, and the 80 slots are 96 % full.
- **A screen never replaces a live run.**
