# X-consent-gate-052 decisions (PR pending)

Spec: `docs/plan/2026-11-06-v052-feature-manifest.md` §3.4 and Q4 (runner's call). Until SRC-15b ships owner-approved consent text, `PATCH /sources/{id}` refuses to turn on a source that needs consent. This tightens §18.7's enabling rule for v0.5.2. It loosens nothing.

- **The gate is by class, and a stored acknowledgement doesn't open it.** `Control::update_source` refuses `enabled: true` for any source whose class is turned on by accepting a consent text (`consent::needs_ack`: External, Restricted, Overlay). It refuses whatever the request names: a correct `consent` and `consent_version`, the password, or an acknowledgement already in the store, which makes `consent::need` None. The plan's wording is "whose `consent::need` isn't None". Taken literally, that would let through a source whose acknowledgement a nightly build or a hand edit had already stored. Every draft text is unapproved, so an old acknowledgement of one isn't consent either. The class rule covers every case the literal rule refuses, plus that one.
  - **Account** sources still need their credentials (`CredentialsRequired`, unchanged). Once those are stored they can be turned on, because Account has no consent text (`text_version` 0, nothing acknowledged).
  - **None** sources (the Sonarr/Radarr webhooks) are unchanged: still opt-in and turned on through the API (Q4).
  - In this build that means the torrent cache can't be turned on. Internet Archive and Sukebei aren't registered.
- **Where the PATCH check runs.** It's the first check in the enable path, inside the store-locked closure and ahead of the purge check and `consent::need_in`. A refused request writes nothing: no state, no acknowledgement, no priority, no settings. Disabling and other changes work as before. The rule is one function, `control::consent_text_approved(class)`. SRC-15b changes that function only for the classes whose approved text it ships, and the acknowledgement path below it then applies again unchanged.
- **The error reuses `SourceError::Invalid { field: "enabled", .. }`.** It's the same shape as the existing "a purge didn't finish" refusal, so the API answers `400 invalid_setting` with `field: "enabled"` and the message "The setting wasn't saved: this source asks for your consent before it's turned on, and this version of Lodestar can't show you an approved consent text yet, so it stays off. It can be turned on in a later version." There's no new error code, so `crates/api/src/ops.rs` and `crates/lodestar/src/ops.rs` are untouched, as the slice notes allow (only `crates/lodestar/src/ops/tests.rs` changes). The text is `control::CONSENT_GATE_REASON`. It names no address and no version.
- **The start path is gated too (runner, 2026-11-06).** No tagged release can have a consent-class source enabled, because v0.5.1 has no sources table. The nightly image (`ghcr.io/dvortsis/lodestar-v2:nightly`, built from `main`) can: a nightly user who acknowledged the torrent cache through `PATCH` before this gate would otherwise keep it running after upgrading, and so would a backup restored from such a build. The gate exists so that no consent-class source runs before approved text ships, so the runner put the start in this slice rather than a follow-up.
  - `control::switch_off_unapproved` runs at every start, ahead of `prepare`'s existing condition check. It switches off any enabled source whose class isn't `consent_text_approved`, and logs `pipeline.source_state_changed` with the plugin and `disabled`. It leaves the stored acknowledgement alone, so once SRC-15b ships the approved text, `consent::need_in` decides whether that record still covers what's shown.
  - The log event carries no reason field. Adding one, or a new event, would touch `crates/pipeline/src/log_events.rs`, the logs golden catalogue and the web logging messages, none of which this slice owns. The existing event already names the source and its new state.
  - `crates/pipeline/src/lib.rs` (WK-0 owns it) gets only that one call line. The runner recorded it as a shared one-line edit: whichever PR merges second brings `main` in.
- **One code shared with the purge refusal.** A client can tell this refusal from "a purge didn't finish" only by its message, because both are `invalid_setting` on `enabled`. That's acceptable while no screen offers the toggle. A distinct code (say `consent_unavailable`) would need a new `OpsError` mapping in files this slice doesn't own, and SRC-15b removes the refusal anyway.
- **Tests.**
  - `crates/pipeline/tests/control.rs`:
    - The test that used to accept Restricted and External acknowledgements now checks the refusal. It covers every class that needs an acknowledgement, every combination of class, version and password, a refusal bundled with a priority change (nothing saved), a stored current acknowledgement (still refused), disabling a gated source an earlier build left on, and a restart where neither source runs.
    - The restart test now also checks that a current Restricted or External acknowledgement doesn't keep a source on (the record is kept), and that an Account source with credentials stays on.
  - `crates/lodestar/src/ops/tests.rs` (added to `owns` by the runner). Three tests drove the acknowledgement flow through the real router. They now assert the refusal and keep their other parts; none was deleted.
    - `no_class_can_be_enabled_past_its_condition`: External, Restricted and Overlay give `400 invalid_setting` on `enabled` for every request, and no consent record is written. The settings-import and Account parts are unchanged. A wrong password is still `401` first.
    - `a_restart_honours_consent_and_a_new_text_asks_again` became `a_restart_ignores_a_stored_acknowledgement_and_a_new_text_asks_again`. Records a nightly could have stored are seeded. At the next start neither source runs, the records are kept, and `PATCH` is still refused. The "plugin moved to a new host asks again" part is unchanged.
    - `a_config_written_through_the_api_turns_the_cache_off_until_acknowledged` became `a_config_written_through_the_api_applies_at_the_next_start_and_the_cache_stays_off`. The config checks are unchanged. Enabling is refused without quoting an address. A cache an earlier build turned on is off after the start, and the moved list still asks for a new acknowledgement.
  - `crates/lodestar/tests/consent_gate.rs` runs the real binary. The torrent cache is refused with the exact `GET /sources` acknowledgement, with the password and alongside a priority change, and nothing is saved. The webhooks source still turns on and runs at the next start. A cache that an earlier build turned on with a current record is switched off at the start before it runs, the log says so, and the record is kept.
  - SRC-15b brings back the acceptance assertions from these tests' history for the classes it approves.
- **Follow-up for whoever owns `crates/api/src/dto/ops.rs`:** the `consent_required` and `SourcePatch.consent` descriptions in the OpenAPI document still describe the acknowledgement flow, which this build refuses. They're accurate again once SRC-15b lands, so this slice leaves them alone.
