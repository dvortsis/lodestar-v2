# X-consent-gate-052 decisions (PR pending)

Spec: `docs/plan/2026-11-06-v052-feature-manifest.md` §3.4 and Q4 (runner's call). Until SRC-15b ships owner-approved consent text, `PATCH /sources/{id}` refuses to turn on a source that needs consent. This tightens §18.7's enabling rule for v0.5.2. It loosens nothing.

- **The gate is by class, and a stored acknowledgement doesn't open it.** `Control::update_source` refuses `enabled: true` for any source whose class is turned on by accepting a consent text (`consent::needs_ack`: External, Restricted, Overlay). It refuses whatever the request names: a correct `consent` and `consent_version`, the password, or an acknowledgement already in the store, which makes `consent::need` None. The plan's wording is "whose `consent::need` isn't None". Taken literally, that would let through a source whose acknowledgement a dev build, a hand edit or an import had already stored. Every draft text is unapproved, so an old acknowledgement of one isn't consent either. The class rule covers every case the literal rule refuses, plus that one.
  - **Account** sources still need their credentials (`CredentialsRequired`, unchanged). Once those are stored they can be turned on, because Account has no consent text (`text_version` 0, nothing acknowledged).
  - **None** sources (the Sonarr/Radarr webhooks) are unchanged: still opt-in and turned on through the API (Q4).
  - In this build that means the torrent cache can't be turned on. Internet Archive and Sukebei aren't registered.
- **Where it runs.** It's the first check in the enable path, inside the store-locked closure and ahead of the purge check and `consent::need_in`. A refused request writes nothing: no state, no acknowledgement, no priority, no settings. Disabling and other changes work as before. The rule is one function, `control::consent_text_approved(class)`. SRC-15b changes that function only for the classes whose approved text it ships, and the acknowledgement path below it then applies again unchanged.
- **The error reuses `SourceError::Invalid { field: "enabled", .. }`.** It's the same shape as the existing "a purge didn't finish" refusal, so the API answers `400 invalid_setting` with `field: "enabled"` and the message "The setting wasn't saved: this source asks for your consent before it's turned on, and this version of Lodestar can't show you an approved consent text yet, so it stays off. It can be turned on in a later version." There's no new error code, so `crates/api/src/ops.rs` and `crates/lodestar/src/ops.rs` are untouched, as the slice notes allow. The text is `control::CONSENT_GATE_REASON`. It names no address and no version.
- **Not gated here: the start path.** `Pipeline::start_with` (`crates/pipeline/src/lib.rs`, outside this slice's `owns`) still runs a source the store has as enabled with a current acknowledgement. No released build can have stored one: v0.5.1 has no sources table, and v0.5.2 can't write one past this gate. The spec scopes the gate to `PATCH /sources/{id}`. Gating the start as well, for defence in depth on dev-build stores, is a possible follow-up for the runner.
- **Tests.**
  - `crates/pipeline/tests/control.rs`: the test that used to accept Restricted and External acknowledgements now checks the refusal. It covers every class that needs an acknowledgement, every combination of class, version and password, a refusal bundled with a priority change (nothing saved), a stored current acknowledgement (still refused), and a restart where neither source runs.
  - SRC-15b brings back the acceptance assertions from that test's history for the classes it approves.
  - `crates/lodestar/tests/consent_gate.rs` runs the real binary. The torrent cache is refused with the exact `GET /sources` acknowledgement, with the password and alongside a priority change, and nothing is saved. The webhooks source still turns on and runs at the next start, while the cache stays off and doesn't run.
- **Follow-up for whoever owns `crates/api/src/dto/ops.rs`:** the `consent_required` and `SourcePatch.consent` descriptions in the OpenAPI document still describe the acknowledgement flow, which this build refuses. They're accurate again once SRC-15b lands, so this slice leaves them alone.
