# CR-1b decisions (256-prefix lookup targets)

The reversible 256-prefix target experiment (`docs/plan/dht-crawler-implementation-plan-2026-10-25.md` §2 and §7; build plan §0.5, candidate 5), behind its own switch, off by default. It changes which routing targets the sampler draws, nothing else. Caps, timeouts and rates are untouched: the BEP 51 intervals and the 60 s floor, the query rate and its 50% sample share, the outstanding cap and its maintenance fifth, `LOW_FRONTIER` (64, the refill watermark the plan keeps), `MAX_LOOKUPS`, and the sampler's 20k frontier and 200k states. No crawler table, index or cache memory changes.

## The switch
- **`dht.target_prefixes`, a bool, off by default.** It's set in `config.toml` (`[dht] target_prefixes = true`) or with `LODESTAR_DHT_TARGET_PREFIXES=true`, and read at start. A bad value is a config error (`target_prefixes_is_off_unless_asked_for`). It isn't in the Settings UI; like the other crawler candidates it needs a restart.
- **Off is today's behaviour exactly; that's the plan's "random rollback".** `Actor::prefixes` is `None`, so no cursor is allocated, and `routing_target` makes the same single uniform 20-byte draw from the actor's RNG at the same two places as before. Proof: `switch_off_draws_each_target_uniformly_as_before` replays the RNG and checks the sample target sent on the wire, and the four CR-SIM goldens are byte-identical (unchanged by this PR). The new counters with the switch off are either always-counting (`dht_target_novel_nodes_total`, `dht_sample_sent_total`), which no golden prints, or stay 0.

## What it changes (`crates/dht/src/node/prefixes.rs`, `actor.rs`)
- **Two targets, both "random region" draws in `sample_tick`:** the `sample_infohashes` target, and the exploration `find_node` the sampler starts per family when its frontier is below 64. Both steer which routing contacts come back (BEP 51 targets don't choose the sampled hashes). Peer lookups, scrapes, bucket refreshes and the self-lookup keep their targets.
- **A target is the cursor's prefix byte plus 19 random bytes** from the actor's RNG.
- **Independent cursors:** one per address family and per kind (`explore`, `sample`), so sampling's much higher rate doesn't make the exploration sweep look random, and one family's sends don't move another's.
- **A cursor moves only when its query goes out.** A sample cursor moves when its `sample_infohashes` is sent; an explore cursor on its lookup's first `find_node` send, whenever that happens (`Lookup::prefix_pending`, one count per lookup). A lookup throttled on its first drive moves the cursor when a later drive sends. A throttled or refused sample, an exploration lookup refused at `MAX_LOOKUPS` or with no usable candidate (an empty or unusable table), the pause, the restart suppression and sampler saturation (all of which return before a target is drawn or sent) leave it where it was, so no prefix is skipped. Wrap after position 255 counts a cycle.
- **Refinement: bit-reversed order.** A pass visits the prefixes as 0, 128, 64, 192, 32, … (the position's bits reversed), not 0, 1, 2, …. Every prefix is still used once per pass. Consecutive targets then always land in opposite halves of the keyspace, instead of in neighbouring prefixes whose closest nodes overlap. The plan doesn't fix an order. This was chosen **after** the first screen of the plain sequential order, which cost about 6% of new contacts (table below); the mechanism holds outside the sim, but the runner should read it as a choice informed by the screen, on the same seeds, not as an independent one. The order is now fixed: the live A/B runs it as predeclared, with no further change.
- **No coverage claim.** A cycle is a count of passes, not evidence that the keyspace was covered.

## Attribution
- **Routing novelty goes to the target.** `dht_target_novel_nodes_total{kind}` counts contacts in a reply that entered the sampler's frontier as new (`Sampler::offer` now returns whether it queued the node), by the kind of target the query carried: `sample` for a `sample_infohashes` reply, `explore` for a reply to an exploration lookup (marked by `Lookup::explore`). Pings, peer lookups and refreshes aren't attributed. It counts with the switch off too, so both arms of the A/B have it.
- **Hashes go to the responder's call.** That's the existing counting: new sample hashes per call is `dht_harvested_total{strategy="sample"}` over `dht_sample_sent_total`. The latter existed as a counter but wasn't exported; this slice exports it.
- `dht_target_prefix_queries_total{kind}` and `dht_target_prefix_cycles_total` show the switch working; they stay 0 off. No series has an infohash, endpoint or prefix label (`docs/metrics.md`, "Target prefixes").

## CR-SIM screen (off against on, `SCREEN_SEEDS` 1–8)
`cargo test -p lodestar-crawler-sim --test sim target_prefixes_screen -- --ignored --nocapture`. Stored is steady stored per minute after warmup (the primary metric); "spread" is the off arm's range across the eight seeds, the noise floor. New hashes are `harvested_sample` per run (10 simulated minutes); novel contacts are both kinds of `target_novel_nodes`. Means over the eight seeds. The screen ran twice with identical output apart from wall time (94 s each).

**Adopted order (bit-reversed):**

| Scenario | Stored off → on | Change | Off spread | Sign | New hashes off → on | Sign | Novel sample off → on | Novel explore off → on | Samples sent | Hashes/call | Cycles |
|---|---|---|---|---|---|---|---|---|---|---|---|
| `healthy` | 76.0 → 76.2 | +0.2% | 10.9% | Inconclusive | 17,951 → 17,992 (+0.2%) | Inconclusive | 1,491 → 1,505 | 208 → 258 | 3,345 → 3,356 | 5.37 → 5.36 | 15.0 |
| `high-latency` (H1) | 33.1 → 32.7 | −1.0% | 15.1% | Inconclusive | 15,240 → 15,269 (+0.2%) | Inconclusive | 1,386 → 1,364 | 288 → 329 | 2,862 → 2,871 | 5.33 → 5.32 | 12.2 |
| `admission-pressure` (H2) | 29.8 → 31.2 | +4.9% | 19.7% | Inconclusive | 131,320 → 131,217 (−0.1%) | Inconclusive | 6,733 → 6,688 | 817 → 929 | 11,661 → 11,648 | 11.26 → 11.26 | 47.1 |

**First screen, plain sequential order (0, 1, 2, …), not adopted** (run before the review fix that stopped an unsent exploration lookup moving its cursor, so its explore numbers are only indicative):

| Scenario | Stored change | New hashes change | Sign (hashes) | Novel contacts change | Novel explore off → on |
|---|---|---|---|---|---|
| `healthy` | −1.0% | −0.1% | Inconclusive | −6.6% | 208 → 133 |
| `high-latency` | −2.8% | −0.4% | Inconclusive | −5.8% | 288 → 222 |
| `admission-pressure` | −1.7% | −1.0% | **Worse** (8/8) | −6.1% | 817 → 473 |

- **Prefixes don't beat the noise floor in any scenario.** Every stored change is far inside its spread and no sign test agrees on all eight seeds. Discovery is flat: new hashes within 0.2%, hashes per call unchanged. The bit-reversed sweep adds 14–24% exploration novelty, but exploration brings only 12–20% of new contacts, too few to move anything else.
- **Politeness held in both arms:** BEP 51 re-asks before the interval (`sample_early`) were 0 in every run; the scripted network's own per-node rate-limit drops were 0 except in `high-latency`, where they were 3 off and 4 on summed over eight seeds (a node's 20 qps limit; noise at that count, not a cap of ours). `target_prefixes_sweep_deterministically` checks the query-rate bound and `sample_early` on every CI run.
- **Why the sequential order lost, as the sim shows it:** about 8 of CR-SIM's 2,000 nodes share each prefix, and its routing answers from a ±16-rank window, so neighbouring prefixes return largely the same nodes, which are already queued or cooling. The live DHT has orders of magnitude more nodes per prefix, so the sim overstates that overlap, and it equally can't show any coverage benefit a sweep might have there.
- **What this doesn't show.** The sim's limits apply (CR-SIM README): IPv4 only (so one family's cursors), uniform node ids, approximated routing, no churn, and stored meaning "reached the writer". This is a screen; the live A/B decides.

## Tests
- `crates/dht/src/node/prefixes.rs`: each pass uses every prefix once in bit-reversed order, wraps and counts two cycles in 512 draws; families and kinds keep independent cursors; reading a target doesn't move a cursor.
- `crates/dht/src/node/prefix_tests.rs`, against the real actor: `switch_off_draws_each_target_uniformly_as_before`; `switch_on_walks_the_prefixes_and_holds_on_throttle_and_pause` (positions 0–2 sent, an exploration lookup with an empty table moves nothing, a throttled tick sends nothing and moves nothing, a paused `maintain` moves neither cursor, and sampling resumes at position 3); `a_cursor_wraps_after_prefix_255_and_counts_a_cycle`; `new_contacts_are_counted_by_the_target_that_brought_them` (a sample reply's new contacts count, a ping's don't, a repeat isn't new); `the_exploration_lookup_is_marked_and_its_contacts_count_as_explore`; `the_explore_cursor_moves_only_when_its_lookup_sends`; `a_throttled_exploration_lookup_moves_its_cursor_when_it_sends`. Blocking reads use a 10 s socket deadline; no sleeps.
- `crates/lodestar/src/config.rs`: `target_prefixes_is_off_unless_asked_for`. `crates/lodestar/src/metrics.rs`: `target_prefix_families_render_each_kind_with_its_own_value`.
- CR-SIM: `target_prefixes_sweep_deterministically` (runs in CI: the off arm counts no prefix queries, every on-arm sample carries a prefix, cycles complete, both arms count novelty, the rate and interval bounds hold, the same seed is byte-identical), and the ignored `target_prefixes_screen`.

## What the live A/B needs from the owner
- **A 6 h ABBA run with at least two repetitions** on the experiment host (build plan §0.5), switching only `LODESTAR_DHT_TARGET_PREFIXES` between arms. Measure it separately from CR-1a and from any cooldown-floor change (plan §7): the other crawler switches stay at the same values in both arms.
- **Predeclare before the run:** primary metric verified searchable per minute (`searchable_new_total{origin="network"}`); discovery metrics `dht_harvested_total{strategy="sample"}` per hour, that over `dht_sample_sent_total`, and `dht_target_novel_nodes_total`; guardrails `dht_sample_deferred_total`, `dht_throttled_total`, `dht_timeouts_total` and RSS. Given this screen, the expected outcome is "inconclusive, stays off"; a threshold from the CR-0 baseline's variance should be set before the run, as the protocol requires.
- **Check it's on:** `dht_target_prefix_queries_total{kind="sample"}` should equal `dht_sample_sent_total`'s increase in the "on" arm, and stay 0 in the "off" arm.
- Nothing else: no schema, table or memory change, and the switch is read at start.

## Recorded for the runner
- **Refinements to flag to the owner (§2.19):** the bit-reversed visiting order (above); prefixes applied to both the sample and the exploration target, with a cursor per kind as well as per family (the plan says "independent family cursors" and doesn't list the targets); `dht_sample_sent_total` newly exported.
- **Shared files outside the slice's own:** `crates/dht/tests/{harvest,network,scrape}.rs` gain `target_prefixes: false` in their `Config` literals; `Sampler::offer` now returns a bool that existing callers ignore.
