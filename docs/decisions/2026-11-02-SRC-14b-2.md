# SRC-14b-2 decisions (purge job and snapshot scrub)

Slice SRC-14b-2: the second half of SRC-14b, after 14b-1 (#399, egress hardening). It covers the brief's steps 1 and 2 and SRC-14's must 5: purging a source is a tracked job that leaves no trace, rollback snapshots included. Architecture §18.1 (Purged), §18.7, §18.8, §9 (`/jobs`) and §12 (snapshots and rollback). It closes the handoffs that `2026-11-02-SRC-1.md` (in-memory queue keys) and `2026-11-02-SRC-14a.md` (the final Purged write) left here.

## The purge job: `POST /sources/{id}/purge`
- **It runs over `/jobs`** (`kind: purge`), with progress, pause, cancel and a `purge` block:
  - `stage`: `stopping`, `removing`, `finishing`, `purged`;
  - `keys_dropped`, `unverified_deleted`, `torrents_deleted`, `kept`;
  - `snapshots_scrubbed` and `snapshots_left`.
- **Every count is of rows already committed.** A purge that stops partway (cancelled, failed, a restart) reports exactly what it did. The source stays off, with `purge_pending: true` in `GET /sources`, until a purge run again finishes it.
- **It needs the admin password, every time** (`428 confirm_required`, `401`). It's checked fresh before the source is read. **Refinement for the runner to flag (§2.19):** §10.10.7 asks only for a confirmation dialog for destructive actions. A purge deletes credentials and data for good, so a stolen session mustn't be able to run one. This follows the rule SRC-14a set for egress.
- **One purge per source at a time:** `409 purge_running`.
- `PATCH /sources/{id}` still refuses `purge` (`409 not_editable`), and the message now points to the route.

## What a purge does, in order
1. **Begin** (`Store::begin_source_purge`): sets the source Disabled and records `sources.purging.<plugin>` (its start time), in one transaction. From here nothing the source finds is written (below).
2. **Stop** (`Monitor::stop_source`):
   - signals the plugin's own stop (new: each plugin now has one, which the pipeline's plugin shutdown also sets) and waits up to the 15 s plugin stop timeout, then aborts it;
   - drops the source's keys from the fetch pool (`PoolHandle::drop_source`). A key others found too keeps them: it loses the bit and passes to the lowest remaining finder. A dropped key ends as `Loss::Evicted`, which releases its coordinator lease.
   - Its egress monitor ends with it.
3. **Remove**, in steps of at most 4,096 rows: SRC-1's `Store::purge_source`, unchanged. A pause or cancel takes effect between steps.
4. **Finish** (`Store::finish_source_purge`), in one transaction:
   - sets the source Purged;
   - drops its consent record, credentials, egress, schedule and agents (what was written meanwhile goes too, as SRC-14a planned);
   - clears the purge under way;
   - records `sources.purged.<plugin>` = now.
5. **Scrub the snapshots** (below), as the hourly pass does. A snapshot that can't be written now is counted in `snapshots_left`.

- **Running it again starts over from the first step.** Every step is idempotent: what's already deleted is gone, and the rest is found again.
- **Enabling a source while its purge is under way is refused:** `400 invalid_setting` on `enabled`, and `Error::Invalid` from `Store::enable_source` itself. Saving credentials or settings stays allowed; the final write drops them.
- Tested: `a_purge_stops_the_source_survives_a_crash_and_finishes_when_run_again` (pipeline) and `purging_a_source_is_a_job` (API).
  - The pipeline test covers the password, the plugin stopping at once, and a crash after Begin: the source is off, the purge is recorded, the credentials are still there, it's shown as pending after a restart and can't be enabled. Run again, it finishes, and the source can be enabled afresh.
  - The API test covers the password, `404`, `409 purge_running`, a cancel that reports only committed steps, and a rerun that finishes.

## A stopped source's fetches aren't written (runner, option 1)
- **The gap:** `put_unverified` and `put_claims` already refuse a disabled or purged source (SRC-1's `check_running`), but stored torrents didn't. A fetch already past the pool when the purge started (in prepare, or the writer's batch) could commit a torrent, or add the purged bit to one, after `purge_source` had passed it. A torrent stored after the final write would have stayed for good.
- **The fix, in the write's own transaction:** `Store::write` reads the bitmask of Disabled and Purged sources once per batch (`sources::stopped_mask`: one cached query over at most 64 rows, about 2 µs measured, against about 300 µs per stored torrent at zstd 19; no per-row query). Because it runs inside the transaction, a purge (which disables first) and a batch can't interleave.
  - **Touches** never add a stopped source's bits. A touch only stopped sources made adds nothing: no bit, and no `last_seen_at`.
  - **A fetched torrent whose finding source is stopped** is stored under the lowest live source that also reported it in the batch (the DHT included), without the stopped bit.
  - **With no live finder left, it's `Inserted::Refused`:** nothing is written.
  - **`Store::promote`** (an unverified item's promotion) applies the same mask:
    - it adds no stopped bit;
    - it carries no stopped source's claims;
    - a kept torrent's `first_source` is a live finder;
    - with no live finder left it returns `Gone`, and the torrent goes through the usual insert, which refuses it.
- **`Inserted::Refused` only comes from `WriteBatch::prepared`** (the pipeline's fetches). `Store::insert` and `WriteBatch::torrents` (imports) never return it, so `Inserted::id()` keeps its signature. It panics on `Refused`, and the writer reads `stored()`.
- **Accounting:**
  - the writer treats a refused key as never stored: it isn't put in the have-filter or the hot columns;
  - its lease ends as `Loss::Evicted`, as a purge's dropped pool keys do: a documented reuse, with no new persisted loss kind;
  - the gate counts it as `metadata_excluded_total{reason="source_stopped"}`, a new label on an existing series (`docs/metrics.md`), never as a filter drop;
  - a live source finding the key later fetches and stores it, once the fetch pool's memory of recent fetches (`PoolConfig::recent`) has let it go, or after a restart. **Known gap (fresh review, left):** until then a live source's sighting is passed over as a duplicate. It matters only for keys in flight when a source is turned off, and forgetting them would need a writer-to-pool command.
- Tested (`crates/store/tests/source_stop.rs`):
  - a fetch written after its source turns Disabled is refused, and is stored as new once the source runs again;
  - a torrent the DHT also found keeps everything except the purged bit, whether the stopped source or the DHT fetched it, and a stopped source's rediscovery adds nothing;
  - a batch that lands during the purge's steps and one after its end leave no torrent with the purged bit or `first_source`.
- **Not covered: imports** (`WriteBatch::torrents`, the bitmagnet importer) aren't refused. **Handoff to the importer framework:** an importer that's a source must stop its import before its purge, or refuse while one runs.

## The snapshot scrub (must 5): scrub, not refuse (runner-approved)
- **Why scrub:** refusing a rollback across a purge would block every rollback for 90 days after any purge.
- **The record:** a purge records `sources.purged.<plugin>` (when it ended) in `settings`. It isn't exported (SRC-4's export skips `sources.`). It's dropped once older than the 90-day window plus a day, as the deletion journal's rows are.
- **What's scrubbed:** in every snapshot taken before the purge (its time, less the day's margin `TAKEN_MARGIN`, is at or before the purge's), the source's row is set Purged and its records are dropped: consent, credentials (`sources.secret.<plugin>/…`), egress, schedule and agents, and any purge under way. The purge's own record is added too.
  - Torrents and items the purge deleted are already journalled (`snapshot_deletions`), so the existing pass removes them.
  - The claims and bits on rows others found too stay, until those snapshots expire (SRC-1's accepted limit).
- **A snapshot taken after the purge keeps what was saved since,** such as the source enabled again with new credentials. Tested: `a_snapshot_taken_after_the_purge_keeps_new_credentials`.
- **Runner condition 1 (the restore):** `purge_for_restore` applies every recorded purge to the copy being restored, whatever its time, before it's put in place. A snapshot the hourly pass hasn't reached yet still comes back clean. The cost: a rollback to a snapshot taken after a re-enable loses that source's new credentials, and asks for them again.
- **Runner condition 2 (crash safety):** the scrub is part of `purge_one`'s single transaction (`secure_delete`, WAL, then a TRUNCATE checkpoint).
  - A scrub that stops before its commit leaves the snapshot unchanged and still holding the records, so the next pass finds it.
  - One that committed but stopped before the checkpoint is folded in by the next pass (or the restore's `settle`).
  - Tested: `a_scrub_interrupted_partway_is_done_again_or_folded_in`.
- **Runner condition 3 (the record survives a rollback):** a rollback's copy always takes every purge's record, even one that holds nothing of the source's.
  - The restored store then goes on scrubbing the other snapshots, and a rollback from it is clean too.
  - The source comes back Purged, so enabling it asks for fresh consent and credentials.
- Tested: `a_rollback_across_a_purge_brings_back_no_credentials_or_consent`:
  - restored before any pass: no secret or ack bytes in the file, the record is there, and the state is Purged;
  - the hourly pass then scrubs the snapshot itself;
  - a restore after the pass is clean too.

## From the fresh review
- **The persisted fetch queue leaves out stopped sources' keys** (`save_fetch_queue`, in its transaction, by the same mask). A pool snapshot taken during the plugin's stop, or a key still on its way to the pool, can't outlive the purge in `fetch_queue`. Tested: `a_stopped_sources_queued_keys_arent_saved`.
- **The snapshot pass runs on a connection of its own** (`Store::reopen_args`), so the shared control store (the Sources routes, the credential lookups) isn't held while it rewrites snapshots. Only the final write takes it.
- **One purge per source is checked and started as one step** (`Jobs::start_purge`).
- **A snapshot older than the `sources` table still takes the purge's record,** so a store rolled back to it goes on scrubbing newer snapshots.
- **More tests:** the writer path end to end (`a_stopped_sources_fetch_is_refused_not_filtered`: excluded as `source_stopped`, not filtered, not in the have-filter, its lease ended, nothing stored) and promote's mask (`a_promotion_writes_nothing_of_a_stopped_source`).
- **Left, with reasons:**
  - **A touch from stopped sources only** still reports the torrent's id. The writer counts the sighting (hot `last_seen`, rediscovered), while the row gains nothing. Returning `None` would send the key to be fetched again.
  - **Keys passed to another finder by `drop_source` stay in the purged source's ready queue** until they're served. They're fetched under its weight once; nothing is lost.
  - **`snapshots_scrubbed` and `snapshots_left`** count what the whole pass did and met, not this source alone; their docs say so.
- **Handoff to the Jobs screen (web):** `JobsScreen.svelte`'s `kindName` falls through to "Export" for the new `purge` kind. It needs a label (English and Chinese messages) with SRC-15a's Sources screen, or in a small web PR.

## From the runner's review (#400)
- **Every restore entry point applies recorded purges** (blocking):
  - `lodestar rollback` (`cli/rollback.rs`): `purge_for_restore`, as above;
  - **the update rollback** (`update/journal.rs`: the supervisor's rollback of a failed update, the in-app Roll back and `lodestar rollback --update`): `choose_snapshot` applies every purge the live store records to the snapshot (`snapshots::apply_source_purges`, one transaction, the purge's record included) after settling it and before it's verified and hashed. A snapshot that can't be scrubbed isn't used, so the rollback is refused rather than bring credentials back. Tested: `an_update_rollback_brings_back_nothing_a_purge_removed`.
  - No other path renames a snapshot over the store.
- **A torrent passed to a live finder is stored private** (privacy). Whether a fetch is public comes from all its finders' sightings, the stopped one's included, and the store can't tell which live finder was private. So `commit_live` sets `PRIVATE_SOURCE`, and a touch that a stopped source's sighting is merged into never makes a torrent public. A live public sighting makes it public again through the existing rule. Tested: `a_torrent_passed_to_a_live_finder_is_stored_private`.
- **`snapshots_left` counts every warning of the pass,** as its doc now says.
- **Not done, noted:** Insights still credit `Stage::Stored` to the purged source after its key passes to another finder (`writer.rs`, from the lease). A purge doesn't delete Insights rows anyway, so this is noise in a purged source's history.
