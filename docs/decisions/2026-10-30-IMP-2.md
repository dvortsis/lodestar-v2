# IMP-2 decisions: the Magnetico SQLite adapter

The contract note for the Magnetico adapter (the plan's IMP-03, `docs/plan/2026-10-29-magnetico-bitmagnet-migration.md` §5 "Magnetico SQLite", §9, §10), written before the reader code for the runner's OK. It builds on IMP-1's contracts (`docs/decisions/2026-10-30-IMP-1.md`) and redefines none of them: records go through `Store::commit_import_batch` as `ImportRecord::{Torrent, Candidate, Invalid}`, with IMP-1's quality states, merge rules and counters.

Owned code: `crates/sources-importers/src/magnetico.rs`, its tests and fixtures, one fuzz target and its CI matrix entry.

## Column mapping
Each Magnetico parent row becomes exactly one IMP-1 record. Nothing in a row is ever used as SQL, a path on the filesystem, or a log field.

| Magnetico column | IMP-1 field | Rule |
|---|---|---|
| `torrents.id` | cursor only | Keyset position. Never stored in Lodestar. |
| `torrents.info_hash` | `Prepared.info_hash` / `ImportCandidate.hash` | Must be a **BLOB of exactly 20 bytes** (`typeof = 'blob'`), not all zeros. Anything else (TEXT, hex, 32 bytes, NULL) is `Invalid`, reason `bad_hash`. `hash_v2` is always `None`: Magnetico is v1 only. |
| `torrents.name` | `Prepared.name` / `name_raw`, candidate `name` | Read as **raw bytes** whatever its storage class (`CAST(name AS BLOB)`). See "Untrusted text". |
| `torrents.total_size` | `Prepared.size`, candidate `size` | An INTEGER > 0. NULL, ≤ 0, REAL or TEXT is **missing**, never 0 and never coerced. |
| `torrents.discovered_on` | `source_at` | Unix seconds, INTEGER only. In range `[2008-01-01, batch time + 1 day]`; otherwise `None` with finding `date_out_of_range`. Milliseconds are never guessed. IMP-1 then dates the row from it only when it's positive and not after the batch. |
| `torrents.updated_on` | — | Not imported: IMP-1 has no field for it, and it says when magneticod last scraped, not anything about the torrent. Left for IMP-06. |
| `torrents.n_seeders`, `n_leechers` | — | **Hints only, never swarm truth.** Not imported: swarm observations are IMP-06. Not even selected. |
| `torrents.modified_on` | — | **Ignored.** It has a far-future default, so it says nothing reliable. |
| `files.torrent_id`, `files.id` | — | Join and order only. |
| `files.path` | one `File.path` | Raw bytes (`CAST(path AS BLOB)`), split on `/` into segments. See "Files". |
| `files.size` | `File.size` | An INTEGER ≥ 0. Anything else makes the row malformed. |
| `files.is_readme`, `files.content` | — | **Not imported, never selected.** A source where any `is_readme` is set is counted as one aggregate finding (`readme_not_imported`, a count). Annotations are IMP-06, deferred. |

**Prepared fields Magnetico doesn't have:** `piece_len`, `piece_count` and `info_size` are 0, `raw` and `extra` are `None`. `info_size` 0 is safe under IMP-1's read rule because every record this adapter writes has its own `import_quality` row.

## Quality, privacy and file order
- **Privacy is always `unknown`.** Magnetico stores no private flag, so the adapter never claims public or private. IMP-1's sticky-private merge still applies against other sources.
- **Verification is always `unverified`.** Magnetico once fetched the info dict, but the database keeps no info dict and nothing ties the stored fields to the hash any more. A record is never `verified` because magneticod fetched it (IMP-1 refuses `verified` from an import anyway).
- **Completeness:**
  - `reported_complete` when every file row of the parent was read and well formed, and the file sizes sum to `total_size`;
  - `partial` otherwise, with repair bits: `MISSING_FILES` for a parent with no file rows, `INCONSISTENT_FILES` for a dropped or over-limit row, or sizes that don't sum to `total_size`. `partial` sets `FILES_PARTIAL`, so the existing verified re-fetch picks it up.
- **File order and single-file mode are never claimed.** File ids give a stable iteration order, not the original bencode order. `SINGLE_FILE` is never set, even for one file row whose path equals the name: Magnetico stores single-file torrents that way, but it can't be told apart from a one-file directory.
- **Torrent or candidate:**
  - a valid hash with a name and a size is a `Torrent`;
  - a valid hash missing its name or size (after the rules here) is a `Candidate`, with privacy `unknown` and `source_at`. IMP-1 derives `missing`;
  - an invalid hash is `Invalid`.

## Untrusted text
- **Names and paths are raw bytes,** decoded UTF-8 first. Valid UTF-8 is stored as is.
- **Invalid UTF-8 is decoded lossily, with a flag:** the store's existing `name_raw` (`TextEncoding::UTF8`, the original bytes) is the flag, and finding `name_lossy` / `path_lossy` counts it. The same mechanism `Store::prepare` already uses for non-UTF-8 names, so search, display and later verified upgrades treat it like any other undecodable name. Paths go through `filetree::encode` with the same `path_encoding`.
- **The original bytes are kept exactly, not only hashed.** The brief asks for a hash of the original bytes (IMP-0's `SQL_ASCII` rule). `name_raw` already holds the original bytes whenever they aren't plain UTF-8, so the hash is derivable and no new column is needed. **Runner: please confirm** this satisfies the rule, or name where a separate hash should live (IMP-1 has no column for one).
- No guessed legacy encodings: Magnetico wrote Go strings, so anything not UTF-8 is damage, not GBK or Shift-JIS.

## Files
- **A file row is malformed** when its `path` is NULL or empty, has an empty segment (leading, trailing or doubled `/`), contains a NUL byte, is over `Limits::DEFAULT.max_path_bytes` (4096) or `max_path_depth` (64), or its `size` isn't an INTEGER ≥ 0.
  - A malformed row is dropped, counted in `files_dropped`, and marks its parent `partial` with `INCONSISTENT_FILES`, plus finding `file_malformed`. **It never drops the parent.**
  - `.` and `..` segments are kept as bytes. Paths never touch the filesystem, and the search and UI already treat names as untrusted text.
- **A file row whose parent is missing** (an orphan) is never read: files are read by the batch's parent ids, so orphans are skipped by construction. They're counted once, at inspection, as an aggregate finding (`orphan_files`) when the plan check shows the query is cheap; otherwise not counted. The brief's orphan test asserts they never become records.
- **Over the limits, a record is kept as partial, never silently truncated into a complete one:**
  - more than `max_files` (200,000) file rows, or a parent whose file rows exceed the per-parent budget (8 MiB of path and size bytes): the first rows in id order are kept, the rest dropped and counted, `partial` with `INCONSISTENT_FILES`, finding `files_over_limit`;
  - a name over `max_name_bytes` (4096): no truncation. The record becomes a `Candidate` with its name missing, finding `name_over_limit`;
  - a size sum that overflows `u64`: `partial` with `INCONSISTENT_FILES`.

## Opening the source
- **The path** goes through one validated open function: `magnetico::open(path, &OpenPolicy)`. It refuses, with a fixed reason:
  - anything that isn't a regular file (a directory, device, pipe or socket);
  - a symlink or reparse point whose target is outside the given file's own directory;
  - a UNC path (`\\server\…`, `\\?\UNC\…`) unless `OpenPolicy` lists its root as approved. IMP-4's CLI fills `OpenPolicy`; this slice has no CLI.
  - It opens the canonical path with `SQLITE_OPEN_NOFOLLOW`, then re-checks that the file's identity (device and inode, or the Windows file id) hasn't changed since validation.
- **SQLite flags:** `SQLITE_OPEN_READ_ONLY | NO_MUTEX | NOFOLLOW`, then `PRAGMA query_only=ON`, `trusted_schema=OFF`, `cell_size_check=ON`, `mmap_size=0`, and `SQLITE_DBCONFIG_DEFENSIVE`. Extension loading stays off (rusqlite's `load_extension` feature isn't enabled). **Never `immutable=1`, never a write, never a repair.**
- **Bounds:** `sqlite3_limit` caps `LENGTH` (16 MiB), `SQL_LENGTH` (64 KiB), `COLUMN` (64), `ATTACHED` (0), `EXPR_DEPTH` (100) and `VARIABLE_NUMBER` (1,024). A progress handler interrupts any statement after a per-statement deadline (30 s) or a cancel request. An interrupted statement is the adapter error `statement_timeout` or `cancelled`, never a partial batch.
- **Tables:** only `torrents` and `files`, checked to be ordinary tables in `sqlite_master` (`type = 'table'`, not virtual). FTS tables, views and triggers are never read; they can't fire on reads anyway, and `trusted_schema=OFF` stops any schema function from running.
- **Consistency: a live or inconsistent source is refused** with `source_not_quiescent`, before any read:
  - a non-empty `-wal` sibling, or any `-journal` sibling, refuses it;
  - the message gives the safe step: stop magneticod, or import a consistent copy.
  - At inspection that's an adapter error; on resume the job blocks with IMP-1's `source_unavailable` reason, since IMP-1's reasons are a fixed enum. The adapter's own reason is kept in its findings.
  - **WAL siblings (runner, question C).** magneticod always sets `journal_mode=WAL`, so every real source is a WAL-mode database. Checked on SQLite 3.45: opening one read-only creates an empty `-wal` and a `-shm` beside it and leaves both after close (a read-only connection can't remove them). `nolock=1` and the `unix-none` VFS both refuse to open it. Only `immutable=1` avoids the siblings, and the brief forbids it. The options:
    1. **(Recommended)** Accept the two siblings. The database file itself stays byte-for-byte unchanged (the tests assert bytes and mtime), and the `-shm` is exactly what keeps the read safe if magneticod is started mid-import: SQLite then sees its writes coherently, and the next batch's identity check blocks the job with `source_changed`. The adapter never deletes them; the user docs (IMP-4) say they may appear and are harmless.
    2. `immutable=1` after the quiescence check, with an identity recheck before every batch. No siblings, but a magneticod started mid-batch could give torn reads that commit before the recheck catches them. It loosens the brief's rule, so it isn't my call.
    3. Require a copy converted to `journal_mode=DELETE`. Safe, but costs the user another 100 GiB of disk.
- **Corruption:** `SQLITE_CORRUPT` or `SQLITE_NOTADB` mid-read stops the job (block, `source_unavailable`, finding `source_corrupt`). Committed batches stay.

## Capability detection and source identity
- **By columns, not version numbers.** `PRAGMA table_info` on both tables gives the capability set.
  - **Required:** `torrents(id, info_hash, name, total_size, discovered_on)`, `files(id, torrent_id, size, path)`. `torrents.id` and `files.id` must be `INTEGER PRIMARY KEY` (rowid aliases), so keyset order is the rowid.
  - **Optional:** `updated_on`, `n_seeders`, `n_leechers`, `modified_on`, `is_readme`, `content`. Only `is_readme` is ever read (for the aggregate finding).
  - A missing required column or a non-rowid id is `unsupported_schema`, naming the missing columns. `user_version` is recorded, never trusted.
- **Supported layouts, each with a fixture built in the tests** (from magneticod's own `pkg/persistence/sqlite3.go` history):
  - **v3**, the observed schema: every optional column, the FTS5 table `torrents_idx`, its triggers, and `modified_on`;
  - **v2**, the older layout: `updated_on`, `n_seeders`, `n_leechers`, `is_readme`, `content` and `readme_index`, but no `modified_on` and no FTS;
  - **v3 missing one optional column** (`n_seeders`).
  - **v0 and v1** have the required columns but **no index on `files.torrent_id`**, so they need the spool below, or are refused.
- **`files.torrent_id` is nullable** in every magneticod version. A NULL `torrent_id` is an orphan and is never read (the range query can't match NULL).
- **Source identity** (IMP-1's `{adapter, dataset, schema_sig}`):
  - `adapter = "magnetico"`, adapter version 1.
  - `schema_sig` = SHA-256 of the sorted capability set: each used table's columns with declared type, `notnull` and `pk`, plus the indexes the keyset plan uses. 32 bytes.
  - `dataset` = SHA-256 of `user_version`, the `sqlite_master` SQL normalised (whitespace collapsed, rows sorted by type and name), `page_size`, `page_count`, and the first and last `torrents.id`. 32 bytes. It's content-derived, so a renamed copy is the same dataset and any write to the source changes it.
  - **Resume** recomputes both. A difference blocks the job with `source_changed` through IMP-1's `revalidate`; the job never restarts from zero.
- **Digest crate:** `sha2` 0.11, already in the workspace.

## Keyset reads
- **Torrents:** `SELECT … FROM torrents WHERE id > ?1 ORDER BY id LIMIT ?2`. No `OFFSET`, no `COUNT(*)`.
- **Files, one ranged query per batch, never per parent:** `SELECT torrent_id, id, CAST(path AS BLOB), size FROM files WHERE torrent_id BETWEEN ?first AND ?last ORDER BY torrent_id, is_readme, id`, read in pages of at most 10,000 rows continuing on that key, and joined to the batch's parents in order. Ids in the range that aren't parents of this batch can't exist (the range comes from the same keyset), so nothing extra is read.
  - **Why `is_readme` is in the order:** magneticod's only index on `files.torrent_id` is `readme_index (torrent_id, is_readme)`, with the rowid after it. Ordering by `(torrent_id, id)` alone would sort every batch's files in a temporary B-tree; ordering in index order needs no sort. So the stable order is file id, except that a readme row (at most one per torrent) comes last. Order isn't claimed either way.
- **Plan check:** a test runs `EXPLAIN QUERY PLAN` on each fixture schema and asserts both queries search the primary key or `readme_index`, with no `SCAN` of a whole table and no `USE TEMP B-TREE`. Inspection runs the same check on the real source, so a source with a different index shape is caught by its plan, not its version.
- **No usable `files.torrent_id` index (v0, v1):** the adapter never creates one on the source. The brief's answer is a bounded spool: read `files` once in rowid order into a temporary SQLite file in the job's staging folder, indexed by `torrent_id`, under the importer's disk gate, then keyset from the spool. **Runner, question B:** the observed source is v3 and has the index; v2 covers the brief's "older schema". I'd suggest refusing v0/v1 in this PR with `unsupported_schema` (`missing_index: files.torrent_id`, with the safe step: open the database once with a current magneticod, which upgrades it to v3), and deferring the spool. Building it here adds roughly 300 lines and a disk gate.
- **Batch bounds:** at most **500 parents or 8 MiB** of normalised record bytes, whichever comes first, with **one reader**. A parent is never split across batches: a parent over the budget is the batch's only record, cut to the per-parent limits above.
- **Position** (IMP-1's opaque cursor): a version byte plus the last parent id, 9 bytes. `seq` advances by one per batch. A replayed batch rereads the same id range and yields the same records.
- **Duplicate hashes across ids or batches** are passed through; IMP-1 counts the second as `merged`. Duplicate ids can't happen in a rowid table, and the test that asks for them asserts the keyset never yields one twice.

## Findings, logs and metrics
- **Findings are a fixed enum with counts:** `bad_hash`, `name_lossy`, `path_lossy`, `name_over_limit`, `files_over_limit`, `file_malformed`, `no_files`, `size_mismatch`, `date_out_of_range`, `missing_name`, `missing_size`, `readme_not_imported`, `orphan_files`, `source_not_quiescent`, `unsupported_schema`, `source_corrupt`, `statement_timeout`. The adapter returns them with each batch; persisting per-reason counts was left to the adapter slices by IMP-1, and IMP-2 keeps them in memory and returns them to its caller (IMP-4 persists or prints them).
- **Logs and metrics carry those reason labels and aggregate counts only.** No name, hash, path, row id or row content, ever. Errors carry the reason and, for `unsupported_schema`, the missing column names, which come from this adapter's own constant list, not from the source.

## Tests (per the brief)
- Fixture databases built in the tests: v3, v2, and v3 missing an optional column; plus v1, with no `files.torrent_id` index, for the spool or refusal path.
- Malformed rows: a bad hash length, negative and huge sizes, invalid UTF-8 in names and paths, an oversized path, an orphan file row, a parent with no files, and duplicate hashes across batches.
- Source unchanged: the file's bytes and mtime after a full read; a write attempted on the adapter's connection fails under `query_only`.
- Resume mid-source, and the `source_changed` block after the source is modified.
- The non-quiescent refusal, for a `-wal` and a `-journal` sibling, and the query-plan assertions.
- A property test: random fixture databases through the adapter into a temporary store keep IMP-1's counter conservation.
- A `cargo fuzz` target (`magnetico_row`) for the row normaliser, with seeds in `fuzz/seeds/magnetico_row/`, added to the CI fuzz matrix.
- No fixed sleeps.

## Dependencies
`sources-importers` gains `rusqlite` (0.40.2, `bundled`, the store's exact version) and `sha2` (0.11.0), and `proptest` (1.11.0) as a dev-dependency. All three are already in the workspace's lock file; no new crate enters the build.
