# IMP-2 decisions: the Magnetico SQLite adapter

The Magnetico adapter (the plan's IMP-03, `docs/plan/2026-10-29-magnetico-bitmagnet-migration.md` §5 "Magnetico SQLite", §9, §10). It builds on IMP-1's contracts (`docs/decisions/2026-10-30-IMP-1.md`) and redefines none of them: records go through `Store::commit_import_batch` as `ImportRecord::{Torrent, Candidate, Invalid}`, with IMP-1's quality states, merge rules and counters.

The runner OK'd this contract before the reader code was written (2026-10-30) and answered three questions, recorded below as **runner A, B and C**. Where the implementation refined the agreed note, the entry says so.

Code: `crates/sources-importers/src/magnetico.rs`, its tests (`magnetico/tests.rs`) and fixtures (`magnetico/fixtures.rs`), and the fuzz target `fuzz/fuzz_targets/magnetico_row.rs` with seeds in `fuzz/seeds/magnetico_row/`. The CI fuzz matrix is built from `fuzz/fuzz_targets/*.rs` (`.github/scripts/ci_changes.py`), so the target joins it with no workflow edit.

## Column mapping
Each Magnetico parent row becomes exactly one IMP-1 record. Nothing in a row is ever used as SQL, as a path on the filesystem, or in an error or log.

| Magnetico column | IMP-1 field | Rule |
|---|---|---|
| `torrents.id` | cursor only | Keyset position. Never stored in Lodestar. |
| `torrents.info_hash` | `Prepared.info_hash` / `ImportCandidate.hash` | Must be a **BLOB of exactly 20 bytes**, not all zeros. Anything else (TEXT, hex, 19 or 32 bytes, an integer, NULL) is `Invalid`, finding `bad_hash`. `hash_v2` is always `None`: Magnetico is v1 only. |
| `torrents.name` | `Prepared.name` / `name_raw`, candidate `name` | Read as the stored value: TEXT or BLOB bytes, untouched. An INTEGER, REAL or NULL name is missing. See "Untrusted text". |
| `torrents.total_size` | `Prepared.size`, candidate `size` | An INTEGER > 0. NULL, ≤ 0, REAL or TEXT is **missing**: never 0, never coerced. |
| `torrents.discovered_on` | `source_at` | Unix seconds, INTEGER only, in `[2008-01-01, batch time + 1 day]`. Otherwise `None`, finding `date_out_of_range`. Milliseconds are never guessed. IMP-1 then dates the row from it only when it's positive and not after the batch. |
| `torrents.updated_on` | — | Not imported: IMP-1 has no field for it, and it says when magneticod last scraped, not anything about the torrent. Left for IMP-06. |
| `torrents.n_seeders`, `n_leechers` | — | **Hints only, never swarm truth.** Not imported (swarm observations are IMP-06), not even selected. |
| `torrents.modified_on` | — | **Ignored.** It has a far-future default, so it says nothing reliable. |
| `files.torrent_id` | — | Join and order only. |
| `files.path` | one `File.path` | TEXT or BLOB bytes, split on `/` into segments. See "Files". |
| `files.size` | `File.size` | An INTEGER ≥ 0. Anything else makes the row malformed. |
| `files.is_readme` | — | Read only as `is_readme IS NOT NULL`, to count finding `readme_not_imported` per batch. A readme row is still a file of its torrent and is imported as one; only the readme text isn't. Annotations are IMP-06, deferred. |
| `files.content` | — | **Never selected.** |

**Every value is size-guarded in the SQL** (self-review, blocking). Each column is selected as `CASE WHEN octet_length(x) <= limit THEN x END` beside `octet_length(x)`. SQLite answers `octet_length` without loading the value, so an over-limit value is never read into memory, and it can't fail the read with `SQLITE_TOOBIG` and wedge the import on resume. It reaches the normaliser as `Raw::TooLong`. The limits are 64 bytes for the hash, size and date, and metainfo's 4,096 for the name and path. So an oversized name is `name_over_limit`, an oversized hash is `bad_hash`, an oversized size or date is missing, and an oversized path is a malformed file row.

**Prepared fields Magnetico doesn't have:** `piece_len`, `piece_count` and `info_size` are 0; `raw` and `extra` are `None`. `info_size` 0 is safe under IMP-1's read rule because every record this adapter writes gets its own `import_quality` row.

## Quality, privacy and file order
- **Privacy is always `unknown`.** Magnetico stores no private flag, so the adapter never claims public or private. IMP-1's sticky-private merge still applies against other sources.
- **Verification is always `unverified`.** Magnetico once fetched the info dict, but the database keeps no info dict and nothing ties the stored fields to the hash any more. A record is never `verified` because magneticod fetched it (IMP-1 refuses `verified` from an import anyway).
- **Completeness:**
  - `reported_complete` when every file row of the parent was kept and well formed, and the file sizes sum to `total_size`;
  - `partial` otherwise, with repair bits:
    - `MISSING_FILES` for a parent with no file rows (finding `no_files`);
    - `INCONSISTENT_FILES` for a dropped or over-limit row, or sizes that don't sum to `total_size` (finding `size_mismatch`);
    - both, when file rows existed but none survived.
  - `partial` sets `FILES_PARTIAL`, so the existing verified re-fetch picks it up.
- **File order and single-file mode are never claimed.** File ids give a stable iteration order, not the original bencode order. `SINGLE_FILE` is never set, even for one file row whose path equals the name: Magnetico stores single-file torrents that way, but it can't be told apart from a one-file directory.
- **Torrent or candidate:**
  - a valid hash with a name and a size is a `Torrent`;
  - a valid hash missing its name or size is a `Candidate`, with privacy `unknown` and `source_at`, and IMP-1 derives `missing`. A candidate holds no files, so its file rows aren't evaluated, and they aren't counted in `files_dropped` (IMP-1's `ImportCandidate` has no such field);
  - an invalid hash is `Invalid`.
  - A torrent record that `Store::prepare` rejects is committed as `Invalid` by the caller. That's the driver's rule (IMP-4); the tests' driver follows it.

## Untrusted text
- **Names and paths are raw bytes,** checked as UTF-8 first. Valid UTF-8 is stored as is.
- **Invalid UTF-8 is decoded lossily, with a flag.** The record carries the original bytes and `TextEncoding::UTF8`. `Store::prepare` then stores the lossy name and keeps the original bytes in `name_raw`, the same mechanism it already uses for any non-UTF-8 name. So search, display and later verified upgrades treat it like any other undecodable name. Findings `name_lossy` and `path_lossy` count them. Paths go through `filetree::encode` with the same encoding.
- **The original bytes are kept exactly, so there's no separate hash** (runner A). The brief asked for a hash of the original bytes, as IMP-0's `SQL_ASCII` rule does. `name_raw` holds the exact original bytes whenever they aren't plain UTF-8, so no new column is needed.
- **No guessed legacy encodings.** Magnetico wrote Go strings, so anything that isn't UTF-8 is damage, not GBK or Shift-JIS.

## Files
- **A file row is malformed** when:
  - its `path` isn't TEXT or BLOB, is empty, has an empty segment (a leading, trailing or doubled `/`), or contains a NUL byte;
  - its `path` is over `Limits::DEFAULT.max_path_bytes` (4096) or `max_path_depth` (64);
  - or its `size` isn't an INTEGER ≥ 0.
- **What happens to a malformed row:** it's dropped and counted in `files_dropped`, and its parent becomes `partial` with `INCONSISTENT_FILES`, plus finding `file_malformed`. **The parent is never dropped.**
- **`.` and `..` segments are kept as bytes.** Paths never touch the filesystem, and search and the UI already treat names as untrusted text.
- **A file row whose `torrent_id` isn't an INTEGER** (possible only in a constraint-free source) is treated as an orphan and skipped.
- **Orphan file rows are never read.** That covers a NULL `torrent_id`, which magneticod's schema allows, and a parent that no longer exists. Files are read by the batch's parent id range and joined to the parents read, so an orphan is skipped by construction, and a test asserts this.
  - *Refined from the note:* the note proposed an aggregate `orphan_files` count. Counting orphans needs a scan of all of `files`, so it was dropped.
- **Over the limits, a record is kept as partial, never silently truncated into a complete one:**
  - **Too many files:** more than `max_files` (200,000) rows, or rows over the per-parent budget of 8 MiB, which counts memory, not just bytes (see "Batch bounds"). The first rows in file order are kept, as a prefix: once one row is over the budget, every later row is dropped and counted too. The record is `partial` with `INCONSISTENT_FILES`, finding `files_over_limit`.
  - **A name over `max_name_bytes` (4096):** no truncation. The record becomes a `Candidate` with its name missing, finding `name_over_limit`.
  - **A size sum that overflows `u64`:** `partial` with `INCONSISTENT_FILES`.

## Opening the source
- **The path goes through one validated function,** `magnetico::open(path, &OpenPolicy)`. It refuses each of these with a fixed reason:
  - anything that isn't a regular file (a directory, device, pipe or socket): `not_a_file`;
  - a symlink or reparse point whose target is outside the given file's own directory: `symlink_escape`;
  - a UNC path (`\\server\…`, `//server/…`, `\\?\UNC\…`) unless it's under a root in `OpenPolicy::approved_unc_roots`, or one that climbs out of a root with `..`: `unc_not_approved`. IMP-4's CLI fills `OpenPolicy`; this slice has no CLI.
  - a device namespace path (`\\.\pipe\…`, `\\.\NUL`), a verbatim path that isn't a drive (`\\?\Volume{…}`, `\\?\GLOBALROOT\…`), or on Windows a DOS device name in any component: `not_a_file`. The device names are `CON`, `PRN`, `AUX`, `NUL`, `COM0`–`COM9`, `LPT0`–`LPT9` (superscript digits too), `CONIN$` and `CONOUT$`. They match in any case, with trailing dots or spaces, and with any extension or `:stream` suffix, since Windows before 11 opens the device for `NUL.txt` (runner re-review).
- **Network and device paths are refused lexically, before any I/O** (runner review, blocking, security). On Windows, merely resolving `\\attacker\share\x` opens an SMB session, which can leak the service account's NTLM hash, and a metadata call on a device path opens the device. So, before any filesystem call on a path:
  - its text is checked, with `/` read as `\`, the NT prefix `\??\` read as `\\?\`, `\\?\UNC\` read as `\\`, and case ignored when matching approved roots. Win32 passes `\??\…` straight to the object manager, so `\??\UNC\server\…` reaches SMB and `\??\pipe\x` a pipe, while Rust parses it as a plain root-relative path. Reading it as `\\?\` lets the verbatim rules classify it (runner re-review, blocking);
  - every component that's a link (a symlink, or a junction on Windows) has its target text checked the same way, read with `read_link`, which doesn't follow it, and so on down a chain of at most eight links. A longer chain, or a loop, is `symlink_escape`;
  - only then is the path resolved, and the canonical path is checked again against the approved roots.
  - **A junction to another local volume by GUID** (`\\?\Volume{…}`) is refused too. That's stricter than needed, but such a path can't be told from a device path by its text. **Users should point at the database through its drive letter instead;** IMP-4's docs say so.
  - **A mapped network drive letter** (say `Z:` mapped to a share) looks like a local drive by its text. It's caught only after `canonicalize`, which resolves it to its UNC form for the approved-root check. That's accepted: the user mapped the drive themselves, so reaching it isn't a surprise connection.
  - **The swap window** between these checks and the open needs local write access to the source's folders. The "known limit" under "The open itself" covers it.
- **The open itself:**
  - It opens the canonical path with `SQLITE_OPEN_NOFOLLOW`, then re-checks the file's identity against what was validated. On Unix that's device and inode. On Windows it's length and creation time, because std's file index is unstable.
  - **No URI filenames.** The bundled SQLite parses `file:` URIs even without `SQLITE_OPEN_URI` (it's built with `SQLITE_USE_URI`). The name it gets is the canonical, absolute path, which never starts with `file:`, and `open` refuses one that does anyway. So a name can't smuggle in `immutable=1` or another VFS (security review).
  - **A known limit:** `NOFOLLOW` covers only the last path component, and the identity re-check reads the path's metadata, not the opened handle. Someone able to swap directories on the same machine between the check and the open could point it at another file. That needs local write access to the source's parent folders, and the file is still only read.
- **Hardening:**
  - `SQLITE_OPEN_READ_ONLY | NO_MUTEX | NOFOLLOW`;
  - db_config `DEFENSIVE` on, and `TRUSTED_SCHEMA`, `ENABLE_TRIGGER` and `ENABLE_VIEW` off;
  - `PRAGMA query_only=ON`, `trusted_schema=OFF`, `cell_size_check=ON`, `mmap_size=0`.
  - Extension loading stays off: rusqlite's `load_extension` feature isn't enabled.
  - **Never `immutable=1`, never a write, never a repair.** A test proves inserts, deletes, DDL, `PRAGMA user_version`, `ATTACH` and switching `query_only` back off all fail.
- **Bounds:**
  - The row count at open (see "Source identity") may take 20 steps' time (10 minutes), since it scans one index once.
  - `sqlite3_limit` caps `LENGTH` (16 MiB), `SQL_LENGTH` (64 KiB), `COLUMN` (64), `ATTACHED` (0), `EXPR_DEPTH` (100) and `VARIABLE_NUMBER` (1,024).
  - A progress handler (every 10,000 VM steps) interrupts on cancel, or when one step runs past `OpenPolicy::statement_timeout` (30 s). The deadline is re-armed before each row step, and it's capped by **a whole-batch deadline of ten steps' time** (5 minutes). So neither one step nor a batch full of orphan or over-budget rows can run unbounded (self-review, polish).
  - An interrupted statement is the refusal `statement_timeout` or `cancelled`, never a partial batch.
- **Tables:**
  - Only `torrents` and `files` are read, each checked to be an ordinary rowid table in `sqlite_master` (`CREATE TABLE`, not virtual and not `WITHOUT ROWID`).
  - FTS tables, views and triggers are never read.
  - **magneticod v3's FTS index may be damaged.** On current SQLite its `modified_on` default trigger fires before the FTS insert trigger. The FTS5 external-content delete that causes reports the index as malformed (reproduced on 3.45). A real source's `torrents_idx` may therefore be inconsistent, which is one more reason never to read it. The fixtures supply `modified_on` explicitly so the trigger stays idle.
- **Consistency: a live or inconsistent source is refused** with `source_not_quiescent`.
  - **When it's checked:** before the open, and again before every batch.
  - **What fails it:** a non-empty `-wal` or any `-journal` sibling.
  - **What passes:** an empty `-wal`, including one our own earlier open left (runner C, condition 2).
  - **The message gives the safe step:** stop magneticod, or import a consistent copy.
  - **On a running job** it blocks with IMP-1's `source_unavailable`, since IMP-1's reasons are a fixed enum. The refusal keeps its own label.
- **WAL siblings (runner C, option 1; a runner refinement of the brief, owner-decisions §2.19).**
  - **Why they appear:** magneticod always sets `journal_mode=WAL`, so every real source is a WAL-mode database. On SQLite 3.45, opening one read-only creates an empty `-wal` and a `-shm` beside it and leaves both after close; a read-only connection can't remove them. `nolock=1` and the `unix-none` VFS both refuse to open it. Only `immutable=1` avoids the siblings, and that stays forbidden.
  - **So the adapter accepts the two siblings and never deletes them.** The database file itself is never written, and a test asserts it's byte-identical, with the same mtime, after a full read.
  - **The `-shm` keeps the read coherent** if magneticod starts mid-import. The next batch's check then refuses: either the `-wal` is no longer empty, or the dataset identity changed.
  - **A folder where the siblings can't be created** is `source_unavailable` with label `folder_not_writable`, and the message says to make the folder writable or import a copy. Only a permission error counts: `SQLITE_PERM`, `SQLITE_READONLY_DIRECTORY` and `SQLITE_READONLY_CANTINIT`.
  - **Any other open failure,** such as a stale `-shm`, a hot WAL that needs recovery (`SQLITE_READONLY_RECOVERY`) or `SQLITE_CANTOPEN`, is the file's problem, not the folder's: label `open_failed`, with advice to make sure magneticod stopped cleanly or to import a consistent copy (runner review). Other read failures carry their own label (`value_too_big`, `read_failed`), with advice to check the file or import a copy, not the folder advice.
  - **User docs:** IMP-4's docs tell the user that two small files appear beside their database.
- **Corruption:** `SQLITE_CORRUPT` or `SQLITE_NOTADB`, at open or mid-read, is `source_corrupt`. A running job blocks with `source_unavailable`, and committed batches stay. A non-database file is refused this way at open, not reported as a missing schema.

## Capability detection and source identity
- **By columns, not version numbers.** `pragma_table_info` on both tables gives the capability set.
  - **Required:** `torrents(id, info_hash, name, total_size, discovered_on)` and `files(id, torrent_id, size, path)`. Both `id`s must be the table's only primary key, declared `INTEGER` (a rowid alias), so keyset order is rowid order.
  - **Optional:** `updated_on`, `n_seeders`, `n_leechers`, `modified_on`, `is_readme`, `content`.
  - **Anything missing** is `unsupported_schema`, naming what's missing from this adapter's own constant list, never text from the source. `user_version` goes into the dataset identity but never decides support.
- **Supported layouts, each with a fixture.** The fixtures replay magneticod's own `pkg/persistence/sqlite3.go` schema history:
  - **v3**, the observed schema: every optional column, the FTS5 table `torrents_idx`, its triggers, and `modified_on`;
  - **v2**, the older layout: `updated_on`, `n_seeders`, `n_leechers`, `is_readme`, `content` and `readme_index`, but no `modified_on` and no FTS;
  - **v3 without one optional column** (`n_seeders`);
  - **a constraint-free layout with v3's columns,** for malformed values a damaged or hand-made source can hold.
- **v0 and v1 are refused** (runner B; a stated scope reduction). They have the required columns but no index on `files.torrent_id`.
  - They get `unsupported_schema` (`missing_index: files.torrent_id`). The message gives the safe step: run a current magneticod on the database once, which upgrades it to v3.
  - **The bounded spool the brief describes is deferred.** That's a temporary indexed copy of `files` in the job's staging folder, under the importer's disk gate. The observed source is v3, and v2 covers the brief's older schema.
  - The adapter never creates an index on the source.
- **Source identity** (IMP-1's `{adapter, dataset, schema_sig}`):
  - `adapter = "magnetico"`, adapter version 1.
  - `schema_sig` is a domain-separated SHA-256 of the capability set (each known column's name, declared type, `notnull` and `pk`) plus the chosen files query. 32 bytes.
  - `dataset` is a domain-separated SHA-256 of a **fingerprint** plus `SELECT count(*) FROM torrents`. The fingerprint is a SHA-256 of:
    - `user_version`, `page_size`, `page_count` and `freelist_count`;
    - every `sqlite_master` row's type, name and SQL, whitespace collapsed and sorted by type and name;
    - the first and last `torrents.id`.

    It's 32 bytes and content-derived, so a renamed copy is the same dataset. The row count needs one scan of the smallest index, so it's computed at open only; each batch re-checks the cheap fingerprint (runner review).
  - **What it can't detect:** an in-place edit that changes no page count, free-page count, schema, end id or row count. For example, a row's name rewritten to the same length, or deletes and inserts that cancel out without freeing a page. magneticod doesn't edit rows that way; it only inserts. And a source that's being written is refused anyway by the `-wal` check.
  - **On resume** the caller reopens and passes both to IMP-1's `revalidate`, which blocks a changed source with `source_changed`. The job never restarts from zero.
  - **Within a run, each batch is one read transaction** (`BEGIN DEFERRED`, which `query_only` allows). The fingerprint and schema signature are recomputed inside it, before the rows are read, so the identity check and both queries see one snapshot. A change made between batches is refused with `source_changed`. A change made during a batch isn't in that batch's snapshot, and the next batch refuses it (self-review, important).

## Keyset reads
- **Torrents:** `SELECT id, <guarded columns> FROM torrents WHERE id >= ?1 ORDER BY id LIMIT 500`. The start is `i64::MIN`, and each later batch starts at the last id plus one, so even a row at `i64::MIN` is read (self-review). No `OFFSET`, no `COUNT(*)`.
- **Files: one ranged query per batch, never one per parent.** `SELECT torrent_id, <guarded path, size>, is_readme IS NOT NULL FROM files WHERE torrent_id BETWEEN ?first AND ?last ORDER BY torrent_id, is_readme, id`, joined in order to the batch's parents.
  - **Why `is_readme` is in the order:** magneticod's only index on `files.torrent_id` is `readme_index (torrent_id, is_readme)`, with the rowid after it. Ordering by `(torrent_id, id)` alone would sort every batch's files in a temporary B-tree; index order needs no sort. So file order is by id, except that a readme row (at most one per torrent) comes last. Order isn't claimed either way.
  - **A source without `is_readme`** but with some index on `torrent_id` is tried with `ORDER BY torrent_id, id`. The plan check decides which order is used.
  - *Refined from the note:* the query is **streamed** row by row, not paged at 10,000 rows. SQLite steps through the index lazily and the adapter stops stepping at the budget, so memory stays bounded by the batch and per-parent budgets without a second keyset on a nullable column.
- **Plan check:**
  - **At open:** `EXPLAIN QUERY PLAN` must show the torrents query as `SEARCH torrents USING INTEGER PRIMARY KEY`, and the files query as a `SEARCH files USING …` index with no `SCAN` and no `TEMP B-TREE`. Otherwise the source is `unsupported_schema`. So a source with a different index shape is caught by its plan, not its version.
  - **In the tests:** the same check on v2, v3 and v3 without `n_seeders`. `Source::plans` exposes it for inspection.
- **Batch bounds:** at most **500 parents or 8 MiB**, whichever comes first, with **one reader**. The 8 MiB counts memory, not just source bytes: each kept row is charged its bytes plus 64 bytes of overhead, and each path segment another 24 (runner review). So many tiny file rows can't hold far more memory than the budget says. `source_bytes` stays the bytes actually read.
  - Parent rows count toward the budget as they're read, and the budget is checked again over every kept parent, so file-less parents are bounded too (self-review, blocking).
  - A parent is never split across batches. A parent that won't fit beside the earlier ones starts the next batch, and its readme count goes with it, so nothing is counted twice.
  - A single parent is held to the per-parent limits above, so no batch exceeds 8 MiB.
- **Position** (IMP-1's opaque cursor) is a version byte (1) plus the last parent id, big-endian: 9 bytes. Anything else is refused as `bad_position`. `seq` advances by one per batch.
  - A replayed batch rereads the same id range and yields the same records. A test checks that against IMP-1's `Replayed`.
- **Duplicate hashes across ids or batches** are passed through, and IMP-1 merges the second. Duplicate ids can't happen in a rowid table.

## Findings, refusals, logs and metrics
- **Per-record findings are a fixed enum with counts, returned with each batch:** `bad_hash`, `name_lossy`, `path_lossy`, `name_over_limit`, `files_over_limit`, `file_malformed`, `no_files`, `size_mismatch`, `date_out_of_range`, `missing_name`, `missing_size`, `readme_not_imported`.
  - IMP-1 left persisting per-reason counts to the adapter slices. IMP-2 returns them to its caller, and IMP-4 persists or prints them.
- **Source-level refusals are a fixed enum too** (`source_unavailable` carries one of the fixed labels `not_found`, `open_failed`, `folder_not_writable`, `value_too_big` or `read_failed`): `not_a_file`, `symlink_escape`, `unc_not_approved`, `source_not_quiescent`, `source_unavailable`, `unsupported_schema`, `source_corrupt`, `statement_timeout`, `cancelled`, `source_changed`, `bad_position`.
  - `Refusal::job_reason` maps each to the IMP-1 reason a running job blocks with: `source_changed`, or `source_unavailable`. It gives none when the job should fail (an unsupported or refused source), or when the caller stopped it.
- **Logs and metrics carry only those labels and aggregate counts:** no name, hash, path, row id or row content, ever.
  - Records, sources and identities have hand-written `Debug` impls that print lengths and counts only, and a test checks a record's `Debug` output.
  - SQLite's own error text is never passed on: each error maps to a refusal.

## Tests
- **Fixtures** (built in the tests): v0, v1, v2, v3, v3 without `n_seeders`, and the constraint-free layout.
- **Malformed rows:**
  - bad hash types and lengths (and an all-zero hash);
  - missing, negative, zero, REAL and TEXT sizes;
  - a huge size;
  - invalid UTF-8 in names and paths;
  - an oversized name and path;
  - every malformed path shape;
  - a NULL-parent orphan, a deleted-parent orphan and an out-of-range orphan;
  - a parent with no files;
  - duplicate hashes across batches;
  - dates out of range.
- **Text rewriting and device names (every platform):** the Windows text rewriting (`\??\`, `\\?\UNC\`, `/`, case) and the DOS device-name match are pure functions with their own tests, so Linux runs them too.
- **Lexical refusals (Windows CI):** `\??\UNC\…`, `\??\pipe\x` and device names such as `nul`, `NUL.txt`, `con \…`, `COM1.sqlite3`, `lpt9.` and `CONOUT$`, plus `\\.\pipe\…`, `\\.\NUL`, `\\?\GLOBALROOT\…`, `\\?\Volume{…}`, `\\server\share\…`, `//server/share/…` and `\\?\UNC\…` are refused by their text. The servers named don't resolve, so a refusal other than `not_found` shows no I/O happened. `..` out of an approved root is refused; an approved root matches in any case and in either UNC form. On Unix, a chain of links is followed and checked, and a loop is refused.
- **Labels and identity:** only permission errors blame the folder; a deleted middle row changes the dataset but not the schema signature; per-row overhead cuts a parent of 100,000 tiny files to its budget.
- **Size guards:** a 17 MiB name, hash, size and path each become a finding, and the batch stays small. 500 parents with 3 MiB names stay within the batch budget.
- **Keyset edges:** a row at `i64::MIN` is read; a cut parent's readme is counted once; over-budget files are dropped as a suffix.
- **Debug output:** raw values, rows and batches print no content, number or id.
- **Source unchanged:** the file's bytes and mtime after a full read; every write path fails; the WAL sibling is empty, and our own empty `-wal` doesn't block a reopen.
- **Resume and change:** a mid-source resume from a fresh open returns exactly the next batch; a replay through IMP-1 writes nothing; every imported row has its quality row; and a source changed while the job was interrupted blocks the job with `source_changed` through IMP-1's `resume_import_job`. A source written mid-import is refused, and once magneticod has closed cleanly it reopens as a different dataset with the same schema signature. A renamed copy is the same dataset.
- **Refusals:** non-quiescent (`-wal` and `-journal`), v0 and v1, missing columns, a non-database file, a directory, a missing file, a FIFO and `/dev/null`, a symlink escaping its folder (one inside it opens), cancel, and the deadline.
- **Query plans** on every supported fixture.
- **Batches:** the 500-parent split, the 8 MiB split that keeps parents whole, and a parent over its own budget kept as partial.
- **A property test:** random constraint-free sources go through the adapter into an in-memory store and keep IMP-1's counter conservation. They include malformed values of every storage class for hashes, sizes and dates, and batches of 1 to 8 parents so batch boundaries are crossed.
- **The `magnetico_row` fuzz target** checks that the normaliser never panics, that a complete record's files add up, that kept plus dropped equals the rows given, and that names stay in bounds.
- No sleeps.
