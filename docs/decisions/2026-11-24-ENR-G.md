## How the suite tests it
- **Real plugins, real runtime.** ThePornDB and StashDB run through `AdultEnrichSource` over a real store and filter, with their real manifests and kit. Only the transport is fake: it records every request, and either replays the plugin's recorded fixture or answers 503.
- **Visibility rests on the item, not the match.** A match never makes an item adult (`crates/pipeline/src/enrich.rs`, `with_match`): it only pins the kind of an item already adult. So the visibility tests cited for item 5 hold for matched items too, though their fixtures store no enrichment claim; the API's own section tests (`crates/api/tests/adult_enrichment.rs`) cover the claim.
- **Spellings.** Every request's URL, headers and body are checked for each guarded hash in lower and upper hex, base32 and percent-encoded form, and for each blocked item's words.
- **The log.** The test installs the binary's only sink with every pipeline and filter event on. Today the lookup, the plugin and the hold log nothing; a canary event proves the sink is live, so a line someone adds later is scanned for names, answer text and hashes.
- **No fixed sleeps.** Every wait polls a condition with a deadline of at least 10 s.

## The holes the gate found, and their fixes
Each fix is outside this slice's first owns, so the runner approved it before it was written (2026-11-24T14:45Z for the first, 15:32Z for the other three changes). Each tightens content safety, so none needs an owner call.

1. **A purge left the match in the record.** `Store::purge_source` deleted an enrichment source's claims and plugin state but left `torrent_parsed` as it was, so a matched torrent kept the match's adult kind, its `adult:<kind>` search tag and any identification title (ENR-10/11) until something else re-derived it. **Fix:** the Claims stage deletes each page with `RETURNING torrent_id, data` and marks those torrents for re-derivation (`parser_ver = 0`, as `drop_one` and `Store::mark_unenriched` do) in the same transaction. Two `LIMIT` subqueries without an order could pick different rows, so the marks come from the delete itself. `crates/store/tests/unverified.rs::a_purge_marks_the_torrents_that_lost_a_record_shaping_claim` checks it at one row a step and at a hundred.
2. **A purge on a running server waited for a restart.** The writer's backfill makes one pass per start, so a torrent marked after that pass stayed marked until the next start. **Fix:** `Control::purge_step` re-arms the writer's backfill (the shared `reenrich` flag, through `Monitor`) whenever a step removed claims. `crates/pipeline/tests/control.rs::a_purge_on_a_running_server_derives_the_record_again` purges after the start's pass and waits, with a 20 s deadline, for the record to be derived without the match; it times out without the fix.
3. **The mark is narrowed to claims that shape the record.** Only a claim with an adult section that pins a kind, or identification details, changes the derived record, so only those torrents are marked. `Claims::shapes_the_record` is the one predicate; `enrich::mark_matched` uses it too, so the purge and the match path can't disagree. **Plain feed claims aren't re-derived on purge**, which is today's behaviour: they never shaped the record. The runner is opening a follow-up for it, and for the `Fate::Keep` re-derive gap (X-purge-rederive).
4. **An answer emitted before consent was withdrawn was stored after.** The lookup checked consent, but the writer stored the answer later without checking again. **Fix:** `unverified::ingest` drops a claim with an adult section from a listed adult-enrichment source unless its consent condition still holds, using the runtime gate's own check (`adult_enrich::consent_met`, through `EnricherConsent`), not a copy. `::an_answer_written_after_consent_is_withdrawn_is_not_stored` withdraws consent between the answer and the write; the drop logs nothing and counts as refused.

## For the wiring slice (item 7)
- The binary has no `AdultEnrichSource` and no `Switches` implementation yet. `the_binary_wires_no_adult_enrichment_yet` fails as soon as either appears in `crates/lodestar`, so the wiring slice must replace it with a test of its own.
- **Its `kill_switch_tripped` must be true for every `RouteState` but `Up`**, including `Unchecked`, and a Direct route must be checked (`check_now`) before its first lookup.
- Meanwhile the egress client is only a partial backstop. A proxy or interface route probes before it sends and refuses on a failed probe; a Direct route never probes. `an_unavailable_route_or_an_unchecked_one_whose_proxy_is_gone_sends_nothing` gives the runtime a host switch that says "up": a route down for good and an Unchecked SOCKS5 route whose proxy is gone each send no request and make no DNS lookup, and the refusal is counted. So the host's switch must not lean on the client for an Unchecked Direct route.
