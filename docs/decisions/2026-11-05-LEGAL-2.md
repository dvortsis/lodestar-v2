# LEGAL-2 decisions (the crawler held on a fresh data directory until setup)

LEGAL-2 is the runner's slice adopted under §2.26 (`docs/decisions/2026-11-04-X-legal-docs.md` line ~50; owner §2.38, §2.40): on a fresh data directory the crawler starts paused until setup completes, so nobody's address joins the DHT before anyone has read the Legal Notice. Existing installs are unaffected. The points below are runner-level refinements under §2.19, flagged to the owner.

## What counts as fresh
- **Held means no admin password in `auth.json` when `serve` starts.** That's the same test `POST /setup` uses (`Auth::needs_setup`), and setup saves the password and `notice_version` in one atomic write, so "setup complete" is one durable fact. Nothing new is stored. A restart before setup finds no password and holds again.
- **Fail closed.** A data directory whose `auth.json` has no password is held whatever else it holds: a store created by this run, a store first made by `lodestar import`, a crash between creating the store and setup, and an install whose password was reset by removing `auth.json`. Each of these is waiting for someone to set a password and read the notice, so the crawler waits too.
- **Set up before LEGAL-2 means not held.** An install with a password starts as before, with or without `notice_version`. If the notice is shown again at login (LEGAL-1's gate), the crawler doesn't stop: the brief excludes existing installs, and the gate is about the admin, not the network.
- **Releasing only goes one way.** `Auth::watch_set_up` turns `true` when `POST /setup` has saved and published the password. Nothing turns it back while the process runs. If the signal's sender went away while still held, the hold would stay on (fail closed).

## What the hold pauses (`crates/pipeline/src/setup_hold.rs`)
- **Every source plugin's start.** Each enabled plugin's task waits before calling `run`. So **the DHT doesn't bind its sockets, bootstrap, answer or announce** (a user's pause still lets the node answer other nodes, but the hold doesn't). The torrent cache and any other source don't dial out either. A stop while held ends the plugin without running it, so a held DHT writes no `dht-state.bin`. A waiting plugin counts as running for `/healthz` and `lodestar_source_up`, so a container's health check passes before setup.
- **The scrape scheduler** (tracker and BEP 33 swarm counts). Its tracker tasks only act on its jobs, so no tracker and no DHT node is asked. Hints that arrive meanwhile queue while there's room, then drop and count as ever.
- **The fetch pool** starts paused, so no metadata fetch or lookup runs, including keys saved from an earlier run.
- **`Control`** reads `paused` while held, whatever `crawler.paused` says, and reports `waiting_for_setup`. It tracks the setting underneath. When the hold lifts it applies the setting, so the crawler resumes on its own unless the user paused it. A pause or resume saved while held is kept and applies after setup. The resume is an ordinary `RESUME` event and a `pipeline.crawler_toggled` line. If setup were to complete between the pipeline's start and `Control::start`, which can't happen today because nothing is served yet, `Control::start` hands the pool the setting's value itself, so it can't stay paused.

## Out of scope, and why
- **`lodestar import` and other local imports.** They read files and use no network.
- **Blocklist subscriptions.** On a fresh store none is subscribed (off until chosen, X-legal-docs), so the refresher fetches nothing. They download filter lists, not crawl.
- **Update checks** (B-update, GitHub). They're off unless turned on, and they aren't the crawler.
- **Notification channels and webhooks.** They're set up by the admin after setup.
- **Resolving a source's proxy name** at start (`egress::build`). It needs a proxy saved in the app, so it isn't on a fresh store. For an `auth.json` reset it's a DNS lookup of the admin's own proxy, not traffic to the swarm.

## Status
- **`GET /api/status`** (the status page's JSON) gains `crawler: {paused, reason}`. `reason` is `"setup"` while held, `"user"` for the setting, and `null` while running. **`/status`** shows "Crawler paused: waiting for setup." from it. Before sign-in, its first-run line adds that nothing connects to the network until setup is done.
- **No en/zh message key.** The brief asked for one, but the status page is English-only by design, with no message catalogue. And every localized surface (the web UI, `/api/v1/crawler`) needs a session, which exists only after setup, when the hold has already lifted. A key would never be shown, so the runner decides whether to add one somewhere else (the setup wizard, say) in a later slice. `/api/v1/crawler`'s DTO is unchanged for the same reason.

## Follow-up for the runner

## Tests
- `crates/pipeline/tests/setup_hold.rs`: no source runs and the crawler reads paused before setup, even with the setting saying run; after setup the source starts and the crawler resumes; a pause chosen before or during the hold stays after setup; an instance already set up starts unheld; a stop before setup never runs a source; a dropped signal keeps the hold.
- `crates/lodestar/tests/setup_hold.rs`, through the real binary: on a fresh directory the DHT never starts (no `pipeline.dht_started`, no DHT metrics, no `dht-state.bin` after a clean stop); a restart before setup is still held; `POST /setup` starts the DHT and `/api/status` reports it running; a set-up install crawls at the next start with no setup; a user who paused, then reset the password, is held and stays paused after setup (`reason: "user"`).
- Waits are on conditions with deadlines of 10 s (in-process) and 30 s (binary), never fixed sleeps.
