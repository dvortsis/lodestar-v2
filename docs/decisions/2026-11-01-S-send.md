# S-send decisions: "Send to client" in the row menu, the detail drawer, `/t` and the `s` key

Closes the S-e2e (#314) app gap: §10.17's keyboard flow "search → open → send" ended at copy.

- **How "a client is configured" is known.** No store existed, so `features/detail/send.ts` reads `GET /settings/integrations` once, lazily, and keeps the answer for the session: the client named by `default_client`, else the first saved one (its name, else its id). A failed read is asked again next time. Nothing is fetched on first paint: the drawer and `/t` ask right after they mount, the row menu on the first More press, and the `s` key's registration after the search page or `/t` mounts (`registerDetailCommands`). That last one is a chosen cost: one `GET /settings/integrations` after first paint of every search session. A found client is kept for the session; "none" is not, so one added in Settings shows up on the next ask. A renamed or removed client shows stale until reload (a removed one gives the `no_client` toast).
- **The load path.** One module, `send.ts`, loaded by dynamic import from `DetailActions.svelte` (drawer and `/t`), `RowActions.svelte` and `commands.ts`. It holds the settings read, the label ("Send to qBittorrent"), `POST /send` with `{ hashes: [hash] }` (the default client, so no client id) and the toasts.
- **Drawer and `/t`.** With a client, "Send to <name>" is the primary button and Copy magnet turns secondary. With none, nothing changes. The button shows only with a loaded torrent, and the drawer only loads torrents the viewer may see (the API refuses hidden ones anyway).
- **Row menu.** "Send to <name>" is the first item once a client is known.
- **`s`.** `send.ts` registers `detail.send` itself, once, when a client is known, so with no client the key doesn't exist and does nothing. It sends the drawer's torrent, else the focused row's.
- **Feedback, no retries.** A sent torrent shows a polite "Sent to <name>"; a duplicate shows "Already in <name>". A refusal shows the server's sentence for people; `no_client` (404) says no download client is set up and where to add one; anything else says it couldn't send. Messages in en and zh.
- **Size measurement.** `detail/send.ts` is a stop for the size walkers, like the filters door (`FLOWS_DOOR`, `detailLazy`), and has its own entry, "Send to client (on demand)", 5 KB (measured 4.6 KB: the settings read, the POST, the toasts and the key registration).
- **Edit outside the owned paths:** `filters/block-entry.test.ts` asserted that the drawer sent _no request at all_; the header now reads the settings once, so it asserts no `/filters` request instead.
- **Sizes** (gzip bytes, `npx size-limit --json`, local builds): see the PR description; the drawer and `/t` don't both fit the brief's "+0.3 KB with 0.1 KB headroom" (the brief's two rules conflict there: they had 177 and 135 B of headroom).
- **Runner ruling (§2.26):** Send to client is §10.5's primary action, so it earns the bytes. "Detail drawer" 27.2 → 27.4 KB and "/t/[hash] route" 20.8 → 21.0 KB (measured 27,183 and 20,827 B). Settings KeyboardScreen's first view grew 133 B and is under its 45 KB limit (35,485 B).
- **`block-entry.test.ts`:** the drawer test asserts no `/filters` request of any kind and no non-GET request at all; the header's one GET reads the client.
- **tokens.test.ts** (2 screenshot tests) fails identically on `main` locally (Chromium mismatch); CI is the judge.
