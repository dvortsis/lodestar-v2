# SRC-14a decisions (Sources API v0.6: egress, schedule and agents)

Slice SRC-14a: the first half of SRC-14, which the runner split on 2026-11-02. It covers architecture §18.4 (per-source settings), §18.7 (every connection goes through the plugin's egress setting) and §18.8 (the Sources screen this feeds), and closes the handoffs `2026-11-02-SRC-5.md`, `2026-11-02-SRC-4.md` and `2026-11-02-SRC-2.md` left for SRC-14. **The purge job and the snapshot scrub (the brief's must 5) moved to SRC-14b.**

## The API
- **`GET /sources` and the new `GET /sources/{id}`** give each source:
  - its manifest: kinds, networks, endpoints, risk, consent class;
  - its consent state: `needs`, `consent_version` and `password_required`, as SRC-4 built them;
  - credential names, never values;
  - health and 24-hour yield, as before;
  - `egress`, `schedule` and `agents`.
- **`PATCH /sources/{id}`** now takes `egress`, `schedule` and `agents` as well as `enabled` and `priority`. They're stored in `settings` under `sources.egress.<plugin>`, `sources.schedule.<plugin>` and `sources.agents.<plugin>`, beside SRC-4's keys, with no migration. Their text is the pipeline's to encode (`control::EgressSetting`, `encode_schedule`).
  - They apply at the next start, like `enabled`.
  - A purge drops them with the consent record and the credentials (`set_source_state(Purged)`, one transaction).
  - The settings export never reads `sources.` keys (SRC-4), so they aren't exported.
- **`purge` is the only field still refused** (`409 not_editable`), until SRC-14b.
- **Errors:**
  - `409 route_unavailable` for the interface and bind-address routes, from the route and from the implementation alike;
  - `400 invalid_egress`, `invalid_schedule` and `invalid_agents` for malformed values, checked before the password or the store;
  - one code per field, whichever layer refuses it: agents beyond the plugin's maximum are `400 invalid_agents` too;
  - `428 confirm_required` and `401` for the password, as SRC-4.

## Egress
- **Every enabled plugin's client is built by `EgressFactory`** from its saved setting, with SRC-4's `SourceCredentials` as the factory's `EgressCredentials`. It goes into the plugin's `Kit` (`Kit::for_plugin`, the plugin's own policy) instead of `Kit::default()`. A plugin with no setting goes direct through the factory, so the SSRF guard and the manifest's host list apply to every plugin's request (§12, SRC-5's `Endpoints::manifest`).
  - **Handoff to the first plugin with user-entered endpoints** (SRC-7, Prowlarr): it needs `Endpoints::user_entered`, which the manifest can't express yet.
  - `PipelineConfig::egress` is `None` in tests and when a fixture is served offline, which keeps `Kit::default()` (`NoEgress`: nothing leaves the machine).
- **`PluginEgress::monitor` is spawned for every running plugin with a non-direct route,** every 15 s (`EGRESS_PROBE_EVERY`).
  - The same task logs `pipeline.source_egress_down` and `pipeline.source_egress_up` when the state changes. The reason is a fixed label, never an address.
  - It ends at the plugins' shutdown, and `Pipeline::shutdown` awaits it, aborting it after the plugin stop timeout.
  - A plugin that has stopped shows no live route and has no series.
  - Tested: `the_monitor_follows_the_route_and_stops_at_shutdown`.
- **The kill switch has its own error, `HttpError::EgressDown`** (must 1). `HostLimiter::record` ignores it, as it ignores `NoEgress`, so a route outage doesn't back off the plugin's hosts. It's used for:
  - a refusal before sending;
  - an abort in flight;
  - a request that failed to connect or timed out where the re-probe then finds the route down (self-review). This is a route that died inside the 10 s a good SOCKS5 probe is trusted. It counts as a kill-switch abort, not a transport failure.
  
  Policy refusals stay `Transport`, as SRC-5 set them. Tested: `a_kill_switch_refusal_doesnt_back_the_host_off` and `a_route_that_dies_between_probes_is_the_kill_switchs_error_not_the_hosts`.
- **The network-interface and bind-address routes aren't offered** (must 2, the runner's #380 ruling). Their DNS lookups go through the system resolver, outside the route, and owner question q-egress-dns-leak is still open. The API refuses them with `409 route_unavailable`, and the message recommends a whole-container VPN or the VPN's SOCKS5 proxy. The stored encoding can't express them either, so a hand edit can't select one. They come back when a resolver bound to the route exists, or when the owner accepts the leak.
- **SOCKS5 takes `host:port`**: a DNS name, an IPv4 literal or a bracketed IPv6 literal.
  - A name is resolved once, when the plugin starts, through the factory's resolver (`EgressFactory::build_socks5`). Docker service names such as `gluetun:1080` work this way.
  - A name that doesn't resolve, or resolves only to addresses no proxy can be at, leaves the plugin's egress down for good (`DownReason::ProxyUnresolved`), with the reason shown, until the next start. Re-resolving on each probe would need a route the factory can rebuild. **Known limit:** a proxy container that starts after Lodestar needs a restart. Compose's `depends_on` covers the usual case.
  - **Refused as a proxy address:** the unspecified address (`0.0.0.0`, `::`, which connects to this machine), multicast and broadcast. The API, the stored setting and the factory each refuse them; the factory skips such answers for a name and takes the first usable one.
  - **The proxies resolve concurrently at start,** one task per enabled plugin, so several slow or failing names cost one 5 s timeout, not one each.
- **DNS on SOCKS5, when the user leaves it on `auto`, follows the plugin's endpoints, not the proxy's address** (must 3). This is the runner's #394 ruling, which **replaces the #380 ruling** (flagged to the owner, §2.19).
  - **Plugins pinned to their manifest's hosts** (`Endpoints::manifest`, every plugin wired today) get `proxy` (`socks5h`), so no lookup leaves outside the tunnel. A name can't steer such a request anywhere else: the host list allows only the manifest's hosts.
  - **Plugins whose endpoints the user enters** (`Endpoints::user_entered`, SRC-7's Prowlarr first) get `local`: Lodestar resolves through its address checks, so a public name that the proxy would resolve to its own network can't reach that network. SRC-15b makes the choice explicit for them.
  - **Why the #380 rule went:** nearly every SOCKS5 proxy a self-hosted user can reach is on a private, loopback or CGNAT address: gluetun's on 172.x, Mullvad's in-tunnel `10.64.0.1`, Tor's or a VPN client's on 127.0.0.1. "Local DNS when the proxy is on the LAN" leaked every lookup outside the tunnel for exactly the users who chose a proxy.
  - The stored value stays the literal `auto`, so the rule can change without rewriting anyone's setting. An explicit `dns` wins, and `egress.setting.dns` is left out when the user didn't choose.
  - **The help text** (the `SocksDns` and `EgressSetting.dns` schema docs, and the warning below) states the trade.
  - **The warning** "The proxy resolves names, so lookups stay inside the tunnel. Because the proxy is on your network, a public name that resolves to one of your devices would reach that device…" shows whenever the proxy resolves names (chosen, or by `auto`) and is on the LAN.
    - While the source runs on what's saved, it's judged by the address the name resolved to at start.
    - Otherwise it's judged by the saved setting: a literal's address, or nothing for a name not yet resolved.
    - Once the user changes the setting, the warnings follow the new one at once, not at the next restart (runner I2). `EgressLive::setting` records what the running route was built from.
  - Tested at private, loopback, CGNAT (`100.64/10`) and public proxy addresses, for both endpoint kinds: `auto_dns_follows_the_endpoints_not_the_proxys_address`.
- **`HTTPS_PROXY` and `ALL_PROXY`** (must 1). When either is set (upper or lower case):
  - each running source that connects directly is logged once per start as `pipeline.source_proxy_env_ignored`;
  - each source whose route is direct, running or not (it will connect directly when it starts), gets the warning "HTTPS_PROXY or ALL_PROXY is set, but source plugins never use it…" in `egress.warnings`.
- **Changing egress needs the admin password, for every class** (`428 confirm_required` without it, `401` for a wrong one, checked before the store is read). The route is what keeps a source's traffic on the VPN, so a stolen session mustn't be able to take a Restricted or Overlay source off it. Applying the same rule to every class keeps it simple. `Control::update_source` refuses an unconfirmed egress change too, so the rule doesn't rest on the route alone. **Refinement, the runner's call (§2.19):** SRC-4 asks for the password only when enabling Restricted and Overlay sources.
- **Egress changes don't re-check consent.** The consent version is bound to the class's text and the endpoint list (SRC-4's `consent::version`), and egress changes neither. The External consent text names the egress setting, but the user is changing it themselves, behind the password.
- **Status:** `egress.live` gives the running source's state (`direct`, `unchecked`, `up` or `down`), the down reason, SRC-5's privacy notice and the counters. It's null when the source isn't running.
- **`/metrics`:** `source_egress_up{plugin,route}`, `source_egress_requests_total{plugin,outcome}` and `source_egress_trips_total{plugin}`, as SRC-5 named them in `docs/metrics.md`. Only running plugins have series.

## An unreadable egress setting fails closed (runner #394, blocking)
- **A saved egress that doesn't decode is never taken as direct.** That covers a rollback from a version with a route this one can't read, a stricter parser, or a damaged row.
  - The plugin's client is built down for good: `EgressFactory::unavailable(…, DownReason::SettingUnreadable, …)`. Its kill switch refuses every request with `EgressDown`.
  - `GET /sources` reports `egress.setting: null` and the warning "This source's saved network setting couldn't be read, so its requests are refused rather than sent directly…". There's no `direct` in the response.
  - Saving any route replaces it.
- **The other settings keep falling back to their defaults:** an unreadable priority, schedule or agents value can't send traffic around the VPN.
- Tested at start with a route a newer build might add (`interface wg0`) and a damaged SOCKS5 value: `an_unreadable_egress_setting_refuses_every_request`.

## Plugins and `EgressDown` (runner #394, I1)
- **Plugin contract:** while a route is down, `EgressDown` comes back at once, and nothing paces a retry (the host isn't backed off). A plugin must not retry in a loop; it waits at least its poll interval. The rule is in `HttpError::EgressDown`'s documentation.
- No HTTP plugin is wired yet. **Handoff to SRC-14b** (which wires SRC-7): a route-level delay, so the contract doesn't rest on each plugin alone.

## Settings on a purged source
- **Egress, schedule and agents can be written on a purged source,** as credentials could already (SRC-4 left the question to this slice). A purged source is a fresh, disabled one, and setting its VPN route before enabling it again is the safe order.
- **Handoff to SRC-14b:** the purge job ends by setting Purged, which drops these keys, the consent record and the credentials in one transaction. A write made while the job runs is dropped with them.

## Schedule and agents: stored, checked and shown, not enforced (runner, 2026-11-02)
- **Schedule:**
  - up to 8 windows of `HH:MM-HH:MM` in the server's local time, put in canonical form;
  - an end at or before the start wraps past midnight;
  - `[]` runs the source at any time;
  - left unset, the plugin's `Policy::schedule` applies, and is reported as `schedule.default`.
- **Agents:** 1 to `Policy::max_agents`, a new field whose strict default is 1, so a plugin that doesn't declare it can't be changed. No plugin declares more yet.
- **`schedule.enforced` and `agents.enforced` are always false.** The runner ruled out checking the window only at start: a plugin would run past its window and look enforced when it isn't. SRC-15a labels them "not active yet".
- **Handoff to scheduler v2 (§18.4):** enforce the windows while plugins run (start, and stop at the window's end), and give each plugin its agent count. Then set `enforced` to true.
- **No reset to the plugin's default yet.** The UI sends `schedule.default` (or one agent) to get it back. A `null` that removes the saved value can come with SRC-15a if it's wanted.
- **An unreadable saved value** is logged once, at start (`pipeline.source_setting_unreadable`). For a schedule or agents value (and a priority) its default applies; an unreadable egress setting doesn't fall back to direct but fails closed (above). `GET /sources` reads the values on every call but doesn't log. *(Corrected by SRC-14b.)*

## Verification stays off (must 4) — flag for the owner (§2.19)
- SRC-2's `PipelineConfig::verify_unverified` stays false. No API, config key or setting reaches it: the binary never sets it, `PATCH /sources/{id}` has no such field (an unknown field is refused, `400`), and the settings registry has no `sources` section.
- **Why:** a per-source pending cap in the pool, or a Low priority class, isn't built. Dead swarms from one source could hold about 30k of the pool's 200k keys, and `evict_one` ignores the source.
- **Handoff:** the cap or the class (scheduler v2 or the pool's owner), then the switch.
- **Flagged to the owner through the runner:** §18.4 and §18.5 expect unverified items to be verified in the background; until then they stay unverified unless the crawler finds the same hash.

## Secrets (must 7)
- Credentials stay names only, as in SRC-4. `SourcePatch`'s `Debug` skips the password and now prints `egress`, `schedule` and `agents`. None of them is secret: a SOCKS5 proxy's user name and password are credentials, kept apart under `PATCH /sources/{id}/credentials`.
- Down reasons, log labels and metric labels name a rule or a state, never an address, URL or credential.

## Log events
`pipeline.source_egress_down` (warn), `pipeline.source_egress_up` (info), `pipeline.source_proxy_env_ignored` (warn) and `pipeline.source_setting_unreadable` (warn). They're in the logs catalogue, with English and Chinese labels in the Logging settings screen. An unreadable saved schedule or agents value keeps its default, as an unreadable priority does; an unreadable egress setting fails closed instead (see above). *(Corrected by SRC-14b.)*
