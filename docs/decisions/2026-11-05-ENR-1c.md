# ENR-1c decisions (enrichment polish before the plugins land)

Slice ENR-1c (runner, 2026-11-05T15:34Z): the polish from ENR-1b's (#497) review, closed before ENR-4 and ENR-5 add real plugins. Read it with `2026-11-05-ENR-1.md` and `2026-11-05-ENR-1b.md`. Where they differ, this file wins.

- **An adult-enrichment source is one the host lists, not a kind** (#498 self-review). `Kind::Enrichment` alone isn't enough: the torrent cache is that kind, and the server always registers it.
  - Before this change it counted as an adult enricher, so it could attach adult sections, and the commit hook ran in every real run.
  - `EnrichSources::of` now also takes `PipelineConfig::adult_enrichers`, the manifest ids of the `AdultEnrichSource` plugins the host runs. Empty by default, so none until ENR-4 or ENR-5 is wired in.
  - This adds a field to `PipelineConfig` in `lib.rs`, beside `torrent_cache`. Every caller builds the config with `..Default::default()`.
- **One test for a match** (`adult_enrich::is_match`): an adult section from an adult-enrichment source. The strategy code isn't part of it, because the writer's gate (`unverified::ingest`) doesn't read it either. Intake and the writer can't disagree about which discoveries are matches. This supersedes the ENR-1b bullet that described the test as "strategy 202 and an adult section".
- **An adult-enrichment source is never always adult.**
  - `AdultEnrichSource::new` refuses such a plugin (`NotAdmitted`), so none can run.
  - `EnrichSources::of` also refuses a listed manifest that claims both (`adult_enrich::admitted`), and a `debug_assert!` makes that a bug in debug builds.
  - So a plugin can't be both an enricher and always adult, and a refused one never runs to have its answers stored as sightings. The refusal is `NotAdmitted`, which also covers a manifest that isn't an enrichment source.
  - A match isn't a find, so it never sets the source's bit on a torrent, and an always-adult mask on it would never apply.
  - No shipped plugin is both.
- **A section-only claim from an enrichment source that isn't listed is refused** (#502 review). Examples are the torrent cache, or an `AdultEnrichSource` the host forgot to list or whose id was renamed. Its answers aren't finds, so nothing is stored and it gains no bit on the torrent. Storing them as bare sightings would set its bit on every matched torrent (the source facet, "found by" and purge) and count them as rediscoveries. ENR-1b refused them, and this keeps that. `EnrichSources` carries both sets: the listed ones, and every registered `Kind::Enrichment` source.
  - **A startup warning** for a registered `Kind::Enrichment` manifest that is neither listed nor the torrent cache needs a new log event. That means the catalogue in `log_events.rs`, its golden list and the web logging settings' names and messages, all outside this slice. It's left for the host-wiring slice, the first that can register one.
- **A section-only claim from any other source is a bare sighting.** The section is dropped, and what's left is the key with no claims. It's stored and counted exactly as a bare sighting of that key would be by the writer:
  - On a stored torrent, the source gains its bit (`put_unverified` with no claims), and it's a rediscovery (`touched`). For an always-adult source that means its mask really applies. ENR-1b's push of the id to `adult` without the bit didn't apply it.
  - On a key nothing stores, it's refused (`Put::Bare`). The writer doesn't fetch, and a bare key reaches the fetch pool only through intake.
  - On a key an unverified item holds, it's that item's sighting, as any claim from the source would be. The item gains the source and its time, and a public source clears the item's private mark (a private one never does). It's counted as `existing`. A bare sighting of the same key would go to intake's fetch path instead. This path stores nothing new, since any claim from the source already has the same effect.
- **One daily cap for user interest and background** (plan Q15: "user-interest lookups jump the queue within the same cap"; the runner, an owner-decision compliance fix). This supersedes ENR-1's "doesn't count against the daily cap".
  - ENR-1 counted only background lookups against the 5,000 a day, so opened drawers could add more. With ENR-7's API limits that was about 9,350 a day per service.
  - Now an opened item still goes first, but every lookup takes one from the same UTC day's budget.
  - When the budget is spent, an opened item waits first in line, and a background item goes back to the front of its queue, so no item loses its place.
  - An item opened while a plugin-wide condition fails (Show adult content off, the kill switch, the source off or unconsented) is still dropped, never sent later.
  - `Config::per_day` now counts both, and `AdultEnrichSource::new` clamps it to `BACKGROUND_PER_DAY`, so a host can't set it above the owner's cap.
  - `Config::background` switches the backfill off; the tests use it instead of a zero budget. `Config::idle` is the wait before trying again (60 s by default). `new` floors it at 10 ms (`MIN_IDLE`), so a host can't make the runtime busy-loop.
  - An opened item held for the budget is checked against every condition again when it's tried. If Show adult content went off meanwhile, it's dropped.
  - A store error in the gate drops an opened item (`Step::Wait`). A budget count that can't be read or written holds it (`Step::Spent`), failing closed. A read error is never a fresh budget (#502 review).
  - **A stored day later than today** (the clock was ahead, then stepped back; runner's call). `Budget::load` normalises it on every read: it becomes today with its count, and is written back whether or not a lookup is taken.
    - So a budget spent on a future day is never spent until that day. It counts as today's, and the real next day starts fresh (#502 review: the old code refused before writing, so a budget spent in 2030 stayed spent until 2030).
    - **Accepted cost:** after a step back is normalised to today, stepping forward again can hand out a fresh budget on the same real day. That's at most one extra day's cap per clock correction across midnight. The runner chose this over any risk of starving the budget.
  - Intake doesn't count an enrichment answer as harvested (`is_match`): a listed source's section, or an unlisted enrichment source's section-only claim, which is refused. An unlisted source's section that comes with other claims is stored as its find, so it is harvested.
  - `BACKGROUND_PER_DAY` keeps its name for its callers; its doc in `crates/sources/src/enrich.rs` now says it's the one cap. That's a doc-only line outside this slice's paths, named to the runner.
- **The commit hook's failures** (`Writer::mark_rewritten`):
  - When `enrich::mark_matched` fails (a busy or failed claims read), every rewritten row is marked for the backfill and `reenrich` is raised, as `adult_by_source` does. The error is still logged and counted.
  - The hook does nothing while no adult-enrichment source is listed, so it costs nothing until ENR-4 or ENR-5 is wired in.
  - When the fallback mark fails too, that error is logged as well. The rows keep their kind until the next rules or parser change re-marks them: the same window ENR-1b accepts for a crash between the commit and the mark. The same holds for a failed mark in `ingest`.
  - A match stored in an earlier run under a source that isn't listed now isn't re-marked by the hook. It keeps its kind until the next rules or parser change. This is accepted: the kind is a refinement, never a safety decision (#502 review).
- **A failed mark in `ingest` is logged and counted** (`ENRICHMENT_FAILED`, `UnverifiedStats::enrich_failed`, one per failed store call), never dropped. So is a failed `apply_matches`. The flag still starts a pass.
- **`enrich::stored_match`'s doc** now says what ingest guarantees: sections are kept only from an enrichment source, only on a stored torrent, and never through a private source.
- **`writer.rs` hunks** (shared with RP-4, kept minimal):
  - `mark_rewritten`'s early return without enrichment sources, the fallback mark and its error log;
  - `w.enrichers` in `a_rewritten_match_is_marked_at_commit`;
  - the new test `a_failed_match_read_marks_every_rewritten_row`.
- **`crates/pipeline/tests/adult_enrich.proptest-regressions`** is committed on purpose. It pins the seed of a real stall: an opened item held while Show adult content was off blocked the queue. That was fixed before the push, and the case replays every run.
- **Tests.** Each fails without its fix; I checked the writer fallback and the counted mark by reverting them.
  - the writer hook marks every row when the claims read fails, and does nothing with no adult-enrichment source listed;
  - a failed backfill mark in `ingest` is counted and still raises the flag;
  - a section-only claim from an always-adult source sets its bit and is a rediscovery; from another source it's a rediscovery on a stored key and refused on an unstored one;
  - a section-only claim on an unverified item is its sighting, private and public;
  - interest and background never exceed one day's cap together, and opened items go first;
  - an opened item meeting a spent budget waits first in line and is asked the next day; with Show adult content off by then, it's never asked (fails if the held item is dropped);
  - the cap is clamped to the owner's;
  - a clock step back keeps the count, a budget spent on a far-future day leaves the real next day its whole cap, and an unreadable budget is spent;
  - `is_match` ignores the strategy code;
  - only listed adult enrichers count, and the torrent cache's kind alone doesn't;
  - an always-adult plugin is refused by `AdultEnrichSource::new`, and a listed always-adult manifest is a debug-build bug.
- **Left for the runner:** a `crates/sources-plugins` test that no shipped manifest is both an enrichment source and always adult (outside this slice's paths). `AdultEnrichSource::new` already refuses one at construction.

  No fixed sleeps.
