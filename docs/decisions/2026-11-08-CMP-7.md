# CMP-7 decisions

Companion compose services and Unraid templates (plan `docs/plan/2026-11-06-v06-companions.md` §4.3 CMP-7 and Q11, architecture §11 and §18.10). These are the slice's own decisions under the brief (owner §2.33), flagged to the owner by the runner (§2.19). None loosens an owner decision. None adds a capability, mount or host-network mode beyond what the brief allows, and none stores a VPN key.

## Q11: no pre-filled Unraid link, so a file plus values
- **Finding: Unraid can't open a template pre-filled from a link.**
  - Add Container (`/Docker/AddContainer`) takes one parameter, `xmlTemplate=<type>:<path>`. It reads the template only with `is_file($path)` on the server, so the template must already be on the flash drive. A URL is ignored. No other query parameter fills a field. Source: [`CreateDocker.php`](https://github.com/unraid/webgui/blob/master/emhttp/plugins/dynamix.docker.manager/include/CreateDocker.php), the "LOAD TEMPLATE" block (about lines 333–336), read 2026-11-08T14:00Z.
  - The "Template repositories" URL field was removed in Unraid 6.10.0-rc1. Source: [forum topic 112170](https://forums.unraid.net/topic/112170-allow-template-repositories-to-be-hosted-from-other-sources/).
  - We found no entry point in Community Applications that takes a template from a link either. Its templates come from its own feed.
- **So `unraid()` returns `UnraidTemplate { file_name, xml, fields }`.**
  - `file_name` is `my-<container name>.xml`, Unraid's naming for a user template. You save it to `TEMPLATES_USER` (`/boot/config/plugins/dockerMan/templates-user`).
  - `fields` holds each label and value, in form order, for filling the form by hand.
  - `add_container_path()` gives `/Docker/AddContainer?xmlTemplate=user:<templates-user>/<file>`. That opens the template once it's saved. The UI (CMP-9) puts the server's address in front.
- **Unraid pastes `ExtraParams` into its `docker create` line unescaped** ([`Helpers.php`](https://github.com/unraid/webgui/blob/master/emhttp/plugins/dynamix.docker.manager/include/Helpers.php), `xmlToCommand`). So that field only ever holds fixed flags, port numbers and a `ContainerName`, none of which can hold a space or a shell character. A test checks every generated `ExtraParams` against that character set.

## API (what CMP-5 and CMP-6 call)
- **`compose::compose(&Catalogue, &CompanionId, &ServiceInput) -> Result<String, TemplateError>`** is what `lodestar companion compose <id>` prints. **`unraid::unraid(...)` takes the same arguments and returns `Vec<UnraidTemplate>`:** gluetun's template first when it's generated, because the companion's can't be applied before gluetun exists, then the companion's.
- **`ServiceInput` holds only closed values:**
  - `Puid` and `Pgid`;
  - `network: NetworkName`, the user-defined network Lodestar is on;
  - `route: Route::{Direct, Gluetun, ExistingGluetun(ContainerName)}`;
  - `paths: Paths { config, downloads }` (`HostPath`s);
  - `publish: Vec<Publish { port: PortName, bind: Bind::{Loopback, Lan}, host_port: PortNumber }>`;
  - `data: DataFolders`;
  - `taken: Vec<HostPath>`: other companions' folders that CMP-5 and CMP-6 know about.
- **`TemplateError` is a closed enum with a stable `code()`** (`awaiting_pin`, `inside_data_folder`, `p2p_through_vpn`, …). It carries no input value. Nothing here can panic outside tests.
- **An image awaiting its pin is refused** (`awaiting_pin`), through CMP-0's `Entry::renderable`.
- **Each companion's mounts and variables are a profile in code, keyed by catalogue id.** The catalogue has no field for them, so adding one is reviewed code rather than data. The profiles are qBittorrent, Prowlarr, gluetun and FlareSolverr. FlareSolverr's is ready for CMP-12's catalogue entry and is tested against a test entry until then. An entry without a profile, or without the template id in its `templates`, is refused (`no_template`).
- **`NetworkMode` isn't taken as input.** A routed companion needs both the network (for gluetun) and the route, so the input is `NetworkName` plus `Route`. The `network_mode` value is still `NetworkMode::ServiceGluetun.compose_value()`.

## Output rules
- **YAML:** a small tree written line by line.
  - Every key and string goes through `serde_json`. Port numbers and the two booleans (`external`, `create_host_path`) are JSON numbers and booleans, because compose needs those types.
  - A string holding `$` is refused (`interpolation`), because compose interpolates inside quotes.
  - A string holding a control character, U+2028, U+2029 or U+FEFF is refused (`unprintable`). YAML can't hold DEL or the C1 controls in a quoted string, and YAML 1.1 reads U+2028 and U+2029 as line breaks. No closed input holds any of them; this keeps the writer safe on its own.
  - Volumes and ports use compose's long syntax, so no value is joined to another with `:`.
  - Comments are fixed text from the code.
  - Bind mounts set `create_host_path: true`, as the short syntax would.
- **XML:** written only through `quick-xml`'s writer.
- **`TZ` is fixed at `Etc/UTC`** (log times are UTC, as Lodestar's are) **and `UMASK` at `022`.** Neither is an input.
- **Default bind address per port: none.** Every catalogue port stays on the Docker network unless a `Publish` names it. Publishing is per port, either `Bind::Loopback` (`127.0.0.1`) or `Bind::Lan` (every address).
  - Why: Lodestar reaches a companion by name on the shared network, so nothing needs publishing to work. qBittorrent's catalogue peer port (6881) would also clash with Lodestar's own DHT port in the default compose file.
  - On Unraid, `Lan` is a Port field. `Loopback` has no field, so it becomes a `--publish=127.0.0.1:H:C/proto` flag.
- **Through gluetun:**
  - The companion has `network_mode: service:gluetun` and `depends_on: gluetun: service_healthy`, and no ports or networks of its own.
  - Its published ports move to gluetun.
  - gluetun joins the network with the companion's name as an alias, so Lodestar and CMP-8a still reach it by that name. On Unraid that's `--network-alias=<name>`; the companion template is `Network: none` with `--network=container:gluetun`, following `packaging/unraid/lodestar-gluetun.xml`.
- **A gluetun you already run is kept** (`Route::ExistingGluetun(name)`, found in self-review). Lodestar's own VPN setup (`packaging/unraid/lodestar-gluetun.xml`, `docs/operations.md`) already has a container named `gluetun`, often from Community Applications' `my-gluetun.xml`. Saving and applying a generated `my-gluetun.xml` would replace that file and container, VPN key included.
  - With this route nothing is generated for gluetun. The companion gets `network_mode: container:<name>`, or `--network=container:<name>` on Unraid. That's fixed text plus a closed `ContainerName`.
  - It can't publish a port (`publish_on_existing`): the port would belong on a container this doesn't write.
  - Lodestar then reaches the companion at gluetun's name (note for CMP-8a).
  - Every Unraid template's Overview, the compose header and `unraid()`'s docs say that a container or template of the same name is replaced (Unraid) or blocks the start (compose).
  - **For the runner:** a different container name for the generated gluetun is a catalogue question (CMP-0, CMP-13), so it isn't changed here.
- **Port numbers follow what the image needs** (self-review):
  - A peer port listens inside on the host port it's published on, and qBittorrent's `TORRENTING_PORT` is set to it, so peers reach the port qBittorrent announces. All of an entry's peer ports share one host port (`port_remap`).
  - A port the image is told about that isn't a peer port (qBittorrent's `WEBUI_PORT`) must be published on its own number (`port_remap`). linuxserver.io's qBittorrent checks the port its web UI is reached on.
  - A peer port can't be published on `127.0.0.1` (`p2p_loopback`), where no peer reaches it.
  - gluetun's control port can't be published on your network (`lan_refused`). Its control server reports the public address and can change the VPN's state.
- **A peer port can't be published through gluetun** (`p2p_through_vpn`). Inbound peers through a VPN need a port your provider forwards. Publishing it on the host would answer peers from your own address, outside the tunnel. Forwarding is provider-specific, so you set it in gluetun yourself.
- **gluetun gets one capability and one device, both from its upstream setup** (README "Setup" and the wiki's Docker Compose example, github.com/qdm12/gluetun):
  - `NET_ADMIN` lets it create the tunnel interface, set routes and run its firewall, which is the kill switch;
  - `/dev/net/tun` is the kernel tunnel device WireGuard and OpenVPN use.
  - Nothing else gets a capability or a device, and nothing is `privileged`, `pid: host` or `network_mode: host`.
  - gluetun doesn't get `FIREWALL_INPUT_PORTS`. It would open the companion's ports on gluetun's non-VPN interface, and container-to-container traffic on the shared network doesn't need it.
- **gluetun's VPN settings are placeholders:**
  - compose writes `FILL_IN_YOURSELF` for `VPN_SERVICE_PROVIDER`, `WIREGUARD_PRIVATE_KEY` and `WIREGUARD_ADDRESSES`, each with a comment;
  - Unraid writes them empty, required and always shown. The key and address are masked; the provider isn't, so you can check what you typed.
  - gluetun won't start with them, and a routed companion can't start without gluetun, so nothing leaves outside the VPN before you fill them in. `VPN_TYPE` is fixed at `wireguard`.

## Host paths
- **Lodestar's data folders (`DataFolders`)** are the main folder plus Unraid's optional hot and cold paths, as the template or you give them. An empty hot or cold value, which is how Unraid's template stores an unset one, counts as unset. Natively they come from `DataFolder::from_running`, which resolves symlinks with `canonicalize` first (`data_folder_unreadable` if it can't).
  - **Unraid shows one share under every pool and disk.** `/mnt/user/x`, `/mnt/user0/x`, `/mnt/cache/x` and `/mnt/disk1/x` are the same files. So two paths under `/mnt` are also compared from the share down, whatever the pool. That's stricter than needed on a non-Unraid host with unrelated `/mnt/a/x` and `/mnt/b/x`, which is the safe direction (found in self-review).
  - A companion folder that is, holds or sits inside one is refused (`inside_data_folder`).
  - Comparison ignores case, like `HostPath`'s own checks.
  - `DataFolder` takes any clean absolute path, because it's compared and never written. `/var/lib/lodestar` is valid here, though a `HostPath` refuses it.
  - `DataFolders::none()` is only for data in a Docker named volume. That lives under `/var/lib/docker`, which `HostPath` already refuses.
- **Another companion's folder is refused** (`inside_other_companion`, the crate README's CMP-7 contract):
  - any path inside another catalogue companion's `appdata/<name>`, so qBittorrent can't be given `/mnt/user/appdata/prowlarr`, where Prowlarr's `ApiKey` lives;
  - any path that overlaps one in `taken`, either way round and through Unraid's aliases. The library can't know where another companion was put elsewhere, so CMP-5 and CMP-6 pass the folders they generated.
- **Any path component starting with `.` is refused** (`dot_folder`). This settles CMP-0's open choice for `/mnt/<letter>/Users/<u>/.ssh` under Docker Desktop's WSL, with one rule for every place: no companion needs a hidden folder, and a hidden folder is where keys and per-user state live.
- **Symlinks can't be seen in a path typed for another machine.** The output and the Unraid field help say to mount real folders only.

## Tests and layout
- **Golden files** are in `crates/companions/tests/golden/compose/<id>[-gluetun|-existing].yml` and `golden/unraid/<id>[-gluetun|-existing]/my-<name>.xml`, plus `keywords.yml` and `keywords.xml`. Those two cover a network named `null` and paths like `/mnt/yes/on/0x10` and `/mnt/user/My Downloads/1e3 true`. The goldens use a test catalogue with the digest `abab…`.
- **Packaging examples** (`packaging/companions/`) are generated from the compiled-in catalogue and checked byte for byte. An image still awaiting its pin is written with the digest `00…01`, which no registry serves; the catalogue refuses an all-zero placeholder. The test also fails on a leftover file there. When CMP-13 pins the images, it fails until the examples are regenerated (`UPDATE_GOLDEN=1 cargo test -p lodestar-companions --test templates`).
- **The property test** puts text containing newlines, `: `, `---`, `&`, `*`, `<`, quotes, `\`, `#`, `$` and NUL into every input that accepts text: both `HostPath`s, `NetworkName`, `Puid`, `Pgid` and a `DataFolder`.
  - A value the parser accepts must leave the YAML and XML structure unchanged. The structure is the YAML with every JSON string replaced and each one checked to parse, and the XML's element and attribute names.
  - The test also checks for no `---` or `...` line and no XML entity other than the five predefined ones.
  - The newtypes refuse most of that text first, so a second property test in `compose.rs` feeds any string straight to the YAML writer. Each key and value is either refused or written as one JSON string on its own line that reads back as itself.
