# B13 decisions (#77)

Siblings ("Related", §10.5), Compare batch detail (§10.6) and `/discover` (§10.7). Moved here from §16 when decisions moved to this folder.

- **Routes:** `GET /torrents/{hash}/siblings` and `POST /compare` live in `api/src/compare.rs`, `GET /discover` in `api/src/discover.rs`, with their DTOs in `dto/compare.rs` and `dto/discover.rs`. `torrents.rs` only makes `parse_hash` and `hex` crate-visible, and `search.rs` only `enrich`, so every row is filled the way search fills it.
- **A section that can't be served is typed, never empty-as-zero.** `HitGroup { hits, reason, status, truncated }`: `status` is `available` or `unavailable`, and `reason` is a stable key (`search_disabled`, `no_title`, `needs_swarm_history`, `needs_resolution_history`, `needs_payload_signature`, `needs_piece_roots`). Siblings' groups and Discover's Rising and Recently resolved all use it.
- **"Same title identity" (other versions):** two torrents are versions of one work when their stored enrichment records agree on all of these:
  - the effective title's words, as search's tokenizer folds them (only the `Part` tokens, so `Spider-Man`, `Spider Man` and `SpiderMan` are all `spider man`, and diacritics and case fold away);
  - the sets of `year`, `season`, `episode` and `absolute` spans, compared as sets of the rendered spans. "Absent" is a value of its own: a release with no year isn't the same work as one with 2008, a season pack isn't one of its episodes, and absolute numbering never equals season numbering.
  - Alternative titles, quality, source, codec and group play no part.
  - **Finding them:** the index is asked for the title's words as a phrase in `title`, plus a range per span on `year`, `season` and `episode`, through the base query (`shown`, below). That over-matches (a longer title, a wider span) and never under-matches; the identity check then decides on the stored records. Candidates are the best 1,000 by relevance (`title`'s BM25 favours the exact title), self excluded, and the first 20 that match are listed (`truncated` when there are more). The order is search's relevance; the swarm and freshness priors join it with M4. **Known limit:** a short, common title with no year, season or episode (`Up`, `Heat`) narrows little, so its siblings can rank past the 1,000-candidate window and be missed; `truncated` doesn't report that. A title-identity key in the index (an exact-match keyword of the normalized title plus its spans) would close it, and needs a schema bump in the search crate.
  - A torrent with no parsed title is `unavailable: no_title`; without search it's `search_disabled`.
- **Identical-payload clones and the same file elsewhere** are `unavailable` (`needs_payload_signature`, `needs_piece_roots`) until M7's schema bump #2 adds `payload_sig` and per-file `pieces_root` to the index.
- **Compare (`POST /compare {hashes}`):** 2–5 distinct hashes; fewer or more is a `400 compare_count`, a repeat a `400 duplicate_hash`, a malformed one a `400 bad_hash`, all with `field: "hashes"`.
  - **Attributes** are the stored record's release fields (`title`, `year`, `res`, `vcodec`, `group`, …; repeated ones comma-joined). Every column carries every key any of them has, null where it has none. `differs` is computed on the server per key: true when any column's value (null included) differs from the first's.
  - **The shared scale** is `scale_bytes`, the largest `size` in the set; the composition bars divide by it.
  - **The file diff** matches files by decoded path (inside the torrent, `/`-joined) plus size. Padding files are left out. `common` is the files every torrent has, in the first torrent's order; `only[i]` is torrent *i*'s files that no other torrent has, in its own order. With three or more torrents, a file some but not all have is in neither list. Each list carries its full `count` and at most 2,000 entries, with `truncated` when the count is larger.
  - **Bounded memory:** the store only decodes a whole file-tree blob, so streaming means one decoded tree held at a time. The shared reader is locked only for each hash lookup and each blob read, never across the comparison. Between passes, each torrent keeps only its sorted 128-bit keys (two SipHash runs over path and size), 16 bytes a file: five maximal trees (200,000 files, metainfo's cap) cost about 16 MB. A streaming decoder in the store would cut the peak tree, not the keys.
- **What's withheld, and how it reads:** a torrent hidden by a filter rule, or Adult while Adult is hidden, is in Compare exactly an unknown hash: `404 torrent_not_found`, the same body, which names nothing. Siblings answers for a hidden torrent (the drawer opens one from `hidden=true`) but 404s for Adult while hidden, as detail does with B17. Neither lists a hidden or Adult torrent among siblings. Stored state decides as well as the index, so a torrent reclassified since the last index commit stays out.
- **One base query, following "Show adult content".** Siblings build their index query with B17's `search::base_query(node, Visibility { hidden: false, adult }).query()` (`discover::shown`), and Discover's Newest is `search::search_get` itself (sorted `-discovered`, with no visibility clause of its own), so the hidden-torrent and Adult clauses, leases, cursors, counts and the `adult_hidden` notice are search's. `newest.notices` carries that notice, so the `adult` tab can say why it's empty. Siblings and Compare read `show_adult` once per request and use the same value for the index query and the stored-state check (`discover::withheld`); with it on, Adult siblings are listed and an Adult hash compares, and a hidden torrent still doesn't. Siblings lock the shared reader per candidate, not across the 1,000.
- **Discover:** `GET /discover?type=&limit=&cursor=` returns all three sections. `type` is checked against the content-type names (never pasted into a query as text; `400 unknown_type`). Newest pages like search (`limit` 1–200, default 50; `next_cursor` bound to its tab). Adult while hidden is excluded entirely, including the `type=adult` tab, which is empty (§20.9).
  - **Rising** is `unavailable: needs_swarm_history` until M4's continuation of #48 serves swarm history; then it's the top N by `swarm_trend`.
  - **Recently resolved** is `unavailable: needs_resolution_history`. The store can't tell when a torrent's resolution changed: `torrent_parsed` has no timestamp, `reindex_log` no time or reason, and only the current `resolved` is kept. **B8 (the M5 migration) should add** `torrent_parsed.resolved_at INTEGER` (unix seconds), set when enrichment first writes a non-null `resolved` for a torrent whose previous record was ambiguous or unresolved (or whose title changed), with an index on it. Recently resolved is then the newest by `resolved_at`, through the same base query.
