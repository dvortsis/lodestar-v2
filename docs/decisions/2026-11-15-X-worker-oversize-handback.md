# X-worker-oversize-handback decisions

**Where it came from:** the build was parked on `parked/X-worker-oversize-handback` (be79123a, 2026-11-14Z). The runner relaunched it as this slice on 2026-11-15Z: the parked commit, carried over to current `main`, plus the refusal-before-grant change and the tests the runner asked for (below). The runner's review of #939 (head 69630e87) then made the calls marked "review" below (§2.19).

This builds on X-fetch-room-fix (`2026-11-14-X-fetch-room-fix.md`), which held a worker's largest dict to just under 3 MiB and left larger ones to this slice. Architecture §19 (workers and the coordinator). This file says only what the code now does.

## Calls
- **A key too large for a remote worker goes to the built-in worker instead of being lost.** A worker still reports it as it always has: a `Lost` outcome with the oversize reason, under its lease's token. No wire change and no new protocol version.
  - **The refusal check comes first** (runner). Before any grant, the server asks its sink whether the built-in worker refuses the key (`InboundSink::refuses_local`: held, or blocked by the filter, the same check its own intake runs). A refused key ends there as a blocked loss, remembered as any blocked loss is (`LeaseAuthority::report`). It is never granted to the built-in worker or put in its pool. In the parked build the grant came first and the refusal only afterwards, though still before any fetch.
  - Otherwise the coordinator's server routes that report to `LeaseAuthority::hand_to_local`. Under one lock, if the worker holds the key under that token, the lease is granted to the built-in worker under a new token. The key keeps its cohort, sources and strategy, and it isn't a loss or a new harvest.
  - The server's sink then starts the built-in worker's fetch (`RemoteIntake::take_handed`), as it does for a parked key: into the built-in worker's pool, keeping its privacy (§18.7). `take_handed` checks the refusals again, for a key whose hold or filter verdict changed in the moment between, and ends that lease as blocked.
  - **If the pool has no room,** or no sink takes it, the key is an oversize loss, as before hand-backs (review). The server ends the built-in worker's new lease as `oversize`. It isn't parked: a parked key would count against no remote worker's limits (`MAX_PENDING_PER_WORKER`, the hourly return allowance), the reporting worker's own lease frees at once so it could claim again straight away, and a re-granted parked key goes to a remote worker again, where it's lost as oversize anyway. In the parked build such a key was re-queued.
  - **What the sink did is an enum** (`LocalIntake`: `Fetching`, `Refused`, `Full`), not a bool, so the server can tell a key the pool took from one the intake ended as blocked in the race window.
  - The built-in worker fetches up to its own limit, 47 MiB. A key too large there too is lost as `oversize`, once.
  - **A worker's report is trusted for nothing but "hand it over".** It carries no size, and the key reaches the built-in worker's pool as a bare key built from the coordinator's own lease (source, strategy, privacy), with no peers, claims or provenance from the worker. So a worker that lies can't lend the built-in worker a bound or skip it. All it can do is move keys it holds to the built-in worker, within its hand-back allowance (below).
  - **The refused path tells the sink the worker's own outcome.** The authority records the loss as blocked, but `InboundSink::outcomes` gets the worker's `Lost { oversize }`. That keeps the server's own refusal off the worker's floor budget, which counts only the blocked losses a worker reports itself (review).
- **Each key is handed back once** (`HANDED_BACK`, 16,384 keys remembered, the oldest forgotten first). A key handed back before, found again and too large for a worker again, is lost as before, so no key goes round. The built-in worker's own oversize report is always a loss.
- **Each remote worker may hand back at most 120 keys an hour** (`HAND_BACK_ALLOWANCE` per `HAND_BACK_WINDOW_SECS`, review; the number is the runner's call under §2.26). Past it, its oversize reports are losses, as before hand-backs, until the window turns. The window is fixed: it starts at the worker's first hand-back after the previous window ended. It's kept per worker under the authority's lock, beside the return allowance, on the floor budget's pattern (`FLOOR_BUDGET`, 100 an hour).
  - **Why this size:** the once-only memory doesn't limit a worker that reports random keys as too large. Without an allowance it could keep the built-in worker's fetch intake, which it shares with its own DHT discoveries, full indefinitely. At 120 an hour, one worker adds at most two keys a minute.
  - **Why it's well above honest use:** dicts over a worker's 3 MiB are rare (very many-file torrents), and the built-in worker grows one large dict at a time (X-fetch-room-fix). So it can't take many more than this from the whole fleet in an hour anyway, and a higher allowance would buy an honest worker nothing.
- **Counted** as `cluster_handed_back_total` (`docs/metrics.md`): only keys the built-in worker's pool took (review). A key the sink has no room for counts as an outcome (a loss), and so does one refused before or after the grant. Neither counts as handed back.
- **What's left:** a lying worker can spend up to its hand-back allowance, 120 built-in fetch slots an hour, on keys it holds. Random keys find no peers, so each costs a pool slot until its fetch gives up, not a large download. Peers in three networks agreeing on a false "too large" (the size rule) can move a key from a worker to the built-in worker, at one fetch each. That's bounded by the size rule, the once-only memory and the allowance.

## Tests
- **Lease authority** (`leases.rs`):
  - An oversize key is handed to the built-in worker once, only by its holder under its current token, keeping its cohort and sources, not as a loss, and a second time it's a loss. The keys handed back are bounded.
  - A worker's hand-backs keep to its allowance. Past it they're losses, not handed or parked. Another worker's allowance is its own. It's still spent just before the window ends and comes back once it has.
- **Server** (`tests.rs`):
  - A remote worker's oversize report hands the key to the built-in worker through the sink, counted as handed back, not as an outcome. If the sink has no room, the key is a loss: not parked, not counted as handed back. A repeat of the same report is stale.
  - Hand-backs with no room never fill the shared queue. One worker reports more than `MAX_PENDING_PER_WORKER` keys as too large, with its allowance lifted, and nothing waits. With the item-1 fix removed (the old re-queue put back), this test fails at the per-worker limit, and so does the one above.
  - A second hand-back of a key, claimed again by another worker after the built-in worker's fetch ended, counts as a loss and isn't handed over again.
  - An oversize claim for a key the built-in worker refuses ends as blocked: it isn't handed over, and isn't granted to the built-in worker or left waiting. A refusal that changed in between (the sink answering `Refused`) ends the same way. Neither path moves the hand-back counter.
- **Intake** (`tests/remote_intake.rs`): keys handed back reach the built-in worker's pool with their privacy kept; one it refuses ends as blocked; one that finds the pool full is left for the server to end (`LocalIntake::Full`). A key handed back carries nothing from the report: the pool gets exactly `Found::key` with the lease's own source and strategy. `refuses_local` agrees with the intake's refusals. The parked-key test, which now shares the same path, passes unchanged.
