# B2b decisions (#89)

The settings API for the Settings screen (architecture §10.10.9).

- **Schema hints** sit on each property of a section's runtime schema: `x-group` (an id; the heading is the message `settings.group.<id>`), `x-order`, `x-advanced`, `x-preview`, and where they apply `x-unit` (`seconds`, `mebibytes`, `connections`), `x-widget` (`radio`, `slider`, `theme`, `shortcuts`, `language`, `time-zone`), `x-auto`, `x-keywords` (the message `settings.<section>.<field>.keywords`), `x-danger` (§10.10.7's `disruptive`, `privacy`, `destructive`, `security`), `x-config`, `x-env`, `format` (`socket-addr`, `log-filter`) and `writeOnly`. A test holds every field to the vocabulary. They're hints: the server checks everything.
- **Revisions:** one per section, saved as `settings.<section>#revision` (no migration). It goes up with each save that changes the section's saved values; a save that changes nothing (the same value, resetting an unsaved field) leaves it. `if_revision` is a reserved key inside any section's patch, beside the fields, so the single-section and batch bodies have one shape; a stale one is `409 stale_revision` with `current` holding every stale section's values. A save without it isn't checked.
- **Batch patch and errors:** `PATCH /settings` plans the whole batch under the registry's write lock (sections, then revisions, then fields and confirmations, in display order), writes every changed section and its revision in one transaction, then publishes each changed section's `watch` channel. Settings errors use the API envelope plus `error.section` and, for stale revisions, a top-level `current` (`SettingsErrorEnvelope`, typed in `dto/settings.rs`); the shared `ErrorEnvelope` is unchanged. B17's `confirm_adult` hook applies per section inside a batch.
- **Preview:** `POST /settings/preview` runs the same planning and saves nothing (a property test holds that it accepts exactly what a save accepts, with the same refusal). It returns each patched field's would-be value, live or restart, and the section's warnings and estimates (`sockets`, `url`, `memory_mib`). Size projections for storage wait for the retention work (§7).
- **The `settings` SSE topic** (`{section, revision}`, no values) is published by the settings routes through `EventHub::settings_saved` after each save that changed a section, imports included. The hub has 6 topics; a compile-time check guards the `u8` set (`updates` will make 7).
- **Preferences** are a registry section, `preferences`: theme, `theme_dark` (empty: the same family), mode, density, motion (`system`, `reduced`, `full`), illustrations, shortcuts, `shortcut_keys` (action → one key, conflicts refused), language and time zone (empty: the browser's), and first day of the week (§10.10.8's Language & region lists it). No `config.toml` key or variable; all live. **Per account:** Lodestar has one admin account, so one set is saved under `settings.preferences.<field>`; when accounts arrive, a migration moves those keys to the first account's and nothing else changes. Show adult content stays `content.show_adult`.
- **`POST /settings/test`** runs a download client's own `test()` (login and version) from `crates/integrations` on unsaved values, through its SSRF guard and the download-client network policy, within 30 s. The result is `200` with `ok` and a coded reason, never the URL or a credential. The API crate depends on `lodestar-integrations` for it. Notification channels' Send test is left to the Notifications slice: their senders deliver a real message and have no test call yet.
- **Export and import** are TOML laid out by section (`[crawler]`), each key with its `config.toml` key and variable in a comment, rather than in `config.toml`'s own tables: the two don't map one to one (`network.dht_port` is the port of `dht.bind`'s addresses) and the file must read back exactly. Export holds only values saved in the app (no secrets, nothing the environment sets, no read-only field, `preferences` only on request); §20 state is in no section. Import is JSON-wrapped (`{toml, confirm_adult, revisions}`) so it stays a same-origin JSON write; it's bounded to 64 KiB, the TOML parser bounds nesting, and parse errors give the parser's message and line, never the file's text. It lists keys it leaves alone (`unknown`, `read_only`, `secret`, `set_by_environment`), and saves the rest through the batch planning, all or nothing; `dry_run=true` returns the diff and the revisions to pass back.
- **Secrets:** no section has one yet (credentials live in the integrations `SecretStore`). The registry's rule for the first: `writeOnly`, `value: null` in every response (`source` says whether one is set), never exported, imported or previewed, and never quoted in an error or log line; a test section holds it.
- **Left for later:** the `logging` section and moving `general.log_level` into it (B-log1), `/system`, restart and the HTTP-address timer (B2c).
