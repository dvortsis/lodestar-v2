# B8 decisions (#101)

Migration V10 adds the M5 tables and their store APIs (architecture §7, §8 "Saved searches → alerts", §10.8, §10.9.5, §12, §12.1). No owner decision is changed.

- **One migration, V10.** It adds `saved_searches`, `alerts`, `user_items`, `collections`, `collection_items`, `api_keys`, `index_watermark_hour`, `query_log` and `torrent_parsed.resolved_at`. Every table is `STRICT`, like the rest of the schema. Every child of `torrents` cascades and is indexed on `torrent_id`, so deleting a torrent doesn't scan.
- **`AUTOINCREMENT` where an id is referred to from outside its row:** saved searches, alerts (SSE cursors, RSS guids), collections (URLs) and API keys (log references). A deleted id never comes back meaning something else (§7). `query_log` uses a plain rowid, because nothing refers to its rows.
- **The store validates what it stores.** Names are 1–200 characters, trimmed, with no control characters. Notes are 1–4,000 characters. A query is at most 2,048 bytes (the parser's limit), and the AST must be JSON. The tables carry the same rules as `CHECK`s. A refusal is the new `Error::Invalid`, and an unknown referenced row is `Error::NotFound`. The API trims input before it calls the store.
- **Saved searches and percolation.**
  - A new search's `watermark` starts at the index's current one, so it alerts only on what's indexed afterwards.
  - `record_percolation` writes a run's hits and the new watermark in one transaction. A crash can then re-run a range but never skip one. A repeated hit is ignored.
  - Hits at or below a search's watermark are skipped. A hit above the run's range is the caller's bug and fails the whole run.
  - **Paused is its own column** (`paused`), apart from the channels: `alert` (in the app), `rss`, and a `channels` bitset for webhook, ntfy, Discord and email (bits defined by the notifier, B9). Pausing leaves the channels untouched, so resuming an RSS-only search restores RSS-only (§10.8, "Pausing is a toggle").
  - Resuming moves the watermark up to the index's current one, so it doesn't alert on everything indexed while it was paused. Editing the query keeps the watermark.
  - A search that isn't paused percolates even with every channel off, because the list view shows its new hits (§10.8).
  - Alerts are bounded with `prune_alerts(keep)` per search (B9 picks `keep`). Marking read takes the highest alert id the user saw, so alerts that arrive while the page is open stay unread. That's the "New since …" divider (§10.8).
- **User items: one row per marked torrent.** Clearing the last mark deletes the row (a `CHECK` forbids an empty one). "Hidden" here is the user's own, separate from a filter rule's `flags::HIDDEN`.
  - Labels are one canonical text. Each label is trimmed, with whitespace runs folded to one space, and is 1–64 characters with no control characters. A torrent has at most 32. They're stored sorted by byte order, deduplicated and joined with U+001F, so equal sets always encode equally. A property test covers this.
  - Labels are case-sensitive: `Anime` and `anime` are two labels. Folding case needs locale rules, so it's left to the UI's suggestions.
- **Collections:** integer positions within a collection, with appends after the last one. A reorder must name every entry exactly once, so a reorder sent from a stale page can't drop or duplicate entries.
- **API keys store a SHA-256 of the secret, not Argon2id.**
  - The secret is at least 256 random bits, made by the auth code (B12). It can't be guessed, so a slow hash adds nothing. Argon2 (19 MiB, tens of ms) on every Torznab or RSS request would be pure cost.
  - The store never receives the secret: B12 passes a short public **prefix** (8–32 of `A-Z a-z 0-9 _ -`, unique) and the hash.
  - Lookup is by prefix, then a constant-time hash comparison. Revoked or expired only shows once the hash matches, so someone with only the public prefix learns nothing.
  - `last_used_at` is written at most once a minute per key.
- **Feed tokens share the `api_keys` table** (`kind` 1). A token belongs to one saved search and is deleted with it, or (`saved_search_id` NULL) covers every feed. §12 names keys and tokens separately, but they differ only in kind and scope, so one table and one verify path serve both.
- **`index_watermark_hour` only grows, in both columns.**
  - An id at or below one already recorded changes nothing.
  - An hour earlier than the latest recorded (the clock was set back) counts in the latest hour. So "the first hour whose `last_id` ≥ id" is always well defined.
  - **Hour 0** is seeded by the migration with the highest id stored at the time. Those torrents were indexed before hourly tracking existed, so their searchable hour is unknown (`searchable_hour` → `None`). `lodestar rollup --repair` can't recompute them exactly.
  - **Known limit:** the seed is `max(torrents.id)` at upgrade time, not the index's own watermark. Torrents stored but not yet indexed when the upgrade runs (the last couple of seconds of ingest, or a backlog while search was off) are counted as before tracking, so they never get a searchable hour.
- **Query log: off unless the caller says on.** `log_queries(QueryLogging, …)` writes nothing for `Off` (the default), so the setting's current value is passed in on every append and the store keeps no switch of its own.
  - It holds time, query, result count and latency only.
  - Words are split on any whitespace. Any word containing `://`, `magnet:`, `passkey=`, `apikey=`, `api_key=`, `token=`, `secret=` or `password=` (in any case) is replaced with `[link]` before writing, because a pasted magnet or tracker URL can carry a passkey.
  - It's bounded by `prune_query_log(before, max_rows)` (both an age and a row cap) and `clear_query_log`.
- **`torrent_parsed.resolved_at`,** which B13 asked for, gives Discover's "Recently resolved". The store records the time it's given (`set_resolved_at`). Deciding that a torrent "became resolved" belongs to enrichment, whose record is opaque to the store. Re-enrichment keeps the time.
- **Deletes and the WAL (§2.17).** `Store::after_user_delete` runs after every user-data delete, prune and clear. It also runs after an update that clears or replaces stored text: a name, query or AST, a note, or labels. The old text would otherwise stay in WAL frames. It runs #81's WAL scrub (`Store::scrub_wal`), best effort, with `scrub_pending` retrying a scrub that couldn't finish.
- **Counts used as `LIMIT` or `OFFSET` saturate** (`sql_limit`). A plain `as i64` cast turns `usize::MAX` into -1, which SQLite reads as "no limit" for `LIMIT` but as 0 for `OFFSET`, so `prune_alerts(usize::MAX)` would have deleted everything.
- **Every M5 write transaction is `BEGIN IMMEDIATE`** (`crate::begin_write`, #81's rule for `crates/store`). A deferred transaction that reads first gets SQLITE_BUSY at once when another connection holds the write lock, because SQLite doesn't run the busy handler for a read-to-write upgrade.
