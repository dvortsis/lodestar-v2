# ENR-3 decisions (StashDB response parser and query documents)

Slice ENR-3 of `docs/plan/2026-11-04-v06-rulepacks.md` (§4.3, architecture §18.9, §20.9). It adds `crates/sources-feeds/src/stashdb.rs`: two fixed GraphQL query documents and a pure, bounded parser from a stash-box answer to scene matches plus skip counts, on ENR-2a's `json.rs` (read-only). No I/O, no new dependency, no `serde_json`, no GraphQL client crate.

- **Two query documents, fixed strings:** `SEARCH_SCENE` (`searchScene(term, limit)`, for ENR-1's display-name or parsed site/date/title lookups) and `FIND_SCENE` (`findScene(id)`, to refresh a known match). Both select exactly `id title release_date studio { id name } performers { performer { name } } }`, and the caller passes values only as GraphQL variables, so no user text is ever spliced into a document. A unit test splits both documents into words and fails on any word outside a 17-word allowlist, and on any `id` inside the performer selection. No fingerprint query: fingerprints are of files, and ENR-1 never sends file data (plan Q2).
- **Fields kept: id, title, release date, studio (id and name), and performer names.** The brief lists kind, id, title and performers; the plan (§4.3) says to extract "only the fields ENR-0 can store", and ENR-0's section is studio, scene title, release date and performers, so studio and release date are kept too, as in ENR-2b's brief. **The runner confirmed this** (runner, §2.33, ENR-3 review; flagged to the owner under §2.19): they're ENR-0's fields, and the owner's Q2–Q5 answers (§2.37) don't exclude them.
- **No performer ids (runner's call, ENR-3 review, under Q4 and §2.37).** The owner's Q4 answer rules out per-performer pages and cross-item lists, and an external id is exactly what would link one person across scenes. So the queries don't ask for one, `Performer` is a name only, and an id a server sends anyway is read past. A studio keeps its id: it's an organisation, not a person.
- **Kind is always `Scene`.** Stash-box has scenes only: no movie type, and VR is a tag, not a field. Reading tags to infer VR would request more data than the claim needs, so it's left out; `Kind` is an enum so another variant can come with a real field.
- **Performers come back beside the match, not in it** (`Scene { matched, performers, performers_truncated }`), so dropping them under Q4 is taking `matched`. A performer is a name. The credited alias (`as`) isn't requested: it's an alias, which Q5 rules out.
- **Never requested, never kept (plan Q5):** birth dates and every other personal field stash-box has (measurements, birthplace, country, ethnicity, aliases, disambiguation, gender, tattoos, piercings, career years, images, URLs). The types have no field to hold one; unknown keys are read past with `skip`, never decoded. `personal.json` carries every one of them, marked `PERSONAL-…` or `999…`, and the test asserts none reaches the output.
- **A scene is used whole or not at all,** and extra evidence degrades instead of spoiling it (**runner's call**, ENR-3 review, one rule shared with ENR-2b: cut data only ever means less extra evidence, and skipping the scene would lose all of it). A scene is handed out only after its object closes and every kept field checked out.
  - **Degraded, scene kept:**
    - a title over `MAX_TITLE` is cut with `common::clean_title` (on a character boundary, hidden characters removed) and trimmed, as the other feeds do;
    - a studio without a valid id and a usable name (missing, empty after cleaning, over `MAX_NAME`, a bad escape, a repeated key, an over-long array inside) is dropped;
    - a performer entry without one usable name (not an object, no `performer`, the same name faults) is left out;
    - performers past `max_performers` are left out, and nothing is stored past the cap (an entry is pushed only while there's room); `max_performers: 0` reads none and keeps the scene.

    A left-out performer sets `performers_truncated`, so a caller knows the cast list is partial.
  - **Skipped and counted:**
    - `no_id`: no `id`, or a `null` one;
    - `over_cap`: a string in the scene's own fields over `max_text` raw (it isn't decoded, so it can't be cut), or an array read past in the scene that's longer than `max_array`;
    - `malformed`: a kept field of the wrong type (a studio that isn't an object or `null`, performers that aren't a list or `null`, and so on), an id that isn't a UUID, a date that isn't a real `YYYY`, `YYYY-MM` or `YYYY-MM-DD`, a bad escape, a repeated scene key, or a scene that isn't an object.

  A repeated key spoils the scene, since which value the server meant is unclear (`archive_org` keeps the first; here the scene is small and the stricter rule costs nothing). Inside a studio or performer entry, it drops just that entry. Keys are compared as written, so an escaped `"\u0069d"` is an unknown key and read past.
- **Outside a scene, odd shapes are read past, not counted:** a second `data` or `errors`, a `searchScene` that isn't a list, or a second `findScene` after a non-null one. They hold no scene the parser could count. The parser doesn't know which query an answer is for and reads `searchScene` and `findScene` alike; a `FIND_SCENE` caller (ENR-5) checks the returned id is the one it asked for.
- **`null` is an absent field** for title, release date, studio and performers, read as `peek` then `skip` (#422's review). An empty or hidden-only title is absent too.
- **A structural fault ends the parse** (bad JSON, input cut short, the depth, value, item or byte cap). `json::Stop` doesn't latch and the cursor is then mid-token, so every read propagates its `Err` with `?` and nothing reads on (#422's review). Scenes finished before it are kept; the one it was in never is. A test cuts a two-scene answer at every byte.
- **GraphQL `errors` are counted, never read** (`Page::errors`; 1 if the field isn't a list). Their messages are the server's text. Partial `data` beside them is still parsed, as GraphQL allows. A `null` `findScene` is no scene and isn't counted.
- **Ids are canonical lower-case UUIDs** (StashDB's ids), so the same scene from two answers compares equal; `Match::link` is `https://stashdb.org/scenes/<id>`. Stash-box instances other than StashDB aren't in scope; ENR-5 can add a base-URL parameter if one is ever added.
- **Release dates are `Date { year, month, day }`,** stash-box's fuzzy-date precision kept rather than padded to a day, so ENR-0 can store what was said and no more.
- **The caps (`LIMITS`), and why:**
  - `max_bytes` 4 MiB: a `searchScene` page of 100 scenes with 64 performers each is under 1 MiB with the selected fields;
  - `max_depth` 16: the deepest selected path is 7 (`root > data > list > scene > performers > entry > performer`);
  - `max_values` 200,000: about 200 values a scene with a full cast of 64, times 100 scenes, with room for fields a server adds;
  - `max_items` 100: `searchScene`'s `limit` is ENR-5's choice and should stay far below; a server ignoring it is cut off;
  - `max_performers` 64: casts are a handful; a compilation past 64 keeps its first 64 and sets `performers_truncated`;
  - `max_array` 1,000: arrays read past (tags, URLs, fingerprints a server adds unasked);
  - `max_text` 8 KiB raw: room for a `MAX_TITLE` (1,024-byte) title written with `\u` escapes;
  - `MAX_TITLE` 1,024 (the claims' name limit, shared with the other feeds) and `MAX_NAME` 256 for studio and performer names. `MAX_NAME` stays in `stashdb.rs` for now; whichever of ENR-2b and ENR-3 lands second moves it into `common.rs` (runner).
- **Fixtures are synthetic, from public docs** (`crates/sources-feeds/tests/fixtures/stashdb/README.md`): written by hand in the shapes of stash-box's public GraphQL schema, with obviously synthetic names and ids. Recording from the live service needs an account, an API key and network access this session didn't have. **Recording real fixtures, with keys scrubbed, moves to the plugin slice (ENR-5)**, which should also check that `release_date` is the field name the live schema serves (older stash-box versions had only the now-deprecated `date`).
- **Tests:** golden tests on the five fixtures; field faults each skipping exactly one scene; property tests that each cap (bytes, depth, values, items, performers, read-past arrays, text) stops or skips exactly at its value; arbitrary bytes and stash-box-shaped fragments never panic and keep every invariant; generated answers read back exactly while scenes with a fault anywhere are skipped whole and leak nothing; and the fuzz target's checks over 200,000 mutated fixtures.
- **Fuzz target `fuzz/fuzz_targets/stashdb.rs`,** seeded from `fuzz/seeds/stashdb/` (copies of the fixtures). The first byte picks tight caps, as `archive_org`'s does. Run for 10 minutes on stable with the coverage flags cargo-fuzz passes (no nightly here, so no AddressSanitizer), as ENR-2a did; the result is in the PR.
