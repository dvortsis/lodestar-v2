# SRC-2 decisions: the unverified pipeline

Slice SRC-2 of `docs/plan/2026-11-01-v06-sources.md`, built on SRC-1's V14 store (`2026-11-02-SRC-1.md`). It covers architecture §18.4, §18.5, §20.1 and §20.5. There's no schema change.

## Where claims go
- **Intake sends a discovery with claims to the writer, not the pool.** The writer judges the claims and stores them: as an unverified item, or as claims on the torrent that already holds the key (SRC-1's `Put::Torrent`).
  - A held key (the held set, or the floor's hash list) is refused first, as for fetches.
  - **The channel is bounded in bytes, not only in entries:** each discovery holds a share of a 64 MiB budget (`CLAIMS_BUDGET_KIB`, counted by `claims_kib`: text plus each entry's own size) until the writer has stored or dropped it. One discovery's claims run to a megabyte and feeds are untrusted, so a count alone would allow gigabytes in flight (self-review).
  - Intake waits for budget and room, as it does for the pool. Live sources drop and count; importers back up.
  - Bare keys (no claims, such as the DHT's) go to the pool as before.
- **Why the writer:** it's the only task that changes the store, so judging and storing in one place keeps holds and their pre-commit marks (`2026-10-31-B-held-precommit.md`) on the paths that already handle them.
- **Batches:** up to `batch_max` discoveries and 8 MiB of claims (`CLAIMS_STEP_KIB`) per step, so a step of judging and storing stays short beside the crawler's commits in the writer's unbiased `select!`. Holds are written first, then one `put_unverified` per source. A source disabled or purged meanwhile is refused alone (`Error::Invalid`) and counted, so a poll still in flight can't undo a purge (SRC-1).

## Filter before storage (§20.1, §20.5)
- **Every claimed name and every claimed file path passes the full pipeline** (`unverified::judge`):
  - the key against the floor and the dropping lists;
  - then the claimed name and all claimed paths together, classified as they claim (sizes the source left out count as 0, so a claimed list can't reach CS-8a's size test);
  - with your classification rules (`judge_with_rules`), the same entry point import candidates use.
  - The store's held-hash guard is the second line, not the first.
- **A floor or core (CS) hit always holds the hash.** It's a tombstone or a quarantine, as the rule's action says. If a core rule's action is ever weaker, the hold is forced to a quarantine. Such a claim is never stored, promoted or left only flagged (SRC-1's rule for SRC-2).
  - **When a torrent is already stored under the hash,** every one of its swarm hashes is held (a hybrid's other key too) and the torrent is deleted, in **one transaction** (`Store::hold_claims`, logged for the index). A failure between two transactions could otherwise leave it stored under a held hash (self-review).
- **Any other hold** (your drop or quarantine rule, a pack, a list):
  - On a key with no verified metadata, it holds the hash, as the import path does.
  - **On a stored torrent, it never holds or deletes it.** The claim is dropped and counted (`dropped`).
  - Why: claims are hints, and verified metadata is the truth (§18.5). A source could otherwise get a verified torrent deleted by claiming a name your rule drops. The torrent's own metadata is judged by the existing paths.
- **Weaker actions** (flag, hide, demote) and **shadow-mode rules** don't stop storage. An unverified item isn't searchable, and its verified metadata is judged again at promotion. Shadow hits on claims aren't recorded.
- **Not judged:** claimed trackers, external IDs, the description and the publisher. Rules match names and paths (§20.2's `publisher:` and `tracker:` fields read stored torrents). This is a known gap for SRC-7, whose feeds carry publishers.
- **Quarantined names are sealed.** A `Hold` and the writer's logs carry rule ids and evidence codes only, never claim text. Store errors carry none either (SRC-1).

## Nothing is stored under a held hash (self-review, blocking)
- **`Store::write` doesn't check holds.** Before SRC-2 every hold came from judging the same metadata the commit judges again, so it didn't need to. A claim's hold is about text the fetched torrent doesn't have.
  - So a fetch in flight when a feed's claim holds its hash would pass the commit's judgement and be stored under the held hash.
- **The writer's commit now refuses any result whose swarm hash is in the held set**, read before the batch marks its own holds. It's an in-memory lookup, with no store read per insert. The held set already has every tombstone, quarantine and CS-1 hash, plus pending marks.
  - A refused result counts as filtered and lost as blocked, as a held verdict does. Its hold already exists, so nothing more is written.
- Tested: `a_hash_a_claim_held_after_judging_is_never_stored`.

## The refile sweep
- **`unverified::refile_step`, driven by the writer's `Sweep`.** It copies `CandidateSweep` (#280):
  - it runs at start and again whenever the filter engine's version changes (`note_engine` on the flush tick);
  - it reads one keyset page per step: SRC-1's `unverified_after`, then `claims_after`;
  - it writes through `refile_unverified` or `refile_claims`. Those refuse the write (`None`) when the rules moved on, and the sweep then starts again;
  - after a store error it backs off (`Backoff`) and retries the same step.
- **Bounded memory:** one page, by SRC-1's page bound, which its tests measure in decoded bytes (`a page of 1 MB claims` and `all-empty file lists`). That's at most `MAX_PAGE` (1,024) rows and under 9.5 MiB of decoded claims (SRC-1's bound), plus the holds for that page.
  - It runs between ingest batches in the writer's unbiased `select!`, so it gets a fair share and stops at shutdown between any two steps.
  - Tested: `the_sweep_reads_one_bounded_page_per_step` (2,053 items take three pages plus the two ends).
- **Items:** any hold removes the item and holds its hash. Claims that don't decode are removed. An item whose claims a purge took is kept, waiting for its other finder's claims (SRC-1).
- **Claims on stored torrents:**
  - A floor or core hold removes the claims, holds every swarm hash of the torrent and deletes it.
  - Any other hold only removes the claims, with no hold, for the reason above.
  - SRC-1 notes that claims removed without a hold stay in older snapshots until those expire. Only non-safety removals take that path.

## Verification (§18.4, plan §3)
- **Behind `PipelineConfig::verify_unverified`, default off.** It's the plan's `sources.verify_unverified`.
  - **Handoff to SRC-14:** the config key and the API switch. `config.rs` has no `[sources]` table yet, and SRC-14 makes source settings editable.
- **The store is the queue.** The `Verify` cursor reads `VERIFY_PER_FLUSH` (64) items after its last id on each flush (5 s). It hands them to intake's retry channel, which claims and fetches them through the shared pool like any key.
  - It never takes more than half of that channel's free room.
  - After the last item it waits `VERIFY_ROUND_SECS` (6 h) and starts again, so dead swarms are retried a few times a day, not in a loop.
- **Nothing is held in memory,** however many items there are. Shutdown stops it between flushes. Keys already in the pool are persisted with the pool's queue, as every key is.
- **Fair to the crawler:** about 13 keys a second at most, against the crawler's thousands a minute. Fetches go through the pool's per-source DRR under the item's source. Each promotion is one short transaction in the writer's normal commit.
  - **Not Low priority by itself:** the pool schedules by source weight, and a key can't carry its own priority without a `crates/sources` change. The rate cap is what keeps it small.
  - **Handoff to SRC-14 / scheduler v2:** a per-key Low class.
- **A private item stays private:** the request carries `private_source`, so the pool never sends it to public peer finding (§18.7, CR-0's contract).
- **§5 Q11 (the cap on bare dead hashes):**
  - Bare source keys aren't rows and don't enter this cursor. They go to the pool, whose `max_pending` (200,000, oldest idle evicted first) already caps them below Q11's 1M.
  - No second queue was needed. Items with claims are rows, which the purge and snapshot rules cover.
- **A feed's sighting of a stored torrent is a rediscovery:** the hot column, the health scheduler, the REDISCOVERED rollup and the gate's `Rediscovered` count it, as for a bare sighting (self-review).
- **Funnel:** a verification fetch is claimed at the time it's sent, so the source's cohort counts it as harvested then. Counting it again at the item's first sighting would double-count the sighting that stored it.

## Promotion (§18.5)
- **In the writer's commit, before the batch's inserts.** Every verified torrent's swarm hashes are probed in `unverified_items`. A hit promotes the item through SRC-1's `promote`:
  - the torrent keeps the item's id;
  - a torrent already stored under the hash merges instead (`Promoted::Merged`);
  - a hash held since the torrent was judged stores nothing.
  - It's the same for a verification fetch and for the crawler finding the same hash: nothing is stored twice. A hybrid whose v1 and v2 keys were found apart promotes one and merges the other.
- **The item's claims are judged again under the current rules first** (self-review, blocking). A rule added after they were stored, which the restarted sweep hasn't reached yet, must not let them be promoted.
  - **A floor or core hold:** every swarm hash is held, the item is removed (journalled), and nothing is stored. The marks are set before the write, as the batch's own are.
  - **Any other hold, or unreadable claims:** the item is removed and the torrent is stored as usual, under a new id and without the claims. Claims never override verified metadata, and the item would have been removed by the sweep anyway.
  - Tested: `promotion_judges_the_claims_under_the_current_rules`.
  - The pre-commit marks of all three new holding paths (ingest, sweep, promotion) are tested with the `marked` and `between` hooks: `claim_holds_are_refused_from_before_their_commit`.
- **A promotion commits in its own transaction, before the batch's write.** When the batch's write then fails, the promoted rows are still accounted (have-filter, hot columns, counters, gate): `Outcome::failed`. Only the rest of the batch counts as `StoreFailed` (self-review).
- **A classification change during the batch (§20.9):** `write` marks its own rows for enriching again, but `promote` takes no generation. So a promotion stored while the generation moved is stored without its enrichment, and the background pass enriches it under the current rules (self-review).
- **Funnel attribution:** a promoted torrent's Stored stage is recorded under the item's first-sighting cohort and source, the ones its row records as `discovered_at` and `first_source`. That's where `count_promoted` and `record_searchable` count it searchable, so the cohort's stored and searchable stages agree. The fetching lease's own cohort records no terminal stage for it (self-review).
- **Only verified metadata promotes.** Every commit result is a fetched, hashed info dict (`verified: true`). `promote` refuses anything else.
- **The duplicate check is skipped when the store holds no unverified item.** That's one `EXISTS` read per batch (`Store::has_unverified`), so a store with no sources pays nothing per insert.
- **Promoted ids below every watermark:**
  - **Search index:** `promote` writes `reindex_log`. The live indexer's replay deletes and then adds the document, so an id it never indexed is added under its own id. Tested in `crates/search/tests/promoted.rs`: searchable, with the watermark unchanged.
  - **Hot columns:** a promotion counts as a new row in the commit's accounting, so the writer touches its last-seen slot.
  - **Insights** (SRC-1's handoff): `promote` now counts a kept id as newly searchable, inside its own transaction, when the id is at or below the searchable watermark (`insights::count_promoted`). That covers NEWLY_SEARCHABLE, TIME_TO_SEARCHABLE, the cohort's searchable stage and the imported total.
    - The rows are the same ones `record_searchable` writes: both use one `Tally`, so the day tables compact them alike.
    - An id above the watermark is left to `record_searchable`. Because the check sits in the insert's transaction, one of the two counts it and never both.
    - Time-to-searchable is measured at promotion, which the index's replay follows within a commit interval.
    - SRC-1's purge reconciliation is extended to promoted torrents (`purge_reconciles_promoted_torrents`): newly searchable minus removed equals the torrents stored, before and after a purge.
  - **The percolator: see "Open" below.**
- **The store's `promote` signature changed** to take the `SearchableCodes` and the time. The SRC-1 test call sites are updated.

## Claim mismatch (§18.5)
- **`JunkReason::ClaimMismatch` (`claim-mismatch`, weight 30)** in `crates/classify/src/junk.rs`, with `claim_mismatch(verified, claimed)`:
  - Claimed files are matched by their last path segment, case-insensitively, since sources differ on the root folder and separators.
  - It's a mismatch when fewer than half the claimed files have a verified file of that name, or a matched file's claimed size is none of that name's verified sizes.
  - An empty claimed list asserts nothing. Padding files are ignored.
- **At promotion it's recorded, and claims never override verified metadata:** the reason is added to the torrent's stored enrichment, re-scored and re-encoded. The verified name, files and sizes are untouched. The mismatch is counted (`mismatches`).
- **Known limits:**
  - A later re-enrichment (an `ENRICHMENT_VERSION` bump, a classification-rule change) recomputes the record from the verified files alone and drops the reason. Keeping it needs the enrichment paths to read `torrent_claims`.
  - Claims that arrive for an already-stored torrent aren't compared.
  - **Handoff to SRC-3:** both, since it reads claims for search.

## Measurements
Release build, this session's container. Both are `#[ignore]` tests in `crates/pipeline/tests/unverified.rs`.

- **The duplicate check's per-insert cost** (`duplicate_check_cost`), on a file store holding 1M unverified items:
  - a miss, the crawler's usual case, costs **3.8 µs** per swarm hash;
  - a hit costs **5.1 µs**;
  - an insert itself costs **28.5 µs** in batches of 256, so the check adds **13%** per v1 hash.
  - With no unverified items stored, it's skipped: one `EXISTS` per batch.
  - Building the 1M items took 50 s through `put_unverified` in batches of 10,000.
- **Hot-column memory at 1M unverified ids** (`rss_delta_at_1m_unverified_ids`): the arrays are allocated in 64K-id chunks of 6 columns, each written with the default when it's first touched, so allocation is resident memory.
  - 1M torrents alone: **24.0 MiB**.
  - 1M unverified ids in one block (an importer's burst), then 1M torrents: **+0.0 MiB**. The block's chunks are never touched.
  - 1M unverified ids interleaved one-for-one with 1M torrents (a feed as busy as the crawler): **+22.5 MiB**, the worst case, because every chunk holds a torrent.
  - The process RSS deltas printed beside these are unreliable within one process (freed chunks are reused). The allocated figures are the ones to read.

## Refinements for the runner to flag (§2.19)
- **Verification isn't Low priority** in the pool. §18.4 and §18.5 say verification fetches are low priority. Here they go under the item source's own DRR weight, with a hard rate cap (about 13 a second). A per-key priority class needs a `crates/sources` change (see Verification).
- **A non-core hold never deletes a stored torrent on a claim.** The plan says every claim passes the filter before storage, and that holds. Its consequence for a stored torrent is a refinement made for §18.5's "verified metadata is always the truth".
