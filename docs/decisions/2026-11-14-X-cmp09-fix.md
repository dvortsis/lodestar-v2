# X-cmp09-fix decisions

This is the first of two PRs for CMP-09 (managed companion readiness). It covers the companions crate. The second, X-cmp09-fix-2, covers the credential clients outside it. This file says what the code now does (`docs/security/v1/README.md` §5).

## The listener is checked before a run is ready
- **A passing health check is not enough on its own any more.** Before `Bindings::try_ready` marks a run ready, every listening socket on the port that takes connections to `127.0.0.1` must belong to that run's own process (`supervise/listener.rs`). The process is the one the supervisor started for the run, now in `Status::pid`.
  - Sockets that take `127.0.0.1` connections are those bound to `127.0.0.1`, to `0.0.0.0`, to `::` or to `::ffff:127.0.0.1`.
- **The answers:**
  - `Ours`: the run may be marked ready.
  - `Other`, `Nobody` and `Unknown`: the port stays not ready. `Bindings::refusal` keeps the reason as a code: `listener_not_ours`, `listener_missing` or `listener_unverified`.
  - What can't be read or parsed is `Unknown`, and never counts.
- **Linux:**
  - The socket's inode comes from `/proc/net/tcp` and `tcp6`, read in Lodestar's own network namespace, which is the companion's.
  - It must be among the open sockets of the child or of a process descended from it, found by each process's parent in `/proc/<pid>/stat`. The launcher `exec`s the companion, so the child's pid is the companion's.
  - Descent is by parent, not by process group.
  - If the child's descriptors, or a live descendant's, can't be read, the answer is `Unknown`.
- **Windows:**
  - The companion is spawned directly. The launcher is Linux-only: `launcher_main` returns at once off Linux, and only the Linux limits wrap the spawn. So the pid in `Status` is the companion's own process.
  - Each listener's owning process comes from one `Get-NetTCPConnection -State Listen -LocalPort <port>` call, through the crate's existing PowerShell helper (System32 PowerShell 5.1 by absolute path, with a time limit). Each owner must be the child itself.
  - "No such listener" is told apart from any other error of the cmdlet. Any other error, or a call that fails or doesn't finish its output, is `Unknown`.
  - The script uses no double quotes, so argument quoting can't change it. The port is a number.
- **Not chosen: `GetExtendedTcpTable` through `windows-sys`.** Calling it needs `unsafe`, and the workspace forbids `unsafe_code`. The one exception (the store's memory statistics) is an owner decision (`docs/owner-decisions.md` §2.35). The PowerShell call needs no new dependency, and the supervisor already runs PowerShell at each start. It runs once per readiness attempt, after a passing health check, never per request.
- **Other platforms** always answer `Unknown`, so nothing is ever ready there. The catalogue offers no native companion outside Linux and Windows.
- **A later check can take readiness away.** If a readiness attempt under the same claim finds the listener to be another's, or gone (or can't tell), the run is no longer ready. It becomes ready again only once its own listener is found again.
- **Every configuration is followed by a fresh check** (`Run::recheck`), the install's included.
  - `Supervised` marks the port not ready (`Bindings::unready`) and runs its health check again, listener and all, before the configure step counts. qBittorrent's bind-address setting moves its listener, for one.
  - A run that isn't found ready again fails the step.
- **The reason reaches the log.** A failed health check, or a failed check after a configuration, carries the listener's code (`listener_not_ours`, `listener_missing`, `listener_unverified`) as the step's reason in the existing `companions.install_failed` event, in place of `unhealthy`. No new event and no user wording.
- **The check runs on a blocking thread** and holds no lock while it runs. The claim and the run it was made for are compared again before the run is marked ready.

## A port in use isn't started on
- **Before each start of a companion with a loopback port** (the first and every restart), the supervisor binds `127.0.0.1:<port>` and lets it go at once.
- **If the port is in use,** it's looked at again every 100 ms for up to 2 s, since what an earlier run started may still be exiting. On Windows, an exclusive hold's "access denied" also counts as in use.
- **If it's still in use,** the companion isn't started.
  - The try counts as a crash, so it backs off.
  - When the crash window fills, the companion waits for you with `port_in_use` (`Attention::PortInUse`) if every crash in the window was a port in use, and with `crash_loop` otherwise.
  - A restart once the port is free starts it.
- **Any other bind failure** leaves the start to the companion, as before.
- **The listener check above still applies to every run,** whatever happened at the start.

## From the #883 review
- **Each claim of a port has its own number** (`Port::claim`, taken from a counter in `Bindings`).
  - A readiness attempt records the claim and the run it began under. It marks nothing ready if the port was released and claimed again meanwhile, even when the new claim's run has the same number.
  - `mark_ready` with no checks is now for tests only (`testing` feature), and `Bindings::trusting` is a test-only `Bindings` whose listener check always says `Ours`.
- **The manager's follow starts from the run the start's check found ready** (`Run::ready_run`, from #883). A test now covers a restart before the follow begins.
- **The wording in `tests/supervised.rs`** now states the general rule.

## Where the codes show
- **`port_in_use` and the listener codes** don't reach the API or the web app. The supervisor's attention codes and `Bindings::refusal` are read only inside the crate and by tests. They need no user wording now; a page that shows them later should say it generally ("the port is in use by another program").

## Tests
- **`supervise/listener.rs`:**
  - parsing `/proc/net/tcp` and `tcp6` rows, the addresses that take `127.0.0.1`, parents, descent and socket links;
  - a table or `/proc` that can't be read reads `Unknown`;
  - `Get-NetTCPConnection` output, judged on every platform.
- **`supervise/bind.rs`:**
  - only the run's own listener makes it ready, and each other answer leaves its code;
  - a run with no process is `Unknown`;
  - a check from an earlier claim counts for nothing.
- **`tests/supervise.rs`, with real processes** (Linux and Windows):
  - a child listening on its port is `Ours`, a listener the test opens is `Other`, and an unused port has `Nobody`;
  - a readiness attempt for the child's run on the test's listener is refused with `listener_not_ours`.
- **`tests/supervise.rs`, the port check:** a port the test holds means the companion is never started and ends at `port_in_use`; freed, a restart starts it.
- **`supervise/bind.rs`:** a ready run whose listener is found to be another's or gone loses readiness, and `unready` takes it away.
- **`tests/manager.rs`:** a configuration is followed by a fresh check (both checks ask about the listener), and a listener found to be another's then fails the configure step with `listener_not_ours` and leaves the port not ready.
- **`tests/manager.rs`:** a restart before the follow begins is checked again and found ready. It covers #883's starting point (`Run::ready_run`), and fails when the follow starts from the current run instead.
- Each new test fails with its part of the code removed: the listener check, the claim comparison, the port check, the follow's starting point, the loss of readiness and the check after a configuration.
- Descent by parent is covered by a unit test (`descends`). The rule for `port_in_use` against `crash_loop` has no test of its own. Waits are conditions with deadlines of at least 10 s.
