# X-gluetun-leak decisions (#800)

Fixes testing blocker #1: gluetun's kill switch let packets of established flows leave by the host's network when the tunnel went down. The testing session found 61 such packets on a fleet VM on 2026-11-12. Sources were read in gluetun's repository at tag `v3.41.3` (commit `3d1e20c5`, the digest the fleet pins) and at `master` (`236b10ba`, 2026-11-12T04:29Z).

## What gluetun does
- **The cause, confirmed in source.** `enable()` (`internal/firewall/enable.go`) sets DROP policies, then appends `OUTPUT -o lo ACCEPT`, then `acceptEstablishedRelatedTraffic`, which is `-A OUTPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT` with no interface (`internal/firewall/iptables.go`). The `-o wg0` accept comes later (`SetVPNConnection`, `vpn.go`). When wg0 goes down, the kernel routes a flow opened through the tunnel out of eth0, still carrying the tunnel's source address, and that first accept passes it.
- **(c) No release fixes it.** `v3.41.3` is the newest tag. `master` still has the unrestricted accept. Commit `2429c0d` (#3158, on `master`, in no tag) adds `flushExistingConnections` (`internal/firewall/flush.go`). That flushes conntrack, or falls back to the `GLUETUN_PUBLIC_ONLY` chain, but only when the firewall is turned on, not when the tunnel drops. A newer version is not the fix.
- **(a) The supported hook is `/iptables/post-rules.txt`.** `runUserPostRules` runs at the end of `enable()`, once, before the VPN starts. It runs each line that starts with `iptables`, `ip6tables` or their `-nft`/`-legacy` forms, and skips every other line, so comments are inert. A missing file is skipped without a word. A failing line makes `enable()` return an error: its deferred `fallbackToDisabled` resets the policies to ACCEPT, and `main.go` then exits. That happens before any VPN or app traffic, but the rules must never fail, and the leak test checks that they loaded.
- **gluetun's image sets `VPN_INTERFACE=tun0`** (`Dockerfile` line 79), and WireGuard takes that value (`internal/configuration/settings/wireguard.go`). Rules that name `wg0` need `VPN_INTERFACE=wg0` set explicitly. The fleet compose and the PIA example set it.

## The fix
- **Three rules per family, all inserted at the top of OUTPUT** (`packaging/companions/gluetun-post-rules.txt`, which explains each line):
  1. `-o wg0 -j CONNMARK --set-xmark 0x800000/0x800000` marks every connection that sends a packet through the tunnel. It changes no verdict.
  2. `! -o wg0 -m connmark --mark 0x800000/0x800000 -j DROP`: a connection that used the tunnel never leaves by another interface.
  3. `! -o wg0 -p icmp -m addrtype ! --dst-type LOCAL -j DROP`: no ICMP of any type leaves outside the tunnel. For IPv6: `! -o wg0 -p ipv6-icmp ! -d fe80::/10 -m addrtype ! --dst-type LOCAL,MULTICAST -m hl ! --hl-eq 255 -j DROP`.
     - **Why all types: defence in depth.** No container ICMP leak is proven. On the VM, a port-unreachable-only rule left 2 + 1 ICMP in the down-phase counts, but run 3 showed phase A's 2 were the host's own router solicitation and DAD frames, inbound, and the veth check now ignores those. The one candidate, run 1's single ICMP to the endpoint on eth0, most likely came from the host's own stack (see "The leak test"). Rule 3 keeps the container from ever sending ICMP outside the tunnel, at no cost to anything gluetun needs.
     - **The candidates found in gluetun's source:** its health check pings the VPN server IP every minute by default (`healthcheck/checker.go`, `vpn/tunnelup.go:35-38`, over a raw socket), and the kernel's errors are of other types.
     - **What gluetun needs outside the tunnel: no ICMPv4 at all.** For IPv6, only link-scoped traffic that can't leave the Docker network: neighbour discovery (hop limit 255 by RFC 4861), link-local and multicast destinations (MLD).
     - **The `LOCAL` exemption** keeps loopback's errors, so a UDP send to a closed local port still gets ECONNREFUSED.
     - **Side effect:** the container no longer answers pings from the Docker network or the LAN.
     - **Checked:** both rules load on the pinned image, and the leak test's check passes against it. In the namespace rebuild, three UDP packets to a closed port drew three "port unreachable" replies without the rule. With it, all three were dropped (counter 3) and none reached the wire.
- **Why a connection mark, not an interface rule alone.** The brief's sketch, `! -o <tun> ESTABLISHED,RELATED -j DROP`, would also drop WireGuard's own UDP to the endpoint, the replies to the web UI and companion traffic on the Docker network, because all of them are established flows on eth0. A mask-free exemption list would need the endpoint and the Docker subnet, which a static file can't know. The mark catches exactly the flows that have used the tunnel. Loopback, the Docker network, inbound UI connections and the WireGuard socket never do, so they keep working.
- **Only what gluetun's image ships (the runner's condition).** The image's iptables is v1.8.11 on the nft backend: `iptables` and `iptables-nft` hold gluetun's rules, `iptables-legacy` is empty, and `ip6tables-legacy` doesn't work on this kernel. Rules used: the `connmark` match, the `CONNMARK` target, the `icmp`/`icmp6` and `addrtype` matches and the interface match. All three loaded through gluetun's own post-rules path on the pinned digest, and `iptables -C` finds them in both families (see "Checked" below). The VM run is the proof on the fleet's kernel: `post_rules_ipv4`/`_ipv6` fail loudly if anything there differs.
- **The ICMP drop's scope.** It applies only off the tunnel and only to non-local destinations, but to every ICMP type. Web-UI replies to the Docker network are TCP, and so is everything Lodestar exchanges with its companions, so neither is affected. The IPv6 exemptions (link-local or multicast destinations, hop limit 255) don't depend on the type, and they are bounded by gluetun's own policy: a marked flow still meets rule 2, a new echo to a global address meets gluetun's DROP policy, and kernel errors use the default hop limit. The rules file's comment calls the multicast exemption "link-scoped", but `--dst-type MULTICAST` matches every scope. That's harmless here because the host routes neither multicast nor IPv6. It is left for X-gluetun-leak-cmp, since changing the file means a new pin and SHA.
- **A fixed tunnel name, set explicitly.** `-o wg+`/`tun+` wildcards would cover both of gluetun's defaults, but the DROP needs "not the tunnel". One rule can't negate two interface patterns, and a user chain made with `-N` fails if gluetun's firewall is ever re-enabled without a flush, which would disable it. So the rules name `wg0`, and every compose that ships them sets `VPN_INTERFACE: wg0`. The leak test reads the name from gluetun's config, checks that the interface is live under that name (`vpn_interface_live`), and checks all three rules for that name (`post_rules_ipv4`/`_ipv6`): each with `-C`, and the three heading OUTPUT above every gluetun accept. A mismatch fails instead of passing silently. The user guide's manual step says the same: set `VPN_INTERFACE=wg0`, or the rules do nothing.
- **It never loosens gluetun's firewall.** The rules only mark or drop, and a test enforces that (`test_steps.py`: no ACCEPT, RETURN, policy, flush or delete). **Re-verify on any gluetun upgrade.** `master`'s fallback chain sets connmark `0x567` with a full mask and accepts only on an exact `0x567`. Our bit would make that `0x800567`, so those flows would fall to its DROP. That fails closed, but it breaks traffic. The pin stays at v3.41.3 until a new version is checked with the leak test.
- **Checked three ways:**
  - The syntax on iptables 1.8.10 (nft), both families.
  - On real gluetun `v3.41.3` (the pinned digest), started here with a fake tunnel: it loads the file and the three rules head OUTPUT in iptables and ip6tables, and they stay there through gluetun's own VPN restarts. A missing file that Docker turned into a folder stops gluetun with `read /iptables/post-rules.txt: is a directory`.
  - A network-namespace rebuild of the VM's case, with gluetun's v3.41.3 OUTPUT/INPUT rules and a TCP flow opened through `wg0` before `wg0` went down. Without the post-rules, 4–5 PSH/FIN packets left by eth0 with the tunnel's source address. With them, none did. A web-UI request into the namespace and a connection to the Docker network both still worked.
- **How it gets there: copied in, not bind-mounted.** Compose `configs:` with inline `content:`, in the fleet's `compose.yaml` and the PIA example. Without Swarm, Compose copies the text into the container as a 0444 file at `/iptables/post-rules.txt`. Checked: there is no mount entry, and gluetun's own root could write to it. That differs from the brief's "read-only, mounted", and it is a deliberate trade. Only gluetun's root can change the file, gluetun reads it once at start, and a bind mount would need a host file copied by `steps/run.py`, which this slice doesn't own. The manual Unraid step is a real read-only bind. This needs no new file copied to the VM and no host path. Tests check that both copies equal `packaging/companions/gluetun-post-rules.txt` byte for byte.
- **Where the rules can't load, gluetun doesn't start.** On a host without ip6tables (gluetun's `ip6Tables` empty) or without connmark support, a post-rule line fails. gluetun then briefly resets its policies to ACCEPT (its existing handling of any failure while turning the firewall on) and exits, before the VPN starts. The container restarts and fails again, an outage rather than a leak. On the fleet VMs, the leak test's `post_rules_ipv6` check fails first. The user guide's troubleshooting table tells users with no IPv6 firewall to delete the `ip6tables` lines. The template slice should decide whether Lodestar writes an IPv4-only file there.
- **The PIA example is pinned** to the fleet's digest (it was `:latest`), the version the rules were checked on.

## The leak test
- **Recreating gluetun is guarded (the VM re-run on 2026-11-13).**
  - **The windows.** The VPN endpoint keeps sending the old session for a while after a recreate. Two paths can then draw a "port unreachable" back to it:
    - **The container.** The old one shutting down, or a new one before gluetun has turned its firewall on, can answer the endpoint's packets that still reach it.
    - **The host itself, the likelier source of run 1's single ICMP to the endpoint on eth0** (the delta review's B1). Docker deletes every conntrack entry naming the container's IP when the old endpoint leaves and the new one joins (moby v27 `libnetwork/drivers/bridge/bridge_linux.go:1466-1468, 1503-1506`). The endpoint's leftover packets for the old session then match no NAT state. They go to the host's own INPUT, never FORWARD, and the host's kernel answers from its public address. Once conntrack is flushed, no such packet can come from the new container. The DOCKER-USER guard, the counter and the veth capture all miss this path.
  - **The guards.**
    - **The recreate guard:** a DOCKER-USER DROP (`-s <endpoint> -p udp --sport <port>`, tagged `lodestar-leak-guard`). `tunnel_up` uses it at the start and in recovery, and lifts it only once the leak test's own check finds the post-rules in both families. Rules that never load (a 30 s deadline) leave it on, fail `post_rules_before_egress`, and are reported as `recreate_guard_held`, never as a credentials problem. `cleanup` lifts it.
    - **The host guard:** an INPUT DROP for the endpoint's UDP (tagged `lodestar-leak-host`), held from just before the first recreate until `cleanup`. It can't touch the tunnel: the new session's replies are de-NATed and forwarded, never delivered to the host. It hides nothing the test judges either, because the container's traffic never crosses the host's INPUT.
    - **Removal:** both are removed copy by copy (`-C` then `-D`, as the counter is). A killed run's leftovers are cleared at the start, and a copy that won't come off fails `recreate_guard_lifted`.
  - **Tests:**
    - the stub refuses a recreate made without either guard;
    - a guard that can't be set stops the run (`recreate_guarded`, `host_guarded`);
    - rules that never load, in both families or in IPv6 alone, keep the guard on;
    - leftovers are cleared;
    - a stuck delete fails.
  - **Outside the fleet:** for a user's own gluetun restart, the same window can't be closed from the post-rules, because they load with gluetun's firewall. What can leave in it is a kernel error to the VPN server, which already knows the host's address. Recorded for X-gluetun-leak-cmp.
- **New checks:**
  - `vpn_interface_live`, `post_rules_ipv4` and `post_rules_ipv6`: the interface gluetun's config names exists, and all three rules are present for it, each by line number before the first ACCEPT in OUTPUT (the review's O1; a unit test runs the check against a fake `iptables`), in whichever iptables backend gluetun uses. Because gluetun silently skips a missing file, the test checks rather than assumes.
  - `ping_up`, `flow_started` and `flow_alive_<phase>`: an unprivileged ping (`--cap-drop ALL`; Docker sets `ping_group_range` for the namespace, checked here) is opened through the tunnel before phase A and kept running through both down phases. The leak no longer depends on gluetun happening to hold a connection open (the self-review's finding). The flow is removed before gluetun is recreated.
  - Phase B's counter and capture start before the interface goes down, so a flow's first packets after the drop are seen too.
  - `no_host_egress_<phase>`: a packet counter in the host's DOCKER-USER chain, just below the endpoint block, matching the compose bridge in and the egress interface out. It must read 0. This is the brief's "nothing from the compose bridge leaves the host's eth0 apart from the endpoint's own UDP", measured where the packets leave rather than on gluetun's veth. An unreadable or unset counter fails.
  - **The veth capture judges only what the container sends** (the runner, after X-test-vm's diagnostic run 2 on 2026-11-13). That run saw 0 ICMP on the bridge and 0 on the host's eth0, yet counted 2 ICMP in phase A of the veth capture, which records both directions.
    - A plain pcap holds no direction, so an embedded parser (`python3 -I` on the host) reads it and counts a packet as sent when its Ethernet source is the container's MAC.
    - Packets towards the container are counted apart (`captured_inbound_<phase>`) and never judged.
    - Every ICMP and ICMPv6 packet is reported by type, code, direction and the far end's class (`icmp_<phase>_<in|out>_t<type>_c<code>_<endpoint|linklocal|multicast|other>`), never by address.
    - Unit tests build pcap fixtures:
      - inbound packets pass and are classed;
      - outbound ICMP to any class fails;
      - ICMPv6 is classified;
      - an unreadable pcap fails `capture_read_<phase>`;
      - a bad MAC stops the test.
  - Per-class counts of what the container sent (`captured_tcp/udp/icmp/other_<phase>`, from the parser), as evidence. A counter or capture that can't be read prints no count line rather than a misleading 0, and still fails. Run 3's host router solicitation and DAD frames are a fixture: classed inbound, never judged.
- **The earlier criterion.** The veth capture would also have seen these packets. The new checks make the cause explicit (the post-rules) and add the host-side view the brief asks for.
- **(b) Host rules.** The leak test adds three, all for its own run and all removed by `cleanup`: the DOCKER-USER counter, which only counts, and the two guards, which hold the endpoint's UDP only while gluetun is recreated or the test runs. A standing host DROP rule for the fleet VMs, as defence in depth while they crawl, is still not added, because it would hide a gluetun regression from the leak test. Propose it with the crawl phase if wanted. It is never something an Unraid user is asked to do.

## X-gluetun-leak-cmp (the runner's follow-up, Opus): brief notes
- **Compose templates:** emit gluetun's `configs:` entry with the file's inline `content:` (as `infra/fleet/steps/vm/compose.yaml` does). This needs no host path; the file is copied in as 0444. Also set `VPN_INTERFACE: wg0`.
- **Unraid XML:** add a read-only Path, host `<gluetun folder>/post-rules.txt` → `/iptables/post-rules.txt`, plus a `VPN_INTERFACE=wg0` Variable. Lodestar writes the file. A missing host file fails closed: Docker creates a folder there and gluetun exits with `read /iptables/post-rules.txt: is a directory`, which was checked on v3.41.3.
- **Source of the text:** `packaging/companions/gluetun-post-rules.txt`, embedded at build time so the generator and the fleet can't drift. A test keeps the fleet's copies equal to it.
- **Also:** correct the gluetun Overview ("Its firewall blocks all traffic while the VPN is down"), regenerate the goldens (`UPDATE_GOLDEN=1 cargo test -p lodestar-companions --test templates`), and drop the guide's **(planned)** note.
- **O2 (review of d60760d5):** re-run the `post_rules_ipv4`/`_ipv6` checks after phase B's reconnect, before the flow is removed, for in-VM evidence that the rules survive gluetun's own VPN restart. (Seen here on the pinned image, but not yet on the VM.)
- **O3 (review of d60760d5):** flows opened before gluetun's `enable()` never touch wg0, so the rules don't cover them. v3.41.3 doesn't flush conntrack when it turns the firewall on. Templates should start the companion only once gluetun is healthy (`depends_on: gluetun: condition: service_healthy`, or the Unraid autostart wait). The fleet is already safe here: Lodestar starts `--no-deps` into a healthy gluetun (`block-lib.sh`).
- **OpenVPN:** gluetun writes `dev <VPN_INTERFACE>` into the OpenVPN config with no `dev-type` (`internal/provider/utils/openvpn.go:65`, `provider/custom/openvpnconf.go:78`). OpenVPN can't tell what kind of device `wg0` is, so `VPN_INTERFACE=wg0` is not for OpenVPN. The rules must name `tun0` there. The guide gives that variant as untested, behind its iptables check. The generator should emit the name to match the VPN type.
- **Pinning the text users download:** the guide and `operations.md` give a commit-pinned raw URL and the file's SHA-256, because gluetun runs its lines as root. A test checks that the SHA matches the file. The generator should embed the file instead of downloading it.
- **gluetun's startup window:** packets that arrive before gluetun's firewall is on draw kernel errors from the new container (see "The leak test"). The templates should start nothing that sends until gluetun is healthy (O3). Whether a host-side guard is worth offering to users is an owner question; it isn't one we ask an Unraid user to set up.
- **Not in scope:** an existing gluetun that Lodestar routes through by name. Lodestar can't change its mounts, so it can only point the user at the manual step.

## Follow-ups (X-gluetun-leak-cmp)
From the runner's review of #800 at 87be769b, and O3 of its review of e46cb683. No decision changes.
- **The guards in the leak test:**
  - **IPv4 only, by design:** `endpoint_valid` accepts only an IPv4 endpoint, so the endpoint's packets never arrive over IPv6.
  - **Set before they're inserted:** each guard's flag is set before its `iptables -I`. A signal in between still has `cleanup` look for the rule, and `drop_all` checks with `-C` first.
  - **`drop_all`:** only an `-C` exit of 1 counts as absent. Any other exit is an error, never "gone".
  - **The recreate guard's flag still set** reports `recreate_guard_held`, not a credentials problem.
  - **Released before the verdict:** `finish` releases both guards first. A guard that won't come off fails `guards_released`, so a run can't end `ok` with one left. On a signal, `cleanup` releases them and reports a failure itself. A test sends TERM mid-recreate and finds no copies left.
  - **Leftovers are removed by tag** (`--comment lodestar-leak-guard`, `lodestar-leak-host`), whatever endpoint they name. A killed run against an earlier endpoint no longer leaves its guards behind.
- **The host-stack path outside the fleet:** when a user restarts their own gluetun, Docker flushes the container's conntrack, just as on the VM. Their host's kernel can then answer the VPN server's leftover UDP with a "port unreachable" from the home address. The recipient is the VPN server, which already knows that address, so no privacy is lost. The post-rules can't reach the host, and no user is asked to add host rules. The user guide's sentence is now "Nothing Lodestar or gluetun sends leaves outside the VPN", which holds in that case.
- **The rules file's comment** now says what the IPv6 exemptions match: link-local destinations, multicast destinations of any scope, and hop limit 255. None of them can carry a flow off the tunnel, because rule 2 and gluetun's own policy still apply. Only the comment changed, but the file's SHA-256 changed with it, so the docs' pin moved too. The pin test now also checks, where history has the pinned commit, that the commit serves this file.
- **Not done:** `tcpdump -Q in` (old O7). It would drop the inbound evidence (`captured_inbound_*`) that showed run 3's router solicitation and DAD frames for what they were. The MAC check and the host counter already cover what `-Q in` would add.
