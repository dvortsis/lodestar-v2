# WK-20 decisions (#712): the chaos harness

A coordinator and N workers in one test process, with injectors for worker kills, partitions, coordinator restarts and clock skew, plus a funnel reconciler and a per-key fetch log (architecture §19.8, workers plan WK-20). WK-G's §19.8 gate tests run on it. Brief: runner, 2026-11-11T19:50Z.

## Where it lives
- **`crates/lodestar/src/cluster/testing.rs`, behind `#[cfg(test)] mod testing;`.** The `lodestar` package is a binary with no library target. So a test binary under `crates/lodestar/tests/` can't link the worker `Runtime`, `Cluster::start` or anything else in the package, and can't run them in-process. The existing in-process end-to-end test (`worker/runtime.rs`, `tests::end_to_end`) is a unit test of the binary for the same reason. No feature is added: the harness compiles only under `cfg(test)`.
- **The scenarios are `crates/lodestar/tests/cluster_chaos/scenarios.rs`**, compiled into the binary's tests as a child module of `testing.rs` (`#[path]`). The folder has no `main.rs`, so cargo doesn't also build it as its own test target. Run them with `cargo test -p lodestar --bin lodestar cluster::testing`. The runner approved this layout (2026-11-11, runner's call), and a comment at the `#[path]` line says why no `main.rs` may be added there.
- **WK-G's `cluster_gate.rs` needs the same arrangement:** another `#[path]` module under `testing.rs`, or a module beside it.

## The API
All of it is `pub(crate)` and documented at the top of `testing.rs`, with an example.
- **`Harness::start(Options::workers(n))`** starts the coordinator: a real `Pipeline` and store, and `serve`'s `Cluster` on them, wired as `serve` wires it. Then it joins `n` workers through the real join path (a join token, `lodestar_cluster::join`, credentials saved in each worker's own folder) and waits until each one is connected.
  - Each worker is the real `Runtime` behind the real `Worker` session loop, over TCP and mutual TLS.
  - `add_worker` joins one more.
- **Work in:**
  - `swarm.add(name)` makes a torrent every peer serves.
  - `find(i, key)` has worker `i` see a key with peers, as its DHT would.
  - `sight(keys)` has every eligible worker see the keys (see "What a test must allow for").
  - `swarm.hold(i)` and `swarm.release(i)` make worker `i`'s fetches wait, so its leases stay held.
- **Injectors:**
  - `kill(i)` and `restart(i)`;
  - `partition(i, Cut::{Both, ToCoordinator, ToWorker})`, `heal(i)` and `sever(i)`;
  - `restart_coordinator()`;
  - `skew(i, ms)`, `skew_coordinator(ms)` and `advance(by)`.
- **Waits:** `wait_connected`, `wait_fetched`, `wait_leased`, `wait_stored`, `wait_stored_sighting` and `wait_reconciled`, plus the generic `wait(name, within, cond)` and `wait_until`.
  - All are conditions with a deadline of at least 10 s, asserted. There are no fixed sleeps.
  - A wait that fails prints `diagnosis()`: the funnel; the server's counters; the fetch log; and for each worker its counters, what its runtime was handed (`Seen`: sessions, events by kind, the lease-moving events in order, its assignment, whether its stages run) and its status lines.
- **Checks:**
  - `funnel()` and `Funnel::reconciles()`;
  - `fetch_violations()`;
  - `remote_stats()` (stale, late and refused results);
  - `fleet()`, `epoch()`, `planned(i)`, `seen(i)`, `counts(i)` and `lines(i)`.

## How each injector works
- **Kill.**
  1. The worker's link is cut both ways, so nothing it says while dying gets out.
  2. Its task is aborted. The runtime and the session are dropped, never drained or shut down; the runtime's `Drop` aborts its stages.
  3. Its connections are closed at both ends.

  Its leases stay with the coordinator until they expire. `restart(i)` runs it again from its saved credentials and the same data folder, so WK-11's spool replays once it exists.
  - **It's a crash for the cluster, not for the disk.** Destructors still run: the runtime's `Drop` stops its stages and its DHT saves its state, and WK-11's spool writer will clean up the same way. A torn or unflushed file needs a process kill (start `lodestar worker` as `tests/worker_join.rs` does) or a crash hook in the runtime.
- **Partition.** Each worker dials the coordinator through a TCP relay of its own: a fixed address for the worker, whichever port the coordinator listens on now.
  - A cut direction holds what it read, end of stream included, as TCP's retransmissions would through a real partition. Healing lets it through in order, and nothing is lost.
  - `sever` closes the connections instead, so both ends see them drop.
  - A unit test checks each cut by condition, not by timeout: the relay counts the reads it holds (`Relay::held`).
- **Coordinator restart.**
  1. The cluster and the pipeline are shut down cleanly.
  2. The harness waits for the wall-clock second to change, because the epoch is the pipeline's start second.
  3. Both start again on the same store, data folder and seal key.

  The relays follow the new port, so workers reconnect to the same address. The fetch log counts restarts (`generation`). Each one starts a new epoch, so every token is new; the saved leases are restored, to the built-in worker.
- **Time.** One `ManualClock` (the base) moves only when a test says so. Every node, the coordinator included, reads it through its own `NodeClock` with an offset.
  - These clocks drive the leases, heartbeat offsets, the silent-session sweep, certificate checks, and each worker's TLS and session upkeep.
  - **The base starts at the wall clock and only moves forward.** The pipeline also expires remote leases by the wall clock: its heartbeat task calls `LeaseAuthority::expire(unix_now())` every few seconds. A base behind the wall would let a silent holder's leases expire before the test moved time at all. An earlier draft started the base 15 minutes behind, and the review's early-expiry check caught it (#712's review, M2). The converse limit: a scenario whose wall time outruns its base time by a TTL (10 minutes) would see the same thing. A coordinator ahead of the workers' wall-clock sealing day by less than an hour is fine, because from 23:00Z it pre-sends the next day's key.
- **The funnel reconciler.** `funnel()` reads `cohort_hour` (harvested, stored, lost) and `rollup_hour`'s `LATE_RESULTS` from the coordinator's store, and the lease authority's in-flight count: leases held plus keys waiting for a re-grant (a scenario has every worker dead after an expiry, and the funnel still reconciles). `reconciles()` is plan Q7's identity: harvested = Σ terminal − late results + in flight. `wait_reconciled(cond)` waits for it to hold together with a condition, because the writer flushes on its own cadence.
- **The fetch log.** Every fetch is recorded: the key, the node (`COORDINATOR` for the built-in worker), the peer, the base time, the generation, and the key's lease (holder and token) as the coordinator's authority had it when the fetch started.
  - `fetch_violations()` lists each key fetched by two nodes outside a lease expiry. A second node may fetch a key only after one of these:
    - a coordinator restart (a new generation);
    - a TTL of base time since the first node's fetch: the least an expiry needs, since heartbeats only push a live holder's expiry later;
    - an early hand-back the test recorded with `Swarm::handed_back` between the two fetches (for a drain or a revoke).
  - Two fetches that saw the same lease are a violation at any gap.
  - **The recorded leases never excuse a fetch** (#712's review). A coordinator bug that re-grants a live key under a new token would otherwise look like a hand-over.
  - The restart scenario's second fetch of a restored key comes after a restart, so it isn't a violation; the scenario pins it as expected (see below).
- **The checks catch the bugs they're named for.** The review mutated production code to test them, and each mutation was reverted afterwards (#712's review, re-run on this PR's final code):
  - **M1**, intake checking `authority.get(key)` instead of `held(worker, key, token)`: the partition scenario fails. Stale results now arrive while newer leases hold the keys.
  - **M2**, leases expiring at half the TTL: the kill scenario fails at its "not before the TTL" check.
  - **M4**, a claim overwriting a lease another worker holds: `fetch_violations` fails the partition scenario. Two workers fetched the same key under different leases at the same base time. The funnel and store waits fail in the kill and restart scenarios too.
- **No live network.** Every fetcher, the coordinator's built-in worker's included, is the swarm, and no node runs a DHT. Peers are public addresses (`203.0.114.x`) only so the network policy passes them as hints; nothing dials them.

## What WK-G can and can't test with it
- **Can:**
  - exactly-once and the funnel after kills, partitions and coordinator restarts (the four smoke scenarios show each);
  - current-epoch fencing: stale results arrive while newer leases hold the keys, are counted in `remote_stats().stale`, and nothing is stored from them;
  - Q7's earlier-epoch behaviour (below);
  - clock skew (flagged past `max_skew_ms`; refused at the TLS handshake past the certificates' 5-minute slack);
  - revocation, drains and pauses, through `server()`, recording each early hand-back with `Swarm::handed_back` so the fetch-log check allows it;
  - same-IP politeness as planned, through `planned(i)`. The fetch log records which peer each fetch dialled, so per-remote-IP sums can be counted from it.
- **Can't, without more:**
  - **A per-remote-IP politeness gate on real dials** needs a recording fake peer that counts concurrent connections per IP. The swarm records fetch starts, not connections or their overlap.
  - **The DHT side** (BEP 51 intervals, `get_peers`, §19.8's multi-worker test "on the in-process DHT test network") needs the workers on that network: `lodestar_dht::node::Node` on loopback, as `crates/dht/tests/network.rs` runs it. The harness doesn't start one; finds are injected by hand. Every announced peer would also be `127.0.0.1`, a single peer IP that only one same-IP bucket may dial. **The runner's call (2026-11-11):** the harness ships without the DHT network, and DHT reuse goes into WK-G's notes. This narrows the plan's WK-20 row ("on the DHT test network"): a refinement, flagged to the owner (§2.19).
  - **Spool replay** waits for WK-11; `restart(i)` already keeps the folder.
  - **The four budgets** belong in `bench/`, not here.

## What the runtime is missing for WK-G
Found while building the scenarios. Each is outside this slice's paths, and each has a scenario or a harness note that works around it today. The runner has them: (a) went to WK-11's session (it owns `worker/runtime.rs`); the rest are in WK-G's notes.
- **A worker that sights a key it holds can end its own lease as lost.** The holder's repeated claim gets its own lease back (`server.rs`: `Claimed::Held` by the holder). The runtime puts that in its pool as a new sighting, outside a reply. If the pool fetched the key lately, it turns the sighting away (`on_discovery`, `recent`), and the worker's `Funnel::duplicate` override ends the lease as lost. Another worker then harvests and fetches the key again.
  - Seen with three workers: `harvested 6, stored 3, lost 3`, and two workers fetching each key.
  - A real DHT sights the same key often, so WK-G's exactly-once and funnel gates will hit this.
  - **`sight` never sights from a key's holder.** `sight_with(keys, true)` includes it, for the test that pins the fix. The fix belongs in `worker/runtime.rs`: don't claim a key the worker holds, or don't treat a holder's own grant as a new sighting. A WK-G gate built on `sight` alone passes while this bug stands.
- **Hints are best-effort.** The server relays them with `try_send_spare`, so a sighting right after a holder reconnects can be dropped while the holder's queue is full of snapshot chunks. The key then waits for a later sighting. `wait_stored_sighting` re-sights every 2 s, from every worker but the holder.
- **Withdrawn: a stalled tick.** Reported to the runner before the push: a partitioned worker's hung connection stalled the coordinator's tick. A direct measurement disproved it: 9 ticks in 45 s, one every 5 s, both with the connection hanging and with it severed. The cause was the harness: `wait_leased` counted the cut-off worker's leases while the server still had it connected (until a tick swept it), so sightings sent their hints to it. `wait_leased` now counts only workers the harness can reach.
- **A re-granted key comes with no peers.** A worker with no DHT then waits out a 30 s lookup and a 120 s back-off before using peers that hints bring. **The harness shortens both to 1 s** (`PoolConfig` in the worker's `Config`, as the pool's own tests use short timers). A real worker would look peers up on its DHT.
- **Time that tests can't move.**
  - The runtime seals, and stamps discovery times, by the wall clock (`runtime.rs`: `unix_now`), not by the `Clock` the session gets.
  - The pipeline's epoch is its wall-clock start second, and it restores the leases it saved, which go to the built-in worker, at that wall time.
  - WK-G can't test midnight or a skewed worker's discovery times end to end until a `Clock` reaches the runtime and the pipeline.
- **One-way cuts** (`Cut::ToCoordinator`, `Cut::ToWorker`) are checked against the relay only (a unit test), not against the real cluster; WK-G's one-way partition gates are the first to use them there.
- **Two clocks expire leases.** The cluster server expires them by its `Clock` on each tick, and the pipeline by the wall clock on its own heartbeat (`pipeline/src/lib.rs`, the built-in worker's heartbeat task). They agree in production, where both are the system clock. In a test they don't: a lease decision follows whichever reads later. WK-G needs the `Clock` passed to the pipeline before it tests expiry around skew.
- **Heartbeat (5 s), lease TTL (600 s) and the silent window aren't set through `Wiring`** (`serve::server_config` keeps the protocol's defaults; `pipeline::LEASE_TTL_SECS`). So any jump past a TTL also passes the silent window: every live session times out and reconnects, and re-grants go to the sessions that follow (`wait_leased`). A test-only override in `Wiring` would let WK-G expire leases without that churn.
- **After a restart, a worker's earlier-epoch results for keys the coordinator restored are dropped as stale, not taken as late.** The pipeline restores the saved fetch queue as the built-in worker's leases, so under Q7 the key is held. The coordinator's built-in worker then fetches it again once a sighting brings it peers. That's consistent with Q7 as written ("a key that's stored or held is dropped as stale"), but it fetches a finished key twice. The restart scenario pins it, so WK-G sees any change.

## Other choices
- **Three workers in the kill, partition and restart scenarios,** so a re-granted key's holder always has another live worker whose sighting brings it peers.
- **The worker's per-peer-IP split is real:** with the coordinator and two or more workers behind one (unknown) public address, the planner splits each peer IP's two connections (WK-5). With a single peer IP, a worker in the other bucket gets 0 and never fetches. So each find names 16 peers (`PEERS`).
- **`Probe`** wraps the real runtime as the session's `Work`, forwards every call and records what it was handed (`Seen`). The runtime's own accessors aren't reachable once `Worker::run` owns it, and a failed wait needs them.
