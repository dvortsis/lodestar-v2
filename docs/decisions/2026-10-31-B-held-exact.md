# B-held-exact decisions: intake's held set follows the store exactly

The follow-up that `2026-10-31-X-import-refile-2.md` item 2 left. No schema change, no API change, no new metric or log event. Content safety is tightened, not loosened: no path leaves a hash out of `HeldSet` while the store holds it, once that path has finished its update.

- **Option (a): a per-hash hold query, and the releases use it too.** After a sweep (`refile_candidates`) or backfill batch commits, the writer holds `HeldSet`'s write lock, asks the store which of the batch's hashes a tombstone or quarantine row still holds (`Store::held_among`, on the writer's connection), and inserts only those (`HeldSet::insert_held`). The releases (`release`, `release_many`, `release_rules` in `api/src/filters.rs`) and the writer's quarantine expiry (`purge`) work the other way round. After their store commit they hold the same lock, ask the same question, and remove only the hashes nothing holds any more (`HeldSet::remove_released`). `HeldSet::remove`, the unchecked removal, is gone, so nothing can bring one back by accident.
  - **Why not (b), a removal generation.** It can't be exact from the writer side alone. A release commits its delete, a writer batch then holds the hash again and commits, and only then does the release remove it from the set. Whether the writer read the generation before or after its commit, it either skips a hash the store holds (unsafe) or keeps one the store released (over-strict). A generation only tells you a removal happened. It can't tell you whether that removal came before or after your commit in the store.
  - **A content-safety fix: the releases change too.** The order is: a release deletes its row, a writer batch holds the hash again and inserts it, and then the release removes it from the set. The store holds the hash, intake's set doesn't, and intake would fetch it. That hole is older than #282: every unconditional insert had it, and a writer-only query (option (a) as written) leaves it open. The release-side check closes it. It's flagged to the owner under `docs/owner-decisions.md` §2.19. The cost is a short over-strict window: `release_rules` removes its hashes from the set once, after its last chunk, so intake keeps refusing them while the release runs. Owned paths (runner, 2026-10-31): the three release bodies in `api/src/filters.rs` and the new methods in `filter/src/held.rs` were added to the brief's "Own". The `filters.rs` hunk is small because X-polish-1031c is editing the same file.
  - **Why it's exact.** Each store change to a hash's hold is followed by a reconcile: lock, read the store, update the set, unlock. Reconciles take turns under the lock. Take the last reconcile for a hash. Any store change that came after its read would need a reconcile of its own, also after that read, and so a later one. So the last reconcile read the store's final state. If the store holds the hash, a writer reconcile inserts it and a release reconcile doesn't remove it. If the store doesn't hold it, a release reconcile removes it and a writer reconcile doesn't insert it.
  - **Errors fail closed.** If the store can't answer, `insert_held` inserts every hash (the old behaviour) and `remove_released` removes none. Either way intake stays over-strict until the next start. The writer logs `pipeline.enrichment_failed` (or `pipeline.filter_purge_failed` for the purge), and a release returns its usual internal error.
  - **The cost.** Intake's `contains` waits behind one indexed read per batch hash (a sweep batch, a backfill batch, a release chunk). Readers don't wait for writers in WAL mode, so a batch's check takes milliseconds. A release checks in chunks of 1,024 hashes (`UNHOLD_CHUNK`), dropping the lock between chunks. Exactness is per hash, so it holds across chunks, and intake never waits behind a 200k-hash release all at once. If the check fails after a release committed, the release returns its usual 500 and the remaining hashes stay refused until the next start. `release_rules` now removes its hashes from the set once, after its last chunk, not after each one. While a large release runs, intake keeps refusing hashes the store has already released.
  - **`HeldSet` lives in `crates/filter/src/held.rs`,** not in `pipeline/lib.rs` as the brief says. The two new methods and `snapshot()` (for the tests) are added there.
- **The interleavings traced.** C is the writer's commit, Q+I its locked query and insert, S a release's store delete, M its locked check and remove, and V a non-release rule change (an engine reload, a list refresh, an exception).
  1. C, Q+I, S, M: M reads the hash released and removes it. **Released.**
  2. C, S, Q+I, M (the #282 case): Q reads it released and doesn't insert. **Released.**
  3. C, S, M, Q+I: M removes a hash the set didn't have. Q reads it released. **Released.**
  4. S, C, Q+I, M (the old hole): the batch held it again after the release. M reads it held and keeps it. **Held, as the store has it.**
  5. S, C, M, Q+I: M keeps it, and Q inserts it. **Held.**
  6. S, M, C, Q+I: Q inserts it. **Held.**
  7. A release can't land inside Q+I or inside M: both hold the write lock.
  8. C, V, Q+I: the store still holds it, so Q inserts it whatever the rules say now. **Held.** This is why the version check #282 removed must stay removed.
  9. V before C: the sweep's commit checks the version inside its transaction and writes nothing (`refile_import_candidates`), and backfill's does too (`b.rejected`). There's nothing to insert. A `release_rules` reloads the engine (V) before its delete (S), so a batch judged under the old rules is refused, never written after the release.
  10. Restart: the set is loaded from `filter_state().held`, the same tables `held_among` reads, so a reload and a reconcile agree.
  11. Purge (the writer's own task) and the writer's batches never overlap. Against an API change (a release, or the `correct` endpoint holding a hash) it's a release reconcile like M.
- **Not changed, still over-strict at worst:** the writer's ingest commit (`commit`'s blocked arm) and the API's `correct` still insert without asking the store. In the order C, S, M, I they keep a released hash refused until the next start. They never leave a held one out, and they're outside this slice's paths.
- **Tests.** Each test injects a step between a batch's commit and its hold check, through the test-only `Writer::between` hook: no sleeps.
  - `a_release_after_the_commit_stays_released`: both arms, released hashes stay fetchable.
  - `a_rule_change_after_the_commit_keeps_the_hold`: both arms. An edited class rule plus a narrowed rule with an `unless` leaves both holds in place.
  - `a_release_racing_a_new_hold_keeps_it_held`: the hole above, step by step (S, then C+I, then M), and the reverse order (S, M, then C+I). Both arms; the set ends held, equal to the store's.
  - `the_held_set_follows_the_store_through_a_purge`: the set equals `filter_state().held` after both arms and after an expiry purge.
  - `HeldSet`'s own unit tests cover the fail-closed error paths.
