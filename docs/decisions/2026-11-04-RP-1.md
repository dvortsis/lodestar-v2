# RP-1 decisions: pack corpora and the pack precision corpus

Slice RP-1 of `docs/plan/2026-11-04-v06-rulepacks.md` (§4.3 RP-1). Architecture §20.6 (packs and their guard column), §20.7 (shipped pack fixtures may be plain text) and §20.8 (fixture suites, precision corpus). It builds on RP-0's manifest (#424, `docs/decisions/2026-11-04-RP-0.md`).

## The corpora
- **One corpus per pack, `crates/filter/data/packs/<pack>/corpus.txt`, and one precision corpus, `crates/filter/data/packs/precision.txt`.** They're plain text, compiled in with `include_str!`, in a line format documented at the top of `crates/filter/src/corpus.rs`. Each line starts with a keyword: `rule`, `match` / `miss` (or `item` in the precision corpus), then `file <size> <path>`, `pad` (a BEP 47 padding file), `type`, `guards` and `gap`.
- **`type` overrides the classified content type,** as `POST /filters/test` does. Without it, an example is classified as ingest would classify it. Most examples leave it out, so the corpus also checks the classifier's part of each guard. For example, a screensaver or codec pack with a version and an architecture is classified as software, and MW-2 and MW-5 let it pass.
- **Today's numbers:** 110 pack examples, at least 3 must-match and 3 must-not-match for each of the 17 built stateless rules (SC-2 under its own id). There are 20 precision items, each labelled with the rules whose guard it exercises (`guards`), and together they cover every rule §20.6 gives a guard (MW-2–5, LU-1, LU-2, FK-1, FK-2, FK-5, SP-2, SC-1, SC-2).
  - **The labels are checked** (`precision_items_reach_their_guards`): each item must carry the evidence its rule reads before the guard (an executable for MW-2, a tiny HD video for FK-2, a long repetitive name for SP-2, and so on). So it is the guard that lets the item pass, not missing evidence.
  - The items include the plan's whole list: disc PC players (Blu-ray and DVD), VST and sample packs, screensavers, scene RAR sets (`.sfv`/`.nfo` and multipart), samples and trailers, short-episode packs, discographies, offline cracks, and single-player trainers and mods.
- **A rule with fewer than 3 examples of either kind fails the report** (`Report::failures`), not only the test, so RP-3 reports the same pass or fail that CI enforces.
- **The parser is bounded and never panics:** 1 MiB per file, 4,096 bytes per line (SP-2's examples need names over 300 characters), 1,000 examples per file, 64 files per example, sizes checked for overflow. Every error names the file and the line (`<file>:<line>: <message>`, line 0 for the file as a whole). `Corpus::builtin()` returns the parse error rather than panicking, because RP-3 calls it in production. Property tests feed it arbitrary text and keyword soup, and round-trip generated examples.

## How examples are made (content safety)
- **Names and file lists only.** No infohashes, magnet links, URLs or real release names. Items carry an empty hash list.
- **Every name is synthetic:** "Example Movie 2019", "Sample Band", "GRP" for a scene group, and the reserved `example.com` / `.org` / `.net` domains for site adverts. The executables, lure notes and scam names are made-up file names and sizes. They show the shape a rule reads, never a working lure or a real download.
- **The service and game words the scams rules read** (Spotify, Netflix, Robux, Fortnite and the rest) appear as bare words in made-up names, because SC-1 and SC-2 match on them. No example names a real scam download or links to one.
- **No adult, child-safety or CSAM-adjacent examples.** No pack rule is CSAM-related; the core's fixtures stay hashed and are not part of this corpus (§20.7).

## How they run (`lodestar_filter::corpus`)
- **One rule at a time, through `Engine::judge`.** Each example is judged with only its pack on and every other rule of that pack switched off. So the result is that rule's own, including SC-2 by its own id. With the whole pack on, the strongest rule would decide, and a must-match for a hide rule could pass because a drop rule took it. A must-match passes when that rule decides with its version's action. A must-not-match passes when nothing decides.
- **The core runs with empty term lists,** so only the pack rules decide. A non-pack decision is reported as it is (`RuleRef`), so it can never pass as the rule's match.
- **The current versions are judged,** recorded as accepted, so nothing is pending and the run shows what this build ships. It doesn't use an install's applied versions: the corpus checks the rules, not the install's state.
- **Precision items are judged against every built stateless rule, one at a time.** An item passes when none of them holds it.
- **The API for RP-3, with no I/O:** `Corpus::builtin()?.run(&manifest)` returns a `Report` with results per pack, per rule (version, action, counts per kind, `disagreements()`) and per item (line, name, expectation, what decided). It also has the precision results, the direction checks, `failures()` as readable lines and `gaps()`. `GET /filters/fixtures` can report counts and disagreements per rule from it directly.

## Directions (RP-0's records against the corpus)
- **Each version is compared with the one before** (a first version against nothing), over the pack's examples and the precision items. The comparison calls each version's own code (`Version::matches`), which is the code the engine applies for that version.
  - The corpus *shows* `widens` (an example only the new version matches) or `narrows` (one only the old version matches).
  - With the same matching, it shows `action-heavier` or `action-lighter` (from the versions' recorded actions).
  - It shows `mixed` for anything that combines these.
- **The record must agree.** `mixed` agrees with any change shown, since it already counts as weakening.
- **A version the corpus shows no change for never agrees.** A version bump then fails CI until an example that shows the change is added. That keeps "bumped whenever what a rule matches or its action changes" honest in both directions. The pass/fail check above catches a change *without* a bump.
- **A version whose code (or its predecessor's) is gone from the build isn't compared** (`Observed::NotChecked`). Only its record is left.
- **SP-3 and SP-4 are exempt** (`corpus::STATEFUL`). They depend on state, so their cases are sequence fixtures run in RP-4's and RP-5's tests, which also check their directions. The parser refuses `rule SP-3` / `SP-4`, and the coverage test skips them by id once they're built.

## RP-0's GOLDEN
- **Kept.** The corpus now guards against silent matching changes the way the plan intends. A must-match or must-not-match flips, and any version bump must be shown by an example. GOLDEN still adds something the corpus can't: it runs 3,000 generated combinations of every rule's evidence and guards, so a change in a corner no hand-written example covers still fails it. It costs one test and only changes with a version bump. Retiring it is left to the runner (RP-G, or the first slice that bumps a rule's version).

## Known gaps: guards §20.6 names that aren't built (flagged to the runner)
The precision corpus found two guards from §20.6's guard column that the shipped code doesn't have. RP-1 owns neither `packs/**` nor `engine.rs`, and fixing either is a matching change that needs a version bump (RP-0). So the items are recorded with a `gap <rule>` line rather than left out:
- **MW-2: "music production packs (VST/samples)".** MW-2@1's only guards are `type:software|game` and disc layouts. A VST collection or a sample library whose files are mostly audio classifies as Music, so its installer makes MW-2 hide it. Both precision items (`Example Synth VST Collection v2.1 x64`, `Example Drum Samples Vol 3 WAV`) are held today.
- **FK-2: "short-episode pack".** FK-2@1's guards are the `sample` / `trailer` words and a `Sample/` folder. A pack of short HD episodes, each under the classifier's 40 MiB tiny-video threshold, is flagged (`Example Shorts S01 1080p WEB`).
- **A `gap` line is checked.** A gap must be one of the item's `guards`. The item passes only while exactly its gap rules hold it. If another rule holds it, it fails. When the guard is built, the item stops being held, the corpus fails with "remove its `gap` line", and the fix's version (`narrows`) is shown by that item. `known_gaps_are_listed` pins the list, so a new gap can't be added quietly.
- **`Report::passes()` is true while gaps exist,** because they're recorded and pinned. RP-3 has to report them per rule in `GET /filters/fixtures` (`Report::gaps`), and RP-6 has to show them, so a known over-filter never shows as a clean pass. This was flagged to the runner for those briefs.
- **Suggested follow-up** (the runner decides where it goes, perhaps RP-2's successor in the engine sequence or its own slice): MW-2@2 `narrows`, with a music-production guard (audio samples plus an installer and plug-in extensions such as `.dll` / `.vst3`, or the classifier's software signals). FK-2@2 `narrows`, not flagging when several tiny videos form an episode sequence. Each needs a changelog entry and, through RP-3, the acceptance preview.

## Not covered
- **SP-2's "many unrelated high-demand titles"** half (§20.6) isn't built: SP-2@1 matches only a name over 300 characters of repeated words. It is a missing match, not a guard, so it has no precision item. The corpus covers only what SP-2@1 does. Its examples include a 290-character Cyrillic name (over 300 bytes), because the length is counted in characters.
