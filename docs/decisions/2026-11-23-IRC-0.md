# IRC-0 decisions (IRC client in the new crate `sources-irc`)

Slice IRC-0 (API lane, 2026-11-23). Spec: plan `docs/plan/2026-11-05-v07-m7.md` (IRC-0 row and §4 "IRC-0"), architecture §18.1 (the plugin's egress), §18.4 (per-plugin egress and kill-switch), §18.7 (every external connection through the plugin's egress; politeness). Builds on NOS-2a (`docs/decisions/2026-11-12-NOS-2a.md`, `connect_tcp_routed`). IRC-1 (announce matcher), IRC-2 and IRC-3 build on it.

## Shape
- **A new crate, `lodestar-sources-irc`, with no IRC library** (plan: "no IRC crate"). Two modules: `line` (framing, parsing, encoding: pure, fuzzed) and `client` (the connection task). Nothing depends on it yet, so it lands inactive (plan §1: "IRC-0/IRC-1 (no plugin)"), and no workspace-dependency line is added (cargo would warn that it's unused); IRC-2 adds it with the first user.
- **API:** `spawn(Config, Egress) -> (Handle, Events)`. `Events` is a bounded `mpsc::Receiver<Message>` of every server message except `PING`, CTCP, `CAP`, `AUTHENTICATE` and the SASL numerics 900–908 (they carry the account name). `Handle` is cloneable: `privmsg`, `join`, `part` (validated and encoded at the call, then queued), `state()` (a `watch` of `State`), `stats()`, `shutdown()`. Dropping every `Handle`, or the `Events` receiver, stops the client. IRC-1 reads `Events`; IRC-2 sends a bot's invite command, which carries the user's IRC key, with `privmsg_secret` (refused on plaintext, built in a wiped buffer, like a channel key in `join`), and joins with `join`. **A busy server can't hold back `Handle` lines:** the session's `biased` select takes a queued `Handle` line before it reads the socket, still gated by flood control and after the protocol's own lines (runner, 2026-11-23T17:54Z).
- **A sans-I/O state machine** (`Proto`) does the protocol: it takes parsed messages and the clock and queues lines. The session loop only reads, writes and waits. So every protocol path is unit-tested without sockets, and the integration tests check the wiring against a scripted loopback server.
- **No logging in the crate.** It reports through `State` (with `Disconnect` and `Stop` reasons) and `Stats` counters; no variant carries a credential. The only server-chosen text in them is the nick in `State::Ready`, which is filtered: at most 64 bytes, no space, `!`, `@`, `:` or `,`, no control character and no Unicode format character (category Cf: bidi controls, zero-width characters, the soft hyphen, tag characters; Unicode 16's list written out, no new dependency). A nick that fails the filter is ignored and the client keeps the one it has. The plugin logs what it chooses with `log_event!`.
- **`Events` carry raw, untrusted server text.** A `Message`'s source, parameters and tag values can hold any character but `NUL`, `CR` and `LF`: control characters, mIRC formatting, bidi controls, zero-width characters. Both types say so in their docs. **IRC-1 (and any later consumer) must strip formatting and control characters** (`line::strip_formatting` plus a control and format-character filter) before it stores, logs or shows any of it.

## Egress (§18.1, §18.4, §18.7)
- **Every connection is `connect_tcp_routed`** over an `Egress` built from the plugin's resolver, `NetPolicy`, `Route` and `KillSwitch`. The switch is a required argument of `Egress::new` (an `Option`, `None` only when the plugin has none, as §18.4 makes it optional), so it can't be left out by accident. The crate opens no socket of its own. The guard's refusal (`Blocked`, `InvalidUrl`) and a route that can't work stop the client for good (`Stop::Refused`); resolve, connect, proxy and kill-switch failures are retried with back-off.
- **The kill-switch stays on after the hand-over,** as NOS-2a says the stream's owner must: it races the TLS handshake, every read and every write, and is polled before each line goes out, so nothing is written once it's down and the connection is dropped at once. While it's down, each retry is refused by `connect_tcp_routed` before any lookup, with the usual back-off, so nothing connects until it's up again.

## Limits (all bounded; none is a number the owner set)
- **Lines:** a body of at most 512 bytes including `CR LF` (RFC 1459), plus an IRCv3 tags section of at most 8,191 bytes (`@` and its space included), so the framer passes on at most 8,703 bytes a line. **A longer line is reported once and discarded up to its `LF`, never accumulated:** the read buffer never holds more than one line. Outgoing lines have the 512-byte limit.
- **At most 15 parameters** (RFC 2812: the fifteenth takes the rest of the line, so no line makes more). **At most 64 tags;** later ones, and tags whose key isn't a valid IRCv3 key, are ignored; a repeated key keeps the last value. **At most 128 `;` items are examined per line** (twice the tag cap); later items are ignored unread, and a key is checked before its value is unescaped, so a section of thousands of tiny items costs a bounded amount of work.
- **Text is UTF-8 when it's valid UTF-8, Latin-1 otherwise** (decided for the tags section and the body separately), so no byte is lost and a decoded line is at most twice its bytes. `NUL`, and `CR` anywhere but before the `LF`, make a line invalid (dropped and counted).
- **Queues:** 256 messages waiting for the plugin (more are dropped and counted, so a slow plugin can't stop `PONG`s); 64 lines from `Handle`; 64 protocol lines (a server that makes the client queue more is flooding it and is disconnected); at most one pending `PONG` (a newer `PING` replaces it). At most 16 `CAP LS` lines, 32 configured channels, and 3 alternative nicks (`nick_`, `nick__`, `nick___`).
- **Worst-case memory per client: about 4.5 MB of event-queue text, under 5.5 MB in all.** A message decodes to at most about 17.4 KB of text (an 8,701-byte line, every byte doubled by Latin-1 decoding), so 256 waiting messages hold at most about 4.5 MB of text, plus under 1 MB of per-message vectors (64 tags and 15 parameters each, at most). The rest is small: 64 + 64 outgoing lines of at most 512 bytes, one line's read buffer (8,703 bytes) and a 4 KB read chunk. A plugin running many clients budgets this per client; IRC-2 drains the queue promptly, so the worst case needs a plugin that has stopped reading.

## TLS and credentials
- **TLS by default** (port 6697), rustls on ring with the platform verifier, or `Roots::Only` for a server with its own CA, as `sources-importers` does it. A certificate that doesn't verify stops the client (`Stop::Certificate`) instead of retrying. Plaintext is a separate `Transport::Plaintext` the user must choose.
- **No credential ever goes out without TLS:** a plaintext `Config` with a server password, a login or a channel key fails validation (`CredentialsNeedTls`), `Handle::join` refuses a key on plaintext, and the state machine checks again before writing `PASS`, SASL, `IDENTIFY` or a key (`Stop::Internal`). Outgoing lines are in buffers wiped on drop; `Debug` of `Config`, `Auth` and `Channel` prints neither the account nor any secret.
- **SASL PLAIN** with `CAP LS 302`, `CAP REQ :sasl`, then `account\0account\0password` in 400-byte base64 chunks (with a final `+` after an exact multiple). **It fails closed: the client never registers without SASL.** How each refusal ends (runner, 2026-11-23T17:54Z):
  - **Retried with back-off** (`Disconnect::SaslUnavailable`): a server that doesn't offer `sasl` with PLAIN, and one that registers the client without it (a server with no `CAP`, or a welcome mid-login). The connection is dropped before any join; networks drop the capability while services are split, so a later attempt can succeed. The usual back-off (up to 10 min by default) keeps the retries polite.
  - **Stops for good:** a `CAP NAK` of `sasl`, or an `ACK` without it (`Stop::SaslUnavailable`), and 902/904/905/906 (`Stop::AuthFailed`). A failed login isn't retried, so a wrong password can't hammer services into an account lock.
  - `AUTHENTICATE +` that the client didn't ask for gets nothing.
- **SASL EXTERNAL is left out:** it needs a client certificate and key in the settings and the secret store, and no source the plan lists needs it. A later slice can add it.
- **NickServ:** `PRIVMSG <service> :IDENTIFY <account> <password>` after the welcome; channels are joined once services confirm with 900 or after 10 s, since NickServ's notices are free text. So a failed NickServ login isn't detected (only SASL's is). **`Auth::NickServ` has a `service` target** (runner, 2026-11-23T17:54Z): `None` sends to `NickServ`, or the user sets a nick with its services server, `NickServ@services.<network>`, which the server delivers only to that server's `NickServ`, so a password can't reach an impostor holding the nick during a services split. The target is validated: an RFC 2812 nick, optionally `@` and a host name (letters, digits, `-`, `.`); never a channel, mask or list, and no space, comma, `:` or control or format character. The IRC-2 settings text should recommend SASL where the network offers it, and the `nick@server` form otherwise. A nick the server assigns is accepted up to 64 bytes (a network's NICKLEN can be over RFC 2812's 30), so invitations and joins still track it.
- **Credentials are single IRC words** (no space or control character), at most 64 bytes for the account and 256 for a password; channel keys at most 32.

## Politeness and reconnect
- **Flood control:** a token bucket over every outgoing line, `PONG` and registration included: a burst of 4, then one line per 2 s (the common server allowance; irssi's defaults are close). Hard limits a setting can't pass: a burst of at most 10, at least 500 ms a line.
- **Reconnect:** the wait after the n-th failure in a row is `min(cap, base × 2ⁿ⁻¹)`, jittered uniformly into its upper half (so never under half the step). Defaults: base 5 s, cap 10 min; the count resets once a connection has been registered for 5 min, so a server that accepts and then drops the client keeps backing off. Hard limits: base at least 1 s, cap at most 1 h, and `stable_after` at least 60 s, so no setting turns the back-off off. Jitter comes from the standard library's random hash keys (no new dependency).
- **Stops for good** (a retry can't fix them): shutdown, the guard's refusal, a bad certificate, a failed SASL login (902/904–906) or a refused SASL request (`NAK`), a wrong server password (464), a nick the server calls invalid (432), a server ban (465), and **three connections in a row that the server ends with `ERROR` before any registers** (`Stop::Banned`; a K-line sends `ERROR`, not 465). A registration ends that streak; other failures in between (a connect error, a timeout) neither end nor extend it. Everything else is retried. A nick that's taken (433), collides (436) or is held for a while (437) gets the next alternative.
- **Keepalive:** by default, after 120 s of silence the client sends `PING`; 60 s more and it reconnects, so 180 s is the default idle limit. Each of the two is settable from 1 s to 10 min, so `validate` allows an idle limit of up to 20 min. Registration must finish within 60 s by default.

## Behaviour the plan fixed
- **CTCP (and so DCC) is ignored:** never answered, never passed on, counted. `Handle::privmsg` refuses `\x01`, so the client never sends it either.
- **Invitations join only configured channels,** and only one not joined or being joined. A kick isn't rejoined on its own; an invitation can bring it back. A failed join (403, 405, 471, 473, 474, 475, 477) can be retried by a later invitation.
- **Case mapping is RFC 1459's** (`[]\~` fold to `{}|^`), the default when a server doesn't say. ISUPPORT isn't parsed; IRC-1 can add it if a network needs another mapping.
- **`line::strip_formatting`** (bold, colours, hex colours and the rest) is here for IRC-1's matcher, fuzzed with the parser.

## Tests
- **The parser** has golden lines, invalid-line cases, property tests (hostile bytes never panic and stay within limits; `encode` → `parse` round-trips; framing doesn't depend on how the stream is cut; tag escapes round-trip; formatting removal never grows), and the `irc_line` fuzz target (parse, framing, re-encode round-trip, CTCP, formatting, `CAP` lists).
- **The client** against a loopback server through `connect_tcp_routed`: registration, joins, `PING`, CTCP dropped, SASL over TLS, a failed login stopping for good, a certificate for another name, the guard refusing loopback under a public-only policy, an over-long and a malformed line dropped, reconnect back-off, the kill-switch dropping the connection and holding retries, flood pacing, and a silent server timing out. The TLS tests reuse the email tests' throwaway CA and `mail.test` leaf (`crates/integrations/tests/fixtures/email/`), read by path, rather than adding a second set of keys.

## For the merge review (runner, 2026-11-23T15:39Z)
- **Owns widened by the runner** for this PR to two one-line edits: the `irc_line` row in `fuzz/README.md`, and `("lodestar_sources_irc", Component::Sources)` in `crates/lodestar/src/logging/mod.rs` `TARGETS`, which `logging::tests::targets_cover_every_crate` needs for every workspace crate. The crate itself still writes no log lines.
- **Fuzz run:** `cargo +nightly fuzz run irc_line` from an empty corpus (no seeds are committed; the property tests and goldens cover the known shapes), 300 s (about 2.9 M runs), then 60 s more on the final code (about 0.5 M runs). No crash, no timeout, no leak report.
- **No secret reaches logs, `Debug`, `State` or `Stats`:** the crate does no logging; `Debug` of `Config`, `Auth` and `Channel` prints neither the account nor any password or key (unit-tested); `State`, `Disconnect`, `Stop` and `Stats` hold only enums, counters and the filtered, server-chosen nick, never a credential; `Events` drops `AUTHENTICATE` and the SASL numerics 900–908, which carry the account name. Lines carrying a secret are built in buffers wiped on drop.
- **Read and idle bounds:** every read is raced against the kill-switch and the protocol's next deadline. The idle clock moves only on a complete, parsed message, so a server trickling a partial line, or sending only over-long or malformed lines, still times out (a unit test through the session's framing and a loopback test pin it). Defaults (each settable only within 1 s to 10 min): connect 30 s (TCP, proxy and TLS handshake each), registration 60 s, `PING` after 120 s of silence and reconnect 60 s later (so 180 s without a message by default; `validate` allows up to 20 min), each write 30 s, the NickServ wait 10 s. A partial line is at most 8,703 bytes buffered, so a slow server costs no more memory than one line.
- **Writes and shutdown:** every write races the kill-switch and, after the write itself, a shutdown, so a shutdown during a stalled write ends it at once instead of after the 30 s write timeout (nothing more is written then, not even `QUIT`). The shutdown's best-effort `QUIT` goes through the same guarded write, with a 1 s limit and never once the switch is down.
- **Exact-edge tests** pin both line limits to the byte: a tags section of 8,191 bytes is parsed and one of 8,192 refused; a body of 510 bytes plus `CR LF` is parsed and one of 511 refused; the longest line the framer passes on (8,703 bytes) parses, and one byte more is dropped as over-long.
