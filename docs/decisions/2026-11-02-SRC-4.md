# SRC-4 decisions (consent framework)

Slice SRC-4 of `docs/plan/2026-11-01-v06-sources.md`. It covers architecture §18.7 (consent classes, credentials), §18.9 ("consent gating can't be bypassed through the API"), §20.11 (the password) and owner decision §1.8.8 (no audit), with the plan's Q13 and Q14 as the runner accepted them. The code is `lodestar_sources::consent`, `Control::update_source` and `Control::update_credentials`, the pipeline's start-up registration, and `PATCH /sources/{id}` and `PATCH /sources/{id}/credentials`.

## Class gating
- **The server checks each class's condition (`consent::need`) on every path that can turn a source on:**
  - **None:** a toggle.
  - **External:** an acknowledgement of the endpoint list.
  - **Account:** at least one stored credential that isn't a SOCKS5 one.
  - **Restricted and Overlay:** an acknowledgement of the consent screen, and the admin password every time they're enabled (Q13, tightened below).
- **The paths:**
  - **`PATCH /sources/{id}`:** the check and the write happen under the store's lock, and a new acknowledgement and the `enabled` state are written in one transaction.
  - **Every start:** the pipeline checks every source the store has as enabled. One whose condition doesn't hold is written as disabled before anything runs: no record, a stale or declined record, or missing credentials. A source enabled by an older build, by a hand edit, or by the import CLI's `register_source` is caught this way too.
  - **Settings import** can't reach source state: the registry only writes `settings.<section>.<field>` keys, and consent and credentials live under `sources.`. A test imports files that try it.
- **Removing what an enabled Account source needs disables it in the same write** (`Store::update_source_secrets` with a state).
- **The API reports what's missing:** `needs` is `endpoints_ack`, `credentials`, `consent` or null. `consent_version`, `endpoints`, `credentials` (names only) and `password_required` are also returned. `consent_required` now means "its class is enabled by an acknowledgement", so it's true for External too.
- **Errors:**
  - `409 consent_required` names the class and the version to send;
  - `428 confirm_required` when the password is missing;
  - `401` for a wrong password, which is checked before the store is read whenever an enable carries one;
  - `409 credentials_required`;
  - `400 invalid_credentials`, which names the rule and never a value.

## Consent-text versions
- **An acknowledgement is bound to `<text version>-<endpoint digest>`** (`consent::version`):
  - `consent::text_version(class)` is the version of the class's consent text. Raise it when a text changes in substance.
  - The digest is FNV-1a over the sorted, de-duplicated endpoint list.
  - So either a new text or a plugin update that contacts new hosts asks again. The digest isn't a security boundary: the manifest is compiled in, and the digest only notices a change.
- **Per class, not per manifest.** The brief says "the manifest's consent-text version". The consent texts are per class (Q1), and `manifest.rs` is outside this slice, so the text version is a function of the class. **Follow-up:** a plugin that needs its own wording can add a manifest field later; `consent::version` is the one place to fold it in.
- **A version change disables an enabled source at the next start,** rather than letting it run on an acknowledgement of something else.

## Consent records (Q14)
- **A record holds the class, the version and a boolean: `<class>|<version>|<0 or 1>`.** There's no time and no author (§1.8.8). An unreadable or declined record counts as none.
- **Stored in `settings` under `sources.consent.<plugin>`,** beside the existing `sources.priority.<plugin>`. That needs no schema migration while other slices may be adding one, and the settings export never reads these keys.
- **Disabling keeps the record,** so re-enabling the same version doesn't show the consent screen again. **Purging drops it** (`set_source_state(Purged)`, in the same transaction).
- **Enabling a Restricted or Overlay source asks for the password every time,** not only when its consent is first accepted. Q13 asks for it "to accept" consent. Without this, a stolen session alone could switch a source that had been turned off back on. §20.11's "asked every time, never remembered" is the model. This is a tightening of Q13, flagged under §2.19.

## Credentials
- **Sealed with the integrations `SecretStore`,** under the context `source:<plugin>:credential:<name>`. A sealed value copied onto another source or name doesn't open; a test copies one to check.
  - Stored as the sealed blob in `settings` under `sources.secret.<plugin>/<name>`.
  - The key file (`secrets.key`) stays outside the database. A store snapshot (`VACUUM INTO`) or a copied database holds sealed blobs only.
  - `SourceCredentials` opens the key file the first time it's needed, so an install without credentials never creates it.
- **Never returned, logged, put in an error or exported:**
  - responses list names only;
  - `Secret`'s `Debug` prints `Secret(***)`;
  - `SourcePatch`'s and `CredentialsPatch`'s `Debug` skip the password and values;
  - the credentials body is read by hand, so a malformed one is refused with a fixed message;
  - the settings export only writes registry fields.
  - **Tests:** every response in the API test, the settings export, and every file in the data directory are scanned for the value.
- **Names:**
  - 1–64 of `a-z`, `0-9` and `_`, plus the reserved `egress.socks5.username` and `egress.socks5.password`;
  - values are 1–4096 bytes, and the SOCKS5 pair 1–255 (RFC 1929), refused when saved rather than when SRC-5 builds the route;
  - at most 16 per source.
- **Plugin ids may not contain `/`** (`register_source_as` refuses one): it ends the plugin's part of a credential key.
- **Credentials have their own route,** so `editable` on `GET /sources` doesn't list them. `SourcePatch.password` is never serialized, and `CredentialsPatch` has no `Serialize`.
- **"Stored" means present, not that it opens.** A database restored without its `secrets.key` keeps an Account source enabled whose credentials can't be read: the plugin fails at run time, which is safe. SRC-14 can show that state.
- **Storing credentials on a Purged source isn't refused yet.** Nothing sets Purged before SRC-14, which owns purge and should decide.
- **Account's condition doesn't read the plugin's config schema yet.** Any stored credential that isn't a SOCKS5 one counts. **Follow-up for SRC-7** (the first Account plugin): require the schema's `writeOnly` + `required` names.
- **`SourceCredentials` implements SRC-5's `EgressCredentials`:**
  - both SOCKS5 names give a `SocksAuth`;
  - neither gives `None`;
  - half a pair or a value that doesn't open is `CredentialError`, so the route stays down.
  - It reads on the blocking pool.
  - **Wiring it into `EgressFactory` is SRC-14's**, with the rest of the egress settings.
- **Not zeroized everywhere:** the request body and the `serde_json::Value` it's parsed into hold the value until they're dropped, as the settings registry's secrets do.

## Atomic first registration
- **`Store::register_source_as(plugin, version, first, now)`** inserts a new plugin in its first state in one write. The pipeline uses it:
  - **Enabled** only for a plugin that's on by default and whose class needs nothing more than a toggle;
  - **Disabled** for every other plugin.
  - The second write that used to disable it is gone.
- **`set_source_state` refuses `Enabled`** (runner, #388 review): `enable_source`, which the consent check sits in front of, is the only way to enable a source.
- **`register_source` keeps its old meaning** (enabled on first sight) for the import CLI and about 20 tests. Closing it would be churn outside this slice, and it's safe:
  - it only enables on first sight, never a source already stored;
  - its callers are the import CLI and tests, which register importer adapters, not gated plugins;
  - every start checks each enabled source's condition before anything runs. A gated plugin that it enabled is switched off there; the restart test covers that case.
- **Test:** a temporary trigger aborts every later state write (the "crash"). Registering one plugin of each class still leaves every gated one disabled on disk.

## Draft consent texts — DRAFT, owner approval required (Q1)
**These are drafts.** They aren't UI copy. The owner approves the wording before SRC-15b merges (`docs/owner-decisions.md` §2.28). Each is written per §10.14: what happens, then what to do. `{name}`, `{hosts}` and the like are filled in from the manifest. When an approved text differs in substance, raise `consent::text_version` for its class.

### External
> **{name} connects to outside services.**
> When it's on, Lodestar contacts these sites on your behalf: {hosts}. They can see your IP address (or your VPN's) and when you connect, as they would if you visited them. Lodestar sends them search terms and info hashes, never your files or your account details.
>
> Traffic goes through this source's network setting ({egress}). If the list of sites changes in an update, you'll be asked again.
>
> [Turn on {name}] [Cancel]

### Account
> **{name} signs in with your account.**
> Enter the credentials {name} needs. Lodestar encrypts them on this server and uses them only to talk to {hosts}. They're never shown again, written to logs, included in a settings export or sent anywhere else. You can remove them at any time, and purging the source deletes them.
>
> Results found through your account stay on this server: Lodestar never shares them through Torznab, Stremio, exports or public peer finding, because private trackers usually forbid it.
>
> [Save and turn on] [Cancel]

### Restricted
> **{name} can expose you to legal risk.**
> {name} reaches sources that may index copyrighted or otherwise restricted material, or it announces your IP address to other peers. Depending on where you live, using it can break the law or your internet provider's terms, and other people can see that your address took part.
>
> - Lodestar collects metadata only: names, sizes and hashes. It doesn't download content.
> - **Use a VPN.** Set this source's network setting to your VPN, so the kill switch stops it if the VPN drops.
> - You're responsible for whether using it is lawful where you are.
>
> Enter your password to turn it on. You'll be asked again if this notice changes.
>
> [Turn on {name}] [Cancel]

### Overlay
> **{name} joins another network.**
> {name} connects Lodestar to {network}, a separate peer-to-peer network. Other peers on it can see your IP address (or your VPN's), and what you search for may be visible to them. That network has its own content and its own risks, and Lodestar can't check what others share there.
>
> - **Use a VPN** for this source, so the kill switch stops it if the VPN drops.
> - What it finds is kept apart from your BitTorrent results, and **Purge** removes all of it in one step.
> - Lodestar collects metadata only. It doesn't download content.
>
> Enter your password to turn it on. You'll be asked again if this notice changes.
>
> [Turn on {name}] [Cancel]
