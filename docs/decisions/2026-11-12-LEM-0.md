# LEM-0 decisions (Lemmy API v3 post-list parser)

Slice LEM-0 of `docs/plan/2026-11-06-v08.md` (§5, LEM-0). It covers architecture §18.2 (source #22, Lemmy), §18.5 (claims) and §18.9 (parser safety). The parser feeds LEM-1, the polling plugin. It lands inactive: nothing calls it until LEM-1 merges. It holds to the safety bar SRC-6 set (`docs/decisions/2026-11-01-SRC-6.md`) and reads JSON with the bounded reader SRC-9 built (`docs/decisions/2026-11-02-SRC-9.md`), never `serde_json`.

- **`lemmy::parse_each(body, &Limits, emit)`** is a pure function from bytes to posts, in `crates/sources-feeds/src/lemmy.rs`. It returns a `Page`: SRC-6's `Summary` plus `removed`, `recognised`, `next_page`, `newest_id` and `error`. `lemmy::parse` collects the posts with the default caps. No I/O.
- **The shape** is `GetPostsResponse`: `{"posts": [PostView, …], "next_page": "…"}`. From each `PostView` it reads `post` (`id`, `name`, `url`, `body`, `nsfw`, `removed`, `deleted`, `published`, `ap_id`), `community` (`name`, `nsfw`, `removed`, `deleted`, `actor_id`) and `creator` (`name`, `actor_id`). Everything else is skipped unread.
  - `recognised` says the root was an object with a `posts` array, so LEM-1 can tell a reshaped answer from an empty page. The software version is never read (plan: a Lemmy 1.x that still serves v3 works).
  - An error answer, `{"error": "rate_limit_error"}`, gives `error`: a code of ASCII lower-case letters, digits and `_`, at most 64 bytes, else nothing. LEM-1 uses it for "blocked by source".
- **Keys come only from magnet URIs** in `post.url` and `post.body`, read with `common::magnet_hashes` (v1 hex or base32, v2 `btmh`). An `http(s)` `.torrent` link gives no key and counts as `no_hash` (plan Q-r12).
  - A `url` that is a magnet (after trimming) is read whole: it's one URL, so a `dn` with `'`, `|`, brackets or non-ASCII text doesn't cut it short. A magnet inside an `http(s)` url (a query parameter) is not a key.
  - The body is Markdown, so there a magnet runs from `magnet:` (any case) to whitespace, a character that ends a Markdown or HTML link (`()[]<>{}"'`` ` ``|\`), or a non-ASCII byte. Trailing `.,;:!?` is dropped, so a magnet that ends a sentence still parses. The scan is linear in the text.
  - A post can link several torrents. Each distinct key is one `Torrent`, url first, then the body in order, with the magnet's `dn` (`+` read as a space) cleaned like a title. **At most 16 per post** (`MAX_TORRENTS`); more set `torrents_truncated`. *Runner's call:* the plan names no cap, and one post with a list of magnets is common in these communities.
  - Text that starts like a magnet but gives no hash counts the post as `bad_hash`; no magnet-like text, `no_hash`.
- **Removed and deleted posts are skipped** and counted in `Page::removed`, outside `Skipped`, so LEM-1's health can tell moderation from parse faults. *Narrower than the plan:* a post in a removed or deleted community is skipped the same way. A removal flag read cleanly as `true` counts as removed even when another field of the post is bad (over a cap, malformed), so moderation is never counted as a fault.
- **Adult:** `Post::adult` is `post.nsfw || community.nsfw`; LEM-1 turns it into the `content-type:adult` claim that ADH-0 reads. *Narrower than the plan (content safety):*
  - `post.nsfw`, `post.removed`, `post.deleted`, `post.id` and `community.nsfw` must be present, and the flags must be JSON booleans. Otherwise the post is skipped as `malformed`, so a reshaped answer can't drop the flag or the removal unseen.
  - A repeated `nsfw`, `removed` or `deleted` key is OR-ed in: a repeat can only add a restriction. Every other repeated key keeps its first value, as in SRC-9.
  - A repeated `post`, `community` or `creator` object skips the post as `malformed`, since the second could carry a flag the first lacks (fresh review).
- **`newest_id`** is the highest `post.id` among posts read whole and sound, kept or skipped (removed, no magnet), so LEM-1's cursor (plan: the newest local post id, never `published`) can move past posts that will never be kept. A malformed post or one cut short never moves it.
- **Ids into claims (plan §3, "NOS-0 and LEM-0 read … Lemmy ids into the existing `ids` claims").** This crate doesn't build `Claims` (`lodestar-sources` is only a dev-dependency here, as for every parser in it), so the parser exposes the ids and **LEM-1 maps them**:
  - `Post::link` (`post.ap_id`, through `external_ref`) is the post's external reference, `Claims::external_ref`. It's the post's canonical URL on its home instance, the same on every instance that federates it.
  - `Post::id` is this instance's own number. It's LEM-1's cursor, not an id claim: it means nothing on another instance.
  - No other `ExternalId` scheme applies: a Lemmy post carries no IMDb, TMDB or similar ids. If LEM-1 wants the `ap_id` as an id claim as well, it must fit `MAX_ID_PART` (128 bytes) or be left out, never cut; most `ap_id`s are well under it, but `MAX_REF` allows 2,048.
- **Other fields:** `title` from `post.name` (`common::title`: hidden characters removed, ≤ 1,024 B); `published` from RFC 3339 with a zone (Lemmy 0.19 sends `Z`; a zoneless date is dropped, not guessed); `link` from `post.ap_id`, and the actors' `actor_id`s, through `common::external_ref` (credentials stripped, ≤ 2,048 B); actor names ≤ 256 B (`MAX_NAME`), dropped when longer. `next_page` is kept only as ASCII letters, digits and `_-`, ≤ 1,024 B.
- **Caps.** As in SRC-6, structural caps stop the parse and keep the finished posts; field caps skip the one post.

  | Cap | Default | Over it | Why this value |
  |---|---|---|---|
  | `max_bytes` | 8 MiB | stop (`Bytes`); the prefix is parsed | 50 posts with 64 KiB bodies is about 3.2 MiB; a real page is tens of KiB |
  | `max_depth` | 16 | stop (`Depth`) | SRC-6's. The deepest field read is 4 levels (`root > posts > view > post`) |
  | `max_values` | 200,000 | stop (`Elements`) | A real page has a few thousand values. It bounds the work spent skipping fields the parser doesn't read |
  | `max_posts` | 50 | stop (`Items`) | The plan's cap, and Lemmy's own `limit` maximum. Kept, skipped and removed posts all count |
  | `max_text` | 64 KiB raw | skip the post (`over_cap`) | The plan's body cap; the same for every string read. Lemmy's own body limit is 10,000 characters |
- **Tests:** `crates/sources-feeds/tests/lemmy.rs` (a synthetic post list, nsfw, removed and deleted, missing and odd flags, error answers, each cap, hidden characters and credentials, proptest properties, and a 100,000-input mutated corpus) and the fuzz target `fuzz/fuzz_targets/lemmy.rs`. The test fixtures are inline: no real post is copied.
