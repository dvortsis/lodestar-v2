# CMP-11b decisions

The follow-up to CMP-11 (#705): the review's Important findings and nits, done before the Windows version gate is registered, and then its registration with CMP-5g's guided tests updated (fallback (b), runner, 2026-11-11). Review: `runner-state:reviews/rv-705-3544233f.md`. These are the slice's decisions under §2.33. None loosens an owner decision or a security decision. The runner flags the refinements to the owner (§2.19).

## Corrections to `2026-11-11-CMP-11.md`
- **I1's wording overstated the loopback refusal.** CMP-11 refused `localhost`, `127.x` and all-numeric short forms, but read `0177` as decimal and let anything with an `x` through as a name. So `\\0177.0.0.1\…`, `\\0x7f.0.0.1\…`, `\\0x7f000001\…` and `\\0--1.ipv6-literal.net\…` were accepted. This file supersedes that bullet (below).
- **The size in its self-review section** was about 1,800 changed lines at merge, not 1,550.

## UNC loopback spellings (review I1)
- **Refused as well:**
  - any numeric label with a leading `0` and more than one digit (octal to Windows' address parser, and an unusual spelling of a decimal one: `\\192.168.001.20` is refused too);
  - any label `0x` followed by hex digits;
  - any name ending in `.ipv6-literal.net`, Windows' built-in name form for an IPv6 address.
- **Not decoded:** a spelling Windows might read as an address is refused rather than worked out, so no parser difference can let one through.

## A save path's kind matches the platform (review I2)
- **CMP-8b's adapter checks it before anything is sent** (`save_path_wrong_platform`):
  - behind the Windows gate, only a `WindowsPath`: a Linux `/downloads` would land on the current drive's root;
  - without it, only a `HostPath`.
- The gate is what marks a qBittorrent as Windows', so the check reads `gate.is_some()` rather than the host's platform. It holds wherever the configurator is built.

## Registration
- **On Windows, `configure::configurator("qbittorrent")` is the version gate** (`windows_qbittorrent::configurator`), so every configuration passes it: the guided path's plan and apply, and anything later. Elsewhere it's CMP-8b's adapter, unchanged.

## While unpinned, the gate accepts CMP-8b's checked range (option (D), runner, 2026-11-11)
- **This supersedes CMP-11's "refused until pinned"** (`2026-11-11-CMP-11.md`, the version gate's "fails closed" bullet). Owner flag 2 from #705's review (Windows configuration blocked until CMP-13) no longer applies. The runner tells the owner (§2.19).
- **The range is one constant, `windows_qbittorrent::CHECKED_RANGE`:** from `4.6.0` up to, not including, `5.3`. Those are the releases CMP-8b's adapter was checked against (`2026-11-08-CMP-8b.md`: `release-4.6.3`, `5.0.3`, `5.1.2` and `5.2.0`, every line from 4.6).
  - Once the installer is pinned, the pin's range replaces it: the pin and later patch releases of the same `major.minor`.
  - Neither range contains the other. A pin at `5.0.3` refuses `4.6.7`, which the checked range accepts, and a later pin at `5.3.1` would accept `5.3.2`, which it refuses.
- **Why it isn't a security change:** the version gate is a compatibility check on a qBittorrent you installed yourself, and it was never the integrity control. Under owner cq4, integrity is you checking the pinned SHA-256 of the installer you download, and that doesn't change. What the gate guards is that CMP-8b's adapter only talks to a WebUI it was checked against, which the checked range keeps.
- **Order unchanged:** the version is read after sign-in on CMP-8b's own session, and before any read or write, in both the plan and the apply. An out-of-range, unreadable or error answer refuses with nothing written. Only a missing catalogue or no Windows installer at all is refused before anything is sent (`no_platform`).
- **No hash is shown or invented while unpinned:**
  - The guide's download step says this release of Lodestar has no checked qBittorrent installer yet, so there's no checksum to compare, and points to qBittorrent's official download page. There's no `check_sha256` step.
  - The API and the screens show a SHA-256 only from the manager's install offer. On Windows the manager answers `guided_only` before any offer is made (below), so no screen gets a hash line, empty or otherwise. Nothing in `crates/api` or `web/` changes.
- **Tests:**
  - `crates/lodestar`'s guided tests: their fake qBittorrent answers `/api/v2/app/version` with `v5.0.3` when signed in, as a real one does with its localhost bypass off. So on windows-latest all of them, the six that broke under CMP-11 included, run through the real gate.
  - Checked locally by forcing the gate on: all 70 companion and guided tests pass, where the same six failed before the fake answered.
  - `tests/windows_qbittorrent.rs`: unpinned, `4.6.0`, `5.0.3` and `5.2.9` are configured; `4.5.9`, `5.3`, `5.3.0` and `6.0.0` are refused with nothing written; an unreadable version is refused, pinned or not.
  - The unit tests check the checked range's bounds, and that a pin's range replaces it. A pinned entry can't be built in `crates/lodestar` without the `testing` feature, which CI keeps out of the binary's tree (dev-dependencies included). So the pinned case is tested in `lodestar-companions`, which may use it.

## The manager says `guided_only` on Windows, pinned or not (review I3)
- **An installer artifact is refused as `guided_only` before the pin is looked at** (`manager.rs` `installable`). CMP-11 left it answering `awaiting_pin` while unpinned, which a screen could read as "Lodestar will install this once pinned". That isn't owner cq4's flow.
- The API's sentence and the wizard already map `guided_only` to the guided install, so nothing changes in `crates/api` or `web/`.
- `tests/manager.rs` checks `offer` and `install` on Windows with the shipped, unpinned catalogue, and that a build Lodestar installs (the unpinned Linux binary) still answers `awaiting_pin`.

## From #692's review (`rv-692-cfc09faa.md`)
- **N1: each place that logs a timeout at its bound is logged once,** and each one is tested by its own count:
  - the undo's release (`manager.rs` `release_now` from an undone first install): one `release`/`timed_out` line and no `rollback_failed`;
  - the pending release: one line, after it finally answers;
  - a restart's hand-over: one `handover`/`timed_out` line and none under `restart`.

  Mutation-checked: removing each guard fails its test.
- **N2: a restart or regenerate whose hand-over hangs leaves the companion stopped until the store answers** (or Lodestar shuts down). The live operation halts it, waits for the hand-over (which holds the slot so no removal can release under a late save), then starts it. The request itself isn't blocked, because it returns its pending handle. Starting the companion alongside the hand-over is left for a later slice.

## Nits
- **`windows_qbittorrent::configurator`** returns `None` for anything but qBittorrent, so it can't be registered for another companion.
- **`Windows.old`** (an earlier install and its profiles) is refused like `Windows`.
- **Documented, not refused:**
  - `X:\Users\Default\…`, the template profile, passes like any profile (its `AppData` and dot folders are still refused);
  - a drive root shared under another name than its folder's (`\\nas\C\Windows`) passes, because the folders after a share are checked as if the share were named after the root.
- **`last_refusal`** is one slot shared by the configurator's calls. Two plans run at once can overwrite each other's. The guided path runs one at a time.
- **`Supported::check`** reads the found version's `major.minor` once.
