# B-update-6 decisions (PR pending)

- **An unreadable version fails closed in Roll back's checks.** `journal::kept` returns `Kept::Missing` (Roll back is refused as `snapshot_missing`) and `restore_plan` refuses the rollback when the failed version can't be parsed, where both used to treat it as "never touched the store". Without the version there is no `migration.json` to read, so nothing says the store is one the previous version reads (§12.2). It never strands the running version: every caller passes a parsed version (`active.version` matches the running one; the supervisor's rollback names the version it ran), a refused requested rollback keeps running, and overlay pruning (`supervisor::passed`) doesn't use `kept`.
- **`GET /updates` caches Roll back's cheap check** (`update/rollback_cache.rs`), so a polled status no longer lists the store's folder and opens the store every time. An answer is reused only while a probe of its inputs still matches: the version, `migration.json`'s size and time, and the store folder's time. Not every filesystem moves a folder's time when a file in it goes (a union or network one), so a cached "restores the store" also needs one of the snapshots it found to still be a regular file, checked on every poll; a stale "not kept" or "keeps the store" only offers Roll back later. It's never cached when an input changed less than 3 s ago (a coarse file clock may not move again), is kept 30 s at most, and is cleared on every `updates` event. `POST /updates/rollback` always checks afresh, and the supervisor still verifies the snapshot at step 2. A status still reads `active`, `pending` and `history.json` (small files) and stats two or three paths.
- **`rollback.restores_store`** (optional, `bool`) on `GET /updates` says whether a rollback replaces the store with the snapshot taken before the version's migration (`true`) or keeps the store as it is (`false`: no migration, or no migration step committed). It's derived from the same check (`migration.json` and the snapshots beside the store), sent whenever that check found the version to roll back, and absent otherwise. The Roll back dialog will use it in a later web slice.
- **Test knobs, not production changes:** the engine's test fixture can run unsupervised (`env_with`) and report a restart already requested (`Env::restart_requested`), for the `not_supervised` and restart-pending `busy` reasons.
