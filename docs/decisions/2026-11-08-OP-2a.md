# OP-2a decisions (fleet AWS templates and the Terraform S3 backend)

The slice writes the CloudFormation templates the owner deploys (`infra/aws/fleet-control/`) and moves Terraform to an S3 backend, as the plan's OP-2a row asks (`docs/plan/2026-11-08-cloud-operator.md` §3–§4, "Owner setup" step 4). Nothing calls a cloud. These are the choices the plan left open, or narrowed. None loosens §4's containment, an owner decision or an owner-set number; the runner flags them to the owner (§2.19).

## Stacks and trust
- **Two stacks.** `fleet-control.json` holds the OIDC provider, `LodestarFleetOperator`, `LodestarOperatorBridge`, the three buckets, the fleet token's secret shell and a deny-all policy. `pia-delivery.json` holds `LodestarPiaDelivery`, the firewall token's secret shell and its own deny-all policy, so it can sit in the account that holds `lodestar/pia-vpn` (plan §4).
- **The firewall token's secret shell lives in the PIA stack,** because plan setup step 6.3 puts `lodestar/akamai-firewall-token` in the same account as `lodestar/pia-vpn`, and the role then names it by reference, not by a pasted ARN.
- **The OIDC provider is optional.** An account holds one provider per URL, so each stack creates it only when `ExistingOidcProviderArn` is empty.
- **Trust uses the customized subject** (owner setup step 2.8: `repo`, `context`, `job_workflow_ref`), for example `repo:dvortsis/lodestar-v2:environment:cloud-fleet:job_workflow_ref:dvortsis/lodestar-v2/.github/workflows/fleet.yml@refs/heads/main`. Every role checks `aud` = `sts.amazonaws.com` and `sub` with `StringEquals`, never `StringLike`. The bridge lists its three exact subjects (`operator-wake.yml`, `operator-apply.yml`, `operator-injection.yml`, each in `cloud-operator`), which `StringEquals` matches as any one of them.
- **Sessions last at most 1 hour.**
- **The trust names the repository** (`dvortsis/lodestar-v2`), which is public. No account ID or resource ID appears: they come from pseudo-parameters, parameters and references, and parameter defaults are empty.

## Exact keys
- **The fleet lock is the one key `locks/fleet.json`,** not the plan's `locks/fleet*` prefix: the runner asked for exactly the keys OP-1's decisions name, which is narrower than the plan.
- **`fleet.json` is `fleet/fleet.json`** in the state bucket (OP-1). A test checks both keys against `infra/fleet/lock.py` and `state.py`.
- **The Terraform state key is `terraform/lodestar.tfstate`,** with native locking's `terraform/lodestar.tfstate.tflock`. `LodestarFleetOperator` may read and write the state and `fleet.json`, and delete only the lock object. It can't delete the state or `fleet.json`; the bucket is versioned.
- **`fleet.json` is never deleted** (the runner's refinement, 2026-11-08). Once `down` has emptied the inventory, it overwrites `fleet.json` with a tombstone (for example `{"fleet": null, ...}`), and the key exists from setup on. The plan's "deletes `fleet.json`" becomes "writes the tombstone". The tombstone write, and who writes the first one, are OP-2's.
- **The bridge keeps the plan's `locks/operator*` prefix** and the exact `operator/claude-lock.json`, because no slice has named the operator lock keys yet. OP-4 can narrow the prefix to exact keys when it names them.
- **The evidence grant is the `fleet/` prefix** of the evidence bucket, inside the plan's "read and write the evidence bucket".

## Listing
- **Why listing matters:** without `s3:ListBucket`, S3 answers a GetObject or HeadObject on a missing key with 403, not 404. A list grant limited by an `s3:prefix` condition doesn't change that, because those requests carry no `s3:prefix`. It only lets `ListObjectsV2` with that exact prefix answer "does this key exist".
- **`LodestarFleetOperator` may list the whole state bucket, unconditionally.** Terraform's first `init`, `plan` and `apply` on a fresh state read the missing state key and fail on a 403 (checked against Terraform 1.10.5 with a local fake S3). The role already reads and writes every object that matters there; listing shows only key names.
- **In the control bucket, `LodestarFleetOperator` may list only the prefix `locks/fleet.json`.** `infra/fleet/lock.py` reads the lock only after a conditional write has failed, so the key exists. A rare 403 from a race fails closed, ending the job with a fixed error.
- **The bridge may list only `locks/operator*` and `operator/claude-lock.json`** in the control bucket. OP-4 checks whether a key exists with `ListObjectsV2` and that exact prefix, and treats any error as "exists".
- **The bridge may not list the state bucket:** its scope stays exactly the plan's, GetObject on `fleet/fleet.json` only (the runner's decision; a prefix-limited list would still widen a credential). The bridge, and so OP-4 and OP-5, read "no fleet" only from a readable tombstone. Any error, a 403 included, means "a fleet may exist", and the harness refuses.
- **`LodestarPiaDelivery` may list nothing.** It reads `fleet.json` only after `up`, so a 403 means refuse.

## Buckets and secrets
- **Names are generated by CloudFormation,** so nothing account-specific is committed. The outputs name the GitHub secret each value goes into.
- **Every bucket:**
  - SSE-S3 with a bucket key, and no KMS key, so no KMS grant is needed (plan §4);
  - all four public-access blocks;
  - `BucketOwnerEnforced`, so ACLs are off;
  - a bucket policy that denies any request without TLS;
  - `Retain` on delete and replace, so deleting the stack never deletes state or evidence.
- **State is versioned,** with old versions kept 30 days, so a bad write can be rolled back. Delete markers (from each lock-file and `fleet.json` delete) are dropped once no older version remains. **Evidence expires after 14 days** (plan setup step 4). **Control isn't versioned:** a lock's history has no use, and S3's conditional writes work either way.
- **The cross-account grant** is a conditional bucket-policy statement: when `PiaDeliveryRoleArn` is set, that one role may `s3:GetObject` on `fleet/fleet.json`, nothing else. The parameter only accepts a role named `LodestarPiaDelivery`.
- **`PiaSecretArn` only accepts the exact `lodestar/pia-vpn` ARN** with its six-character suffix, so a wildcard can't be passed.
- **The secret shells are empty,** with `Retain`. The owner sets each value in the console (setup steps 5 and 6.3).
- **Each stack's deny-all policy** is a managed policy that isn't attached to anything. Attaching it is kill-switch step 4.
- **Role sessions last at most 1 hour,** so every job that uses AWS keeps `timeout-minutes` at 60 or less (OP-1's lock-holding jobs do). A longer job would lose its credentials partway, for example in the middle of a destroy.

## Outside the templates, and open items for the runner
- **Two outside settings protect the trust:**
  - each GitHub environment allows deployments from `main` only (owner setup steps 2.4 and 6.1);
  - none of `fleet.yml` and the `operator-*.yml` workflows declares `workflow_call`, which OP-1's test checks and OP-4 extends.
- **OP-2 needs more keys.** OP-2 adds the keys for the monthly spend ledger and the mismatch flag to this template; the owner updates the stack before `FLEET_LIVE=true`.
- **OP-2b's fencing** (the runner's decision): `deliver-pia` writes firewall rule sets but can't read `locks/fleet.json`, so a `cloud-fleet` job fences on the lock just before delivery. The PIA role's scope doesn't change.
- **Residual of the shared state:** the manual `Deploy.ps1` and `Destroy.ps1` share the fleet's state but not its lock or `fleet.json`. The README says not to run them while a fleet exists; OP-3's runbook repeats it.
- **Later, optional:** GitHub's `include_claim_keys` can add `repository_id`, so trust survives a rename of the account or repository. The runner logged it as a hardening for later; it would change owner setup step 2.8.

## Terraform
- **`backend.tf` is a partial S3 backend** with `use_lockfile = true` and `encrypt = true`. The bucket, key and region come only from `-backend-config`. `required_version` is now `>= 1.10.0`, and CI's `infra` job runs Terraform 1.10.5 (the runner agreed).
- **The manual scripts share the fleet's state** (the runner's decision, 1a). `Deploy.ps1`, `Destroy.ps1` and `Preflight.ps1` read `LODESTAR_TF_STATE_BUCKET` and `LODESTAR_TF_STATE_REGION` through a new helper, `scripts/StateBackend.ps1`, and pass `-backend-config` with the fleet's fixed key.
  - **Why:** two states for the same Linodes could recreate or orphan machines (#625's warning), so the manual path and `fleet.yml` must see one state.
  - **Unset variables:** the scripts refuse, with a clear message, before anything runs. They never fall back to local state.
  - **An old local backend:** the scripts pass neither `-migrate-state` nor `-reconfigure`, so an old local `.terraform` makes `init` stop. The README tells the operator to delete it rather than migrate, because the plan's reconciliation is a fresh S3 state with no old local state imported.
- **`fleet.py` runs no `init` yet;** OP-2's `apply.py` passes the same `-backend-config`. CI's validate keeps `-backend=false`.

## Tests
- **The templates are JSON generated by `build_templates.py`,** so the policy tests parse them with the standard library. CI fails if the committed JSON differs from the builder's output.
- **cfn-lint isn't in CI.** Pinning it by hash means about 15 packages, one of them released the same day, so the brief's fallback applies: standard-library policy tests in CI. cfn-lint 1.60.0, run locally, reports nothing on either template, and catches a planted error.
- **The policy tests check:**
  - every trust's `aud` and its exact `sub`s;
  - no wildcard action or `*` resource outside the deny-all policies;
  - each role's exact object grants;
  - list grants only on exact prefixes;
  - every bucket is private, encrypted and TLS-only;
  - empty secret shells;
  - no account ID, ARN with an account ID, IP, or literal parameter default;
  - the partial backend and `required_version`;
  - every script that runs `terraform init` uses the shared state;
  - `StateBackend.ps1` and its test stay pure (no terraform, AWS CLI or network call).
- **`tests/Test-StateBackend.ps1` runs in CI's `infra` job** (the runner's decision). It checks that unset, blank or malformed values are refused, that a refusal names the missing variable without echoing the value, and that valid values give exactly the three `-backend-config` arguments with the fixed key. The job's rule is now: no script that can reach a cloud runs in CI, and pure test files may.
