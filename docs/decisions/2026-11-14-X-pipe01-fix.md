# X-pipe01-fix decisions (#877)

- **PIPE-01 (blocking, pipeline; the fetch pool) fixed.** Its detail is held under `docs/security/v1/README.md` §5 until a release with the fix is published. This file says only what the code now does.

## Calls
- **One address has peers in a bounded number of keys at once** (architecture §6, the fetch pool). The pool counts, for each address, the public keys in it that have a peer there. An address is an IPv4 address, or an IPv6 address by its /64.
- **So does one network.** The pool also counts the public keys with a peer in each network: an IPv4 /24, or an IPv6 /48. Both limits hold at once, so addresses inside one network share that network's limit.
- **Both limits are a share of the queue** (`address_caps`), worked out once when the pool starts:
  - per address: the queue's size / 512, at least 1 and at most 256 (`MAX_VOUCHED_PER_IP`);
  - per network: the queue's size / 128, at least the address limit and at most 1,024 (`MAX_VOUCHED_PER_NET`).

  | Queue (`max_pending`) | Per address | Per network |
  |---|---|---|
  | 200,000 (the default) | 256 | 1,024 |
  | 50,000 | 97 | 390 |
- **Every address and network a key's peers are at counts.** A key with peers at three addresses in two networks takes a place at each address and in each network.
- **A peer is added only with both places.** If its network is full, the place at its address is not kept.
- **The count is taken where a peer is added,** so it holds however the peer came: with the key when it was found, with a later sighting of the same key, or in a lookup's answer.
- **Past the limit, the key goes without that peer.** It is still taken, with its other peers if it has any. With none it is looked up like any key found with none: found again through the lookup if it has peers elsewhere, and it gives way to newer keys when the queue is full, as any key still looking does. No discovery is refused for it.
- **An IPv4-mapped address and a NAT64 address (`64:ff9b::/96`, `64:ff9b:1::/96`) count as the IPv4 address inside them, for both limits. Ports don't matter.
- **Only public keys count.** A private source's peers are the user's own (their client, a private tracker): those keys are never limited, and never go to a public lookup (§18.7). A private key that a public source then finds keeps the peers it has, and they count from then on, past the limit if need be. A key that turns private again (its public source was dropped) gives its places back.
- **A key that leaves the pool gives its places back,** fetched or lost, and so does a key that drops peers the policy no longer lets it dial.
- **Only a pool with a peer finder limits.** A pool with none (a worker that runs no DHT) can't look up a key that goes without a peer, so it keeps the peers its keys came with, as before.
- **Why these numbers** (the runner's call, §2.26, flagged to the owner under §2.19): 256 is well above the number of queued keys one honest address is a peer of at once, and a network gets four addresses' worth. They are constants, not settings, and not owner-set numbers.
- **Fetching is unchanged:** the per-address connection cap, the timeouts and the attempts are as they were.

## What it costs
- **An honest address with peers in more keys than its limit** (256 at the default queue) (a large seeder that is the only peer of many torrents) has that many of them in the queue at a time. The rest are looked up, find the same peer, go without it and end as keys with no peers; they come back when they are next seen. The per-address connection cap already meant such keys were fetched a few at a time.
- **Honest peers that share one /24 or one /48 share its network limit.** Keys past it are admitted without that peer and go to a lookup, as above.
- **Memory:** one map entry (about 30 bytes) for each distinct address, and one for each distinct network, among the public keys' peers, on top of the 32 bytes each peer already takes in its key. The map shrinks again after a burst. No field was added to an entry, so `diagnostic_entry_storage_is_bounded` holds as before.

## Tests
- `crates/sources/tests/pool.rs`:
  - `one_network_has_peers_in_a_bounded_number_of_keys`: for a /24 and for a /48, one key at each of many addresses inside it stops at the network's limit, and another network has its own share.
  - `one_address_has_peers_in_a_bounded_number_of_keys`: on a small queue, so with a scaled limit; the keys past the limit, and only they, go to a lookup and start no fetch, whether found with the peer twice or first with none; with the queue full, new keys get in and the address's first keys are kept.
  - `a_finished_key_gives_its_place_back`: three rounds at the limit, none past it; peers at two addresses take a place at each.
  - `a_lost_key_gives_its_place_back`.
  - `a_private_keys_peers_count_once_it_is_public`.
  - `a_key_that_turns_private_gives_its_places_back`.
  - `dropped_peers_give_their_places_back`.
  - `a_pool_with_no_finder_keeps_every_peer`.
  - Each fails with its part of the change taken out.
- `crates/sources/src/pool.rs`: `a_peer_counts_under_its_address_and_its_network`, `the_limits_follow_the_queue`, `places_are_counted_per_address` and `a_peer_takes_both_places_or_neither`.
- **A check in debug builds:** whenever the pool's queue is snapshotted (at every stop), the counts per address and per network are compared with ones taken afresh from the entries. Every pool test ends with it.
- `crates/pipeline/tests/stages.rs`: the worker test helper gives each key a peer in a network of its own (documentation addresses). `a_stalled_link_pauses_fetching` sent 400 keys with one peer, which is past the limits; the test is about back-pressure, not about one peer.
- The tests run on tokio's paused clock, as the pool's other tests do: their waits are virtual time, not sleeps.
