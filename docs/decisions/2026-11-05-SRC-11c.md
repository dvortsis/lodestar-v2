# SRC-11c decisions (Sonarr and Radarr webhooks wired into the host)

Slice session, 2026-11-05. Runner brief SRC-11c. It carries out the "Wiring" handoff in `docs/decisions/2026-11-05-SRC-11b.md` and supersedes that file's "the plugin isn't registered" and "until then the route answers `503 webhooks_unavailable`". Architecture §18.2 rank 17, §18.7, §12.

## Wiring (`crates/lodestar/src/services.rs`)
- **The `arr_webhooks` plugin is registered at every start,** beside the torrent cache, off by default (its manifest's `enabled_by_default: false`). Turning it on in Settings → Sources applies at the next start, as for every source.
- **The sink is the plugin's own `Inbox`** (`ArrSink`, a one-to-one mapping of `webhooks::Integration` to `arr::App` and `arr::Delivery` to `webhooks::Delivered`). The inbox parses with SRC-11b's bounded reader and puts a find on the running plugin's `Emitter` with `try_emit`. So a webhook find takes exactly the path every source's finds take: the emitter's channel, intake, the filter before storage (SRC-2), the always-adult mask and the private-source guards. Nothing in the pipeline is special-cased for it, and no new path to the store exists.
- **`Webhooks::new(sink).layer()` is added in `Services::run`** with the other `Extension` layers on the whole router, so it reaches `/api/v1/webhooks/*` through the nest. `crates/lodestar/src/http.rs` and `main.rs` are unchanged: the layer sits where the other host extensions do, which keeps the hunk small against LEGAL-1 (#472), which edits `http.rs`.
- **The route's order and answers are SRC-11b's, unchanged:** one `401 login_required` for every failure to authenticate, the body caps before and while reading, the per-integration rate, the per-address failure bucket, `200 {"dropped": true}` for a real event dropped, and `503 source_off` only for the Test call. With the hub wired, the token hashes come from its cache, so a call does no I/O before it authenticates.
- **Fixture mode** registers it too. It sends nothing, so it needs no egress.

## The Legal Notice gate
LEGAL-1 (#472) lists `("post", "/webhooks/{integration}")` in its `PENDING_ALLOWED` table (`crates/api/tests/keys.rs`), and the inbound route isn't under `protected`, so the gate never applies to it, as for API keys and feed tokens. The token routes (`GET /webhooks`, `POST`/`DELETE …/token`) are session routes and do meet the gate, which is right: they're the admin's. No coordination was needed.

## End-to-end test (`crates/lodestar/tests/webhooks_e2e.rs`)
The real binary, with the DHT and tracker scrapes off, so nothing leaves the machine:
1. the source is listed and off; a Sonarr token is made through `POST /webhooks/sonarr/token` with the password;
2. with the source off, a real Grab is `200 {"found": false, "dropped": true}` and the Test call `503 source_off`;
3. the source is turned on through `PATCH /sources/{id}`, and the binary restarted;
4. a wrong well-formed token, Sonarr's token on Radarr's route, and no token are each `401 login_required`, and Radarr's counts stay at zero;
5. the right token's Grab is `200 {"found": true}`, the Test call `200`, and the key reaches the store as an unverified item, `private_source` with private claims, carrying the release title and size; the refused Radarr grab's key is never stored;
6. the token never appears in the log.

Waits are on a condition with a 30 s deadline, polled every 50 ms; no fixed sleeps. Unix only, as the other binary tests that stop the server with `SIGTERM`.
