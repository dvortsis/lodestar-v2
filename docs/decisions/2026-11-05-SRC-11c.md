# SRC-11c decisions (#490, Sonarr and Radarr webhooks wired into the host)

Slice session, 2026-11-05. Runner brief SRC-11c. It carries out the "Wiring" handoff in `docs/decisions/2026-11-05-SRC-11b.md` and supersedes that file's "the plugin isn't registered" and "until then the route answers `503 webhooks_unavailable`". Architecture §18.2 rank 17, §18.7, §12.

## Wiring (`crates/lodestar/src/services.rs`)
- **The `arr_webhooks` plugin is registered at every start,** beside the torrent cache, off by default (its manifest's `enabled_by_default: false`). Turning it on in Settings → Sources applies at the next start, as for every source.
- **The sink is the plugin's own `Inbox`** (`ArrSink`, a one-to-one mapping of `webhooks::Integration` to `arr::App` and `arr::Delivery` to `webhooks::Delivered`). The inbox parses with SRC-11b's bounded reader and puts a find on the running plugin's `Emitter` with `try_emit`. So a webhook find takes exactly the path every source's finds take: the emitter's channel, intake, the filter before storage (SRC-2), the always-adult mask and the private-source guards. Nothing in the pipeline is special-cased for it, and no new path to the store exists.
- **`Webhooks::new(sink).layer()` is added in `Services::run`** with the other `Extension` layers on the whole router, so it reaches `/api/v1/webhooks/*` through the nest. `crates/lodestar/src/http.rs` and `main.rs` are unchanged: the layer sits where the other host extensions do, which keeps the hunk small against LEGAL-1 (#472), which edits `http.rs`.
- **The route's order and answers are SRC-11b's, unchanged:** one `401 login_required` for every failure to authenticate, the body caps before and while reading, the per-integration rate, the per-address failure bucket, `200 {"dropped": true}` for a real event dropped, and `503 source_off` only for the Test call. With the hub wired, the token hashes come from its cache, so after the first call (which reads the store once to fill it) a call does no I/O before it authenticates.
- **Fixture mode** registers it too. It sends nothing, so it needs no egress.

## The Legal Notice gate
- LEGAL-1 (#472) lists `("post", "/webhooks/{integration}")` in its `PENDING_ALLOWED` table (`crates/api/tests/legal.rs`), and the inbound route isn't under `protected`, so the gate never applies to it, as for API keys and feed tokens. The token routes (`GET /webhooks`, `POST`/`DELETE …/token`) are session routes and do meet the gate, which is right: they're the admin's.
- #472 has merged; this branch brought `main` in, and `webhooks_e2e.rs`'s setup body sends `notice_version`.

## Sources whose finds are private (§18.7; runner's call on #490)
- **The leak, found in self-review:** provenance (`crates/api/src/torrents.rs`) counted a source as public unless its consent class was Account. The webhooks source is Consent None. So when a Sonarr or Radarr grab names a torrent that's also stored publicly, the plugin's source bit is added to that row, and a public viewer (API key, feed token) could have seen "Sonarr and Radarr webhooks" among its sources or in the source facet's list. That would tell a key holder which public torrents your Sonarr or Radarr grabbed. No route showed it yet (only `/feeds/{id}` takes keys, and it renders no source names), but the runner ruled that the fix ships with the wiring that makes it possible.
- **The fix: `Manifest::finds_private`** (`crates/sources/src/manifest.rs`), a property of the plugin's code like `always_adult`. It reaches `GET /sources` as `finds_private` (the DTO, `openapi.json`, `schema.d.ts`), and provenance's rule is now `public = consent != Account && !finds_private`, in one function (`plugin_name`). A non-public source is never named to a public viewer, on any row, whether or not the row is `private_source`.
- **Set on each source whose name would reveal your own setup:**
  - `arr_webhooks` (Sonarr and Radarr webhooks): **yes**. The releases your apps grabbed.
  - `clients` (your download clients, SRC-11): **yes**, though Account already covered it. It says so on its own now, so a later change of class can't expose it.
  - `prowlarr` (Prowlarr / Jackett): **yes**, for the same reason. Your indexers may be private trackers.
  - `torrent_cache`: **no**. It asks public caches about hashes Lodestar already knows; what it adds is public metadata, and its name says only that a cache is listed, not what you run or grabbed.
  - `dht`, `nyaa`, `sukebei`, `academic`, `archive_org` and `full_scrape`: **no**. Public sources.
  - Imports (Magnetico, bitmagnet, `crates/sources-importers`) aren't listed plugins. A bit provenance can't name is already never shown to a public viewer (`SourceEntry::public` is `None`).
- **Tests:** `a_source_whose_finds_are_private_is_never_named_to_the_public` (`crates/api/src/torrents.rs`). A public row found by the DHT and by the webhook names only the DHT to a public viewer, gives the DHT as its hit source, and leaves the webhook out of the source facet's list; the signed-in admin sees both, the webhook marked private. The manifest tests of `arr`, `clients` and `prowlarr` check the flag.
- **Paths outside the brief's list (runner-approved on #490):**
  - `crates/sources/src/manifest.rs`: the field;
  - every `Manifest` literal adds `finds_private`: the plugins in `crates/sources-plugins/src/`, `crates/pipeline/src/{dht,egress,source_adult}.rs`, `crates/sources/src/consent.rs`, `crates/lodestar/src/{metrics,services,ops/tests}.rs`, the pipeline, sources and plugin tests, and `bench/examples/mem-{churn,ingest}.rs`;
  - `crates/api/src/dto/ops.rs` and `crates/lodestar/src/ops.rs`: the DTO field and its mapping;
  - `crates/api/src/torrents.rs`: the rule and its test;
  - `crates/api/tests/{ops,provenance}.rs` and the `ops_source*` goldens: the new field;
  - `web/src/lib/api/{openapi.json,schema.d.ts}`: regenerated;
  - `web/src/lib/features/sources/fixtures.ts`: the new field.

## End-to-end test (`crates/lodestar/tests/webhooks_e2e.rs`)
The real binary, with the DHT and tracker scrapes off, so nothing leaves the machine:
1. the source is listed and off; a Sonarr token is made through `POST /webhooks/sonarr/token` with the password;
2. with the source off, a real Grab is `200 {"found": false, "dropped": true}` and the Test call `503 source_off`, both counted `refused`;
3. the source is turned on through `PATCH /sources/{id}`, the binary restarted, and the test waits for the source to report running;
4. a wrong well-formed token, Sonarr's token on Radarr's route, and no token are each `401 login_required`, and Radarr's counts stay at zero;
5. the right token's Grab is `200 {"found": true}`, the Test call `200`, and a body that isn't an event `400 malformed_webhook`, with the counts to match; the key reaches the store as an unverified item, `private_source` with private claims, carrying the release title, size and the series' `tvdb` id (read from `series`, so the route mapped to Sonarr);
6. Radarr with its own token: its Grab lands private with the movie's `tmdb` id (read from `movie`, so Radarr's mapping holds too);
7. neither token appears in the log.

Waits are on a condition with a 30 s deadline, polled every 50 ms; no fixed sleeps. Unix only, as the other binary tests that stop the server with `SIGTERM`.

## User guide
Section 5.5 "Connect Sonarr and Radarr" (`docs/user/05-use-lodestar.md`), a glossary entry for "webhook", and a correction to 5.4, which said this version lists only Mainline DHT. **Making a token has no screen yet** (SRC-15b's webhook panel), so the guide marks the panel **(planned)** and gives a terminal procedure for now, in bash (Unraid's web terminal, Linux, macOS) and PowerShell (Windows). The password is read without echo (`read -rs`, `Get-Credential`), never put in a program's arguments (bash pipes the JSON body on stdin, escaped for `"` and `\`; PowerShell builds it with `ConvertTo-Json`), and the session cookie lives in a private `mktemp` file removed afterwards. The bash procedure was run against the built binary with a password holding a quote, a backslash and a space. That procedure goes when SRC-15b's panel lands (handoff below).

## Handoffs
- **The slice that opens `/search`, `/facets` or the detail view to API keys or feed tokens:** today all three are `auth::protected` (session only), so a public viewer never reaches them. `finds_private` hides a non-public source from the facet list, but a `source:arr_webhooks` term in a query still filters by it. For `Viewer::Public`, that slice must reject or neutralise `source:` terms naming a non-public plugin, so a key holder can't learn by filtering which public torrents your Sonarr or Radarr grabbed. It should review `withheld: true` and `discovered_at` on such rows the same way (runner's review of #490).
