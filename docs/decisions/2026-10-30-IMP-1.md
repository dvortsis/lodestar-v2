# IMP-1 decisions: import contracts and the durable job table (V13)

The runner OK'd this contract before the migration was written (2026-10-30), with the conditions recorded below under "Runner conditions".

The contracts for imports (the plan's IMP-01) and the durability core of IMP-02, from `docs/plan/2026-10-29-magnetico-bitmagnet-migration.md` §6–§7, as narrowed by the master plan's "Imports" (owner-decisions §2.25). Adapters, the CLI, the UI, recovery (CR-3, V14) and the rich merge (IMP-06) build on these and are out of scope here.

## V13 tables
Additive only: new tables, indexes and four triggers. No existing table or column changes.

- **`import_sources`: one row per source identity** `{adapter, dataset, schema_sig}`, `UNIQUE` together.
  - `adapter` is the stable adapter name (`bitmagnet`, `magnetico`), `CHECK` lowercase `[a-z0-9_]`, ≤ 32 bytes.
  - `dataset` is the adapter's dataset identifier: a snapshot or database identity, never a file or database name alone (plan §7). Opaque bytes, 1–64.
  - `schema_sig` is a digest of the source schema the adapter read, 1–64 bytes.
  - The store compares identities byte for byte and never interprets them.
- **`import_jobs`: one row per job.**
  - `id` is `AUTOINCREMENT`, so a deleted job's id is never reused.
  - Identity: `source` → `import_sources`, plus `adapter_ver` (the adapter's integer version) and `contract_ver` (this contract, `1`).
  - State: `phase` and `control`, each a small integer; `reason`, the last blocked or failed reason code, or `NULL`. See "State model".
  - `options`: the adapter's options as an opaque blob, ≤ 4 KiB. Adapters must never put credentials in it.
  - `credential`: a sealed-secret **reference**, never the secret. `CHECK` `[a-z0-9_-]{1,64}`, so a URL, password or DSN can't be stored there by mistake.
  - The counters (see "Counters").
  - `max_new_id`: the highest torrent id the job inserted, so the engine knows when indexing has caught up.
  - `revision`: bumped by every phase or control change, for the API's optimistic concurrency. Batches don't bump it, so pausing a busy job doesn't keep failing on a stale revision.
  - `created_at`, `updated_at`, `finished_at`.
  - A partial unique index allows **at most one unfinished job per source identity**.
- **`import_cursors`: one per job** (`job` primary key, `ON DELETE CASCADE`). It holds `seq`, the last committed batch number, and `position`, the adapter's opaque resume point (≤ 512 bytes). The cursor is bound to the source identity through its job. The store never reads cursor files: the legacy unqualified `import-bitmagnet.cursor` is never trusted automatically. Binding one explicitly is the CLI's job (IMP-4).
- **`import_membership`, compact:** `(torrent_id, job, created)`, `WITHOUT ROWID`, primary key `(torrent_id, job)`. `created` is 1 when this job inserted the row and 0 when it only added provenance. It cascades from `torrents`, and it's indexed by `job` so removal by job provenance can be tested later (master plan). About 12 bytes a row.
- **`import_candidates`: valid hashes too incomplete for the canonical row** (plan §6).
  - Columns: `hash` (20 bytes, primary key), `hash_v2` (32 or `NULL`), `job`, `name` (raw bytes or `NULL`), `size` (or `NULL`), `missing` (a bitmask of name, size, files), `privacy`, `source_at` (or `NULL`), `at`.
  - `CHECK (name IS NULL OR length(name) BETWEEN 1 AND 4096)` and `CHECK (size IS NULL OR size > 0)`: **no empty names and no zero sizes**, ever. A candidate is never searchable and never invented into `torrents`.
  - A candidate whose hash is already a stored torrent isn't written. That record merges instead.
  - **`missing` is derived by the store,** not taken from the caller: missing name, missing size, and always missing files, since a candidate never holds files. An empty name, a name over 4096 bytes or a zero size from the source is stored as missing.
  - A later record for the same hash fills missing fields and never blanks one. Privacy merges sticky-private. The first job stays the owner.
- **`import_quality`: the per-record states for imported rows** (`torrent_id` primary key, cascading from `torrents`).
  - Columns: `completeness`, `verification`, `privacy`, `repair` (reason bits), `source_at` (the source's own date, or `NULL` when unknown or a sentinel), `imported_at`.
  - It has no job column: `import_membership` already says which jobs touched a row, and a job column would need an index on every quality row to delete a job.
  - **A torrent with no row is network-fetched:** verified, complete, its privacy from its info dict and `flags`. So the crawler's write path costs nothing extra, and a quality row exists only for what an import touched.
- **Triggers:**
  - A hash entering `tombstones`, `quarantine` or `cs_hashes` deletes its candidate (by primary or truncated v2 hash). `cs_hashes` is included because reporting a hash as abuse, or a floor list file, adds it there with no tombstone (self-review, blocking). If a candidate existed, its hash goes into `snapshot_deletions`, so snapshots lose the candidate's name too.
  - A hash becoming a torrent, from any path, deletes its candidate. This isn't journalled, because nothing was deleted for safety. It costs the crawler's insert one or two primary-key probes.
- **Snapshots:** `Plan::KNOWN_THROUGH` becomes 13. A V13 snapshot also drops candidates whose hash the live store deleted or holds, by primary or truncated v2 hash (`PurgeReport::candidates`). The other import tables cascade from `torrents` or carry no names.
  - An existing test changed for this reason: opening a pre-release V12 store now also takes V13's pre-migration snapshot, which the purge then cleans as well. So that test's purge count went from 1 to 2.
- **Backup and restore** copy the whole database file (`VACUUM INTO`, then a file copy back). The new tables ride along with no file-list change, and a store test proves a copy holds them and resumes the job.

## State model
- **Phases, in order:**
  - `inspecting` (0) → `ready` (1) → `reading` (2) → `committing` (3) → `indexing` (4) → `complete` (5) or `complete_with_issues` (6).
  - `reading` means source batches are being read and committed. `committing` means the source is exhausted and the last batches are draining. `indexing` means everything is committed and the job waits for the index watermark to pass the job's highest new id.
  - `complete_with_issues` is complete with `invalid > 0`, `files_dropped > 0` or `candidates > 0`.
- **Controls**, orthogonal to the phase so a job resumes where it was:
  - `none` (0): runnable;
  - `paused` (1): by you;
  - `blocked` (2): with a `reason`;
  - `cancelled` (3) and `failed` (4): terminal, with committed work kept.
- **Reasons** (a fixed enum, bounded labels, `CHECK`ed in the schema): `needs_credentials`, `source_changed`, `source_unavailable`, `no_space`, `interrupted`, `store_error`.
- **Transitions are checked in the store against `revision`.** A stale revision, a finished job or an illegal move is an `Error::Invalid`, and nothing changes.
  - Phases only move forward, and only while the job is running.
  - `complete` is reachable only from `indexing`. The store decides between `complete` and `complete_with_issues`; a caller can't ask for the latter.
  - `pause` works from running or blocked, and pausing a paused job changes nothing. `resume` works from paused or blocked and always revalidates. `block` works from running. `cancel` and `fail` work from any unfinished state. Pause, resume and cancel are **truthful**: once one returns, no batch commits under the old control, because `commit_batch` refuses unless the control is `none` and the phase is `reading` or `committing`. A batch refused that way is simply replayed after resume.
- **Restart:** on start the engine calls `Store::interrupt_import_jobs`. Every running job that reads its source (`inspecting` to `committing`) becomes `blocked: interrupted`. An `indexing` job reads nothing and carries on. A paused job stays paused. A job leaves `interrupted` only through `revalidate`, which takes the source identity the adapter sees now, whether the credential reference resolves, and whether space is enough. It resumes, or blocks with `source_changed`, `needs_credentials` or `no_space`. It never restarts from zero.
- **Credentials** are sealed references only. Secrets never appear in `options`, `position`, errors, logs or metrics. The store's own error and `Debug` text never print `options` or `position`.

## The three per-record states, plus privacy
They're independent columns, never folded into one:
- **completeness:** `unknown` (0), `partial` (1), `reported_complete` (2);
- **verification:** `unknown` (0), `unverified` (1), `verified` (2), `conflicting` (3);
- **repair:** reason bits (missing name, missing size, missing or inconsistent files). IMP-1 records them and **schedules nothing**. Recovery eligibility and its queue are V14 (CR-3);
- **privacy:** `unknown` (0), `public` (1), `private` (2).

**Merge rules in IMP-1** (the rich merge is IMP-06):
- **New hash, usable fields:** inserted as a torrent with its quality row. Its `discovered_at` and `last_seen_at` are the source's date only when that's positive and not after the batch; otherwise the import time. `source_at` keeps the source's value as given. It's flagged `IMPORTED`, plus `FILES_PARTIAL` only when completeness is `partial`. `unknown` doesn't flag it, so the existing re-fetch isn't triggered just because a source didn't say (plan §6).
  - It also gets `PRIVATE` when its privacy is private: declared, from its info dict, or from a candidate for the same hash.
  - An import record can't claim `verified`: that's `Error::Invalid`. Promoting verified metadata from an archived info dict is IMP-06's job, so nothing in IMP-1 can mark an import verified except a network fetch. The import is a new row for the IMP-06 merge to work on later; its `discovered_at` and `last_seen_at` are the source date, or the import time when the date is unknown.
- **Stored and verified** (no quality row, or `verified`): **provenance only.** It gains a membership row and the adapter's source bit. No canonical field, flag or state changes, so an import never downgrades a verified row.
- **Stored and not verified:** provenance, plus privacy merged **sticky-private**: `private` beats `unknown`, which beats `public`. Nothing else changes until IMP-06.
- **An import never clears `PRIVATE_SOURCE`.** The import path never calls `make_public`.
- **A network fetch that upgrades a partial import** (`upgrade_partial`) sets its quality to `verified` and `reported_complete`, and clears the repair bits it resolved, in the same transaction. A private import keeps `PRIVATE` through that upgrade: the restriction is sticky. A private fetched info dict makes the quality row private too, never public.
- **A held decision on an already-stored hash** keeps the record out (counted `filtered` or `quarantined`), but writes no hit or hold. The stored row's own filter state stands, and refiling stored torrents is §20.9's path, not an import's.
- **V13's migration** inserts a quality row for every existing `IMPORTED` torrent: verification `unknown`; completeness `partial` if `FILES_PARTIAL`, else `unknown`; privacy `private` if `flags` has `PRIVATE`, else `unknown`; repair 0. It's one pass over `torrents` that touches nothing else. Nothing is queued, and `fetch_queue` is untouched.

## Policy checks on every record
Each torrent and candidate record carries a mandatory filter **decision**: its hits (held, marked or shadow) and its `flags` marks. The caller runs the filter engine, so content rules and the floor see the name, the same as ingest. Inside the transaction, the store also refuses any record whose swarm hash is in `tombstones`, `quarantine` or `cs_hashes` (the floor's hash list), whatever the decision says. So:
- an import never resurrects a tombstone;
- an import never bypasses quarantine;
- an import never slips past the floor, even if a hold landed after the caller decided.

A held decision writes its filter hit and tombstone or quarantine row with the batch, as ingest does.

**Defence in depth (runner):** the floor and hash checks run in the store whatever the caller decided. A caller's decision can only make a record stricter, never looser. A record the store finds held writes none of the caller's hits.

## Counters and conservation
Per job, persisted, advanced only inside the batch transaction:
- `read`: parent records in committed batches;
- `new`;
- `merged`: already stored, with provenance added;
- `candidates`;
- `filtered`: dropped by a rule, the floor or a tombstone;
- `quarantined`;
- `invalid`: rejected with a fixed reason;
- `files_dropped`: malformed child rows the adapter dropped, counted whatever became of their parent record;
- `partial`: new rows stored with a partial file list. It's a subset count, not part of the sum;
- `source_bytes`: input bytes the adapter consumed for committed batches.

**Conservation:** `read = new + merged + candidates + filtered + quarantined + invalid`, after every commit and every replay. Replays aren't counted by the store. The adapter counts retried source batches on its own.

**Imports aren't DHT discoveries.** Nothing on this path touches the crawler gate's counters, so imports can't appear under `origin="network"`.
- `docs/metrics.md` already reserves `origin="import"` and says it isn't rendered until it's counted. So IMP-1 doesn't add a variant to `pipeline/src/gate.rs`: it would only render a permanent 0, against that contract.
- The slice that routes imports through the online writer adds the variant and counts it. That changes the plan the runner OK'd (which allowed the edit), and leaves `gate.rs` and `docs/metrics.md` untouched. It's named in the PR for the runner to acknowledge.

## The store API for one destination batch
`Store::commit_import_batch(&ImportBatch) -> Result<BatchCommitted>`:
- **Input:** `ImportBatch { job, seq, position, source_bytes, at, class_gen, records: &[ImportRecord] }`. Each `ImportRecord` is one of:
  - `Torrent { prepared, quality, source_at, decision }`;
  - `Candidate { hash, hash_v2, name, size, privacy, source_at, decision }`;
  - `Invalid`: counted only. The adapter keeps the reason; persisting per-reason counts is left to the adapter slices, which know their reasons.
- **One `BEGIN IMMEDIATE` transaction** on the store's writer connection: the job's control and phase check, the policy checks, the records, provenance and quality, the reindex entries (for merged rows whose `flags` changed), the counters, the filter hits, and the cursor advance to `(seq, position)`. The caller ACKs to the source **only after this returns `Ok`**.
- **Idempotent replay:**
  - `seq` must be the cursor's `seq + 1`;
  - a `seq` at or below the cursor's returns `BatchCommitted::Replayed` and writes nothing, which covers a crash after the commit but before the ACK. When `seq` equals the cursor's, `position` must match the stored one, or the adapter's numbering has drifted and it's `Error::Invalid`;
  - `seq` 0 and a gap are `Error::Invalid`: faults;
  - a job that isn't running (paused, blocked, finished, or not in `reading` or `committing`) is `Error::ImportNotRunning`. Nothing was written, and the caller sends the batch again after resume. It's its own variant so an adapter never mistakes it for a fault, or a fault for it.

  So counters never double-count. **A `Replayed` batch changes no counter**, and the tests assert it (runner).
- **One writer.** It's a `Store` method on the existing writer connection, so it runs wherever the single writer runs: the pipeline's writer task online (wiring in a later slice), or the offline CLI under the data folder's exclusive ownership. It never opens a second writer.
- **Job control:** `create_import_job`, `import_job`, `import_jobs` (paginated by id, for the Jobs UI), `set_import_phase`, `pause_import_job`, `resume_import_job` (which revalidates), `block_import_job`, `cancel_import_job`, `fail_import_job`, `interrupt_import_jobs`, and `import_quality` to read a row's states. Each is one transaction and bumps `revision` when it changes something. Pausing a paused job changes nothing.
- **Nothing prints the opaque bytes.** `ImportJob`, `NewImportJob` and `ImportBatch` have hand-written `Debug` impls that give lengths only.
- **Fail points:** a test-only seam (`cfg(test)`) injects a failure after each step: records, counters, cursor, just before the commit, and after the commit before the return. Tests crash there and then replay.
- **The writer task's channel.** The online path, the writer message and the routing are a later slice's. IMP-1 is the store's contract.

## Runner conditions (2026-10-30)
- **A v0.5.1 build refuses a V13 store cleanly.** `migrate` already refuses a schema newer than it knows (`Error::SchemaTooNew`, "database schema v13 is newer than this build supports (v12)"), before any migration or snapshot. Read-only connections refuse it in `check_current`. The v0.5.1 release branch has the same `migrate_with`. A test runs the V12 code path (this build's migrations through V12) against a V13 file. It asserts the refusal, no snapshot or side file, and an unchanged database file.
- **Size:** about 3k changed lines as one PR, stated in the PR. That's at the runner's split line, but most of it is tests. The schema, the API and the required crash and property tests are one unit.
