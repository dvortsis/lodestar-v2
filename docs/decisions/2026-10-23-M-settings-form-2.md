# M-settings-form follow-up decisions (engine diet, time-range)

The runner's follow-up to the Settings form engine (`web/src/lib/features/settings/form/`, architecture §10.10.5, §10.10.11, §10.1). S-settings-1 measured `/settings/[section]` at 51.1 KB gz over the owner's 45 KB route budget, so the engine sheds what a section's first view doesn't need, and the client learns B-update's `time-range` format. Items marked **(§2.19)** refine an owner decision and are for the runner to flag; one item asks the runner to confirm with the owner.

## What loads when
- **The first view is the store's first half and the field controls.** `form.svelte.ts` keeps loading, the field view, staging an edit, previews' debounce and events; its state moved into an `Engine` class so the on-demand halves can work on it. Everything else is a dynamic import, loaded once per page.
- **The edit chunk (`edit.ts`) is one download.** It holds the save pipeline (`saving.ts`: gates, the PATCH, refusals, Undo, `removeSecret`, retry, discard), the merge, drafts, validation, and the UI only an edit, a save or a conflict shows: the save bar, the error summary, the offline and save-error banners, a field's "Saved" mark and instant Undo, a field's conflict row, and the discard, leave and disruptive questions. Splitting these further measured worse: Rolldown pays ~400 B gz of imports per chunk, and every first-view module a lazy chunk shares becomes its own small chunk. One entry keeps the edit path to one request and one chunk header.
- **It loads with the first edit, a stored draft (in parallel with the values, so the offer still shows with the first view), the first `settings` event, a save, or `removeSecret`.** `SettingsForm.svelte` also prefetches it when the browser is idle after the first view (`requestIdleCallback`, 2 s timeout), so the first edit finds it in place, even if the connection drops in between.
- **Instant mode (`instant.ts`) loads with the first instant change**, with the edit chunk it sends through. Changes made while it loads keep their order on its chain. If it can't load, the value goes back with the offline message, as a failed send does.
- **Previews (`preview.ts`) load during the first preview's 300 ms debounce**, so a section with an automatic previewed field gets its estimate as before without the edit chunk.
- **The secret, chip-list and JSON controls load per field type.** `SettingsForm.svelte` starts them as soon as the form knows its fields (while the values load), so in a form they're normally in place at first paint. A field rendered before then shows a hidden box of the control's empty height: an input's for a chip list or a secret (whose buttons share the input height), the four-row Mono textarea for JSON. A chip list that already has chips grows by its chip row when the control arrives; inside `SettingsForm` that only happens if the control loads after the values.
- **Copy's toast loads on the first copy.** The clipboard write stays in the click, where Safari allows it.
- **The load-error banner stays in the first view**: a form that couldn't load may not reach the edit chunk either.
- **Drafts are written from the first view** (`draft-store.ts`: `draftOf` and `writeDraft`), so an edit is kept from the first keystroke even if the edit chunk never arrives. Reading and restoring one load with the edit chunk.
- **A chunk that fails to load needs a reload.** Browsers keep a failed module, so trying the same import again fails too. `save()` and `removeSecret()` return `network`; the form shows "Part of this page couldn't load. Check your connection, then reload the page." with a Reload button (two new messages), and the draft brings the edits back after it. A control that can't load shows the same line in its place. If the leave dialog can't load, leaving runs as a full page load, so the browser's own unsaved-changes prompt asks. A copy whose toast can't load still copies, without a toast.
- **The error summary takes focus once per failed save.** Loaded on demand, it mounts again when its error count returns from 0 (a field fixed, then made invalid again); it doesn't take focus then, only for a save it hasn't focused yet.

## Behaviour
- **No behaviour changes beyond timing.** Every existing unit and e2e test passes unchanged except where a test needed the on-demand parts in place up front: `form.test.ts`, `SettingField.test.ts` and `SettingsForm.test.ts` preload them in `beforeAll` (`preloadSettingsForm()`, `loadControl`), as they already did for the dialog and menu. `lazy.test.ts`, `LazyControl.test.ts` and `SettingsForm.lazy.test.ts` load each part cold and check it works; `SettingsForm.offline.test.ts` checks a form whose edit chunk can't load.
- **Asks the runner to confirm with the owner.** The owner's budget decision (`2026-10-23-M-settings-form.md`, Budget) chose the 45 KB route budget "over splitting the engine further, which would have put async seams on the merge and draft restore". This follow-up splits them, as the runner asked. The merge and the restore themselves stay synchronous: their code is in place before either can run (a conflict needs an edit or an event, an offer waits for the chunk with the values). The seams are at those loads instead: an event before any edit waits for the edit chunk, and a stored draft's offer waits for it alongside the values.

## Size (§10.1, §10.10.11)
- **The first view is 7,345 B gz smaller.** Measured as S-settings-1 measured its route, on the `/dev/settings-form` showcase (no prod route imports the engine yet): what it loads beyond `/search`, gzip level 9, went from 41,820 B to 34,475 B.
- **The engine's own first-view part is about 16.6 KB gz (§2.19).** The ≤ 22 KB engine target was set when the engine was one chunk (22.1 KB in the showcase). After the first edit the engine totals about 26.6 KB gz across its chunks (first view 16.6, edit chunk 9.4, previews 0.7); all of it, gzipped together, is 29.1 KB against main's 22.7. The growth is the split's cost: per-chunk imports, gzip's dictionary restarting per chunk, and the `Engine` class's property accesses, which the minifier can't shorten as it did the closure's locals. Read as "the part every section pays", the target holds; read as "the whole engine once edited", it doesn't. The runner decides which reading applies.
- **A new size-limit entry, "Settings section route (beyond /search)", 45 KB**, the owner's route budget: the JS and CSS `/settings/[section]` loads beyond `/search`, from the build manifest (`scripts/size-entries.mjs`). The engine's on-demand parts are dynamic imports and stay out of it. Today it measures the placeholder page (167 B); once S-settings-1's screen lands it guards the first view, engine included, so it can't creep back.

## Validation
- **`time-range` is `HH:MM-HH:MM`, 24-hour, two digits each, and may wrap midnight**, as B-update's `update::window::parse` reads it. A window that starts and ends at the same minute is refused with its own message, as the server refuses it. The client is a little stricter than the server on odd input (`+3:00`, which Rust's integer parse accepts); the server still has the final say. B-update adds `'time-range'` to `schema.test.ts`'s expected formats in its own PR, so that list is untouched here.
- **Two new messages**, `settings_form_error_time_range` and `settings_form_error_time_range_same`, in the existing pattern (what's wrong and what to enter, §10.14). English only, like the other engine errors.
