# X-healthz-count-async decisions

X-healthz-cold-start (#1159) took the have-filter's scan off the start, but `count(*)` stayed in `prepare()` for `Monitor::torrents()`. At 10M it was about 1 s of a cold start, and likely 3–4 s on the test VM. This slice moves the count to the fill thread too. `stats.stored_torrents` is now null until the count lands. This supersedes [X-healthz-cold-start](2026-11-28-X-healthz-cold-start.md) on where the count is taken, how the filter is sized, and the `pipeline.starting` log's `stored` field. Architecture §5 (the have-filter) and the `/stats` contract (`docs/metrics.md` §7.6) are affected.

- **The count is taken on the fill thread, in a snapshot pinned before the writer exists.** `prepare()` opens the fill's reader and begins a read transaction on it (`BEGIN DEFERRED` plus one read, so the snapshot is taken then, not at the count). That happens where `count(*)` used to run: after the held sweep, before the writer starts. The fill thread counts in it first, then scans in it. So `count + writer.stored` (the formula `Monitor::torrents()` always used) stays exact: every torrent the writer stores is after the snapshot and in `writer.stored`, and none is in both. The pin costs about 0 ms. No store API changes: it goes through `Store::connection()`.
- **The count is published as soon as it's taken, before the scan** (runner, step 0): it's final then. `Monitor::torrents()` is `Option<u64>`, `None` until then.
- **A stop during the count ends the fill there** (runner's review). The scan doesn't start and the snapshot is let go at once. Before, a stop during a count of 1–4 s at 10M ran the whole scan with the WAL pinned, and the writer's stop-time `TRUNCATE` checkpoint then waited out its 5 s busy timeout. Tested with `count_gate`: no reader is opened for a scan, and a passive checkpoint passes.
- **`pipeline.have_fill_failed` carries a `stage`:** `pin` (the start counted on its own connection instead), `count` (the count stays unknown until the next start and isn't tried again) or `scan` (tried again, and crawling waits). Its message, doc, en and zh help and the metrics.md row are true for each stage. The pipeline event-names chunk is 3,432 B, inside the 3,456 B budget.
- **The filter is sized as soon as its size is known, before the scan** (the runner's nit). `Have::size` gets an empty filter of the count's size, replaying what was inserted during the count, and the scan then fills it in place beside the writer's inserts. So the pending list holds only what the writer stored during the count.
- **A count that fails is never tried again, and never holds the fill.** It's logged as `pipeline.have_fill_failed` (`stage` `count`, `attempts` 0). The snapshot is let go at once, and the scan goes on in the same try from a reader of its own, with the filter sized from `Store::torrent_bound`. The count stays null for the rest of that run (runner: null on a lost snapshot, and `writer.rs` not touched). No later snapshot can be squared with what the writer has stored since without a count on the writer's own connection. **This is narrower than step 0's "retry in the same snapshot while its transaction holds"** (the self-review's finding). A count that keeps failing without SQLite ending the transaction, a corrupt index being one case, would have held the snapshot all run. That means a WAL growing without bound and crawling never starting. Null is honest where a guess isn't. **A snapshot SQLite has ended under it is never counted in:** outside it, the count could include torrents the writer counts too.
- **A snapshot that can't be pinned** (the reader doesn't open) falls back to the old path: `prepare()` counts on the main connection, and an error there fails the start as it always did. The filter is then sized from that count and filled on the thread. In-memory stores (tests) are still counted and filled in `prepare()`.
- **The transaction always ends.** The pinned reader is owned by the fill. It's dropped, which rolls back the read transaction, as soon as the scan ends or fails, when the fill stops (checked before each try and every second of a wait), and when the filter is gone. So a stuck or failed fill can't hold the WAL back for the rest of the run. Tested: a passive checkpoint passes the snapshot once the fill has finished, and once it has stopped. A scan in progress still isn't interrupted, as before.
- **The have-filter is sized late, from the exact count (runner: memory matters, §3).** The alternative, `capacity_for(torrent_bound)`, could be several times the memory. `Have::unsized_filling` starts as a one-word placeholder. While it's unsized, each insert (the writer's, during the count) also goes on a pending list under that list's mutex. Once the count is in, `Have::size` replays the pending list into an empty `Bloom` of `capacity_for(count)` and swaps it in under the same mutex; the scan then fills it, before `mark_filled`. An insert that read "unsized" takes the lock, so it lands either in the list (replayed) or, after the swap, in the new filter. One that reads "sized" (`Acquire`, set after the swap with `Release`) finds the new filter. **Once sized, `insert` reads one flag and never takes the lock** (tested by holding the lock). The pending list holds only what's committed during the count: the intake is parked, so imports and uploads, 20 bytes each. On a lost count the filter is sized from `Store::torrent_bound` (two seeks).
- **`lodestar_torrents` is absent from `/metrics` until the count lands,** never 0, following metrics.md's rule for series that can't be read yet. Dashboards see a gap, not a drop.
- **Nullable alike:** `stats.stored_torrents` (`#[schema(required = true)]`: always present, may be null), the SSE `crawler` event's `torrents`, and `/status`' `torrents`. The status page shows "—" for null. No web screen reads either field today, so the web change is only the regenerated `openapi.json` and `schema.d.ts`.
- **`pipeline.starting` loses its `stored` field; the new `pipeline.torrents_counted` (Info) carries `stored` and `ms` when the count lands.** Nothing in `tools/`, `bench/`, `soak/`, `packaging/`, `runner/` or the docs parses `stored` (one 2026-10-23 soak log quotes it). - **The soak analyzer's fresh-store check follows the absent gauge** (runner: granted and shipped in this PR, so no `main` has one without the other). `docs/soak/tools/analyze_cr.py`'s `fresh_store` read the first scrape's `torrents` as `== 0`, so a first scrape inside the null window would have made check 6.7 invalid. Now:
  - It reads the first scrape that has a `torrents` value, if that scrape is within one scrape interval (`collect.SAMPLE_SECONDS`, 60 s) of the first scrape that reached the server (`start_time_seconds` read).
  - Later than that, `fresh_store_at_start` reads **not measured** (§6.4's rule, effect `not_measured`): neither valid nor invalid. Crawling may have stored rows by then.
  - An absent value is unknown, never 0 and never a pass: `gate-round` still needs `fresh_store` to be true.

  Tests in `test_gate_round.py` cover the value present at the first scrape, absent then present within an interval, and absent past one. The default round-1 fixture still reads as before, and the committed golden verdict is unchanged. The soak tools' suites pass (520 and 266 tests).
- **Every soak tool that reads `torrents` was checked; each one that misread an absent value is fixed in this PR** (runner: granted, since the rehearsal pins the collector from this commit). `analyze_cr.py` was not the only reader outside the slice:
  - **`linux/collect.py`:** `torrents` stays in `REQUIRED`, but it's `NULLABLE`. An absent series is recorded as null and the sample keeps `metrics_ok`. A series that's present but unreadable still fails the sample. Before this, a lost count would have failed every sample and stopped the soak after three (`three_consecutive_metrics_failures`).
  - **`cr0-soak.ps1`:** the same rule, through `Read-SoakOptionalMetric` in `cr0-common.ps1`.
  - **`cr0-common.ps1`'s `Get-SoakTorrentCount`** (the upgrade record's `torrents_after`) polls `/metrics` for up to 120 s, then fails with an error naming the start-up count.
  - **`smoke_windows.ps1`** polls for `lodestar_torrents` and `lodestar_start_time_seconds` the same way, up to 120 s, instead of failing at once.
  - **Already safe:** both copies of the screen's `screen_inputs` (stored per 1,000 torrents) leave a non-number out, and `analyze_cr.py`'s first-stored check skips one, as does `analyze_cr0.py`'s memory context. `stored_per_min` comes from `metadata_new_verified_total`, not this gauge.
  - **Tests:** `linux/test_collect.py` covers a count absent at the start and one absent all run (no failed sample, null values, the screen leaving it out). `test_cr0_collector.ps1` covers the late count, the deadline's error and the optional read, and now parse-checks `smoke_windows.ps1` too. The Python suites pass (520 and 268 tests). The PowerShell suite runs in CI's Windows job; PowerShell isn't available in this container. The field keeps its name on the new event anyway. The prepare-time fallback logs it too.
- **The pipeline event-names chunk's size budget goes from 3,328 B to 3,456 B** (runner, §2.26). The new event's name and help, in en and zh, measure 3,407 B, rounded up to 64 B as X-vpn-bind did. The help strings were already shortened, which took the chunk from 3,468 B to 3,407 B.
- **The have-filter gauges read the placeholder during the count** (`have_capacity` 1, `have_bytes` 8, `have_entries` the writer's inserts since the start), then the real filter's once it's sized. Under X-healthz-cold-start they read the final size throughout. Recorded in `docs/metrics.md`.
- **`PipelineConfig::count_gate`** (hidden, tests only) runs on the fill thread before the count, so a test can hold the null window.

## Measured (`bench/examples/cold-start.rs`, 10M)
A synthetic store of 10,000,000 torrents (one in eight hybrid; 1.36 GB) in a cloud container (4 cores, 15 GB). It's the largest size the container's free disk allowed beside the build. "Cold" means the page cache was dropped before the run. Before is `origin/main` at 46d7f463; each cell is two runs.

| | Start (first `/healthz`) | Count lands (`stored_torrents` non-null) | Fill done (crawling starts) |
|---|---|---|---|
| Before, cold | 1,032–1,127 ms | the same: in the start | 6,237–6,454 ms |
| Before, warm | 71–85 ms | the same | 4,870–5,058 ms |
| After, cold | 9–10 ms | 1,162–1,262 ms | 6,148–6,420 ms |
| After, warm | 4 ms | 85–109 ms | 4,745–5,039 ms |

- **The start no longer reads the torrents table at all.** On the test VM, where X-healthz-cold-start measured about 3–4× this container, the first `/healthz` should now take well under the ~2 s goal. The runner's 10M re-check there reads `start_ms`, `counted_ms` and `filled_ms` from the second run.
- **The WAL while the fill holds its snapshot (runner 2a).** A side connection wrote 1,000 rows of 1 KiB a second (a heavy import's rate) into a scratch table during the fill. The WAL peaked at 69–84 MB after, against 71–76 MB before: about 14 KB of WAL per row with 16 KiB pages, for as long as the snapshot is held. Before this slice the scan already held one snapshot for its whole length. The pin adds the count's time to that, about 1 s cold and 0.1 s warm at 10M, so at that write rate about 14 MB more WAL on a cold start, given back at the first checkpoint after the fill. At the crawler's own rate (tens of rows a second) it's under a megabyte.
- **Memory is unchanged:** the filter is `capacity_for(count)`, 25 MB at 10M, as before. The placeholder is one word.
