# ENR-debrid decisions (debrid cache status: skipped, no code ships)

Slice ENR-debrid (`runner/slices.yaml`). Spec: architecture §18.2 and §18.7, plan `docs/plan/2026-11-05-v07-m7.md` §6 Q4 and Q5, decided by `docs/owner-decisions.md` §2.47 ("the plan row is the decision"). The owner's Q4 answer: "Debrid: only for a provider that offers a cache check today and whose terms allow it, otherwise dropped from v0.7."

## Decision: no provider qualifies, so debrid cache status is dropped from v0.7
- **The test applied (Q4, and the runner's note for this slice):** a provider qualifies only if (a) its current, official API documentation offers a cache or instant-availability check by infohash, **and** (b) its terms clearly allow a third-party app to make those lookups automatically with the user's own key. Where either is unclear, the provider doesn't qualify.
- **Result:** none of the five providers checked passes both. Three no longer document a cache check at all; the two that still have one (Premiumize, TorBox) have terms this check couldn't read from the provider itself. So, per Q4, **this slice ships no code** and debrid status is out of v0.7. This applies the owner's decision as written; it doesn't loosen or change it.
- **Nothing was sent to any provider's API.** Only public documentation, changelog and terms pages, plus web searches, were read. No account, key or contact detail was used.

- **Context, not a reason on its own:** Real-Debrid began filtering cached items by filename pattern in May 2026 (TorrentFreak, `https://torrentfreak.com/real-debrids-renewed-piracy-crackdown-follows-corporate-restructuring/`). Providers are changing what their caches answer and what their terms say, which is why Q4 asks for a check that holds today.

## What would bring it back (for the runner)
- **TorBox is the nearest candidate,** then Premiumize. If a person reads TorBox's current terms (and its abuse-system article) in a browser and finds they clearly allow a third-party app to check hashes with the user's own key, the runner can relaunch ENR-debrid for TorBox under the same Q4 answer, with a new decisions file that supersedes this one. That's a re-check of facts, not a new owner question: Q4 already says yes for a provider that qualifies.
- **The slice's other limits stay as they are for any relaunch:** Account consent, the user's own key (never logged or stored outside `SecretStore`), only verified public items' hashes (never `private_source`, held, hidden, unverified or Adult-off), the provider's own rate limit, and a "Cached on <service>" badge as the only output.
- **The runner marks the slice and its plan row** (`runner/slices.yaml`, `runner/dashboard.yaml`, the v0.7 plan) as skipped; this PR doesn't edit them, as they're the runner's files.
- **The badge follow-up (UI review 02 §5.5) isn't needed** while no provider ships.
