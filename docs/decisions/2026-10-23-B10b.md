# B10b decisions (`/export` and `/jobs`)

- **One request type for every export** (`ExportRequest`, §9, §10.4). The source is one of: a query (`q` or `ast` with `sort` and `hidden`, as `/search` takes them; none at all exports everything), up to **10,000** `hashes` (the bulk bar's selection, repeats exported once in the order first given), or a `collection` id (its order). `GET /export` takes the query and collection forms; `ast` and `hashes` need `POST` (same-origin JSON). Mixing sources is a `400 one_source`; `sort` with a selection or collection is `400 sort_unused`.
- **Formats:** `csv` (the default; RFC 4180 with CRLF and a header row), `json` (NDJSON, one object per line, keys sorted, written by `serde_json`) and `magnets` (`text/plain`, one per line, byte for byte the detail view's `magnet`; `torrents::percent_encode` became `pub(crate)` for it). No UTF-8 BOM: RFC 4180 has none, and spreadsheets that need one can import the file as UTF-8.
- **Fields:** the summary fields of `docs/metrics.md` §7.1 that hits carry, built by the same code as hits (`torrents::hit` + `search::enrich`), so the null rules are the same: a never-scraped swarm field is an empty cell in CSV and `null` in JSON, never 0. Left out: `score` and `matched_files` (they describe one search, not the torrent). Added on request only: `magnet`. `fields=` takes a comma-separated subset (`ExportField`), always written in that type's order. CSV writes lists joined with `;` and `composition` as `group:pct_bytes` pairs. Dates stay Unix seconds, as in the API.
- **Swarm fields come from the hit code only (for M4, #48):** an export takes every summary field, the swarm ones included, from `torrents::hit` + `search::enrich`, the code search hits are built by. Today those fill the swarm fields as null (never scraped). So #48 must fill `seeders`, `leechers`, `completed`, `trackers_reporting`, `trackers_checked` and `last_scrape_at` there (or in a helper both call), not only in `/search`'s handler, or exports keep writing them as never scraped.
- **CSV safety:** a cell starting with `=`, `+`, `-`, `@`, tab or CR gets a leading `'`. Control characters (C0, DEL, C1) and the bidirectional formatting characters (U+061C, U+200E/F, U+202A–U+202E, U+2066–U+2069, which can make a name display as something else) are written `\u{hex}`. A cell with a comma or quote is quoted, quotes doubled. Names are the stored, decoded name the detail view shows. JSON keeps the name's characters (serde_json escapes the controls JSON requires). The escape is for reading, not round-tripping: a backslash isn't escaped itself, so a name that literally contains `\u{7}` reads the same as an escaped BEL.
- **Never exported:** what search wouldn't show, and private sources (§18.7, §18.9, §20.3, §20.9). A query runs through `search::base_query` (filter-hidden only with `hidden=true`; Adult only while export's own adult setting is on, below); every row read is checked again with `discover::withheld` (the index can lag a reclassification) plus `flags::PRIVATE_SOURCE`. Quarantined and tombstoned items have no `torrents` row, so nothing finds them. Every row left out (withheld, private, deleted since indexing, an unknown hash) counts in the job's `skipped`, which never says which or why; a withheld hash and an unknown one look the same. This applies to all three sources. A query that names the hidden flag itself (`hidden:yes`) without `hidden=true` keeps hidden torrents in the index query, as `/search` does, but the row check then withholds them all: such an export comes out empty with every match in `skipped`. Send `hidden=true` to export them.
- **Adult follows export's own setting, not "Show adult content"** (§20.9: each output has its own adult setting, off by default; §16 B17 reserved `content.export_adult` for this slice). The API takes it as an `Extension<export::ExportAdult>`, a live `AdultVisibility`. `lodestar serve` layers one that follows `content.export_adult` live (`settings::content::follow_export`, a shared-file edit in `crates/lodestar/src/services.rs` the runner asked for in this PR), and its help no longer says "Not used yet". Without one (tests, tools), **exports never include Adult**, which is `export_adult`'s default. Whether `export_adult` should also require "Show adult content" is left to whoever wires it (§2.19); this slice reads only the export setting. This supersedes the brief, which asked for "Show adult content": the architecture's own setting outranks it.
- **Adult mid-export:** export's setting is read when the export starts (the query's lease is taken without Adult while it's off), and read again before each chunk. Turning it off mid-export withholds Adult from the next chunk read on, counted in `skipped`; up to the chunks already queued for the socket (at most `queue + 1`) may still carry Adult read before the change. Turning it on mid-export adds none. This is stricter than reading it once.
- **Reading: chunked, short transactions, nothing on disk** (§7 "Read path", §15, §2.17). Rows are read **256** at a time: ids from a slice of the hashes, a page of the collection, or a query's buffer of ids. That buffer is filled from the export's own searcher lease (in the query's sort) **16,384 ids at a time** (128 KiB), because each page after a position scans every match: one page per 16,384 rows, not per 256, keeps a 1M-row export to about 60 scans. Their rows are read under the reader lock inside one read transaction, which ends before the rows are formatted or queued. No lock or transaction is held across chunks, the throttle's wait, a pause or a slow client, so WAL checkpoints are never starved (the §15 test: a writer inserting and checkpointing with `TRUNCATE` beside an export finds the WAL empty after every checkpoint). The body is streamed from memory through a queue of **4** chunks; nothing is written to disk.
- **Throttle: 2,000 rows read per second, shared by every running export** (withheld rows count, since they're read too). One pacer lives in the jobs registry: each export books the rows it just read on one timeline and waits for its turn, so four exports at once read 2,000 rows/s between them, not 8,000. Time nobody booked (idle, paused, slow clients) is never banked: booking restarts from now, so no export bursts to catch up. A full 1,000,000-row export alone takes about 8½ minutes. The rate comes from measuring §1.6.4's budget (search p95 +≤ 5%, ingest −≤ 2%) with exports streaming beside searches and a writer (`tests/export.rs`, `overhead`, ignored; run in release; `LODESTAR_EXPORTS`, `LODESTAR_EXPORT_RATE`, `LODESTAR_EXPORT_CHUNK` and `LODESTAR_EXPORT_TORRENTS` vary it). Its searches are all different, so B5c's result cache can't answer them. One export: 20,000 rows/s raised search p95 ~15%, 5,000 ~6%. At 2,000 rows/s with four exports, five runs measured search p95 +2.1, +4.2, +1.1, −3.9 and +2.3% (mean +1.2%) and ingest +0.9, −4.3, −0.4, −4.7 and −1.0% (mean −1.9%). Identical quiet runs vary by about ±3% (search) and ±4% (ingest), so ingest's 2% can't be resolved by this harness, and 1,500 rows/s measured no differently. Earlier single-export runs on 1,000,000 torrents were within the same noise. The 10M bench set isn't reachable from this test (`bench/` isn't this slice's); the per-chunk index cost is bounded by the 16,384-id pages above. The constants are `export::{CHUNK, ID_PAGE, ROWS_PER_SEC, CAP}`; a later bench gate can tune them.
- **Backpressure:** a client that stops reading fills the queue, and the export waits there holding nothing. If it reads nothing for **10 minutes** the export fails (`export_stalled`), so a stalled download can't keep a job slot or a lease forever.
- **The export's lease is its own**, not in the search registry: the registry's 10-minute idle expiry and its per-session LRU (64 leases) could otherwise end a long or paused export, or a user's own searches could evict it. So nothing has to renew it. Instead an export runs at most **1 hour** in all (`export_expired`), the bound a cursor's lease has for keeping a retired index open after a swap (`LeaseConfig::max_age`). Rows committed after the export began aren't in it: it reads one snapshot, like a cursor.
- **Cap: 1,000,000 rows per export.** A capped export ends cleanly at the cap and says so: the job's `export.truncated` is `true`, and an NDJSON file's last line is `{"trailer":{"cap","rows","skipped","truncated"}}`. CSV and magnet lists have no room for a trailer, so their job carries it (the response's `X-Export-Job` header names the job). A file that ends any other way short of complete (cancelled, failed, past a limit, the worker gone) ends with a **transport error**, never a clean end, so a browser marks the download failed rather than keeping a truncated file that looks whole; an NDJSON file without its trailer is incomplete.
- **Response:** `Content-Disposition: attachment; filename="lodestar-export-YYYYMMDD-HHMMSS.<csv|ndjson|txt>"` (UTC, generated, never from a torrent name), `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Export-Job: <id>`. Validation errors, `search_disabled`, `collection_not_found` and `too_many_jobs` are the usual JSON envelope, before anything streams.
- **`GET /export` starts a job, which is a change of state on a GET.** That's acceptable here: the session cookie is `SameSite=Strict`, so a cross-site page can't make the browser send an authenticated GET (a link, an `<img>` or a form), and a same-site one is the app itself. The worst a stray GET does is start a download its own tab receives, holding one of the four slots until it's read, cancelled or stalls out.
- **`/jobs`** generalizes the filters' preview jobs (#52) without moving them: at most **4 running or paused** (all kinds together; past it `429 too_many_jobs`), **64 kept** (the oldest finished go first), each finished job kept **10 minutes**, swept on every start and read. A worker that panics or is dropped unfinished finishes its job as `failed` with a 500 (`internal`) and frees its slot. `GET /jobs` (newest first), `GET /jobs/{id}`, `POST /jobs/{id}/pause|resume|cancel` (same-origin JSON; each returns the job; `409 job_finished` once it's finished; pausing a paused job or resuming a running one does nothing; nothing undoes a cancel). Unknown ids are `404 job_not_found`. Session only, like every protected route.
- **Job states:** `running`, `paused`, `done`, `cancelled` (by `/cancel`, or the client went away), `failed` (with `error`). `kind` is `export`, or `import`, reserved for the importer framework (§18.8). A job reports `done`, `total` (null when unknown; an estimate, `total_approx`, above 100,000 query matches), `skipped`, `rate` (items per second, paused time left out), `eta_s` (only while running with a known total), `started_at` and `finished_at`, and for an export `{cap, format, truncated}`.
- **A paused export** stops at its next chunk and holds nothing (no lock, no transaction; its lease is only memory). It fails as `pause_expired` unless resumed within **10 minutes**; if its client goes away meanwhile it ends at once as `cancelled`, freeing its slot.
- **A slot is taken before any work, and freed if setup doesn't finish:** an export takes its job slot before it parses hashes, counts a collection or runs its query, so a request past the limit costs nothing. Until its worker owns the job, a guard discards it on drop: a failed setup, or a request the client dropped mid-setup (an aborted fetch, navigating away, a proxy timeout on a slow query), frees its slot instead of leaving a `running` job for good. The job is dropped from the registry rather than listed as failed.
- **`rate` and `eta_s` count every item read**, `done` and `skipped` together, since `total` counts both; a heavily withheld export's ETA is then right.
- **`done` means queued, not delivered:** an export is `done` once its last bytes are queued for the socket, so a client that disconnects in the last few chunks leaves a `done` job. The file itself ends with a transport error in that case, so the client still knows it's incomplete.
- **`truncated`** means the export stopped at the cap with ids left to read, even if every one of them would have been withheld; telling the two apart would mean reading past the cap.
- **The registry is an `Extension`, not an `ApiState` field:** `jobs::routes()` uses an `Extension<Arc<Jobs>>` the server layers over the router when there is one, and otherwise its own (one per router, so one per process; tests get a fresh one each). No `ApiState { .. }` literal had to change, and #48's `ApiState` additions don't conflict.
- **Shutdown:** `Jobs::close()` cancels every job (a cancelled download ends at once) and refuses new ones with `503 shutting_down`. `lodestar serve` layers one registry over the router and closes it on the shutdown signal beside `EventHub::close` (the same `services.rs` edit), so open exports never hold axum's graceful shutdown.
- **Filter preview jobs stay where they are for now.** They return an assessment rather than a stream and have no pause; moving them under `/jobs` (as `kind: preview`, with their result on the job) is a reasonable follow-up once the Jobs view (W-slice) exists, so one view shows everything that runs.
- **Logs:** nothing in `/export` or `/jobs` logs a torrent detail (§12.1); errors log only through `internal`, which never carries a name or hash.
