## Split (runner, 2026-11-09)
The slice was estimated at 3.5–4.5k changed lines, so it lands as three PRs in sequence, each opened once the previous one merges:
- **CMP-5g-1:** wiring and watch. It covers CMP-6's carry-overs, the watch loop, the companion gate's feed and CMP-8b's `ConfigSink`.

## CMP-5g-1

### CMP-6's carry-overs
1. **`Service::installed` reads the journal.** It's `state::load(<data>/companions/<id>)` with an installed version, read-only (runner-approved). It no longer uses the snapshot, which detected companions now join. Inside a container it's always false. Tested: a journal that recovery hasn't published counts, and a snapshot whose journal is gone doesn't.
2. **The provenance marker** comes with CMP-5g-2's records, which write it when you paste a credential. The reveal will then require `generated`.
3. **The template data guard's positive path is tested.** On a native install, the resolved data folder is in the generator's input. Inside a container it isn't.
4. **`manager::field_of` is public** (doc only, no behaviour change), and the binary's copy is gone.
5. **I1 through the real generators:** no catalogue pin lands in this slice, so the field naming stays tested with a fake generator (`blame`). The first pinned image adds the end-to-end case.

### Guided records
Their format is runner-approved (2026-11-09): `companions.<id>.target`, `.origin` and `.provenance.<field>` `settings` rows, read strictly. They land with CMP-5g-2, which also documents the format here. Until then, the watch and the gate take the companions you added as plain `(id, target)` pairs (`companion_wiring::Added`), and serve starts with none.

### The watch (`crates/companions/src/watch.rs`, tested in `crates/companions/tests/watch.rs`)
- **Q7's cadence:** each companion you added is checked when it's added or its target changes, then every 30 s. The check uses CMP-8a's `Health` adapter and the guarded client only, on its record's target (Q12).
- **Debounced, per Q7's "3 failures in a row":** a companion seen healthy stays healthy until three checks in a row fail. That's because CMP-10 restarts a plugin on every flip it's sent. A first result counts at once, and a changed target starts the debounce again.
- **A change of list checks only what's new or moved;** the full round is the 30 s tick, whose first comes a whole period after the start's round. So edits to the list never hurry another companion's debounce (self-review I4).
- **Reports:** `Healthy`, `Unhealthy` (it answered wrongly) or `Missing` (nothing answered). A companion without a health adapter (gluetun) isn't listed.

### The companion gate (`crates/lodestar/src/companion_wiring.rs`; CMP-10's contract)
- **`PipelineConfig::companions` is now `Some`** whenever companions are on for the run (`companion_wiring::gate`). **With companions off** (a fixture, a held lock, a bad catalogue), it stays `None`, which turns the gate off: the sources run as before (runner's condition; `gate`'s test, and `requires`' own tests of `None`).
- The gate holds `Unknown` until the feed's first snapshot. That's sent once the sources' ops exist, so gated plugins wait until then: it fails closed.
- **What it sends:**
  - every companion Lodestar installed, healthy only when its last check passed. Not checked yet counts as unhealthy: after a restart that's every installed companion, until CMP-5g-3 starts them;
  - every companion you added, as the watch sees it, with a missing one unlisted, so its dependents show "Needs X";
  - `external_client`: an `integrations.clients` entry other than `lodestar-qbittorrent`;
  - `external_indexer`: the Prowlarr source is on, and the address in its saved config (`sources.config.prowlarr`'s `url`) isn't a companion's. A companion's is a record's target, or loopback on the catalogue's WebUI port for an installed Prowlarr. The manifest lists no endpoints for the source, so `/sources`' `endpoints` can't be used (self-review B1).
  - a watched companion counts only at the target it's added at now: a removed or moved companion's last result never carries over (self-review I3).
- **Addresses compare canonically:** without a trailing `/`, with the scheme and host in lower case.
- **When it updates:** on any change to the installed companions, the watch, the integrations or the records, and every 30 s for the Prowlarr source being turned on or off.
- **Existing setups keep working** (runner's condition, clarified 2026-11-09): with companions on and nothing installed, a download client you set up yourself counts as `external_client`, and a Prowlarr source pointed at your own Prowlarr counts as `external_indexer`. Either meets its source's need from the first snapshot (`your_own_setup_keeps_working_with_companions_on`).
- **"Needs prowlarr" and "Needs qbittorrent" with nothing configured are accepted** (runner): with no address or client saved, those sources couldn't run anyway.
- **The gate's on/off choice is `companion_wiring::gate(companions.as_ref())`,** which `services.rs` calls with the run's companions, so the off case can't be mistyped there (#645's review, M9).
- **A failed read of the Prowlarr source keeps what the gate last knew** (a busy store or a lock error never stops a working source). The first failure of a streak is logged as `companions.config_failed` (setting `gate.prowlarr_address`, reason `read_failed`), with no value.
- **Addresses compare as parsed URLs:** scheme, host and port, with the scheme's default port filled in, then the path without a trailing `/`. One that doesn't parse equals only itself.
- **If the watch stops,** the feed logs `companions.install_failed` (step `watch`, reason `stopped`) and ends. The gate then reads as unknown and holds gated sources.
- **The window until CMP-5g-3 merges** (runner's condition): a companion Lodestar installed isn't started yet, so it counts as unhealthy, and a source that needs it waits. Its status says why in plain terms, through CMP-10's `needs` on `/sources` (`{"companion": "qbittorrent", "state": "unhealthy"}`), never as an unexplained stall. Nothing in this window is released.
- **A failed start** (the guarded client couldn't be built) is logged as `companions.install_failed`, step `wire`, and leaves the gate `Unknown`.

### `ConfigSink` (`companion_wiring::Sink`; CMP-5g-2 calls it)
- **qBittorrent:**
  - It becomes the `integrations.clients` entry `lodestar-qbittorrent` ("qBittorrent (Lodestar)"), through the settings registry's own save, so its validation and sealing apply.
  - The rest of the list is saved as it is, each other client without its password, which keeps the saved one.
  - The address is the target's, and the user name, password and category come from CMP-8b's entry.
- **qBittorrent's list is read right before the save,** on the save's own thread, so a save you made meanwhile isn't overwritten with an old list (self-review I6). The registry's save isn't conditional on a revision, so two saves in the same instant can still race; the window is the time between that read and the save.
- **The id `lodestar-qbittorrent` isn't reserved:** a client you name that is treated as the managed one (not external) and replaced by a hand-over. Ids are yours to choose; the UI (CMP-9a) can warn.
- **Prowlarr, ordered so no key meets the wrong server whatever fails** (#645's security review):
  1. the key you saved is removed first, so it can't go to the companion's address;
  2. then the source's config gets the companion's address, keeping any other value you saved, such as `agents` (self-review I2);
  3. then the companion's key is stored.

  If step 3 fails, the config goes back to the one you saved, or the source is turned off when none was saved or it doesn't parse. A failed rollback is logged as `companions.config_failed` (setting `lodestar.settings`, reason `rollback_failed`), never with a value. Each write applies at the next start. The order and every rollback are tested (`hand_over_prowlarr`, over a recorder of the source writes).
- **After a hand-over the Prowlarr source shows `restart_required`** (runner, 2026-11-09, option a). This corrects CMP-10's contract in `2026-11-08-CMP-5.md`, which said the source "is restarted or its config supplied again". A saved source setting applies at Lodestar's next start, as for any saved source setting, and nothing reloads one source live. Reloading one source live is a follow-up candidate the runner logged; it isn't queued.
- **Tested here:** the qBittorrent save through a real registry (your client keeps its saved password; the managed entry is added, then replaced), and the Prowlarr config merge. **Not tested here:** the thin adapter from those source writes to `OpsApi`; CMP-5g-2's confirmation tests drive it end to end.
