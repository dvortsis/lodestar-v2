# CMP-5g decisions

Guided and detected companions, end to end (plan `docs/plan/2026-11-06-v06-companions.md` CMP-5g, Q7, Q12, Q19; architecture §18.7, §18.10; `docs/owner-decisions.md` §1.7.2). These are the slice's decisions under §2.33. None loosens an owner decision or a security decision. The runner flags them to the owner (§2.19).

## Split (runner, 2026-11-09)
The slice was estimated at 3.5–4.5k changed lines, so it lands as three PRs in sequence, each opened once the previous one merges:
- **CMP-5g-1:** wiring and watch. It covers CMP-6's carry-overs, the watch loop, the companion gate's feed and CMP-8b's `ConfigSink`.
- **CMP-5g-2:** the guided endpoints and their records (`guided.rs`, runner: not in -1). Add a detected companion or a URL, paste a key or temporary password, see the plan, then confirm, apply and hand over.
- **CMP-5g-3:** starting managed companions at serve. It covers `Supervised` behind `manager::monitored`, Q18's `companions.<id>.egress` and real restart, logs and regenerate. Until it merges, the managed routes keep answering `not_wired`.

## CMP-5g-1

### CMP-6's carry-overs
1. **`Service::installed` reads the journal.** It's `state::load(<data>/companions/<id>)` with an installed version, read-only (runner-approved). It no longer uses the snapshot, which detected companions now join. Inside a container it's always false. Tested: a journal that recovery hasn't published counts, and a snapshot whose journal is gone doesn't.
2. **The provenance marker** comes with CMP-5g-2's records, which write it when you paste a credential. The reveal will then require `generated`.
3. **The template data guard's positive path is tested.** On a native install, the resolved data folder is in the generator's input. Inside a container it isn't.
4. **`manager::field_of` is public** (doc only, no behaviour change), and the binary's copy is gone.
5. **I1 through the real generators:** no catalogue pin lands in this slice, so the field naming stays tested with a fake generator (`blame`). The first pinned image adds the end-to-end case.

### Guided records
Their format is runner-approved (2026-11-09): `companions.<id>.target`, `.origin` and `.provenance.<field>` `settings` rows, read strictly. They land with CMP-5g-2, which also documents the format here. Until then, the watch and the gate take the companions you added as plain `(id, target)` pairs (`companion_wiring::Added`), and serve starts with none.

### The watch (`crates/companions/src/watch.rs`, tested in `crates/companions/tests/watch.rs`)
- **Q7's cadence:** each companion you added is checked when it's added or its target changes, then every 30 s. The check uses CMP-8a's `Health` adapter and the guarded client only, on its record's target (Q12).
- **Debounced, per Q7's "3 failures in a row":** a companion seen healthy stays healthy until three checks in a row fail. That's because CMP-10 restarts a plugin on every flip it's sent. A first result counts at once, and a changed target starts the debounce again.
- **A change of list checks only what's new or moved;** the full round is the 30 s tick, whose first comes a whole period after the start's round. So edits to the list never hurry another companion's debounce (self-review I4).
- **Reports:** `Healthy`, `Unhealthy` (it answered wrongly) or `Missing` (nothing answered). A companion without a health adapter (gluetun) isn't listed.

### The companion gate (`crates/lodestar/src/companion_wiring.rs`; CMP-10's contract)
- **`PipelineConfig::companions` is now `Some`** whenever companions are on for the run (`companion_wiring::gate`). **With companions off** (a fixture, a held lock, a bad catalogue), it stays `None`, which turns the gate off: the sources run as before (runner's condition; `gate`'s test, and `requires`' own tests of `None`).
- The gate holds `Unknown` until the feed's first snapshot. That's sent once the sources' ops exist, so gated plugins wait until then: it fails closed.
- **What it sends:**
  - every companion Lodestar installed, healthy only when its last check passed. Not checked yet counts as unhealthy: after a restart that's every installed companion, until CMP-5g-3 starts them;
  - every companion you added, as the watch sees it, with a missing one unlisted, so its dependents show "Needs X";
  - `external_client`: an `integrations.clients` entry other than `lodestar-qbittorrent`;
  - `external_indexer`: the Prowlarr source is on, and the address in its saved config (`sources.config.prowlarr`'s `url`) isn't a companion's. A companion's is a record's target, or loopback on the catalogue's WebUI port for an installed Prowlarr. The manifest lists no endpoints for the source, so `/sources`' `endpoints` can't be used (self-review B1).
  - a watched companion counts only at the target it's added at now: a removed or moved companion's last result never carries over (self-review I3).
- **When it updates:** on any change to the installed companions, the watch, the integrations or the records, and every 30 s for the Prowlarr source being turned on or off.
- **Existing setups keep working** (runner's condition, clarified 2026-11-09): with companions on and nothing installed, a download client you set up yourself counts as `external_client`, and a Prowlarr source pointed at your own Prowlarr counts as `external_indexer`. Either meets its source's need from the first snapshot (`your_own_setup_keeps_working_with_companions_on`).
- **"Needs prowlarr" and "Needs qbittorrent" with nothing configured are accepted** (runner): with no address or client saved, those sources couldn't run anyway.
- **The gate's on/off choice is `companion_wiring::gate(companions.as_ref())`,** which `services.rs` calls with the run's companions, so the off case can't be mistyped there (#645's review, M9). The runner accepts it as correct by construction; no serve-path test is needed.
- **A failed read of the Prowlarr source keeps what the gate last knew** (a busy store or a lock error never stops a working source). The first failure of a streak is logged as `companions.config_failed` (setting `gate.prowlarr_address`, reason `read_failed`), with no value.
- **Addresses compare as parsed URLs:** scheme, host and port, with the scheme's default port filled in, then the path without a trailing `/`. One that doesn't parse equals only itself.
- **If the watch stops,** the feed logs `companions.install_failed` (step `watch`, reason `stopped`) and ends. The gate then reads as unknown and holds gated sources.
- **The window until CMP-5g-3 merges** (runner's condition): a companion Lodestar installed isn't started yet, so it counts as unhealthy, and a source that needs it waits. Its status says why in plain terms, through CMP-10's `needs` on `/sources` (`{"companion": "qbittorrent", "state": "unhealthy"}`), never as an unexplained stall. Nothing in this window is released.
- **A failed start** (the guarded client couldn't be built) is logged as `companions.install_failed`, step `wire`, and leaves the gate `Unknown`.

### `ConfigSink` (`companion_wiring::Sink`; CMP-5g-2 calls it)
- **qBittorrent:**
  - It becomes the `integrations.clients` entry `lodestar-qbittorrent` ("qBittorrent (Lodestar)"), through the settings registry's own save, so its validation and sealing apply.
  - The rest of the list is saved as it is, each other client without its password, which keeps the saved one.
  - The address is the target's, and the user name, password and category come from CMP-8b's entry.
- **qBittorrent's list is read right before the save,** on the save's own thread, so a save you made meanwhile isn't overwritten with an old list (self-review I6). The registry's save isn't conditional on a revision, so two saves in the same instant can still race; the window is the time between that read and the save.
- **The id `lodestar-qbittorrent` isn't reserved:** a client you name that is treated as the managed one (not external) and replaced by a hand-over. Ids are yours to choose; the UI (CMP-9a) can warn.
- **Prowlarr: the key is replaced, then the address** (runner's call on #645's delta review, option a, "replace"). It replaces the security review's earlier order, which removed your key first. Removing an Account source's last credential turns it off for good (`Control::update_credentials`), and the consent gate doesn't let it be turned back on. So that order disabled a running source even after a successful hand-over.
  1. The companion's key replaces the one you saved, so the source never loses its credential and stays on.
  2. Then the source's config gets the companion's address, keeping any other value you saved, such as `agents`.
  3. If step 2 fails, the companion's key is removed, which turns the source off: it fails closed. **Your own key is gone after a failed hand-over**, and you enter it again. A failed removal is logged as `companions.config_failed` (setting `lodestar.settings`, reason `rollback_failed`), never with a value.
  - **Every write applies at the next start**, and the source shows `restart_required`, after a successful hand-over too.
  - **Accepted risk, wider than one window** (#645's delta review, P-a, P-c):
    - A saved address applies only at the next start, but the companion gate restarts the plugin on every health flip, and each run reads the key from the store afresh. So **until Lodestar restarts, even after a successful hand-over, the companion's key can go to your own address**.
    - **Step 1 can fail after it has saved:** `update_credentials` saves, then reads the source back. If that read fails, the companion's key stays beside your own address. It's left as it is, because removing it could take your own key on a real failure, and it's logged as `companions.config_failed` (reason `key_not_confirmed`), never with a value.
    - Low severity: nothing in this build triggers it, since the Prowlarr plugin isn't registered and its settings can't be saved. **`X-prowlarr-settings` must handle it**, for example by making the address and key apply together, or by holding the plugin until the restart.
  - **Tested over a real `Control`** with an enabled source: a hand-over leaves it on with the companion's key, and a failed address write leaves it off with no key. The order and the logged failed rollback are tested over a recorder.
  - **Not tested here:** the thin adapter from those writes to `OpsApi`; CMP-5g-2's confirmation tests drive it.
- **After a hand-over the Prowlarr source shows `restart_required`** (runner, 2026-11-09, option a). This corrects CMP-10's contract in `2026-11-08-CMP-5.md`, which said the source "is restarted or its config supplied again". A saved source setting applies at Lodestar's next start, as for any saved source setting, and nothing reloads one source live. Reloading one source live is a follow-up candidate the runner logged; it isn't queued.
- **Tested here:** the qBittorrent save through a real registry (your client keeps its saved password; the managed entry is added, then replaced), and the Prowlarr config merge. **Not tested here:** the thin adapter from those source writes to `OpsApi`; CMP-5g-2's confirmation tests drive it end to end.

## CMP-5g-2

### The routes (`crates/api/src/companions_guided.rs`; runner-approved API, 2026-11-09)
All are admin only (a session; an API key or a proxy header gets `401`), same-origin JSON writes, and `503 companions_unavailable` when companions are off for the run.
- **`POST /companions/detect`:** runs every fixed probe (Q12: loopback and, in a container, the catalogue's container names, on their catalogue ports) at once, each within `Limits::PROBE`, under an overall cap of 15 s. Each companion is listed once, at the first target in probe order that answered. A second detection while one runs is `409 busy`. Nothing is written.
- **`POST /companions/{id}/target`:** `{kind: loopback|container, port}` or `{kind: url, url}`. A catalogue target takes only the companion's own internal ports, and a container name only inside a container. A typed address goes through the egress rules: CMP-0's `EnteredUrl` (`http`/`https`, no user name or password, query or fragment), then `net::check_url` with `NetPolicy::download_client()`, which allows loopback and the private LAN and refuses link-local, cloud metadata and unspecified addresses (`409 address_refused`). A name's DNS answer is checked at connect by the guarded client, which also follows no redirects (CMP-8a's tests). Detection must then find the companion there (`409 not_detected`); only then is the target row written.
- **`POST /companions/qbittorrent/paste` `{value}`:** sealed at once (`credentials::accept_pasted`), marked `pasted`, answers `204`. The API bounds it before the binary sees it: 1–128 bytes, no control character (`400 bad_value`, field `value`). The value is never in a response, an error body, a log line or the OpenAPI document (its example is a placeholder), and `CompanionPasteRequest`'s `Debug` hides it. Nothing in the API logs request bodies.
- **`POST /companions/qbittorrent/plan`:** the settings Lodestar would change, by name. A POST because it signs in with the temporary password. At most one a minute: `429 rate_limited` with `Retry-After` (never `0`).
- **`POST /companions/qbittorrent/confirm` `{settings}`:** see below.
- **`POST /companions/{id}/guided/forget` `{confirm: "<id>"}`:** as CMP-6's removal (no DELETE body). It deletes the target, origin and provenance rows and the credential row, and returns their keys. `credential_in_use` is true when the deleted credential was a generated one, which is, or may be, the password qBittorrent uses now; the route's description says to reveal it first (#653's review, B1). The `integrations.clients` entry stays. A companion Lodestar installed, or is installing, is refused.
- **Prowlarr waits for `X-prowlarr-settings`** (runner): its target, paste, plan and confirm answer `409 handover_later`, and so does gluetun, which has no hand-over. Prowlarr's detection and health are unchanged, so it still shows in detection's list. The earlier note that "CMP-5g-2's confirmation tests drive" the Prowlarr adapter to `OpsApi` end to end moves to that slice.
- **A companion Lodestar installed** is refused by every guided step (`409 installed`): it's managed on its own. **One it's installing** (its journal holds an operation and no installed version) is `409 busy`, so no guided step races CMP-5's first install (#653's review, L1). An install that starts after the check isn't stopped by it; the window is one request.
- **A companion already added and confirmed** refuses a new target, paste, plan or confirmation (`409 already_added`): you forget it first. So its record never points somewhere Integrations doesn't, and its generated password, the one qBittorrent takes, stays the one you can reveal (self-review I1).
- **One guided change at a time:** target, paste, plan, confirm and forget share one lock, and a second change while one runs is `409 busy`. Detection has its own (self-review B1).

### The records (`crates/companions/src/guided.rs`)
- **Format** (runner-approved): `settings` rows, no migration, nothing under `<data>/companions/<id>/`.
  - `companions.<id>.target`: `{"kind":"loopback","port":N}`, `{"kind":"container","port":N}` or `{"kind":"url","url":"…"}`, with the URL as you typed it.
  - `companions.<id>.origin`: `confirmed` or `guided`. This version writes `confirmed` at the confirmation; `guided` is kept for CMP-9a's Docker and Unraid screens.
  - `companions.<id>.provenance.<field>`: `pasted` or `generated`, for the companion's own field only.
- **Read strictly:** each row into its closed type, at most 4 KiB. Anything unparseable, unknown or out of place (a port the catalogue doesn't list, a container target outside a container, another field) reads as no record. A stored URL isn't checked against the egress rules again at read; the guarded client checks every connection.
- **A record** is a target and an origin. A target alone (added, not confirmed) is no record: it isn't watched, and the gate doesn't count it.
- **At serve,** the records are read once and the watch starts with them; every confirmation and forget sends the watch the records as stored then.

### Reveal (CMP-6's gating, unchanged)
A credential is revealable when Lodestar installed the companion (its journal) or its provenance is `generated`. A pasted one never is. Tested over the real `Service` (`an_added_companions_credential_reveals_only_when_generated`).

### The confirmation, step by step
1. **One at a time** (`409 busy`), and **one per plan:** the last plan's settings are taken, and a body that doesn't echo them exactly is `409 confirmation_mismatch` before qBittorrent is signed in to again. A mismatch uses the plan up, so you plan again (after the minute).
2. The temporary password is replaced: CMP-3's `replace_temporary_password` issues the generated one, which is **stored durably first, then marked `generated`**. A crash between the two leaves it marked `pasted`, which is never revealed.
3. **The plan is made again,** signing in with the temporary password only, and must equal what you confirmed. If it differs or fails, nothing has been applied, so the temporary password is sealed and stored again and marked `pasted`: you can look again and confirm.
4. CMP-8b applies it (`Origin::Guided`) and hands it over through CMP-5g-1's `Sink` as the `lodestar-qbittorrent` client.
5. `origin` is written `confirmed`, the records go to the watch, and the companion's detail is returned.
- **Once the apply has started, the generated password stays,** marked `generated`, with no `origin` row, whatever fails after: CMP-8b writes the password first, so qBittorrent may already have it (#653's review, B1).
  - **Paste is refused then** (`409 generated_pending`, pointing to reveal): pasting would drop the only copy of a password that may be live, and qBittorrent no longer accepts the temporary one.
  - **A retry signs in with the generated password:** plan and confirm see `generated` without `origin` and run as a companion you confirmed (`Origin::Confirmed`, the stored credential), with nothing to replace. They finish the apply and the hand-over and write `origin`. No temporary password is needed.
  - **If qBittorrent never took it** (the apply failed before the password write), the retry's sign-in is refused (`companion_unauthorized`). You forget the companion (its answer says the credential was generated) and add it again with the temporary password, which still works.
- **The write orders are the safe direction both ways:** paste writes `pasted` before the credential; the confirmation writes the credential before `generated`. With the guided lock, no other request writes in between, and the reveal reads the provenance and the sealed row in one query. So neither a crash nor a concurrent request leaves a pasted value revealable (self-review B1).
- **A crash, or a dropped request, after the generated password is marked `generated` but before the apply** is the same state: a retry is refused at sign-in, and you forget and add it again (self-review P5).
- **A failed restore** of the temporary password is logged as `companions.config_failed` (setting `guided`, reason `restore_failed`), never with a value. A failed apply or hand-over is logged by CMP-8b's own `config_failed` line (self-review I3).
- **The last plan is forgotten** when the target, the pasted password or the record changes, so a confirmation can't echo a plan made from other rows (self-review P4).

### Choices made here
- **The guided sign-in uses qBittorrent's own `admin` account,** not CMP-3's default `lodestar`. The temporary password qBittorrent prints is for `admin`, so `lodestar` could never sign in with it. The hand-over keeps `admin` and changes only the password. Renaming the account isn't in CMP-8b's plan; a later slice can add it. Found while writing the flow test; without it every real confirmation would have failed.
- **No refused sign-in per flow with the right password** (#653's review, L2). A guided plan holds the temporary password as the credential too, and CMP-8b now signs in once when they're the same, so a wrong one costs one refused sign-in a plan, not two. Plans name settings, never values, so the confirmation's re-plan also uses the temporary password, and the apply tries it first. **After three refused sign-ins in a row** across plans and confirmations, both answer `409 sign_in_refused` without asking qBittorrent, before its ban at five. One that signs in, or forget, resets the count; so does a restart, since qBittorrent's own count starts again when it restarts too.
- **The pasted value's bound is the API's** (1–128 bytes, no control character), so the binary never sees an over-long value or a terminal escape. Unicode format characters (bidi overrides, zero-width) aren't control characters and pass; they can't escape a terminal (self-review P6).
- **`Retry-After` rounds up,** so a client that waits as told isn't refused again (self-review P1).
- **Detection's cap is a field of `Guided`** (15 s in the shipped build), so the tests can shorten it without a paused clock: tokio's `test-util` stays out of the binary.
- **Refusal codes are new for these routes:** `not_detected`, `address_refused`, `handover_later`, `installed`, `no_target`, `no_temporary_password`, `bad_value`, `busy`, `rate_limited`. An adapter's own codes (`companion_unauthorized`, `companion_unreachable`, `companion_protocol`, CMP-8b's refusals) pass through as `409`.
