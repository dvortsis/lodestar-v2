# X-search01-fix decisions

- **SEARCH-01 (blocking, search; the indexer's document builder) fixed.** Its detail is held under `docs/security/v1/README.md` §5 until a release with the fix is published. This file says only what the code now does.

## Calls
- **A torrent's extensions are gathered in one pass** (architecture §8, the `ext` field). `distinct_extensions` keeps each extension once, in the order first seen, and looks up what it has seen in a set. The cost of building a document's extensions is linear in the number of files.
- **At most 1,024 distinct extensions are indexed per torrent** (`MAX_EXTS`), the first in file order. An extension is at most 10 ASCII letters and digits, so the `ext` field of one document holds at most about 10 KB of terms.
- **What a search sees:** nothing changes for a torrent with up to 1,024 distinct extensions, which is every ordinary one. For a torrent with more, everything that reads the `ext` field sees the first 1,024 only: `ext:`, a lone `file:(ext:…)` (which is answered from the same field), the `ext` facet's counts and `ext:` suggestions.
- **The file index is unchanged, and not capped.** Each file it covers keeps its own extension there, and `file_ext_bucket` on the torrent's document keeps one term for each covered file's extension and size bucket. So a compound clause such as `file:(ext:x size:>1GB)` can still find a torrent past the cap by an extension that `ext:x` alone no longer does. A torrent can only pass 1,024 distinct extensions with more than 1,000 files, where the file index covers the larger and the media and software files only.
- **No schema change and no rebuild.** Documents written before this hold the same terms unless they had more than 1,024 distinct extensions; those keep what they have until they are next written.
- **Which are kept is fixed by file order:** the torrent's files are read in the order the store holds them, so a rebuild indexes the same 1,024.
- **Why 1,024** (the runner's performance call, §2.26, flagged to the owner under §2.19): far above any real collection's variety, and small enough that one document's `ext` field stays a few kilobytes (`file_ext_bucket` is bounded by the covered files, as before). It is not an owner-set number.

## Tests (`crates/search/src/doc.rs`)
- `distinct_extensions_are_each_kept_once_in_file_order`: against a plain reference, on generated names that repeat, differ only in case or have no extension.
- `distinct_extensions_stop_at_the_cap`.
- `the_extension_first_seen_last_is_the_one_left_out`: at the boundary, 1,024 are all kept; of 1,025 the one first seen last in file order is left out.
