# WK-11b decisions: lease reconciliation after a worker reconnects

Corrects the drift WK-11 detects (`docs/decisions/2026-11-11-WK-11.md`, "Lease counts after a replay"). Brief: runner, 2026-11-12. Affects §19.2, §19.3 and §19.6.

## The problem
- **A worker can stop knowing a lease the coordinator still has on record for it.** Examples: the `Grants` message was lost with a connection, the worker restarted, or the coordinator restarted and restored the lease under a new token.
- **Heartbeats renew all of a worker's leases** (V6-cluster2), so such a lease never expires while the worker lives, and its key is never fetched.
- **WK-11 only counts it** (`worker_spool_lease_drift_total`). This slice gives it back.

## The message (protocol 1.1)
- **`ToCoordinator::Holding`**, worker → coordinator: `round` (never 0), `part`, `last`, and up to 8,192 `(key, token)` pairs (`MAX_HOLDING_BATCH`, about 240 KiB, well under the 1 MiB frame).
  - A list goes in at most 256 parts (`MAX_HOLDING_PARTS`), so 2,097,152 leases at most (`MAX_HOLDING`). That's twice the largest pool an assignment allows (`MAX_POOL_CAP`), to cover keys held plus results out.
  - A worker holding more sends no list. A partial list would give back leases it holds.
- **`ToWorker::Reconciled`**, the answer to the last part: `Done { returned, unknown, leases }` or `Refused`. Parts before the last get no answer.
- **Pairs, not bare tokens.** The coordinator's table is keyed by info-hash, so each pair is checked with one lookup, holder and token together.
- **The count is checked before anything is allocated.** `HeldList` has its own `Deserialize`: postcard states a sequence's length up front, and a length over the cap is refused there. `validate` checks `round != 0`, `part < MAX_HOLDING_PARTS` and the length again.
- **The fuzz target needs nothing new.** `cluster_frame` already decodes every `ToCoordinator` and `ToWorker` variant through `decode_to_coordinator` and `decode_to_worker`, and its `-malloc_limit_mb=8` run checks the cap.

## When it's sent
- **Only when WK-11's check finds a difference.** At the upkeep after a replay drains, the session asks for a heartbeat as before. If the counts differ, it asks the work for its list (`Work::holding`), sends it (`WorkerSession::holding`) and records the answer (`Work::listed`, counted in `worker_spool_lease_reconcile_total`).
- **The list is every lease the worker still holds:** keys held, and every out entry its `WorkerLeases` keeps (a result sent, spooled or accepted under that token, finished or not).
  - **Why the finished entries too:** the runtime marks an accepted batch's entries committed before its `Fetched` report goes out. A list built in that gap, without them, could reach the coordinator before the marks. Listing them costs only an `unknown` count once their commit lands.

## What the coordinator does
- **It gathers the parts** for that worker's current session: one round at a time, in order, from part 0.
  - It keeps only listed tokens that worker holds, so the gathered set is never bigger than the worker's share of the lease table.
  - A part out of order, or of a round the session didn't start, spoils the round. The round is answered `Refused` once, at its last part.
  - A new session drops a half-gathered round.
- **On the last part, under the fleet lock** (so no grant on the session lands in between), the worker's leases that the list left out go back for re-grant, except:
  1. **leases handed to it on the listing session itself.** Each lease records the session it was last handed to its holder on: a grant, a re-grant (marked when it's reserved, before the store check), or the holder's own claim answered with the lease. One of these may still be in the session's outgoing queue while the worker builds its list. The leases a worker can have lost all came from earlier sessions.
  2. **leases marked fetched** (X-wk-fetched-lease): the result is in the coordinator's hands, and the commit ends the lease.
  3. **a late result's lease** (`restore_if_free`, plan Q7): the coordinator holds it for a result it already has. It's pinned and never returned.
- **Returned is the expiry path.** The key waits for a re-grant with its cohort, sources and finder kept. It's not a loss, so nothing is counted twice, and it's not a new harvest. Its old token is stale from then on.
  - The server runs a re-grant at once, so the key may go straight back to the same worker under a new token, which it now knows.
- **Listed but not on record:** counted as `unknown`, never created. Examples: another worker's lease, a lease that ended while the list travelled, or a made-up token.
- **Holder-checked.** Every check is `holder == sender && token == listed token`, so a list can only give back its sender's own leases. Another worker's lease is never touched, listed or not.
- **Refused, changing nothing,** for:
  - a paused worker: WK-14's pause, which WK-13's quarantine and purge build on;
  - a session that is no longer current (replaced, or revoked: a revoked worker's leases were evicted already);
  - the built-in worker.

  A draining worker may still reconcile.
- **Counted** in `cluster_lease_reconcile_total{result}` (`FleetSnapshot`'s `reconcile_returned`, `reconcile_unknown` and `reconcile_refused`).
- **Cost:** the last part scans the lease table once under the authority's lock, as each heartbeat's lease count already does. One round per worker per heartbeat interval is carried out; another within it is refused. A half-gathered round is dropped when its session ends.
- **Liveness:** the worker sends a list's parts back to back. A list of many parts sent to a coordinator that isn't reading can stall until the send timeout ends the session, and the next session lists again.

## Races
- **The list is a snapshot.**
  - A lease committed before the list lands stays committed. If it was listed, it's counted `unknown`.
  - A listed lease committed after the list lands commits as usual: it was kept.
- **A result in flight while the list is built** is listed (its out entry), so its lease is kept and its commit counts once.
- **A returned lease reported later** is a stale report: no loss counted, `cluster_stale_reports_total` +1. A result under its old token is a late result under WK-9: stale while the key is in flight again.
- **A `Fetched`-marked lease is never returned.** The runtime sends `Fetched` from its own task, so nothing orders it before the list, and a session lost in between loses it. The list covers that gap itself: an accepted batch's leases stay in `WorkerLeases` as finished out entries for the 180 s grace, including a replayed batch's, which had no entry until its commit made one (self-review). A writer lagging past that grace is the trade-off X-wk-fetched-lease already describes.
- **Accepted risk:** a loss report sent on an old connection that reaches the coordinator after the new session's list. The lease came from an earlier session, so it's returned, and the late report is then stale. The key is fetched again. Nothing is lost or counted twice.

## Compatibility
- **`PROTOCOL_MINOR` is 1** (`MINOR_HOLDING`). The new variants come last in both enums, so every older message keeps its postcard tag (tested).
- **A newer worker and an older coordinator:** the worker sends a list only when `Welcome.minor` is at least 1. Otherwise `holding` returns `Ok(None)` and sends nothing. An older coordinator would fail to decode an unknown variant and close the session, so the worker never sends one.
- **An older worker and a newer coordinator:** the worker never sends `Holding`, and `Reconciled` only ever answers one. Nothing changes for it, and its drift stays as before WK-11b.
- **The major version is unchanged.** Until WK-G freezes protocol 1.0, minors may add messages this way (plan Q11).

## Refinements flagged (§2.19)
- **Only leases delivered on an earlier session are returned.** That's narrower than "every unlisted lease", and it's what makes the list race-free against grants still in the session's queue. A grant the worker lost within one session isn't corrected here.
- **The list includes finished out entries.** That's wider than "the leases the worker holds", for the race above. It shows up only as `unknown` counts.
- **`Work::holding`/`listed` hooks.** The session gets the list from the work, as WK-11's `reconcile`/`reconciled` hooks get the count.
