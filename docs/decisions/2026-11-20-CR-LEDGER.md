# CR-LEDGER decisions

The lookup ledger: counters and histograms only, under r5 "Path to 100" (`docs/build-plan.md` §0.5, `docs/decisions/2026-11-20-path-to-100.md`). Series and identities: `docs/metrics.md`, "Lookup ledger".

- **The ledger counts a peer request (one slot), not a family leg.** CR-0's `W`, `q` and `y` are per admitted lookup, and a slot covers both legs (CR-ADM). A request ends once, when its last leg finishes or at shutdown. Harvest-only requests (`Dht::get_peers`, unused in production) share the slots, so they're counted too.
- **Residence and time to first values start when the request leaves the queue, not at admission** (the brief said "from admission"; flagged to the runner). That's the same start as `dht_peer_lookup_seconds_total`, so the two stay comparable. An admitted request waits for the next maintenance tick (up to 1 s by default, longer while lookups are parked for the bootstrap), holding its slot. So `W` here is run time, a few percent under the slot hold. Starting at admission would mean carrying an `Instant` in the queue entry, whose tuple other slices' tests destructure, so it was left for a follow-up if the runner wants it. Requests dropped from the queue aren't in the ledger: `dht_peer_queued_dropped_total` already counts them.
- **End reasons are taken from the code's real exits,** with this precedence: `cancelled` (the same check that counts `dht_peer_cancelled_total`), `deadline` (the request's `expired` flag), `query_cap` (a leg finished with its 64-query budget spent and its closest set not converged), then `values` or `no_values`. `shutdown` covers requests still running when the actor stops; it's recorded after the permits are returned.
- **Values are the request's distinct peers, at most 64.** The two legs can return the same peer, so summing the legs would double count. Streaming requests now also merge each finished leg's peers into the request's set, which only the ledger reads. That costs at most 64 addresses per streaming request, once per leg end, not per packet. Nothing a stream sends changes.
- **Time to first values is observed when the request ends,** so `_count` plus `dht_lookup_without_values_total` equals the requests ended. The clock is the request's own start, and the value is fixed at the first reply with values that passes the endpoint policy.
- **Query purposes are the code's own:** `peer_lookup`, `hint`, `scrape`, `bootstrap`, `refresh`, `explore`, `sample` and `ping`. They're counted where `dht_queries_out_total` is, so they sum to it exactly. There's no `announce` purpose, because the actor never sends `announce_peer`. To label a hinted query as it's sent, `send_hint` now calls `admit_query` and `send_admitted` itself, as `dispatch_query` did, and the pending query is marked hinted at insert instead of just after. The packet, its timing and its accounting are unchanged.
- **Hint outcomes are per hinted query, plus `guard_skipped`** for a hint the per-IP guard refused. That refusal is also in `dht_hint_fallbacks_total`, so `values` + `no_values` + `unanswered` = `dht_hint_queries_total`.
- **`dht_lookup_slots_occupied` counts running requests only, never queued ones** (runner, after reviewing CR-COL-5: r5.1's A1 check reads it). The queue has its own gauge, `dht_lookup_queued`. Both are set on the tick, next to `dht_peer_active` and `dht_peer_queued`, and the capacity once at start. The exact average of running lookups is the rate of residence (Little's law), so the gauge is a convenience.
- **No behaviour change.** Rates, the outstanding cap, `LOOKUP_DEADLINE`, the 64-query cap and `ALPHA` are untouched. The hot path adds one relaxed atomic increment per query sent, plus one map lookup to classify a lookup's query.
- **New files.** The counters are in `crates/dht/src/node/ledger.rs` (inside `Stats`, which lives in `node/mod.rs`), and the actor tests are in `node/ledger_tests.rs`, following `hint_tests.rs`.
