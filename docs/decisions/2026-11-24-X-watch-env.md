# X-watch-env decisions (#1104)

`LODESTAR_WATCH_DIR` and `[watch] folder` for the watch folder (UP-1, `docs/decisions/2026-11-12-UP-1.md`; the runner named this follow-up on 2026-11-12).

- **The file key is `[watch] folder`,** the setting's own section and field name, like every other backed field (`content.show_adult`, `dht.intensity`). Only `folder` gets a key and a variable; `after` stays app-only, because the slice names only the folder and Docker users need only the path.
- **Layering is the registry's, unchanged** (`settings/README.md`): default, then the file, then a value saved in the app, then the variable. The variable makes the field read-only in the app (`409 set_by_environment` on a patch, the form's "Environment variable" note) and never erases a saved value, which applies again once the variable is removed. Nothing in the registry was changed for this: the field gains `.file("watch.folder").env("LODESTAR_WATCH_DIR")`, and `from_config` / `apply` read and write `Config::watch`.
- **A blank `LODESTAR_WATCH_DIR` counts as unset,** in both the value and `Layers::env`. An Unraid template field left empty passes the variable with no value; counting that as set would turn the watch off and lock the setting with no way to change it in the app. `LODESTAR_DHT_WITNESS_DIR` already ignores an empty value the same way.
- **Validation is the setting's own code, split where the setting already splits it,** with no second copy of the rules:
  - **At start (`Config::load`):** the setting's load-time check (`Watch::check("folder")`: empty or absolute). A relative value stops Lodestar with a clear error that names the variable or the key (`LODESTAR_WATCH_DIR: Use a full path, such as /watch or D:\Torrents.`), the same as any value that can't be parsed (`LODESTAR_HTTP_BIND`, `cluster.*`). The value isn't quoted, as the watch's fixed causes never name the path.
  - **When the watch applies the folder and on every poll (`watch`, `folder_problem`):** there, a directory, not a link, and not the data directory, inside it or holding it, resolved (`..` and links included). A problem pauses the watch with its reason in `watch.disabled`, exactly as for a saved folder; the folder is never read.
  - **Why not refuse those at start too:** `Config::load` runs before the Windows service sets its data directory (`windows::service::default_data_dir_unless_set`), so a data-directory comparison there would use the wrong folder. `healthcheck` also loads the config at every interval, and stat-ing a hung network share there would mark the container unhealthy (the watch already looks at the folder on the blocking pool for this reason, rv-765 O3). And a share mounted after start keeps working, as a saved folder does (rv-765 B1). So nothing is half-applied: either the start stops on a malformed value, or the value is taken and the watch, which re-checks everything on every poll, refuses it with its reason.
- **The user guide** gains "Add a watch folder (optional)" at the end of §2.4, covering Compose and Unraid, marked newer than v0.5.1, recommending a folder of its own outside the data folder mapped as its own volume at `/watch`. The variable also joins the table in `docs/operations.md` and the extra-variables notes in appendix B.
