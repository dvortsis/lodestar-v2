# RX-1 decisions

Regex search: the trigram producer, `/…/` queries, the prefilter and the time-budgeted verify (plan `docs/plan/2026-11-05-v07-m7.md` RX-1; architecture §8, §3). Builds on RX-0 (`crate::regex`, `docs/decisions/2026-11-11-RX-0.md`). Choices the plan left open are below; the ones marked **(refinement)** are flagged to the owner (§2.19). **The trigram switch is not in this PR** (see "Left for a follow-up"), and the runner re-split the size budget (see "Size").

## The producer
- **`name_trigram` generation 1** (`population::GENERATIONS`): every existing index walks once to fill it, through SB-6's population contract. Until the walk is done, a `/…/` clause doesn't prefilter (`Cx::trigrams` is false unless the field is `Ready` in the snapshot), so nothing is lost mid-walk, only slower.
- **Trigrams of the name's first 96 bytes, plus a marker term on longer names** (plan Q10 (a)): `doc::trigram_tokens`, `TRIGRAM_PREFIX_BYTES = 96` (cut back to a character boundary), `TRIGRAM_MARKER = "\0lng"`. The marker is four characters, so no gram equals it. Every prefilter is `marker OR plan` (RX-0's note), so a match past the prefix is never lost. The grams come from `trigram_analyzer` on the stored `name` itself, so they fold exactly as RX-0's planner does.
- **Pre-tokenized**, not the field's tokenizer: that's the only way to add the marker and the cap. The field's registered analyzer is unchanged, so `TOKENIZER_VERSION` stays.

## Queries
- **`/…/` and `name:/…/` are the same clause** (`Node::Regex`): §8's regex is "on full name", and there's no other text field a regex could run on cheaply (paths have no stored text in the index).
- **Lexing:** a `/` at the start of a term opens a regex that runs to the next `/` not escaped by `\`; `\/` is a slash in the pattern, every other escape is passed through to the regex parser. An unclosed or empty `//` is a parse error at the literal. `to_query` writes `/` back as `\/`, so stored text parses back to the same node.
- **Slashes delimit a regex only where one can start and end** (runner call, general review item 8): the closing `/` must be followed by what ends a word: ASCII whitespace, a parenthesis, a quote, `|` or the end of the query. The opening `/` must be followed by something other than whitespace, `)` or the end of the query (a pattern may start with `(`: `/(720|1080)p/`). Starting and ending exactly where a word could keeps a plain word from rendering back as a pattern: the `query` fuzz target found `/or/(x)`, which lexed as a word but rendered as `/or/ x`, and a lone `/` at the end would render as an unclosed one. `tests/regex.rs` runs the fuzz target's round trip over slash-heavy text. Otherwise the text lexes as plain words, so `tv / movies / 1080p` and `/usr/bin` are words. The opening rule is this PR's reading: with only the closing rule, `tv / movies / 1080p` still held the regex ` movies `. A pattern that starts with whitespace is written `/[ ]x/`. Whitespace here is ASCII, as the lexer splits on it. The suggest proptest's `in_regex` excuse now covers only words inside a literal's span.
- **At most 4 `/…/` clauses per query** (`query::MAX_REGEX_CLAUSES`, S8-10). The parser refuses a fifth at its span with code `query_syntax`, `reason` `regex_too_many` (`ParseError::reason`, sent by the API as the error's `reason`) and the message "Use at most 4 /regex/ terms in one search." Refused patterns now carry their RX-0 code as the `reason` too. The code stays `query_syntax` because the web highlights the span only for that code. At compile time a stored node over the cap matches nothing and verifies nothing (`compile_at`). The API's posted `ast` gets the same error as typed text. `percolate` lists a saved search over the cap under `failed` and logs `search.percolate_search_failed`, so it keeps its watermark instead of silently matching nothing. `Node::has_regex` looks inside `file:(…)` as well, although the parser refuses a regex there.
- **Errors keep RX-0's stable codes:** a refused pattern is a `ParseError` at the literal whose message ends with the code (`regex: … (regex_too_long)`), so the UI's error line shows the reason and place (UI review 02 §5.2).
- **Not inside `file:(…)`** (`files::file_clause_ok` refuses it): the file index stores no names to verify.
- **Filter rules refuse regexes** (security review): `Node::mentions_provenance` now counts `Node::Regex` as search-only, as it does `sig:`, so the API refuses a rule, exception or override query with one (`provenance_in_rule`, message updated in `api/src/filters.rs`) and stored ones are skipped on load (`filter/src/load.rs`). Otherwise `-/x/` in an exception would match, and exempt, every torrent. In the judge, `Node::Regex` still matches nothing (`filter/src/matcher.rs`, `matcher_reference.rs`), only to keep the match exhaustive.

## The verifier (`regex_verify.rs`)
- **`regex` `=1.13.1`**, the version already in the lockfile through tantivy (plan: "RX-1 `regex` with its size and DFA limits"). It compiles `Pattern::verify_pattern()` with Unicode on, `size_limit` 10 MiB and `dfa_size_limit` 2 MiB (its defaults, spelled out so an upgrade can't move them). A pattern it still refuses matches nothing.
- **Re-checked at compile time.** `Node` is `Deserialize` (saved searches), so a stored node isn't trusted: the clause re-runs `crate::regex::parse` with every limit, and a refusal matches nothing. Planning and compiling are lazy (first use), since the compiler may build a clause and drop it.
- **The stored `name` is read from the docstore** in document order (a 4-block cache per segment), as §8 planned: no SQLite reads per candidate.
- **The time budget: 2 s per search** (`VERIFY_BUDGET`, S8-11 and general review item 1). Every clause of one search verifies against one deadline, started by the search's first regex compile (`CancelToken::regex_deadline`), so planning and compiling count. The deadline lives on the request token's scope: the root token, or a `CancelToken::regex_scope`. `with_budget` children share it. A lease keeps its search's deadline, and later passes over it that compile their own clauses (facet variants, the adult-facet pass, recovery counts) run under `Lease::regex_token`, which is `CancelToken::regex_scope_until` that deadline. So they spend what's left of the search's 2 s even when `/facets` is a later request, and never get a fresh budget. A `/facets` request a while after its search therefore reports its own facets as partial. The cap of 4 bounds planning and compiling to 4 patterns, each within RX-0's limits. A facet whose pass stopped is marked `partial` (`TermCounts::partial`). When the shared pass stopped, `Facets::partial` is set and the histograms are `approx`. A recovery count whose regex stopped is left out (`None`), and the later removals are still counted, so the removal that drops the regex is still offered. The UI review's banner says "Stopped after 2 s" (02 §5.2). §3's p95 < 500 ms is the target for typical patterns, and the 2 s is the hard stop for the rest. **(refinement)**
- **Verifying under the pass's token** (general review item 6). `regex_verify::seal` verifies every segment of a searcher before a pass, under that pass's cancel token: a lease when it's taken, facet variants, recovery. A pass that didn't seal verifies a segment when it first reaches it, under the deadline only. A compiled query keeps no token, so a later pass never inherits a cancelled one.
- **Each segment's matches are kept in the smaller form**, a sorted id list (4 B a match) or a bitset (max_doc / 8 B), switching to the bitset while verifying as soon as the list would be larger. Every pass over one compiled query sees the same answer. A clause with no work (out of time, `Plan::Nothing`, no candidates) keeps an empty list and allocates no bitset (S8-10).
- **A lease keeps only the verified matches** (S8-10, the runner's preferred option). It seals its whole snapshot when it's taken, then `regex_verify::release` drops the verifiers, DFA caches and prefilters. Later pages read the kept matches, so they agree with page 1's count, cost no verification, and a stopped lease stays stopped on every page (`Lease::regex_stopped`). `Lease::regex_bytes` is the real retained size (the matches plus a fixed overhead per clause and segment). The new `LeaseConfig::max_regex_bytes` (64 MiB) bounds it across leases: past it, the least recently used regex leases go. A query at the cap costs at most about 4 × N / 8 bytes, 5 MB at 10M torrents.
- **A stop is reported, never silent:** `regex_verify::stopped(&Compiled)` is true when any `/…/` clause stopped early. The hits are then what was verified in time, and the total is a lower bound, or an upper bound when the stopped clause is negated (`-/x/`). Wiring it into the API's response (a `partial` flag for RX-2's "Stopped after 2 s" with a ≈ count) is RX-2's. Until then the API says nothing about a stop, and the user guide says so.
- **Regex searches aren't cached anywhere** (`Node::has_regex`, `Compiled::regex`): not in the result cache (search, facets, facets on a lease), and not in the segment cache of a sorted search's per-segment tops (`sorted.rs`). A partial answer must never be served later as complete. `tests/cache.rs` pins it for a stopped search and its facets.
- **Saved searches and alerts honour a stop** (S8-12, the runner's preferred fix). `percolate` leaves a search whose verify stopped out of `matched` and lists it in `Percolation::regex_stopped`, so its watermark stays and the range is retried next run. It doesn't set `stopped` or `more()` itself. Each search in a run gets its own regex budget (`regex_scope`). Any search that got as far as running makes the next ones stoppable, whether it matched or stopped, so a regex that stopped can't leave the next search unstoppable. **Backoff (`Seen::regex_backoff`):** a stopped saved search waits 1 minute before its next run, then twice as long after each further stop, up to 1 hour. A run that completes clears the wait. Without it, a pattern that always takes its whole 2 s would run first in every run (its watermark stays lowest), spend the run's budget and starve every search after it. A promoted row is held, without running the search, while that search waits. In the promoted path, `matched_promoted` (`crates/lodestar/src/percolator.rs`, approved by the runner) holds the row for that search, so it's retried with the next batch. Live queries aren't recorded either and retry. **The cost:** a saved search whose range always takes longer than 2 s never advances, and its alerts wait. It's logged as the new warn event `search.percolate_regex_stopped`, at most once an hour per saved search (`Seen::regex_stopped`), with the saved search's id only and never the pattern. RX-2 shows it in the UI. There's no per-saved-search health field to set, and no endpoint was added.
- **S8-13** is recorded here by id. No shipped pack or test fixture has the shape in question.
- **No refusal for a verify-only pattern** (`Plan::All`, e.g. `/\d+/`). The plan suggested refusing one over a large corpus unless another clause narrows it; the time budget already bounds it, and the stop is reported, so a refusal would only take away a slow but working search. The user guide says such patterns are slower. **(refinement)**

## rv-755 (from the review of X-rx0-nits)
- **Pinned the folded flags** in `regex.rs`'s `fold_costs_follow_what_gets_folded`: `[[:upper:]]` and `[A-Z--0]` each cost more than 10× `[A-Z]`, so the `true` flags in `class_item` (ASCII) and `class_set` (set operations) can't silently become `false`.
- **`class_text` maps a one-codepoint property (`\p{Zl}`) to that codepoint**, not an empty set: `regex-syntax` translates it to a literal (`HirKind::Literal`). The test pins `[^\p{Zl}]` costing differently from `[^\P{Any}]`.
- **The "as long again" comment** on `MAX_FOLD_COST` now says the verifier compiles in up to about 2.3× the parse baseline for compiled-size-bound shapes.
- **`[^/]` × 127 is in the timing table** (`tests/regex_plan.rs`), refused at 128 by the node limit.
- **RX-0's "No bound loosened" (X-rx0-nits) is superseded by:** no limit's value changed, and every charge is still at or above the work it stands for; N3 charges a bracket of only literals exactly where it was over-charged, so more such brackets are accepted, up to the node limit. (Recorded here rather than editing RX-0's file, per this folder's rule.)

## Bench
- **The zero-results recovery pass leaves the regex class out:** each removal keeps the `/…/` clause and re-verifies its candidates, now under the search's own regex budget, so its recovery is cut at the 20 ms budget by design (CI measured p95 20.06 ms, 6 of 100 cut). Whether recovery should reuse the search's verified matches is part of X-regex-lazy-verify.
- **`size-report` prints the long-name marker's document frequency** (`SearchIndex::long_names`, general review item 4): the names every regex always verifies, for G-v07-scale.
- **`search-bench` has a `regex` class gated at §3's 500 ms p95** (cold cache): a rare word, two adjacent words joined by `[ ._-]+`, a common word then a year, and a case-sensitive word with `\w*`. CI runs it at 200k torrents; G-v07-scale measures 10M on the owner's host.

## Left for a follow-up
- **The `search.trigram` switch** (on by default, §8): a `settings/search.rs` field, its `config.rs` key, the writer skipping the field when off and a generation that empties it on the next walk (plan RX-1; LR-0 sets it in low-resource mode). It touches `config.rs`, the index writer in `index.rs` and the settings golden, outside this slice's owns, so it's a separate slice, X-trigram-switch (the runner adds it to `runner/slices.yaml`). Low-resource mode turns the field off there, as §3 says. Until then the producer is always on.
- **The API's `partial` flag** from `regex_verify::stopped` (and `Lease::regex_stopped`), for RX-2, which also shows a saved search whose regex keeps stopping.
- **Lazy or intersected verification** (general review item 3): verification still ignores the query's other required clauses, so a word beside a pattern doesn't narrow the regex work (the user guide says so). Follow-up slice X-regex-lazy-verify, before G-v07-scale (runner).
