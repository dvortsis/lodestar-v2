# M-security-settings decisions (part 1: password, sessions, secure cookies)

Settings → Security (§10.10.7, §10.10.8's Security row, §12), on B12's password confirmation. No owner decision, security decision or owner-set number changes. Refinements the runner flags to the owner (§2.19) are marked **(§2.19)**.

- **Split in two PRs, as the brief allows past ≈1,200 lines.** This one: the screen, the shared password confirmation, Change password, Sessions and the secure cookies status. Part 2: API keys and feed tokens, and auth mode with the trusted-proxy header, both on the same dialog. No API-key UI existed to reuse (S-keys is keyboard shortcuts).
- **One password dialog** (`security/PasswordDialog.svelte`, opened by `confirmWithPassword` in `confirm.ts`, loaded on first use). Focus starts in the password field. The typed password is copied out and the field cleared before the request goes, so it's never kept after a try, whatever comes back; it reaches only the request body. A wrong password shows the server's `error.message` as the field's error and refocuses the field. Cancel, Esc and ✕ send nothing. An empty password asks without sending. A close asked for while the request is on its way waits for the answer, so the result isn't lost. A 401 `login_required` closes the dialog; the API client's existing handler takes the user to sign in with `next` set, which is how the engine already returns them to the screen.
- **The lock-out is shown truthfully.** A 429 shows "Too many wrong passwords." with a countdown from `Retry-After`, or 12 s when there's none (the login bucket refills one try every 12 s, M-auth), capped at 15 minutes; the button holds (`aria-disabled`) until it ends, then "You can try again now." The moving digits are hidden from screen readers and the wait is read once, as in the filters dialog. One `Lockout.svelte` serves the dialog and Change password.
- **Change password needs no second confirmation** (§10.10.7: it needs the current one). The rules show under New password before submit: at least 10 characters and the advisory strength hint, from `features/auth/password.ts`, the same as setup. Too short, too long or mismatched is refused without sending. The server's field (`old` or `new`) decides which field shows its error. All three fields are cleared once the request goes. On success it says every other session was signed out and this browser stays signed in, because `POST /password` always does that (B12, F-auth).
- **The leave guard is the engine's decision, without its draft.** Passwords must never reach the sessionStorage draft (§10.10.5), so Change password doesn't use `createSettingsForm`. It calls the engine's `leaveDecision` with "something typed" as dirty and asks Leave / Keep editing with the engine's `ask`; Leave clears the fields. Closing the tab lets the browser ask. **(§2.19)** The dialog has no Save: the change is a single action, so "Save" would mean submitting a password without the user pressing the button.
- **Sessions shows this browser only.** The API has no session list (sessions are signed cookies under one key, B12), so the screen says "This browser is signed in" and offers Sign out other sessions behind the password. It says trusted-proxy users aren't affected, as the route does.
- **Secure cookies is a status line, not an engine field.** `network.secure_cookies` is read-only in the registry (turning it on over plain HTTP would lock everyone out), so the screen reads `GET /settings/network` and shows On or Off with an icon and text, and either the variable that set it or where it can be set (`LODESTAR_SECURE_COOKIES`, `http.secure_cookies`), then restart. A failed read says so. It doesn't load the network section's message map, so `bodyMaps` lists none for `SecurityScreen`.
- **Sizes.** The password dialog is its own on-demand entry ("Settings security dialog", measured + 10%); the screen's first view is gated by the existing per-body 45 KB entry. No existing limit was raised. Numbers are in the PR.
- **Copy** is `settings_security_*` in en and zh. Change password reuses the setup screen's `auth_*` rule and strength strings, so both say the same.
