# WK-8 decisions (what a worker judges with)

Plan `docs/plan/2026-11-06-v06-workers.md` §4.3 WK-8 and Q1; architecture §19.4, §19.6, §20.1, §20.3, §20.4; owner §2.17. Q1 is decided as the plan recommends (owner §2.46 and §2.47; `ext:owner-wkq1`). Builds on WK-0, WK-5, WK-6, WK-7 and WK-3's chunk pattern.

**For the owner (§2.19), from the runner:** the sealing below is **stricter than Q1's plan row** in two ways.
- **Every record leaves a worker sealed**, not just the held-back ones; only the hash-list drops, which never leave, are exempt.
- **The plan row seals the spool with the worker's own `SecretStore`, which the worker can open.** Here a record is sealed under a wire key that the worker holds only in memory and never writes down. So nothing on a worker's disk, its `SecretStore` included, opens the names in its spool once the process has stopped. While it runs, the worker holds that day's key and could open what it sealed. Every worker gets the same daily key, so one compromised, running worker could open another worker's sealed records if it got hold of them. Revoking a worker doesn't rotate the day's key: a revoked worker keeps whatever it held until the next day's. Zeroizing can't reach copies the OS wrote to swap or a core dump. This is a security tightening, not a loosening. Per-worker keys (the HMAC over the worker id as well) are a possible later refinement: the snapshot would then differ per worker (WK-10).

## The filter snapshot (`crates/pipeline/src/wire/filter_snapshot.rs`)
- **It carries the store's rows, not a compiled engine.** These are the rows the commit judges with:
  - CS-1 entries with their origins, CS-8 signatures and your core switches (`FilterState`, without `held`);
  - your rules, pack switches, overrides, exceptions, *Always allow*, the pack-version rows and pack-rule overrides (`RuleSet`);
  - classification rules;
  - SP-4's signature rows;
  - every subscribed content list as `lodestar_filter::lists::apply` applies it: id, floor mark, action, hashes, and for a floor-marked list the hashes its publisher removed but you haven't (owner §2.7).
- **The worker builds its engine with the coordinator's own loader.** It runs `default_filter` and `load_filter` on those rows, then sets the lists exactly as `lists::apply` does. A rule can't be read two ways, and a row that doesn't parse fails closed the same way on both sides. Tests: `the_snapshot_holds_exactly_what_the_commit_judges_with` builds the server's engine the server's way from one store, and the worker's from the snapshot after a wire round trip; the two decide the same on every hash and name tried. `the_workers_engine_decides_as_the_coordinators` does the same with every field set.
- **Left out on purpose:**
  - the held set (tombstones and quarantine): the commit refuses held keys, the worker never needs them;
  - IP lists: they govern peers, not records;
  - term lists: both sides use the shipped ones.
- **The version is a digest of the encoded bytes** (SipHash-1-3, never 0, which `Assign` reserves for "none yet"). The same content always has the same version, so a rebuild that changed nothing resends nothing. It's a change detector, not a security check: the bytes arrive over mTLS.
- **The encoding is bounded and all-or-nothing.** It uses `wire`'s varint layout with shortest-form varints, booleans and tags of exactly 0/1/2, UTF-8 checked, and trailing bytes refused. Caps:
  - 64 MiB per snapshot assembled (`MAX_SNAPSHOT`);
  - **96 MiB of decoded memory** (`MAX_DECODED`, runner), the snapshot and the engine built from it. This is well inside a worker's 256 MB (owner §1.6.5). It's estimated row by row as the payload is decoded: each row at its in-memory size plus what the engine adds for it, 64 bytes per listed hash or CS-1 entry, and text at four times its length. Past the budget the whole snapshot is refused. It allows about 1.5 million listed hashes. The encoder runs the decoder on what it built, so the coordinator never sends a snapshot a worker would refuse;
  - 2^20 rows per table, 4,096 lists, 64 KiB per text, 256 bytes per id.

  Every count is checked against its cap and against the bytes left before anything is allocated. A store past the caps can't be encoded: `install` changes nothing, so **workers keep the snapshot they have** and go on judging with it, and the commit's re-judge stands as always. **That lasts only until the installed key's day ends:** after it, every record is refused (`NotReady`, fail closed), so a store past the caps stops every worker within a day, until it's back under them. The failed build is remembered, so the store isn't read again until something changes, and the error (it names a cap, never a rule) is returned once.
- **The dictionary** (`DictSnapshot`) is the active `file_dict`: its id, which is also its version, and its bytes, at most 4 MiB. The worker builds its `Preparer` from it with `Preparer::from_dict`, so every blob names that id.
- **Chunking** reuses WK-0's `Snapshot`/`SnapshotAck` and WK-3's rule that chunks arrive strictly in order. `Incoming` takes chunk 0 as a new transfer and refuses any chunk that doesn't follow the last one, or isn't full unless it's the last, and drops the transfer when it does. What's installed stays in use until a new snapshot is complete. `Complete::filter` and `Complete::dict` check the payload against the version it came under (its digest; the dictionary's id).

## The judge (worker side)
- **`Judge`** owns the engine the prepare stage uses (`Judge::filter()` → `WorkerStages::filter`) and judges every prepared torrent before it goes out. `Judging` wraps the outbound queue, which takes only `SealedRecord`s, so only what the judge lets through reaches the queue that feeds the wire and the spool.
  - **A hash-list drop is dropped on the worker:** the floor's CS-1a/1b and CS-8a, or a subscribed list that drops. It's counted and reported as `Loss::Blocked`, and never sent or spooled. A key on such a list is already refused by prepare before parsing (`blocked_hash`); the judge catches the rest, such as a CS-8a repost that only its files show. **A remote one leaves no tombstone:** CS-1 and the lists refuse the key again before it's fetched, but a CS-8a repost (another key, the same payload) can be fetched and dropped again, until WK-10's floor-drop report lets the coordinator tombstone it.
  - **Every other record goes sealed (runner, §2.33, stricter than the plan):** quarantine, the adult hold, a drop by one of your rules or a pack, hide, demote, flag, and no decision at all. **The worker's verdict is sealed too, never in clear** (runner): nothing on the coordinator needs it before opening, since it re-judges, and in clear every spooled or wired record would show which keys were quarantined or dropped. The reason: some holds are decided only at commit. An always-adult source the worker doesn't know of (the worker judges with no always-adult sources, and neither the snapshot nor the lease carries them), and SP-3 and SP-4, judged only at commit, can quarantine a record the worker saw as clean. That record's name would otherwise cross the wire in clear. The clear encoding stays in the codec for the built-in worker's path and WK-6's pinned bytes.
- **Runner's call: a rule's drop goes sealed, not dropped.** Q1's "drop (hash-list matches)" names hash lists only. A drop by a query needs its tombstone on the coordinator (§20.3), so that removing or narrowing the rule re-queues it.
- **Before a snapshot is installed nothing is judged:** a result is reported lost (`Blocked`), fail closed. WK-10 starts fetching only once one is in.
- **A worker judges with its own fetch time as the discovery time.** The commit judges again with the lease's, so a rule that depends on time can decide differently on the two sides, and the commit's decision stands.
- **A result prepared under an older engine is judged again** with the installed one before it goes out (`a_result_from_before_an_install_is_judged_again`). It's stamped with the snapshot's version, not the worker engine's internal counter, which keeps counting up across installs.
- **The coordinator still re-judges every remote result** (the writer's `rejudge` for any `worker != LOCAL`, which WK-9 keeps). A sealed record is never exempt.

## Sealing (runner, 2026-11-07, §2.33)
- **The whole record is sealed, not just the name.** A single-file torrent's file tree holds the same name, and so may its extras and enrichment. The sealed form is one record of WK-6's codec, sealed with XChaCha20-Poly1305 under a random 24-byte nonce.
  - **In clear:** the leased key, the token, the rule version and the wire key's id. That's what fencing and opening need; the commit keeps the hash in any case. The worker's verdict is inside the seal.
  - **Bound as AAD:** that clear header, encoded, plus the worker's id. A sealed blob opens only under the same key, token, version and worker (the tamper cases in `a_quarantine_goes_sealed_and_opens_only_for_its_worker`).
  - **What opens:** exactly one record in clear, in a batch numbered 0, with no sealed record nested inside, whose key, token and version are the clear header's (`open_refuses_what_a_worker_never_seals`).
- **`Sealer::seal_bytes` / `open_bytes`** (approved edit to `crates/filter/src/seal.rs`). They take the AAD. `seal`/`open` delegate to them with empty AAD, with no change in format or behaviour: the existing seal test is unchanged and still passes, and a new test checks that a text seal and a bytes seal with no AAD open each other.
- **Wire keys** (`crates/lodestar/src/cluster/filter.rs`). Each is HMAC-SHA256 of the label `lodestar-wire-v1`, a zero byte and the coordinator's own UTC day number, keyed with the coordinator's seal key. The worker's clock never enters. The coordinator accepts today's key and the day before's: a spool holds a record for at most 24 h. The seal key never leaves the coordinator, and keys are re-derived after a restart, never stored. A known-answer test pins the derivation (`the_wire_key_derivation_is_pinned`), since spooled records depend on it staying the same across upgrades.
- **`install` takes its day from the snapshot's key** (runner): a snapshot read at 23:59:59Z and installed after midnight is built for its own day, so the new day's snapshot is due at once (`install_takes_its_day_from_the_snapshots_key`). A snapshot whose key isn't the seal key's for its day is refused.
- **A worker seals only while its clock is on the installed key's day** (`Judge::judge_at`). The coordinator accepts today's key and yesterday's, so anything a 24 h spool replays still opens. A worker cut off past midnight would otherwise keep sealing under an old key and spool records that could never be opened. Past the key's day, until a new snapshot arrives, every record is refused (`NotReady`): its lease ends and the key is fetched again (`nothing_is_sealed_past_its_keys_day`).
- **On the worker, keys live in memory only:** never on disk, in logs or in `Debug`. `WireKey` prints only its id and is overwritten with zeros on drop. The assembly buffer is allocated at its announced size so it never reallocates, each chunk's bytes are zeroed once copied, and a partly received transfer is zeroed when dropped. A finished snapshot's bytes go to `decode` and are freed without zeroing, as are the coordinator's encoded copy and the engine's own copies. That's best effort, using a compiler fence and no `unsafe` or new dependency. A worker that restarts waits for a fresh snapshot before it can seal (WK-10, WK-11).
- **On the wire:** `flag::SEALED` in WK-6's `Results` codec (approved edit). A sealed record's flags are exactly `SEALED`. Its seal is capped at the payload size before anything is allocated, must hold at least a nonce and a tag, and counts against the batch's record cap and its one-key-once rule. Sealed records follow every record in clear: a clear one after a sealed one is refused, so whatever decodes re-encodes to the same bytes. A seal is capped below the payload by the batch and clear headers, so a sealed record always fits a batch (`the_largest_sealed_record_fits_a_batch`). `encode_with` / `decode_with` carry sealed records. **`decode` leaves them out**, so an intake that doesn't open them refuses them: the lease expires and the key is fetched again (fail closed). `cluster_results` now fuzzes `decode_with`, since a plain `decode` of a batch with sealed records no longer re-encodes to the same bytes.
- **Nothing here prints a name, a key or a rule:**
  - every type that holds one has a hand-written `Debug` showing ids and lengths: `WireKey`, `SealedRecord`, `Judged`, `Judge`, `FilterSnapshot`, `ContentList`, `DictSnapshot`, `Complete`, `Incoming` (its progress, never its bytes), and the coordinator's `Sender` (version and lengths) inside `WorkerSnapshots`;
  - every error is a fixed string;
  - the one log line (a record the codec refuses) names the key and the error;
  - `ToWorker`'s `Debug` already prints a snapshot chunk's length only (WK-3).

  Tests format each type and search for the name.

## The coordinator side (`crates/lodestar/src/cluster/filter.rs`)
- **`WorkerSnapshots`** keeps each kind's current payload and every worker's transfer: `WINDOW` (4) chunks ahead of the acks (2 MiB per kind, 4 MiB of the 8 MiB session queue with both in flight), starting over after 60 s with no progress, as WK-3 does. A stale, repeated or foreign ack moves nothing. A full queue is reported and retried on the next sync.
- **Sent on change.** `due` is true only while a remote worker is connected and the filter engine's version, the day or the active dictionary has changed since the last build. With no remote worker, nothing is read, built or sent (`a_single_machine_builds_and_sends_nothing`).
- **`read_snapshot` and `read_dict`** read the store: `StoreFilter::read`, the subscriptions as `lists::apply` reads them, and the active dictionary's row. They block, so they run on a read connection off the async threads.

## Size (§19.8)
Measured by `snapshot_sizes`, encoded, before frame compression:
- **At the store's defaults: 51 bytes** (no rules, no CS-1 entries; the wire key is most of it), so one chunk.
- **With 10,000 rules of your own** (`name:"release group N" size:>1GB`): **421 KB**, one chunk.
- **With those and 100,000 CS-1 entries: 2.5 MB**, 5 chunks.

Listed hashes cost 20 bytes each on the wire, and a rule about its query's length plus 6 bytes. The decoded-memory budget, not the 64 MiB payload cap, is what bounds lists: about 1.5 million listed hashes.

## Gates
- **A blob under an unknown dictionary id is refused at commit.**
  - Per record, before the write, by WK-9's intake: `remote_intake.rs` `a_bad_blob_is_refused_alone`.
  - Through this slice's path: `filter_snapshot.rs` (tests) `a_blob_under_a_dictionary_the_coordinator_lacks_is_refused`. The dictionary goes over the chunks, the worker's preparer names its id, and a coordinator store without that dictionary refuses the write.
- **A drop-action fixture prepared on a worker never reaches the wire or the spool:** `drops_stay_on_the_worker_and_quarantine_goes_sealed`. A worker's real pool, prepare stage and judge run with a CS-1 key, a CS-8a repost and a listed hash. None of the three reaches the outbound queue, each is reported `Blocked` under its token, and none of their names is in the encoded payload. Unit tests: `a_hash_list_drop_never_goes_out`.
- **A quarantine-action fixture reaches the coordinator's quarantine with its name sealed throughout:**
  - the same test, and `a_quarantine_goes_sealed_and_opens_only_for_its_worker`: the record leaves the worker sealed, its name in neither the payload nor any `Debug`;
  - the coordinator opens it only under the authenticated worker's id, and the commit's own `rejudge` quarantines it, where the writer seals the name under its own key as for local work.
  - **The last hop is WK-9b's:** opening sealed records in the intake (runner). The end-to-end assertion through the writer to `quarantined()` goes with it (below).
- **A stale snapshot is re-judged at commit:** `a_stale_snapshot_is_rejudged_at_commit`. A worker on an old snapshot sends a record with no action. The record goes sealed over the wire codec, is opened, and the commit's `Results` is rebuilt from it, file list and classification decoded from its blob as WK-9's intake does. The commit's `rejudge` then quarantines it under today's rules. The writer keeps a verdict only for the built-in worker's result under its own engine version and runs `rejudge` for every other (`writer.rs`, `judge`: `r.worker == WorkerId::LOCAL && r.version == engine.version`). WK-9's `remote_intake.rs` drives remote results through that writer.
- **The decoder fuzz target:** `fuzz/fuzz_targets/cluster_filter_snapshot.rs` covers the filter and dictionary snapshots and chunk assembly, and `cluster_results` covers sealed records. Proptests in the module run the same decoders on arbitrary and bit-flipped input. The chunk case pads chunks so a multi-chunk transfer can complete, and decodes what completes. `cargo fuzz` and a nightly toolchain aren't in the build session: the targets build, and running them is for the runner or CI.

## Notes for later slices
- **WK-9b (the intake), in `RemoteSink::results`'s decode** (`crates/pipeline/src/remote.rs`):
  1. Replace `ResultsBatch::decode(payload)` with `ResultsBatch::decode_with(payload)`.
  2. For each sealed record, call `keys.open(&sealed, worker)`, where `keys` is `WorkerSnapshots::keys()` (an `Arc<WireKeys>` handed to `intake::attach`) and `worker` is the authenticated session's id.
  3. Put the opened record through the same fencing, rebuild and re-judge as any record in clear, before the rebuild.
  4. A record that doesn't open is refused alone and its lease ended once as `Invalid`, like any refused record; count it. Never log the sealed bytes.
  5. Add the end-to-end test: a sealed quarantine through the writer to `Store::quarantined`, with the name sealed under the coordinator's key and absent from the data folder in clear.
  6. **Refuse and count any record in clear from a remote worker** (every remote record is sealed): a WK-13 signal. Only the built-in worker sends records in clear.
- **WK-10 (the runtime):**
  - build the `Judge` with the worker's own id, hand `judge.filter()` to `WorkerStages`, and wrap the outbound queue in `Judging`;
  - start fetching only once a filter snapshot is installed (and a dictionary, when `Assign`'s `dict_version` isn't 0);
  - feed `Snapshot` chunks to one `Incoming` per kind, acknowledge each step, and on `Done` decode and `install`;
  - on the coordinator, call `forget(worker)` when a worker's session starts, so a worker that restarted gets both snapshots again from chunk 0;
  - on the coordinator, take the engine version before `read_snapshot`, so a change that lands mid-read is rebuilt on the next tick, then run `due`, then `read_snapshot` / `read_dict` on a blocking read connection, then `install` with the seal key (`read_seal_key`); call `sync` every tick and `ack` from the inbound sink; put `versions()` into placement's `set_versions`;
  - `due`'s `engine` is the coordinator filter handle's `current().version`;
  - with no seal key (one is made at the server's first start), don't allow workers;
  - **set the wire keys at coordinator start** (`wire_keys(seal_key, now)` into `WorkerSnapshots::keys()`), not only on `install`, so a spool replayed before the first install opens;
  - run `install` off the async threads: it encodes and then decodes the snapshot, up to about 96 MiB at the cap;
  - log `install`'s error once, with a new log event (the event registry, its web names and `docs/metrics.md` are WK-10's to add with the tick); the error names a cap, never a rule;
  - add a key-only "floor drop" report that the coordinator tombstones, so a CS-8a repost isn't fetched again and again;
  - the outbound queue takes only `SealedRecord`, with a test that nothing else can be queued;
  - encode with `encode_with(&[], &sealed)`;
  - per-worker wire keys stay an option.
- **WK-11 (the spool):** spool the `Results` payload as encoded. Sealed records are already sealed under the wire key, which the worker never writes down. A worker seals only on its key's day, and the coordinator opens that day's key and the next day's, so a 24 h spool always replays records it can open. A record kept longer than that can't be opened: it's refused and its key fetched again. The segment's own `SecretStore` seal and secure deletion (owner §2.17) are as planned.
- **WK-13 (re-verification):** a sampled key whose record went sealed is re-verified like any other, from the info dict, not the sealed bytes. A worker whose sealed records don't open, or whose open records disagree with their clear header, is a candidate for quarantine.

## Checks
- `cargo fmt --check` and `cargo clippy --workspace --all-targets -- -D warnings` pass. `cargo test` passes per package (the session's disk can't hold every test binary at once).
