# SRC-3 decisions

Search's `verified:`, `source:` and `network:` fields, with unverified items hidden by default. This is the first producer under SB-6's population contract (`2026-11-04-SB-6.md`, `2026-11-04-SB-6b.md`). It applies architecture §18.6 and §18.5 ("indexed with `verified:no`, hidden from search by default") and §8.

## What is indexed
- **Every torrent is written with `verified:yes`, `network:bt` and one `source:` term for each bit set in `torrents.sources`** (`doc.rs` `DocProvenance`). Everything in `torrents` is verified clearnet BitTorrent metadata (§18.5). The other tiers (§18.6) arrive with v1.1–v1.3.
- **A `source:` term is the plugin's manifest id, lowercased** (`query::source_value`): ASCII letters, digits, `.`, `_` and `-`, starting with a letter or digit, at most 32 bytes. That is the same rule the parser uses, so every indexed term can be asked for. A registered plugin id outside that rule isn't searchable by name. The store's only rule is "no `/`", and every shipped id fits.
  - The indexer maps bits to ids through the store's registry (`index.rs` `SourceNames`). It reads the registry again only when a torrent carries a bit it hasn't seen. Ids are never reused and a plugin's id never changes, so an entry never goes stale.
- **Generations:** `verified`, `source` and `network` go from 0 to 1 (`population::GENERATIONS`). Every existing v6 index backfills them through SB-6's walk: resumable, committed with the documents, reported as `Backfilling` until complete. A new index, or the v5 → v6 rebuild, is complete at once.

## The query language (`query.rs`)
- **`verified:yes|no`** (and `true`/`false`, `1`/`0`), **`source:<id>`** and **`network:<tier>`** each take a comma list matching any value, like the other keyword fields. The AST nodes are `verified`, `source` and `network` (JSON `{"op":"network","any":["bt"]}`).
- **Bounded values:**
  - `network:` takes only the five §18.6 names. An unknown network is a parse error that lists them.
  - A `source:` value must fit the rule above. An id no source has parses and matches nothing, because sources can be registered at any time and the parser has no registry.
  - The query's existing length and clause caps apply.
- **Hidden by default:** a search adds `verified:yes` to the user's part of the query unless the query names `verified:` anywhere, including negated or under `|` (`Node::without_unverified`, applied in `api::search::base_query`). `verified:yes,no` shows both values, and it's the form SRC-17's "Show unverified" toggle should send.
  - It goes on the user's part, as `hidden:no` does, rather than among the visibility clauses. So the Verified facet (SRC-17) can strip it and count both values.
  - Every path through `base_query` gets the default: `/search`, `/facets`, export, live search, discover and suggest.
  - **Saved-search alerts (the percolator) don't go through `base_query`,** so they don't get the default. That changes nothing until unverified items are indexed, and SRC-3b must add it there (below).
- **The field catalogue** lists `verified` and `network` as enums and `source` as a keyword.

## Complete while backfilling (`compile.rs`)
- Documents indexed before SRC-3 carry none of the three fields. Every one of them is a stored, verified clearnet torrent, because unverified and other-network items are only ever indexed with their fields.
- **So `verified:yes` compiles to "everything but `verified:no`", and a `network:` list that includes `bt` compiles to "everything but the tiers it leaves out".** Both are complete on a partly backfilled index. The hidden-by-default clause therefore never hides a torrent the walk hasn't reached, and a `network:bt` default (SRC-17's Network facet) won't either.
  - **The cost:** one `MustNot` term clause on every query. Today it has no postings, since no `verified:no` document exists. These clauses don't drive the query (`excludes_only`), so a range clause still drives as it did before. The search latency gate checks this.
- **`source:` has no complement.** While it backfills, it matches only the documents done so far, as the contract allows. The search says so (next section). Nothing in SRC-3 prefilters on these fields, so `SearchIndex::prefilter` has no new caller.
- On an older index serving during a rebuild (field `Missing`), `verified:yes` and `network:bt` match everything, which is correct for such an index. `source:` and `verified:no` match nothing.

## Availability in the API (`api/search.rs`, `dto/search.rs`)
- **`/search/state` gains `unpopulated`:** `SearchIndex::unpopulated()`, one entry per field with `state` (`missing`, `no_producer` or `backfilling`) and `done`/`upto` while backfilling. `unavailable` stays as it was, for its existing readers.
- **A search gains the notice `fields_incomplete` and `incomplete_fields`,** with the same entries, for the fields its clauses name that aren't complete (`Node::population_fields`). Today that means `source:` only.
  - Only the user's clauses count. The default `verified:yes` is complete by construction (above), so it never triggers the notice.
  - It reads the index's latest commit, which a lease's snapshot can predate by one commit, so a field that just completed may be reported once more. That errs towards saying "partial".

## Content filter rules (`crates/filter`)
- The rule judge doesn't see provenance, so in a filter rule `verified:`, `source:` and `network:` match nothing, as `seen:` does. That needed a two-line match arm in `matcher.rs` and `matcher_reference.rs`, outside SRC-3's paths, because the AST is shared. A follow-up should decide whether the filter API refuses these fields in rules or the judge gets them.

## Not in SRC-3: indexing unverified items (handed to SRC-3b)
The brief asks for unverified items to be indexed so they can be found when asked for. **They aren't in this PR,** because doing it safely needs store changes outside SRC-3's paths. **The runner decided (2026-11-04) that this is a separate slice, SRC-3b:** it changes store triggers through a migration, which goes through the migration queue with the store owner's review. SRC-3b needs:
1. **The store never logs unverified items for the index.** `put_unverified` (new item, new claims, a new finder), `delete_item` (refile, purge, a promotion that merges) and V14's tombstone, quarantine and `cs_hashes` triggers write no `reindex_log` entry. `ids_after` reads only `torrents`.
   - So an index built from `crates/search` alone would keep a held or purged item searchable. That's a content-safety hole, so this PR doesn't ship it.
   - SRC-3b needs `reindex_log` entries for each of those writes: put, delete, refile, purge, the merge on promotion, and the three triggers (through a migration). It also needs `ids_after`, or the indexer's new-id walk, to cover unverified ids.
2. **A document built from claims,** in the indexer's loader: name, files and size from the claims, `verified:no`, `network` from the item's row, `source` from its bitset.
3. **Hits for unverified items.** `/search` builds hits from `store.torrent(id)` and drops ids it doesn't find, so an unverified hit would vanish. It needs an unverified hit shape (SRC-17's badge reads it).
4. **The percolator's default** (above).
- **`source:` drifts with later sightings, for the same reason.** A stored torrent that gains a source's bit after it was indexed (`add_sources`), or loses one when a purge keeps it (`torrents_kept`), isn't logged for reindexing. Its `source:` terms update at its next reindex (an enrichment, an edit, or a later generation's walk). SRC-3b should log those two writes too. They're rare: a bit is added only when it's new for that torrent, never on a repeat sighting.

## Tests
- `query.rs`:
  - golden parses, renders and JSON for the three fields;
  - bounded-value errors, including an unknown network and over-long or malformed source ids;
  - the hidden-by-default rule (named anywhere, applied once, composing with `hidden:`);
  - `population_fields`.
- `tests/query_props.rs` gains the new fragments. The `query` fuzz target now also checks the JSON round trip and that the default clause is idempotent and parses back, with new seeds under `fuzz/seeds/query`.
- `tests/provenance.rs`:
  - every torrent is verified and clearnet, with its sources, and an unknown source matches nothing;
  - a reindex picks up a torrent's current sources;
  - **the backfill restart:** an index rewritten as a pre-SRC-3 build left it walks, loses an uncommitted step to a crash, resumes from its commit and completes, while the default clause, `verified:yes` and `network:bt` find every torrent at every step;
  - **`verified:no` asked for explicitly:** it finds an unverified document that is hidden otherwise.
- SB-6's tests that used `verified` as "a field with no producer" now use `payload_sig` and `group_key`.
