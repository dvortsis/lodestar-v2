# OUT-0 decisions (bitmagnet-format export)

Slice OUT-0, 2026-11-11 (UTC). Plan `docs/plan/2026-11-05-v07-m7.md` §4.3 "OUT-0"; architecture §18.2 Outputs, §18.7, §18.9, §20.9.

- **The format is bitmagnet's `/import` endpoint input, checked against bitmagnet's source on 2026-11-11.** That source is `internal/importer/httpserver/httpserver.go` and `internal/importer/importer.go`, plus the guide `bitmagnet.io/guides/import.md` in bitmagnet's repository. The endpoint reads `\n`-separated JSON objects and decodes each with Go's `encoding/json` into `importer.Item`, matching keys without regard to case. Lodestar writes six keys in a fixed order, the ones the plan names: `infoHash` (40 lowercase hex digits, as `protocol.ParseID` takes them), `name`, `size` (bytes), `source`, `publishedAt` and `contentType`. Null values are left out, as bitmagnet's guide does. It goes out as `format=bitmagnet` on the existing `/export`, so it needs no new route and no router line. The response is `application/x-ndjson`, saved as `lodestar-export-<UTC time>.bitmagnet.ndjson`. The file is ready for `curl --data-binary @file http://bitmagnet:3333/import`.
- **`source` is always `lodestar`.** bitmagnet creates one torrent source per key and files each torrent under it. That lets a bitmagnet user filter by where torrents came from, and it says nothing about this install.
- **`publishedAt` is `discovered_at`, as `YYYY-MM-DDTHH:MM:SSZ` (UTC).** That is when Lodestar first saw the torrent, the closest it has to a publication time. Lodestar leaves the key out when the time is 0 or negative: bitmagnet then stores no time rather than 1970.
- **`contentType` maps Lodestar's types to bitmagnet's enum where the two mean the same:** movie → `movie`, tv → `tv_show`, music, audiobook, ebook, comic, software, game, and Adult → `xxx`. Images, video and other have no bitmagnet equivalent, so Lodestar leaves the key out and bitmagnet classifies those torrents itself. bitmagnet keeps any content type it is given as a hint, so Lodestar never guesses one. A unit test checks that every mapped value is in bitmagnet's enum and that each of its nine values has exactly one Lodestar source.
- **No trailer line, unlike the NDJSON format.** bitmagnet would decode a trailer as one more item, and a missing `infoHash` fails its whole import. So the file itself can't say it's incomplete. A cancelled or failed download still ends with a transport error, never a clean end, as in every format. An export cut at the 1,000,000-row cap ends cleanly, and only its job's `truncated` says so; OUT-2's Settings → Outputs should show that. `publishedAt` is also left out for a time before 1970-01-01T00:00:01Z or after 9999-12-31T23:59:59Z, since Go's parser refuses a five-digit year and one bad line fails the import.
- **No `fields`:** the format's keys are fixed, so `fields` gets `fields_unused`, as it does with `magnets`.
- **Exclusions are stricter than the other formats', and stricter only.** bitmagnet queues every imported hash for metadata, which means DHT `get_peers` lookups. §18.7 and §18.9 say a private hash must never reach a DHT lookup, so a bitmagnet export leaves out:
  - every row a §18.7 privacy gate refuses (`flags::PRIVACY`): `private_source`, BEP 27 `private`, and a remote worker's unverified row (WK-9), not only `private_source`;
  - hidden torrents, whatever is asked. `hidden=true` gets `hidden_unused` (400) instead of being quietly ignored. This is "the same exclusions as TZ-0", which never serves hidden items;
  - Adult unless `export_adult` is on (§20.9; off by default, already wired by the server and followed live, as for the other formats);
  - as before, anything deleted, tombstoned or quarantined: an abuse report confirmed after storage removes the row, and an export of the stale index entry skips it.

  The CSV, NDJSON and magnet formats keep their rule (never `private_source`; `hidden=true` allowed). They are files for the user, not a feed into a crawler. `crates/api/tests/export_bitmagnet.rs` proves they leave out `private_source` from every source: query, hashes and collection. The fix the plan allowed for wasn't needed.
- **Hostile names.** JSON escaping keeps every line break, quote and control character inside its string, so a name can't end a line or add a key. A NUL is valid JSON, but PostgreSQL text refuses it, so one name would fail bitmagnet's whole import batch. Lodestar writes a NUL as U+FFFD and keeps every other character. It writes C1 controls, DEL, bidirectional formatting and U+2028/U+2029 as `\uXXXX` escapes, which every JSON reader decodes to the same string, so neither the file nor bitmagnet's UI shows them raw.
- **Limits are `/export`'s own:** the session or API key like every API route, same-origin JSON for POST, four jobs at most, the shared rows-per-second pacer, the 1,000,000-row cap, chunked reads with a small send queue for bounded memory, and the stall, pause and lifetime limits. A line holds only the six fields, never a setting, a key or a path.
- **Round trip:** no code in this repository reads bitmagnet's import lines (the importer in `crates/sources-importers` reads bitmagnet's PostgreSQL). So the format is pinned by a golden file, `crates/api/tests/golden/export_bitmagnet.ndjson`, and by a model of bitmagnet's decoding in the test. The model refuses unknown keys, hashes that aren't 20 hex bytes, non-`uint` sizes, content types outside the enum, non-RFC 3339 times and NULs.
