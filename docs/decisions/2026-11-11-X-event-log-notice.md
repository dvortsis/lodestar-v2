# X-event-log-notice decisions

- **Legal Notice version 5, section 5's fifth exception (owner §2.55, option A).** Both copies (`docs/legal/legal-notice.md`, `crates/api/src/legal/notice.md`) gain the owner-approved clause word for word, as the fourth item, before "and the optional safe-restart switch…", and "four exceptions" becomes "five exceptions". The version line reads "Version 5 · 2026-11-11". Nothing else in the notice changes. `NOTICE_VERSION` goes from 4 to 5, so every admin sees the notice once more at their next request.
- **One version for both of §2.55's changes.** X-prowlarr-register adds its section 2 text later under the same version 5, with no second raise, because no release is cut between the two. If a release has to be cut in between, X-prowlarr-register moves to version 6 instead (§2.55).
- **The service writes its refusals to the Application event log, as source "Lodestar".** When the data folder isn't private (or couldn't be checked or created) the start is refused and an ERROR event, ID 3 (Windows service error 3), says so. When an update rollback holds the store, the service waits idle and a WARNING event, ID 4, says why. The second is the notice's "has to be undone" case, seen from the service. The update helper keeps its own source, "Lodestar update helper", and its ID 900, unchanged.
- **The Event Log message is a fixed sentence and the folder path, never the ACL check's own reason (a refinement of the brief).** The brief allowed "paths, account names and the fix (the icacls command)". The owner-approved clause promises "version numbers, the step that stopped and folder paths only", in a log every local user can read, so `event_log_text` writes only what happened, the data folder, the fix (run the installer's Repair) and where the full reason is: `%SystemRoot%\Temp\lodestar-service.log`. That log keeps the exact account, SID and `icacls` command, as before. Control and bidirectional characters in the folder name are flattened, so a folder name can't forge a second line, and a long configured folder is cut at 260 characters.
- **Through `eventcreate.exe` from `System32`, as the helper does.** The workspace forbids `unsafe`, so the service can't call `ReportEventW`, and the helper's writer lives in `update/windows/**`, which this slice doesn't edit. The service's call is best effort: the temp log and the exit code already carry the refusal.
- **The MSI registers both sources as `eventcreate` custom sources** (`packaging/windows/main.wxs`, component `EventSources`): `EventMessageFile` `%SystemRoot%\System32\EventCreate.exe`, `TypesSupported` 7, `CustomSource` 1, with `ForceDeleteOnUninstall`. `eventcreate`'s own message file renders IDs 1–1000 as the text alone, so events show without "The description … cannot be found". `eventcreate` writes only to a source it created or one marked `CustomSource`, and the service's virtual account can't create one, so registering the source is what lets the service write at all. Uninstall removes both keys; before this, the helper's `eventcreate` left its key behind. The portable build has no installer and no service: its helper still creates its own source the first time it writes, as before.
- **`legal_facts.rs` checks the Event Log positively.** The notice must name "the Windows Application event log" with the approved limits and say "five exceptions". Every file under `crates/*/src` or `packaging/**/*.ps1` that uses an Event Log writer (`eventcreate`, `ReportEvent`, `RegisterEventSource`, `EvtReport`, `Write-EventLog`, `New-EventLog`, .NET's `Diagnostics.EventLog` or `WriteEntry`, matched ignoring case) must be the helper or the service, and every `event_log(` caller must be the helper, its rollback or the service, with no third call site in the service. No crate may depend on an Event Log crate. The MSI must register both sources. A new writer fails the test, naming section 5. The old check that the notice must not name the Event Log is gone: its premise ("no code writes there") stopped being true with #644.
- **`settings.logging.event_log_errors` stays hidden and unread** (§2.55: general errors are out of scope).
- **The OpenAPI example follows the version** (as in X-notice-v4): `LegalNotice`'s example in `dto/auth.rs` is version 5, and `openapi.json` and `schema.d.ts` are regenerated, so the e2e mock serves 5.
- **Follow-ups for the runner, in files this slice doesn't own:**
  - the comments in `settings/logging.rs` that say nothing writes to the Event Log;
  - `docs/user/06-troubleshooting.md` §6.2 "Fix Windows service error 3", which can now point to the Application log (source "Lodestar", event 3) as well as event 7024;
  - `docs/legal/operator-guidance.md` ("version 4 of the Legal Notice") and `docs/releases/v0.5.2.md` ("Legal Notice v4") name version 4. The latter is right for v0.5.2, which ships notice 4. The notice's own "Applies to Lodestar 0.5.2" line is the owner's wording, so it stays as it is;
  - the update helper's own Event Log text (`update/windows/**`) interpolates its error reasons. Someone should confirm that none of them can carry an account name or a configuration value.
