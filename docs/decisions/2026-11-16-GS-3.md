# GS-3 decisions (collapse-by-group: best version plus N others, groups and torrents counted, stable pages)

Spec: architecture §8 "Results, facets and features" (counts, stable pagination, cancellation, collapse-by-group) and §3; owner-decisions §2.66 item 2 ("Group versions" on by default once group data is ready); plan `docs/plan/2026-11-05-v07-m7.md` §4.3 "GS-3"; the population contract (`docs/decisions/2026-11-04-SB-6.md`); `docs/decisions/2026-11-16-GS-2b.md` (the `group_key` column this reads). Builds on GS-2b (#963).

- **Groups are `group_key` values; a torrent without one is its own group** (plan §4.3). The column gives each hit's group. A group's members are its `title_identity` term's postings, which GS-2b writes with the same value, because `group_key` isn't indexed. So "+N others" and Related's "other versions" (B13b) count the same set.
- **Best version = the group's first hit in the lease's own order** (relevance windows included, or the chosen sort). Ties break the way that order already breaks them: by document address, lowest first. The plan says "best by the phase-2 score within the phase-1 window". That is what relevance's order is (§8: exact within a window, approximate only at window boundaries), and the field sorts follow their own key. **Refinement (§2.19):** collapse follows every sort, not only relevance.
- **`others` counts the group's members among all the query's matches**, not just those on or after this page: the term's postings checked against the query, ranges and deletes included. `others + 1` summed over a full scan is the torrent count (tested).
- **Stable pages without a seen-set (the runner approved cursor v2 with re-derivation).** A collapsed cursor carries the last row's position, the same position an uncollapsed cursor holds, plus a collapse flag.
  - A page from it skips every group with a member ranking at or before that position: such a group was served from its best member then. That check is the new `Lease::ranks_at_or_before`.
  - Nothing grows with depth, and under one lease no group is served twice or skipped. A property test walks every page of a collapsed result over random corpus shapes, sorts and page sizes, with an NRT commit after a page, and checks that the groups served are exactly the distinct groups of a full scan, in order.
  - Swarm values aren't pinned by a lease (§7, `lease.rs`), so a hot sort or priors can move a torrent across a cursor between pages. That's true of collapsed and uncollapsed pages alike.
- **Cursor format.** A collapsed cursor is version 2 (only the version byte differs). An uncollapsed cursor is written exactly as before (version 1), so cursors from before GS-3 still open. The fingerprint is unchanged: `/facets` keeps reading the search's lease from either kind.
  - A collapsed cursor is refused (`bad_cursor`) for a request without `collapse=group`.
  - An ungrouped cursor is refused for `collapse=group` unless its lease had no group data, the fallback's own cursor.
- **Bounds (§8 cancellation, §3).**
  - **Per page:**
    - at most `MAX_SCAN_GROUPS` = **4,096** groups are decided (served, or skipped as served before);
    - at most `MAX_SCAN_HITS` = **16,384** hits are walked, so repeats of decided groups can't make a page walk on. Each step of 64–1,024 hits is a ranked pass over the matches.
    - A page that reaches either bound ends **short, even empty, with a cursor** after the last hit it decided. The next page carries on, and nothing is skipped (tested with tight bounds).
    - An offset page may decide up to `offset + limit` groups, at most 10,000 (the API's `offset + limit` limit). If it reaches the hits bound first, it reports the groups it passed, and the response's `offset` says so (the GET `offset` description says this too). **GS-5 pages collapsed results with cursors only.**
    - A page that fills knows there's no next page when every later hit it has read belongs to a group already decided and no hits follow. Otherwise it hands out a cursor, which can lead to an empty last page. The API description says so; GS-5 shows an empty last page as the end.
  - **Ranked order:** read in chunks of 64–1,024 hits through the lease's own paging.
  - **Members are leapfrogged, never loaded whole** (the runner's review, I1). Per segment, the groups' `title_identity` postings are merged in doc order and walked against the query. Each step seeks whichever side is behind to the other's document. So finding a group's members costs about the smaller of the group and the query's matches, and memory holds one posting cursor per group:
    - a selective query in a group of about 2,700 takes at most 8 steps (tested);
    - a broad query visits each member about once.

    Counting `others` exactly still takes O(min(group, matches)) per page for a group on it. A huge single-identity group (DHT spam) under a broad query costs its size in time, under the cancel token's checks. It no longer costs its size in memory.
  - **Member addresses** for the served-before check are held at most `MAX_MEMBERS` = 262,144 at once, then checked and let go (tested with a batch of 16 against a group of about 2,700). Groups already known served are skipped. The check stays exact.
  - **The two-phase window bound** that the served-before check compares against is found once per page, not once per batch (I2). There's no check at all when no addresses are pending.
  - **Exact groups count:** at most `GROUPS_EXACT_CAP` = 1,048,576 distinct keys held. Past it, nothing more is inserted (the segment's walk finishes, holding nothing more) and the estimate stands. **Peak memory:** that set is about 16–32 MB (a `u64` hash set at the cap) per exact request, times the exact requests running at once. Below 100k matches it's under 2–3 MB.
  - **Rounding:** the served-before check rescores members by seeking, and a union of several clauses can sum in another order than the ranked walk did. So the cursor's own row and the window bounds also match by address. A test pages a five-clause union across fields.
  - **Cancellation:** the token is checked before each chunk, between segments, and every 4,096 documents in every walk (the members check, the counts and the new lease helpers), as the code around them does.
- **Counts: `groups` beside `total` (torrents),** for "128 groups · 412 torrents" (UI review 02 §5.1).
  - The groups count is exact whenever the torrents count is: up to 100k matches, or with `exact` on demand. **On demand, the torrents and the groups are counted under one shared 5 s `EXACT_BUDGET`** (`collapse::counts`). A collapsed request reads its torrents count from there, never from `Lease::exact_total`, so nothing is counted twice or under a second budget (the runner's review, B1). A test counts visits: each is counted once, and a spent budget stops both. Out of time, the estimate stands, run under the request's own token, as for torrents. A kept estimate is replaced when the exact count is asked for, and a kept exact count answers both (tested).
  - Otherwise `groups_approx` is true: a **Horvitz–Thompson estimate**.
    - Keyless matches (groups of one) are counted over every match the count's strata slices visit, weighted as the count weights them.
    - Keyed matches go into a fixed weighted sample of `HT_SAMPLE` = 1,024 (A-Res, keyed by a scramble of the torrent id, so it's the same sample whatever the segments' order). Each drawn group's members `m` are counted exactly, and the keyed groups are `keyed × mean(1/m)`.
    - Kept on the lease, so later pages don't recount.
  - **The estimate's error, from the seeded test** (`the_groups_estimate_is_within_its_stated_error`, 40,000 documents, groups of every size, keyless every 11th):
    - **The draw alone** (every match visited): worst 0.7 % over five queries. The test holds it at 5 %.
    - **With the count's slices** at a 2,048-document threshold: worst 9.9 %, held at 12 %. That is dominated by the slices' error on the keyless share. At this fixture's size it's a 1/16 sample of a few hundred documents. At the 200,000 matches below which nothing is estimated, it's the count's own tolerance (`count.rs`: σ ≈ 1/√(k/16) for k keyless matches, e.g. 2.8 % at 20,000).
    - So the "≈" label is honest: the groups estimate is about as good as the torrents estimate beside it.
- **The fallback** (owner §2.66, plan §4.3): collapse needs both `group_key` and `title_identity` Ready in the lease's snapshot (`availability_in`).
  - Otherwise the search answers ungrouped: `collapse_unavailable: "group_key_not_ready"`, no `groups`, no `others`. It's never an error.
  - That covers a build before GS-2b, a v7 index serving during GS-2b's rebuild (read-only population, `NoProducer`), and any later walk of either field.
- **API** (`/search`, GET and POST):
  - `collapse=group|none` (an unknown value is `unknown_collapse`).
  - With collapse on: `others` on each hit, `collapsed: true`, `groups` and `groups_approx` on the response, and `offset` counting groups.
  - `total`/`total_approx` still count torrents.
  - Every new response field is omitted when it doesn't apply, so ungrouped responses and every existing golden are unchanged.
  - `explain` with `collapse` is refused (`explain_collapse`): explain covers the ungrouped ranking.
  - A collapsed first page bypasses the result cache, which keeps ungrouped first pages only (the runner's approval; `cache.rs` is untouched).
  - `openapi.json` and `schema.d.ts` are regenerated with `cargo run -p lodestar --bin openapi` and `npm run api:types`.
  - **`collapse` is left out of the POST body's schema, as `explain` is** (`#[schema(ignore)]`). In the generated client types, every `SearchRequest` field is required, so a new one broke every caller that builds a body (`svelte-check` in `web/`). `GET` lists it as a parameter, and `POST` accepts it the same way. GS-5 sends it as a query parameter, or adds it to its body type with the UI.
- **Shared edits, each approved by the runner:**
  - `crates/search/src/lease.rs`:
    - `page_ranked`, `page_at` with each hit's position (`page_at` now calls it and drops the positions; a test shows the hits and cursors identical);
    - `ranks_at_or_before`, with its phase-1 window bound and score helpers, all `pub(crate)`;
    - the groups count kept on the lease;
    - one line in `lease/tests.rs`'s literal.
  - `crates/search/src/lib.rs`: the `collapse` module and its re-exports.
  - `crates/api/src/torrents.rs`: `others: None` in `torrents::hit`.
  - `count.rs` gains `Matcher::contains`, for the members check. `crates/api/tests/search_collapse.rs` is new.
- **Bench** (`search-bench`, a new reported table, not gated): the keyword classes with `collapse=group`, each timing a lease, the groups count, the first collapsed page and its rows (with the groups count's and the page's own p95).
  - **This container, 1M torrents, 100 queries per class:**
    - "1 common word" has a p95 of 12.9 ms (groups count 7.7, page 4.1), against 3.5 ms for the same class's ungrouped lease and first page;
    - "word + file clause": 28.3 ms;
    - "word + OR'd swarm": 27.3 ms.

    Every class is within §3's 30 ms keyword target. The synthetic names give about 1.1 torrents per group.
  - **The exact groups count is the largest part.** It visits every match up to 200,000, the same rule as the torrents count. Group keys are hashed with the key itself (`KeyHasher`, they're FNV hashes already), not SipHash, which took about 2 ms off the common-word p95.
  - **G-v07-scale measures the keyword p95 with collapse on at 10M**, and that decides whether the default stays on (§2.66). No budget changes.
  - **At the API, collapse is opt-in** (`collapse=none` is the default). GS-5 makes it the UI default and rechecks the p95 then. The runner flags the latency cost to the owner as a UX/performance call.
- **Tests cover every sort kind:** two-phase and phase-1 relevance, field sorts with missing values (every 13th torrent has no size), and hot sorts with missing values (seeders and leechers, every 5th unscraped).
- **Not in GS-3:** the UI (GS-5: the toggle, "+N others", the count line).
