# X-spool-damage-log decisions

Follow-ups to WK-11's spool (`docs/decisions/2026-11-11-WK-11.md`, #699) from its reviews: damage logged by segment, and three fixes in `crates/pipeline/src/spool.rs`.

## Damage is logged (rv-699 I3)
- **One event, `pipeline.spool_damaged`** (Warn, component Workers), in the pipeline's catalogue. It fires when a segment's header doesn't read or names another worker (`header`), its last write was torn (`torn`), a frame part-way is bad (`frame`), a record doesn't open (`seal`) or doesn't decode (`record`).
- **It names the segment by its number, never a path or a byte.** The number is in decimal; the file name is that number in 16 hex digits, inside the spool folder (segment 26 is `000000000000001a.lsp`). Both fields are labels (`Count` for the number), so they show at every logging setting; a data kind such as sizes could be switched off and would hide which segment it was.
- **It can't flood the log.** A segment logs one line, naming the first damaged part found, the first time it's read: however many of its frames are bad, and however often a lost session has it read again. A spool logs at most `MAX_DAMAGE_LOGS` (64) lines in all (a worker runs one spool), counted per spool (`SpoolStats::damage_logged`). Past the cap nothing more is logged until the worker restarts; the counts (`worker_spool_dropped_total`) still count everything. Each line carries only the segment's number and the part; a test captures the line and checks it holds nothing else (`the_damage_line_carries_only_the_segment_number_and_part`).
- **Not logged, only counted (left for a later brief):** a segment with a bad header that `open()` can't remove (another program holds it) is counted in `leftovers` and tried again at the next start; records that `reseal()` drops because they don't open are counted as damage. Neither writes a line. After the cap, no closing "further damage isn't logged" line is written either.
- **Shared edits (approved in the brief):** the event's names and en/zh rows in the logging settings (`web/src/lib/features/settings/logging/event-names/workers.ts`, the chunk for the event's component, Workers; `messages/{en,zh}.json`), and the regenerated catalogue golden (`crates/lodestar/src/settings/golden/logs_catalog.txt`). The words are plain; `docs/ui-glossary.md` has no term for the spool yet.

## A segment's number is spent before its write (rv-699 r3 I1)
`start_segment` moves `next_seq` on before writing the new segment. Before, a write that failed part-way left the number where it was. That happened if the folder sync failed (EMFILE, EIO), or a file was planted at that name after the spool opened. Every later append then tried the same name and failed until a restart. Now the failure costs one append, and the next takes a fresh number (`a_planted_name_at_the_next_number_doesnt_wedge_the_spool`). A segment placed whose folder sync then fails stays in the counts as header-only, so they match the disk (`a_failed_folder_sync_keeps_the_counts_matching_the_disk`).

## Appends go through the handle that made the segment (rv-699 r3 N1, done another way)
The brief asked for the reopen check to refuse a file with another hard link. The reopen is gone instead, which closes the gap on both platforms. A new segment is appended through the handle that created and wrote it, so its appends go to that very file. A file swapped in at the segment's name afterwards (a planted symbolic or hard link, or any other file) gets nothing: between placement and the first append (`a_segment_swapped_out_after_placing_gets_the_appends`, which a test hook runs right after placing, and which fails if a reopen by name comes back), and later (`appends_never_follow_the_segments_name`). The reopen had checked only that the name pointed to a regular file, the one the name pointed to at that moment. It never checked the link count, so it couldn't tell that file from a hard link planted to another one. Std opens files on Windows with delete sharing, so the temp name is still unlinked while the handle stays open, or, under Windows' older delete rules, stays delete-pending until the segment closes. That's harmless: its number is already spent.

A residual window, not this PR's: between creating the temp file and linking it into place, someone who can write the spool folder could rename the temp file away and plant another at the temp name, which would then become the segment. The spool would go on appending to its own file wherever it was moved, so all they get is sealed frames, no more than they could read in the folder anyway. The precondition is the one secure removal has (below): the folder's owner on Unix (it's 0700), or write rights from the data folder's ACL on Windows.

## What secure removal does on each platform (rv-699 r3 I2; corrects WK-11's note)
WK-11's decisions file said a planted link's target is never zeroed "on either platform". That holds on Unix only:
- **Unix:** a file with another hard link (a link count above 1) is unlinked without being overwritten, so nothing planted in the folder can have another file zeroed. A symbolic link is never followed.
- **Windows:** a symbolic link or other reparse point is never followed, as on Unix. But a file's link count isn't on stable Rust, so a hard link isn't detected: a regular file planted in the folder as a hard link to another file has that file's contents zeroed. Planting one needs the right to create files in the spool folder, which takes its permissions from the worker's data folder. The spool doesn't check those permissions itself, so on Windows this protection is only as strong as that folder's ACL. The spool's own leftover second link, a temp name beside its segment, is never zeroed, because `Spool::open` unlinks it without overwriting it.

## A flake in WK-11's replay test (shared edit, the runner's call under §2.24)
`batches_spooled_offline_are_replayed_once_then_removed` (`crates/lodestar/src/worker/spool.rs`) failed on Windows CI (#717): `rt.reconcile()` returned `None` where `Some(0)` was expected. The spool's bytes reach 0 when the last segment is removed, and the flag asking for the lease-count comparison is set just after that. The test waited on the bytes, then read the flag at once. It now waits on the flag itself (`until("drained", …)`, the shared 20 s deadline, no fixed sleep), then checks that the next call returns `None`. Test code only. No other spool test reads something set after the bytes reach 0.
