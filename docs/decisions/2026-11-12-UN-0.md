# UN-0 decisions

The usenet network in the store's unverified tier. This is the first slice of v0.7's usenet tier (`docs/plan/2026-11-05-v07-m7.md` §5, Q13 and Q16; architecture §18.6 and §18.7). It's inactive until UN-1's plugin writes usenet items.

## The network and the key (`unverified.rs`)
- **`Network::Usenet = 4`,** the position `usenet` has in §18.6's list and in search's `query::Network` (`bt`, `bt-i2p`, `ed2k`, `ipfs`, `usenet`). The value is persisted. `Network::as_str` (and `Display`) give `usenet`, the same name search's `network:` field uses, so SRC-3b can write the `network:usenet` term straight from the stored item. Any other stored value (1–3, 5–15) still fails to decode as `Error::Corrupt("unknown network")`.
- **`UsenetKey` is SHA-256 of a length-prefixed preimage:**

  ```text
  "lodestar.usenet.v1" || u32be(len(indexer)) || indexer || u32be(len(guid)) || guid
  ```

  - `indexer` is the indexer's id and `guid` the item's Newznab GUID, both as UTF-8 bytes exactly as the indexer sent them, with no case folding or trimming.
  - The length prefixes make the encoding injective, so ("ab", "c") and ("a", "bc") can't collide, and a part can't forge the next prefix.
  - The tag is a domain separator, and gives a later encoding a new version.
  - Each part must be 1–1024 bytes (`USENET_MAX_PART`). An empty or longer part is `Error::Invalid` and isn't hashed. That bounds the work an indexer's input can cause, and fits the `u32` prefix.
  - The NZB link isn't part of the key, because it embeds the indexer's API key. Send rebuilds it from the indexer id and the GUID (UN-1, UN-3).
  - Its `Debug` prints only a 4-byte prefix.
- **A usenet key is exactly 32 bytes;** `put_unverified` refuses any other length.
- **No migration (Q16).** V14's CHECKs (`network BETWEEN 0 AND 15`, key 1–64 bytes, 20 bytes only for network 0) already accept a usenet row. Tests show it on a V13 → V14 upgrade and on a reopened store.

## The invariants, enforced in the store
- **Always private-source (§18.7).** `put_one` sets both private marks (`PRIVATE` and `CLAIMS_PRIVATE`) on every usenet write, whatever `NewUnverified::private_source` says. The "public sighting clears it" path can't run for usenet. A usenet row read back (`unverified`, `unverified_after`) reports `private_source` (and `claims_private` when it has claims) even if a row was written without the flags outside this module.
- **Never verified or promoted.** `Store::promote` refuses a usenet item with the new typed error **`Error::NeverVerified`** before it compares any hash, and leaves the item as it was. `Store::pending_keys_after`, the verification cursor (SRC-2, the torrent cache), returns clearnet BitTorrent keys only. So a usenet key is never offered for metadata fetching, and never reaches the DHT, PEX or a tracker.
  - `lodestar_store::Error` is `#[non_exhaustive]`, so the new variant breaks no match.
- **No info hash.** `put_one` looks up only a BitTorrent key among holds (`tombstones`, `quarantine`, `cs_hashes`) and stored torrents (`put_bt_torrent`). A usenet key is never cut to 20 bytes or compared with a swarm hash. So a tombstone that happens to equal a key's first 20 bytes neither holds nor deletes a usenet item.
  - The filter engine still judges usenet claims before they're written, and the re-judge sweep still sees usenet items (`unverified_after`).
- **Purge per tier (§18.6).** `Store::purge_network(network, after, limit)` deletes one tier's unverified items in steps of at most `MAX_PURGE_STEP`, one transaction each, whatever sources found them, and returns the cursor to go on from. `Store::unverified_count(network)` is the count it would remove. The clearnet tier is refused (`Error::Invalid`): its unverified items are the verification queue's, and its torrents aren't a tier purge's. `purge_source` already covers usenet items through their sources' bits.
  - **Usenet deletions aren't journalled for the snapshot purge.** `snapshot_deletions` holds 20-byte swarm hashes only (V12's CHECK). A snapshot taken before a tier purge keeps its usenet rows until it's pruned. They're private, local-only rows (never exported). Journalling them would need a migration, which isn't this slice's.

## The cap (Q13)
- **`USENET_CAP` = 1,000,000 usenet items, oldest first:** the lowest ids go first, which is the order they were first found. It's a constant the runner sets (§2.26).
- **The cap is enforced in `put_unverified`'s own transaction.** A call that adds at least one new usenet item counts the tier and deletes the oldest past the cap, at most `MAX_PURGE_STEP` (4,096) rows in that call. Seeing a known item again adds nothing, so it evicts nothing.
- **A call takes at most `MAX_USENET_BATCH` (4,096) usenet items** (`Error::Invalid` past it, nothing written). With the cap at least that (a compile-time assert), one call's eviction always brings the tier back under the cap, and never evicts the call's own new items. If the runner lowers the cap below the stored count, the excess drains at most 4,096 rows per call.
- **The cost:** the count walks the usenet range of the `(network, key)` index, and the eviction finds the lowest usenet ids. At 1M items that's tens of milliseconds per batch that adds an item. Prowlarr polls bring a few hundred items every few minutes, so that's acceptable. If UN-1 measures more, an index on `(network, id)` can join SRC-3b's migration.

## For later slices
- **The re-judge sweep would remove usenet items today.** `pipeline/src/unverified.rs` `judge_item` removes any item whose key isn't a 20-byte swarm hash. UN-1, or a pipeline slice before it, must judge usenet items by their claims instead, before any usenet item is written. Reported to the runner; it's outside UN-0's owns.
- **`pending_keys_after` now skips usenet rows** inside its id-ordered page. In the worst case, a verification round walks past every usenet row once.
