# CMP-4b decisions (companion limits, sandbox and egress)

Slice CMP-4b of `docs/plan/2026-11-06-v06-companions.md` (§4; §5 Q3 as decided by `docs/owner-decisions.md` §2.47, Q8, Q9, Q13, Q18, Q20 as decided by §2.46); architecture §11, §18.4, §18.10. The brief left each choice below to the slice (§2.33). None of them loosens Q3 or Q7, changes `packaging/systemd/lodestar.service` (Q20: no relaxation), adds a privilege, or starts a companion on the direct route when its route isn't direct.

- **API for CMP-5 and CMP-6.**
  - `Sandbox::new(Limits, Launcher::lodestar()?)` once per supervisor. Its `hook()` is the supervisor's `AfterSpawn`.
  - `sandbox.prepare(spec, &Confinement { install, downloads })` turns each companion's `SpawnSpec` into the one the supervisor starts, and returns its `Report`.
  - `supervise::egress::add(&mut supervisor, companion, Follows::of(&id), Route::of(&plugin_egress))` adds it behind its route. A refusal is `GateError::CantFollow(kind)`, code `cant_follow_route`: the "Can't follow your VPN setting" screen.
  - `Gated::decision` (`Direct`, or `Follow(kind)`) tells CMP-5 which bind or proxy setting to configure.
  - Lodestar's `main` must call `supervise::limits::launcher_main()` first (CMP-5's wiring, not this slice's).
- **Landlock runs in the child before the companion does, without `pre_exec`.** The supervisor starts Lodestar's own binary as a launcher, `lodestar __lodestar-companion-launcher`, with the plan in one environment variable, `LODESTAR_COMPANION_PLAN`. The plan is length-prefixed, so any path is safe to carry, and it's decoded strictly. The launcher runs single-threaded and does these steps in order:
  1. re-checks the target as CMP-4a does: an absolute path to a regular file (not a link) under `<data>/companions/`, not `companions/run/`, and never a `PATH` search (`launcher_bad_target`);
  2. re-checks what the plan grants: no path that is or holds the data folder, and inside it only folders inside the companion's own, `<data>/companions/<id>/…`, with the id taken from the target's path (never `companions/`, `run/`, the companion's folder itself or another companion's; paths carry no `..`);
  3. sets its rlimits;
  4. opens every granted path with `openat2(O_PATH, RESOLVE_NO_SYMLINKS)` and applies the Landlock ruleset to itself;
  5. checks that it reached the level the report promised;
  6. removes the plan variable and `exec`s the companion (`CommandExt::exec`, safe). The rest of the environment it was given passes through unchanged, so CMP-4a's `env_clear()` still holds.

  Rlimits and the Landlock domain carry across `exec` and into everything the companion starts, so untrusted code never runs outside them. If any step fails, the launcher exits with a distinct code (120, 122 to 126). The hook reads it from the zombie's `/proc/<pid>/stat` and maps it to a typed reason (`launcher_bad_plan`, `launcher_rlimit`, `launcher_landlock`, `launcher_below_level`, `launcher_exec`, `launcher_bad_target`), which comes back as `SpawnError::Hook`, and the start counts as a crash.
- **The runner's conditions for the launcher (2026-11-08), and how each is met.**
  - **Selected only by the argv sentinel:** `launcher_main()` checks that `argv[1]` is `__lodestar-companion-launcher`. An environment variable never selects it. `run_launcher` is public only so the tests' fake can act as the launcher.
  - **Before any Lodestar initialisation:** CMP-5 calls `lodestar_companions::supervise::limits::launcher_main()` first in `crates/lodestar` main, as `if let Some(code) = launcher_main() { std::process::exit(code) }`, before config, the data folder or logging. The launcher itself reads no config, opens no Lodestar file and writes only its code to stderr, which goes to the companion's log ring.
  - **The target re-check, the environment passed through, rlimits and Landlock before `exec`, and never claiming `full` silently:** steps 1, 6, 3 and 4, and 5 above.
  - **Distinct exit codes, mapped to typed reasons:** above.
  - **The bounded wait kills on timeout:** a hook error makes CMP-4a's spawn kill the group and the child before anything is recorded.
- **Rlimits are set by the launcher (`setrlimit`), not by `prlimit` from the parent.** The plan accepted a window of microseconds before a `prlimit` applies; the launcher leaves none, and it can carry per-companion values that the shared `AfterSpawn` hook can't see. `rustix`'s `process` feature was already on (CMP-4a), so nothing changes in its features.
- **The Linux hook waits for the `exec`.** `ExecHook` polls `/proc/<pid>` until the process is no longer the launcher's executable (`/proc/<pid>/exe`) and its readable environment has no plan variable. It needs both, because either can be read in the middle of an `exec` (an environment read empty mid-`exec` let the record name the launcher once in six local runs). The first poll comes after 100 µs, and the gap doubles up to 20 ms, with a 10 s bound. It runs on the blocking pool, as CMP-4a's spawns do. A launcher that has exited gets its typed reason (above); the bound running out is `launcher_timeout`, and CMP-4a then kills it. Only after this does CMP-4a record the pid, so the record and the orphan check name the companion's executable, not Lodestar's.
- **Default rlimits.**
  - `RLIMIT_NOFILE` 4096, soft and hard, held to Lodestar's own hard limit. qBittorrent keeps a socket per peer, and 4096 is several times its default 500 connections while staying under the unit's `LimitNOFILE=8192` for Lodestar as a whole.
  - `RLIMIT_CORE` 0, because a core dump would hold the companion's credentials.
  - `RLIMIT_AS` only when `Limits::memory` is set, and unset by default: .NET (Prowlarr) and Chromium reserve far more address space than they use.
- **No cgroup (runner, 2026-11-08 review).** The first version detected a "delegated" parent cgroup, but that matched the systemd user manager's `app.slice` (moving a companion out of Lodestar's unit, so stopping Lodestar no longer killed it) and never a real `Delegate=yes` unit. The slice now uses no cgroup: rlimits and Landlock apply, and `Applied::cgroup_skipped` is always `not_delegated` on Linux. Should a later slice add cgroup limits, they are best effort against a compromised companion, which can leave a cgroup its own uid owns (`clone3(CLONE_INTO_CGROUP)` with a same-uid parent).
- **The Landlock ruleset.** It handles every file-system right up to ABI 9, best effort, `ResolveUnix` (connecting to a Unix socket by path) included. It also scopes signals and abstract Unix sockets (ABI 6), so a compromised companion can't signal Lodestar or another companion, or reach their abstract sockets. Its own children are in its domain and unaffected.
  - **Read, write and everything but execute (W^X):** the companion's home (`<data>/companions/<id>/home`) and its downloads folder, which includes connecting to sockets inside them. Neither qBittorrent nor Prowlarr runs programs from them; Landlock's execute right governs `execve`, not mapping a library.
  - **Read and execute:** its install folder (`<data>/companions/<id>/<version>`), `/usr`, `/lib`, `/lib64`, `/lib32`, `/bin` and `/sbin`.
  - **Read only:** the loader cache, the resolver and NSS files, time zone, CA certificates, `/etc/passwd`, `/etc/group`, `/etc/os-release`, `/proc`, `/sys/fs/cgroup` and `/sys/devices/system/cpu`, plus `/dev/urandom` and `/dev/random`.
  - **Read, write, truncate and device ioctls:** `/dev/null`, `/dev/zero` and `/dev/full` (so `>/dev/null` works).
  - **Connect only:** the name-resolution socket folders `/run/systemd/resolve`, `/run/nscd` and `/var/run/nscd`.

  Paths are made canonical in the parent. A system path that is, or holds, the data folder (data under `/usr`, say) is left out, so the companion may fail to load but never reads the data. `/proc` is safe to read, because Landlock refuses ptrace-mode access (another process's `environ`, `mem` or `fd`) across domains.
- **What stays reachable (the residual; runner, 2026-11-08 review).** Files outside the grants are refused on every Landlock ABI. Below ABI 9 (Linux 7.1), though, connecting to a Unix socket by its path isn't mediated. A compromised companion run as a login user could then ask a user service outside the sandbox to run code: `systemd --user` through `/run/user/<uid>`, the session or system D-Bus, X11, an ssh agent or a writable `docker.sock`. That code would read Lodestar's data. The shipped systemd unit (`DynamicUser`, `ProtectHome`, `PrivateTmp`) gives the companion no such user session. The report says `partial` (`landlock_unix_sockets`) wherever this holds, rather than proving the sockets unreachable.
- **No granted path is followed through a link.** The launcher opens each one with `RESOLVE_NO_SYMLINKS`. A companion's own folders must exist; a missing system path is skipped. So a granted folder swapped for a link to the data folder between starts makes the start fail. Without this the swap was a full escape (self-review, reproduced).
- **Nor through a second mount.** A downloads folder that is a bind mount of a folder above the data folder would pass the canonical-path check. `prepare` therefore repeats it on the filesystem itself: from `/proc/self/mountinfo` it takes the device and the path from the filesystem's root for both the downloads folder and the data folder, and on the same device refuses (`downloads_overlap_data`) a grant that holds the data folder or lies in it outside the companion's own folder.
- **Sandbox report shape.** `Report { sandbox: Sandboxed { level, reason }, limits: Applied { mechanism, open_files, memory, dies_with_lodestar, cgroup_skipped } }`, every field a value or a stable code.
  - **Levels:**
    - `full` (`landlock`, ABI 9 or later: files, truncation, signals, abstract sockets and pathname Unix sockets);
    - `partial`, with the gap as the reason: `landlock_unix_sockets` (ABI 6 to 8, the residual above), `landlock_no_scopes` (ABI 3 to 5: also no signal or abstract-socket scoping) or `landlock_old_abi` (ABI 1 or 2: also no truncation control);
    - `none`, with reason `landlock_unavailable`, `no_safe_wrapper` (Windows) or `unsupported_platform`.
  - **How the level is known:** Lodestar applies the same handled rights to a throwaway thread once (Landlock restricts only the calling thread, and the thread then ends) and reads the kernel's ABI from the result. The launcher refuses to run a companion below that level (`launcher_below_level`), so the report can't overstate.
- **Windows.**
  - **One Job Object** (`win32job`) with kill-on-job-close holds every companion of a `Sandbox`. Lodestar holds the only handle, so companions and their children die with it, however it exits.
  - **The assignment race: a residual window, accepted by the runner (2026-11-08).**
    - **Where it comes from:** CMP-4a's spawn doesn't create the process suspended, and std gives no safe way to resume a `CREATE_SUSPENDED` main thread. So `JobHook` assigns the process right after `CreateProcess` returns.
    - **What it allows:** a companion that started a child of its own inside that window (microseconds, while its loader runs) would leave the child outside the job. That's the same class as the plan's accepted `prlimit` window. qBittorrent and Prowlarr start none at start-up.
    - **What would close it, should a later slice need it (FlareSolverr's browser, CMP-12):** a launcher on Windows too. It would be started with stdin piped, assigned to the job first, and spawn the companion only after reading a byte that `JobHook` writes once it's assigned, so the companion is created inside the job.
  - **No memory cap.** `win32job` sets only the working-set size, which trims memory rather than capping it. Setting the job's process memory limit would need `unsafe`. `Applied::memory` is `None` on Windows.
  - **No Q3 sandbox.** No safe, maintained restricted-token or AppContainer wrapper exists, so the report is `none` / `no_safe_wrapper`, and the install confirmation (CMP-5, CMP-6) says the companion could read Lodestar's data.
- **The egress gate (Q8, Q9, Q18).**
  - **Which routes a companion follows.** The catalogue has no route field, so `Follows::of(id)` holds the plan's table: qBittorrent, an interface or a bind address; Prowlarr, SOCKS5; anything else, direct only.
  - **When it runs.** On a non-direct route the companion is added held (`Supervisor::add_held`). It's released while the route's state is `Up` and held otherwise. `Unchecked` counts as down, and so does a closed state channel, which fails closed.
  - **Holds aren't crashes.** A hold stops the companion through the supervisor's normal stop and never adds to `restarts` or the crash history, so route flaps never reach Needs attention. Needs attention already shown survives a hold: when the route comes back, it's still waiting for you. Only `restart` clears it.
  - **Dropping `Gated` fails closed.** It holds the companion, and it's `#[must_use]`. `abort` can't stop a follow task that's mid-poll on another worker, so the task sends only while holding a shared `closed` lock, after checking it; `Drop` takes the lock, sets `closed`, sends the hold, then aborts. No release can land after the hold (runner's review; tested deterministically).
  - **qBittorrent's bind address is followed only on Windows.** Elsewhere `EgressFactory` marks that route down for good, so `Follows::of` refuses it (`cant_follow_route`) instead of holding the companion forever.
  - **The probe.** Whoever builds the `PluginEgress` runs its `monitor`, as the pipeline does for plugins.
  - **Not covered:** a companion that crashes on its own when its interface disappears, before the hold arrives, counts that one exit.
- **Supervisor change (shared edit in CMP-4a's `supervise/mod.rs`, about 110 lines, more than the brief's "a few"; approved by the runner).**
  - **New API:** `State::Held` (code `held`), public. `Supervisor::add_held`, `Supervisor::handle(id) -> Handle` and `Handle::{hold, release}` are `pub(crate)`: only the route gate holds and releases, so nothing outside the crate can start a gated companion while its route is down.
  - **A queued hold wins:** before each start the loop takes one queued command without waiting, so a hold that arrived during a stop (after a restart, say) holds the companion instead of racing the start.
  - **Behaviour:**
    - a hold stops the running companion, cancels a backoff, or interrupts a Needs-attention wait, which resumes after the release;
    - a hold doesn't add to `restarts`;
    - a restart while held clears the history and the attention, but stays held;
    - a release when not held is ignored.
  - **Restructured:** the Needs-attention wait moved to the top of the loop (`parked`). A refused spawn no longer has its own wait.
- **No log events.** As in CMP-1, CMP-2 and CMP-4a, results are typed codes (`Report`, `GateError`, `SpawnError::Hook`) and `Status` changes, and CMP-5 logs them. The launcher writes only its code to stderr, which goes to the companion's redacted log ring.
- **Dependencies (plan Q13).**
  - `landlock =0.4.7`, Linux only:
    - MIT OR Apache-2.0;
    - released 2026-07-27, maintained by the Landlock author (l0kod);
    - new crates: `enumflags2`, `enumflags2_derive`. `libc` and `thiserror` 2 were already in the lockfile.
  - `win32job =2.0.3`, Windows only:
    - MIT OR Apache-2.0;
    - released 2025-05-15, maintained by ohadravid, about 500k recent downloads;
    - the only maintained safe Job Object wrapper. None is built on `windows-sys`.
    - It pulls in `windows 0.61` (Microsoft's, MIT OR Apache-2.0) and its family (`windows-core`, `-collections`, `-future`, `-implement`, `-interface`, `-link`, `-numerics`, `-result`, `-strings`, `-threading`) and `thiserror 1` with its `-impl`, a duplicate beside the `thiserror 2` already in the lock: 13 crates, Windows only, and about 190 lockfile lines with `landlock`'s.
    - Raised with the runner before building, as the brief required; approved 2026-11-08.
  - `lodestar-sources` is a new path dependency. `cargo tree -p lodestar-sources` has no `lodestar-companions`, so there's no cycle.
  - There's no `test-util` and no first-party `unsafe`.
- **Tests (`tests/limits.rs`).** The fake companion is the test binary, and so is the launcher (filtered to `fake_launcher`). On Linux, the binary is copied into the companion's install folder, because Landlock lets it execute only from there.
  - **Linux:**
    - the companion reports its `RLIMIT_NOFILE`, `RLIMIT_AS` and `RLIMIT_CORE`;
    - the pidfile names the companion, not the launcher;
    - where Landlock is enforced, the companion can't read `secrets.key`, `companions/run/` or another companion's folder, and can write its home; where it isn't, the test asserts the report says so;
    - a damaged plan, or a target that became a link out of `companions/`, fails the start and ends in Needs attention with no record;
    - a downloads folder swapped for a link to the data folder makes the start fail; it never reads the data.
  - **Windows:** the companion is in the job, and closing the job kills it.
  - **The gate:**
    - nothing starts while the route is unchecked or down;
    - each time the route comes up, the companion starts exactly once;
    - four flaps with a crash limit of 2 never reach Needs attention, and `restarts` stays 0;
    - a closed route holds it;
    - Needs attention survives a route flap, with no new starts;
    - dropping a `Gated` holds a running companion;
    - route kinds a companion can't follow add nothing;
    - on Linux, a real `EgressFactory` route (`lo` up, a missing interface down) drives it.
