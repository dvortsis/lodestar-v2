# P-m6-audit decisions

Planning slice P-m6-audit: the gap audit of build-plan P3 and architecture §14 (M6), and the `PK-*` slices in `docs/plan/2026-11-06-m6-gap-audit.md`. Docs only; no code, and `runner/slices.yaml` and `runner/dashboard.yaml` are left to the runner. Everything below is a recommendation for the runner to accept or change at review. None of it reverses or loosens an owner decision. Four questions are the owner's: Q6 (winget), Q8 (the nightly key, already queued), Q13 (the Windows updater's privileges) and Q14 (G-m6's manual installs).

- **The audit's answer to the known items.**
  - FUSE and network-filesystem detection exists (`crates/lodestar/src/fsdetect.rs`). It reaches the start-up log, `lodestar stats`, About and the Settings Overview, but not the Insights exception list (§10.9.2) or the wizard. PK-exc and PK-ui close those.
  - The worker template is already labelled: the Overview starts "Requires Lodestar v0.6+.", it has a `<Requires>` tag, and `validate.py` checks it. No relabelling is planned. A `worker` placeholder (PK-cli) makes the container log explain itself (plan Q4).
  - The guide's v0.5.1 refresh exists on `release/v0.5.1` (D-v051, #201), but not on `main`: D-v051-main ports only the release notes and the root README. PK-guide-1 ports the `docs/user/**` changes and adds when full speed starts, which the owner's rule asks for and the shipped text doesn't say. PK-ui adds the wait to the wizard on `main`.
- **Gaps the brief didn't list:**
  - `lodestar settings get|set|reset` (§10.10.6);
  - Windows Restart now, and memory and free space on Windows (B2c's deferrals);
  - the Windows updater (B-update-r4 gave it to E-M6), including the portable `.exe` swap and the boot-time `--resume` from §12.2;
  - `LODESTAR_VERSION` and the signed manifest in `release.yml` (B-update-r2's follow-up; §16's "with M6");
  - a smoke that reaches setup and search;
  - the Windows and Linux install chapters of the guide;
  - a stale `docs/operations.md`;
  - the Unraid hot and cold fields that nothing reads.
- **Slice prefix `PK-`, gate `G-m6`.** Ids starting `M6-` would sit beside the merged `M6-win`, and a `M6-*` placement rule would catch it. `PK-` is unused, so one `PK-*` rule places the whole epic. The gate follows the lowercase `G-m5` style, and the docs slices use `kind: docs` like D-v051.
- **The Windows updater's install step waits for the owner (Q13).** The service runs as its own stripped virtual account, so whatever it starts can't install a per-machine MSI. Any fix adds a privileged component, which widens the security posture. Check and notify (PK-win-upd-1) and the portable updater (PK-win-portable-upd) don't wait for the answer. The recommended helper is acceptable only under Q13's six rules: the service account controls `<data>`, so a SYSTEM helper that trusted anything there would make write access to `<data>` worth SYSTEM, where on Linux it's worth only Lodestar itself (runner review, round 2).
- **The Windows updater is split in four** (check and notify, MSI install, MSI rollback, portable). Each part is a separate failure surface with its own `/security-review`, and together they'd be about 3,450 lines (CLAUDE.md, ≲ 1,500 per PR). The portable part stands alone so it isn't held behind the owner's Q13.
- **No manifest format change.** Format 1 already has the Windows target and the `msi` and `portable` kinds, and every struct refuses unknown fields, so a change would make every v0.5.x engine refuse the manifest (`crates/update/README.md:78-82`). PK-manifest publishes format 1 in `freshness.yml`'s `<channel>.json` envelope and doesn't touch `doc.rs`.
- **A Windows merge/GC stress in CI (PK-win-soak-ci)** rather than counting the 7 h service soak as enough: architecture §11 asks for it in CI, and the soak isn't repeatable per PR.
- **Recommended for the runner (plan §5):**
  - Q1, measuring M6's "crawling → search" on packaged artifacts without a release-build switch that loosens the network policy, plus a warn-only check of the public routing table. Keeping the policy as it is was chosen because a test-only escape hatch in a shipped binary is a security weakening.
  - Q2, the CLI's limits: no secrets, no `x-danger: security` fields, and no turning on adult or privacy opt-ins, which the UI confirms. A CLI 18+ confirmation would be the owner's and isn't planned.
  - Q3, removing the hot and cold fields and keeping split paths out of M6.
  - Q5, no macOS in M6, since macOS isn't one of the owner's three targets (§1.7.1).
  - Q6, deferring the tray icon.
  - Q7, G-m6 waits for Windows updates.
  - Q9, no new dependency for Windows memory.
  - Q10, keeping the approved design for Restart now as a service (exit for the SCM's recovery action, §10.10.6 and B2c), with the dialog saying it takes about a minute. The SCM doesn't expose its failure count, so Lodestar keeps its own and offers Restart now only when no recovery was used in the last 24 h, so a crash always has one left. This affects availability, so it is flagged to the owner explicitly. A self-start grant on the service was considered and dropped: it would widen the hardened service's rights, which is the owner's call, and Q13's helper could carry it later.
  - Q15, leaving the connection-rate limiter to the crawler track behind a switch, since it changes fetch pacing.
  - Q11 and Q12, the wording.
  - Each of these is a §2.19 refinement or a §2.26 UX choice. They are named in the PR description so the runner can flag them to the owner.
- **Slots and order.** The waves assume four slots (owner §2.41) and the soak verdict first. M6 stays rung 4 of the ladder, and the plan doesn't reorder it.
