# F-filters decisions

Three content-filter semantics fixes from the v0.5 code review, Area 3 (A3-1 to A3-3; `docs/code-review/codex-review-v0.5-area-3-results.md` on `fix/dht-cr0`). They restore architecture §20.6, §20.9 and §20.12 as written. No owner decision changes.

- **A3-1: an exception covers its own list only (§20.12, §20.6).** The pack layer used to reduce the subscribed lists that had a torrent to the strongest one, then apply exceptions to that one list. An exception to that list therefore lifted every other list too. Now each list is excepted on its own, and then the strongest action left among packs and lists wins. With no exceptions, the verdict and the rule it names are unchanged: the last of the strongest still wins.
  - **Before the fetch (`blocked_hash`)**, a torrent is refused when any dropping list still has it and no exception to *that* list could release it. Before, only the strongest list was checked, so an exception to one dropping list let a torrent through to the fetch even when another list still dropped it. *Always allow* and hash-matching Override entries still let the fetch happen, as before, because they need the text. After the fetch, every list is judged again.
- **A3-2: stored reclassification reads the swarm hashes (§20.7, §20.9).** Classification rules on a stored torrent were judged with no hashes, so `hash:` never matched and `-hash:` always did. They now get the same hashes ingest uses: the primary hash and, for a hybrid, the truncated v2 hash. Your own correction still comes first.
- **A3-3: a neutralized word supplies no evidence in any form (§20.6, "Neutralize term removes that word's evidence from the core and from query rules").** A *Neutralize term* used to be compared only with a whole query word, or with a whole phrase as if it were one word. Phrases compared the folded text of the entire phrase, and NEAR ignored neutralizing altogether (the follow-up recorded in `2026-10-22-F-near.md`). Now a torrent's token that is a neutralized word supplies no evidence, wherever it stands. That's the token's fold, as the core reads a neutralized word in its own tokens. A query token only ever matches a token of the same text, so the matcher applies this on the query side, and positions are kept:
  - **A query token that is a neutralized word can't be matched.** A word's parts in a row aren't used if one of its parts is neutralized (`AmberBeacon` can't borrow a standalone `amber`). A whole or compound form that is neutralized is dropped. A phrase with a neutralized part is false, and so is a NEAR word left with no form. So `amber` is neutralized in `"amber beacon"`, `amber NEAR/1 beacon`, `amber.beacon` and the parts of `AmberBeacon`.
    - **A whole or compound form is a token of its own.** A torrent has `x265` and `webdl` as tokens beside their parts. So neutralizing `x` or `web` leaves the words `x265` and `web-dl` matching those tokens. It doesn't leave a phrase `"x265 beacon"`, which reads parts only.
  - **A neutralized word of several parts** (`x265`, `web-dl`) is caught as a run of two or more parts with no space between them, up to 8. A word with no space is also compared whole, as before. A phrase as a whole never is: neutralizing `amberbeacon` no longer takes away `"amber beacon"`. That was the old whole-phrase compare, which took away evidence the word never supplied.
  - **Prefixes and fuzzy words skip a token that is a neutralized word.** So `amb*` and `~ambar` no longer match on `amber` alone, but still match on other tokens such as `ambient`, or a joined token such as `amberbeacon`.
  - **Negation is unchanged in kind:** a neutralized clause is false, so its negation is true, as for a bare word since CSX-5 shipped (`neutralized_words_never_count`).
  - **Always allow never matches more because of neutralizing.** It was already judged with neutralizing, so a neutralized word inside a negated clause would make that clause true and the allow query match more (`foo -"bar baz"` with `bar` neutralized would release "foo bar baz"). The security review of this PR found this. An allow query now releases a torrent only when it matches both with and without the neutralized words. That also closes the same gap for a bare negated word (`foo -bar`), which has been there since CSX-5 shipped. It protects more, never less.
  - **`unless`, exceptions and CSX-5 scopes read the torrent as it is**, unchanged. They never read neutralized words, so neutralizing can't widen them. They differ from Always allow, which was already judged with neutralizing and needed the fix above. This keeps `beacon unless amber` and `beacon -amber` apart when `amber` is neutralized, as they already were for bare words. Bringing `unless` under neutralizing (with both, as for allow) would hide more. That choice is the runner's to make; this PR doesn't change it.
  - **The reference matcher** (`matcher_reference.rs`) takes a neutralized word's tokens out of the torrent's text, positions kept. That's the semantics stated directly, so the property test comparing the two matchers checks the query-side implementation against it. The test now neutralizes folded words, including words of several parts (`1080p`, `x265`).
- **What this changes for users.** A user rule whose phrase, NEAR, dotted or joined word, prefix or fuzzy word depended on a neutralized word stops matching on that word, as §20.6 describes. An allow query stops releasing what only neutralizing let it release. Core rules don't change: they already read the neutral term set. Subscribed lists now hold where an exception to another list wrongly released them. A stored torrent with a matching `hash:` classification rule becomes Adult at its next reclassification.
- **Not changed, a follow-up for the runner:** pack rules (MW-3, LU-2, LU-4, FK-2, SC-1) read their own keyword lists without the neutral term set, though §20.5.5 says Neutralize stops counting "in every non-floor core rule and pack rule". That gap is older than this PR and outside its brief.
- **Cost.** Compiling a rule now folds its words' runs and each token once. When nothing is neutralized, evaluation costs one empty-slice check per text clause. The `budget` gate (10,000 rules; release, build VM, base `origin/next` then this branch, back to back) is within this VM's noise. The mixed shape, the gated maximum, measured 52.8 µs on the base and 52.4 / 55.5 µs on this branch, in reference-runner µs. Single shapes swing up to 2× between runs in both directions: Title was 66 µs on the base and 40 µs here. The base is over 50 µs on this VM too, so CI's `filter budget` job is the gate. The bench has no Neutralize terms. With them, a clause pays a fold comparison per token, and prefix and fuzzy matches fold the matched token.
