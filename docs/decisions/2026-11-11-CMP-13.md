# CMP-13 decisions

The companion pin-refresh tool (`tools/companion-pins/`) and its workflow (`.github/workflows/companion-pins.yml`). Plan `docs/plan/2026-11-06-v06-companions.md` CMP-13 and Q2; owner cq2 as the runner applied it (`docs/decisions/2026-11-06-runner-planning-wave-answers.md`, row cq2); architecture §12, §18.10. These are the slice's decisions under §2.33. None loosens an owner decision or a security decision. The runner flags the ones marked **(refinement)** to the owner (§2.19).

## What the tool does
- **Python, standard library only, and the runner image's `gpg`.** No new dependency anywhere, and no OpenPGP code in the binary (cq2). The tool is small, runs on any GitHub runner, and its tests need nothing installed.
- **One run pins one companion at one version.** It reads `catalogue.json`, downloads each artifact the request names (default: every artifact but installers), checks upstream's signature where upstream signs, runs the pin-time checks, resolves the image digest, and writes the catalogue.
- **What it writes per artifact:** `{"version", "url", "size", "sha256", "upstream_sig"}`, CMP-0's format unchanged. `upstream_sig` is `{"kind": "verified_at_pin", "fingerprint": "<primary key>"}` only when the check below ran and passed; otherwise `{"kind": "none"}`, and only where `upstream.py` records that upstream signs nothing. No format change, so `catalogue.json` and `tests/catalogue.rs` are untouched.
- **Deterministic output.** Keys keep the catalogue's order, pins are written in one fixed order, and one layout rule (which objects go on several lines) is applied to the whole file. Today's file is already in that layout (a test checks the committed file formats to itself), so a pin PR's diff is only the pins. The same inputs give the same bytes, and pinning again from a pinned file changes nothing (tested). The report has no time stamps.

## Downloads (the rules of `crates/lodestar/src/update/download.rs`)
- **Hosts:** the entry's `hosts`, and only those also in the tool's copy of `catalogue.rs`'s `DOWNLOAD_HOSTS`. So an entry naming another host is refused here as the loader would refuse it.
- **Never SourceForge or FossHub,** or any name below them, whatever an entry or a redirect says (runner, 2026-11-11). That check comes before the allowlist.
- **Every hop:** `https`, no port, no user information, at most 5 redirects (`check::MAX_HOPS`). Redirects are followed by the tool, never by `urllib`, so each one passes the same check. A relative `Location` is resolved against the hop that sent it.
- **Byte cap:** 512 MiB (`MAX_ARTIFACT_SIZE`) for an artifact, refused on a `Content-Length` over it or one byte past it while streaming. 64 KiB for a signature file, 4 MiB for a manifest, 64 KiB for a registry token, 256 MiB for a source archive. 30 minutes for one download, every hop included.
- **SHA-256 and size** are computed while the body streams to a fresh file in a temporary folder, which is removed at the end.
- **The URL** is `native.release` + tag + `/` + file name, both checked to be URL-safe, so it's exactly what the loader accepts (`<tag>/<file>` inside the release folder).

## Upstream OpenPGP signatures (cq2)
- **Checked once, here, at pin time,** never at run time. The SHA-256 pin is the run-time gate.
- **Keys are pinned by full fingerprint in `upstream.py`,** with each key's public half committed as `keys/<FINGERPRINT>.asc`.
- **In a fresh `GNUPGHOME`** (a temporary folder, mode 0700, removed after), with `--no-options`, `--no-auto-key-retrieve` and only `PATH` and `LC_ALL=C` in gpg's environment:
  1. each key file must hold exactly one primary key, the one its name and the policy say, or it isn't imported;
  2. the keyring must then hold exactly the pinned keys;
  3. the signature file must be only signature packets: a signed message carries its own data, which gpg could verify instead of the artifact;
  4. `gpg --verify` must exit 0, report no `BADSIG`, `ERRSIG`, `EXPSIG`, `EXPKEYSIG`, `REVKEYSIG`, `NO_PUBKEY`, `KEYREVOKED` or `KEYEXPIRED`, and give one `GOODSIG` and `VALIDSIG` per signature;
  5. each `VALIDSIG`'s primary key must be pinned, and its hash SHA-224 or stronger (no SHA-1 or MD5).
- **An artifact upstream doesn't sign** is probed for `.asc`, `.sig` and `.gpg` beside it. Finding one refuses the pin: upstream has started signing, and its key needs pinning first.

## Each companion's signing story
Checked against what each project publishes. This session's network blocked every upstream host (see "The real dry run"), so the first real pin run re-checks it.
- **qBittorrent on Linux (userdocs `qbittorrent-nox-static`):** the static `x86_64-qbittorrent-nox` and `aarch64-qbittorrent-nox` binaries are GitHub release assets with build-info JSON beside them and no `.asc` or `.sig` (CMP-0 recorded the same). Pinned `upstream_sig: none`; the probe above catches a change.
- **qBittorrent on Windows (the official installer):** published on SourceForge and FossHub, which are never fetch hosts. The qBittorrent project signs its source tarballs with its release manager's OpenPGP key. Whether the installers carry signatures, and that key's fingerprint, is checked when the installer pin is built (below). **No key is pinned in this PR.** A fingerprint from memory or from a single key server would be a pin nobody checked.
- **Prowlarr:** tar.gz and zip builds as GitHub release assets, with no signature files. Pinned `upstream_sig: none`.
- **gluetun:** container only. The image digest is the pin; Docker Hub carries no OpenPGP signature.
- **So `keys/` is empty today,** and every pin the tool can make now is `none`. The OpenPGP path is still built and tested in full (fixture keys), so a companion that signs needs only a policy line and its key.

## The installer can't be pinned yet
- **CMP-11 needs a per-artifact release folder for installers, off the fetch hosts.** Today a pin URL must sit in the entry's one `native.release` folder on its fetch hosts, and the loader (`crates/companions/src/catalogue.rs`) enforces it. That's a format change in `crates/companions/src`, where CMP-11b is working.
- **So the tool refuses an installer** (`installer`) when asked for one, and by default leaves it awaiting its pin, saying so in the report. That's the fail-safe state (CMP-0): the guide claims no checksum while it's unpinned.
- The artifact-level release field and installer pins are **X-cmp13-installer-pins**, after CMP-11b (runner, 2026-11-11). "Never a fetch host" is Lodestar's run-time rule; whether the pin tool may fetch the installer from SourceForge or FossHub at pin time, and what it verifies it against, is decided there. This tool doesn't fetch from them.

## Pin-time checks (CMP-13's notes in `runner/slices.yaml`)
- **Prowlarr's .NET reads the proxy variables, `socks5://` included** (`dotnet_socks5`, every Prowlarr artifact). The archive must hold the catalogue's executable and its `<name>.runtimeconfig.json` beside it, within 64 KiB. It's checked as `manager::runtime_reads_proxy_env` checks it at launch: `tfm` of .NET 8 or later, and at least one `Microsoft.NETCore.App`, every one 8 or later.
  - **A framework-dependent build whose `runtimeconfig.json` lists only `Microsoft.AspNetCore.App` is refused** (#672's review). Lodestar would refuse it on SOCKS5, so pinning it would ship a Prowlarr that can't follow a VPN setting.
  - .NET 6 and 7 are refused: they take only `http://` from those variables.
  - The report records the `tfm`, self-contained or framework-dependent, and the runtime version.
- **Prowlarr's source at the pinned tag** (`prowlarr_source`), from `codeload.github.com`'s archive of that tag, `.cs` files outside its test projects (any path part with a `Test` component):
  - `ConfigService.cs` must still say `ProxyEnabled => GetValueBoolean("ProxyEnabled", false)`, so its own proxy is off at the first start and .NET's `DefaultProxy` applies;
  - there must be exactly one `ManagedHttpDispatcher.cs`, and no `UseProxy = false` anywhere;
  - X-cmp-egress-prelaunch's searches are re-run with that slice's counts as ceilings: no `TcpClient`, `UdpClient`, `WebRequest.Create` or `HttpWebRequest`; at most one `new SocketsHttpHandler`, one `new Socket(` and six `Dns.*` calls.
  - More than a ceiling refuses the pin until someone re-reads the new code and raises the number in `upstream.py` in a reviewed PR. The report lists where each match is, for the pin PR's reviewer.
  - **What this can't show:** that the build was made from that source. The tag's archive is evidence for review, not a proof.
  - **(refinement)** The counts came from `develop`. If the released `master` differs, the first pin run is refused and the maintainer looks, which is the point.
- **Container images:** the digest of the tag's manifest (an index for a multi-arch image) is computed from the bytes received, never taken from the registry's header. A `Docker-Content-Digest` that disagrees refuses the pin. The manifest must be an OCI or Docker index or manifest; an index must have a `linux/amd64` build. The tag must be a fixed version, never `latest`.
  - **Registry hosts:** `lscr.io` (and `ghcr.io`, where it redirects and issues tokens), `ghcr.io`, and Docker Hub's `registry-1.docker.io` with `auth.docker.io`. The token is anonymous, its scope is the tool's own (`repository:<repo>:pull`), and it's sent only to the host that asked for it, never across a redirect.

## What the tool refuses (exit 1, nothing written)
Each refusal has a stable code on stderr. The catalogue and the report are written only after every check passed, each through a temporary file and a rename.
- `host_not_allowed`: a host off the allowlist, SourceForge or FossHub, `http`, a port, user information, at any hop or for a token realm.
- `redirect`: more than 5 redirects, or one without a `Location`.
- `too_large`, `timeout`, `http_status`, `network`.
- `signature_missing`: upstream signs this artifact and the signature isn't there.
- `signature_unexpected`: an unsigned artifact now has a signature beside it.
- `key_not_pinned`, `unknown_key`, `bad_signature`: the OpenPGP rules above.
- `digest_mismatch`, `registry`: the image rules above.
- `check_failed`: a pin-time check.
- `installer`: an installer asked for.
- `request`: an unknown companion or artifact, a version outside `inputs::Version`'s grammar, a tag or file name that isn't URL-safe, or a run that would leave one entry with pins of two versions (the loader refuses that).
- `catalogue`: an input catalogue that isn't format 1, or has a duplicate key.

## The workflow
- **`workflow_dispatch` only,** with `permissions: contents: read` and no secrets. The checkout keeps no credentials.
- **(refinement) Inputs:** `companion` (a choice) and `version`, as briefed, plus optional `tag`, `image_tag` and `artifacts`. qBittorrent's userdocs tags (`release-<qBittorrent>_v<libtorrent>`) can't be derived from the version alone.
- **Inputs reach the tool as environment variables,** never interpolated into the script.
- **It uploads `catalogue.json`, `report.md` and `catalogue.diff`** as the `companion-pins` artifact, and puts the report and diff in the job summary, or the refusal when it refuses.
- **It never pushes, commits or opens a PR.** A person opens the pin PR from the artifact, with the report in its description, and the runner reviews it.

## How a maintainer runs a pin
1. In GitHub, Actions, **Companion pins**, Run workflow. Choose the companion, type the version (and the tag for qBittorrent).
2. Read the job summary. A refusal names its code and reason; nothing was written.
3. Download the `companion-pins` artifact. Put its `catalogue.json` over `crates/companions/data/catalogue.json` on a new branch.
4. The first pin also updates `tests/catalogue.rs`'s `builtin_entries_await_their_pins_and_are_refused` (CMP-0's note).
5. Open the pin PR with `report.md` in its description. The runner reviews it like any other.

Locally: `python3 tools/companion-pins/pin.py --catalogue … --out … --report … --companion … --version …` (`tools/companion-pins/README.md`).

## Not done here
- **The release gate** ("a release must not offer anything still awaiting its pin", CMP-0) and **"CI fails a `catalogue.json` change whose pins the tool didn't produce"** (plan §4): this PR builds the tool those checks would call. Re-running the tool in CI needs network and upstream to be unchanged, so the runner decides where that check lives.
- **The real dry run** against current upstream, only partly. This session's network refused github.com's release downloads, `lscr.io`, ghcr.io's blob host, `keys.openpgp.org` and `qbittorrent.org`. Docker Hub answered: `gluetun 3.40.0` resolved `docker.io/qmcgaw/gluetun:v3.40.0` to `sha256:2b42bfa046757145a5155acece417b65b4443c8033fb88661a8e9dcf7fda5a00` (an index with linux/amd64 and arm64 among six platforms), with no catalogue change committed. A second run got Docker Hub's 429 and was refused with nothing written. A `workflow_dispatch` workflow can be dispatched only once it's on `main`, so the first dispatch after merge is the dry run for the native builds, and its report goes with the first pin PR (runner, 2026-11-11). The dispatches, each from `main`:
  - `gh workflow run companion-pins.yml -f companion=prowlarr -f version=<Prowlarr version, e.g. 1.28.2.4885>`
  - `gh workflow run companion-pins.yml -f companion=qbittorrent -f version=<qBittorrent version> -f tag=release-<qBittorrent version>_v<libtorrent version>`
  - `gh workflow run companion-pins.yml -f companion=gluetun -f version=<gluetun version, e.g. 3.40.0>`

## Tests (`tools/companion-pins/test_pin.py`, offline)
An in-memory network, and OpenPGP keys generated per run with `gpg --quick-gen-key` in a temporary home. No private key is committed.
- **Signatures:** a good signature by the pinned key; a tampered artifact (wrong SHA-256); a valid signature by an unpinned key; a key file carrying an extra key, or holding another key; a corrupted and a non-signature `.asc`; a signed message instead of a detached signature; a missing signature where one is expected; a signature redirected off the allowlist; a pinned fingerprint without its key file.
- **Downloads:** an unsigned pin; a redirect inside the allowlist; a host outside it; redirects to other hosts, `http`, a port, user information, SourceForge and FossHub; too many redirects; an oversized body, streamed and by `Content-Length`; HTTP errors; a signature appearing beside an unsigned artifact; the installer; bad versions and tags; mixed versions in one entry.
- **Determinism:** the committed catalogue formats to itself; a re-run, and a run from the pinned file, are byte-identical; duplicate keys are refused.
- **.NET and Prowlarr:** the `runtimeconfig.json` rules (AspNetCore only, .NET 6, a .NET 7 runtime under a .NET 8 `tfm`, unreadable), in zip and tar.gz; the source checks pass, skip tests and fail closed; an end-to-end Prowlarr pin of all three builds, the source and the image, leaving every other entry as it was.
- **Images:** the digest from the bytes, the token sent to its own host only; a wrong `Docker-Content-Digest`; `latest`; a token realm or redirect off the allowlist; an index without `linux/amd64`.
- **CI:** `ci.yml`'s `companion-pins` job runs them inside `ci-ok` when a PR touches `tools/companion-pins/` (a `companion_pins` output in `.github/scripts/ci_changes.py`, a shared edit the runner approved on 2026-11-11), and on every push to `main`.
