# P-v07 decisions (#514)

The planning slice for E-M7 (v0.7, build-plan P5). The plan is `docs/plan/2026-11-05-v07-m7.md`. These are the plan's structural choices, made under §2.19. Every product question (Q1–Q18) stays open in plan §6 until the runner or the owner answers it; none is decided here. No owner decision, security or content-safety decision, or owner-set number changes.

- **No schema bump, and no migration in any M7 slice.** v6 and v7 already define every SB-6 field M7 fills, and enrichment writes into the existing `title` and `tag` fields, so M7 keeps build-plan §1.3's "users rebuild once, v5 → v7". Usenet items fit V14's `unverified_items` CHECKs (networks 0–15, keys ≤ 64 B), but searching them needs SRC-3b, the runner's 2026-11-04 follow-up to SRC-3 that changes store triggers through a migration. The plan lists SRC-3b as a prerequisite of usenet search (UN-3), placed after GS-3 and ENR-11 because they share files; its number and the alternative (no usenet search in v0.7) are plan Q16.
- **Enrichment terms aren't SB-6 generations.** An enriched torrent's document is rewritten through `reindex_log` when its claims are stored, and unenriched ones don't change, so there's nothing to walk. Only GS-0, GS-2 and RX-1 raise generations.
- **Runner's review of #514 (2026-11-06), applied:** enrichment is the critical path, so ENR-9 takes the first M7 slot and Q5 is urgent; the producers (GS-0 → … → ENR-11) and the new live surfaces (TZ-0, UP-0, OUT-0) wait for the v0.5.2 cut (dep `P-v052-cut`), since a generation walk or a live route can't ship inactive; a new GS-gate slice puts `size-report --gate` in `ci-ok` before any producer lands; Q10 shrinks the producers first, and turning trigrams off by default is the owner's call, because it trades §1.6's regex budget for the 512 B; ENR-11 ships a bounded `reindex_log` sweep of torrents already holding v3 claims and indexes at most 8 alternative titles each; OUT-2 and UP-2 move to Opus; the harness files are `identify.rs`, so they're never confused with ENR-1's `enrich.rs`; SRC-3b also takes SRC-3 decisions item 4 (`fields_incomplete` on `/facets` and export, after OUT-0); low-resource mode is LR-0 in M8 hardening.
- **The search-core producers are one chain** (GS-0 → GS-1 → GS-2 → RX-1 → ENR-11; GS-1 for `compare.rs`) because they share `doc.rs` and `population.rs`, and three of them `query.rs`/`compile.rs`. The SB-6 walk serves every changed field in one pass, so chaining costs released users nothing; it costs wall-clock, which is why the chain gets the first M7 slot.
- **The `payload_sig` hash moves to `classify` with `fmix64`, giving the same value.** Filter (CS-8a, RP-5's SP-4) and search must hash the same way, or `sig:` and "block this payload" would disagree. `filter::payload_sig` keeps its `PayloadSig { sig, specific }` shape and its own `specific` rule on top.
- **One Opus slice per enrichment plugin, parser and glue together.** The v0.6 plan split them so Sonnet could take the glue. Here each plugin is ~500–650 lines, and pairing them halves the number of slices and reviews under four slots. The parsers stay Opus as CLAUDE.md requires. ENR-14 (Wikidata, no key, External consent) sets the pattern first.
- **Id families:** `GS-*` grouping and signatures, `RX-*` regex, `TZ-*` Torznab, `OUT-*` other outputs, `UP-*` upload and watch, `UN-*` usenet, `IRC-*` IRC; general enrichment continues the `ENR-*` family from `ENR-9`, as the rule-pack plan suggested, with plugins named `ENR-<service>`.
- **The upload exception's recommendation is written in plan §5** (raw `application/x-bittorrent` body on one route, admin session plus the same-origin check, bounded, one file per request, judged as a verified file). It is the recommendation owner §2.37 asked the runner to identify; UP-0 restates it in its decisions file before any code and the runner confirms it.
- **An uploaded or watched torrent with `private=1` is `private_source`.** BEP 27 forbids its hash on the DHT, and §18.7's isolation is the existing mechanism for that. This strengthens §18.7; it doesn't change it.
- **Owner-gated tails join G-v07 conditionally, by one rule** (Q1, Q2, Q3, Q4, Q6): a "no" removes the slice and leaves the gate reachable. Q5 is the exception: every general enrichment slice needs it, so it's required for v0.7.
- **"Same file" in v0.7 is `pieces_root` only** (plan Q18): the v1 per-file hashes would need a new indexed field.
- **Not sliced:** uTP (CR-4 has it), the companion-manager entry for SABnzbd/NZBGet (no §18.10 manager exists yet, Q14), DAT files and direct JSON API plugins (not in P5, Q15).
- **`runner/slices.yaml` and `runner/dashboard.yaml` are untouched,** as the brief says. Plan §4.1 has the entries ready to paste, and the new `ext:owner-v07-q1..q6` conditions and the E-M7 placement rule are listed for the runner.
