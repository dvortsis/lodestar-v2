# X-gluetun-restart-recover decisions

Two problems found on the cloud test VM (gluetun v3.41.3, PIA over WireGuard): gluetun restarted the VPN about every three minutes, and after gluetun's container restarted, Lodestar was left in gluetun's old, dead network until someone restarted it by hand. The recovery plan was the runner's call (2026-11-15, recorded as runner decisions under `docs/owner-decisions.md` §2.19).

## Health check
- **Every gluetun config we generate or ship sets `HEALTH_SMALL_CHECK_TYPE=dns`:** the companion generator (`crates/companions/src/compose.rs` and `unraid.rs`, so every compose and Unraid template, and the `packaging/companions/` copies), the guide's Compose recipe (chapter 3), the fleet stack (`infra/fleet/steps/vm/compose.yaml`) and the akamai example (`infra/akamai/terraform/pia-example/compose.vpn.yaml`). A test in `crates/companions/tests/templates.rs` fails if a gluetun template loses it, and `infra/fleet/tests/test_steps.py` checks both stacks.
  - **Why:** gluetun's default small check pings 1.1.1.1 and 8.8.8.8 through the tunnel. PIA, like many providers, doesn't answer ICMP: five VPN restarts in 12 minutes on the test VM. With `dns` there were none in the next 30 minutes (three in the first 20 s while DNS warms up). The post-rules weren't the cause: their ICMP DROP counter stayed at 0.
  - **Leak protection doesn't depend on it.** The setting changes only what makes gluetun restart its VPN. gluetun's firewall (the kill switch: `FIREWALL` stays on in every config) and Lodestar's post-rules (`gluetun-post-rules.txt`, unchanged) apply the same either way.

## Recovery after gluetun restarts
Two mechanisms, because neither alone covers every way gluetun restarts.
- **(a) Compose: `depends_on: {gluetun: {condition: service_healthy, restart: true}}`** on Lodestar in the guide's recipe and on every generated companion in gluetun's network (qBittorrent, Prowlarr, FlareSolverr through gluetun), and in the akamai crawler example. The fleet's Lodestar keeps `condition: service_started` and gains `restart: true`.
  - **Needs Docker Compose 2.17.0 or later.** Older Compose refuses the file ("Additional property restart is not allowed"). The generated companion files already needed 2.23.1, so nothing changes for them. The guide's recipe now says 2.17 and shows `docker compose version`.
  - **The gap it leaves:** `restart: true` acts only when Compose itself restarts or recreates gluetun (`docker compose restart gluetun`, `up -d` after a pull or an edit). Docker's restart policy restarting gluetun after a crash, `docker restart gluetun`, an update by another tool and a host reboot are not Compose operations, so Lodestar stays stranded. (b) closes that gap.
  - A companion routed through a gluetun you already run (`container:<name>`) is in another Compose project and can't depend on it. The guide's "restart it after gluetun" stays for those, and for Unraid companions.
- **(b) `LODESTAR_EXIT_ON_NETWORK_LOSS` (`crates/lodestar/src/net_watch.rs`).** Environment only (not a `config.toml` key, not in the Settings registry), off by default and in every native default. Set by our gluetun recipes only: the **Lodestar-gluetun** Unraid template (an advanced Variable, `true`; `packaging/unraid/validate.py` fails without it), the guide's Compose recipe and the fleet stack.
  - **The rule, Linux only:** every 5 s, read `/proc/self/net/dev`, `/proc/self/net/route` and `/proc/self/net/ipv6_route`. "Lost" means no interface but `lo` **and** no default route (up, not a reject route, not through `lo`; the kernel's unreachable `::/0` on `lo` doesn't count). It exits once "lost" has held for 30 s without a break.
  - **gluetun's own VPN restart never trips it** (runner's addition): `wg0` goes down but `eth0` and its default route stay, so there is still an interface besides `lo`. Only a namespace with nothing but `lo` counts. A test covers it.
  - **It never exits on doubt:** it arms only after it has seen an interface besides `lo` (so `--network=none` with the setting can't loop); a read that fails breaks the hold; while an update's self-test hasn't decided (`update::probation::Child::undecided`) it is disarmed, so its exit can't count as a failed attempt.
  - **Exit:** one Error line (`system.network_lost`), then the same graceful stop as a signal (the store is flushed), then status 75 (`EX_TEMPFAIL`). The Unix supervisor passes the child's status through, and the restart policy (`unless-stopped`, Unraid's) starts Lodestar again inside gluetun's current namespace. Unraid's Extra Parameters name gluetun by name, so it reattaches. A signal during that stop still wins: a plain stop.
  - **Off Linux** the setting is ignored with one Warn line (`system.network_watch_unsupported`), so a Windows or macOS install never exits from it.
  - **What the user sees:** that log line; the web UI's "Lost contact with the server" banner until Lodestar is back after its start wait; and in the guide, "When gluetun restarts or updates, Lodestar notices it has lost its network within about half a minute and restarts itself; the web UI comes back once its start wait is over." That sentence describes the current release's start wait; D-start updates it when CR-0w removes the wait.
- **(c) The fleet VM keeps `restart: "no"`, and its watcher is unchanged** (runner's call). With the setting, a gluetun restart outside Compose leaves a visibly dead Lodestar instead of one that looks alive in a dead network, and the watcher's `link_outage` note explains the gap. The soak's restart semantics don't change.

## Refinements for the runner to flag (§2.19)
- **Status 75** for the exit, and the 5 s sample and 30 s hold, are this slice's choices, approved by the runner with the plan.
- **v0.5.1 ignores the variable** (it reads only the variables it knows), so the Unraid template and the guide's recipe can carry it now. The guide marks the self-restart "(Newer than v0.5.1)" and keeps the manual restart, and what it costs (the six-hour sampling wait), for v0.5.1.
