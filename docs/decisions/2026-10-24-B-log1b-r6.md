# B-log1b decisions, part 4b: the runner's follow-ups to #163

The runner's review of #163 (2026-10-24) asked for these in a small PR after it. They refine part 4's file (`2026-10-24-B-log1b-r5.md`) and supersede it where they differ. No owner decision is reversed or loosened, and no security or content-safety decision is weakened.

- **The canary has a positive control for hashes.** Run 2's new case starts a server with the DHT on a loopback UDP port, bootstrapping from nowhere, so it hears only what the test sends it. With every event on, it sends a KRPC `get_peers` for a fresh key in each of three phases:
  - **Private:** the key is harvested as `ref:…`, and no key's hex is in that phase's lines.
  - **The hash kind on:** that phase's key is in the file, as hex.
  - **Off again:** no key's hex is in that phase's lines.

  No key's hex is ever on the console.
  - **Each phase is judged by its own lines.** After a harvest, the pipeline's own lookup for the key logs it again (source `lookup`) under whatever the kind is by then.
  - **This supersedes r5's limit for hashes.** Paths, names and queries stay limits as r5 names them.
  - **Peers stay a limit too.** `fetch.failed` needs a fetch from a peer that fails, and the canary has no peer to dial. `logging::tests` holds it per output.
- **`search.enrichment_unreadable` is `Trace`, off by default** (it was Debug and on). It's a line per document, and a rebuild over a store of bad records would write one each at Detailed, which breaks Build 3's rule.
- **The summaries say "since the last summary"** (`dht.harvest_summary`, as `fetch.failed_summary` already did), and their `seconds` field gives the window.
- **`fetch.failed_summary`'s counters are aligned to their own cache lines** (`#[repr(align(128))]`).
- **Counting is tested at the one place it happens:** `fetch()` counts its final result once (`counted`). A success or a blocklisted address counts nothing, and any other failure counts by its kind. `fetch_via`, which runs once per transport, doesn't count, so a uTP failure before a TCP success counts nothing.
  - A test that drives the fallback and reads the global counters would race the other fetch tests in the same binary, so the test is on `counted`.
- **`log_lint.py`:** a list declared with no value (`NOT_YET_SWEPT: list[str]`) reads as unreadable, so the base check fails closed. This is tested.
- **The unused `tracing` dependency is dropped** from `crates/pipeline` and `crates/search`, and `fuzz/Cargo.lock` is refreshed for the workspace's own crates only (`cargo update -w`): `lodestar-log` added and `tracing` removed, with no third-party version changed. These three paths are outside the brief's list; the runner's review of #163 asked for both changes.
- **The canary case waits for what it needs, never a fixed time:** each phase waits for its own key's `get_peers` line, so the pipeline's later `lookup` line for an earlier key can't end the wait. Each switch of the hash kind waits for its `logging.kind_switched` line. Turning every event on waits for the `logging.applied` line that says Everything applied, since the key's line is Trace and its resends are dropped as seen. Its DHT port is probed and released before the server takes it, so another test could take it in between; the server then fails to start, and the case fails waiting for the setup token. A server that binds port 0 and reports it would close that gap, but the DHT doesn't log its port.
