# OP-4 decisions (the operator agent and its bridge)

The slice builds the operator's agent files, `operator-apply.yml`, `operator-wake.yml` and `operator-tripwire.yml`, with their code in `infra/operator/`, as the plan's OP-4 row asks (`docs/plan/2026-11-08-cloud-operator.md` §1–§4). Nothing calls an API in tests or CI. These are the choices the plan left open, or narrowed. None loosens an owner decision or a security decision, or changes an owner-set number. The runner flags them to the owner (§2.19). The first item departs from the plan's wording, so the runner should look at it first.

## Apply
- **`operator-apply.yml` calls the Managed Agents API directly instead of running `ant apply`.**
  - **What:** `agent_apply.py` creates or updates the agent, the environment and the vault from `infra/operator/agent/`. It updates the agent with its recorded version (optimistic concurrency: a 409 means someone changed it outside the workflow). It keeps the IDs in `operator/claude-lock.json` in the control bucket, written with If-Match, in its own small format.
  - **Why:** `ant` is a downloaded binary, and it would run in the job that holds the workspace key. Its release can't be pinned by hash from a session here (no route to its releases), and the repo pins every action by SHA and every Python wheel by hash. The API calls are few, and they're tested on fakes.
  - **The plan's file and key names stay:** `claude-lock.json`, and the bridge role's grant on it.
- **The rendered agent:**
  - the routine model comes from `OPERATOR_MODEL_ROUTINE`, at `effort: medium`;
  - the system prompt gets `RUNNER_USER_ID`, `OPERATOR_BOT_USER_ID` and `CHANNEL_PR` filled in. These are public numeric repository variables. A change to any of them, or to the model, needs `operator-apply.yml` run again;
  - web tools are off and the toolset is on `auto`;
  - `limited` networking allows `api.github.com` only, with package managers and MCP hosts off;
  - the vault has one `environment_variable` credential, `GITHUB_TOKEN`: header only, `api.github.com` only. It holds a placeholder until a wake fills it.
  - No model ID is committed, and a test checks that.
- **Who may apply:** only the owner (`github.actor_id == vars.OWNER_USER_ID`, OP-1's variable), on a first attempt, from `main`, with `OPERATOR_STOP=false`. Apply takes the operator lock, so the agent never changes under a live session.
- **What a re-run of apply doesn't do:**
  - It updates the agent, the environment and the vault's name, but not the credential. A change to the credential's `networking` or `injection_location` in `vault.json` needs the credential archived and recreated by hand, and its new ID written into `credential_id` in `claude-lock.json`. Apply refuses a lock file with a field missing.
  - A first run that fails partway can leave orphan resources that `claude-lock.json` doesn't record. They hold only the placeholder, never a token: the bridge writes tokens only to the recorded credential. The owner archives them in the Console.

## The bridge (`operator-wake.yml`)
- **The ledger checks run in the `cloud-operator` job, not the filter job.** The id-is-new check, the rate limit and the $200 total all need the Anthropic key, and the plan's filter job has no secrets. So the filter does what it can without secrets (the channel PR, `created` only, the runner's numeric ID, the header and the stop). The wake job repeats all of that in code, then takes the lock, then checks the ledger. That way nothing paid starts and no token is minted before every check has passed.
- **The ledger is the workspace's own sessions, archived ones included** (`GET /v1/sessions?include_archived=true`). No extra S3 key is used.
  - **Id is new:** each session carries `metadata.instruction_id`.
  - **Rate:** at most 6 sessions an hour and 60 a day. OP-5's harness sessions count too.
  - **Spend:** the summed `usage.list_cost`, plus this session's own budget, must stay at or under $200. That is a little stricter than "refuse past $200": a session can't take the total over the cap.
  - **Fails closed:** an unreadable entry, a currency other than USD, a bad timestamp, or more than 50 pages refuses.
  - **The 50 × 100 page cap:** once the workspace holds more than 5,000 sessions, archived ones included, every wake refuses. The owner then deletes old sessions in the Console (archiving isn't enough, since archived sessions still count), never the most recent one, which the next wake looks for. Deleting removes their cost from the ledger, so do it only with the $200 total in mind; the Console's workspace spend limit still holds.
- **`mode: triage` is an optional instruction field** (default `routine`), so the runner asks for triage itself. Triage is an `agent_with_overrides` session with `OPERATOR_MODEL_TRIAGE` at `effort: high` (an override replaces the whole model object) and a $15 budget. Routine sessions pin the agent version from `claude-lock.json` and have a $3 budget.
- **The App token:**
  - it's asked for this repository only, with `pull_requests: write` and `metadata: read`;
  - if the reply shows any other permission, another repository, or a selection that isn't `selected`, the token is revoked at once and the wake refuses;
  - the JWT is signed in pure Python, so the private key never reaches a file or a subprocess;
  - after the session, the token is revoked and the vault credential is reset to a placeholder.
- **Every session is archived when it ends, a normal end included.** An idle session keeps its vault attachment, so whoever holds the workspace key could later resume it and use the next wake's token.
- **The ledger cross-checks itself.** Each wake records its session in `claude-lock.json` (`last_session_id`, If-Match). The next wake refuses if the list doesn't contain it: if archived sessions ever stopped appearing despite `include_archived=true` (documented for `GET /v1/sessions`), every total would read low, and the cap would fail open.
- **Stale sessions are archived first.** A cancelled or lost job can skip its cleanup. So, before minting a token, each wake archives any session that has a bridge `run_id` and isn't archived, and says so on the channel. OP-5's harness takes the operator lock, so it never has a live session at that point.
- **Pre-lock failures are answered.** A missing setting, a failed OIDC or S3 call, or a lock error still posts a fixed escalation, so the runner never waits on an instruction that won't run.
- **Watching the session:** it's polled every 10 s, with a 30-minute deadline, through `GET /v1/sessions/{id}` and its event list. This uses the standard library only; the SSE stream would need a parser. At the deadline the bridge sends `user.interrupt` and escalates.
  - **After an interrupt** the bridge waits up to a minute for the session to stop before it archives, since a running session can't be archived.
  - **A disabled `operator-wake.yml` stops a live session.** Each poll reads the workflow's state (`actions: read`), so a tripwire trip, or the owner's kill-switch step 2, interrupts the session at once. Disabling a workflow doesn't cancel a job that's already running. A failed read doesn't stop anything.
  - **Calls paused for approval:** each one is denied once, with a message telling the operator to escalate.
  - **Stalls:** a `requires_action` with nothing left to deny, for a minute, counts as a stall and is escalated.
  - **Budget stops and errors** (`budget_reached`, `retries_exhausted`, a terminated session with an error) are escalated too.
- **The bridge's escalations** are `operator-report v1` comments with `kind: escalation` and id `bridge-<run>-<attempt>`, posted with the job's `GITHUB_TOKEN` (`github-actions[bot]`, which the reader helper trusts as the control plane). Busy and refusal notices are fixed lines.
- **The operator lock is `locks/operator.json`**, with a 60-minute TTL, above the wake job's 45-minute timeout. A held lock answers "busy, retry", and a run never takes it twice. An unreadable lock fails closed until it's cleared by hand.
- **HTTP:** standard library only. Requests go to `https://api.anthropic.com` and `https://api.github.com` only, with the URL checked before any request. Redirects are refused, and each call has a 30 s timeout. Errors carry the method and the first two path segments, never an ID, a body or a token. A list of more than 50 pages refuses rather than give a partial ledger.
- **A runner comment on the channel that isn't an instruction gets no reply.** Every other refusal is answered with its fixed reason.
- **The API version header** is `anthropic-version: 2023-06-01` with the `managed-agents-2026-04-01` beta. The plan's first-run test (§5) is what proves the live calls.

## The operator's side
- **The agent fetches `infra/operator/thread.py` and `infra/fleet/reader.py` from `main`** through the contents API, without a token (the repository is public, and the App has no Contents permission). If the fetch or the helper fails, it escalates and ends its turn instead of reading the thread another way. It reads the channel only through them. `thread.py post` accepts only a report or a one-line `/fleet` command. Like the plan's reading rule, this is a prompt rule backed by OP-5's injection test, not a hard barrier.

## The tripwire
- **One workflow, `operator-tripwire.yml`:**
  - `pull_request_target` for the plan's eight types;
  - `issue_comment` for `created`, `edited` and `deleted`;
  - an hourly sweep, plus the same sweep at the end of every wake (a job in `operator-wake.yml`).
  - No secrets, no environment.
  - The trip job gates on `github.event.sender.id` in its job-level `if:`, checks out `main` (never PR code), and reads only numbers and event enums.
- **It's stricter than the plan:** the bot may only post a new comment on the channel PR. Anything else the bot does, on the channel PR too, is a trip: an escalation, then `operator-wake.yml` disabled (`actions: write`), never `fleet.yml`.
- **What the sweep checks** (a 130-minute lookback, two hourly runs, so a delayed or dropped scheduled run is still covered):
  - issue events by the bot;
  - PRs the bot opened that were active;
  - reviews and review comments by the bot;
  - the bot's comments on other PRs, and its edited comments.
- **A base-branch change or an edited review comment by anyone** is escalated without disabling anything, because the API can't say who made it.
- **The sweep fails closed.** A list that runs past 10 pages counts as a trip: an escalation, then `operator-wake.yml` disabled (the runner's call). An API error posts a best-effort escalation and fails the job, so the run shows red.
- **A PR against an old base** runs that base's copy of the tripwire, if it has one at all.
  - The sweep still catches what the API attributes to the bot there: issue events (renames, labels, close and reopen, draft toggles, base changes), reviews, review comments, and PRs the bot opened.
  - An edit to the body of someone else's PR on such a base leaves no attributable record, so neither the trip job nor the sweep sees it. That is the plan's accepted residual, and the steward rule covers it: a PR body, title or review body never counts as an instruction, a finding or a verdict.
