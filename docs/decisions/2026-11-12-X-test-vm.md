# X-test-vm decisions

An interactive, disposable test machine for each platform, so Claude sessions can build, test and run bounded, VPN-isolated DHT crawls on real Linux and Windows hosts. It is separate from the Terraform fleet (`infra/akamai/terraform`, `infra/fleet`), whose shared state backend is unresolved (`docs/operations/fleet-backend-investigation.md`). Nothing here changes the fleet, the watchdogs or GitHub OIDC. Its only IAM is what `infra/dev-vm/aws-claude-testvm.json` creates (the `lodestar-claude-testvm` user, its managed policy, and the Windows and Linux test instance roles with their instance profiles), and it changes no other IAM.

**Runner's calls under §2.26, flagged to the owner under §2.19:**
- **Linux machine type `g6-dedicated-4`** (4 dedicated vCPU, 8 GiB, 160 GB, $0.108/h), not the plan's shared `g6-standard-4`.
  - Dedicated CPU has no steal from neighbours, so crawl and bench numbers repeat. 8 GiB matches the plan's Main.

- **Outside both reapers' scope on purpose.** The legacy watchdog matches `lodestar-*` labels with `lodestar` and `test` tags; this VM is `claude-dev-*`, tagged `claude-dev`. The watchdog would delete it at 48 h mid-test, and its deletion path is unproven anyway. Cleanup is `devvm.py delete`, which verifies a 404, plus the owner's revocation of the token. The monthly cap bounds the cost if both are missed.
- **Firewall: inbound DROP, with TCP/22 only from the owner's current `/32`.** No UI port and no DHT listener is public. The UI is reached over `ssh -L`, as in the fleet plan (ground rule 7). `devvm.py set-admin-ip` moves the `/32` when the owner's address changes, and LISH is the way in out of band.
- **The host key is pinned before first contact** (the fleet's OP-2 pattern): `devvm.py` generates the ed25519 host key, puts it in the user data, deletes the local private copy, and records the fingerprint. The user data also holds the owner's public key, and nothing secret beyond the host key. That private key stays readable through the metadata service while the VM exists, which is accepted: it lives only as long as the VM.
- **Disk encryption is on, and backups are off.**
- **The toolchain comes from upstream:** Docker's apt repo, Node 22 from nodejs.org checked against its SHASUMS, rustup, and Claude's native installer. An 8 GiB swap file covers release builds with LTO.
- **Claude Code on the VM runs under the owner's own login, in `tmux`, through Remote Control**, so it shows in the owner's Claude app. Only outbound HTTPS is used, and no cloud credential goes onto the VM.
- **PIA credentials are typed by the owner on the VM** into `infra/pia-bridge/vm/pia-wireguard.sh`'s flow. They never go in chat, git, user data or a session environment.
- **Crawls on this VM are exploratory leads, never CR-SPEC evidence,** under the cloud test plan's ground rules (`docs/plan/2026-11-08-cloud-test-plan.md`). Rule 5, metadata only, nothing identifying leaves the VM, applies unchanged.

## Review fixes (2026-11-16Z, the coordinator's calls)

- **Claude's stop, delete and run-command rights need `Purpose=X-test-vm`,** and every launch must carry that tag. The owner's own fleet instances share `Project=Lodestar` and `Environment=Test`, so those two tags alone left them in reach. This tightens the guardrail and loosens nothing.
- **Canonical's publisher account is a template parameter (`UbuntuImageOwnerId`)** the owner looks up at deploy (the image's Owner in EC2 → AMIs), so no file under `infra/dev-vm/` holds a 12-digit number.
- **A failed VM create on Linode deletes its firewall only if no VM came of it.** A client-side timeout after Linode accepted the create would otherwise leave the VM with no firewall.
- **On AWS the `lodestar` user loses sudo and the `docker` group,** and the launch policy requires an IMDS hop limit of 1. The secret was approved as readable by the instance's root only; without these, any code run as `lodestar` could reach the role. Builds run as `lodestar`, and everything else as root through SSM.
- **On AWS, root runs the stack from `/opt/lodestar-run`, which only root owns,** and `pia-login.sh --aws-secret` refuses any other kind of folder. Under `~lodestar`, code running as `lodestar` could rewrite what root runs and reach the role.
- **Correction, for the owner (§2.19):** the 2026-11-15 approval said Claude's AWS user can't read the PIA secret. That user is denied the Secrets Manager API, but Run Command runs as root on a Linux test instance, and root there can use the instance role. So a Claude session can reach the secret. It is kept from doing so by rule (never read, print or copy it), not by a technical control. The owner-facing text now says so.

The owner's own instance role is no longer a parameter and can't be passed.
  - **Residual risk, accepted:** the test user can still launch a Windows instance with the Linux profile. IAM can't tie a profile to an image in one statement without something fragile, so the Windows runbook names the Windows profile only. The user can already reach the secret through the Linux lane, so this widens nothing for the user itself; it matters only for software on a Windows instance launched with the wrong profile.
- **Stop, start, reboot, delete and Run Command reach only instances the same principal launched** (I1): every launch must carry `LaunchedBy=${aws:userid}`, tags can be set only at launch, and those actions require the tag to match the caller. Launches need default tenancy (I4).
- **Every statement of the policy is pinned exactly in a test** (I2), so any widening fails until it is reviewed.
- **No instance attribute reads** (O4): an explicit deny on `ec2:DescribeInstanceAttribute`; nothing in the runbooks uses it.
- **`pia-login.sh --aws-secret` runs only a root-only copy of the step and CA**, checked before the secret is read (O2).
- **`Connect-TestVm.ps1`** (I6): the test VMs use their own SSH key, never the Akamai fleet's, which the script refuses (S1); the setup script runs from a pipe and Claude starts without a script file, so nothing is left in the VM user's home (S2); SSH trusts only the pinned host key, also as the global known-hosts file, and forwards nothing whatever the PC's SSH settings say (S3).
- **`devvm.py` refuses multicast admin addresses**, and the tests pin that private and reserved addresses change nothing and that near-miss firewalls are never touched (I8).
- **The runbooks** mark the Linode flow and the Windows Phase 1 as historical, and point to the current flows (I5).
- **Not changed (O3):** IAM has no condition that counts a launch's volumes. Each volume is bounded (encrypted, at most 100 GiB, tagged), and the per-cloud spend check bounds the rest.
