# ENR-tvdb decisions (TheTVDB v4 parser and plugin, Account)

Slice ENR-tvdb (API lane, 2026-11-15). Spec: plan `docs/plan/2026-11-05-v07-m7.md` (ENR-tvdb row, Q4, Q5, Q12), architecture §18.2, §18.7, §18.9, and ENR-14's pattern (`docs/decisions/2026-11-12-ENR-14.md`, "How to add the next plugin"). It copies Wikidata's shape. Only what differs is recorded here.

## Terms and usage policy (owner §2.28), checked 2026-11-15
- **How it was checked:** TheTVDB's own pages, read directly on 2026-11-15: `https://thetvdb.com/api-information` (API licensing), `https://thetvdb.com/api-information/signup` (key tiers), `https://thetvdb.com/tos` (terms of service, "last updated on: October 23, 2020"), and the API's OpenAPI document `https://github.com/thetvdb/v4-api` `docs/swagger.yml` (v4.9.0).
- **What they require, and what the plugin does:**
  - **Access is through a licensed API key, per product.** The terms grant a "non-exclusive, non-transferable, revocable and limited license to access and use the API solely for the product" approved at sign-up, and may cancel access for sharing credentials. Projects with under $50k of revenue get a key for free, "requires attribution"; a user-supported key adds the subscriber's PIN at login. **The plugin ships no key.** You sign up for your own key (and, for a user-supported key, enter your PIN), which is what the Account class asks for (§18.7). Nothing of one install's key is shared with another.
  - **Attribution.** The API page: unless TheTVDB approves otherwise, end users who see its metadata must see "attribution with a direct link to TheTVDB.com"; its sample text is "Metadata provided by TheTVDB. Please consider adding missing information or subscribing." with a link. **The plugin carries that text and link as `tvdb::ATTRIBUTION` and `tvdb::ATTRIBUTION_URL`.** `lodestar_sources::Manifest` has no attribution or description field, and the catalogue has none either, so they can't be shown from this slice without cross-crate UI work outside its files. **For the runner:** the UI that shows an identification (the detail drawer's "Identified by", `crates/api/src/dto/torrents.rs`) and the Sources row must show `ATTRIBUTION` with its link wherever TheTVDB's data is shown, before the source can be switched on. That's a follow-up (a manifest field, or a per-plugin notice the API serves).
  - **No numeric rate limit**, only "excessive calls to the API, as determined by us" are prohibited. **The plan's cap holds: at most one request a second, no burst** (§2.26), one lookup at a time, back-off from 60 s to 6 h after a 429 or 5xx. A lookup is one search; a login happens about once a month (a token lasts a month, renewed after 25 days).
  - **Redistribution.** The terms forbid reselling or distributing "the API or the Data", and creating derivative works. The plugin stores an identification as the plugin's own local claims (Account class: results local-only, §18.7). **Doubtful, for the runner:** whether TheTVDB-sourced alternative titles or ids may then leave the install through Torznab, Stremio or the bitmagnet export (OUT-*). Ids alone are facts; titles from its translations may count as its Data. That's a decision for the output slices, flagged here.
  - **Images and media** need the content owner's permission. The plugin never reads an image, a poster, a thumbnail or an overview.
- **What a lookup costs the service:** one search answer of up to ten results (each a few KiB with its translated overviews; the cap is 1 MiB). At one request a second the ceiling is 86,400 lookups a day, under Q12's 100,000; user interest and the cache keep it far below.

## Terms (ENR-terms), checked 2026-11-16
ENR-terms (#962) gives every plugin a `Terms` and an adult marker on each answer (`crates/sources/src/terms.rs`). TheTVDB's `tvdb::TERMS`, from the pages above (its "API Information" page, its terms of service and the v4 OpenAPI document, read again on 2026-11-16):
- **`background_walk: false`.** The licence is "limited" and "solely for the product", and the terms prohibit "excessive calls to the API, as determined by us". Nothing clearly allows bulk use, so it looks up only the items you open, within its cap.
- **`redistribute: false`.** The terms forbid distributing "the API or the Data". Its answers stay in Lodestar's own UI and never rename the record that search, Torznab and export serve. This settles the "Doubtful, for the runner" point above the strict way.
- **`retention: Retention::DEFAULT`** (180 days). The terms set no shorter limit on keeping what the API returned.
- **`attribution`: `tvdb::ATTRIBUTION` linking `tvdb::ATTRIBUTION_URL`.** The API page requires an attribution with a direct link to TheTVDB wherever its metadata is shown; this is its sample text. ENR-terms' `Attribution` is now the field the follow-up above needed: the runtime shows it beside its answers.
- **`adult_marker_required: false`, `adult: None`.** TheTVDB's v4 search results have no adult or mature field, and `/search` has no filter for one. The runtime's gate never asks about an Adult item, and the plugin's kind is TV only. A marked-adult answer is still refused by the runtime (`terms_tests`).

## Account class, off by default
- **The manifest:** `tvdb`, an Enrichment source, Consent `Account`, Risk Low, endpoint `https://api4.thetvdb.com` only, `enabled_by_default: false`, never always-adult, never finds private. Nothing is sent until the key is stored and the source enabled (`off_by_default_nothing_is_sent`).
- **Credentials** (`Policy::credentials`): `api_key` (required) and `pin` (optional, user-supported keys only), both `Secret`, stored through the credential store (SRC-4) and never a setting (empty `CONFIG_SCHEMA`). `Tvdb::need` judges against the spec, so a PIN alone doesn't stand in for the key. Both are read on each lookup, the PIN even when absent, so what's read is exactly what's declared (`credential_spec.rs`).
- **Checked before use:** a key is 1–128 ASCII letters, digits and `-` (v4 keys are UUIDs); a PIN 1–64 letters and digits. Anything else is "isn't valid" and nothing is sent. Because of that check the login body is built from a fixed template (`{"apikey":"…","pin":"…"}`) with no escaping needed.
- **Kinds: TV only.** TheTVDB's search also has movies, but a TVDB movie id and a TVDB series id are separate number spaces, and the stored `tvdb:` scheme (ENR-9, ENR-11, Torznab's `tvdbid`) means a series. A movie match would write a `tvdb:` id that names another work. Films are TMDB's (ENR-tmdb) and Wikidata's. A film query sends nothing.
- **No host wiring**, as ENR-14: library code, listed in the catalogue.

## The token
- **Only in memory.** `/v4/login` turns the key (and PIN) into a bearer token, held in the plugin's struct in a zeroizing `Secret` beside a fingerprint of the key and PIN it was issued for (SipHash with a random per-process key, so no copy of the key is kept) and when. It's never written to the store, `source_state`, a log, an error, `Debug` or a fixture; it goes only in the search's `Authorization: Bearer` header. `Tvdb`'s `Debug` names nothing. A changed key or PIN gets a new token; a token older than `TOKEN_TTL` (25 days; TheTVDB's last a month) is renewed before use.
- **A refusal never loops (the host limiter's rule).** `lodestar_sources::http::classify` treats a 401 or 403 as the host refusing us: it holds every request to the host, to the back-off ceiling (6 h) when the answer names no `Retry-After`. So a lookup sends at most one login and one search, and nothing is retried inside it. **A 401 on the search** drops the held token ("refused the session"), and the first lookup after the hold logs in again: the token is refreshed once. **A token refused just after it was issued, or a refused login**, is the key refused (`REFUSED`), and the hold covers the next attempts too. The brief asked for "refresh on 401 once, then fail cleanly": that's met across lookups instead of within one, because the shared limiter (outside this slice) won't send to a host that just refused us. **Doubtful, for the runner:** a stale token costs up to 6 h of lookups. Proactive renewal at 25 days makes that rare; letting a plugin answer a 401 without a host-wide hold would need a change to `crates/sources/src/http.rs`.
- **Tests:** `a_401_refreshes_the_token_once`, `a_second_401_fails_cleanly_not_in_a_loop` (five requests in all, then held), `a_refused_key_is_held_and_never_retried_in_a_loop`, `the_token_is_renewed_when_old`, `the_token_is_reused_and_lookups_are_paced`, and `no_key_or_a_bad_one_sends_nothing`. Every error is checked to hold no key, PIN, token or service text.

## What is sent (Q5)
- **Login:** `POST https://api4.thetvdb.com/v4/login`, `Accept` and `Content-Type: application/json`, body `{"apikey":"…"}` (and `"pin"` when stored). No item data.
- **Search:** `GET https://api4.thetvdb.com/v4/search?query=<title>&type=series&limit=10`, `Accept` and `Authorization`. The title is one parameter encoded by the `url` crate's form encoder (`a_hostile_title_is_one_parameter`). **The year isn't sent:** TheTVDB's `year` filter would do the same work, but the year is only needed locally to choose, so it stays home. Ten results, not five: a series search ranks spin-offs and specials near the top.

## The parser (`sources-feeds/src/tvdb.rs`)
- **Wikidata's rules:** the shared bounded JSON reader, pure, no panics or unwraps, repeats found with a bitmask over the keys read and a scan of what's kept (at most `max_texts` translation languages, past which the rest are passed over and the result says `truncated`). `many_unknown_keys_are_read_in_linear_time` reads 300,000 unknown keys in the root and in a result.
- **The caps, as named fields of `Limits`:**
  - `SEARCH_LIMITS`: 1 MiB, depth 16, 100,000 values, 1,000 elements per array, 64 KiB per decoded string (an overview passed over is skipped, not decoded, so this bounds titles and ids), 10 results, 64 titles per result, 32 remote ids and 16 genres per result. A result's translated overviews are most of its size, a few KiB each, so ten results stay well under 1 MiB.
  - `LOGIN_LIMITS`: 16 KiB, depth 8, 256 values; the token at most `MAX_TOKEN` (4,096 bytes, the credential store's value limit; a JWT is under a kilobyte).
  - Past the result cap the parse stops (`Stop::Items`), so the answer isn't whole and is an error, never a miss.
- **Strict shape:** whole means read to its end, `status` is `success`, `data` is there in the type asked (an array or `null` for a search, an object for a login), no repeated or escaped root key, nothing trailing and nothing skipped. In a result, an escaped or repeated read key, a field of the wrong type, a translation key that isn't a language tag or is repeated, a `year` that isn't four digits, a `first_air_time` that isn't `YYYY-MM-DD`, or a remote id without `id` and `sourceName` spoils it. Optional fields may be `null` or empty. A `status` other than `success` on a 200 is an API error: the plugin holds itself for its `Retry-After` (60 s if none, 1 s to 1 h), as Wikidata does for `maxlag`. **A login answer that isn't whole yields no token** from the parser itself, not only from the plugin's check: CI's `fuzz (tvdb)` found a 66-byte answer (no `status`, bytes after the root) where the parser returned a token beside a page that wasn't whole. The plugin checked `whole` first, so no such token was ever used, but the fuzz target's invariant is the right one: the parser now drops it, and the input is a regression test and the seed `fuzz/seeds/tvdb/login-trailing.bin` (runner, 2026-11-16).
- **What it keeps:** `tvdb_id` (1–20 digits, no leading zero), `type`, `name`, `aliases`, `translations` (language → name), `primary_language`, the years of `year` and `first_air_time`, `genres`, and from `remote_ids` only an `IMDB` title id (`tt…`, never a person's `nm…`) and a `TheMovieDB.com` id. Never an overview, image, network, company, director, person, slug or other remote id. **The token** must be 1–4,096 bytes of letters, digits and `-_.~+/=`, so nothing in it can end a header (`tvdb_bad_token`); it's kept in a `Token` whose `Debug` prints its length.
- **To confirm against real answers** (the fixtures are hand-written from the OpenAPI document): whether `data` is `[]` or `null` for no result (both read as no match), whether `year` is always four digits, and the exact `sourceName` spellings (`IMDB`, `TheMovieDB.com`). A different spelling means a missing cross-id, never a wrong one.

## Choosing a match (`tvdb::choose`)
- **One series must agree:** `type` is `series`, a title (name, alias or translation) equal to the query's after Wikidata's fold, and the query's year among its years when it has one. The same `tvdb_id` listed twice is still one. None, or two different series, is no match (`tvdb_candidates`).
- **Confidence:** 90 with a matching year, 70 without, as Wikidata.
- **The answer:** `tvdb:<id>`; `imdb:` and `tmdb:` only when the series holds exactly one value of each; the English translation (else the name) as the canonical title; the name in its primary language, the other translations and the aliases (language `und`) as alternative titles; its genres; the year. TheTVDB's ISO 639-2 codes are stored as the two-letter BCP 47 tag where one exists (`eng` → `en`, `jpn` → `ja`, 26 codes in `tvdb::LANGUAGES`); any other code is kept as written, which is still a valid tag. ENR-10's `into_claims` clamps it again, and the writer judges every title before storage (`an_answer_is_judged_and_a_held_one_is_not_stored`).
