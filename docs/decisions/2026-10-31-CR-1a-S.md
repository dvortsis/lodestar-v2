# CR-1a-S decisions (part 1)

Streaming peer batches (`LookupSession`) between the DHT actor and the fetch pool, behind their own switch (master plan, lane C; `docs/plan/2026-10-27-streaming-and-hints.md`, "Current boundary and required replacement", "Bounded peer delivery", "Independent lifetimes"). Part 1 is the boundary, the actor's batching, the pool's ownership and the regression cases. Part 2 adds the CR-SIM switch and screen, the metrics export and their `docs/metrics.md` contract, and the screen's results. No cap, timeout or rate changes: the 32 owned requests, the pool's 256 lookups and 32 peers per key, `lookup_wait` (30 s), `LOOKUP_DEADLINE` (25 s) and the 64-query budget all stay.

## The switch

- **`dht.streaming_peers`, a bool, off by default.** It's set in `config.toml` (`[dht] streaming_peers = true`) or with `LODESTAR_DHT_STREAMING_PEERS=true`, read at start. A bad value is a config error (`streaming_peers_is_off_unless_asked_for`). It isn't in the Settings UI; like the other crawler candidates it needs a restart.
- **It lives in the pool** (`PoolConfig::streaming_peers`). The actor serves a streaming request whenever one arrives, so it needs no switch of its own.
- **Off is today's behaviour exactly.** The pool sends `PeerRequest.session: None`, every request takes the existing `Admission`/`Completion` path, and every new branch keys off `Request::streaming`, which is false. The plugin forwards with `request_peers_with` as before. The new counters stay 0 (`off_sends_no_session_and_counts_nothing`), and the CR-SIM goldens are byte-identical (checked in part 2, which adds the switch to CR-SIM).

## The boundary as built

- **`PeerRequest` gains `session: Option<SessionAdmission>`**, declared before `permit` so a request dropped whole closes its admissions before its permit returns (CR-ADM's ordering). `admit` keeps its type, so finders and tests that don't stream are untouched.
  - A streaming finder answers `session` with `Some(LookupSession)` or `None`, and drops `admit`.
  - **Refinement:** a finder that doesn't stream may answer `admit` as before and drop `session`; the pool accepts that as an ordinary final answer (`a_finder_that_does_not_stream_still_answers`). Only both admissions closed reads as unacknowledged.
- **`LookupSession { batches, terminal }`**: a `mpsc::Receiver<Vec<SocketAddr>>` of capacity `STREAM_QUEUE` and a separate `oneshot::Receiver<Terminal>`. `Terminal` is the fixed enum `Complete`, `Deadline`, `Cancelled`, `SourceFailed`, with no peer list. Rejection stays `None`.
- **`lodestar-dht` still doesn't depend on `lodestar-sources`, nor the other way round.** The actor talks to the caller through two small traits, `SessionAdmit` (is the caller gone, admit with a batch receiver, refuse) and `SessionEnd` (send the terminal). The DHT plugin (`crates/pipeline/src/dht.rs`) adapts the pool's session to them (`PoolSession`, `PoolEnd`); `lodestar-dht` implements them for its own `LookupSession` for direct callers and tests. The actor's `LookupEnd` has three variants: it never sends `SourceFailed`, which is only how the caller reads a dropped terminal sender.
- **Allocation after admission.** `NodeHandle::request_session` sends `Command::RequestSession`. The actor's admission is shared with `RequestPeers` (`admit_request`, same precedence and counters). The batch channel and the terminal are created only in `Admit::accept`, after the capacity check; a caller that went before hearing gets nothing, the channel is freed at once, and it counts `ack_failed`. A refusal answers `None` before the permit returns, as CR-ADM requires; a failed handoff drops the admission before the permit.

## Bounded delivery (actor, `crates/dht/src/node/stream.rs`)

- **Candidate defaults (§2.19), named constants, from the spec:** `STREAM_BATCH = 8` endpoints per batch, `STREAM_QUEUE = 2` queued batches per session, one actor-pending batch, `STREAM_SEEN = 32` endpoints in a session's seen set.
- **Every endpoint is checked before buffering.** A reply's values are normalized (`lodestar_network_policy::normalize`) and filtered by `endpoint_allowed` (the existing public-endpoint policy) in `on_response`, then offered to the session, which dedupes against its seen set. The pool dedupes against the entry's retained and tried peers (`add_peers`). Once the seen set is full, further endpoints are ignored and counted (`peer_stream_seen_full`); the set never grows.
- **A dropped peer stays seen.** A new endpoint enters the seen set before the room check, so a peer dropped to backpressure isn't offered again later in that session, and drops count toward the 32. This keeps the set's meaning simple ("offered once") and the churn bounded; the spec doesn't say which. The loss is counted either way.
- **Full channel:** new peers merge into the one pending batch; past it they're dropped and counted (`peer_stream_backpressure`). The maintenance tick retries a held batch, so it goes out once there's room even if no reply arrives.
- **Termination:** when the last family leg ends, one nonblocking flush, any pending peers counted as backpressure discards, the batch sender closed, then the terminal sent. The terminal never waits for channel space. Discards to a caller that has gone aren't counted as backpressure.
- **Terminal kind:** `Deadline` if the request's 25 s deadline ended it, `Cancelled` if the caller had gone, else `Complete` (converged or out of its 64 queries). Counted in `peer_stream_terminals`.
- **Cancellation is seen with the channel full:** the actor checks `mpsc::Sender::is_closed`, not channel room, so a dropped session is reclaimed on the next drive or tick as before.
- **Memory (per admitted session):** 2 × 8 queued + 8 pending + 32 seen = 56 endpoints, about 1.8 KB of `SocketAddr` plus the seen set's table, so about 100 KB at the actor's 32 owned requests across both families (one session per logical request). The pool side adds one `Instant` per key that has had a batch but no fetch yet (`first_batch`, bounded by `max_pending`, cleared on fetch start, success and loss).

## Pool ownership (`crates/sources/src/pool.rs`)

The spec's event table, as built:

| Event                                 | Lookup ownership                                                                     | Fetch/entry                                                    |
| ------------------------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| First valid batch                     | kept: the `Request` stays in `requests`, `lookups` unchanged                         | `make_ready`: the key queues for a socket                      |
| Fetch fails, more peers               | kept                                                                                 | next peer, as today                                            |
| Fetch fails, no peers, lookup active  | kept                                                                                 | the entry waits in `Lookup` (new generation); no second lookup |
| One finder's terminal, another active | that finder's session dropped only                                                   | other sessions and usable peers kept                           |
| Every finder's terminal               | released once: `requests.remove`, `lookups -= 1`                                     | peers fetch on; a key with none left backs off as today        |
| Verified fetch                        | released if still held: dropping the request cancels every session                   | one result to the writer; nothing stale can reach it           |
| Eviction, loss                        | released (`lose` now also releases a stream held while the key is ready or fetching) | buffers dropped with the request                               |
| Source crash or channel close         | read as `SourceFailed` for that finder                                               | other finders continue; never counted as complete              |
| Deadline (`lookup_wait`)              | released; every session cancelled                                                    | a key with no peer to try backs off                            |

- **One logical attempt.** The first accepted finder uses the attempt, as today; batches, more finders and fetch failures don't add one or move the deadline. Multiple finders share the one `lookup_wait` timer from the send (`two_finders_are_one_attempt_under_one_deadline`).
- **The fence.** The `Request` owns every receiver and leaves the map whenever its entry does, so a recreated entry with the same hash gets a new request and the old receivers are gone (`a_stale_session_cannot_touch_a_recreated_entry`). A stream's deadline timer carries the request's generation, which stays put while the entry's generation moves with its state; `on_timers` matches it against the request (pool generations are unique, #223).
- **Drain before release.** On a terminal, or a closed terminal, the pool reads the session's queued batches again before dropping it: the finder closes the batch sender before it sends the terminal, so whatever it queued is there (`a_terminal_drains_the_batches_queued_before_it`). A terminal seen in the same poll as a batch doesn't lose the batch.
- **No double release.** Ownership is released only by removing the `Request` from the map, and each path decrements `lookups` only when it removed one. The pool is one task, so success and terminal can't interleave inside a turn; the pool's `lookups -= 1` would panic on underflow in the tests.
- **Refinement: accepted and dropped with nothing delivered** (a pause dropping a queued request, CR-0f) is read as cancelled, as today: the attempt is given back and the key requeues without back-off. It still counts `source_failed`. A session that delivered peers before failing keeps them.
- **Refinement: peers from another source** (a discovery carrying peers) while a stream is accepted also make the key ready without releasing the lookup, so the lookup runs to its terminal either way.
- **Batches are read on the pool's existing 25 ms reply poll** (and on discoveries for that key), not a new `select!` arm per session. That bounds the pool's work per turn and keeps CR-SIM deterministic, at up to 25 ms of added latency before a batch is seen.
- **CR-ADM composes unchanged.** The permit stays with the actor's request until its slot frees at the terminal, so a fetch running on a batch holds no permit and a waiting key gets the permit when the lookup ends, not when the batch arrives (`coordinated_admission_keeps_one_permit_per_streaming_request`). The actor's permit returns with streaming are tested at every boundary (`streaming_admission_returns_each_permit_once_at_every_boundary`, `a_dual_stack_session_is_one_request_ended_by_its_last_leg`, `a_handoff_failure_closes_the_session_admission_before_the_permit`).

## Counters (exported and documented in part 2)

With no infohash or endpoint labels:

- dht: `peer_stream_batches` (batches delivered), `peer_stream_backpressure` (peers dropped to backpressure, final-flush discards included), `peer_stream_seen_full`, `peer_stream_terminals` by `LookupEnd`;
- pool: `stream_batches` (batches read), `stream_peers_capped` (peers an entry's 32-peer cap turned away, apart from backpressure), `stream_terminals` by `Terminal` (including `source_failed`), and `stream_first_fetch_millis` with its count `stream_first_fetches` (time from a key's first batch to its first fetch start).

## Tests

- `crates/dht/src/node/stream.rs`: batch and backpressure bounds, the seen-set cap, termination order (flush, discards, close, terminal), cancellation with a full channel, and admission to a gone caller.
- `crates/dht/src/node/stream_tests.rs`, against the real actor on tokio's paused clock: early batch, full channel with the terminal still delivered and both queued batches drainable, the tick sending a held batch, the deadline terminal, a hinted reply's values streamed as a batch (`hint_tests.rs`), dual stack (one session, ended by the last leg, cancellation closing both legs with one permit return), permit returns at every streaming boundary, and the handoff failure.
- `crates/sources/tests/streaming.rs`, the streaming rows of "Prepared regression cases" with a scripted finder and fetcher, paused time and 10 s condition deadlines: early batch, final drain of queued batches, success racing a batch and a terminal (every order over a 3 × 3 × 3 grid of times, with the pool's 25 ms poll putting several of them into one turn), session refusal, unacknowledged and silent streaming requests under CR-ADM (no attempt, no back-off, the 1 s hold), failed first peer, stale generation, dual finder, source failure (with and without a delivered batch), plus entry-cap counting, the non-streaming finder, the switch off, and CR-ADM with streaming on. Each ends with no lookup owned (the final-drain row).
- **The interleaving test is a systematic grid, not loom.** The pool is a single task whose events are ordered by its `select!`, so the only interleavings are the orders in which a fetch result, a batch and a terminal reach it; the grid drives each order on the paused clock. Loom would need the pool's tokio runtime under loom, which it doesn't support.
- `crates/pipeline/src/dht.rs`: `the_session_adapter_allocates_on_admission_and_maps_every_end`.
- `crates/lodestar/src/config.rs`: `streaming_peers_is_off_unless_asked_for`.
- The dual-stack actor test skips (and says so on stderr) where the host has no IPv6 loopback, like CR-ADM's.
