# CR-1a-H decisions (responder hints)

Responder hints as a capability that can be measured on its own (master plan H1; `docs/plan/2026-10-27-streaming-and-hints.md`, "Responder hints are a separate capability"). Everything is behind one switch that is off by default. It doesn't change any cap, timeout or rate: the 32 owned requests, the 3-RPC in-flight budget and 64-query cap per request, `LOOKUP_DEADLINE` (25 s), the query rate and the outstanding cap all stay as they are.

## The switch
- **`dht.responder_hints`, a bool, off by default.** It's set in `config.toml` (`[dht] responder_hints = true`) or with `LODESTAR_DHT_RESPONDER_HINTS=true`, and read at start. A bad value is a config error (`responder_hints_is_off_unless_asked_for`). It isn't in the Settings UI, and like `dht.coordinated_admission` it needs a restart.
- **Off is today's behaviour exactly.** `Actor::hints` is `None`, so no hint table or guard is allocated. Every new branch is taken only through that `Option`. `Pending::hinted` stays false, and an owned request starts its legs exactly as before, through the unchanged `start_lookup_as`. Proof: `switch_off_allocates_no_hint_state_and_sends_as_today`, and the four CR-SIM goldens are byte-identical. The new counters read 0 and are tolerated as new zero counters.
- **It composes with CR-ADM.** Hints take no permit and no slot. A hinted request is the same owned request, so it uses the same admission and the same permit.

## The contract as built (`crates/dht/src/node/hints.rs`, `actor.rs`)
- **Capture.** A hint is recorded when a `sample_infohashes` reply lists a hash that is new to the seen filter *and* was handed to the pool (`harvest_hash` returns whether it was delivered). The endpoint recorded is the responder's address, normalized, with the actor's monotonic receipt time.
  - At most one hint per address family per hash, and an existing hint is never replaced or refreshed. A rediscovery isn't new, so it captures nothing.
  - Hints are never persisted and never take a timestamp from outside.
  - The public-endpoint checks run before insertion and again before sending (`hints::check`, which uses the existing `lodestar_network_policy` helpers and the blocklist). Port 0 and scoped IPv6 count as `invalid`. Private, reserved and blocklisted addresses count as `private`. A family with no socket counts as `family`.
- **Dispatch.** An owned request takes its hash's hints, so each is used once. It creates every family leg first. Each fresh hint then sends one direct `get_peers` as an extra query outside the candidate list (the bootstrap-seed path), and only then does ordinary routing drive the legs. On dual stack, building the legs first means the second family's hint isn't crowded out of the shared 3-RPC budget by the first leg's routing.
  - The hint shares the request's in-flight and sent counts, the global rate and outstanding cap, and the request's deadline, which starts at admission and never moves (`a_silent_responder_falls_back_inside_the_deadline`). It reserves no socket and adds no logical attempt.
  - The guard, the checks and the per-request budget are all tested before sending. Any failure means the leg goes straight to ordinary routing, counted by reason.
  - A hinted reply's nodes join the lookup at their own XOR distance (`Lookup::absorb`). It settles no candidate and its values are ordinary lookup peers, so the responder is never a peer and never reaches the fetcher (`a_hinted_reply_is_routing_help_never_a_peer`). As with any reply, the responder goes into the routing table as a node that answered. The hint itself adds nothing there.
- **The per-IP guard.** It's keyed by canonical IP (`IpAddr::to_canonical`), which covers every port and folds IPv4-mapped IPv6 to IPv4.
  - One hinted query is allowed in flight per IP, and each permitted send starts a 60 s not-before interval. A restriction is held while it's in flight or inside that interval.
  - The guard holds at most 20,000 IPs. An unexpired restriction is never evicted: when the guard is full, the hint is skipped as `guard_full`.
  - Ordinary routing (every lookup query in `drive_lookup`) checks a held restriction before sending to that IP. A restricted candidate counts as failed for that lookup and is counted in `dht_hint_guard_skips_total`. An IP with no restriction keeps today's policy. Pings and samples aren't routing and aren't checked.
  - Pruning runs on every maintenance tick. Memory bounds: `the_hint_table_is_bounded_and_pruned` and `guard_saturation_evicts_no_restriction_and_prunes_on_expiry`.
- **Private keys.** The pool never sends a private key's lookup to the public DHT (`pool.rs`, `!e.private`), so a hint for one is never dispatched and simply expires. The harvest the pool receives is byte-for-byte what it is without hints, so a hint adds nothing to provenance (`private_key_work_gets_no_public_dispatch_or_provenance`). Consent is re-checked at dispatch as the endpoint policy and blocklist, read live. The DHT plugin is `Consent::None`.

## Refinements (named for the runner)
- **Hints live in the actor, not on the pool's entries.** The pool would need a new field in `Found` and in `PeerRequest`, and the brief allows pool changes only if admission truly needs them. It doesn't. The cost is that the actor can't see a pool eviction. Instead, a hint lasts at most `HINT_TTL` plus one tick, and the table has its own cap, `HINT_CAPACITY`. When the table is full, new captures are refused (`dht_hint_capture_rejected_total{reason="full"}`), and nothing fresh is evicted.
- **The guard covers every lookup query, `find_node` included,** not only `get_peers` for hashes. Ordinary routing to a restricted IP shouldn't be able to go around the restriction through a maintenance lookup.
- **Hints that expire unused are counted** (`dht_hints_expired_total`). Only a hint found at a leg's start counts as a fallback. Without this counter, most of the screen's hints wouldn't show up in any series.
- **Lookup duration is now exported** (`dht_peer_lookup_seconds_total`, a sum of completed owned requests' run times). The screen needs it, and it always counts, with the switch on or off.
- **A CR-SIM net option, `samplers_hold`.** With it on, a BEP 51 node also answers `get_peers` with values for the hashes it samples, at the scenario's latency classes. It's off in the baselines, because turning it on changes routing results that ordinary lookups see, and the goldens predate it. Both arms of the screen turn it on.

## CR-SIM screen (off against on, `SCREEN_SEEDS` 1–8, `samplers_hold` on in both arms)
`cargo test -p lodestar-crawler-sim --test sim responder_hints_screen -- --ignored --nocapture`. The table gives steady stored per minute after warmup. "Spread" is the off arm's range across the eight seeds, which is the measured noise floor. Lookup time is the mean over completed owned requests. Hint counts are per-seed means for the on arm.

| Scenario | Off mean | On mean | Change | Off spread | Sign test | Lookup ms off → on | Captured | Expired unused | Queries | Useful | Throttled | Guard skips |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| `high-latency` (H1) | 32.0 | 33.6 | +5.1% | 12.1% | Inconclusive (6+/2−) | 16,404 → 16,511 | 15.3k | 14.4k | 209 | 82 | 203 | 376 |
| `healthy` | 75.2 | 74.3 | −1.2% | 13.5% | Inconclusive | 5,616 → 5,737 | 17.9k | 16.7k | 461 | 195 | 468 | 1,085 |
| `admission-pressure` (H2) | 30.2 | 29.1 | −3.7% | 14.2% | Inconclusive | 5,485 → 5,648 | 122.7k | 115.2k | 1,064 | 154 | 528 | 2,839 |

- **Hints don't beat the noise floor in any scenario.** Every change is well inside its spread, and no sign test agrees on all eight seeds. Lookup duration doesn't fall either: it rises slightly, by 1–3%.
- **Why, as far as the screen shows it.** About 94% of hints expire before the pool asks for their hash, because keys wait in the pool longer than 60 s. Of the hints that are found, about half are throttled by the per-IP guard. A responder lists 20 hashes at once, and the guard allows one hinted send per IP per minute. The guard also costs ordinary routing up to about 2.8k skipped queries per run. Between 15% (H2) and 42% of hinted queries return peers (`useful`/`queries`), but that's too few lookups to move stored per minute.
- **What this doesn't show.** The sim's limits apply (CR-SIM README): IPv4 only, approximated routing, and stored meaning "reached the writer". `samplers_hold` is an optimistic model of a responder. This is a screen; the live A/B decides. A candidate that lets hints act on more keys, for example by combining them with CR-ADM or streaming, would be a separate measurement (spec: "Do not merge streaming, hints, … into one performance comparison").

## Tests
- `crates/dht/src/node/hints.rs`: one hint per family that's never refreshed and is used once; the TTL boundary (age < TTL); IP rotation with a mapped form; an in-flight restriction that outlives its interval; guard saturation with no eviction and pruning on expiry; hint-table bounds and pruning; the endpoint checks; and the property test `accepted_hints_are_public_and_canonical` over arbitrary endpoints (mapped, port 0, scoped, reserved).
- `crates/dht/src/node/hint_tests.rs`, on tokio's paused clock against the real actor: `switch_off_allocates_no_hint_state_and_sends_as_today`, `hint_expiry_is_age_below_the_ttl_and_falls_back_at_once`, `one_hinted_query_in_flight_per_ip`, `ip_rotation_shares_one_restriction_with_no_fallback_bypass`, `guard_saturation_evicts_nothing_and_ordinary_work_continues`, `private_key_work_gets_no_public_dispatch_or_provenance`, `a_silent_responder_falls_back_inside_the_deadline` (a 10 s condition deadline, no sleeps), `a_hinted_reply_is_routing_help_never_a_peer`.
- `crates/lodestar/src/config.rs`: `responder_hints_is_off_unless_asked_for`. `crates/lodestar/src/metrics.rs`: the hint families render each label with its own value.
- CR-SIM: `responder_hints_send_hinted_queries_deterministically`, which runs in CI and checks that the same seed gives byte-identical output with the switch on, and the ignored `responder_hints_screen`.
- Not covered by a test: `send_failed`. Every other failure is caught by a check before the socket is reached, so only a real socket error leads to it. Its counting is the same code path as the other reasons.
