# SRC-11 decisions (download clients as a source)

Slice SRC-11 of `docs/plan/2026-11-01-v06-sources.md`. It covers architecture §18.2 (rank 17) and §18.7 (`private_source`), and the plan's §5 Q4 and Q6. The code is `crates/integrations/src/clients/{mod,qbittorrent,transmission,deluge}.rs` (the trait and the adapters), `crates/sources-plugins/src/clients.rs` (the plugin), its fixtures and contract tests, and `fuzz/fuzz_targets/client_list.rs`.

## The trait
- **`DownloadClient` gains `list` and `export`, with default bodies that return `Unsupported`.** A new `Feature::List` and `Feature::Export` name them. rTorrent and Aria2 keep the defaults, so their files are unchanged.
- **The protocol lives in a `Lister` over a `Wire`, not in the adapters' reqwest code.**
  - A `Wire` sends one request in plain values (method, URL, headers, body, a body limit, and whether it's the poll). `GuardedWire` is one over the adapters' `GuardedClient` (`GuardedClient::exchange`, SRC-5's seam). The plugin has its own over `ctx.kit.http`.
  - Why: the plugin must send every request through its egress (SRC-5) and its paced `Client`, and its contract tests replay fixtures through that `Client`. The adapters' add paths build reqwest requests (multipart for qBittorrent) that can't go through it.
  - `QbitLister`, `TransmissionLister` and `DelugeLister` log in the way their adapters do (qBittorrent's cookie and `Origin`/`Referer`; Transmission's 409 session id and basic auth; Deluge's `auth.login`, daemon connect and request ids), and answer an expired session once, never in a loop. The adapters' `list` and `export` delegate to a lister over their own guarded client, so both callers share one protocol.
  - The login code is duplicated between each adapter and its lister (about 40–60 lines each). Moving the adapters' add paths onto `Wire` would remove that, at the cost of rewriting tested code this slice doesn't need. **Handoff:** a later integrations refactor.
  - `WireRequest`'s and `WireResponse`'s `Debug` print header names and body lengths only: the headers carry cookies, session ids and basic auth.
- **Export works for qBittorrent only (deviation from the brief's "implement both for all three").**
  - qBittorrent: `GET api/v2/torrents/export?hash=…` (API 2.8.14, qBittorrent 4.5 and later). A 404 is "no such torrent, or the client is older than 4.5"; a 409 is "no metadata yet".
  - **Transmission's RPC has no call that returns a torrent's `.torrent` bytes.** `torrent-get`'s `torrentFile` is a path on the daemon's disk. Its `export` is `Unsupported(Export)`.
  - **Deluge's RPC has none either.** `core.get_magnet_uri` gives a magnet, and `core.prefetch_magnet_metadata` would make the daemon look the hash up on the public DHT, which §18.7 forbids for a private find. Its `export` is `Unsupported(Export)`.
  - `Lister::can_export` says which, so the plugin doesn't ask.

## Untrusted list answers
- **Bounds:** each answer is read up to `MAX_LIST_BYTES` (16 MiB) and refused past it. At most `MAX_LISTED` (50,000) torrents are kept; the rest are counted in `Listing::over_cap`. A name over `MAX_LISTED_NAME` (4,096 bytes) makes its entry malformed. State strings over 64 bytes are ignored. serde_json's recursion limit (128) bounds depth.
- **Nothing is buffered beyond one entry's kept fields** (self-review). Each client names the keys it reads; every other key's value, and any entry that isn't an object, is skipped as it's read (`IgnoredAny`). A first version used `#[serde(untagged)]`, which buffers each entry into serde's `Content` tree first: one 16 MiB array entry would have taken about 256 MiB. Tested with a million-element entry and field.
- **qBittorrent is read a page at a time** (self-review): `torrents/info?sort=added_on&limit=1000&offset=…`, until a short page or `MAX_LISTED`. A real entry is 1–2.5 KB (about 50 fields, the magnet link and paths among them), so one answer of 16 MiB would hold only 7,000–12,000 torrents, fewer than a large seedbox has. A page stays at 2.5 MB or less. Oldest first, so a torrent added between pages shifts nothing already read; a repeat across pages is counted as malformed once. At one request a second, the largest client takes about 50 s a poll. Transmission and Deluge ask for 5 and 3 fields, so one answer covers `MAX_LISTED`.
- **Malformed entries are skipped and counted** (`Listing::malformed`): not an object, a missing hash or one that isn't 40 hex digits, a field of the wrong type, an over-long name, or a repeated hash. One bad entry never fails the list. The plugin adds both counts to `Clients::skipped()`.
- **What's kept:** the hash (lowercased), the name (control characters dropped, trimmed), the total size (only when positive; clients say -1 or 0 before they have metadata), and a common `TorrentState`. qBittorrent's `total_size` is used before `size`, which counts selected files only.
- `clients::parse_list(kind, body)` is the pure entry point for the fuzz target and the property tests. Deluge's request-id check is done by the lister, not there.

## The plugin
- **Id `download_clients`, kind Discovery, consent Account, risk Low, no built-in endpoints.** Its egress is narrowed to the client's host under the download-client policy (`Endpoints::user_entered(download_client()).only_hosts`), as Prowlarr's is.
- **Credentials reuse Settings → Integrations.** `Clients::new` takes the `ClientConfig` the integrations settings already hold, opened from the integrations `SecretStore`. The plugin has no settings and no credentials of its own (an empty config schema), so nothing is entered twice and there's no second copy at rest.
  - **Handoff to SRC-14/SRC-15b:** the host builds the plugin from the configured client, and rebuilds it when the client's settings change. Nothing is wired into `services.rs` or the pipeline here (the brief).
- **Q4: at most one poll a minute.** `min_poll_interval` is 60 s, the global floor. One request a second with a burst of 4 lets a login, the list and a poll's exports through. Back-off is 60 s to an hour. Distribution is `Coordinator`: the client is on the coordinator's network.
- **Each poll** lists the torrents and emits every torrent it hasn't emitted since the plugin started, all in that poll, with the list's claims unless its export works then. A torrent is emitted a second time when a later export brings the `.torrent`'s claims. The poll's gated request (`Client::poll`) is qBittorrent's login and Transmission's and Deluge's list call; everything else goes through `Client::send`.
- **qBittorrent logs in afresh every poll** (self-review). Its sessions expire after an hour by default. A 403 for the expired session would reach the plugin's limiter, which reads any 401 or 403 as a refusal and blocks the host for the back-off ceiling (an hour), so logging in again on the 403 could never work there. A fresh login each minute never sends a stale session. Each successful poll ends with `auth/logout` (`Lister::finish`, runner review), so the logins don't leave a session a minute on the client until each expires; a poll that fails part-way leaves its session to expire. The adapters' own path (no limiter) still logs in again once on a 403.
- **A blocked host is waited out, and every cycle starts a poll interval after the last** (self-review). When the limiter has the host blocked, the plugin's `Wire` waits until the block ends before reporting the client unreachable, so a caller can't spin. And the run loop starts each cycle at least `poll_interval` after the last, so a failure before the gated request (a sign-in page instead of the login, a Deluge Web UI with no daemon) is tried a minute later, not at once (Q4). Both are tested on fixtures. The seen set is trimmed to the current list each poll, so it stays within `MAX_LISTED`, and a removed and re-added torrent is found again. It's in memory: a restart emits everything once more, which the pipeline's have-filter absorbs.
- **Exports:** at most `EXPORTS_PER_POLL` (20) per poll, so a large client isn't sent hundreds of export requests at once. New torrents come first. **A new torrent over the budget is still found at once** (runner review), with the list's claims, and its export waits for a later poll. So a 50,000-torrent client's every key is found on the first poll; its exports follow at 20 a minute, about 42 hours in all, and again after a restart. Retries go fewest failures first, so a torrent not asked yet isn't starved by ones whose metadata is slow.
- **A failed export is tried again** (self-review). An export that fails for any reason but authentication (no metadata yet, which every magnet has at first, or unreachable) emits the list's claims, and the export is tried again on later polls, after the new torrents and within the same budget, up to `MAX_EXPORT_TRIES` (60) failed polls, about an hour. A poll that didn't ask (over the budget) doesn't count. When it works, the torrent is emitted again with the `.torrent`'s claims. Bytes that hash to another torrent end the retries.
- **Stops rather than retries** on an authentication failure, an address the plugin's client refuses, or an unsupported client (rTorrent, Aria2), with a fixed message that holds no URL or secret. A session refused straight after logging in (Transmission's second 409, a daemon restarting) is tried again next poll, as is anything else. A destination the egress policy refuses comes back as a transport failure (SRC-5) and is retried paced, like any unreachable client.
- **`Clients::skipped()` is the last poll's count** of malformed and over-cap entries, not a running total that would count the same entry every minute.

## §18.7 and Q15
- **Every find is `private_source`:** no peers, no external reference, no publish date, no trackers. The pool never sends a private key to DHT `get_peers`, PEX or a public announce (`crates/sources/tests/pool.rs`, `private_keys_never_reach_peer_finders`), and Torznab, Stremio and exports leave private items out (SRC-G's `tests/safety.rs` covers them across plugins). A torrent in your own client may be from a private tracker, and a public lookup would leak its hash (BEP 27).
- **Exported bytes go through `lodestar-metainfo`** (`TorrentFile::parse`, its default limits; fuzzed by the `metainfo` target). The info dict is used only when its primary hash is the listed key. Then its name, total size and files (padding left out, at most `claims::MAX_FILES`) are the claims, with strategy `STRATEGY_EXPORT`. Otherwise the list's name and size are the claims (`STRATEGY_LIST`).
- **Trackers are never kept**, not even from a matching `.torrent`: a private tracker's announce URL holds the user's passkey.
- **§18.2 row 17 is narrowed (deviation).** The row lists "complete `.torrent`s with real trackers and creation dates" and the kinds discovery and enrichment. The plugin declares `Kind::Discovery` only: its finds carry their claims, as every other source's do, and there's no separate enrichment event to send. Trackers are dropped (above). The `.torrent`'s `creation date` is dropped too: `Claims` has no field for it, and `Provenance::published_at` means when the source published the item, which for your own client it didn't. **Handoff:** a creation-date claim, if SRC-3's claim search wants one.
- **Q15 (owner: claims only for `private_source` items; no automatic `.torrent` download through a private indexer) holds, as the runner should confirm (§2.19).** The export reads the user's own client on the LAN and never contacts the tracker, so it can't count as a snatch. And what it yields still enters as claims at Medium confidence, not as verified metadata. **Handoff to SRC-14 or SRC-G (runner's call):** handing the matching info dict to the writer as verified metadata (which would store the torrent without a fetch) needs a `Found` field and a pipeline path that the brief keeps out of this slice. That would be a refinement of Q15 for the user's own client; it's flagged here, not done.

## Fixtures and tests
- **The fixtures are hand-written, not recorded.** This session had no client to record from. `fixtures/clients/make_fixtures.py` writes them in each client's documented answer shapes (qBittorrent 4.6, Transmission 4.0, Deluge 2.1), with real `.torrent` files whose info-hashes are the listed keys, `.example` hosts, `REDACTED` credentials and open-licence titles. Replace them with scrubbed recordings when a client is available; the tests don't change.
- **Contract tests** (`tests/clients.rs`, SRC-7's pattern, paused clock, no sleeps): two polls per client with poll spacing checked; qBittorrent's export with a matching, a missing-then-retried and a mismatched `.torrent`; a sign-in page instead of the login (retried a poll later); a 403 on the list (waited out, nothing in between); Transmission's 409; Deluge's expired session; a refused login; setup failures before any request; the caps; and the isolation check that every find is private and carries nothing public. Property tests cover the parsers. The adapters' unit tests cover each lister over a scripted `Wire`, paging, and each adapter's `list` and `export` over real HTTP on loopback.
- **The fuzz target `client_list`** parses each client's list and maps every entry to a find, with the rest of the input as its export, checking the bounds, that every find is private, and that an export's claims are used only when the bytes parse and hash to the key. Its input is a client byte, a two-byte list length, the list and then the export, so a list can name a real info dict's hash (runner review: a single shared buffer could never reach the export branch). `fuzz/seeds/client_list/` seeds each client's list, and one list with its matching `.torrent`; a test checks that seed reaches the export branch. This session has no nightly toolchain, so it was built, not run. Its row in `fuzz/README.md` and the seeds were added in this PR with the runner's leave, as was the plugin README's Q15 line.
