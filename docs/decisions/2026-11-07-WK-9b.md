## Counters (HARD REQUIREMENT 2; `crates/pipeline/src/rollups.rs` `Admit`)
- **A `Counters` payload is now taken, not refused.** Each counter passes `Admit`, then goes into the rollups twice: once as the fleet's own row (the same metric, dim and key, so every existing Insights query reads the fleet's totals as before), and once as a `BY_WORKER` row (metric code 17, the next free code; the codes are append-only). The batch is answered `accepted: true` even when some or all of its counters are refused, or it doesn't decode: nothing in it is worth keeping in the worker's spool.
- **Only four metrics, each in its own domain** (`metric::FROM_WORKERS`):
  - `REDISCOVERED`: dim = source 0–63, key = strategy 0–255;
  - `DROPPED`: dim = source 0–63, key 0;
  - `SCRAPED`: dim = lane 0–3, key = result 0–2;
  - `DHT_SCRAPES`: dim 0, key 0–1.

  Everything else is refused. That includes `HARVESTED`, `STORED` and the funnel, which the coordinator counts itself at grant and commit (§19.3: nothing is counted twice), and `BY_WORKER` itself. The value must be positive (WK-6's codec already bounds it to 2⁴⁰ per batch).
- **The four are counts only the worker sees, so none is counted twice.** The coordinator counts `REDISCOVERED` and `DROPPED` for its own sightings (`writer.rs`, `lib.rs`) and `SCRAPED` and `DHT_SCRAPES` for its own scrapes (`health/service.rs`). A worker's sighting of a stored key stops at its own have-filter, or at the claim, which answers `Stored` and counts nothing.
- **The worker can't write another worker's rows.** A `BY_WORKER` row's dim is the authenticated session's worker id (WK-6), never anything in the payload. Its key is `metric << 16 | dim << 8 | key` of the counter's own metric, dim and key (`metric::by_worker_key`), which the domains above keep within 8 bits each.
- **The window: the 24 hours before now, plus the hour under way, on the coordinator's clock** after correcting the worker's hour by its measured offset (`hour × 3,600,000 − offset_ms`, in `i128`, floor-divided). A spool holds a day (owner §2.17), so an honest replay fits. A counter for a later hour, or for one more than 24 hours back, is refused.
- **Caps:**
  - **All workers together** may add at most 32 distinct rows (metric, dim, key) an hour (`FLEET_ROWS_PER_HOUR`) and 64 a UTC day (`FLEET_KEYS_PER_DAY`). The day cap bounds the daily rows the nightly compaction leaves. A row already there still takes any worker's counts. Each worker's `BY_WORKER` rows follow its fleet rows one to one, so these caps bound them too (at most 32 per worker an hour).
  - **Each worker** may add at most 2³² to any one row in one hour (`WORKER_ROW_CAP`). Anything over is cut (saturation), never wrapped.

  With that cap, a fleet row in one hour stays below (workers + 1) × 2³². So a `rollup_hour` value, a `STRICT INTEGER` summed as `value + excluded.value`, can't leave the integer range for any realistic fleet, and neither can a day's or a year's sum. Without the cap, WK-6's decisions note that about 2²³ batches of 2⁴⁰ would overflow one row and fail every later write to it.
- **Why the row caps cover the whole fleet, not each worker (measured; see the budgets below).** The draft capped each worker at 64 rows an hour and 128 a day. With 8 workers counting disjoint keys, that is 512 new fleet rows an hour, and the Discover page then took 154–173 ms against its 50 ms budget. The pages read the fleet's rows, so the cap that keeps them fast is on the fleet's distinct rows, whatever the number of workers. 64 more an hour still measured about 24 ms, and 96 failed, so 32 keeps a margin. A real fleet shares about 22 rows: every worker counts the same few sources, strategies and lanes.
- **Refinement (§2.19): one worker can use up the fleet's new rows for an hour or a day.** Its own counts then crowd out other workers' new rows, not their existing ones. That costs statistics, never safety or correctness. It is what WK-13's quarantine is for, and `remote_counters_total{outcome="refused"}` shows it.
- **Refinement (§2.19): the caps are counted in memory and start again at a restart.** After a restart the workers can add up to the caps again for hours still in the window. Restarts are rare, so this costs at most one more set of rows per restart; persisting the counts would add a table for no real gain. The maps hold at most 25 hours of 32 fleet rows, plus each worker's row totals for those rows, and drop hours as they leave the window.
- **Tests (each fails with its check removed; see "Checks"):** `rollups.rs` `worker_counters_stay_in_their_domains`, `worker_hours_are_corrected_and_windowed` and `worker_rows_are_capped` (the fleet's hour and day caps across eight workers, and saturation at 2³²); `remote_intake.rs` `counters_go_into_the_rollups_with_the_worker`. That one sends an in-domain counter, out-of-domain dims and keys, the coordinator's own `HARVESTED`, a `BY_WORKER` row with another worker's dim and one with its own, and hours outside the window both ways. One fleet row and one `BY_WORKER` row (dim 7, the session's) are written.

## The Insights budgets with the worker dimension (owner §1.6.4)
- **Rollup storage**, at the plan's fleet size of 8 workers (WK-15's gate), measured the way `bench/examples/reporting-overhead` measures it: a year of rows, compacted (30 days hourly, the rest daily) and vacuumed.
  - **The coordinator alone** (the busy crawler's wide hour, rollup rows only): 2.95 MB a year.
  - **A realistic fleet:** 22 shared rows (2 sources × 3 strategies rediscovered, 2 dropped, 12 scrape lanes × results, 2 DHT scrapes), each also a `BY_WORKER` row for each of the 8 workers: 6.46 MB a year.
  - **The caps' worst case:** 32 distinct fleet rows every hour (64 a day), each written as a `BY_WORKER` row by all 8 workers: 9.91 MB a year (587,445 rows, 358,400 of them `BY_WORKER`). The budget is 50 MB. Under the draft's per-worker caps the same measurement gave 26.48 MB.
- **Page time:** `crates/api/tests/insights.rs` `a_year_of_rollups_answers_within_budget`, in a release build, its year of hourly rows never compacted. The added rows were 32 fleet rows an hour and 512 `BY_WORKER` rows an hour, twice the most the caps allow.
  - Without them, the slowest page took 19.6 ms.
  - With them, the slowest page took 16.6–23.9 ms over three runs, inside the run-to-run noise. The budget is 50 ms.
  - The `BY_WORKER` rows alone cost nothing measurable: no page reads code 17 yet, and the `(metric, hour)` index skips them. WK-15's per-worker queries will read them through that same index.
- These were measured once for this record with local, uncommitted edits to the bench and the test; neither file is changed here. **For WK-15:** add the worker rows to `wide_hour` and `year_of_rollups` when the per-worker queries land, so CI gates them.

## Grant backpressure (§19.5; `RemoteSink`'s `GrantAdmission`)
- **No new lease once the writer's queue reaches its high-water mark** (three quarters of its 64, read from the channel's capacity), **or while the intake's queue is full.** The server asks under the authority's lock; the hook reads two channel capacities and takes no lock. Keys already held elsewhere still merge their sources and relay hints, as WK-0 built. Each denied key counts in `remote_grants_held_back_total`, and in the server's `cluster_busy_total`.
- **Late results aren't held back** (WK-9's note): they take no grant. Results for keys already leased aren't held back either, since their leases are spent. The intake's queue of 16 (`INTAKE_QUEUE`) bounds them, and a full queue answers "later", so the batch stays in the worker's spool.
- **Test:** `backpressure_bounds_the_writer_queue`. A writer that never reads (8 slots, mark 6) admits grants up to the mark and none from it on, then refuses a flood of 1,000 grant requests of 64 keys. Harvested batches then queue up to the intake's bound and are refused. The writer's queue stays at 8, and every wait is on a condition.

## The fetch queue (§19.3, WK-1's "leases after off")
- **Remote and waiting leases are saved with the built-in worker's queue** (`RemoteIntake::queue_rows`, from `LeaseAuthority::outstanding_remote`). That means every lease whose holder isn't the built-in worker, plus every key waiting for a re-grant, with its cohort, first source, strategy and privacy, at both the saver's interval and shutdown. After a restart the built-in worker holds them, restored and not harvested again, and a late result for one finds its record (plan Q7). Before WK-9b such a result was stale.
- **Shutdown order (runner, 2026-11-07):** the intake is closed, then the heartbeat is stopped and awaited, so no parked key moves between the pool's snapshot and the remote rows. The remote rows are taken before the writer's final flush, so a key is saved exactly once and none is lost.
- **Parked keys go to the built-in worker while no server runs** (`RemoteIntake::hand_parked`, at each heartbeat). A key whose remote holder was revoked or expired waits for a re-grant. With "Allow workers" off, or before the server is built, nothing would grant it, so the built-in worker takes up to 512 a beat (`PARKED_PER_BEAT`) as a re-grant, not a harvest, with the key's cohort and sources kept. A key the pool has no room for goes back to wait. Each counts in `remote_parked_total`.
- **Test:** `remote_leases_survive_a_restart_and_parked_ones_go_to_the_built_in_worker`. Two remote leases are listed. One worker is revoked and its key goes to the built-in worker within a heartbeat. Shutdown saves each key once. After the restart (a new epoch), the built-in worker holds the remote worker's key, loses it, and the remote worker's late result is stored from the coordinator's record. The funnel reconciles across both runs: harvested = Σ terminal − late + in flight. `leases.rs` `remote_and_waiting_leases_are_listed_for_the_fetch_queue` covers the listing, with local leases excluded.

## Notes for later slices
- **WK-10 (the funnel's `PeerFound` and `Fetched` for remote keys):** the coordinator still counts no intermediate stage for a remote key. It counts harvested at grant and the terminal row at commit or loss, so the funnel reconciles on those, and the worker's own funnel holds the stages in between. If Insights should show them for the fleet, the server's outcome path (`report` for `PeerFound`, `held` for `Fetched`) is where to count them, once per lease, holder-checked. They must not come through `Counters`: `Admit` refuses the funnel's metrics, and must keep doing so. A worker's `Counters` should send only `FROM_WORKERS`' four metrics, in their domains. Anything else is refused and counted in `remote_counters_total{outcome="refused"}`.
- **WK-13:** quarantine and purge should also stop counters, since one worker can use up the fleet's new rows (above). Today `counters` takes every authenticated worker's. Purging a worker's `BY_WORKER` rows (dim = its id) is one delete per metric code 17. Keep the session's id as the only source of the dim.
- **WK-15:** read per-worker rows from metric 17, split by `by_worker_key`. The fleet's totals stay in the counters' own metrics, so no existing query changes. Gate the budgets above in CI with the worker rows added. The marginal-gain view can't take a worker's count from anything but these rows, which `Admit` bounds.
