# WK-0 decisions (one lease authority, the v1 protocol messages)

Plan `docs/plan/2026-11-06-v06-workers.md` §4.3 WK-0 and Q4/Q5; architecture §19.2, §19.3, §10.9.3.

## Leases
- **One `LeaseAuthority` (`crates/cluster/src/leases.rs`) holds the fleet's leases:** the `LeaseTable`, the queue of keys waiting for a re-grant, and a `LeaseEvents` hook. The pipeline's `Coordinator` builds it and keeps the funnel accounting on the hook (`harvested` at first grant, `lost` on a loss under the current token, the `outstanding` gauge). `Monitor::lease_authority()` hands it out. `ClusterServer::with_hooks` takes the `Arc`, so a server grant is counted in the same funnel as a local one. Building the server needs the PKI, so nothing opens or creates a cluster CA until WK-1 builds one for "Allow workers" (§19.6). `ClusterServer::new` keeps its signature and makes a private authority with `NoEvents`, for a server on its own.
- **The local worker calls the authority directly (plan Q4).** No `Link`, no fleet mutex and no certificate on the local path; the authority's lock is the only one, as the old `Coordinator` table's was. Lock order where both are taken: the fleet, then the authority. `harvested` and `lost` run after the authority's lock is released; `outstanding` runs under it so the gauge never goes backwards.
- **A key waiting for a re-grant is still in flight.** Expired and evicted leases go to the authority's queue, not back to the caller. A claim for a waiting key (by any worker) takes it over under a new token with its cohort and source bits kept, and is **not** a new harvest. Before, the server's re-grant queue sat outside the table, so a claim in that window was granted as new and harvested twice. `in flight = leases held + keys waiting`, so `harvested = Σ terminal + in flight` holds across expiries (`tests/lease_authority.rs`, a property test over local and remote claims).
- **The built-in worker's leases never expire.** It runs in the coordinator's process; `expire` renews it first. Its keys sit in its own pool, so moving them would strand them. A remote worker's expired keys wait for the cluster server to re-grant them to a live remote worker; handing them to the local pool is WK-9's ("remote leases kept in `fetch_queue`"). The pipeline's heartbeat loop now calls `Coordinator::expire` (which only parks remote keys) instead of `expire_to(LOCAL)`.
- **Outcomes:** `PeerFound` and `Lost` end the lease and count a loss (their `reason` is the funnel's `Loss` code; a code the funnel doesn't know is counted as `Invalid`, so it still ends once). **`Fetched` no longer ends the lease** (V6-cluster2 had it end it): a remote result is committed under the lease's token and the commit ends the lease, as for the built-in worker, so the funnel gets its stored or lost row and WK-9's "token current for that worker" check doesn't drop every result. Only the holder's current token counts (`LeaseAuthority::report`, `held`). `tests/transport.rs`'s `fetched()` helper now sends a terminal outcome, so its assertions are unchanged.
- **A remote claim racing a commit.** The server's store check runs before the claim; a commit landing in between would let the key be granted and harvested again. Once a server is built on the authority (`serve_remote`), it remembers the last 16,384 commits (`RECENT_COMMITS`, about 10 s at the §19.8 ingest target) and answers a remote claim for one as stored. The built-in worker's path doesn't look (its have-filter already has the key), and a single machine keeps nothing.
- **Expiry** can be run by the pipeline's heartbeat and by the server's tick; both are idempotent, and `LeaseEvents::expired` counts it once whoever ran it.
- **`LeaseEvents` may run under the server's fleet lock** (a server claim holds it): implementations record and return, never call back into the authority or the server.

## Protocol (every v1 message; may still change until WK-G, plan Q11)
- **`ClaimItem.hints`:** up to 8 `SocketAddr`s per key (`MAX_HINTS`). A claim denied as held elsewhere relays them in memory to the holder, one message per holder per claim, without port-0, unspecified, multicast or broadcast addresses: `ToWorker::Hints` for a remote holder (sent only while its queue is under half its count and byte caps, so hints never crowd out grants or snapshots), `InboundSink::local_hints` for the built-in worker. `ClusterServer::relay_hints` does the same for a caller (WK-9's local-to-remote direction). Nothing stores them (§18.7). Serde writes an address and port only; IPv6 flow info and scope don't travel.
- **`Results` and `Counters` carry a `Payload { batch, bytes }`** (batch ≠ 0, bytes ≤ 512 KiB, WK-6's codec inside) and are answered with `ToWorker::Accepted { batch, accepted }`; `accepted: false` is backpressure ("send it again later"), so WK-11 can delete a spool segment only on `true`. A replaced or revoked session's payload is not answered.
- **Snapshots travel as `ToWorker::Snapshot(SnapshotChunk)`** (`kind`: filter, dictionary or have-filter; `version`; `seq` < `total` ≤ 2¹⁷; ≤ 512 KiB each), each acknowledged by `ToCoordinator::SnapshotAck`, which reaches `InboundSink::snapshot_ack`. The sender sends the next chunk after the acknowledgement, so a snapshot never fills a queue (plan Q5: "paced by acknowledgements"). `HaveSnapshot`/`HaveDelta` stay as opaque messages for WK-3 to use or retire.
- **Re-verification:** `ToWorker::Reverify { id, keys ≤ 256 }` and `ToCoordinator::Reverified { id, payload ≤ 512 KiB }` (WK-13 defines the payload).
- **`DenyReason::Busy`:** a `GrantAdmission` hook says how many of a claim's keys that would get a **new** lease may get one now (§19.5 backpressure, WK-9), asked under the authority's lock; the rest are denied as busy and not leased. Keys already held, by the claimer or elsewhere, aren't counted, so their source still merges and their hints still relay.
- **The server's TTL is the authority's:** `with_hooks` overrides `ServerConfig::lease_ttl_secs`, so `Welcome` and every grant state the TTL that's enforced.
- Every new limit is checked in `validate` on both transports, so the `cluster_frame` fuzz target covers them unchanged; `frame.rs`'s tests prove the largest message of each kind still fits a frame.

## Server hooks and queues
- **`InboundSink`** (results, counters, accepted outcomes, snapshot acknowledgements, re-verification replies, local hints) runs on the session task with no lock held and must not block. With no sink, or by its defaults, `Results` and `Counters` are **refused** (`accepted: false`), never acknowledged and dropped, so a worker's spool keeps them; the rest is dropped.
- **`Drain` has its own one-slot channel**, read ahead of the queue, so a full queue can't turn a drain into a stop.
- **`ClusterServer::send` / `broadcast`** queue without waiting; they refuse what only the server sends (`Grants`, `Welcome`, `Stop`, …) and anything over a limit. `broadcast` returns the workers whose queue was full.
- **Byte caps (plan Q5), 8 MiB by default (`QUEUE_BYTES`):** each coordinator session's outgoing queue (`ServerConfig::session_queue_bytes`, beside the 256-message count) and the worker's event queue to its caller (`WorkerConfig::event_queue_bytes`). A message holds its share until it's on the wire (server) or taken by `next_event` (worker). The server refuses what doesn't fit (`SendError::Full`; a re-grant goes back to waiting); the worker stops reading the connection until there's room, which pushes back on the coordinator. One message larger than the cap passes alone. Sizes are upper bounds from `approx_size` (tested against postcard's). `queued_bytes()` on both sides shows the current fill.
