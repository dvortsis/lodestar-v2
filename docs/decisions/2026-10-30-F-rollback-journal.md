# F-rollback-journal decisions

Refines BB-1, the deletion guarantee (owner decisions §2.16, §2.17, §2.21; `2026-10-23-S-snapshots.md` and the V12 deletion journal), for `lodestar rollback` (architecture §12). Fixes I3 from the L4 review. Nothing here loosens BB-1 or changes an on-disk format: the journal table and its rows are V12's, unchanged.

- **A rollback never brings back a deleted torrent.** The hourly snapshot purge can lag (the server was stopped before its next tick) or be interrupted, so a snapshot can still hold a torrent deleted after it was taken. `restore` now applies the current store's purge to the staged copy before the rename: `snapshots::purge_for_restore` runs the same `purge_one` the tick runs, with the same matching (the deletion journal and the CS-1, tombstone and quarantine holds by hash, v1 and truncated v2; journal and held rows from a day before the snapshot's modification time, or all of them when that time is unknown or ahead of the clock). Expired quarantine, sealed names, the query log and deleted or revoked user data are purged as on the tick. Filter hits aren't deletions, so they're left for the restored store's own tick.
- **The journal comes along.** In the same transaction, the current store's whole journal is merged into the copy's own (`ON CONFLICT … max(at)`), so the restored store goes on scrubbing the other snapshots beside it. A snapshot before V12 has no journal table; nothing is added to its schema, and the torrents are still removed from the copy. After that, the snapshots beside the store rely on the holds that schema's purge knows, as they did before V12.
- **The store doing the rollback can be older than the copy** (undoing a rollback to a schema before V12, say). The purge reads only the tables that store's schema has: a missing journal or hold table has nothing to apply, and a missing query log or user-data table takes nothing from the copy (it can't say what was deleted).
- **Not covered: holds.** The purge removes held torrents (CS-1, tombstones, quarantine) from the copy, but the holds recorded since the snapshot aren't carried into the restored store, as before this change. A hash held after the snapshot isn't refused by the restored store until it's held again. Raised with the runner as a follow-up, since it's content safety and outside this slice.
- **A snapshot this build can't purge isn't restored.** A schema with no purge plan (`Plan::for_version`, say a kept copy from a newer release) is refused before the confirmation, with a message to restore it with the version that uses that schema. Stricter than before, never laxer.
- **Crash safety:** only the rename makes the copy the store, and it happens after the purge commits, its WAL is folded in (checked) and the file is synced. A crash before it leaves the old store. The staged `<stem>.rollback-<time>.tmp` (and any SQLite side file) it leaves is an unpurged copy, so `snapshots::remove_stale_stages` deletes it at the start of the next rollback (which refuses if it can't) and on every purge tick (a failure there holds the journal back, as a failed snapshot unlink does). Neither runs while a rollback holds the store lock.
- **The kept pre-rollback copy (`*.before-rollback-*.db`) isn't purged at rollback time.** It's the store as it was, so it already lost every deletion the store made; it's the user's undo, and the tick purges and expires it as any snapshot.
- **The confirmation text** adds "torrents deleted since stay deleted".
