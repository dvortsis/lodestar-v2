## Terms check (owner §2.28, plan Q4), 2026-11-15

- **The owner's limit (Q4):** yes for srrDB, at most one request a second, user interest first, the slice recording its terms check.
- **What was read:**
  - `https://api.srrdb.com/robots.txt`: for every client, `Crawl-delay: 10`, and the web pages (`/browse`, `/api`, `/account`, `/admin` and others) disallowed. **The API's own path, `/v1/`, is not disallowed.** The API answers JSON with `Access-Control-Allow-Origin: *`, which is meant for programs.
  - `https://www.srrdb.com/robots.txt` disallows a list of AI crawlers by name. Its help page sits behind a bot check (Anubis) and couldn't be read by an automated session, so this check didn't try further.
  - Four requests in all were sent to the API to learn its shape (a search for `test`, its details, and a search for a well-known film, read twice), each well over 10 s apart. Nothing from them is in the repository: every fixture is made up.
- **Finding:** no published term found forbids automated use of the API at a polite rate; its robots file sets 10 s between requests. **The plugin sends at most one request every 10 s** (`HostRate::every(10 s)` with no burst, `MIN_INTERVAL` 10 s, one request a lookup). That's stricter than the owner's one a second, which is a cap, not a target, so no owner number changes.
- **Not confirmed:** srrDB's help page (its API notes) couldn't be read here. **For the runner:** before the External consent gate lifts, a person should read `https://www.srrdb.com/help` in a browser and confirm nothing there forbids this use. If it does, the plugin stays off and comes out of the catalogue.
- **No account, no key.** The search needs none, so the class is External.

## Off by default, External class

- **The manifest:** `srrdb`, an Enrichment source, Consent `External`, endpoint `https://api.srrdb.com` only, `enabled_by_default: false`, never always-adult, never finds private. ENR-10's runtime sends nothing until it's enabled and its endpoint acknowledged (`off_by_default_nothing_is_sent`).
- **Eligibility is ENR-10's, as is:** never a `PRIVACY` item, held, hidden or Adult-off (`a_private_item_is_never_sent`).
- **Kind: Movie only.** srrDB's search results carry an IMDb id, the one thing the plugin can give the claims (below). For TV the id on an episode's release may be the episode's or the series', so a TV answer could name the wrong work; music, games and software have no IMDb id. The parser rejects any name with a season or episode token (`S01`, `S01E02`) for the same reason.
- **No host wiring**, as for Wikidata (runner, 2026-11-12): the plugin is library code listed in the catalogue.
- **`SENDS`** (`srrdb::SENDS`) says in plain words what leaves the install, for the Sources row. `Manifest` has no field for it; the runner decides where the row reads it from. srrDB asks for no attribution that this slice found, so there's no `ATTRIBUTION`.

## What is sent (Q5)

- **One request a lookup:** `GET https://api.srrdb.com/v1/search/<word>/<word>/…/<year>`, headers `Accept` and `User-Agent` only. The User-Agent is `Lodestar/<version> ( <the project's repository URL> )`, the same for every install.
- **The parsed title's words and the year, nothing else.** The title is folded (lower case, letters and digits only, every other run one separator) and each word is one encoded path segment, at most 12. So no word can be one of srrDB's search operators (`r:`, `imdb:`, `-word`), add a path segment, a query string or a fragment (`a_hostile_title_is_plain_words`, and the property test `any_title_is_plain_segments`). The year narrows the search; Q5 allows it. The kind isn't sent.
- **Never the torrent's raw name, hash, files, sizes or CRCs.** That's Q5's rule, and srrDB isn't one of its exceptions.

## What scene names, sizes and CRCs can and can't do here

- **The parser reads them:** `parse_search` keeps each result's release name, IMDb id and size; `parse_details` (for `/v1/details/<release>`) keeps a release's name and each stored and archived file's name, size and CRC-32. Both are fuzzed and tested.
- **The plugin can't use sizes or CRCs yet.** Matching a torrent to one scene release locally (same name, or the same file sizes and CRCs) needs the torrent's raw name and file list inside the plugin, and the runtime's `Query` gives it only the parsed title, year and kind (Q5). Widening `Query` was out of this slice, and sending them is ruled out. So the plugin matches on what `Query` has: **the film's title and year against each release name's title and year.**
- **Follow-up for the runner (not built):** a local-match step in ENR-10's runtime that hands an Identifier the torrent's own name and file sizes **without sending them**, would let srrDB confirm a torrent is a specific scene release (its details by the release name the search returned, then a local compare of sizes and CRCs; the CRCs need the torrent's file hashes, which BitTorrent v1 doesn't carry, so sizes and names are the practical match). It also needs a claims field for "scene release name", which `Identification` doesn't have.

## Choosing a match (`srrdb::choose`)

- **Each release name is read locally** (`scene_title`): the group after the last `-` is dropped when it has no separator; the words are split at `.`, `_` and spaces; the year is the **last** four-digit token from 1880 to 2100 after the first word (so `1917.2019…` is the film _1917_ and `Blade.Runner.2049.2017…` is _Blade Runner 2049_); the title is every word before it, folded.
- **A release agrees** when its title equals the query's folded title and, when the query has a year, its year equals it.
- **A match needs every agreeing release that carries an id to carry the same one, and every agreeing release the same year.** Two ids or two years (a remake, a mistagged release) are no match: it never guesses. No agreeing release with an id is no match.
- **The answer:** `imdb:tt…` (the store's one spelling, `ImdbId::parse`), the year (the query's, else the releases'), **no title, alternative titles or genres** (a scene name isn't a work's title). Confidence 80 with the query's year, 65 without; under ENR-10's cap.
- **A paged answer:** srrDB returns one page (45 results in the answers seen) and a `resultsCount`. The plugin reads only the first page: a release on a later page with another id isn't seen. Sending the year makes that rare, and a disagreement on the page seen is still no match.

## The parser (`sources-feeds/src/srrdb.rs`)

- **On the shared bounded JSON reader**, Wikidata's shape: pure, no I/O, no panics, no unwraps, linear time (a bitmask over the read keys; `many_unknown_keys_are_read_in_linear_time` reads 300,000 unknown keys in the root and in a result).
- **The caps** (`SEARCH_LIMITS`, `DETAILS_LIMITS`): 1 MiB, depth 8, 100,000 values, 1 KiB per decoded string, 255 bytes per kept name (`MAX_RELEASE`, the scene limit), 1,000 results a search and 2,000 files a list. Why: a page of 45 results is about 9 KiB, and a release stores a few files and archives at most a few hundred (multi-disc sets), so each cap is far above a real answer and far below what could hurt. Past a cap the parse stops and the answer isn't whole. The search is parsed on the blocking pool.
- **Strict shape:** a result needs a non-empty `release` string; `imdbId` is `null`, `""`, or seven digits (eight to ten with no leading zero; `tt` accepted), never all zeros; `size` is a whole number or `null`. A details file needs `name`, `size` and `crc` (exactly eight hex digits). Anything else spoils its part, so the answer isn't whole. A repeated or escaped read key spoils its part; unknown keys and their repeats don't matter.
- **What it keeps:** the names, ids, sizes and CRCs above. Never the dates, NFO/SRS/foreign flags, `warnings`, `query` or `adds`.

## Errors

- **Status first:** 200 is parsed; 429 or 503 is "limiting requests" and the host limiter holds the host (60 s to 6 h); a 3xx is never followed; anything else, or a transport failure, is "the request failed". A 200 whose body is an error object holds the plugin for its `Retry-After` (60 s when there's none, at least 10 s, at most an hour). A 200 that isn't `whole` (a bot-check HTML page among them) is "wasn't understood". **None of them is a miss**, and no error holds the service's text. A title with no word sends nothing.

## Terms (ENR-terms)

ENR-terms (#962) gave every identify plugin a `Terms` and an adult marker on its answers. srrDB's choices (`srrdb::TERMS`), from the terms check above (`api.srrdb.com/robots.txt`; srrDB's help page is still behind a bot check, so the runner's read of it before the consent gate stands), within the owner's v0.7 Q4 answer (at most one a second, user interest first):

- **`background_walk: false`.** Q4 says user interest first, and srrDB publishes nothing that allows bulk use; its `robots.txt` asks for 10 s between requests. Lookups stay on the items you open.
- **`redistribute: false`.** srrDB publishes no licence for its data, so nothing clearly allows passing its answers on. They stay in Lodestar's own UI.
- **`retention: Retention::DEFAULT`** (180 days). No published term asks for less.
- **`attribution`:** "srrDB", linked to `https://www.srrdb.com/`. srrDB asks for no credit that this slice found; the link is a courtesy.
- **Adult marker: `adult_marker_required: false`.** srrDB's search answer has no adult or category field. The scene's own adult mark is the `XXX` tag in a release name, so an answer whose agreeing releases include one tagged `XXX` (a whole word between `.`, `_`, space or `-`, any case) is `adult: Some(true)` and the runtime refuses it (`an_xxx_tagged_release_is_marked_adult_and_refused`, `srrdb::xxx_tagged`). An untagged name isn't a "not adult" mark, so every other answer is `None`. Requiring a marker would refuse every answer: the plugin answers Movie only, and the runtime never looks up an Adult item, which is the gate that matters.
