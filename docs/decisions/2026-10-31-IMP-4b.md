# IMP-4b decisions: the `lodestar import` CLI, docs and throughput

The second of IMP-4's two PRs, on top of IMP-4a (`2026-10-31-IMP-4.md`, the driver and removal). No migration.

## The commands
`lodestar import inspect|start|status|pause|resume|cancel|remove`, in `crates/lodestar/src/cli/import.rs`.
- **`inspect` only reads.** It prints:
  - the source's identity (the first 8 bytes of its dataset and schema digests, never a name or path);
  - its capabilities;
  - a row estimate: Magnetico's exact count from open, or Bitmagnet's `reltuples`, with no `count(*)` scan;
  - a free-space check.
  It exits 3 (refused) when space is short, and names an unfinished job already bound to the source.
- **`start`** creates a job for the source and runs it.
  - It refuses when an unfinished job already uses the source's identity, and names the job to resume.
  - It takes `--source magnetico --path …` (plus `--allow-share`), or `--source bitmagnet` with IMP-3's connection flags.
  - A flag of the other adapter is an error, not ignored.
- **`resume <job>`** reopens the source with the same flags, then revalidates through `Store::resume_import_job`:
  - identity;
  - credentials, always true here because nothing is sealed;
  - space for what's left.
  It then runs the job.
- **`pause`, `cancel`** change one job. **`remove`** takes a job's records back in steps of 5,000 (IMP-4a's rules). It asks first, as `rollback` does, unless `--yes`.
- **`status [job]`** lists jobs (the newest 50) or one job.
- **Output:**
  - plain lines by default;
  - `--json` on `inspect`, `start`, `resume`, `status` and `remove`;
  - progress on stderr every 50,000 records.
- **Exit codes:** the binary's usual ones.
  - 0: done or paused.
  - 1: the job blocked or failed, or another error.
  - 2: bad arguments.
  - 3: refused for safety, nothing changed. That covers a source refusal, the server running, a job that must be cancelled before removal, and no space at `inspect` or `start`.
  - At `resume`, too little space or a changed source blocks the job through the store's revalidation, so it exits 1 with the reason.
- **Per-reason counts are printed, not persisted** (IMP-2 and IMP-3 left the choice to IMP-4). They cover the adapter's findings plus `prepare_rejected`, for the run that found them, in the text and the JSON. The job's own counters, which are persisted, already carry `invalid` and `files_dropped`. Persisting per-reason counts across runs would need a schema change.
- **`OpenPolicy::approved_unc_roots`** comes from `--allow-share`, which can repeat. There's no config key: a share is approved for the one command that names it.

## Server running: refused (the brief's fallback)
- **Writes run only while the server is stopped.** That covers `start`, `resume`, `pause`, `cancel` and `remove`.
- **How the store is held:** these commands open the store and take SQLite's exclusive lock (`locking_mode = EXCLUSIVE`, then a write).
  - Every open connection holds a shared lock on the database file, the server's read-only ones included. So the lock fails while anything else has the store open, once the store's 5-second busy wait runs out. A busy error while opening the store is the same refusal.
  - The command then refuses (exit 3) with the safe step: stop Lodestar, import, start it again.
  - Once held, the lock keeps a server started meanwhile from opening the store until the import ends.
  - The import is then the store's only writer, which is IMP-1's "offline CLI under the data folder's exclusive ownership".
- **Routing an import through the running server's writer task** is a later slice's job, together with `origin="import"` in the gate (IMP-1).
- **`inspect` and `status` only read,** through `Store::open_reader`, and are safe while the server runs.
- **A data folder with no store yet is refused.** Lodestar must start once first, so it sets the store up and registers its own sources before an adapter's.
- **Pausing a running import from another process isn't possible,** because the import holds the store. So:
  - **Ctrl-C** sets the driver's stop flag and cancels the adapter's read. The job is paused at the last committed batch.
  - **A second Ctrl-C** exits at once (130). Every committed batch is safe; the job is left running, and `resume` carries on from its cursor after the driver rechecks the source.
  - `pause` applies to a blocked job.

## The filter, as the server builds it
The CLI builds the engine the way the server does at start:
1. `default_filter()`;
2. the config's blocklist files synced into the store's floor (`floor::sync_files`);
3. the config's subscriptions synced (`subscriptions::sync_config`), then the subscribed lists applied (`subscriptions::apply`);
4. the store's CS-1 entries, signatures and core switches;
5. packs, your rules and your classification rules.

Details:
- **The classification rules' generation is read before any of it** (IMP-4a).
- **Rules that no longer parse are skipped,** as the server skips them, and their number is printed.
- **The seal key:** `seal.key` is read if the server made one. Without it, a quarantine keeps no name, which is the safe direction. A key that can't be read or is malformed is warned about, not fatal. The CLI never creates the key; the server does.
- **A test runs `start` through this filter:** a hash in a config blocklist file and a name a drop rule matches are both refused.
- **The engine is assembled in two places,** here and at the server's start (`pipeline::load_filter` is private to `pipeline`). A shared loader in `pipeline` is the follow-up (fresh review, important), outside this slice's paths.
- **The quarantine length** comes from the config's pipeline settings.

## The legacy command
- **`lodestar import-bitmagnet` keeps its flags** and runs `import start --source bitmagnet`. It first prints that the command has a new name.
- **Run again, it resumes its unfinished job** for the same database, as the old command carried on from its cursor.
- **Its cursor file is bound explicitly once** (IMP-1: never automatically):
  - it's read through IMP-3's format and must name the source's dataset, or it's refused with the safe step;
  - its position becomes the new job's batch 1, committed with no records;
  - the file is renamed `….bound-to-job-<N>`, so it's never bound twice;
  - if a crash left the file in place, a later binding finds the job it was bound to (marked by its options, `legacy-cursor`; a plain `import start` job of the same database isn't one) and refuses with the safe step;
  - **the file is checked before the job is created** (runner, #257 review): a refusal leaves no job behind for a rerun to resume from an empty position past the cursor.
- **Removal and the indexing phase:** a job that read its whole source (`indexing`) can be removed even if paused; only a job that can still read is refused. The docs say so (runner, #257 review).
- **Torrents the old command stored can't be removed by job:** they have no membership row. The docs say a backup is their only undo.
- **`main.rs` no longer runs it.** It goes through `cli::run` like the other maintenance commands. The old in-process import (`bitmagnet::import`, `Options`, `Report`) has no caller left. It stays in the adapter's file for a later clean-up, since its tests still exercise the cursor format.

## Throughput (master plan F16)
- **Measured:**
  - `driver::tests::throughput_on_a_synthetic_100k_source` (ignored by default; run it in release with `--ignored throughput --nocapture`);
  - the source: 100,000 Magnetico torrents with three files each, an 80-byte release-style name, 33 MiB;
  - the run: imported through the full filter and enrichment into a file-backed store;
  - **the result on the build container: 7.2 s, about 13,900 torrents a second.** The store grew by 45 MiB, about 470 bytes a torrent before the search index.
- **The pass line for the pilots, set by this slice (not by the owner): at least 2,000 torrents a second** offline, in a release build, on the owner's server.
  - That's 10 million in under 1.5 hours.
  - It's about a seventh of the measurement here, to allow for an Unraid array disk and a real source's longer file lists.
- **Online, at most 50% of the writer's share** (F16), this slice's line halves to **1,000 a second**: 10 million in under 3 hours. That's the proposed target for the online-writer slice; the owner can change either line.
- **The line wasn't tuned to win.** Nothing was changed to improve the number.
- **Space:**
  - **The per-torrent figure** is the store's own size (the database plus the index) divided by its torrents, once it holds at least 10,000.
  - **Before that, 4 KiB a torrent:** about eight times the 470 bytes measured, which covers the index, the WAL and longer file lists.
  - **Headroom:** 25% on top.
  - **Free space** is measured on Unix only. Elsewhere it reads as unknown, and nothing is refused for space.

## Folded in from #253's review (runner)
- **The driver reports a job stopped elsewhere truthfully.**
  - **When it happens:** while the source ends or is refused, another connection pauses or cancels the job.
  - **Before:** the store refused the driver's own phase, block or pause change, and the run returned a store error.
  - **Now:** the driver reloads the job and ends `NotRunning` with that control.
  - A test covers both: a cancel after the last batch, and a pause before a refused read.
- **The crash-replay test compares every membership and quality row** with a clean run's, not only the counters and row count.
- **Removal and folded candidates:**
  - Candidates fold into the oldest row and keep its job, with no record of which other jobs contributed (IMP-1).
  - So removing a job also deletes a **public** candidate a later job folded into its row. That later job's waiting candidate is lost and can't be counted.
  - **Private ones are kept** (IMP-4a).
  - **What the loss costs:** nothing searchable. A candidate is never stored as a torrent, and the later job's source still holds the torrent for a re-import.
  - Keeping every folded candidate would need candidate membership, which is a schema change.
  - **Removal therefore takes back everything the job alone contributed, plus any public candidate folded into its rows.**
- **What a kept row loses:** a torrent kept because it was verified, reported by another source, or holds your items keeps `IMPORTED` and its quality row. It loses the removed job's membership. So no later job's removal reaches it: it's the crawler's or yours now.
