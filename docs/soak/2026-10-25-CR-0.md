## Stop conditions and assessment

Stop on process exit, three consecutive health/required-metric failures, three consecutive capacity violations, working set above 1 GiB for five samples, or active peer requests without a completion for five minutes. The sampler's reaching its capacity alone is expected backpressure and is not a stop condition. Guardrails are conservative operational stops, not a proof of per-request liveness or a throughput acceptance threshold.

To request an early stop, create an empty `stop.request` file in the run directory. The collector requests Ctrl+C, waits up to 60 seconds, and records whether the process exited or required force termination. It never automatically restarts either crawler. Raw process logs may contain a first-run setup token and remain local; publish only reviewed, sanitized evidence.

Review the completed run for ownership leaks, lookup progress, sampler bounds, memory trend, metadata conversion and searchable yield. Aggregate metrics cannot prove per-request queue age, first-peer latency, or exactly-once cleanup; deterministic tests cover those interfaces, and missing live measurements must remain explicit. Compare windows with matching configuration and include failures. Prior runs do not establish a throughput target, and this run will not by itself prove a speedup or Linux/Unraid behavior.
