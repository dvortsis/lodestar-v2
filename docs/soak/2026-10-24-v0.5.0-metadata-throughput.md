# Ongoing v0.5.0 soak: metadata-throughput investigation

Date: 2026-10-24, America/Denver. Status: investigation complete; findings open; soak still running.

## Assessment

**The throughput is severely inadequate, and the immediate bottleneck is finding useful peers, before metadata downloads.** At 22:10:55 MDT, approximately 13 hours 27 minutes into the run, 16,690,814 intake reports had produced 308 verified metadata fetches and 307 stored/searchable torrents. The pool had evicted 16,489,458 entries. Its 200,000-entry queue was full, its 256 logical lookup slots were occupied, and its metadata-fetch active gauge was zero.

This is not evidence that 16.7 million unique, live torrents were available: the counters count reports/admissions, the DHT seen filter rotates, and many sampled hashes can represent dead swarms. Nevertheless, evicting approximately 98.8% of admitted work while leaving metadata sockets idle demonstrates a severe scheduling/capacity mismatch. The roughly 23 stored torrents/hour average also masks deterioration: the last complete hourly interval produced **one** new stored torrent.

The source contains a reproducible lookup-progress defect that can permanently consume DHT lookup slots. It also contains an uncancelled lookup backlog whose work can outlive the pool entries requesting it. These should be addressed before raising metadata socket limits or increasing harvest intensity. **No code, configuration, settings, database, or running-process changes were made.** Only this report and diagnostic evidence were written; no restart, pause, update, network probe against public peers, or load test was performed.

## Findings

### S01 — High: ordinary DHT lookups can stall permanently and consume the 32-slot limit

**Evidence:** [actor.rs](../../crates/dht/src/node/actor.rs), lines 1240–1307, 1331–1365 and 1438–1453; [lookup.rs](../../crates/dht/src/node/lookup.rs), lines 125–185 and 225–238.

`drive_lookup` asks `Lookup::next()` for one batch of up to three candidates. For a failed send, or throttling of a non-scrape lookup, it marks the candidate failed. If all currently outstanding work settles through those immediate outcomes while other fresh candidates remain, the lookup has:

1. no pending packets to receive a response or expire;
2. fresh candidates, so `is_done()` is false;
3. no reschedule entry to run the next batch.

Maintenance drives lookups touched by packet timeouts. The explicit stalled-work list and overall deadline apply to scrapes, not ordinary `get_peers`. Thus this lookup can retain an `active_get_peers` slot indefinitely. The maximum is only 32, fixed independently of the intensity/socket preset. The same no-progress path can affect routing-maintenance lookups.

An offline diagnostic included the **actual current `Lookup` module** and simulated the actor's all-sends-fail branch. It produced:

```text
initial_batch=3
in_flight=0 extra_in_flight=0 fresh_candidates=13
is_done=false
manual_second_drive_batch=3
```

The lookup still has work but requires a drive the actor does not schedule. See [probe source](evidence/2026-10-24-metadata-throughput/lookup-progress-probe.rs) and [output](evidence/2026-10-24-metadata-throughput/lookup-progress-output.txt).

**Confidence:** high for the source defect; the probe tests the real lookup state machine with simulated send outcomes, not the full actor/network. The falling soak completion rate is consistent with slot leakage, but no current metric exposes active ordinary-DHT lookup ages or stalled-slot count. The number of slots affected in this process, and the share of slowdown caused by this defect, remain unproven. Cumulative throttling was only 257 at capture; low ongoing throttling does not release previously stalled slots. Send-error totals are not exported here.

**Recommended correction, not implemented:** give every lookup a bounded progress/deadline contract; reschedule work after immediate send failures/throttling, preserving rate limits and avoiding a busy loop. Release slots and report a terminal result on expiry. Add actor-level deterministic regressions for total/partial batch send failure, throttling, and slot recovery over repeated failures.

### S02 — High: pool and DHT request lifetimes diverge, allowing obsolete lookups to consume capacity

**Evidence:** [pool.rs](../../crates/sources/src/pool.rs), lines 88–99, 598–630, 637–677, 856–882 and 440–447; [dht.rs](../../crates/pipeline/src/dht.rs), lines 140–158; [actor.rs](../../crates/dht/src/node/actor.rs), lines 49–50, 565–568 and 1402–1407; [node/mod.rs](../../crates/dht/src/node/mod.rs), lines 506–511.

The pool allows 256 logical requests, starts a 30-second timer at submission, and uses a fire-and-forget channel. The DHT separately allows 32 running lookups and a 10,000-hash FIFO. Submission failure is ignored at both the pool→plugin and plugin→node boundaries; the internal DHT FIFO can also silently refuse a request. There is no acceptance/start acknowledgement, cancellation or request generation in the hash-only protocol.

When the pool timer expires, it releases its logical slot and can submit another request while the old DHT request is still queued/running. Evicting an entry also does not cancel the DHT request. When results arrive for an evicted key, the pool intentionally discards the reply. Empty completed lookups also do not explicitly end the pool's wait: `add_peers` returns if no peers were added, leaving timeout to settle it.

This permits throughput to be spent on hashes that no longer have a consumer. At the observed late-run completion rate, a **full** 10,000-entry DHT queue would require roughly 46–51 hours to drain, whereas a 200,000-entry pool exposed to 324–381 new reports/second turns over in approximately 9–10 minutes. These are conditional capacity estimates, **not measurements of the internal DHT FIFO length**. That length is not exported. The pool's 256/30-second timeout mechanism alone can cycle roughly 8.5 submissions/second when replies do not settle them, far above the observed 0.054–0.061 completions/second.

**Confidence:** high for the lifecycle mismatch in source and observed pool saturation. Exact stale-work count and reply lateness are unmeasured.

**Recommended correction, not implemented:** use an acknowledged request lifecycle with terminal empty/error/completed outcomes, deadlines and cancellation on eviction. Remove obsolete queued work, coalesce duplicate requests, and avoid charging a running timeout entirely to hidden queue wait. Keep queue capacity aligned with useful work lifetime.

### S03 — High: admission optimizes hash collection while starving useful metadata conversion

**Evidence:** [pool.rs](../../crates/sources/src/pool.rs), lines 466–510 and 853–882; [actor.rs](../../crates/dht/src/node/actor.rs), lines 49–58; [config.rs](../../crates/lodestar/src/config.rs), lines 672–703.

Every newly admitted peerless hash competes for the capped pool; once full, older idle entries are evicted. The 400-socket Balanced default does not expand the fixed 32-slot DHT peer-finding stage. Raising the preset can increase harvest/query volume and metadata socket capacity while leaving that hard lookup limit intact.

Evictions already accounted for approximately 98.8% of admissions by live end, and all non-eviction terminal fetch-loss counters were zero. This does not establish every eviction had never attempted a lookup, but it shows entries overwhelmingly leave through churn instead of completing the retry lifecycle. Peers-ready entries are protected by the current eviction rule, which is useful; the missing control is how much peerless work is admitted for available peer-finding capacity.

At the current hour-13 ratio there are roughly 5,978 incoming reports per completed DHT lookup. Increasing the pending cap would delay eviction while using more memory; it would not increase lookup throughput. Increasing metadata sockets alone would not supply those sockets with peers.

**Confidence:** high for the observed mismatch. There is no valid estimate yet of how many sampled hashes are actually fetchable, so no numerical speedup is promised.

**Recommended correction, not implemented:** after fixing S01/S02, allocate bounded work across discovery and peer finding based on measured conversion and queue age; prioritize fresh peer-bearing announcements and useful lookups; use an explicit bounded admission policy for excess sampled hashes. Preserve content-safety checks and per-IP limits. Benchmark useful stored/searchable metadata per time and network budget, rather than raw hash reports.

### S04 — Medium: peer reachability is poor, and uTP is not connected to the application fetch path

**Evidence:** [fetch.rs](../../crates/peer-wire/src/fetch.rs), lines 80–103 and 148–175; [config.rs](../../crates/lodestar/src/config.rs), lines 684–694; [transport.rs](../../crates/lodestar/src/settings/transport.rs), lines 1–3 and 43–49; [services.rs](../../crates/lodestar/src/services.rs), lines 101–122.

Most attempted TCP fetches fail and recorded connect timeouts dominate. This is a secondary limitation after supplying fresh peers. The peer-wire library implements uTP, but application construction inherits `Transport::Tcp` and `utp: None`. The stored transport settings explicitly have no runtime effect. The soak's zero uTP attempts corroborates that this run is TCP-only; changing the UI setting would not wire in uTP in the reviewed source.

The data cannot distinguish dead/stale addresses, remote firewall/NAT behavior, local connectivity issues or differences in protocol support. Successful TCP fetches and millions of DHT responses rule out complete connectivity failure, but do not prove inbound UDP reachability. Only 12 announces occurred in the last 60 summaries. A network/port-forwarding diagnosis needs the reachability evidence, not an assumption based on low announces.

**Recommended investigation, not performed:** after fixing lookup freshness/progress, measure fresh-peer yield and latency by transport and failure stage. Complete and validate the existing uTP integration as a separate change. Assess inbound reachability using the application's measured evidence and an authorized controlled test. Do not disable encryption, filtering or protective limits based on these aggregate counts.

### S05 — Medium: current telemetry hides where peer-finding capacity and queue time go

**Evidence:** [pool.rs](../../crates/sources/src/pool.rs), lines 909–920; [metrics.rs](../../crates/lodestar/src/metrics.rs); [actor.rs](../../crates/dht/src/node/actor.rs), lines 584–609.

- `fetch_lookups=256` is the pool's logical waiting count, not the DHT's actual running lookup count (maximum 32).
- `fetch_lookup_backlog` reports deque length, including lazily removed stale entries. It reached 204,821 while the entire live pool contained 200,000 entries. It is not an exact count of distinct live waiting keys.
- `harvest_summary dropped=0` reports the DHT emission boundary. It does not mean work was retained downstream; over 16 million entries were evicted later.
- There are no exposed ordinary-DHT queue ages, running ages, no-progress slots, rejected asks, expired/cancelled queued requests, empty responses or late results discarded after eviction.
- The supervisor health endpoint measures process/source liveness, not useful progress. Of 802 captured samples, 798 returned 200 and four were `ERR`; it still allowed many near-idle fetching hours. The four errors occurred at 08:50:51, 21:03:14, 21:05:36 and 21:07:48 MDT. Its catch-all does not identify the error cause.

**Recommended correction, not implemented:** add stage-specific throughput and latency, accepted/started/completed/cancelled/empty/rejected lookup counts, live queue size/age, stalled-slot gauges and evictions-before-first-attempt. Show metadata progress separately from harvesting and liveness. Alert on sustained high admission plus near-zero useful completions.

## What the evidence does not support

- **A saturated writer/indexer:** successful fetches reconcile with stored plus quarantined torrents, and storage/index errors are zero.
- **Metadata socket exhaustion in this application:** 12 of the 13 hour-1-through-hour-13 snapshots have zero active metadata fetches; the other has one. The observed attempt rate is very low. System-wide Windows port exhaustion was not measured, so it is not categorically ruled out.
- **CPU or RAM saturation as the primary cause:** supervisor CPU averaged about 13% of one core, private memory ranged 179–366.2 MiB and was approximately 280 MiB at capture. These are process-level samples, not CPU profiling or a machine-wide resource survey.
- **A successful ongoing soak:** the run has not reached its deadline, four health reads failed, and performance is unacceptable. The previous stability-only pass cannot be transferred to this build.

## Recommended order and validation for a later implementation

1. Repair lookup forward progress and deadlines (S01), with deterministic actor-level tests proving slots recover after failed sends and throttling.
2. Couple pool/DHT request lifetimes and cancellation (S02), then test a sustained harvest flood against slow and empty peer lookups. Verify obsolete work cannot dominate the DHT queue and valid late results have a defined policy.
3. Add the telemetry in S05 and balance admission/peer discovery (S03). Compare the same controlled corpus, reachable-peer distribution and network budget; separate first-hour performance from steady state. Require no progressive loss of lookup capacity.
4. Measure useful-peer coverage and TCP/uTP behavior (S04) after peer-finding flow is healthy. A socket/concurrency increase is only justified when active fetches actually approach the configured cap.
5. Repeat the real-network soak with per-minute throughput, latency and queue-age captures. Record verified metadata and searchable additions per hour, conversion by discovery source, eviction-before-first-attempt and the proportion of lookup work whose consumer has already disappeared. Set a product throughput target explicitly before using the next run as an acceptance gate; these observations cannot establish achievable public-network yield on their own.

Validation performed here: read-only telemetry reconciliation, deterministic offline execution of the existing lookup module, source tracing, and report/evidence checks. No full test suite or synthetic network load was run against the machine during the soak.
