# Additional crawler performance methods — 2026-11-16

> Evidence correction: the [counter-review](2026-11-16-antigravity-throughput-assessment-review.md) distinguishes measured improvements from reference implementations and cross-system simulations. In particular, the “seven proven methods” framing below overstates the evidence for methods 5–7; the clone/sort claim and unconditional low-risk subnet recommendation are also corrected there. This document preserves the assessed proposal.

Seven routing-table and lookup-execution techniques pass the screen for credible external primary-source measurements or mature reference implementations and have no prior proposal, implementation, or test found in this project's inspected records (following three initial routing-table methods plus four additional proven methods identified in the follow-up review). None establishes an end-to-end Lodestar throughput gain on its own. This extends the [strategy assessment](2026-11-16-dht-throughput-strategy-review.md) without changing production code or running network experiments.

## Primary evidence

### Initial three routing-table methods (updated with churn & Lodestar code links)

1. **Prefer lower-RTT routing contacts (`NRTT`)** — Raul Jimenez, Flutra Osmani, and Björn Knutsson, *"Sub-Second Lookups on a Large-Scale Kademlia-Based Overlay"*, IEEE P2P 2011 ([university-hosted paper](https://www.diva-portal.org/smash/get/diva2:436670/FULLTEXT01.pdf), §V-C, Table I). Live Mainline DHT (`3,078` infohashes, `80+` hours): median first-value latency improved **510 → 459 ms** (`−10.0%`) under standard lookup (`-S`) and **284 → 185 ms** (`−34.9%`, p75 **420 → 291 ms**, p98 **2,619 → 512 ms**, p99 **3,247 → 566 ms**) under aggressive lookup (`-A`), while keeping maintenance traffic identical to `NICE`. Standard-lookup p99 worsened slightly (`5,488 → 5,737 ms`).
2. **Enlarge distant routing buckets (`NR128`, `128/64/32/16/8`)** — Jimenez et al., IEEE P2P 2011 (§V-D, Table I) and Hani Salah, Stefanie Roos, and Thorsten Strufe, *"A Lightweight Approach for Improving the Lookup Performance in Kademlia-type Systems"*, 2014 ([technical report](https://arxiv.org/pdf/1408.3079), Fig. 1(b), Tables I & II, §VI-B).
   - *Live MDHT gain (after `NRTT`):* median latency improved **459 → 286 ms** (`-S`, p75 **928 → 589 ms**, p98 **5,060 → 4,375 ms**) and **185 → 164 ms** (`-A`, p75 **291 → 269 ms**, p98 **512 → 506 ms**), while cutting `NR128-S` lookup cost below `UT` and cutting maintenance traffic far below `UT` (`20 queries/min` vs `UT`'s `15-min` bursts).
   - *Lodestar code connection (`insert_lookup`):* In [actor.rs](../../crates/dht/src/node/actor.rs#L1893-L1900), every lookup is seeded with `table.closest(&target, 16, self.now_secs())`. Because bucket 0 (`prefix_len == 0`, covering `50%` of uniform targets) currently holds at most `K = 8` contacts, `8` of the `16` initial lookup candidates for any opposite-half-space target are pulled from buckets `1..` (wrong half-space, `0` shared prefix bits), and the closest initial contact in bucket 0 shares only ~`log2(8) + 1 = 4` bits instead of ~`log2(128) + 1 = 8` bits.
   - *Implementation caveat & churn risk:* Currently, `RoutingTable::closest` ([routing.rs](../../crates/dht/src/routing.rs#L376-L383)) clones and sorts **every** non-bad entry across the whole table on both outbound lookup starts and inbound `nodes_for` replies ([actor.rs](../../crates/dht/src/node/actor.rs#L1179-L1195)); before enlarging buckets, replace full-table clone+sort with an outward walk from `bucket_index(target)` as in `arvidn/libtorrent`'s `routing_table::find_node` ([RC_2_0 `routing_table.cpp`](https://github.com/arvidn/libtorrent/blob/70272f366804ded6c3bfefb2af5088acc6bddae1/src/kademlia/routing_table.cpp#L1104-L1189)). Furthermore, Salah et al. (2014, §VI-B, Tables I–II) observe that under churn (`10,000 s` mean session), flat `128/64/32/16` buckets (`iMDHT`) fill slowly and accumulate stale contacts compared with smaller multi-bucket prefix partitions (`2.69084` vs `2.31668` mean hops).
3. **Within-bucket ID prefix diversity** — Salah, Roos, and Strufe (2014, Theorem 1, §IV-C, §VI-A–C, Tables I & II): preferring contact replacements that maximize the distinct prefix bits covered inside each bucket (without changing bucket structure or query rate) reduced **live eMule KAD** mean hops from **3.39862 ± 0.01583 → 3.23172 ± 0.01310** (`4.08%` conservative CI difference, ~`4.9%` point difference). In simulated **MDHT**, it cut static mean hops (`N = 10,000`) by **4.32%** (`2.89185 → 2.76774`) and under **churn** (`20,000 s` and `10,000 s` mean session lengths) cut hops by **6.20%–6.26%** (`3.21380 → 3.01311` and `3.32362 → 3.11264`, Table II).

### Four additional proven methods (not yet discovered or tested in Lodestar)

4. **`NICE` routing-table quarantine (3-minute stability gate) and smooth single-contact stale probing**
   - *Credible primary sources:* Jimenez, Osmani, and Knutsson, IEEE P2P 2011 (§V-B, §VII-A–C, Tables I & II, Figs. 5–6), building on their Mainline DHT connectivity study (IEEE P2P 2009) and Godfrey, Shenker, and Stoica, *"Minimizing Churn in Distributed Systems"*, ACM SIGCOMM 2006 (filtering short-lived contacts under heavy-tailed uptime distributions).
   - *Why the initial survey missed it:* The earlier pass extracted `NICE → NRTT` and `NRTT → NR128` from Jimenez et al. (2011) Table I, omitting the single largest routing-table improvement in that same table: **`BEP5 → NICE`**.
   - *Measured primary evidence (live MDHT, `3,078` infohashes, `80+` hours):*
     - Standard lookup (`-S`): `BEP5-S → NICE-S` cut median first-value lookup latency from **1,105 → 510 ms (`−53.8%`)**, 75th percentile from **3,011 → 877 ms (`−70.9%`)**, 98th percentile from **6,828 → 4,468 ms (`−34.6%`)**, and 99th percentile from **7,540 → 5,488 ms (`−27.2%`)** (Table I).
     - Aggressive lookup (`-A`): `BEP5-A → NICE-A` cut median latency from **825 → 284 ms (`−65.6%`)** and 75th percentile from **2,601 → 420 ms (`−83.9%`)** (Table I).
     - Query response rate & maintenance cost (Table II, Figs. 5–6): `BEP5-S` received replies to only **54%** (`36,361 / 67,454`) of lookup queries (**46% timeouts**), whereas `NICE-S` raised lookup query response rate to **64%** (`43,937 / 68,923`, cutting timeout waste by ~10 percentage points) while **reducing** cumulative maintenance traffic below `BEP5-*` via smooth `1 ping / 6 s` (`10 queries/min`) stalest-contact probing instead of `15-minute` bursts.
   - *Current Lodestar gap & cold-start mitigation:* In [routing.rs](../../crates/dht/src/routing.rs#L206-L305) and [actor.rs](../../crates/dht/src/node/actor.rs#L1400-L1418), any node answering a single outbound query (`Contact::Response`) enters a live bucket immediately (`Inserted::Added` or `Inserted::Replaced`) with zero quarantine or 3-minute uptime check, and `maintain()` ([actor.rs](../../crates/dht/src/node/actor.rs#L2253-L2275)) pings up to `PINGS_PER_TICK = 16` questionable nodes per tick plus up to 2 pings per `Pending` response. In `CR-0` final ([cr0-final.md](../soak/evidence/2026-10-30-cr0-final/cr0-final.md#L213-L216)), **2,512,425 of 6,576,224 outbound DHT queries (38.2%) timed out** — making contact stability gating directly relevant to Lodestar's lookup slot occupancy. *Cold-start constraint:* do not hold contacts in quarantine when a bucket has empty slots or while `table.len() < HEALTHY_NODES (32)` ([actor.rs](../../crates/dht/src/node/actor.rs#L2309-L2315)), or initial bootstrap would stall and re-trigger `start_bootstrap` every `30 s` during `CR-SPEC` warmup; instead populate empty slots directly and use `Bucket::replacements` (`routing.rs:308–329`) as the 3-minute quarantine staging buffer before replacement promotion.

5. **Two-stage decoupled `short_timeout` (1 s stall-slot release without cancelling the RPC or penalizing the routing table)**
   - *Credible primary sources:* `arvidn/libtorrent` (`RC_2_0` commit `70272f366804ded6c3bfefb2af5088acc6bddae1`, [`rpc_manager.cpp#L397-L463`](https://github.com/arvidn/libtorrent/blob/70272f366804ded6c3bfefb2af5088acc6bddae1/src/kademlia/rpc_manager.cpp#L397-L463) and [`traversal_algorithm.cpp#L350-L408`](https://github.com/arvidn/libtorrent/blob/70272f366804ded6c3bfefb2af5088acc6bddae1/src/kademlia/traversal_algorithm.cpp#L350-L408)); Crosby and Wallach, *"An Analysis of BitTorrent's Two Kademlia-Based DHTs"*, IPTPS 2007 (cited in Jimenez et al. 2011 §IX: dead routing-table nodes combined with multi-second RPC timeouts dominate Mainline latency tails); Jimenez et al. (IEEE P2P 2011, Fig. 2: live Mainline RTT CDF has p25 **94.8 ms**, median **175.2 ms**, p75 **343.6 ms**, and p98 **1,093.9 ms**).
   - *Why it is distinct from already-covered adaptive hard timeouts or global `α`/`β` branching:* Raising `α` or `β` increases packet fan-out on *every* hop even when peers are fast; shrinking the hard timeout (`query_timeout = 4 s` in Lodestar) discards legitimate slow replies and falsely marks slow live nodes `Status::Bad`. Instead, `libtorrent` decouples lookup pacing (`short_timeout = 1 s`, near the 98th percentile of live MDHT RTTs) from transaction eviction (`timeout = 15 s`):
     - When an in-flight lookup RPC passes `short_timeout`, `observer::short_timeout()` fires *without* deleting the transaction and *without* calling `table.node_failed(...)` (`traversal_algorithm.cpp:355`).
     - It increments `m_branch_factor` (`line 375`) and immediately calls `add_requests()` (`line 399`) to dispatch the next fresh candidate.
     - If the slow node later replies before the hard timeout, its `nodes`/`values` are absorbed and `restore_branch_factor()` restores concurrency (`lines 396–408`).
   - *Current Lodestar gap & integration requirements:* In [mod.rs](../../crates/dht/src/node/mod.rs#L241-L243), [actor.rs](../../crates/dht/src/node/actor.rs#L1955-L1965), [actor.rs](../../crates/dht/src/node/actor.rs#L2206-L2237), and [lookup.rs](../../crates/dht/src/node/lookup.rs#L139-L158), Lodestar uses a single hard `query_timeout = 4 s` checked only on `cfg.tick = 1 s`, caps concurrency in **two** places (`self.in_flight >= ALPHA` inside `Lookup::next_limit` and `3usize.saturating_sub(r.inflight)` across family legs inside `drive_lookup`), and blocks termination in `Lookup::is_done()` ([lookup.rs](../../crates/dht/src/node/lookup.rs#L254-L265)) while `self.in_flight > 0 || self.extra_in_flight > 0`. Implementing `short_timeout` cleanly requires: (a) advancing both `Lookup::in_flight` and `PeerRequest::inflight` stalled-slot counters while keeping the transaction in `self.pending`; (b) exempting short-timed-out RPCs from blocking `is_done()` once the `K` closer non-stalled candidates settle (and pairing with `CR-1a-S` early fetch verification); and (c) checking `short_timeout` on a sub-second timer (`~200–250 ms`, matching `libtorrent`'s `200 ms` minimum tick at `rpc_manager.cpp:462`) instead of the coarse `1 s` tick (`1.0–2.0 s` actual delay).

6. **Multi-bit prefix (`b`-bit / zone-split) routing-table tree (including splitting around all local BEP 42 `virtual_ids`)**
   - *Credible primary sources:* Petar Maymounkov and David Mazières, *"Kademlia: A Peer-to-Peer Information System Based on the XOR Metric"*, IPTPS 2002 (§2.4: splitting `b` bits per level cuts expected hops from `log2 N` to `(1/b) log2 N`); Daniel Stutzbach and Reza Rejaie, *"Improving Lookup Performance over a Widely-Deployed DHT"*, IEEE INFOCOM 2006; Salah, Roos, and Strufe (2014, §II, Fig. 1(a)–(c), Tables I & II: direct comparison of `MDHT`, `iMDHT`/`NR128`, and `KAD`'s multi-bucket prefix tree).
   - *Measured / validated primary evidence (Salah et al. 2014, Tables I & II, `N = 10,000`):*
     - Static (`Table I`): `MDHT` **2.89185** mean hops vs `iMDHT` (`NR128`) **2.31113** hops vs `KAD` multi-bucket prefix tree **1.98609** hops (**−31.3%** vs `MDHT`, **−14.1%** vs `iMDHT`).
     - Under churn (`10,000 s` mean session, `Table II`): `MDHT` **3.32362** hops vs `iMDHT` **2.69084** hops vs `KAD` **2.31668** hops (**−30.3%** vs `MDHT`, **−13.9%** vs `iMDHT`). Unlike one flat `128`-node top bucket in `NR128`, splitting top levels into `K = 8` prefix sub-buckets maintains smaller, fresher buckets while guaranteeing coverage across every top-level keyspace prefix.
   - *Current Lodestar gap:* In [routing.rs](../../crates/dht/src/routing.rs#L278-L280), `RoutingTable` only splits the single bucket containing `self.own` (`idx == count - 1`). Under `WK-4` ([2026-11-06-WK-4.md](../decisions/2026-11-06-WK-4.md#L5-L12)) and [`Actor::id_for`](../../crates/dht/src/node/actor.rs#L750-L756) ([dispatch_query](../../crates/dht/src/node/actor.rs#L1062-L1065)), `Actor` already generates `virtual_ids = 4` BEP 42 node IDs ([mod.rs](../../crates/dht/src/node/mod.rs#L134), capped at `Shard::id_cap` when keyspace sharding is active) and presents the closest of `self.ids` on every node-targeted query (`ping`, `find_node`, `get_peers`). Yet [`RoutingTable::new(ids[0], ...)`](../../crates/dht/src/node/actor.rs#L663) ([rebuild on external IP change](../../crates/dht/src/node/actor.rs#L1590)) splits only around `ids[0]`, discarding prefix resolution around `ids[1..4]`. Allowing bounded top-level multi-bit zone splits (or splitting buckets covered by all `self.ids`, and focusing sub-range `WK-4` shards on their `[start, end)` prefix range) avoids `NR128`'s stale top-bucket weakness under churn while achieving multi-bit hop reductions.

7. **Per-lookup `/24` (IPv4) & `/64` (IPv6) candidate shortlist diversification and same-IP multi-port deduplication**
   - *Credible primary sources:* `arvidn/libtorrent` (`RC_2_0` commit `70272f366804ded6c3bfefb2af5088acc6bddae1`, `settings_pack::dht_restrict_search_ips = true`, [`traversal_algorithm.cpp#L194-L229`](https://github.com/arvidn/libtorrent/blob/70272f366804ded6c3bfefb2af5088acc6bddae1/src/kademlia/traversal_algorithm.cpp#L194-L229), [`routing_table.cpp#L468-L494`](https://github.com/arvidn/libtorrent/blob/70272f366804ded6c3bfefb2af5088acc6bddae1/src/kademlia/routing_table.cpp#L468-L494)); Liang Wang and Jussi Kangasharju, *"Real-World Sybil Attacks in BitTorrent Mainline DHT"*, IEEE GLOBECOM 2012 / IEEE P2P 2013; Ingmar Baumgart and Sebastian Mies, *"S/Kademlia: A Practicable Approach Towards Secure Key-Based Routing"*, IEEE ICPADS 2007.
   - *Current Lodestar gap:* Lookup shortlist diversity; see the runner's security records.

## Why these are additional methods here

The audit covered checked-in DHT source/tests, the October 24 research, October 25 implementation plan, build plan, crawler decision/soak records and the earlier review, plus reachable Git history searched for the techniques and their terminology. No previous proposal, implementation or test of these specific policies was found. This cannot rule out experiments outside the repository or under substantially different terminology.

Current implementation evidence:

- [Routing table](../../crates/dht/src/routing.rs): `K = 8`; entries track contact health and times (`last_response`, `failures`), with no RTT estimate or 3-minute admission quarantine (`insert` admits `Contact::Response` directly into live buckets at lines `263–291`). Full buckets retain good contacts, replace bad contacts or cache replacements; only `self.own` (`ids[0]`) splits (`idx == count - 1`). `closest` (`lines 376–383`) collects and sorts the entire non-bad table on every call.
- [Lookup](../../crates/dht/src/node/lookup.rs): `ALPHA = 3`; candidates are selected by XOR distance; actor checks a single hard `query_timeout = 4 s` once per `1 s` tick ([actor.rs](../../crates/dht/src/node/actor.rs#L2206-L2237)).
- [Earlier research](../soak/2026-10-24-modern-dht-research.md) already covers hard lookup deadlines, global `α`/`β` aggressive branching, metadata peer racing, UDP batching, uTP/hole punching, and IPv6. Neither `NICE` 3-minute quarantine + paced single-node probing, decoupled `short_timeout` slot release without transaction cancellation, multi-bit prefix zone splitting, nor per-lookup `/24`/`/64` candidate diversification appears there or in the decision slices.
- [Prefix traversal experiment](../decisions/2026-11-01-CR-1b.md) changes exploration/sampling target prefixes (`CR-1b`). Changing lookup-shortlist subnet diversity (`Method 7`), routing-table tree branching (`Method 6`), or within-bucket replacement (`Method 3`) alters which contacts route or answer for any target; `CR-1b` did not test any of those mechanisms.
- Routing-table stability/structure and lookup slot unblocking are orthogonal to enlarging the BEP 51 cooldown ledger proposed in the original survey.

The history check included `git log --all -G` over routing/lookup code and research/decision/plan records for `NRTT`, `NR128`, `Kadabra`, `NICE`, `quarantine`, `short_timeout`, `dht_restrict_search_ips`, proximity, identifier diversity, bucket diversity and low RTT. It returned no matching commits before this review work. Broader source/document searches likewise found no relevant prior candidate beyond the already-known techniques above.

## Applicability and experiment order

Note that **Method 7** (per-lookup `/24` & `/64` shortlist diversification and same-IP deduplication) is a low-risk eclipse-resilience change that can be verified in unit tests and `CR-SIM` before or alongside routing changes. For throughput experimentation under frozen [CR-SPEC](../decisions/2026-11-02-CR-SPEC.md) (after `CR-AB-ADM`, `CR-AB-4`, and `CR-1a-*` / `CR-1c` address admission and metadata conversion):

1. **Decouple lookup stalls first via `short_timeout` (`Method 5`) and outward bucket-walk `closest`:** Before raising routing-table size, remove the `4–5 s` single-timeout freeze on `38.2%` dead queries by firing a `short_timeout` (`~1 s`) slot advance without failing the routing node or aborting late replies, and replace the full-table sort in `RoutingTable::closest` with an outward bucket walk from `bucket_index(target)`. Screen against `CR-SIM` first at matched aggregate `queries_per_sec` / `max_outstanding` caps.
2. **Test `NICE` quarantine (`3 min`) + paced single-contact stale probing (`Method 4`):** Directly targets Lodestar's `38.2%` outbound DHT timeout ratio and maintenance burstiness by validating transient responders before promoting them out of `replacements` and smoothing pings to `1 / 6 s`. Measure lookup query response rate, `dht_timeouts_total`, and occupied lookup duration at equal aggregate query budgets.
3. **Compare multi-bit top-level prefix splitting (`Method 6`) vs nonuniform `128/64/32/16` capacity (`Method 2`):** Under churn (which Mainline experiences continuously), test splitting top prefix levels or splitting around all local `virtual_ids` against flat `128/64/32/16` distant buckets (keeping internal bucket sizes decoupled from wire `K = 8` replies and lookup termination constants, and defining capacity strictly by bucket prefix length). Measure stale-entry ratio and maintenance cost alongside first-peer and full-lookup duration.
4. **Evaluate `NRTT` low-RTT retention (`Method 1`) and within-bucket ID prefix diversity (`Method 3`):** Collect RTT from clean first-attempt responses (using aging and replacement hysteresis so instantaneous jitter does not churn buckets; watch p99 latency and geographic concentration as rejection criteria), and prefer replacement contacts that increase sub-prefix diversity once stability/health gates pass.

For every experiment, follow frozen `CR-SPEC`: use `searchable_new_total{origin="network"}` at matched aggregate DHT packet budgets, logical lookup slots (`32`), and metadata socket limits; record first-peer latency separately from full occupied lookup time, `dht_timeouts_total`, empty/no-peer outcomes, new verified inserts/min, bytes per new insert, and maintenance traffic; include cold/rare sampled hashes rather than popular swarms alone; use paired ABBA + BAAB blocks (`dht.safe_restart=true` with host-mounted witness) to handle warmup and catalog depletion. No live experiment or production edit is authorized by this research note.

## Exclusions

Already-discovered approaches were excluded even when untested: trackers, PEX, IPv6, uTP/hole punching (`CR-4`), hints (`CR-1a-H`), streaming (`CR-1a-S`), freshness/admission (`CR-ADM`), shared lookup caching, deduplication, single hard-timeout / global `α`/`β` branching tuning, peer racing, socket/UDP batching (`aquatic`/Syscall batching), and target-prefix traversal (`CR-1b`). Simulator-only or cooperative-overlay proposals requiring protocol changes on remote DHT peers were not promoted to the shortlist. The list deliberately contains no claimed multiplier for verified torrents/minute.

Validation: source and experiment-history inspection (`crates/dht`, `docs/`, `arvidn/libtorrent` `RC_2_0` at `70272f36`), primary-paper/table verification (`jimenez2011.pdf`, `salah2014.pdf`), and documentation diff checks only. No production tests were rerun for this documentation-only addition; no fleet, configuration or runtime was changed.
