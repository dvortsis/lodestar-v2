# DHT throughput strategy assessment — 2026-11-16

**Yes: improving admission, freshness and peer conversion can plausibly produce a material throughput gain. The strongest local evidence favors coordinated admission. The proposed sampling scheduler alone has a much weaker case, and 100 newly verified searchable torrents/minute remains an unproven target.** This is the strategy follow-up to the [crawler survey and scheduler review](2026-11-16-dht-crawler-survey.md). It incorporates the earlier review findings in the same review-branch commit; no production source, configuration or runtime was changed.

The assessment below distinguishes recorded experiments, arithmetic and proposed experiments. The existing simulation screens and historical soak were inspected, not rerun here. The scheduler counterexamples were reproduced offline. No current process configuration or live throughput was measured.

The follow-up [additional methods research](2026-11-16-dht-additional-methods.md) identifies seven routing-table and lookup-execution techniques (`NRTT`, `NR128`, within-bucket prefix diversity, `NICE` 3-minute quarantine + paced probing, two-stage decoupled `short_timeout`, multi-bit prefix splitting / `virtual_ids`, and per-lookup `/24`/`/64` shortlist diversification) with credible external measurements or reference implementations and no prior proposal or test found in the inspected project records, while distinguishing lookup gains from crawler throughput.

## Evidence that changes the priority order

The original survey acknowledged existing hints and streaming code but omitted their checked-in performance screens. That omission made the ranking too optimistic about hints alone. The repository already contains a stronger basis for choosing the first experiment:

While Bitmagnet clamps intervals >300 s down to 60 s when novel hashes arrive and reports `stored` rather than Lodestar's strict-interval `searchable_new_total{origin="network"}`, this proves the host/link can sustain >300 torrents/min when discovery and fetch pipeline occupancy are resolved.

That baseline cluster (`11.1–17.0 stored/min`) predates enabling the opt-in switches (`CR-ADM`, `CR-4` uTP/route backoff, `CR-1a-*`) and measures `stored`, not searchable yield. Reaching 100/min would require **~6–9×** the observed stored rates, making conversion and fetch-timeout recovery (`74.1%` fetch timeouts → `CR-4` uTP) just as central as admission control.

## Where the gain could come from

1. **Coordinate admission and keep admitted work alive long enough to finish.** Remove repeated submissions to a full finder, distinguish waiting from an attempted lookup, and preserve cancellation/deadline ownership. This reduces wasted local work and premature backoff without spending more network budget. It is already implemented behind `dht.coordinated_admission`, off by default. Confirm the deployed binary and effective switch before counting it as new work. The recorded first version actually collapsed from 29.8 to 0.3 simulated stores/min when FIFO admission selected entries that oldest-first eviction immediately removed; the corrected screen includes bounded protection for permitted lookups. A “small fresh queue” must retain that protection. [Admission design](../decisions/2026-10-30-CR-ADM.md)

2. **Spend scarce lookup service on fresh, actionable evidence.** Keep a small ready set and a bounded deferred set; preserve source, observation time, hints, peer batches and attempt state. Give exploration and old/rare hashes an explicit fair share. Novel hashes alone are a poor productivity score: rank sources by eventual new verified output per query or occupied lookup-second, using bounded aggregation and delayed attribution. A token-valid announcement or syntactically valid peer address is still untrusted evidence of a live swarm. Preserve endpoint policy checks and cap work contributed by one source.

3. **Make hints usable before expecting hints to help.** Existing hint TTL and destination-IP spacing are both 60 seconds. A sample containing many hashes from one responder cannot give every hash an immediate hinted query; ordinary routing also honors that IP restriction. Select a bounded representative fresh candidate per responder and measure capture-to-admission age, expired hints, guard skips, peers returned and verified output. Keep the guard. Simply enabling hints on an aging queue reproduced little benefit in the existing screen. BEP 51's stored-key association supplies a sound reason to try the responder, but no guarantee of a reachable metadata peer. [Hint contract](../decisions/2026-10-30-CR-1a-H.md), [BEP 51](https://www.bittorrent.org/beps/bep_0051.html#sampling-rpc)

4. **Relieve the next measured limit.** If cooldown capacity blocks useful discovery while lookup service is hungry, expand safe retention incrementally. If admitted lookups hold all slots, reduce occupancy or test bounded concurrency under the same aggregate query budget. If metadata sockets are busy with failures (`74.1%` of `CR-0` failures were `timed_out`), run `CR-AB-4` (`dht.utp`, already wired by [CR-4](../decisions/2026-11-02-CR-4.md)), then test timeout policy and selective peer racing. If sockets are idle, adding sockets or racing peers cannot supply missing candidates. Streaming can overlap stages and sometimes cancel a successful lookup earlier, but does not itself increase the 32-request actor cap.

## Code-level blind spots and immediate opportunities in Lodestar

Inspecting [actor.rs](../../crates/dht/src/node/actor.rs), [hints.rs](../../crates/dht/src/node/hints.rs), [admission.rs](../../crates/sources/src/pool/admission.rs), and the decision records exposes four specific code interactions not called out in the initial review:

1. **Opportunity A — Fix `CR-1a-H` (`dht.responder_hints`) collateral routing damage safely ([actor.rs](../../crates/dht/src/node/actor.rs#L1976-L1988), [lookup.rs](../../crates/dht/src/node/lookup.rs#L119-L131)).** `Hints::sent` sets a 60 s per-IP restriction in `Hints::guard`, and `drive_lookup` checks `self.hints.as_ref().is_some_and(|h| h.restricts(n.addr.ip(), Instant::now()))` on **every ordinary lookup** (`get_peers` and `find_node`), incrementing `hint_guard_skips` and calling **`l.on_failure(&n.id)`** — permanently marking that routing-table node `State::Failed` for that lookup (unlike query throttling at line 2027, which calls `l.retry_later(&n.id)`). In the `CR-1a-H` screen ([hints screen](../decisions/2026-10-30-CR-1a-H.md#L48-L55)), `hint_guard_skips` (`376` to `2,839`) exceeded `hint_queries` (`209` to `1,064`) by **1.8×–2.7×**, explaining why `CR-1a-H` lengthened mean lookup duration (`5,485 → 5,648 ms`) and reduced yield (`−1.2%` to `−3.7%` in two scenarios). Note that neither deleting the check globally nor replacing it with `l.retry_later(&n.id)` is safe: removing it violates `ip_rotation_shares_one_restriction_with_no_fallback_bypass` (allowing the same lookup's ordinary fallback leg to re-query the hinted IP inside 60 s), while `l.retry_later(&n.id)` leaves the restricted node `State::Fresh` (`HINT_NOT_BEFORE = 60 s > LOOKUP_DEADLINE = 25 s`), occupying a top-`K` slot and preventing `Lookup::is_done()` from finishing early. The safe fix is introducing a non-blocking `State::Skipped` candidate state excluded by `Lookup::slot_filter` (so guard-restricted contacts neither mark routing nodes failed nor block `K`-slot completion), or scoping the guard to per-lookup / hinted dispatch while skipping hint capture for already cooling IPs.
2. **Opportunity B — Resolve the `CR-ADM` FIFO residency violation (`Little's Law`) alongside `CR-1a-H` (`pool.rs`, [admission.rs](../../crates/sources/src/pool/admission.rs#L106-L112), [gate.rs](../../crates/pipeline/src/gate.rs#L91-L115)).** Under `CR-ADM`, `discovered_at` is stamped when a hash enters `Pool::entries` ([pool.rs](../../crates/sources/src/pool.rs#L1318-L1339)) and measured at index commit via `discovery_to_searchable_seconds`. When `entries` saturates at `max_pending = 200,000`, `evict_one()` ([pool.rs](../../crates/sources/src/pool.rs#L2485-L2507)) evicts from the front of `self.admitted` (oldest waiting keys), while `drain_admission()` also pops from the front of `Admission::queues[Background]` (oldest surviving keys). At `CR-0`’s harvest rate (`178,908/h ≈ 49.7/s`), a saturated `200,000`-entry FIFO `LookupQueued` buffer has steady-state wait residency `W ≈ 200,000 / 49.7 ≈ 4,024 s (~67 minutes)`:
   - Every surviving background key is already **~67 min old** before lookup starts, automatically expiring 100% of `HINT_TTL = 60 s` responder hints (`CR-1a-H`) **and** violating `CR-SPEC`’s `p95 discovery-to-searchable <= 10 min (600 s)` release gate ([CR-SPEC](../decisions/2026-11-02-CR-SPEC.md#L58-L60)) by more than 6×.
   - Bounding `LookupQueued` residency well below `600 s` (and below `60 s` for hinted work) requires either a bounded-age admission/demotion lane (`fresh-first` / LIFO within a freshness cap, expiring stale tails out of `LookupQueued` rather than serving 67-minute-old keys first) or sizing `LookupQueued` residency to the lookup completion rate.
3. **Opportunity C — Eliminate the 1-second tick start latency on admitted lookups ([actor.rs](../../crates/dht/src/node/actor.rs#L1600-L1612), [maintain](../../crates/dht/src/node/actor.rs#L2297-L2302)).** `admit_request` pushes accepted requests onto `get_peers_queue`, which is only drained inside `maintain()` on the **1 s** `cfg.tick`. While `active_get_peers < MAX_GET_PEERS (32)`, each admitted lookup sits idle for up to 1.0 s (mean ~0.5 s, or ~9–13% of a 3.84–5.5 s lookup budget) while already holding a `PeerPermit`. Starting `start_peer_request` immediately on admission (deliberately deferred from `CR-ADM` to avoid confounding `CR-AB-ADM`, per [CR-ADM](../decisions/2026-10-30-CR-ADM.md#L46)) reclaims ~0.5 s of idle permit occupancy per lookup with zero extra packets.
4. **Opportunity D — Streaming lookup (`CR-1a-S`) permit retention ([CR-1a-S-2](../decisions/2026-10-31-CR-1a-S-2.md#L26-L28)).** Under `dht.streaming_peers`, the DHT `Lookup` continues until all `K = 8` closest nodes respond (or `LOOKUP_DEADLINE = 25 s` / `MAX_PEER_QUERIES = 64`), and the 32-slot `PeerPermit` only releases early if the metadata fetch completes and verifies before the lookup finishes. When fetch attempts fail or stall on the first batch, the actor lookup slot remains pinned until terminal completion.
5. **Opportunity E — Retain proven BEP 51 responders in `sampler.rs` and preserve throttle order ([sampler.rs](../../crates/dht/src/node/sampler.rs#L178-L193), [actor.rs](../../crates/dht/src/node/actor.rs#L2440-L2442)).** Lodestar's production `Sampler::prune` removes expired entries completely from `states` and `expiry` rather than re-offering proven productive BEP 51 nodes back into `frontier`, while `sample_tick` pushes `Sent::Throttled` candidates to the back of a `20,000`-entry `frontier`. Tracking a 1-bit `productive` marker in `State::Cooling` to re-queue expired productive nodes (inside the existing `CR-0d` restart proof) and preserving front priority on rate-limit throttles (`push_front`) delivers productive-node retention without an external SQLite scheduler.

## The missing lookup-capacity calculation

For work that requires a DHT lookup, an approximate saturated steady-state bound is:

`new searchable/min ≤ 60 × active logical lookup slots × new searchable yield per admitted lookup / mean occupied lookup seconds`.

The current actor allows **32 logical peer requests**; its deadline is 25 seconds. The pool's 256 logical slots and 400 metadata sockets do not override that actor limit. Mean occupancy includes terminal failures and cancellations, not just successful lookups. Direct announced-peer work can bypass this stage, so measure it separately. [Actor limits](../../crates/dht/src/node/actor.rs), [request capacity](../../crates/dht/src/node/mod.rs)

| Illustrative mean occupancy | Illustrative new searchable yield per admitted lookup | Lookup-stage capacity at 32 continuously occupied slots |
|---|---|---|
| 25 s | 20% | 15.4/min |
| 8 s | 20% | 48/min |
| 5 s | 30% | 115.2/min |

These are scenarios, not predictions. At 20% yield, 100/min requires mean occupied time at most **3.84 seconds**, or more lookup capacity / work bypassing lookups. Even perfect yield cannot reach 100/min if all 32 slots remain occupied for 25 seconds. Conversely, a 25-second deadline does not mean every request lasts that long. Measure the mean and tail before deciding to raise the cap.

This makes the strategy concrete: increase *useful lookup completions and their conversion*, alongside the socket-occupancy calculation in the original survey. Do not multiply isolated percentage gains; the stages share bottlenecks and may benefit the same hashes.

## What the proposed scheduler can and cannot contribute

Separating the safety ledger, ready candidates and productive-node retention is sensible. Preserving cooldowns while dropping low-value scheduling work can sustain discovery after the current ledger fills. However, the current sampler already uses an indexed `BTreeSet` with one expiry entry per restriction; a heap or timing wheel is not automatically an algorithmic improvement. The proposal adds SQLite writes and potential heap-compaction pauses, so benchmark its admission latency and memory/disk use against the existing implementation. [Current sampler](../../crates/dht/src/node/sampler.rs)

Under the simplified assumption that every new endpoint occupies a record for exactly six hours, 200,000 records sustain 9.26 new endpoints/s. The proposal's 25/s sample cap would need about **540,000 live restrictions**, plus queued/in-flight state, hot retention and headroom. Four million is a capacity choice, not a demonstrated requirement. Increasing the table twentyfold does not imply twentyfold sampling: 25/9.26 is only about **2.7 times** the old simplified steady admission bound, and even that does not predict metadata yield. Fleet scaling can lengthen retention; retained hot nodes, failed cleanup and database/WAL growth need separate limits.

Productive-node preference should decay after failures and account for duplicates and downstream conversion. Historical novelty can keep unreachable nodes “hot”; concentrating on familiar productive nodes can reduce discovery diversity. Retain exploration capacity and exact live restrictions independently. The scheduler's default 25/s and per-IP buckets also require explicit composition with all other DHT traffic and existing fleet guards; they are not a replacement for the aggregate limiter.

The [ten reproduced scheduler counterexamples](dht-survey-evidence/verification.md) in `review_regressions` (`0/2`) and `followup_review` (`0/8`) are integration blockers, including permanent ledger wedging once `max_cooldown_entries` fills with productive endpoints (`reclaim_expired_locked` ignores `hot_heap`), stale hot re-queuing on failed `ExplicitUnsupported` completion, six-hour RAM poisoning on failed WAL reservations, 128-op SQLite batch rollback contamination, unbounded multi-restart drift via repeated `<= 600 s` clock skews, and AS112/AMT IPv4 bogon acceptance. Fixing them establishes correctness, not a speedup. Prefer improving admission, bounded queue residency, and productive-node re-queuing in the existing pipeline (`pool.rs`, `sampler.rs`) before a wholesale scheduler replacement.

## Experiments that can justify implementation choices

Every live run on the experiment host is governed by frozen [CR-SPEC](../decisions/2026-11-02-CR-SPEC.md), which supersedes ad-hoc variance thresholds:

1. **Use CR-SPEC mechanics and baselines.** Pin binary/image digest and source SHA; use a fresh data directory per block (`dht.safe_restart=true` with host-mounted `LODESTAR_DHT_WITNESS_DIR`), `60 min` warmup/wash-out after `T_open`, `6 h` measured per A/B segment (`24 h` for comparator / `CR-COMB`), carry-in cohort bound subtraction (`discovery_to_searchable_seconds`), and paired **ABBA + BAAB** blocks (~12 h phase offset) analyzed via OLS on `ln(net window mean)` against the frozen **+5%** practical effect / equivalence margin (`Rule 6.3`). Primary numerator: `searchable_new_total{origin="network"}` alongside `metadata_new_verified_total`, per-transport/family fetch conversion, lookup occupancy, hint expiry/guard skips, sampler-full time, RSS, and WAL growth.
2. **Execute the queued single-switch A/B order (`Rule 6.1`).** Run **CR-AB-ADM** (`dht.coordinated_admission`), then **CR-AB-4** (`dht.utp`, plus `dht.route_backoff` only if baseline `fetch_no_route_total{family="ipv6"} > 0`), each alone with every other switch off, to establish Checkpoint 1 ([build plan](../build-plan.md#L75-L78)). Do **not** skip single-switch isolation or collapse unrelated switches into an unattributed live run.
3. **Screen code-fix interactions in `CR-SIM` before live factorial testing.** Before running `CR-AB-1*` or `CR-COMB`, screen (a) the fixed `CR-1a-H` hint guard (`State::Skipped` excluded by `Lookup::slot_filter`, avoiding both `l.on_failure` and `is_done()` blocking), (b) bounded-residency fresh/hinted admission vs FIFO backlog (`CR-ADM × CR-1a-H` and `p95 <= 600 s`), (c) immediate admission start without waiting for the 1 s `maintain()` tick (`CR-1c`), (d) standalone/combined streaming (`CR-1a-S`), and (e) `Sampler` productive-node re-queuing on cooldown expiry (`sampler.rs`) under `CR-SIM`.
4. **Relieve the next Checkpoint 1 limiter.** If cooldown capacity saturates after `CR-AB-ADM` / `CR-AB-4`, expand safe retention incrementally; if lookup slots remain saturated or `dht_timeouts_total` (`38.2%` of CR-0 outbound DHT queries) dominates occupancy, promote the seven routing-table and lookup-execution candidates in the [additional methods note](2026-11-16-dht-additional-methods.md) (especially per-lookup `/24`/`/64` shortlist hardening, two-stage decoupled `short_timeout`, `NICE` 3-minute quarantine + paced probing, and multi-bit/`virtual_ids` prefix splitting alongside bucket-walk `closest`). Never reset cooldown protection to equalize an arm or run independent same-egress workers that bypass shared restrictions.

Pursue the conversion strategy, beginning with the strongest admission evidence, while treating the replacement sampler and the 100/min target as hypotheses to test.
