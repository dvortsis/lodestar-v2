# M8 hardening to 1.0: the sliced plan (E-M8)

Planning slice P-m8, 2026-11-06, for the build runner. It turns build-plan P7 ("M8 hardening → 1.0") into `M8-*` build slices, a release cut (`R-v1-cut`) and `G-v1-*` gates. Docs only: nothing here writes code, and nothing edits `runner/slices.yaml` or `runner/dashboard.yaml` (§4.1 holds the entries ready to paste, §4.5 the dashboard proposal).

**Authority:** `docs/owner-decisions.md` §1.4, §1.6, §1.8, §2.14, §2.18, §2.19, §2.20, §2.22, §2.24–§2.26, §2.35, §2.36; architecture §3, §10.1, §10.17, §17, §18.9, §19.8, §20.8; build-plan §0.4, §0.6 and P7. Where they're silent the plan says so (**silent**) and puts the question in §5. It decides nothing that belongs to the owner.

## 1. Fixed constraints
- **1.0 ships when every §17 gate is green** (build-plan P7). This plan adds no product feature. Anything a gate finds is fixed in its own slice (§4.4), never inside a gate slice.
- **The budgets are the owner's** (owner §1.6; architecture §3, §10.1). §2.26 lets the runner decide performance and UX changes to owner-set numbers; this plan still sends any miss to the owner with what drives it, as the conservative choice (RQ7). No threshold here loosens one, and G-v1-10m names every one (§4.3).
- **Politeness and network guardrails are never relaxed to pass a gate** (build-plan §0.6).
- **The 50M numbers are the owner's to approve** (owner §2.25, `ext:owner-50m-approval`). `G-import-50M` already exists; this plan only depends on it.
- **The repo is public** (owner-decisions §3). A real torrent name, an owner hash or an unfixed vulnerability's detail is never committed (§5 OQ2, OQ6).
- **Model policy** (CLAUDE.md): Opus for parsers, untrusted input, on-disk formats, concurrency, security and search; Sonnet for CI workflows, docs and scaffolding that follows a pattern, except security-sensitive CI. Every review is Opus.
- **No migration.** No slice here changes `crates/store/src/schema.rs`.
- **Nothing starts before the v0.5.1 soak verdict** (r5; baseline ends 2026-11-06T13:12Z). Every slice with no other unmet dep carries `ext:v051-soak-verdict`, so the dashboard doesn't show it as ready. Slots: at most 4 from 2026-11-06T00:00Z, shared with every other track.

### 4.3 What each slice must do (spec and gates)
- **M8-REL-1:** `--dir` already reads a `corpus.txt`/`judgments.txt`/`baseline.txt` folder, so this adds only judgments keyed by info hash over an existing store and index (`--data-dir`, read-only, refused while a server holds the writer). `--held-out` prints NDCG@10, MRR, recall@50 and the query count, never a name, hash or per-query line, and writes no file into the repo. - **M8-REL-2:** ≈ 300 torrents and ≈ 150 queries with real names from sources whose licence allows redistribution (Internet Archive public-domain items, openly licensed datasets, Linux and BSD images, Creative Commons media), in the same hard-case families as the synthetic set. The risk with a self-hosted runner on this **public, user-owned** repo:
  - any workflow that names the runner's label can run on it. There are no runner groups on a user-owned repo, so "used only by `bench-10m.yml`" is a property of that file, not something GitHub enforces;
  - **same-repo branches run `pull_request` and `push` workflows without approval**, so any branch pushed by anyone with write access (every session) can target the label; fork pull requests need approval only under the "require approval for all outside collaborators" setting;
  - **`workflow_dispatch` runs the workflow file from the chosen ref**, so an in-file ref check can be edited out on that ref;
  - **the trade-off:** the 10M numbers stop gating pull requests. The 200k gates stay in `ci-ok`, and a 10M regression is caught up to a week later by the weekly run.

  *Mitigations:*
  - (a) an isolated machine (not the soak PC, not the experiment host during a run, separated from the owner's LAN, holding no credentials), registered as an **ephemeral** runner, so a hostile job finds nothing to steal and leaves nothing behind;
  - (b) a ruleset on `release/*` limiting who can create and push those branches;
  - (c) M8-PERF-3's `runner-guard` check, which fails any other workflow naming the label. It detects misuse after the fact, because a pushed branch runs at the same time as the check;
  - (d) the fork-PR approval setting above;
  - (e) CODEOWNERS on `.github/workflows` with required code-owner review. It would make every workflow change wait for the owner, which slows the runner's merges.

  *Recommendation:* (a) + (b) + (c) + (d), not (e). Alternative: a paid GitHub larger runner, which avoids the risk entirely but may need an organisation plan. Gates M8-PERF-3 and G-v1-10m.
- **OQ2. Relevance on real data.** The synthetic set invents every name on purpose. *Recommendation:* (a) commit a second set with real names from openly licensed sources only (M8-REL-2), gated in CI; (b) run a held-out set on the import host against the 10M pilot data, judged there, and commit only its aggregate scores. Never commit names or hashes from the owner's corpus. Gates M8-REL-2 and the held-out half of G-v1-relevance.
