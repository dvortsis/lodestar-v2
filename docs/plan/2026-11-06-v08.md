# v0.8: the sliced plan (E-v08)

Planning slice P-v08, 2026-11-06, for the build runner. It turns build-plan P6 into slices for `runner/slices.yaml`, the way `docs/plan/2026-11-01-v06-sources.md` and `docs/plan/2026-11-04-v06-rulepacks.md` did for P4. P6 has two items:
- **[M]** placement of singleton, account and overlay plugins on workers, and companions on workers;
- **[S]** Nostr NIP-35 and Lemmy plugin glue, where the parsers are Opus work.

There's no Anna's Archive or LibGen importer (owner §2.38). Docs only.

**Authority:** `docs/owner-decisions.md` §1.9.7, §2.16–§2.19, §2.26, §2.28, §2.38; architecture §18.1, §18.2 (rows 21 and 22), §18.4, §18.5, §18.7, §18.9, §18.10, §19 (above all §19.2, §19.5, §19.6, §19.8), §20.1 and §20.9; build-plan §0.2 (Tracks W and K) and P6. Where they're silent the plan says so (marked **silent**) and puts the question in §6. It decides nothing that belongs to the owner.

**Sibling plans.** P-v06-workers (`docs/plan/2026-11-06-v06-workers.md`) and P-v06-companions (`docs/plan/2026-11-06-v06-companions.md`) are being written at the same time. Neither had landed on `main` when this plan was written (2026-11-06T00:00Z). §3 states each assumption this plan makes about them and the interface points it depends on, so the runner can reconcile them. Paths marked *provisional* in §5 follow those assumptions and may move. P-v07 (`slice/P-v07`, not merged) is read only for its ids and its rule on JSON parsers.

## 1. Fixed constraints
- **Every source is off by default and metadata only.** Child-safety filtering runs on every source before storage and can't be disabled; private results stay local; no profiles of people (owner §1.9.7; §18.1, §18.7, §20.1).
- **The coordinator's commit is authoritative** (§19.4). Whatever a worker finds goes through the coordinator's blocklist check and filter-before-storage, exactly as a local plugin's finds do. A worker's own check is only a pre-check.
- **Politeness caps are global** (§19.1, §19.5). More workers never multiply a source's request rate. Per-host caps reach workers as token leases in heartbeats.
- **Account and private sources default to the coordinator** (§19.5). They run on a worker only where you allowed it, with credentials sealed per worker. `private_source` items never go into public peer finding, on any machine (§18.7).
- **Restricted and Overlay consent applies per worker** (§19.5), because each machine has its own IP and legal exposure. Weakening consent needs the admin password every time (SRC-4, §18.7).
- **Overlay plugins only land on workers that have their companion** (§19.5, §19.8).
- **Least data on workers** (§19.6): a worker gets only the have-filter, its assignments, sealed credentials for assigned plugins and leases. It can't query the database, search or UI.
- **Terms and robots:** a plugin ships only if its recorded check finds automated access allowed; a grey case goes to the owner (owner §2.28, sources plan Q2).
- **JSON is read with the shared bounded reader** `crates/sources-feeds/src/json.rs`, never `serde_json`, so caps hold while reading (ENR-2a's rule, also P-v07's).
- **New dependencies need the brief's explicit approval** (standards §2), pinned exactly.
- **Slots:** four from 2026-11-06T00:00Z (owner §2.41's cut). Building waits for the v0.5.1 soak verdict (`ext:v051-soak-verdict`; r5's baseline ends 2026-11-06T13:12Z). Higher rungs of the build-plan §0.2 ladder go first. The waves in §7 are upper bounds.

## 4. Store impact: none (no migration)
- **Placement pins and allowances** (PL-3, PL-4): one `settings` row per plugin, `cluster.placement:<plugin-id>`, a small versioned encoding (Auto or pinned worker ids; allowed worker ids for Account/private sources). **An unreadable row fails closed:** pins read as Auto, allowances as none, so an account plugin falls back to the coordinator.
- **Per-worker consent** (PL-5): `settings` rows `source.consent@<worker-id>:<plugin-id>` holding the same `Ack` encoding as the `sources` table's consent (class, text version, address list; no time, no author, Q14). Revoking a worker or purging its data deletes them. Unreadable: no consent.
- **Nostr and Lemmy cursors** (NOS-3, LEM-1): `source_state` (V14). Their finds go to `unverified_items` and `torrent_claims` like every other source's; purge, the snapshot purge (§2.21) and `secure_delete` (§2.17) already cover them.
- **Credentials on workers** are never written to the worker's disk (Q-r6).
- **Search `SCHEMA_VERSION`:** no new field.

**New dependencies, approved per slice in its brief** (standards §2):
- **NOS-1:** `k256` with only its `schnorr` feature, pure Rust (Q-r2). The brief checks which `sha2` it pulls: the tree pins `sha2 =0.11.0`, and a second `sha2` version is acceptable only if no `k256` release uses 0.11.
- **NOS-2:** no new crate. `tokio-tungstenite =0.30.0` (`handshake` feature, as `crates/cluster` uses it with `client_async_with_config` over its own TLS stream) and `tokio-rustls =0.26.6` are already in the lockfile; `crates/sources` gains them. Server certificates are checked with the same verifier the plugin HTTP client uses (`rustls-platform-verifier`, in the lockfile).
- **No GraphQL, Nostr or ActivityPub client crate.** No `serde_json`.

**Owner questions that gate no slice (Q-o2):** the slices build the narrower option, so any other answer only adds a later slice.

### 5.3 What each slice must do (spec and gates)
- **PL-0** (§19.2). In one `PROTOCOL_MINOR` bump: a `Plugin` assignment entry (plugin id, config, config revision, units for `sharded(unit)`, the **assignment epoch**, credentials only for an allowed worker); `Finds` W→C (≤ 512 `Found` items per batch, claims in the store's claim encoding, the epoch, and the plugin's state writes in the same batch so a cursor never moves past finds that weren't delivered); token-lease fields in `Heartbeat`/`HeartbeatAck`; companion health in heartbeat stats. Every limit checked by `validate` on both transports, as today. Property tests: round-trip, every limit refused, a minor-version peer without the new messages handled cleanly.
- **PL-1** (§19.4, §19.5). The worker builds a `SourceCtx` for each assigned plugin: the emitter sends `Finds`; state is the coordinator's (an assignment carries a snapshot; writes ride in `Finds`); HTTP goes through the worker's own `EgressFactory`, so its egress and kill-switch are the worker's. Unassign, drain and revoke stop the plugin within `STOP_WITHIN`. The coordinator ingests `Finds` through the same path as a local plugin's emits: blocklist, filter-before-storage, `private_source`, `always_adult`, the unverified tier. **Finds from a stale epoch are dropped and counted.** Tests: a plugin on a worker yields the same stored rows as on the coordinator; a blocklisted fixture from a worker is dropped before storage; a stale-epoch batch changes nothing.
- **PL-2** (§19.5). The coordinator holds each host's bucket (from `Caps.per_host` and the poll gate) and leases tokens to the instances that need them in heartbeats; the worker's `Client` spends only leased tokens, and **sends nothing without one**. **A lease's TTL is at most one heartbeat timeout**, so a worker cut off from the coordinator stops sending before a replacement starts (PL-3). The coordinator's own plugins draw from the same buckets. Property test over random fleets, partitions and failovers: requests per host in any window ≤ `burst + t / interval`.
- **PL-3** (§19.5, §19.8). A pure engine plus the coordinator's assigner. **Eligibility** per worker: the plugin's `distribution`; consent for its class on that worker (PL-5's records through a trait PL-3 defines, so PL-3 doesn't wait for PL-5); for Account/`finds_private` plugins, the allowance (default: coordinator only); for a plugin that needs a companion, the companion bit (I7); the kill-switch state. **Singleton:** the healthiest eligible worker (the coordinator's built-in local worker is always eligible when the plugin's conditions hold there); on a missed heartbeat timeout the next is chosen with **epoch + 1**, so failover completes within one timeout and the old instance's finds are fenced. **`sharded(unit)`:** units spread by capacity, re-spread on join and loss. **Pins** win over Auto but never over eligibility. **Hysteresis:** a healthy instance isn't moved just because a slightly healthier worker appears (no oscillation under steady load, §18.9). **Remote placement is off by default** (`cluster.remote_sources`), so every source stays on the coordinator until G-v08 passes (Q-r8). Property tests: exactly one active singleton instance per epoch; overlay never on a worker without its companion; account plugins never on a worker without an allowance; units covered exactly once.
- **PL-4** (§19.5, §19.6, §18.7). Allowances per plugin in the `cluster.placement:` row. **Credentials** go only in the `Assign` to an allowed worker, over its mTLS session, **held in memory only** on the worker (never in its spool or on disk), and dropped on unassign, drain, revoke and allowance removal (Q-r6). **Private isolation on workers:** a worker never sends a `private_source` key into DHT `get_peers`, public trackers or PEX, whatever its other assignments; its finds go straight into `Finds`. Tests: credentials never reach a worker without an allowance, not even in a rejected `Assign`; revoke drops them within one heartbeat; a private find on a worker never appears in that worker's DHT lookups.
- **PL-5** (§19.5, §18.7). Consent records keyed by worker as well as source (§4). Restricted and Overlay need the consent screen and the admin password **per worker**; External's endpoint acknowledgement also counts per worker, since the requests leave from that machine's IP (Q-r10). A changed text or address list asks again, as SRC-4 does today. Revoking a worker and "Purge data from this worker" drop its records. Unreadable records read as no consent. Tests: no path through the API or the assigner runs a Restricted or Overlay plugin on a worker without that worker's consent.
- **PL-6** (§19.5, §19.7). `GET/PUT /sources/{id}/placement` (Auto or pins, allowances), `POST /sources/{id}/workers/{worker}/consent` (password-gated for Restricted and Overlay, same weakening rules as SRC-4), "running on" per plugin, and per-worker companion state. Every write re-checks eligibility on the server. Tests: consent bypass through every route; an allowance for a revoked worker refused.
- **PL-7a / PL-7b** (§19.7, §18.8, §10.14). Placement shown and edited as §19.7 says; per-worker consent uses the same consent dialogs as SRC-15b, with the per-worker text the owner approves (Q-o3). Companions per worker show "Needs setup" with the CW-2 command to copy.
- **CW-0** (§18.10). The worker runs detection (known ports, container names, configured URL) and, natively, supervision of its own companions, through the companion manager's library (I8). It reports the bitset in `Hello` and health in heartbeats; a change re-runs placement. Companions on a worker bind to its localhost or internal network only, and their traffic follows that worker's egress.
- **CW-1** (§18.10, §19.5). A plugin that needs a companion (Prowlarr today) is placed only where the companion is, and talks to it on that machine. **The companion's credentials are generated and sealed on that worker and never sent to the coordinator** (Q-r6); the coordinator sees "configured" or "Needs setup". The plugin is still Account class: its allowance and consent rules hold.
- **CW-2** (§18.10). `lodestar worker companion install <id>` on native workers verifies the catalogue entry, checksum and signature from the worker's own binary and asks for confirmation; on containers it prints the compose service or opens the Unraid template text. Nothing on the coordinator can start an install (Q-o2).
- **NOS-0** (NIP-01, NIP-35). Relay messages `EVENT`, `EOSE`, `CLOSED`, `NOTICE`, `OK`; `AUTH` is recognised and refused (no NIP-42). Events: `id`, `pubkey`, `created_at`, `kind`, `tags`, `content`, `sig`, each checked for shape (64- and 128-hex lowercase). The **event id is recomputed** as SHA-256 of NIP-01's canonical serialisation `[0,pubkey,created_at,kind,tags,content]` with NIP-01's exact escaping, and a mismatch is dropped. **NIP-35 kind 2003** maps to claims: `title` → name; `x` → the v1 info hash (the only source of the key); `file` → files with sizes; `tracker` → trackers; `i` → ids (`imdb:`, `tmdb:`, `tvdb:`, `mal:`, `anilist:` and other prefixes kept as their own scheme); `t` → tags; `content` → description; `pubkey` (as `npub`) → publisher. NIP-36 `content-warning` and adult `t` tags (`nsfw`, `porn`, `xxx`, `adult`) → a `content-type:adult` claim (ADH-0). Caps: message ≤ 128 KB, tags ≤ 512, tag values within claims limits. The slice re-reads NIP-01 and NIP-35 and records the revision it follows in its decisions file. Fuzz target and golden fixtures (canonical-serialisation vectors).
- **NOS-1.** Verifies BIP-340 signatures over the event id; an invalid signature drops the event. Test vectors from BIP-340, plus real events. Verification cost measured: a relay flood is bounded by NOS-2's message caps and NOS-3's rate caps, so it can't take more than the plugin's CPU share (§18.4).
- **NOS-2** (§18.1, §18.6, §12). A client WebSocket over a TCP stream that the plugin egress opens (interface binding or SOCKS5, the kill-switch, the SSRF guard for user-entered addresses: `wss://` only, no LAN addresses unless the user's policy allows, as for HTTP). Caps: frame ≤ 128 KB, no permessage-deflate, ping every 60 s, idle timeout, exponential back-off with the manifest's floors, connect timeout. A WebSocket transcript replayer in `testing.rs` beside the HTTP one, so plugin tests run on recorded fixtures with no network.
- **NOS-3.** External consent; the relay list is the user's (Q-o1), shown before enabling as SRC-13c does for torrent caches. One `REQ` per relay, `{"kinds":[2003],"since":<cursor>,"limit":500}`, cursor per relay in `source_state`, one agent per relay connection (§18.4). Caps (Q-r11): ≤ 8 relays, reconnect back-off from 30 s up to 1 h, at most 1 new connection per relay per 30 s, events per relay per minute capped (excess dropped and counted). `Distribution::Singleton` (§19.5). Every event becomes an unverified item with claims, never a stored torrent until metadata is fetched.
- **LEM-0.** `GetPostsResponse` from `GET /api/v3/post/list`: `post` (`id`, `name`, `url`, `body`, `nsfw`, `removed`, `deleted`, `published`, `ap_id`), `community` (`name`, `nsfw`, `actor_id`), `creator` (`name`, `actor_id`), `next_page`. Keys come only from magnet URIs, in `url` or in `body`, parsed by the existing magnet parser in `common.rs`; an `http(s)` `.torrent` link gives no key in v0.8 (Q-r12). Removed and deleted posts are skipped. `post.nsfw` or `community.nsfw` → a `content-type:adult` claim. Body ≤ 64 KB, posts per page ≤ 50. Lemmy's API version is read from `GET /api/v3/site` and an unknown major is refused, so Lemmy 1.0's `/api/v4` is a later slice. Fuzz target.
- **LEM-1.** External consent (stricter than §18.7's None, because we poll a third party; Q-r1). One user-entered instance URL through the SSRF guard and a list of communities. Caps (Q-r11): one request per second per host, each community polled no more than every 10 minutes, ≤ 20 communities, newest first with a cursor of the newest post id seen, back-off on errors and a visible "blocked by source" state. `Distribution::Singleton`. The instance's own terms are the user's to accept (Q-o1).
- **ADH-0** (§20.9, X-source-adult). A `content-type:adult` claim from **any** source makes the item Adult in every place X-source-adult listed (prepare, commit re-judge, promotion, claims and the refile sweep, the background enrichment), **stricter only**: no claim can make an item non-adult, and your own Not adult correction still wins. Filtering judges both readings and the stricter verdict stands. Tests as in `crates/pipeline/tests/source_adult.rs`, per path, plus "an item without the claim is unchanged".
- **G-v08** (§19.8, §18.9). On the in-process multi-worker network: singleton failover within one heartbeat timeout, with no doubled finds; overlay (test plugin) never on a worker without its companion; fleet-wide request rate per host under each cap through failovers and partitions; credentials never on a worker without an allowance and gone after revoke; `private_source` keys never in a worker's public lookups; per-worker consent can't be bypassed through the API; a blocklisted fixture hash through Nostr and Lemmy is dropped before storage; a forged Nostr id or signature is dropped; Lemmy and Nostr adult claims hide items while Show adult content is off (e2e). If it passes, the gate's PR turns `cluster.remote_sources` on by default.
