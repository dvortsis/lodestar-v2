## 1. Fixed constraints
- **Every source is off by default and metadata only.** Child-safety filtering runs on every source before storage and can't be disabled. Private results stay local, and there are no profiles of people (owner §1.9.7; §18.1, §18.7, §20.1).
- **The coordinator's commit is authoritative** (§19.4). Whatever a worker finds goes through the coordinator's blocklist check and filter-before-storage, exactly as a local plugin's finds do. A worker's own judgement (WK-8's filter snapshot) is only a pre-check.
- **Politeness caps are global** (§19.1, §19.5). More workers never multiply a source's request rate. Per-host caps reach workers as token leases in heartbeats (deferred to v0.8 by the workers plan's Q9).
- **Account and private sources default to the coordinator** (§19.5). They run on a worker only where you allowed it, with credentials sealed per worker. `private_source` items never go into public peer finding, on any machine (§18.7).
- **Restricted and Overlay consent applies per worker** (§19.5), because each machine has its own IP and legal exposure. Weakening consent needs the admin password every time (SRC-4, §18.7).
- **Overlay plugins only land on workers that have their companion** (§19.5, §19.8).
- **Least data on workers** (§19.6, as the workers plan's Q1 widens it). A worker gets:
  - the have-filter;
  - WK-8's filter and dictionary snapshot;
  - its assignments;
  - sealed credentials for assigned plugins;
  - leases.

  It can't query the database, search or UI. v0.8 adds the plugin assignments and their state snapshot (PL-0), and nothing else.
- **Worker RSS ≤ 256 MB at defaults** (owner §1.6.5), under the workers plan's Q6 rule. Plugins and companions on a worker fit inside it (§5.5).
- **Terms and robots:** a plugin ships only if its recorded check finds automated access allowed. A grey case goes to the owner (owner §2.28, sources plan Q2).
- **JSON is read with the shared bounded reader** `crates/sources-feeds/src/json.rs`, never `serde_json`, so caps hold while reading (ENR-2a's rule, also P-v07's).
- **New dependencies need the brief's explicit approval** (standards §2), pinned exactly.
- **Slots and start:** four slots from 2026-11-06T00:00Z (owner §2.41's cut). Building waits for the v0.5.1 soak verdict (`ext:v051-soak-verdict`; r5's baseline ends 2026-11-06T13:12Z). Higher rungs of the build-plan §0.2 ladder go first (Q-r5). The waves in §7 are upper bounds.

## 4. Store impact: one migration (PL-8)
- **PL-8, the only migration.** It's needed because purge-by-worker must cover a plugin's finds (§19.4), and claims and unverified items don't record which worker found them (Q-r14).
  - **The table:** `find_worker (source_id INTEGER NOT NULL REFERENCES sources (id), network INTEGER NOT NULL, key BLOB NOT NULL, worker INTEGER NOT NULL, PRIMARY KEY (source_id, network, key)) STRICT`, with an index on `worker`.
  - **Its rows:** written only for finds from a **remote** worker, so a single-machine install writes nothing. A later find of the same key by the same source overwrites the row, just as it overwrites the claim. So the row always names whoever wrote the current claim.
  - **Names:** it holds none. `snapshots.rs` `Plan::KNOWN_THROUGH` moves to the new version, and the snapshot purge (§2.21) follows `unverified_items`.
  - **Number:** the next free one when it reaches `ext:migration-slot`. That's after WK-12 and CR-3 (V15) in the §0.7 queue; the runner records it in `migration_order`.
- **Plugin placement** (PL-3, PL-4): one `settings` row per plugin, `cluster.plugin.placement:<plugin-id>`. It's a small versioned encoding: Auto or pinned worker ids, plus the allowed worker ids for Account/private sources. **An unreadable row fails closed:** pins read as Auto and allowances as none, so an account plugin falls back to the coordinator.
- **Per-worker consent** (PL-5): `cluster.consent.<worker-id>:<plugin-id>`, holding the same `Ack` encoding as the `sources` table's consent (class, text version, address list; no time and no author, Q14). Revoking a worker or purging its data deletes the row. An unreadable row means no consent.
- **Nostr and Lemmy cursors** (NOS-3, LEM-1) live in `source_state` (V14). Their finds go to `unverified_items` and `torrent_claims`. Purge, the snapshot purge (§2.21) and `secure_delete` (§2.17) already cover those.
- **On a worker:**
  - account credentials from the coordinator are never written to disk (Q-r6);
  - companion credentials made on the worker sit in CW-3's sealed state file, an on-disk format.
- **Search `SCHEMA_VERSION`:** no new field.

**24 slices, about 16,900 lines; one migration (PL-8).** Every slice is under 1,500 lines; the largest is PL-1 (~1,100).
- **PL-0 is one minor bump.** It fixes every v0.8 wire shape and owns `server.rs`, so PL-1, PL-2, PL-3 and CW-0 can then run side by side.
- **NOS-2 is split in two.** The routed TCP connect (NOS-2a) needs a SOCKS5 client handshake, which is another untrusted-input parser, in `crates/integrations/src/net.rs` where the SSRF guard lives.
- **NOS-3 is Opus, not P6's [S].** Managing up to eight relay connections is concurrency-heavy. LEM-1 stays Sonnet glue.
- **CW-3 is its own slice.** It's an on-disk format.
- **G-v08 doesn't wait for DOC-v08.** The docs describe the result; they don't decide whether it's safe.

**ADH-0 builds only what the owner answers to Q-o4.** If the owner says no, it's dropped. NOS-3 and LEM-1 then emit the claim, and it stays unread, as Sukebei's is today.

**New dependencies, approved per slice in its brief** (standards §2):
- **NOS-0:** `sha2` added to `crates/sources-feeds`, for the event id. It's already in the tree (the lockfile has one version, 0.11.0); the brief pins `=0.11.0`.
- **NOS-1:** `k256` with only its `schnorr` feature, pure Rust (Q-r2). The brief checks which `sha2` it pulls in: a second `sha2` version is acceptable only if no `k256` release uses 0.11.
- **NOS-2a:** no new crate. The SOCKS5 client handshake is written in-house, bounded and fuzzed, like `net.rs`'s other guards.
- **NOS-2b:** no new crate. `tokio-tungstenite =0.30.0` (the `handshake` feature, used the way `crates/cluster` uses it: `client_async_with_config` over its own TLS stream) and `tokio-rustls =0.26.6` are already in the lockfile; `crates/sources` gains them. Server certificates are checked with the same verifier the plugin HTTP client uses (`rustls-platform-verifier`, in the lockfile).
- **Nothing else:** no GraphQL, Nostr or ActivityPub client crate, and no `serde_json`.

### 5.3 What each slice must do (spec and gates)
- **PL-0** (§19.2), in one **compatible minor bump** after WK-G's protocol 1.0:
  - **Assign payload v2:** v1's fields, plus a plugin list. Each entry carries the plugin id, config and config revision, the units for `sharded(unit)`, the **assignment epoch**, a state snapshot, and credentials only for an allowed worker. A worker that knows only v1 still gets v1 and runs no plugins.
  - **`Finds` (W→C):**
    - up to 512 `Found` items per batch;
    - claims in the store's claim encoding;
    - the epoch;
    - the plugin's state writes, in the same batch, so a cursor never moves past finds that weren't delivered.
  - **Heartbeats:** token-lease fields in `Heartbeat`/`HeartbeatAck`, and companion health in heartbeat stats.
  - **`server.rs`:** the `Finds` intake goes through WK-0's inbound sink, under its inbound queue caps, and the heartbeat-lease hook is added.
  - **Credentials** in an `Assign` use a redacting type that zeroizes on drop, as `SocksAuth` does. They never appear in `Debug`, errors or logs.
  - **Limits:** every limit is checked by `validate` on both transports, as today.
  - **Tests:**
    - a property test of v1 and v2 round-trips;
    - every limit refused;
    - a v1-only peer handled cleanly;
    - a fuzz target for `Finds`.
- **PL-1** (§19.4, §19.5, owner §1.6.5).
  - **The worker's plugin host** builds a `SourceCtx` for each assigned plugin:
    - the emitter sends `Finds`, after WK-8's snapshot has pre-judged them;
    - state belongs to the coordinator: the assignment carries a snapshot, and writes ride in `Finds`;
    - HTTP goes through the worker's own `EgressFactory`.
    - Unassign, drain and revoke stop the plugin within `STOP_WITHIN`.
  - **Memory reservation** (§5.5):
    - one shared response-body slot of **8 MiB** on a worker, a semaphore across plugins, so at most one body is in flight at a time;
    - a plugin whose policy needs bodies above 8 MiB is never placed on a worker (PL-3);
    - ≤ 1 MiB of state per plugin, and at most eight plugins per worker.
  - **The coordinator trusts nothing in a batch beyond what it can check** (§19.4 "trust but verify"):
    - each batch must match an active assignment of that plugin to that worker at that epoch, or it's dropped and counted;
    - a batch from a quarantined, purged or revoked worker is refused, like WK's late results (I7);
    - the source id comes from the assignment, never from the message;
    - a find from a `finds_private` or Account plugin is always stored `private_source`, whatever the batch says;
    - claims are decoded with the store's bounded decoder;
    - then the finds go the same way a local plugin's emits do: blocklist, filter-before-storage, `always_adult` and the unverified tier.
  - **Tests:**
    - a plugin on a worker yields the same stored rows as on the coordinator;
    - a blocklisted fixture from a worker is dropped before storage;
    - each of these changes nothing: a stale-epoch batch, a batch for a plugin the worker isn't assigned, a batch from a quarantined worker;
    - a private find with the flag cleared is stored private;
    - the body slot holds under concurrent plugins.
- **PL-2** (§19.5).
  - **Buckets:** the coordinator holds each host's bucket, from `Caps.per_host` and the poll gate, and leases tokens in heartbeats to the instances that need them. The coordinator's own plugins draw from the same buckets.
  - **The worker's `Client` spends only leased tokens**, and **sends nothing without one**.
  - **A lease's TTL is a relative duration on the worker's monotonic clock, counted from receipt** (worker clocks may be up to 60 s off, §19.3). It's strictly shorter than the heartbeat timeout minus one heartbeat. So a worker cut off from the coordinator stops sending before PL-3 notices it has gone and starts a replacement.
  - **What each mechanism guarantees:** the fleet cap holds anyway, because every token comes out of one bucket. The epoch fence (PL-3) is what stops doubled finds.
  - Workers sharing an external IP need nothing extra (I8).
  - **Test:** a property test over random fleets, partitions and failovers: requests per host in any window ≤ `burst + t / interval`.
- **PL-3** (§19.5, §19.8). It extends WK-5's planner (I5) and builds what WK Q9 deferred.
  - **Eligibility per worker:**
    - the plugin's `distribution`;
    - consent for its class on that worker, read through a trait PL-3 defines (PL-5 provides the records);
    - for Account and `finds_private` plugins, the allowance (default: coordinator only);
    - for a plugin that needs a companion (CMP-10's map), the companion bit (CW-0);
    - the kill-switch state;
    - the worker's **memory admission:** the plugin's reservation (§5.5) must fit the worker's reported headroom;
    - not quarantined.
  - **Singleton:**
    - the healthiest eligible worker. The coordinator's built-in local worker is always eligible when the plugin's conditions hold there.
    - When a heartbeat timeout is missed, the next worker is chosen with **epoch + 1**. So failover completes within one timeout, and the old instance's finds are fenced.
  - **`sharded(unit)`:**
    - units are spread by capacity and re-spread when a worker joins or leaves;
    - **for a plugin that needs a companion, units go only to workers that host it.** That's Prowlarr today, with its indexers as units (CW-1).
  - **Pins** win over Auto, but never over eligibility.
  - **Hysteresis:** a healthy instance isn't moved just because a slightly healthier worker appears (no oscillation under steady load, §18.9).
  - **Remote placement is off by default** (`cluster.remote_sources`). Every source stays on the coordinator until G-v08 passes (Q-r8).
  - **Property tests:**
    - exactly one active singleton instance per epoch;
    - overlay plugins never on a worker without their companion;
    - account plugins never on a worker without an allowance;
    - companion-backed units only on hosting workers;
    - units covered exactly once.
- **PL-4** (§19.5, §19.6, §18.7).
  - **Allowances** per plugin, in the `cluster.plugin.placement:` row.
  - **Credentials:**
    - they go only in the `Assign` to an allowed worker, over its mTLS session;
    - they're **held in memory only** on the worker, never in its spool or on disk;
    - they're dropped on unassign, drain, revoke, quarantine and allowance removal (Q-r6).
  - **Private isolation on workers:** a worker never sends a `private_source` key into DHT `get_peers`, public trackers or PEX, whatever its other assignments are. Its private finds go straight into `Finds`.
  - **Tests:**
    - credentials never reach a worker without an allowance, not even in a rejected `Assign`;
    - revoke drops them within one heartbeat;
    - no link error or log line contains them;
    - a private find on a worker never appears in that worker's DHT lookups.
- **PL-5** (§19.5, §18.7).
  - **Consent records** are keyed by worker as well as source (§4).
  - **Restricted and Overlay** need the consent screen and the admin password **per worker**.
  - **External's endpoint acknowledgement** also counts per worker, because the requests leave from that machine's IP (Q-r10).
  - **Changes:** a changed text or address list asks again, as SRC-4 does today. Revoking a worker, or "Purge data from this worker", drops its records. Unreadable records read as no consent.
  - **The Q-o3 wording** is drafted in the decisions file.
  - **Test:** no path through the API or the planner runs a Restricted or Overlay plugin on a worker without that worker's consent.

    - detection (known ports, container names, a configured URL);
    - supervision of its own companions, on native installs;
    - the bitset in `Hello`, using the companion bit mapping CW-0 defines (catalogue id → bit, compiled in and never renumbered);
    - health in heartbeats;
    - a change re-runs placement.
  - **Companions on a worker** bind to its localhost or internal network only, and their traffic follows that worker's egress.
  - **Memory line** (§5.5): log rings of 1 MiB per companion (CMP's redacted ring), and ≤ 1 MiB of health and detection state. The companion processes themselves sit outside the worker's RSS, under CMP-4b's limits.
- **CW-3** (§18.10, §12, §2.17).
  - **The file:** the worker's own sealed state, holding companion credentials (CMP-3's, generated on the worker) and per-companion settings. It's sealed with the worker's `SecretStore`.
  - **Format and writes:** a versioned header, records checksummed, written atomically.
  - **Fails closed:** an unreadable file means "Needs setup", and never a reused credential.
  - **Deletion:** removed with secure deletion when a companion is uninstalled or the worker is revoked.
  - **Fuzz target** for the decoder.
- **CW-1** (§18.10, §19.5).
  - **Placement:** a plugin that needs a companion (Prowlarr today) is placed only where the companion is, and its `sharded(unit)` units spread only over such workers (PL-3). It talks to the companion on that machine.
  - **The companion's credentials** stay in CW-3's file and are never sent to the coordinator (Q-r6). The coordinator sees only "configured" or "Needs setup".
  - **Rules:** the plugin is still Account class, so its allowance and consent rules hold.
- **CW-2** (§18.10).
  - **Native workers:** `lodestar worker companion install <id>` verifies the catalogue entry, checksum and signature through CMP-1 from the worker's own binary, and asks for confirmation.
  - **Containers:** it prints CMP-7's compose service or Unraid template.
  - **Nothing on the coordinator can start an install** (Q-r13).
- **NOS-0** (NIP-01, NIP-35).
  - **Relay messages:** `EVENT`, `EOSE`, `CLOSED`, `NOTICE`, `OK`. `AUTH` is recognised and refused (no NIP-42).
  - **Events:** `id`, `pubkey`, `created_at`, `kind`, `tags`, `content`, `sig`, each checked for shape (64- and 128-hex lowercase).
  - **The event id is recomputed** as the SHA-256 of NIP-01's canonical serialisation `[0,pubkey,created_at,kind,tags,content]`, with NIP-01's exact escaping. A mismatch is dropped.
  - **NIP-35 kind 2003** maps to claims:
    - `title` → name;
    - `x` → the v1 info hash, the only source of the key;
    - `file` → files with sizes;
    - `tracker` → trackers. These are untrusted URLs, so they pass `net::tracker::public_tracker_url` before any announce;
    - `i` → ids. NIP-35's typed prefixes (`imdb:`, `tmdb:movie:`, `ttvdb:`, `mal:anime:` and so on) each keep their own scheme. The category prefixes `tcat:` and `newznab:` aren't ids, so they go to tags;
    - `t` → tags;
    - `content` → description;
    - `pubkey` (as `npub`) → publisher.
  - **Adult claims:** adult `t` tags (`nsfw`, `porn`, `xxx`, `adult`), or a NIP-36 `content-warning` whose reason matches those terms, produce a `content-type:adult` claim. Other content warnings (spoilers, violence) don't.
  - **Caps:** message ≤ 128 KB, tags ≤ 512, and tag values within the claims limits.
  - The slice re-reads NIP-01 and NIP-35, and records the revision it follows in its decisions file.
  - **Tests:** a fuzz target, and golden canonical-serialisation vectors.
- **NOS-1.**
  - **The check:** verifies BIP-340 signatures over the event id; an invalid signature drops the event.
  - **Tests:** BIP-340's test vectors, plus real events.
  - **Cost:** verification cost is measured. A relay flood is bounded by NOS-2b's message caps and NOS-3's rate caps, so it can't take more than the plugin's CPU share (§18.4).
- **NOS-2a** (§12, §18.6). A raw TCP connect in `crates/integrations/src/net.rs`.
  - **Routes:** the same choices the HTTP client has: direct, interface or bind address, or SOCKS5. The SOCKS5 client handshake is written in-house, with every reply bounded, checked and fuzzed.
  - **The SSRF guard:** no LAN or private addresses unless the user's policy allows. It's checked after resolution, and again on the proxy's reported address.
  - **The kill-switch** covers it.
  - **Lands inactive:** existing callers keep the direct route, and `connect_tcp`'s behaviour doesn't change.
  - **Tests:** one per route, plus a refused LAN address and a malformed proxy reply.
- **NOS-2b** (§18.1, §18.6, §12).
  - **The client:** a WebSocket client (`wss://` only) over a stream from NOS-2a, opened through the plugin's egress (`egress.rs` gains the connector).
  - **Caps:** frame ≤ 128 KB, no permessage-deflate, ping every 60 s, an idle timeout, exponential back-off with the manifest's floors, and a connect timeout.
  - **A WebSocket transcript replayer** in `testing.rs`, beside the HTTP one.
- **NOS-3.**
  - **Consent:** External. The relay list is the user's (Q-o1), shown before enabling, as SRC-13c does for torrent caches.
  - **Subscription:**
    - one `REQ` per relay: `{"kinds":[2003],"since":<cursor>,"limit":500}`;
    - one cursor per relay, in `source_state`;
    - one agent per relay connection (§18.4).
  - **A publisher can't push the cursor forward.** `created_at` is the publisher's own claim. So:
    - events dated more than 10 minutes ahead are dropped and counted;
    - the cursor never moves past now minus that allowance;
    - each `REQ` overlaps the last by an hour;
    - events are deduplicated by id, bounded (64k ids) over the overlap window. That also covers the same event arriving from several relays.
  - **Caps** (Q-r11):
    - ≤ 8 relays;
    - reconnect back-off from 30 s up to 1 h;
    - at most one new connection per relay per 30 s;
    - events per relay per minute capped, with the excess dropped and counted.
  - **Distribution:** `Singleton`.
  - **Storage:** every event becomes an unverified item with claims.
  - **Memory line** (§5.5): 8 × (one 128 KB frame buffer, one 128 KB message buffer, TLS state) ≈ 3 MiB, plus the dedupe set ≈ 4 MiB.
- **LEM-0.**
  - **The response:** `GetPostsResponse` from `GET /api/v3/post/list`:
    - `post`: `id`, `name`, `url`, `body`, `nsfw`, `removed`, `deleted`, `published`, `ap_id`;
    - `community`: `name`, `nsfw`, `actor_id`;
    - `creator`: `name`, `actor_id`;
    - `next_page`.
  - **Keys:** only from magnet URIs, in `url` or `body`, read with the magnet parser in `common.rs`. An `http(s)` `.torrent` link gives no key (Q-r12).
  - **Skipped:** removed and deleted posts.
  - **Adult claims:** `post.nsfw` or `community.nsfw` produce a `content-type:adult` claim.
  - **Caps:** body ≤ 64 KB, posts per page ≤ 50.
  - **The API version:** the parser targets `/api/v3` by path and checks the response's shape. It ignores the software version that `GET /api/v3/site` reports (`0.19.x`), so a Lemmy 1.x that still serves v3 works.
  - **Tests:** a fuzz target.
- **LEM-1.**
  - **Consent:** External. That's stricter than §18.7's None, because we poll a third party (Q-r1).
  - **Settings:** one instance URL you enter, through the SSRF guard, and a list of communities.
  - **Caps** (Q-r11):
    - one request per second per host;
    - each community polled at most every 10 minutes;
    - ≤ 20 communities.
  - **The cursor is the newest local post id seen, never `published`.** Federated posts carry their origin's dates, while local ids only grow. Each poll re-reads the first page and pages back at most 5 pages, so a burst can't push the cursor past posts not yet read.
  - **Errors:** back-off, and a visible "blocked by source" state.
  - **Distribution:** `Singleton`.
- **ADH-0** (§20.9, owner §1.8.12). It builds only what the owner answers to Q-o4. The recommended shape:
  - **What a claim does:** a third-party `content-type:adult` claim (Nostr, Lemmy) may only **hide** an item while Show adult content is off, **pending local detection**:
    - it's a visibility hold, not a classification;
    - once detection classifies the item, detection's reading stands;
    - a title that detection reads as mainstream with confidence is never moved into Adult by the claim (§1.8.12).
  - **It never feeds the child-safety path.** Not the CS-5 adult-only core, and not tombstones. That's so a stranger can't use it to destroy data.
  - **Scope:** it applies only to items that only claiming sources found (unverified items, their promotion, and the fetch they lead to). It never touches a stored torrent another source found.
  - **Where:** in X-source-adult's places:
    - prepare (`worker.rs`, after WK-7);
    - commit and promotion (`writer.rs`, after WK-9);
    - claims and the refile sweep (`unverified.rs`);
    - the backfill (`enrich.rs`, `adult_enrich.rs`).

    Each path needs a claim lookup.
  - **Residual risk, stated:** anyone with a free Nostr key, or a Lemmy account, can hide an unverified release that only those sources found, until local detection clears it.
  - **Tests:**
    - each path;
    - an item without the claim is unchanged;
    - a stored torrent the DHT found first is unchanged;
    - the claim never reaches CS-5 or tombstones.
- **G-v08** (§19.8, §18.9, owner §1.6.5). On WK-20's harness:
  - **Placement and politeness:**
    - singleton failover within one heartbeat timeout, with no doubled finds;
    - an overlay test plugin never on a worker without its companion;
    - Prowlarr units only on companion hosts;
    - the fleet-wide request rate per host stays under each cap through failovers and partitions.
  - **Credentials, privacy and consent:**
    - credentials never on a worker without an allowance, and gone after revoke;
    - `private_source` keys never in a worker's public lookups;
    - per-worker consent can't be bypassed through the API;
    - purge-by-worker removes a worker's plugin finds.
  - **Worker RSS:** WK-G's `worker_rss` bench re-run with eight plugins and three companions assigned, against §5.5's budget at 10M stored (≤ 256 MB during a swap).
  - **Nostr and Lemmy:**
    - a blocklisted fixture hash through Nostr and Lemmy is dropped before storage;
    - a forged Nostr id or signature is dropped;
    - a future-dated event doesn't move the cursor;
    - ADH-0's behaviour as the owner chose (e2e).
  - **If it passes,** the gate's PR turns `cluster.remote_sources` on by default.
