## 1. Fixed constraints
- **No search schema bump.** M7's two bumps are spent: SB-6 (v6) and X-search-files-5 (v7), so a v0.5.1 user rebuilds once, v5 → v7 (build-plan §1.3). Every M7 slice fills fields v6/v7 already define, or writes terms into fields that exist (`title`, `tag`). A slice that finds it needs a new indexed field stops and tells the runner.
- **SB-6's population contract** (build-plan Track M7, `crates/search/src/population.rs`): each producer of an SB-6 field raises its generation in `population::GENERATIONS`, adds its `doc.rs` writes, uses `SearchIndex::prefilter` / `Availability` so a partly populated field is never read as "no match", and tests SB-6 → import → producer on an existing database with a restart mid-backfill. The generic resumable walk (`index.rs` `backfill`) already exists; a producer needs no backfill code of its own beyond the generation bump and its tests.
- **`private_source` never leaves the install** (§18.7, §18.9): never in Torznab, Stremio or any export, never sent to an enrichment service, and its hashes never reach a public lookup. Every output and enrichment slice tests this.
- **Outputs have their own adult settings, off by default** (§20.9; `torznab_adult`, `stremio_adult`, `export_adult` already exist as "Not used yet", `crates/lodestar/src/settings/content.rs`). Each output slice wires its own.
- **Every source and enrichment plugin is off by default** with its consent class (owner §1.9.7, §18.7), reuses SRC-5's egress (`crates/sources/src/egress.rs`) and `http::Client` behind `HostLimiter`, and ships only if its recorded ToS/robots check finds automated access allowed; a grey case goes to the owner (owner §2.28, sources-plan Q2).
- **The `.torrent` upload exception goes with the runner's recommendation** (owner §2.37): §5 below records it; UP-0's brief makes its decisions file restate it before any code, the runner confirms, and it returns to the owner only if what's built deviates. `/security-review` on the slice.
- **Untrusted-input parsers, on-disk formats, search core, concurrency and what leaves the install are Opus** (CLAUDE.md). Sonnet takes UI only here.
- **Slots:** four from 2026-11-06T00:00Z (owner §2.41), shared with Track C, Track I, the rule-pack tail and X-search-files-6.

## 3. SB-6 fields: producers, backfill and cost

Each producer below raises one generation, so on an existing index the walk (`backfill`) rewrites every document once. **One walk serves every field whose generation changed** ("one pass serves every field being backfilled", SB-6 decisions), so a released user upgrading v0.6 → v0.7 walks once whatever the number of producers; a nightly or dev install walks once per producer merge.

| Field | Producer | What it is | Index cost (estimate, per torrent) | CPU at index time |
|---|---|---|---:|---|
| `payload_sig` | GS-0 | `payload_sig` of the non-padding file sizes, moved from `filter` to `classify` so filter and search share one function | ~16–20 B (u64 fast column ~8 B; one mostly unique term + posting) | one sort of the file sizes |
| `group_key` | GS-2 | the fast-column copy of B13b's title identity (`TitleIdentityParts::key`), one identity rule (Q8) | ~12–20 B (shared terms; fast column) | none beyond `title_identity` |
| `group_minhash` | GS-2 | MinHash over the major file sizes, `b` band terms (Q9) | ~10–12 B per band; ~40–50 B at 4 bands, 0 for torrents below the threshold | `k` hashes over ≤ N sizes |
| `name_trigram` | RX-1 | lowercased 3-grams of `name`, docs only; empty in low-resource mode | ~50–90 B (≈ name length postings, bitpacked; small dictionary) | trivial |

- **Sum: ~120–180 B per torrent.** The torrent index measured **391.0 B at 10M** on v7 (X-search-files-5 decisions), and X-search-files-6 may take it to **420 B** (its brief, runner §2.26), against §3's **512 B**. So **the estimates predict going over 512 B** (511–600 B): Q10 is the expected case, not a contingency. Each producer re-measures with `size-report --torrents 50000` in its PR, in chain order: GS-0 first (the smallest), then GS-2, then RX-1 (the largest), so the runner sees the trend before the trigram field lands; G-v07-scale measures all of them at 10M on the owner host.
- **Walk time:** X-search-files-5 measured the full rebuild at ~1,439 torrents/s on 4 cores (1 h 55 min at 10M, both indexes). The walk rebuilds documents the same way but takes at least an eighth of each indexer step while crawling, so: **10M ≈ 2 h idle, up to ~16 h under a busy crawl; 50M ≈ 10 h idle, up to several days under load.** Disk: the walk deletes and re-adds documents, so merges hold old and new segments; peak ≈ 1.3–2× the torrent index during the walk (to measure). RSS: the indexer's 256 MB heap each, no new caches; the regex verify adds none at rest.
- **Recommendation (Q11): land GS-0, GS-2 and RX-1 before G-import-50M.** Then the 50M import indexes these fields directly (no walk), and the 50M approval names them as populated (build-plan §0.6). If any lands after, G-v07-scale measures its walk at 10M and budgets it for 50M, as Track M7 requires.
- **Fields that are not SB-6 fields:** enrichment's alternative titles go into the existing `title` field and its IDs into `tag` terms (ENR-11). Each enriched torrent is rewritten through `reindex_log` when its enrichment is stored, so there's no generation and no corpus walk. Cost: a few documents per second at the plugins' rate limits; store cost ~100–300 B of claims per enriched torrent, only for enriched ones (user interest plus a capped backfill, Q5, Q12). File-index fields need nothing: `pieces_root` is already populated, so GS-1's "same file" is free.
- **Usenet items** (UN-0) are `unverified_items` rows. They become searchable only once SRC-3b indexes unverified items (documents built from claims, `verified:no`, their `network` term; `compile.rs` `provenance` already compiles those terms). No new search field. Store cost ~0.3–1 KB per item (claims), capped (Q13).

## 5. The `.torrent` upload exception: the runner's recommendation (owner §2.37)
**Recommended solution:** one route, `POST /api/v1/torrents/upload`, outside the JSON extractor, with these terms. It's the narrowest exception that lets a browser send a file:
1. **Raw body, not multipart.** `Content-Type: application/x-bittorrent` exactly; anything else is 415. The UI sends one `fetch` per file with the file as the body. No multipart parser, no filenames, no form fields.
2. **Same guards as a JSON write.** An admin session cookie, and the same-origin check JSON writes rely on (`same_origin_json`'s Origin/Sec-Fetch-Site rule, `extract.rs` ~194), so a cross-site form can't post a torrent. API keys can't upload (no scope has it).
3. **Bounded.** A body cap of 8 MiB (a `.torrent` with 2²⁰ pieces is ~20 MB; anything near the cap is almost always a `pieces`-heavy file whose info dict we still need, so the cap is a §2.26 number the runner may raise to 32 MiB if real files hit it), read with a length limit before parsing; `TorrentFile::parse_with` with its limits; one file per request; the login rate limiter's per-session limit (§12).
4. **Nothing stored but what a BEP 9 fetch would store**, plus the out-of-info-dict claims (§4.3 UP-0). The raw file is dropped unless the info-dict archive is on.
5. **Same judgement as any metadata:** SRC-13b's verified-file path, floor first.
Folder watch (UP-1) adds no network surface. If what's built differs from this (multipart, a second route, another auth path), it goes back to the owner (§2.37).
