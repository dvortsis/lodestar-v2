Planning slice P-v06-rulepacks, 2026-11-04, for the build runner. It turns build-plan P4 "Filters" ("**[M]** curated rule packs; **[S]** ThePornDB/StashDB enrichment following the plugin pattern") into `RP-*` and `ENR-*` slices, the way `docs/plan/2026-11-01-v06-sources.md` turned P4 "Sources" into `SRC-*`. Docs only.

**Authority:** `docs/owner-decisions.md` §1.8, §1.9.7, §2.7, §2.8, §2.16–§2.21, §2.26, §2.28; architecture §1.8 (via owner §1.8), §12.2, §18.1, §18.2, §18.5, §18.7, §20 (above all §20.1, §20.6–§20.9, §20.11); build-plan P4. ## 1. Fixed constraints
- **Packs are off until chosen** and pre-checked in the first-run wizard; an install that skips the wizard has none (owner §2.8, §20.6). Nothing here changes that.
- **Precedence is §20.1's:** the locked floor, then CSX-5, the rest of the core, your exceptions, your rules, then packs. Packs and enrichment sit below the core and can never release what the core holds.
- **Weakening needs the effect warning and the password, every time; strengthening doesn't** (owner §1.8.8, §20.11). Any new pack operation that can release or soften a decision goes through `POST /filters/preview` and `apply` with that assessment, on the server.
- **Every filtering change is previewed before it takes effect,** and §20.10 names "accepting a signed update" among them (owner §1.8.7). A release that changes a pack is such an update, so it waits for the user's acceptance (RP-0, RP-3).
- **No audit log** (owner §1.8.8, §1.8.9; §20.8): overrides and pack state keep no author, reason, time or history beyond the current set and `rule_set_prev`'s one Undo step.
- **Loading fails closed** (#357, `docs/decisions/2026-11-01-F-filter-load-fail-closed.md`; stand-ins, #367): a stored row that no longer reads never loosens filtering. Every new stored filter row follows that rule: one that withholds fails closed, one that releases is skipped, and both are reported.
- **The budget is the owner's:** under 50 µs per torrent at 10,000 rules on the reference runner, every rule shape held (owner §1.6.6, §2.20, §2.21; §20.8). New pack rules run inside that budget.
- **Adult is a visibility preference, off by default with an 18+ confirmation** (owner §1.8.12; §20.9). Adult sources and enrichment use the normal consent classes. ThePornDB and StashDB are **Account class, off by default** (§20.9).
- **The child-safety core always applies to Adult,** with stricter age-signal thresholds there (§20.5, §20.9).
- **Sealed names never leave the install.** A name the core quarantines or drops is sealed (§20.7) and is never sent to any third party, enrichment included.
- **Every source is off by default and metadata only; private results stay local; no profiles of people** (owner §1.9.7; §18.7). `private_source` keys are never looked up anywhere else (§18.7, as SRC-13 does for torrent caches).
- **ToS and robots:** a plugin ships only if its recorded check finds automated API access allowed; a grey case goes to the owner (owner §2.28, sources plan Q2).
- **Migrations:** V14 (SRC-1) is on `main`; V15 is reserved for CR-3 behind the 50M gate (runner-state `migration_order`). Every migration snapshots the whole store first (`docs/decisions/2026-11-02-SRC-2b.md`). This plan needs **no migration** (§3, Q9).
- **Search `SCHEMA_VERSION`:** one bump per milestone, and SB-6's field list is the v0.6/M7 bump. This plan adds no search field (Q14).
- **Slots:** the runner's current limit (runner-state `limits`; eight when this slice launched on 2026-11-04, where `runner/slices.yaml` still records owner §2.30's two). Waves in §6 are upper bounds; higher rungs of the build-plan §0.2 ladder go first.

## 3. Store impact: none (no migration)
Everything new fits existing tables, as #367 and SRC-2b did (Q9):
- **Pack versions applied** (Q7): a `settings` row (`filter.packs.applied`, one line per rule: `RULE-ID@version`), read by the engine at load. A rule whose built version is newer than the applied one is **pending** until accepted (RP-0, RP-3).
- **Pack-rule overrides:** one `settings` row per overridden rule (`filter.pack_override:<RULE-ID>` → a small versioned encoding: base version, action, optional `unless` query text). `RuleSet` in `crates/store/src/rules.rs` gains them, so `rule_set_prev` (Undo) snapshots them with everything else.
- **SP-4's signature set:** packed 8-byte signatures in append-only `settings` chunk rows of at most 64 KB (`filter.sp4.sigs.<n>`), so a new hide writes one small row, not the whole set; releases mark removals and a compaction rewrites a chunk only when a quarter of it is removed. Capped (Q12).
- **SP-3's rate state:** memory only, bounded, rebuilt from zero at start (a restart forgets at most one window).
- **Enrichment results:** `torrent_claims` rows under the enrichment source's id (V14). Purge (`purge_source`, SRC-1/SRC-14b), the snapshot purge (§2.21) and `secure_delete` (§2.17) cover them already. As with every purge, claims on torrents that survive stay in older migration snapshots until those expire (90 days, §2.21; SRC-1's decisions file). The claim blob gains **encoding version 2** with an optional adult-enrichment section (ENR-0); version 1 blobs keep decoding.
- **Enrichment caches** (hits, misses, cursors): `source_state` (V14).

### 4.3 What each slice must do (spec and gates)
- **RP-0** (§20.6, §20.8, §20.10, owner §1.8.7). Split `packs.rs` into `packs/` without changing any rule's behaviour (the existing tests pass unchanged). Add a compiled-in manifest: each rule's version (a pack's version is the set of its rules'), bumped whenever what a rule matches or its action changes, plus a changelog file per pack. Split **SC-2** out of SC-1 so that SC-1 and SC-2 together match exactly what SC-1 matches today; a stored `SC-1` switch applies to SC-2 too, so no install's behaviour changes (Q16).
  - **A changed rule is pending until accepted** (§20.10's "accepting a signed update"). The store records the version this install last applied per rule (§3). When a release changes a rule, the manifest keeps **the previous version's code beside the new one** (`MW-2@1` and `MW-2@2`), and the engine goes on applying the applied version while the new one runs in shadow (hits logged with the shadow bit, nothing applied), so RP-3's preview has real numbers. Acceptance (RP-3) switches the applied version and then re-judges through the existing rule-change path (generation and enrichment pass, §20.7). A version two releases old is dropped from the code only once no supported upgrade path can still have it applied. **If an install's applied version is gone anyway** (it skipped that far), it fails closed until acceptance: the engine applies, per item, **the stronger of the oldest retained version and the current one** (the heavier action of the two, and a match if either matches), and every existing hold is kept. The acceptance's direction is the combination of every version from the applied one up to the current one (the manifest keeps the direction records of dropped versions): if any of them `narrows`, lightens the action or is `mixed`, accepting is weakening.
  - **Each version records its direction against the one before:** `widens`, `narrows`, `action-heavier`, `action-lighter`, or `mixed`. RP-1's corpus checks it (a `widens` bump may not lose a must-match; a `narrows` bump may not gain one), and RP-3 compares it with the shadow results. `narrows`, `action-lighter`, `mixed`, a disagreement with the shadow, or no record counts as weakening. **A rule's first version records `widens`** (against nothing), so accepting a newly added rule is strengthening and needs no password (owner §1.8.8).
  - **Acceptance never releases a hold by itself** (Q7). Tombstones (drop: MW-4, FK-4) keep no name, so they're kept and counted per rule as a whole. Quarantine and stored hide/demote/flag stamps that the new version wouldn't make stay as they are and are counted for review; the re-judge only ever adds decisions. Releasing goes through `release` with the warning and password.
  - **Seeding on the first RP-0 start.** No install has a `filter.packs.applied` row before RP-0. When the row is missing, RP-0 seeds it: every rule that existed before RP-0 is recorded at its **baseline version** (version 1, today's behaviour), so nothing that was on changes. SC-2 is recorded at baseline too and takes SC-1's stored switch, since its matching was already part of SC-1. No rule goes to shadow and nothing needs accepting.
  - **A rule added after RP-0** (SP-3, SP-4, later rules) that this install has never applied is pending (applied version = none), shadowed and accepted like a version bump, so an upgrade never turns it on unpreviewed where its pack is on.
  - **Turning a pack on records its rules' current versions.** Switching a pack on, in the wizard or in Settings, is itself previewed under §20.10, so it records the current version of each of its rules and asks for no second acceptance. This is also why **a fresh install needs no special detection:** its packs are off until chosen, and choosing them records current versions. A pending version only ever exists for a pack that's on.
  - A stored switch or applied version for a rule this build doesn't know is kept and ignored (#357).
  - **Gates:** the existing pack tests unchanged; SC-1 ∪ SC-2 equals today's SC-1 on the pack tests; a fake version bump stays pending, applies the old version, logs the new one in shadow, and releases nothing on acceptance; a widening bump holds newly matching torrents only after acceptance; a per-rule golden of today's behaviour fails if a rule's matching changes without a version bump (RP-1's corpus takes over once it exists); seeding on the first RP-0 start (no row) keeps every pre-RP-0 rule applied at baseline, SC-2 included, with nothing pending or shadowed; a rule added after RP-0 is pending on an upgraded install with its pack on, and current once a pack is turned on (fresh install or Settings); a rule's first version records `widens` and accepting it needs no password; an applied version whose code is gone applies the stronger of the oldest retained and current versions until acceptance, and the combined direction decides the password.
