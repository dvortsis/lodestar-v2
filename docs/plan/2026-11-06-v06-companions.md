# v0.6 Companion manager: the sliced plan (E-v06-companions)

Planning slice P-v06-companions, 2026-11-06, for the build runner. It turns build-plan Track K and P4 "Companion manager" ("**[M]** the signed catalogue, checksum and signature checks, supervised child processes and encrypted credentials; **[S]** compose and CA-template generation, detection adapters and the Companions UI") into `CMP-*` slices, the way `docs/plan/2026-11-01-v06-sources.md` and `docs/plan/2026-11-04-v06-rulepacks.md` did for Sources and rule packs. Docs only. Building waits for the v0.5.1 soak verdict (`ext:v051-soak-verdict`, r5; the baseline ends 2026-11-06T13:12Z).

**Authority:** `docs/owner-decisions.md` §1.7.2, §1b.5, §2.13, §2.19, §2.21, §2.23, §2.26, §2.35; architecture §10.10.2 and §10.10.8 (Settings → Companions), §10.10.10 (first-run wizard), §10.10.13 (About), §11 (deployment, CLI, PUID/PGID), §12 and §12.2 (security summary, update trust core), §13 (`crates/companions/`), §14 (v0.6 scope), §18.4, §18.7, §18.10, §18.9 (companion tests), §19.1 and §19.5 (companions on workers, v0.8), §19.6 (worker updates); build-plan Track K and P4. Where they're silent the plan says so (**silent**) and puts the question in §5. It decides nothing that belongs to the owner.

## 1. Fixed constraints
- **Native installs are fully automatic from a signed, pinned catalogue, with confirmation per install** (owner §1.7.2, accepted adjustment). Windows and bare-metal Linux only.
- **Docker and Unraid are guided, never self-installing:** a generated compose service or a pre-filled Unraid template, then automatic detection and configuration (owner §1.7.2). Lodestar never gets the Docker socket by default (§18.10).
- **Companion traffic follows the VPN settings, and the kill-switch covers companions** (owner §1.7.2; §18.10 "Rules").
- **A missing companion disables only the plugins that need it** ("Needs qBittorrent · Set up", owner §1.7.2; §18.10).
- **Nothing runs unless its SHA-256 matches the pin** (§18.10, §12). Every install, update and removal needs the user's confirmation; nothing auto-updates.
- **Least privilege:** a separate low-privilege process, bound to localhost or the internal network; only the P2P ports it needs exposed (§18.10).
- **Credentials are random and encrypted at rest** (§12), with the existing per-install sealing (`crates/integrations/src/secret.rs`).
- **Downloaded on demand, never bundled** (GPL programs stay separate, §18.10).
- **No `unsafe`** outside the store's narrow exception (owner §1b.5, §2.35). Windows Job Objects and Linux resource limits go through safe APIs or an approved dependency.
- **Code signing is deferred** (owner §2.23): Lodestar's own Windows binaries are unsigned, which doesn't change how Lodestar checks what it downloads.
- **v0.6 scope** (§14, §18.10 table): qBittorrent, Prowlarr with optional FlareSolverr, and gluetun (containers only; the native VPN route is the existing per-plugin egress, §18.4, SRC-5). SABnzbd/NZBGet (v0.7), i2pd (v1.1), aMule (v1.2), Kubo (v1.3) and companions on workers (v0.8, §19.5) are later.

## 3. Store impact: none (no migration)
Everything fits the `settings` table, as #367 and the rule-pack plan did (Q10):
- **Per companion:** one `settings` row `companions.<id>` with a small versioned encoding: how it's present (managed, detected, guided), the installed version and path, the previous version kept for rollback, the URL for a detected one, and the last health. Written in one transaction with the credentials.
- **Credentials:** sealed values in `settings` rows `companions.<id>.secret.<field>` (`SecretStore::seal`, context `companion:<id>:<field>`). Covered by the existing rotation (`reseal`) and kept out of exports and support bundles, as SRC-4's are.
- **Logs:** a bounded in-memory ring per companion plus catalogued events; nothing in the database.

No slice takes the migration slot (`ext:migration-slot`), and the queue (V15 CR-3) is unaffected.

**21 slices, about 13,900 lines; no migration.** Every slice is under 1,500 lines. The largest is CMP-6 at ~1,200, of which ~400 is the regenerated `openapi.json` and `schema.d.ts`; then CMP-4a at ~1,050, because process supervision and orphan cleanup are one concurrency design; then CMP-5 at ~1,000, because the install flow is one state machine (confirm, fetch, verify, extract, configure, start, roll back) that should be reviewed as one. The supervisor is split (CMP-4a, CMP-4b) to keep the platform-specific limits apart from the concurrency core. The guided path (CMP-5g), Windows qBittorrent (CMP-11), FlareSolverr (CMP-12) and the pin-refresh tool (CMP-13) are their own slices, so each owner answer changes one slice.

**Model changes from the build plan, all stricter (Q14):** the build plan marks compose and CA-template generation and the detection adapters **[S]**. All three are Opus here: compose and template output (CMP-7) is run by a root-equivalent `docker compose`; detection (CMP-8a) probes a URL you enter, reads untrusted responses and chooses the SSRF guard's loopback-allowed mode; auto-configuration (CMP-8b) writes generated credentials into third-party APIs. Sonnet keeps the UI (CMP-9a, CMP-9b, CMP-9c) and the guide (CMP-D).

**New dependencies, approved per slice in its brief** (standards §2; Q13): `zip` (no default features, deflate only) and `tar` for CMP-2 (`flate2` is already in the lockfile); `pbkdf2` for CMP-3 (qBittorrent's `WebUI\Password_PBKDF2` is PBKDF2-HMAC-SHA512; `hmac` and `sha2` are already in the lockfile); for CMP-4a/CMP-4b, a safe Job Object wrapper on Windows (`win32job`, or `windows-sys` through an existing safe wrapper) and, if the owner picks Q3 (b), `landlock` on Linux and a safe restricted-token or AppContainer wrapper on Windows if one exists. No first-party `unsafe`. Prowlarr's `config.xml` and the Unraid template are written with `quick-xml` (already in the lockfile), compose YAML scalars with `serde_json` quoting, never a hand-written escaper. No OpenPGP crate (Q2: CMP-13 uses the CI runner's `gpg`).

**Owner questions that gate a slice:** Q1 and Q15 (CMP-0), Q2 (CMP-1, CMP-13), Q3 (CMP-4a), Q4 (CMP-11), Q5 (CMP-6), Q20 (CMP-G, and any unit relaxation in CMP-4b), Q21 (CMP-12). No slice builds an answer to an owner question before the owner gives it. Every other question is the runner's.

### 4.3 What each slice must do (spec and gates)
- **CMP-0:** the adapter traits (`Detect`, `Health`, `Configure`) that CMP-4a, CMP-8a and CMP-8b use, so those slices can run at once, and the closed input types CMP-7 renders (`inputs.rs`: host paths, PUID/PGID, network name or `service:gluetun`, port numbers, each a validated newtype with no free-form string). The catalogue is data compiled into the binary (`include_str!` of `data/catalogue.json`) and parsed at start with `deny_unknown_fields`; a malformed catalogue fails the build's tests and, at run time, disables installs (never crashes). Each entry: id, name, licence and its URL, what it's needed for, whether it's opt-in, per platform and architecture `{url, size, sha256, archive: zip|tar.gz|installer, upstream_sig?}` with what CMP-13 verified at pin time, the executable path inside the archive, ports (bound and exposed), health endpoint, config template ids, container image and digest for compose. Validation: `https` only; hosts in a per-entry allowlist; sizes capped (Q16); unique ids; no entry for a platform v0.6 doesn't support. The v0.6 entries per Q15. Tests: every pin is well-formed, a property test that validation rejects mutations. A different catalogue can be loaded only under `cfg(any(test, feature = "testing"))`, never through config or the environment.
- **CMP-1:** the download rules of `crates/lodestar/src/update/download.rs`: `https`, the entry's hosts for every redirect, at most `MAX_HOPS`, one byte past the size stops it, hashed as it streams, `O_NOFOLLOW` 0600 `.part`, fsync, then SHA-256 and size must equal the pin or the file is removed. Upstream signatures per Q2. Nothing identifying is sent (`User-Agent: Lodestar-Companions`). Downloads use Lodestar's own route, like updates (Q16). Tests with a local TLS server: wrong hash, wrong size, extra byte, redirect off the allowlist, slow drip timeout.
- **CMP-13:** a tool (`tools/companion-pins/`) and a manual-dispatch release-workflow step that, for each entry, downloads the artifact, checks its upstream OpenPGP signature against a key pinned by fingerprint in the tool (where upstream signs), computes SHA-256 and size, and writes the entry with `upstream_sig: verified-at-pin` only when that check ran and passed. CI fails a `catalogue.json` change whose pins the tool didn't produce. This is what makes "verified at pin time" (Q2) a checked claim.
- **CMP-2:** extraction into a fresh `<data>/companions/<id>/<version>.staging/`, renamed into place only when complete. Refused: absolute paths, `..`, symlinks and hard links, device files, setuid/setgid bits, duplicate names, more than the entry cap, more than the total-size cap, a compression ratio over the cap. Removal deletes only paths under `<data>/companions/<id>/`. A fuzz target over both formats. Tests with crafted archives for each refusal.
- **CMP-3:** for native installs, credentials from the OS RNG (32 bytes, encoded as each companion needs), sealed per §3; qBittorrent's `WebUI\Password_PBKDF2` in `qBittorrent.conf`, Prowlarr's `ApiKey` and bind address in `config.xml` (`quick-xml`), written before first start with bind addresses set to `127.0.0.1`. The config writers emit only what the template names. Never logged (a test greps every event), never in exports or support bundles. For guided installs, per Q19: a pasted key or temporary password is sealed the same way and the temporary password is replaced by a generated one.
- **CMP-4a:** spawn with a minimal environment: `env_clear()` plus the template's variables on Linux, and on Windows the base a process needs (`SystemRoot`, `TEMP`/`TMP`, `PATH` limited to the system directories, `USERPROFILE`/`APPDATA` pointed at the companion's folder) plus the template's; a working directory under the companion's own folder (0700); stdin closed; stdout/stderr into a bounded ring with credential redaction (Q7); restart with exponential backoff; health through CMP-0's `Health` trait (CMP-8a implements it); stop in reverse dependency order at shutdown, with a deadline then kill. **Orphans (design point, gated):** on Linux the init (`update/supervisor.rs`) is a subreaper that reaps but doesn't kill, and there's no `PR_SET_PDEATHSIG` without `pre_exec`. So each running companion is recorded by pid and process start time (and a pidfd where the kernel has one) in `<data>/companions/run/`; at start-up, a recorded process whose pid, start time and executable path still match is killed before anything starts; and the init kills the companions it adopts when the work child dies. Unix reaping must not race the init's reaper (the companion supervisor runs in the work child). Tests: kill the work child with SIGKILL and assert no companion survives the restart.
- **CMP-4b:** Windows: every companion in one Job Object with kill-on-job-close, so companions die with Lodestar; optional memory cap; the Q3 sandbox if chosen. Linux: rlimits (files, address space when set) applied with `prlimit` on the child's pid right after spawn, leaving a window of microseconds before they apply, which is acceptable because the child is still loading; cgroup v2 limits only when the unit delegates a subtree (detect; never require; the shipped unit has `ProtectControlGroups=yes` and no `Delegate=`, so rlimits are what it gets); Landlock if Q3 (b) is chosen. The route comes from the companion's own egress setting (Q18), built through `lodestar_sources::EgressFactory` and `PluginEgress` handed in by `crates/lodestar`, so `crates/companions` never depends on `crates/pipeline` (CMP-10 makes pipeline depend on companions). A companion whose route is non-direct starts only when the route is up and is stopped when `PluginEgress`'s probe reports it down (Q8, Q9). Any change to `packaging/systemd/lodestar.service` is made here and only as the owner approves in Q20.
- **CMP-5:** the install flow as one state machine with a journal row, so a crash at any step leaves either the old version or nothing, never a half-install: confirm (the API carries an explicit confirmation token from CMP-6) → fetch → verify → extract → credentials → configure files → start → health → configure through the API (CMP-8b) → done. Updates keep the previous version until the new one passes health, then remove it. Refuses native installs inside a container (Q17) and on unsupported platforms. CLI: `companion list|install|remove|compose`.
- **CMP-5g:** the guided and detected path end to end (owner §1.7.2 "then automatic detection and configuration"): endpoints to add a detected companion or one at a URL you enter, to paste its key or temporary password (Q19, sealed by CMP-3 and never echoed back), and to confirm the configuration CMP-8b will apply (the list of settings it changes, shown before it runs); a watch loop that runs detection and health for companions Lodestar doesn't supervise, with Q7's health cadence, and moves dependents to "Needs X" when one disappears; and the binary wiring that hands CMP-8a's and CMP-8b's adapters, and the `ConfigSink` that writes the Prowlarr plugin's address and key and the `integrations.clients` entry, in from `crates/lodestar`.
- **CMP-6:** admin scope only; install, update and removal require a confirmation token naming the exact entry, version and SHA-256 shown to the user; responses never include credentials except the reveal endpoint per Q5; logs pass through redaction again. The Companions row in `/system` gets its data; the About row already exists (`AboutScreen.svelte`, `settings_about_conn_companions`) and CMP-9a relabels it.
- **CMP-7:** generated compose and Unraid XML are built only from catalogue values and CMP-0's closed input types; every YAML scalar is emitted quoted with `serde_json` and the Unraid template through `quick-xml`, never by string concatenation or a hand-written escaper; the image is pinned by digest; ports bound to the internal network by default; no Docker socket mount, ever. gluetun's VPN keys stay placeholders that you fill in yourself; Lodestar never asks for or stores them. Golden tests per companion, with and without gluetun, plus a property test that no input value can add a key or a document. Unraid per Q11.
- **CMP-8a:** detection probes only (a) loopback on the catalogue's ports, (b) the catalogue's container names on Docker's network (`qbittorrent`, `prowlarr`, `gluetun`; `flaresolverr` comes with CMP-12), (c) a URL the user enters; never a range scan (Q12). Each probe has a timeout and a byte cap and goes through the SSRF guard's loopback-allowed mode for these fixed targets only. Recorded fixtures per adapter, the SRC-7 pattern.
- **CMP-8b:** per companion, the settings it changes, each idempotent and logged by name (never value); qBittorrent: WebUI bound to localhost or the internal network, categories and save path, the network interface per the egress route; Prowlarr: its SOCKS5 proxy per the route. Writes to Lodestar's own settings (the Prowlarr plugin's address and sealed key, a qBittorrent entry in `integrations.clients`) go through a `ConfigSink` trait that `crates/lodestar` implements (CMP-5g), so `crates/companions` depends on neither `crates/pipeline` nor the settings code. Never configures a companion Lodestar didn't install without the user's confirmation. For guided installs, it starts from the key or temporary password the user pasted (Q19). FlareSolverr is CMP-12's, never wired here.
- **CMP-9a/9b/9c:** per §10.10.8 and the UI rules: tokens only, no hex; install confirmation shows the program, version, licence, size, SHA-256 and where it will run; Remove says what it deletes; a pasted secret field never shows its value again. Chips read CMP-10's state. The wizard option appears only on native platforms.
- **CMP-11:** the install path the owner chooses in Q4, its catalogue entry, and the hand-off to CMP-5g's guided path; whatever runs on the user's machine passes CMP-1's checks first. Under Q4 (a): the verified installer is offered as a download through your browser (the service can't start a desktop program), the screen says to turn on qBittorrent's WebUI (Tools → Options → Web UI, bound to localhost) after installing, and detection then finds it.
- **CMP-12:** FlareSolverr only if the owner says yes to Q21: its catalogue entry (marked opt-in), its detection and health adapter, and setting it as Prowlarr's indexer proxy, each only after you switch it on for Prowlarr. It's never installed, detected into use or wired by default.
- **CMP-10:** the map (Prowlarr plugin → Prowlarr; download-client source → a client; later i2pd plugins → i2pd) and a state per plugin (`ok`, `needs(companion)`, `unhealthy(companion)`); a plugin whose companion is missing doesn't start and reports `needs`, never an error loop; the others are unaffected.
- **CMP-G:** §18.9's companion tests: a checksum or signature mismatch is refused and nothing runs; companions bind to localhost or the internal network only; their traffic follows the egress setting and the kill-switch stops them; a missing companion puts its dependents in "Needs setup"; credentials never appear in logs, API responses (except the reveal), exports or support bundles; uninstall leaves nothing under the data folder but logs the user kept; after the work child is killed, no companion survives (Linux and Windows). A Windows and Linux CI smoke installs a fake companion from a test-only catalogue (the `testing` feature) and checks a tampered artifact is refused; a test asserts the release build has no catalogue override; a Linux smoke runs the real qBittorrent and Prowlarr builds under the shipped `packaging/systemd/lodestar.service` and records what, if anything, the unit blocks (input to Q20). Every `catalogue.json` pin came from CMP-13's tool. §18.9's managed-container test is out of scope while that mode is deferred (Q11).
