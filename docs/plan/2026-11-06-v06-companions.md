## 1. Fixed constraints
- **Native installs are fully automatic from a signed, pinned catalogue, with confirmation per install** (owner §1.7.2, accepted adjustment). Windows and bare-metal Linux only.
- **Docker and Unraid are guided, never self-installing:** a generated compose service or a pre-filled Unraid template, then automatic detection and configuration (owner §1.7.2). Lodestar never gets the Docker socket by default (§18.10).
- **Companion traffic follows the VPN settings, and the kill-switch covers companions** (owner §1.7.2; §18.10 "Rules").
- **A missing companion disables only the plugins that need it** ("Needs qBittorrent · Set up", owner §1.7.2; §18.10).
- **Nothing runs unless its SHA-256 matches the pin** (§18.10, §12). Every install, update and removal needs the user's confirmation; nothing auto-updates.
- **Least privilege:** a separate low-privilege process, bound to localhost or the internal network; only the P2P ports it needs exposed (§18.10).
- **Credentials are random and encrypted at rest** (§12), with the existing per-install sealing (`crates/integrations/src/secret.rs`).
- **Downloaded on demand, never bundled** (GPL programs stay separate, §18.10).
- **No `unsafe`** outside the store's narrow exception (owner §1b.5, §2.35). Windows Job Objects and Linux resource limits go through safe APIs or an approved dependency.
- **Code signing is deferred** (owner §2.23): Lodestar's own Windows binaries are unsigned, which doesn't change how Lodestar checks what it downloads.
- **v0.6 scope** (§14, §18.10 table): qBittorrent, Prowlarr with optional FlareSolverr, and gluetun (containers only; the native VPN route is the existing per-plugin egress, §18.4, SRC-5). SABnzbd/NZBGet (v0.7), i2pd (v1.1), aMule (v1.2), Kubo (v1.3) and companions on workers (v0.8, §19.5) are later.

## 3. Store impact: none (no migration)
Everything fits the `settings` table, as #367 and the rule-pack plan did (Q10):
- **Per companion:** one `settings` row `companions.<id>` with a small versioned encoding: how it's present (managed, detected, guided), the installed version and path, the previous version kept for rollback, the URL for a detected one, and the last health. Written in one transaction with the credentials.
- **Credentials:** sealed values in `settings` rows `companions.<id>.secret.<field>` (`SecretStore::seal`, context `companion:<id>:<field>`). Covered by the existing rotation (`reseal`) and kept out of exports and support bundles, as SRC-4's are.
- **Logs:** a bounded in-memory ring per companion plus catalogued events; nothing in the database.

No slice takes the migration slot (`ext:migration-slot`), and the queue (V15 CR-3) is unaffected.

**Model changes from the build plan, all stricter (Q14):** the build plan marks "detection adapters" **[S]**. Detection and health stay Sonnet (CMP-8a) because they parse nothing new: they use the existing qBittorrent client and the bounded `json.rs`. Auto-configuration (CMP-8b) moves to Opus, because it writes generated credentials into third-party APIs. If CMP-8a finds it needs a new parser, that parser is split out as an Opus slice.

**New dependencies, approved per slice in its brief** (standards §2; Q13): `zip` (no default features, deflate only) and `tar` for CMP-2 (`flate2` is already in the lockfile); a safe Job Object wrapper for CMP-4b on Windows (`win32job`, or `windows-sys` through an existing safe wrapper, so no first-party `unsafe`). No OpenPGP crate (Q2).

**Owner questions that gate a slice:** Q1 (CMP-0), Q2 (CMP-1), Q3 (CMP-4a), Q5 (CMP-6). Q4 gates only CMP-G: the slices build the narrower Windows qBittorrent path, and the gate holds the epic until the owner answers. Every other question is the runner's.

- `web/src/lib/api/openapi.json` and `schema.d.ts`: regenerated after a rebase by CMP-6 (and CMP-10 if its DTO field lands first), never merged by hand.

### 4.3 What each slice must do (spec and gates)
- **CMP-0:** the catalogue is data compiled into the binary (`include_str!` of `data/catalogue.json`) and parsed at start with `deny_unknown_fields`; a malformed catalogue fails the build's tests and, at run time, disables installs (never crashes). Each entry: id, name, licence and its URL, what it's needed for, per platform and architecture `{url, size, sha256, archive: zip|tar.gz|installer, upstream_sig?}`, the executable path inside the archive, ports (bound and exposed), health endpoint, config template ids, container image and tag digest for compose. Validation: `https` only; hosts in a per-entry allowlist; sizes capped (Q16); unique ids; no entry for a platform v0.6 doesn't support. The v0.6 entries per Q15. Tests: every pin is well-formed, a property test that validation rejects mutations.
- **CMP-1:** the download rules of `crates/lodestar/src/update/download.rs`: `https`, the entry's hosts for every redirect, at most `MAX_HOPS`, one byte past the size stops it, hashed as it streams, `O_NOFOLLOW` 0600 `.part`, fsync, then SHA-256 and size must equal the pin or the file is removed. Upstream signatures per Q2. Nothing identifying is sent (`User-Agent: Lodestar-Companions`). Downloads use Lodestar's own route, like updates (Q16). Tests with a local TLS server: wrong hash, wrong size, extra byte, redirect off the allowlist, slow drip timeout.
- **CMP-2:** extraction into a fresh `<data>/companions/<id>/<version>.staging/`, renamed into place only when complete. Refused: absolute paths, `..`, symlinks and hard links, device files, setuid/setgid bits, duplicate names, more than the entry cap, more than the total-size cap, a compression ratio over the cap. Removal deletes only paths under `<data>/companions/<id>/`. A fuzz target over both formats. Tests with crafted archives for each refusal.
- **CMP-3:** credentials from the OS RNG (32 bytes, encoded as each companion needs), sealed per §3; qBittorrent's `WebUI\Password_PBKDF2` in `qBittorrent.conf`, Prowlarr's `ApiKey` and bind address in `config.xml`, written before first start with bind addresses set to `127.0.0.1` (native). The config writers emit only what the template names, escaping values. Never logged (a test greps every event), never in exports or support bundles.
- **CMP-4a:** spawn with `env_clear()` plus the template's variables only, a working directory under the companion's own folder (0700), stdin closed, stdout/stderr into a bounded ring with credential redaction (Q7); restart with exponential backoff; health through CMP-8a's adapter trait (defined here, implemented there); stop in reverse dependency order at shutdown, with a deadline then kill. Unix reaping must not race `update/supervisor.rs`'s reaper (the companion supervisor runs in the work child, never in the init).
- **CMP-4b:** Windows: every companion in one Job Object with kill-on-job-close, so companions die with Lodestar; optional memory cap. Linux: rlimits (files, address space when set) through `rustix`; cgroup v2 limits only when the unit delegates a subtree (detect; never require). The egress hook: a companion whose route is non-direct starts only when the route is up and is stopped when the route monitor (`crates/pipeline/src/egress.rs`) reports it down (Q8, Q9).
- **CMP-5:** the install flow as one state machine with a journal row, so a crash at any step leaves either the old version or nothing, never a half-install: confirm (the API carries an explicit confirmation token from CMP-6) → fetch → verify → extract → credentials → configure files → start → health → configure through the API (CMP-8b) → done. Updates keep the previous version until the new one passes health, then remove it. Refuses native installs inside a container (Q17) and on unsupported platforms. CLI: `companion list|install|remove|compose`.
- **CMP-6:** admin scope only; install, update and removal require a confirmation token naming the exact entry, version and SHA-256 shown to the user; responses never include credentials except the reveal endpoint per Q5; logs pass through redaction again. The Companions row in `/system` and the catalogue line in About's "everything Lodestar connects to" (§10.10.13).
- **CMP-7:** generated compose and Unraid XML use only catalogue values and a closed set of user inputs (paths, PUID/PGID, the network or `service:gluetun`), each validated and escaped; the image is pinned by digest; ports bound to the internal network by default; golden tests per companion, with and without gluetun. Unraid per Q11.
- **CMP-8a:** detection probes only (a) loopback on the catalogue's ports, (b) the catalogue's container names on Docker's network (`qbittorrent`, `prowlarr`, `flaresolverr`, `gluetun`), (c) a URL the user enters; never a range scan (Q12). Each probe has a timeout and a byte cap and goes through the SSRF guard's loopback-allowed mode for these fixed targets only. Recorded fixtures per adapter, the SRC-7 pattern.
- **CMP-8b:** per companion, the settings it changes, each idempotent and logged by name (never value); qBittorrent: WebUI bound to localhost or the internal network, categories and save path, the network interface per the egress route; Prowlarr: FlareSolverr as its indexer proxy, its SOCKS5 proxy per the route; then the Prowlarr source plugin's address and sealed key, and a qBittorrent entry in `integrations.clients`. Never configures a companion Lodestar didn't install without the user's confirmation.
- **CMP-9a/9b:** per §10.10.8 and the UI rules: tokens only, no hex; install confirmation shows the program, version, licence, size, SHA-256 and where it will run; Remove says what it deletes. Chips read CMP-10's state. The wizard option appears only on native platforms.
- **CMP-10:** the map (Prowlarr plugin → Prowlarr; download-client source → a client; later i2pd plugins → i2pd) and a state per plugin (`ok`, `needs(companion)`, `unhealthy(companion)`); a plugin whose companion is missing doesn't start and reports `needs`, never an error loop; the others are unaffected.
- **CMP-G:** §18.9's companion tests: a checksum or signature mismatch is refused and nothing runs; companions bind to localhost or the internal network only; their traffic follows the egress setting and the kill-switch stops them; a missing companion puts its dependents in "Needs setup"; credentials never appear in logs, API responses (except the reveal), exports or support bundles; uninstall leaves nothing under the data folder but logs the user kept. A Windows and Linux CI smoke installs a fake companion from a test catalogue signed with a test key, and checks a tampered one is refused.

## 6. Order and parallelism
Slots are limited to four from 2026-11-06T00:00Z, and higher rungs of the build-plan §0.2 ladder share them and go first, so the waves are upper bounds. Nothing launches before the soak verdict and Q1.

| Wave | Runs at once | Why |
|---|---|---|
| 1 | CMP-0 | The crate skeleton and catalogue everything else builds on; needs Q1 |
| 2 | CMP-1 (after Q2), CMP-2, CMP-3, CMP-4a (after Q3) | Disjoint files under `crates/companions/src/`; only `lib.rs` mod lines are shared |
| 3 | CMP-4b, CMP-7, CMP-8a, CMP-10 | CMP-4b after CMP-4a; the others need only CMP-0 and fill slots as wave 2 drains |
| 4 | CMP-5, CMP-8b | The manager needs fetch, extract, credentials and limits; configuration needs credentials and detection |
| 5 | CMP-6 (after Q5) | The API over the manager, templates, configuration and dependency state |
| 6 | CMP-9a, CMP-9b | UI after its API |
| 7 | CMP-D, CMP-G (after Q4) | Last |

**Critical path:** soak verdict and Q1 → CMP-0 → CMP-4a (Q3) → CMP-4b → CMP-5 → CMP-6 (Q5) → CMP-9a → CMP-G (Q4): eight slices in sequence. The owner's answers are the likely long pole, so Q1–Q5 go to the owner first. CMP-7, CMP-8a and CMP-10 can start as soon as CMP-0 merges, and fill slots while the supervisor chain runs.

Nothing here touches the crawler, `fetch_queue` or the fetch pool, so the epic doesn't affect the crawler gate (build-plan §0.6). CMP-10 edits the plugin host in `crates/pipeline/`; if CR-3 (V15, which owns `crates/pipeline/**`) launches during this epic, the runner orders them.

**Gates in summary** (§4.3):
- **Fuzz target** for archive extraction (CMP-2); a property test for catalogue validation (CMP-0).
- **Verification:** a wrong hash, size, host or signature is refused and nothing runs (CMP-1, CMP-G).
- **Least privilege:** clean environment, own folder, localhost binding, Job Object or rlimits, never root or administrator (CMP-3, CMP-4a, CMP-4b, CMP-G).
- **Egress:** companions follow the route and stop with the kill-switch; one that can't follow it doesn't start (CMP-4b, CMP-8b, CMP-G).
- **Credentials:** never logged, exported or returned except the password-gated reveal (CMP-3, CMP-6, CMP-G).
- **Install smoke** on Windows and Linux from a test catalogue (CMP-G).
- **`/security-review`** for every slice except CMP-9b and CMP-D, which say why in their notes; an **unanchored second read** for CMP-0, CMP-1, CMP-2 and CMP-G (companion verification, build-plan).
