## 1. Fixed constraints
- **One coordinator, workers dial out** (§19, owner §1.10). A worker has no database, no index and no UI, and can't query any of them (§19.6 "least data").
- **Exactly-once accounting** (§19.3): "harvested" is counted at grant, once per key across the fleet; the holder reports the terminal outcome once; a stale fencing token is ignored. Cohort conservation (§10.9.3) holds.
- **The coordinator's commit is authoritative** (§19.4): the blocklist and rule checks run again at commit for every remote result. `writer.rs` already re-judges any result whose worker isn't `WorkerId::LOCAL` (line ~1825). Workers never decide what's stored.
- **No profiles of people** (§18.7, §19.6): peer addresses leave a worker only as in-memory peer hints. Nothing about peers is stored or spooled.
- **Worker budgets** (owner §1.6.5; architecture §3, §19.8): RSS ≤ 256 MB at defaults, ≤ 3 KB per torrent on the wire (median). The coordinator ingests ≥ 1,000 new verified torrents/s; grant latency p95 < 50 ms on a LAN.
- **The fetch pool's 200k cap doesn't fit a worker** (soak r3 verdict): 200,000 × ~690 B ≈ 132 MiB, half the budget on its own. The worker gets its own cap (§4.3 WK-10, Q5).
- **Single-machine parity** (§19.8): with no remote worker joined, behaviour and benchmarks match today's pipeline. No crawler behaviour changes without remote workers, so the crawler rules (BEP 51 intervals, per-IP limits, §18 caps, switches default off) are untouched.
- **Migrations:** one migration PR at a time, in the §0.7 queue (`ext:migration-slot`); V14 (SRC-1) is merged and V15 is reserved for CR-3. The one worker migration takes the next free number when it reaches the slot (§3).
- **Security:** `/security-review` for everything that touches the cluster port, credentials, untrusted bytes, the spool or what a worker may hold (standards §7). The cluster crate's chaos and transport tests stay green (build-plan Track W).

## 3. Store and schema impact
**One migration in one slice (WK-12),** numbered by §0.7's rule: the next free number when it reaches the slot (V16 if CR-3 has taken V15 by then, else V15; the runner records it in `runner-state` `migration_order`). Opus, store owner only.

| Object | Shape | Why |
|---|---|---|
| `torrent_worker` | `(torrent_id INTEGER PRIMARY KEY REFERENCES torrents ON DELETE CASCADE, worker INTEGER NOT NULL)`, `STRICT`, a row only for torrents a **remote** worker prepared | Purge-by-worker and quarantine (§19.4, §19.7) need to know which torrents came from which worker. No row = the local worker, so single-machine installs write nothing (parity) |
| index `torrent_worker(worker)` | | Purge and per-worker counts |
| `snapshots.rs` `Plan::KNOWN_THROUGH` | to the new version | The snapshot purge (§2.21) already follows `torrents`; the table holds no names |

**No other table:**
- **Worker records, budgets, intensity and pins** live in `settings` under `cluster.` as V6-cluster1 does (versioned records, one transaction per operation).
- **Outstanding remote leases** persist in the existing `fetch_queue` (`info_hash`, `source`, `cohort`, `strategy`, `priority`, `attempts`, `flags`), as the local worker's do (§19.3). The holder isn't stored: a coordinator restart starts a new lease epoch, every old token goes stale, and the keys are re-granted (Q7 covers results spooled across it).
- **The worker dimension** is a new `dim` code in `rollup_hour`/`rollup_day` (§19.7), not a column.
- **The worker side has no database.** Its credentials file is V6-cluster1's; its spool is WK-11's own segment format (an on-disk format: Opus, fuzzed).

### 4.3 What each slice must do (spec and gates)
- **WK-0** (§19.2, §19.3). Today a key can be leased in the pipeline's table and again in `ClusterServer`'s. Make `ClusterServer`'s `LeaseTable` the only one: the pipeline's `Coordinator` keeps the funnel accounting and calls the server for claims, outcomes, completions and restores, and the server calls back into it for "harvested" and re-grants. The local worker keeps direct calls (Q4). Add every v1 protocol message and field (§4.2), the inbound sink trait, the grant-admission hook and `send`/`broadcast`; the new messages' `validate` limits are fuzzed by the existing `cluster_frame` target. **Gates:** a property test that one key is never granted to two holders across local and remote claims; the funnel reconciles (harvested = Σ terminal + in flight) with a local and a fake remote worker; every existing cluster and pipeline test passes; the single-machine parity bench within noise.
- **WK-1** (§19.2, §19.6, §12). `[cluster]` config (listen address, default `0.0.0.0:8091` once allowed); the port isn't bound until workers are allowed (Q3). Open `Coordinator`, build `ClusterServer` with the store's `StoredKeys`, run `maintain` from the tick, and call `Coordinator::reseal` in the secrets-key rotation between `rotate` and `retire_old_keys` (V6-cluster2 hooks). Metrics: sessions, pre-auth refusals, leases, stale reports, PKI errors. **Gates:** a fresh install binds nothing; allowed, it binds and refuses an unauthenticated client; a rotation test that the PKI opens after reseal.
- **WK-2** (§19.6, §13). `lodestar worker --join <url> --token-file <path|->`, then `--data <dir>` runs from the saved credentials. Reconnect with capped exponential back-off and jitter; renew at half-life; on `Drain`, finish leases and report; on `Stop(Revoked)` or `Expired`, stop and say to join again. Call `Credentials::reseal` in the worker's secrets-key rotation (V6-cluster2). **Gates:** join, restart, renew; reseal then retire opens the credentials; a revoked worker stops within one heartbeat; a reused or expired token fails with one message; the token never reaches logs, argv or the environment (Q2 may change the last).
- **WK-3** (§19.3, §7). Replace `RandomState` with a keyed PRF, SipHash-1-3 under a random 128-bit key per filter, so a copy answers the same on any machine while peers still can't choose colliding hashes (the reason `have.rs` keys it today). The key travels only in the snapshot header over mTLS, never in logs or `Debug` output; false-positive rate unchanged (property test). Snapshot = a versioned header (key, bits, hashes, capacity, count) and chunks ≤ 512 KiB with a sequence and total; deltas = batched inserts with the filter generation. A rebuild bumps the generation and sends a fresh snapshot; a worker keeps the old filter until the new one is complete (peak 2× the filter). Decoding is bounded and fuzzed (bytes come from the network, authenticated or not). **Gates:** a worker never reports "not stored" for a key the coordinator stored before the snapshot it holds; out-of-order and missing chunks are refused; the fuzz target; the key never appears in logs or `Debug`; memory at 10M stored (25 MB, 50 MB during a swap, since `capacity_for` sizes the filter at 2× the stored count).
- **WK-4** (§19.5, BEP 42, BEP 51). A `Shard { prefixes: start..end of 256, id_slots: u8 bitset }` in the DHT config. The target-prefix cursor walks only its range; `virtual_ids` uses only its slots, both at start (`actor.rs` `initial_ids`, where saved ids outside the shard are regenerated) and on an IP change (the re-id). The node still runs `dht.virtual_ids` ids (default 4), capped at its number of slots. No shard is today's behaviour, byte for byte (the existing DHT tests pass unchanged). Per-node BEP 51 intervals and per-IP limits don't change. **Gates:** property tests that disjoint shards never target the same prefix in a pass and never mint the same BEP 42 prefix; the full-range shard equals no shard; saved ids outside the shard are regenerated.
- **WK-5** (§19.5). `Assign` payload v1: revision, the DHT shard, budget and intensity, the worker pool cap (Q5), the dictionary and filter-snapshot versions (their bytes travel in WK-0's chunked messages). Placement v1: workers sharing an external IP split that IP's 8 id slots and the 256 target prefixes; workers on different IPs each get the full id slots and a share of target prefixes; the coordinator's own DHT counts as one member of its IP. Fetch and prepare run everywhere. Every source plugin is refused for workers (Q9). Re-plan on join, leave and pin, with a new revision. **Gates:** a planner property test (no overlap, full cover); a plugin with any `Distribution` other than the DHT's is never assigned; the decoder fuzz target.
- **WK-6** (§19.4, §3). One versioned encoding for a `Results` batch (batch id, then per torrent: key and swarm hashes, the prepared row, the compressed file-tree blob, `torrent_extra`, parsed and classified fields, provenance, token, the worker's verdict and rule version, and the raw info dict minus `pieces` only when `archive_raw` is on, Q8) and one for `Counters` (rollup deltas keyed by metric, dim, key, hour). `pieces` is never encoded. Bounded decode: counts, lengths and total bytes capped before allocation, unknown versions refused, nothing half-used. **Gates:** the fuzz target; round-trip property tests; median ≤ 3 KB over a golden corpus of real-shaped torrents at defaults (`archive_raw` off), with the p95, and the median with `archive_raw` on, reported.
- **WK-7** (§19.4, owner §1.6.5). Build the fetch pool, prepare stage and `WorkerFunnel` from a `WorkerStages` builder that takes a `Preparer` built from dictionary bytes and id (`Preparer::from_dict`, which doesn't care where they came from: the store on the coordinator, WK-8's snapshot on a worker), a filter handle and a claim/report interface, not a `Store`; the coordinator's local path uses the same builder. Claims are batched (≤ 512 keys or 250 ms, §19.2). Outbound bytes queued to the coordinator are capped (default 8 MiB), so a slow link pauses fetching instead of growing memory (the session queue of 256 messages could otherwise hold 256 MiB). **Gates:** single-machine parity bench; the outbound cap holds under a stalled link.
- **WK-8** (§19.4, §19.6, §20). Implements Q1's answer. Recommended shape: the worker gets a versioned snapshot of exactly what the commit judges with (locked floor, CS-1 entries, signatures, switches, packs, your rules, classification rules), judges every prepared torrent before it's sent or spooled, and drops what's held (counted, never kept). The coordinator still re-judges every remote result. The coordinator also sends its current file-tree dictionary (the store's `file_dict`), versioned: every blob names its dictionary id, and the commit refuses an unknown or retired id. **Gates:** a blob under an unknown dictionary id is refused at commit; a blocked fixture prepared on a worker never reaches the wire or the spool; a stale snapshot is re-judged at commit; the decoder fuzz target.
- **WK-9** (§19.3, §19.4, §18.7). Decode `Results`; drop any record whose token isn't current for that worker (counted as stale); hand the rest to the writer's commit, which re-judges (§1). Outcomes end leases. Counters go into rollups with `dim = worker`. A claim denied as held elsewhere relays its peer hints to the holder in memory, never stored. Grants slow when the writer's queue passes its high-water mark (§19.5 backpressure), through WK-0's grant-admission hook. Remote leases are written to `fetch_queue` with the local ones. Results from an earlier epoch follow Q7's late-result rule. **Gates:** current-epoch stale-token results and outcomes are ignored; a late result never counts "harvested" again and the funnel still reconciles; nothing is counted twice; backpressure bounds the writer queue; hints never reach the store.
- **WK-10** (§19.1, §19.5, owner §1.6.5).
