## 1. Fixed constraints
- **One coordinator, workers dial out** (§19, owner §1.10). A worker has no database, no index and no UI, and can't query any of them (§19.6 "least data").
- **Exactly-once accounting** (§19.3): "harvested" is counted at grant, once per key across the fleet; the holder reports the terminal outcome once; a stale fencing token is ignored. Cohort conservation (§10.9.3) holds.
- **The coordinator's commit is authoritative** (§19.4): the blocklist and rule checks run again at commit for every remote result. `writer.rs` already re-judges any result whose worker isn't `WorkerId::LOCAL` (line ~1825). Workers never decide what's stored.
- **No profiles of people** (§18.7, §19.6): peer addresses leave a worker only as in-memory peer hints. Nothing about peers is stored or spooled.
- **Worker budgets:** "a worker uses ≤ 256 MB of RAM and sends about ≤ 3 KB per torrent" (owner §1.6.5); architecture §19.8 and §3 measure it as steady-state RSS at defaults and a median on the wire. The coordinator ingests ≥ 1,000 new verified torrents/s; grant latency p95 < 50 ms on a LAN.
- **The fetch pool's 200k cap doesn't fit a worker** (soak r3 verdict): 200,000 × ~690 B ≈ 132 MiB, half the budget on its own. The worker gets its own cap (§4.3 WK-10, Q5).
- **Single-machine parity** (§19.8): with no remote worker joined, behaviour and benchmarks match today's pipeline, and no cluster CA is opened or created (§19.6: "created on first use"). No crawler behaviour changes without remote workers, so the crawler rules (BEP 51 intervals, per-IP limits, §18 caps, switches default off) are untouched. **With workers, guardrails still hold per remote address:** workers behind one NAT and the coordinator share one public IP, so per-remote limits (2 connections per peer IP, BEP 51 intervals per node) are divided among them (WK-5), never multiplied (build-plan §0.6).
- **Migrations:** one migration PR at a time, in the §0.7 queue (`ext:migration-slot`); V14 (SRC-1) is merged and V15 is reserved for CR-3. The one worker migration takes the next free number when it reaches the slot (§3).
- **Security:** `/security-review` for everything that touches the cluster port, credentials, untrusted bytes, the spool or what a worker may hold (standards §7). The cluster crate's chaos and transport tests stay green (build-plan Track W).

## 3. Store and schema impact
**One migration in one slice (WK-12),** numbered by §0.7's rule: the next free number when it reaches the slot (V16 if CR-3 has taken V15 by then, else V15; the runner records it in `runner-state` `migration_order`). Opus, store owner only.

| Object | Shape | Why |
|---|---|---|
| `torrent_worker` | `(torrent_id INTEGER PRIMARY KEY REFERENCES torrents ON DELETE CASCADE, worker INTEGER NOT NULL)`, `STRICT`, a row only for torrents a **remote** worker prepared | Purge-by-worker and quarantine (§19.4, §19.7) need to know which torrents came from which worker. No row = the local worker, so single-machine installs write nothing (parity) |
| index `torrent_worker(worker)` | | Purge and per-worker counts |
| `snapshots.rs` `Plan::KNOWN_THROUGH` | to the new version | The snapshot purge (§2.21) already follows `torrents`; the table holds no names |

**No other table:**
- **Worker records, budgets, intensity and pins** live in `settings` under `cluster.` as V6-cluster1 does (versioned records, one transaction per operation).
- **Outstanding remote leases** persist in the existing `fetch_queue` (`info_hash`, `source`, `cohort`, `strategy`, `priority`, `attempts`, `flags`), as the local worker's do (§19.3). The holder isn't stored: a coordinator restart starts a new lease epoch, every old token goes stale, and the keys are re-granted (Q7 covers results spooled across it).
- **The worker dimension** is a new `dim` code in `rollup_hour`/`rollup_day` (§19.7), not a column.
- **The worker side has no database.** Its credentials file is V6-cluster1's; its spool is WK-11's own segment format (an on-disk format: Opus, fuzzed).

The key travels only in the snapshot header over mTLS, never in logs or `Debug` output; false-positive rate unchanged (property test). Snapshot = a versioned header (key, bits, hashes, capacity, count) and chunks ≤ 512 KiB with a sequence and total; deltas = batched inserts with the filter generation. A rebuild bumps the generation and sends a fresh snapshot; a worker keeps the old filter until the new one is complete (peak 2× the filter). Decoding is bounded and fuzzed (bytes come from the network, authenticated or not). Built so either Q6 answer fits: the snapshot header carries its own capacity and bits per hash, so the coordinator can send its own filter or a separate, count-sized worker filter that it rebuilds when full; above 64 MB the worker swaps in place. **Gates:** a worker never reports "not stored" for a key the coordinator stored before the snapshot it holds; out-of-order and missing chunks are refused; the fuzz target; the key never appears in logs or `Debug`; memory at 10M stored under Q6's answer (today's replicated filter: 25 MB, since `capacity_for` sizes it at 2× the stored count, and about 12.5 + 25 MB while a growth swap holds both copies).
