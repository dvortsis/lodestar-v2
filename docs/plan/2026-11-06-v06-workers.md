## 1. Fixed constraints
- **One coordinator, workers dial out** (§19, owner §1.10). A worker has no database, no index and no UI, and can't query any of them (§19.6 "least data").
- **Exactly-once accounting** (§19.3): "harvested" is counted at grant, once per key across the fleet; the holder reports the terminal outcome once; a stale fencing token is ignored. Cohort conservation (§10.9.3) holds.
- **The coordinator's commit is authoritative** (§19.4): the blocklist and rule checks run again at commit for every remote result. `writer.rs` already re-judges any result whose worker isn't `WorkerId::LOCAL` (line ~1825). Workers never decide what's stored.
- **No profiles of people** (§18.7, §19.6): peer addresses leave a worker only as in-memory peer hints. Nothing about peers is stored or spooled.
- **Worker budgets** (owner §1.6.5; architecture §3, §19.8): RSS ≤ 256 MB at defaults, ≤ 3 KB per torrent on the wire (median). The coordinator ingests ≥ 1,000 new verified torrents/s; grant latency p95 < 50 ms on a LAN.
- **The fetch pool's 200k cap doesn't fit a worker** (soak r3 verdict): 200,000 × ~690 B ≈ 132 MiB, half the budget on its own. The worker gets its own cap (§4.3 WK-10, Q5).
- **Single-machine parity** (§19.8): with no remote worker joined, behaviour and benchmarks match today's pipeline. No crawler behaviour changes without remote workers, so the crawler rules (BEP 51 intervals, per-IP limits, §18 caps, switches default off) are untouched.
- **Migrations:** one migration PR at a time, in the §0.7 queue (`ext:migration-slot`); V14 (SRC-1) is merged and V15 is reserved for CR-3. The one worker migration takes the next free number when it reaches the slot (§3).
- **Security:** `/security-review` for everything that touches the cluster port, credentials, untrusted bytes, the spool or what a worker may hold (standards §7). The cluster crate's chaos and transport tests stay green (build-plan Track W).

## 3. Store and schema impact
**One migration in one slice (WK-12),** numbered by §0.7's rule: the next free number when it reaches the slot (V16 if CR-3 has taken V15 by then, else V15; the runner records it in `runner-state` `migration_order`). Opus, store owner only.

| Object | Shape | Why |
|---|---|---|
| `torrent_worker` | `(torrent_id INTEGER PRIMARY KEY REFERENCES torrents ON DELETE CASCADE, worker INTEGER NOT NULL)`, `STRICT`, a row only for torrents a **remote** worker prepared | Purge-by-worker and quarantine (§19.4, §19.7) need to know which torrents came from which worker. No row = the local worker, so single-machine installs write nothing (parity) |
| index `torrent_worker(worker)` | | Purge and per-worker counts |
| `snapshots.rs` `Plan::KNOWN_THROUGH` | to the new version | The snapshot purge (§2.21) already follows `torrents`; the table holds no names |

**No other table:**
- **Worker records, budgets, intensity and pins** live in `settings` under `cluster.` as V6-cluster1 does (versioned records, one transaction per operation).
- **Outstanding remote leases** persist in the existing `fetch_queue` (`info_hash`, `source`, `cohort`, `strategy`, `priority`, `attempts`, `flags`), as the local worker's do (§19.3). The holder isn't stored: a coordinator restart starts a new lease epoch, every old token goes stale, and the keys are re-granted (Q7 covers results spooled across it).
- **The worker dimension** is a new `dim` code in `rollup_hour`/`rollup_day` (§19.7), not a column.
- **The worker side has no database.** Its credentials file is V6-cluster1's; its spool is WK-11's own segment format (an on-disk format: Opus, fuzzed).

### 4.3 What each slice must do (spec and gates)
- **WK-0** (§19.2, §19.3). Today a key can be leased in the pipeline's table and again in `ClusterServer`'s. Make `ClusterServer`'s `LeaseTable` the only one: the pipeline's `Coordinator` keeps the funnel accounting and calls the server for claims, outcomes, completions and restores, and the server calls back into it for "harvested" and re-grants. The local worker keeps direct calls (Q4). Add the inbound sink trait and `send`/`broadcast`. **Gates:** a property test that one key is never granted to two holders across local and remote claims; the funnel reconciles (harvested = Σ terminal + in flight) with a local and a fake remote worker; every existing cluster and pipeline test passes; the single-machine parity bench within noise.
- **WK-1** (§19.2, §19.6, §12). `[cluster]` config (listen address, default `0.0.0.0:8091` once allowed); the port isn't bound until workers are allowed (Q3). Open `Coordinator`, build `ClusterServer` with the store's `StoredKeys`, run `maintain` from the tick, and call `Coordinator::reseal` in the secrets-key rotation between `rotate` and `retire_old_keys` (V6-cluster2 hooks). Metrics: sessions, pre-auth refusals, leases, stale reports, PKI errors. **Gates:** a fresh install binds nothing; allowed, it binds and refuses an unauthenticated client; a rotation test that the PKI opens after reseal.
- **WK-2** (§19.6, §13). `lodestar worker --join <url> --token-file <path|->`, then `--data <dir>` runs from the saved credentials. Reconnect with capped exponential back-off and jitter; renew at half-life; on `Drain`, finish leases and report; on `Stop(Revoked)` or `Expired`, stop and say to join again. **Gates:** join, restart, renew; a revoked worker stops within one heartbeat; a reused or expired token fails with one message; the token never reaches logs, argv or the environment (Q2 may change the last).
- **WK-3** (§19.3, §7). Replace `RandomState` with positions derived from the info hash's bytes and a per-filter seed, so a copy answers the same on any machine; false-positive rate unchanged (property test). Snapshot = a versioned header (seed, bits, hashes, capacity, count) and chunks ≤ 512 KiB with a sequence and total; deltas = batched inserts with the filter generation. A rebuild bumps the generation and sends a fresh snapshot; a worker keeps the old filter until the new one is complete (peak 2× the filter). Decoding is bounded and fuzzed (bytes come from the network, authenticated or not). **Gates:** a worker never reports "not stored" for a key the coordinator stored before the snapshot it holds; out-of-order and missing chunks are refused; the fuzz target; memory at 10M hashes (12.5 MB, 25 MB during a swap).
- **WK-4** (§19.5, BEP 42, BEP 51). A `Shard { prefixes: start..end of 256, id_slots: u8 bitset }` in the DHT config. The target-prefix cursor walks only its range; `virtual_ids` uses only its slots. No shard is today's behaviour, byte for byte (the existing DHT tests pass unchanged). Per-node BEP 51 intervals and per-IP limits don't change. **Gates:** property tests that disjoint shards never target the same prefix in a pass and never mint the same BEP 42 prefix; the full-range shard equals no shard.
- **WK-5** (§19.5). `Assign` payload v1: revision, the DHT shard, budget and intensity, the worker pool cap (Q5), the dictionary and filter-snapshot versions. Placement v1: workers sharing an external IP split that IP's 8 id slots and the 256 target prefixes; workers on different IPs each get the full id slots and a share of target prefixes; the coordinator's own DHT counts as one member of its IP. Fetch and prepare run everywhere. Every source plugin is refused for workers (Q9). Re-plan on join, leave and pin, with a new revision. **Gates:** a planner property test (no overlap, full cover); a plugin with any `Distribution` other than the DHT's is never assigned; the decoder fuzz target.
- **WK-6** (§19.4, §3). One versioned encoding for a `Results` batch (batch id, then per torrent: key and swarm hashes, the prepared row, the compressed file-tree blob, `torrent_extra`, parsed and classified fields, provenance, token, the worker's verdict and rule version) and one for `Counters` (rollup deltas keyed by metric, dim, key, hour). `pieces` is never encoded. Bounded decode: counts, lengths and total bytes capped before allocation, unknown versions refused, nothing half-used. **Gates:** the fuzz target; round-trip property tests; median ≤ 3 KB over a golden corpus of real-shaped torrents (and the p95 reported).
- **WK-7** (§19.4, owner §1.6.5). Build the fetch pool, prepare stage and `WorkerFunnel` from a `WorkerStages` builder that takes a `Preparer` (from a shipped dictionary, `Preparer::from_dict`), a filter handle and a claim/report interface, not a `Store`; the coordinator's local path uses the same builder. Claims are batched (≤ 512 keys or 250 ms, §19.2). Outbound bytes queued to the coordinator are capped (default 8 MiB), so a slow link pauses fetching instead of growing memory (the session queue of 256 messages could otherwise hold 256 MiB). **Gates:** single-machine parity bench; the outbound cap holds under a stalled link.
- **WK-8** (§19.4, §19.6, §20). Implements Q1's answer. Recommended shape: the worker gets a versioned snapshot of exactly what the commit judges with (locked floor, CS-1 entries, signatures, switches, packs, your rules, classification rules), judges every prepared torrent before it's sent or spooled, and drops what's held (counted, never kept). The coordinator still re-judges every remote result. The dictionary travels the same way. **Gates:** a blocked fixture prepared on a worker never reaches the wire or the spool; a stale snapshot is re-judged at commit; the decoder fuzz target.
- **WK-9** (§19.3, §19.4, §18.7). Decode `Results`; drop any record whose token isn't current for that worker (counted as stale); hand the rest to the writer's commit, which re-judges (§1). Outcomes end leases. Counters go into rollups with `dim = worker`. A claim denied as held elsewhere relays its peer hints to the holder in memory, never stored. Grants slow when the writer's queue passes its high-water mark (§19.5 backpressure). Remote leases are written to `fetch_queue` with the local ones. Q7's rule for results from an earlier epoch. **Gates:** stale-token results and outcomes are ignored; nothing is counted twice; backpressure bounds the writer queue; hints never reach the store.
- **WK-10** (§19.1, §19.5, owner §1.6.5). The worker process: its DHT with the assigned shard, the pool with the worker cap (Q5), the WK-7 stages, claims through the session, the replicated have-filter in front of them, and `Assign` changes applied without a restart. Per-worker budget and intensity as §18.4's scheduler does locally. Heartbeat stats (claimed, fetched, processed, CPU, RSS, spool bytes). **Gates:** a worker against an in-process coordinator stores torrents end to end; the RSS budget breakdown in the decisions file, measured (Q6).
- **WK-11** (§19.6). While disconnected, results and outcomes go to a bounded spool: append-only segments with a versioned header, records checksummed, written atomically, at most 1 GB or 24 h (defaults); full means fetching pauses and the DHT keeps only routing. Replay on reconnect in order, idempotent by batch id and token; a segment is deleted once acknowledged. Reconcile lease counts on reconnect (V6-cluster2 "lease-count drift"). Spool records hold no peer addresses. **Gates:** replay twice = once; a torn final record is dropped, not half-used; the fuzz target; caps hold.
- **WK-12** (§19.4, §2.17, §2.21). The migration in §3, the commit write for remote workers, and `purge_by_worker` (in batches, with rollup reconciliation as other purges do). **Gates:** migration up from the previous version's fixtures; a previous build refuses the new version cleanly; the snapshot purge test; nothing written on a single-machine install.
- **WK-13** (§19.4). Sample 0.5% of each worker's results; another worker (or the coordinator) re-fetches the info dict and compares derived fields. A failed sample quarantines the worker: paused, flagged, and offered purge-by-worker as a `/jobs` job. **Gates:** a deliberately corrupted worker is caught and quarantined; a sampled key is never counted twice.
- **WK-14** (§19.6, §19.7, §10.10.7). `GET /workers` (from `ClusterServer::snapshot` plus settings), `POST /workers/tokens` (token shown once, never stored in clear or logged), `drain`, `resume`, `pause`, `revoke`, `purge`, and `PATCH` for budget, intensity and DHT pins. Admin only. Revoke and purge are Danger zone actions (§10.10.7). **Gates:** API tests per action; a revoked worker is gone within one heartbeat; a token isn't in any response but the create.
- **WK-15** (§19.7). The worker dimension on the Discover and Fetch stage queries; Marginal gain (Q12); a fleet summary ("3 workers · 4.2k/h") for the status pill.
- **WK-16** (§19.7, §10.10). Status as icon + text, the columns §19.7 lists, Add worker with the copyable commands (CLI, docker run, compose, Unraid, Windows), Drain, Pause, Revoke and Purge (Danger zone), budget and intensity, DHT pins.
- **WK-17** (§19.7, §10.9). Per-worker breakdowns on the Discover and Fetch pages, the Marginal gain view, and the pill.
- **WK-18** (§19.6). A compose `worker` service, the Unraid template (token per Q2, the spool path, the DHT port), the WiX option. The template's "Requires v0.6" labelling is E-M6's; the runner orders the two.
- **WK-19** (§19, owner §2.14). What a worker adds and what it doesn't (§19.1 "honest limits"), the safe setup (only the cluster port, ideally over Tailscale or WireGuard; workers on different networks for crawl gains), joining, draining, revoking, quarantine and purge, with screenshots.
- **WK-20** (§19.8). A coordinator and N workers in one test process on the in-process DHT network, with injectors for worker kills, partitions, coordinator restarts and clock skew, and a funnel reconciler. No fixed sleeps.
- **WK-G** (§19.8). Every §19.8 test on WK-20's harness, the e2e spec for Settings → Workers, and the four benchmarks: coordinator ingest ≥ 1,000/s (commit + index), worker RSS ≤ 256 MB (Q6), results ≤ 3 KB median, grant latency p95 < 50 ms. **Every slice:** the CLAUDE.md pre-push checks, a decisions file, no fixed sleeps (owner §2.24), no live network in tests, and `crates/cluster`'s tests green.
