# v0.6 Sources: the sliced plan (E-v06-sources)

Planning slice P-v06-sources-plan, 2026-11-01, for the build runner. It turns build-plan P4 "Sources" into `SRC-*` slices (`runner/slices.yaml`). Docs only. The rule packs and ThePornDB/StashDB enrichment (also under P4 "Filters") are left to their own plan. Workers and the companion manager are separate epics (`E-v06-workers`, `E-v06-companions`).

**Authority:** `docs/owner-decisions.md` §1.8, §1.9, §1b.6, §2.16–§2.19, §2.21, §2.25, §2.26; architecture §5, §7, §10.10.8, §18 and §20; build-plan §0, §1.3 and P4. Where they're silent the plan says so (marked **silent**) and puts the question in §5. It decides nothing that belongs to the owner.

## 1. Fixed constraints
- **Every source is off by default, metadata only, and passes child-safety filtering.** Consent levels apply to risky tiers; private results stay local; no profiles of people (owner §1.9.7; arch §18.1, §18.7). Only the Mainline DHT is on by default (§18.1).
- **Each source is a compiled-in plugin behind a cargo feature** that can be switched on and off (owner §1.9.5; §18.1).
- **The HTTP client is reqwest + rustls** (owner §1b.6). User-configured URLs go through the SSRF guard (`crates/integrations/src/net.rs`, §12).
- **The CSAM hash and pattern blocklist runs on every source before storage and can't be disabled** (§18.7, §20.1, §20.5). That covers claims and unverified items, not only verified torrents.
- **Deletion guarantees cover new name-bearing tables.** Sealed names never outlive §2.16's 30 days, deleted rows are zeroed (§2.17), and migration snapshots get the same purge (§2.21). Claims and unverified items carry names, so V15 extends the snapshot purge to them.
- **Migrations:** V12 → V13 → V14 is fixed and written only by an Opus slice that owns the store schema (`docs/decisions/2026-10-30-master-plan.md`). V13 (IMP-1) is on `main`. V14 is reserved for CR-3 eligibility. The release branch `release/v0.5.1` is cut, so the rule that V13+ waits for it (build-plan §0.2 lane I) is met.
- **CR-3 isn't scheduled.** It has no entry in `runner/slices.yaml`, and build-plan §0.6 puts "CR-3 recovery" after the 50M import-scale gate, whose numbers go to the owner. If Sources waited for V14, the whole critical path would wait on that gate. So SRC-1 takes **the next free migration number** when it's ready: V14 if CR-3 hasn't claimed it, and CR-3 then takes the next one (§5 Q12).
- **Silent or conflicting on timing:** build-plan §0.6 lists "then the other source families" after the import-scale gate, while P4 says source work "continues in parallel; only the tag waits". The runner's launch brief follows P4. The plan names the conflict and doesn't resolve it (§5 Q12).
- **Search `SCHEMA_VERSION`:** one bump per milestone. The v0.6 `network`/`source`/`verified` fields ride the **M7** bump (build-plan §1.3).
- **Slots:** at most four helper slices at a time in this phase (owner §2.25; build-plan §0.2). v0.6 epics are seventh in the priority ladder. Only the v0.6 *tag* waits on the crawler gate (build-plan §0.6, P4).
- **Crawler-gate isolation:** the gate runs on a fresh data directory with no imports and the Balanced preset (build-plan §0.6). All sources are off by default, so the gate is unaffected. Anything that touches the shared fetch pool or `fetch_queue` still ships behind a switch, default off, until the crawler acceptance soak ends (§3).

## 3. Store and schema impact

**One migration in one slice (SRC-1),** numbered by §1's rule (V14 or V15, written "V15" below). Opus, store owner only.

**Reconciling with V13:** `import_candidates` is already an unverified tier for imports. The recommendation (§5 Q16) is to keep it import-only, since it's job-scoped and cascades with its job, and to add `unverified_items` for source discoveries, which carry claims and `id_seq` ids. Both use **one promotion function** in the writer. SRC-1 copies V13's pattern: triggers on `tombstones`, quarantine and `cs_hashes` delete matching unverified rows and journal them into `snapshot_deletions`. It adds **no trigger on `torrents` inserts**: IMP-1 measured V13's at up to four index probes per insert on the crawler's hot path. Promotion runs in writer code.

| Object | Shape (arch §) | Notes |
|---|---|---|
| `unverified_items` | `(id, network, key, source_id, claims BLOB, first_at, last_at)`, `UNIQUE(network, key)` (§18.5) | Ids come from `id_seq` and are kept on promotion (§18.5). The table holds names, so the snapshot purge must cover it (§2.21) |
| `torrent_claims` | `(torrent_id, source_id, data BLOB)`, PK `(torrent_id, source_id)`, zstd (§18.5) | Only for sources that supply claims. It cascades on torrent delete and is covered by the snapshot purge |
| `source_state` | `(source_id, key TEXT, value BLOB)` | The plugin KV store (§18.1 sketch: cursors, `since`, ETags). **Silent** on where it lives; a table is proposed so it's transactional with emitted items |
| claim encoding | a versioned, bounded binary encoding inside the zstd blob | An on-disk format: Opus only, with a fuzzed decoder |
| `snapshots.rs` `Plan::KNOWN_THROUGH` | to the new version | The purge drops claims and unverified rows whose hash the live store deleted or holds |

**No change to crawler tables, the index or cache memory in V15:**
- `torrents` gains nothing: `sources`/`first_source` exist since V2.
- Verification of unverified keys reuses `fetch_queue` (`source`, `priority`, `flags`) at Low priority (§18.4). It's behind `sources.verify_unverified` (default off) until the crawler acceptance soak closes.
- **Hot columns:** unverified ids take slots from `id_seq`, so the hot arrays (sized by the highest id, §18.5) grow with them. Unverified items get no hot-column writes, but the id range still grows. **Flagged:** SRC-2 measures the RSS delta at 1M unverified ids and reports it to the runner before merge.
- **Index:** unverified documents enter Tantivy only after the M7 `SCHEMA_VERSION` bump (SRC-3). Until then they're stored and counted but not searchable.
- **Caps:** bare dead hashes with no claims are kept only as a capped verification queue, not as rows (§18.5). SRC-2 sets the cap (§5 Q11).

**Merge rule:** one migration PR at a time (`ext:migration-slot`). No source migration merges before the release branch is cut (met).

### 4.2 What each slice must do (spec and gates)
- **SRC-0** (§18.1, §18.4, §18.9). Extend `Found` into a discovery event with optional claims and provenance (external ref, time, confidence). Add manifest fields: politeness caps (min poll interval, max requests per host per second, max full scrapes per day), a JSON-schema config, `distribution` (§18.1, §19.5), and schedule windows. Add a `PluginState` trait (the name avoids `lodestar_store::SourceState`), a per-host token-bucket limiter with exponential back-off and a "blocked by source" state, and `testing::FakeCtx` with a fixture replayer (recorded HTTP exchanges, no network). **Gates:** property tests that caps can't be exceeded and back-off is bounded; a cancellation test (a plugin stops within 1 s of shutdown); the DHT plugin keeps passing unchanged.
- **SRC-1** (§18.5, §7, owner §2.16, §2.17, §2.21). The migration as in §3, with V13's trigger pattern and no `torrents` insert trigger. Store APIs: `put_unverified`, `promote` (one transaction; keeps the id; moves claims), `put_claims`, `source_state` get/set, and `purge_source` (unique items and all claims; clears the bit elsewhere, §18.1). **Gates:** migration up from V14 fixtures; a v0.5.1-shaped build refuses V15 cleanly (as in IMP-1); a snapshot purge test for claims and unverified names; the claim decoder fuzz target; the rollup reconciliation after purge (§18.9).
- **SRC-2** (§18.5, §20.1, §20.5). Every claim and unverified item passes the filter engine **before** storage, including the locked floor, as the importer path does. A blocklisted fixture hash or name is dropped and counted, never stored. Verification fetches enter the shared pool at Low priority; user-interest fetches jump the queue (§18.4). Promotion runs when metadata arrives, and the "claim mismatch" junk reason applies when files contradict the verified list. `private_source` keys never enter DHT `get_peers`, PEX or public announce (§18.7); private keys wait for their own source (§18.4 CR-0 contract). **Gates:** the safety injection test; a property test that promotion keeps the id; the RSS measurement in §3.
- **SRC-3** (§18.6, §8). Adds the fields to the M7 bump (build-plan §1.3), with `verified:no` hidden unless asked for. **Gates:** golden query tests; the query-language fuzz target still passes.
- **SRC-4** (§18.7). The server refuses to enable a source until its class's condition holds: None needs a toggle; External needs the endpoint list acknowledged; Account needs credentials stored; Restricted and Overlay need the consent screen acknowledged. An ack is bound to the manifest's consent-text version, and a new version asks again. Credentials are sealed with `SecretStore` (own `context` per source), never returned, logged or exported, and dropped on purge. **First registration is atomic:** today `Store::register_source` commits a new plugin as Enabled and `crates/pipeline/src/lib.rs` disables it in a second write, so a crash in between leaves a consent-gated source on. SRC-4 registers new plugins as disabled in one write. **Gates:** a crash-between-writes test; an API test that every class can't be bypassed (§18.9); a settings-export test that no credential leaves; `/security-review`.
- **SRC-5** (§18.4, §18.7, §5). One factory gives each plugin an HTTP client bound to its egress: direct, an interface, or SOCKS5. The per-plugin kill-switch refuses to send when the egress isn't up. It composes with `GuardedClient`'s SSRF guard for user-entered URLs; built-in public endpoints use the egress client with a public-only policy. **Gates:** tests with a fake interface and a SOCKS stub; kill-switch refusal; redirect re-check.
- **SRC-6** (§18.2, §18.9). A Torznab/Newznab parser on `quick-xml`, streaming: entity expansion off, DTDs refused, and caps on depth, items, attribute and text length, and total bytes. It yields info hash (from `torznab:attr infohash` or a magnet), title, size, category, files, seeders/leechers, indexer flags and publish date. Malformed items are skipped and counted, never half-used. **Gates:** a fuzz target; property tests (never panics, never exceeds caps); golden fixtures from Prowlarr and Jackett.
- **SRC-7** (§18.2 rank 1, §18.7). Lists indexers through Prowlarr's or Jackett's API, polls each one's RSS within its caps (one agent = one indexer queried in parallel, §18.4), and emits keys with claims. An indexer the manager marks private makes its finds `private_source`. Their metadata follows §5 Q15: claims only by default, with no automatic `.torrent` download through a private indexer. Its README is the contract-test pattern every later plugin copies: the fixture layout, `FakeCtx`, the cancellation, caps and blocklist tests. **Gates:** the recorded-fixture contract tests; a test that private finds never reach Torznab output or a public lookup.
- **SRC-8 / SRC-9** (§18.2). The same parser bounds as SRC-6. **Gates:** fuzz, property and golden tests.
- **SRC-10a–d.** Glue only: manifest (endpoints, consent class per §18.7, caps), config schema, mapping to claims, fixtures, and the SRC-7 contract tests. Nyaa polls at most every 5 minutes (§18.1). AnimeTosho's file lists and media info become claims (§18.2 rank 13).
- **SRC-11** (§18.2 rank 17, §18.7). Lists torrents and exports `.torrent` bytes. Bytes go through `crates/metainfo` (fuzzed). Client JSON is untrusted, so it has bounded parsing and a fuzz target. Every find is `private_source`. Client credentials reuse the existing settings secrets.
- **SRC-11b.** Inbound webhooks: a per-integration token compared in constant time, size-capped bodies, and no unauthenticated route. **Silent** in §18 on the auth design (§5 Q9).
- **SRC-12** (§18.1, §18.2 rank 16). A full scrape omits `info_hash`. The reply is a bencoded dict that can be many megabytes, so it's parsed streaming with a byte cap and an entry cap, and it emits keys in batches. It runs at most once per tracker per day, inside a schedule window (01:00–07:00 default, §18.4), and never on a tracker whose torrents are `private_source`. **Gates:** a fuzz target; a 50 MB fixture with flat memory; the cap test.
- **SRC-13** (§18.2 enrichment #3, §18.7). Fetches `.torrent` by hash from the configured caches through the plugin egress. Only an info dict whose SHA-1 matches the key is used (§5 Q8). Never queried for `private_source` hashes, because a lookup leaks the hash (§18.7). External consent.
- **SRC-14** (§18.8, §10.10.8). `GET /sources` gains manifest, endpoints, consent state, health, 24 h yield and unique finds. `PATCH` accepts `egress`, `schedule` and `agents`. Purge runs as a `/jobs` job with progress (§9). It's a §10.10.7 Danger zone action: a confirmation dialog with the exact count and size, the action named on the button, focus on Cancel, and no password.
- **SRC-15a/b** (§18.8, §10.10, §10.10.7, §10.14). Generated from the API. The consent dialogs use the class texts (§5 Q1). Status shows icon + text. Purge is a §10.10.7 Danger zone action.
- **SRC-16** (§18.8, §9). Reads `/jobs`, with import jobs included once IMP's adapter registers them.
- **SRC-17** (§18.6, §18.8). "Found by: DHT · Nyaa", claim-vs-verified differences, and the Unverified badge.
- **SRC-G** (§18.9). A blocklisted hash injected through every plugin kind is dropped; `private_source` never appears in Torznab, Stremio or export output or a public lookup; unverified items are hidden by default; consent can't be bypassed; the no-profiles schema and log scan; and the §3 overhead benchmark with every v0.6 source on.

**Every slice:** the CLAUDE.md pre-push checks, a decisions file, no fixed sleeps (owner §2.24), and no live network in tests (fixtures only).
