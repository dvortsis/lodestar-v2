## 1. Summary

- **Priorities, in order:** (1) a reliable 1.0, (2) performance better than bitmagnet, measured side by side on the same host and VPN (crawl rate at least 100/min on the way there), (3) low cost and a short calendar, (4) politeness, after 1.0.
- **The biggest time savers are scope and testing design, not code:**
  1. **Freeze 1.0 scope** to what is built or nearly built. Move unstarted v0.7 and all of v0.8 to 1.1 (about 30 slices).
  2. **Test the crawler top-down:** start from a loose, bitmagnet-like profile with every efficiency change on. If it clears 100/min, that is the 1.0 crawler. Attribution and politeness tuning move after 1.0.
  3. **Use the new host for runs of record, with parallel arms on separate VPN exits,** instead of serial ABBA segments on one instance. Cloud becomes optional screening.
  4. **Combine 24 h runs:** one 24 h run on the release candidate serves the crawler re-measure and the Linux memory soak.
- **Kept in full (this is what makes 1.0 "solid"):** the security gate (eight reviews, Track Q's blocking and important findings), the chaos gate, the memory soaks (Linux and Windows), full CI on the RC, the design gate's blocking findings, content-safety rules, and VPN leak protection for every test crawl.
- **Calendar (estimate):** about **5–6 weeks** to v1.0.0 if the loose profile clears 100/min in its first runs; **7–9 weeks** if the crawler needs another round of lookup or fetch work. The crawler is the critical path either way. **Beating bitmagnet's crawl rate as a 1.0 gate** (§4.8, D13 option A) adds an unknown amount: bitmagnet's 317.8/min is about 26× today's 12.3, against 8× for 100/min. The other comparisons in §4.8 (search speed, storage, memory) are where Lodestar's design should already win, but none is measured side by side yet.
- **Cost:** Claude session time is the largest cost, then cloud. Levers are in §6.

## 4. The crawler: maximum throughput, fastest proof

### 4.1 The loose profile (one new slice, then settings)
Build once, behind switches, off by default until the gate run:
1. **Re-sample productive nodes sooner** (new switch, X-resample-fast): when a BEP 51 reply had novel hashes, sample that node again after 60 s whatever interval it advertised, as bitmagnet does; nodes with no novelty keep their interval. Breaks BEP 51's interval rule (owner instruction 1 allows it). The total packet budget doesn't rise; it moves to productive nodes.
2. **Hint-first with a wider per-IP guard:** CR-HINT-FIRST on, the hinted-send guard raised from one per IP per minute to cover one responder's whole sample (~20).
3. **Every efficiency switch on:** ADM, the sampler split with X-split-resume-gate, CR-LOOKUP-END, CR-1c, CR-SOFT-TIMEOUT, and the uTP first-window fix (#1054) where it has a switch.
4. **Throttle telemetry:** per-node reply rate over time, so a fall in replies from nodes we re-ask often is visible (§5 uses it).

Plus one setting arm that needs no code: **the Aggressive preset** (1,000 packets/s and 1,000 fetch sockets, against Balanced's 200/s and 400). It has never been measured live.

### 4.2 Test design: parallel arms on separate VPN exits (needs §7 D3)
- On `lodestar-host`, run each arm in its own Lodestar + gluetun pair, each gluetun on a different PIA server (a different exit IP).
- **Paired and swapped:** day 1 arm A on exit 1 and arm B on exit 2; day 2 swapped. The swap cancels exit differences, as the cloud's paired-instance design does (r17).
- **24 h blocks,** so every number has the gate's shape (24 h mean, worst hour, p95 latency).
- **Bitmagnet runs beside them on its own exit,** with its harvest rate recorded (it re-calibrates the new host; CR-SPEC requires a comparator re-run after a host change).
- **Capacity:** with 4 vCPU and 16 GB, about three Lodestar arms plus bitmagnet at once (estimate). Raising the VM to 8 vCPU and 32 GB, if the Unraid host has the cores, allows five or six.
- **Host-safety rules simplify:** the VM's disks are on the `ssd_apps` pool, so mover runs and parity checks don't touch them. Proposed: those no longer invalidate a VM segment (a CR-SPEC rule change, §7 D3).
- **Cloud (AWS, $295 cap)** becomes optional: a second site for a replicate, or screens while the host is full.

### 4.3 The sequence

| Days (estimate) | Run | Decides |
|---|---|---|
| 0–2 | Build X-resample-fast and the guard setting (one Opus slice). Meanwhile: bitmagnet comparator + an A/A pair of base, 24 h | The new host's calibration and noise floor |
| 2–4 | **Round 1:** base, loose profile, loose + Aggressive; 24 h, then swap exits, 24 h | Does the loose profile clear 100/min? Which preset? |
| 4–6 | **If yes:** CR-COMB acceptance, 24 h, the winner as default → **G-v06-crawler** | The gate |
| 4–14 | **If no:** read CR-LEDGER on the loose arm (slot hold time, queries per lookup, time to first values, fetch success) and build the fix for the largest loss, then round 2 | The next lever |

**What counts:** the gate is unchanged: 24 h mean ≥100/min, no hour under 70, p95 discovery-to-searchable ≤10 min, on the experiment host. Memory is read from the same runs (anonymous-memory slope), so a profile that wins on rate but breaks the 2.0 MiB/h bar is caught before the RC.

### 4.4 Imports on the same host
- The 1M and 10M pilots need ~362 GiB for the bitmagnet restore plus the Lodestar index; the 1 TB data disk holds them.
- They compete with crawler arms for CPU and disk, which would bias rate measurements. **Run them in a second VM** (`lodestar-import`, its own cores) if the Unraid host has spare cores, or in the gaps between crawler rounds.
- **50M:** see §7 D5.

### 4.5 Beyond 100/min
- After the gate, keep the same harness running in 1.x: tuning rounds aimed at bitmagnet's 318/min, and the workers' multi-IP route to the 1,000/min stretch.
- Not a 1.0 blocker.

### 4.6 VPN for users (owner instruction 3)
- **X-vpn-bind** (Opus, Linux and Windows): an optional setting "Crawl only through this network interface" (Any by default, or a named interface such as `wg0`/`tun0`). DHT and fetch sockets bind to it; if it disappears, crawling pauses with a "VPN down" status and never falls back to the normal connection. One leak guard that works with any VPN: system-wide, another container, or gluetun.
- **Guide §3.3** rewritten as "Use a VPN (optional)" with three routes and a leak check for each.
- Estimate: a few hundred lines with tests.

### 4.7 Test-crawl VPN rule
Every test crawl, on any host or cloud, runs inside gluetun (WireGuard) with the post-rules, and starts only after `leak-test.sh` passes. Unchanged from today; recorded here because the owner restated it.

### 4.8 Better than bitmagnet (owner instruction 5)

**Measured side by side, not against an old number.** bitmagnet's 317.8/min came from the old host, on a different day. The comparison that counts is a paired one: bitmagnet and Lodestar on `lodestar-host`, same hours, each on its own VPN exit, swapped the next day (the §4.2 design). The owner's own earlier rule already asks for "final parity ... against a pinned bitmagnet run on the same host" (`docs/owner-decisions.md` §2.25).

**The scorecard** (one node each, defaults except where named):

| Measure | How | Today |
|---|---|---|
| **Crawl rate:** new verified torrents per minute, 24 h | Lodestar's `metadata_new_verified_total`; bitmagnet's `torrents` row count (CR-SPEC 5.4) | 12.3 against 317.8 (different days); unmeasured side by side |
| Worst hour | Same counters, hourly | — |
| Discovery to searchable, p95 | Lodestar's funnel; bitmagnet's `created_at` to its search index | — |
| Memory and CPU at that rate | Process RSS and CPU seconds per stored torrent | — |
| Disk per torrent | Store + index size ÷ torrents | Lodestar target ~2.3 KB all-in; bitmagnet unmeasured on the same set |
| Search latency, p95 | The same query set against both, same corpus (the bitmagnet import gives Lodestar the same torrents) | — |

**The owner chose B (2026-11-26, §7 D13):** 100/min stays the 1.0 crawl gate; every other row of the scorecard must be better than bitmagnet at 1.0 (a new 1.0 gate, G-v1-vs-bitmagnet, run on the RC); crawl-rate parity is the 1.1 target. The two forms that were offered:
- **A. Crawl rate is a 1.0 gate:** Lodestar's 24 h mean ≥ bitmagnet's over the same paired days, plus no worse on the other rows. The surest "better than bitmagnet", and the slowest: the crawl-rate gap is the largest risk in this plan.
- **B. 100/min stays the 1.0 crawl gate; bitmagnet parity on crawl rate is the 1.1 target;** the other rows must already be better at 1.0. Faster to ship, and it still shows the rebuild beating bitmagnet where Lodestar's design is meant to.

**Either way, the crawler lane changes like this:**
- Round 1 includes the Aggressive preset (1,000 packets/s, 1,000 sockets) as a full arm, not a side test.
- The rounds continue past 100/min until the target is met, using CR-LEDGER to pick each next fix. Candidates, in the order the ledger is expected to rank them (author's estimate): lookup cost (fewer queries, earlier ends), fetch success per peer (more peers tried per hash, shorter per-peer deadlines), sampler coverage (more BEP 51 nodes sampled per minute), and the packet budget.
- Bitmagnet's harvest rate is recorded beside ours, so the comparison separates "hears about fewer torrents" from "stores fewer of what it hears".

## 5. Politeness, after 1.0 (release 1.1)

**Goal:** keep throughput; be as polite as possible within it.

1. **Measure each loosened rule's cost** from the shipped profile, one rule at a time, in the same parallel-arm harness: re-sample delay at 60 s, 5 min, 15 min and "honour the interval"; the per-IP hint guard at several levels; the preset's packet rate.
2. **Non-inferiority test:** a politer setting ships as the default only if its 24 h rate is within a set margin of the current default (proposed: no worse than 3%, with the lower bound of the estimate above −5%). The margin is the owner's to set (§7 D9).
3. **Adaptive politeness:** use the throttle telemetry (§4.1 item 4). Re-ask a node sooner only while it keeps returning new hashes and its reply rate holds; back off when its replies fall. This can be politer and faster at once, because throttled nodes waste budget.
4. **Bound the load per node and per network:** caps on queries per node per minute, so no single node sees bitmagnet-level pressure from us even when it is productive.
5. **Publish what Lodestar does:** a short page in the guide stating its DHT behaviour and limits, and a "polite" choice in Settings for users who want strict BEP 51 compliance at some cost in speed.
6. **Then the full politeness audit** (the part of G-v1-audits deferred from 1.0) as a 1.1 gate.

**Not done, at any stage:** fake node identities (Sybil tricks), which damage other people's routing tables; and anything that loosens content-safety or privacy rules (private hashes never reach `get_peers`, the blocklist, the VPN leak protection).

### 6.2 Cost levers
- **Sessions are the largest cost.** Proposed: 4 build sessions + 2 test sessions (down from 4 + "as many as needed"), filled only when ready work fits.
- **Models per policy:** Opus for core and security work and every review; Sonnet for patterned work (packaging, docs, CI, UI per §10); Haiku for mechanical edits.
- **One fresh reviewer per PR,** not several; reviewers get the diff and the brief, not the whole history.
- **Fewer CI runs:** one push per round of fixes; the landing lane for PRs that keep needing `main`; no `main` merges while CI runs.
- **Stop polish that isn't gated:** Track U items that aren't blocking design findings wait for 1.1.
- **Host over cloud:** runs of record on `lodestar-host` (no per-hour cost). AWS only for optional replicates, within the $295 cap.
- **Combine runs:** the RC's one 24 h run serves two gates (§6.1 week 5); the comparator day doubles as the host calibration.

## 8. Risks

| The loose profile still falls short of 100/min | Round 1 under ~60/min | CR-LEDGER names the loss; build the fix for it; consider the Aggressive preset and more fetch time per peer |
