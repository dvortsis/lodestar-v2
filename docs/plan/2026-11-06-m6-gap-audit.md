# M6 packaging: the gap audit and its slices (E-M6)

Planning slice P-m6-audit, 2026-11-06, for the build runner. It audits build-plan P3 and architecture §14 (M6) against the code on `main` at `63a2c6df`, item by item, and turns what's missing into `PK-*` slices, the way `docs/plan/2026-11-01-v06-sources.md` and `docs/plan/2026-11-04-v06-rulepacks.md` sliced their epics. Docs only. Choices are in `docs/decisions/2026-11-06-P-m6-audit.md`.

**Authority:** `docs/owner-decisions.md` §1.7.1 (Docker, Unraid, Windows), §2.14 (user docs), §2.19, §2.23 (unsigned Windows builds), §2.26, §2.36 and §2.41 (slots), §2.37 (the Unraid CA submission after 1.0); architecture §10.9.2, §10.10.6, §11, §12, §12.2, §14 (M6); build-plan §0.1, §0.2 Track M6, P3. Where they're silent the plan says so and puts the question in §5. It decides nothing that belongs to the owner.

## 1. Fixed constraints
- **M6's exit (§14):** "Clean install → crawling → search on all three targets in CI/smoke tests", for Docker multi-arch, the Unraid template, the Windows MSI and service, and the first-run wizard.
- **Building waits for the v0.5.1 soak verdict** (r5; its baseline ends 2026-11-06T13:12Z). E-M6 depends on `ext:v051-soak-verdict`, so every root slice below does too.
- **Slots:** 4 in total from 2026-11-06T00:00Z (owner §2.41). M6 is rung 4 of the build-plan §0.2 ladder; rungs 1–3 (v0.5.1, crawler evidence, the Sources path) take free slots first. The waves in §6 are upper bounds.
- **Windows builds ship unsigned** (§2.23). The update engine trusts only the Ed25519-signed manifest and its SHA-256 and size pins, and checks Authenticode only when an artifact carries a signature.
- **The Unraid Community Apps submission is the owner's, after 1.0** (§2.37). It isn't part of M6's exit. A winget submission is the same kind of owner action (Q6).
- **Release keys stay in their GitHub environments** (owner §2.21, architecture §12.2): the release key in `release` (`v*` tags only), the nightly key in `nightly` (main only; the environment exists and `release.yml:543` already uses it for nightly Windows builds, but the nightly update-signing key isn't created yet: build-plan §0.3 item 3), the freshness key in `freshness`. Any workflow that writes the `update-manifest` release joins the concurrency group `update-manifest` with `cancel-in-progress: false` (`docs/decisions/2026-10-30-X-freshness-hardening.md`).
- **`.github/workflows/*` has one owner at a time** (build-plan §1.3), so the two slices that edit `release.yml` are chained.
- **No migration, no search `SCHEMA_VERSION` bump.** Nothing here changes the store or the index format.
- **The manifest format is fixed at 1** (`crates/update/src/doc.rs`, `crates/update/README.md:78-82`). It already has the `x86_64-pc-windows-msvc` target and the `msi` and `portable` kinds. Every struct is `deny_unknown_fields`, so any new target, kind or field needs a new format that every deployed engine refuses. Publishing never changes the format. Docker has no image kind: containers update through the musl binary overlay (§12.2).
- **The Windows service runs as its own virtual account,** `NT SERVICE\Lodestar`, stripped to two privileges (`docs/decisions/2026-10-22-P-release.md`). Anything it starts inherits that account, which can't install a per-machine MSI or change its own service's start mode. Giving any process more rights is the owner's (Q13).
- **The v0.5.1 guide refresh exists on `release/v0.5.1`** (D-v051, #201): the first-hours note, the status-pill rows and a troubleshooting row. D-v051-main brings only `docs/releases/**` and the root README to `main`, so `docs/user/**` still has to be ported (PK-guide-1).
- **The workspace forbids `unsafe`.** Windows-only measurements use a safe crate already in the lock, or stay unknown (Q9).
- **User docs follow the `user-docs` skill** (`github-docs` for `docs/user/`) and owner §2.14: plain, safe choices first, screenshots or illustrations where they help.

## 3. Store and contract impact
No migration and no search schema bump. New API surface, all additive: two `InsightsException.kind` values (PK-exc), possibly a `RestartMethod` value for Windows (PK-win-restart), and the end of `unavailable: "windows_helper"` (PK-win-upd-1). `web/src/lib/api/openapi.json` and `schema.d.ts` are regenerated by whichever of these merges later, never merged by hand. **The signed manifest format doesn't change:** PK-manifest publishes format 1 as it stands, in the `<channel>.json` envelope `freshness.yml` reads and re-signs. A new target or kind would need format 2, which every v0.5.x engine refuses, so none is planned.

**17 slices, about 9,250 lines; no migration.** Every slice is under 1,500 lines; the largest is PK-win-upd-2 at ~1,000. The Windows updater is split four ways (check and notify; MSI install; MSI rollback; portable) because each is a separate failure surface that needs its own review, and together they'd be ~3,450 lines. Only the MSI install and rollback wait for the owner's answer to Q13: checking runs in the service with no extra rights, and the portable build runs as the user who unpacked it, so neither needs the helper.

**New dependencies, approved per slice in its brief** (standards §2): none expected. PK-win-restart measures free space with `fs4` (already in the lock through tantivy); Windows memory stays unknown unless a safe crate already in the lock reports it (Q9).

### 4.3 What each slice must do (spec and gates)
- **PK-cli.** `get` prints a field's saved value, its default and its source (environment, file, saved, default); a secret prints only "set" or "not set". `set` validates through the settings registry exactly as `PATCH /settings` does and refuses a secret field (no secret on argv), any field with `x-danger: security`, turning on any adult field (`content.show_adult` and the fields behind `confirm_adult`), and turning on any `x-danger: privacy` field (Q2). It adds no CLI confirmation path. `reset <field>` and `reset --all` clear saved values only, never `config.toml` or the environment (§10.10.6). All three run under `privdrop::Scope::DataDir` like the other store commands (`main.rs:80`), since the image starts as root and a root-owned WAL or SHM file would break the server. `set` or `reset` of `network.http_bind` also settles a pending `system.keep_or_revert.http_bind` record (`system/address.rs:12,84`), so the timer can't revert the operator's recovery at the next start. All three refuse while `serve` holds the store lock (`cli/lock.rs`) or while `rollback.json` exists (§12.2). Exit codes follow `cli/mod.rs` (`Refused` vs `Failed`). `lodestar worker …` prints that worker mode arrives in v0.6 with a pointer to the guide and exits 2 (Q4). Tests: every registered section through `get`; a `set` then `get` round-trip; a running server refused; `rollback.json` refused; a secret never printed; adult and privacy opt-ins refused; files written as the data folder's owner; a pending keep-or-revert record settled.
- **PK-exc.** `data_filesystem` when `fsdetect::detect(data_dir).is_risky()`, with the fix "move the data folder to a pool path" and a link to the guide; `ephemeral_ports` on Windows when `ports.rs`'s threshold trips, with the `netsh int ipv4 set dynamicport` remedy (§11). Both are re-checked at most hourly, never per request (mount-table reads are cheap but not free). The port result comes from a function in `ports.rs`; `windows/mod.rs` isn't edited, and the `ephemeral_port_pressure` KPI stays `None`. Linux tests feed `fsdetect`'s parser a `fuse.shfs` mount table; the Windows threshold is a plain function, tested on every OS.
- **PK-ui.** The storage step shows `/system`'s `filesystem_warning` with the safe alternative; the How step and the Done step say the first hours are slow because sampling waits about six hours after every start, and that safe restart skips the wait after later clean restarts (Q12). Exceptions render the two new kinds with icon, text and fix (§10.9.2). Tokens only; message keys in `en` and `zh`; tests for both kinds and both wizard states.
- **PK-win-restart.** As a service: Restart now stops gracefully and exits with a dedicated service-specific code, so the SCM's recovery action starts it again (§10.10.6, B2c:49; Q10). The SCM doesn't expose its failure count, and each Restart now uses one of the two daily recoveries (`main.wxs:114-116`), so Lodestar keeps its own conservative count in the data folder: every Restart now and every start after an unclean stop in the last 24 h. Restart now is offered only while that count is 0, so a crash always has a recovery left; otherwise the hint says to restart the service from Services. The dialog says it takes about a minute (the 60 s restart delay), and the guide says each one logs Service Control Manager events 7024 and 7031. Portable: start a new copy with the same arguments once this one has released the port, then exit. `/system` reports `available` and the method on both. Free space on Windows through `fs4`; memory per Q9. Tests: the service's restart request path (in `windows_service.rs`, run on the Windows CI job), the count, the portable relaunch, and smoke.ps1 pressing Restart now on the installed service and seeing `/healthz` return.
- **PK-manifest.** Every build sets `LODESTAR_VERSION` (tarball, MSI, zip, image) so nightlies rise. On a `v*` tag the `release` environment signs a format-1 manifest for the stable channel with each artifact's URL, SHA-256 and size (the two Linux musl binaries, the MSI, the portable zip; Docker updates through the musl binary overlay, so it has no entry), wraps it in the `<channel>.json` envelope `freshness.yml` reads and re-signs, and uploads it to `update-manifest` in the `update-manifest` concurrency group. The nightly step runs only when the `nightly` environment has the nightly update key, and otherwise logs a notice and skips (Q8). `crates/update/src/doc.rs` isn't touched. The manifest builder has unit tests (`test_update_manifest.py`), checks its output against the README's caps, round-trips it through `lodestar-update`'s verifier in CI, and never prints a key.
- **PK-win-upd-1.** On Windows, check and notify run in the service as on Linux: the same window, policy and check request, choosing the manifest's MSI or portable artifact by how Lodestar was installed. `trust_file.rs` depends on `layout.rs`, which is Unix-only today (`open_nofollow`, `write_atomic`, `flock`, `fchmod`, `geteuid`), so this slice adds a Windows layout with the same guarantees: refuse reparse points, replace atomically, one writer at a time, owner-only access. Install stays unavailable with a reason until PK-win-upd-2 or PK-win-portable-upd. Tests on every OS for artifact selection; the Windows layout on the Windows CI job; the `/updates` contract test for Windows.
- **PK-win-upd-2.** The service never runs `msiexec` itself: it writes the pending record and starts the privileged helper the owner approves (Q13), which runs `lodestar update-helper` from the install folder. The helper follows Q13's rules: it copies the MSI from `<data>\updates\` into a staging folder only SYSTEM and Administrators can write, verifies that copy against the manifest's signature, channel, freshness and pins (and Authenticode only if the file carries a signature, §2.23), and installs from the copy with fixed `msiexec /i … /qn` arguments. It parses every file it reads from the data folder as untrusted input, and refuses a version that isn't newer than the installed one. The current MSI and its pins are kept in the SYSTEM-only folder for rollback. Then it health-checks the new service. Tests: a file swapped after the service wrote it is never installed; a replayed, validly signed older manifest is refused; a wrong size or hash is refused; the arguments are fixed; a failed health check hands over to rollback.
- **PK-win-upd-3.** Rollback restores the store snapshot first, then reinstalls the previous MSI from the SYSTEM-only folder, checked against the pins held there, with the service set to manual start until the store is back (B-update-r2:162). The only older version the helper accepts is the journal's rollback target with those pins. The journal and `rollback.json` formats are reused unchanged, and parsed as untrusted. Probation survives a reboot: the MSI registers the one-shot boot-time `update-helper --resume` (§12.2) through the same helper. `serve` and every CLI subcommand still refuse while `rollback.json` exists. Tests: an interrupted rollback resumes; a downgrade over a newer schema never starts the old service on it; a planted rollback target in the data folder is ignored.
- **PK-win-portable-upd.** The portable build runs as the user who unpacked it and needs no helper: verify the downloaded zip against the manifest, rename the running `.exe` aside, put the new one in place, relaunch (PK-win-restart), and keep the old one through probation; on a failed health check rename it back (§12.2). No live-network requirement (Q1); a warn-only step logs whether the public DHT routing table grew above 0 nodes, and never fails the job. Every wait has a deadline of at least 10 s.
