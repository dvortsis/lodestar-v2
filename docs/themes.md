# Theme palettes: 24 families × light/dark

This is the source table for the 24 theme families (48 themes) in §10.18 of `docs/architecture.md`. Each family below has one fenced YAML block in Riverstone's schema; the theme files in `web/themes/*.json` are generated from these blocks, and the theme compiler derives every role token (inks, muted text, borders, tints, status colours, data variants) from them.

## Format

Each family is exactly one ```` ```yaml ```` block:

```text
id: <kebab-case id; use as the file name, e.g. web/themes/<id>.json>
name: "<display name>"
group: official | accessibility | community | original
light:
  background: "#RRGGBB"   # the page (daisyUI base-200)
  surface: "#RRGGBB"      # panels, rows, drawer (base-100)
  text: "#RRGGBB"         # base-content
  primary: "#RRGGBB"
  accent: "#RRGGBB"
  categorical: ["#RRGGBB", ×6]
dark:
  ... same keys ...
```

- Every value is a quoted, upper-case 6-digit hex (quoted because `#` starts a YAML comment).
- **`categorical[i]` is data slot `i+1`** (`--data-1` … `--data-6`) in the §10.18 slot order: 1 Video (blue), 2 Audio (ochre/yellow), 3 Software & executables (terracotta/red), 4 Documents (slate, or the palette's next most distinct hue), 5 Images (sage/green), 6 Archives & disc images (plum/purple). Riverstone is listed in this slot order too. Note that `brand/source/tokens/colors.json` lists Riverstone's categorical colours in a different order (blue, sage, ochre, terracotta, slate, seafoam), so don't copy that order.
- `accent` is green wherever the source palette has a usable green, because the compiler derives `success` from `accent-ink`.
- Categorical colours are per mode. Values under 3:1 on the surface are allowed: the compiler derives a data variant by shifting OKLCH lightness only (§10.18), as it does for Riverstone light.

> **Family count.** §10.18 says "24 families", but its table names 23. The 23 listed families are all here; the 24th, **Rosewood** (Originals), is a proposal to make the count match and is marked as such in its section.

**Hard gates on these values:** text ≥ 4.5:1 on background and surface (≥ 7:1 for High Contrast). **All 48 themes pass.** Two community themes needed a deviation from the published palette to get there (Solarized light text, Tokyo Night Day text); both are explained in their sections.

**ΔE_ok ≥ 5 warning:** every theme clears 5 under normal vision; the weakest is Riverstone at 5.1 (sage vs slate), which §10.18 grandfathers anyway. Most community palettes put blue and purple, or red and orange, close together under simulated colour-vision deficiency. That's inherent to those palettes and stays a warning; the composition-bar mitigations in §10.18 (gaps, fixed order, text, patterns) cover it. The Accessibility and Originals families were tuned (lightness only) to keep CVD pairs ≥ 5 where possible; only Sandstone light and Moss light (4.9 deutan) and Okabe-Ito light (4.9 deutan, after the derived orange shift) fall just short.

**Derived-token gates** (`*-ink` ≥ 4.5:1, field border and focus ring ≥ 3:1, data ≥ 3:1) apply to compiler-derived values, so they aren't checked here. Raw categorical values sitting at exactly 3.00–3.02:1 (several Originals light modes) pass as written, but if the compiler rounds differently it will simply derive a variant one step darker.

**Simulation caveat:** this script's CVD figures for Riverstone (weakest pairs 3.4 deutan and 4.5 protan, both involving sage) are lower than the ≥ 5.5 quoted in §10.18, and it measures the old sage–seafoam pair at 4.4 rather than ≈ 1.9. The normal-vision figures and the data variants match §10.18 exactly, so the difference is the CVD model (and possibly the ΔE scale used for the old pair). The compiler should pick one model and document it; until then treat CVD numbers as relative, not absolute.

### Okabe-Ito

```yaml
id: okabe-ito
name: "Okabe-Ito"
group: accessibility
light:
  background: "#F4F4F2"
  surface: "#FFFFFF"
  text: "#1A1A1A"
  primary: "#0072B2"
  accent: "#009E73"
  categorical: ["#0072B2", "#E69F00", "#D55E00", "#56B4E9", "#009E73", "#CC79A7"]
dark:
  background: "#121417"
  surface: "#1E2226"
  text: "#EDEDED"
  primary: "#56B4E9"
  accent: "#009E73"
  categorical: ["#56B4E9", "#E69F00", "#D55E00", "#F0E442", "#009E73", "#CC79A7"]
```

Text contrast: **light** 15.80:1 on background, 17.40:1 on surface; **dark** 15.76:1 on background, 13.67:1 on surface.

Categorical slots are the canonical Okabe-Ito set, mapped by hue: blue `#0072B2`, orange `#E69F00`, vermillion `#D55E00`, sky blue `#56B4E9`, bluish green `#009E73`, reddish purple `#CC79A7`. In dark mode slot 1 uses sky blue and slot 4 uses yellow `#F0E442` (blue `#0072B2` is only 3.09:1 on the dark surface and too close to it in lightness to read well; yellow fails on white but is ideal on dark). Neutrals are plain greys so the categorical set carries all the colour. The light mode keeps the canonical values and lets the compiler derive data variants for orange and sky blue (both under 3:1 on white); after that shift orange vs vermillion is 4.9 ΔE_ok under deuteranopia (warning only).

Source: Masataka Okabe and Kei Ito, *Color Universal Design (CUD): how to make figures and presentations that are friendly to colorblind people* (2002, rev. 2008), <https://jfly.uni-koeln.de/color/>. The colour values are a published recommendation, free to use; credit the authors.
