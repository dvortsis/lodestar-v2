## Findings

### FILTER-01 The child-safety core reads only the first 128 tokens of a name or path and only the first 1,000 files; the rest is stored, shown and searchable unjudged
- Severity: blocking
- Kind: security
- Confidence: confirmed
- Where: `crates/filter/src/normalize.rs:28` (`MAX_TOKENS = 128`), `:336-338` (`room`), `:406-409` (`emit` returns once the text has 128 tokens), `:441`; `crates/filter/src/core.rs:461` (`MAX_FILES = 1_000`), `:774-778`, `:991` (`item.files.iter().take(MAX_FILES)`), `:1038` (a path's cap counts its folders' tokens too: `continue_path(&[name], tokens, 0, d.end)`); `crates/filter/src/matcher.rs:961-989` (your rules' file reads take `MAX_FILES` too); limits upstream: `crates/metainfo/src/info.rs:36-39` (`max_files: 200_000`, `max_path_bytes: 4096`, `max_name_bytes: 4096`); what is shown and indexed: `crates/api/src/torrents.rs:758-779` (every file, paged), `crates/search/src/doc.rs:16`, `:198` (the non-padding files' path tokens, up to 20,000 per torrent)
- What: the tokenizer stops emitting tokens for a text after 128 (a DoS bound), and the core's pattern rules (CS-2a, CS-3a/3b, CS-4a, CS-5a/5b) read at most the first 1,000 file paths. Both caps fail open: what lies past them is never judged, but the full name (up to 4,096 bytes) and every file path (up to 200,000) are stored, returned by the API and indexed for search. The 128 cap is cheap to exhaust: a 32-character word alternating letters and digits (`a1a1…`) plans to 34 tokens (32 parts, the whole word, the letter-for-number reading), so four such words (about 135 characters) use it up, and a folder path of 128 tokens hides every file name under it. Padding-marked files (`.pad/…`, `_____padding_file_…`, BEP 47 `p`) are skipped by the core too (`core.rs:995`) but listed by the files API.
- Failure scenario: (a) a name of four `a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1` words followed by a minor age next to a `@cs/sexual` term: CS-2a/CS-4a see no token of the tail, the torrent is stored and its full name shows in search. (b) a pack of 1,001+ files whose first 1,000 are innocuous (or zero-length filler) and whose indicative file names come after: CS-2a/CS-3b/CS-4a file evidence is never read, yet the files page lists the names and `path:` finds them. (b) also happens with no adversary: any large collection whose indicative names come after the first 1,000.
- Suggested fix: make the caps fail closed or lift them for the core. The core's read is linear (one hash lookup per token), so reading the whole name (bounded at 4 KiB by metainfo) and every stored path is affordable off the common case: read everything when a text or file list exceeds the cap, or quarantine on overflow ("too large to judge") instead of passing. Add tests that pin a term placed after token 128 and after file 1,000 (today `normalize.rs:811` and `tests/props.rs:49` only assert the cap holds).
- Tracked?: not found. `docs/decisions/2026-10-31-LU-1-neutralize.md` notes LU-1 reads every file "not only the first 1,000 the other rules read", and `docs/decisions/2026-11-05-RP-1b.md` records the cap for pack rules, so the cap is known; no decision records it as an accepted child-safety trade-off, and nothing in `runner/slices.yaml` covers it.

### FILTER-02 CS-8a (locked floor, renamed reposts) can never fire: nothing in production ever stores a CS-8 payload signature
- Severity: blocking
- Kind: gap
- Confidence: confirmed
- Where: `crates/store/src/filter.rs:308` (`Store::add_cs_sig`: its only callers are tests, `crates/lodestar/src/cli/import/tests.rs:535`, `crates/lodestar/src/cluster/filter.rs:592`, `crates/store/src/snapshots.rs:2082`); `crates/api/src/filters.rs:2192-2206` (`Change::ReportAbuse`: `add_cs_hashes`, engine update, `delete_torrents`; no signature) and `:2269-2288` (`Change::Confirm`: the same); the reader side is complete: `crates/pipeline/src/lib.rs:293-295`, `crates/filter/src/core.rs:838-843`
- What: §20.5.2 says a confirmed or reported torrent's "payload signature becomes a CS-8 key", and §20.5.1 lists CS-8a as implemented and part of the locked floor. The engine evaluates CS-8a against `cs_sigs`, the store has the table, snapshots and the worker wire carry it, but no production path writes a row: Report abuse deletes the stored torrent without computing `payload_sig` of its files first, and Confirm releases the quarantine row (which keeps no file sizes) the same way. `cs_sigs` is always empty, so `Core::floor` returns at `if self.cs.sigs.is_empty()`.
- Failure scenario: the owner reports a stored torrent as child-abuse material. Its hash goes to CS-1a and it is deleted. The same payload re-uploaded under another name and info hash (the case CS-8a exists for) is fetched, judged by the pattern rules only, and stored if its new name is clean.
- Suggested fix: in `ReportAbuse`, read each stored torrent's file list before `delete_torrents`, compute `lodestar_filter::payload_sig`, and `add_cs_sig` + `core.cs.add_sig` when it is `specific`. For Confirm, keep the signature with the quarantine row at hold time (the writer has the files then) so Confirm can promote it; `RemoveCs1` must then remove the matching signature. Add an API-level test that a renamed repost of a reported torrent is dropped by CS-8a.
- Tracked?: not found (`runner/slices.yaml`, `docs/build-plan.md`, `docs/decisions/`, open PRs). GS-0 covers the `sig:` search field only.

### FILTER-03 A hash that joins the floor or a dropping list from a file or a subscription never removes the torrent already stored under it; no rule change is applied to stored torrents at all
- Severity: blocking
- Kind: gap
- Confidence: confirmed
- Where: `crates/lodestar/src/floor.rs:18-36` and `crates/store/src/filter.rs:279-293` (`sync_files` → `add_cs_hashes`: inserts only); `crates/filter/src/lists.rs:563-630` (`apply`: swaps the engine's layers only); `crates/api/src/filters.rs:2037-2058` (`AddRule`), `:1931-1967` (core and pack switches on): store the row and reload, nothing else; the only production `delete_torrents` callers are `crates/api/src/filters.rs:2205`, `:2287` and `crates/lodestar/src/cluster/serve.rs:506`; every `Engine::judge*` call site outside tests is ingest, the unverified/import refile, or an API preview (`crates/pipeline/src/{worker,writer,torrent_cache,unverified}.rs`, `crates/sources-importers/src/driver.rs:684`, `crates/api/src/filters.rs:592`, `:3458`); `crates/store/src/filter.rs:516-571` (`release_rules` deletes quarantine and tombstone rows only); spec: `docs/architecture.md:3419`, `:3489`, `:3708`
- What: §20.3 promises "Retroactive re-evaluation: when rules change, a throttled background job re-applies flag/demote/hide to the existing index and re-queues affected tombstones", §20.5.3 that switching a core rule back on "re-evaluates recent ingest and the index", and §20.8 that "removing a rule restores hidden items". None exists for the `torrents` table. The writer's sweeps on an engine version change cover unverified items, claims and import candidates only (`Writer::note_engine`, `writer.rs:1443-1454`). The sharpest case is the locked floor: a CS-1b hash that arrives through `blocklist.files` at start, or through a floor-marked subscription's refresh, is refused at intake from then on, but a torrent stored under that hash before stays stored, indexed, searchable and exportable. Only Report abuse and Confirm delete. The schema's triggers on `cs_hashes` (`crates/store/src/schema.rs:105-116`, `:245-253`) already remove unverified items, claims and import candidates under a hash that joins the floor, but not the `torrents` row, and a floor-marked list's hashes never enter `cs_hashes` at all. In the other direction, removing a hide rule leaves `flags::HIDDEN` on the rows it hid.
- Failure scenario: the operator obtains a vetted child-abuse hash list and adds it as a floor-marked subscription (or a `blocklist.files` entry). Torrents the crawler stored last week under listed hashes remain in search results with their names and file lists. The same holds for a new drop/quarantine/hide rule, a pack turned on, or a core rule switched back on: existing matches stay visible.
- Suggested fix: on every engine version change run a throttled sweep over stored torrents (hash-only for floor and list changes: join `cs_hashes` and list entries against the swarm-hash index and `delete_torrents`; a full judge for rule, pack and switch changes), applying the decision as ingest would (tombstone or quarantine plus delete, or set and clear the HIDDEN/DEMOTED/FLAGGED bits). At the very least do the hash join for floor additions in `floor::sync_files` and `lists::apply`. Pin with a test: store a torrent, add its hash through a floor list, assert it is gone from the store and the index.
- Tracked?: not found as a slice or open PR. `docs/decisions/2026-11-04-X-legal-docs.md:51` records "Drop doesn't delete stored records" as a documentation fix and recommends a Delete action; `docs/decisions/2026-11-01-F-filter-load-fail-closed.md:20` notes "nothing clears [HIDDEN] when the rule is fixed". Neither records the missing re-evaluation as accepted, least of all for the floor.

### FILTER-04 Look-alike mapping covers about 36 letters, not the UTS #39 skeleton §20.4 promises; several cheap spellings pass the core
- Severity: important
- Kind: gap
- Confidence: confirmed
- Where: `crates/filter/src/normalize.rs:59-103` (`confusable`), `:205-217` (`leet`), `:527-542` (the letter-for-number reading is added only when every character becomes a letter), `:44-56` (`Token::new` reads a number only from ASCII digits), `:509-521` (parts split on ASCII digits only); spec: `docs/architecture.md:3422`
- What: §20.4 says look-alike characters are "mapped to one form (UTS #39 confusables skeleton)". The code maps a hand list of Cyrillic, Greek and six Latin letters (its own header says "the common confusables, not the whole UTS #39 table"). Not mapped, for example: Latin alpha `ɑ` (U+0251), script `ɡ` (U+0261), Cyrillic `һ` (U+04BB) and `ӏ` (U+04CF), Armenian `օ ս հ`, small capitals (`ꜱ ᴀ ᴇ` …), Cherokee letters. Also: (1) `1` reads only as `i`, never `l`; (2) the swapped reading is dropped when the word also holds a digit outside the table (`2 6 8 9`), so a term written with one leet digit and one other digit attached gets no letter reading; (3) decimal digits NFKD doesn't fold (Arabic-Indic and others) are treated as letters, so an age written with them never becomes `num` and CS-2a/CS-5b can't see it.
- Failure scenario: a `@cs/…` term written with one unmapped look-alike letter hashes differently from the list entry, so no core pattern rule fires, while the name renders as the term to a reader.
- Suggested fix: generate the table from UTS #39 `confusables.txt` (every letter and digit whose skeleton is ASCII), fold every `Nd` digit to ASCII, add `1→l` as a second alternative, and build the swapped reading from the letter run when other digits are attached. Extend `tests/normalize_reference.rs` with the new classes. If the short table is deliberate, record it and correct §20.4.
- Tracked?: not found in `docs/decisions/` (the F-normalize-invisible and two-readings decisions cover invisible and format characters only), `runner/slices.yaml` or the open PRs.

### FILTER-05 The built-in exceptions cancel explicit evidence more widely than §20.5.4 describes: one context word in a name, or a rating word before an age
- Severity: important
- Kind: gap
- Confidence: confirmed
- Where: `crates/filter/src/core.rs:1068-1071` (`educational = texts[0].1.context && !adult`), `:1100-1102` (the name is skipped for CS-2a/CS-4a), `:494-515` (the context words, among them `health`, `medical`, `docu`, `lecture`, `biology`, `anatomy`, `parenting`), `:890-897` (`marked && !rated`), `:483-489` (the rating words, among them `pg`, `nc`, `rated`, `rating`); pinned by `crates/filter/tests/core.rs:187-188`; spec: `docs/architecture.md:3501-3502`
- What: (1) CSX-2 is specified as cancelling ambiguous terms only with "context terms + a non-adult category + no explicit-content file structure". The code needs one context word anywhere in the name and a non-Adult classification; the file-structure condition isn't there, and what it cancels includes an explicit minor age next to a sexual term (the test asserts `"Title 15yo lexa education"` passes). The adult classifier is softened by the same kind of word (§20.9: "a documentary, educational or medical word cancels the supporting score"), so the word also keeps the torrent out of Adult, where CSX-2 never applies. For a multi-file torrent the name is the folder, so no file path repeats it. (2) CSX-3 treats a number after a rating word as a rating even when an explicit age marker follows it: `pg 13yo`, `rated 9 years old`, `nc 12 y o` yield no age.
- Failure scenario: a multi-file torrent named with an explicit under-18 age, a `@cs/sexual` term and the word `health` (or with `rated` before the age) and neutral file names is stored and shown; CS-2a and CS-4a report nothing.
- Suggested fix: let CSX-2 cancel only the ambiguous evidence it is specified for (CS-4 role terms), never an explicit age (CS-2a), and add the file-structure condition or drop the claim from §20.5.4. Let CSX-3 apply only when no age marker (`AFTER`, `AFTER_FIRST`+`AFTER_SECOND`) follows the number. Update the test at `tests/core.rs:188` accordingly.
- Tracked?: partly: `docs/architecture.md:3465` says CSX-2 is built for "name evidence only, outside Adult", without saying the file-structure condition is missing or that explicit ages are cancelled. No slice or decision found.

### FILTER-07 A floor change between a batch's judgement and its commit is not seen, and nothing repairs it afterwards
- Severity: important
- Kind: correctness
- Confidence: likely (traced by reading; not reproduced)
- Where: `crates/pipeline/src/writer.rs:489` (the judge takes `self.filter.current()` once per batch), `:725-817` (the commit that follows checks only `held.contains` per hash, `:768-776`; no engine version or `blocked_hash` re-check in `transaction`, `:2311`); `crates/api/src/filters.rs:2192-2206` (`ReportAbuse` updates the store and the engine and deletes stored rows, but puts nothing in the `HeldSet`); `crates/filter/src/lists.rs:609-628` (a list refresh swaps layers the same way)

- Suggested fix: inside the commit task compare the engine version with the one the batch was judged under and, when it moved, re-check `engine.blocked_hash` for each item (cheap, hash-only); or mark floor additions in the `HeldSet` before the engine update, as holds are.
- Tracked?: not found. `2026-10-31-B-held-precommit.md` and `B-held-exact.md` cover tombstones and quarantine only.

### FILTER-08 Per-torrent token map uses an unkeyed, invertible hash as its table hash: a crafted file list makes one judgement quadratic
- Severity: important
- Kind: resource
- Confidence: likely (complexity argued from the code; not measured)
- Where: `crates/filter/src/hash.rs:55-73` (`IdHasher` passes the key through), `crates/filter/src/prefilter.rs:285-287` (`DocKeys.text: IdMap<u32>`), `:1338-1352` (`Scan::add_text`: `self.out.entry(hash)`), `:1363-1392` (the key is `fmix64(fnv1a(lowercased word))` under a fixed prefix), `:1105-1116` (`Vocabulary::find` walks a chain of same-hash texts); built for every torrent: `crates/filter/src/matcher.rs:828-831`, `:862-866`, `crates/filter/src/engine.rs:1232`
- What: `DocKeys` holds one entry per distinct token text of the name and the first 1,000 paths (up to about 4 MB of text, several hundred thousand tokens), in a std `HashMap` whose hasher is the identity. The keys are a public, unkeyed function of attacker-chosen text, and `fmix64` is a bijection, so words whose keys share their low 20 bits cost about a million trials each to find. With every key in one probe sequence, inserting n of them costs on the order of n²/32 group probes: for 400,000 tokens that is billions, seconds to tens of seconds of CPU for one judgement, against a 50 µs budget. `flood.rs` and `spam_sigs.rs` key their maps with `RandomState` for exactly this reason ("signatures are the sender's to choose"); this map was left out.
- Failure scenario: a peer serves metadata with 1,000 paths of about 4 KiB each, built from precomputed colliding words, for many announced info hashes. Each one pins a prepare thread for seconds; any re-judge at commit (a remote worker's result, a rule-set version change, SP-3/SP-4) does the same on the single writer.
- Suggested fix: hash the table with a per-process key (`RandomState` over the u64, or XOR-fold with a random seed and re-mix), keeping the stored key as it is; bound the distinct tokens scanned per torrent for the narrowing (falling back to "maybe" for every rule past the bound, which is the safe side).
- Tracked?: not found. §20.8's budget notes discuss hash collisions for correctness ("never yes from a hash") only.

### FILTER-09 Decoding a list holds the download, the expansion and a second copy at once, three times the expansion when it isn't UTF-8
- Severity: important
- Kind: resource
- Confidence: likely (sizes from reading; not measured)
- Where: `crates/filter/src/lists.rs:654-672` (`decode`: `body.to_vec()` for plain text, `String::from_utf8_lossy(&bytes).into_owned()`, the NUL check on the first 4,096 bytes only), `crates/lodestar/src/subscriptions.rs:307-328` (`body` lives until the parse returns), `crates/lodestar/src/config.rs:649-651` (64 MiB and 256 MiB defaults), `crates/filter/src/lists.rs:173-177` (`IpRange` is 48 bytes; up to 4M kept before merging)
- What: with the default caps a 256 MB list needs the 64 MB body, the 256 MB expansion and a 256 MB `String` copy together (about 0.6 GB); a body of invalid UTF-8 past the first 4 KiB turns each byte into a 3-byte replacement character, so the `String` alone reaches 768 MB (over 1 GB in all), before 4M parsed entries are added. The caps bound the bytes read, not the memory used. `checked_at` is written only after the parse, so a refresh that gets the process killed is due again at the next start.
- Failure scenario: a subscribed list's host (any URL a signed-in session added, `http` allowed) serves a 64 MB gzip of `0xFF` bytes. On a memory-limited container the refresh is killed for memory, the list is still due, and the server repeats it at each start.
- Suggested fix: `String::from_utf8(bytes)` to reuse the buffer and fall back to lossy conversion per line; drop `body` before parsing; reject bodies whose share of invalid bytes is high; record `checked_at` before parsing.
- Tracked?: not found. `docs/decisions/2026-10-31-X-soak-docker-memrule.md` is about soak memory rules, not this path.

## Checked and found sound
- Start fails closed: `filter_load::sync_sources`, `StoreFilter::read` and `ensure_seeded` errors stop the server before any ingest (`crates/lodestar/src/services.rs:192-199`, `crates/pipeline/src/lib.rs:1507-1509`).
- Unreadable stored rows: a withholding rule becomes a match-all quarantine stand-in, a lost `unless` is dropped and the rule marked a stand-in, releasing rows (CSX-5, exceptions, Always allow, an unreadable scope or strength) are skipped, an unknown action code quarantines, an unreadable Is adult rule matches everything (`crates/filter/src/load.rs:360-379`, `:441-667`); stand-ins never pre-empt a stronger later decision (`engine.rs:1276-1283`, `stronger_of`).
- Stand-in undo releases only through refetch and a full judgement; a sealed name that won't open stays held; adult holds are counted, never released; a row a writer replaced isn't deleted (`crates/api/src/filters/standin.rs:260-298`). A row with no sealed name is judged on an empty name and so released, which costs a refetch and a full judgement, not a leak.
- The floor is judged first on every path (`judge`, `judge_classified_with`, `at_commit`, `judge_at_commit_reusing`, the Adult reading) and can't be switched off or excepted (`core.rs:167-181`, `rules.rs:315-322`); an unknown stored CS-1 origin stays in the floor as Imported (`pipeline/src/lib.rs:284-290`); floor-marked lists only add, with removals kept pending (`lists.rs:587-595`).
- `HeldSet`: a store error or an unsettled mark leaves hashes held, never free; removal is checked against the store under the lock; pending marks are counted per batch (`held.rs`).
- Remote workers' verdicts are never trusted: the writer re-judges anything not from the built-in worker at the current version, and a re-judge replaces the trail (`writer.rs:1868-1873`, `:2010-2016`). A `Trail` is reused only for the same engine generation, version, torrent fingerprint and clock edges, and the floor is re-judged on that path too (`engine.rs:386-396`, `:883-898`).
- Empty or odd keywords can't become match-all: `in_a_row` is false for no words, `decode_match` refuses empty hash lists, a provenance query that would negate to match-all reads as unreadable (`rules.rs:366-369`, `load.rs:46-48`, `:66-80`).
- List parsing of untrusted text: lines over 1,024 bytes are skipped, octets, prefix lengths and range order are checked, IPv6 arithmetic saturates, gzip expansion is capped by `take(max + 1)`, a binary body is refused, unknown list actions fall back to Drop (`lists.rs`). Downloads go through the SSRF guard with a redirect cap, an https-to-http refusal, a byte cap per chunk and a whole-fetch timeout (`subscriptions.rs:217-304`).
- Sanity gates keep the previous version on a parse failure, an empty list, a shrink of over half or tenfold growth, and a failed store write changes nothing (`subscriptions.rs:173-192`, `:332-398`).
- No regular expressions anywhere in the crate (`crates/filter/Cargo.toml`), so no pattern compile failure or backtracking; packs are compiled in and covered by the release signature, not fetched; pack version rows that are lost, differ or name a dropped version resolve to the stronger side, held at most at quarantine (`packs/upgrade.rs:401-617`).
- Sealing: XChaCha20-Poly1305 with a fresh 24-byte random nonce, AAD-bound variant for worker records, a failure to seal still quarantines (without a name) (`seal.rs`, `writer.rs:1936-1941`).
- Bounded, keyed state where the sender picks the keys: SP-3's origin map and SP-4's signature index (`flood.rs`, `spam_sigs.rs` headers).
- Alerts: the percolator records every match, and the list, badge, feed and SSE event leave out filter-hidden and Adult-hidden torrents in SQL (`crates/api/src/alerts.rs:1-23`, `crates/store/src/saved.rs:461-470`). Search, facets, Torznab and export share `search::base_query` with `hidden: false` by default (spot-checked by grep, not read).

## Area-level concerns
- The core's reach is narrower than what the product shows. Caps (128 tokens, 1,000 files), skipped padding files, a short look-alike table and two generous built-in exceptions each leave text that is stored, displayed and searchable but never judged (FILTER-01, -04, -05). The tests pin that the caps hold and that the exceptions pass; none pins what happens past a cap.
- Filtering is ingest-only. Everything in §20 that speaks of the existing index (retroactive re-evaluation, restoring hidden items, switching a rule back on) has no executor for stored torrents (FILTER-03), so a rule's effect depends on when a torrent arrived. The same absence turns narrow races into permanent states (FILTER-07).
- The floor's second leg is unreachable (FILTER-02). The tests that exercise CS-8a put the signature in directly (`Store::add_cs_sig`, `CsList::add_sig`), which is why the missing producer went unnoticed; floor tests should go through the API operations that are meant to feed it.
- Subscription gates measure entry counts only. A version with the same count and different content passes (by §20.13's wording), `http` list URLs are accepted, and there is no integrity check on a list; for floor-marked lists the add-only rule contains this, for other lists a swapped body silently unblocks. Worth a recorded decision.
- `matcher.rs` and `prefilter.rs` (about 5,200 lines) carry a three-valued pre-check, per-thread caches keyed by address and two readings of every torrent. They are well covered by differential property tests, but a reviewer cannot hold them in their head; a wrong "no" there silently disables one of your rules. I did not read them in full.
