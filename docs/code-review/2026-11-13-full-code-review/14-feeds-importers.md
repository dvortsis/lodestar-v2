## Findings

### IMP-01 A verified info dict never upgrades a complete-but-unverified import; the follow-up it is left to is not scheduled
- Severity: important
- Kind: gap
- Confidence: confirmed
- Where: `crates/store/src/lib.rs:1311-1329` (`commit_one`), `crates/store/src/lib.rs:1439-1446` (`upgrade_partial` returns when `FILES_PARTIAL` is clear), `crates/store/src/import.rs:1696-1703` (an import gets `FILES_PARTIAL` only when `completeness == Partial`), `crates/sources-importers/src/magnetico.rs:590-594`, `crates/pipeline/src/torrent_cache.rs:469-472` (`interest` skips rows without `FILES_PARTIAL`), `crates/store/src/lib.rs:1049-1067` (`partial_hashes`)
- What: an import record whose file rows are consistent is stored `reported_complete` + `unverified`, flagged `IMPORTED` but not `FILES_PARTIAL`, with `piece_len`, `info_size` 0 and no raw dict. Every path that later brings a verified info dict for that hash (a `.torrent` upload, the watch folder, a torrent-cache file, a crawler fetch) reaches `commit_one`, finds the row, and calls `upgrade_partial`, which does nothing unless `FILES_PARTIAL` is set. The verified name, file list, piece data and v2 hash are discarded, and the quality row stays `unverified`. Nothing else queues these rows either: the refetch queue and the cache's interest lookups both select on `FILES_PARTIAL`.
- Failure scenario: import a Magnetico database (most rows have file rows that sum to `total_size`, so they are `reported_complete`). Upload the real `.torrent` for one of them. The route answers `202` with the hash, the upload is added as a source, and the stored row keeps Magnetico's unverified name and file list, with `piece_len` 0, permanently. At 10M imported rows most of the corpus can never become verified.
- Suggested fix: let `commit_one` upgrade any row whose quality reads `verification != verified` when the commit is `verified` (the same write `upgrade_partial` does, keeping sticky-private), with a store test; or schedule the slice that does and say so in IMP-1's follow-ups.
- Tracked?: partly. `docs/decisions/2026-10-30-IMP-1.md` ("Promoting verified metadata … is IMP-06's job", "Nothing else changes until IMP-06") records the limit. IMP-06 exists only as a row in `docs/plan/2026-10-29-magnetico-bitmagnet-migration.md:435`; it is not in `runner/slices.yaml`. CR-3 ("durable fair partial upgrades") covers partial rows only. No test pins the behaviour: `crates/store/tests/import_insights.rs:335` only asserts `Inserted::Existing`.

### IMP-02 Bitmagnet adapter: source-defined functions in index predicates or expressions on the read tables run in the importer's session at plan time
- Severity: important
- Kind: security
- Confidence: likely (traced in the code; the PostgreSQL behaviour was not executed here)
- Where: `crates/sources-importers/src/bitmagnet.rs:853-863` (`INDEXES_SQL` leaves partial and expression indexes out of the keyset choice but does not refuse a source that has them), `:973-1179` (`schema`: no check of `pg_index.indpred`/`indexprs`, `pg_inherits` or table constraints), `:1277` (`ENDS_SQL`, the first statement the server plans against `public.torrents`), `:1296-1304` (the four reads are prepared after it), `crates/sources-importers/src/bitmagnet/conn.rs:210-229` (`session_sql`)
- What: IMP-3 treats source-defined code running as the importer's role as a blocking security issue and closes the cast route in three layers. The same result is reachable without a cast. PostgreSQL's planner loads every valid index of a scanned table and runs its predicate and expressions through constant folding (`RelationGetIndexPredicate`/`RelationGetIndexExpressions` call `eval_const_expressions`), which executes any function marked `IMMUTABLE` whose arguments are constants. So `CREATE INDEX ON public.torrents (size) WHERE public.f()` with `f()` declared immutable runs `f()` as the importer's role whenever a statement on `public.torrents` is planned, inside the read-only transaction. A CHECK constraint on an inheritance child of a read table is folded the same way. `search_path = pg_catalog`, the type-namespace check, the opclass check and `enum_eq` do not apply to it.
- Failure scenario: a source database (a dump that carries its own DDL, which the restore guide allows: "If the dump does contain `CREATE TABLE`, skip `apply-migrations.sh`") holds such an index. At `open`, planning `ENDS_SQL` runs `f()`. `f()` can call `set_config('search_path', 'public, pg_catalog', false)`, after which the reads prepared at lines 1301-1304 resolve their unqualified `octet_length`, `convert_to`, `isfinite`, `floor` and comparison operators against `public` first, per row; it can also lift `statement_timeout`. With the documented least-privilege `bitmagnet_reader` role the damage is limited to that session (the hardening is void, reads as that role). If the user connects as a superuser instead, which nothing refuses, `f()` can do anything a superuser can on the database server.
- Suggested fix: before the first statement that plans a scan of a read table, and again in `quiet`, refuse (`unsupported_schema`) when any read table has an index with a non-null `indpred` or `indexprs` that depends on a function outside `pg_catalog`, any `pg_inherits` row, or any constraint or default depending on such a function (a `pg_depend` walk covers all three). Add a PostgreSQL test like the cast one (`pg_tests.rs:421-449`) that proves the function never ran. Consider refusing a superuser connection (`rolsuper`) outright.
- Tracked?: not found. `docs/decisions/2026-10-30-IMP-3.md` covers casts, operator classes and type namespaces only; no test in `pg_tests.rs` creates a partial or expression index. Note on severity: the runner rated the cast route "blocking, security" in that file. This route gives the same capability, so by that precedent it may be blocking too; I rated it important because it is unconfirmed at runtime and its impact with the documented reader role is small.

### IMP-03 `Store::interrupt_import_jobs` has no caller: the restart rule in IMP-1's state model is not implemented
- Severity: important
- Kind: gap
- Confidence: confirmed
- Where: `crates/store/src/import.rs:893-914` (defined; the only non-test reference in the workspace), `crates/lodestar/src/cli/import.rs:726-751` (`resume` runs a job whose control is still `running` with no revalidation), `crates/lodestar/src/cli/import.rs:934-945` (`explain(Reason::Interrupted)`, unreachable)
- What: `docs/decisions/2026-10-30-IMP-1.md` ("Restart: on start the engine calls `Store::interrupt_import_jobs`…") and `2026-10-31-IMP-4.md` ("If it can't, the next start's `interrupt_import_jobs` blocks it") both rely on this call. Neither the server's start nor any CLI verb makes it. A job whose process died (kill, power loss, the second Ctrl-C's `exit(130)`, a store error whose block could not be written) stays `control = running`, `phase = reading` indefinitely. `Reason::Interrupted` is never written.
- Failure scenario: an import is killed mid-run and the server is started. `lodestar import status` reports "Job 3 (magnetico): reading" for as long as nobody resumes it, with nothing reading. A later `resume` skips `resume_import_job` entirely because the control is `running`, so the free-space check at `cli/import.rs:729-740` is skipped (the driver still checks the source identity). The online-import slice (B-import-server-2) inherits a job table whose `running` state does not mean a driver exists.
- Suggested fix: call `interrupt_import_jobs` when the server opens the store and at the start of `open_exclusive`'s callers that write (`start`, `resume`, `pause`, `cancel`, `remove`), so `resume` always goes through revalidation; or record in a decisions file that the CLI's "resume a running job" replaces it, and remove the dead reason.
- Tracked?: not found in `runner/slices.yaml`, `docs/build-plan.md` or the decisions. `2026-10-31-IMP-4b.md` describes resuming a job left `running` but does not say the interrupt step was dropped.

### IMP-04 `import resume` on a job that has already read its whole source can block it for good
- Severity: polish
- Kind: correctness
- Confidence: confirmed (by reading; no test covers it)
- Where: `crates/sources-importers/src/driver.rs:385-392` (identity check) before `:401-404` (the phase check that would end the run), `crates/store/src/import.rs:846-863` (`block_import_job` accepts any running phase), `:819-841` (`resume_import_job` re-blocks on a changed identity), `:768-796` (`complete_indexed_import_jobs` takes only `control = running`)
- What: for a job in `indexing` (control `running`), `driver::run` compares the opened source's identity with the job's before it looks at the phase. If the source has changed since the read finished, the job is blocked with `source_changed`, although it has nothing left to read.
- Failure scenario: a Magnetico import finishes and waits in `indexing`. The user restarts magneticod (it was stopped only for the import), the database grows, and they run `lodestar import resume 1 …` again before starting Lodestar. The job becomes `blocked: source_changed`. Every later `resume` fails the same revalidation, the server never completes it, and the only exit is `cancel`, so a fully imported job ends as cancelled. The same happens to a Bitmagnet job after a statistics reset changes its dataset identity.
- Suggested fix: in `driver::run`, return `Exhausted` for a job past `committing` before the identity check; in the CLI, skip opening the source for such a job.
- Tracked?: not found.

### IMP-05 The legacy `bitmagnet::import()` is still public and writes with no filter
- Severity: polish
- Kind: maintainability
- Confidence: confirmed
- Where: `crates/sources-importers/src/bitmagnet.rs:1637-1836`
- What: `import()`, `Options`, `Report` and `write_cursor` have no caller outside the crate's own tests (`pg_tests.rs:857-885`). The function stores records through `Store::insert` with `IMPORTED` set: no filter engine, no floor or tombstone check by the caller, no quality or membership rows, candidates counted as "skipped". It is exactly the fail-open path the driver replaced, kept as a public API of the crate.
- Failure scenario: a later slice (the online import, a test helper promoted to production) calls it and imports records that never pass the content filter.
- Suggested fix: delete it and keep `read_cursor`/`legacy_cursor` with their unit tests; or make it `#[cfg(test)]`.
- Tracked?: `docs/decisions/2026-10-31-IMP-4b.md` ("has no caller left. It stays … for a later clean-up"); no slice names the clean-up.

## Checked and found sound
- Feed XML (`rss.rs:216-254`, `torznab.rs:175-214`, `common.rs:112-165`): a `<!DOCTYPE` stops the parse; only character references and the five XML entities resolve, so nothing expands and nothing external is read; bytes (16 MiB), depth, elements, items, attributes per element, attribute length and field text are capped before any copy; non-UTF-8 input is cut at the first bad byte (recorded in SRC-6). No recursion: the parser keeps one draft and a depth counter.
- `common.rs` slicing (`magnet_hashes`, `external_ref`, `rfc3339`, `zone`, `percent_decode`): every index follows a `get(..)` or an ASCII byte test, so multi-byte input cannot split a character. Dates are computed from validated fields in UTC; a numeric zone is subtracted; out-of-range days and times are refused.
- `json.rs`: `skip` is iterative with a stack bounded by `max_depth`; every public read counts against `max_values`; `num()` does not skip whitespace itself, and every caller in `archive_org`, `tpdb`, `stashdb` and `wikidata` calls `peek()` first.
- `archive_org.rs`: recursion depth is fixed by the three known shapes; files are capped by count and by total name bytes with `files_truncated` set; the hash source choice (`finish`, lines 549-609) cannot index out of range.
- Magnetico open (`magnetico.rs:836-1099`): `READ_ONLY | NOFOLLOW`, `file:` names refused, `DEFENSIVE` on, `TRUSTED_SCHEMA`, triggers and views off before the first read, `query_only`, `ATTACHED = 0`, `mmap_size = 0`, `cell_size_check`; only ordinary rowid tables named `torrents` and `files` are read; FTS tables, views and triggers never are; every value is size-guarded in SQL so an oversized value is never loaded; a progress handler bounds each step and each batch; SQLite error text is never passed on.
- Magnetico batching (`magnetico.rs:1456-1582`): keyset by rowid from `i64::MIN`, one ranged files query streamed row by row, a parent never split across batches, memory bounded to about two budgets (16 MiB) at the cut, an orphan or non-integer `torrent_id` skipped without a panic, position `i64::MAX` ends cleanly.
- Bitmagnet connection (`bitmagnet/conn.rs`): no URL or free-form option reaches the connection; the password comes only from a capped file or the environment and never appears in `Debug` or an error; plaintext only to a Unix socket or a pinned loopback address; a non-loopback host needs TLS with certificate and name verification (rustls, platform verifier or the given CA only), and a server without TLS fails rather than falling back; server error text is mapped to fixed labels.
- Bitmagnet reads (`bitmagnet.rs:904-952`, `1374-1552`): every statement is a constant with schema-qualified tables; text is fetched as `bytea` under an `octet_length` guard; keys compare the same way in PostgreSQL (`bytea`, built-in opclass enforced) and in Rust (`Vec<u8>`); files come through a portal 1,000 rows at a time; an over-budget parent restarts the range after itself; each batch is one read-only repeatable-read transaction with a client-side deadline.
- Content filter on import (`driver.rs:459-534`, `644-773`; `store/import.rs:1533-1548`, `1659-1739`): every torrent and candidate record is judged (hash lists first, then the full engine) before the commit; a record `prepare` rejects is committed as `Invalid`; an `adult_finders` read error counts as adult; the store re-checks tombstones, quarantine and the floor's hashes inside the batch transaction whatever the caller decided; a held decision on a hash that isn't stored yet writes its tombstone or quarantine in the same transaction (on a stored hash it only keeps the record out, as IMP-1 records). The CLI builds the engine with the server's loader and fails the command if the floor, subscriptions or rule tables cannot be read (`cli/import.rs:758-792`); a single rule that no longer parses is skipped and counted, as the server does (recorded in IMP-4b). No fail-open path was found on the driver route.
- Exactly-once (`store/import.rs:918-1053`): records, hits, quality, membership, counters and the cursor commit in one `BEGIN IMMEDIATE` transaction; `seq` must be the cursor's plus one; a replay writes nothing and must match the stored position; a job that is not running refuses the batch with its own error. The driver advances its cursor only after `Committed`.
- Merge rules (`store/import.rs:1560-1590`, `1673-1684`): an import into a stored row adds a source bit and a membership row; a verified row changes nothing else; privacy only moves towards private; an import never clears `PRIVATE_SOURCE`; an import cannot claim `verified`.
- CLI exclusivity (`cli/import.rs:312-357`): `locking_mode = EXCLUSIVE` plus a write takes the database file's EXCLUSIVE lock in WAL mode, which fails while any other connection (the server's readers included) holds its SHARED lock. `inspect` and `status` use `open_reader`.
- `.torrent` upload (`api/upload.rs`, `pipeline/local_torrent.rs:114-146`): behind `auth::protected` and a same-origin check, exact content type, per-address token bucket spent before the body, `Content-Length` over 8 MiB refused unread, streamed bodies cut at 8 MiB, a 60 s read deadline, four requests in flight; the file is never written to disk; the key is the hash of the raw info-dict span, re-parsed with no encoding hint; v2-only files key on the truncated SHA-256; a `private=1` file keeps no tracker or comment and is stored as a private source; the judge runs the floor's hashes and the full filter before anything reaches the writer, and a panic fails only that file.
- Dates: Magnetico `discovered_on` and Bitmagnet `created_at` are taken as Unix seconds (UTC) only inside `[2008-01-01, batch time + 1 day]`; a row is dated from the source only when the date is positive and not after the batch (`store/import.rs:1711-1714`); otherwise the import time is used and `source_at` keeps the original.
- Tests: no fixed sleep assumes finished work in the area's tests (the two `sleep` calls found are pacing inside deadline polls); the one ignored test is the documented throughput measurement.

## Area-level concerns
- **Fuzz and property coverage against `fuzz/fuzz_targets/`.** Every `sources-feeds` parser has a target that asserts invariants, not only "no panic": `rss`, `torznab`, `json`, `archive_org`, `stashdb`, `tpdb`, `wikidata`. `magnetico_row` covers the Magnetico normaliser; `local_torrent` covers the upload reader. Without a fuzz target:
  - `bitmagnet::Normaliser` has a property test only (recorded in IMP-3 as allowed by its brief);
  - the Magnetico path classifier (`windows_text`, `is_dos_device`, `lexical`, `magnetico.rs:937-1017`), the legacy cursor reader (`bitmagnet.rs:1710-1745`) and the host classifier (`conn.rs:157-206`) have unit tests only. The first is security-relevant on Windows and is the best candidate for a property test (any text that reaches a UNC, device or verbatim form must be refused);
  - the driver has no property test of its own; it relies on the adapters' and the store's.
- **The Bitmagnet hostile-schema defence is a list of known vectors** (casts, operator classes, type namespaces). IMP-02 is one the list misses. A positive rule (nothing outside `pg_catalog` reachable from the read tables through `pg_depend`) would close the class instead of the next instance.
- **Unverified imports have no route to verified at scale.** Partial rows wait for CR-3; complete rows wait for an unscheduled IMP-06 (IMP-01). After a 10M to 50M import the corpus is mostly unverified names with no piece data, and nothing in the plan changes that.
- **Bitmagnet quiescence is cluster-wide and the driver does not retry.** Any transaction id assigned anywhere on the server (autovacuum, autoanalyze) between batches blocks the job with `source_unavailable` and ends the CLI run; the user must `resume` by hand. This is recorded (IMP-3, `docs/operations.md:385`), but on a freshly restored 50M-row database it is likely to interrupt a multi-hour run more than once.
- **The area's description and the code layout differ.** `sources-importers` holds only the two database adapters and the driver; `sources-feeds` holds only pure parsers. Polling, client lists, remote blobs, blocklists, full scrapes and the watch folder are in other crates and need their own reviewers' coverage (listed under "Not read").
- **Per-batch job reloads count the job's candidates.** `JOB_SELECT` (`crates/store/src/import.rs:476-483`) carries `SELECT count(*) FROM import_candidates WHERE job = j.id`; a batch commit loads the job twice (`:933`, `:1044`) and the driver loads it once more after every batch (`driver.rs:573`). The store review has this as STORE-09; the driver's extra load is the part in this area. Real Magnetico and Bitmagnet rows rarely lack a name or size, so candidates stay few in practice.
- **Related findings in other review files:** STORE-08 (`upgrade_partial` and the `torrents_v2` unique index) is the partial-row side of IMP-01; PIPE-06 (an upload is answered once queued, not once committed) is about the same route as the upload notes above; SRC-04 covers feed polling state, which this file does not.
- **Open PRs:** none of the listed open PRs changes the files reviewed here, by their titles. The tests review notes that 778 (X-test-blockers-1112) edits `crates/sources-importers/src/bitmagnet/pg_tests.rs` (tests only); I did not read that PR. 780 (M8-PERF-1a, the 10M dataset) is the nearest in subject and is not import code.
