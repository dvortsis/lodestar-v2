## Findings

### CMP-01 A companion's credential is sent to whatever listens on its loopback port, including `[::1]`
- Severity: blocking
- Kind: security
- Confidence: likely (the code path is confirmed; the outcome depends on start-up timing, which I did not run)
- Where: `crates/companions/src/detect/mod.rs:358-369` (the `::1` fallback); `crates/companions/src/manager.rs:1537-1550` (start, then `healthy`), `:1465-1468` and `:1650-1669` (configure right after), `:2589-2609` (`Supervised::healthy`); `crates/companions/src/configure/qbittorrent.rs:375-389` (sign-in form with the password); `crates/companions/src/configure/prowlarr.rs:280-286` (`X-Api-Key`); `crates/companions/src/config_files.rs:40` (managed companions bind `127.0.0.1` only)
- What: A `Target::Loopback` request goes to `127.0.0.1:<port>` and, when that is refused, to `[::1]:<port>`. A managed companion is configured to listen on `127.0.0.1` only, so anything answering on `[::1]` is never it. Nothing checks that the listener is the supervised child, before or after the start: no port-free check before launch, no ownership check after. Health accepts any `200 v<version>` or `403 Forbidden` (qBittorrent) or `/ping` answer (Prowlarr). The manager then signs in or sends the API key to the same target.
- Failure scenario: An unprivileged local process binds `[::1]:9696` (or `[::1]:8080`). Lodestar starts Prowlarr. The first health poll runs straight after the spawn, before Prowlarr listens; IPv4 is refused, the request falls back to `::1`, the impostor answers healthy. Configuration runs milliseconds later, IPv4 is still refused, and `X-Api-Key: <key>` (or qBittorrent's `username`/`password` form) goes to the impostor. This repeats at every start, restart and regenerate. The same holds if the process takes `127.0.0.1:<port>` first: the companion can't bind, but health and configuration succeed against the impostor and the install is reported healthy. With the credential the process controls the real companion later (qBittorrent's run-on-completion program, Prowlarr's indexer credentials and custom scripts).
- Reachability today: the managed path needs a pin, so not yet. The guided path uses the same fallback now, for a qBittorrent you run on loopback: weaker, because it only bites while that qBittorrent isn't listening on IPv4.
- Suggested fix: For a companion Lodestar installed, never fall back to `::1` (it binds `127.0.0.1`). Refuse the start when the port already answers on either family (`port_in_use`). Before sending a credential, check the listening socket belongs to the supervised child's process group (Linux `/proc`, Windows TCP table), or fail the start. Add a test with an impostor on `::1`.
- Tracked?: not found. `docs/decisions/2026-11-08-CMP-8a.md` line 12 records the `::1` fallback as "doesn't widen Q12" and lists "another program on the port" only as a detection fixture; nothing covers managed companions or credentials.

### CMP-02 A native qBittorrent has no downloads folder, so downloads land in its own folder, which Remove deletes
- Severity: important (blocking once the Linux qBittorrent pin lands)
- Kind: data-loss
- Confidence: confirmed for the wiring and the deletion; likely for where qBittorrent saves (upstream's custom-profile default, from memory, not checked against a pinned build)
- Where: `crates/lodestar/src/companions.rs:423` (`Supervised::new(..., None)`); `crates/companions/src/manager.rs:2227-2229` (`Api::configure` never calls `.downloads()`); `crates/companions/src/supervise/limits_linux.rs:537` (writable grants are home and the downloads folder only); `crates/companions/src/manager.rs:1141` and `crates/companions/src/layout.rs:527-549` (removal deletes every child of `<data>/companions/<id>`); `crates/lodestar/src/companions.rs:1451-1465` (the removal plan names only the folder)
- What: `Supervised.downloads` is documented as "where qBittorrent saves, if set", and nothing can set it: serve passes `None`, and no setting or API field feeds it. The configuration step never sets a save path either. Under Landlock the companion can write only its home, so the only place a native qBittorrent can save is inside `<data>/companions/qbittorrent/home/` (with `--profile=<home>` its default is `<home>/qBittorrent/downloads`).
- Failure scenario: You install qBittorrent natively on Linux, download for a month, then select Remove. The confirmation says "Folder: companions/qbittorrent" and deletes it, with every downloaded file. Separately, downloads fill the disk that holds Lodestar's database and index, and choosing another save path in qBittorrent's own UI fails with permission errors under the sandbox.
- Suggested fix: A downloads-folder setting (asked at install, checked by `limits::check`), passed to both `Supervised` and `ConfigureInput::downloads`. Until then, have the removal plan say that downloads inside the folder go too, or refuse removal while the downloads folder isn't empty.
- Tracked?: not found in `runner/slices.yaml` or the CMP decisions (CMP-4b's file describes the grant; nothing says who sets it).

### CMP-03 In a container, generated templates never check the host folder against Lodestar's own data folder or other companions' folders
- Severity: important
- Kind: security
- Confidence: confirmed
- Where: `crates/lodestar/src/companions.rs:1180-1187` and `:1199`; `crates/lodestar/src/cli/companion.rs:278-279`; contract in `crates/companions/README.md` ("The CMP-7 contract", item 3) and `docs/decisions/2026-11-06-CMP-0.md:108-111`; `crates/companions/src/compose.rs` `check_path`
- What: `check_path` refuses a folder that overlaps `input.data` or `input.taken`. Inside a container the API passes `DataFolders::none()`, and every caller passes `taken: Vec::new()`. `DataFolders::new(main, hot, cold)`, written for exactly this case, has no production caller, and `TemplateRequest` has no field for the host data path. Docker and Unraid are the only deployments that use the templates, so there the two checks never run; only `HostPath`'s fixed list applies, which the README says can't see `/srv/lodestar`, `/data/lodestar` or `$PWD/data`.
- Failure scenario: Lodestar's data is bind-mounted from `/srv/lodestar`. You ask for a qBittorrent template with downloads `/srv` or settings `/srv/lodestar/qbit`. The template is generated, and the qBittorrent container gets read-write access to `secrets.key`, the database and the auth file. `packaging/companions/README.md` tells you "Lodestar refuses a folder that overlaps its own data folder", which is false in that deployment. The same gap lets Prowlarr's settings folder be given to qBittorrent as its downloads folder outside `appdata/<name>`.
- Suggested fix: Take the host data path as a template input in a container (required, or read from the Unraid template's values as CMP-0 said), remember generated folders for `taken`, and correct the README until then.
- Tracked?: not found as a gap. `docs/decisions/2026-11-11-PK-unraid.md:11` notes every production caller passes `DataFolders::none()` and calls the parameters "dead API for the companions owners to drop", the opposite direction.

### CMP-04 `lodestar companion remove --yes` leaves the managed download client in Integrations
- Severity: important
- Kind: correctness
- Confidence: confirmed
- Where: `crates/lodestar/src/companions.rs:139-149` (`Unwired` implements only `configure`); `crates/companions/src/manager.rs:371-373` (the trait's default `release` answers `Ok`); `crates/companions/src/manager.rs:1681-1705`; `crates/lodestar/src/cli/companion.rs:224-249`
- What: A removal first releases the `lodestar-qbittorrent` entry (`ApiConfigure::release`), and `docs/decisions/2026-11-11-X-cmp-native-handover.md:38` says that without the sink a removal "is refused at … the release (`not_wired`)". Serve's `Wiring` does that. The CLI's manager uses `Unwired`, whose `release` is the default no-op, so the CLI removes the companion, its credential rows and its folder and reports success, while the entry and its sealed password stay in `integrations.clients`. The CLI's list of what it deletes doesn't mention the entry.
- Failure scenario: With the server stopped you run `lodestar companion remove qbittorrent --yes`. At the next start Integrations still shows "qBittorrent (Lodestar)", the companion gate counts it as your own client and releases the download-client source against nothing, and a new install is refused `managed_client_in_use` until you delete the entry by hand. The CLI also stops nothing (`Unwired::stop` is a no-op and no supervisor is built), so a companion orphaned by a hard kill keeps running from a folder being deleted.
- Suggested fix: Make `Unwired::release` refuse `not_wired` for qBittorrent, as the decision says, or give the CLI the settings sink; add a CLI test.
- Tracked?: not found.

### CMP-06 A native qBittorrent can only run on the direct route; the spec's interface binding and kill-switch cover don't exist for it
- Severity: important
- Kind: gap
- Confidence: confirmed
- Where: `crates/companions/src/manager.rs:2398-2412` (`launch_env`: direct or SOCKS5 only); `crates/companions/src/supervise/egress.rs:56-72` (qBittorrent can't follow SOCKS5); `crates/lodestar/src/companions.rs:587-616` (the route is copied from `sources.egress.download_clients`, which is `direct` or `socks5` only); `crates/companions/src/configure/qbittorrent.rs:193-199` (a direct route clears the interface and address binding on an installed qBittorrent)
- What: Architecture §18.10 says companion traffic follows the egress settings, "interface binding on native installs", and "the kill-switch covers companions"; plan Q8 says qBittorrent follows an interface or bind address. As built, no setting can name an interface or address route, and qBittorrent refuses SOCKS5. So the one companion that carries the actual BitTorrent traffic either runs on the default route with its binding cleared, or doesn't start. The supervisor's hold-while-down gate never applies to it, because a direct route isn't gated.
- Failure scenario: You run Lodestar behind a VPN and install qBittorrent from the wizard. It downloads over your ISP connection. Nothing on the install confirmation says so; the Companions screen only has a general note that the route is copied from the source.
- Suggested fix: This is a recorded limit, but I think it's unsafe to ship unannounced: either add an interface route for qBittorrent (set `Connection\Interface` before first start, as the config writer already does for the WebUI keys, and gate on the interface), or state on the install confirmation and wizard step that a native qBittorrent runs outside any VPN.
- Tracked?: recorded, not planned. `docs/decisions/2026-11-11-CMP-5g-3.md` ("qBittorrent follows direct only … need a setting shape sources don't offer yet") and `docs/decisions/2026-11-11-X-cmp-egress-prelaunch.md`. `X-cmp-egress-api` and `X-cmp-egress-ui` add an editor for the same two route kinds; no slice adds an interface route. The architecture text hasn't been amended.

## Checked and found sound
- **Download and pin check** (`fetch.rs`, `verify.rs`): every hop is `https`, default port, no user info, on both the entry's hosts and `DOWNLOAD_HOSTS`, at most 5 redirects; the redirect URL is never logged; bytes are capped at the pin's size and hashed while streaming; size and SHA-256 are both compared; any failure removes the file; the `.part` file is created new with `O_NOFOLLOW`; the writer is joined before removal. A mismatch, a 404 or an oversized body fails the install, which is rolled back.
- **Catalogue trust root**: compiled in; `Catalogue::from_json` and every loosening seam (`fetch_from`, `Guarded::unchecked`, `InstallReceipt::for_tests`, `ConfigPlan::for_tests`, fault points) sit behind `cfg(test)` or the `testing` feature, which only the crate's own dev-dependency enables. An unpinned entry is refused by `installable()` and `renderable()`; an invalid catalogue turns companions off (`start` returns `None`, routes answer 503).
- **Archive extraction** (`extract.rs`): names are printable ASCII only, no absolute, `..`, backslash, colon or Windows device names; links, devices and setuid/setgid/sticky bits are refused; duplicates compare case-folded; every file is `create_new` inside a staging folder this run created; entry, total, ratio and overhead caps are counted as bytes are written, not from headers; any refusal removes the whole staging folder; the gzip trailer is read so damage past the last entry is caught.
- **Layout and journal** (`layout.rs`, `state.rs`): the pointer and the record are written temp-file, fsync, rename, fsync-folder; deletion is confined to direct children after re-checking the folder isn't a link; a record that an operation couldn't have written is refused on load; recovery rolls back before `configured` and forward after; a folder with files Lodestar has no record of is never installed over or deleted.
- **Process start** (`supervise/process.rs`, `pidfile.rs`): no shell anywhere; the executable is an absolute regular file; the environment is cleared; root or administrator is refused in shipped builds; orphan kills need pid, start time and executable to match, an executable under `<data>/companions/`, and go through a pidfd; the PowerShell scripts interpolate only integers.
- **Egress gate** (`supervise/egress.rs`, `manager.rs`): a route the companion can't follow, an unreadable setting, an unresolved proxy, or a .NET that ignores `socks5://` all refuse the start rather than fall back to direct; a dropped gate holds the companion under a lock so no release can land after it; a dead route monitor reads as down.
- **Companion HTTP** (`detect/mod.rs`): no redirects, no proxy, no cookie jar; one deadline covers connect to last body byte; bodies are capped; container names must resolve to private or loopback addresses; only the one named session cookie is read, with a checked value; answers are parsed with the bounded JSON reader and only closed values leave the adapters.
- **Credentials**: generated from the OS RNG, sealed per row with a context that names the companion and field; never in a URL, path, log line or `Debug`; reveal needs the admin password again, answers `no-store`, and never returns a pasted value; logs are redacted on entry to the ring and again on read.
- **Config writers** (`config_files.rs`): only Lodestar's own keys are set; malformed or ambiguous existing files are refused rather than overwritten; XML goes through `quick-xml`; parents are created one at a time refusing links.
- **Templates** (`compose.rs`, `unraid.rs`, `packaging/companions/**`): images by digest only; every YAML scalar is a JSON string and `$` is refused; no Docker socket, `privileged`, host network or host PID; only gluetun gets `NET_ADMIN` and `/dev/net/tun`; Unraid `ExtraParams` flags are held to a shell-inert allowlist; ports stay internal unless asked; a routed companion uses `network_mode: service:gluetun` with `depends_on: service_healthy`, and VPN settings are placeholders gluetun won't start with.
- **API** (`crates/api/src/companions.rs`, `companions_guided.rs`): every route is behind `auth::protected`; writes require same-origin JSON; install and remove need an echoed confirmation checked in the handler and again in the manager; errors are stable codes with no path, URL or value.
- **Guided flow** (`companion_wiring.rs`): one lock shared with a native qBittorrent install; the generated password is stored before it is set and only ever retried at the address it was set on; sign-in refusals are capped at three before qBittorrent's ban; a plan is single-use and must be echoed.
- **Pin tool** (`pin.py`, the workflow): keys pinned by full fingerprint, imported into a throwaway home that must hold exactly the pinned keys; the signature must be detached, class 00, a strong hash, and every signature in the file good; workflow inputs reach the tool as environment variables; the job has read-only permissions and commits nothing.
- **Tests**: no fixed sleep that assumes work finished in `crates/companions/tests/` (the sleeps are 5-50 ms poll intervals or writer pacing); no ignored tests.

## Area-level concerns
- **Nothing has run a real companion yet.** The fetch, extract, sandbox, supervise and configure chain is tested against fakes and a test binary. Real qBittorrent and Prowlarr have never been started under the cleared environment (no `HOME`, no `TMPDIR`) and the Landlock grants (no write to `/tmp`). .NET and Qt both expect some of that. CMP-G's install smoke is where this would show; treat the first pin PR as the first real test, not a data change.
- **Local processes are in the threat model in some places and not others.** qBittorrent's localhost bypass is turned off "so a process on the same machine must sign in too", and the pidfile and config writers defend against planted links, but the loopback port itself is trusted (CMP-01), and Prowlarr is left on whatever authentication mode it defaults to with only its bind address set. One written statement of what a local unprivileged process may and may not do would settle these consistently.
- **Three contracts written in CMP-0's README are unmet by their consumers** (CMP-03's data-folder check, the `taken` list, and the Prowlarr half of the sink in CMP-05). Each was handed to "a later slice" and no slice picked it up. A pass over the README's "must" sentences against callers would find any others.
- **`manager.rs` is 2,800 lines** holding the install state machine, recovery, the live operations, the health follower, the launch environment, the .NET runtime check and the supervisor adapter. The follower's run-counter and slot protocol is correct as far as I traced it, but it is the part most likely to break under a later change; it would be safer in a module of its own with its invariants stated once.
- **Update rollback assumes the companion's own data survives a downgrade.** A failed update points back at the previous version but keeps `home`, which the new version may already have migrated (Prowlarr's database migrations are forward-only). I found no decision on this and did not verify upstream behaviour; worth a line in CMP-G.
