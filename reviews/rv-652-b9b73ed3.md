## Findings

### 1. MEDIUM (security, plan-level): the tunnel-down phase checks routing into the tunnel, not gluetun's firewall
`infra/fleet/steps/vm/leak-test.sh:112-136`

- **Failure path:**
  - The test drops the WireGuard endpoint in the host's `DOCKER-USER` chain. Inside gluetun's namespace, the VPN interface and gluetun's policy routing (every unmarked packet goes to the tunnel's table) stay up.
  - So every down-phase probe is routed into the tunnel, encrypted, and sent as UDP to `ep_ip:ep_port`: IPv4 by name, TCP to 1.1.1.1:443, `dig @1.1.1.1`, and the UDP send. That is exactly the flow the capture filter excludes (`not (udp and host $ep_ip and port $ep_port)`), and DOCKER-USER drops it.
  - IPv6 fails because the default bridge has no IPv6 and the peer's AllowedIPs is IPv4 only, not because of the firewall.
  - So a gluetun whose firewall is off, or broken by a later image, passes every check. The only exception is the millisecond window while gluetun's health loop re-creates the interface.
- **Why it matters:** the plan's premise ("gluetun keeps running, so its firewall is what's tested", test plan 0d) doesn't hold. A leak test that passes is a precondition for crawling (OP-3b), and the risk it guards against (crawling from the Linode's own address when the tunnel interface goes away) is never exercised.
- **Proposed fix (runner's call):**
  - Keep the endpoint-block phase and add a **tunnel-interface-down** phase. From the throwaway probe image, take the interface down inside the namespace, for example `docker run --rm --network container:gluetun --cap-drop ALL --cap-add NET_ADMIN $PROBE_IMAGE ip link set dev <VPN interface> down`. That's gluetun's `VPN_INTERFACE`, `tun0` by default; verify this against v3.41.3. It removes the tunnel routes, so unmarked traffic falls through to the main table and `eth0`, and only the firewall stands in the way.
  - Rerun the same probes with the capture on the veth and require zero packets.
  - Then recover with `docker compose up -d --force-recreate gluetun`, and require a healthy tunnel and the same exit address.
  - Test it with the stubs, including a case where the stub "leaks" only in this phase.
  - If the runner defers it, the decisions file should say plainly that the endpoint block checks routing into a dead tunnel, not the kill switch, and OP-3b should carry the follow-up.

### 2. MEDIUM (correctness, a stated acceptance criterion): the mid-block checks fail open on a Docker error
- **Where:**
  - `infra/pia-bridge/deliver.py`: the new bootstrap line `if docker ps --filter 'name=^lodestar-collector' --format x 2>/dev/null | grep -q .; then exit {MID_BLOCK}; fi`;
  - `infra/fleet/steps/vm/leak-test.sh:73`.
- **Failure path:**
  - **deliver's check:** if `docker ps` errors, for example a daemon timeout or a "context deadline exceeded" error, its output is empty and `grep -q` fails. The check reads as "no collector", so the bootstrap goes on to `docker inspect` and restarts gluetun and Lodestar mid-block. I reproduced this: with `ps` returning 1 and inspect returning true, the stub log shows `restart gluetun` and `restart -t 60 lodestar`, rc 0.
  - **The leak test:** it has the same shape under `pipefail`, where `ps` failing and grep failing still make the condition false. It then force-recreates gluetun and blocks the endpoint under a live block.
  - The brief asked for fail closed (don't restart), and no test feeds a failing `docker ps`.
- **A further gap (LOW, for OP-3b):** "no collector running" isn't "no block". The arm switch stops Lodestar and starts the next collector (up to 10 minutes, test plan 0e), and between segments neither may be running. renew-vpn would then restart the tunnel mid-block, and the leak test, which also checks `lodestar`, could run in the gap. The arm-switch and collector scripts run detached and don't take `/run/lodestar-pia.lock`.
- **Proposed fix:**
  - `out=$(docker ps --filter ... --format x) || exit 30` in deliver (treat an unknown state as mid-block: "renewed; takes effect after the block"), and `|| { bad block_check; finish; }` in the leak test.
  - Do the same for the `docker inspect` of `lodestar` in the leak test: treat any answer other than `true` or `false` as unknown and refuse.
  - Add stub tests with a failing `ps`.
  - In OP-3b, have start-block write a durable block marker (removed at the block's end) that renew-vpn, the leak test and every step check, and have the detached block scripts take the VM lock around their container changes.

### 3. MEDIUM (correctness): a live step makes one SSH attempt just after opening its firewall rule
`infra/fleet/steps/run.py:126-127`

- **Failure path:**
  - `run_step` opens `job-<run>-<attempt>` and calls SSH once (`ConnectTimeout=15`).
  - deliver-pia retries rc 255 for 120 s (`SSH_ATTEMPTS_SECONDS`) because "the firewall rule can take a little while to apply" (`infra/pia-bridge/deliver.py`).
  - Linode applies firewall changes with a delay, so `run vm-status` and `run leak-test` will often report "couldn't connect, or its host key didn't match the pin" on a healthy fleet. They then close the rule and give up.
- **Proposed fix:**
  - Retry rc 255 every 5 s until a bound, for example 120 s, with the session timeout unchanged. The act job's 50 minutes easily covers 120 s + 720 s + the open and close.
  - A retry after a session lost mid-step meets the VM lock (`fail vm_busy` after 60 s), which is safe.
  - Test it with a fake SSH that returns 255, 255, 0 on a fake clock or a stubbed sleep, plus the bound case.

### 4. MEDIUM (tests: guards with no test, the recurring theme from #650): the leak test's meaning isn't pinned
`infra/fleet/tests/test_steps.py` (`STUB_DOCKER`, `STUB_TCPDUMP`)

- **Mutations that pass the whole suite:**
  - `probe()`'s `--network container:gluetun --cap-drop ALL` → `--network host` (the probes then test the host, not gluetun's namespace);
  - tcpdump `-i "$veth"` → `-i lo`;
  - the capture filter → `"not arp and not host $ep_ip and not ip"` (excludes all IPv4);
  - `resolves example.org 3 @1.1.1.1` → without `@1.1.1.1`.
- The docker stub skips everything before the image name, and the tcpdump stub ignores the interface and the filter.
- **Proposed fix:**
  - **The docker stub:** exit 99 unless every `run` carries exactly `--rm --network container:gluetun --cap-drop ALL <pinned image>`.
  - **The tcpdump stub:** record its argv, and have the test assert `-i vethabc123` (the veth from the `iflink` stub) and the exact filter string.
  - **The probes file:** assert `dig ... @1.1.1.1`, plus the UDP send's target.

### 5. LOW (deadline arithmetic): deliver's new restart isn't bounded or budgeted
`infra/pia-bridge/deliver.py`, the `bootstrap()` tail, `SSH_TIMEOUT`, `CLEAN_WAIT_SECONDS`

- **Failure path:**
  - `SSH_TIMEOUT = 180 + 480 + 150 + 60` (870 s) was sized for the lock wait, the cloud-init wait and the step. The restart adds `docker ps`, `inspect`, `restart gluetun` (10 s stop grace and start) and `restart -t 60 lodestar` (up to 60 s stop grace and start), with no `timeout` on any of them.
  - So the restart alone can take the whole 60 s margin. A wedged daemon leaves an orphan holding `/run/lodestar-pia.lock` indefinitely.
  - That breaks the documented invariant: "an orphan's remote bound (FLOCK_WAIT + CLOUD_INIT_WAIT + STEP_TIMEOUT, under SSH_TIMEOUT) ends before the deadline", and the clean wait sized from it.
  - A slow but successful restart is then reported as "the session didn't finish in time" and escalated, although the login was delivered.
- **Proposed fix:**
  - Wrap each docker call in `timeout` (for example 30 s for ps and inspect, and 30 s and 90 s for the two restarts).
  - Add a `RESTART_SECONDS` term to `SSH_TIMEOUT` and `CLEAN_WAIT_SECONDS`, and update the comment.
  - Check that `WORK_SECONDS` (1,320 s) still fits a whole session (it does: about 1,000 s).
  - Have the existing arithmetic test include the new term.

### 6. LOW (vacuous pass): a down-phase probe that never runs counts as "blocked"
`infra/fleet/steps/vm/leak-test.sh:119-124`

- **Failure path:**
  - `refute` passes on any non-zero exit. If `docker run` itself fails during the down phase (exit 125, for example no space for the container layer on Worker's 25 GB disk, or a daemon error), every down probe reads as blocked and nothing is sent.
  - The capture is alive and empty, so `no_egress_captured` passes, and with the other checks green the result is `ok leak_test`.
  - The up-phase controls ran a minute earlier, so this needs Docker to start failing between the phases. That's unlikely, but it's exactly the "probe that never sends" case.
- **Proposed fix:** run each down probe as `sh -c '<tool> ...; echo "rc=$?"'` and require that the marker came back, with the tool's own failure code (curl 6, 7 or 28; nc non-zero; dig 9). A probe without the marker fails with a new `probe_ran` name. Add stub cases for it.

### 7. LOW (P8 hardening): `S3Store` still falls back to a client without an owner
`infra/fleet/lock.py:82`

`S3Store(..., client=None)` builds a plain `boto3.client("s3")` with no `ExpectedBucketOwner`. Today's only constructor (`apply.live_context`) passes `OwnedS3`, but a later caller could bypass P8 without noticing. **Proposed fix:** make `client` required, or reject anything that isn't an `OwnedS3`, with a test.

## Verified sound
- **Command, step and VM input:**
  - the command, step and VM come only from the parser's allow-list;
  - unbuilt steps refuse before any network call;
  - the remote command is a constant (`sudo -n bash -c '<bootstrap>'`, where only `int(timeout)` and constant paths are interpolated);
  - step arguments are key- and value-checked before SSH, and are not used yet.
- **Targets:**
  - the address and host key come only from `fleet.json`;
  - the address must be canonical IPv4, not loopback, link-local, multicast, unspecified or reserved;
  - the key must be one ed25519 line whose fingerprint matches;
  - the per-run `known_hosts` holds exactly the pin, with `StrictHostKeyChecking=yes`, `-F /dev/null` and `BatchMode`.
- **Step files** are read with `git show <pinned commit>:infra/fleet/steps/vm/<file>`, after the HEX40 and ancestor-of-main checks. A fleet pinned before a step existed refuses.
- **The job `/32`:**
  - it is opened under the strict fence, and only for one IPv4 address inside `/meta`'s Actions ranges;
  - it is always closed in `finally` under the tolerant fence;
  - a half-opened rule set is closed;
  - a rule that won't close is escalated in the report;
  - `LockLost` propagates.
- **The VM lock:**
  - steps and delivery share `/run/lodestar-pia.lock` (flock, fd 9);
  - both take the fleet lock first, then the VM lock, so there is no lock-order inversion;
  - the waits are bounded (60 s and 180 s), and a busy VM answers `fail vm_busy` (21).
- **After a lost session:**
  - the remote side keeps running to its own `timeout` while holding the VM lock;
  - the EXIT traps (bootstrap and leak test) run on HUP, INT and TERM, and on SIGPIPE (tested);
  - so the endpoint block is lifted and tcpdump is killed.
- **The output allow-list:**
  - output is ASCII-decoded with replacement (so U+0085, U+2028 and U+2029 can't occur);
  - lines are split with `splitlines()`, so CR, VT, FF and FS–RS split, and each fragment must match on its own;
  - each line must match `re.match` with `\Z`, and NUL, ANSI escapes, tabs and spaces fail;
  - names are `[a-z][a-z0-9_]{0,40}`, and counts are 1–12 digits;
  - input is capped at 64 KiB and 200 lines, and stderr goes to DEVNULL;
  - the report can't form a `::` workflow command.
- **Masks:** each line of the key is masked, and the runner's address is masked once it has been validated.
- **The compose file:**
  - both images are pinned by digest;
  - the only port is `127.0.0.1:8090:8090`;
  - Lodestar uses `network_mode: service:gluetun` with `cap_drop: ALL` plus CHOWN, SETGID and SETUID, no NET_RAW or NET_ADMIN, and `no-new-privileges`;
  - nothing in the file is privileged, uses host network or host PID, or mounts the Docker socket;
  - nothing disables the gluetun firewall, `FIREWALL_VPN_INPUT_PORTS` is empty and no `FIREWALL_OUTBOUND_SUBNETS` is set;
  - TZ is `Etc/UTC`, and gluetun's `oom_score_adj` is −500.
- **P8:**
  - `OwnedS3` passes `ExpectedBucketOwner` on `get_object`, `put_object` and `delete_object`, including the conditional writes, and refuses other methods;
  - the owner value is checked as 12 ASCII digits;
  - every cloud-fleet job gets `FLEET_BUCKET_OWNER`;
  - the value is in the public-log leak test's secret list, and the LiveAct test asserts the fake `111122223333` is never shown;
  - the PR body names the secret for the owner.
- **The workflow:**
  - the only changes are env lines;
  - `permissions` are unchanged and minimal;
  - actions stay pinned by full SHA;
  - there's no OIDC or IAM widening and no PR-controlled string in `run:`.
- **renew-vpn:**
  - exit codes 30 and 31 don't collide with `pia-wireguard.sh`'s 10–16 or the 124–143 range;
  - `mv -f` swaps in a new inode, so a restart (not a running bind mount) is what picks it up, as intended;
  - between the gluetun restart and the Lodestar restart, Lodestar is left in the old namespace with no veth (no leak).
- **Tests use no network and no fixed sleeps:** `sleep` is stubbed in the VM-script tests, and SSH, S3 and Linode are fakes.
