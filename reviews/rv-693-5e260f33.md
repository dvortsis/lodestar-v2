## Important
- **I1: the "stop waits for the last look" claim isn't true in production.** The claim is in docs/decisions/2026-11-11-X-win-upd-window.md:8 ("The service's stop waits for that look") and in the comment at check.rs:595-597 ("so its last look ... always finishes"). But services.rs:903-906 (`Handles::shutdown`) does `stop.send(true); task.abort(); let _ = task.await;`.
  - **What the abort does:** it cancels the check task at its next yield point, which is `(&mut watcher.0).await` at the latest. Dropping the task drops `AbortOnDrop`, which aborts the watcher too. So the new await only holds in the tests, which stop without aborting. The decisions file's own mutation note says the same thing from the other side: the await guard isn't separable by a test.
  - **Experiment:** I added a temporary test that copies the services.rs sequence exactly: switch to Off, send the stop, abort, await, on a 4-worker multi-thread runtime. It ran 40 times per run, in 3 runs.
    - `task.await` returned before `request.json` was gone in 80 of 120 iterations (29, 27 and 24 of 40).
    - The file was still removed in 120 of 120. The blocking-pool work had already started, and `runtime.shutdown_timeout(RUNTIME_GRACE = 5 s)` (service.rs:963, main.rs:237) lets it finish.
  - **Failure scenario:** in production, Off saved just before a graceful stop is withdrawn only because the blocking work already started and the 5 s runtime grace lets it run, not because the stop waits. If the abort lands before the watcher has been polled at all, neither the change nor the last look runs, and the request survives. This is the I2 case, in a window of microseconds. The risk is tiny, but the record says the case is closed.
  - **Cheap fix in this PR (owned files):**
    - Reword decisions line 8 and the comment at check.rs:595-597 along these lines: "services.rs aborts the updates task right after the stop, so the last look is best effort: work already on the blocking pool finishes within the runtime's 5 s grace."
    - Add the not-yet-polled window to the Residuals list.
  - **Runner's call (services.rs is outside the owns):** whether `Handles::shutdown` should give the updates task a short bounded wait before it aborts, for example `timeout(1–2 s, &mut task)` and then abort. The abort is still needed, because a check under way may be mid-download.

- **I2 and concurrency.** `biased;` puts the settings branch first, the stop branch makes one more `settings_changed` call, and the check task awaits the watcher.
  - **No hang path:**
    - At a stop the watcher awaits only `blocking(settings_changed)`. That takes a brief `watch` read borrow and no mutex. `withdraw` is an atomic bump plus `remove_request`, which is bounded by about 1.07 s of retry pauses (5+20+80+320+640 ms) plus the syscalls.
    - The watcher always exits. The stop branch returns, and so does a `settings.changed()` error (sender dropped). `stop.changed()` also resolves when its sender is dropped.
    - The check task's `checks` future returns at its stop arms. A check under way was already waited for (or aborted) before this change.
    - In production, services.rs aborts the task anyway, so nothing new is added to the SCM stop timeline (STOP_WAIT_HINT, runtime grace 5 s).
  - **No double removal or helper race:** the last look withdraws only on a not-Off→Off transition it hasn't handled. The watcher runs those looks one after another, never in parallel. A second removal finds the file gone (NotFound), which is ignored. Epoch ordering against an install is unchanged.
  - **New test `a_switch_off_just_before_a_stop_still_withdraws`:** the mutant with no `biased` and no last look (the pre-fix select) is killed in 2 of 3 runs, as expected for an unbiased select.
- **The two accepted mutants survive, as the session said** (both 3 of 3): no last look at stop, and drop(watcher) in place of the await. I found no cheap test that kills them. The experiment above shows the await isn't what production relies on in any case.
