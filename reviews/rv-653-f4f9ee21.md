## Findings

### BLOCKING

**B1. After a failed hand-over, the only way forward is a paste, and the paste destroys the only copy of the password qBittorrent now uses. The user is locked out of their own qBittorrent.**
- Where: `crates/lodestar/src/companion_wiring.rs:1063-1100` (paste), `:1102-1110` and `:928-946` (plan and `temporary()` need provenance `pasted`), `:1159-1166` (confirm needs a plan), `:1243-1259` (apply and hand-over failures return with the generated password kept).
- How it happens:
  1. Confirm runs. CMP-8b's apply sets `web_ui_password` to the generated password first (`configure/qbittorrent.rs`, "The password first"), so qBittorrent now uses it.
  2. A later step fails: a refused category or save path, a dropped connection, or a Sink save error. Confirm returns an error. The companion row holds the generated password, marked `generated`, and there's no `origin` row.
  3. Plan now answers `no_temporary_password`, because the provenance isn't `pasted`. Confirm answers `confirmation_mismatch`, because the plan was used up. That leaves two routes, and both delete the password: paste overwrites it, and forget removes it.
  4. The user does the natural retry and pastes the temporary password again. `not_added` passes, because there's no origin row. The provenance becomes `pasted` and the row is overwritten with the temporary password, which qBittorrent no longer accepts. The generated password is gone from Lodestar, and the next plan fails with `companion_unauthorized`.
  5. Recovery means stopping qBittorrent and editing `qBittorrent.conf` by hand. Our audience (§2.14) may not know how.
- The PR's own test stops one step short of this. `a_failed_apply_or_hand_over_keeps_the_generated_password` (`companion_wiring_guided_tests.rs:775-814`) ends with qBittorrent holding the generated password after a refused hand-over. One more `g.paste(...)` there loses it.
- The decisions file says "pasting again recovers". That's true only when qBittorrent never took the new password, and the server can't tell the two cases apart. Nothing warns the user and nothing can be undone; only a password-gated reveal before the paste saves them.
- Suggested fix (either works):
  - (a) Paste refuses with `409` (say `generated_kept`) while the provenance is `generated` and there's no origin row. The message points to reveal, or to forget for a deliberate discard.
  - (b) Allow a retry that signs in with the stored generated password: `temporary()` also accepts `generated` without an origin row, and only the apply's remaining steps and the hand-over run again.
  - Either way, extend the failure test so it shows a paste after a refused hand-over is refused (or that the retry hands over), and that the generated password survives.

### LOW

**L1. The guided steps and forget race CMP-5's first install, so a pasted value can end up revealable.**
- Where: `companion_wiring.rs:883-897` (`handed_over`), `:1285-1292` (forget) and `companions.rs:634-636` (`revealable` returns early for an installed companion). They check only `Service::installed`, the journal's *installed version*. The guided lock doesn't cover CMP-6's install or remove.
- How it happens:
  1. During a first native install of qBittorrent, after the manager's `Credentials` step has stored the generated row but before the journal records the installed version, a paste passes `handed_over` and overwrites the row with the pasted value.
  2. The install finishes with the generated password in memory, so the config file has it. `installed()` is now true, and `revealable` opens the row without looking at the provenance. The pasted value is revealed, which breaks Q5's rule that a pasted value is never revealed, and the real password is lost.
  3. Forget during the same window deletes the new credential row of a companion that's mid-install.
- It needs the admin to act concurrently, and the value leaked is one they pasted themselves.
- Fix: refuse (`installed` or `busy`) when any journal record exists (`state::load` is `Some`, including one with an op in progress). Cheap hardening on top: in `revealable`, an installed companion whose provenance row says `pasted` reveals nothing.

**L2. A wrong temporary password gets Lodestar's address banned by qBittorrent after three plans.**
- Where: `companion_wiring.rs:1130-1135` (the held random password) and CMP-8b's `sign_in`, which `plan_inner` calls with `temporary_first = false` (`configure/qbittorrent.rs:359-381`, `:563`).
- How it happens:
  1. Every plan tries the held password first. It's a fresh random value, so that attempt always fails.
  2. With a wrong paste, the temporary password fails too: two failures per plan. qBittorrent clears its per-address counter only on a successful sign-in.
  3. So plans at t=0, 60 s and 120 s reach five failures, and qBittorrent bans the address for an hour by default. On a native loopback setup that address is also the user's own browser.
- The decisions file's "a stale page can't run up a ban" holds only for a correct password.
- Fix: avoid the guaranteed-failing attempt in the guided plan (try the temporary password first), or slow plans down after `companion_unauthorized`. At least, correct the decisions file and make sure `banned_after_failed_sign_ins` has a plain message.

**L3. After forget, the download-client source reads "Needs qbittorrent" even though its Integrations entry still works.**
- Where: `companion_wiring.rs:1277-1311`.
- Forget keeps the `lodestar-qbittorrent` entry (as documented). But CMP-5g-1's gate counts only entries *other than* `lodestar-qbittorrent` as `external_client`, and the record is gone. So once companions are on, the source is gated even though the client it uses still works.
- Fix: document it, or remove or rename the managed entry when you forget the companion (with consent).

**L4. Regenerate now reaches the live adapter for an added companion.**
- Where: `companions.rs:896`. The gate went from `installed` to `generated`.
- Today `live` is `Unwired`, so the answer is `not_wired`. Once CMP-5g-3 wires `live.regenerate` for supervised companions, a guided qBittorrent marked `generated` would rotate the stored password with no CMP-8b apply and no Sink save, so the password Lodestar holds and qBittorrent's would drift apart.
- Fix: keep regenerate on `installed`, or record this as a constraint for CMP-5g-3.

## Item 1: qBittorrent's `admin` account (judged on its merits)

**Not a security regression, and it doesn't need the owner.**
- CMP-3's `lodestar` user name applies to installs where Lodestar writes `qBittorrent.conf` itself. The temporary password a guided qBittorrent prints is for `admin`, so `lodestar` could never sign in.
- Q19 asks for the temporary password to be replaced by a generated one, and it is: CMP-8b's apply sets a 32-byte random password and then confirms it signs in. The user isn't asked to change the password; Lodestar rotates it.
- The user name isn't a secret. `admin` is qBittorrent's own default, and the password's strength is what protects the account.
- The generated password is revealable only behind CMP-6's fresh-password confirmation.
- Renaming the account is a reasonable later refinement, the runner's call under §2.19. One caveat: a user who already renamed qBittorrent's account can't use the guided flow, because there's no user name field. That's a UX gap, not a security one.

## Security

- **Server-side request forgery (SSRF): OK.**
  - A typed URL goes through `EnteredUrl` (http/https only; no user info, query or fragment; length-capped), then `net::check_url` with `download_client()`.
  - At connect time, `CompanionHttp`'s `entered` client is a `GuardedClient` with the same policy. It checks every DNS answer (rebinding) and follows no redirects (3xx comes back as a status, and `Location` is never read).
  - Fixed targets use `LocalOnly`, which allows private and loopback answers only.
  - A stored URL isn't checked again when read, but every connection is.
  - Mutation M3 shows the early check is tested. The connect-time guard also kept `a_refused_address_writes_nothing` green with the early check removed: real defence in depth.
- **Credentials: OK.**
  - The paste value appears in no response, error body or log line, and the OpenAPI example is a placeholder. `Debug` is redacted, and a 422 body names the field without the value. The API tests capture logs and scan the document.
  - Failure logs carry codes only (`failed()`, CMP-8b's `config_failed`).
- **Reveal: OK, apart from the install race in L1.**
  - The reveal route is unchanged: a session plus `confirm_fresh_password`, `no-store`, and an audit event.
  - The new `revealable` reads the provenance and the sealed row in one `settings_with_prefix_raw` query.
  - Provenance can't be forged through the API: the settings registry writes only `settings.<section>.<field>` keys, and the `companions.*` rows are written by CMP-5g-2's code alone. Mutation M2 is caught.
- **Auth and CSRF: OK.**
  - Every route is in `auth::protected`, the same as `/companions`: a session only, so an API key or a proxy header gets 401.
  - Every handler calls `same_origin_json`, which requires JSON (forcing a CORS preflight) and a matching Origin.
  - The API tests cover no session, every API-key form, a proxy header and a cross-origin page.
- **Input bounds: OK.**
  - Paste: 1–128 bytes, no `char::is_control`.
  - URL: capped by `ENTERED_URL_MAX`.
  - `settings` and other bodies: axum's 2 MB limit through `extract::Json`.
  - Ids are checked twice (API and binary).
  - Stored rows are read strictly, at most 4 KiB.
- **Locking: OK, apart from L1.**
  - Guided changes use `try_lock` on a tokio mutex, so the answer is 409 `busy`, never a wait, and there's no deadlock. Detection has its own lock.
  - The lock is held across network I/O, but every request has `Limits` timeouts and the whole of `CompanionHttp::send` is under one deadline, so it's bounded. Others are refused, not queued.
  - A dropped request mid-confirm is documented (and is part of B1's exposure).
  - Mutation M1 is caught.
- **Sign-in limits: one plan a minute and one confirmation per plan.** A mismatch is refused before any sign-in. Mutations M4a and M4b are caught. See L2 for the wrong-password ban.
- **Secrets on disk:** nothing new beyond CMP-3 and CMP-6. Credentials are sealed with `SecretStore`. The target, origin and provenance rows aren't secret, and `EnteredUrl` keeps credentials out of the URL row. **No new key file was found:** `git status` stayed clean after the tests.
- **Availability:** B1 (lockout) and L2 (ban) are the open security-adjacent risks.

## Correctness

- **The state machine works as documented** (target → paste → plan → confirm → forget, and `already_added` after confirming), except for the dead end after a failed apply or hand-over (B1).
- **Detection:** probes run concurrently in a `JoinSet` under `tokio::time::timeout(detect_cap)`, then `abort_all`. Each probe keeps its own `Limits::PROBE`. The 15 s cap is a field, shortened in tests. The test that probes run at once uses a barrier.
- **Error codes:**
  - They match the conventions: 409 with a stable code, 400 `bad_value` and `bad_template_input` with `field`, 429 with `Retry-After` of at least 1, and 503 `companions_unavailable`.
  - The OpenAPI response lists match the code.
  - CI's `openapi.json drift` and `web` jobs (`api:types` diff) pass.
