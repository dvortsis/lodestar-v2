## Blocking

1. **The new "does not rewrite the live region" test is vacuous, and it waits with a fixed sleep.**
   - Where: `web/src/lib/features/restart/watch.test.ts:94-107`.
   - The sleep: line 105, `await new Promise((done) => setTimeout(done, 50))`, assumes the effects have run. That is a sleep that assumes work has finished (runner/standards.md §2, Blocking per §113).
   - Why it can't fail: line 95, `api.get.mockResolvedValue(system([...]))`, returns the *same object* on every refresh. `system` is `$state.raw`, so assigning the same reference doesn't trigger the effect, and the round-2 scenario (a new but identical `/system` response) is never exercised.
   - Verified:
     - with the guard at `watch.svelte.ts:55` removed, the test still passes;
     - with the mock changed to `mockImplementation(async () => system([...]))` (a fresh object each time), the same mutation fails the test, and the real code passes.
   - Fix:
     - use `mockImplementation(async () => system(['network.dht_port']))`;
     - replace the sleep with `await tick()` (or `flushSync()`) from `svelte` after the refreshes, which deterministically flushes the effects.

2. **"Settings messages (on demand)" was loosened from 4 KB to 4.9 KB, and nothing records or explains it.**
   - Where: `web/.size-limit.mjs:1320`, changed in 2f9b9f6e4 next to the banner's own 4 KB → 4.9 KB, which looks like a replace-all of `'4 KB'`.
   - That entry measures `features/settings/form/message-maps/*.ts`, which this PR doesn't touch. It measures 3.99 KB, so the old limit still passes.
   - It's outside the runner-approved shared edit, which covers the restart entries. The decisions file and the PR description don't mention it, and it hands 0.9 KB of unreviewed headroom to another slice's budget.
   - Fix: restore `'4 KB'`.

## Important

3. **At 0:00 the prompt sends the tab "back" when the address was *kept*.**
   - Where: `AddressPrompt.svelte:47-49`.
   - The code returns only for `answered && state === 'awaiting_confirmation'`. Any other answer, including `address_change: null` (what the server reports after a Keep, `address.rs:777-784`), falls through to `goBack(previousUrl)` when `restart.available`.
   - Scenario A: the browser clock is ahead, which is exactly the case round 3 targets. The prompt sits at 0:00 and re-checks every 5 s. The address is kept from another tab or device. Within 5 s this tab shows the full-page, inert "Restarting…" for the old address.
     - Reproduced in a scratch e2e on `/`: the deadline was 10 s in the past by the browser's clock, the server still waited, I flipped `/system` to `address_change: null`, and `restarting-page` appeared.
     - In production the old address never goes down from this origin's view. `waitUntilDown` runs its full 2 minutes and then says "Lodestar hasn't come back after 2 minutes", while Lodestar is fine.
   - Scenario B, in the same tab: a 0:00 check's `GET /system` is in flight when the user presses Keep. `answer()`'s `restart.refresh()` joins that in-flight promise and gets the pre-Keep answer, so the prompt stays. The next check, 5 s later, sees `null` and goes back.
   - A single failed `/system` (`!answered`) also goes back at once, while the server may still be waiting.
   - Fix:
     - go back only on `state === 'reverted'` (with `available`), and treat `null` as kept, which hides the prompt;
     - count "stops answering" as two or three consecutive failures, or as a failed `/healthz`;
     - add unit tests for `null` after 0:00 and for one transient failure.

4. **The 72 px lift clears Save mid-page, but no space is reserved, so at the end of a page on a phone the tray covers the last control and part of the save bar.**
   - Where: `RestartBanner.svelte:104-113`. Nothing adds bottom padding or `scroll-padding-bottom` while the tray shows. Round 2 listed reserving the tray's height as part of the fix.
   - Scratch e2e at 390 × 800, scrolled to the end:
     - `/settings/crawler`, not dirty: the last switch ("Automatic", y 646) is 67% covered. `elementFromPoint` at its centre is the tray, and it can't be scrolled clear.
     - Dirty: the sticky bar settles in-flow at y 720–760. The tray (y 654–728) covers 20% of Save and Discard, and 78% of the last field ("Options for Fetch timeout").
     - 1366, and `/settings/network` at both widths: nothing covered.
   - The banner can stay up indefinitely: when the server can't restart itself, it stays until the container is restarted.
   - Save's centre is still clickable, and focus isn't entirely hidden (2.4.11 AA passes), but the last control of a Settings screen needs a tap on its label or the keyboard.
   - The lift also couples to the save bar's height. The bar is `flex-wrap` (`SaveBar.svelte:51`), so a longer message, zh or text zoom can wrap it past 56 px.
   - Fix:
     - while the tray is mounted, set `padding-bottom` (or `scroll-padding-bottom`) on the body or main to the tray's measured height plus its offset, through a `ResizeObserver` or a CSS variable the tray sets;
     - alternatively, read the save bar's real height instead of assuming 56 px;
     - extend the e2e test to the end of the page at 390.

5. **The screen-reader line always says "after about 5 minutes".**
   - Where: `AddressPrompt.svelte:83-86`, `messages/en.json` and `zh.json` `restart_keep_countdown_sr`.
   - On the new address, the prompt shows up to 30 s after load, or later after a reload, and at 0:00 it stays while the server re-checks. A screen-reader user who reads the line at 0:40, or at 0:00, still hears "after about 5 minutes", and the real time left is hidden from them (`aria-hidden`).
