## New findings

### LOW-A: a 3010/1641 rollback reinstall still lets the failed version run on the restored store, and a local user can cause it
- **Where:**
  - `rollback.rs:689-696`: the 3010 branch's `set_start(Disabled)` and `stop_service()` are both `let _`.
  - `rollback.rs:703-712`: the step-5 wait returns `Retry` without disabling or stopping again.
  - Background: the marker is removed at step 3 (`:625`), before the reinstall.
- **Who can do it and how:**
  - **The attacker** is a local unprivileged user. `%ProgramFiles%\Lodestar` inherits Users: Read & execute, because `main.wxs` sets no permissions on INSTALLFOLDER.
    - While a rollback is in progress, the user starts `lodestar.exe` in a loop of short-lived runs, or once with `CREATE_SUSPENDED`.
    - They time it so `wait_free` (polling every 200 ms) sees a gap. Their process then holds the image when msiexec reaches InstallFiles, after the hash, `sc stop` and `tasklist`, a window of a few seconds.
  - **What follows:**
    - Windows Installer queues the replacement for reboot and returns 3010.
    - The MSI's `ServiceControl Start="install"` starts the service from the old file, which is the failed `to`.
    - The marker is already gone, so `to` opens the restored store and can migrate it again before the helper's next run disables it.
    - After the reboot, `from` finds a store it can't read. The rollback reports `healthy: false`, and the journal is cleared.
  - **A compromised `NT SERVICE\Lodestar`:** if it is running again as that `to` instance, it can ignore `SERVICE_CONTROL_STOP`. `stop_service` then fails silently, `done = 4` is saved anyway, and nothing tries to stop it again before the reboot.
  - The decisions file flags this as a residual risk that "needs a file held by something else". Any local user can be that something else.
- **Why only LOW:**
  - It needs a rollback already under way: a release that fails probation, or a compromised service account crashing during probation.
  - There's no privilege gain. The only effect is availability: the newly taken pre-migration snapshot keeps the data recoverable.
  - This round already narrows the window. Before it, step 5 started `to` right away.
- **Fix (two parts):**
  1. **Keep the marker until step 5** and remove it just before `set_start`/`start_service`. A `to` started by StartServices then refuses at `service.rs:120` before it opens the store. The SCM's restart failure action finds the service disabled. The recovery text for steps 3 and 4 would need to say the marker stays.
  2. **Run `stopped(sys)?` in the step-5 wait branch on every pass,** and treat a failed disable or stop in the 3010 branch as `Retry` (save `done = 4` first). A failed best-effort call then gets retried and isn't lost.

### LOW-B: a reinstall waiting for a restart can wait forever with the service disabled
- **Where:** `rollback.rs:703-712`.
- **What happens:** if a restart doesn't put `from` in place, every boot run returns `Retry` with "waiting for Windows to restart", and the service stays disabled. This happens if the pending rename was cancelled or failed, or the image is still `to`. The rollback never halts, and the Event Log never gets the recovery steps.
- **Who can do it:** I found no attacker path. `PendingFileRenameOperations` is HKLM, writable only by admins. SMSS replaces the files before any user process runs, so a local user can't hold them. A crash or power loss doesn't cause it either. This is availability under abnormal conditions, rated as asked for "permanently disabled".
- **Fix:** record a boot identity in the journal with the 3010, such as the boot time from `GetTickCount64`, or a flag that only `--resume` clears. Halt with recovery steps when a later boot run still sees `to`.

### LOW-C (predates this round, missed in my last report): a local user can block updates indefinitely, and hold a rollback pending
- **Where:** `cli/update_helper.rs:169-181` (`wait_free`) and `helper.rs:647-649`. Since this round, `rollback.rs:640` also resets `copies` on every refusal.
- **Who can do it and how:**
  - **The attacker** is a local unprivileged user who keeps any `lodestar.exe` process alive. Running it, starting it suspended, or opening it with share-read only all work.
  - **What follows:**
    - `wait_free`'s open for writing fails, and after 120 s the copy refuses with `program_files_in_use`.
    - **A forward install** becomes `copy_refused`: the service is started again and the update is never installed, which also blocks security fixes.
    - **A rollback** becomes `rollback_pending` with the service disabled until the next run, usually the next boot.
    - The refusal resets `copies`, so the user can repeat this forever and it never halts.
  - **Limits:** the user must be logged on during every helper run. Each refusal is in the Event Log, and an administrator can still install by hand.
- **Why only LOW:** it's availability only, it needs the attacker present all the time, it's visible, and it's outside this delta.
- **Fix:** have the copy wait only for its parent helper process. The service's own processes are already excluded by `stopped` and `no_service_processes`. For example, pass the parent's PID and wait on a process handle with `SYNCHRONIZE`. Any other holder is then left to Windows Installer, which queues the replacement and returns 3010, a path this round handles. Combined with LOW-A's marker fix, a local user then gets nothing from holding the file. A follow-up task is reasonable.

## The other security-relevant changes in this round

- **`deny_unknown_fields` dropped:**
  - **An attacker who can write the journal gains nothing:**
    - Every type is a plain struct or an internally tagged enum, with no `flatten`, `untagged` or aliases.
    - serde still rejects duplicate fields.
    - Unknown keys are dropped and never reach a path, a command line or a decision.
  - **The ACL assumption still holds:**
    - The journal and `msiexec-result.json` live in `%ProgramFiles%\Lodestar\updates`.
    - Every `rollback::read` runs after `secure_staging`, which checks the ACL and scans for reparse points: in `run()` at `helper.rs:315-320` (and inside `resume`), and in `run_copy` at `:626-632`, now with staging pinned first.
    - SYSTEM writes the journal by temporary file and rename, so it inherits staging's ACL.
  - **Dropping it removes a real DoS.** After a reinstall, `from`'s helper reads the journal that `to`'s helper wrote. With `deny_unknown_fields`, any field added by a future `to` would make that journal unreadable, and the service would stay disabled for good.
  - **One inaccuracy in the decisions file (informational):** it says `touched` and `reinstall_restart` "follow" the contract that new fields are safe to ignore. They wouldn't be: a helper ignoring `reinstall_restart` would start `to` in step 5. They're safe only because no released helper has journal code without them. Better to say that, so the contract isn't read as already proven for these two.
- **`touched`:**
  - It's saved before the first change to the service (`rollback.rs:588-592`). A crash after that resumes the rollback.
  - `halt` keys on it, not on `start_before`, which is now recorded at install time.
  - It's only writable through the journal, so no new input.
- **Recorded start type:**
  - It's read before the stop, and `Disabled` or an error records none (`helper.rs:475-480`).
  - It's restored on a pass (`rollback.rs:371-375`), in step 5, on a refusal and on an interrupted install.
  - The service's DACL is the default, and `main.wxs` sets no ServiceConfig permissions. So only SYSTEM and Administrators can set what gets recorded, and the service account can't use this to set its own start type.
  - Not restoring `Disabled` is a choice for the correctness reviewer, not a security issue.
- **`msiexec.lock` created after staging is checked and pinned (`helper.rs:626-631`):**
  - This is strictly better. Before, the copy created a file by path in staging before checking it.
  - `copy_running` now opens with `create(false)`, and `NotFound` counts as not running. A copy that has started but not yet taken the lock is still covered: the run can't remove the copy's running image (`rollback.rs:241-250`). The longer pre-lock window (`secure_dir`'s scan) adds no exposure.
  - The early `copy_running(ctx, None)` (`helper.rs:305`) runs before `secure_staging`. It no longer creates anything there, which is also an improvement.
- **`take_result` records the answer before removing the file (`rollback.rs:186-207`):**
  - A failed journal write leaves both the file and the old journal. The next run then either takes the file again or, through a fresh copy name, discards it as a mismatch.
  - The stored `answer` isn't matched against `msi` again. That's not reachable: every path that sets a new `msi` starts with `answer = None`, and only SYSTEM or Administrators write the journal. Matching it again would still be cheap defence in depth.
- **An unfinished msiexec writes no answer (`helper.rs:589-600`, `:670-685`, `:1128-1147`):**
  - It changes nothing that runs, only who judges the result: the program on disk, or a fresh, bounded copy.
  - An unprivileged user or the service account can't kill the SYSTEM copy or msiexec, or force a 90-minute hang.
  - `ExitStatus::code()` is always `Some` on Windows, so `Interrupted` effectively never happens.
- **At most 3 fresh copies (`rollback.rs:643-650`):**
  - A copy fails to answer only through its own failure (a crash, power loss, a 90-minute hang) or through staging that SYSTEM or Administrators changed. Neither an unprivileged user nor the service account can cause either one.
  - The halt is the documented final stop, with recovery steps.
  - Three power losses in a row during msiexec would end in that halt (service disabled, recovery in the Event Log). That's acceptable and rated informational.
  - Filling the disk halts sooner through `save`, as before this round.
- **3010/1641 on the reinstall:** see LOW-A and LOW-B. The direction is right, and it narrows a window the previous head left wide open.
- **Logs:**
  - Nothing new is secret. The new messages carry paths (staging, the data folder, the marker) and io errors.
  - The refusal from `refuse_during_update_rollback` reaches `%SystemRoot%\Temp\lodestar-service.log` as before: paths only.

## Not security (for the correctness reviewer)
- **An unfinished install can finish later.** After an unfinished msiexec on a forward install, if Windows Installer's server side is still running, the next run (started at once by the copy's `start_task`) can find `from`, clear the journal and start the service. The install may then finish later with no probation.
- **A copy can be counted as running after it answered.** When no answer is written, the copy calls `start_task` before it exits. If the new run reaches `copy_running` first, the copy's image can't yet be removed, so the result is `HandedOff` with nobody left to start the task. It stalls until the next boot. With an answer the race doesn't matter.
- **An error from `try_wait` after msiexec started** is classed as `msiexec_not_started` and answered as a refusal, although msiexec may still be running. This is rare.
- **`inside_staging` is case-sensitive** (`Path::starts_with`). If the install path is spelled differently between the run that wrote the journal and a later one, the check fails closed into "journal.json can't be read", with the service disabled. Every run uses the task's registered path, so it's unlikely.
