# Review: PR #756, X-dht-lookup-converge, head 3f950dffab73770e7849e57ed7d19f2098a81e02

Reviewer: a fresh, independent reviewer (read-only; no pushes, comments or messages).

## Summary

The PR fixes two real causes of empty early lookups:
- **Parking:** owned `get_peers` requests wait in the existing bounded queue until the bootstrap settles, a table reaches K, or `PARK_DEADLINE` (30 s) passes.
- **The join refresh:** once per start, per family, one `find_node` per prefix level above the closest neighbour, capped at 32 levels and paced at ≤ 8 maintenance lookups.

The design is sound:
- Parking is bounded in time twice: the self-lookup's own `LOOKUP_DEADLINE` (25 s) and `PARK_DEADLINE` (30 s).
- It's bounded in number by `MAX_GET_PEERS` (32).
- It releases FIFO and exactly once.
- Shutdown hands back the queued requests' permits.
- No router is asked on a request's behalf.
- The join refresh is bounded and once per start.

The tests are deterministic and catch both requested mutations.

One correctness hole remains, in exactly the case the second commit ("Settle the bootstrap per family") was written for. "Every self-lookup has ended" is judged while `start_bootstrap` is still creating the round's lookups. So a family that ends at once **before** the other family's self-lookup exists settles the whole bootstrap. With `dht.bind = ["[::]:6881", "0.0.0.0:6881"]`, a config the validator accepts, on a host without working v6 (or with no v6 router), parking is off from the first instant. I confirmed this with a test. It is no worse than `main`, but it's the scenario the decisions file says is handled, and the fix is small. Hence CHANGES.

## State-machine analysis

**State:**
- `bootstrapped: bool`, false at start and set once, never cleared;
- `join_planned[f]`;
- `join_refresh: Option<Vec<(family, target)>>`;
- `Lookup::bootstrap`.

**Parking:** `parks_lookups(now) = !bootstrapped && routers resolved && every table < K && now - epoch < 30 s`. It's evaluated on each pop of the `maintain` queue loop.

**Transitions into `bootstrapped`:** these happen only in `finish_lookup`, the single removal path for lookups. The deadline, `is_done`, budget exhaustion and cancellation all route through it. `bootstrapped` is set when a bootstrap lookup ends and either:
- (a) its family's table is non-empty; or
- (b) no other bootstrap lookup remains in `self.lookups`.

**Liveness (can parking stick?):** no.
- A self-lookup is a maintenance lookup with `LOOKUP_DEADLINE` 25 s.
- Stalled lookups are re-driven every tick by `scrape_tick`, which runs unconditionally and checks `finish_if_due`.
- Router queries carry `extra_in_flight` and time out at `query_timeout`.
- `PARK_DEADLINE` is an independent wall-clock bound.

The probed cases:
- No routers resolved: no parking.
- All routers refused at send: both lookups end inside `start_bootstrap`, and the last one sets (b).
- All silent: they end at timeout or deadline.
- Node shut down while parked: `run` breaks, then `release_permits` returns every queued permit; dropped replies tell the pool it was cancelled.
- Paused: the queue loop doesn't run, and `SetPaused` drops queued owned requests, as before.

**Boundedness:** the queue is shared with `GetPeers` and is capped at `MAX_GET_PEERS` (32), counting active requests. A flood is refused at admission (`peer_rejected_capacity`) or held by the pool's permits, as before. Parking adds no memory.

**Release order:** FIFO `pop_front`, one at a time, up to `MAX_GET_PEERS` active, exactly once. Requests whose caller closed are dropped by `drop_cancelled_queued` and permit-counted.

**Per family:**

| Case | Behaviour |
|---|---|
| v4 only | (a) or (b) on its single lookup. Correct. |
| v6 only | Same. Correct. |
| Dual stack, v4 listed first, v6 dead or no v6 router | v6 ends inside `start_bootstrap` after v4's lookup exists, so (b) is false and parking holds until v4 ends. Correct; this is the PR's test. |
| **Dual stack, v6 listed first, v6 dead** | v6's lookup ends inside its own `start_lookup_as → drive_lookup → finish_lookup` before the loop has created v4's lookup, so (b) is wrongly true. **Wrong** (finding I-1). The mirror case is the same: v4 listed first with v4 unroutable on a v6-only host. |
| Both dead | The last to end sets (b): at once, at `query_timeout`, or at 25 s. Requests end empty as before. Correct. |
| A family fills, then empties | `bootstrapped` and `join_planned` stay set. There's no new parking or join refresh; the existing thin-table re-bootstrap takes over. That's the intended "once per start". |

**Untrusted input:**
- Hostile responders can't hold parking open past `min(25 s self-lookup deadline, 30 s PARK_DEADLINE)`. Feeding ever-closer fake nodes only keeps the self-lookup busy until its deadline.
- They can settle early, for example a router that answers with no nodes but is itself inserted. That's the old behaviour.
- A planted node sharing a long prefix with our id can push the join refresh to at most `JOIN_LEVELS` (32) lookups, each bounded by the lookup rules.
- A hostile router listing only far nodes shrinks the refresh, which costs nothing.

**Join refresh:**
- It's planned once per family, on that family's first self-lookup that ends with nodes.
- It's drained after the turn's released requests, while maintenance lookups are fewer than 8 (`MAX_LOOKUPS / 2`). That leaves 8 slots for the stale-bucket refresh and the re-bootstrap. Owned lookups don't count.
- Queries go through `try_query`, so through the shared `query_rate` bucket; throttled sends are retried, not dropped.
- Cost: on a ~2^23-node DHT the closest neighbour shares ~23 bits, so ~23 lookups of 8–20 queries each, about 180–460 queries. That's consistent with the claim of 200–450, with a hard ceiling of 32 lookups.
- It holds lookups in flight for a second or two, so it delays a re-bootstrap (`lookups.len() == active_scrapes`) by that long. Harmless.

**Concurrency:** the actor is single-threaded and owns its state. There are no locks and no awaits in the changed code, and all new transitions are synchronous inside `finish_lookup`/`maintain`. Cancellation safety is unchanged: the `select!` arms call sync methods only.

**routing.rs:** `join_targets` takes the max `prefix_len` over the entries. It returns `0..min(closest, max, 159)` targets, each placed with `id_in_bucket`, so each is exactly at its level. It's bounded and correct; the unit test checks the levels and the cap.

**Goldens:**
- The re-blessed deltas are explained: the join refresh changes the query sequence, so the RNG paths diverge, and the 8-seed means fall within the spread in both directions.
- `restart-honoured`:
  - Every honour invariant still holds: `samples_in_suppression=0`, `sampled_before_expiry=0`, `fresh_nodes_sampled=0`, `resampled_after_expiry == expiring_in_leg2` (954), `reason=resumed` and `first_sample_after_start=2s`.
  - `restart.rs`'s assertions on these pass.
  - Leg 2 stored/min is 27.7 → 27.9.
  - The added `stream_*=0` lines are new zero counters, which the golden check ignores by rule.
  - `sealed 1 → 0` is one in-flight sample at the stop; it's path noise.
- No regression is hidden.

## Findings

### Blocking
None.

### Important

**I-1. A family whose self-lookup ends at once settles the bootstrap if it comes first in `dht.bind`.**
- **Where:** `crates/dht/src/node/actor.rs:2138-2141` (`others_out`), together with `start_bootstrap`'s loop at `actor.rs:2260`.
- **Scenario:**
  - `config.toml` has `dht.bind = ["[::]:6881", "0.0.0.0:6881"]`. The validator accepts either order (`node/mod.rs:1058-1064`), and `docs/operations.md` §4.4 only shows an example order.
  - The host is Docker in bridge mode with no v6, or no router resolves to v6.
  - At start, family 0 (v6) gets its self-lookup, which has nobody to ask and finishes inside `start_lookup_as`. v4's self-lookup hasn't been inserted yet, so `others_out` is false and `bootstrapped = true`.
  - Parking is then off from the first tick, and the restored queue's requests start against an empty table and end empty: shape A, with 120 s of `retry_backoff`. The same happens with the default v4-first order on a v6-only host where v4 is unroutable.
- **Impact:** this is the exact case the decisions file (§A, "judged per family … fresh-review finding") says the PR handles. The per-family rule's correctness depends on an arbitrary, user-visible ordering. It's no worse than `main`, but it's a hole in the stated invariant, in untested code.
- **Reproduced:** a variant of `a_v6_family_without_a_router_doesnt_end_the_parking` with the v6 family inserted at index 0 fails on `assert!(!a.bootstrapped)`.
- **Fix:** judge "every self-lookup of the round has ended" only once the round is fully created. Either:
  - In `start_bootstrap`, create every family's lookup first (`insert_lookup`, mark `bootstrap`, send the seed queries), then `drive_lookup` each. Or:
  - Keep a `bootstrap_starting: usize` set to `families.len()` before the loop and decremented as each is started, treat it as "others out" in `finish_lookup`, and after the loop, if no bootstrap lookup remains and `!bootstrapped`, set `bootstrapped = true`. Without that last step, the case where every family ends at once would wait for `PARK_DEADLINE`.
- **Test:** add the v6-first variant, and a both-end-at-once variant (routers refused at send) asserting `bootstrapped` straight after `start_bootstrap`.

### Nits

**N-1. `epoch` predates DNS resolution, so slow DNS eats into `PARK_DEADLINE`.**
- **Where:** `actor.rs:491` (`let now = Instant::now()`) is taken before `resolve(&cfg.bootstrap).await` at `actor.rs:498`, and `Actor::new` stores it as `epoch`.
- **Scenario:** a resolver that takes 10–30 s (a common Docker DNS timeout) leaves little or none of the 30 s parking window.
- **Fix:** take the parking start after `resolve`, either as a separate `park_from: Instant` set in `start_bootstrap`'s first call, or by passing `Instant::now()` after the await.

**N-2. Parked time counts against the pool's `lookup_wait` (30 s, `sources/src/pool.rs:560`).**
- **Scenario:** a bootstrap taking 20 s leaves a released request about 10 s before the pool times it out and backs off for 120 s. The outcome matches an empty answer, so there's no regression, but `PARK_DEADLINE == lookup_wait` is a coupling worth one sentence in the decisions file. Or cap the park at well under `lookup_wait`.

**N-3. A BEP 42 id change during the bootstrap leaves the new id's neighbourhood unlooked-up.**
- **Where:** `actor.rs:1613`. `on_external_ip` rebuilds the tables around the new id while the self-lookup still targets the old one. `join_targets` then counts levels against the new id, using nodes found near the old one.
- **Scenario:** a typical public start. The refresh covers far levels, but the levels near the new id wait for the 15-minute stale refresh.
- **Fix:** this predates the PR. A follow-up could queue one extra self-lookup for `ids[0]` when the id changes before `join_planned`.

**N-4. Decisions file wording.**
- **Where:** `docs/decisions/2026-11-12-X-dht-lookup-converge.md:30` says "With no routers configured (tests, a saved table), nothing parks".
- **Problem:** a saved `state.bin` doesn't stop parking while routers are configured, because saved nodes seed the self-lookup and aren't inserted into the table.
- **Fix:** say "With no routers configured (as in tests), nothing parks; a saved table still parks until its self-lookup ends."
