## Important

### I3. NZBGet's guard looks for the raw password and user name, but they only ever travel as Basic base64
**Where:**
- `crates/integrations/src/clients/nzbget.rs:181-185` (`Nzbget::read`)
- the header is set at `nzbget.rs:157`

**The problem:**
- NZBGet's request body is JSON-RPC with no credentials in it. The user name and password go only in `Authorization: Basic base64(user:pass)`.
- So a reverse proxy or debug page that reflects the request, which is the threat the guard exists for (decisions file, "Why it matters at all"), reflects NZBGet's credentials in base64 form. That form isn't in the guarded list.
- P2 shows it reaching `Rejected("HTTP 502: … Authorization: Basic …")`, which UN-3 shows in the UI and logs. Base64 isn't protection: it's the credential.
- The raw-password fixtures in the new test (`bad login USER:PASSWORD`, `password=PASSWORD`) cover a client that types the password into its own text, which NZBGet never does.
- This gap was already present at 1003d77e: the old scrub was also raw-only, and the prior review's N2 raised the base64 form for logs only.

**Fix:**
- Add `base64(format!("{user}:{password}"))` to the secrets `Nzbget::read` passes (built once in `Nzbget::new`, held in a `Secret`, or a `Zeroizing<String>`).
- Add one 502 fixture whose body echoes `Authorization: Basic <that>` to `an_answer_that_echoes_a_credential_keeps_it_out_of_the_error`, plus the `basic` string to its secret list.
- SABnzbd needs nothing: its key is hex and travels raw in the form body, which the test already covers.

## Nits
- **N1. The guard is tested only on the add path** (M3h survives). `version`, `access` and `categories` go through the same `read` wrapper, so the risk is low. A single `categories()` case with an echoing 500 in the same test would pin it.
- **N2. A JSON-escaped credential split by the 200-character cut leaks a prefix** (P3, `usenet.rs:329-341`).
  - The body doesn't hold the raw form, and the cut reason holds only a prefix, so neither check fires.
  - It needs a client or proxy that both escapes the secret (`\/`, `\uXXXX`) and echoes it at character 195 or later, so it's contrived.
  - **Fix:** also treat a reason that ends with a 4-byte or longer prefix of a secret as leaking, which sends it to the scrub-or-withhold path.
- **N3. Guarding the user name blanks out NZBGet's default user name** (P4). NZBGet ships with `ControlUsername=nzbget`, so any proxy or client text that mentions "nzbget" reads `***`. This is cosmetic. Either accept it and say so in the decisions file, or don't guard a user name equal to `nzbget`.
- **N4. A clean reason can be withheld** (P5). When the body holds a numeric password only through the echoed request id, the scrubbed copy no longer parses, and a plain refusal or `Invalid parameter (…)` becomes `WITHHELD`. It's still `Rejected`, so behaviour is correct and only the text is lost. You could return the first-pass reason when it holds neither a secret nor a trailing secret prefix (the N2 check), and fall back only otherwise.

## Credential paths (check 2)
- **Only `ClientError::Rejected(String)` carries dynamic text** (`clients/mod.rs:221-248`). Every other variant is a unit variant, an enum or a `&'static str`.
- **Every `Rejected` producer in both adapters goes through `parse_guarded`:**
  - `rejected_status`, `forbidden` and `refusal` for SABnzbd;
  - RPC `error.message` and the non-200 branch in `answer` for NZBGet;
  - the fixed texts.
- **A scrubbed re-parse can't produce `Ok`.** Its `Ok` and non-`Rejected` arms map to `WITHHELD`, so a refusal can never be turned into a success.
- **The scrubbed copy is `Zeroizing`.** No copy is made when nothing matches, so the prior review's N1 (an unzeroized 4 MiB config copy) is moot.
- **No new logging, `Debug` or URL path.** The `CLIENT_REQUEST` log line is unchanged and carries status and size only.
- **The leak test now also checks the Basic base64 form** in `Display`, `Debug` and logs (prior N2). Its encoder is checked by a round trip.
- **Success values are returned as parsed** (job id, version, categories, access). That's by design and documented. They're strictly validated, and none can carry a credential in practice.
- The one gap found is I3.
