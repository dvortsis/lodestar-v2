## Security review: no findings
- **SOCKS5 parsers** (`crates/integrations/src/net/socks.rs`) are pure and panic-free. `reply_len` (socks.rs:216) bounds a reply to 10..=262 bytes before anything is read. The handshake (`net.rs:1414-1429`) reads into a fixed `[u8; MAX_REPLY]` stack buffer, with exact reads through `try_read`, so it allocates nothing on proxy input and no tunnelled byte is consumed (the test proves it with `after: b"tunnel"`). `parse_reply` (socks.rs:238) rejects a wrong length, a non-zero reserved byte, an unknown ATYP, an empty name, and a name that isn't printable ASCII. The slice math in `split_at(len - 6)` holds for every ATYP. Both proptests and the fuzz target assert these bounds.
- **Escaped and duplicate key pattern** (rv-787 B1, X-enr-page-flag): this is a binary protocol with no keys, so the hole can't arise as such. The analogous risk is an encoded host name that gets past the plainly-local-name rule on proxy-side DNS. The name the guard checks and the name put on the wire are the same `url.host_str()` value, normalised by `host_url`. I probed it with a temporary test, since deleted. `localhost.`, `LOCALHOST`, `localhost%2e`, `local%68ost`, `localhost。` (ideographic full stop), fullwidth `ｌｏｃａｌｈｏｓｔ`, `127.1`, `0x7f.0.0.1`, `2130706433`, `::ffff:7f00:1`, `[::1]`, `0`, `metadata.google.internal.` and `instance-data` were all refused with the right class. NUL, space and `%00` are InvalidUrl. Nothing gets past the rule.
- **Downgrade:** one method is offered, and a reply naming the other one is NoAcceptableMethod. Login lengths are checked before any connect (`check_route`). The login buffer is `Zeroizing`. No error carries a credential, a host or proxy bytes.
- **DoS:** resolving, connecting and the whole handshake sit under `timeout`. A silent or trickling proxy is capped. Per-target retries happen only on `Refused` and stay inside the same timeout.
- **Kill-switch:** checked before any lookup, raced with a bias toward the switch (`poll_fn`, `net.rs:1240-1266`), and checked again before hand-over. When the attempt is abandoned the in-flight socket is dropped. For `watch::Receiver<bool>`, a closed sender counts as down (`has_changed().is_err()` and `wait_for` returning Err), so a lost switch fails closed. Tested before the connect, during it, and with the sender dropped.
- **No fallback:** a bind address that's gone, a missing interface, a destination of the other family and an unreachable proxy each end in `NetError::Connect`. Tests assert zero accepts on the real server.
- **Lands inactive:** `connect_tcp` and `connect_tcp_with` are byte-identical to main, and `NetError` is unchanged.

## Important

The plan's §5.3 NOS-2a line says the guard is checked "again on the proxy's reported address". The PR checks `BND.ADDR` for form only. I agree on the technical merits: RFC 1928's BND.ADDR is the proxy's own outbound socket, so it says nothing about the destination, and checking it would refuse working proxies that report 0.0.0.0.
