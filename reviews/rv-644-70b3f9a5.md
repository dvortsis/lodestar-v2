## The `touched` side change
- **New journals: correct at every crash point.** I walked these:
  - **Crash before the `RollingBack` save** (in probation): the journal is `Installing`. The next run (`to`) restores the start type, starts the service and judges again. The rollback hasn't touched anything, which is right.
  - **Crash after the `touched` save** (`rollback.rs:591-596`), before or inside `stopped()`: `RollingBack{done:0}` with `touched`. A later halt (say a tampered MSI) disables and stops the service. That's conservative, and right because the stop may have begun. The recovery text says "after step 1 of 5", which is harmless.
  - **`done` 1 or more:** `touched` is always true.
  - **The save itself fails:** `touched` is true in memory, so the halt disables the service. The journal on disk is still `Installing`, so the next run re-enables it and judges again. That heals itself.
  - **Halts before the first save** (previous MSI missing or tampered, an invalid version): `touched` is false, the journal goes, and nothing is changed. Tested (M17).
- **Older journals have no `touched`.** It defaults to false (`#[serde(default)]`).
  - A probe stripped `touched` from a `RollingBack{done:1}` journal and forced a halt. The result was wrong:
    - the journal was **dropped**;
    - the marker **stayed**;
    - the service stayed disabled;
    - the Event Log said "Nothing was changed: 0.7.0 keeps running".
  - Only unreleased builds of this PR wrote such journals, because no release or nightly ships this code. So it isn't blocking.
  - It does break the contract the PR itself records: a missing field should default to the old behaviour. The old code treated any `RollingBack` journal as touched.
  - `touched` is exactly equivalent to `matches!(j.state, State::RollingBack { .. })`. The only writer of `RollingBack` is `save` in `steps`, and its first call is the `touched` save. That holds in memory too. See P-1.

## The state machine
- **No double msiexec:**
  - A new hand-off happens only with no answer, either recorded or in the file.
  - The lock must be free and the named copy's file removable.
  - After B-2's kill, a fresh copy meets the Installer's own lock and gets 1618, so no two transactions overlap.
- **Lock order:** `.lock` and `msiexec.lock` are still never held together. The copy now runs check → pin → lock.
- **Answer handling:** `answer` is cleared together with `msi` on every path. That covers the refused and code arms in `steps`, the halt, `after_install`'s `msi.take()` and `CopyRefused`'s `clear`. So a recorded answer can't apply to a later copy.
- **Resume after a reboot:** this holds for the rollback, including the new 3010 wait. **It doesn't hold for the forward install's 3010 (B-1).**

## Blocking

**B-1. A forward install's 3010/1641 skips probation even when `to` is already on disk and running.** At `crates/lodestar/src/update/windows/helper.rs:580-584`, with `rollback.rs:361-367` and `:436`.
- **The code:**
  - `after_install` sets `restart = (code is RestartNeeded)` from the exit code alone.
  - `probation(restart=true)` returns `Installed{restart:true}` without a health check.
  - The journal stays `Installing{restart:true}`.
- **Why the exit code alone isn't enough:**
  - Since the hand-off, the run that takes the copy's answer is the Program Files `lodestar.exe`.
  - The copy ran `msiexec` only once that program had ended (`wait_free`), and with the service stopped.
  - So the decisions file's own premise ("an in-use file is only replaced at the next restart", line 155) no longer makes 3010 mean "`to` isn't on disk yet". A 3010 now usually means `lodestar.exe` was replaced and something else wants a restart.
- **What happens then:**
  - The answer-taking run is `to`, which the MSI's StartServices has started.
  - It reports `restart: true`, and nothing judges `to` until the next helper run, which is normally the next boot. That can be weeks away on a server.
  - A failing `to` runs on the migrated store for that whole time, with no rollback.
- **The same path** is hit when the answer is first taken by the boot run after the restart: the copy died after writing its answer, or its `schtasks /Run` failed or was dropped.
- **Probe:** hand off, the copy answers 3010, `running = 0.7.0`, an unhealthy Fake. The run returned `Installed { restart: true }` with calls `[]`: no health check, no rollback.
- **This contradicts:**
  - the decisions file's "**`to`:** … probation is judged" (line 21). Only "**still `from`**, after exit 3010" (line 19) should wait.
  - architecture §12.2 ("health-checked and rolled back on failure").
  - the item-4 reasoning the PR already applies to the reinstall (`rollback.rs:703-712`).
- **Fix** (I verified it locally; all 80 `update::windows` tests still pass, and the probe then rolls back and hands off the reinstall):
  ```rust
  let restart = done == Installed::RestartNeeded
      && ctx.running.as_ref().map(|v| v.to_string()).as_deref() == Some(journal.from.as_str());
  journal.restart = restart;
  journal.answer = None;
  let _ = rollback::write(ctx, &journal);
  rollback::probation(ctx, sys, journal, restart)
  ```
  - Add a test: the hand-off, then a copy answering 3010, then the run with `running = to` and an unhealthy Fake. It should roll back, not report `Installed { restart: true }`.
  - Add the healthy twin: 3010 with `to` on disk and healthy gives `Installed { restart: false }` and clears the journal.
  - Add a line to the decisions file's 3010 bullet: "a 3010 counts as waiting only while the program on disk is still `from`".

## Polish
- **P-1. Derive `touched` from the journal state, or OR it with the state** (`rollback.rs:512`): `let touched = j.touched || matches!(j.state, State::RollingBack { .. });`. It's identical for new journals, correct for older ones (the probe case above), and keeps the cross-version contract. The simpler option is to drop the field.
- **P-2. Tests for the untested fixes** (the survivors above), each cheap with the existing harness:
  - an unreadable `skipped` still rolls back (item 3, M8);
  - a quiet run and a resumed run leave no `msiexec.lock` (item 6, M9);
  - the crash window between recording the answer and removing the file. Write the journal with `answer` set and the file left, then check the answer is used once (item 7, M10–M11).
  - 1618, then two no-answer copies, still allows a third copy, so the reset is checked (item 5, M5 and M6).
  - CopyRefused restores the recorded start type (M23).
- **P-3. B-2 on the forward install: the next run comes at once and may judge while Windows Installer is still finishing** (`rollback.rs:440-448`).
  - After the deadline kill, the copy starts the task straight away.
  - With `from` still on disk, that run reports `install_interrupted`, clears the journal and starts the service.
  - If the Installer's server-side transaction then completes, `to` is installed with no journal and no probation.
  - For a rollback this is safe: the fresh copy gets 1618.
  - The deadline is 90 min, so this is rare. Record it as a residual risk next to the B-2 text (decisions line 166). Better: have the copy wait, bounded, for the Installer to go idle (`Global\_MSIExecute`) before it drops its lock.
- **P-4. Two small gaps in B-2's classification and timing:**
  - **Classification:** `child.try_wait()?` at `helper.rs:1132` propagates a post-spawn error with its own kind, so it's classified `msiexec_not_started` and answered as refused ("Nothing was changed"). Map every error after `spawn()` to `Interrupted` (or classify by position, not by kind).
  - **Timing:** the copy calls `start_task` (`cli/update_helper.rs:162`) while its image is still mapped. A fast task run that finds no answer sees `copy_running` true (the copy's file can't be removed), returns `HandedOff`, and nothing runs again until the next boot. This only matters on no-answer paths, which B-2 has now made a designed path. Either:
    - have `copy_running`, when the lock is free, retry the removal for a bounded time of at least 10 s; or
    - say "the next boot run" in the decisions file.
- **P-5. A write failure in `take_result` reads as "no answer"** (`rollback.rs:199`, `write(ctx, j).ok()?`). In the install path that can turn a recorded 3010 into `install_interrupted`. The file is still there, so returning the answer without removing the file would be safer. This only matters on an admin-only folder, so it's negligible.
- **P-6. Stale order docs after item 6:**
  - decisions line 169 says "**The copy takes its lock before anything else.**";
  - `run_copy`'s doc at `helper.rs:611-614` says "1. its lock, first of all … 2. staging checked again".

  Both contradict the code and decisions line 177.
- **P-6b. A stale comment** at `rollback.rs:453-454`: "disabled by a rollback's first step that wasn't recorded yet". This can now only happen when the `touched` save fails, so the comment should say that.
- **P-7. The module docs don't state the cross-version contract.** Item 9 put it in the decisions file only. One sentence in `rollback.rs`'s header ("new fields must be safe for an older helper to ignore; otherwise bump `FORMAT`") would keep it next to the types that later slices edit.
- **P-8. `reinstall_restart` with a pending rename that never happens.** If the rename never takes effect, `to` stays on disk, step 5 retries at every boot for ever, and the service stays disabled. Consider halting after N boots with the recovery text, or record this as accepted.
- **P-9. `start_before` = None means two things.** It stands for both "was Disabled" and "couldn't be read". So `CopyRefused` and `InstallInterrupted` (`rollback.rs:413`, `:443`) turn an administrator's Disabled into delayed automatic even though nothing ran. This is consistent with the runner's item 8 ("otherwise delayed automatic"), so it's only worth a line in the decisions file.
