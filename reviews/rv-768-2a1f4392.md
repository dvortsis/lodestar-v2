## Optional

**O-1. A re-bootstrap in the same tick can make the rejoin a duplicate self-lookup.** `crates/dht/src/node/actor.rs:1649-1666` (`rejoin_tick`) and `:2300-2331` (`start_bootstrap`).
- `maintain` runs `rejoin_tick` (line 2461) before `scrape_tick` (whose `finish_if_due` and stalled drives can end lookups) and before the thin-table re-bootstrap check (lines 2469-2475).
- Scenario: the rejoin flag is set and waits on a stale self-lookup (or on `MAX_LOOKUPS`). That lookup hits its deadline in `scrape_tick` in the same tick, no other lookups are left, and the table is thin and the re-bootstrap is due. `start_bootstrap` then starts a self-lookup for the new `ids[0]` in every family. On the next tick, `rejoin_tick` sees the flag, finds no stale lookup (the bootstrap lookup targets the current id) and starts a second self-lookup for the same id.
- At the default 1 s tick this needs a re-bootstrap due (30 s) after a stale lookup's 25 s deadline. In practice that means a second id change within about 25 s, or every maintenance lookup expiring in one tick. So it's rare and costs one bounded extra lookup. It is still the "already targets the new id" case the self-review called unreachable.
- Fix: in `start_bootstrap`, clear the flags (`self.rejoin.fill(false);`), because it starts a self-lookup for the current `ids[0]` in every family. Or skip in `rejoin_tick` when family `f` already has a `bootstrap` lookup with `target == self.ids[0]`, and clear the flag. Add a one-line test: set the flag, call `start_bootstrap`, then `maintain`, and expect one self-lookup for the id.

**O-2. Each IP flip now also re-plans the join (about 200-450 queries).** `crates/dht/src/node/actor.rs:1609-1642`, with `ExternalIp::vote` at `:209`.
- The behaviour before this PR is unchanged: a flip needs at least 5 distinct /24 (or /64) reporters and a strict majority of the 32-vote window, and votes come only from responses that match a pending tid and its address. A hostile majority that flips A→B→A could already re-id the node each time.
- This PR adds a bounded cost per flip. The flags can't pile up, `join_refresh = None` drops the old queue instead of appending to it, the join runs at most `MAX_LOOKUPS / 2` lookups at a time, and the query token bucket caps the rate. So there's no amplification beyond the existing query budget, and it isn't blocking.
- Possible follow-up (not this slice): a minimum interval or hysteresis between id changes, which would cap the cost of a flip-flopping majority.
