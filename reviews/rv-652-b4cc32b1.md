## New findings

### BLOCKING-1: `resolves` reads dig's error text as an answer, so the leak test can't pass on a healthy fleet and `dns_up` can't fail
Location: `infra/fleet/steps/vm/leak-test.sh:72`, `resolves() { probe sh -c "dig +short +time=$2 +tries=1 $1 ${3:-} | grep -q ."; }`. It is used at `:154` (`dns_up`) and `:107-108` (`dns_blocked_*` and `dns_direct_blocked_*`, both phases). This was already present at b9b73ed3 (line 47), so it predates round 2; the round-1 review missed it.

**`dig +short` prints its failures on stdout and exits 9.** I verified this on BIND 9.18.39 (Ubuntu's `bind9-dnsutils`, run against a silent UDP listener on 127.0.0.1):

```
$ dig +short +time=2 +tries=1 -p 5399 @127.0.0.1 example.net   # rc=9, stderr empty
;; communications error to 127.0.0.1#5399: timed out
;; no servers could be reached
$ sh -c "dig +short ... | grep -q ."; echo $?
0
```

netshoot's `dig` is Alpine's bind-tools (the 9.18 or 9.20 series), which prints these lines the same way. Confirm it against the pinned image in the first cloud run.

**What this breaks:**
- **On a correct, firewall-on gluetun:** in phase A (`_down`) and phase B (`_ifdown`), `dig … @1.1.1.1` times out. The `;;` lines reach `grep -q .`, so `resolves` returns 0 and `refute dns_direct_blocked_*` reports **fail**. The same happens to `dns_blocked_*` whenever gluetun's local resolver times out rather than answering SERVFAIL. The leak test therefore ends in `fail leak_test` on every healthy VM. A passing leak test is the precondition for starting a crawl (OP-3b), so the step as shipped blocks the cloud test.
- **The `dns_up` positive control:** a gluetun whose DNS is broken still prints `;; …` lines, so `check dns_up` passes. The control can't fail.
- **Why the tests miss it:** the docker stub (test_steps.py:429) models `"sh -c dig"*` as exit 1 with no output when blocked, which encodes the wrong behaviour.

**Fix:**
- Accept only an address line, for example `dig +short … | grep -Eq '^[0-9]{1,3}(\.[0-9]{1,3}){3}$'`. Alternatively, capture dig's output and its rc and require rc 0 plus an A-record line.
- Change the stub so a blocked `dig` prints `;; communications error to 1.1.1.1#53: timed out` / `;; no servers could be reached` on stdout and exits 9. An up-phase case where dig prints only `;;` lines must fail `dns_up`.
- Mutation-check the new pattern back to `grep -q .`. With the corrected stub, that mutation must fail the suite.

### LOW-1: phase B doesn't check that gluetun's interface is still down while its probes run
Location: `leak-test.sh:169-175`.

**How it happens:**
- In phase A the endpoint is dropped, so gluetun's health loop sees a dead tunnel and restarts its VPN, deleting and re-creating `wg0`.
- After phase B's `ip link set dev wg0 down`, gluetun's next VPN restart can bring `wg0` back up with its routes, even with the endpoint still blocked. The restart is driven by gluetun's health timing, roughly every few seconds to a minute.
- The later phase B probes then route into the dead tunnel again, which is phase A's case, and pass whatever the firewall does.

**Consequences:**
- A firewall that is fully off is still caught: the first probes, and gluetun's own health and DoT traffic, leave through `eth0` within a second or two of the interface going down.
- A partial firewall regression could slip through if the restart comes first. Two examples: a firewall that lets DoT (853) or plain DNS out, which only the later DNS probes exercise; or IPv6.
- The stub can't model the restart, so no test covers this.

**Suggested fix** (the slice's call; recording it as a residual in the decisions file is acceptable):
- Bring the interface down again immediately before each phase B probe.
- Or, after the probes, read the link state with `probe ip -o link show dev "$iface"` and fail `vpn_interface_stayed_down` unless it is DOWN or absent. Be aware this can fail closed intermittently.
- Or, if gluetun v3.41.3 can turn off its VPN-restart-on-unhealthy, set that for the leak test's recreate only. Verify the setting exists before relying on it.

### NIT-1: "A 255 ran nothing remotely" is inaccurate
Location: `infra/fleet/steps/run.py:10-12`, and the decisions file's "Exit 255 … A 255 ran nothing remotely, so a retry can't overlap a step".

`ssh` also exits 255 when an established session drops mid-step, after the remote side has started. The retry is still safe, for a different reason: the VM flock serialises the sessions. A live orphan holds the lock, so the retry gets `vm_busy` (21), which is never retried. An orphan already ended by its EXIT trap leaves the retry to run an idempotent step from scratch. Reword both places to give that reason.

### NIT-2: deliver reports an unknown Docker state as "renewed; takes effect after the block"
Location: `deliver.py:147-157`. This is correct fail-closed behaviour, with two reporting gaps:
- **The message:** on a first `up` to a VM whose Docker daemon isn't answering, the report says "renewed; takes effect after the block" when no block exists.
- **A timed-out gluetun inspect:** it reads as "not running", so the restart is silently skipped and the result is `delivered`.

Neither leaks anything; both are about the report. A distinct exit and wording for "Docker didn't answer" would make them visible. Optional.

### NIT-3: the probe marker can stick to tool output with no trailing newline
Location: `leak-test.sh:65`, `sh -c '"$@"; echo "probe_rc=$?"'`.

If a tool's last output line has no newline, the marker lands on the same line and isn't matched (`^probe_rc=`). The probe then reads as `NOT_RUN`. That fails closed, so it's not a security problem, but it's a spurious failure. `printf '\nprobe_rc=%s\n' "$?"` makes the marker robust. Today's probes (curl to checkip, which ends in `\n`; nc; dig piped to grep) are unaffected.

## Security review of the delta
- **Fail-closed paths:** both mid-block checks now refuse on a Docker error. A probe that never ran can't pass. A failed interface-down fails the test. An interface name that is missing or hostile refuses before any iptables call (tested). Interrupted runs still end in the EXIT trap, which lifts the DOCKER-USER block (tested with a failing first delete). An interrupt during phase B leaves gluetun's interface down, which doesn't leak.
- **Bounds:**
  - **SSH retry:** at most 120 s, then one more attempt, inside the act job's budget.
  - **deliver:** every Docker call is bounded and the sum is budgeted.
  - **Leak test:** phase B adds up to 7 probes × `timeout 40`, all still under the step's outer `timeout 600`. The control-side session bound (720 s) is unchanged. A pathological worst case reaches the outer timeout and exits non-zero, which fails closed.
- **Shell injection:** `$iface` is regex-checked and passed as an argv word through `sh -c '"$@"…'`. Phase B's DNS names are constants. deliver's new lines interpolate only integer constants.
- **Secrets:** no new output carries an address, endpoint, interface or key. The report grammar is unchanged.
- **P8:** `S3Store` can no longer be built without the owner-checked client.
- **Fixed sleeps in tests:** none. The SSH retry uses a fake clock and sleep. The leak-test scripts use the stubbed `sleep`, and the tcpdump stub's `/bin/sleep 0.05` only paces a placeholder process that runs until it gets TERM.
