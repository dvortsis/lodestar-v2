## B1: wizard labels (root cause and fix)
- The root cause is correct. On `main`, `SettingsForm` read the sections once with `untrack(form.specs)`. A form built from keys has `specs = []` at mount, so only the `group` map loaded and every field fell back to `spec.name`. The bug was persistent, not just a flash.
- The fix, a `$effect` over `sectionsOf(form.specs)`, is sound:
  - **No loop.** The effect reads only `form.specs`, a `$state.raw`. `messagesLoaded` and `messagesFailed` read plain module objects. It writes `labelsReady` and `labelsFailed`, which it doesn't read.
  - **No repeated map loads.** `loadMessages` memoises per map (`loading[s] ??=`). A retry re-sets `specs` to the same sections, so it takes the `messagesLoaded` fast path.
  - **A stale load is ignored.** The cleanup sets `live = false`, so the earlier `group`-only load can't overwrite state after the specs change or the component unmounts.
- **On a load error, fields are never hidden for good.** `loadMessages` never rejects. A failed chunk sets `maps[s] = {}` and adds it to `failed`, so `labelsReady` turns true and `labelsFailed` turns true. The existing lazy-part failure notice shows, and the fields render under their names, as before. A failed index load still goes to `load-error` with Retry.
- **No raw-key flash.**
  - `form.load()` sets `specs` before it awaits the section values, so `status` is still `loading` when the effect runs and sets `labelsReady = false`. Children render only once both are in.
  - The keys test's MutationObserver also checks this.
- **Spec-built Settings screens are unchanged.**
  - `first` is computed as before, and `labelsReady` and `labelsFailed` start with the same values.
  - The effect's first run either takes the loaded fast path or makes the same single `loadMessages` call the old `if (!inPlace)` made.
- `FieldsStep.svelte` is untouched. The wizard now uses the same index specs and message maps as Settings: one source, not a copy.

## B2: Sign out
- **`signOut()` is correct.**
  - `pending ??= logout().then(ok, fail).finally(reset)` shares a press while one is in flight.
  - It resets after success and after failure (the `.finally` runs after either handler) and never rejects.
  - The tests cover the shared request and the retry after a failure.
- **The error toast** reuses `m.auth_logout_failed()` and the shell's toaster. The menu and Sessions tests both assert "Couldn't sign out", no navigation, and that the session stays `signed_in`.
- **Overflow menu:**
  - It's a Bits `DropdownMenu.Item` (`role="menuitem"`), so arrows, Home/End, typeahead and Esc all come from `Menu.svelte`.
  - The separator uses the existing `separatorBefore`, which renders `DropdownMenu.Separator` (`role="separator"`, allowed inside `role="menu"`).
  - It's handled as an action in `onSelect`. The menu chunk stays lazy.
- **Settings → Security → Sessions:** `LogoutButton variant="secondary"` sits beside "Sign out other sessions…". `busy` is reset because `signOut` never rejects.
- **No new strings or icons:** it uses `auth_logout` and `auth_logout_failed`, which already exist in en and zh.

## Findings

### I1. `SettingsForm.keys.test.ts` caps its 10 s wait at vitest's 5 s default
- **Where:** `web/src/lib/features/settings/form/SettingsForm.keys.test.ts:31-37`.
- **Failure scenario:**
  - The file never raises `testTimeout`, so the test is killed at vitest's default 5 s, before its `waitFor({ timeout: 10_000 })` deadline.
  - On a slow or loaded runner, the label chunk plus the settings index can take longer than 5 s. The test then fails as a timeout without saying what it saw, which defeats the ≥ 10 s condition-wait rule (`runner/standards.md` §2).
  - It showed when I ran it without the fix: "failed 5013ms".
  - Its sibling files in this PR (`FieldsStep.labels.test.ts`, `OverflowMenu.test.ts`) and `security.test.ts` all set `vi.setConfig({ testTimeout: 30_000 })`.
- **Fix:** add `vi.setConfig({ testTimeout: 30_000 });` at the top of the file.
- **Why it isn't blocking:** it's a real condition wait, not a sleep, and the web vitest job runs only on ubuntu.

### O1. A navigation failure after a successful logout shows "Couldn't sign out"
- **Where:** `web/src/lib/features/auth/sign-out.ts:15-22`, with `session.svelte.ts` `logout()`.
- **Failure scenario:**
  - `logout()` awaits `toLogin()` after `setSession('signed_out')`.
  - If `goto` rejects, for example because a navigation was aborted, the session has already ended but the user sees the failure toast.
  - This behaviour is inherited from the old `LogoutButton`.
- **Fix, optional:** catch only the `api.post` failure for the toast, or treat `toLogin` errors separately.

### O2. No feedback in the overflow menu while sign-out is in flight
- **Where:** `web/src/lib/shell/OverflowMenu.svelte:21-25`.
- **Failure scenario:** the menu closes at once, and on a slow server nothing shows until the navigation or the toast. Repeated presses are safe because they share one request.
- **Fix, optional:** none needed now. A pending toast or a busy state on the trigger could come later if the review asks for it.
