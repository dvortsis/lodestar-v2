### I1 (Windows: link names left behind): fixed

- The window between the probe and the removal is covered by that cleanup.
- **Test:** `a_file_that_cant_be_removed_leaves_no_names_behind` (`watch.rs:1767`). It holds the file with `share_mode(FILE_SHARE_READ)` over three polls, then checks `added\` is empty, and that the file moves once the handle is dropped. I read through the Windows semantics:
  - our read (`GENERIC_READ`, default share RWD) is compatible with the held handle, so the file is judged;
  - `CreateHardLinkW` needs no access that share mode governs, so without the fix a link would be created, and the test would fail;
  - the `DELETE` probe gets a sharing violation, error 32. In the installed std, 32 maps to `Uncategorized`, not `AlreadyExists`, so the result is `MoveError::Io`, and the file is stuck without a link.

## Optional
- **P1. The O1 pruning uses the classified entries, not the raw listing** (`watch.rs:313` with `:328`).
  - `entries` is built with `filter_map(|n| f.entry(&n)...)`. A stuck name whose `symlink_metadata` fails for a moment (an SMB `EIO` or `EACCES`) is missing from `listed` even when `whole` is true, so it's dropped from `stuck`.
  - On the next two polls it's a new file: read once more, submitted again, and stuck again, with another `watch.stuck` line.
  - It's bounded (one re-read per hiccup per file) and harmless to the store, which deduplicates by info hash. But it's an eviction followed by a re-read, which brief req. 4 rules out.
  - **Fix:** build `listed` from `names`, before `entry()` filters them. That's a one-line move.
- **P2. `MoveError::Left` depends only on `ErrorKind::Unsupported`** (`watch.rs:815`).
  - I checked the installed `x86_64-pc-windows-gnu` std's `decode_error_kind` by disassembly: only `ERROR_CALL_NOT_IMPLEMENTED` (120) maps to `Unsupported`. `ERROR_NOT_SUPPORTED` (50), `ERROR_INVALID_FUNCTION` (1), and sharing and lock violations (32, 33) map to `Uncategorized`. 80 and 183 map to `AlreadyExists`.
  - So FAT, exFAT and SMB without hard links still end up as `Io`, which means stuck and never re-read. Correct today.
  - If a regular file ever did get `Left`, `left.remove` on `Entry::File` (`watch.rs:347-351`) would re-read it on every poll.
  - **Cheap hardening:** in `finish`, treat `Left` as `Io` when `shape.is_some()` (only a link entry has no shape), or return a private marker instead of an `io::ErrorKind`.
- **P3. `retry_stuck` ignores a `Subfolder` error from its own `put_away`** (`watch.rs`, the `retry_stuck` body). The poll goes on and reads at most one more new file before `finish` stops it. It's bounded, but returning the problem and stopping there would be tidier.
- **P4. Windows: holding the folders for the whole poll** includes the `sink.submit` awaits.
  - While the judge is backlogged, the user can't rename or delete the watch folder, or a parent of it, in Explorer.
  - A sync or antivirus tool that holds the folder open with `DELETE` access makes `hold` fail with `unreadable` for that poll, which can log `watch.disabled` and `watch.started` in turn.
  - Worth one line under "For the guide" (the folder can't be renamed while Lodestar is checking it).
- **P5. Decisions line 20 is garbled:** "Neither check sees the data directory, not the data directory, so …".
- **Not this PR's:** `cargo tree -e features -p lodestar` lists `lodestar-tracker-scrape` and `lodestar-update` with the `testing` feature. These are existing dev-dependency features of other crates. The PR changes no `Cargo.toml` or `Cargo.lock`, and tokio's `test-util` isn't enabled.
