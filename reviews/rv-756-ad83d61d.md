## I-1 analysis

**The flag's lifetime** (`actor.rs:2270`, `actor.rs:2289`):
- It is set and cleared around a plain `for` loop whose body calls `start_lookup_as`, which returns `()`. There is no `?`, `return` or `break` between the two assignments.
- Nothing in `start_lookup_as → query_seed / drive_lookup → finish_lookup` calls `start_bootstrap` again, so the flag can't be cleared mid-loop by re-entry.
- It is false at construction (`actor.rs:722`).
- Only a panic could leave it set, and a panic ends the actor anyway.
- So it can't stay true, and parking can't outlive its bounds:
  - each self-lookup still ends by `LOOKUP_DEADLINE` (25 s), or at `query_timeout` (4 s) for a silent router;
  - `PARK_DEADLINE` (30 s from `park_since`) still releases on its own.

**Every path that ends a self-lookup inside the loop:**

| Path | Behaviour |
|---|---|
| Nobody to ask (no router and no node in that family) | `drive_lookup` → `is_done` → `finish_lookup` with `others_out` true. It doesn't settle, unless the table is non-empty: `found` still wins, which is the stated rule. |
| Error path (router refused by policy or socket, `Sent::Failed`) | Same as above. The test refuses a port-0 router through `allows_seed`, which is deterministic on every platform. |
| Throttled seed (`Sent::Throttled`) | Same. This is impossible at start, because the bucket begins full. |
| No lookup created for a family (`MAX_LOOKUPS` refusal) | Impossible at start (0 lookups). The re-bootstrap runs only when `lookups.len() == active_scrapes`, and by then `bootstrapped` is already true. |
| A bind that fails | Fatal at `node/mod.rs:1080` (`bind(*addr)?`), so no actor exists with a missing family. |

**The after-loop settle** (`actor.rs:2290-2294`):
- It only sets a bool. Parked requests are released in exactly one place: `maintain`'s FIFO `pop_front` loop (`actor.rs:2416`), which runs on the next tick.
- That gives no double release and no reordering. The per-lookup path and the after-loop path can both write `true`, and writing it twice is harmless.
- On later re-bootstrap rounds `bootstrapped` is already true, so the settle does nothing.
- `finish_lookup` is still the only place a lookup is removed (`actor.rs:2142`). Pause doesn't remove lookups. So every way a round can end now sets `bootstrapped`.

**Both orders with a live v4 lookup:** v6 ends inside the loop and v4 stays out, so the round doesn't settle. When v4 later ends without nodes, `others_out` is false, so it settles; with nodes, `found` settles it. Correct.

## N-1 analysis (`park_since`)

- It's set to `Instant::now()` in `Actor::new` (`actor.rs:723`). `run` constructs the actor after `State::load` and after `resolve(&cfg.bootstrap).await` (`actor.rs:499-516`), so slow DNS no longer eats into the window.
- `epoch` still predates both, but it's used only for `now_secs` (table ages), so it's unaffected.
- **Restart and restore:** each start (a process restart, or a node rebuilt by `run`) builds a new actor, so parking gets a fresh 30 s. A restored `state.bin` doesn't change `park_since`, because saved nodes only seed the self-lookup.
- **Clock:** this is `tokio::time::Instant`, so under paused tokio time (crawler-sim) it moves with the same clock that `maintain` reads.
- **Arithmetic:** `parks_lookups` uses `now.duration_since(park_since)`, which saturates in tokio, so it can't underflow or panic.
- The test's `Instant::now().checked_sub(PARK_DEADLINE).expect(..)` is the same construction as before the delta; only the field it sets changed.

### Nits

**N-a. A large saved table does park.**
- **Where:** `docs/decisions/2026-11-12-X-dht-lookup-converge.md:31` says "A saved table of K or more nodes doesn't park either."
- **Code:** saved nodes only seed the self-lookup's candidates (`start_bootstrap`, `actor.rs:2273-2286`). `Actor::new` creates every table empty, and `parks_lookups` counts table entries, not saved nodes.
- **Scenario:** a restart with a `state.bin` of 16 v4 nodes and routers configured. A request made right after `start_bootstrap` is parked. I confirmed this with a probe: `queue=1 table=0 bootstrapped=false`. It parks until K saved nodes have answered (a few round trips) or the self-lookup ends.
- **Impact:** the behaviour is fine; only the sentence is wrong.
- **Fix:** "With no routers configured, nothing parks. A saved table doesn't stop parking: its nodes seed the self-lookup, and parking ends once K of them have answered or the bootstrap settles, usually within a few round trips."

**N-b. The worst-case sentence names the wrong case.**
- **Where:** `docs/decisions/2026-11-12-X-dht-lookup-converge.md:33` says "In the worst case, a bootstrap that never answers, `PARK_DEADLINE` and `lookup_wait` run out together".
- **Code:** a router that never answers times out at `query_timeout` (4 s by default). That drops `extra_in_flight`, the self-lookup is done, and the round settles, which is what line 29 and `a_failed_bootstrap_ends_parked_requests_empty` say. The longest real park is a bootstrap that answers but whose self-lookup doesn't converge before `LOOKUP_DEADLINE` (25 s). That leaves about 5 s of `lookup_wait`. `PARK_DEADLINE` is only a backstop.
- **Fix:** "A bootstrap that never answers ends at `query_timeout` (4 s). The longest park is a self-lookup that runs to its 25 s deadline, which leaves a released request about 5 s of `lookup_wait`. `PARK_DEADLINE` (30 s) is a backstop. If it runs out, it does so together with `lookup_wait`, and the key retries after the pool's backoff, as it did before parking."
