## Summary

The PR is solid. The moved hash is byte-identical. The parser is strict and can't panic. The content-safety gate for `sig:<info hash>` is correct on every live path I traced.

- **The hash move:**
  - `classify::payload::payload_sig` is pure `u64` arithmetic: `sort_unstable`, `fmix64` and `wrapping_mul`, with no byte order, hasher state or platform dependence.
  - Its seed, its mix and its length mix match the old code. `fmix64` matches `filter::hash::fmix64` constant for constant.
  - Six goldens are pinned in both crates. A proptest checks the new function against a verbatim copy of the old one.
  - `filter::payload_sig` keeps `PayloadSig { sig, specific }`. Specificity still ignores padding, and a test now covers that.
  - The store's `FileTree` carries the full metainfo file list with `attrs`, and `is_padding` is the same predicate (`FileAttrs::PADDING`) on both sides. So the index's value equals CS-8a's.
  - The filter API prints payload keys as `{sig:016x}`, the same text as `sig_hex`, so a signature copied from a block rule works in `sig:`.
- **The parser:**
  - It takes exactly 16 ASCII hex bytes (`len()` is in bytes and `is_ascii_hexdigit` is per byte, so Unicode, fullwidth digits, `+`, `0x` and other leading or trailing junk can't pass).
  - It also takes a 40-hex hash, or a magnet link through the existing `bare_hash`.
  - Values are lowercased. The error message never echoes the value.
  - `hex8` and `hex20` in the compiler re-validate the value, so an AST deserialized from stored JSON can't panic either. `pair[0] as char` maps a non-ASCII byte to a non-digit.
  - The clause count is bounded by the parser's existing limits.
- **Visibility (B13):** the reference torrent must pass the top-level visibility clauses that `compile()` extracts from its own node (`hidden:no`, `verified:yes`, `-type:adult`). I traced every caller that runs user query text against the index, and each builds its node with `base_query(..).query()`, which ANDs `-type:adult` onto the top level:
  - `/search`, counts, cursors and facets (each facet pass re-applies `filters` after `without_facet`);
  - live queries (`search_live.rs:224`);
  - Discover;
  - export (`export.rs:469`);
  - Torznab, which builds an AST, so there's no `sig:` there anyway.

  The only server-enforced clause, `-type:adult`, is therefore always present. `hidden` and `verified` are the user's own choices (`hidden=true`, `verified:yes,no`). Negation, OR and conjunction all reduce to "the reference's own hash term", which the same clauses remove. The test checks exactly that for `sig:`, `-sig:`, `x | sig:` and `item sig:`.
- **Percolation (option (a)):** saved searches whose query has `sig:<hash>` get `with_default_visibility()`. Live (`count_only`) queries keep the visibility they were registered with.
- **The snapshot:** `SamePayload::weight` resolves through `scoring.searcher()`, the searcher the query runs on. Every `weight()` call site uses `*_from_searcher` (none uses `disabled_from_schema`), so leases, facets (`compile_at` plus `lease.searcher()`), counts and percolation each read one snapshot. There is no race with the filter reload, because the hidden flag and the type tag are read from the same snapshot.
- **The schema:** no new field. SB-6 already defined `payload_sig` (u64, `INDEXED | FAST`). GS-0 bumps its generation from 0 to 1, so:
  - an existing index walks under SB-6's backfill and reports `payload_sig` partial (`incomplete_fields`);
  - an index without the field reads `Availability::Missing`, which is also reported;
  - a blue/green rebuild writes it at once (`tests/rebuild.rs` updated).

  The restart-mid-walk acceptance test is real. It rewrites the index to a pre-GS-0 state, walks it, crashes before a commit and resumes.

**One gap, with a cheap fix:** saved-search alerts for `sig:<info hash>` silently miss clones while the walk hasn't reached the reference, and the watermark moves past them. Details are under Important below.

### Important

**I1. Saved-search alerts silently drop `sig:<info hash>` clones while `payload_sig` backfills, and never catch up.** This is at `crates/search/src/percolate.rs:153` (with `compile.rs:1141`/`1183`).

- **Scenario:**
  1. A user upgrades an index of millions of torrents, which starts the generation-1 walk. This can take a long time.
  2. During the walk they save `sig:<hash of an old torrent H>` with alerts on. H's id is past the walk's cursor, so its document has no `payload_sig` yet.
  3. A new clone C arrives. It's indexed with its signature by the new producer.
  4. `SamePayload::resolve` finds H but no fast-field value, returns `None`, and the query becomes "H's hash only". C isn't alerted.
  5. `Matched.through` moves the watermark past C. Once the walk completes, nothing rescans that range, so the alert is lost for good.

  `-sig:<hash>` over-alerts in the same window.
- **Why it matters:** `/search` covers the same state with `incomplete_fields`. Alerts have no such channel, so this contradicts the brief ("reported partial while the walk runs. It never answers 'no match' on an unpopulated document") and the decisions file's "never answers 'no match' without saying the field is partial". GS-2, RX-1 and ENR-11 will add more fields that resolve or are partial, so the pattern is worth settling now.
- **Fix (about 10 lines plus a test):** in `percolate`, for a `Due` whose query `mentions_same_payload()`, skip it without a `Matched` entry while the snapshot's `payload_sig` isn't Ready. Read Ready-ness with `availability_at`/`availability_in` for the searcher's generation. That is the existing "Not run: it keeps its watermark" path. Once Ready, the held range is scanned in `max_range` steps. A test can reuse `unpopulate`:
  1. Save `sig:<hash of id 28>` with watermark 30.
  2. Add a new populated clone.
  3. Assert that no `Matched` entry is returned while the walk runs.
  4. Finish the walk and assert the clone alerts.

  The more general option is to hold any alert query whose `population_fields()` aren't Ready. Live counts (`count_only`) can stay as they are, or be held the same way.

  If the runner prefers to defer this, standards §5 allows putting it in the next brief that touches percolation. Record it in the decisions file as a known limitation, and say so in `docs/query-language.md`.

### Nit

- **N1.** `fuzz/seeds/query/sig`: the seed ends in `(x | sig:7A9F3C12)`, an 8-digit value. The whole input is a parse error, so the fuzz target never takes the Ok path (render, re-parse) with a valid `sig:`. Split it into a valid seed (`sig:7a9f3c12dd0e44b1 -sig:0123…4567 (x | sig:7A9F3C12DD0E44B1)`) and a separate error seed.
