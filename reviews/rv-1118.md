## Security judgment: the persisted SipHash keys
- The keys only spread addresses across the filter's blocks, as a defence against crafted collisions: filling chosen blocks to make inserts fail, or making chosen nodes read as cooling. Leaked keys would give at most a sampling-efficiency attack that needs many attacker-controlled IPs. They give no code execution and no data exposure.
- The keys sit in `dht-restart.bin`, beside the crawler's other state, with the same file permissions (the default umask). They're kept out of `Debug` for both `Spilled` and `Spill`. Anyone who can read the data directory can already read and change the restart state, so persisting the keys doesn't widen the trust boundary.
- Moving from keys per process to keys that persist while the filter is non-empty (in practice long-lived, see the nit) is acceptable. The `testing` feature's fixed keys follow the seen filter's existing pattern.
- The SHA-256 trailer is an integrity check, not authentication. That's unchanged from CR-0d: a forged file still has to pass the marker, witness and state_bin chain.
