## Correctness summary (no findings unless listed below)
**`--join-only`:**
- It requires `--token-file`, so it never takes `LODESTAR_TOKEN`, and it conflicts with `--rotate-key`. Clap rejects it with `LODESTAR_TOKEN` alone, bare, or with a rotation, and unit tests cover all three.
- On a joined folder it refuses (`Failure::Refused`, exit 3) before the token is read. Both the unit test and the Unix end-to-end test use a token file that doesn't exist, so a token read would fail first.
- The success path exits 0 after `save_joined`, which is atomic: tmp file, `create_new`, 0600 on Unix, rename, directory fsync. It writes the address first on a first join, so a crash leaves the folder unjoined.
- The token never reaches stdout, stderr or errors. The refusal message names only the worker.
- One exception, I1: the refusal opens the key, and creates one if it's missing.

**Windows SCM worker:**
- `service_command` accepts only plain `worker`, through an exhaustive struct pattern, so a new flag won't compile until someone decides whether it is a service command line.
- The worker path reuses `run`'s state machine as it is: Running at once; StopPending on Stop, Shutdown and Preshutdown with ticks every 5 s; Stopped with 0, 1 (`0x20000001`) or 3.
- `SERVICE_FAILED` carries kind `worker`.
- The stop is bounded:
  - `Worker::run` checks the stop in every select;
  - `Runtime::drop` only aborts tasks;
  - `dht::stopped` gives up after 11 s;
  - `block_on` now ends with `shutdown_timeout(RUNTIME_GRACE = 5 s)`.

  The worst case is about 16 s plus the existing drain deadline, inside the 30 s wait hint. I found nothing that can hang a stop.
- The temp-log append reuses `temp_log::append` (reparse points refused) and carries only fixed sentences and local paths.

**Tests:** no fixed sleeps.
- `wait_for` polls every 250 ms with deadlines of 30 s and 90 s.
- The coordinator start uses `recv_timeout` with 90 s.
- `worker_join` uses the existing 30 s `DEADLINE` helpers.
- The `TEMP_LOG` mutex is held across both service tests' temp-log sections, and the worker test removes the file only when `created`.

## Important

### I1. The `--join-only` refusal opens the secrets key, and creates one if it's missing
- **Where:** `crates/lodestar/src/cli/worker.rs:331-336`, which calls `Layout::load` (`worker/mod.rs:82`), then `Layout::secrets` (`SecretStore::open_or_create`).
- **Contradiction:** the comment says "Before anything else is read or created". The decisions file says it "refuses (exit 3, "refused") before reading the token **or opening the key**". The code opens the key to get the worker's name. When `cluster/credentials` exists but `secrets.key` doesn't, `open_or_create` writes a brand-new `secrets.key` from the refusal path.
- **Failure path:**
  1. A folder has credentials but lost its key: a partial restore, or a key moved aside.
  2. The installer, as SYSTEM, re-runs `--join-only`.
  3. It refuses, which is right, but leaves a fresh SYSTEM-owned key that can't open those credentials.
  4. Restoring the real key later now means overwriting a file the user didn't know was created.

  Your own unit test `join_only_refuses_a_joined_folder_before_reading_the_token` goes down this path: it writes garbage credentials with no key, and the refusal creates `secrets.key`. Nothing asserts against it.
- **Fix:** look up the name only when the key file already exists, for example `if layout.data.join(SecretStore::KEY_FILE).exists() { layout.load().ok().flatten()… }`, or add a non-creating open. Add `assert!(!dir.path().join("secrets.key").exists())` to that unit test. Alternatively, reword the comment and decisions file to say the key is read (never created) for the name.

### I2. The service worker still reads `LODESTAR_TOKEN` and `LODESTAR_JOIN` from its environment, so "a service never joins" isn't enforced
- **Where:** `crates/lodestar/src/windows/service.rs:1146-1167` calls `cli::worker::run_until` (`cli/worker.rs:274-282`) with `&|k| std::env::var(k).ok()`.
- **Contradiction:** the decisions file says "a service never joins". The slices.yaml notes say "the worker runs under the SCM with no token on its command line or in its environment".
- **Failure path:**
  - With `LODESTAR_TOKEN` and `LODESTAR_JOIN` set machine-wide (someone following the container instructions on Windows) and an unjoined folder, `plan()` returns `TokenSource::Env`, and the service joins on its first start.
  - With only `LODESTAR_TOKEN` set, the service fails with "set LODESTAR_JOIN", which is misleading for a service.
  - Once joined, the warning to remove it goes to the no-op `report` and is lost.

  This isn't a privilege issue, since only an administrator can set those variables, but it breaks a stated invariant.
- **Fix:** have `run_until` (or `scm::worker`) pass an `env` that returns `None` for `LODESTAR_TOKEN`, `LODESTAR_TOKEN_IGNORED` and `LODESTAR_JOIN`. A unit test is easy because `run_with` takes `env`: an unjoined folder with an env token and the filter gives "hasn't joined", not a join attempt.

### I3. The Windows service test never shows the worker connected before Stop
- **Where:** `crates/lodestar/tests/windows_service.rs:1127-1146`.
- **What's missing:** after `--join-only`, the test waits for `STATE 4`. The service reports Running at once (`service.rs:819`), before `load()` and long before the worker connects. It then sends `sc stop` straight away and asserts exit 0.
- **Failure path:** a worker service that reads its credentials but can never connect still passes: wrong address saved, TLS rejected, or stuck in back-off. So does one that fails a few seconds after start (spool, DHT), because Stop usually arrives first. The doc comment says "it runs until Stop", but the test only proves it starts and stops. The Unix test waits for "connected as worker once"; the Windows one has no equivalent.
- **Fix:** before `stop`, wait (deadline of at least 30 s) for evidence of a session:
  - an established TCP connection from the service's PID (`sc queryex`) to the cluster `port` (`Get-NetTCPConnection -RemotePort <port> -State Established`); or
  - the worker's `last_seen` / online state in the coordinator's store, opened the way `make_token` already does it.

### I5. `--join-only` runs as SYSTEM in a folder it doesn't check, and WK-18w's entry doesn't carry the ordering it depends on
- **Where:** `cli/worker.rs` run_with, with `Layout::lock` and `save_*` (create_dir_all, File::create, rename under `<data>\cluster`).
- **The dependency:** the decisions file says the installer must run `SecureDataFolder` before the join, "because `--join-only` doesn't check the folder's ACL itself". `%ProgramData%` lets ordinary users create folders. If the join ever ran before the folder was secured, a planted `Lodestar\cluster` junction would turn SYSTEM's lock, tmp and rename writes into writes wherever the junction points.

  The service path checks the folder first (`load()` calls `acl::secure_dir`); the new SYSTEM entry point doesn't. Today the only thing enforcing the order is a sentence in this decisions file. WK-18w's `notes` in `slices.yaml:917` don't mention it.
- **Fix (runner):** add "SecureDataFolder runs before `--join-only`, and the join is refused if it failed" to WK-18w's notes and review checklist. Optionally, defence in depth in a later slice: on Windows, have `--join-only` refuse a `--data` folder that `acl::verdict` doesn't call private.
