## New findings

### BLOCKING

**N-1. With the marker kept through step 4, the reinstalled `from` service refuses at once when the MSI starts it. With `ServiceControl Wait="yes"`, Windows Installer can treat that as error 1920, which fails a `/qn` reinstall with 1603. The rollback then halts on its normal path.**
- **Where:**
  - `rollback.rs:645-647`: the marker is no longer removed at step 3.
  - `packaging/windows/main.wxs:121`: `<ServiceControl … Start="install" … Wait="yes" />`.
  - `windows/service.rs:630-655`: the service reports Running at once, then `rollback_refusal` exits with REFUSED, within milliseconds of the Running report (an ACL check, a config read and a log write in between).
- **Failure scenario** (the main rollback path, exit 0 expected):
  1. Step 4 hands the `from` reinstall to the copy. The major upgrade removes `to` (whose `Remove="uninstall"` deletes the service), installs `from`, and StartServices starts the new service.
  2. `from` is a build with the marker check, so it reports Running and stops with exit 3 straight away.
  3. With `Wait="yes"`, Windows Installer polls the service status for up to 30 s after `StartService` returns. If its poll after START_PENDING lands after the stop, it sees STOPPED. That gives error 1920 ("Service … failed to start"). In `/qn` the error takes its default answer and the install ends 1603, rolling back the transaction.
  4. The helper's step 4 maps 1603 to `Stop::Halt("reinstalling 0.6.0 failed")` (`rollback.rs:708-710`). The service is disabled and stopped, and the recovery text applies.
  5. Recovery step 2 ("installs the {from} MSI by hand") runs while the marker still exists, because step 3 of the recovery deletes it afterwards. So a silent manual reinstall hits the same race. An interactive one shows the 1920 dialog, where Ignore works.
- **Before this delta:** the marker was gone before step 4, so StartServices brought up a healthy `from`.
- **Why I can't be sure:** whether Windows Installer misses the brief Running window is timing inside msi.dll that I can't observe on Linux. No test or smoke step covers an MSI install while the service refuses at start:
  - `smoke.ps1`'s refusal checks start the service directly, or stop the install in a custom action.
  - P-release's note that "an MSI downgrade over a newer schema installs fine and then stops" is reasoning, not a CI check.
  - The Fake can't model it: its `run_msiexec` returns whatever code it's given.
- **Why it blocks:** it's a plausible break of every completed rollback, introduced by this delta, and it ends in the service disabled. The session can choose one of three ways to clear it:
  - **(a) Verify on CI.** In `smoke.ps1`, write `<data>\bin\rollback.json`, then reinstall or upgrade the MSI with `/qn` and assert exit 0, then delete the marker. If it passes on windows-latest, record the evidence in the decisions file and this drops to a NIT. Better still, repeat it a few times, because it's a race.
  - **(b) Make the service tolerate the marker.** On the marker, stay Running (accepting stop), poll for the marker to go (a bounded interval, say 2 s), then carry on into the normal start. A stop ends it. Then:
    - StartServices always sees Running;
    - in the 3010 case, step 5's `stopped()` stops it;
    - in the exit-0 case, step 5's marker removal lets it continue, and the later `start_service` does nothing;
    - manual recovery works too.
    - The cost is a small `service.rs` change and a test.
  - **(c) Suppress the MSI's start during the helper's reinstall.** Pass a public property such as `LODESTAR_NO_START=1` in the rollback's `msiexec_args`, and put the `ServiceControl Start` in its own component conditioned on it. Step 5 starts the service anyway. This keeps LOW-A's protection during `msiexec`.
  - Reverting LOW-A part 1 (removing the marker at step 3 again) would also work, but it reopens LOW-A's window. Part 2 alone doesn't cover the StartServices start during `msiexec`.

## Crash safety and races (the delta)
- **Journal writes come before the side effects they guard:**
  - `done=4` is saved before step 5's wait stops the service.
  - Step 5's order on a repeat: remove the marker (idempotent, under `.lock`), restore the start type, start, rotate, save `done=5`.
  - A crash after the marker is removed but before `done=5` repeats step 5 safely. The store is restored and `from` is on disk.
  - If `set_start` fails after the marker is removed, it's a Retry with the service still disabled from `stopped()`. That's safe.
- **Step 3 without the marker removal:** a crash between `restore` and the save repeats the restore, whose repeat check is unchanged.
- **`take_result`'s new removal** is of a fixed name in staging, and only when `j.answer` is Some. Every path that sets a new `msi` clears `answer`, so a later copy's file is never removed.
- **The B-1 path:** the answer-taking run is `to` (Program Files), so probation runs at once. If the copy died and the boot run takes the answer, it's also `to`, and it's judged.
  - If `from` is still on disk (a pending rename because a file was held), it waits as before. If that never resolves, it's LOW-B's residual, which is accepted.
  - This closes the fail-open path in which an unjudged `to` kept running on the migrated store.
- **SCM:** step 5's wait now re-asserts disabled and stopped, with no service processes, on every pass, so a start from the SCM's failure actions or StartServices doesn't survive a pass.
- **Unbounded waits:** none new. The step-5 wait is per run (a Retry), not a loop.
- **Fixed sleeps:** none in the new tests or code.
