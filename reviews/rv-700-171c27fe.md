## Blocking

**B1. §2 Unraid worker bullet: "signed in as an admin or with an API key" is wrong.** This comes from the B5 fix. The round-1 review suggested this wording, and that suggestion was mistaken.
- **API keys are refused.** `crates/api/src/workers.rs:197-207` mounts every `/workers` route through `auth::protected`. Its guard (`crates/api/src/auth/http.rs:107-122`) calls `check_session`, and that calls `logged_in` (`http.rs:177-183`). `logged_in` accepts only a session cookie or the trusted proxy's user header. The module header says so outright (`workers.rs:23-24`): "every route is behind a session (API keys and feed tokens are refused)".
- **The request also needs the admin password in its JSON body.**
  - `create_token` calls `auth::confirm_fresh_password` (`workers.rs:~283`).
  - The body is `CreateWorkerToken { name, password }` (`dto/workers.rs:131-141`).
  - Without the password the call fails with `428 confirm_required`; with a wrong one, `401 bad_password`.
  - The body must be sent as `Content-Type: application/json`, and a cross-origin `Origin` is refused (`same_origin_json`).
- **The path is now correct:** `/api/v1/workers/tokens` (`crates/lodestar/src/http.rs:79`).
- **Fix:** something like "today a token comes from the API: `POST /api/v1/workers/tokens` from a signed-in browser session (API keys are refused), with a JSON body holding the worker's `name` and your admin `password`." Or say plainly that joining a worker isn't practical from the app yet **(planned)**.

**B2. The round-1 B2 fix is incomplete: §7's Windows update text has no "(newer than v0.5.1)" mark.** The round-1 list named "Windows self-install in §7".
- At v0.5.1, Windows has no update engine at all:
  - there is no `crates/lodestar/src/update/windows/`;
  - `update/unavailable.rs` reads "`/updates` where there's no update engine: … until E-M6's helper, Windows";
  - `can_install: false` and no checks.
- This head's §7 says, unmarked, "**Windows:** Lodestar checks and tells you. It installs only when you press **Install now** (MSI or portable) …", and the next bullet says checks run every 6 hours.
- A Windows user on the released v0.5.1 finds neither checks nor **Install now**.
- Line 15 promises that the text marks anything newer than v0.5.1.
- **Fix:** mark the §7 Windows sentence **(newer than v0.5.1)**. On v0.5.1 Windows, updating means installing the new MSI or zip by hand. The §10 update-helper heading is already marked.

**B3. "I can't reach the UI", step 3: "A narrower address, such as your LAN address, is safer than `0.0.0.0`" breaks the default Docker install.** This is new with the N4 fix.
- The Unraid template is `<Network>bridge</Network>` (`packaging/unraid/lodestar.xml:6`), and `docker-compose.yml` publishes `8090:8090`.
- In bridge mode the host's LAN address doesn't exist inside the container. A user who sets `LODESTAR_HTTP_BIND` to it gets a `serve` that can't bind, so the advice locks them out in the very section meant to get them back in.
- On Windows, the Start-menu shortcut is fixed to `http://localhost:8090/` (`main.wxs:163`), so a LAN-only bind also breaks the shortcut. The same paragraph mentions it.
- §4.2 already scopes this advice correctly: host networking only.
- **Fix:** scope the sentence. For example: "With host networking or a native Linux install, binding to your LAN address is narrower than `0.0.0.0`. In Docker bridge mode (the Unraid and Compose default), leave it at `0.0.0.0`: the port mapping decides who can reach it. On Windows, keep the MSI's `WEB_FIREWALL` option off unless other PCs need the UI." The "never forward it on your router" line is good; keep it.

## Non-blocking

- **N1. The v0.5.1 fallback in "The web address is wrong".** "Set `LODESTAR_HTTP_BIND` or `bind` under `[http]` in `config.toml` instead" is only half true.
  - At v0.5.1, a saved address also beats `config.toml` (`settings/network.rs` `effective_bind`, and `Field::new("http_bind").file(...).env(...)`).
  - v0.5.1's keep-or-revert (`system/address.rs`) reverts a pending address that fails to bind. A saved address that was confirmed and later becomes unbindable stays, though, and `config.toml` doesn't override it.
  - Suggest: "`LODESTAR_HTTP_BIND` always works; `config.toml` only when no address is saved in the app."
- **N2. The backup Result in "I changed several settings".** It lists `config.toml` as always present. `backup.rs` copies it only if one exists (`config_file: Option`). Suggest "and `config.toml`, if you have one", as user guide §3.7 says.
- **N3. "`reset --all` also removes the passwords, API keys …".** A reader may think this means Lodestar's own API keys, the ones other apps use to call it. Those aren't settings rows and aren't touched. The secret settings are `integrations.torznab_api_key` and the notification URLs, tokens and password. Suggest "the Torznab API key".
- **N4. §7: "A failed MSI update does roll back by itself."** The portable build also rolls back by itself after a failed self-test (`update/windows/portable.rs`, journal step 4). Suggest "A failed update (MSI or portable) rolls back by itself."
- **N5. The §2 "Commands from §10 on Windows" example uses `settings get`.** It's unmarked, and on v0.5.1 it's an unrecognized command. Use `stats` as the example, or add the mark.
- **N6. Step 1 of "I changed several settings": "on Docker, use the one-off container from §7".**
  - While the container still runs, `docker exec <name> /lodestar backup` is simpler.
  - The §7 example also needs adapting: drop the `/import` mapping and replace `import inspect …` with `backup`. One clause would help.
- **N7. The restore link goes to the user guide's §3.7, which gives Unraid paths only.** Native users have the backup's `README.txt`, which repeats the restore steps. A half-sentence saying so would help them.
- **N8 (carried from round 1, out of scope).** `packaging/unraid/lodestar-worker.xml:13` and `cli/worker.rs` (`JOIN_AGAIN`) still point to a "Settings → Workers → Add worker" screen that doesn't exist. Route this via the runner.
