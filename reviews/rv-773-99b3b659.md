## Verified

- **The fix (check 1).**
  - `start_bootstrap` always starts one `bootstrap`-marked self-lookup for the current `ids[0]` in each family. That is exactly what a pending `rejoin[f]` waits to start, and its `finish_lookup` plans the join (`done.target == self.ids[0]`, `join_planned` was reset by the id change). So clearing every flag there is equivalent to the rejoin running, and loses nothing.
  - The flags are cleared before the loop, and `target` is read inside it, so the lookup is for the id the flag meant. Everything is synchronous actor code: `on_external_ip` can't run inside `start_bootstrap`, so there's no window between the clear and the starts.
  - **The O-1 race is closed.** Stale lookup ends in `scrape_tick`, re-bootstrap starts in the same `maintain`, and the flag is now false, so the next `rejoin_tick` starts nothing. The same holds when the flag waited on `MAX_LOOKUPS` instead of a stale lookup.
  - **Id change mid-bootstrap (rv-756 N-3) is unchanged.** The flags are set only in `on_external_ip`, after the tables are rebuilt; `rejoin_tick` still waits for an old-id self-lookup and then starts one for the new id. A re-bootstrap can't run while that old lookup is out (it needs no maintenance lookups), so it can't clear a flag whose lookup would then be missed. An id change after a re-bootstrap sets the flags again and the old-id bootstrap lookups count as stale. A second id change while the rejoin lookup is out marks it stale for the newer id. The existing rejoin tests (mid-bootstrap, after bootstrap, exempt, `MAX_LOOKUPS` wait, per-family wait in both orders) pass.
  - The initial `start_bootstrap` (`:521`) runs with the flags all false from `Actor::new`, so the change is a no-op there.
  - **Sequential, not duplicate:** a rejoin lookup that ends at once and a re-bootstrap later in the same tick give two self-lookups for the same id one after another. That's the ordinary thin-table re-bootstrap, not two running at once, and was so before.
