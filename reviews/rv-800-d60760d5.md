## How each egress path fares
- **Flows opened through the tunnel (TCP, UDP, ICMP echo, DoT on :853):** rule 1 CONNMARKs them on `-o wg0`. Rule 2 drops them on any other interface. Both sit above gluetun's interface-less ESTABLISHED accept. RELATED ICMP errors carry the master conntrack, so they inherit its mark. Closed.
- **ICMP port-unreachable to the endpoint:** that flow is unmarked, so rule 3 covers it. Rule 3 only drops, so the exemption can't widen anything. `! LOCAL` keeps loopback's ECONNREFUSED. Closed.
- **DNS:** plain DNS goes over loopback to gluetun. DoT is marked. Closed, and `dns_*_blocked` checks it.
- **IPv6:** the rules mirror IPv4. The leak test asserts `post_rules_ipv6`, no IPv6 on the bridge, no global address in the namespace, and no host IPv6 forwarding. Closed.
- **The web UI reply path, the Docker network, and WireGuard's own UDP:** these flows never use wg0, so they stay unmarked and keep working. No rule accepts anything.
- **Order and reconnect:** gluetun appends its VPN accepts (`SetVPNConnection`) and runs the post-rules once, at `enable()`. Our `-I 1..3` rules stay on top. A container restart re-runs `enable()` along with the rules.
- **FORWARD:** the namespace forwards nothing. The host side is measured by the new DOCKER-USER counter.
- **Flows opened before gluetun's `enable()`** never touch wg0, so these rules don't cover them (see O3). The fleet isn't exposed: Lodestar starts `--no-deps` into a gluetun that's already healthy (`block-lib.sh:74-75`).
- **The 0444 `configs:` copy:** only gluetun's own root can rewrite it, and gluetun reads it once at start. That root also has NET_ADMIN and could rewrite iptables directly, so the copy adds no new risk. Lodestar shares only the network namespace and has no capabilities. `--force-recreate` refreshes the copy. This doesn't matter in practice.
- **The pin:** the digest is kept. pia-example uses the same digest, and a test enforces that.

## Important
- **I1** `docs/user/03-keep-lodestar-safe.md:96`: the step's **Result** doesn't prove the rules loaded. gluetun logs `[firewall] enabled successfully` even when it skips a missing file. A failed `wget -O` at `:90` leaves an empty file that gluetun also skips. Either way the user believes the gap is closed when it isn't. Fix: make the Result `docker exec gluetun iptables -S OUTPUT | head -4`, which should show the CONNMARK line and the two DROP lines naming `wg0`, plus `docker exec gluetun ip link show wg0`. Also check `grep -c '^ip' <file>` gives 6.
- **I2** `docs/user/03-keep-lodestar-safe.md:94`: "It works for OpenVPN too" has no evidence. The decisions file shows only that WireGuard reads `VPN_INTERFACE`, and the leak test exercises WireGuard only. If gluetun's OpenVPN path ignores the name or rejects `wg0`, one of two things happens: the rules silently do nothing, which overclaims, or OpenVPN won't start. Fix: check it on v3.41.3, or replace the sentence with "Checked with WireGuard; with OpenVPN, run the check in step 4", which I1 provides.
