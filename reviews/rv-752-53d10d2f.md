## State-machine analysis
Every operation below runs under the one authority mutex, so the interleavings at the authority are serial. The question is only which order they land in.

- **Grant** (`LeaseTable::claim`, `regrant`/`restore`):
  - These only insert when the key has no lease, so a token is never replaced in place.
  - Tokens are never reused (epoch plus seq, rolling over to a new epoch).
  - So a mark keyed by token names exactly one lease.
- **Mark** (`mark_fetched`):
  - It requires `holder == worker && token == lease.token`.
  - It is idempotent, and the first mark time is kept.
  - It changes nothing else: no heartbeat, no sources.
  - Its time is the coordinator's clock, never one the worker supplies.
- **The holder's claim:**
  - **Mark, then claim:** `Committed`. The source merges, and `finder` stays because the claimer is the finder.
  - **Claim, then mark:** `Held{self}`, which the server sends as `Granted` with the same token, as on main. The worker's 180 s grace covers this window, and it's only one link round-trip wide.
  - Both orders are tested: `…as_committed` and `a_holder_that_never_reports_fetched…`.
- **Another worker's claim:** `Held{A}` with its hints relayed, as before. A marked lease can never be granted to a second worker, because it stays in `leases` until it ends.
- **Commit or loss** (`release`, `commit`, `report`, `take_back`): all go through `LeaseTable::release`, which clears the mark (`:211`).
  - **Commit, then `Fetched`:** no lease is left, so nothing happens and it isn't counted stale.
  - **`Fetched`, then commit:** the mark goes with the lease.
  - Both orders are tested.
- **Expiry:**
  - The silent-holder path clears marks via `inspect`.
  - A marked lease whose holder is also dead is filtered out of `stuck`, so it isn't listed twice. A duplicate would be dropped by `filter_map` anyway, so `n` is right.
  - Expired keys are parked in `pending` with their cohort and sources, and come back out by claim or re-grant under a new token. The re-grant does its own store check.
  - **Mark versus expiry:** both run under the lock. A mark after the expiry finds no lease and returns `None`.
- **Eviction (drain, revoke):** clears the marks too. Tested.
- **Restore or `restore_if_free`:** inserts only when the key is free, and never touches marks.
- **Leaks:** marks are removed only in `release`, `expire` and `evict`, which are the only `leases.remove` sites. So the invariant "every mark's token is the current token of a live lease" holds.
  - The map is bounded by the number of live leases, which admission already bounds.
  - `expire` walks the marks once a tick, O(marks), which is fine.
- **Double commit:** not possible. The store de-duplicates by infohash, and after an expiry the old token's commit, `release` and report are all stale.
  - If a result already with the writer commits after its marked lease expired, the re-grant ends at its store check (`report(.., None)`) or at the refetch's `AlreadyStored`.
- **Lost key:** never. An expired marked key is in `pending` until something takes it.
- **Arithmetic and clocks:**
  - `marked + ttl < now` follows the pattern of the existing `seen + ttl < now`, on the same server clock as heartbeats.
  - `marked` comes from the coordinator, so a worker can't push it to overflow.
  - A wall-clock jump behaves as it already does for heartbeats.
- **Locks:**
  - `fetched()` takes the authority lock once, and no await happens under it.
  - `outcome()` takes no fleet lock.
  - The tick still goes fleet → authority, as before. No new nesting.
- **WK-11b (reconnect and replay):**
  - A replayed batch can't carry a marked lease, because a batch is dropped from flight and spool on the same `Accepted` that triggers `Fetched`.
  - A reconnecting holder that claims again a key it already delivered now gets `Denied{Stored}` instead of its lease back (`server.rs:1660-1668`). That is correct: its result is in, and its new session's `held` never needs that token.
  - A `Fetched` sent on a newer session for an older session's lease is accepted, as all outcomes are.
  - Nothing in WK-11b's planned scope (reconciling replayed batches against the leases) depends on a holder getting a delivered lease back.
- **Protocol compatibility:**
  - **Older worker:** never marks, so nothing changes. Tested.
  - **Newer worker, older coordinator:** the older coordinator's `held` check keeps the lease. Each `Fetched` after a commit is one stale-report tick there, which is noise only.
  - There's no wire change.
- **A malicious or buggy `Fetched`:**
  - **For a key it doesn't hold, or under a stale token:** `mark_fetched` returns `None` and nothing changes. If the key has a lease it is counted stale, as before.
  - **For a key with no lease:** silent. This is an observability gap, not a safety one, because no state changes (Nit 1).
  - **For its own lease, before delivering the result:** it only denies its own claims, and its lease now expires 600 s later instead of living for as long as it heartbeats. It harms only itself, and it's stricter than main.
  - **A flood:** one or two lock acquisitions per item, at most 1,024 items a message. It's the same order as any report, with nothing to grow.

### Nit
1. **A `Fetched` for a key with no lease is invisible, whatever the reason** (`crates/cluster/src/server.rs:1749`).
   - The expected case is a `Fetched` that arrives after its commit. But a `Fetched` for a key that was never leased, or one whose lease expired and was re-granted and then committed, is silent too.
   - A buggy worker that sends `Fetched` for random keys leaves no trace in `cluster_stale_reports_total`.
   - The check is also two lock acquisitions (`fetched`, then `get`), with a harmless gap between them for the metric.
   - **Fix:** have `LeaseAuthority::fetched` return a tri-state under one lock: `Marked(lease)`, `Committed` (no lease, and the key is in `recent`, which always exists once `serve_remote` ran), or `Stale`. Count only `Stale`.
2. **The module docs still list two ways a lease ends** (`crates/cluster/src/leases.rs:9-13`, "A lease ends exactly once: … commits … or … silent").
   - **Fix:** add a third bullet: a lease marked fetched expires a TTL after the mark, holder alive or not.
   - The PR description should name this as a refinement of §19.3 ("If a worker vanishes, its leases expire") for the runner to flag. The decisions file already records it.
3. **Hints for a marked lease are still relayed to its holder** (`server.rs:1670-1686`). Another worker's claim on a marked lease sends hints to a holder that has already delivered and will discard them.
   - **Fix (optional):** skip the relay when `is_fetched(holder, key)`. It's small and saves wasted frames under a writer stall.
4. **Untested edges** (`leases.rs` tests):
   - a marked lease whose holder also went silent is expired once (`n == 1`);
   - after a marked lease expires, the holder's own claim is `Granted` under a new token from `pending`, not `Committed`.

   Both hold by reading the code. Two asserts would pin them.
5. **The decisions heading lacks the PR number** (`docs/decisions/2026-11-12-X-wk-fetched-lease.md:1`). The README asks for `# X-wk-fetched-lease decisions (#752)`.

### Observed, outside this PR
A drained worker's accepted but uncommitted results meet the same fate as an expired marked lease: `evict` parks the keys, and `take` drops the records as stale. That is main's behaviour, unchanged here. I mention it because it belongs with the follow-up below.

## The intake-drop trade-off
**Dropping the result is safe.** The decisions file states the loss accurately.

- **What can be lost:** a fetched info dict whose lease expired more than 600 s after `Accepted` while it still sat in intake.
  - The key is parked in `pending` with its cohort and sources, then re-granted and fetched again.
  - If its peers are gone by then it ends as an honest `lost` row. That's a re-fetch, not a silent loss.
- **What can't happen:**
  - a double commit (the store de-duplicates, and old-token commits are stale);
  - a double lease (the mark never grants);
  - a key that is never leased again (it is in `pending`).
- **One accounting wrinkle:** a result already with the writer that commits after the expiry writes no funnel row, because there is no lease to end. The re-grant then ends at its store check with `report(.., None)`, so that key can have no terminal row.
  - The same thing happens today for a silent worker's expired lease, so it isn't new. It is now reachable with a live holder, under a writer more than 600 s behind.
- **Is it worth it:**
  - A writer 600 s behind, with 80 batches queued, is far outside the §19.8 budgets.
  - The expiry is the only thing that frees the lease of an undecodable batch. On main that lease lived for as long as its holder heartbeated, so the expiry is a net improvement.
- **On the follow-up:**
  - **It's warranted only as low-priority hardening, not as a fix this PR needs.**
  - **As described, it would do nothing:** after the expiry the key is in `pending`, and `restore_if_free` refuses a pending key (`leases.rs:683`).
  - **What it would need:** take the key out of `pending`, if it's still there and neither stored nor committed recently, and lease it to the result's sender under a new token, keeping its cohort. If the key has already been re-granted, the record must stay stale.
  - **Two cases would benefit:** the drain-eviction case above and this one.
  - **Where it belongs:** it needs `remote.rs` and a new authority method, so it's a separate slice.
