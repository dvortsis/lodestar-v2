## 1. I1: is it really fixed?

- **Detection is on the AST, not a string match.** `percolate.rs:159` calls `d.query.mentions_same_payload()` (`query.rs:1484`). That returns true for `Node::Sig` whose value isn't 16 characters, and it recurses through `And`, `Or`, `Not` and `File`. I checked it with a temporary parse probe, since removed:
  - `sig:<40hex>`, `-sig:<40hex>`, `x | sig:<40hex>`, `(a (b | -sig:<40hex>))`, `sig:magnet:?xt=urn:btih:<40hex>`, and `sig:<40hex> sig:<16hex>` all give **held**;
  - `sig:<16hex>` and `-sig:<16hex> | x` give **not held**;
  - `"sig:<40hex>"` parses as a `phrase` and isn't held. That's correct: it's not a `sig:` clause and resolves nothing;
  - `SIG:`/`Sig:` parse as plain words. Field names are case-sensitive throughout the language, so these aren't `Sig` nodes and resolve nothing. This is no false negative;
  - `file:(sig:…)` is a parse error.

  No false positives or negatives. Negated `-sig:<hash>` is held too, which also closes the over-alerting half of the old I1.
- **Readiness uses the run's snapshot.** `index.prefilter("payload_sig", &searcher, EmptyQuery).is_some()` (`percolate.rs:160–163`) is true only when the field's availability is `Ready` *and* the searcher's generation is at or past `ready_since`. A run whose snapshot predates completion is held one more run. That's correct, and it's the same gate every prefilter uses. `Missing` (an older index serving during a rebuild) is held as well. `NoProducer` can't happen at generation 1.
- **The watermark is kept, and alerts fire exactly once.**
  - **While held:** the search is `continue`d before any `Matched` is pushed. It isn't in `matched`, `failed` or `capped`, so `run_once` records nothing for it and its watermark stays put. `more()` stays false, so there's no spinning.
  - **Each run:** `percolation_due` (`store/src/saved.rs:294`) has no LIMIT, so held searches can't crowd out others.
  - **Once Ready:** the search scans `(watermark, …]` in `max_range` steps, as any search that fell behind does. `alerts` is unique per (search, torrent), so it can't alert twice.
  - **No flood:** the range holds only ids indexed after the search was saved, because a new search starts at the index watermark and `sig:` couldn't be saved before GS-0. So it's exactly what normal alerting would have produced, subject to the usual `keep` and prune bounds.
- **If the backfill never completes,** the search is held with no signal of its own. That's acceptable:
  - the walk is SB-6's one-time job, driven by the indexer's `catch_up`. A stuck walk is an SB-6 bug that the status page already shows: `unpopulated()` lists `payload_sig` as `Backfilling { done, upto }`;
  - `/search` with the same query shows `incomplete_fields`;
  - a blue/green rebuild writes the field at once (Ready), which releases the hold.

  What's missing is any hint on the alert side. See N1.
- **The bare 16-digit exception.** `mentions_same_payload` is false when `sig.len() == SIG_DIGITS`. Such a query is `sig_term(payload_sig, value)` (`compile.rs:1074`), one term lookup that resolves no reference. It's safe mid-backfill because an alert's range covers only torrents indexed after the search was saved, and those are written by the new producer with the field. That matches the brief ("never answers 'no match' on an unpopulated document") and the decisions file ("The bare 16-digit form looks nothing up and runs as now"). I found one narrow edge, listed under N2.

### Important

**I1. Promoted clones during the walk are dropped for a held `sig:<info hash>` search, and the delta makes that unconditional.** The hold is at `crates/search/src/percolate.rs:159–166`. The row is consumed at `crates/lodestar/src/percolator.rs:335` and `356`.

- **Scenario:**
  1. During the generation-1 walk, a user saves `sig:<hash of R>`. R has already been walked and carries its signature. The search's watermark W is the index watermark at save time.
  2. An unverified item with id P < W, a clone of R, is promoted (SRC-2b). It's re-indexed with its signature and queued.
  3. `run_promoted` → `matched_promoted` calls `percolate` over `(P-1, P]`, because the search's `watermark >= P`.
  4. The hold `continue`s, so there's no `Matched` and no hit.
  5. `done = Some(row.seq)`, and `record_promoted` deletes the row.
  6. The clone never alerts. Once the walk completes, nothing replays it.
- **Probe, since removed:** mid-walk (12 of 30), with reference id 4 and promoted clone id 7, both walked, `percolate(watermark 6, through 7)` returns `matched=[]` at aa09693a. With the hold removed it returns `torrent_ids: [7]`. So before this delta that clone alerted; now it doesn't.
- **Why it matters:**
  - It's the same lost-alert class as the old I1, and the decisions file now says "An alert never loses a clone to the backfill". That isn't true for promoted arrivals.
  - GS-2, RX-1 and ENR-11 will reuse whatever hold pattern this sets.
- **Fix options, for the runner to choose:**
  - **(a) Make the hold visible to callers.** Add `held: Vec<i64>` to `Percolation`. In `run_promoted`, stop the batch at the first row for which a held search was due, without consuming it or later rows and without setting `more`, as a row the index hasn't reached already waits. This is about 15 lines plus a test in `percolator.rs`, which is outside GS-0's owns. The cost is that every promotion alert waits until the walk ends, a bounded one-time delay. The decisions file should say so.
  - **(b) Opt the promoted path out of the hold** with a `Due` flag. That restores the pre-delta behaviour (it alerts when R was already walked), and the residual miss gets recorded.
  - **(c) Record it as a known limitation** in the decisions file and `docs/query-language.md`, then put (a) or (b) into the next brief that touches percolation (standards §5).

  I lean to (a) or (c). Whichever is chosen, correct the decisions-file sentence ("An alert never loses a clone to the backfill") to match.

### Nit

- **N1. Held alerts give no hint at all.** This is at `percolate.rs:164` and `docs/query-language.md:437`.
  - **Scenario:** a user saves `sig:<hash>` during a long walk and sees no alerts for hours.
  - **Fix:** add one sentence to the user doc's "After an upgrade" bullet, for example "Alerts for a pasted info hash wait until that's done, then catch up; none are missed." Optionally, log a count of held searches in `ALERTS_RUN`, since a walk stuck by an SB-6 bug would otherwise hold them silently.
- **N2. The bare-signature exception assumes the alert's range is all post-upgrade ids.** This is at `query.rs:1486`.
  - **Scenario:** a saved search is unreadable or failing, so it keeps an old watermark ("Skipped, not moved past", `percolator.rs:168`). It's re-saved after the upgrade as a bare `sig:<16hex>`. It then catches up over pre-upgrade ids the walk hasn't reached, and their clones are missed while the watermark advances.
  - **Fix:** none is needed now, since it's very narrow. Mention it in the decisions file's bare-form sentence ("the new torrents an alert covers"), or hold bare forms only when the range reaches below the walk's `high`.
- **N3. Small cleanups.**
  - The readiness check runs once per due search (`percolate.rs:160`), taking the population read lock each time. Hoisting it above the loop as a `let payload_sig_ready = …` would be clearer and cheaper.
  - `Percolation`'s doc ("Searches that ran") and `percolate`'s doc don't mention that a search can be held. Say so in one line. It's relevant to I1's callers.
- **N4. Unit coverage for the hold's detection.** `mentions_same_payload` has no unit test for `-sig:<hash>`, an OR group, or the 16-versus-40 split. The integration test covers only the top-level forms. Add 4 asserts next to `sig_takes_a_signature_or_an_info_hash` (`query.rs:2533`).
