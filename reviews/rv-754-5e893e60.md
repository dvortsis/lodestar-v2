## 2. New lost-alert or double-alert paths

I found none.

**Promoted pass with forward held, no double alert.**
- The promoted pass is due only when `watermark >= P`.
- The held forward search's later catch-up range is `(W, …]`, which excludes P.
- `alerts` is unique per (search, torrent) anyway.

**P > W, no loss.**
- The row is consumed without running, because the filter `watermark >= torrent_id` is false.
- The forward run meets P in its own range after the walk completes. P is then indexed with its signature, and R is walked.
- This is the existing "a search below it meets it in its own range" design. The hold makes it safe, not lossy.

**The readiness check is hoisted, with no TOCTOU between check and use.**
- `sig_complete` is computed once per `percolate` call (`percolate.rs:163–165`), from the same `searcher` that every query in that call runs on.
- `prefilter` reads the live availability, then gates on `searcher.generation() >= ready_since`.
- **Readiness can't be early.** A completion that lands after the snapshot was taken still reads as not complete for this snapshot.
- **Readiness can't flip back.** Availability doesn't go from Ready to non-Ready on a live `SearchIndex`: a generation bump happens at open, and a rebuild is a new index.
- So a single read is consistent for all due searches. That's strictly better than the previous per-search reads, which could in principle disagree within one run.

**Concurrency between the backfill and percolation.**
- Each `percolate` call is one snapshot.
- `run_promoted` calls `percolate` once per row, and each call takes a fresh searcher. Rows may therefore see different completeness, but each is self-consistent. The promoted path isn't held now in any case.
- The backfill rewrites existing ids, and percolation selects by id range, so re-indexed documents are never re-alerted as "new".

**Live queries.** `percolate_live` sets `count_only: true`, so it never enters the hold branch. Its `hold_unresolved: false` is moot but consistent with "live queries are never held".

- **Fix (cheap, either one):**
  - **(a) Smallest.** Build the two `Due`s through two tiny named helpers in `percolator.rs`, for example `fn forward_due(id, watermark, node) -> Due` and `fn promoted_due(id, torrent_id, node) -> Due`. It's a pin rather than a behaviour test, but it's enough for two literals.
  - **(b) Behavioural.** Add a `percolator.rs` test on its existing index-and-promotion harness (`tests` at `:564`, `promote` at `:1084`) with `payload_sig` set back to generation 0 in the index metas, as `payload_sig.rs::unpopulate` does. Save `sig:<hash>`, run `run_once` mid-walk and assert the watermark didn't move, then promote a clone of an already-walked reference and assert it alerted. This is more work, about 80 lines, and needs the `unpopulate` helper in `lodestar`'s tests.

### Nit

**N1. The user-doc line is slightly off in both directions.** This is at `docs/query-language.md:438`.
- "Sends no alerts" isn't quite true: a promoted clone of an already-backfilled reference does alert during the walk.
- "Catches up on the torrents it missed" isn't quite true either: a promoted clone of a not-yet-backfilled reference is never caught up (X-percolate-promoted-hold).

The reader impact is tiny, and the line is fine as a first cut. Optionally soften it to "sends almost no alerts until that background work is done, then catches up", or leave it until X-percolate-promoted-hold lands and the sentence becomes exact.

**N2. `sig_complete` is computed on every call,** including the per-row promoted calls and runs with no `sig:` search. This is at `percolate.rs:163`. It costs one read lock each time, so it's negligible. It could be lazy (`OnceCell`, or computed only when `due.iter().any(|d| d.hold_unresolved && …)`), but that isn't worth churn now.
