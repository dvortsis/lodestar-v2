## Blocking

**B1. §5 "One folder" (line ~262): `lodestar backup --to <folder on the array>` sends an Unraid user's backup to the wrong place.**
- On Unraid, Lodestar runs in a container. `docker exec Lodestar /lodestar backup --to /mnt/user/...` writes to that path *inside the container*.
- Nothing maps an array path into the container: `packaging/unraid/lodestar.xml` maps only `/data`. The backup lands in the container's writable layer, and the next update or re-create deletes it. The user believes they have a backup when they don't.
- The line also drops the user guide's "keep it on a private share" warning. The backup holds `seal.key` and `auth.json`.
- **Fix:** follow `docs/user/03-keep-lodestar-safe.md` §3.7. Run `lodestar backup` into the data folder, then `cp -a` the folder to a private share. Link there. Mention `--to` only for a path the container can see, and say that it needs its own path mapping.

**B2. Line 15 promises "Where a feature needs a newer version than v0.5.1, the text says so". The new text doesn't keep that promise.**
- At tag v0.5.1, `crates/lodestar/src/cli/mod.rs` has only these commands: serve, healthcheck, import-bitmagnet, lists, backup, rollback, vacuum, reindex, stats, rollup.
- These are missing from v0.5.1:
  - `settings`
  - `worker`
  - `companion`
  - the `import` job commands (the page already marks these)
  - the Windows update helper: v0.5.1's `main.wxs` has no `update-helper`
- The PR also removed the old "(planned; requires Lodestar v0.6+)" on the worker template. The template itself still says "Requires Lodestar v0.6+" (`packaging/unraid/lodestar-worker.xml:13`).
- The result: a v0.5.1 user, which includes everyone on the `:latest` tag, follows "I can't reach the UI" or "I changed several settings" and gets clap's "unrecognized subcommand" error (exit 2).
- **Fix:** add a newer-than-v0.5.1 note to each of these:
  - the `settings` steps in §8 (both procedures);
  - the `settings`, `worker` and `companion` rows in §10;
  - §10's "Settings from the command line";
  - the worker bullet in §2 Unraid and the Workers row in §1;
  - Windows self-install in §7 and §10's update helper section.

  Where a v0.5.1 user has another way out, give it: `LODESTAR_HTTP_BIND`, or `bind` under `[http]` in config.toml.

**B3. §7 (line ~288) claims Windows installs updates itself, which isn't built.** The doc says: "Lodestar can also install updates itself on Linux and, through the MSI's update helper, on Windows. That is off until you turn it on…"
- On Windows nothing installs automatically:
  - `crates/lodestar/src/update/windows/check.rs:745-746`: "nothing installs on its own on Windows yet";
  - a scheduled (window) install returns `not_built_yet` (`check.rs:958-959`);
  - the app's Roll back answers `not_built_yet` on Windows (`check.rs:1328`).
- Only **Install now** works there. For the MSI it goes through the helper. The portable build uses its own install (`check.rs:769-777`, `update/windows/portable.rs`), which the sentence leaves out.
- That documents planned behaviour as built (user-docs §3).
- **Fix:** something like: "On Windows, Lodestar checks and tells you. It installs only when you press **Install now** (MSI or portable). Automatic installs on Windows are **(planned)**." Keep "rolls back on its own" for Linux, and for the MSI helper's probation (`update/windows/rollback.rs`), which is real.

**B4. §8 "I changed several settings and now nothing works": `reset --all` has no proper backup step and no stated loss.**
- Step 1 makes the backup conditional ("If the server still runs, run `lodestar backup`"). But `backup` works with the server stopped. I tested it at this head and it wrote all four files. So a user who has already stopped Lodestar skips the only undo.
- The Result line doesn't say what is lost. Every saved secret goes too: notification URLs and tokens, download-client passwords and the Torznab API key. All are `settings.` rows that `reset_all` nulls (`cli/settings.rs`, `reset_all`). The user has to enter them again in the app, and the page should name the undo: restore the backup (user guide §3.7).
- Standards §5 item 8 treats "a risky step without a warning and an undo" as blocking.
- **Fix:**
  1. Always take the backup first: Docker in the one-off container from §7, native as is.
  2. Add a line: "This also removes the passwords, API keys and notification addresses saved in the app; enter them again afterwards. To undo, restore the backup (user guide §3.7)."

**B5. §2 Unraid worker bullet (line ~86): the API path is wrong.**
- The doc says `POST /workers/tokens`, but the API is nested under `/api/v1` (`crates/lodestar/src/http.rs:79`, `crates/api/src/workers.rs:201`). The path as written returns 404.
- The call also needs an admin session or API key, which the page doesn't mention. The reader can't do this step from what the page gives.
- **Fix:** write `POST /api/v1/workers/tokens` and say it needs a signed-in admin or an API key. Or say plainly that joining a worker isn't practical from the app yet **(planned)**.

## Non-blocking

- **N1. §10 "Where to run it", systemd (line ~635).**
  - The consequence it gives for running as root is inaccurate. With `DynamicUser=yes`, systemd makes `/var/lib/lodestar` a symlink to `/var/lib/private/lodestar`. The privilege drop refuses a symlinked data dir (`privdrop.rs:509-515`), so the command stops with an error rather than handing the folder over. systemd also re-owns its StateDirectory at start. The advice not to run as root is still the safe one; reword the reason.
  - "editing `/var/lib/lodestar/config.toml`" doesn't fix a *saved* `http_bind`: a saved value beats config.toml (tested: source `saved`, "without the saved value: … (config.toml)"). On systemd, only an `Environment=LODESTAR_HTTP_BIND=` line recovers from that. Say so.
- **N2. Healthcheck example in §8 (line ~459).**
  - The real text ends `Connection refused (os error 111)`.
  - Worth adding: with a bad saved address, `healthcheck` probes *that* address (tested: `unhealthy: connecting to 192.0.2.1:18791: …`). That points straight at the cause.
- **N3. §10 `companion` row.** "Safe use" should say that `install` and `remove` need the server stopped, as `--help` does.
- **N4. `0.0.0.0` isn't defined.** The default `0.0.0.0:8090` and the `0.0.0.0:8080` example appear without a definition. Say once that it means every network interface on the machine. Recommend a LAN address, and never forwarding 8090 (user-docs §6: use a VPN for remote access).
- **N5. §7 update checks.** "makes one signed check" reads as a one-off. It's every 6 hours, plus a manual check (docs/decisions/2026-11-08-PK-win-upd-1.md).
- **N6. Windows Start-menu shortcut.** It is fixed to `http://localhost:8090/` (`main.wxs:163`). After changing the port it won't open the UI. Worth one line in the I-can't-reach section.
- **N7. Commit bodies.** Two of the three commits have no body ("a body that says why", standards §2).
- **N8. Out of scope for this PR (route via the runner).** `packaging/unraid/lodestar-worker.xml:13,26` and `cli/worker.rs:49` (`JOIN_AGAIN`) tell users to use "Settings → Workers → Add worker", which doesn't exist: there is no workers screen under `web/src/lib/features/**/screen.ts`. The doc correctly marks that screen **(planned)**.
- **N9. §1 "Not built yet" row.** It could also list the other planned items the page marks: the address screen, the worker-token screen and automatic Windows installs. Then the table is the one place to see them.
