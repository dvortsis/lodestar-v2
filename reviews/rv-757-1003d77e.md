## Important

### I1. Scrubbing credentials from the parsed answer can corrupt a valid answer, so a successful add is reported as failed
**Where:**
- `crates/integrations/src/clients/usenet.rs:299-319` (`scrub`)
- applied to the raw body before parsing at `nzbget.rs:166-167` and `sabnzbd.rs:161`

**The problem:** `scrub` replaces every occurrence of the NZBGet password or user name (anything of 4 bytes or more) in the body before it's parsed. Those strings can occur in a legitimate answer.

**Scenario, reproduced as M4:**
1. A user has the numeric NZBGet password `2024`.
2. NZBGet accepts the NZB and answers `{"version" : "1.1", "id" : 1, "result" : 12024}`.
3. `scrub` turns this into `"result" : 1***`, which isn't JSON.
4. `add_nzb` returns `Protocol("the answer isn't NZBGet's JSON")` although the job is queued.
5. UN-3 reports a failure, the user clicks Send again, and the release is queued twice.

The same happens when the request `id` (a per-adapter counter, so long-lived adapters reach 4+ digits) contains the password. A password or user name equal to a JSON key the parser needs (`result`, `Name`, `Value`) also silently breaks parsing: `Name` or `Value` yields an empty category list. SABnzbd is practically unaffected, since its 32-hex key never occurs inside an 8-character `nzo_id`.

**Fix:**
- Scrub only the text that becomes an error reason, never the bytes that are parsed for ids, versions or categories. Concretely: apply the scrub inside the error paths (`rejected_status` / `forbidden` / `refusal` for SABnzbd, and the RPC `error.message` and the non-200 branch in `answer` for NZBGet).
- Add a regression test: a numeric password plus an NZBID containing it must still return the job id.

### I2. No adapter-level test covers the scrub, and removing it passes every test
**Where:**
- `crates/integrations/tests/usenet_clients.rs:631-699`
- `usenet.rs:388-396` (the only scrub test, on the bare function)

**Scenario:** M3 removes all three `scrub(...)` calls and the whole suite stays green. A later refactor could drop or misplace the scrub, for example by moving it after error mapping, and a reverse proxy that echoes the request body on a 500 or 403 would then put the SABnzbd key into `Rejected("HTTP 500: … apikey=…")`, which UN-3 shows and logs.

**Fix:** add fixtures whose error bodies echo the credentials:
- a SABnzbd 500 whose body contains `API_KEY`;
- an NZBGet JSON-RPC `error.message` and a 502 body containing `PASSWORD`.

Then assert that neither the `Display` nor the `Debug` of the error contains them. This pairs naturally with the I1 fix.

## Nits
- **N1. One copy of the config answer is never zeroized** (`usenet.rs:304-318`). When nothing matches, `scrub` builds `out`, a full copy of the body, and drops it without zeroizing. For NZBGet's `config`, that's a 4 MiB copy holding `ControlPassword` and the `ServerN.Password` values, which undercuts the "zeroized once parsed" claim in `nzbget.rs:29-30` and in the decisions file. Fix: find the first match before allocating, or zeroize `out` on the no-change path. The I1 fix makes this moot if scrub no longer runs on the full config body.
- **N2. The leak test only looks for the raw strings** (`usenet_clients.rs:681-687`). It searches the logs for `USER` and `PASSWORD`, not for `base64("USER:PASSWORD")`, the form the Basic header would leak in. Add that string to the list.
- **N3. NZBGet's refusal of an add-only user maps to `Rejected("Access denied")`** (`nzbget.rs:285-288`, used by `categories`). UN-3 can't tell it apart structurally, the way SABnzbd's `Access::AddOnly` can. It's documented, but `Auth(..)` for JSON-RPC code 401 would let UN-3 show the same "this key can only add" hint for both clients. This is optional.
- **N4. The access-log claim in the decisions file is broader than the source supports** ("Credentials", SABnzbd key). The key stays out of URLs and CherryPy's access log. But with SABnzbd's `api_logging` on, `secured_expose` debug-logs every request's `kwargs`, POST body included (`interface.py:143-150`). Worth one clause so nobody over-relies on it.
- **N5. `fuzz/Cargo.lock` is stale** on `main` (the `lodestar-store` → `sha2` entry), so `cargo check --locked` in `fuzz/` fails. This isn't the PR's doing; it's for the runner to note.
