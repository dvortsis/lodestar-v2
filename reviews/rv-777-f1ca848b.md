## Blocking

1. **The runner-approved "file version" binding does nothing, and the decisions file says it is in place.**
   - Where: `docs/soak/tools/cr0-common.ps1:211`, `docs/soak/tools/cr0-soak.ps1:146`, `docs/decisions/2026-11-12-M8-WIN-1.md:4`.
   - Problem: `lodestar.exe` has no VERSIONINFO resource. There is no winres, embed-resource or .rc in `crates/lodestar/build.rs`, `Cargo.toml` or `packaging/`. So `(Get-Item).VersionInfo.FileVersion` is always `$null`, and `run.service_version` is always null. It is also recorded only at attach, not at every sample, and the analyzer never compares it with anything. The approval was "SHA-256 and file version, checked at every sample and rebound after the upgrade". Only the hash part exists.
   - Fix: take the version from the binary itself: `Get-SoakExecutableVersion` on the ImagePath exe, at attach. The per-sample hash already proves it doesn't change. Have the analyzer require `run.service_version == upgrade.to_version`.
   - Alternatively: correct the decisions file to say no file version exists, and get the runner's OK.
   - Either way, the decisions file should say that clap's `--version` prints Cargo.toml's base version. `release.yml` requires the tag's base to equal Cargo.toml's version, so an RC prints `1.0.0`, not `1.0.0-rc.N`, and two RCs can't be told apart by version. The hash is the only real binding.

2. **New evidence producers have no tests** (standards §5: a missing test for new behaviour).
   - Where: `docs/soak/tools/cr0-common.ps1:221-258`.
   - Untested: `Save-SoakUpgrade`, `Save-SoakUninstall`, `Get-SoakTorrentCount` and `Get-SoakInstalledVersion`. These compute the booleans and counts the analyzer trusts: `service_restarted` (tick comparison), `image_matches_installed`, `data_present` (empty or missing data folder), `service_present` and `program_files_present`, plus the `lodestar_torrents` parse and the `lodestar X.Y.Z` strip.
   - Why they can't be tested now: they call Get-Service, Get-Process, Get-FileHash and Invoke-WebRequest directly, with no injection seam, unlike `Get-SoakServiceIdentity` and `Get-SoakServiceImage`.
   - Fix: add scriptblock seams, or shadow the cmdlets with functions in `test_cr0_collector.ps1`. Cover the pass case and each failure: service stopped (throws), empty data folder (false), metric missing (throws), and version output with a prefix.

## Important

1. **`service_restart` passes on missing or truncated samples.**
   - Where: `docs/soak/tools/analyze_cr0.py:869-882`.
   - Probe: `service_mode: true`, an empty `samples.jsonl`, and a result of `{reason: baseline_window_complete, samples: 1440, service_detached: true}`. That gives `service_restart: pass ("one service process across 0 samples, window complete")`, even with `no_samples`, `result_sample_count_mismatch` and `finalization_incomplete` all raised. A truncated file also passes.
   - Why this isn't blocking: the memory gate is "not judged" on such evidence, so the run as a whole can't pass.
   - Fix: still, the line must not say pass. Require non-empty rows, `result["samples"] == len(rows)` and `finalization_complete is True`.

2. **Nothing has ever parsed `cr0-soak.ps1`.**
   - Problem: the author had no pwsh, and the CI job runs only `test_cr0_collector.ps1`, which dot-sources `cr0-common.ps1`. A syntax or runtime slip in the service-mode branches would first show up on the owner's PC at soak time.
   - Fix (cheap, in the already-approved shared test file): parse it with `[System.Management.Automation.Language.Parser]::ParseFile` and assert there are no errors.

3. **The runbook's verdict line doesn't match the report.**
   - Where: `docs/soak/v1-windows.md:93`, `docs/soak/tools/analyze_cr0.py:1405`.
   - Problem: the runbook says the Windows section "shows `pass` for all three", but the report prints four lines (service restart, build binding, upgrade, uninstall). The section heading also omits build binding.
   - Fix: say "all four" and name them, and fix the heading.

4. **v0.5.1 is hard-coded as "the last public release".**
   - Where: `docs/soak/v1-windows.md:9,18,32`.
   - Problem: v0.5.2 and v0.6 tags are planned before 1.0 (`docs/build-plan.md` P4 and P5). OQ3 says "the last public release", and by the RC this would be the wrong value.
   - Fix: parameterize it, for example "the newest release before the RC on the Releases page (v0.5.1 as of 2026-11-12Z)", with a `<last-release>` file name.

5. **A runbook step can't be done.**

   - Fix: move the check to after the upgrade (Settings → Updates → Off, which is the Windows default) and say why: an update installed during the soak restarts the service.

6. **A destructive pre-step has no undo.**

   - Problem: the pre-step runs `REMOVE_DATA=1` on the owner's existing Lodestar. It warns, but gives no backup step.
   - Fix: link the backup section (`03-keep-lodestar-safe.md#37-back-up-and-restore`) first, or recommend a PC or user with no existing install. This is the user-docs safe-choice rule.

7. **The PR description doesn't name the refinements of the owner decision** (CLAUDE.md, §2.19). The decisions file records them. The description should list each one so the runner can flag it to the owner:

## Optional

1. **A sentinel key in the parsed data can hide two check lines.**
   - Where: `docs/soak/tools/analyze_cr0.py:897-924`.
   - Problem: `life = {"invalid": True}` puts the marker in the same dict as the file's data. A `lifecycle.json` that itself contains `"invalid": true` drops the upgrade and uninstall lines entirely (probe confirmed).
   - Fix: use a local flag instead.

2. **`build_binding` is `absent` in service mode when no hash was recorded.** (`analyze_cr0.py:885`) Absent should mean old evidence only. In service mode, report it as fail.

3. **The constants test checks five of the six `MEMORY_FIT` values.** (`test_analyze_cr0.py:987`) It omits `max_gap_seconds` (180). Assert the whole dict.

4. **A service exit can be reported as a collector error.**
   - Where: `cr0-soak.ps1:161`.
   - Problem: on a process the collector didn't start, `$p.ExitCode` can throw after `HasExited`. The result reason then becomes `collector_error` instead of `process_exited`.
   - It still fails closed. In service mode, set a fixed `service_process_exited` reason instead.

5. **Two traps in the upgrade step.**
   - `Save-SoakUpgrade` defaults `-Bind` to `127.0.0.1:8484`, but the MSI serves on 8090 (`cr0-common.ps1:233`).
   - `Get-SoakTorrentCount` can throw if it runs the moment the service shows `Running`. The runbook should say to wait until the page loads, then retry.

6. **Attach mode doesn't check what it attached to.**
   - It doesn't verify that the listener on `-Bind` belongs to the service PID (`Get-NetTCPConnection -State Listen -LocalPort`).
   - It doesn't verify that no other `lodestar*` process is running.
   - A portable copy on 8090 would feed another process's metrics while memory is read from the service.

7. **Intensity isn't checked in service mode.** `settings.intensity = 'balanced'` is recorded, and the analyzer's limits use it.

8. **The owner is asked to send their time zone.** `run.json` records `timezone` (the local zone ID; this predates the PR), and the runbook asks the owner to send `run.json`. Consider dropping the field in service mode (§2.35).

9. **Two runbook gaps.** Tell the owner to pause Windows Update for the ~32 h, since a forced reboot wastes the run. Tell them to `cd` to the MSI's folder before the relative `msiexec` commands.

10. **The test fixture's version isn't what the binary prints.** It uses `to_version: "1.0.0-rc.1"`, but `--version` on an RC prints `1.0.0` (see B1).
