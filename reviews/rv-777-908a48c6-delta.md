## Important

1. **The stated way to verify the hash doesn't exist as written.**
   - Where: `docs/decisions/2026-11-12-M8-WIN-1.md:6`, `docs/soak/v1-windows.md:100`, PR description refinement 3.
   - Problem: all three say the runner compares `service_image_sha256` "with the RC's published checksums". `release.yml` publishes SHA-256 for the MSI, the portable zip, the tarballs and the Linux binaries (`files=(... *.msi *.zip *.sha256 SHA256SUMS)`), but never for `lodestar.exe` itself.
   - Failure scenario: the runner reads the report, finds no published hash to compare against, and the hash-only binding (which the runner accepted as the only proof of which build ran) goes unverified.
   - Fix (docs only): name the real route. Take `lodestar.exe` from the RC's portable zip (after checking the zip against the signed `SHA256SUMS`) and hash it. Today the MSI and the zip are built from the same signed `target/.../lodestar.exe` in one job (`build-msi.ps1:20`, `build-portable.ps1:15`).
   - Do the same for `from_image_sha256` against `<last-release>`'s zip. Nothing else shows that the upgrade really started from the last public release: `from_version` is never compared, and `from_image_sha256` is typed in by the owner.

2. **The runbook pauses Windows security updates for 5 weeks and never says to resume them.**
   - Where: `docs/soak/v1-windows.md:17`.
   - Problem: the run takes about 32 h. Five weeks is the longest pause Windows offers, so the PC stays unpatched for a month after the soak, and no step says to undo it. That goes against the safe-choice rule in `user-docs`, which the brief requires for this runbook's wording.
   - Fix: "Pause for 1 week" (the shortest option, enough for the run), plus a line in Phase 5: "Resume updates (Settings → Windows Update → Resume updates)."

3. **The producer tests stub out the logic B2 asked to test.**
   - Where: `docs/soak/tools/test_cr0_collector.ps1:147-148,164,170`.
   - Problem: the `Data`, `Hash` and `Exists` probes replace the very expressions that compute `data_present`, `image_matches_installed`, `program_files_present` and uninstall `data_present`. The empty-folder → false and missing-folder → false cases that B2 named are never exercised.
   - Those defaults are plain filesystem calls that work on the CI runner. They don't need stubbing.
   - I read the defaults statically and they're correct (`-ErrorAction SilentlyContinue`, `Select-Object -First 1`), so this isn't blocking.
   - Fix: in the upgrade and uninstall tests, override only the service, process and HTTP probes, and point the rest at temp files:
     - `-DataDir` at a new empty temp dir (expect false), then at one with a file (expect true);
     - `-Exe` and `ProcessImage` at two temp files with the same and different contents;
     - `-ProgramDir` at a missing path.

## Optional

1. **The collector never checks that the running process is the file it hashes.**
   - Where: `cr0-soak.ps1:143-147`.
   - Problem: at attach and at each sample, the binding hashes the ImagePath file. It never checks that the service process was loaded from that file.
   - Failure scenario: an MSI upgrade replaces the file but leaves the old process running (files in use, reboot pending). The soak then binds the RC hash while it measures the old binary. The upgrade record's `image_matches_installed` and `service_restarted` catch this case today, so it's covered, but only indirectly.
   - Fix: at attach, throw unless `Get-FileHash (Get-Process -Id $svcId.pid).Path` equals `$img.sha256`. While there, also throw if `$originalExeHash` (`-Exe`) differs from `$img.sha256`. Otherwise `run.sha256` and `run.version` can describe a different file than the one bound, if the owner passes a different `-Exe`.

2. **Malformed values crash the analyzer instead of failing a check.**
   - Where: `analyze_cr0.py:858,889`.
   - Problem: an unhashable `service_start_ticks` or `service_image_sha256` (for example a list) raises `TypeError: unhashable type`. I probed both. It fails closed (no report), but with a traceback, not the analyzer's usual `ValueError` message.
   - Fix: require `number()` / `str` before building the sets, and fail the check otherwise.

3. **The decisions file's "Shared edit" bullet is out of date.**
   - Where: `docs/decisions/2026-11-12-M8-WIN-1.md:11`.
   - Problem: it still lists only the first round's tests. The parse check and the producer tests are named only in the "Not run here" bullet.
   - Fix: add them to the "Shared edit" bullet.

4. **The upgrade step passes trivially if the owner skips Phase 1's capture.**
   - Where: `Save-SoakUpgrade` (`cr0-common.ps1:107`).
   - Problem: if `$OldPid` was never set, `-PreviousStartTicks` binds `$null` → 0, and `service_restarted` is then trivially true.
   - Fix: make `PreviousStartTicks`, `FromImageSha256` and `TorrentsBefore` `[Parameter(Mandatory)]` with `[ValidateRange(1, [long]::MaxValue)]` / `[ValidateNotNullOrEmpty()]`.
