# Review: PR #699 (WK-11, the worker spool), delta 85d8d267..13397e42

This covers both the code delta review and the security delta review.

Every claimed fix is in the code and does what it says:
- B1 and L1–L3;
- I1, I2 and I4;
- N1, N2, N5, N6 and N7.

Crash safety and replay idempotency haven't regressed. No lock is held across an await, and there are no fixed sleeps.

There is **one blocking finding**, and it's about tests, not behaviour: two of the delta's new behaviours have no test. Mutations that undo them pass every test. One of them is the "resume" half of B1. There's also one robustness regression from the new hard-link placement (I1 below). It's cheap to fix in the same round.

## Blocking

**B1. Two new behaviours have no test (standards §5: "a missing test for new behaviour").**

1. **The DHT resuming after a replay frees room (the second half of the B1 fix).**
   - Where: `crates/lodestar/src/worker/runtime.rs:2071`, `:2115` and `:2162` call `refresh_spool_pause()`.
   - Mutation L4 changes those three calls back to `refresh_pause()`. That drops the `want_dht` re-check. **It survives** all 94 `worker::` tests.
   - Why the test misses it: `a_full_spool_with_a_session_up_claims_nothing_and_pauses_the_dht` (`worker/spool.rs:713`) changes `sp.full` by hand. It then reads the DHT state through `test_dht_runs` (`runtime.rs:2231`), which calls `refresh_spool_pause()` itself. So the test never checks that the production removal path re-checks the DHT.
   - Failure path if this regresses:
     1. A session is up and the spool is full, so `want_dht` returns Pause.
     2. The replay removes segments and `after_removal` clears `full`.
     3. Nothing calls `want_dht` again while the session stays up. That function only runs on session, assignment and start events.
     4. The DHT stays at routing only for the rest of the session, while claims and fetching resume.
   - The decisions file says "All three resume once the replay brings the spool under half its cap". Nothing tests that.
   - Fix: drive a real removal instead of changing `sp.full` by hand. For example:
     1. Spool two batches with small caps until `put` reports full.
     2. Connect, and accept the replayed batches.
     3. `until` the DHT's `Desired` is `Run`, read from the watch without calling `refresh_spool_pause`.
   - Add a read-only `test_dht_state()` that doesn't refresh.

2. **A spooled record's age running from when its batch was made (the I2 fix).**
   - Where: `worker/spool.rs:248` (`at` passed into `Record`) and `runtime.rs:1969` (`at: unix_now()` in `batch_up`).
   - Mutation L6 makes `put` ignore its `at` and stamp `unix_now()`, which is the old behaviour. **It survives.**
   - Effect if this regresses: the I2 gap comes back silently, and the decision's wire-key-day proof ("drops a record more than 24 h after its batch was made") is false again.
   - Fix: a unit test on `WorkerSpool::put` with `at = now - max_age - 1`. The record must read back as `dropped_old`. Or a runtime test that holds a batch in flight before disconnecting and checks the opened record's `at`.

- **Also untested, optional:** the claim loop's own gate, `runtime.rs:1727`. Mutation L3 survives, because the test goes through `sift` only. A test through `claim()` would cover it. The `sift` gate (mutation L2) is killed.

## Important (non-blocking; cheap, worth doing in this round)

**I1. New-segment placement by hard link can wedge the spool for the rest of the run, and a leftover temp file that shares the segment's inode gets zeroed.**
- Where: `crates/pipeline/src/spool.rs:799` and `secure_remove` (`:693`).
- **(a) A wedged spool.**
  - `Place::New` does `fs::hard_link(&tmp, &target).and_then(|()| fs::remove_file(&tmp))`. If the link succeeds but removing the temp file fails, `write_atomic` returns Err and `start_segment` leaves `next_seq` where it was. Removal can fail on Windows when another program (antivirus, an indexer) holds the new file without delete sharing. That's the same situation N6 named.
  - `<N>.lsp` now exists, so every later `start_segment(N)` fails on `hard_link` with AlreadyExists. Nothing new can be spooled until the next restart, and every batch counts as an error and stays in memory.
  - Before this delta the retry renamed over the header-only segment and recovered.
- **(b) Zeroing through a second link.**
  - A temp file left hard-linked to `<N>.lsp` has a link count of 2. That happens after (a), or after a crash between the link and the unlink.
  - `secure_remove` sees a regular file whose device and inode match, then zeroes the shared inode, and with it the live segment.
  - Probe: a hard-linked `.tmp` next to a segment holding two records left the `.lsp` all zeros after `Spool::open`, with 0 records read back.
  - In the cases the code itself can produce, the segment holds only its header, so no record is lost. The probe shows the mechanism.
  - The same mechanism lets a folder writer zero any file it can hard-link in. With `fs.protected_hardlinks=0`, that includes the worker's own `secrets.key`. Probe: a hard-linked victim file was zeroed at open.
- **Fix:**
  - In `write_atomic`, treat a successful `hard_link` as placed. If removing the temp file then fails, ignore that and let open clean it up.
  - Or advance `next_seq` whenever the target name exists.
  - In `secure_remove`, unlink a file with `nlink() > 1` without overwriting it. `privdrop.rs:643` already follows the rule "a link count above 1 is left". This closes both (a)'s leftover and the hard-link attack.
- **No fallback is needed for filesystems without hard links.** `SecretStore::open_or_create` (`integrations/src/secret.rs:252`) already requires hard links in the same data folder. No `.tmp` is left behind on a link failure: it's removed (`:802`) and only ever held the header.

## Nits

- **N1. After a clock set back, the open segment's frames can be dropped early.**
  - Where: `spool.rs:921` (`roll`), and `:1143` (`is_expired`'s future check).
  - After the clock goes back by more than 60 s, `now - created` is negative, so the active segment doesn't roll by time. It keeps taking records stamped by the new clock.
  - Once it closes, `is_expired` sees `created > now + 60` and drops the whole segment as old, including records stamped after the change.
  - They're counted, unacknowledged, and their leases expire anyway. The cleaner fix: roll the active segment when `now < created - MAX_FUTURE_SECS`.
- **N2. The clock-forward limit is now in the decisions file, and that's honest.**
  - A Pi with no clock battery that was off for more than 24 h drops everything it spooled before NTP corrects the clock.
  - It's worth one line in the owner flag, since it loses genuinely fresh records.
- **N3. `worker_spool_errors_total` doesn't count every sync failure.**
  - A failed sync inside `append` (`:973`) bumps `sync_failures` but not `WorkerSpool::errors`. A failed sync at the end of a round (`sp.sync()`) bumps both.
  - Either is defensible. The metrics row says errors counts "writes … that failed", so say which.
- **N4. The N2 change has no test.** Mutation P12 restores `self.sync()?` in `append` and survives. That's hard to inject without a fault-injecting file, so it's acceptable. Just noting it.
- **N5. Comment wording at `runtime.rs:1929`.** "Just after its records were sealed" is slightly generous. Records wait in the outbound queue until the session task takes them, which is normally at once but can be longer while `send_due` is blocked on a slow session. The decision's "edges" paragraph covers this.
- **Carried over and not in scope here:** the earlier report's I3, N3, N4 and N8–N11 are unchanged.

## Security (delta)

| Item | Status |
|---|---|
| **L1 (Unix)** | **Fixed.** `symlink_metadata` comes first, and a link or non-regular file is unlinked without being opened. The device and inode comparison runs right after the open and **before any write** (`:704-710`), so a swap between the lstat and the open can't make it overwrite another file: the mismatch returns Err (counted as a leftover at open). Writes go to the file descriptor that was checked, and the final `remove_file` doesn't follow links. Temp files: a stale one goes through `secure_remove`, then `create_new` at 0600, which never opens through a link. |
| L1 residual: FIFO | A symlink to a FIFO swapped in during the race makes `open(O_WRONLY)` block before the check. That's a stall at open, not a write. `O_NONBLOCK` (and `O_NOFOLLOW`) through `custom_flags` would close it. The pipeline has no libc or rustix dependency, so this would need the constant hard-coded per target. Low. |
| L1 residual: hard link | Hard-linked victims, see I1(b). Low; fixed by the nlink rule. |
| L1 residual: append open | `start_segment` reopens `<seq>.lsp` with `append(true)` (`:992`), which follows a link. A link swapped in between placement and reopen would get sealed frames appended to its target. That's a narrow race for a folder writer and only appends ciphertext. Reusing the temp file's handle, or a device and inode check against it, closes it. Low. |
| **Windows reparse points** | Not swapped: `symlink_metadata` reports name-surrogate reparse points (symlinks, junctions) as not files, so they're unlinked, or fail as leftovers for directory junctions, and never opened. Swapped mid-race: `same_file` is `b.is_file()` only (`:738`), so a file symlink swapped in after the lstat is followed and zeroed. The decisions file's "a planted link's target is never zeroed" is true on Unix, and on Windows only without a race. Mitigated: creating a symlink needs a privilege or developer mode, and the data folder's ACL check (`windows/acl.rs`) refuses reparse points and foreign owners at every start. A stable fix: `OpenOptionsExt::custom_flags(FILE_FLAG_OPEN_REPARSE_POINT)` and refuse when `opened.file_attributes() & FILE_ATTRIBUTE_REPARSE_POINT != 0`. Low; reword or fix. |
| **L2** | **Fixed.** The folder is created at 0700 and narrowed with `set_permissions` if it exists. Files are 0600 through `create_private`. The worker's `for_layout` uses the same helper. |
| L2 notes | `set_permissions` follows a symlinked `spool` folder, which only narrows the target's mode. A pre-existing spool folder owned by another user now makes `for_layout` fail, so the worker refuses to start with a message. Docker's privdrop chowns the tree first, so this matters only for hand-run workers, and refusing is the safe choice. |
| **L3** | **Fixed.** Only `.tmp` and `.lsp` names count toward `next_seq`. `checked_add` refuses at `u64::MAX`, and a new segment never replaces a file of its name. Each of the two guards backs up the other, see the mutations. |
| **N1 scan** | **Bounded and linear.** `good_frame_within` makes one pass over the positions, with O(1) work per position plus sums capped at 2× the bytes. It's called at most once per decode. Probes: 9 MiB crafted tails took 0.34 ms and 0.37 ms. |
| Fuzz | `worker_spool`, built with nightly and sancov, debug assertions and overflow checks on. 30.5M runs in 91 s at `-malloc_limit_mb=64`: no crash, leak or over-allocation. |
| Supply chain | No `Cargo.toml` or `Cargo.lock` change in the delta. `cargo tree -e features -p lodestar` shows no tokio `test-util` and no new `testing` feature; `lodestar-update` and `lodestar-tracker-scrape` are pre-existing. |
