## Security / concurrency assessment (no blocking issues)
- **Holder check.** `held_tokens` (leases.rs:1052-1063) keeps only `holder == sender && token == listed`. `LeaseTable::reconcile` (leases.rs:358-380) iterates only `l.holder == worker`.
  - A worker can't return, renew or release another worker's lease, listed or not.
  - Listed leases the coordinator doesn't hold are only counted, never created.
  - Tokens carry the epoch, so old-epoch tokens never match.
- **Memory.**
  - Each part is capped at 8,192 when decoding starts (proto.rs:376-379), and again in the loop and in `validate`.
  - There's one `Gathering` per worker. Its `listed` set holds only tokens that worker holds, deduplicated, so it's bounded by the worker's share of the lease table.
  - A new session, the session's end and a heartbeat timeout all drop the gathering.
  - `delivered` marks are made only for an existing lease under its holder and token, and end with the lease on every end path: `release`, `expire`, `evict`, `reconcile` (via `ended`/`end_all`). The PINNED mark is inserted only for a lease `restore_if_free` just created.
- **Refusals.**
  - A non-current (replaced or revoked) session's parts touch nothing, not even the current round.
  - A paused (quarantined) worker and the built-in worker are refused.
  - A second round within one heartbeat interval is refused before the table scan.
- **Races.**
  - The reconcile runs under the fleet lock. The claim path (server.rs:1737-1858) and both regrant paths (reserve marks at server.rs:2055-2060; `send_regrants` at 2151) mark under the same lock.
  - The session handles one inbound message at a time, so a claim answered on the listing session is always marked before the list is processed.
  - A reservation marked for an older session that is returned is skipped by `regrant`'s re-validation (`current` check).
  - `Reconciled` goes on the link before the queued `Grants`, so the reply can't deadlock behind them.
  - Out entries cover a result in flight. The finished entries cover the Fetched gap.
  - The `committed_at` change covers replayed batches.
- **Compatibility.** Only `major` is checked on both sides. The new variants come last, which the tag test checks. The worker sends a list only when `Welcome.minor >= 1`, which the older-coordinator test checks.

## Important
1. **crates/cluster/src/proto.rs:376-379 / test at proto.rs:766-771: the "refused before allocating" guard isn't covered by any unit test.**
   - **What I saw.** I deleted the `hint > MAX_HOLDING_BATCH` check and `a_holding_part_over_its_caps_is_refused` still passed.
     - The `lie` prefix `[ff ff ff 7f]` is about 2^28 entries. `Vec::with_capacity` of about 7.5 GB succeeds lazily under overcommit, and decoding then fails at end of input, not at the cap.
     - The 8,193-element case is caught by the in-loop check instead.
   - **Why it matters.** The guard is correct and needed: this custom visitor doesn't get serde's `size_hint::cautious` cap that postcard's own `Vec` decoding uses. Without it, one authenticated worker could make the coordinator try a huge allocation (a capacity-overflow panic or an OOM abort).
   - **Cheap fix.** Use a length prefix near `u64::MAX` (for example nine `0xff` bytes and then `0x01`). That panics with "capacity overflow" if the guard goes, so the test fails.
   - **Fuzzing.** The decisions file (line 17) says the `-malloc_limit_mb=8` fuzz run checks this cap, but CI's fuzz job runs with libFuzzer's default limit. Either run it once with `-malloc_limit_mb=8` and say so, or soften the sentence.
2. **crates/pipeline/src/worker.rs:288-302 (`committed_at` now records a finished out entry for a replayed result): runner, please confirm this was approved.**
   - The approval I was given covers `tokens()` and its test. This changes `committed()` behaviour in `crates/pipeline/**`. The PR description lists it under the approved edits, but the decisions file's "Approved shared edits" section names only `tokens()`.
   - The code is correct and tested (`a_replayed_results_commit_keeps_it_listed`). Without it, a replayed batch's lease would fall out of the list before its `Fetched` lands.
   - A side effect: `insert` of the same key and token now returns `Out` (held again) instead of `New`. That matches X-wk-own-lease-lost.
   - If it wasn't approved, it's a scope finding. It's wanted for correctness, so the fix would be to approve it and add it to the decisions file's approved list.
