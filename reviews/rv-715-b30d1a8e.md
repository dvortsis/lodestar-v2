## Nits / polish
1. **`crates/api/src/torznab.rs:117-120`**: the notice gate's `409` is mapped to `102` with the description "Insufficient privileges: use an API key with the Torznab scope". Only a signed-in browser whose notice is pending can get a 409 (keys skip the gate, `auth/guard.rs`). For that browser the hint is wrong: the fix is to accept the notice, not to use a key. Scenario: a session cookie, notice pending, `GET /api/v1/torznab/api?t=caps` returns `409 <error code="102" description="… use an API key with the Torznab scope"/>`. Either give 409 its own fixed description, or keep 102 with the plain "Insufficient privileges".
2. **`crates/api/src/torznab.rs:389-391`**: the RSS `<channel>` has `title` and `description` but no `<link>`, which RSS 2.0 lists as required. The *arr parsers don't read it, but a strict RSS reader (or a browser checking the feed) may. A constant `<link>` with no key in it (for example the caps-relative path, or an empty string) would make the feed valid RSS 2.0. Note that the golden caps document would not change; only the feed would.
3. **Plan vs. build: the writer.** Plan `docs/plan/2026-11-05-v07-m7.md:126` says "the Torznab writer use[s] the existing `quick-xml`". The PR writes XML with its own 164-line writer and uses quick-xml only as a dev-dependency, to parse output back. The decisions file says this ("the server writes them with its own escaping writer"; quick-xml "a dev-dependency only: runner, 2026-11-11"), but it doesn't name it as a departure from that plan line. One sentence saying so (and why: constant names, a single escaping path, no CDATA) would make it findable for ENR-anidb, which the same plan line also points at quick-xml.
4. **HTTP status on errors** (decisions file "Errors keep real HTTP statuses, not 200"): this is a reasonable choice, and 429 with `Retry-After` is the case the apps handle best. Many Newznab/Torznab servers answer errors with 200, though. Some clients surface a non-2xx as a generic "unable to connect" instead of parsing `code="100"` as "invalid API key". I couldn't check this against the real apps here, so it isn't a finding. D-outputs-guide should check what Sonarr, Radarr and Prowlarr show for a wrong key and word the troubleshooting step to match.
5. **`crates/api/src/torznab/xml.rs:130`**: the overrides and isolates are removed. The bidi *marks* (U+200E, U+200F, U+061C) are kept. That is harmless, because marks can't reorder text the way overrides can. This is noted only so the doc comment's "can't display reversed" claim is understood as overrides and isolates.
6. **`crates/lodestar/src/settings/content.rs:34`**: the user-visible help now reads "Adult results in Torznab feeds (`/torznab/api`)". The real path is `/api/v1/torznab/api`. Either give the full path or drop it, since help text is read by people setting this up.

## Security pass
- **Auth:**
  - Torznab uses the existing guard, `auth::key_or_session(…, scope::TORZNAB)`. Keys are stored as hashes and compared in constant time. Every bad secret gets one `401 bad_api_key` answer.
  - There is a per-IP failed-check bucket and a per-key request bucket (`429` with `Retry-After`). Keys are read-only (GET/HEAD) and `Set-Cookie` is dropped.
  - Two different secrets in one request are refused.
  - `as_torznab_error` sits outside the guard and turns its JSON refusals into fixed-description XML. The JSON message isn't carried over, the status is kept and `Retry-After` is copied.
  - Missing, wrong, unknown, revoked, feed-token and malformed keys all give `401/100`. A valid key without the scope gives `403/102`. This matches the guard's existing contract: it says "valid but wrong scope", and only to the key's holder.
  - Mutation check: changing the route's scope to `scope::SEARCH` fails 5 or more of the integration tests.
- **The key is never echoed or logged:**
  - Documents contain only magnet links, with no URL back to the server. Error descriptions are `&'static str` and never contain a value. Tests assert that the key is absent from every refusal body and that no feed contains `http`.
  - `api.request` logs only the matched route template, never the URI or query (`crates/api/src/request_log.rs`). `lodestar-log`'s URL redaction also covers `apikey=`.
  - The PR adds no new log events. Search failures go through `search::search_error` and `error::internal`, which log the error and not the request.
- **Input:**
  - The raw query string is capped at 4 KiB and 64 parameters, then `q` at 256 bytes and 32 words, with control characters removed. `cat` takes at most 32 ids of 6 digits, `season` and `ep` up to 4 digits or a validated `MM/DD` with a 1900–2999 year, and `limit` 1–100.
  - `offset` takes up to 9 digits, and past `MAX_WINDOW` it returns an empty page.
  - Repeated known parameters are refused. ID parameters with a value are refused with `203`, and unknown parameters are ignored.
  - Number parsing is digits-only (no sign, spaces, hex or overflow). Proptests cover arbitrary and structured strings and found no panics.
  - The search AST is **built, never parsed**. `q` becomes `Node::Word` on `TextField::Any`, so `verified:no`, `flag:hidden`, `-flag:private_source`, `type:adult` and `a*` are plain words. A word with `*` is tokenized, not turned into a prefix: prefixes exist only in the parser's `word()`.
  - `base_query` adds `verified:yes` (the AST never mentions `verified`, so `without_unverified` always applies), `-flag:hidden` (the AST names only `private` and `private_source`) and `-type:adult` unless `torznab_adult` is on.
- **Exclusions:**
  - The index query carries `-flag:private -flag:private_source`. Every stored row is checked again: `discover::withheld(row, e, false, adult)` covers HIDDEN and the stored Adult class, and the full `flags::PRIVACY` mask covers PRIVATE, PRIVATE_SOURCE and REMOTE_UNVERIFIED.
  - Mutation check: dropping the `PRIVACY` row check fails `private_hidden_and_unverified_are_never_served` (the REMOTE_UNVERIFIED row has no index term) and `stored_rows_decide_when_the_index_lags`.
  - Totals count a REMOTE_UNVERIFIED row, as documented, but the row is never served. The count is off by one and no data leaks.
- **Adult:**
  - `TorznabAdult` defaults to off, and without the extension Adult is never served (fail-closed, tested). It is independent of "Show adult content" (tested with `show_adult: true`) and followed live.
  - `cat=6000` with the setting off is ANDed with `-type:adult` and finds nothing, and the stored class is re-checked.
  - Mutation check: forcing `adult` to true when the extension is missing fails `adult_follows_torznab_adult_not_search`.
  - Unclassified items list under Other, the same as UI search, export and discover. That isn't a new gap.
- **Output escaping:**
  - Every value goes through `escape`: `& < > " '` become entities, tab, CR and LF become a space, and every other `Cc` (C0 and C1) is removed. U+FFFE, U+FFFF, U+FEFF and the bidi overrides and isolates are removed too. No CDATA, comments or PIs are written, and names are `&'static str` constants (`debug_assert!(is_name)`).
  - Rust `str` can't hold surrogates, so with those removals every character that remains is XML 1.0 `Char`. `dn` is percent-encoded byte-wise and cut at 256 bytes on a char boundary.
  - The integration test parses every response with a strict hand-written XML 1.0 reader and with quick-xml. The hostile names include `]]>`, markup, C0 and C1 controls, invalid UTF-8, bidi characters, entities and `<![CDATA[`.
  - Mutation check: removing the `<` escape fails `hostile_names_are_well_formed_xml`.
  - Responses carry `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`.
- **Headers:** no CORS, CSP or `connect-src` change. Torznab is a GET on the same router, under the same global security headers.
- **Resource bounds:**
  - Each request makes one lease and at most 5 page reads (`MAX_REFILLS = 4`) of at most 100 hits each, with the reader lock held per page read and released between reads.
  - The work runs on the blocking pool with `cancel_on_drop`, so a client that disconnects cancels the search.
  - The search has no result cache or cursor state, and the document is built in memory with at most 100 items.
  - Every request is throttled by the per-key 300-burst / 5-per-second bucket.
  - There's no per-request concurrency cap beyond that, which is the same as `/search`.
- **The tripwire:** `crates/sources-plugins/tests/safety.rs` sets `COVERED = &["torznab"]` and names the two leak tests, which exist and fail when the leak is introduced (above). Stremio stays guarded. The test passes.

## Spec / correctness
- **Caps:**
  - search, tv-search (`q,season,ep`), movie, music, audio and book, with `limits 100/100` and the documented category tree. It names no version and is pinned byte for byte.
  - ID parameters aren't advertised (they come with ENR-11), which matches plan §269.
- **Modes:**
  - Each mode searches its default categories when there's no `cat`, and an explicit `cat` replaces them.
  - The daily `season=YYYY&ep=MM/DD` form becomes a phrase. Numeric season and episode become ranges.
  - With no words, results are newest first. With words, they're by relevance.
  - Unknown categories find nothing, with `total=0`. A mix of listed and unlisted categories finds the listed ones.
- **Paging:**
  - `limit` is capped at 100.
  - `offset` is echoed as requested, and past the window there's an empty page with the true total.
  - The refill keeps pages full past rows the stored check removes, so a short page means the results ran out. Overlap with the next page is possible, and the apps de-duplicate by `guid`.
- **Items:** `guid` is the info hash, and `pubDate` is RFC 822 UTC (date maths tested, including negative times and leap days). Items carry `size`, the magnet as `link`, `enclosure` and `magneturl` (v1, hybrid and pure v2 handled), category and subcategory, and `files`. Seeders, peers and grabs appear only once scraped, with `downloadvolumefactor=0` and `uploadvolumefactor=1`.
- **Errors:** `200`, `201`, `202` and `203` for parameters (status 400); `100`, `102`, `500`, `202`, `910` and `900` for the guard and runtime. Descriptions are fixed and never echo a value.
