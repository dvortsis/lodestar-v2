## Round-4 checklist
- **B1 (a stale `/system` read could undo Keep): fixed.**
  - **The logic** (`restart.svelte.ts`):
    - `setAddressChange` and `begin` bump `generation`;
    - `refresh` captures `mine` at start and writes `system` only if `mine === generation`;
    - it joins `inflight` only when `inflightGeneration === generation`;
    - `finally` clears `inflight` only if it is still this read.
  - **The concurrency questions from the brief:**
    - *Can a newer answer be dropped forever?* No. Only a read that started before a bump is dropped. Every later `refresh` starts a read in the current generation, and that read writes. The watch asks on focus, on route change and every 15 s (Settings) or 60 s (elsewhere), so the store converges on the next ask. A dropped read is one whose state the bump already replaced: Keep's or Go back's own answer, or the Restarting state.
    - *A promise that never resolves?* No. JS is single-threaded, so nothing runs "during" the bump. `refresh` returns either `Promise.resolve(true)` (while restarting), a joined read of the current generation, or a new `api.get` chain that always settles (`then` / `catch` / `finally`). A dropped read still resolves `true`. Every caller copes with that: the 0:00 check returns early on `answered`, and `answer()`'s catch path doesn't bump.
    - *Duplicate parallel GETs?* At most one extra GET per bump. A read from before the bump runs to completion while a new one starts. Bumps come only from Keep, Go back (POSTs guarded by `busy`) and `begin`, so the count is bounded by user actions. The old read's `finally` leaves the newer `inflight` alone, and nothing leaks.
    - *Other callers:* the banner's `onMount` refresh, the watch's `ask` and the prompt's catch path behave as before within a generation (they still join).
  - **Mutations (each reverted):**

## Nits
1. **The `begin` bump is unpinned, and the third store test's title claims it.**
   - **Where:** `restart.svelte.test.ts:60-66`, "a restart that began is newer than any read in flight, and reads pause while it lasts". The test has no read in flight. It only checks that `refresh` returns early while `waiting` is set, which was already true before this round. Removing `generation++` from `begin` passes every test.
   - **Effect:** none in production today. `!waiting` already blocks the write while restarting, and no non-test code calls `begin(null)`. The bump also helps the tests: each `beforeEach`'s `begin(null)` stops a read leaked from an earlier test being joined.
   - **Fix (optional):** pin the bump: a read in flight, then `begin(w)`, then `begin(null)`, then release the old state and expect `system` unchanged. Or rename the test to what it checks.
2. **Two yields in the new tests could be more direct.**
   - **Where:**
     - `RestartBanner.test.ts:197` (`await new Promise((done) => setTimeout(done, 0))`);
     - `restart.svelte.test.ts:57` (`await Promise.resolve()`).
   - **Why it's only a nit:** neither is a timing sleep. The released read's `then` and `finally` are microtasks, and the zero-delay macrotask runs after all of them on any runner. The `M2` mutation shows both assertions catch the stale write.
   - **Fix (optional):** keep the stale `refresh()` promise and `await` it (the first store test does this). That states the condition outright.
3. **Delegation note for the runner, not a defect.** The commit carries the harness's helper-model trailer, and the generation guard is client-side async-race code. CLAUDE.md keeps concurrency-heavy code off helpers. This guard is small, UI-local and reviewed and mutation-tested here, so I don't count it against the PR.
