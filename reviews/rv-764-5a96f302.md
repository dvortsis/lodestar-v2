VERDICT: CHANGES

One blocking defect: a quadratic path in the untrusted-input parser, which the brief and the PR's own decisions file ("Linear time") rule out. Everything else is sound. The fix is a few lines plus one test.

## Blocking

### B1. `aliases` language keys are tracked without bound, so a hostile entities answer parses in quadratic time
- **Where:** `crates/sources-feeds/src/wikidata.rs:696-718` (the `"aliases"` arm of `Parser::entity`).
- **What:** `langs: Vec<&str>` gets every alias language key while the text cap isn't reached, and `langs.contains(&lang)` scans all of it for each new key. An empty array (`"k1":[]`) adds a key but no alias, so `e.labels.len() + e.aliases.len()` never reaches `max_texts`. `langs` then grows to every key in the map, and each key costs O(n).
- **Failure scenario:** one entity with `"aliases": {"k0":[],"k1":[],…}`. The keys are unread data, so `language_ok` never runs. An 8 MiB answer holds about 600,000 of them, inside `max_values` (1M) and `max_bytes`. The parse also comes back `whole() == true`. Timings I measured with a temporary probe test (debug build, `parse_entities`, `ENTITY_LIMITS`):
  - n=10,000: 0.19 s
  - n=20,000: 0.43 s
  - n=40,000: 2.2 s
  - n=80,000: 9.6 s

  Each doubling costs about 4×, so roughly 9 minutes debug for about 600k keys, and still minutes in release. The plugin runs this inside `spawn_blocking`. ENR-10's 60 s `lookup_timeout` can't cancel that, so a blocking-pool thread keeps burning CPU after the lookup has failed. Every later hostile answer adds another such thread. This is exactly the "list of every key seen" pattern the decisions file says the self-review removed. `many_unknown_keys_are_read_in_linear_time` misses it because it only covers unknown keys of an entity, the root and a search result, not the keys of the `aliases` map.
- **Fix:** bound the keys tracked.
  - Count every alias-map key against a cap before pushing it. For example, at the top of the closure: `if langs.len() >= p.l.max_texts { e.truncated = true; return p.skip_in(&mut s); }`. Then `langs` holds at most `max_texts` entries, as the labels check already does with `e.labels`.
  - Add a case to `many_unknown_keys_are_read_in_linear_time` (or a sibling test): an entity whose `aliases` map holds about 300,000 empty-array keys, read whole within the test's normal time. Removing the cap should make that test take minutes.
  - While there, look again at each map's per-key work: `labels`, `aliases`, `claims`, the root `entities` and search `match`. Only `aliases` has this problem today.

## Important

### I1. An answer missing a requested id is treated as a miss and cached, not as an error
- **Where:** `crates/sources-plugins/src/wikidata.rs:226-231`.
- **What:** the entities it got are filtered by the requested ids. An id that is neither kept nor `missing` just disappears, and `choose` returns `NoMatch`, which ENR-10 caches as a miss. A known case is `wbgetentities` answering a redirected id under the target's key: that parses whole, then gets dropped here. The decisions file (§The parser, "To confirm against real answers") says a redirect is "a failed lookup, never a wrong match". In that case it's a cached miss instead. That also cuts against the plugin's own rule that a broken answer is never mistaken for a miss.
- **Fix:** if any requested id is absent from both `got.entities` and the missing set, return `BAD_ANSWER`. This needs the parser to report the missing ids, or `kept + missing == ids.len()` plus a per-id check. Add a fixture or unit case where the answer keys a different id.

### I2. The User-Agent carries the owner's GitHub handle; the owner should confirm
- **Where:** `crates/sources-plugins/src/wikidata.rs:64-70`, via `CARGO_PKG_REPOSITORY` = `https://github.com/dvortsis/lodestar-v2`.
- **What:** the brief says the User-Agent carries "no user name, email or host". The decisions file reads that as the end user's name and argues that the repository URL is the project's public identity. That's reasonable, and Wikimedia's policy needs a contact. Still, every install would send the owner's personal handle to Wikimedia. This refines an owner-facing privacy rule, so it's a §2.19 flag for the runner to put to the owner before the consent gate lifts.
- **Fix:** no code change needed now. Name it in the PR description as a refinement for the runner to flag. If the owner objects, a project page URL that doesn't carry the handle can replace it later.

### I3. Some files outside the brief aren't listed in the decisions file
- **Where:** `docs/decisions/2026-11-12-ENR-14.md` §"Files outside the brief's own".
- **What:** it lists `catalogue.rs`, `crates/lodestar/src/ops.rs`, `pipeline/src/lib.rs` and the `mod` lines. It leaves out `crates/sources-plugins/tests/credential_spec.rs` (+9/-1) and `crates/sources-plugins/tests/manifests.rs` (+4).
- **Judgement:** both edits are test-only. Both are forced by the existing every-catalogued-plugin guard tests once the plugin is in `catalogue.rs`, and both are minimal. They're acceptable. The `let mut plugins = plugins;` rebinding in `credential_spec.rs` is clumsy but harmless.
- **Fix:** list both files in the decisions file and the PR description.

### I4. The fixtures are hand-written and the ToS was read second-hand
- **Where:** `fixtures/wikidata/README.md` and the decisions file §Terms.
- **What:** the brief says "recorded fixtures only", and the owner's §2.28 asks for a ToS check before code that calls the service. The session couldn't reach Wikimedia, so the fixtures follow the documented shape and the policies were read through search results quoting them. Both are recorded honestly, with dates, and gated in "Before it can be switched on". Since the plugin has no host wiring and External consent can't be switched on in this build (`control::consent_text_approved`), nothing calls the service.
- **Fix:** none in this PR. The runner should record this as an explicit condition, or as an owner-queue item, on the slice that lifts the External consent gate:
  - re-record the fixtures live;
  - re-read the policies directly;
  - settle the open "bulk" question.
