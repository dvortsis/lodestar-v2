## Findings

### 1. MEDIUM (blocking under standards §113): four new behaviours have no test that fails without them
- **a. The deadline runs from the program's start.**
  - **Where:** `deliver.py:426,461` and `tests/test_deliver.py:448`.
  - **Gap:** the test's 700 s pre-SSH delay sits in `my_ip`. That runs in `open_rules`, after `Delivery` is built, so dropping `deadline=deadline` passes every test.
  - **What that mutant would do live:** OIDC/STS, the S3 read, two Secrets Manager reads (each up to 3 × 40 s under `AWS_CALL`) and the git ancestry check would fall outside the budget. That's up to about 8 more minutes, enough for GitHub to cancel the job before the close and the report.
  - **Fix:** put the delay in `connect` or in `FakeS3.get_object`. My probe with a slow S3 read passes on the current code (first session timeout 740 = `WORK - 700`, elapsed 1,450 s).
- **b. "Out of time before it could connect".**
  - **Where:** `deliver.py:358,364`. This branch is new, and no test reaches it.
  - **Gap:** both connect-guard mutants survive. So does changing the line to `"{role}: delivered; /run " + ...`. With a clean check, that line ends "delivered; /run clean", so `ok` becomes True and the job exits 0 having delivered nothing (fail open).
  - **Fix:** add a test where the pre-SSH calls leave under 60 s. Assert no `remote_command()` call, the line "main: out of time before it could connect; /run clean", rc 1 and the rule closed. My probe confirms the current code does exactly that (one check with a 30 s timeout).
- **c. `lost_any` and `BUSY_VM`.**
  - **Where:** `deliver.py:360,370`.
  - **Gap:** the only test, 255 then 21 then checks 1, 1, 0, is covered by either term alone, so each mutant survives.
  - **Fix:** add a 255 then 20 case (`lost_any` alone must poll). My probe gives 3 checks and "the VM isn't ready…; /run clean". Also add a lone 21 with checks 1, 1, 0 (`BUSY_VM` alone must poll).
- **d. The 10 s floor.**
  - **Where:** `deliver.py:384`.
  - **Gap:** `Hangs` returns 1 whatever the timeout, so dropping the floor passes. Live, the timeout would be 0 or negative, which reads as 256, "unchecked; escalate". That still fails closed, but it's the opposite of the stated "always one check".
  - **Fix:** in `test_every_ssh_wait_is_clamped_to_the_job_deadline`, assert `timeouts[-1] == 10`. My probe shows `[740, 10]`.

### 2. LOW (fail closed): a session started with less than `SSH_TIMEOUT` left can leave an orphan running past the deadline and the lock
- **Where:** `deliver.py:358`. A session may start with as little as 60 s left.
- **Failure path:**
  1. The pre-SSH calls are slow (700 s in the PR's own test), so the session is clamped (to 740 s there).
  2. It ends with 256 while the remote bootstrap is still in its flock wait or its cloud-init wait. There's no PTY, so the bootstrap keeps running: up to `FLOCK_WAIT + CLOUD_INIT_WAIT + STEP_TIMEOUT` = 810 s from the session's start.
  3. The clean poll is clamped to the deadline, so the line reads "NOT clean; escalate".
  4. pia-release then frees the fleet lock while that orphan can still write `wg0.conf`.
- **Why it's only LOW:**
  - It escalates.
  - The orphan writes the intended login.
  - The per-VM `flock` serializes any later delivery.
  - Typical runs never start a session late: about 1,410 s are left at the first connect, and at least about 1,280 s at the last retry.
- **Fix:** start a session only when `self._left() >= SSH_TIMEOUT` (870 s); otherwise take the out-of-time path. Then every orphan's bound ends at least 60 s before the deadline, so the clamped clean poll can always wait it out, and "NOT clean" means a real problem. The 700 s test would then expect "out of time before it could connect".

### 3. LOW / nit: the reserve sum is exactly full and leaves out terms; the clock is not monotonic
- **Where:** `tests/test_deliver.py:430-433` and `deliver.py:78-85`.
- **The sum:** `RESERVE` (360 s) is set equal to `before (120) + close (2 × 3 × 30) + report (60)`. It leaves out three things:
  - the floor's overrun of up to 10 s past the deadline, which the other test allows (`WORK + 10`, line 460);
  - the report, which is up to 3 channel POSTs of 30 s each (two targets plus the close-failure line), so 90 s, not 60;
  - the close's sweep, which calls `lookup_run` once for each other job rule (30 s each), more than one "middle call" when there are several.
- **Worst case:** with every Linode and GitHub call hanging to its timeout and setup really taking 2 minutes, that's 120 + 1,440 + 10 + 2 × (30 + 30k + 30) + 90 ≥ 1,840 s for k ≥ 1, past 1,800 s.
- **Effect if it happens:** the close runs before the reports, so the rule is the likelier part to survive; the reports are what get cut.
- **Fix:** count these terms in the test, and take a 7-minute reserve (`WORK` = 23 min) or trim `CLEAN_WAIT_SECONDS`' margin.
- **Nit:** the deadline uses `datetime.now(timezone.utc)`, a wall clock. A backwards step stretches the budget. `time.monotonic()` for the deadline would be exact.

## Answers to the brief's questions
- **Clock and start:**
  - The deadline is set at `deliver()`'s entry, right after `limits.load()` and before the gates, `connect`, AWS and git. That's early enough.
  - Checkout (fetch-depth 0) and pip run before the program. They're inside the reserve's 2 minutes, which is an estimate rather than a bound, but generous for those steps.
  - It's a wall clock, not a monotonic one (finding 3).
- **Calls outside SSH:**
  - The pre-SSH calls aren't clamped, but they spend the same budget. Their worst case is about 700 s, under `WORK`.
  - If they did exhaust it, the target takes the out-of-time path with one check of at most 10 to 60 s, then the close.
  - The close is bounded only by urllib's per-operation timeouts of 30 s (no total clamp; finding 3).
- **The 10 s floor:** at most one late check per target, run in parallel, so at most 10 s past `WORK`. That reaches past `WORK + RESERVE` only when the close and the report also take their full budgets (finding 3).
- **False escalations:**
  - Under typical conditions (pre-SSH under about 60 s) no session or poll is cut short. The first session gets the full 870 s.
  - Retries start within 125 s of the first, and each orphan's bound ends by about 965 s, well before the 1,440 s deadline.
  - The clamp bites only after an abnormally slow pre-SSH phase, and then it escalates (fail closed).
- **Fail closed:**
  - `close_rules` and the report are still in `finally`.
  - "clean" requires the check's rc 0.
  - The out-of-time line can never satisfy `ok`, as written.
  - pia-release (`always()`, a conditional delete) is unchanged.
  - The only case where the lock goes while the remote side can still act is finding 2. It escalates.
- **`BUSY_VM` counted as lost when no session was lost** (a genuinely concurrent holder, which in practice is a previous job's orphan):
  - It polls for up to 660 s, clamped to the deadline.
  - The line is never "delivered", so the job exits 1. A lone 21 with the VM still held escalates after 650 s; it's never reported clean early.
  - It's safe, and costs only time.
- **The `test_lock` nit:** fixed. The marker is built after the clock moves, with the control case. Dropping `holder.kind == "run"` from `_ours` (`lock.py:174`) now fails `test_lock`, so last round's surviving mutant is caught.
