## New findings

### BLOCKING

**R4-1. After a reinstall that ends 0, step 5 removes the marker and calls `sc start` while the idle service is still RUNNING. The start is a no-op. Within a second the idle process sees the marker gone and exits 0. Exit 0 triggers no failure action, so the service is left STOPPED, and `healthy()` reports the rollback unhealthy.**
- **Where:**
  - `rollback.rs:717-743`: when `reinstall_restart` is false, step 5 doesn't stop the service before `remove_marker` (`:731`). It goes straight on to `set_start` and `sys.start_service()` (`:739`).
  - `helper.rs:1043-1045`: the real `start_service` is `sc start` with the result ignored. On a running service that's ERROR_SERVICE_ALREADY_RUNNING (1056), and nothing happens.
  - `service.rs:155` and `:693-694`: `MarkerGone` ends the process with 0, and `report(.., Stopped, .., 0)` sets NO_ERROR.
  - `main.wxs:115`: `FailureActionsWhen="failedToStopOrReturnedError"`. A clean stop with exit 0 is neither, so the SCM doesn't restart it.
- **Failure scenario** (the main rollback path, where the `from` reinstall ends 0):
  1. During step 4's MSI, StartServices starts the new `from` service. It sees the marker and idles in RUNNING. This is the N-1 fix working.
  2. The copy answers 0, and the helper saves `done = 4`.
  3. Step 5 removes the marker, then runs `sc config … delayed-auto` and `sc start`. Both are process spawns, roughly 50–200 ms in all.
  4. The idle loop looks once a second, at a random phase. In roughly 80–90 % of runs it is still asleep when `sc start` arrives, so the start is a no-op.
  5. Within 1 s the idle loop sees the marker gone and returns `MarkerGone`. The service reports STOPPED with exit 0, and no failure action fires.
  6. `roll_back` calls `sys.healthy()` (`rollback.rs:496`). `wait_for("RUNNING")` may pass on the dying idle process. The 60 s hold then sees STOPPED and returns false. The result is `RolledBack { healthy: false }`, the journal is cleared, and the service stays stopped with start type delayed-auto until the next boot or an administrator starts it.
  7. Even when the idle process loses the race and `sc start` starts a fresh process, the result is right only by timing.
- **The same pattern elsewhere:**
  - **The drop path** (`rollback.rs:411-416`): another version installed by hand while the marker existed. Its service idles, and the helper removes the marker. The idle process then exits 0, and nothing starts the service again.
  - **Recovery text step 3:** if an administrator scripts "delete the marker; `sc start`", the start can land in the same window.
- **Before this delta:** the service exited 3 at once, which caused the 1920 risk (N-1), but the failure actions (restart after 60 s) and step 5's start covered a stopped service. **In round 2:** the marker was gone before step 4, so StartServices brought up a healthy `from`.
- **Why tests miss it:** the Fake's `start_service` only records a call. It doesn't model a service that is already running, and the service tests stop at `idle_during_rollback`'s return value. The decisions file's claim that "step 5's start … brings up a fresh process" holds only when the idle process exits first.
- **Fix:** either of these clears it. (a) is preferred because it covers every path.
  - **(a) Carry on rather than exit (option (b) as first proposed).** On `Idle::MarkerGone`, fall through into the normal start in the same process (`init_logging`, then `serve`), reloading the config if wanted. Keep exit 0 for `Idle::Stopped`. Step 5's `sc start` is then a harmless no-op on a service that keeps running, and the drop path and manual recovery work too.
  - **(b) Stop before removing the marker.** In step 5, call `stopped(sys)?` unconditionally before `remove_marker`. Today it runs only on the `reinstall_restart` path. That brings step 5 into line with the brief's "stop → remove marker → set_start/start". The drop path then also needs a stop before `remove_marker` and a start after it, or it keeps the same gap.
  - **Either way, add a test.** Give the Fake a running state (an MSI answer of 0 sets it running; `start_service` on a running service does nothing; a marker removal while it is running sets it stopped, for the exit-0 variant). Then assert that the service is running after a full rollback that ends 0.

### NIT
- **R4-2. The MarkerGone test hangs rather than fails when the guard is broken** (`service.rs:1468-1473`). After the 10 s drain deadline, `handle.join()` blocks forever on a loop that never ends. Mutation M2 was "caught" only by the harness timeout. Add `assert!(handle.is_finished(), "the idle wait ended");` before the join, and in the first test set `stop` before any assert that could panic, so a failure can't leave the thread looping. Not blocking: there's no fixed sleep, and the deadline is 10 s.
- **R4-3. The SCM arm itself (`service.rs:686-695`) is `cfg(windows)` and has no unit test.** It compiles on CI (`test (windows-latest)` passes). Whatever R4-1's fix becomes, a small pure helper that maps an `Idle` to the next action (exit 0, or serve) would make that choice testable on every OS.
