## Polish
- **P-a.** The accepted-risk window is wider than recorded (`companion_wiring.rs:571-573`, `docs/decisions/2026-11-09-CMP-5g.md:60`).
  - **Why it's wider:**
    - The address write only applies at Lodestar's next start, so the running plugin keeps your address in memory.
    - The companion gate re-runs a gated plugin on every health flip or Unknown snapshot (`pipeline/src/requires.rs:15-29`, `pipeline/src/lib.rs:921`).
    - Each re-run reads the key from the store again (`prowlarr.rs:307-310`).
  - **Consequence:** the companion's key can reach your own server at any point until Lodestar restarts, and that includes after a successful hand-over, not only "between steps 1 and 2" or after a restart.
  - **Severity:** low.
    - The key is Lodestar-generated, and it goes to the server you configured.
    - Earlier orders had the same property.
    - There's no live path in this build: Prowlarr isn't registered, and CMP-5g-2 hands over qBittorrent only.
  - **Fix:** correct the wording, and name it as something X-prowlarr-settings must handle (for example, stop or reload the source after a hand-over).
- **P-b.** The failure test bypasses the real refusal (`companion_wiring.rs:1059`).
  - **Today:** `fail_config` returns `false` without calling `Control`. Reading the code, a real non-editable source fails the same way: the default `check_config` refuses ("this source has no settings to change", `sources/src/plugin.rs:126-128`), and `update_source` returns `Invalid`.
  - **Better:** route the failure through `Control`. Give `StandIn` an editable flag (an `AtomicBool`) that the test sets after seeding, or a `check_config` that refuses the loopback address. Then the runner's "refused config write when not editable" is exercised end to end.
- **P-c.** Step 1 can fail after it commits.
  - **How:** `update_credentials` commits, then calls `self.view(id)` (`pipeline/src/control.rs`, the end of `update_credentials`, about `:1446-1452`). If that read fails, the hand-over returns `Rejected`, but the companion's key is already stored beside your address, and nothing is rolled back or logged.
  - **No safe rollback:** on a real failure, removing the key would destroy yours, so rolling back isn't safe either.
  - **Fix:** add this path to the accepted risk in `:60`. It's rare: a store read has to fail straight after a successful write.
- **P-d.** The rollback-log test (`companion_wiring.rs:1042`) uses a process-global counter with `>`.
  - **The risk:** a parallel test that also logs `CONFIG_FAILED` could hide a regression.
  - **This run:** the mutation was caught.
  - **Fix:** also assert `w.log() == ["key set", "config …", "key removed"]`, so the test shows the removal was tried.
