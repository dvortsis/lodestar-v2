## How B1 holds up (check 1)
- **Scope.** The rule is `INPUT 1 -s <ep>/32 -p udp --sport <port>`, tagged `lodestar-leak-host`, and nothing broader. It is built only after `endpoint_valid` (`leak-test.sh:322-328`), from validated values, as a quoted array (`:345`), so no word splitting or globbing can widen it.
- **Timing.** The leftovers are cleared, then the guard goes in (`:347-349`), after `compose_installed` and before the first `tunnel_up`.
  - So it is in place before the old container stops, which is when Docker's first conntrack flush happens.
  - It is held through the recovery recreate.
  - It is removed only by `cleanup` (`:77`), on the EXIT trap.
  - The tests assert all three points: `-I INPUT` comes before the first `up`, `-D INPUT` comes after the last `up`, and no copies are left on every `test_leak_test_failures` path.
- **Every exit path runs `cleanup`:**
  - success: `finish` calls `exit 0`, which fires the EXIT trap;
  - failure: `finish` calls `exit 1`;
  - interrupt: the HUP, INT and TERM traps call `exit 1xx`, which fires the EXIT trap.
  - The one gap is a signal landing while `iptables -I` itself runs (O1).
- **It can't block the tunnel.**
  - The fleet compose publishes only `127.0.0.1:8090` (TCP, `compose.yaml:42-43`). So no UDP DNAT rule can steer an unsolicited endpoint packet into a container.
  - The new session's WireGuard UDP leaves the container, is MASQUERADEd, and creates the conntrack entry. Its replies are de-NATed in PREROUTING and routed to the container IP, so they go through FORWARD, never INPUT.
  - A leftover packet that reaches INPUT and is dropped there never gets its conntrack entry confirmed, because confirmation runs after the filter hook. So it also can't take the host port that the new session's SNAT mapping needs.
  - gluetun is the only thing that talks UDP to the endpoint. PIA's API is TCP and runs before the leak test.
- **It can't hide anything the test judges.**
  - The test judges two things: the veth capture of what the container sends, and the DOCKER-USER counter on `-i <bridge> -o <egress>`, which is FORWARD.
  - Container traffic never crosses host INPUT.
  - The host guard only removes the host kernel's own replies, which is exactly what the external eth0 capture is meant to stop seeing.
  - A container ICMP to the endpoint would still leave through FORWARD and POSTROUTING, and the counter, the capture and eth0 would all still see it.
- **IPv6.** Only `iptables` is handled, and that is correct. `endpoint_valid` accepts only an IPv4 literal, so the endpoint's packets can't arrive over IPv6. The reason isn't written down anywhere (O4).
- **The host's own firewall.** Cloud-init sets up no ufw or nftables on the VMs, so with INPUT policy ACCEPT the kernel's UDP "port unreachable" is what the guard suppresses. Linode's cloud firewall is external and doesn't matter here.

## Optional
- **O1. A signal in the insert window leaves a guard.** `leak-test.sh:348-349` and `:144-145`.
  - **Scenario:** bash defers a trapped TERM or INT until the foreground `iptables -I` returns, then runs `exit 143`. The EXIT trap's `cleanup` then runs with `host_set`/`guard_set` still empty, so the copy just inserted survives the run.
  - **Why it's minor:** the next run clears it if the endpoint is unchanged. A left host guard can't hurt the tunnel, but a left DOCKER-USER guard blocks the tunnel until then, which fails closed.
  - **Fix:** set the flag before the insert, which is safe because `drop_all` checks with `-C` first: `host_set=1; iptables -I INPUT 1 … || { bad host_guarded; finish; }`, and the same for `guard_set`.
- **O2. `drop_all` reads any `-C` error as "gone".** `leak-test.sh:86`.
  - **Scenario:** a transient `iptables -C` error (exit 2 or 4, not 1) while the recreate guard is present makes `tunnel_up` clear `guard_set` with the guard still in place.
  - **Result:** the tunnel stays blocked for the rest of the run and after it. That fails closed, but the report then says `wireguard_handshake_never_completed`, which is O2's original misdiagnosis.
  - **Fix:** treat only exit 1 as absent, and return 1 otherwise. Also consider reporting `recreate_guard_held` when `guard_set` is still on (`:386`: `[[ -n $guard_held || -n $guard_set ]]`), so the `recreate_guard_lifted` case isn't also reported as a credentials problem.
- **O3. `cleanup` ignores a failed `drop_all`.** `leak-test.sh:76-78`.
  - **Scenario:** on the success path, a host guard that won't come off is never reported, and the run still prints `ok leak_test` and exits 0.
  - **Why it's harmless:** it only drops the endpoint's UDP to the host itself, and the next run clears it.
  - **Fix:** if wanted, `exit 1` from the EXIT trap when a removal fails. Otherwise, say in the decisions file that the host guard's removal at `cleanup` is best effort.
