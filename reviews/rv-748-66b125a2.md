## Summary
The slice adds `Network::Usenet = 4` and `UsenetKey`, which is SHA-256 over a domain-tagged, `u32be` length-prefixed (indexer, GUID) preimage. Each part must be 1–1024 bytes. The store enforces the invariants itself, whatever the caller passes:
- private-source is forced on write and on read;
- `promote` refuses a usenet item with the new `Error::NeverVerified`, before any other check and again inside the transaction;
- `pending_keys_after` and `has_unverified` are limited to `network = 0`;
- holds and torrent lookups are skipped for non-BitTorrent keys (a behaviour-preserving extraction into `put_bt_torrent`).

It also adds the tier purge `purge_network`, which runs in bounded steps, refuses BitTorrent and scrubs the WAL. The Q13 cap (`USENET_CAP` = 1M, lowest id first) is enforced inside `put_unverified`'s own transaction, with a batch bound (`MAX_USENET_BATCH` = 4096) and a compile-time assert that the cap is at least the batch bound. There's no migration: V14's CHECKs accept the rows, and two tests show it (a real V13 → V14 upgrade and a reopened file store).

The snapshot tier-purge retention choice the runner accepted is implemented as written:
- `purge_network` calls `delete_item(.., false)`;
- `cap_network` deletes raw, with no journal;
- `delete_item(.., true)` journals only `network = 0`;
- V14's hold triggers match only `network = 0`.

So nothing is journalled for usenet rows, and a pre-purge snapshot keeps them until it's pruned. Runner follow-up 655 tracks this.

I found no Blocking or Important issues. There are four Nits.

### Nit
1. **`claims_private` for a usenet row with unreadable claims reads false** (`crates/store/src/unverified.rs:1349-1350`).
   - *Scenario:* a usenet row whose flags lack bit 2 (written outside the API) and whose claims blob doesn't decode reads `claims_private = false`, though claims are stored.
   - *Impact:* in practice nil. `put_one` always writes flags 3, and unreadable claims can't be served.
   - *Fix:* use `network == Network::Usenet && self.claims.is_some()` on the raw blob before decoding, or simply `network == Network::Usenet`, for symmetry with `forced_private`.
2. **No store-level hold for usenet keys** (`unverified.rs:1439-1445`). By design, `put_one` skips `held()` for non-BitTorrent keys, because tombstones, quarantine and `cs_hashes` hold 20-byte swarm hashes.
   - *Scenario:* a usenet item a refile deletes as held (see `a_held_refile_of_a_usenet_item_touches_no_hash`) is re-added on the next Prowlarr poll. Only the filter engine's pre-write judgment gates it, and that judgment is deterministic, so it's held again.
   - *Impact:* a future user "delete and keep deleted" action for a usenet item has nothing to record into.
   - *Fix:* no change in UN-0. Name this in UN-1 or UN-3's brief, together with follow-up 651 (the re-judge sweep must judge usenet items by their claims).
3. **The wording about the tier purge's race** (decisions file line 31; doc comment at `unverified.rs:1182`): "an item a running source writes behind the cursor would survive".
   - Ids come from the monotonic `id_seq`, so a new item lands ahead of the cursor, not behind it. What survives is an item written after the final step.
   - The conclusion (disable the sources first) is right. Only the reason is slightly off.
   - *Fix (optional):* reword it as "written after the last step". `purge_network` could also refuse while any enabled or paused source's bit is set on a `network = 4` row, a cheap partial guard.
4. **Shared edits outside the brief's owns.** `lib.rs` gains the `NeverVerified` variant and its `Display` arm, not just a `pub use`. `crates/store/Cargo.toml` and `Cargo.lock` gain the `sha2` edge.
   - The decisions file records both as runner-approved on 2026-11-12. I couldn't see the approval itself; the runner should confirm.
   - Both edits are minimal and safe: `Error` is `#[non_exhaustive]`, and `sha2 0.11.0` is already in the tree.

The cap's cost (count plus sort, about 160 ms per adding batch at 1M, inside the writer's transaction) is already documented. The runner tracks it as follow-up 656, and UN-1 must measure it before enabling. I don't raise it again.

## What was verified
- **The new dependency.** `sha2 = "0.11.0"` is not new to the tree. The same version is already used by `lodestar-metainfo`, `lodestar` (×3) and `sources-importers`, `=0.11.0` by `companions` and `update`, and `0.11` by `api`, `dht` and `peer-wire`. `Cargo.lock` gains one dependency edge on the existing `sha2 0.11.0` entry (checksum unchanged), with no new crate or version. It's the RustCrypto crate, MIT/Apache-2.0 and actively maintained. It's needed for the SHA-256 key.
- **Schema.** There's no migration, and `schema.rs` and the migrations are untouched. V14's CHECKs are `network BETWEEN 0 AND 15`, a key of 1–64 bytes, and 20 bytes only for network 0, so a 32-byte key under network 4 passes. The flags CHECK (0–3) is satisfied by 3. The claims length CHECK is bounded by the existing `claims` limits.
- **Rollback.** `lodestar rollback v13` restores a pre-V13 snapshot at schema 12, which has no `unverified_items`. With no migration in this PR, rollback is unaffected.
- **Indices.** `count(*) WHERE network = ?` and `EXISTS … WHERE network = ?` use the `(network, key)` autoindex. There's no new index; the decisions file defers a `(network, id)` index to SRC-3b.
- **Bounded sizes.**
  - Key parts are 1–1024 bytes, checked before hashing.
  - The stored key is exactly 32 bytes (`check_key`).
  - A batch holds at most 4096 usenet items.
  - Eviction and tier-purge steps are each at most `MAX_PURGE_STEP`.
  - Claims sit under the existing caps.
- **Atomicity.** The cap runs in the same `begin_write` transaction as the inserts. `purge_network` takes one transaction per step. `promote` checks the network again inside its transaction.
- **Eviction.** Ids are monotonic (`id_seq`), and the batch size never exceeds the cap (compile-time assert), so a batch's own new items are never evicted. A lowered cap drains at most 4096 rows per adding call. "Oldest first" by first-found id matches sources-plan Q11's wording.
- **SQL injection.** Every value is bound (`?N` params). The only `format!` is in a test (`ITEM_COLUMNS`).
- **DHT and privacy reachability.**
  - `pending_keys_after` is `network = 0` only. That covers the torrent cache's cursor and its single-id lookup at `pipeline/src/torrent_cache.rs:476`, which also filters on `id == id && network == Bt`.
  - `partial_hashes`, `adult_finders` and every `store.unverified(..)` caller in pipeline and lodestar already pass `Network::Bt`.
  - Nothing outside the store builds a `Network::Usenet` item today: the pipeline hard-codes `Network::Bt` at `pipeline/src/unverified.rs:942`. So the slice is inactive, as the plan requires.
- **Private source (§18.7).** It's forced on in `put_one`, both on insert and in the update path's `flags & keep_private` arm, and forced again on read through `forced_private`, including in `PendingKey`. `put_bt_torrent` is behaviour-identical to the removed inline code.
- **`has_unverified`.** Narrowing it to `network = 0` is correct for both writer callers (`writer.rs:1843`, `:2413`), which look up swarm hashes only.
- **Unknown networks.** 1–3 and 5–15 (and -1, 16, `i64::MAX` in the unit test) still fail as `Error::Corrupt("unknown network")`.
- **Tests.** There are no sleeps or timing waits in the new tests.
- **Hygiene.** No model identifiers in code, docs or commit bodies; the commit trailers are the harness-supplied ones, which CLAUDE.md allows. No 12-digit numbers. No local times or zones.
- **Owned paths.** Everything is within the brief's owns except the shared edits in Nit 4.
