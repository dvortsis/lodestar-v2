## Blocking

1. **An older `/system` read can still overwrite Keep's answer, and no test pins the "Keep's own answer is applied" fix.**
   - **Where:**
     - `restart.svelte.ts:24-26` (`setAddressChange`) and `:35-45` (`refresh` writes `system = s` whenever a GET lands);
     - `AddressPrompt.svelte:67-70`;
     - `AddressPrompt.test.ts:98-109`.
   - **What happens:** a GET that left before the POST but answers after it writes the pre-Keep `awaiting_confirmation` back into the store. That GET can be the watch's focus, route or 15 s refresh, or the prompt's own 0:00 check.
     - Reproduced in a scratch unit test on `RestartBanner` (route `/`, time left): GET pending, Keep pressed, POST answers `{address_change: null}`, so the prompt goes. Then the stale GET lands, the store is `awaiting_confirmation` again, and **"Keep this address" is back**.
     - It stays until the next watch refresh (15 s on Settings, 60 s elsewhere). The watch's region re-announces "Lodestar is now at …. Choose Keep this address…" after the user has already kept it.
     - A second Keep gets `NoAddressChange` from `address.rs:786`, shown as a failure message.
     - At 0:00 the remounted prompt re-checks at once, so it heals in one round trip, but with the same flash and re-announcement.
     - It's rare, because the GET left first, but it's the race round 3's I3 (scenario B) asked to close, and the brief's I3 claim is that "Keep pressed while a check is in flight wins".
   - **Not pinned:** replacing `restart.setAddressChange(outcome.address_change)` with `await restart.refresh()` (the round-3 behaviour) passes every restart and shell unit test and the Keep e2e.
     - The in-flight test renders the prompt standalone with a fixed `system` prop, and never asserts the store or the banner, so it only exercises the `answered` guard.
     - runner/standards.md §113: a missing test for new behaviour is blocking.
   - **Fix:**
     - give the store an epoch: `setAddressChange` (and `begin`) bump it and drop `inflight`, and `refresh` captures the epoch when it starts and doesn't write `system` if it changed;
     - add a test at the store or banner level: GET pending, then Keep, then release a stale `awaiting_confirmation`. The store's `address_change` must stay `null` and the prompt stay gone.
     - This test also fails under the `refresh()` mutation above.
