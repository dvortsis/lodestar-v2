  - a 60 s read deadline;
  - 4 requests in flight;
  - a bucket per IP.

### Important
**I1. CI is red at the reviewed head because the new built-in source breaks the consent safety test. Resolved at `40e524ea`.**
- **Where:** `crates/sources-plugins/tests/safety.rs:735` (at `290db5e6`).
- **Failure:** `Pipeline::start_with` now registers an `upload` source row at every start (`crates/pipeline/src/lib.rs` +684). The safety test does `manifests.iter().find(|m| m.id == row.plugin).unwrap()` for every stored row, and `upload` has no manifest. So `no_enable_path_opens_a_consent_class_in_any_shipped_plugin` panics, which fails `test (ubuntu-latest)` and `ci-ok`. CI on `290db5e6` confirms it.
- **Fix, already pushed in `40e524ea`:** skip the `upload` row and assert that it's `Enabled`. I reviewed it: it's correct and test-only.
- **Production code is safe:** I checked the consumers of `store.sources()` (`torrents.rs` `Catalogue::read`, `control.rs` `switch_off_unapproved`, `cli/import.rs` `adult_sources_of`, the torrent-cache and adult-enrichment lookups). All of them handle a row with no manifest, as they already do for import sources.
- **Still to do:** add `crates/sources-plugins/tests/safety.rs` to the PR description's and the decisions file's shared-edits lists, since it's outside the brief's `owns`.

### Nit
**N1. The served-binary test's RSS check can pass vacuously.** `crates/lodestar/tests/upload.rs:265-269`.
- **The problem:** it waits until the feed shows the *public* alert, then asserts that the private one is absent. The percolator runs asynchronously after commits, so a run covering only the first commit can record the public alert before the private one exists. In that interleaving the assertion proves nothing. It was caught in my M7 run, but nothing guarantees the order.
- **Fix:** move the `until("the private alert", ..)` wait (`:283`) above the RSS fetch, so the private alert is known to exist when the feed is checked.

**N2. `feed_xml`'s `PRIVACY` check (`crates/api/src/alerts.rs:352`) has no test of its own.** M5 survives because `shown_alerts` filters first in SQL. It's harmless defence in depth. If you want it pinned, a unit test that hands `feed_xml` a row past the SQL filter would do; otherwise leave it.

**N3. A panic while judging ends the upload judge for the process.** `crates/pipeline/src/local_torrent.rs:378-386`.
- **What happens:** every later upload is `503 uploads_unavailable` until a restart. It's documented, and `read` is fuzzed (clean). But an authenticated user who finds a `judge_sealed` panic could switch uploads off.
- **Fix, optional and for a follow-up:** wrap `judge_one` in `catch_unwind`, as the writer's `rejudge_stale_holds` does, answer `Malformed`, and build a new `Preparer` from the store.

**N4. "A crawl can't clear the private bits" holds only for `PRIVATE`.**
- **What's built:** a later *public* sighting of the same hash clears `PRIVATE_SOURCE` through `make_public` (`crates/store/src/lib.rs:1316`, `unverified.rs:725`). A DHT crawl's leased commit, an import, or a public upload of a non-private file are all public sightings. `PRIVATE` (BEP 27, from the info dict) stays.
- **What that means:**
  - RSS, Torznab, the bitmagnet export, Send, scrapes, cache lookups, refetches and ENR-1 stay closed.
  - But the row then reappears in the plain CSV, NDJSON and magnet exports, exactly like a crawled BEP 27 torrent under OUT-0.
- **Where it stands:** the decisions file documents this ("Later sightings"), and it's consistent with OUT-0, since the hash is then on the DHT. A re-upload can't clear either bit: `|=` plus `commit_one`'s no-`make_public` for a private commit, which I verified. I'm flagging it only because the review brief expected a crawl not to clear the bits. No change is needed unless the runner wants `PRIVATE_SOURCE` to stick for uploads.

A follow-up for whichever slice wires alert notifications.** ntfy, Discord, email and webhook build `NotificationItem.private_source`, but nothing in production constructs those items from alerts yet. When something does, it should take the flag from `flags::PRIVACY`, matching the feed, or at least from `PRIVATE_SOURCE`, which uploads now carry. Not this PR's to fix.

## Verified correct
- **Size cap before buffering.**
  - A `Content-Length` over 8 MiB is a 413 before the permit or any read (`upload.rs:229-235`).
  - The streamed read stops at cap + 1 (`:383`), and `with_capacity` is bounded by the cap (`:369`).
  - `read` re-checks the cap, and `parse_with` and `raw_info` check `max_torrent_bytes` too.
  - The memory bound is about 9 bodies: 4 in flight, plus a queue of 4, plus 1 in the judge. Clients that leave after sending can't grow it past the queue.
- **Bencode bounds.**
  - `LIMITS` is the cache's: depth from `Limits::DEFAULT`, 1 M items, 100 k files.
  - The lenient decode still rejects duplicate keys in unsorted dicts (`bencode/src/decode.rs:282-289`), so the parsed torrent and the raw info span can't pick different `info` dicts.
- **The info hash comes from the exact raw span.**
  - `TorrentFile::raw_info` returns the dict's own `raw()` slice.
  - It's parsed again with no `encoding` hint, and the key is `primary_hash()`: SHA-1 for v1 and hybrid, truncated SHA-256 for v2.
  - The fuzz target asserts this on every accepted input.
- **v1, v2 and hybrid:** each is stored, with its claims (pipeline test). The hybrid is refused by the cache gate under both swarm hashes.
- **No path traversal:** file names live only inside the info dict and go through the existing `prepare`. Nothing is written to the filesystem.
- **No panics on attacker data:**
  - The only `unwrap`/`expect` calls in the new non-test code are on the poisoned-mutex fallback (`unwrap_or_else(into_inner)`).
  - The `as` casts are clamped (`wait`), and `declared as usize` happens only after the ≤ cap check.
- **Auth.**
  - The route is behind `auth::protected` only: a session or trusted-proxy auth, plus the accepted notice.
  - An API key in the `Authorization` header, in `X-Api-Key` or in `?apikey=` gets 401 (tested).
  - The Origin–Host comparison is identical to `same_origin_json` (table test), with the stricter `Sec-Fetch-Site: cross-site`, and a non-UTF-8 value counts as cross-site.
  - `application/x-bittorrent` isn't CORS-safelisted, so no cross-site simple request can carry it.
- **Rate limits.** The bucket is the upload's own, keyed on the resolved `ClientIp`: behind a trusted proxy that's the forwarded client, and a spoofed left-hand XFF entry is ignored (tested). It's spent before the body is read. A full table refuses newcomers without evicting live buckets.
- **Errors and logging.**
  - Every error body is a fixed string.
  - `Debug` for `Local`, `Outcome`, `Upload` and `Uploader` shows no hash, name or text.
  - `local_torrent` doesn't log.
  - The responses carry only the info hash and `private` (tested: `each_outcome_names_its_cause_and_nothing_from_the_file`).
- **Privacy.**
  - **Private uploads are stored as `PRIVATE | PRIVATE_SOURCE`.** Their trackers and comment are dropped, the passkey host is found nowhere in any table, and the claims are marked private.
  - **No outward output carries them:** they're absent from CSV, NDJSON, magnets (end to end and in api tests), Torznab (end to end) and RSS (end to end, and the SQL and row checks). The bitmagnet export masks `PRIVACY` (`export.rs:771`, unchanged).
  - **Public uploads appear** in each of those.
  - **A crawled BEP 27 torrent** stays in the plain exports (`a_private_upload_is_never_exported_and_a_crawled_bep27_one_still_is`) and is out of RSS (`the_feed_leaves_out_bep27_private_and_unverified_remote_rows`).
  - **`crates/api/src/export.rs` is unchanged.**
- **The `|=` path.**
  - It runs only for lease-free commits (`if !c.leased`).
  - The cache's files pass `false`, so their behaviour is unchanged.
  - `rejudge_stale_holds` mutates `judged` in place, so `private_source` survives a re-judge.
  - The upload's claims are ingested after the commit, with `private_source` taken from what was stored.
  - **No other writer path overwrites flags.** The other `SET flags` statements in the store either OR bits in, or clear `PRIVATE_SOURCE` only through `make_public` on a public sighting. `upgrade_partial` keeps `PRIVATE_SOURCE` only when both the row and the commit have it, and an upload's row is never `FILES_PARTIAL`.
- **Held and floor-blocked uploads are never stored.**
  - A floor block is dropped at judge time with no `ToCommit`.
  - A hold goes through the writer's existing hold path: a tombstone or quarantine, never a torrent row.
  - The archive is kept only with the setting on, and minus `pieces` (tested).
- **No fixed sleeps.**
  - The pipeline `until` polls for 10 s (400 × 25 ms), and the binary test's `until` for 20 s.
  - The api tests' `sleep`s run under `tokio::time::pause()`: an idle-advance in virtual time, not a wall-clock wait.
  - The binary's socket reads time out after 10 s.
- **Unit tests in every changed crate:**
  - api `upload.rs` has 5 unit tests;
  - pipeline `local_torrent.rs` has 8;
  - store `saved.rs` has an extended test;
  - lodestar `upload.rs` has 1.
- **Hygiene:**
  - no model identifiers in the diff; the only matches in commit messages are the harness's `Co-Authored-By` trailers;
  - no 12-digit numbers;
  - no local times, offsets or places, and dates are written as plain dates.
- **The size reason holds.** The description's breakdown is honest: about 1,510 lines of tests, about 275 generated or seed lines, and about 1,500 lines of code with about 420 of them unit tests. The reasons for one PR are sound.
