## What holds (checked)
- **No validation bypass.** Every body goes through `Uploads::submit` (the `Sink` impl for `Uploads`, `watch.rs:193`): the same `local_torrent` queue as the upload route, so the same metainfo parser, floor, full filter, adult and visibility rules, `private=1` → both privacy bits, and the lease-free writer entry. The cap is `local_torrent::MAX_BYTES` (equal to the API's `MAX_BYTES`). Nothing writes to the store directly. The route's per-IP rate buckets don't apply, but `MAX_SUBMIT` (32 per 10 s) and one in-flight `submit` bound the rate and give back-pressure.
- **Unix file handling is solid.** The folder is opened `O_DIRECTORY|O_NOFOLLOW` once per poll. Reads use `openat(fd, name, O_NOFOLLOW|O_NONBLOCK)`. `fstat` on the handle checks a regular file, the listed size and mtime, `nlink == 1` and the cap before `take(cap+1)`. Moves, creates and deletes use `renameat2(NOREPLACE)`, `mkdirat` and `unlinkat` on that fd, with `added/` and `failed/` opened `O_NOFOLLOW|O_DIRECTORY`. The path-based `read_dir` and `symlink_metadata` calls are only hints: a name listed from a swapped-in folder is still opened through the real fd. A FIFO opened non-blocking goes to `Wait`. An oversize file isn't opened. Delete mode removes only accepted files, by name, inside the folder.
- **Data-directory rules:** checked by `canonicalize` on both sides when the setting is applied and at the start of every poll. A root folder is refused because it holds the data directory. A trailing `/` is normalised away (tested).
- **Logs:** only fixed labels and counts. Settings save and load log field names, never values. The tests check that no file name reaches the log (unit test and served-binary test).
- **Lifecycle:** one task. `interval` with `MissedTickBehavior::Delay` means no busy loop. A section change that keeps the same folder keeps the watcher's memory. The task ends when the registry's sender drops. Blocking I/O in `poll` runs on `spawn_blocking`.
- **N1, N2, N3:** done. `catch_unwind` runs per item. The preparer's zstd `bulk::Compressor` starts a fresh frame on each call. No `panic = "abort"` profile, so the catch also works in release builds. No `writer.rs` edit.
- **Tests:** no fixed sleeps. The served test's `sleep(200ms)` is the poll step of a 60 s condition wait. The unit tests drive `Watcher::poll` directly. `crates/lodestar/Cargo.toml` has no tokio `test-util` or `testing` feature, and the PR changes no `Cargo.toml` or `Cargo.lock`.
- **`web/.size-limit.mjs`:** the "Settings section (own JS + CSS)" line is still exactly `'45 KB'` (line 1357), unchanged by the PR. The three raised on-demand limits are recorded in the decisions file under runner §2.26 with measured numbers, and §2.26 decisions are flagged under §2.19:
  - sources event names: 490 B → 768 B, measured 704 B;
  - Settings messages: 4 KB → 4.25 KB, measured 4220 B;
  - Wizard steps: 53.6 KB → 53.7 KB, measured 53603 B.

## Blocking

### B1. A saved folder that's missing at start is silently dropped and never resumes (contradicts the brief's req. 1 and the decisions file)
**Where:** `crates/lodestar/src/settings/watch.rs:73-84` with `crates/lodestar/src/settings/mod.rs:835/850`.

**What happens:**
- `Section::check("folder")` calls `shape_problem`, which reads the filesystem (it exists, it's a directory, it isn't a link).
- The registry runs the same `check` on every saved value when it loads at start (`validate::<T>` at `mod.rs:835`).
- A value that fails it is skipped as `settings.saved_ignored reason=invalid` (`mod.rs:850`). The effective `folder` becomes `""`, so `Watcher::new` returns `None` and the watch is simply off for the whole run:
  - no `watch.disabled reason=missing`;
  - no re-check on each poll;
  - no resume when the share mounts.

**Scenario:**
- Unraid, with the watch folder on an Unassigned Devices SMB/NFS mount that comes up after Docker autostart.
- Or a Windows service that starts before a NAS path or USB drive is reachable.
- Lodestar starts and the folder isn't there yet. The user's watch is off until they restart Lodestar again once the share is up. Nothing tells them why, except a generic "saved setting ignored" line.

**What it contradicts:**
- Brief req. 1: "validate … again at start … A bad path disables the watch, with one clear status reason."
- The decisions file, line 23 ("a share that mounts after Lodestar starts … resumes without a save or a restart").
- The "For the guide" fact at line 101, which the docs slice will teach users.

**Fix:**
- Keep `Section::check` to what doesn't depend on the filesystem's current state: empty, or absolute.
- Do the existence, directory and link checks on save in the PATCH path only (for example `confirm`, or a save-only hook), and leave everything else to `folder_problem` when the setting is applied and on each poll. That path already reports `missing` and recovers.
- Add a test: save a folder, remove it, re-open the registry from the same store, and the watcher still exists with `Problem::Folder(Missing)`.

### B2. The "never read twice" set can grow past `MAX_STUCK` (brief req. 4: "a bounded in-memory set … when full, disable")
**Where:** `crates/lodestar/src/watch.rs:454-458`, the `MoveError::Subfolder` arm of `finish`.

**What happens:**
- That arm inserts into `self.stuck` with no `MAX_STUCK` check, then `poll` carries on through the rest of the poll's entries (`watch.rs:313-373`).
- Every later entry in that poll can land there too:
  - each `Link` entry and each oversize entry (neither is bounded by `MAX_SUBMIT`);
  - each read that fails;
  - up to 32 submitted files.
- So the set can reach about `MAX_SCAN` (10,000) entries, ten times `MAX_STUCK`, in one poll.
- Entries are never pruned when their name leaves the folder. `retry_stuck` only runs for names that are listed.

**How it's reached:**
- **Without an attacker:** a transient error on `symlink_metadata(folder/added|failed)` partway through a poll (an SMB/NFS hiccup: `EIO`, `ENOTCONN` or `EHOSTDOWN` map to `SubfolderCreate` at `watch.rs:626`) after `Folder::open` succeeded.
- **With an attacker:** someone with write access to the folder swaps `added/` or `failed/` between the start-of-poll check and the moves. Each won race adds up to 10,000 names. With names deleted and recreated between races, the set grows with no bound.
- The same path also means files keep being read and submitted after the watch already knows it can't put them away.

**Fix:**
- On `MoveError::Subfolder`, record that one file (subject to the same `MAX_STUCK` check) and `break` the poll, with `out.problem = Some(p)`.
- Apply the `>= MAX_STUCK` check to both arms.
- Add a unit test: make `failed/` a link after `Folder::open`. On Unix, call `finish` directly or use a `Sink` that swaps it inside `submit`. Then assert `stuck.len()` stays at most `MAX_STUCK` and the poll stops.

## Important

### I1. Windows: a move that fails after its hard link was made leaves a new link name in `added/` or `failed/` on every poll
**Where:** `crates/lodestar/src/watch.rs:789-796` with the retry in `retry_stuck` and `move_out`'s suffix loop (`watch.rs:729-736`).

**What happens:**
- `hard_link(from, sub\target)` succeeds, then `remove_file(from)` fails. For example another program holds the file open without `FILE_SHARE_DELETE`, or, depending on the std version, the file has the read-only attribute.
- The error isn't `AlreadyExists`, so the file is marked stuck. The link already made is left behind.
- Each later poll retries: `x.torrent` exists, so `AlreadyExists`, then `x-1.torrent` gets a new hard link, and `remove_file` fails again.
- That's one new name per stuck file every 10 s, up to `MAX_SUFFIX` (1,000).
- After that, each poll makes 1,000 failing `CreateHardLinkW` calls per stuck file: up to about 1M a poll with 1,024 stuck files.

**Fix:** if `remove_file(&from)` fails, `remove_file` the link just created before returning the error.

**Test:** this is Windows-only. A unit test can hold the source open without delete sharing (`OpenOptionsExt::share_mode(FILE_SHARE_READ)`) and run three polls.

### I2. Windows: the folder itself is used by path after the per-poll check (unrecorded residual)
**Where:** `crates/lodestar/src/watch.rs:567-593` (`Folder::open` keeps no handle on Windows), then `list()`, `entry()`, `read()`, `subfolder()` and `move_out()`, all path-based.

**What happens:**
- `FILE_FLAG_OPEN_REPARSE_POINT` protects only the last component.
- Someone who can rename entries in the watch folder's parent can swap the folder for a junction after `folder_problem`.
- For the rest of that poll, the listing, reads and moves act on the junction's target:
  - link and oversize `.torrent` entries there are moved on first sight;
  - `added\` and `failed\` are created there;
  - files whose names and shapes match the previous poll are read, and in delete mode deleted.
- The decisions file records only the `added/`/`failed/` junction race (line 44), not this one.
- On Unix this is closed by the fd.

**Fix without `windows-sys` or `unsafe`:**
- Open the folder, `added\` and `failed\` at the start of the poll with `OpenOptions` and `custom_flags(FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT)`, and `share_mode(FILE_SHARE_READ | FILE_SHARE_WRITE)`, so no `FILE_SHARE_DELETE`.
- Check from the handle's metadata that each is a directory and not a reparse point.
- Keep the handles for the whole poll. While they're open, none of the three can be renamed, deleted or replaced by a junction. That also closes the recorded `added/`/`failed/` race.
- Otherwise, record this residual next to the one at line 44 as a §2.19 flag.

### I3. Windows: reparse-point entries aren't moved to `failed/`, despite what the decisions file and guide facts say, and each one takes a stuck slot
**Where:** `crates/lodestar/src/watch.rs:791-793`.

**What happens:**
- `rename_no_replace` refuses any entry whose attributes have a reparse point (`Unsupported`), so the result is `MoveError::Io`: stuck, with a `watch.stuck` line.
- That contradicts decisions lines 47 and 102 ("OneDrive placeholders, deduplicated files … go to `failed/` as `link`"). Line 43 of the same file says the opposite, and that's what the code does.
- Each one takes one of the 1,024 stuck slots for the life of the process.
- Any user can make a directory junction named `*.torrent` without privilege, so 1,024 of them turn the watch off with `too_many_stuck`. That's a small DoS by someone who can already write to the folder.

**Fix:**
- Correct lines 47 and 102 (they're the guide's facts): such files stay where they are and are never read.
- Then either keep them in a separate bounded "left alone" set that doesn't count toward `too_many_stuck`, or accept and record the DoS.

## Optional
- **O1. Stale stuck entries.** A stuck file the user deletes or moves by hand stays in `stuck` until a restart (`retry_stuck` only sees listed names), so `too_many_stuck` can be reached by files that are long gone. When the listing wasn't truncated by `MAX_SCAN` or `MAX_LIST`, drop entries whose names weren't listed.
- **O2. Transient I/O counts as permanent.** An `openat` or read failure other than busy, `ENOENT` or `ELOOP`, such as `EIO`, `ENOTCONN` or `ESTALE` on a flaky share, sends a good file to `failed/<stem>.unreadable.torrent` without judging it (`open_error`, `watch.rs:809-819`). Consider treating network-ish errnos as `Wait` for a bounded number of polls.
- **O3. Blocking filesystem calls on async threads.** `apply` → `Watcher::check` → `folder_problem` (`watch.rs:920`) and `Section::check` during a PATCH run `symlink_metadata` and `canonicalize` on runtime threads. On a hard-hung CIFS or NFS mount that pins a worker. The decisions file says nothing blocks the runtime. Move `apply`'s check into `spawn_blocking`.
- **O4. `too_many_stuck` "until the setting changes".** `inherit` carries `halted` over when only `after` changes (`watch.rs:276`), so only a change of folder (or clearing it) or a restart clears it. Say that in the decisions file and for UP-2.
- **O5. Coverage gaps.**
  - No test pins the `MAX_SCAN` cap itself; `other_entries_dont_hide_a_new_torrent` covers `MAX_LIST` > `MAX_SCAN`.
  - No Windows test of a reparse entry. Junctions need no privilege: `cmd /c mklink /J` in a `cfg(windows)` test.
- **O6. A bind-mount alias of the data directory.** On Unix, `folder_problem` compares canonical paths. Two bind mounts of the same host folder, at `/data` and `/watch`, pass. The data directory holds no `.torrent` files today, so the only effect is `added/` and `failed/` appearing there. Comparing `(st_dev, st_ino)` of the folder against the data directory and its ancestors would close it cheaply.
