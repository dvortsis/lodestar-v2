### I1. X-gluetun-templates-hostfile's note gives `companions_dir_shared` the wrong meaning
- **Where:** the new note text: "the native install uses only a folder the user names (no default beside the data folder) and refuses one shared with Lodestar's data (companions_dir_shared)".
- **What #825 does:** in `crates/lodestar/src/companions.rs`:
  - `NativeError::Data` maps to `inside_data_folder`, which covers a folder that is, holds or sits in the data folder.
  - `NativeError::Shared` maps to `companions_dir_shared`, doc "It, or `gluetun` in it, is another user's or others can write it".
  - The decisions file agrees: "Both folders must be Lodestar's user's (or root's), with no group or other write. Otherwise it refuses with `companions_dir_shared`".
- **Why it matters:** X-gluetun-hostfile-ui maps these codes to user text. A runner note saying `companions_dir_shared` means "overlaps the data folder" would mislead that slice and its reviewer.
- **Fix:** something like "refuses a folder that overlaps the data folder (`inside_data_folder`) and one that another user owns or others can write (`companions_dir_shared`)".

The rest of the note matches #825:
- privdrop's `save_companions_rules` runs as root before `drop_to`, using `openat(O_CREAT|O_EXCL|O_NOFOLLOW)` on a temp file, then fsync, `renameat` and a folder fsync.

- `/companions` and `/companions/gluetun` must be root-owned with no group or other write, checked at start-up and again in the template-time read.

### I2. WK-18w's exit-3 sentence garbles rv-801 N4 and leaves out a refusal case
- **Where:** WK-18w's new note text: "exit 3 also means the folder is in use, so the installer tells the user to check the cluster and the credentials".
- **What main does:** in `crates/lodestar/src/cli/worker.rs` `run_with`, `Failure::Refused` (exit 3, `cli/mod.rs:304`) is returned in three cases:
  1. the folder is a coordinator's data folder (:317);
  2. another `lodestar worker` holds the lock (:326);
  3. the folder has already joined (:356).

  A coordinator rejecting the token is `Failure::Failed` (exit 1).
- **What rv-801 N4 asked:** WK-18w shouldn't read 3 as "joined, carry on" without checking for `cluster\credentials`. That's a check by the installer. The note turns it into advice to the user ("check the cluster and the credentials"), which doesn't fit the "in use" case (stop the running worker) or the coordinator-folder case. That last case is plausible on a machine where a coordinator's `%ProgramData%\Lodestar` was kept.
- **Fix:** something like "exit 3 means refused: already joined, the folder in use by another `lodestar worker`, or a coordinator's folder. The installer never treats 3 as joined without finding `cluster\credentials`, and shows the refusal's stderr message (never a token)".

The rest of the WK-18w note matches main:
- SecureDataFolder before `--join-only`, with the join not run if it failed: `--join-only` doesn't check the ACL itself (WK-18s decisions), and rv-801 I5 asked for this line.
- The service ignores `LODESTAR_TOKEN`, `LODESTAR_TOKEN_IGNORED` and `LODESTAR_JOIN`: `never_joins`, used by `run_until`, returns `None` for exactly those three.
