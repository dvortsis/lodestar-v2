## Findings

### BLOCKING

**B2. While a hand-over is pending, `set_target` can move the target, and the retry then sends the generated password to the new host. This gets round reveal's fresh-password gate.**
- Where:
  - `crates/lodestar/src/companion_wiring.rs:1166-1199`: `set_target` checks `handed_over`, the lock and `not_added`, but not the provenance.
  - `:1277` and `:1323-1329`: the `Held::Pending` retry signs in to whatever `self.target(e)` holds now, using `Origin::Confirmed` and the stored generated password.
  - `finish` then hands over to that target as well.
- How it happens:
  1. A confirm fails after the apply, so the state is `generated` with no `origin` row. Lodestar now holds the password qBittorrent uses, which is the very thing Q5 puts behind `confirm_fresh_password` on reveal.
  2. Anyone with an admin session calls `set_target` with a URL they control. `download_client()` allows public addresses (`net.rs:195`, `Public => true`), and the detector only needs a page that looks like qBittorrent's.
  3. They call `plan`. Lodestar POSTs `username=admin&password=<generated>` to that host.
  4. `confirm` then writes `lodestar-qbittorrent` into Integrations pointing at that host, with the same password.
- Confirmed with a probe test (since reverted): after a refused hand-over, `set_target` to a second fake server answered `Ok`. That server saw one sign-in, which succeeded with the generated password. `confirm` then handed over to it.
- Before this round, plan refused the `generated` state (`no_temporary_password`), so this path is new. It breaks the check in the brief: "the target must be the same validated companion".
- Fix:
  - `set_target` refuses with `409 generated_pending` while the provenance is `generated` (the same one-line check `paste` has at `:1211-1214`).
  - Add a line in `a_failed_hand_over_is_retried_with_the_generated_password` showing `set_target` refused and the target row unchanged.
  - A user whose qBittorrent really did move in that window can reveal the password (password-gated) and forget. That trade-off is fine.
- Pre-existing, not this delta: in the `pasted` state the same `set_target` then `plan` sends the pasted temporary password to a new host. Round 1 accepted that, and that value is the user's own paste and never revealable, so I'm only noting it here.

### LOW

**L5. No test covers the plan echo in the pending retry.**
- Where: `companion_wiring.rs:1325`.
- Mutation M9 (skip `if !echoes(&plan)` on the `Held::Pending` branch) left every test green.
- The guard matters: qBittorrent's state can change between the plan and the confirm, and the confirmation must match what was shown.
- Fix: add a test that changes the fake's save path (or categories) between a pending `plan` and `confirm`, and expects `confirmation_mismatch` with no hand-over.

**L6. The refusal count lives in memory, and a Lodestar restart resets it. The decisions file's reason for that doesn't hold.**
- Where: `companion_wiring.rs:846`, and the decisions file at `docs/decisions/2026-11-09-CMP-5g.md:164`: "so does a restart, since qBittorrent's own count starts again when it restarts too".
- Restarting Lodestar doesn't restart an external qBittorrent. So 3 refusals, a Lodestar restart and 2 more reach qBittorrent's ban at five. The same holds for forget followed by a re-add without restarting qBittorrent, though the `sign_in_refused` message does tell the user to restart qBittorrent first.
- Judgement: acceptable.
  - It needs the admin's own repeated wrong pastes.
  - The ban expires (an hour by default).
  - An attacker without a password can't reset the count: only a successful sign-in, forget (admin) or a restart resets it.
  - It can't lock a user out for good, because forget or a restart clears it.
- Fix: correct the sentence to say that a Lodestar restart resets Lodestar's count but not qBittorrent's.

**L7. L1's busy check is a TOCTOU, but harmless in practice.**
- Where: `companions.rs:572-586` (`lodestar_owned`) and `companion_wiring.rs:923`, both read before the guided lock. CMP-5's install doesn't take the guided lock.
- An install can start right after the check. Its effect is contained:
  - `Inner::begin` refuses `Present` when a credential row already exists (`manager.rs:742-751`), so an install can't start over a guided row.
  - A paste that lands inside the window is overwritten by the install's own `Credentials` step, which comes after the download. The installed companion then reveals its real generated password.
- The decisions file already says this ("the window is one request"). No change needed.
