## Findings

### B1: the multiset MinHash ignores the distinct-size rule, so unrelated split archives share band terms and fill the candidate window

**Where:**
- `crates/classify/src/group.rs:113-131` (`MinHash::of_major`: element `(size, k)` for every copy);
- `crates/api/src/compare.rs:497-519` (`similar_payload`: the newest 1,000 band matches, then `confirmed`).

**What happens:**
- The PR's own refinement notes that unrelated split archives share their volume size. It fixes this on the confirmation side: `similar` needs 3 shared distinct sizes. The signature still hashes every copy.
- Take a scene release: N × 50,000,000-byte volumes, a last part and a sample, which is 3 distinct major sizes, so it's signed. Two unrelated releases share N of about N + 2 elements, a multiset Jaccard of about 0.9. They almost always share a band.
- I reimplemented `group.rs` in Python; it reproduces the golden `[0xfcfebd3a19dd117d, 0xac54f58748e7582b]` exactly. I ran 400 synthetic scene releases: 40-60 × 50,000,000 B parts, a random last part, and a 30-80 MB sample. 196 of them are signed.
  - 64 % of unrelated pairs share a band.
  - One band term is carried by 139 of the 196.
- In a real index, the posting list of that term holds a large share of all scene releases with that volume size.

**Failure scenario:**
1. The user opens Related on a scene release.
2. `torrents_with_minhash_bands` returns the newest 1,000 visible torrents carrying its band terms. Almost all are unrelated releases with the same volume size.
3. `confirmed` reads and decodes 1,000 file trees, one store lock each, and `similar` rejects them all.
4. A genuinely similar torrent older than that window (for example a repack with an extra file) is never examined.
5. The response is `similar_payload: {status: available, hits: [], truncated: false}` and `similar_payload_partial: false`. That's a confident "none" when the index couldn't answer. The brief says never to claim none in that case, and the decisions file says "a missing similar torrent is a miss". Here, though, the miss is systematic for a whole content class, with no signal.
6. Each such request also does the 1,000 tree reads.

The 4 GiB FAT32 game splits and `.7z.001` volumes behave the same way.

The existing tests don't catch it:
- `unrelated_split_archives_are_never_similar` (`crates/classify/tests/group.rs:97-119`) checks only `similar`, never band collisions.
- `unrelated_payloads_never_share_a_band` uses random distinct sizes.

**Suggested fix:**
1. Sign the distinct major sizes: `MinHash::of_major` over `major.dedup()`, or cap `k` at 0. This makes the signature consistent with the distinct-size rule. In the same simulation, the share of unrelated scene pairs sharing a band falls from 64 % to 0.4 %.
   - For payloads of distinct sizes (seasons, packs) nothing changes: set and multiset are equal. The recall rates in `tests/group.rs` hold.
   - The cost: split-archive variants that differ in a non-volume file are found less often. For example, 19 × V + {x, y, z} against 19 × V + {x, y, w} has a set Jaccard of 0.6, so it becomes a candidate about 39 % of the time. Today it's found almost never, beyond the newest 1,000.
   - Confirmation can stay multiset Jaccard plus 3 shared distinct sizes.
2. Re-bless the three goldens. The generation stays 1 because nothing has shipped.
3. Add a band-collision bound to the split-archive corpus test, for example at most 5 % of unrelated pairs share a band.
4. Optional, and the runner's call against GS-1's short-list rule: when `more` is true and the window yields fewer than `MAX_SIBLINGS` hits, set `similar_payload_partial` or `truncated`, so a saturated window is never reported as a complete "none".

### O1: the size number in the PR body and decisions file is a little out of date

- `docs/decisions/2026-11-12-GS-2.md` (Size bullet) and the PR body say 496.0 B per torrent.
- CI's `size budget (§3)` job on this head measured **495.8 B** (PASS ≤ 512), probably after the distinct-size fix reduced the signed share.
- Fix: update the number, and the headroom to 16.2 B, when B1's fix is measured. Both change again then anyway.

### O2: torrents that can never confirm still take window slots

`crates/search/src/doc.rs:244` writes band terms for torrents with `FILES_PARTIAL`. Identical clones also carry the reference's terms. Both always fail confirmation but still take slots in the 1,000-candidate window. Two options:
- skip `group_minhash` when the row has `FILES_PARTIAL`, which changes nothing stored for complete lists;
- add a `MustNot` on the reference's own `payload_sig` term in `torrents_with_minhash_bands`, so clones, which `identical_payload` lists, never fill the window.

This is optional, and secondary to B1.

## Checked and correct
1. **Major-file rule** (`group.rs:76-87`):
   - ≥ 1 MiB and ≥ 1 % of the non-padding total, in u128, so there's no overflow (tested at `u64::MAX`);
   - at most 100 major files, so the per-torrent work is bounded whatever the file count.
2. **Distinct-size threshold** (`distinct`, `shared_distinct`, `similar`): correct on the confirmation side. `shared_distinct` skips every copy on both sides. `similar` is symmetric (proptest). The rule is the runner's accepted Q9 refinement; B1 concerns only the signature's inconsistency with it.
3. **Determinism:**
   - fixed-seed `fmix64`; constant seeds built in a `const` block;
   - no HashMap or random hasher in the producer;
   - the result doesn't depend on order (proptests);
   - goldens pin it, and my independent reimplementation matches them.
4. **Population contract:**
   - `GENERATIONS["group_minhash"] = 1`; `group_key` stays at 0 with a comment;
   - new writes go through `TorrentDoc::new`, the same path the walk uses;
   - `tests/grouping.rs` covers GS-0 → this build, the walk in steps, a crash before commit, the resume from the last commit, Backfilling (not complete) meanwhile, Ready after, and no duplicates;
   - `Missing` for an older schema maps to `needs_group_minhash`, tested through `Serving` with the rebuild held;
   - this matches SB-6 and GS-0's `payload_sig`.
5. **`similar_payload`** (`compare.rs:481-531`):
   - visibility (`shown(Node::All, adult)`) goes inside the index query, before the window;
   - `CancelToken` is checked before the lookup, in the collector (`TopIds`), and per candidate in `confirmed`;
   - B13's `withheld` is applied on stored state (hidden always, Adult unless shown);
   - `FILES_PARTIAL` candidates are dropped in `pre`;
   - identical clones are excluded (`theirs != sizes`);
   - exact multiset Jaccard on the stored sizes;
   - `MAX_SIBLINGS` = 20 with `truncated`, plus `more && full`, as GS-1 does;
   - partial while not Ready.
   - The reference rules run in order: `no_content_files`, `partial_file_list`, `payload_not_specific`, `few_major_files`, `search_disabled`. Signature-less torrents never match each other.
6. **`torrents_with_minhash_bands`** (`index.rs:1848-1897`):
   - mirrors `torrents_with_pieces_roots`;
   - term fan-out is the caller's 2 band terms;
   - the `TopIds` heap is bounded by `limit`, and `more` comes from the heap cut;
   - collection is linear in postings and cancellable;
   - `ABSENT` and empty input answer empty;
   - the new unit test covers the limit (2 → `[3,5]`, true; 3 → `[1,3,5]`, false: no off-by-one), visibility before the limit, cancel and out-of-time.
7. **Tests:**
