## Correctness checks (all OK)
- **Spoofing the flag:** `LODESTAR_RELAUNCH_TOKEN` in the environment can at most make a failing run print a message and wait for one line on its own console. That's no privilege, no injection and no file write. Anyone who controls the environment controls far more already.
- **A second Restart now from a relaunched copy:** it exits through `std::process::exit(EXIT_RELAUNCHED)` (restart.rs:423), which skips the wrapper. So the old copy never prompts on the shared console. Verified.
- **Ctrl+C:** `serve_as` returns `Ok(None)`, so the exit is SUCCESS and nothing waits.
- **Abandoned hand-over:** `wait_if_successor` returns `Some(SUCCESS)`, so nothing waits.
- **The service:** it has no token from the SCM and no console, so `CONIN$` fails and nothing waits. Even a token set machine-wide doesn't wait, because there's still no console.
- **An ordinary run:** no token, so `relaunched` is false and it returns at once. Covered by `an_ordinary_run_that_fails_at_start_exits`.
- **Children:** `lodestar.exe` never respawns itself on Windows except for the relaunch. `system32_command` and msi.rs strip `MARKER` from the tools they run.
- **Companions retry:** bounded by `LOCK_WAIT`, checked against a monotonic `Instant`. The only caller that waits is serve (inside `spawn_blocking`) and the CLI, as documented.
- **Security:** the relaunch arguments are unchanged: `args_os().skip(1)`, no shell. `log_folder` only re-parses argv with clap and reads the config read-only, and `std::path::absolute` doesn't touch the disk. No injection surface.

### LOW
1. **A hidden console can wait forever.** crates/lodestar/src/system/restart.rs:451-454, and the decisions file line 14 ("a detached run").
   - The guard is "`CONIN$` opens". That's false only with no console at all (`DETACHED_PROCESS`, the SCM). A process started with `CREATE_NO_WINDOW`, or by a wrapper that allocates a hidden console (Task Scheduler "run whether user is logged on or not", NSSM's default), has a console, so `CONIN$` opens.
   - Scenario: portable Lodestar auto-started at boot this way. The user clicks Restart now in the UI. The relaunched copy fails at start (the port is still held past `EXIT_LIMIT`, or the config was edited badly). It prints to an invisible console and blocks in `read_line` with no deadline. The process lingers with nobody able to press Enter, where before it exited.
   - Not a service and not a documented setup, so it's LOW. Suggested fix: also require a visible console window (`GetConsoleWindow()` non-null and `IsWindowVisible`), or give the wait a generous deadline (such as 15 min). Either way, correct the decisions file's "a detached run" claim.
2. **It holds on any failure, not only a failure at start.** restart.rs:451 and :497.
   - The brief says "only on a failure at start". The wrapper holds on any non-success exit of a relaunched copy, and always prints "couldn't start again after Restart now".
   - Scenario: a relaunched copy serves for days, then `services.run` returns an error. Or its own later Restart now hand-over fails (main.rs:295 returns `Err("restarting: …")`). The window says Lodestar "couldn't start again after Restart now", which is wrong.
   - Keeping the window open there is arguably useful, so this is LOW. Fix: choose the text by whether the services ever started (`Restart::started` is already set in `Services::start`), or use neutral wording ("Lodestar stopped with an error after Restart now").

### NIT
1. **Two different tests for "relaunched".** restart.rs:357 `relaunched_here` uses `var_os(MARKER).is_some()`, while `wait_if_successor` (windows/mod.rs:250-255) ignores an empty token and a terminal stdin (a hand-run with the variable inherited). A run with `LODESTAR_RELAUNCH_TOKEN=` (empty) counts as relaunched for the hold but not for the hand-over. It's harmless, since it can only wait on an interactive console, but the two should agree: add `.filter(|t| !t.is_empty())`.
2. **The printed log folder can be wrong.** restart.rs:472-478 prints `<data>\logs`, which is only `logging.file_folder`'s default. A user who moved the log folder in Settings, or turned file logging off, is shown a folder that doesn't hold the log. Consider "the log (by default in …)" wording.
3. **Stale field doc.** restart.rs:71-74 says `relaunched` is recorded "early in start: the Windows hook's `set_prepare`". It's now `main`'s first call.
4. **The Unix lock wait isn't pinned.** No test pins the non-Windows `LOCK_WAIT` (manager.rs:988) to zero. Mutating it to 10 s still passes, and only slows `a_second_manager_is_refused_while_one_runs`. A one-line `#[cfg(not(windows))] assert_eq!(LOCK_WAIT, Duration::ZERO)` would cover "one attempt elsewhere". On Windows that integration test now spends about 10 s on the expected Busy. Acceptable.
