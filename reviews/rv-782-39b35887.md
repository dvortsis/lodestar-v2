## Blocking

**B1. 08-add-companions.md:215. The Windows qBittorrent steps leave its web page open to the whole LAN, which breaks safety rule 2 (line 49).**
- qBittorrent's **Web UI** page defaults to **IP address `*`**, so it listens on every network interface.
- The step that would bind it to `127.0.0.1` runs during configuration (`configure/qbittorrent.rs` `webui.bind_address`). That step has no UI yet: the guide marks it (planned) at line 256, and the store never calls `/plan` or `/confirm`.
- So a reader who follows step 3 gets a WebUI reachable from the LAN, guarded only by a password they chose.
- The first start also brings up a Windows Firewall prompt. The guide doesn't mention it, and user-docs §6 requires "firewall prompts get private networks only".

**Fix.** In step 3:
- Set **IP address** to `127.0.0.1` and keep **Port** `8080`.
- Leave **Bypass authentication for clients on localhost** off.
- Use a long, unique password from a password manager.

Add a step: when Windows Firewall asks, allow **Private networks** only (or Cancel, because Lodestar reaches it on `127.0.0.1`).

## Important

**I1. 08-add-companions.md:280-287, 91, 153. Only qBittorrent can be added under "Companions you already run". Prowlarr and gluetun are refused.**
- `companion_wiring.rs:759` sets `HANDED_OVER = "qbittorrent"`.
- `handed_over()` (`:1022-1026`) refuses any other id with `handover_later`. The UI shows **This can't be done yet.**, and `api/src/companions_guided.rs:21` documents it.
- The dropdown still lists every catalogue entry (`CompanionsScreen.svelte:127`).
- Yet 8.3 and 8.4 send every companion to 8.7, and 8.1 (line 34) offers 8.7 as the way around the missing pins.

**Fix.** In 8.7, say plainly that today only qBittorrent can be added. Prowlarr and gluetun answer **This can't be done yet.** (planned). Point Prowlarr users to its source in **Settings → Sources** (Chapter 7) instead. Add a row for that message to 8.8.

**I2. 08-add-companions.md:191-192, 203. The CLI text doesn't match what this build does.**
- Every pin is `null`, so `install` fails in `offer()` → `installable()` (`manager.rs:761-786`) before it shows anything.
- The messages it actually prints:
  - "this release has no pinned build of it for this machine (awaiting_pin)";
  - in a container, the `native_in_container` sentence;
  - for Windows qBittorrent, "on Windows its installer is offered for you to run … (guided_only)".
- It doesn't "still show the version and SHA-256". `not_wired` appears only once a build is pinned.
- `list` also needs Lodestar stopped (`open()` → `StoreLock::acquire`, `cli/companion.rs:129-133`). So `docker exec … companion list` against a running container fails. Only `compose` runs alongside the server.

**Fix.**
- Say that today `install` answers `awaiting_pin`. Once a release pins a build, the CLI still can't start companions (`not_wired`), so install from the app.
- Change "Both commands need Lodestar stopped" to "`list`, `install` and `remove` need Lodestar stopped; `compose` doesn't".

**I3. 08-add-companions.md:168, 66 (and the `cgroups` index tag at 166). The guide overstates how native companions are confined.**
- No cgroup is ever used: `supervise/limits_linux.rs:15-17` reports `cgroup_skipped: not_delegated`.
- On Linux the companion gets rlimits and a Landlock sandbox where the kernel has it.
- On Windows it gets a Job Object, and `limits.rs:20-23` records "sandbox not applied" (`no_safe_wrapper`).
- Native companions run as Lodestar's own account, not "their own low-privilege user". The code refuses to start any companion when Lodestar runs as root or an administrator (`process.rs:309`).

**Fix.**
- Line 168: "Lodestar caps what it can use: a Job Object on Windows; resource limits and, where the kernel supports it, a Landlock sandbox on Linux."
- Line 66: "native companions run as Lodestar's own (non-administrator) account, and Lodestar refuses to start them if it runs as root or an administrator; container companions run as `PUID`/`PGID`."
- Optionally add that on Windows a companion can read Lodestar's data folder.
- Change the `cgroups` index tag to `Landlock`.

**I4. 08-add-companions.md:218 and 311. The qBittorrent version gate can't be reached from the app today.**
- `WindowsQBittorrent` refuses a version only inside configure (plan/confirm). That has no UI, and the guide marks it (planned) at lines 256 and 289.
- Detection and **Add** use the plain detector (`detect/mod.rs:57-60`), so any version is added.
- The guide still tells readers to install an older 5.2.x and blames "That didn't work" on the version.

**Fix.** Drop the 8.8 row. Rewrite line 218 as: "Lodestar is tested with 4.6.0 to 5.2.x; when its set-up step arrives (planned), it will refuse a version outside the range." Don't tell readers to downgrade.

**I5. 08-add-companions.md:73-78, 136. The Unraid network setup will silently disappear.**
- On Unraid, a network made with `docker network create` is deleted when the Docker service restarts, unless **Settings → Docker** (Advanced View) has **Preserve user defined networks** set to **Yes**.
- Step 1 also doesn't say where an Unraid user runs the command.

**Fix.** Add an Unraid note:
- open the terminal (the `>_` icon), run `docker network create lodestar`;
- stop Docker, set **Preserve user defined networks: Yes**, start it again;
- then pick `lodestar` under **Network Type**.

**I6. 08-add-companions.md:146. The Unraid steps lack the warning to keep Lodestar's data folder out.**
- When Lodestar runs in a container (always the case on Unraid), the app builds templates with `DataFolders::none()` (`lodestar/src/companions.rs:1180-1186`), exactly like the CLI.
- So mounting `/mnt/cache/appdata/lodestar`, or a folder inside it, into qBittorrent isn't caught. That folder holds Lodestar's secrets file.
- Line 95 warns about this only for the CLI.

**Fix.** In 8.4 step 4: "Never use Lodestar's own appdata folder (such as `/mnt/cache/appdata/lodestar`) or a folder inside it; Lodestar can't check this from inside its container."

**I7. 08-add-companions.md:260-262, 306. On Docker and Unraid, the guide never says how to reach a companion's own web page.**
- The generated files publish no port. Yet the reader must set qBittorrent's password (configuring a companion you run is planned), add indexers in Prowlarr, and fill in gluetun.
- Row 306 says "open the address in your browser from the Lodestar computer", which a browser can't do for `http://qbittorrent:8080`.

**Fix.** Add a short, safe procedure:
- to open its web page, add a `ports:` entry for the web UI port (for example `8080:8080`), or on Unraid a Port in the template;
- reach it only on your LAN, never forward it (rule 4), and remove the entry when you're done if you don't need it;
- for a companion behind gluetun, publish the port on gluetun instead.

Reword row 306 for containers.
