## How each egress path fares
- **ICMPv4 off the tunnel,** of any type and to any address except this namespace's own: rule 3 drops it ahead of every gluetun accept. Closed. Loopback errors are kept.
- **ICMPv6 off the tunnel:** dropped unless the destination is link-local, local or multicast, or the hop limit is 255.
  - The exemptions are type-agnostic, not limited to 133–137.
  - They can't carry data off the tunnel. Rule 3 only drops, so exempt packets fall through to rule 2 and then gluetun's own rules:
    - a flow that used wg0 is marked, and rule 2 drops it with no exemption;
    - a new echo to a global address meets gluetun's DROP policy;
    - kernel errors use the default hop limit, not 255.
  - What's left is only what gluetun already allows: its Docker or outbound subnets, and the unmarked WireGuard socket.
  - Narrowing to 133–137 would need a user chain, which the decisions file rules out, or a deny list. That isn't worth it (O3).
- **Flows that used the tunnel** (TCP, UDP, ping, DoT): rules 1 and 2 are unchanged and still sit above gluetun's ESTABLISHED accept. Closed.
- **Unaffected:** wg0 traffic, loopback, the web-UI reply path (TCP) and WireGuard's own UDP. The health ping goes into wg0. Side effect, documented: there are no ping replies to the Docker network or LAN.
- **Rule order:** the rules use `-I 1..3`, and gluetun appends its own afterwards. Checked on a real kernel and by the new IPv6 unit test.
- **The veth judgement after 613f8498** counts only frames with the container's source MAC.
  - The container's own kernel can't send anything else.
  - Forging a source MAC needs CAP_NET_RAW in the namespace. In the phases only gluetun's root has it: the probes and the flow run `--cap-drop ALL`, and the ifdown probe adds only NET_ADMIN.
  - Anything forged that the host forwards out of the host still hits the `-i $bridge -o $egress` counter, which ignores MACs. A forged frame can hide only from the veth view, and only if it never leaves the host.
  - gluetun is attached only to the stack's default network, so there is no second veth or bridge to leak through.
  - `-Q in` would make the direction kernel-attributed rather than MAC-attributed (O7).
- **Host rules in user docs:** none tell users to add a host or DOCKER-USER rule. The decisions file keeps "offer a host-side guard?" as an owner question, never asked of an Unraid user. That's consistent with the runner's recommendation.

## Blocking
- **B1** `infra/fleet/steps/vm/leak-test.sh:111-137` and decisions `:37`: the guard drops in FORWARD, but after a recreate the endpoint's packets go to the host's INPUT. Run 1's packet most likely came from the host's own stack, which the guard never sees.
  - **Why.** Docker deletes every conntrack entry that names the container's IP, both when the old endpoint leaves (`RevokeExternalConnectivity`, `bridge_linux.go:1503-1506`) and when the new one joins (`:1466-1468`; `purgeConntrackState` uses `ConntrackNatAnyIP`).
  - **Failure scenario:**
    1. After the flush, the PIA server keeps relaying the old session to the host's mapped port. These are remote retransmits of the flows that were open, and they can go on for tens of seconds.
    2. With no conntrack and no DNAT rule, those packets go to host INPUT, never FORWARD.
    3. The host's own kernel answers with ICMP port-unreachable from its public address, unless the host's INPUT policy silently drops them.
  - **What that packet looks like.** It is exactly run 1's single "NATed" ICMP to the endpoint, seen on eth0 but not on the bridge or veth.
  - **Why it escapes.** The DOCKER-USER guard never sees it, nor does the leak test's counter (`-i $bridge`) or the veth capture. Its timing has nothing to do with the post-rules, so the measured ~320 ms gap is a coincidence of the recreate, not its cause.
  - **The decisions file's account is also wrong.** It says the endpoint "keeps sending to the address it knew, the kernel's port unreachable goes back NATed". After the flush, no NAT state can steer an unsolicited packet into the new container.
  - **The re-run can't settle it.** Runs 2 and 3 already read 0 without the guard, so a 0 there proves nothing about it.
  - **Fix:**
    - Hold a host INPUT drop for the endpoint's unsolicited UDP from just before the first `compose up` until `cleanup`:
      - `iptables -I INPUT 1 -s $ep_ip/32 -p udp --sport $ep_port -m comment --comment lodestar-leak-host -j DROP`
      - or `-I OUTPUT 1 -d $ep_ip/32 -p icmp -j DROP` for the host's own ICMP to the endpoint.
    - Either one never touches the tunnel: the new session's replies are de-NATed and forwarded, never delivered locally. It hides nothing the test judges either, because the container's traffic never crosses host INPUT or OUTPUT. It can therefore stay up for the whole run.
    - Keep the DOCKER-USER guard as it is; it is cheap, and it covers the old container's shutdown.
    - Give the new rule the same removal discipline as in O2.
    - Correct decisions `:37` and the `tunnel_up` comment to describe the host-stack path.
    - Add a stub test: the rule is in place before the first `compose up` and gone after `cleanup` on every failure path.
  - **To confirm from existing evidence:** if run 1's bridge or veth capture doesn't show the packet, but eth0 does, it was host-originated.
