## Security / untrusted input
- **Unchanged and still sound:**
  - Pages are capped at 2 MiB before parsing.
  - At most 100 results are kept per page and 4,096 per poll. `take_one` uses a CAS and never wraps.
  - There are no new unwraps on input.
  - The API key is only in a header, and fixture requests assert no key in a URL. No new log lines or error strings were added.
- **Retry-After isn't parsed by the plugin.** The shared limiter caps it at `MAX_RETRY_AFTER` (24 h).
- **The retry loop is bounded:**
  - one request per indexer per round;
  - rounds are paced by the 15-minute poll gate;
  - at most 48 counted hits per indexer in any 24 h;
  - no sleeps in the plugin.
- **`tokio::time::Instant::duration_since` saturates,** so the clock arithmetic can't panic.
- **The std `MutexGuard`s are temporaries.** They're dropped before every `.await`: the guard in the `if` condition, and the guard in the statement after `emit_usenet(..).await?`. Clippy's `await_holding_lock` is clean.
- **L3:** nothing new sets `external_ref` or keeps a link. `UsenetFind::into_found` and `store_claims` are untouched. The new fixture's links and enclosures, which carry fake keys, are dropped by the existing `to_usenet`.
- **Tests:** no fixed sleeps. The new integration test uses `start_paused` and the existing `wait_for` deadlines. The unit test uses explicit instants, which act as a fake clock.
- **Fixtures** are deterministic: an unordered replayer with an exact request count. The `+0000` values are RFC 822 feed data.

## Findings

### Blocking
1. **The budget-cut retry, brief item 1's third bullet, has no test.** Location: `crates/sources-plugins/src/prowlarr.rs:720-721`, with the test gap at `tests/prowlarr_usenet.rs:556`.
   - Standards §"Blocking" lists "a missing test for new behaviour".
   - The change from `break` to `return Ok(false)` is what makes results that a page cut short "come back on the next poll". No test reaches it on a second round.
   - `a_poll_emits_at_most_its_cap` runs one round only, and it asserts `1 + 42` requests either way.
   - **Failure scenario:** someone restores `break` (or `Ok(true)`). Every test still passes, and an indexer whose page was cut at item 96 waits an hour, dropping its remaining results on a busy indexer. That is the rv-762 nit 1 regression this slice exists to fix.
   - **Fix:** extend `a_poll_emits_at_most_its_cap`, or add a sibling test.
     - Set `agents` to 1 so the order is deterministic.
     - Add a second round: a list, then exchanges for only the indexers not fully sent (41 and 42).
     - Assert the request count, and that their results arrive on the second round while indexers 1–40 aren't asked.

### Important
1. **Successful polls drift to about every 75 minutes, not hourly.** Location: `prowlarr.rs:684` (`done(.., Instant::now())` after the response) together with `prowlarr.rs:151` (`< USENET_POLL_EVERY`).
   - `done` is stamped after the request's gate, the RTT and every `emit().await`, which can wait on channel backpressure.
   - The `take` four rounds later happens at about the same offset into its round as the previous `take`. The list gate opens every 15 minutes exactly, from gate time.
   - So `now - done` is about 60 min minus (RTT + emit time), which is under 60 min. The indexer is skipped and asked at 75 minutes: about 19 polls a day, not 24.
   - Under paused time the replayer's latency is 0, so `usenet_indexers_are_polled_hourly_and_torrent_ones_as_before` can't see this.
   - **Wrong claims:** the decisions file says "Only then does it wait `USENET_POLL_EVERY` (an hour)", and the PR says "Successful polls still come hourly". Both are wrong in practice.
   - **Effect:** indexers posting more than 100 an hour lose more results. Quota isn't affected.
   - The old code was knife-edge at exactly 60 minutes. This change biases it towards 75 minutes.
   - **Fix:** pass the instant `take` granted into `done`, and compare with a slack under one round. For example, due when `elapsed >= USENET_POLL_EVERY - min_poll_interval / 2`. Rounds are 15 minutes apart, so the next eligible round is still about 60 minutes on. If drift matters, keep the daily cap on successful polls too.
2. **An indexer polled after the poll's 4,096 is gone spends an API hit for nothing, now up to 4 times an hour.** Location: `prowlarr.rs:667-672` (`take`, then the request) with `prowlarr.rs:720`.
   - When `usenet_left` is already 0, the indexer is still `take`n and requested. `emit_usenet` then returns `Ok(false)` without emitting anything, so it isn't marked done and is asked again next round.
   - **Scenario:** 60 busy Usenet indexers.
     - Each round, about 20 of them pay a request and get nothing.
     - In steady state, every indexer runs close to the 48-a-day cap, where before it would have used 24. About half of those hits are wasted.
     - That's the user's daily indexer quota, shared with Sonarr and Radarr. The brief's item 4 calls it out as the thing to protect.
   - **Fix:** before `take`, skip the indexer when `self.usenet_left.load(Relaxed) == 0`. Return `Ok(())`, with no hit counted and no request sent; it's asked next round. A race between the two agents costs at most one request. Add it to the Blocking 1 test: indexer 42 isn't requested in round 1.

### Optional
1. **`prowlarr.rs:132`: the doc's "At most [`MAX_INDEXERS`] entries" isn't true.** Entries now live up to 24 h, and the bound is per list, not per day. A manager whose usenet ids change between lists (churn, or a hostile or buggy reply) can leave up to 96 × 500 entries. `take` retains over all of them on every call, so the cost is O(entries) per indexer per round.
   - It's still bounded: tens of thousands of small entries.
   - **Fix:** correct the doc, or cap the map. For example, refuse to `take` an id that's new when the map is over `MAX_INDEXERS` and still full after pruning.
2. **Hits are counted for requests that are never sent.** Location: `prowlarr.rs:667-672`.
   - The hit is counted before `http.poll`. When the unit is `Blocked`, after a 429 or 503 with `Retry-After` of up to 24 h, `gate_poll` returns `HttpError::Blocked` without sending.
   - Each round still counts a hit. A 12 h block fills all 48, and the indexer then waits up to 12 h more after the block lifts.
   - This errs on the side of quota. Either record the hit only when a request was sent, or note it in the decisions file.
3. **Stale docs:**
   - `prowlarr.rs:118`: `USENET_POLL_EVERY` still says "hourly, 24 API hits a day". With retries, it's up to 48.
   - `unverified.rs:179`: the `dropped` doc says "on a stored torrent", but the field now also counts non-core usenet hits, and BitTorrent hits with no stored torrent.
   - `prowlarr.rs:113-114` and `206-209`: the added doc lines are re-flowed unevenly (one line of 96 characters beside short ones). This is cosmetic.
4. **`crates/pipeline/src/lib.rs:1556-1561`: `claimable` was inserted between `intake`'s doc comment and `async fn intake`.**
   - `intake` loses its doc, and `claimable`'s doc now starts with "The built-in worker claims key by key…".
   - **Fix:** move `claimable` (and its doc) above the `/// The worker's intake` block.
   - The test checks only the predicate. A test that sends a usenet find down `io.retry` and asserts `refused`, with no coordinator claim, would pin the wiring. This isn't required by the brief.
5. **Process:** the PR says no self-review was run. The steward skill (step 4) asks for a one-line self-review summary in the description.
