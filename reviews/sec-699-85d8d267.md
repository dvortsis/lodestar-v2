# Security review: PR #699 (WK-11, the worker spool) at 85d8d267

**Verdict: FINDINGS. Three are Low and none block the merge.** There is nothing High or Medium. The seal, the bounded decoder, the coordinator's Q7 refusal, secure deletion and the no-peer-address rule all hold. The three findings are hardening of the spool's file handling. Each one needs an attacker who can already write inside the worker's data folder. That attacker can already delete or corrupt everything in it, and under every shipped package such a write gains nothing outside that folder. They are worth fixing because the repo already sets these defences for the credentials file, and the Windows data-folder check exists to prevent this kind of planted link.

## Findings

### L1: secure removal follows symlinks, so a planted link zeroes its target (Low)
- **Where:**
  - `crates/pipeline/src/spool.rs:649-674` (`secure_remove`);
  - its callers in `Spool::open`, `:720` (any `<16hex>.tmp`) and `:731` (any `<16hex>.lsp` whose header isn't this worker's);
  - `write_atomic`, `:680-685` (`create(true).truncate(true)` on `<seq>.tmp`).
- **Attack path:** someone who can create entries in `<data>/spool` (or replace `<data>/spool` itself) plants `0000000000000001.tmp -> /some/file`. At the next start, `Spool::open` calls `secure_remove`. It opens the path with `OpenOptions::write`, which follows the link, overwrites the target with zeros for its full length, syncs it, then unlinks only the link.
  - A link named `<16hex>.lsp` gets the same treatment, since its "header" never decodes as ours.
  - `write_atomic` would likewise truncate and write through a planted `<seq>.tmp` link.
- **Probe:** a link to a file outside the spool folder left that file all zeros after `Spool::open` (`victim after open: [0, 0, …]`).
- **Impact:** any file the worker's user can write gets destroyed.
  - **Docker:** no privilege is gained. The process drops to PUID and every file it can write is in `/data`.
  - **systemd:** no privilege is gained. The state folder is 0700 under `DynamicUser`.
  - **Windows:** mostly covered. The private data-folder check refuses reparse points at start.
  - **Where it matters:** a hand-run worker whose data folder other users can write.
- **Fix:**
  - In `secure_remove`, check `fs::symlink_metadata` first. Unlink a link or any non-regular file without opening it, and overwrite only a regular file. Where possible, open with `O_NOFOLLOW` (`custom_flags(libc::O_NOFOLLOW)` on Unix).
  - In `write_atomic`, remove any leftover temp file and then open with `create_new(true)`, as `Credentials::save` does (`crates/cluster/src/worker.rs:224-236`).

### L2: spool folder and segments use the umask's default modes (0755 and 0644), not 0700 and 0600 (Low)
- **Where:**
  - `crates/pipeline/src/spool.rs:707` (`create_dir_all`) and `:680` (`write_atomic`'s open);
  - `crates/lodestar/src/worker/spool.rs:66` (`create_dir_all`).
- **Probe:** with umask 022, the folder came out 755 and the segment file 644.
- **Path:** another local account, or anything that can read the bind-mounted appdata folder, can list and read every segment.
- **Impact:** little, because every record is sealed under `secrets.key`, which is 0600 with a restricted ACL. What leaks is metadata: how many batches the worker spooled offline, their sizes and the segments' creation times (the header isn't encrypted).
  - The precedent differs. The sealed credentials file is created 0600 (`crates/cluster/src/worker.rs:236`).
  - systemd's `UMask=0077` and the private Windows data folder hide this in those packages. Docker's default umask does not.
- **Fix:** create the folder with `DirBuilderExt::mode(0o700)` and open segments and temp files with `OpenOptionsExt::mode(0o600)` on Unix. That is the same pattern as `Credentials::save` and `secret.rs:557`. Windows inherits the private data folder's ACL, so it needs nothing more.

### L3: any file name in the folder can push `next_seq` to `u64::MAX` (Low)
- **Where:** `crates/pipeline/src/spool.rs:714-718` and `:859`.
- **The cause:**
  - `next_seq = max(seq + 1)` is taken from **any** entry whose stem is 16 hex digits, whatever its extension (`ffffffffffffffff.x` counts).
  - `saturating_add` pins it at `u64::MAX`.
  - In `start_segment`, `self.next_seq += 1` then overflows.
- **Probe:** the test profile panicked with `attempt to add with overflow` at `spool.rs:859`.
- **Impact by build:**
  - **Release** (overflow checks off): the counter wraps to 0. The next segments are 0, 1, 2…
    - A wrapped `start_segment(1)` renames `0000000000000001.tmp` over a live, unreplayed `0000000000000001.lsp`, so its records are lost silently.
    - Replay order is also scrambled, because `u64::MAX` sorts last.
  - **Debug:** every append panics on the blocking thread. The batches stay in memory and are counted as errors.
- **Attacker:** someone who can write the data folder. The impact is losing data, not gaining access.
- **Fix:**
  - Count only `.lsp` and `.tmp` names toward `next_seq`.
  - Use `checked_add` and refuse (or reset) at `u64::MAX`.
  - Make `write_atomic`'s final step refuse an existing target outside reseal. For example, use `create_new` on the temp file and check the target is absent when called from `start_segment`.

## Notes (no finding)
- **Frame order and count inside a segment aren't authenticated.** The seal binds the worker and the segment: the context is `worker-spool/v1:<worker>:<seq>`, and the associated data is the seal header + 0xFF + context. It doesn't bind a frame's index or the number of frames.
  - A folder writer can duplicate, drop or reorder frames within one segment. The probe confirmed a duplicated frame opens twice.
  - This can't be exploited. A replay is idempotent on the coordinator (by token, WK-9), the age is inside the seal, and dropping frames is no more than deleting the file.
  - Adding the frame index to the context would make the decisions file's claims fully accurate. It's optional.
- **The header isn't authenticated.** Its sum is fixed-key SipHash, and the decisions file says so plainly.
  - A forged `created` can only make `is_expired` drop a segment. That's equivalent to deleting it.
  - A forged worker or seq can't open frames, because the seal context binds both.
  - The record's `at` (the age cap) is inside the seal. The purge cut-off uses the coordinator's `lease.discovered_at`, never a time the worker gives.
- **Sequence numbers are reused after the spool empties.** `next_seq` restarts at 1, so an old copy of segment 1 opens again under the same key. This is harmless: the age cap is sealed, and the coordinator ignores tokens it has already committed.

## What I checked
1. **The decoders** (`spool.rs` `Record::decode`, `Header::decode`, `decode_segment`, `count_frames`, `read_capped`):
   - every length is checked against what's left and its cap (`MAX_FRAME` 1 MiB, `MAX_LEASES`, `MAX_PAYLOAD`, `MAX_PLAIN`) before any allocation;
   - `n * LEASE_LEN` can't overflow (n ≤ 1024);
   - `Cursor` never panics, `expect`s only follow length checks, and the zero-tail `all()` scan short-circuits;
   - segment reads are capped at 9 MiB, and a 200 MiB sparse segment read and reopened stayed bounded.
   - The fields of a record are trusted only after `open` succeeds (AEAD), and the sum is never the only check on a record. `needs_reseal`'s cap (`SEGMENT_BYTES + 2·MAX_FRAME`) differs from `read_capped`'s, but only a segment no writer can produce would see the difference.
2. **Sealing** (`secret.rs` `seal_bytes` and `open_bytes`):
   - XChaCha20-Poly1305 with a random 192-bit nonce from `getrandom` per seal;
   - same key ids as `seal`, so `rotate`, `retire_old_keys` and `needs_reseal` work unchanged;
   - the 0xFF separator gives real domain separation from text seals, since a UTF-8 `&str` can't start with 0xFF;
   - sizes are checked before `split_at` (`from_bytes` sets a minimum length, `open_bytes` a maximum).
   - Plaintext stays in `Zeroizing`, and `Record`'s `Debug` shows sizes only. Nothing in the spool code logs.
   - No key or plaintext goes to disk or a temp file. The WK-8 wire key is never touched: spooled payloads are the wire-sealed bytes.
3. **Rotate-key reseal** (`worker/mod.rs`): each segment's rewrite is atomic (temp, sync, rename).
   - The retire happens only after `needs_reseal` is false. A crash mid-reseal leaves both keys in `secrets.key` and every segment readable, and the leftover `.tmp` is securely removed at the next open.
   - When the worker hasn't joined, there's no spool reseal and the old key is retired. A spool left in that state is unusable anyway.
4. **§2.17 secure deletion:** `remove`, `drop_expired`, foreign or damaged segments and leftover temp files all go through overwrite, sync, close, unlink.
   - The reseal's rename-over leaves the old blocks unzeroed, and the decisions file says so.
   - The decisions file describes the SSD, copy-on-write and snapshot, Windows VSS and MFT, and `data=journal` limits accurately.
5. **No peer addresses:** a `Record` holds exactly kind, batch, at, leases (key and token) and the payload.
   - The wire `Results` payload is post-judge, so the worker's drop has already run (wkq1).
   - `no_peer_address_reaches_the_spool` grants a lease with a peer hint and searches the raw segment, the record plaintext and each wire-opened record for the IP and the IP/port in several encodings. It would fail if a field carrying the peer were added.
6. **Coordinator** (`remote.rs` `take`):
   - `refuses_late` is now checked before the epoch split, so a refused worker's results are refused whatever the epoch;
   - purge uses the coordinator's `discovered_at` (current epoch) or its prior record (late);
   - a revoked worker can't open a session, and a spool from an earlier worker id (re-enrolment) is dropped by the worker, and wouldn't open anyway;
   - nothing in a record is applied before the refusal.
   - `requeue_back` acts only on a lease the sender holds under its current token, and puts it at the back. That's no more than a `Drained` outcome already allows, so it can't starve or poison the queue. In production it can't run yet: `NoStanding` is used until WK-13.
   - Pre-existing and unchanged: clear or unopenable records from any worker still end their own lease as `Invalid`.
7. **Denial of service:**
   - Disk is capped at 1 GB, and hitting the cap pauses fetching, then resumes at half the cap.
   - Memory holds one segment (≤ 9 MiB) during replay.
   - A coordinator that keeps answering `accepted: false` holds only the current segment. A trusted coordinator can stall a worker any number of ways anyway.
   - Unreadable or unremovable segments are set aside, so they don't wedge replay.
8. **Supply chain:**
   - No `Cargo.toml` or `Cargo.lock` changes outside `fuzz/`, which adds only a `[[bin]]`.
   - `siphasher =1.0.4` was already a pinned dependency of the pipeline.
   - The `lodestar` package's dependencies are untouched, so no tokio `test-util` or `testing` feature was added.
