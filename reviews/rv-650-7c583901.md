## Findings

### 1. LOW (correctness, regression from the lock-first order). A retry that exits 21 after a lost first attempt gets one clean check, not the polled one
- **Where:** `infra/pia-bridge/deliver.py:351`, `lost = rc in (255, 256)`. Only the last attempt's code counts.
- **Failure path (I reproduced it with a stub SSH: 255, then 21).**
  1. The first session starts the remote bootstrap, then drops with 255 (ServerAlive) inside the 120 s retry window. The orphan holds the VM's lock and is in its cloud-init wait (up to 480 s) or its step.
  2. The retry's bootstrap waits only `FLOCK_WAIT` = 180 s for the lock, then exits 21. Before this round, the retry ran its own cloud-init wait first, then needed only the orphan's step (≤ 150 s < 180 s), so it usually got the lock and delivered. With the lock first, a retry behind an orphan that is still in the cloud-init wait now often exits 21.
  3. Because 21 isn't "lost", `_clean(wait=False)` makes one check. The orphan holds the lock, so it reports "another delivery is still running there; /run NOT clean; escalate", and the job fails.
  4. Meanwhile the orphan finishes. It writes `wg0.conf` and its trap clears `/run`.
- **Result:** fail closed, but it's a false "NOT clean" escalation and an undelivered report on a path the round meant to handle (a lost session). It also contradicts the decisions file's "After a lost session … it polls for up to 11 minutes".
- **Fix:**
  - Track any 255 in the retry loop, for example `lost_any |= rc == 255` inside the loop.
  - Set `lost = lost_any or rc in (255, 256, BUSY_VM)`. Exit 21 means another holder exists, so polling is right for it too.
  - It still fits the budget: 125 s + 180 s + 730 s.
  - Add a `test_deliver` case: SSH returns 255, then 21, and the clean checks return 1, 1, 0. Assert one line ending "/run clean" and that the clean check was polled.

### 2. LOW (correctness, docs and test). The "job's own bounds fit inside that timeout" sum leaves out terms, so the real worst case can pass 30 minutes
- **Where:**
  - `infra/pia-bridge/tests/test_deliver.py:428` (`worst = SSH_TIMEOUT + CLEAN_WAIT_SECONDS + SSH_ATTEMPTS_SECONDS + 120` = 1,770 s, under 1,800 s);
  - `docs/decisions/2026-11-09-OP-2b.md:25`.
- **What the sum leaves out:**
  - **The retry sleep.** The last 255 can come at about 119 s. After the 5 s sleep (`deliver.py:348`), one more session runs for up to 870 s. That's 995 s, not 990 s.
  - **The clean poll's overrun.** The poll checks its deadline only after each attempt (`:364-367`). The last attempt can start just before 660 s and itself take the 60 s SSH timeout, after a 10 s sleep. That's up to 730 s, not 660 s.
  - **Everything that isn't SSH, inside the "120 s" allowance:**
    - job setup: checkout with `fetch-depth: 0`, and pip;
    - the OIDC, STS, S3 and Secrets Manager ×2 calls, each up to 3 × (10 + 30) s under `apply.AWS_CALL`;
    - checkip and `/meta` (30 s each);
    - per firewall, the reads, the sweep lookups and the puts;
    - the close's reads and puts.
- **Failure path.** A late 255, a session that drops near its end, a long clean poll, and a few slow API calls add up to more than 1,800 s. GitHub then cancels the job.
  - The cancel arrives while `pool.map` is waiting on an SSH subprocess, so `close_rules` and the report lines in the `finally` most likely don't run.
  - The job rule stays open until the hourly sweep, and the channel gets no report.
  - pia-release still runs (`always()`), and the lease still covers the job (finding 1 of the last round is fixed), so the lock is safe. This costs availability and leaves a rule open until the sweep. It isn't a containment or secret issue.
- **Fix, either of these:**
  - **(a) A job-level deadline.** Take the job's start in `deliver()`, set `deadline = start + DELIVER_JOB_MINUTES·60 - close_margin`, and clamp each SSH timeout and the clean poll's deadline to it. That makes the sum true by construction. Then test the clamp, not the sum.
  - **(b) Keep the code, but make the test count every term:** `SSH_ATTEMPTS_SECONDS + 5 + SSH_TIMEOUT + CLEAN_WAIT_SECONDS + 10 + 60`, plus an explicit pre-SSH and close budget. Shrink `CLEAN_WAIT_SECONDS`'s margin, or `CLOUD_INIT_WAIT`, until it fits. Reword line 25 so it doesn't say the bounds fit when the test omits terms.

## Nits
- **N1. `CLEAN_WAIT_SECONDS` has no test tying it to the orphan's bound.** Setting it back to `FLOCK_WAIT + 20` passes every test. Add `assertGreaterEqual(CLEAN_WAIT_SECONDS, CLOUD_INIT_WAIT + STEP_TIMEOUT)`. That's the property the decisions file claims ("the orphan's full bound").
- **N2. `test_a_lost_answer_is_ours_only_for_a_live_run_holder` doesn't isolate `kind == "run"`** (`infra/fleet/tests/test_lock.py:67-75`).
  - The reaping marker's body is built by `lock._body(...)` when the tuple is evaluated, at the clock's T0, so it expires at T0 + 90 min. The subtest then advances the clock 91 minutes, so `_ours` rejects the marker for being expired, not for its kind.
  - Dropping `holder.kind == "run"` survives.
  - **Fix:** build the `after` body inside the subtest after `self.clock.sleep(...)`, for example with a lambda. Or give it an explicit future `expires_at`.
- **N3. deliver-pia now follows act's mode too**, so setting `FLEET_LIVE=false` mid-chain no longer turns a delivery already in progress into a dry run. The last review said deliver-pia could keep the variable. `OPERATOR_STOP` is still checked in deliver-pia's `if:` and is the documented stop, so this is fine. The decisions file could say in one clause that `OPERATOR_STOP`, not `FLEET_LIVE`, is the mid-chain brake.
- **N4. A small race in the clean check (theoretical).** After a 255 on both the first attempt and the retry, a polling `flock -n` can land between two orphans' holds (one releases, the next waiting one hasn't acquired yet) and read clean. That needs two dropped sessions in one window. Finding 1's fix makes it rarer, and OP-3's leak test re-checks anyway.
