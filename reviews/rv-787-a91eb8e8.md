## What holds
- **Total and bounded:**
  - No `unwrap` or `expect` touches untrusted data. Every index is guarded: `b[i]` with `i < len`, `&p[3..]` after `p.get(..3)`, and slices taken with `get`.
  - Every cap is enforced as the parse reads, not afterwards: bytes, depth, values, posts, text, and 16 torrents per post.
  - `skip` is iterative.
  - The magnet scan is linear. `i` moves past each magnet it reads, the dedup check is at most 16 entries, and `dn` runs only for kept torrents.
- **Typing:**
  - `post.id`, `nsfw`, `removed`, `deleted` and `community.nsfw` are required, and the flags must be JSON booleans.
  - A wrong type spoils the post, and unknown fields are skipped unread.
- **Identity:**
  - Keys come only from `common::magnet_hashes`: v1 as 40 hex or 32 base32 characters, v2 as `btmh:1220` plus 64 hex, and all-zero hashes are refused.
  - `dn` is used only as a name, never for identity.
  - An `http(s)` `.torrent` link counts as `no_hash`, and nothing is fetched. The parser has no I/O.
- **Adult:**
  - `adult` is `post.nsfw || community.nsfw`, and both flags must be present. Plain repeats of the flags are OR-ed in, and a repeated `post`, `community` or `creator` object spoils the post.
  - The parser never drops the flag: LEM-1 maps it to the `content-type:adult` claim that ADH-0 reads (plan Q-o4).
  - This holds for every input except B1.
- **Removed and deleted posts** are skipped and counted apart from faults. A removed or deleted community skips its posts too, which is narrower than the plan and recorded in the decisions file.
- **Fuzz entry:** the `fuzz/Cargo.toml` `[[bin]]` entry is correct, and `fuzz/Cargo.lock` is unchanged.
- **Scope:** only the owned paths changed, plus the two allowed shared lines and the decisions file.
- **Hygiene:**
  - No model identifiers.
  - No fixed sleeps.
  - Every date is a UTC `Z` timestamp. The one zoneless date is a negative test input.
  - Fixtures use `lemmy.example` and patterned hashes.

## Blocking

**B1. A flag key written with an escape gets past the nsfw and removal rules.**
- **Where:** `crates/sources-feeds/src/lemmy.rs:316-336`, the `post()` key loop, and `:343-349`, `part()`.
- **The cause:** keys are compared as written, still escaped (`json.rs`), so `"nsfw"` and `"removed"` fall through to `_ => skip`.
- **What I saw** (probes with the key built at run time):
  - `{"post":{…"nsfw":false,…,"nsfw":true},"community":{"nsfw":false}}` is kept with `adult: false`.
  - `{"post":{…"removed":false,…,"removed":true},…}` is kept, with `removed` at 0.
  - The same applies to `"post"`, `"community"` and a community's `"nsfw"`. These get past the repeated-object rule that a91eb8e8 added for exactly this reason.
- **Why it blocks:**
  - Any reader that unescapes keys and keeps the last one would read nsfw and removed as `true`. That includes `JSON.parse` in lemmy-ui and serde_json's `Value`.
  - So a post that the instance's own UI shows as NSFW or removed comes out here as non-adult, or as kept. That breaks the PR's own invariant: "a repeated flag can only add a restriction".
  - It's the bug class the runner already closed for ThePornDB and StashDB in `docs/decisions/2026-11-05-X-enr-page-flag.md` (#511 review): "any key containing a backslash … skips it as malformed … A real server never escapes an ASCII key name, so this fails closed at no cost."
  - In practice only the polled instance can write such keys, and it could send `nsfw:false` anyway. Still, this is a content-safety flag, the house rule exists, and the fix costs nothing.
- **Fix:**
  - Follow the tpdb and stashdb pattern. In both closures, before the `match k`, add `if k.contains('\\') { d.spoil(Bad::Malformed); return p.j.skip().map(drop); }`. In `post()`, `d` is the draft. In `part()`, put the check in `self.object(|p, k| …)` before calling `field`.
  - The removal-wins check runs before `bad`. An escaped `removed` leaves `removed == Some(false)`, so the post is skipped as `malformed` and fails closed.
- **Tests:**
  - Add tests for an escaped `nsfw` (post and community), `removed`, `deleted`, `post` and `community`, each in both orders.
  - Build the backslash at run time, for example `format!("nsf{}u0077", '\\')`, as X-enr-page-flag says. A heredoc in this review decoded `w` silently and nearly hid the bug.
  - Add a line under "Adult" in `docs/decisions/2026-11-12-LEM-0.md:17-18`.

## Important

**I1. The fuzz target has no seed corpus.**
- **Where:** `fuzz/fuzz_targets/lemmy.rs`. There is no `fuzz/seeds/lemmy/`.
- **Why it matters:**
  - The CI `fuzz` job runs for 60 s from an empty corpus. Random bytes seldom reach `posts → post → nsfw`.
  - Sibling JSON targets ship seeds: `archive_org/`, `stashdb/` and `tpdb/`.
  - The brief doesn't own `fuzz/seeds/lemmy/**`, so this is the runner's call. It isn't the author's fault.
- **Fix:** ask the runner for the path. Then add three or four seeds built from the test fixtures:
  - a mixed page with a url magnet, body magnets and v2;
  - an nsfw post, a community-nsfw post and a removed post;
  - the `{"error":"rate_limit_error"}` answer;
  - a page with `next_page`.

## Optional

- **O1.** `lemmy.rs:550` / `Magnets::add`: a prose label such as `Magnet: see below` sets `seen` and counts the post as `bad_hash` rather than `no_hash`, which skews LEM-1's health counts. Set `seen` only when the candidate holds `?`, or when `magnet_hashes` finds an `xt=`.
- **O2.** `lemmy.rs:355`: `newest_id` takes any valid id up to `u64::MAX`, and my probe moved it to u64::MAX. That's correct for a pure parser, but LEM-1's "clamped cursor" should bound how far one page can move the cursor. Add it to the LEM-1 brief.
- **O3.** The `newest_id` wording disagrees with itself:
  - The decisions file says "A malformed post … never moves it", but a removed post with a bad field does move it, by design (`removed_wins_over_other_faults` asserts `newest_id == Some(5)`).
  - The `Page::newest_id` doc says "read whole".
  - Fix: say "sound, or cleanly removed" in both places.
- **O4.** `tests/lemmy.rs:442-467`, `posts_round_trip`, randomises only `post.nsfw`. Add `community.nsfw` and an OR of the two, so the property covers the whole content-safety mapping. It could also assert that `adult` agrees with the generated flags in `check`, for posts built by the generator.
- **O5.** `lemmy.rs:304-309`: after `Stop::Items`, nothing later at the root is read, such as `next_page` or `error`. tpdb reads past its item cap (`the_rest_is_read_past_the_item_cap`). Lemmy caps `limit` at 50, so it's harmless. If you keep it, document it.
- **O6.** Fixture names, `tests/lemmy.rs:29-30, 50`: `linux` / `Linux ISOs` matches a real community name on many live instances, though the domain here is `lemmy.example`. The brief asks for invented data, so use something like `example_isos`.
- **O7.** `lemmy.rs:664`: `id(<a 23-digit literal>)` is a 23-digit literal, which falls under the "no 12-digit-or-longer numbers" hygiene rule. Use `format!("{}0", u64::MAX)` to make the overflow plain.
