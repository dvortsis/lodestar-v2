## Blocking

1. **The floating tray covers the Settings save bar's Save button, so a mouse user with a pending restart cannot save other edits, and keyboard focus on Save is hidden (WCAG 2.4.11).**
   - The tray is `fixed; bottom: 16px; z-index: 40`, and on ≥ 640 px it sits on the right at up to 32 rem wide (`web/src/lib/features/restart/RestartBanner.svelte:100-121`).
   - The save bar is `sticky bottom-0 z-10`, with Discard and Save at its right end (`web/src/lib/features/settings/form/SaveBar.svelte:51,75-80`). Its focus-in handler (`SaveBar.svelte:22-36`) scrolls fields clear of the bar only, not of the taller tray.
   - Nothing adds bottom padding or `scroll-padding-bottom` for the tray.
   - Reproduced with a scratch spec (deleted): SettingsBackend on `/settings/crawler`, two pending fields, one radio changed.
     - At 1366 × 800: tray at y 718–784, x 895–1350; Save at y 752–792, x 902–1024.
     - At 390 × 800: tray at y 710–784, full width; Save at y 752–792.
     - At both widths `elementFromPoint` at Save's centre returns the tray ("2 changes apply after a restart … Review").
     - A real `page.mouse.click` at Save's centre sent 0 PATCHes. Save is reachable only after scrolling to the very end of the page, where the sticky bar settles above the tray.
   - Scenario: the user saves a restart-required field, the banner appears within 15 s, and every later edit on any Settings screen needs Ctrl+S or a scroll to the end to save. Keyboard focus on Save is fully hidden behind the tray (2.4.11 AA).
   - The toaster has the same problem: it is `fixed bottom-4 z-50` on the right (`web/src/lib/ui/feedback/Toaster.svelte:143`), so the "Saved" toast lands on the tray right when the banner first appears.
   - The e2e test checks the heading but nothing at the bottom of the page.
   - Fix options:
     - lift the tray above the save bar while it shows (or render the restart line inside the save-bar area);
     - reserve its height with `scroll-padding-bottom`, a bottom spacer, and the SaveBar's clearance logic;
     - stack it with the toaster.
   - Add an e2e assertion that Save is hit-testable (elementFromPoint, or `mouse.click` with a PATCH) while the tray shows, at 390 and 1366.

2. **"Keep this address?" puts a ticking countdown inside a polite live region, so a screen reader hears the prompt again every second for up to 5 minutes.**
   - `AddressPrompt.svelte:62-66` renders the countdown inside the shared `Banner` with `kind="warning"`. `Banner.svelte:32` gives that `role="status"`, which implies `aria-live="polite"` and `aria-atomic="true"`. The Keep and Go back buttons are inside the same region.
   - `AddressPrompt.svelte:21-24` updates `now` every 1 s.
   - Verified in e2e (scratch): the countdown's closest live ancestor is `role="status"`, and its text changed from "Going back in 5:00" to "4:59" within the poll.
   - This contradicts brief item 5 ("announced politely once") and makes the 5-minute window very hard to use with a screen reader, which is exactly when the user has to find Keep.
   - Fix options:
     - render the prompt in a container that is not a live region;
     - give the per-second countdown `aria-hidden="true"`, with an sr-only line that changes only at whole minutes or the last 30 s;
     - announce the prompt once through the watch's region.
   - Add a test that no live region's text changes on a 1 s tick.

## Important

3. **The watch's live region is rewritten on every `/system` refresh, not only "when the pending count changes" as the decisions file and the code comment say.**
   - `watch.svelte.ts:49-53` sets `live.textContent = countText(pending)` each time the effect re-runs. `restart.pending` is a getter that builds a new object from each `/system` response (`restart.svelte.ts:16-18`), so the effect runs on every refresh: every 15 s on Settings, on focus, and on each route change.
   - Verified (scratch e2e with a MutationObserver): 3 refreshes caused 3 mutations of the region with identical text.
   - Replacing the text node can re-announce in some screen-reader and browser pairs. The guarantee the PR states isn't held, and no test checks it.
   - Fix: `if (live.textContent !== text) live.textContent = text;`, and a test that a second identical `/system` causes no mutation.

4. **The keep-or-revert countdown and the automatic hand-over run on the browser's clock against the server's deadline.**
   - `flow.ts:39` computes `ceil(deadline - Date.now()/1000)` with the client's `Date.now()` (`AddressPrompt.svelte:16,19,22`).
   - At 0 the prompt hands over to the Restarting page on the old address (`AddressPrompt.svelte:35-37`). That hides the tray (`RestartBanner.svelte:53`), and the user can no longer press Keep.
   - Scenario: with a browser clock 5 or more minutes ahead of the server (an unsynced PC or NAS), the prompt hands over the moment it loads. The user can never keep the new address, and the Restarting page waits for the new address to go down, which happens only at the server's deadline. A smaller skew shortens or lengthens the window by the same amount.
   - `deadline: null` in `awaiting_confirmation` also counts as 0. The backend sets it at bind, so that case is theoretical.
   - Fix options:
     - derive the offset from the `/system` response's `Date` header;
     - have the server send seconds remaining;
     - at 0:00, refresh `/system` and hand over only once the server reports `reverted` or stops answering.

5. **The vitest condition waits are capped by vitest's default 5 s test timeout, so their 10–15 s deadlines aren't real.**
   - `watch.test.ts`, `RestartingPage.test.ts`, `RestartBanner.test.ts` and `ReviewList.test.ts` use `waitFor(…, { timeout: 10_000 | 15_000 })`, but no `vi.setConfig({ testTimeout })`. The repo config sets none.
   - My mutation run showed the watch test failing at 5005 ms, not 15 s.
   - runner/standards.md §2 asks for a deadline of at least 10 s that holds on the slowest runner. Other specs set `vi.setConfig({ testTimeout: 30_000 })` (e.g. `src/lib/features/companions/NeedChip.test.ts:12`).
   - Fix: one line per file.

## Nits

6. **Stale decisions bullet.** `docs/decisions/2026-11-11-X-restart-banner.md:14` still says "After the restart the page probes the new origin's `/healthz` (an opaque `no-cors` answer is enough)". That contradicts the "never probed" bullet above it and the code.
7. **Stale comment.** `web/src/lib/features/restart/logic.ts:1-3` says it is "all of the feature a Settings first view carries (with the banner and the store)". The banner is no longer in any first view.
8. **Duplicate line.** `watch.svelte.ts:34-35` sets `data-testid` twice (`dataset.testid` and `setAttribute`).
9. **No client-side scheme check.** The target URL isn't checked for `http:`/`https:` (`RestartingPage.svelte:24-26`, `flow.ts:11-22`). It is safe today, because the server only emits `http://` and `javascript:`/`data:` bases throw in `new URL('/settings', …)`. But a non-hierarchical value crashes the page's `$derived` instead of showing the link fallback. A one-line `protocol` check would make it explicit.
10. **The prompt can be up to 30 s late on the new address.** After the one-shot navigation, the prompt appears only after the first interaction or 30 s, because the chrome (and with it the watch) is engaged lazily. That is acceptable within the 5-minute window, but the decisions file could say it for the address case.
11. **The tray is unlabelled and last in the tab order.** It is a plain `div` appended last in `<body>`. Keyboard users reach Restart now only after the whole page, and screen-reader users have no landmark to jump to. `role="region"` with `aria-label` (and Review's existing label) would help. The pill links to `/settings`, so this isn't blocking.
12. **The give-up test's time budget is tight.** `restart.routes.test.ts:129-137` polls with `timeout: 30_000` inside Playwright's default 30 s test timeout, after `go` and `engage` (≤ 15 s). Under load the test timeout can fire first. `test.setTimeout(60_000)` would make it consistent. It passed 3/3 here.
