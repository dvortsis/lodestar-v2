# Delta review: PR #717 (RX-0), head 4a37e94b, since bfbdb9a6

**Scope.** One commit, five files: `crates/search/src/regex.rs`, `crates/search/tests/regex_plan.rs`, `docs/decisions/2026-11-11-RX-0.md`, `fuzz/seeds/regex_plan/seed13` and `seed14`. Nothing else changed.

**Result.** B2 is closed: every pattern in its table is now refused or accepted once, at 2–8 ms. Depth accounting is balanced and saturating, and nothing panics.

**What remains.** The new "audited by search" claim is wrong. The codepoint charge treats every codepoint as equally expensive, but folding a codepoint inside the case-fold table costs about 5 times the average codepoint of `\p{Any}`. As a result, plain and nested in-table ranges reach 40–63 ms, against the documented worst of 9 ms.

**Machine.** All timings are release builds, best of 3 to 7 runs, on a 4-core container. On this machine the documented baseline, `\p{Any}\p{Any}`, measures 10.4–13.1 ms.

## Blocking

### B3. In-table ranges cost about 5 times their charge; the worst accepted pattern is 54–63 ms, not 9 ms, and the decisions file says otherwise

**Where**
- `crates/search/src/regex.rs:527-530`: `ClassSetItem::Range` is charged its width × (depth + 1), whatever the range covers.
- `crates/search/src/regex.rs:380-382` (`in_bracket`).
- `docs/decisions/2026-11-11-RX-0.md:37`.
- `crates/search/tests/regex_plan.rs:292-294`.

**Cause.** This is regex-syntax 0.8.11, `hir/mod.rs:1290-1305` and `unicode.rs`, `SimpleCaseFolder`:
- `ClassUnicodeRange::case_fold_simple` skips a range that holds no fold key.
- Otherwise it walks every codepoint in the range. Inside the table span (U+0041–U+1E943), most codepoints miss the `next` cursor and pay a binary search, about 23 ns each.
- Past the last key, a codepoint costs about 2–3 ns.
- So `\p{Any}` (1.1M codepoints, of which 125k are in the table) folds in 5.3 ms, while `[\x{41}-\x{1E943}]` (125k codepoints, all in the table) folds in 2.9 ms. Per codepoint charged, the in-table range is about 5 times as expensive.
- Nesting makes it worse. Each level re-folds when an unfolded item joins: a literal push clears `folded` (interval.rs:118), and `case_fold_simple` re-runs (interval.rs:143). The real folds approach the (depth + 1) charge as depth grows.

**Measured** (all accepted; the next repetition is refused with `ClassTooLarge`):

| Pattern | Time |
|---|---|
| `[[[[[[[[\x{41}-\x{1E943}]a]a]a]a]a]a]a]` × 2 (78 bytes) | **54.4 ms** best of 7; 63.3 ms in another run |
| `[[[[[[[\x{41}-\x{A7FF}]a]a]a]a]a]a]` × 7 | 53.8 ms |
| `[[[[\x{41}-\x{FFFF}]a]a]a]` × 7 | 57.9 ms (best of 3) |
| `[[[[[\x{0}-\x{1FFFF}]a]a]a]a]` × 3 | 43.9 ms |
| `[\x{80}-\x{FFFF}]` × 19 (flat, no nesting) | 40.5 ms |
| `[\x{41}-\x{1E943}]` × 9 (flat) | 36.1 ms |
| `\p{Any}\p{Any}` (the documented worst) | 10.4 ms |

**Effect on the budget.**
- RX-1's `regex` compile re-parses and re-folds, so the end-to-end cost is about 110–125 ms of CPU.
- That fits §3's 500 ms regex p95, which is why this isn't catastrophic like B2.
- It is still about 5 times the recorded bound and over the ~50 ms the review was asked to hunt for.

**Why the audit missed it.** My own small randomized search (28,000 accepted patterns) found the 40 ms flat `[\x{80}-\x{FFFF}]`×19 shape in its top results. The decisions file says the author's search found "nothing slower than that baseline", which suggests its leaves held no wide in-table ranges.

**Fix.** The runner chooses one:
1. **Recalibrate.** Weight the in-table part of a range (its overlap with U+0041–U+1E943) by about 5, and leave the rest at 1, for `ClassSetItem::Range`. For measured class items, do the same only for ranges that actually contain a fold key, or `\pL` loses most of its allowance:
   - `\pL` has 70,260 codepoints in the table, but its key-free ranges are skipped, so it folds in 168 µs.
   - Weighting all of them would cut `\pL` from 17 per pattern to about 5, and `[\p{L}\p{N}]` to 1.
   - Then re-measure, and add `[\x{80}-\x{FFFF}]` × N and the depth-8 nested range to the I1 table as rows that one more step refuses.
2. **Accept the cost and record it truthfully.** If the runner accepts about 55 ms (about 5 times the baseline, within §3):
   - correct `docs/decisions/2026-11-11-RX-0.md:37` and `regex_plan.rs:292-294` to the measured worst;
   - add the shape above to the I1 table, so a later loosening shows up.

Either way, the sentence "found nothing slower than that baseline" has to go: it is a wrong value in a decisions record (`runner/standards.md` lists "a wrong value" as blocking).

## Important

### I3. The full-scalar charge is badly calibrated in the other direction too; ordinary idioms are refused
**Where:** `regex.rs:371-374` (negated item = 1,112,064 × (depth + 1)) and `regex.rs:558-564` (each set op = 1,112,064 × (depth + 1)).

**Measured** (one occurrence is accepted; the stated real cost is that one occurrence):

| Pattern | Real cost | Result |
|---|---|---|
| `[\W_]` (the usual "separator" idiom) | 39 µs | charged 2.2M, so allowed once |
| `S\d\d[\W_]E\d\d[\W_]` | | refused, `regex_class_too_large` |
| `[^\W_]+[\W_]+[^\W_]+` | | refused |
| `[^\W]` | 39 µs | allowed once |
| `[\w--\d]` (word minus digit, a common Rust-regex idiom) | cheap: `\pL`-sized folds | refused outright (max = 0) |
| `[\pL&&\p{Greek}]` | cheap | refused outright |
| `[\pL~~\pN]` | cheap | refused outright |
| `[[:^alpha:][:^digit:]]` | | refused |

**Why the charge is too high:**
- Most of `\W`'s large ranges hold no fold key or lie past the table, so folding them is skipped.
- `[[:^alpha:]]` is already marked folded after `hir_ascii_unicode_class` (translate.rs:1057; negate keeps the flag), so the bracket never re-folds it.
- A set op's result is folded (both operands are folded at translate.rs:627, and `intersect`/`difference` keep the flag), so the op itself adds no fold beyond its operands.

**Docs:** the decisions file (line 35) says only that "a set operation with a negated operand is refused outright". In fact any set op whose operands are wider than about 290k charged codepoints is refused, `[\w--\d]` included. At minimum, state that.

**Better:** the fold-key-aware model in B3.1 would allow these, and it also fixes B3.

**Checked and fine:** the ordinary patterns the brief lists all pass. See Verified.

## Nits

- **N5, the "three bare ones" claim.** `regex.rs:376-379` and the decisions file, line 32, say "measured: a `\p{Any}` one bracket deep costs about three bare ones", and that each enclosing bracket "folds its whole set again".
  - Measured: `[\p{Any}]` takes 8.0 ms against about 5.3–6.5 ms for a bare `\p{Any}`, about 1.2–1.5 times, not 3.
  - A bracket re-folds only when an unfolded item has joined (interval.rs:143). `[[\p{L}]]` folds once.
  - The multiplier is conservative, so only the wording is wrong.
- **N6, standalone Perl classes.** `docs/decisions/2026-11-11-RX-0.md:31` says a standalone negated Perl class "counts the codepoints of its complement, which is exactly what gets folded for a class outside brackets". A standalone `\W`, `\D` or `\S` is never folded (translate.rs:1093, "We needn't apply case folding here"). Only `\P{…}` folds its complement. This over-charges, which is fine, but the sentence is wrong. Line 31 also ends with a trailing space.
- **N7, comment line length.** `regex_plan.rs:294`: the doc comment line runs past 100 columns ("…found none slower); the bound is generous enough for an"). Rewrap it when the text changes for B3.

  Every refusal returns in under 15 µs.
- **Depth balance.** pre/post pairs match. regex-syntax's `ast/visitor.rs` calls `visit_class_set_item_pre`/`_post` for every `ClassInduct::Item`, binary-op operands included.
  - `[[a]\x{0}-\x{10FFFF}]`, `[[[a]]\x{0}-\x{10FFFF}]`, `[[a][b][c]\x{0}-\x{10FFFF}]` and `[\x{0}-\x{10FFFF}][[a]]` are all accepted, which shows the depth is back at 1 after each nested bracket.
  - `[[a]]\p{Any}\p{Any}` is accepted (11.4 ms). Standalone classes use `named_class`, which never reads `brackets`.
  - `[[[a]--[b]]]` is refused, as a depth-2 set op should be (3.3M).
- **Off-by-one.** A nested `[^…]` is charged at its parent's depth before the increment (`regex.rs:540-549`). Its own items are charged one level deeper. That matches the translator: the parent folds the negated child.
- **Arithmetic.** `saturating_mul`/`saturating_add` are used in `leaf` and `in_bracket`, and `saturating_sub` on exit. The `brackets += 1` is bounded by the parser's nest limit: depth 10 or more is refused with `TooDeep`. No panics in about 30,000 random bracket shapes.
- **Flags.** `(?-i:[\S])`, `(?-i:[\D])x` and `(?i)(?-i:[\D])(?i:x)` are each accepted once at under 10 µs. The charge ignores the flag, which is conservative.
- **ASCII.** `[[:^alpha:]]` is accepted once (2.8 µs), `[^[:^word:]]` once, and `[[:word:]]` 51 times before the length limit.
