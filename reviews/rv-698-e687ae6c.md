# Review: PR #698 (CMP-9b), head e687ae6c

## Verdict: CHANGES

There is one Blocking finding, a missing test for new behaviour (runner/standards.md §5 severity). Both fixes are cheap. Everything else the brief asks for holds up.

## Blocking

**B1. The re-check loop's stop conditions have no test.** The code is at `web/src/lib/features/companions/NeedChip.svelte:33-36` and `:42-51`. `NeedChip.test.ts` has no test for either one.
- Three mutations each left all 11 tests green:
  - (a) delete `gone = true; clearTimeout(timer);` from onDestroy;
  - (b) drop the `gone` check, giving `if (left === 0)`;
  - (c) drop the one-minute cap, giving `if (gone)`.
- The code is correct today. But the decisions file promises two things:
  - "every 3 s, up to a minute";
  - the loop stops when the chip goes, after which Set up comes back.
- **Failure scenario:** a later edit drops the cap or the unmount guard, and CI stays green. Then one of two things happens:
  - a companion that never turns healthy shows "X is starting. Checking again." forever and never gives Set up back;
  - after the chip clears, the screen keeps sending `GET /sources` every 3 s.
- **Fix:** the `recheckMs` prop exists for this, but no test uses it.
  - Render `NeedChip` directly with `recheckMs` set to a few ms and `oninstalled` as a `vi.fn()`, using the same mockFetch offer and install as the other tests.
  - Cap test: wait for 21 calls, then for `companion-need-setup` to come back.
  - Unmount test: unmount while in the starting state, then use fake timers and advance them, or poll a separate counter under a deadline, and assert that the call count doesn't change.

## Important

**I1. If the SetupFlow chunk fails to load, Set up spins forever and can't be pressed again.**
- `NeedChip.svelte:55` sets `loading = true` before the `{#await import('./SetupFlow.svelte')}` at `:85`, and that block has no `{:catch}`.
- Only SetupFlow's `onMount` (`SetupFlow.svelte:145`) ever clears `loading`. Both `if (loading) return` at `:54` and Button's own `loading` ignore further clicks.
- **Scenario:** Lodestar is upgraded while a Sources tab stays open, so the old chunk hash returns 404. The user presses Set up and gets a spinner with no message, which only a page reload clears.
- The same screen already handles this: `SourcesScreen.show()` catches the import and sets `problem = m.sources_error_network()`.
- **Fix:** add a `{:catch}` that sets `loading = false` and shows that sentence, or a plain-words one of its own.
- The same gap exists, less harmfully, at `SourceRow.svelte:138`. If the chip's chunk fails, the row shows nothing about the need.

## Nits

- **N1. Focus moves even if the user has moved on.** This is at `NeedChip.svelte:97-99`.
  - After a dialog is closed mid-install, the user may tab to another row and keep working.
  - When the install succeeds minutes later, focus jumps to this row's heading.
  - Suggest moving focus only when `document.activeElement` is `body` or still inside the chip.
- **N2. The polling ignores hidden tabs.** This is at `NeedChip.svelte:47`.
  - It's bounded at 20 GETs over a minute, after an action the user started. CMP-9a's `store.watch` behaves the same way.
  - The code base has a pattern for this (`JobsScreen.svelte:85-88`, `live.svelte.ts:75`). Optional.
- **N3. Two guards are redundant, and the tests don't exercise them.**
  - Removing `|| busy` (`SetupFlow.svelte:149`) or `if (loading) return` (`NeedChip.svelte:54`) keeps every test green, because Button's `loading` already ignores clicks.
  - The double-press test at `NeedChip.test.ts:93-96` says it covers the busy guard, but it actually tests Button's guard. Keeping both guards is fine; the comment overstates what the test covers.
- **N4. The keyboard test doesn't use the keyboard.**
  - `NeedChip.test.ts:151-165` opens the dialog with `fireEvent.click`, not Enter or Space, and closes it with Cancel, not Escape.
  - `:183-184` sends Escape and then clicks Cancel, so the test can't show which one closed the dialog.
  - I checked with a throwaway probe test:
    - Escape alone closes the dialog;
    - focus returns to Set up, in both the idle and the mid-install path;
    - a later refusal still shows;
    - the scroll lock is released after a successful install.
  - A test for "Escape, then focus back on Set up" would pin this down.
- **N5. `logic.ts:7-15` hard-codes catalogue display names.** The server already sends these in the offer and in `Companion.name`. A companion added to the catalogue later would read "Needs a companion program" until this map is updated. That's acceptable for now: the Sources DTO carries only the id.
- **N6. SourceRow changes more than one mount line.** Besides the lazy chip block, `SourceRow.svelte` gets:
  - an `onrefresh` prop;
  - a reformatted destructure;
  - `tabindex="-1"` and `bind:this` on the h3.

  The decisions file records these as runner-approved and they're needed for the focus target. Noting them for the record only.

## Checked and OK

- **Install request.**
  - The body is exactly `{version, sha256}` from the server's offer. It goes through CMP-9a's unchanged `store.install`, the same call the Companions screen makes, to the path `offer.id`.
  - The test asserts the exact body.
  - There are no changes in `settings/companions/`, and its tests are green.
- **Refusals in plain words.** Both the offer and the install go through `failureWords`, and the tests assert the raw code is absent.
- **Dialog closed mid-install.**
  - It stays mounted, Set up shows `aria-busy`, and no second POST is sent.
  - A refusal shows in a Banner with role alert.
  - Pressing Set up again remounts with `{#key attempt}` and reads a fresh offer.
- **The starting state.**
  - It shows when the next read still reports the need, with no Set up.
  - It re-reads every 3 s, up to 20 times, using a `setTimeout` chain rather than an interval. It's cleared on destroy and re-checks `gone` after each await.
  - The rows are keyed by `s.id`, so the chip keeps its state across reads.
- **The live region.** The screen's `role=status` gets "X is installed. Checking the source again." and keeps it after the chip is gone.
- **Messages.** All 7 keys exist in both en and zh, every one is used, and zh matches CMP-9a's terms (设置, 配套组件). `messages: ok (3754 en, 3754 zh)`.
- **Tokens and layout.**
  - No hex and no arbitrary values (`check-bans: ok`).
  - Spacing uses `gap-2`, which is on the ramp.
  - Badge adds the status icon, so status is never colour alone.
- **Runes.** Usage is fine: `$props`, `$state` and `$derived`, with non-reactive flags kept as plain `let`.
- **Lazy loading.** In the Vite manifest, `NeedChip` and `SetupFlow` are dynamic entries only. `SourcesScreen`'s chunk lists `NeedChip` under `dynamicImports`, and no chunk imports `NeedChip` or `SetupFlow` statically.
- **Waits in tests.** There are no fixed sleeps; every wait is a `waitFor` with a deadline of 10 s or more (15 s for the starting test).
