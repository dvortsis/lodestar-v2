## Should-fix (non-blocking; fix here if cheap, otherwise put it in ENR-terms-ui's or the next terms brief)
- **Make the reader-equivalence test exhaustive instead of sampled.** `crates/search/tests/enrichment.rs:530-555` (from ENR-11, not this PR) runs 64 proptest cases through a real store. Because `record_redistributes` (`crates/store/src/identify_sweep.rs:99`) is a pure byte check, a pure test could cover every version byte × flags byte × lengths 9–11, with a few `secs` values, against `Terms::from_record(v).map(|t| t.redistribute)`, and check the round trip `record_redistributes(&t.record()) == t.redistribute`. That takes milliseconds and catches every drift on every run. Today a drift in the narrow cases (a new flag bit, or a stricter `from_record` such as rejecting `secs == 0`) is caught only by chance. See the §2.19 judgment below.
- **Hardening: governed-by-build as well as governed-by-record.** `terms_closed` (`crates/api/src/torrents.rs:524-545`) treats a non-answer claims row as governed only when its source has a terms record. If a lookup plugin's `record_terms` failed (`stats.unrecorded`), and that plugin were also a finder, its finder claim would reach a public caller. No plugin on main is both: every `impl Identifier` in `sources-plugins` is lookup-only, and every identification carries `match_confidence` (`crates/sources/src/identify.rs:190`), so its rows are already governed as answers. No public route reaches the detail today either. Checking `catalogue::terms(plugin).is_some()` too, for example as a `has_terms` flag on `PluginName`, would make unknown terms fail closed in that case as well.

## §2.19 judgment (the `Store::redistributes` reader instead of `identify::may_redistribute`)
**Acceptable.**
- It is the same reader ENR-11 already uses for search, Torznab and export (`served_identifications`, `identify_sweep.rs:150`), so the detail view and the index can't disagree.
- `lodestar-api` keeps `lodestar-pipeline` as a dev-dependency only (`crates/api/Cargo.toml:44`).
- Any plausible drift is in the safe direction. `record_redistributes` accepts only version 1, exactly 8 trailing bytes, no unknown flag bits and bit 1 set. A new flag, a new version or a longer record all read as *not* redistributable, which only hides answers. The leaky direction needs `from_record` to become stricter within version 1 while the store reader doesn't.
- The existing test runs in CI (`cargo test --workspace`). It is meaningful but sampled: its `(0..8, any u64)` branch covers the flag space well, but not every special `secs` value or unknown-bit combination. The new unit tests (`torrents.rs:1703` `record`) also check `may_redistribute` agrees after each `record_terms`.
- The should-fix above closes the gap. It isn't a merge condition.
