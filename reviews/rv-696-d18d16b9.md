# Review: PR #696 (PK-cli), head d18d16b9882c36813db13060f523a5f28e0f44ee

## Verdict: MERGE

I found nothing blocking and nothing important. The slice does everything the brief asks. The five findings below are all nits, and none needs to be fixed before merge.

## Checked and found correct

- **Same rules as the API, no second copy.** The command copies the store's `settings.` rows into an in-memory store and loads the real `settings::Registry` over that copy. It then saves through `SettingsApi::save`, the same call `PATCH /settings` makes (`api/src/settings.rs:415`). Section `check`s never read the store, so validating against the copy gives the API's answer: types, ranges, `check`, `confirm`, `SECRET_ENDPOINTS`, revisions and sealing. Error text comes from `ApiError::from(SettingsError)`. Only the rows that changed are written back, in one transaction on the locked connection (`settings.rs:247-271`, `322-347`). `Registry::commit` writes only `settings.` rows, so the write-back loses nothing.
- **Stopped store, no race.** `StoreLock::acquire` sets `locking_mode=EXCLUSIVE` and `journal_mode=DELETE`, which fails while any connection is open (readers included). The lock is held from `Offline::open` until `finish` or `release`, so a `serve` started in the meantime can't open the store. `get` takes the same lock. I checked by hand: `settings get` while `serve` was running exited 3 with "open in another process". `refuse_during_update_rollback` runs first and covers `bin/rollback.json` (and the portable journal on Windows).
- **Secrets.**
  - `set` refuses any `writeOnly` field (whole field or a list item's key) before the value is parsed (`settings.rs:526-534`).
  - `get` can't print a secret. The registry's `redact` already returns `null` for a secret field and strips item secret keys, and `shown()` prints `(set)` or `(not set)`.
  - Nothing in the command path prints `SettingsArgs` with `Debug`. `SettingsError::Store` is shown generically.
- **Refusal lists match the code.**
  - `the_refused_fields` pins 7 secret fields and 7 privacy fields to the registry's own schema, and they match the decisions file. No field is tagged `security` today.
  - Adult content is refused through the registry's own `NeedsConfirmation` ("adult_confirmation_required"), exit 3. Turning an adult field off is allowed.
  - `content.confirm_adult` and `if_revision` can't be smuggled in: they aren't field names, and `field()` resolves only real fields.
- **The runner's accepted points are implemented as stated.**
  - Privacy fields are refused whatever the value (`settings.rs:543`).
  - Secrets are refused outright, with no stdin path.
  - `reset --all` also removes saved rows that an environment variable hides; the test uses `LODESTAR_DHT_PORT`, and "Reset 5 saved values" counts it.
  - `cli/worker.rs` is untouched.
- **keep_or_revert.** The command deletes `system.keep_or_revert.http_bind` in the same transaction, after a `set` or `reset` of `network.http_bind` that goes through, and after every `reset --all`. That is exactly what `Address::keep` does (`persist(None)`). A unit test ties the key to what `address::health_bind` reads. A refused change and a change to another field both leave the record alone (tested).
- **Untrusted input.**
  - The value from argv is parsed as JSON or taken as text, then type-checked and normalized by the section (`object(&section)`) before it is stored, so nothing can be injected into stored config.
  - Odd names are echoed with `{:?}`, which escapes U+202E as `\u{202e}` (tried).
  - Control and C1 characters in string values are refused by the registry's own checks (tried on `email_username`, `email_host`, `email_from`, `time_zone`).
  - Floats and out-of-range integers get the API's message, exit 2 (tried).
  - The `expect()`s and the `&k[KEY_PREFIX.len()..]` slice can't fire: the keys are filtered by the ASCII prefix, and every listed field has a value.
  - A non-text row fails with exit 1 instead of panicking.
- **Privilege drop.** `Command::Settings` runs under `privdrop::Scope::DataDir` (`main.rs:101-102`), and `settings_run_as_puid` checks file ownership after `get`, `set` and `reset --all` (it ran here as root).
- **Exit codes.** 3 for refusals, 2 for bad names or values (and clap's own errors), 1 for no store or a failed save. These match `AFTER_HELP`.
- **Windows.**
  - `Bin::check` on Windows only rejects reparse points, so the test's `bin/` folder doesn't make later commands refuse.
  - `StoreLock` is the same code that vacuum, reindex and the other offline commands already use on Windows.
  - The PUID test is `cfg(unix)`.
- **Hygiene.**
  - Only the owned files plus the decisions file changed.
  - Nothing in `Cargo.toml` changed, so there's no tokio `test-util` or `testing` feature.
  - There are no sleeps and no waits in the tests.

### Nit

1. **A new danger kind would be allowed by default.**
   - Where: `crates/lodestar/src/cli/settings.rs:535-551`.
   - What happens: `set` refuses `security` and `privacy` and allows every other `x-danger` value. `Danger::Destructive` ("it can't be undone") already exists in the vocabulary, though no field uses it yet.
   - Failure scenario: a later slice tags a field `.danger(Danger::Destructive)`, for example a purge switch. `lodestar settings set` would then apply it without the UI's dialog, and no test would fail, because `the_refused_fields` only pins the privacy and security lists.
   - Fix: allow only `None` and `Some("disruptive")` and refuse anything else, or add `destructive` to the pinned lists.
2. **The `security` arm is never exercised.**
   - Where: `crates/lodestar/src/cli/settings.rs:536`.
   - What happens: no field is tagged `security`, so no test reaches that branch. When I changed it to `Some("security-mut")`, all 5 integration tests and the unit tests still passed.
   - Effect: today this is only a latent gap. `the_refused_fields` would fail as soon as a security field is added, which prompts a look.
   - Fix: move the refusal decision into `fn refusal_for(&Meta) -> Option<Stop>` and unit-test it with synthetic `Meta`s for `security`, `privacy`, `destructive` and secret.
3. **A reset can say "nothing changed" when the store did change.**
   - Where: `crates/lodestar/src/cli/settings.rs:620-633`, and similarly `set` at `589-591`.
   - What happens: `reset network.http_bind` with nothing saved, but with a pending record, prints "wasn't saved; nothing changed." and then "The pending HTTP address change is settled". The record was deleted, so the store did change.
   - Effect: the operator gets two contradictory lines. It is harmless.
4. **An address set with the CLI gets no bind-failure fallback.**
   - What happens: a `network.http_bind` set by the CLI writes no `awaiting_restart` record. A mistyped but well-formed address that can't be bound (for example a LAN IP the host doesn't have) therefore makes `serve` fail at start. The UI path instead reverts at once (`address::prepare`). The environment variable behaves the same way as the CLI.
   - Effect: this follows from the recorded design (the operator at the machine confirms), and `settings reset network.http_bind` is the way out.
   - Suggestion: PK-ops should mention it in "I can't reach the UI".
5. **The decisions file heading still says "(PR pending)".**
   - Where: `docs/decisions/2026-11-11-PK-cli.md:1`.
   - Fix: change it to `(PR #696)`.

- Secrets reach stdout and stderr only as `(set)` or `(not set)` and item ids.
- Log events carry field names only.
- Stored values are normalized by the section before they are saved.
- The exclusive SQLite lock prevents concurrent writers, including a server that starts mid-command.
- Commands run as PUID/PGID.
- I found no exploitable issue.
