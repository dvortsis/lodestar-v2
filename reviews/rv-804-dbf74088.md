## Findings

### O1: a common size with at most 2 copies can still gather one band term, now bounded and signalled

**Where:** `crates/classify/src/group.rs:197` (`MAX_COPIES = 2`) and `:202` (`signed_sizes`).

**Evidence:** I reimplemented the new signer in Python (`rv804b_sim.py` in the scratchpad). It reproduces the goldens exactly. I ran 2,000-release corpora:

| Corpus | Pairs sharing a band | Top band term carries |
|---|---|---|
| 2 × 50,000,000 B volumes + last part + sample | 0.21 % | 4.2 % of the class |
| 2 × (4 GiB − 1) FAT32 parts + remainder + 1 other file | 1.6 % | **12.7 %** of the class |
| The same with 2 other files | 0.14 % | 3.8 % |
| ≥ 3 volumes + last + sample + extra (the PR's case) | 0 % | 1 release |

**Mechanism:**
- A size kept with 1 or 2 copies is still a single MinHash element shared by the whole class.
- With only 3 or 4 signed sizes, whether it's the minimum of all 3 hashes in a band depends on its own hash ranks. For 4 GiB − 1 those ranks are low, hence the 12.7 %.
- This is a general MinHash property (one frequent element in small sets), and the old design had it for single-copy common sizes too.

**Why it isn't blocking:**
- It hits a narrow tail (exactly 2 full volumes), not every scene release as B1 did.
- To overflow the window, a class needs thousands of visible members.
- When it does overflow, `truncated` now says so (`compare.rs:530`), so the response no longer claims a confident "none".

**Fix (optional):**
- Name this tail in the decisions file's Known limit (2-copy split archives and FAT32 splits can still crowd the window; `truncated` then says so).
- Optionally add the 2-copy class to `unrelated_scene_releases_rarely_share_a_band` with a looser recorded bound. Lowering `MAX_COPIES` to 1 wouldn't fix it: a common single-copy size behaves the same way.

### O2: the `except_sig` unit test doesn't show the exclusion happens before the limit

**Where:** `crates/search/src/index.rs:2793-2795`.

**Evidence:** In this fixture, payload A is ids 1, 3, 5 and hidden 7; payload B is 2, 4, 6. All three assertions give the same result whether the `MustNot` runs before or after the 1,000 window:
- `except(&a, sig(0), 10)` gives `[]`, `false` either way;
- `except(&both, sig(0), 1)` gives `[6]`, `true` either way, because 6 is the newest overall.

The test proves clones are excluded, not that they're excluded before the limit. The code is correct by construction: the `MustNot` is a clause of the query the collector runs (`index.rs:1884-1897`), so excluded documents never reach `TopIds`.

**Fix:** pin it with:
- `except(&both, sig(0), 3) == ([2, 4, 6], false)`: exactly the remainder, so no off-by-one in `more`. A post-limit filter would give `([4, 6], true)`.
- `except(&both, sig(1), 1) == ([5], true)`. A post-limit filter would give `([], true)`.

### O3: the goldens don't pin the new copy and volume rule, which is now part of the stored format

**Where:** `crates/classify/src/group.rs:300-317`.

**Evidence:**

## Checked and correct

1. **The volume-size rule** (`signed_sizes`, `group.rs:202`):
   - `chunk_by` over sorted major sizes, keeping runs of length ≤ 2, takes one value per run. It's deterministic, independent of order and allocation-bounded (≤ 100 major files).
   - A season with distinct episode sizes signs every size. If two episodes share a size, it's kept once. A legitimate size appearing 3 or more times is dropped from the signature but still counts in `similar`'s multiset Jaccard and in `shared_distinct`.
   - **Minimum signed sizes before a release gets bands is 3** (`MIN_MAJOR_FILES`), so a signature is never down to one remaining size.
   - With exactly 3 signed sizes, two releases share all bands only if they have the same three non-volume sizes. If their volume counts differ, confirmation rejects them (for example 20V + {x, y, z} against 30V + {x, y, z}: Jaccard 0.70).
2. **The same function at write and query time:**
   - Writes: `doc.rs:247` calls `band_terms(&sizes)`, then `signature`, then `major_sizes` (sorted), then `MinHash::of_major`, then `signed_sizes`.
   - Query: `compare.rs` calls `MinHash::of_major(major)` on the reference and `similar` on candidates, and both use `signed_sizes`.
   - `few_major_files` (reference), band terms (write) and the `similar` threshold (confirm) all apply the same rule.
3. **Goldens unchanged:** `git diff` of `group.rs` doesn't touch the golden values. Their inputs have no repeated major sizes (case 2's 7 MiB file is under 1 %), and for k = 0 the old and new element hashes are identical. My Python reimplementation of the new code reproduces goldens 1 and 2.
4. **Generation 1:**
   - Stored terms did change between the previous head and this one, but only for torrents with a repeated major size (2 copies now hash once; 3 or more copies are dropped).
   - Nothing has shipped, since GS-2 isn't merged and no index anywhere holds generation-1 terms from the old head. **Keeping generation 1 is correct.**
5. **B1 is fixed for the reported class:** plain scene releases are unsigned, and the signed ones carry no volume-size element. My simulation of the PR's corpus shape finds 0 pairs and a top term of 1.
6. **The corpus test** (`classify/tests/group.rs:135`):
   - It uses a fixed seed (`Rng(9)`, splitmix64), so it's deterministic.
   - The sample, last part and extras are each ≥ 1 % of a payload of up to 2 GB.
   - It would fail on the old head: plain releases had 3 distinct sizes and were signed, so `assert!(plain.is_empty())` trips. The 1 % bounds would trip too (64 % of pairs in my earlier simulation).
7. **Proptests updated soundly:**
   - The doubled-copies equality runs only when `signed_sizes` match. That holds whenever no size had exactly 2 copies, so the branch is often exercised.
   - `below_the_threshold_nothing_matches` uses `signed_sizes`, and `copies_count` still holds.
8. **O2 part 1, a partial list writes no terms** (`doc.rs:247`):
   - The flag is read from the row passed to `TorrentDoc::new`, the same path the walk and catch-up use.
   - `grouping.rs` tests both sides of the flag on the same row and tree, so it would fail without the change.
   - A list that later becomes complete changes the tree and `payload_sig`, so the document is rewritten anyway.
9. **O2 part 2, `except_sig`** (`index.rs:1850-1897`, `compare.rs:504`):
   - `payload_sig_of_sizes(content_sizes)` sorts, and it's exactly what `doc.rs:269` stores as `payload_sig` for the same non-padding sizes. So the excluded set is the identical clones that `similar_to` already rejected (equal sorted sizes), apart from a 2⁻⁶⁴ collision.
   - It's a `MustNot` clause inside the collected query, so it applies before `TopIds` and before `more`. An index without `payload_sig` (`ABSENT`) simply doesn't exclude, and confirmation still drops clones.
   - The reference itself is now excluded too, because it carries its own signature, so it no longer takes a slot.
   - All callers were updated: the one in `compare.rs` and the unit tests.
10. **`truncated |= more`, the content-safety point** (`compare.rs:530`):
    - `more` comes from `torrents_with_minhash_bands`, whose query is `shown(Node::All, adult)`: `hidden:no verified:yes`, plus `-type:adult` unless adult is shown (`discover.rs:37`, `:147`). That's AND-ed with the bands and the clone exclusion.
    - So `more` counts only index-visible torrents, and a withheld torrent (hidden, unverified, Adult when not shown) can never be the one that tips it.
    - The only residual is index lag: a torrent the store has just withheld that the index still shows. In that case the flag reveals only "over 1,000 index-visible band-sharers", nothing identifying, and the same lag already affects every search count. GS-1's same-file rule (`compare.rs:290-294`) stays unchanged, and the difference is documented.
    - The endpoint test `a_full_candidate_window_says_truncated_however_short_the_list` (`siblings_payload.rs:1042`) puts 1,001 near-misses in the window. It would fail under the old `more && hits.len() == MAX_SIBLINGS` rule, and it checks the 20-torrent short-list case stays `false`.
