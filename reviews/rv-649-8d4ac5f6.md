## Focus 1: `lock_root` retry concurrency (accepted runner call, verified safe)
- **It can't succeed while another writer holds the lock.** Success only comes from tantivy's `try_lock_exclusive` (fs4 `LockFileEx` / `flock`), which the OS makes exclusive. The retry only repeats a non-blocking try.
- **It's bounded on every path.** The loop exits once `now() - start >= wait`, measured with the monotonic `Instant`. The worst case is about `LOCK_WAIT + LOCK_POLL` plus the attempt times, roughly 10.1 s. A wait of `ZERO` (non-Windows) is exactly one attempt: `x < ZERO` is always false.
- **No other lock is held while it sleeps.** `retry_busy` holds only a borrow of the `MmapDirectory`. Its only production caller is `Serving::open_or_rebuild`, inside the `spawn_blocking` closure in `Services::start` (`services.rs:235`). No mutex guard is live there, so it doesn't block the async runtime.
- **The error classification is exact to what tantivy gives.** Only `LockError::LockBusy` is retried. `IoError` (from opening the lock file) returns at once, as the mutation shows.
  - Caveat (nit 5): tantivy 0.27 maps any `try_lock_exclusive` error to `LockBusy` (`mmap_directory/mod.rs:493`, `.map_err(|_| LockError::LockBusy)`). So a filesystem that refuses locking is retried for 10 s and then reported as "in use by another instance". That message is the same as before; only the 10 s delay is new.
- **The tests exercise the code that ships.** `retry_busy` isn't cfg-gated, and only the `LOCK_WAIT` constant differs by platform. The tests pass explicit waits, so Linux tests the same loop Windows runs.
- **The cost is acceptable.** A real second instance on Windows is refused after about 10 s. Recorded in the decisions file.

## Focus 2: 409 before 202 (accepted runner call, verified safe)
- **Ordering:**
  1. The availability check comes first, so `restart_unavailable` gives no prepare (the test asserts `prepares == 0`).
  2. Then `prepare_restart()?`.
  3. Then `then_restart`.
  - Nothing awaits between steps 2 and 3, so the handler can't be cancelled in between. `ThenRestart::drop` always calls `restart()`, whether the body was written or the client went away.
  - The only path from a successful prepare to no `request()` is `serde_json::to_vec(RestartAccepted)` failing, which can't happen for that struct. Even then the waiting copy is harmless: `GO_LIMIT` is 600 s, it ends quietly once stdin closes, and `hand_over` re-spawns if needed.
- **No TOCTOU.**
  - `prepare()` and `request()` both take the `prepare` mutex and check `was_requested()` and `prepared` under it.
  - Two concurrent POSTs: the first starts one copy and sets `prepared`; the second sees `prepared` and answers 202. Both drops call `request()`, which is idempotent. One copy, one restart.
  - The address timer racing a POST is covered the same way in both orders.
- **State on failure:** `prepared` is set only on success, so a failed spawn can be retried by a later POST. Nothing is requested, and `app.restart_failed` logs only the error kind.
- **Service and Unix are unchanged:** `prepare()` returns `Ok` unless the method is `Relaunch`, and a paused service still gets `restart_unavailable` first.
- **Golden, openapi and schema.d.ts agree:** the message text is identical in `system.rs` and the golden, and the drift check is green.

## Findings

1. **Important, non-blocking.** `packaging/windows/portable/Start Lodestar.cmd:14-17` with `crates/lodestar/src/system/restart.rs:399`: a relaunched copy that fails to start now closes the window before anyone can read why.
   - **Failure path:**
     1. The old process hands over and exits 80.
     2. The launcher prints "restarted and keeps running", skips `pause`, and `cmd /c` exits.
     3. The new copy then fails at start: the very index-lock case this PR fixes, a still-held port, or an unreadable config.
     4. It prints its error and exits. Nothing is attached to the console any more, so conhost closes the window at once.
   - **Before:** the launcher's `pause` held the window open, so the error stayed visible.
   - This is the exact case the flake fix is about, and the decisions file's "not verified on a Windows desktop" list doesn't mention it.
   - **Proposed fix (follow-up is fine):**
     - Record it in the decisions file now.
     - In a later slice, have a relaunched copy (`MARKER` was set and the hand-over came) that fails at start print "Press any key" and wait on `CONIN$` while a console is attached.
     - Or point PK-guide-3 at `data\logs\lodestar.log` for this case.

2. **Important, non-blocking; follow-up outside this slice's paths.** `crates/companions/src/manager.rs:991`, with the same pattern in `crates/lodestar/src/update/layout.rs:239`: the same root-cause hypothesis applies to other non-blocking `LockFileEx` locks taken at serve start.
   - **Failure path:**
     1. A quick portable restart or service restart on Windows.
     2. The old process's companion `.lock` hasn't been released yet.
     3. `Manager::open` returns `Refusal::Busy`.
     4. `companions::start_with` logs `install_failed step=open reason=busy` and returns `None`, so companions are silently off for the whole run.
   - It doesn't stop serving, so it can't be the "no new copy served" flake. But if the PR's hypothesis is right, the relaunch can degrade the next run this way.
   - In practice the new 10 s index-lock wait runs first in `Services::start`, which makes it less likely but doesn't rule it out.
   - **Proposed fix:** a follow-up slice to reuse a shared busy-lock retry for the companion lock. The `update/layout.rs` lock is PK-win-upd-3's area.

3. **Nit.** `crates/lodestar/src/system/restart.rs:259-276`: `prepare()` runs a process spawn (`CreateProcessW`, which antivirus can slow) while holding a `std::sync::Mutex`, directly on a tokio worker thread in the axum handler. A concurrent restart or address-timer request blocks another worker until it's done.
   - It's a one-off admin action, and `request()` already did the same in `Drop`, so it's acceptable.
   - Optionally wrap the call in `spawn_blocking` in the handler.

4. **Nit.** `crates/lodestar/src/system/restart.rs:408`: `EXIT_RELAUNCHED = 80` duplicates `update::control::EXIT_RESTART = 80` instead of referring to it. If one changes, "80 means restart everywhere" silently breaks. Use `pub const EXIT_RELAUNCHED: i32 = crate::update::control::EXIT_RESTART;`, or add a test that asserts they're equal. That's a read-only reference, so it doesn't edit `update/**`.

5. **Nit.** `crates/search/src/rebuild.rs:553`: the doc says "An I/O error is never retried". That's true only for opening the lock file. tantivy turns every `try_lock_exclusive` error into `LockBusy`, so a filesystem without lock support waits 10 s on Windows and is then reported as "in use by another instance". Reword the doc to say so. No code change is needed.

6. **Nit.** Windows CI cost: `the_index_root_is_locked_once` and the existing `crates/search/tests/rebuild.rs:498` Locked test each now wait the full 10 s on Windows, so about 20 s is added to the Windows test job. Acceptable. Optionally run the new unit test's real-lock check off Windows only, since `retry_busy` already covers the logic.
