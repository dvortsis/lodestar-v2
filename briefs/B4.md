## Build
1. **The commit hook.**
   - After each successful live-index commit, `LiveIndexer` publishes a small `Committed { docs_added, max_torrent_id, at }` through a hook that lives in `Serving`'s shared state, so it **survives a B5b swap** (the new indexer gets the same hook). Use a `tokio::sync::broadcast` or `watch` sender, or a callback trait with no tokio dependency in `crates/search` if the crate has none; follow what's there.
   - The hook never blocks the indexer: a full or absent receiver drops the event.
   - A rebuild's own bulk commits don't publish "new torrents"; only the serving indexer's do.
   - Tests:
     - a commit publishes once with the right count and id watermark;
     - the hook keeps working across a swap;
     - a slow or absent subscriber never delays a commit.
2. **The hub** (`events.rs`).
   - **Topics now:**
     - `torrents` (from the commit hook: `{added, max_id}`, never names or hashes, so nothing private leaves through it);
     - `crawler` (a stats snapshot every 5 s, only while at least one client subscribes to it; read the same counters `http.rs`/`metrics.rs` use, behind a small trait so `crates/api` doesn't depend on `crates/lodestar`).
   - **Topics reserved and typed now, published later:**
     - `alerts` (B9);
     - `insights` (B11a, every 30 s);
     - `rebuild` (progress; publish it now if `Serving::progress()` makes it a one-liner).
   - A client chooses topics with `?topics=torrents,crawler`. Unknown topic: 400 with the envelope's `field`.
   - **Event ids:** `"<epoch>-<seq>"`, where `epoch` is random per process and `seq` is monotonic.
   - **Replay:** a ring of the last N events (e.g. 512, or 5 minutes) serves `Last-Event-ID` reconnects. Send a `resync` event, then live, if:
     - the id is from another epoch (a restart);
     - the id has already left the ring;
     - the id is malformed (don't error).
   - **Per-client bound:** a client that falls behind its bounded buffer (broadcast `Lagged`) gets one `resync` event and continues from live. It's never disconnected for lagging, and memory never grows per client.
   - **Heartbeat:** an SSE comment every 15 s.
   - **Reconnect hint:** `retry:` 5 s.
3. **Connection cap.**
   - A global cap on concurrent streams (e.g. 64) and a per-session cap (e.g. 4; the UI opens one per tab).
   - Past the cap, answer 429 with the envelope and a `Retry-After` header.
   - Slots are released when the client disconnects (a drop guard). Test that 1,000 connect/disconnect cycles leave the count at 0.
4. **Transport details.**
   - `/api/v1/events` behind `auth::protected` (session cookie; `EventSource` sends cookies; API keys come with B12).
   - `Content-Type: text/event-stream`, `Cache-Control: no-store` and `X-Accel-Buffering: no`.
   - **Make sure the router's compression layer doesn't buffer the stream.** Exclude `text/event-stream` from compression, or prove it flushes per event. Add a test through the full router showing an event arrives promptly.
   - Graceful shutdown ends open streams.
5. **API contract.**
   - Typed event payload structs registered in OpenAPI as components: one `oneOf` by event name, with the topic list as an enum.
   - The `/events` path is documented with its query parameter, its 401/429 responses, and a `text/event-stream` response.
   - The drift job must pass.

## Tests
- Topics are filtered; unknown topic gives 400.
- Heartbeat arrives (use a short configurable interval in tests).
- `Last-Event-ID` replay is exact, with no gaps and no duplicates; from another epoch or past the ring, it gives `resync`.
- A lagging client gets `resync` and stays bounded.
- The caps give 429 and are released on disconnect.
- Unauthenticated gives 401 (the route-list test).
- A cross-origin request follows the same rule as the other GETs.
- A crate-level property test: random publish/subscribe/lag/reconnect interleavings never deliver an event twice or out of order to one client, and every gap is announced with `resync`.
