## Build
1. **`api` client** (`lib/api/client.ts`). A thin typed `fetch` wrapper keyed by the generated `paths`. For example, `api.get('/search', { query })` returns the 200 body's type, and bodies are type-checked too.
   - Base `/api/v1`. Cookies are same-origin (`credentials: 'same-origin'`).
   - **Writes** (POST/PATCH/PUT/DELETE with a body) always send `Content-Type: application/json`. The server's same-origin check rejects anything else.
   - **Errors.**
     - A non-2xx response with the envelope becomes a typed `ApiError { status, code, message, field? }`.
     - A non-JSON error body (a proxy error page) becomes `ApiError { code: 'http_<status>' }`.
     - A network failure becomes `code: 'network'`.
     - An aborted request becomes an `AbortError` that callers can recognise and ignore (`isAbort(e)`).
   - **401 `login_required`.**
     - Call one registered handler: the shell (W9) will send it to `/login?next=<current path+query>`.
     - De-duplicate concurrent 401s into one redirect.
     - Never loop on `/login`, `/setup` or `/auth` themselves.
   - **429** gives `ApiError` with `retryAfter` (seconds) parsed from `Retry-After` (both the seconds and HTTP-date forms).
   - **Abort and latest-wins.** A `latest()` helper (or a keyed "request slot") aborts the previous in-flight request of the same slot when a new one starts. A response that resolves after a newer one started is dropped, even if abort raced. This is §10.12's "stale responses can't overwrite newer ones"; test it with out-of-order resolution.
   - **Cursors.** Callers pass `next_cursor` through untouched. `cursor_expired`/`bad_cursor` are ordinary `ApiError` codes, and a helper says "restart from page 1".
2. **URL ⇄ query state** (`lib/state/search.svelte.ts`, Svelte 5 runes).
   - **The URL holds the canonical text**, not a serialized AST. It has `q` (the server's `canonical` string) plus `sort`, `hidden` and `exact`. That keeps URLs short, shareable and stable across AST changes.
   - **The AST comes from the server.**
     - Typing calls `/parse` (debounced, latest-wins).
     - Structured edits, such as removing a chip or the Builder (later slices), produce an AST. The client POSTs it to `/search` (or `/parse` if it gains a POST), and the response's `canonical` becomes the new `q`.
     - **The client never re-implements the parser or the renderer.**
   - **Navigation.**
     - Updates use SvelteKit `goto` with `replaceState` while typing and a pushed history entry on submit, so back and forward walk searches.
     - Back and forward restore the state from the URL.
   - Unknown URL params are preserved, not dropped. Invalid values (e.g. `sort=nonsense`) fall back to defaults without throwing.
   - **Expose:** the current text, the AST (or the parse error with its position), sort and flags, and `submit()`, `setAst(ast)` and `reset()`.
3. **SSE client** (`lib/state/events.svelte.ts`).
   - **Use `fetch` with a streaming body reader, not `EventSource`.**
     - `EventSource` hides the status: on a 401 or a 429 it just errors or closes, so it can't honour `Retry-After` or tell "logged out" from "busy".
     - Parse the `text/event-stream` framing yourself: `id:`, `event:`, `data:` (multi-line), `retry:`, `:` comments as heartbeats, CRLF/LF/CR line endings, and a frame split across chunks. Unit-test the parser with chunk boundaries anywhere.
   - **One stream per tab,** subscribed to the union of the topics that mounted consumers want (`?topics=a,b`). Consumers subscribe through `events.on(topic, handler)`, which returns an unsubscribe.
     - When the topic set changes, reconnect with the new set and `Last-Event-ID`.
     - With no consumers, there's no stream.
   - **Reconnect.**
     - Send `Last-Event-ID` (the last `id:` seen) on reconnect.
     - Use the server's `retry:` as the base, plus exponential backoff with jitter, capped (e.g. 30 s).
     - A clean server close, a network error or a heartbeat timeout (no bytes for 2× the heartbeat, 15 s server-side, so about 35 s) reconnects.
   - **401** goes to the same login handler; don't retry.
   - **429.** The server caps 4 streams per session and 64 overall.
     - Wait `Retry-After`, then retry.
     - While waiting, expose `status: 'busy'` so the UI can say live updates are paused.
     - Never hammer it.
   - **`resync`** (no `id:`): call every consumer's `onResync()` so pages refetch what they show, then carry on.
   - **Batching.** Deliver events to handlers batched per animation frame (`requestAnimationFrame`), in arrival order. When several `crawler` snapshots land in one frame, deliver only the latest; `torrents` events are each delivered (they carry counts). Document the rule.
   - **Hidden tabs.** When `document.visibilityState` is `hidden` for more than about 10 s, close the stream; this frees a slot toward the cap of 4. When the tab is visible again, reconnect with `Last-Event-ID`. A server `resync` covers anything that fell out of the 512-event ring.
   - **Status** exposed as a rune: `connecting | live | busy | offline | stopped`, plus the last error.
4. **Tests (vitest).**
   - The client: envelope parsing, non-JSON errors, network errors, the 401 handler (de-duplicated, no loop on /login), `Retry-After` in both forms, latest-wins with out-of-order resolution and aborts.
   - URL state: round-trips, back and forward, unknown params kept, invalid values defaulted, and parse-error exposure.
   - SSE:
     - the parser across arbitrary chunk splits;
     - reconnect with `Last-Event-ID`;
     - `retry:` respected;
     - backoff capped;
     - 429 waits `Retry-After` and shows `busy`;
     - 401 stops;
     - `resync` fans out;
     - rAF batching and crawler coalescing;
     - the hidden-tab close and reopen (fake timers and a fake `visibilityState`);
     - topic-union changes reconnect;
     - the heartbeat timeout.
   - Use fakes for `fetch` and streams; no real network.
