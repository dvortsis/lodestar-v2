## Build
1. **The builder** (`bench::fixture::build(dir, anchor) -> Manifest`): a fresh data directory (database, index, `auth.json`) built only through public store, pipeline and search APIs, so it stays valid across migrations.
   - **Torrents:** a few hundred hand-specified ones (exact names, sizes, years, extensions, file counts, content types; several versions of one title for siblings and Compare) plus about 2,000 from `Generator::new(<fixed seed>)`. All names synthetic: no real release, group or person names.
   - **Edge cases, each a known count:** Adult, filter-hidden (`flags::HIDDEN`), `flags::PRIVATE_SOURCE`, v2/hybrid, padding files, a non-UTF-8 name, a pack of > 1,000 files, an ambiguous name resolved by files.
   - **M4 fields, null and populated:** `WriteBatch.swarm` updates for some torrents (seeders, leechers, completed, trackers reporting/checked, a DHT estimate, a suspect flag, history) and no swarm row ("never scraped") for others, with at least one in every swarm facet bucket. The server rebuilds hot columns from the store (`Store::load_hot`); don't write `data/hot/*.col`.
   - **Insights:** `rollup_hour` counters (`HARVESTED`, `REDISCOVERED`, `DROPPED`, `STORED`), `cohort_hour` (final cohorts older than 72 h, incomplete recent ones, every `Loss` reason), `events` (start, stop, pause, resume, intensity) and `index_watermark_hour`, consistent with the torrents, over at least 30 days.
   - **User data:** three saved searches (alerting, RSS-only, paused) with read and unread alerts via `record_percolation`; user items (favourite, hidden, labels, a note); two ordered collections. No API keys.
   - **Time:** every timestamp is an offset from `anchor` (start time rounded down to the hour), so "24 h", "7 d" and `discovered:<7d` give the same numbers whenever it's built; everything else is deterministic for one anchor.
2. **The manifest** (`fixture.json` beside the database): the anchor and a format version; total, stored and searchable counts; expected search totals and facet counts for a fixed query set (browse, a keyword, `type:movie`, `ext:mkv`, `hidden=true`; Adult shown and hidden); swarm null vs populated counts; per-cohort funnel numbers and finality; events; saved-search and alert counts. Computed from the builder's own specification, never by calling the code under test.
3. **`lodestar serve --fixture [DIR]`:**
   - No `DIR`: a temp directory, removed on clean exit. With `DIR`: build if empty, reuse if it holds a matching `fixture.json`, and **refuse** any other non-empty directory (exit 3, nothing written), so it can never touch a real install.
   - DHT, fetching, scraping, subscription refresh, plugins and every outbound request off, through existing config fields where possible (one `services.rs` line at most, named). Binds `127.0.0.1:8090` unless `--config`/`LODESTAR_HTTP_BIND` says otherwise, with a warning on a non-loopback address.
   - **Login:** the setup token is printed as usual; `LODESTAR_FIXTURE_PASSWORD`, if set, claims the instance through `lodestar_api::Auth::{load, setup_token, setup}`. No built-in default password.
   - The UI, `/healthz`, `/api/v1/*` and SSE behave as in a normal `serve`.

## Tests
- `bench/tests/fixture.rs`: two builds with one anchor give identical manifests and identical answers; the store opens at main's schema version; manifest counts equal independent `COUNT(*)`s; funnel stages never increase within a cohort; every edge case is present.
- `crates/lodestar/tests/fixture.rs`, the real binary on a free port as `tests/serve.rs` runs it: search, facets, detail and discover match the manifest with Adult hidden and shown; `hidden=true` adds exactly the filter-hidden ones; never-scraped swarm fields are `null`; a foreign non-empty `DIR` is refused untouched; the DHT and fetch pool never start.
