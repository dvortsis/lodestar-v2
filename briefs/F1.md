## Do
1. **Rule packs are off until chosen (§2.8, §20.6).**
   - `crates/filter/src/load.rs` (~line 48) defaults to `PackSwitches::all()` when nothing is stored. Make the default `PackSwitches::default()`, with no pack on.
   - Packs turn on only through a stored choice: the wizard (later UI slice, pre-checked there) or Settings via the filters API.
   - Update the docs and comments that say "on by default". Add a test that a fresh store loads with no pack enabled, and an end-to-end pipeline test that a pack-matching torrent passes on a fresh install.
   - Keep the guards and the pack logic as they are.
2. **The 50 µs budget is the owner's (§1.6.6, §20.8).**
   - Remove `LODESTAR_BUDGET_US` from `crates/filter/tests/props.rs`.
   - The budget test asserts 50 µs per torrent at 10k rules. If it's `#[ignore]`d, keep it ignored for local runs, but add it as a **release-mode CI job** (in `.github/workflows/ci.yml`, a new job next to the bench gates) on the CI runner.
   - Measure it there. If the core exceeds 50 µs on the CI runner, profile and optimise (precompiled matchers, per-torrent context reuse, avoiding allocation, early exits). If it still can't make 50 µs, don't loosen the gate: report the measured numbers in the PR and stop. The runner takes that to the owner.
3. **The floor from config files: add only (§2.7).**
   - `blocklist.files` and subscriptions marked `floor = true` may only **add** floor entries.
   - On start-up, an entry that's in the store's floor but missing from the file, or removed upstream for a floor-marked list, is **kept** and reported once per start ("N floor entries were removed from <file>; remove them in the app to unblock") with a counter metric. It goes into a "pending floor removals" list the filters API can show.
   - A removal takes effect only through the filters API with the effect warning and the password (§20.11). Add that API path if it's missing, following #47's patterns in `crates/api/src/filters.rs`. Add tests for both sources and the API path.
4. **Subscriptions are off by default and chosen by the user (§2.9).**
   - Confirm no list is connected without an explicit choice (`[subscriptions] catalog` defaults to empty; keep it so).
   - Add a **strictness assessment** to the filters API for any candidate set of lists: IPv4 share covered, IPv6 ranges, hash count, content categories and the resulting warning level (none / notice / strong / severe), with plain-language warning text per §10.14. BT_BlockLists at ~49% of IPv4 must come out **severe**.
   - The wizard and Settings UI slices will display it. Add tests.
