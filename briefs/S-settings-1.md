## The screen registry (the contract eight later slices build on)
Fix these names in part 1; a rename after merge breaks S-settings-2, S-logs, S-about, S-updates, S-appearance, M-security-settings, S-filters and S-blocklists. Export them from `$lib/features/settings/shell/registry.ts` and document them in `features/settings/shell/README.md`.

```ts
type ScreenGroup = 'preferences' | 'crawling' | 'library' | 'connections' | 'system';
interface SettingsScreen {
  id: string;                         // the URL segment: /settings/<id> (ids below)
  group: ScreenGroup;
  title: () => string;
  load?: () => Promise<{ default: Component }>;  // hand-built: loaded on open; renders its own <h1 tabindex="-1">
  sections?: readonly string[];       // the schema sections whose fields it shows
  groups?: readonly string[];         // only these x-groups of them (Keyboard: ['keyboard'])
  icon?: Component;                   // a `~icons/ph/*` import; the shell's gear when absent
  search?: () => SearchEntry[];       // a hand-built screen's own findable items (§10.10.3's static registry)
  attention?: (ctx: AttentionContext) => Promise<AttentionItem[]>;  // its Overview rows
}
interface SearchEntry { id: string; label: () => string; words?: () => string[]; anchor?: string }
interface AttentionItem {
  id: string; screen: string; severity: 'problem' | 'restart' | 'notice';
  text: () => string; action: { label: () => string; href?: string; run?: () => Promise<void> };
}
interface AttentionContext { system: SystemInfo; signal: AbortSignal }   // the /system the shell already fetched
```

- **Discovery:** `import.meta.glob(['/src/lib/features/*/screen.ts', '/src/lib/features/*/*/screen.ts'], { eager: true })`. A module exports `screen` (one) or `screens` (several), or a default of either. S-keys' file is found as it is.
- **`screen.ts` stays tiny:** it may import only `$lib/paraglide/messages.js`, `~icons/ph/*` and types. Components and anything else load through `load`. A vitest test reads every matched file and fails on any other import, so no slice can drag its screen into every Settings page.
- **A screen with `sections` and no `load` is generated** by your generated screen. With `load`, the route renders the loaded component and nothing else.
- **Where a field lives:** the first registered screen whose `sections` (and `groups`, when given) include it. S-keys' `screen.ts` declares none, so the registry holds one fallback claim, `keyboard` → `preferences` / `keyboard` (a `TODO(shortcuts)` to move it into their `screen.ts`). **Fields no screen claims** form an interim generated screen per section at `/settings/<section>`, titled by the section's label, in the group from a constant (`preferences`, `content` → Preferences; `logging`, `updates` and unknown → System), in instant mode for `preferences` and staged otherwise. So a new server setting is never unreachable (§10.10.1), and the interim screen disappears when its slice claims the fields. Two screens claiming one field is a dev error and a failing test.
- **Ids and order** (a constant in the shell, §10.10.2; ids match `Connection.settings` and Insights' fix links): Preferences: `appearance`, `keyboard`, `language`. Crawling: `crawler`, `network`, `sources`, `workers`, `companions`. Library: `storage`, `search`, `trackers`, `filters`. Connections: `integrations`, `notifications`, `insights`. System: `general`, `updates`, `logging`, `security`, `about`. An id not in the list goes last in its group, by title. Only registered screens (plus interim ones) appear; nothing is a placeholder.
- **Aliases:** `/settings/backup` and `/settings/import` (the shell's More menu) redirect to `/settings/general#backup`. Any other unknown id is the app's 404.

### Part 3: search, config.toml, backup and reset
13. **Settings search (§10.10.3):** the box at the top of the navigation, `role="combobox"` with a listbox of results. The matcher and index load on first focus (dynamic import) and are built then.
    - **Index:** every field of every screen (generated, interim and claimed), with label, help, group label, `x-config` key, `LODESTAR_*` name and `x-keywords`; every screen's title; every `search()` entry of hand-built screens.
    - **Matching:** case- and accent-insensitive (NFD, combining marks dropped, `toLocaleLowerCase` in the current locale), on word prefixes; label matches rank above help matches. In-house, no dependency.
    - **Results:** a breadcrumb ("Crawling › Crawler › Advanced"), the current value (enum option label, On/Off, number with its unit, string in Mono; values from `GET /settings/{section}` for the matched sections, fetched once per open) and its source badge (glossary `setting_*`).
    - **Choosing a result** navigates to the screen with the field's hash (step 6 does the rest).
    - **No match:** "No setting matches '{query}'" and a link to the user guide (`{system.repository}/tree/main/docs/user`, opening in a new tab; record the choice).
    - Command-palette "Settings: …" entries need a `lib/shell` hook: list them as a follow-up.
14. **View as config.toml** (each generated screen, lazy disclosure): the screen's values not at their default, one line each, `x-config = <TOML value>  # LODESTAR_X` (dotted keys at the top level are valid TOML), then the same as `LODESTAR_X=<value>` lines for a compose file or Unraid template, each block with Copy.
