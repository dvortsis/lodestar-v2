# B2: The runtime settings registry and `/settings`
**Model:** Opus (core: the settings layering touches every subsystem's config, and PATCH is an authenticated write path). **Branch:** `slice/B2`.
**Spec:**
- `runner/standards.md` (the bar; this touches an authenticated write API, so it also gets `/security-review`);
- `docs/build-plan.md` B2 bullet: typed sections, defaults < `config.toml` < DB < env; fields set by env read-only (and say so); `GET/PATCH /settings/{section}` with a JSON schema for form generation; live changes over `watch` channels; restart-required fields flagged; no migration;
- architecture §10.10 (the Settings sections and the first-run wizard that will generate forms from this schema), §11 (one `config.toml` with `LODESTAR_*` env overrides; most settings editable in the UI and persisted in the DB), §12 (auth, CSP), §16 "B1 decisions" (typed DTOs, utoipa, the drift check, the 501 pattern);
- `docs/owner-decisions.md`: the locked floor can be **added to via config files but removed only in the app**; rule packs and blocklist subscriptions are off until chosen. **The settings registry must not become a back door around these:** filter, floor, pack and subscription state stays owned by the filters API (§20.7, F1); the registry neither exposes nor writes it.
- the code: `crates/lodestar/src/{config.rs,services.rs,main.rs}`, `crates/store/src/lib.rs` (`settings` table, `setting_i64`), `crates/api/src/{lib.rs,openapi.rs,dto/*}`, `crates/api/README.md`.

## Build
1. **The registry** (`crates/lodestar/src/settings/`): one module per section, each a typed struct with `serde` + `utoipa::ToSchema` (or `schemars`, if B1 already uses it; no second schema crate), a `const SECTION: &str`, per-field metadata (label key, help key, `restart_required`, validation bounds), and a `Default`.
   - **Sections now:** the ones `config.rs` already backs: General (log level; data dir read-only), Network (HTTP bind, secure cookies, DHT port, DHT on/off), Crawler (intensity, fetch limits), Storage (store options), Search (search options). Plus **Fetch transport**: a `utp` flag (off by default, `restart_required`) and `fallback_to_tcp`; it's stored and exposed now, and wired into `FetchOptions` later (the DHT-side uTP wiring waits on M4 #48).
   - Later slices add sections (Integrations, Notifications, Appearance, Insights & digest…) by adding one module and one registration line; document that pattern in a short README in `settings/`.
2. **Layering** (lowest to highest): defaults < `config.toml` < DB < env. Each field's effective value carries its `source` (`default`/`file`/`db`/`env`). **A field set by env is read-only**: PATCH refuses it with a clear error naming the variable. A DB value never silently overrides env.
3. **Live changes:** each section has a `tokio::sync::watch` channel. Subsystems that can apply a change live (e.g. crawler intensity, log level) subscribe; the rest are flagged `restart_required`, and the response says a restart is needed. Wire at least intensity and log level live, with tests.
4. **API** (`/api/v1/settings`, behind `auth::protected`, same-origin as the other write routes):
   - `GET /settings` lists sections with their schema (for form generation);
   - `GET /settings/{section}` returns effective values, sources, read-only flags and restart flags;
   - `PATCH /settings/{section}` takes a partial typed body, validates every field (bounds, enums, socket addresses), writes all of it to the DB in **one transaction**, publishes on the watch channel, and returns the new effective state plus `restart_required` fields. Invalid input gives the error envelope with `field`.
   - Unknown section: 404; unknown field: 400 (`deny_unknown_fields`).
   - Typed DTOs registered in OpenAPI; the drift job must pass.
5. **Security:** secrets never pass through this registry (credentials live in the integrations `SecretStore`); no field can change `data_dir` or anything that moves files at runtime; the HTTP bind change is restart-only. Add a test that filter/floor/pack/subscription keys are not reachable through `/settings`.

## Tests
- Layering order and `source` for every combination; env read-only enforcement; DB persistence across a restart (store reopen).
- PATCH validation per field type; a partial PATCH leaves other fields alone; one transaction (a failure writes nothing).
- Live propagation over watch for intensity and log level; restart flags.
- API golden tests in B1's style (`crates/api/tests/golden.rs` pattern) for GET/PATCH/errors; the 401 list includes the new routes.
