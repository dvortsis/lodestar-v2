# M-settings-form: Settings form engine
**Model:** Opus (core: every Settings screen and the wizard depend on it, and its failure modes lose user data: staged edits, three-way merges under concurrency, atomic save, drafts in storage; architecture §10.10.11 "Delegation"). **Branch:** `slice/M-settings-form`. **`/security-review` is required** before merge (standards §5.7): the engine handles secret (`writeOnly`) fields and writes drafts to `sessionStorage`.

## The API you expose (S-settings-1, S-wizard and later screens build on exactly this)
Import everything from `$lib/features/settings/form` (types and functions) and components by path. A rename after merge is a breaking change for four slices: get the names right here.

```ts
// Loading (one GET /settings per tab, cached; values per section from GET /settings/{section})
loadSettingsIndex(): Promise<SettingsIndexView>
interface SettingsIndexView {
  sections: { section: string; labelKey: string; helpKey: string }[];
  spec(key: FieldKey): FieldSpec | undefined;          // FieldKey = `${section}.${field}`
  fieldsOf(sections: string[]): FieldSpec[];           // schema order: x-group, then x-order
}
interface FieldSpec {                                  // derived from the section's JSON Schema + SettingField
  key: FieldKey; section: string; name: string;
  labelKey: string; helpKey: string; keywordsKey?: string;   // server message keys, as sent
  kind: 'boolean' | 'enum' | 'integer' | 'number' | 'string' | 'string-list' | 'map' | 'unknown';
  enum?: readonly string[]; minimum?: number; maximum?: number; format?: string;
  unit?: string; widget?: string; auto?: unknown; preview: boolean;
  danger?: 'disruptive' | 'privacy' | 'destructive' | 'security';
  group: string; order: number; advanced: boolean;
  config?: string; env?: string; writeOnly: boolean; readOnly: boolean; restartRequired: boolean;
}
groupFields(specs: FieldSpec[]): { group: string; labelKey: string; essentials: FieldSpec[]; advanced: FieldSpec[] }[]
settingText(key: string): string | undefined           // 'settings.crawler.intensity.label' → m.settings_crawler_intensity_label()
fieldAnchor(key: FieldKey): string                      // the element id and URL hash: 'crawler.intensity'

// One form per screen or wizard step
createSettingsForm(opts: {
  id: string;                          // screen id: draft key and key scope ('crawler', 'wizard.intensity')
  fields: FieldKey[] | FieldSpec[];    // any sections; one save covers all of them
  mode?: 'staged' | 'instant';         // default 'staged'; 'instant' for Preferences screens
  drafts?: boolean;                    // default true (staged only)
  href?: (key: FieldKey) => string;    // "Copy link" target; default location.pathname + '#' + fieldAnchor(key)
}): SettingsForm

interface SettingsForm {                // reactive (runes); read in templates and effects
  readonly specs: FieldSpec[];
  readonly status: 'loading' | 'load-error' | 'ready' | 'saving' | 'saved' | 'save-error' | 'offline';
  readonly loadError?: ApiError;
  readonly dirtyCount: number;          // "2 unsaved changes"; always exact
  readonly errors: { key?: FieldKey; message: string }[];   // the error summary, in field order
  readonly conflicts: FieldKey[];
  readonly restartPending: FieldKey[];  // from the last save's restart_required
  readonly undoUntil: number | null;    // ms timestamp while Undo is offered
  readonly draft: null | { fields: number; dropped: number };   // a restorable draft, before restore
  field(key: FieldKey): FieldState;
  set(key: FieldKey, value: unknown): void;
  reset(key: FieldKey): void;           // stages "remove the saved value" (B2's null patch)
  blur(key: FieldKey): void;            // validates that field
  save(): Promise<SaveResult>;
  discard(): void;
  undo(): Promise<SaveResult>;
  resolve(key: FieldKey, pick: 'mine' | 'theirs'): void;
  restoreDraft(): void; dropDraft(): void;
  retry(): Promise<void>;               // reload after load-error, or re-run a failed save
  onConfirm(code: string, handler: (c: { section: string; field?: string; message: string })
    => Promise<Record<string, unknown> | null>): () => void;
  gate(danger: NonNullable<FieldSpec['danger']>, handler: (c: GateContext) => Promise<boolean>): () => void;
  destroy(): void;
}
interface FieldState {
  spec: FieldSpec; value: unknown; saved: unknown; source: SettingSource; env: string | null;
  locked: boolean;                      // read_only or env-set: no edits, no reset
  dirty: boolean; changed: boolean;     // changed = source !== 'default' (see "Backend gaps")
  pendingReset: boolean; error?: string; conflict?: { mine: unknown; theirs: unknown };
  preview?: { restartRequired: boolean; estimates: PreviewEstimate[]; warnings: PreviewWarning[] };
  savedRecently?: 'live' | 'restart';
}
type SaveResult = { ok: true; restart: FieldKey[] }
  | { ok: false; reason: 'nothing' | 'invalid' | 'conflict' | 'cancelled' | 'network' | 'refused' | 'busy' };
interface GateContext { fields: FieldKey[]; preview: components['schemas']['SettingsPreview'] }

// Widgets: features register their own (S-logs 'log-events', S-appearance 'theme', S-keys 'shortcuts', …)
registerWidget(name: string, component: Component<WidgetProps>): () => void
interface WidgetProps { form: SettingsForm; key: FieldKey; controlProps: FieldControlProps; dense?: boolean }
```

Components (`features/settings/form/*.svelte`):
- `SettingsForm.svelte` `{ form, saveBar = true, leaveGuard = true, shortcut = true, children }`: the error summary at the top, `children`, the draft banner, the network banner, the conflict and save announcements (one polite live region), the save bar, the leave dialog, the default disruptive gate. It owns everything tied to a component's lifetime (`beforeNavigate`, the ⌘/Ctrl+S registration, the `settings` subscription), so `createSettingsForm` itself stays a plain, testable store.
- `SettingField.svelte` `{ form, key, dense? }`: the whole §10.10.4 field. A screen never builds a field by hand.

How S-settings-1 uses it: one `createSettingsForm({ id: screen, fields: index.fieldsOf(['crawler', 'transport']) })` per screen, `<SettingsForm {form}>`, and `groupFields(form.specs)` rendered as groups with `<SettingField>` per essential and an "Advanced (n)" disclosure (the disclosure, headings, Show changed only, search and deep-link focusing are S-settings-1's). How S-wizard uses it: one form per step, `<SettingsForm {form} saveBar={false} leaveGuard={false}>`, and on Next `const r = await form.save(); if (r.ok || r.reason === 'nothing') next();`. ## Build
1. **Schema reader** (`schema.ts`). `SettingsSection.schema` is typed `Record<string, never>`: treat it as `unknown` and narrow every property defensively (it's the server's document, but never trust a shape you didn't check). Read `type`, `enum`, `minimum`/`maximum`, `format`, `readOnly`, `writeOnly`, `additionalProperties`/`propertyNames` (maps), `items` (lists) and the hints `x-group`, `x-order`, `x-advanced`, `x-unit`, `x-widget`, `x-auto`, `x-preview`, `x-keywords`, `x-danger`, `x-config`, `x-env`; take `restart_required`, `read_only`, `env`, `label_key`, `help_key` from `SettingField`. The golden today also uses `x-unit` `files` and `days`, `x-widget` `duration`, `log-events`, `log-kinds`, `log-components`, `shortcuts`, `theme`, `language`, `time-zone`, `radio`, and `format` `int32`/`int64`: handle all of them. A shape you can't read becomes `kind: 'unknown'` with a dev-mode `console.warn` naming the field.
2. **Widget registry** (§10.10.4's table, one function `widgetFor(spec)`): a registered `x-widget` name wins; boolean → `Toggle`; enum ≤ 4 → `SegmentedControl`, or `Radio` with `x-widget: radio`; enum > 4 → `Select`; integer or number with bounds → `RangeInput` with the unit, or `Slider` + input with `x-widget: slider`; `format` `socket-addr`, `host`, `url`, `duration`, `log-filter` → `Input` with format validation, in `Mono` for addresses and filters; string list → a chip list with Add; `writeOnly` → the secret field (step 9). An **unregistered** `x-widget` falls back to the shape's default widget with a dev warning. Only `kind: 'unknown'` (and a map with no registered widget) gets the plain JSON input, also with a dev warning, so a new server setting is never invisible.
3. **Values and dirty tracking** (`values.ts`), the invariants your tests hold:
   - Per section the form keeps `saved` (the last values from the server, with `source`, `env`, `read_only`, `restart_required`), `revision` (the last known), `base` (the saved value each edit started from) and `mine` (the staged value, or the `RESET` sentinel).
   - **Equality is deep JSON equality**, key-order-insensitive for objects; `-0` equals `0`; never reference equality.
   - **A field is dirty iff `mine` differs from `saved`**; setting it back to the saved value makes it clean, so `dirtyCount` is always exact. `RESET` is dirty only while `source === 'db'` (removing a saved value); Reset isn't offered for `default`, `file` (null would change nothing: the help says to edit `config.toml`) or locked fields.
   - **Locked fields** (`read_only`, or `source === 'env'`) never take `set`, `reset` or a draft value.
   - **A save sends only dirty fields**, each section once with `if_revision` = that section's `revision`; untouched sections are never sent; `RESET` is sent as `null`; secrets only when replaced.
4. **Client validation** (`validate.ts`, §10.10.5): on blur for that field and for every dirty field on Save. Type, integer, `minimum`/`maximum` (message "Must be between {min} and {max} {unit}", unit from your unit messages), enum, `socket-addr` (IPv4:port or `[IPv6]:port`, port 1–65535), `url` (http/https), `host`; `log-filter` and `duration` are left to the server and their widgets. Errors go inline under the field (`aria-invalid`, `aria-describedby`). **Save is never disabled.** Saving with errors sends nothing, fills the summary and returns `{ ok: false, reason: 'invalid' }`.
5. **The save pipeline** (one place; every path tested):
   1. A save while one is in flight returns `busy` and sends nothing. Nothing dirty: `nothing`.
   2. Validate (step 4).
   3. **Gates** (§10.10.7): for each `x-danger` among the dirty fields, run that kind's handler once with the dirty fields of that kind and a `POST /settings/preview` of the whole batch. `disruptive` has a default: a dialog naming the effect from the preview's warnings and the `url` estimate ("Lodestar will be at http://… after a restart"), Save / Cancel. `privacy`, `security` and `destructive` have no default and **fail closed**: with no handler registered, nothing is sent, the summary says the change needs a confirmation this screen can't show, and a dev error names the field. A handler returning false is `cancelled`.
   4. **One `PATCH /settings`** with the whole batch, so one save is atomic across sections: everything is saved or nothing is. Never one request per section.
   5. **200:** take `saved`, `revision` and `restart_required` from the response's `sections`; a field is clean if its current `mine` equals what was sent. An edit made while the request was in flight stays dirty, against the new saved value, and is never silently marked saved. Fields in `restart_required` show "Saved · applies after restart". Clear the draft once nothing is dirty. Offer Undo (step 7). Announce politely.
   6. **Errors** (statuses and codes from `crates/api/src/settings.rs`): `422 invalid_setting` → that `section` + `field`'s inline error with the server's message (it never holds a secret), plus the summary; `409 set_by_environment` / `read_only` → the field's error, then refetch its section so it shows locked; `409 stale_revision` → step 6 with `current`; `400 unknown_field` / `404 unknown_section` → a summary error and a dev error (the schema and the server disagree); a 422 whose `code` has an `onConfirm` handler (B17's `adult_confirmation_required`) → call it; returned keys are added to that section's patch and the save is sent again **once**, `null` is `cancelled` with the edit kept; with no handler, the server's message shows on the field. `network` (status 0) → `offline`: the draft stays, a banner says "Couldn't reach Lodestar. Your changes are kept." with Retry. `429`/`503` → the same banner, with `retryAfter` when present. `401 login_required` → W5's handler redirects to sign-in; the draft is already in `sessionStorage`, so nothing is lost. Other 5xx → `save-error` banner, the draft kept.
   7. **The error summary** lists every error as a link in field order and takes focus (a heading with `tabindex="-1"`). Each link moves focus to its field's control, expanding Advanced through a callback S-settings-1 supplies (`onReveal?: (key) => void` on `SettingsForm`). Read §10.10.5's "then focus moves to the first field with an error" as the first link leading there (the GOV.UK pattern); record that reading in your decisions file.
6. **Concurrent edits** (`merge.ts`, a pure function), on `409 stale_revision` (`current` holds each stale section) and on a `settings` event for a section the form shows. For each field, with `B` = base, `M` = mine, `T` = theirs:
   - `M = B` (untouched by you): take `T` silently, and `B := T`.
   - `T = B` (only you changed it): keep `M`, and `B := T`.
   - both changed and `M = T`: clean, with no conflict.
   - both changed and `M ≠ T`: a conflict, "Changed elsewhere to {theirs} · Keep mine · Use theirs". Save returns `conflict` until each is resolved: **Keep mine** keeps `M` with `B := T`; **Use theirs** sets `M := T` (clean).
   - `T` is now locked (env-set or read-only): drop your edit and say so on the field.
   - The field is gone from `T` (a newer server): drop it and count it in a notice.
   - Afterwards the section's `revision` is the one `current` (or the refetch) reported, so the next save sends it as `if_revision`. **Never re-save automatically after a merge**; the user saves again.
   - **Events** (`events.on('settings')`, `{section, revision}`): ignore a `revision` ≤ the known one. While a save is in flight, hold events for the sections in its batch until the response arrives, then drop those at or below the response's revision (your own save's event never looks like someone else's). Otherwise refetch that section: with no dirty field in it, update in place with a quiet "Updated elsewhere" note; with dirty fields, run the merge. On `onResync`, refetch every section the form shows.
7. **Undo** (§10.10.5): offered for 10 s after a successful save (`undoUntil`), announced politely. It sends one `PATCH /settings` with each saved field's **previous** value where the previous `source` was `db`, and `null` (reset) otherwise, with `if_revision` = the revisions the save returned. A `409 stale_revision` means something changed since: say Undo isn't possible any more and refetch; never merge an Undo. Secrets are left out of Undo (their old value is never known); the bar says so when a secret was part of the save.
8. **Drafts** (`draft.ts`, §10.10.5): `sessionStorage` key `lodestar.settings.draft.v1.<id>`, written 300 ms after the last edit, `{ v: 1, at, sections: { [s]: { revision, base: {…}, mine: {…} } } }`. **Never secrets** (`writeOnly` fields are skipped, `RESET` included), never locked fields, at most 64 KiB (larger: no draft, with a dev warning). Every storage call is in `try/catch`: storage that is absent, full or blocked turns drafts off and nothing else. On mount, a draft that still differs from the server offers "You have unsaved changes from earlier · Restore · Discard"; Restore runs the merge with the draft's `base`/`mine` against the current values, after re-validating every field against today's schema (unknown, now-locked or mistyped fields are dropped and counted in `draft.dropped`). The draft is cleared by a successful save with nothing left dirty, by Discard, and by Drop.
9. **The field** (`SettingField.svelte`, §10.10.4), each part tested:
   - **Label** always visible, the unit as a suffix inside the control (your `settings_form_unit_*` messages: seconds, MiB, connections, files, days; an unknown unit shows as sent, with a dev warning).
   - **Help** under the control from `help_key`. A missing message shows no help and warns in dev; never show the schema's `description`, which is written for developers.
   - **Status line** (icon + text, only when it applies): "Applies after restart" (`restart_required`), "Set by {variable}" (locked; the variable name copyable, the text says to change it in the container template or environment), "Read-only" (the value copyable), "From config.toml" (`source === 'file'`). Use the glossary `setting_*` keys.
   - **Modified marker:** a small dot with the accessible name "Changed from default" when `changed`.
   - **Field menu (⋯)** (`Menu`): Reset to default (hidden as step 3 says), Copy link to this setting (`href(key)`), Show `config.toml` key and environment variable (`x-config`, `x-env`, in `Mono`).
   - **Automatic** (`x-auto`): an "Automatic" switch; on stages the sentinel; the effective value shows beside it ("Automatic · 400") from the field's own preview estimate when the server gives exactly one; switching it off reveals the number input pre-filled with that value (empty and invalid when there's none).
   - **Inline preview** (`x-preview`): `POST /settings/preview` with the form's current dirty batch, 300 ms after the last change, through a `latest()` slot (a stale response never overwrites a newer one); show the field's `warnings` and `estimates` as one line (`sockets` → `formatCount`; `memory_mib` → `formatBytes` of MiB × 1,048,576, a unit change; `url` in `Mono`). A preview refusal shows as that field's inline error but never blocks typing or Save.
   - **Secrets** (`writeOnly`): never pre-filled and never shown. "Set" when the server reports a saved value (`source !== 'default'` with `value: null`), with **Replace** (an empty `type="password"` input, `autocomplete="new-password"`, cleared after every save attempt) and **Remove**. Remove is destructive and not undoable (§10.10.7): it runs on its own, after a confirmation dialog, as one `PATCH` of that field to `null`, never as part of Save. Secret values never reach drafts, Undo, the summary, logs or the console. No section has a secret yet (B2b refuses them until sealing exists), so test this with a fixture section.
   - **Ids:** the field's wrapper has `id = fieldAnchor(key)` so `#crawler.intensity` deep-links work. Controls take `FieldControlProps` from `Field`.
10. **The save bar** (§10.10.5): pinned to the bottom of the manuscript column and shown only when something is unsaved, failed, or within the Undo window: "{n} unsaved changes · Discard · **Save changes**", then "Saved · Undo", or "Saved · applies after restart". While it's shown, the column gets bottom padding the bar's height, and a focused field scrolls clear of it (`scroll-margin-bottom`). Discard asks nothing when there's one change and confirms when there are more (record this). ⌘/Ctrl+S saves: register `settings.save` with `keys: ['mod+s']`, `allowInInput: true`, in a scope you `pushScope` while the form is mounted, and stop the browser's own save. Load `$lib/keys` with `import()` inside the effect as the shell does (W9 decisions), never statically. The registry attaches on the first interaction, so also handle ⌘/Ctrl+S in a `keydown` listener on the form itself until `keys` has loaded, without firing twice once it has.
11. **The leave guard** (§10.10.5): in `SettingsForm.svelte`, `beforeNavigate`. Leaving the screen's path with dirty fields cancels the navigation and opens a dialog, **Save** / **Discard** / **Keep editing**. Save continues to the destination only on `ok`; Discard clears the draft and continues; Keep editing stays. A hash or query change on the same path isn't leaving. For `type === 'leave'` (closing or reloading the tab), calling `cancel()` raises the browser's own prompt. Your own navigation after Save or Discard never re-triggers the guard. Off with `leaveGuard={false}` (the wizard).
12. **Instant mode** (Preferences, §10.10.1): each `set` sends its own `PATCH /settings` for that field with `if_revision` (debounced 300 ms for sliders and text, at once for toggles and segmented controls); success shows an inline "Changed · Undo" under the field for 10 s (the toast primitive has no action button). Undo sends the previous value, or `null` where it wasn't saved before. A failure puts the old value back with the error inline. A `409 stale_revision` refetches and retries once with the new revision (the user just acted). No drafts, no save bar, no leave guard.
13. **Messages** (`messages.ts` + your JSON): `settingText(key)` maps a server key to a Paraglide message by replacing `.` and `-` with `_` (`settings.crawler.intensity.label` → `settings_crawler_intensity_label`). Bundle only `settings_*` messages: `import.meta.glob` over the compiled `src/lib/paraglide/messages/settings_*.js` (eager), or a generated map. **Never index `m` dynamically** (`m[key]`), which pulls every message of the app into the chunk. A test fails if the form's sources contain `m[`. A missing key returns `undefined`, and the field falls back to its `name` with a dev warning. Your own strings are `settings_form_*`, en complete; add zh where you can translate confidently and list the rest.
14. **Typing gaps you work around in exactly one place** (`requests.ts`): `SettingsBatch` and `SettingsPatch` are `Record<string, never>` in `schema.d.ts`, so the typed client can't express a body. Build the body as your own `Batch` and cast once, with a comment naming the backend follow-up (`additionalProperties` on those schemas). Everything else uses the generated types.
15. **Accessibility** (§10.10.11, §10.13): every control has a visible `<label>`; help and errors via `aria-describedby`, errors `aria-invalid`; the error summary takes focus; save results, conflicts and "Updated elsewhere" go to one polite live region; status is icon + text; targets ≥ 44 px under `pointer: coarse`; it holds at 200% zoom; dialogs trap and restore focus (the `Dialog` primitive). Bare-character shortcuts aren't yours to add.
16. **Budget:** the Settings route (shell, engine, generated screens) is ≤ 20 KB gzipped (§10.10.11). S-settings-1 adds that `size-limit` entry, so keep the engine, `SettingField` and the built-in widgets **≤ 10 KB gzipped**. A dev route can't be a `size-limit` entry (`routeFiles` throws when the route is absent from a production build), so measure with `VITE_DEV_ROUTES=1 npm run build`: the files `/dev/settings-form` loads beyond `/search`'s, gzipped, minus the showcase page itself. Report the figure. Nothing of yours may enter the search route's first load.
