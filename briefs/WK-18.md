## The decision (owner wkq2, §2.47)
`LODESTAR_TOKEN` is accepted from the environment **only for the first join, while no credentials exist**. After that it's ignored with a warning to remove it, and its value is never logged. The token is single-use, name-bound, and expires in 15 minutes. `lodestar worker` already does this (`crates/lodestar/src/cli/worker.rs`, `ENV_TOKEN_STALE` and `ENV_TOKEN_UNUSED`). **Read that file first** and match the templates to what it does. Don't change it.

## What to build
1. **Compose:** a `worker` service in `packaging/docker/compose.worker.yml`.
   - Data volume, spool path and DHT port.
   - The token as `LODESTAR_TOKEN` for the first join, with a comment saying to remove it after the first start. A `--token-file` alternative is shown commented out.
   - No other secrets, and no ports beyond the DHT port.
2. **Unraid:** the `lodestar-worker.xml` template.
   - The token as a masked variable, described as "first start only, remove after".
   - The spool path and DHT port.
   - Overview and Requires stay as the validator wants: Lodestar v0.6 or newer as the main instance.
3. **WiX:** `packaging/wix/join.wxs`, a "Join an existing Lodestar" option.
   - It writes the token to a file only SYSTEM and Administrators can read, and passes `--token-file`, never the token on the command line or in the service's environment.
   - The file is deleted after the first successful join. If the CLI deletes it, say so; if not, say what does.
   - If WiX needs a custom action you can't build and test here, stop and ask the runner.
