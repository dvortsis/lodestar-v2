## Build
1. **Aggregation kinds (carry-forward a).** `lodestar_store::Aggregation { Sum, Last }`. `crates/pipeline/src/rollups.rs` gets `metric::aggregation(code) -> Option<Aggregation>` over one table listing **every** code: 1–4 and 10–12 `Sum`, 13 `SEARCHABLE` `Last`, 5–9 `Sum` (#48's, not on main yet), 14–15 below. A test fails when a code from 1 to the highest defined has no kind. Compaction, repair and day reads take this table; **a metric with no kind is never compacted** (its hours stay; logged once), so a future gauge can't be summed by accident.
2. **Migration V11** (on-disk format; document each line in `schema.rs`):
   - `rollup_day(day, metric, dim, key, value)` and `cohort_day(day, source, stage, reason, count)`, `STRICT, WITHOUT ROWID`, primary keys as their hourly twins; `day` = Unix time / 86,400 (UTC days, `docs/metrics.md` §2).
   - `insights_state(key TEXT PRIMARY KEY, value INTEGER NOT NULL)`: `compacted_before_day`, `last_compaction_at`, `funnel_events_since_hour`, `imported`.
   - **`imported` seeded by the migration** (the same count `count_flagged_searchable(flags::IMPORTED)` makes, once, at upgrade), then kept exact: `record_searchable` adds each chunk's imports in its own transaction, and an `AFTER DELETE ON torrents` trigger subtracts a searchable import (`old.id <=` the highest `index_watermark_hour.last_id`). This retires the scan at every start (B11a follow-up). The recorder's `Insights.imported` mirrors the row (after each record and each tick).
   - **Removals (lifecycle, §10.9.3):** the same trigger adds 1 to `rollup_hour` at `unixepoch() / 3600` under new code **15 `REMOVED`** (dim = content type or `UNCLASSIFIED`) for a searchable torrent deleted by any path (a filter relabel, `delete_torrents`, retention later). The snapshot purge runs on snapshot copies, so the trigger fires there too: decide whether a restored snapshot should show those as removals, and record it. Codes are persisted: a `crates/lodestar` test holds `metric::REMOVED` to the migration's literal.
3. **Fetch by event time** (`stages.fetch` is "null until … (B11b)"): new code **14 `FUNNEL_EVENTS`** (dim = `Stage` code, key = `Loss` code or 0), written in `writer.rs` from the cohort rows `self.funnel.drain()` returns, at the flush hour (event time within the 5 s flush cadence; say so). `insights_state.funnel_events_since_hour` marks its first hour: **buckets before it are `null`, never 0**, even where coverage exists. If #48's `writer.rs` edits make this more than a few lines, keep `stages.fetch` null and name the follow-up.
4. **Daily compaction** (`Store::compact_rollups`), run by the recorder task:
   - Folds whole UTC days that ended more than 30 days ago, **and never a cohort day at or after `seal_floor()`'s day** (keys restored after a long downtime still write there). One day per `BEGIN IMMEDIATE` transaction (a few thousand rows): insert the day's rows (`Sum` adds, `Last` takes the latest hour's row), delete its hourly rows, advance `compacted_before_day`, commit. That makes it **idempotent and crash-safe**: a crash leaves a day either fully hourly or fully daily. A straggler hourly row found below the boundary is folded in the same way.
   - **Bounded WAL and writer waits:** the recorder's loop runs between days (commits keep being recorded); no read transaction spans days; a run stops after a time budget and resumes at the next tick. After a run, an `incremental_vacuum` bounded to the pages it freed.
   - **When:** a tick checks `last_compaction_at`; it runs when that's ≥ 24 h old, first checked 10 min after start, so start-up isn't slowed. A first run on a year of history goes day by day the same way.
   - **The query log (carry-forward b):** the same daily job runs `prune_query_log(now − 30 days, cap)` (§10.9.5 "retained 30 days"; pick the row cap and record it). Nothing writes the log yet; this is its only production caller.
5. **Reads over both grains.** Every overview and stage read decides hourly vs daily by `compacted_before_day` **read inside the same `read_snapshot`**, so a concurrent compaction never double-counts or drops a day. Days below it read `rollup_day`/`cohort_day` with the same one-seek-per-(day, metric) pattern as `rollup_sums`; `Last` metrics take the last value per bucket (`previous.kpi.searchable` included). B11a's sealed-day cache may shrink to the 8–30-day band or go; keep ≤ 50 ms on a year. A window reaching into compacted days is bucketed by day (`range.bucket: "day"`) even if shorter than 7 days; record it. Finality, gaps and Compare keep B11a's rules; a compacted day is final.
6. **`lodestar rollup --repair`** (`cli/rollup.rs` → `Store::repair_rollups`):
   - **Offline**, like `vacuum`: `refuse_during_update_rollback`, then `StoreLock::acquire`; refused (exit 3) while the server runs, because a recount racing the live writer's pending increments would overcount.
   - **Rebuilds from raw data what raw data holds:** cohort `Stored` (`discovered_at` hour, `first_source`, imports excluded), `metric::STORED` by `metadata_at` hour (dim = `first_source`; the writer counts at commit, seconds later, so an hour boundary can shift: record it), and everything `record_searchable` writes (`NEWLY_SEARCHABLE`, cohort `Searchable`, `TIME_TO_SEARCHABLE` at the watermark hour's midpoint, ≤ 30 min off, only for rows it adds) from `index_watermark_hour` id ranges; it also recounts `imported`.
   - **Raise only:** per (cohort, source) and per (hour, metric), write the recount only where it's **above** what's stored, and replace a cohort's histogram only together with its count. Deletions since then lower the recount, and final cohorts never change (§10.9.3), so it never lowers anything.
   - Default window: the hourly 30 days; `--since <N>d` reaches compacted days, repaired at day grain into the day tables. Chunked (≤ 20,000 ids per transaction, like `SEARCHABLE_CHUNK`); prints what it changed.
   - **Automatic after an unclean shutdown** (§7): in `services.rs`, on the writer's store **before `Pipeline::start` takes it** (so no live increment races it). Unclean = the newest `event::START`/`event::STOP` is a `START`. It recounts only ids stored since `now − 72 h` (find the first by a binary search on the primary key over `metadata_at`), so it takes seconds, not a full scan. Say which cohorts it can't fix (keys restored with an older cohort).
   - **State what's lost for good** in the decisions file and `--help`: pre-storage counts (harvested, peer found, fetched, losses, reports, drops), coverage, gauges and hour-0 ids can't be rebuilt; after compaction, hourly detail older than 30 days is gone (hour buckets, hourly finality, hourly repair).

   - Exceptions you can compute honestly now: `yield_below_baseline` (final cohort hours of the last 24 h vs the trailing 7 days, with a minimum harvested count; record the thresholds) and, once #48 is on main, `scrape_bans` from `SCRAPE_REQUESTS`. List the rest with the counter each needs.

## Tests
- **Aggregation:** the kinds table covers every code; compacting a day keeps every `Sum` total and the last `SEARCHABLE` snapshot (never a sum); an unknown code stays hourly.
- **Compaction:** a crash injected between days, and a repeated run, give identical tables; the overview and every stage response for ranges over compacted days equal the same responses before compaction (byte goldens); a concurrent read during a run never double-counts or drops a day; the seal floor holds a cohort day back; WAL size stays bounded on a year's first run; a synthetic year of rollups (B11a's ~110 rows an hour) stays ≤ 50 MB after compaction (`dbstat` if built in, else page counts).
- **Repair:** after deleting rows from a crash window, `--repair` restores cohort Stored/Searchable, `NEWLY_SEARCHABLE` and `STORED` to independent `COUNT(*)`s; a deleted torrent never lowers a count; a second run changes nothing; it refuses while the store is open; the automatic run fires only after an unclean stop and only over the 72 h id range.
- **Triggers:** deleting a searchable torrent through `set_enrichments_at` and `delete_torrents` adds one `REMOVED` and keeps `imported` equal to `count_flagged_searchable`; deleting an unindexed one changes neither.
- **Stage endpoints:** goldens per stage (24h, 30d over compacted days, compare, `reason`); null vs 0 (paused gaps, buckets before `funnel_events_since_hour`); §10.17 reconciliation still holds; no Adult row while hidden; `EXPLAIN QUERY PLAN` shows a `SEARCH` for every query; each answers ≤ 50 ms in release on a year of rollups; 401 without a session; bad `range`/`reason` 400 with `field`.
- **export.csv:** goldens per panel; a property test that any string in a text cell round-trips through a CSV parser and never starts with a formula character; fixtures with `=HYPERLINK(…)`, `@SUM`, leading tab/CR, bidi overrides and embedded quotes/newlines; numbers including negatives unescaped; nulls empty; headers present; filename from the validated panel only.
- **SSE:** `insights` events every 30 s only with listeners; nullable stages serialize as `null`.
- `prune_query_log` runs from the daily job; `record_index_watermark` and `raise_watermark` still agree (B11a's property test).
