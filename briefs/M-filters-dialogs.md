# M-filters-dialogs: Filters & Safety dialog state machines
**Model:** Opus (core and security-sensitive: the client half of §20.11's warning-and-password protocol, CSX-5, sealed-name reveal and the 18+ confirmation; build plan "the main session writes the dialog state machines, all guardrails stay on the server"). **Branch:** `slice/M-filters-dialogs`. **`/security-review` is required** before merge (runner/README step 4, standards §5.7: filters and credentials).

**The rule over everything here: the server decides.** Whether a change weakens filtering, needs the password, is allowed at all, and what its effect is: all of that comes from `POST /filters/preview` (or a preview job) and `POST /filters/apply`. The client never decides a change is safe, never skips the preview, never caches a password, and never builds a warning of its own. If you find yourself needing a client-side guardrail to keep something safe, stop and say so: that's a server bug to report.

## The API you expose (S-filters builds on exactly this; S-appearance, S-search and S-detail use parts)
Import from `$lib/features/filters/flows`; components by path.

```ts
type Change = components['schemas']['Change'];
createChangeFlow(): ChangeFlow
interface ChangeFlow {                    // reactive (runes); one change at a time
  readonly state: FlowState;
  start(change: Change): void;            // always previews first (a preview job)
  apply(): void;                          // 'review' only (no password needed)
  confirm(password: string): void;        // 'confirm' only; the only way a password leaves the dialog
  variant(change: Change): void;          // re-preview a variant: shadow days, Neutralize term
  cancel(): void;                         // any state → 'closed'; cancels a running job
}
type FlowState =
  | { kind: 'idle' } | { kind: 'closed' }
  | { kind: 'previewing'; progress: JobProgress | null }
  | { kind: 'review'; change: Change; assessment: Assessment }            // confirm: false
  | { kind: 'confirm'; change: Change; assessment: Assessment;            // confirm: true
      error?: 'empty' | 'bad_password' | 'rate_limited'; retryAt?: number; changed?: boolean }
  | { kind: 'applying'; change: Change; assessment: Assessment }
  | { kind: 'done'; response: ApplyResponse }
  | { kind: 'failed'; error: ApiError; canRetry: boolean };

// Change builders (typed to `Change`, no logic beyond shaping)
coreSwitch(rule, on) · packSwitch(id, on) · addRule({ query, action, unless?, shadow_days? }) · updateRule(…) · removeRule(id)
addOverride(input: OverrideInput) · removeOverride(id) · addException(match, rule) · removeException(id)
addAllow(query) · removeAllow(id) · release(hash) · confirmAbuse(hash) · falsePositive(hash) · revealName(hash)
reportAbuse(hashes) · removeCs1(hashes) · floorRemoval(source, remove) · undoChange()

// The 18+ confirmation (§20.9; not a password)
createAdultConfirm(): { ask(): Promise<boolean> }      // render <AdultConfirmDialog confirm={…} /> once
setShowAdult(on: boolean, adult: ReturnType<typeof createAdultConfirm>): Promise<{ ok: true } | { ok: false; error: ApiError }>

// "Block this…" (§20.2)
suggestBlocks(t: { hash: string; hash_v2: string | null; name: string }): BlockSuggestion[]
interface BlockSuggestion { tier: 'torrent' | 'payload' | 'group' | 'phrase'; available: boolean; reason?: string; query?: string }
phraseQuery(words: string[]): string | null
```

Components (`features/filters/flows/*.svelte`):
- `ChangeDialog.svelte` `{ flow, title, applyLabel, shadowDays?: number, onapplied?: (r: ApplyResponse) => void, onclose?: () => void }`: every `FlowState`, the exposure summary, the server's warning, the password field, Apply / Shadow for N days / Cancel, then "What changed".
- `ImpactSummary.svelte` `{ preview, neutralize? }` and `EffectWarning.svelte` `{ text }` (also used by S-filters' rule editor).
- `OverrideDialog.svelte` (CSX-5 entry editor + its flow), `BlockThisDialog.svelte` `{ torrent, open, onclose }`, `RevealNameDialog.svelte` `{ hash, open, onclose }`, `AdultConfirmDialog.svelte` `{ confirm }`.

## Build
1. **The change flow** (`flow.svelte.ts`, a pure transition function plus a thin runes wrapper, so the table is unit-testable without a DOM):
   - `start(change)` → `previewing`: `POST /filters/preview/jobs` (`ChangeBody` **without `password`**), then poll `GET /filters/preview/jobs/{id}` every 250 ms for the first 2 s, then every 1 s, showing `progress.phase` and `done`/`total`. `done` → `review` when `assessment.confirm` is false, `confirm` when it's true. `failed` → `failed` with the job's `error`/`status`. `cancelled` → `closed`. `429 too_many_previews` → `failed` with Retry. A `404` for the job (expired after 10 minutes) → start the preview again, once.
   - `cancel()` while previewing → `POST /filters/preview/jobs/{id}/cancel`, then ignore anything that poll still returns (abort the poll; a late response never changes state).
   - `apply()` from `review` → `applying`: `POST /filters/apply` with **no `password` key**. `confirm(pw)` from `confirm` → `applying` with `password: pw`. An empty password never sends: `confirm` with `error: 'empty'`.
   - **Outcomes of apply:** `200` → `done`. `428 confirm_required` (the server re-assessed and now wants the password, e.g. a race) → `confirm` with **`e.assessment`**, the password cleared, and `changed: true` when its `warning` or `preview` differs from what was shown, announced as "The effect changed. Read the warning again." **Never re-send automatically.** `401 bad_password` → `confirm` with `error: 'bad_password'` and the field cleared (no redirect: the client only redirects on `login_required`). `429 rate_limited` → `confirm` with `retryAt` from `retryAfter` (60 s when absent), a visible countdown, and no request until it passes. `409 changed_since_preview` → back to `previewing` (a fresh job), password cleared. `401 login_required` → `closed`; W5's handler signs you out to `/login`. Any other error (`409 floor_locked`, `400`, `422`, `5xx`, `network`) → `failed` with the server's message as text, the password gone; Retry restarts from the preview.
   - **Floor removals:** for `floorRemoval(source, true)`, after the preview, the change sent to apply carries `hashes: assessment.floor_entries` from **the assessment the user saw**, so a refresh in between can't widen what the password confirms. `floor_removal_needs_hashes` is then a client bug: `failed` plus a dev error.
   - **One apply in flight:** a second `apply`/`confirm` while `applying` does nothing, and the buttons say so (`aria-disabled`, still focusable).
   - **Variants** (`variant(change)`) re-preview from `review` or `confirm` and drop any typed password. Used for "Shadow for N days" (`shadow_days` on `add_rule`, `update_rule`, `add_override`; only offered for those ops) and the CSX-5 strength switch. A shadowed weakening change still gets its own warning and password: the server decides.
2. **Password handling, the invariants `/security-review` checks:**
   - The password lives only in the open dialog's input state. It's cleared on close, on every outcome of apply (success included), on a variant, on `changed_since_preview` and on a changed 428.
   - It's sent only in `POST /filters/apply`'s body, only from the `confirm` state, only for the change and assessment on screen. Never in a preview, a job, a URL, `localStorage`/`sessionStorage`, a log, a toast, an error message or the flow's exposed state.
   - **No "remember for N minutes"** (§20.11). Each weakening change asks again.
   - The field: `type="password"`, `autocomplete="current-password"`, a hidden fixed `username` for password managers as the sign-in form does, `aria-describedby` the warning; the dialog's `initialFocus` is the password field, so the warning is its description and is read first.
3. **What the dialog shows** (§20.10, §20.11), in order:
   1. **The exposure summary** (`ImpactSummary`) from `assessment.preview`: each `Preview` field on its own labelled row, never summed: `quarantine` (released from quarantine now), `tombstones` (dropped torrents fetched again), `stored` (stored torrents whose hide/demote/flag mark is cleared), `removed_from_floor`, `caught_30d` and `core_caught_30d` (the 30-day replay), `per_day` (`formatRate(…, 'day')`). Counts use `formatCount`; when `preview.estimate` is true, each is `≈` with a note that the numbers come from names only. Every number has a `data-testid`.
   2. **The effect warning** (`EffectWarning`): `assessment.warning`, the server's plain-language text, rendered **as text** (never `{@html}`), in its own region, with "Enter your password to apply" under it when `confirm`. Null for a strengthening change: no warning shown.
   3. **The password** (only in `confirm`), then **Apply** (or the caller's `applyLabel`), **Shadow for N days** where offered, and **Cancel**. Enter in the password field applies; nothing applies a weakening change without the password typed.
   4. **"What changed"** in `done`: the response's `assessment` beside what was previewed, plus `released`, `removed`, `deleted`, `settled`, `id`, `version` where present, then Close. S-filters places Undo (`undoChange()` through a new flow, which may ask for the password).
4. **CSX-5 override editor** (`OverrideDialog`, §20.5.5): entry kind (exact torrent: one or more 40-hex hashes; keyword or phrase; pattern or query; payload signature, 16 hex), **strength** (Override, the default, or Neutralize term: keyword only), optional scope (a query), optional expiry (`expires_days`) and shadow (`shadow_days`). Check only shape on the client (hex lengths, non-empty); the server validates the rest. **The preview is mandatory**: Apply appears only after it. **Side by side:** for a keyword entry the assessment's `neutralize` holds the other strength's numbers; show both `ImpactSummary`s in two columns (Override | Neutralize term), and switching strength runs `variant()` so the warning and password are for the strength chosen. Every CSX-5 entry warns and asks for the password because the server says so (`confirm: true`); don't special-case it.
5. **Sealed names** (`RevealNameDialog`, `revealName(hash)`): a weakening change (warning + password). The name from `ApplyResponse.name` is shown in `Mono` inside the dialog only, as text; it's dropped from memory when the dialog closes; there's no Copy button and it never goes to the URL, the title, a toast, storage or the console. Record "no Copy" in your decisions file; S-filters may raise it with the owner.
6. **"Block this…"** (`suggestBlocks`, `BlockThisDialog`, §20.2): suggestions, narrowest first:
   1. **This torrent:** `hash:<hash>` (and the v2 hash when `hash_v2` is set: `hash:<v1> | hash:<v2>` as the query language writes it).
   2. **This payload signature:** `available: false`, because neither `SearchHit` nor `TorrentDetail` carries a payload signature and `sig:` arrives with M7 (`crates/search/src/query.rs`).
   3. **This uploader or group:** `available: false`: there's no release group or uploader field on either response.
   4. **A phrase from the name:** never preselected. The user picks consecutive words from `name` (split on whitespace and the separators `. _ - [ ] ( )`). `phraseQuery` joins them, removes every `"` (the language has no escape inside a phrase), collapses whitespace, refuses empty or over 200 bytes, and returns `name:"<words>"`.
   Show unavailable tiers disabled, with their reason. The action is a choice with **`hide` as the default** (reversible at once, and it applies to stored torrents; `drop` only stops future fetches); offer `quarantine` and `drop` with one line each on what they do. Before Apply, show what the rule matches now: `GET /search?q=<query>&hidden=true&exact=true&limit=1` → `total` (`formatCount`, `≈` when `total_approx`). Then run the normal flow with `addRule({ query, action })`: a strengthening change, so no password unless the server says otherwise. Record the `hide` default as a refinement for the runner (§2.19).
7. **The 18+ confirmation** (§20.9, B17), `createAdultConfirm()` + `AdultConfirmDialog` + `setShowAdult`:
   - The dialog says what turning it on does (adult torrents appear in Search, Discover, Alerts and Insights; outputs keep their own settings, off by default) and asks for confirmation that you're 18 or older. **"Show adult content"** confirms; **Cancel** is the initial focus. No password: B17 made it a preference.
   - `setShowAdult(true, adult)`: `ask()`; on false, send nothing and return `{ ok: false }` without an error. On true, `PATCH /settings/content` with `{ show_adult: true, confirm_adult: true }`. `setShowAdult(false)` sends `{ show_adult: false }` with no dialog. `409 set_by_environment` → an error naming the variable ("Set by LODESTAR_SHOW_ADULT; change it in the container template"). `422 adult_confirmation_required` → an error (it shouldn't happen) and a dev error. `SettingsPatch` is `Record<string, never>` in `schema.d.ts`: cast the body once in `setShowAdult`, with a comment naming the backend follow-up.
   - The settings form's own path: a screen registers `form.onConfirm('adult_confirmation_required', async () => (await adult.ask()) ? { confirm_adult: true } : null)` (M-settings-form's hook). Document that one line in your README section for S-appearance.
8. **Other flows S-filters will drive with the same `ChangeDialog`** (no new machine): core and pack switches, rule add/update/remove, exceptions and Always allow (adding warns, removing doesn't: the server decides), release, confirm, false positive, report abuse, remove from CS-1 (its warning comes from the server), floor removals (step 1), Undo. Ship the builders and one showcase case for each.
9. **Accessibility** (§10.13): every dialog has a labelled title, traps and restores focus, closes on Esc (Esc in `applying` waits for the result, then closes); `initialFocus` is the password field in `confirm` (the warning is its description, so it's read first), Cancel in the 18+ dialog, and the dialog's title while previewing; progress is announced politely ("Previewing… 40%") at most every 2 s; errors are announced; status is icon + text; targets ≥ 44 px under `pointer: coarse`; the countdown is text, not only a disabled button.
10. **Messages** in `features/filters/messages/{en,zh}.json`, `filters_flows_*`, worded per §10.14 and the glossary (torrent, never "item" or "hash" for one). Fixed strings only, apart from the server's `warning` and error `message`, shown as text. en complete; zh where you can translate confidently, the rest listed. **The warning is English-only** because the server sends one sentence string: list "warnings as codes and parameters, translated on the client" as a backend follow-up.
11. **Budget:** everything here loads lazily (a dialog chunk on first use), never in the search route's first load: `npx size-limit` entries don't move except for reported CSS. Report the gzipped size of the flows chunk; target ≤ 10 KB. CSS is 19.82 of 20 KB (W9) and global: prefer existing utilities, or a component `<style>` with token variables; report CSS before and after.
12. **Backend gaps** (list each in the PR; don't fill them in on the client): per-item breakdowns by layer, rule, media category, source and network, and the core-caught items' sealed names (§20.10) aren't in `Assessment`; there's no CSX-5 "contradiction with CS-1/CS-8" flag (§20.5.5); `Preview` has no "matches now" count for strengthening rules (you use `/search`'s `total` instead); no payload signature or release group on results (Block this tiers 2–3); the warning isn't structured for translation; `SettingsPatch` is untyped.
13. **Decide yourself, and record each:** poll timings, the exact layout of the exposure summary, the phrase splitter's separators, the `hide` default, no Copy for sealed names, initial-focus choices. **Stop and ask the runner** if the server's behaviour doesn't match `crates/api/src/filters.rs` as read (a weakening change that applies without 428, a preview that asks for a password), if you'd need a client-side rule to stay safe, or if you'd need to edit outside your paths beyond the `initialFocus` prop.
